# 教材内容の主要な参照先

2026年10月24日、利用者が以下の三つを教材内容の重要な参照先として指定した。企画書、オリエンテーション、共通の「はじめに」、教材本編を検討する担当が共通して参照する。

## 三つのアドバイザー

| 参照先 | 基になる書籍 | 主に確認する内容 |
|---|---|---|
| [ddd-advisor](../../../../../.claude/skills/ddd-advisor/SKILL.md) | 『ドメイン駆動設計をはじめよう』 | 業務の言葉とモデル、区切られた文脈、集約、業務上守る一貫性、設計の見直し。 |
| [meta-thinking-advisor](../../../../../.claude/skills/meta-thinking-advisor/SKILL.md) | 細谷 功『システム開発と「具体と抽象」～問題発見と問題解決を往復する「思考のメタ化」を身につける～』 | 目的と手段、目的の大きさ、具体と抽象の往復、問題発見と問題解決。 |
| [usecase-advisor](../../../../../.claude/skills/usecase-advisor/SKILL.md) | アリスター・コーバーン『ユースケース実践ガイド 復刻版』 | ユースケースの目的レベル、スコープ、アクター、シナリオと拡張。 |

各SkillのSKILL.mdが使い方を、references/criteria.jsonが判断基準を持つ。関連する基準のIDは、各SKILL.mdの一覧から確認する。既存のスライドの説明だけを根拠に、概念の意味や使い方を確定しない。

## 内容を検討するとき

1. 今回の論点と、確認したい概念を特定する。
2. 該当するSkillのSKILL.mdを読み、関連する判断基準をgetで取得する。
3. 定義、適用する条件、注意点と、今回の題材の前提を照らし合わせる。
4. 原稿や図へ適用した内容と、その根拠となる基準のIDを確認記録へ残す。
5. 判断基準が扱っていない部分は、利用者との合意、架空案件の設定、今回の適用案として区別する。

基準を読むコマンドは次の形である。idは各Skillの一覧から選び、未確認のIDを根拠に記載しない。

```bash
.claude/skills/ddd-advisor/bin/ddd-advisor get criteria <id>
.claude/skills/meta-thinking-advisor/bin/meta-thinking-advisor get criteria <id>
.claude/skills/usecase-advisor/bin/usecase-advisor get criteria <id>
```

各論点に関係する基準を読む。全ての枚で三つの全基準を一括で読み込むことや、毎回三つのエージェントを起動することを求めるものではない。助言を依頼する場合は、各Skillと配線表の手順に従う。

## 教材への適用で区別すること

教材1の目的の考え方は、単に抽象度を上げることと同じではない。教材2の文脈の境界と集約の境界も同じものではない。ユースケースのスコープと目的レベルを、実装する機能の単位だけから判断しない。これらの妥当性は、該当する判断基準を読み、題材に当てはめて確認する。

判断基準は、学習ノートから概念ごとに整理したものであり、書籍の原文そのものではない。引用する場合は判断基準の記述として示し、書籍の原文と直接照合したとは断言しない。Agents、Skills、ハーネスへ具体化する部分も、どの概念をどのように適用したかを説明する。

書籍の表紙、ページ画像、長い書き写しを公開リポジトリへ追加しない。参照先の指定は、新しいスライドの内容や正本への適用を承認したことを意味しない。
