# 追加対応とレビュー負担を扱う4枚目の確認

最初の不具合を修正した後の差し戻し・証憑再提出を追加した。業務上の別の判断と、共通の承認状態を使い続ける実装を分けて図示した。

| 判定 | 結果 |
|---|---|
| 1 指し先 | 維持するのは上長の支出承認、やり直すのは経理の証憑確認と示した。 |
| 2 情報の型 | 業務の判断と実装を別領域にし、共通状態と各処理の関係を図にした。 |
| 3 列挙 | 変更制限の修正、差し戻し、再提出を分けた。 |
| 4 見出し | 不具合修正後も追加対応で確認が複雑になるという主張を示した。 |
| 5 結論 | 見出しに結果を置き、図と原稿で業務・実装・レビューへの影響を説明した。 |
| 6 文調 | ナレーションは敬体にした。 |
| 7 用語 | 支出の承認と証憑の確認を区別し、集約と文脈の分割を断定しなかった。 |
| 8 語彙 | 証憑は領収書などと原稿で補足した。 |
| 9 情報量 | 不具合の金額変更の再説明は避け、追加対応と確認負担に集中した。 |
| 10 比喩 | モデルの複雑さを比喩で表現せず、確認する処理と判断を示した。 |

未適用の判定はない。最初の不具合は修正してから追加開発する。個々の変更はレビューしても、業務の判断と実装の対応を確認する負担が残る設定である。フラグや条件分岐自体を悪い設計とはしない。SVGと文書の検査は通過し、通常表示・ダーク設定・幅358pxの描画画像を目視した。正本、音声、動画は未変更である。
