# 受講者レビュー（Luna）

## 1. 受講者として理解したストーリー

経費精算システムの刷新で、AIを使って仕様・設計・コード・テストを速く作れた一方、タスクの「承認後」が何の承認後か曖昧なまま実装し、上長承認後に申請内容を変更できる不具合が出た。テストは経理承認後を確かめていたため、上長承認後・経理確認前の状態を見落とした。その後の証憑差し戻し・再提出では、上長の支出承認と経理の証憑確認を一つの状態にまとめた設計が残り、各処理に条件を足した結果、処理をまたいで確認する負担が生じた。さらに設計を見直さず似た処理を増やせば、影響調査や確認範囲も広がりうる。

教材1は「誰が何を達成するか」から目的と必要要件、作業範囲を決める。教材2は、業務上の対象・判断・関係をモデルにして設計へ反映する。教材3は、そこで得た観点と手順をSkillsに記録し、Agentが要件定義・設計・実装・テストを進める際とAIレビューで使い、人も根拠と結果を見て改善する。三教材の順序と、目的・要件からAIの作業手順までつなぐ関係は理解できた。

## 2. 役割別に読めたこと

### 開発者

- **理解できた：** 要件の曖昧さや業務知識の不足を自分で補ったままAIに渡すと、AIの成果物もその解釈を引き継ぐ。テストの通過や変更説明だけでは不十分で、元の業務要件から設計・コード・テストを照合する。教材1〜3の作業は開発者の日々の仕事に結びついて見えた。
- **自分で補った：** 教材3のSkillsに、どの資料を与え、誰に確認し、どの根拠をレビュー結果として残すかは、原稿の説明から想像した。
- **分からない：** この導入だけでは、自分の担当範囲でどこまでのモデルを作るのか、既存資料が不十分な時にどのように業務担当者へ確認するのかは具体化されない。導入としての範囲外かもしれない。

### PM・PL

- **理解できた：** 表紙の原稿では、対応範囲・変更影響・完了と判断する根拠をチームと確認する役割と説明される。AIで要件や進捗を整理する時も、判断目的と確認情報が必要だと読めた。資料や差分が増えるとレビューの確認が難しくなることも分かった。
- **自分で補った：** PM・PL自身がAIで要件や進捗を整理する仕事は表紙のナレーションにあるが、本文の図や教材1〜3の説明からは具体例を補えない。例えば、AIに論点や変更影響の一覧を作らせ、PM・PLが業務担当者・開発者と確認する、と自分で当てはめた。
- **分からない：** 3教材それぞれでPM・PLが何を持ち帰り、実務で何ができるようになるのか。後半は開発者が目的を実装する話とAgentの工程別作業が中心で、PM・PLのAI活用や判断は見えにくい。成果物の確認者として参加する教材なのか、自身の仕事にもAIを使う教材なのか、表紙の説明だけでは判断しにくい。

### 業務担当者

- **理解できた：** 既存業務の意味やルールを提供し、上長承認と経理確認の違いなどを確かめることが重要。業務を知る人がレビューに関わることも読めた。
- **自分で補った：** 申請者は目的の例として登場するが、ここでいう「業務担当者」と同じ立場かは分からない。教材1の要件確認や教材2のモデル化で、担当者がどの判断に参加するかは説明から想像した。
- **分からない：** 業務担当者自身がAIを使う作業、またはAIの出力に対して担う具体的な役割は示されない。開発工程を学ぶ受講者というより、開発者に知識を提供する人に見えやすい。

## 3. 重大度順の指摘

### 重大：PM・PL自身のAI活用が表紙から本文へつながらない

- **対象：** 閲覧1枚目（表紙）／本文番号なし、閲覧2枚目（本文1）、閲覧7〜9枚目（本文6〜8）
- **実際の文言：** 表紙原稿「自分でAIを使って要件や進捗を整理する場合も、何を判断するために、どの情報を確かめるかが大切です。」／本文6「開発者の目的：要件を満たす変更を、確認の根拠とともに完成させる」／本文8「要件定義・設計・実装・テストの各工程でSkillsを使い、作成・検討とAIレビューを進めます。」
- **受講者として困ったこと：** 表紙でPM・PL自身がAIを使うと聞いたが、以後の具体例は開発者の変更作業・開発工程に寄り、PM・PLがAIで要件や進捗を整理する場面へ戻らない。本文1の図にはPM・PLもいるが、AI活用の説明はチーム全体と開発者の実装例が中心。PM・PLは開発成果物を確認する人にとどまり、自分の仕事にどう使うかを想像しづらい。
- **最小の提案：** 本文1か本文6に、PM・PLの小さな具体例を一つ加える。例として「AIで変更影響・未確認事項を整理し、業務担当者と開発者に根拠を確認して、対応範囲や完了条件を決める」。そのうえで三教材のどこがその判断に役立つかを短く結ぶ。

### 重大：三教材をどの役割がどの深さで学ぶのかが明示されない

- **対象：** 閲覧1枚目（表紙）〜閲覧9枚目（本文8）
- **実際の文言：** 表紙「三つの教材の学びを紹介します。」／本文8「要件定義・設計・実装・テストの各工程でSkillsを使い」
- **受講者として困ったこと：** 三教材の内容の違いとつながりは理解できた一方、PM・PL、業務担当者、開発者が全員この工程を同じ深さで学ぶのか、役割ごとに重点が違うのかは分からない。特に本文8の工程を全受講者が要件定義からテストまで実践するようにも読める。参加前に、自分に求められる学びの深さを見積もりにくい。
- **最小の提案：** 表紙または本文1に「全員で共通理解すること」と「役割ごとに深めること」を一文か簡単な対応図で示す。たとえば、全員が目的・業務ルール・確認根拠を共有し、開発者は設計・実装・テスト、PM・PLは範囲・影響・完了判断、業務担当者は業務目的・ルールの確認に重点を置く。

### 中：本文2の「承認後」が曖昧なことと、後の不具合の関係を一読で取りにくい

- **対象：** 閲覧3枚目（本文2）／閲覧4枚目（本文3）
- **実際の文言：** 本文2「タスクには『承認後は変更不可』と書かれています。」／図「どの承認段階かは、PRに記載なし」／本文3「上長承認後から変更不可」
- **受講者として困ったこと：** 画像の本文2では「承認後は変更不可」と「どの承認段階かは、PRに記載なし」が一つの作業条件欄に入り、PRの条件はむしろ曖昧だった、と理解する必要がある。本文3で初めて「上長承認後」と「経理承認後」の違いが明らかになる。原稿を聞けば追えるが、画面だけでは、開発者の解釈・AIへの指示・PRの記述・仕様のどれがどの段階を指すかを保持するのが難しい。
- **最小の提案：** 本文2に仕様上の条件「上長承認後は変更不可」と、タスク／PRの曖昧な記載「承認後は変更不可」を並べ、どこで曖昧さが入ったかを短い矢印で示す。本文3への因果が見えやすくなる。

### 中：本文7・8は情報量と専門用語が多く、受講者の持ち帰りが埋もれそう

- **対象：** 閲覧8枚目（本文7）／閲覧9枚目（本文8）
- **実際の文言：** 本文7「用語の説明を足すだけでなく、その意味をモデルや状態、処理へ反映します。」／本文8「責務や境界から設計を見直す必要があるかを考えます。」および「要件定義」「業務モデル」「Skills」「Agent」
- **受講者として困ったこと：** 図は「支出内容→上長承認」「証憑→経理確認」と対応が見え、教材2の考え方は具体的。ただ、原稿では状態・処理・責務・境界・レビューを一度に扱う。教材3も工程ごとのSkillsとAIレビューに加えて、人による照合・スキル改善まで含むため、導入スライドとして覚える要点が多い。特に「責務や境界」はこの場では具体例がなく、意味を自分で補った。
- **最小の提案：** 本文7は「誰の判断が何に結びつくか」「変更時に何を保つか」を主メッセージに絞り、用語定義は説明時の補足か次教材へ送る。本文8ではAgent／Skillsの短い平易な言い換えと、「手順を使う→成果を根拠と照合→見落としがあれば直す」の主な循環を目立たせる。

### 良い点：事例から教材への導線と業務上の違いは追いやすい

- **対象：** 閲覧4〜9枚目（本文3〜8）
- **受講者として分かったこと：** 12,000円から18,000円への変更例で不具合が具体化され、上長承認と経理確認が別の判断だと納得しやすい。次に、個別条件の追加で処理横断の確認が増える話から、「目的・要件→業務モデル・設計→AIの作業手順」という教材の順序へ進むため、なぜ三つを学ぶのかが分かった。本文5は想定例と明記され、事実として起きた不具合との区別もできる。

## 4. 修正するなら最小限どの枚に何を示すか

1. **本文1（閲覧2枚目）：** 図のメンバーとAI活用の関係に、PM・PL自身のAI利用例（影響・未確認事項の整理と人への確認）を加える。
2. **表紙（閲覧1枚目）か本文1：** 全員の共通学習と、開発者・PM／PL・業務担当者それぞれが深める点を一目で示す。各職種が全工程を同じ深さで学ぶ印象を避ける。
3. **本文2（閲覧3枚目）：** 「仕様：上長承認後」「タスク／PR：承認後」の対比を見える形にし、曖昧さが混入した箇所を示す。
4. **本文7・8（閲覧8・9枚目）：** 用語と説明を少し絞り、教材2の判断と関係、教材3の手順と確認の循環をそれぞれ一つの主眼として見せる。

## 5. 全体理解と参加意欲

全体のストーリーは理解でき、AIで作業を速くするだけでなく、目的・業務ルール・確認根拠を扱う必要があることに納得した。開発者としては教材1〜3の必要性が具体的で、参加してみたい。一方、PM・PLとして自分のAI利用がどの教材でどう扱われるか、業務担当者として何を学ぶのかは本文だけでは判断しにくい。役割別の参加後の姿を一例ずつ示してもらえると、より自分事として参加できる。
