| 組織への展開 | 参加者の学習と基盤づくりを分け、ポータルや継続利用も検証している | 二つの施策の区別は残す。判断の観点・手順と、その適用条件・試した結果が他の人にも渡ることを組織への効果として示す。掲載件数・利用件数だけを成果にしない |
| 対象者への入口 | オリエンテーションはPM・PLと開発者、資料作成と開発を並べ、確認までの仕事を問う | この流れを残す。案件の細かな承認条件をここへ戻さず、自分の疑問と学びの対応を示す |

## 企画書の構成案

要点版を部長への説明の入口にし、詳細版と付録は補足として扱う。現行の二施策は残す。以下は構成案であり、枚数と削除・統合は未確定。

| 順 | 部長の問い | 内容と図 |
|---|---|---|
| 1 | 何を判断すればよいか | 表紙の次に、試行の目的、対象・期間、運営と必要時間、費用、判断してほしい事項の要点 |
| 2 | なぜ部で実施するか | AIで作成が速くなった効果と、確認・修正・引き継ぎまでの課題。個人と組織の図を活かす |
| 3 | どんな変化を目指すか | 目的に合う品質を確かめ、仕事全体の時間を短くする。学び・残るもの・期待する変化を対応させる |
| 4 | 何を学ぶか | 三教材を最新方針へそろえる。目的、文脈と整合性、AIでの判断・実行・改善 |
| 5 | どう進めるか | ワークショップと基盤づくりの二施策、担当、日程、提出する仕組み・使い方・試した記録 |
| 6 | どれだけ時間と費用が必要か | 参加者・協力者・運営の作業と時間、環境費用、未確定部分。見積り前の数値は置かない |
| 7 | 効果をどう判断するか | 達成条件・実行結果・品質・全体時間の対応。自己評価と試行記録を分ける。継続や展開の判断条件は提案して確認する |
| 8 | 組織に何を残すか | 適用条件、判断の観点・手順、使い方、試した結果と改善の担当。ポータルと相談の循環 |
| 9 | 今回決めてほしいことは何か | 試行の実施、運営、時間、費用、報告の機会。未決事項と決める時期を明示 |
| 付録 | 詳細を確認したい | 教材、参考資料、測定の定義・設問、支援と環境、ポータルの運用 |

企画書には、書籍の紹介やAgentの部品説明より先に、効果・負担・検証・判断事項を置く。金額や製品機能を改稿するときは別途最新の一次情報と社内条件を確認する。今回の現状調査では価格を再検証していない。

## オリエンテーションの構成案

現行14枚の順序を基本にする。前半の疑問から仕事の変化へ進む流れは機能しているため、一律に削減しない。

| 現行枚 | 枚の役割と前後のつながり | 修正案 |
|---|---|---|
| 1 | 表紙：何を学ぶ会か | 三教材の短い説明をそろえる。表紙専用の原稿を用意するか確認する |
| 2 | 開催の目的→仕事全体の問い | 考え方を学び自分の仕事で試す関係を残す |
| 3 | 作成の速さ→仕事全体はどうか | 問いと三段階の流れを残す |
| 4 | 自分のAI利用を振り返る→確認の仕事 | 成果物の種類と量を示す図を残す |
| 5 | 確認・修正・再確認→判断できる成果物とは | 仕様と成果物の照合、循環を残す |
| 6 | 判断に使える形→どう繰り返し使うか | 読む人と根拠・確認先の図を残す |
| 7 | Agent・Skillの実行と改善→三教材でどう学ぶか | 条件の保存に加え、判断の観点と実行手順を表す。専門語はこの枚で短く説明する |
| 8 | 三教材で何ができるようになるか→仕事の例 | 教材2の文脈と整合性、教材3の設計・実装判断の具体化を補う |
| 9 | 資料作成と開発での使い方→考え方の根拠 | 開発では仕様照合だけでなく、変更の影響・設計の見直し・理由と結果の提示まで扱う |
| 10 | 三冊の位置づけ→学習場所 | 教材だけでも学べることを残す。DDDを教材2だけに閉じず教材3への適用にも触れる |
| 11 | どこで学び、何を参照できるか→いつ試すか | ポータルの図を残す。掲載物に判断理由と試した結果を含める案 |

| 13 | 支援と環境→自分が試すこと | 参加者・運営、閲覧と相談の経路を残す |
| 14 | 自分の仕事で何を実現したいか→共通の「はじめに」 | 到達像をそろえる。具体的な案件説明は次の動画に任せる |

最初の修正対象案は企画書要点版10「期待する効果」。何を改善し、何を確かめる企画かを明確にしてから、9「身につけること」とオリエンテーション8へ進む。この順なら期待する効果と学びを対応させ、一枚ずつ利用者が確認できる。

## 判断基準の参照と適用

SKILL.mdを読み、各CLIのgetで取得した基準をcriteria/へ保存した。基準は書籍の原文ではなく、学習ノートから整理された判断基準である。

| Skillと基準ID | 今回の適用 |
|---|---|
| meta-thinking-advisor：means-and-ends、user-perspective | 目的を使う人が実現したいことから考え、依頼の形式やツールの操作へ狭めない |
| usecase-advisor：goal-level、design-scope | 目的レベルと検討する対象範囲を分ける。ユーザーが仕事を終える単位と、AIに一度依頼する単位を同一視しない |
| ddd-advisor：bounded-context | 言葉の意味・業務方針・ルールが一貫する文脈を明確にする |
| ddd-advisor：aggregate | 一緒に守るデータの整合性の境界を考える。文脈の境界とは区別する |
| ddd-advisor：evolving-design | 追加変更の際に既存の設計判断を再検討する考え方を、AIの作業手順に含める |

Agents・Skillsへの具体化、工数の見積り方、測定記録、資料の構成と順序は今回の適用案であり、上記の基準そのものの規定ではない。文脈や集約をどう分割するかは決めていない。
