論点の一覧

Q1

契約に従う Skill を、利用者がどういう操作で導入するか

利用者はシェルに合った1行のコマンドを実行するだけにする。導入スクリプトが OS と CPU を判別し、Release から合う実行ファイルを取得して .claude/skills/ に置く。利用者はどのバイナリかを選ばない
  • 導入スクリプトは、OS と CPU を判別し、Release から合う環境の配布物を取得して、リポジトリの .claude/skills/ に展開する
  • 取得した配布物は、SHA-256 を照合してから展開する
  • 更新も同じ1行を実行し直す
  • Release には環境ごとの配布物を置く ── 利用者はこれを直接選ばない

Q2

何を1つの配布物にし、導入スクリプトと組み立ての定義を誰が持つか

配布物は Skill ごと × 環境ごとに作る（Linux ・ macOS は tar.gz、Windows は zip）。導入スクリプトと組み立ての定義は、配布元のリポジトリに1つずつ置き、skills-creator がそのテンプレートを持つ。利用者は Skill の名前を並べて導入し、省略すると全部を導入する
  • 配布物 ── Skill ごと × 環境ごと。Linux ・ macOS は tar.gz、Windows は zip（例：acdr-x86_64-unknown-linux-musl.tar.gz）。道具を保持しない Skill は、環境に依存しない tar.gz と zip を1つずつ作る
  • 導入スクリプト ── 配布元のリポジトリに1つ（install.sh と install.ps1）。Skill の名前を引数に並べ、省略すると Release にある全部を導入する
  • 組み立ての定義 ── 配布元のリポジトリに1つ（GitHub Actions の workflow）。道具を持つ Skill を探して、すべて組み立てる
  • 持ち主 ── 導入スクリプトと workflow のテンプレートは skills-creator が保持し、配布元のリポジトリへ置く操作を持つ

Q3

道具のソースと実行ファイルを Skill のフォルダのどこに置き、実行ファイルは Skill のフォルダ（references/）をどう見つけるか

道具のソースは tool/（いまの rs/）、組み立てた実行ファイルは bin/ に置く（CLI は 名前、MCP は 名前-mcp）。Skill のフォルダは実行ファイルの位置から求める（bin/ の1つ上）。道具の契約の規定（--skill_root で受け取る）と mcp.json.tmpl を改訂する
  • 道具のソース ── rs/ を tool/ へ改名する。tool/ は配布しない。名前は、道具の契約が使う語（tool-contract ・ 道具を持つ Skill）から取る
  • 置き場所 ── .claude/skills/<名前>/bin/<名前> と bin/<名前>-mcp。Windows だけ .exe が付く
  • Skill のフォルダの求め方 ── 引数 --skill_root があればそれを使う。無ければ、実行ファイルの1つ上に references/ があるかを確認して使う。どちらも無ければ、試した経路を示して停止する
  • 開発時 ── 組み立てた実行ファイルを bin/ へ置く手順に統一する。SKILL.md ・ CLAUDE.md ・ 規則ファイル ・ .mcp.json の rs/target/release/ の記述は、bin/ へ一律に置き換える。開発時の bin/ は .gitignore に入れ、git で追跡しない。実行ファイルは Release の配布物だけが持つ
  • 道具の契約を改訂する ── tool-contract.md の「実行ファイルからの相対で数えない」を、「bin/ の1つ上を Skill のフォルダとする」へ変更する。mcp.json.tmpl の絶対パスをやめる。ACDR 0019 も改訂する

Q4

どこで、どの環境向けに組み立て、配る前に何を確認するか

GitHub Actions の各 OS のランナーで組み立てる。対象は Linux（x86_64 ・ musl）・ Windows（x86_64）・ macOS（universal2）の3つ。組み立てた場所と、展開した先の2か所で起動を試験してから Release に置く。workflow のテンプレートは skills-creator が保持する
  • 組み立てる場所 ── GitHub Actions の ubuntu ・ windows ・ macOS（arm64）のランナー。tag を push したときだけ実行する。workflow は skills-creator のテンプレートから置く
  • Linux ── x86_64-unknown-linux-musl。静的に組み、利用者の glibc の版に依存しない（WSL の distro は利用者ごとに異なる）
  • macOS ── Apple Silicon と Intel の2つを1本にまとめる（universal2）
  • macOS の Gatekeeper ── 署名 ・ 公証はしない。導入スクリプトが端末で取得して展開するので、ブラウザを経由しない。ブラウザで取得した利用者向けには、SHA-256 を照合してから隔離の属性を外す手順を書く
  • 試験 ── 道具を持つ Skill のすべての実行ファイルで、CLI の使い方の表示と、MCP の initialize への応答を検証する。組み立てた場所と、展開した先の2か所で実行する

Q5

契約に従う Skill が呼ぶ外部コマンドをどう扱い、Windows ネイティブ（WSL を使わない）に対応するか

OS によって無い外部コマンド（date ・ timeout）は呼ばない規則を道具の契約に加え、既存の4か所は Rust の処理へ置き換える。呼んでよい外部の道具は、Skill の宣言に列挙させ、skills-creator の check が宣言と実装の一致を検査する。Windows ネイティブにも初回から対応する
  • 契約の規則 ── OS によって無い外部コマンドを呼ばない。日付の計算と時間の制限は Rust の中で実行する
  • 宣言 ── 呼んでよい外部の道具（curl ・ git ・ aws ・ ヘッドレスのブラウザなど）は、Skill の宣言に列挙する。SKILL.md の前提条件は、その宣言から書く
  • 検査 ── skills-creator の check が、部品の中の Command::new に文字列で書かれた道具の名前と、宣言の一覧を照合する
  • 名前が変数で渡される道具 ── 規則に書かれた道具（no-more-spaghetti）や、利用者が指定するブラウザ（slide-deck）は、名前を静的に照合できない。宣言に「利用者が指定する道具」として書き、check はその呼び出しを照合の対象から外す
  • 既存の置き換え ── date（acdr ・ fact-check ・ brainstorming-board）と timeout（narration）
  • Windows ネイティブ ── 初回から対応する。MCP の設定と hook の設定は、導入スクリプトが環境に合わせて書き、Windows 版は経路に .exe を書く
