現在地

論点の一覧

skills-creator の道具の契約に従うすべての Skill を、利用者の環境に Rust が無くても動く形で配布する。配布の形は、契約 ・ テンプレート ・ 検査として skills-creator が保持する。対象の環境は Windows ・ WSL ・ macOS である。

#論点状態いまの答え
1契約に従う Skill を、利用者がどういう操作で導入するか決着利用者はシェルに合った1行のコマンドを実行するだけにする。導入スクリプトが OS と CPU を判別し、Release から合う実行ファイルを取得して .claude/skills/ に置く。利用者はどのバイナリかを選ばない
2何を1つの zipにし、導入スクリプトと組み立ての定義を誰が持つか決着配布用の zip は Skill ごと × 環境ごとに作る。導入スクリプトと組み立ての定義は、配布元のリポジトリに1つずつ置き、skills-creator がそのテンプレートを持つ。利用者は Skill の名前を並べて導入し、省略すると全部を導入する
3道具のソースと実行ファイルを Skill のフォルダのどこに置き、実行ファイルは Skill のフォルダ（references/）をどう見つけるか決着道具のソースは tool/（いまの rs/）、組み立てた実行ファイルは bin/ に置く（CLI は 名前、MCP は 名前-mcp）。Skill のフォルダは実行ファイルの位置から求める（bin/ の1つ上）。道具の契約の規定（--skill_root で受け取る）と mcp.json.tmpl を改訂する
4どこで、どの環境向けに組み立て、配る前に何を確認するか決着GitHub Actions の各 OS のランナーで組み立てる。対象は Linux（x86_64 ・ musl）・ Windows（x86_64）・ macOS（universal2）の3つ。組み立てた場所と、展開した先の2か所で起動を試験してから Release に置く。workflow のテンプレートは skills-creator が保持する
5契約に従う Skill が呼ぶ外部コマンドをどう扱い、Windows ネイティブ（WSL を使わない）に対応するか決着OS によって無い外部コマンド（date ・ timeout）は呼ばない規則を道具の契約に加え、既存の4か所は Rust の処理へ置き換える。呼んでよい外部の道具は、Skill の宣言に列挙させ、skills-creator の check が宣言と実装の一致を検査する。Windows ネイティブにも初回から対応する

Q2

何を1つの zipにし、導入スクリプトと組み立ての定義を誰が持つか

承認された（2026-09-28）。
A
  • 配布用の zip
    Skill ごと × 環境ごと（例：acdr-x86_64-unknown-linux-musl.zip）。道具を保持しない Skill は、環境に依存しない配布用の zipを1つ作る

  • 持ち主
    導入スクリプトと workflow のテンプレートは skills-creator が保持し、配布元のリポジトリへ置く操作を持つ
