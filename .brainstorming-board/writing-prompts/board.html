Q1

x-prompt を、AI が読みやすい構造としてどんな形で持つか

read は1文ずつの配列、write は決まりの配列にし、決まり1件を id ・ rule ・ why ・ test の4つの欄で持つ。
  • 例を示すときだけ、bad と good を対で足す。
  • rule ・ why ・ test と、read の各項目は1文にする。
  • 複数の文を書いてよい文字列は、bad と good だけにする。
  • 形は meta-schema が検証し、1文かどうかは正規表現で見る。
  • id の重なりは JSON Schema で書けないので、check-schemas が見る。
  • 1つの x-prompt に置く決まりの数の上限は、論点3で決める。

採らなかった案（6件）
案採らなかった理由
read と write は文字列のまま、文の数と長さだけを制限する「手順：(1) …」のような構造が文字列の中に残り、決まり1件ずつを置き換える単位が決まらない。
決まりが1件だけなら、文字列で書いてもよいとする形が2つになり、読む側と検査が分岐する。1件が2件に増えるたびに、形の書き換えが起きる。
欄の名前を do と check にするcheck は基盤のツールの名前と重なり、x-prompt の欄とツールのどちらを指すかが文脈で変わる。
read も決まりの形（id ・ rule ・ why ・ test）にするread は値の意味を伝える事実で、守るものではないので、why と test が空の欄として並ぶ。
決まりに履歴の欄（足した日 ・ 版）を持たせる利用者が「古いものに追記という更新はノイズ」と決めており、履歴は git と ACDR が持つ。
決まりを別のファイルに集め、x-prompt は id で指すだけにする欄の決まりを読むたびに2つのファイルを開くことになり、指す先が消えても欄の側では気づけない。
Q2

書き方の決まりを、どこに1回だけ置くか

Skill が書くときに使う決まりは、すべてその Skill の中に置き、ほかの Skill から読まない。
  • 欄の決まりは、その Skill のスキーマの欄の x-prompt に置く。
  • インスタンス全体の決まりは、そのスキーマの根の x-prompt に置く。
  • スキーマの外の出力と手順の決まりは、その Skill の SKILL.md の表に置く。
  • 構造化データに共通の決まりは、基盤の references/writing-rules.json に置き、転写で各 Skill の tool/schema-driven/ へ写す。
  • 転写した複製は Skill の持ち物なので、実行時に基盤の Skill を読まない。
  • doc-writing-skills は Skill の外にあり、人が読む文書に Orchestrator が当てる。
  • 同じ決まりの複製どうしは、check-copy で基盤との差を見て揃える。
