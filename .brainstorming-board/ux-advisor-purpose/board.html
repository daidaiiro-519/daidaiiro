Q3

ux-advisor の根拠と完成イメージを、どの原典で支えるか。標準ではない原典や、中身を読めない原典を入れるか

原典は、標準化団体の勧告か、分野で事実上の標準として参照されるもので、中身を読めて、相談で引く場面があるものだけにする。判断基準は WCAG 2.2 のガイドライン13件と Nielsen の10のヒューリスティクス10件の23件にし、67件から44件を外す。WCAG2ICT は、コマンドと Web ではない文書に WCAG 2.2 を適用する読み方として各件の中に持たせ、件を足さない。体験の描き方は原典から引かず、回答の形の欄（誰が ・ 目的 ・ 状況 ・ 流れ）で作る。デザインシステムとスタイルガイドは advisor が持たず、相談者が持っていればそれで揃え、持っていなければ論点2の形で原則の行を提案し、原則で決まらない値は候補を並べる。18F Methods ・ GOV.UK ・ Design Tokens Format Module ・ Command Line Interface Guidelines は、標準ではないので入れない。デジタル庁デザインシステムと USWDS も、同じ理由で入れない。中身を読めない ISO 9241 ・ JIS も入れない
  • 入れる条件：標準化団体の勧告 ・ 規格か、分野で事実上の標準として参照されるものであること。あわせて、中身を原文で読めて照合できること ・ 相談で根拠として引く場面があること ・ 使用条件で要約を配れることを満たす
  • 判断基準（根拠の欄が引く）：WCAG 2.2 のガイドライン13件（アクセシビリティ）と、Nielsen の10のヒューリスティクス10件（ユーザビリティ）の23件
  • WCAG2ICT：コマンドと Web ではない文書（メールを含む）に WCAG 2.2 を適用する読み方として、WCAG 2.2 の各件の中に持たせる。件は足さない
  • 論点1の「文言」は、2つの原則の中の件で支える。Nielsen の2（使う人の言葉で話す）・ 9（エラーを平易な言葉で示す）と、WCAG 2.2 の 3.1 Readable ・ 2.4 Navigable（見出しとラベル）・ 3.3 Input Assistance である
  • 体験（誰が ・ 目的 ・ 状況 ・ 流れ）とタッチポイントの描き方は、原典から引かない。回答の形の欄で作り、判断ごとの根拠は2つの原則から引く
  • デザインシステムとスタイルガイド：advisor は持たない。相談者が持っていれば、その名前と値と使い分けを写して揃える。持っていない種類は、論点2の形で原則の行を提案し、原則で決まらない値は候補を並べる
  • このリポジトリが相談者のときは、文書は doc-writing-skills、コマンドの呼び方と MCP のツールは skills-creator の契約を、相談者が持つ決まりとして名前で挙げる
  • 判断基準の単位は「原典が名前を付けた単位を1件」のまま変えない

Q4

ux-advisor と usecase-advisor は、どこで受け持ちを分けるか

usecase-advisor は、機能が何をどう振る舞うか（主アクターと目的 ・ 主成功シナリオ ・ 拡張）を、UI を書かずに見る。ux-advisor は、使う人の目的をユースケースから受け取って出所を付けて写し、体験（状況と流れ）と、使う人が触れるタッチポイント（種類ごとの構成 ・ デザインシステムとスタイルガイド）を、守るべき原則を根拠に決める。目的は決めない。ユースケースのステップのうち使う人に見えないもの（職員の作業 ・ システムの処理）は、体験の流れの見えない段へ写すだけで、決めない。ユースケースが無いときは相談者の言葉を前置きに書き、目的レベルが合わない疑いは usecase-advisor への差し戻しとして示す。配線表は、ux-advisor の行の request と when の文を直す
  • usecase-advisor：主アクターと目的（目的レベル）・ 主成功シナリオ ・ 拡張を見る。UI は書かない。今の SKILL.md と判断基準のまま変えない
  • ux-advisor：使う人の目的を受け取り、出所を付けて体験の欄に写す。目的は決めない
  • ux-advisor：体験の状況と流れ、タッチポイント（画面 ・ メール ・ 紙 ・ 窓口 ・ コマンド ・ API ・ 対話 ・ 文書）の構成、デザインシステムとスタイルガイドを、守るべき原則を根拠に決める
  • タッチポイントごとに、担うユースケースのステップ（拡張を含む）を書く
  • ユースケースのステップのうち、使う人に見えないもの（職員の作業 ・ システムの処理）は、体験の流れの見えない段へ出所を付けて写す。手順は決めない
  • ユースケースが無いとき：相談者の言葉を、出所を付けて前置きに書く。それも無ければ未判定と書き、目的を推測しない
  • 目的がユーザー目的レベルに無い疑いがあるとき：差し戻し（referrals）に usecase-advisor を挙げる。ux-advisor から呼び出さない
  • 配線表：ux-advisor の行の request と when を直す。skills と reliance は変えない。usecase-advisor ・ meta-thinking-advisor ・ doc-writing-skills の行は変えない
この答えの完成イメージ ── UI ・ 図

2つの advisor の境目。usecase-advisor が見るユースケースは UI を書かない。ux-advisor はそこから目的とステップと拡張を受け取り、体験とタッチポイント（種類ごとの構成と揃える決まり）を決める。ユースケースが無いときは、相談者の言葉を出所を付けて前置きに書く
