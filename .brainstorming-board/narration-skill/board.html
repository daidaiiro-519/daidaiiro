Q1

このSkillは、原稿からどこまでを受け持つか

原稿から、枚ごとの音声と尺の記録までを受け持つ。動画への結合は、スライドを保持する側が受け持つ。
  • 入力は、枚ごとに区切られた原稿である
  • 出力は、枚ごとの音声ファイルと、尺の記録（各文と各語の開始時刻）である
  • 動画への結合、スライドの画像化、再生の制御は受け持たない
この答えの完成イメージ ── UI ・ コード ・ 図
aws polly synthesize-speech \
  --text-type ssml --text "<speak>下期AI活用ワークショップの企画をご説明します。</speak>" \
  --voice-id Takumi --engine neural --output-format mp3 slide-01.mp3

aws polly synthesize-speech \
  --output-format json \
  --speech-mark-types='["word", "sentence"]' \
  --text-type ssml --text "<speak>…</speak>" \
  --voice-id Takumi --engine neural slide-01.marks.json

原稿から音声と尺までがこのSkillの受け持ちで、結合はスライドを保持する側が行う

案採らなかった理由
音声付き動画まで受け持つ合成と映像の結合という2つの仕事が1つのSkillへ入る。枚と尺の対応はスライド側の知識なので、音声側がスライドの並びを知ることになり、slide-deck Skill と同じ知識を2か所が保持する
HTMLのスライドへ音声を埋め込むまで受け持つ配る形が動画ではなくブラウザの頁になる。企画デッキが約束した「音声付きの短い動画」と一致しない。再生位置の制御も自前で持つことになる
原稿の作成から受け持つ原稿は教材の設計そのもので、音声の都合とは別の判断で決まる。合成の都合が原稿の内容へ流入する
音声だけを返し、尺を返さない尺は合成と同じ操作から取得できる事実である。返さないと、結合する側が音声を解析して測り直すことになり、測り方が相手ごとに相違する
Q2

Pollyの合成を、どこで実行するか（手元のCLI ／ AWS上のジョブ）

既定は手元で実行する。あわせて、AWS側で同じ手順を実行するためのCloudFormationテンプレートをSkillへ同梱する。
  • 既定は手元 ── AWS CLIで合成し、版を固定した公開のffmpegイメージで結合する
  • Skillは、ECR・CodeBuild・S3・権限を作るCloudFormationテンプレートを同梱する
  • 必要になった人は1命令で環境を作る。作らない限り、費用も保守も発生しない
この答えの完成イメージ ── UI ・ コード ・ 図
# infra/narration.yml（Skillが同梱する）
Resources:
  Image:   { Type: AWS::ECR::Repository }
  Build:   { Type: AWS::CodeBuild::Project }
  Artifact:{ Type: AWS::S3::Bucket }
  Role:    { Type: AWS::IAM::Role }   # Polly ・ ECR ・ S3 への権限

# 使うときだけ、1命令で作る
$ aws cloudformation deploy --template-file infra/narration.yml \
    --stack-name narration --capabilities CAPABILITY_IAM

Skillは手元の手順とテンプレートの両方を持ち、どちらの経路でも同じ動画に到達する

案採らなかった理由
ECRとCodeBuildを先に作る使う前に作ると、使っていない設備を保守することになる。試作は手元の道具だけで通った
手元の手順だけを持ち、テンプレートを持たない端末の状態に依存したままである。別の端末や別の担当者へ移るたびに、環境の作り方を各自が考えることになる
手順書（文章）で環境の作り方を残す手で作ると、作るたびに差が出る。差が出た環境では、同じ入力から同じ動画が出ない
端末へ ffmpeg を直接導入する版の差が動画の差になる。公開のイメージを版で固定すれば、同じ結果が出る
Q3

原稿をどの形で受け取り、音声と尺をどの形で返すか（slide-deck Skill との継ぎ目）

2つのJSONで受け渡す。枚のidはスライド側が出したものを使い、durationMsは音声そのものから測った長さとする。
  • 枚のidは、スライドを保持する側が出したものをそのまま使う
  • `durationMs` は、音声ファイルから測った長さとする ── speech marks の最後の印の時刻ではない
  • marks は、語と文の時刻として別に返す ── 字幕や強調に使う

slide-02  17,685 ms        18,264 ms             -579 ms
slide-03  41,162 ms        41,736 ms             -574 ms

  "marks": "cache/d352….marks.json", "format": "mp3", "durationMs": 13488 }

採らなかった案（4件）
案採らなかった理由
発表原稿（speaker-notes.md）を直接読む見出しの規則に音声側が依存する。この企画デッキでは、見出しの形を実際に一度変更した（ACDR 0010）
slide-deck Skill の内部のデータ構造を共有する両者が同じ構造を知ることになり、片方の変更がもう片方へ波及する
音声側が連番を採番する枚の増減で連番がずれ、違う枚に音声が付く。しかも機械では検出できず、動画を見るまで判明しない
出力に画像の場所も書く音声側がスライドの置き場所を知ることになる。キーだけを共通にすれば足りる
Q4

原稿が変わった枚だけを合成し直す判定を、どう持つか。成果物をどこへ置くか

読み上げる文・声・エンジンからキーをつくり、そのキーを音声の名前にしてS3へ置く。キーが在れば取り出し、無ければ合成する。
  • キーは、読み上げる文・声・エンジンの3つから作る ── この3つが同じなら、音声は同じものになる
  • 音声と尺を、そのキーの名前でS3へ置く。ビルドは、キーが在るかだけを確認する
  • `narration.out.json` は、枚のidとキーの対応を持つ
この答えの完成イメージ ── UI ・ コード ・ 図
s3://…/cache/9f2c…a1.mp3        ← キーがそのまま名前である
s3://…/cache/9f2c…a1.marks.json

# narration.out.json

キーをそのまま名前にすると、変更の検出は存在の確認だけで済む

根拠（4件）
結論のどこを支えるかもとにしたことその出どころ
キーに含めるもの合成の入力は、文と声とエンジンで決まる前提Amazon Polly の合成の指定（voice-id ・ engine ・ text）
更新時刻を使わない判断ビルドはリポジトリからソースを取り直す前提CodeBuildでの実行（この板の論点2）
成果物の置き場artifacts:\n files:原典AWS CodeBuild User Guide / Build specification reference（2026-09-22 取得）

採らなかった案（3件）
案採らなかった理由
ファイルの更新時刻で判定するビルドはリポジトリから取り直すため、更新時刻は取得した時刻になる。全部が新しいものとして扱われる
前回の出力と突き合わせて差分を取る比較の基準を別に保存することになる。その保存が失われると、全枚の合成へ戻る
枚の番号を音声の名前にする枚の番号は、枚の増減で他の枚へ移る。中身が変わっていないのに合成し直し、変わったのに古い音声を使う
Q5

日本語の声をどう選び、読み間違いをどう補正するか

声は Takumi（日本語・ニューラル）に固定する。読みの補正は辞書へ集約する。
  • 声は Takumi（日本語・ニューラル）に固定する ── 聞き比べのうえ利用者が決定した
  • 用語の読みは辞書（PLS準拠の発音辞書）に登録し、合成のときに適用する
  • 入力のJSONが持つのは読み上げる文だけである ── 読み仮名は持たせない
この答えの完成イメージ ── UI ・ コード ・ 図
<!-- lexicon.pls（W3CのPLS） -->
<lexeme>
  <grapheme>Kiro</grapheme>
  <alias>キロ</alias>
</lexeme>

$ aws polly put-lexicon --name workshop --content file://lexicon.pls
$ aws polly synthesize-speech --lexicon-names workshop \
    --voice-id Takumi --engine neural … audio/slide-01.mp3

読みの補正は辞書が持ち、原稿は書き換えない ── 合成の前に適用される

案採らなかった理由
発表原稿に読み仮名を書く発表原稿は人も読む文書である。音声の都合で書き換えると、読み手にとっての文書ではなくなる
