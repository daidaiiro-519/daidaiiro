論点の一覧

skills-creator は、利用者が自分で Skill を作るための Skill である。いまの道具の契約は Rust でしか道具を作れない形になっており、抽象の高さが合っていない。このブレストボードは、契約を言語に依存しない形にするために、契約と言語の組の境界 ・ 言語の条件 ・ 検査の形 ・ 外部の道具の宣言の置き場所を決める。このリポジトリの Skill は、引き続き Rust で作り、Rust のバイナリで配布する。

案採らなかった理由
入口の置き場所（bin/）を契約に置く（Round 3 の答え）起動のコマンドを登録に書けば、置き場所に依存せずに呼べる。bin/ を前提にしていた Skill のフォルダの求め方は「入口自身の位置から求める」へ一般化でき、配布は任意の機能になった
配布の形を言語の組に置く（Round 2 の答え）配布を使わない人にも、組ごとに配布の形の宣言を求めることになる。配布の仕組みの大半（配布物 ・ 導入スクリプト ・ CI の枠）は言語に依存しないので、組ごとに持つ理由も無い
配布物と導入スクリプトまで契約に置く（Round 1 の答え）バイナリで配るのは Rust を選んだ結果である。契約に置くと、Python や TypeScript の組が、実行環境を同梱する手段を必ず持つことになる
Rust だけの契約を維持する利用者が自分の言語で道具を作れない。skills-creator の目的（利用者が自由に Skill を作る）と抽象の高さが合わない
振る舞いだけを契約に置き、層と許可辺を規定しない「1つの宣言から CLI と MCP を組む」は、宣言の層を前提にしている。層を外すと、能力を2か所に書く実装を契約が禁じられない
主要な言語の組を、いま全部 skills-creator に持たせる使わない言語の雛形を、試験できないまま保守することになる。組は、必要になった言語から加える

Q3

外部の道具の名前 ・ 理由と、実際に起動するコマンドを、言語に依存しない形でどこに置き、部品へどう渡すか

tool.json の external に、名前 ・ 起動するコマンド ・ 理由の組で書く。部品はコマンドの名前を直書きせず、宣言の層が tool.json から読んだコマンドを、引数として受け取る。利用者は tool.json を書き換えるだけで、呼ぶコマンドを差し替えられる。Rust の定数 EXTERNAL は廃止する
  • command ── 実際に起動するコマンド。既定値を Skill が書き、利用者が書き換えてよい（例：git の経路、別のブラウザ）
  • 部品は名前を直書きしない ── 宣言の層が tool.json を読み、部品の関数へ引数として渡す。試験では偽物のコマンドを渡せる
  • 理由と起動するコマンドが空の宣言は、1段目が検出する。部品の中の直書きは、2段目（言語の組）が検出する
  • "*"（規則ファイルや引数で利用者が指定する道具）は、いまと同じく、実行時に渡された値を起動する

Q4

言語の組を作ってよい言語の条件を何にするか
