ddd-advisor の回答 ・ 判断相談

ユースケース駆動の宣言のうち、ドメイン・サブドメイン・区切られた文脈・集約・値オブジェクト・ドメインサービスの6種類の項目は、(1) 人が描画したものを読んで承認するときの読みやすさと、(2) AI がテストと実装を書くときの情報の過不足と抽象の高さの2つの観点で妥当か

前置き

判定の前に確定させた前提と、その出所

前提内容出所
レビュー対象論点3の答え（q3-fields.md）の6つの表。ユースケースの表は対象外相談者が提示
決まっている前提宣言はモデリング側が書き、技術を書かない。コーディング側はポートとアダプターを外枠に、宣言から実装とテストを作る。条件は論点2の6つの項目の構造で書き、人が読む文はツールが生成する。一覧の要素は ID と短い名前を持ち、畳んだときに1行で出すボード usecase-driven-concrete の論点1・2（相談者が提示）
抽象の高さの線引き業務エキスパートが決める事柄（単位・桁・端数の扱い・個数・業務で使う番号）はモデル側に残し、プログラミング言語や保存の都合で決まる事柄（言語の型名・識別子の内部の型・入れ物の種類・直列化の形・版番号）は実装側へ移す、という線で判定したentity・value-object・domain-model の判断基準から組み立てた（線の引き方そのものは回答の側の判断）
判断基準の範囲外利害関係者・達成の基準・品質の要求の要否、項目を畳むかどうかの表示の判断、title の言い回しは判断基準が扱わない。表の根拠の列に「推測」と書いたものがそれで、判定の根拠には使っていない判断基準の範囲外
読んでいないもの試作（.brainstorming-board/*/trial/）は読んでいない相談者の指示

結論

採る

6種類の項目はほぼ妥当で、直すのは4点に絞れる ── 他の欄から導ける2つ（集約の整合性の境界・値オブジェクトの表す概念）を外し、実装の選択である識別子の型（ルートと内側のエンティティの id_type）を実装側へ移し、AI が推測に頼る4か所（競合・集約のサブドメイン・拒否する例・端数の扱い）を足し、状態と値の型は「値オブジェクトの ID」と「値の種類・単位・桁」までをモデルに残す。

判断基準は、他の集約を ID で参照し（aggregate）、ID の内部の型は業務に応じて選べる実装の事柄とし（entity）、金額のような値は基本の型でなく値オブジェクトで表して丸めや端数処理の不具合を防ぐ（value-object）と定めるので、型を値オブジェクトへの参照で書く高さが合っており、言語の型名と識別子の内部の型だけが低すぎる。整合性の境界は強い一貫性を必要とするかの問い（aggregate）の答えであり、条件の参照から導けるので、手で書くと条件とずれる。

比較した案

案何が起きるか採否
案A：レビュー対象の項目をそのまま採る整合性の境界と表す概念を2か所に書くので、条件や用語集を直したときにずれる。ルートの id_type と VO の型で、AI が言語の型（int・UUID）を宣言に書き込み、宣言が技術を持つ。差別化・拒否・端数は AI の推測になる採らない
案B：判定の表どおりに、外す2つ・実装側へ移す2つ・足す4つ・名前と書き方の直しを当てる承認で読む項目が種類ごとに4〜6個に減り、AI が書く値は enum か ID で決まる範囲が広がる。型は値オブジェクトの参照と値の種類で止まり、言語の型は実装側の定義が持つ採る
案C：型・個数・項目の元をすべて実装側へ移し、モデル側は文だけにする人には読みやすいが、AI がテストの期待値（業務イベントの項目・個数の制約）と値オブジェクトの使い方を推測で決める。基本データ型への執着も検出できなくなる採らない

判断の道筋

  1. その項目は、判断基準が判定に使う問いの答えか

    はい ── カテゴリー・業務ロジックの性質・置く理由・連係方法・状態の型（VO の参照）・個数は残す。性質の3つの真偽は、コーディング側が実装方法を選ぶ唯一の入力でもある

  2. 他の項目や用語集から、ツールが機械で導けるか

    はい ── 集約の整合性の境界（条件の参照から導く）、値オブジェクトの表す概念（用語集の定義）、関係の position（pattern から決まる）、ルートの名前（集約の名前と同じ）は外し、表示はツールが引く

  3. 業務の決まりか、実装の選択か

    実装の選択 ── 識別子の内部の型、言語の型名、入れ物の種類、公開された言葉の直列化の形は実装側へ移す。業務の決まり ── 単位・小数の桁・端数の扱い・業務で使う番号は残す

  4. AI が書くとき、比べる相手や選択肢が決まっているか

    決まっていない ── 差別化の比べる相手（競合）、文脈が複数のサブドメインを持つときの集約の所属、コマンドの拒否、丸めを足す。用語集の kind の選択肢を決める

  5. 承認する人が、その項目を見て判断を変えるか

    変えない ── 例・引数・項目の元・理由の文・調達・品質の要求は既定で畳む。種類ごとの既定の表示と順番は、コードの例の欄の最後の表のとおり

コードの例

ドメイン（9項目：残す4・直す2・畳む2・足す1）

項目（キー）判定効く観点理由根拠
名前（name）そのまま残す人画面の見出しになる。判定に使う情報ではない推測

サブドメイン（8項目：残す4・直す2・畳む2）

項目（キー）判定効く観点理由根拠
名前（name）そのまま残す人業務活動の名前に限る書き方は妥当ubiquitous-language「業務用語だけで構成する」
説明（description）そのまま残す人・AI何をするかだけを書き、どう実現するかを書かない、は原典どおりsubdomain「業務領域は事業として何をするかを説明し、それをどのように実現するかは説明しない」
分類（category）名前や書き方を直す人title を原典の語の「カテゴリー（中核・一般・補完）」にし、選択肢を原典の順に並べるsubdomain の3つのカテゴリー
分類の理由（category_reason）名前や書き方を直す＋既定で畳む人・AI「迷ったときの問い」は迷ったときだけ使う問いで、主な軸は差別化と業務ロジックの複雑さ。competitive_advantage を必須にし、question と answer は迷うときだけ書く。承認では answer の1行だけ見せるsubdomain「差別化も複雑さも小さい業務領域は、一般とも補完ともなりうる」

業務ロジックの性質の根拠の条件（rule_conditions）既定で畳むAI業務ルールが複雑と答えた根拠を AI が確かめるための参照。承認では見なくてよいdesign-heuristics「入り組んだ業務ルール・不変条件・最適化アルゴリズムを持つ」
担う提供価値（serves_values）そのまま残す人・AI中核と判定した理由を、差別化の提供価値で確かめられるsubdomain 中核「競合他社との違いを生み出す業務活動」
調達（sourcing）既定で畳む人一般のときの方針として残す。製品名は書かない（製品の選定は実装側）subdomain 一般「パッケージ製品の購入やオープンソースの利用を選択する」

区切られた文脈（9項目：残す4・直す3・畳む1・外す1）

項目（キー）判定効く観点理由根拠
名前（name）そのまま残す人業務の言葉で書く、は妥当ubiquitous-language「業務用語だけで構成する」
目的（purpose）そのまま残す人・AIモデルは目的のために作るので、文脈の目的が要るmodel「目的の無いモデルは無い」
対応するサブドメイン（subdomains）そのまま残す人・AI1対1に限らない、は原典どおり。表示ではカテゴリーを並べるbounded-context「一対一が最善になることもあれば、別の方針での分割が有効になることもある」
用語集（glossary）名前や書き方を直す人・AIkind の選択肢が決まっていないと、AI は同じ語を2つの種類で登録する。選択肢を決める。人には「語：定義」の1行を種類ごとに見せ、avoid は畳む。title は「用語集（同じ言葉）」ubiquitous-language「1つの用語に1つの意味」「同義語を使用しない」
他の文脈との関係（relations）の with・patternそのまま残す人・AI連係方法を6つの enum で持つのは原典どおりcontext-map の地図に記載する連係方法

集約（17項目：残す7・直す4・外す2・実装側へ1・足す2・一部は直しと畳むの併用）

項目（キー）判定効く観点理由根拠
所属する文脈（context）そのまま残す（欄ではなく見出しの位置に出す）人承認では欄として読む必要が無い。画面の上の「文脈 › 集約」の並びで見せる推測

説明（description）名前を直す人title を「守る一貫性」にすると、何を書くかが名前でわかるaggregate 定義「目標はデータの一貫性の保証であり」
ルート（root）の name外す人・AIルートは集約そのものであり、名前は集約の名前と同じになるaggregate「集約のルート：外部に公開するインターフェース役のエンティティ。1つにする」・entity「集約もエンティティであり、ID を持ち」

状態（state）の typeそのまま残す（書き方を直す）AIVO・ENT・AGG の ID で指すのはモデルの高さで、基本データ型への執着も防ぐ。name を TERM の ID にし、List・Set などの入れ物の種類は書かないvalue-object 基本データ型への執着・aggregate「他の集約は、オブジェクトそのものではなく ID で参照する」
状態の multiplicity名前を直す人多重度はモデルの情報（原典の図も辺に多重度を書く）。title を「個数」にし、値を 1・0か1・0以上・1以上 の4つにするaggregate 図「辺の数字は多重度を表す」
内側のエンティティ（entities）そのまま残す（id_type は実装側へ移す）AI集約の外に置かないのは原典どおり。識別子の内部の型はルートと同じ理由で実装側entity「エンティティを単独で実装せず、集約の実装の一部にする」
不変条件（invariants）そのまま残す（文は既定で見せ、違反する例は畳む）人・AI集約が守るものの中心。1条件を1つのテストへ写せるaggregate コマンド「業務ルールと不変条件に違反した状態になることを防ぐ」・testing-strategy ピラミッド形
操作（commands）の name・pre・post・emitsそのまま残す人・AI名前と事前・事後の文を見せるaggregate コマンド
操作の args名前や書き方を直すAI引数は TERM と VO の ID の組で書き、整数・文字列などの基本の型を書かない。値オブジェクトを指せば、実装の型は VO から決まるvalue-object 基本データ型への執着
操作の accepts名前を直す人title を「受け付ける例」にする推測
操作の拒否する例（rejects）足すAIコマンドは外から渡された内容を検証して拒否する。事前条件ごとの拒否の理由（TERM）と例が無いと、拒否のテストを AI が推測で書くaggregate コマンド「外部から渡された内容を検証し」
業務イベント（events）の nameそのまま残す人・AI過去形の名前は原典どおりaggregate 業務イベント「名前は必ず過去形にし」
業務イベントの fields（項目の元）そのまま残す＋既定で畳むAI項目の元を ST か ARG で指すのは、テストの期待値を一意にするために要る。低すぎない。ただし状態をまるごと写さず、出来事の説明に要る項目だけにするaggregate 業務イベント「出来事に関する必要なデータをすべて持たせる」・event 状態転送との違い
整合性の境界（consistency）外す（ツールが条件から導いて表示する）人・AI状態と、それを使う条件の対応は、不変条件・事前条件・事後条件の参照から機械で引ける。手で書くと条件とずれる。表示では「どの条件にも使われない状態」を警告に出すaggregate「集約の業務ロジックが、その情報に強い一貫性を必要とするか」
対応するサブドメイン（subdomain）足す（文脈が2つ以上のサブドメインに対応するときだけ必須）AI実装方法はサブドメインの業務ロジックの性質で決まる。文脈が複数のサブドメインに対応すると、どの集約がどちらに属するかを AI が推測するbounded-context「内部には業務領域ごとの論理的な境界（名前空間・モジュール・パッケージ）が存在する」

値オブジェクト（10項目：残す5・直す2・外す1・畳む1・足す1）

項目（キー）判定効く観点理由根拠
所属する文脈（context）そのまま残す（見出しの位置に出す）人文脈をまたいで共有しない、は妥当bounded-context 同じ言葉の範囲は文脈の内側
名前（name）そのまま残す人・AI用語集の語を指すubiquitous-language「1つの用語に1つの意味」
表す概念（concept）外す（表示ではツールが用語集の定義を引く）人・AI用語集の定義と同じ文を2か所に書くと、どちらかだけ直されてずれるubiquitous-language「1つの用語に1つの意味」
構成する値（components）の type名前や書き方を直すAI値の種類（数・文字・真偽・日付・日時・時刻・列挙・値オブジェクト）までがモデル。数は「整数か小数か・小数の桁数」を業務の決まりとして書く。プログラミング言語の型名は実装側。title は「値の種類」value-object 金額のアンチパターン（丸めや端数処理）・Height（単位の変換）
構成する値の unitそのまま残すAI単位は業務の概念で、変換と比較のロジックが値オブジェクトに入るvalue-object 身長（Height）の例
構成する値の values（列挙の値）名前や書き方を直す人・AI列挙の値は用語集の TERM を指す。状態区分は同じ言葉の語であるvalue-object「状態区分やパスワードなど、対象領域に固有の概念を値オブジェクトで表す」
不変条件（invariants）そのまま残す人・AI妥当性の検証を値オブジェクト自身に持たせる。作れない値の例がテストになるvalue-object「妥当性を検証するロジックを、値オブジェクト自身に持たせる」
等価の定義（equality）既定で畳む（任意にする）人既定の「すべての構成値」なら書かない。単位の違う身長を等しいとみなすなど、既定と違うときだけ書くvalue-object 定義「値がすべて等しい2つのオブジェクトは同じ値とみなす」
操作（operations）そのまま残す（例は畳む）人・AI新しい値を返し自分を変えない、は原典どおりvalue-object「元のインスタンスを残して新しいインスタンスを返す」
端数の扱い（rounding）足す（小数の構成値か、掛け算・割り算の操作があるときだけ必須）AI丸める桁と方向が無いと、AI は言語の既定の丸めに任せるvalue-object 金額のアンチパターン「丸めや端数処理に危険な不具合が紛れ込みやすい」

ドメインサービス（6項目：残す3・直す2・畳む1）

項目（キー）判定効く観点理由根拠
所属する文脈（context）そのまま残す（見出しの位置に出す）人推測

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
usecase-advisor（利害関係者と達成の基準をドメインに置くか）DDD の判断基準はこの2つを判定に使わない。ユースケースの利害関係者と寄与先との重なりは、ユースケースの判断基準で確かめる必要がある
platform-advisor（品質の要求の置き場所）プロダクト全体にかかる振る舞いでない要求は、インフラ構成とセキュリティ境界の判断に入る可能性がある

  • 値オブジェクトから concept を外し、表示でツールが用語集の定義を引くようにする
  • 区切られた文脈の relations から position を外し、書く側の決まりを write に書く
  • ドメインに competitors、集約に subdomain と commands[].rejects、値オブジェクトに rounding を足す
  • 値オブジェクトの components[].type を値の種類の enum に置き換える
  • records の表の title と write の文を、スキーマの title と x-prompt.write へ写す
  • 種類ごとの既定で見せる項目と順番を、描画の設定へ写す

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
値オブジェクトの type や集約の args に、int ・ decimal ・ string ・ UUID などの言語の型名を書くスキーマで type を enum（数 ・ 文字 ・ 真偽 ・ 日付 ・ 日時 ・ 時刻 ・ 列挙 ・ 値オブジェクト）に限り、args と state の type を VO ・ ENT ・ AGG の ID の形（正規表現）に限る
外した consistency や root.id_type を、前の例を見て書き戻すスキーマの additionalProperties を false にし、外したキーを書いたら検査で拒む
集約の状態 ・ 引数 ・ 拒否の理由の名前を、用語集に無い語や使わない語で書く名前の欄はすべて TERM の ID にし、指した TERM の kind が欄に合うか（状態なら値オブジェクトかエンティティ、拒否なら拒否の理由）を照合する
業務イベントの fields に集約の状態をまるごと並べるfields の元に挙がった ST が、その集約の ST の全件と一致したら警告する
事前条件はあるのに拒否する例を書かないcommands[].pre の件数と、rejects が指す事前条件の ID の種類の数を比べ、足りなければ拒む
文脈が2つ以上のサブドメインに対応するのに、集約の subdomain を書かないcontext が指す BC の subdomains が2件以上なら、集約 ・ 値オブジェクト ・ ドメインサービスの subdomain を必須にする条件をスキーマ（if / then）で書く
