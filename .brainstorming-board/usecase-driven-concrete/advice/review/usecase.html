判断の道筋

  1. 会話で補える状況か

    補えない。AI は書いたあとに承認する人へ確認できず、承認する人も AI に聞き返せない。判断基準は、この場合に完全形式で厳密に書き、利害関係者と利益 ・ 事前条件 ・ 最低保証に特に注意するとする。よって、テンプレートの欄は削らない

  2. その項目は、対象システムの外から見える約束か、内部の仕組みか

    サーガ（補償の手順）と書き換える集約は、区切られた文脈の内部の仕組みである。判断基準は機能要求で内部に触れないとする。利害関係者から見える結果（失敗しても在庫も注文も変わらない）は最低保証と拡張に書けるので、サーガは実装側へ移す

  3. 同じ事実を2つの欄に持っていないか

    書き換える集約は、手順の「内部の状態変化」の参照から導ける。判断基準は、失敗の仕方を最低保証と拡張に二重に書くと食い違うとする。同じ理屈で、導ける欄は外してツールに導かせる（この適用は推測）

  4. AI が具体にするときに推測に頼る項目はどれか

    事前条件の作り手が任意だと、テストの準備を推測する。主アクターの role と on_behalf_of は、どちらが本来の主アクターかが書き方から決まらない。目的レベルの「既定はユーザー目的」は判定の問いを持たない。この3つは書き方を直す

  5. 承認する人は、何をどの順で見れば判定できるか

    判断基準は、スコープとレベルを読み手に最初に読ませ、ステップの前に利害関係者と利益 ・ 保証を並べるとする。テンプレートの欄の順（名前 → スコープ ・ レベル → 主アクター → 利害関係者と利益 → 事前条件 → 最低保証 → 成功時保証 → トリガー → 主成功シナリオ → 拡張）に従い、拡張は精度の段階に合わせて条件の一覧だけを先に見せ、処理は畳む（畳むことは推測）

technology-data-variation対応：条件やアクションステップは書かない ・ 理由：書いているなら、それはリストの使い方の誤りで、拡張に書くべきものである
use-case対応：機能要求として書くときは、対象システムをブラックボックスとして扱い、内部に触れない ・ 理由：要求は設計者の自由を奪ってはならない。よい設計を行うのは設計者の仕事である
system-under-discussion対応：これから作るシステムの要求では、対象システムをブラックボックスとし、内部に触れない ・ 理由：内部を推測して書いた要求は、読みにくく、設計が進むたびに書き直しになった
hub-and-spoke-model対応：複雑なビジネスルールは、それを書いた項目に置き、ユースケースからリンクする ・ 理由：複雑なビジネスルールは、シナリオの形にうまく収まらない
data-requirement-precision対応：ユースケースから、関連するフィールド一覧へのリンクを作る ・ 理由：別名だけでは、プログラマにとって情報が足りず、開発できない
use-case対応：読みやすさを優先し、そのためなら精度や正確さを多少犠牲にして、不足分は会話で補う ・ 理由：読みにくいユースケースは読まれなくなり、役に立たない

注意

アンチパターンリスク代替案
システムの内部を推測して、中の部品同士のやりとりを機能要求として書く（サーガの欄と書き換える集約の欄がこれに当たる）承認する業務の人が判定できない欄が混ざり、設計が進むたびに宣言を書き直す利害関係者から見える結果を最低保証と拡張に書き、補償の仕組みは実装側の定義に置く。書き換える集約は手順の参照から導いて表示する
「口座残高が不足している」のような失敗条件を、最低保証の欄に並べる拡張に書いた失敗条件と二重になり、AI が導くテストの期待値が2か所で食い違う失敗条件と処理は拡張に書き、最低保証には守られる利益だけを断定文で書く
「誰かが ATM を使おうとする」のように、システムが反応しない意図をトリガーにするユースケースがどのイベントで始まるかが決まらず、AI はテストの起点（何を呼べば始まるか）を推測するシステムが受け取って動き始めるイベントを書き、実行中に起きることは拡張の条件にする
（推測）同じ事実を2つの欄に持つ（書き換える集約と手順の参照、切り出した理由の「呼び出し側の UC」と呼び出し側の手順）AI が片方だけを書き換えて食い違い、どちらが正しいかを人が毎回確かめることになる一方だけを書かせ、もう一方はツールが導いて描画する

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
primary_actor の role に代わりに操作する人を書き、本来の主アクターを operated_by に入れるtrigger.kind が「中間の手段を介して始まる」なら operated_by が在り、それ以外なら無いことを validate で検査する。role が stakeholders の who のどれかに一致することも検査する
事前条件の作り手を書かず、テストの準備を推測で作るpreconditions の各要素で established_by を必須にし、指す UC が実在することを宣言の集合で解決する
成功時保証の1件目に名前の目的を置かない、最低保証と同じ文を成功時保証にも書くsuccess_guarantees[0].text に name の動詞が含まれること、success_guarantees と minimal_guarantees の text に同じ文が無いことを検査する
最低保証に失敗の仕方を書くminimal_guarantees の text が、いずれかの拡張の条件の文と一致しないこと、「場合」「とき」「〜ない：」で終わる条件の形をとらないことを検査する
トリガーにシステムが反応しない意図を書く、拡張の条件に検出できない出来事を書くtrigger.event と拡張の条件に、意図や内心の語（「しようとする」「忘れる」「思う」「気づく」）が無いことを、プロジェクトが持つ NG ワードで検査する
サーガを外したあと、複数の集約を書き換えるユースケースで、途中で失敗したときに変わらないものを書かない手順の参照から導いた集約が2件以上のユースケースは、最低保証に1件以上の要素を持ち、失敗で終わる拡張に内部の状態変化の手順（記録）が1件以上在ることを検査する（推測）
