結論

条件付きで採る

各頁の先頭には、その種類が「正しいか」を決める項目（集約なら守る一貫性と不変条件、ユースケースなら目的と主成功シナリオ）を置き、補助の項目は件数付きの見出しだけ見せて畳み、ID は名前の後ろに小さく添え、参照は名前で出すなら採ってよい

判断基準は最初の要素に「そのプロダクト・題材にとって最も特徴的なもの」を選ぶことと、文言に「利用者が認識し操作対象として扱う言葉」を使うことを求める。承認者にとっての題材は種類ごとの正しさの判定材料であり、承認者が認識する言葉は ID ではなく用語集の語だからである

B：種類ごとに判定に使う項目を先頭に置き、補助の項目は件数付きの見出しで畳む。ID は名前に添える頁を開いた時点で判定の材料が見え、補助の項目は必要なときだけ開く。ID は指摘のやり取りに使える採る
C：ID を出さず名前だけにする読むのは楽になるが、承認者が差し戻すときに対象を一意に指せない（推測）採らない

判断の道筋

  1. 品質下限（レスポンシブ・フォーカス状態・reduced-motion）を満たす形にできるか（accessibility-baseline）

    はい。畳むのは HTML の details / summary で作り、キーボードで開け閉めでき、フォーカスの輪を消さない。開閉に動きを付けない（付けるなら prefers-reduced-motion で止める）。表は狭い画面で1件ずつの縦並びに変える。ID の補足を hover だけで出す作りは採らない

  2. 頁の先頭（Hero）に何を置くか（visual-hierarchy-and-restraint (1)）

    種類ごとに「正しいか」の判定に直接使う項目を置く。数字の統計や件数の大きな表示を先頭にしない。7種類の内訳は「具体例」の7件に書く

  3. 番号や区切りを付けてよいか（visual-hierarchy-and-restraint (3)）

    順序に意味があるもの（主成功シナリオの手順、サーガの手順）だけ番号を付ける。不変条件・提供価値・用語集などの並びには 1/2/3 を振らない。ID（INV-2 等）は番号ではなく名札として小さく出す

  4. 項目名と enum の文言は承認者の言葉か、一貫しているか（ui-copywriting）

    大半はそのままでよい。同じ語が別の物を指す（集約の「操作」と値オブジェクトの「操作」）、同じ物を別の語で呼ぶ（「利害関係者とその関心」と「利害関係者と関心」、「書き換える」と「変更しない」）、英語のキーが title を持たない下位の欄、の3つを直す。原典の訳語は変えない

  5. ID と参照をどう出すか（ui-copywriting）

    本文は名前で書き、ID は名前の後ろに等幅の小さな文字で添える。TERM の ID は必ず用語集の語に置き換え、ID だけで出さない。参照先が見つからないときは、ID と「見つからない。参照先の ID を直す」を出す

  6. 作り込みの方向性は一貫しているか（visual-hierarchy-and-restraint (5)）

    最小限の方向にする。色は「分類」「目的レベル」などの enum のタグと、見つからない参照の警告だけに使い、余白と書体の階層で読ませる

実装の手順

  1. 直す文言（ID の扱い以外）

    利害関係者とその関心 → 利害関係者と関心／サブドメインの一覧 → サブドメイン／ルート → 集約ルート／集約の 操作（commands）→ コマンド／等価の定義 → 等しいとみなす条件／書き換える集約 → 変更する集約／置く理由の enum「集約や値オブジェクトでは表しにくい」→「集約にも値オブジェクトにも置けない」、「複数の集約を参照する計算」→「複数の集約にまたがる計算」／切り出した理由の enum「呼び出し側を読みにくくする」→「呼び出し側に書くと読みにくい」

  2. title が無い下位の欄に日本語の title を付ける

    範囲 in / out → 作るもの / 作らないもの／differentiator → 差別化／competitive_advantage・question・answer → 競合との違いになるか・使った質問・答え／needs_tracking・complex_rules・complex_data・rule_conditions → 経緯を追う必要があるか・業務ルールが複雑か・データの構造が複雑か・根拠の条件（意味は推測。スキーマの description で確かめる）／glossary の kind・avoid → 種類・使わない語／id_type → 識別子の型／multiplicity → 個数／established_by → 成り立たせるもの／protects → 守る相手／satisfies → 満たす相手／needed_by → 使う条件／from_event → 元の業務イベント／is_step_1 → 1手順目を兼ねる

  3. 変えない文言

    中核・補完・一般、区切られた文脈、業務イベント、公開された言葉、主アクター、支援アクター、最低保証、成功時保証、拡張、主成功シナリオ、技術およびデータのバリエーション、目的レベルと要約・ユーザー目的・サブ機能、整合性の境界、サーガ（技術用語）は変えない

  4. ID と参照の描画

    見出しと本文は名前で書き、ID は名前の後ろに等幅・小さい文字・薄い色で添える（例：在庫を引き当てる CMD-2）。TERM-n は用語集の語に置き換え、ID は出さない。他の宣言への参照（SD・VAL・AGG・SC・SH など）は名前を出し、その宣言の頁か節へのリンクにする。参照先が見つからないときだけ ID を前に出し「見つからない：VAL-9。参照先の ID を直す」と書く。条件の文の中の ST・CMP の参照も名前に置き換える

具体例

  • 【ドメイン】見せる：名前・解決する課題・提供価値（差別化のものにタグ）・達成の基準・範囲（作るもの／作らないもの）・サブドメイン（1行：名前＋分類のタグ）。畳む：利害関係者と関心・品質の要求。並び：名前 → 解決する課題 → 提供価値 → 達成の基準 → 範囲 → サブドメイン → 利害関係者と関心 → 品質の要求
  • 【サブドメイン】見せる：名前と分類のタグ・説明・分類の理由（使った質問と答え）・担う提供価値（名前）・業務ロジックの性質（3つの問いと はい／いいえ、複雑なら根拠の条件）。畳む：なし（項目が少ない）。調達は分類が一般のときだけ出す。並び：名前＋分類 → 説明 → 分類の理由 → 担う提供価値 → 業務ロジックの性質 → 調達
  • 【区切られた文脈】見せる：名前・目的・対応するサブドメイン・用語集（語と定義の表）・他の文脈との関係（相手・位置・連携のパターン）。畳む：用語集の「使わない語」と種類（行ごと）、関係の理由と使うもの、公開された言葉の項目（fields）、この文脈に属する宣言の一覧（ツールが集めたもの。1行ずつ）。並び：名前 → 目的 → 対応するサブドメイン → 用語集 → 他の文脈との関係 → 公開された言葉 → 属する宣言
  • 【集約】見せる：所属する文脈（頁の上に小さく）・名前・説明（守る一貫性）・不変条件（ツールが作った文と違反する例）・コマンド（名前と、事前条件・事後条件の文）・業務イベント（名前だけ）。畳む：状態の型と個数・集約ルートの識別子の型・内側のエンティティ・コマンドの引数と成功する例・業務イベントの項目・整合性の境界（どの条件にも使われない状態があるときだけ、その状態を見出しの横に警告として出す）。並び：名前 → 説明 → 不変条件 → コマンド → 業務イベント → 状態 → 集約ルート → 内側のエンティティ → 整合性の境界
  • 【値オブジェクト】見せる：所属する文脈（小さく）・名前・表す概念・構成する値（名前・型・単位）・不変条件（作れない値の例つき）・等しいとみなす条件。畳む：列挙の値の一覧（件数が多いとき）・操作の引数と例。並び：名前 → 表す概念 → 構成する値 → 不変条件 → 等しいとみなす条件 → 操作
  • 【ドメインサービス】見せる：所属する文脈（小さく）・名前・置く理由（enum のタグと reason_text の1文）・参照する集約（名前）・操作（名前と、入力 → 出力の1行）。畳む：操作の事前条件・事後条件・例。並び：名前 → 置く理由 → 参照する集約 → 操作
  • 【ユースケース】見せる：名前・目的レベルとスコープ（タグ）・主アクター・トリガー・成功時保証・最低保証・主成功シナリオ（番号付き）・拡張の条件（手順番号と条件の1行）。畳む：拡張の処理（条件ごと）・利害関係者と関心（件数を見出しに）・支援アクター・事前条件（0件なら「なし」と1行）・技術およびデータのバリエーション・関連情報・寄与する達成の基準・変更する集約・切り出した理由（サブ機能のときは見せる）。サーガは書き換える集約が2つ以上のときだけ見せる。並び：名前 → 目的レベル・スコープ → 主アクター → 利害関係者と関心 → 事前条件 → 最低保証 → 成功時保証 → トリガー → 主成功シナリオ → 拡張 → 技術およびデータのバリエーション → サーガ → 関連情報（コーバーンのテンプレートの順を保つ）

accessibility-baseline(2)フォーカス状態——キーボードだけで操作する利用者のために、今どの要素が選択されているかを視覚的に示す。
accessibility-baseline(3)reduced-motion対応——利用者のOS設定で「動きを減らす」が指定されている場合、大きなアニメーション・自動再生を抑える。
