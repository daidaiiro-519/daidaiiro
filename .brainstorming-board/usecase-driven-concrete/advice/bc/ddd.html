見本の区切られた文脈の宣言（BC-1 受注 ・ BC-2 決済）が、業務領域の宣言（SD-1 ・ SD-2）の書き直しになっていて区別が付かない。区切られた文脈の宣言に何を書くべきか。オーケストレーターの案1〜5でよいか

結論

条件付きで採る

利用者の指摘は正しい。BC-1 ・ BC-2 の頭の欄（名前 ・ purpose）は業務領域の書き直しで、区切られた文脈が持つべき「モデルの目的 ・ 同じ言葉 ・ 物理的な境界 ・ 所有権の境界 ・ 文脈の地図」が頭に無い。案2 ・ 3 ・ 4 は採り、案1は目的の例文を書き直す条件で採り、案5は採らない

判断基準は、業務領域を「事業として何をするか」を発見するもの、区切られた文脈を「モデルの境界をどこに置くか」を設計するものとして分けている。業務領域の説明を区切られた文脈の目的に書くと、設計した内容（どの課題をどのモデルで解くか、どこで実装し誰が持つか）が頭から消える。

案何が起きるか採否
案1：目的の欄を、業務ではなくモデルの目的にする（例「注文と調理枠を、受注の言葉で1つのモデルとして扱う」）欄の向きを業務からモデルへ変える点は判断基準と合う。ただし例文は「この文脈の同じ言葉で1つのモデルを持つ」という、どの区切られた文脈にも当てはまる定義を言っているだけで、どの課題を解くモデルかが書かれていない。判断基準は「モデルで解決しようとしている課題、つまり目的を明確にする」を求めるので、例文を、解く課題と外へ出すものの形に書き直す条件で採る。例：「受け取り予定時刻の約束が、調理枠の空きを超えないかを判定する。支払いの承認と商品の価格は、このモデルに入れず他の文脈から受け取る」採る
案2：頁の先頭を、この文脈の中のモデル（集約 ・ 値オブジェクト ・ ドメインサービス）と用語集にする区切られた文脈は同じ言葉の通用する範囲であり、モデルの境界である。業務領域の宣言には無い欄なので、頭に置けば一目で区別が付く。BC-1 の ubiquitous_language は既に集約 ・ エンティティ ・ 値オブジェクト ・ ドメインサービスの種別を持つので、集約を先に並べ、拒否の理由や動作のような語は後ろに畳めばよい（並び順は推測）採る
案3：物理的な境界とコンテキストマップを前に出す物理的な境界 ・ 所有権の境界 ・ 他の文脈との連係は、区切られた文脈だけが持つ欄である。業務領域の宣言に無いものを前に出すほど、2つの宣言の違いが見える。boundary の kind を物理的な境界、owner を所有権の境界と明示して並べる採る
案4：サブドメインとの対応は後ろに1行で示す業務領域と区切られた文脈の対応は一対一に限らないので、対応そのものは欄として残す必要がある。ただし業務領域のカテゴリーや説明を写さず、id を指すだけにする。BC-1 は業務領域ごとに1つの文脈を置いた区切り方だと1行で添えると、名前が同じ理由も読める採る
案5：名前を文脈の名前にする（例「受注の文脈」）判断基準の事例は、文脈を「販売促進」「顧客管理」「イベント処理装置」のように業務の名前で呼び、業務領域ごとに1つの文脈を置く区切り方も原典の事例にある。名前に「の文脈」を足しても新しい情報は増えず、区別は欄の中身でしか付かない。宣言の種別（区切られた文脈）を見出しの札で示せば足りる（推測）採らない

判断の道筋

  1. 業務領域と区切られた文脈は、何が違うか

    業務領域は事業方針から決まり発見するもので、事業として何をするかを説明する。区切られた文脈はモデルの境界をどこに置くかの設計判断で、モデル ・ 物理 ・ 所有権の3つの境界を定める

  2. BC-1 の頭の欄は、どちらの内容を書いているか

    名前と purpose は、SD-1 の名前と description とほぼ同じ「業務として何をするか」である。業務領域の内容である。だから利用者の指摘は正しい

  3. BC-1 の宣言全体が業務領域の書き直しか

    違う。ubiquitous_language ・ boundary ・ context_map は区切られた文脈だけが持つ欄で、既に正しく書かれている。書き直しになっているのは頭の欄だけで、本来の欄が頭の下に隠れているので区別が付かなく見える

  4. 業務ルールを区切られた文脈に置いてよいか

    よい。判断基準は、用語の意味 ・ 業務方針 ・ 業務ルールが一貫するのは区切られた文脈の内側に限られると言う。BR-1 は BC-1 のモデルの要素（AGG-1）を指すので、置き場所は文脈で正しい。SD-1 の rule_conditions は、業務ロジックが複雑かを判定した根拠として BC のモデルの要素を指しているだけなので、重なりではない

  5. 品質の要求を区切られた文脈に置いてよいか

    推測では、よい。物理的な境界は実装する単位であり、「一部の機能だけスケールアウトが必要」なら独立した単位に切り離すという区切り直す契機がある。QR-1 は BC-1 のコマンド（AGG-1.CMD-1）を対象にしているので、実装する単位に付けるのは筋が通る。水準の妥当さは判断基準の範囲外である

  6. 業務領域の宣言にだけ置き、区切られた文脈に置くべきでない欄は何か

    業務の説明（何をする業務か）、カテゴリー（中核 ・ 一般 ・ 補完）、競争優位、外部で手に入るか、作るほうが安いか、調達のしかた。区切られた文脈はこれらを id で指すだけにする。BC-1 の文脈の地図の case「下流の文脈が中核の業務領域を含む」のように、連係方法の理由として参照するのはよい

  7. BC-2（決済）はどう書くか

    BC-2 は決済代行のサービスで、自社はそのモデルを設計しない。モデル変換装置は本来、変換で守られる下流の文脈に所属するので、「受注の側にモデル変換装置を作る」は BC-2 の boundary ではなく BC-1 の文脈の地図に書く（既にある）。BC-2 の目的は、受注の側から見て受け取るもの（承認番号 ・ 承認されなかったこと）に絞り、同じ言葉は自社で決めないので空でよい
