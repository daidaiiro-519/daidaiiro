usecase-advisor の回答 ・ 判断相談

宣言の欄の決め直し（オーケストレーターの見立て1〜7）は、『ユースケース実践ガイド』の概念の意味を変えていないか。聞きたいこと A（意味の変更 ・ 置き場所の誤り ・ 不足）・ C（ユースケースに残す欄と外す欄）・ D（要求の側のビジネスルールと設計の側の業務ルールの関係）に答える。B は差し戻す

前置き

判定の前に確定させた前提と、その出所

前提内容出所
決着済みの前提手法は要求の側と設計の側で構成し、要求のユースケースは内部に触れず、つなぎは設計の側のアプリケーション層の操作が持つ。スコープ欄はプロダクトである。この回答はこれらを変えない相談の材料（ボード use-case-driven-development 論点1〜3、ACDR 0111）
判断基準が扱う範囲判断基準が扱うのは要求の側（要求アウトライン ・ ユースケースの欄 ・ ブラックボックス）までである。アプリケーション層の操作 ・ サブドメイン ・ 集約 ・ 区切られた文脈 ・ 用語集の内部の形（意味の ID、使わない語）・ 競合（competitors）は判断基準の範囲外であり、それらについての記述は推測として書く判断基準の範囲外
いまのユースケースの欄の見え方相談の材料の「いまの宣言の欄」は直す対象の欄だけを挙げていると読む。主アクター ・ レベル ・ トリガー ・ 主成功シナリオ ・ 拡張条件の本文は在るものとして扱う。利害関係者と利益 ・ 最低保証の文 ・ 技術およびデータのバリエーション ・ 関連情報が欄として在るかは未判定であり、C の判定はそれが無い場合を「不足」として書く相談の材料から置いた仮定
B の扱いトランザクションスクリプト ・ アクティブレコードの業務領域で業務ルールと状態の変更を操作に持たせる扱いは、ddd-advisor の判断基準の範囲であり、この回答では判定しない依頼の分担

結論

条件付きで採る

見立て1〜7 は、ユースケースの概念の意味を大きくは変えていないが、見立て4 は支援アクターとのやりとり ・ 支援アクターの失敗の拡張 ・ 外部が作る事前条件を外しすぎており、利害関係者と利益 ・ 最低保証 ・ 技術およびデータのバリエーション ・ 関連情報の欄を足したうえで採る。

ブラックボックスの規則が禁じるのは対象システムの内部（コンポーネント）に触れることであり、支援アクターに何を頼み何を受け取るかと、その失敗の拡張は、判断基準が振る舞い要求として書くよう求めている。外すべきは集約 ・ コマンド ・ 状態の変更 ・ 外部の操作名のような設計の側の識別子だけである。

比較した案

案何が起きるか採否
案1：見立て4 のまま採る（invokes ・ via ・ handles ・ fails_external ・ ensures ・ 成功時保証の established_by を外し、keeps ・ serves ・ ユースケースを指す established_by だけを残す）内部に触れない点は満たす。ただし via を外すと、対象システムが支援アクターに何を頼み何を受け取るかがユースケースから消える。fails_external を外すと、支援アクターの応答が無い ・ 正しくない拡張の置き場所があいまいになる。外部の操作が作る事前条件は、根拠を失ったまま残るか、黙って消える採らない
案2：見立て4 を直して採る（設計の側の識別子だけを外し、支援アクター ・ 支援アクターの失敗の拡張 ・ 利害関係者と利益 ・ 最低保証 ・ 技術およびデータのバリエーション ・ 関連情報をユースケースの欄として持つ）ブラックボックスを保ったまま、判断基準がユースケースに書くよう求める振る舞い（支援アクターとのやりとり、その失敗、利害関係者の利益を守る妥当性確認と内部の状態変化）が残る。外した識別子は、アプリケーション層の操作がユースケースの欄を指す形で設計の側に移る採る
案3：いまの欄を残す（ユースケースが集約のコマンド ・ 業務ルールの拒否 ・ 状態の変更 ・ 区切られた文脈を指す）ユースケースが対象システムのコンポーネントに触れるホワイトボックスになる。判断基準は、これから作るシステムの要求をこの形で書くことを、設計が進むたびに書き直しになるとして退けている。決着済みの前提（要求のユースケースは内部に触れない）にも反する採らない

判断の道筋

  1. A-1：ビジョン記述に problem ・ values ・ success_criteria ・ competitors をまとめ、stakeholders ・ scope{in,out} ・ design_scopes を残し、subdomains と quality を外すのは、要求アウトラインの「目標とスコープ」に沿うか

    沿う。目標とスコープの章の中身は全体のスコープと目的 ・ 利害関係者 ・ スコープの内と外であり、機能スコープの基準はビジョン記述 ・ In/Out リスト ・ アクター-目的リスト ・ 設計スコープの図を4つの作業成果物とする。品質の要求をその他の要求へ移すのも、パフォーマンス ・ 運用 ・ セキュリティ ・ 保守性がその他の要求の章にあることと一致する。subdomains を外すことと competitors をビジョン記述に入れることは、判断基準の範囲外（推測：ビジョン記述はスコープ内かどうかを判断する材料なので、competitors を入れても意味は変わらない）

  2. A-2：ドメインの stakeholders だけで利害関係者は足りるか

    足りない。判断基準は、システム全体で1つの一覧を作って済ませず、ユースケースごとに利害関係者と利益を挙げるよう求める。ドメインの stakeholders は目標とスコープの章として残し、ユースケースには「利害関係者と利益」の欄を置く（ドメインの利害関係者を ID で指し、利益はユースケースごとに書く）

  3. A-3：用語集を要求の側に1つ置き、区切られた文脈から使う意味を指すのは、原典の位置付けを変えるか

    位置は変えない。用語集は要求アウトラインの1つの章で、ユースケースの外に書く。語ごとの意味の ID ・ 使わない語 ・ 文脈が使う意味を指す形は判断基準の範囲外（推測）である。用語集とデータ要求（フィールド一覧 ・ フィールド詳細）は別の章として分け、用語集にフィールドの型や長さを入れない

  4. A-4：「その他の要求」を複雑なビジネスルール ・ 品質の要求 ・ 未決定事項の3つで組むのは足りるか

    その他の要求の章としては意味を変えていない（原典の中身は開発プロセス ・ ビジネスルール ・ パフォーマンス ・ 運用 ・ セキュリティ ・ 保守性 ・ 未決定事項など）。ただし要求アウトラインの残りの章のうち、「使われる技術（相互作用するシステムとその要求）」とデータ要求の置き場所が見立てに無い。見立て4 で via を外すと、外部システムとのインタフェースの要求がどこにも書かれない状態になりやすい。2つの置き場所を足す

  5. C-1：invokes ・ handles ・ ensures ・ 成功時保証の established_by を外すのは、ブラックボックスの規則に照らして正しいか

    正しい。集約 ・ コマンド ・ 業務ルールの拒否 ・ 状態の変更 CHG は対象システムのコンポーネントであり、ユースケースがそれに触れればホワイトボックスになる。ただし外すのは識別子へのリンクだけで、利害関係者の利益を守る妥当性確認のステップ（「システムは…を確認する」）と内部の状態変化のステップ（「システムはその金額を残高から差し引く」）は、外から見た振る舞いとしてユースケースに残す。成功時保証の文も残す

  6. C-2：via（外部の操作）と fails_external（外部の失敗の種類）を外すのは正しいか

    一部だけ正しい。外部の操作名と失敗の種類の識別子は、文脈の地図の側の設計の情報なので外してよい。しかし支援アクターは対象システムの外にいるアクターであり、判断基準は、対象システムが支援アクターに何を依頼し何を受け取るかをステップに書き、支援アクターからの応答が無い場合と正しくない場合を拡張条件に入れるよう求める。via はステップの「支援アクター」（アクターの名前）に置き換え、拡張条件は「在庫システムから応答が無い：」のように検出された状況で残す。外部の操作名は、アプリケーション層の操作と「使われる技術」の章へ移す

  7. C-3：事前条件の established_by のうち、ユースケースを指すものだけを残すのは正しいか

    ユースケースを指すものを残すのは正しい。事前条件は、別のユースケースがすでに実行され、その条件を設定していることを表す。外部の操作を指すものは、外すだけでは足りない。事前条件はシステムが真であると保証できる事柄に限られるので、外部システムが作る状態は、(a) 外部システムを主アクターとする対象システムのユースケース（原典の BSSO が Acura に通知する例）が作る事前条件として書き直すか、(b) 対象システムが保証できないなら事前条件から外し、ステップの妥当性確認と拡張条件として書く

  8. C-4：ステップの keeps（最低保証）と serves（利害関係者）を残すのは正しいか

    残してよいが、指す先を直す。最低保証はユースケースがどう終わっても成り立つ断定文であり、ユースケースの保証の欄に文として置く。keeps はその文の ID をステップから指すリンクとして扱い、拡張のステップからも指せるようにする（判断基準は失敗処理でも利益が守られ、ログが残るかを確認するよう求める）。serves は利害関係者だけでなく、その利害関係者の利益を指す。判断基準の照合は「各利益がどこかで満たされているか」だからである。ステップから保証や利益を指すリンクの形そのものは判断基準の範囲外（推測）である

  9. C-5：scope を設計スコープ（プロダクト）だけにし、区切られた文脈を指さないのは正しいか

    正しい。スコープ欄には対象システムの名前を書く。区切られた文脈は設計の側でプロダクトを分けたものであり、それをスコープ欄に書けば、要求を推測した内部（サブシステム）で書くことになる。レベル欄も必ず埋める

  10. C-6：外した欄のほかに、ユースケースに足りない欄はあるか

    判断基準の完全形式のテンプレートと照らすと、利害関係者と利益 ・ 最低保証（文）・ 技術およびデータのバリエーションリスト ・ 関連情報（優先度 ・ 発生頻度 ・ パフォーマンス要求 ・ 未決定事項 ・ 支援アクターなど）の4つが、相談の材料の欄に見当たらない。とくに関連情報は、その他の要求をユースケースから ID で結ぶ欄（見立て3）であり、これが無いと見立て3 が成り立たない

  11. A-5：アプリケーション層の操作が満たすユースケースを指す（見立て5）のは、要求と設計の関係として原典に沿うか

    向きは沿う。判断基準は、各レベルのユースケースを次のレベルの設計が満たす振る舞い要求として扱い、「この設計は、これらの振る舞い要求を満たす」という形で対応付けるとする。操作が複数のユースケースを満たせる形にしたことも、ユースケースを1つずつクラスやコンポーネントに対応づけるアンチパターンを避ける。操作 ・ 集約 ・ 文脈の地図そのものの形は判断基準の範囲外である

  12. A-6：サブドメインに束ねるユースケースを足す（見立て6）のは沿うか

    判断基準の範囲外である。参考として、判断基準はアクター-目的リスト（ユーザー目的の一覧）を優先度付け ・ 納品 ・ チーム分け ・ 見積もり ・ 開発の土台にするとする。推測：束ねる対象はユーザー目的のユースケースにすると、この使い方と一致する。要約のユースケースは複数のサブドメインにまたがり、サブ機能は複数のクラスにまたがる部分的なメカニズムになりやすい

  13. D：その他の要求の複雑なビジネスルールを、集約の業務ルールの側から ID で指す（見立て7）のは沿うか

    要求の側については沿う。判断基準は、シナリオの形に収まらない複雑なビジネスルールを、ルールを書いた項目に置いてユースケースからリンクするとする。設計の側から要求の ID を指す向きは、設計が振る舞い要求を満たすと対応付ける考え方と同じ向きだが、ビジネスルールを集約が実装する対応そのものは判断基準の範囲外（推測）である。注意点は2つ：(1) 複雑でないビジネスルールは、ユースケースの妥当性確認のステップと拡張条件に書かれるので、集約の業務ルールの多くはその他の要求ではなく、操作の拡張の対応（見立て5）を通じてユースケースにたどり着く。(2) 要求の側のビジネスルールは、システムが利害関係者の代わりに実施するものとして書くので、どの利害関係者のどの利益を守るかを持たせる

supporting-actor対応：拡張条件をブレーンストーミングするときは、支援アクターからの応答が無い場合と、応答が正しくない場合を候補に入れる ・ 理由：そのときの振る舞いが要求に無いと、プログラマがその場で書ける程度の処理を書き込むことになる
supporting-actor対応：支援アクターが見つかったら、それとやりとりする外部インタフェースと、そこで使うプロトコルを洗い出す ・ 理由：データフォーマットや外部インタフェースといった、ユースケース以外の要求を付け加える手がかりになる
supporting-actor対応：支援アクター（二次アクター）を、ユースケースに結び付ける関連情報の1つとして記録する ・ 理由：ユースケースの本体に含めない要求も、ユースケースに結び付けて管理できる
precondition問い：システムはそれが真であることを保証できるか ・ 何が分かるか：事前条件は、システムが真であると保証している事柄である。たいてい真でも、保証できないものは書かない
precondition問い：どのユースケースがその状態を作っているか ・ 何が分かるか：事前条件は、別のユースケースがすでに実行され、その条件を設定していることを表す
minimal-guarantee対応：ユースケースが終了したときに必ず真になることを、いくつかの短い断定文で書く ・ 理由：この欄の目的は、システムが何を約束するかを示すことにある
extension対応：どの失敗処理でも、利害関係者の利益が守られ、ログや回復のための情報が残るかを確認する ・ 理由：書き手は途中で失敗が起きる場面を想定しないので、ログや回復の情報が抜けやすい
extension対応：条件は、検出されたことを表す句か文で書き、末尾にコロン（：）を付ける ・ 理由：「暗証番号が正しくない：」のように書けば、アクションステップと識別でき、それだけで多くの誤りを防げる。できれば過去形にする
use-case-format欄：技術およびデータのバリエーションリスト ・ 何を書くか：将来、別の実現方法になり得るものを、ステップ番号ごとに挙げる
use-case-format欄：関連情報 ・ 何を書くか：プロジェクトが必要とするその他の情報
use-case-format欄：スコープ ・ 何を書くか：設計スコープ。ブラックボックスとして扱う設計対象のシステム
technology-data-variation観点：主成功シナリオと何が異なるか ・ 拡張：システムが「何を」するか ・ 技術およびデータのバリエーション：同じことを「どのように」行うか
data-requirement-precision対応：データ要求の詳細は、ユースケースとは別の場所に書く ・ 理由：多くのユースケースが、同じ情報の別名を参照することがよくある
business-and-system-use-case対応：各レベルのユースケースを、次のレベルの設計が満たす振る舞い要求として扱う ・ 理由：「この設計は、これらの振る舞い要求を満たす」という形で両者を対応付けられる
use-caseユースケースを1つずつ、そのままクラスやコンポーネントに対応づける

注意

アンチパターンリスク代替案
支援アクターとのやりとりを、外部の操作と一緒にユースケースから外す対象システムが支援アクターに何を頼み何を受け取るかが要求に表れず、支援アクターの応答が無い ・ 正しくない場合の振る舞いが要求から漏れる。プログラマがその場で思いついた処理を書き込むステップに支援アクターの名前と依頼の意図を残し（「システムは在庫システムに在庫の引き当てを頼む」）、外部の操作名だけを設計の側へ移す。拡張条件に支援アクターの応答が無い場合と正しくない場合を入れる
外部の操作が作る状態を、事前条件として残す、または黙って消すシステムが保証できない事柄が事前条件になり、ユースケースを始められる場面を不当に狭めるか、本文で確認しなくてよいと誤って読まれる。消せば、その状態を誰が作るかが要求から消える外部システムを主アクターとする対象システムのユースケースが作る状態として書き直す。保証できなければ、ステップの妥当性確認と拡張条件に移す
invokes ・ CHG のリンクを外すときに、妥当性確認と内部の状態変化のステップまで消す主アクターとシステムの間の相互作用だけが残り、その場にいない利害関係者の利益を守る振る舞い（ログ ・ 残高の確認など）が要求から抜ける識別子へのリンクだけを外し、「システムは…を確認する」「システムは…を記録する」のステップは外から見た振る舞いとして残す
利害関係者をドメインの一覧だけで済ませるユースケースごとの利益が挙がらず、成功時保証 ・ 最低保証 ・ serves の照合先が無くなる。原典の実話では、稼働後1年の変更依頼がすべて、見落とした利益の一覧に含まれていたユースケースに「利害関係者と利益」の欄を置き、ドメインの利害関係者を ID で指して、利益をユースケースごとに書く。serves はその利益を指す
（推測）用語集とデータ要求を1つの種類にまとめる語の意味（用語集）と、フィールドの構成 ・ 型 ・ 長さ（データ要求）は変わる時期と書く人が違う。1つにまとめると、どちらかが更新されないまま残る用語集とデータ要求を別の種類にし、ステップの情報の別名からデータ要求へ、語から用語集へ、それぞれリンクする

差し戻し

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
ddd-advisor：聞きたいこと B（トランザクションスクリプト ・ アクティブレコードの業務領域で、業務ルールと状態の変更をアプリケーション層の操作に持たせる扱い）業務ロジックの実装の選択と、集約が無いときに業務ルールをどこに置くかは、『ユースケース実践ガイド』の判断基準の範囲外であり、DDD の判断基準で判定する
ddd-advisor：見立て6（サブドメインのカテゴリーの判定）と見立て2 の後半（区切られた文脈が用語集の意味を指す形）サブドメイン ・ 区切られた文脈 ・ ユビキタス言語は判断基準の範囲外であり、この回答の記述は推測にとどまる

次にすること

  • ユースケースの宣言の形から、設計の側の識別子の欄（invokes ・ handles ・ ensures ・ 成功時保証の established_by ・ scope{context}）を外す
  • via をステップの支援アクターの欄に置き換え、外部の操作名をアプリケーション層の操作へ移す
  • 支援アクターの応答が無い ・ 正しくない場合の拡張条件が、各ユースケースに残っているかを確認する
  • 外部の操作を指していた事前条件を、外部システムが主アクターのユースケースで作るか、妥当性確認と拡張条件に移すかを1件ずつ決める
  • ユースケースに利害関係者と利益 ・ 最低保証の文 ・ 技術およびデータのバリエーション ・ 関連情報の欄を足す
  • serves の指す先を、利害関係者からユースケースの利益へ変える
  • 要求の側に「使われる技術」と「データ要求」の種類を足す
  • 聞きたいこと B を ddd-advisor に渡す

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
ユースケースの欄から設計の側の識別子を外す作業で、AI が支援アクターの名前や支援アクターの失敗の拡張条件まで消す直したあとの宣言で、支援アクターを持つユースケースごとに、(1) ステップのどこかでその支援アクターが現れること、(2) 拡張条件のどれかがその支援アクターの応答の欠落か誤りを表すこと、を道具で数え、0件のユースケースを列挙する
ユースケースの宣言に、集約 ・ コマンド ・ 区切られた文脈 ・ CHG ・ BR の識別子が残る、または文の中に書き込まれるユースケースの宣言の全文字列を、集約名 ・ コマンド名 ・ 文脈名 ・ ID の接頭辞（CHG- ・ BR- ・ RES-）の一覧と照合し、一致が0件であることを検査する
事前条件の established_by が外部の操作を指したまま残る、または外部の操作を指す事前条件が理由なく消えるestablished_by の値がすべてユースケースの ID であることを検査する。直す前に外部の操作を指していた事前条件の一覧を作り、直したあとで、それぞれがユースケースの事前条件 ・ ステップの妥当性確認 ・ 拡張条件のどれかに在ることを照合する
アプリケーション層の操作を、ユースケース1件に1件ずつ機械的に作る操作と満たすユースケースの対応を数え、すべての操作が1件のユースケースだけを満たし、かつすべてのユースケースが1件の操作だけに満たされている状態なら、設計者の判断が入っているかを確認する項目として報告する
