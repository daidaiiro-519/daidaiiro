# 相談の材料：宣言の欄の決め直し（要求の側と設計の側に分けたあと）

## 前提（決着済み。ボード use-case-driven-development 論点1〜3、ACDR 0111）
- 手法は要求の側と設計の側で構成する。要求の側：ドメイン（作りたいプロダクト。ビジョン記述 ・ 利害関係者と利益 ・ スコープの内外）→ アクター-目的リスト → ユースケース（要約 → ユーザー目的 → サブ機能。スコープ欄はプロダクト）→ ほかの要求（用語集 ・ ビジネスルール ・ 品質の要求。ユースケースの外に書いて結ぶ）。設計の側：業務領域（ユースケースを同じアクター ・ 外部システム ・ 密接なデータで束ねる）→ 実装の選択 → 区切られた文脈 → 集約など。
- 要求のユースケースは内部に触れない。つなぎは設計の側のアプリケーション層の操作が持つ（満たすユースケース ・ 呼ぶ集約のコマンド ・ 各拡張が起きる拒否）。技術方式はポートとアダプターに固定、CQRS は目的に応じて。業務ルールは集約に残し、操作は対応だけを持つ。複数の集約を変えるユースケースはサーガかプロセスマネージャー。事前条件で防ぐ拒否は拡張の欠けとして数えない。拡張は検出された状況で書き、ずれは両方の向きから計算する。
- 用語集は要求の側に1つ。区切られた文脈が、用語集のどの語のどの意味を使うかを指す。文脈ごとに意味が違う語は、用語集の中で意味を分けて書き、語の頭に文脈名を付けない。
- 宣言は構造化データ。意味はすべて欄に持ち、文 ・ 例 ・ 境界値は道具が組む。

## いまの宣言の欄（直す対象）
- ドメイン：name ・ problem ・ values（differentiator ・ lacks）・ scope{in,out} ・ subdomains ・ success_criteria ・ stakeholders ・ quality ・ competitors ・ design_scopes
- ユースケース：scope{context}か{domain} ・ steps[].invokes（集約.コマンド）・ steps[].via（外部の操作）・ extensions[].handles（コマンドの業務ルールの拒否）・ extensions[].fails_external（外部の失敗の種類）・ preconditions[].ensures（防ぐ拒否）・ preconditions[].established_by（ユースケース、または外部の操作）・ guarantees.success[].established_by（状態の変更 CHG）・ steps[].keeps（最低保証）・ steps[].serves（利害関係者）
- 区切られた文脈：glossary（用語集）・ context_map ・ business_rules ・ quality ・ subdomains
- サブドメイン：category ・ business_logic ・ category_reason ・ sourcing ・ serves_values
- 集約：commands[].business_rules（BR-n、拒否）・ state_changes（CHG-n）・ emits ・ accept_examples。ドメインサービス：operations[].results（RES-n）

## オーケストレーターの見立て（検証してほしい）
1. ドメイン：ビジョン記述（vision）に problem ・ values ・ success_criteria ・ competitors をまとめる。stakeholders ・ scope{in,out} ・ design_scopes は残す。subdomains と quality は外す（業務領域は設計の側、品質の要求はその他の要求へ）。
2. 新しい種類「用語集」（プロダクトに1つ）：語ごとに意味の一覧（意味ごとの ID と定義）と使わない語。区切られた文脈の glossary は外し、「使う意味」（用語集の語と意味の ID）に替える。
3. 新しい種類「その他の要求」（『ユースケース実践ガイド』の要求アウトラインの章）：複雑なビジネスルール ・ 品質の要求 ・ 未決定事項。ユースケースの関連情報から ID で結ぶ。
4. ユースケース：invokes ・ via ・ handles ・ fails_external ・ ensures ・ 成功時保証の established_by を外す。scope は設計スコープ（プロダクト）だけを指し、区切られた文脈を指さない。残すのは keeps ・ serves と、事前条件の established_by のうちユースケースを指すもの。
5. 新しい種類「アプリケーション層の操作」（区切られた文脈の中）：満たすユースケース（複数可）・ 呼ぶもの（集約のコマンド ・ ドメインサービスの操作 ・ 文脈の地図の外部の操作）・ 拡張の対応（ユースケースの拡張 → 業務ルールの拒否、または外部の失敗の種類）・ 事前条件の対応（ユースケースの事前条件 → 防ぐ拒否）・ 成功時保証の対応（成功時保証 → 状態の変更）。業務ロジックをトランザクションスクリプトかアクティブレコードで実装する業務領域では、集約が無いので、業務ルールと状態の変更を操作が持つ。
6. サブドメイン：束ねるユースケース（UC の ID）を足す。カテゴリーの判定は、競争優位と業務ロジックの複雑さの2つの軸のまま。
7. 集約の業務ルールが、その他の要求の複雑なビジネスルールを実装するときは、集約の業務ルールの側からその ID を指す（設計の側が要求を指す向き）。

## 聞きたいこと
A. 見立て1〜7 で、原典の概念の意味を変えている、置き場所を誤っている、足りないものはどれか。
B. トランザクションスクリプト ・ アクティブレコードの業務領域で、業務ルールと状態の変更を操作に持たせる扱い（見立て5の後半）は原典に沿うか。
C. ユースケースに残す欄 ・ 外す欄（見立て4）は、ブラックボックスの規則に照らして正しいか。事前条件の established_by や、ステップの keeps ・ serves の扱いを含めて。
D. 要求の側のビジネスルール（その他の要求）と、設計の側の業務ルール（集約）の関係（見立て7）は、原典に沿うか。

判断基準からの引用を根拠にし、範囲外は「推測」と書く。新しい語を作らず、原典の語をそのまま使う。比喩を使わない。
