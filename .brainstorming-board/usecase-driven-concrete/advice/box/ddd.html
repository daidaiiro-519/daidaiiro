ddd-advisor の回答 ・ 判断相談

「提供する箱」（設計対象のシステム ・ アプリの形）を、宣言のどこに置くべきか。利用者の考えと、オーケストレーターの見立て1〜5は、ドメイン駆動設計の判断基準から見て正しいか（DDD の側：事業領域 ・ 業務領域 ・ 区切られた文脈の物理的な境界と所有権の境界 ・ 配置の単位との関係 ・ モデリングとコーディングの境目）

前置き

判定の前に確定させた前提と、その出所

前提内容出所
「箱」の2つの意味「提供する箱」には、(a) 裏側で業務ロジックとモデルを実装する単位（サービス ・ プロジェクト）と、(b) 顧客のスマホアプリや店舗のタブレットの画面のように、利用者が操作する入口の、2つが混ざっている。判断基準が扱うのは (a) である。(b) を独立した境界として扱う記述は判断基準に無い相談の材料（input.md の利用者の言葉と見立て2）を、判断基準の記述と突き合わせた
Cockburn の設計範囲見立て1と4の「設計対象のシステム（主アクターから見てブラックボックスの箱）」が正しいか、ユースケースの scope が何を指すべきかは、この回答では判定しない。DDD の側から、ユースケースとモデルのつながりが切れないかだけを見る判断基準の範囲外（usecase-advisor の範囲）
アプリ（入口）の分け方顧客のスマホアプリと店舗のタブレットの画面を別々の箱にするか、どの区切られた文脈の公開インターフェースを使うかは、判断基準が触れていない。この回答で (b) について書く内容は推測である判断基準の範囲外
宣言と実装の定義の分担宣言（ドメイン ・ サブドメイン ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス）はモデリングが書き、実装の定義（技術スタック ・ 層の並び ・ サブドメインごとの実装方法とテストの形 ・ 規則）はコーディングが1プロダクトに1つ持つ相談の材料（input.md の前提）

結論

条件付きで採る

裏側の実装の単位としての箱は、新しい宣言を足さず、区切られた文脈の宣言に物理的な境界と所有権の境界として持たせ、文脈ごとの要素技術 ・ 技術方式 ・ マイクロサービスへの分け方を実装の定義に置く。スマホアプリやタブレットの画面としての箱は判断基準の範囲外で、usecase-advisor ・ ux-advisor ・ platform-advisor の判定を待つ

判断基準では、区切られた文脈がモデルの境界であると同時に、システムを実装する単位（物理的な境界）と所有権の境界も定めるので、裏側の箱を別の宣言にすると同じ境界を2か所で持つことになる。また業務領域は事業として何をするかを説明し、どのように実現するかは説明しないので、箱をドメインの欄に足すと「何を」の欄に「どのように」が入る

案何が起きるか採否
ドメインの宣言に「箱」の欄を足す事業領域 ・ 業務領域は「何を」を説明する欄なので、そこへ「どのように」（アプリの形 ・ サービスの分け方）が混ざる。業務領域と区切られた文脈を一対一に限らないという判断基準とも合わず、ドメインの宣言が実装の変更のたびに書き換わる採らない
「箱」を新しい種類の宣言にし、区切られた文脈と別の配置の単位として定義する裏側の箱について見ると、区切られた文脈が既に持つ物理的な境界と同じものを2か所で持つ。1つの箱に複数の文脈を入れると、文脈を他と分離して開発 ・ 変更 ・ バージョン管理するという物理的な境界の性質と食い違う。アプリ（入口）としての箱を宣言にするかは判断基準の範囲外採らない
区切られた文脈の宣言に、物理的な境界（独立したサービスかプロジェクトか ・ 外部サービスか）と所有するチームを持たせる判断基準の3つの境界がそのまま宣言の欄になる。区切られた文脈は設計するもので、ソフトウェア技術者が決めるので、ここがモデリングとコーディングの境目になる採る
実装の定義に、区切られた文脈ごとの要素技術 ・ 技術方式と、文脈の中をマイクロサービスへ分けるかを置く要素技術は文脈ごとに選べ、技術方式は業務領域のカテゴリーと実装方法から決まり、マイクロサービスは区切られた文脈（最も広い）と業務領域 ・ 集約の間で決める。どれも宣言（モデル）を変えずに変えられる具体の側の判断なので、実装の定義に置ける採る
ユースケースの scope を「箱」だけにし、区切られた文脈への参照を外すユースケースがどの区切られた文脈のモデル（同じ言葉 ・ 集約）を操作するかが宣言から消える。業務領域は強く関連するユースケースの集まりなので、ユースケースから文脈 ・ 業務領域へたどれなくなる。scope に何を置くかの判定は usecase-advisor の範囲だが、文脈への参照は別の欄で残す必要がある採らない

判断の道筋

  1. A-1. 「提供する箱を決めないと、具体の材料がそろわない」は正しいか

    半分は正しい。具体（要素技術 ・ 技術方式 ・ テスト方針）を決める材料が要るのは判断基準のとおりだが、その材料は「箱」ではなく、業務領域のカテゴリーと区切られた文脈である。設計の経験則は、業務領域のカテゴリーから実装方法 ・ 技術方式 ・ テスト方針を順に選び、区切られた文脈は物理的な境界として要素技術を選ぶ単位になる。見本では SD-1 が中核で complex_rules が true なので、ドメインモデル → ポートとアダプター → ピラミッド形が、箱の形を決めなくても既に決まる。足りないのは、区切られた文脈の物理的な境界と所有者の宣言である

  2. A-2. 「ドメインに書くものは1つではない」は正しいか

    2つの意味に分けると判定が変わる。1つの企業が複数の事業領域を持つことはある（アマゾン ・ Uber 社）ので、事業領域が1つとは限らない点は正しい。しかし「ドメインの宣言に複数の箱（アプリ ・ サービス）を書く」という意味なら正しくない。業務領域は事業として何をするかを説明し、どのように実現するかは説明しない。1つのドメインの中に複数あるべきものは、業務領域と、それを実装する区切られた文脈である（見本では SD-1 ・ SD-2 と BC-1 ・ BC-2 で既に複数になっている）

  3. B-1. 箱は Cockburn の設計範囲の設計対象のシステムに当たり、いまの宣言に無いか

    設計範囲に当たるかは判断基準の範囲外（usecase-advisor の範囲）。DDD の側から言えるのは、裏側の実装の単位としての箱は、区切られた文脈の物理的な境界として判断基準に既に在り、宣言に欠けているのは BC の宣言の中の物理的な境界 ・ 所有権の境界の欄だということである

  4. B-2. 1つのプロダクトが複数の箱で提供されることがあるか

    裏側については正しい。1つの事業領域は複数の業務領域に分かれ、区切られた文脈はそれぞれ独立したサービスかプロジェクトとして実装されるので、1つのプロダクトが複数の実装の単位で提供される。スマホアプリ ・ タブレットの画面が別々の箱になるかは判断基準の範囲外（推測では、ありうる）

  5. B-3. 箱と区切られた文脈は一致するとは限らないか

    裏側の箱について、方向によって判定が分かれる。(1) 1つの区切られた文脈を、複数のマイクロサービスに分けることはできる（マイクロサービスはどれも区切られた文脈だが、逆は成立しない）。(2) 1つの文脈が複数の業務領域を含むとき、物理的な境界は1つで、内部はモジュールで分ける。(3) しかし、1つの配置の単位に複数の区切られた文脈を入れることは、文脈を他と分離して開発 ・ 変更 ・ バージョン管理するという物理的な境界と食い違う。1つにまとめたいなら、それは広く区切った1つの区切られた文脈として設計し直す。「1つの文脈を複数のアプリが使う」は判断基準の範囲外（推測では、ありうる）

  6. B-4. ユースケースの scope は区切られた文脈ではなく箱を指すべきか

    scope の意味の判定は usecase-advisor の範囲。DDD の側からは、scope を箱に変えるとしても、ユースケースが操作するモデルの区切られた文脈への参照は別の欄で残すべきである。業務領域は強く関連するユースケースの集まりで、同じデータを操作するユースケースの集まりを複数の文脈に分散させないという規則を、ユースケースから文脈への参照で検査できるからである

  7. B-5. 技術スタックと配置の単位は実装の定義に置き、箱ごとに決まるか

    「実装の定義に置く」は正しい。「箱ごとに決まる」は判断基準とずれる。要素技術は区切られた文脈ごとに選べ、実装方法 ・ 技術方式 ・ テスト方針は業務領域のカテゴリーから決まり、技術方式は文脈の中のモジュールごとに異なることもある。したがって実装の定義は、1プロダクトに1つのままでよいが、中身を区切られた文脈ごと ・ 業務領域ごとに持つ形にする。アプリ（入口）ごとの技術スタックは判断基準の範囲外

  8. C. 箱はどの宣言のどの欄に置くか。モデリングとコーディングの境目はどこか

    区切られた文脈の宣言に「物理的な境界」（独立したサービスかプロジェクトか ・ 外部サービスか）と「所有するチーム」を足し、実装の定義に文脈ごとの要素技術 ・ 技術方式 ・ マイクロサービスへの分け方を置く。境目は区切られた文脈である：事業領域 ・ 業務領域（発見する ・ 何を）と同じ言葉 ・ モデルの境界はモデリング、文脈の物理的な境界の中身（言語 ・ フレームワーク ・ 層 ・ サービスの数）はコーディング。区切られた文脈は設計するもので、モデルの境界と実装の単位の両方なので、両方の側が参照する

  9. D. 見本に当てはめると、箱は何になるか

    裏側の箱は2つで、区切られた文脈と一致する。BC-1 受注：社内で開発する1つのサービス（中核なので社内で開発し、ドメインモデル ・ ポートとアダプター）。業務知識が増えるまでは1つのまま広く保ち、マイクロサービスへ分けない。BC-2 決済：外部の決済サービスそのもの（一般）で、自社が作るのは BC-1 の側のモデル変換装置（独立したサービスにするかは実装の定義で選ぶ）。顧客のスマホアプリ ・ 店舗のタブレットの画面は、BC-1 の公開インターフェースを使う入口と見るのが自然だが、判断基準の範囲外の推測である。なお原典の事例（ライブチケット社 ・ バス・オンデマンド社）ではモバイルアプリを中核の業務領域に挙げているので、アプリが VAL-1 の差別化に関わるなら、箱としてではなく業務領域として識別し直すかを確認する

usecase-advisor（設計範囲 ・ scope）見立て1と4の「設計対象のシステム」と scope が何を指すかは、ユースケースの判断基準の範囲で、DDD の判断基準では判定できない
ux-advisor ・ platform-advisor（アプリの分け方 ・ 配置）顧客のスマホアプリと店舗のタブレットの画面を別々の箱にするか、どこに配置するかは、DDD の判断基準が触れていない

次にすること

  • BC-1 と BC-2 の宣言に、物理的な境界と所有するチームの欄を足す案を作る
  • 実装の定義の中身を、区切られた文脈ごとの節に分ける案を作る
  • ユースケースの scope の意味を usecase-advisor の回答で確定する
  • UC-1 に、操作するモデルの区切られた文脈への参照を残す欄を決める
  • 顧客のスマホアプリが VAL-1 の差別化に関わるかを確かめ、関わるなら業務領域として識別し直すかを検討する

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
ドメインの宣言（DOM-1）やサブドメインの宣言に、アプリ名 ・ サービス名 ・ 技術名の欄を足してしまうkind が domain と subdomain の宣言のキーに、実装の単位や技術を表すキー（app ・ service ・ deploy ・ stack など）が無いことを JSON Schema で検査する
実装の定義の配置の単位に、2つ以上の区切られた文脈を割り当てる実装の定義の各配置の単位が参照する BC の ID が1つだけであることを検査する（1つの BC を複数の単位へ分けるのは可）
ユースケースの scope を箱に書き換えるときに、区切られた文脈への参照を消すkind が use_case の宣言すべてで、区切られた文脈の ID への参照が1つ以上在り、その ID の context の宣言が在ることを検査する
