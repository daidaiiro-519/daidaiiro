ux-advisor の回答 ・ 判断相談

宣言の承認画面（usecase-driven-concrete/sample/viewer.html と、その図の SVG）の配色を、共通のデザイントークン（palette teal の10キー：差し色 accent 1つと警告 warn 1つ）に絞るときの割り当ては妥当か。色の意味の一貫性 ・ コントラスト ・ 色以外の手がかり ・ 認知負荷の観点で判定する

前置き

判定の前に確定させた前提と、その出所

前提内容出所
依存方向の適合判定未判定。この画面がユースケースの port を正しい向きで呼んでいるかは ux-advisor の範囲外なので判定しない。ここでは画面の内側の配色だけを判定するux-advisor の SKILL.md（入力の想定）
利用者と画面の役目利用者は宣言を読んで承認するか差し戻すかを決める人で、「色が多すぎるのが嫌い」と言っている。画面の役目は、承認の前に直すべき所（ずれ ・ 対応の欠け）を見落とさせないことである依頼文
いまの画面独自の tokens.json が中立 ・ 主（緑）・ 情報（青）・ 注意（黄土）・ 否定（赤）の5系統と部品の31トークンを持つ。viewer.html では「合格」の札が23個、失敗の札（t-fail）が11個、最低保証の札が8個、中核の札が5個あるsample/tokens.json と viewer.html を数えた結果

結論

条件付きで採る

色を accent と warn の2つに絞る方針は採る。ただし、warn を「承認の前に直すもの（ずれ ・ 対応の欠け）」だけに使うこと、システムのアクターを塗りの濃淡ではなく文字と枠線の形で分けること、warn の項目に文字の目印を必ず付けること、の3点を直してから採る。

提案の warn は「最低保証」「失敗で終わる拡張」「ずれ ・ 対応の欠け」の3つの意味を持ち、前の2つは宣言に書かれた正しい内容、最後の1つは宣言の誤りなので、同じ色が逆の判断を求めることになる。また surface と paper の比は 1.09 しかなく、塗りの有無だけではシステムのアクターを見分けられない。

比較した案

案何が起きるか採否
提案のまま（warn＝最低保証 ・ 失敗で終わる拡張 ・ ずれ ・ 対応の欠け、システム＝塗り）色の数は減る。ただし warn の項目が「直すもの」と「正しく書けている失敗の道」に混ざり、承認者は warn を見るたびに中身を読んで区別することになる。システムのアクターは塗りがほぼ見えないので、枠線の無い札として読まれる採らない

判断の道筋

  1. この配色の決定は、題材固有の理由に基づいているか

    はい。承認画面で承認者が最初に見るべきものは「直す所があるか」なので、警告の色をそこに使い、他は文字で示すという理由がある。ただし提案の warn の割り当ては、その理由から外れて「否定的に見える内容」全般に広がっている。最低保証と失敗で終わる拡張は宣言として正しく書けている内容で、直す所ではない

  2. 色の意味は1つの色に1つか（意味の一貫性）

    accent は「成功時保証 ・ 中核 ・ 強調」の3つを持つが、どれも「承認者に先に見てほしい所」という1つの意味でまとめられるので許容できる。ただし viewer.html の「合格」の札23個も t-success から accent になるので、合格の札が残る版では accent の数が増えて「強調」の意味が弱まる。warn は上のとおり2つの逆の意味を持つので分ける

  3. コントラストは足りるか

    文字色として使う組（accent ・ warn ・ muted を paper ・ surface ・ 各 soft の上に置く）は明暗とも 5:1 以上ある。面と線は低い（surface/paper 1.09、line/paper 1.40）。そのため「塗り＝システム」「line 色の実線枠＝主アクター」は、目で見分けられない恐れがある。数値の基準（何対1以上が必要か）は判断基準の範囲外で、推測である

  4. 色以外の手がかり（形 ・ 文字）があるか

    元に戻る拡張は「4へ戻る」のようなラベルで示すので文字の手がかりがある。中核の札も「中核」の文字がある。一方で accent と warn は明るさの比が 1.18（暗 1.03）で、色相だけで分かれている。warn の項目には「ずれ」「欠け」のような文字の札を必ず付け、色が見分けられなくても読めるようにする。アクターは「主」「支援」「システム」の文字の札に、枠線の形（実線 ・ 破線 ・ 二重線）を組にする

  5. 認知負荷は下がるか

    下がる。5系統31トークンが2色＋中立になり、承認者が覚える色の意味は「accent＝先に見る所」「warn＝直す所」の2つになる。ただし図（SVG）と画面のどちらかが古い色を残すと、同じ意味が2通りの色で出るので、両方を同じ10キーへ同時に移す

  6. 品質下限（レスポンシブ ・ フォーカス状態 ・ reduced-motion）を満たしているか

    レスポンシブは 760px の切り替えがある。reduced-motion は、transition ・ animation が無いので該当しない。フォーカス状態は :focus-visible で accent の outline を出しているが、.ref と .help は outline:none にして枠線の色だけを accent に変えている。accent を「強調」にも使うので、この2つは色の変化だけでフォーカスを示すことになる。outline を残すほうが確実である

注意

アンチパターンリスク代替案
方向性と作り込み度が一致しない画面だけ10キーに移し、sample/tokens.json の31トークンや図（SVG）の5系統の色が残ると、最小限の方向性を選びながら別の色が混ざる中途半端な仕上がりになるviewer.html と figures の SVG を同じ10キーへ同時に移し、sample/tokens.json の component 層（actor-* ・ ending-* ・ category-* ・ figure-*）を外す
フォーカス状態を見た目のためだけに消す（outline: none等）.ref と .help は outline:none にして、枠線の色を accent に変えるだけでフォーカスを示している。accent が「強調」にも使われるので、どこにフォーカスがあるかが色の違いだけになる（推測）.ref と .help も他と同じ outline:2px solid accent を残す
（推測）同じ警告の色に逆の意味を持たせる最低保証 ・ 失敗で終わる拡張は正しく書けた内容、ずれ ・ 対応の欠けは直す所である。両方が warn だと、承認者は warn を見ても直す必要があるかを判断できず、ずれの見落としにつながる（推測）warn は「ずれ」「対応の欠け」だけに使う。最低保証は成功時保証と同じ形の札にして文字で分け、失敗で終わる拡張は「失敗で終わる」の文字の札で示す
（推測）塗りの濃淡だけでアクターを分けるsurface と paper の比は明 1.09 ・ 暗 1.12 で、塗りの有無がほとんど見えない。line と paper も 1.40 で枠線も弱いので、3種のアクターの区別が目で付かない（推測）アクターの札に「主」「支援」「システム」の文字を入れ、枠線は muted 色にして、主アクター＝実線 ・ 支援アクター＝破線 ・ システム＝二重線で分ける。塗りは見分けの手がかりにしない
