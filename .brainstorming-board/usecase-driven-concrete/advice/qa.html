結論

採る

宣言の単位は「テスト条件」とし、表示のラベルと分けた不変の ID と内容の指紋を道具が振り、テスト実装は（テスト条件 ID ・ 指紋 ・ テストの識別子 ・ テストレベル ・ 結果）の組を1件ずつ報告し、道具は欠け ・ 余り ・ 不合格 ・ 古い ・ 未実行 ・ レベル違いの6種を突き合わせ、すべてのテスト条件が「求めるレベルで、最新の指紋のまま合格」になったときを終了基準とする。

トレーサビリティは「テストベースの各要素」と「テスト結果」との対応関係であり、構成管理は構成アイテムを一意に識別し変更を追跡することを求めるので、突き合わせの鍵は位置で変わらない ID と版を表す指紋の2つが要る。終了基準は「計画したテストの実行」と「不合格になったテストケースの数」で測るので、skip と古い合格は合格に数えない。

設計の手順

  1. 問い1：宣言の単位を「テスト条件」と定め、テストケースと分ける

    JSTQB では、テスト分析がテストベースから「テスト条件の定義」をし（何をテストするか）、テスト設計が「テスト条件から、テストケース」を作る（どのようにテストするか）。宣言はテストベース、材料の表の単位はテスト条件に当たり、テストケースはテスト実装の側が作る。したがって 1単位＝テストケース1件ではなく、1単位＝テスト条件1件とし、1つのテスト条件を複数のテストケースで確かめる（境界値ごとに1件など）のは正常とする。逆に1件のテストで複数のテスト条件を確かめる場合は、報告をテスト条件ごとに1件ずつ分けて出させる（同じテストの識別子が複数の行に出てよい）。ただしコンポーネントテストでは、1件で複数の条件を確かめる形は Eager Test ・ Assertion Roulette になるので、道具は警告を出す。材料の表の過不足は次のとおり：(a) 「コマンドの受け付ける例」は例ごとに分ける（AGG-1.CMD-1 はコマンドそのものと紛れるので AGG-1.CMD-1.OK-1 のように例の ID を付ける）。業務イベントはこの条件の確認の一部に含め、別の単位にしない。(b) 集約の structure に状態があれば、有効な遷移を単位に足す候補になる（状態遷移テストの有効遷移カバレッジ。推測：宣言に遷移が無ければ不要）。(c) 品質の要求は手順の位置でなく、手順の不変 ID に付ける。(d) サーガの手順と補償は、サーガを実装側へ移すなら宣言のテスト条件から外す（問い6）。(e) ユースケースの variations は、宣言の側でテスト条件にするかを決めていないので、いまは単位にしない（推測）。

  2. 問い2：表示のラベルと、突き合わせに使う不変の ID を分ける

    2a のような位置のラベルは表示専用の欄（label）に置き、道具が描画のたびに位置から振り直す。突き合わせには、要素を宣言に足した時点で道具が振る不変の ID を使う。形は「宣言の ID.要素の種類-連番」（例：UC-1.EXT-1、AGG-1.INV-2、AGG-1.CMD-1.PRE-1、AGG-1.CMD-1.OK-1、UC-1.STEP-4、DOM-1.QR-1）とする。連番は宣言の中で増える一方にし、消した ID は退役の一覧に残して再利用しない。主成功シナリオは1つしかないので UC-1.M のままでよい。ID を位置から導くと、手順を1つ足しただけで、関係の無いテストの鍵が変わって突き合わせが壊れる。これは Fragile Test の Interface Sensitivity（SUT のインタフェースのうち、テストが使っている部分が変わって失敗する）と同じ形であり、構成管理の「一意に識別」にも反する。ID の形（区切りの記号 ・ 種類の略号）は推測であり、決めるのは道具の側である。

  3. 問い3：テスト条件ごとに内容の指紋を振り、テストの報告に載せさせる

    道具は、テスト条件ごとに「期待する結果を決める部分」だけから指紋を作る（例：拡張なら条件 ・ 処理の手順 ・ 終わり方 ・ 成り立つ最低保証、不変条件なら条件の構造 ・ 違反する例）。表示のラベル、道具が生成する文、並び順は指紋に入れない。テストは、書いた時点の指紋をテストコードの中に定数や注釈として持ち、報告に載せる。道具は報告の指紋と現在の指紋が違えば「古い」と判定する。これは構成管理のベースライン（承認された宣言の版）とテストを関連付けることに当たり、指紋が変わった条件の一覧はそのまま影響度分析の結果になる。古いと判定した条件では、テストを直して指紋を更新するのが確認テストに、変わらなかった条件のテストを流し続けるのがリグレッションテストに当たる。報告の全体には、宣言の版（git のコミット）も任意で載せ、以前の結果を再現できるようにする。指紋に入れる範囲が広すぎると、関係の無い変更で多くの条件が古くなり High Test Maintenance Cost を招き、狭すぎると古いテストを見逃す。範囲の決め方は推測であり、試して直す。

  4. 問い4：報告は「テスト条件とテストの組」を1件とし、必須の欄を決める

    1件の必須の欄は condition（テスト条件の不変 ID）・ fingerprint（テストが書かれた時点の指紋）・ test（テストの識別子。ファイルとテスト名など、スタックごとに一意なもの）・ level（component ・ component-integration ・ system ・ system-integration ・ acceptance のどれか）・ result（pass ・ fail ・ skip）の5つ。skip のときは reason を必須にする。任意の欄は case（同じ条件を確かめるテストケースの区別。境界値の 10 ・ 11 など）・ message（失敗の要約）・ duration。報告の全体には schema（報告の形の版）・ spec_revision（任意）・ producer（スタックと実行の識別子）を持たせる。同じ（condition ・ test ・ case）の組が2回出たら報告の誤りとする。報告の形は concrete が JSON Schema で持ち、報告を作る手段はスタックごとにコーディングの側が持つ（ACDR 0093 の方向は変えない）。

  5. 問い5：ドリフトを6種に分け、不合格と警告を決める

    テスト条件ごとに状態を1つ決める。(1) 欠け：仕様にあり、報告に1件も無い → 不合格。(2) 余り：報告の condition が現在の宣言に無い。退役の一覧にあれば「取り残し」、どこにも無ければ「不明な ID」として、どちらも不合格（ID の書き間違いや作り話を通さないため）。(3) 不合格：fail が1件でもある → 不合格。(4) 古い：指紋が現在と違う → pass でも不合格。(5) 未実行：その条件の記録が skip だけ → 不合格（skip を合格に数えない）。pass と skip が混ざるときは、求めるレベルの pass があれば合格とし、skip は警告にする。(6) レベル違い：求めるレベルの記録が無く、別のレベルの記録だけがある → 不合格。求めるレベルの記録に加えて別のレベルの記録もある場合は警告にとどめる（テストレベルの重複を避ける考えに照らした注意）。このほか、コンポーネントテストで1件のテストが複数の条件を報告するものは警告（Eager Test の疑い）。報告そのものがスキーマに合わない、同じ組が重なる、レベルの値が不明、は報告の誤りとして全体を不合格にする。

  6. 問い6：テストレベルは「宣言の種類」と「その単位を実装した業務ロジックの実装方法」の組で決め、ID はレベルから切り離す

    テストレベルはテスト対象で区別するので、同じテスト条件でも、それを実装した部品が変わればレベルが変わる。そこで条件の ID はレベルに依存させず、求めるレベルは実装の定義（区切られた文脈やサブドメインごとの実装方法）と宣言の種類の対応表から道具が決める。対応表（推測。上流で承認を得る）：ユースケースのシナリオ → system（駆動する側から動かし、駆動される側は偽物。システムテストではサブシステムのシミュレーションも使用できる）。集約の条件 → ドメインモデルなら component、アクティブレコードなら component-integration（永続化と一体なので）、トランザクションスクリプトなら集約に当たる部品が無いので、条件を実装したスクリプトを駆動する側の入口から動かす system。値オブジェクト → component。ドメインサービス → component。公開された言葉 → 文脈が別のシステムなら system-integration、同じ配置単位なら component-integration。品質の要求 → system（非機能テスト。付いている手順のシナリオのテストケースから導く）。acceptance は道具が求めない（受け入れテストは想定ユーザーが行うのが理想で、宣言の承認と UAT の側で扱う）。前に出た指摘1：上の対応表で答える。同じ条件 ID を、実装方法に応じたレベルのテストへ写す。前に出た指摘2：模擬を使わないなら、入力は値と、テストの中で直接作った集約 ・ 値オブジェクトに限る（リポジトリなどのポートを入力にしない）。ポートを要するなら、それはドメインサービスでなくアプリケーション側の処理である疑いがある（推測。ddd-advisor の判断）。前に出た指摘3：宣言が持つのは拡張の「何が成り立つか」（最低保証）だけとし、補償の「どう戻すか」はサーガとして実装の定義の側に置く。宣言のテスト条件は UC-1.EXT-2 の最低保証で確かめ、サーガの補償の試験は実装の定義から導くテストに移す。こうすれば二重記述にならない（推測。usecase-advisor の判断）。

  7. 問い7：終了基準を、条件ごとの状態とテストレベルごとの集計で決める

    テスト条件は、次をすべて満たしたときに「合格」とする：求めるレベルの記録が1件以上ある ・ その条件の記録に fail が無い ・ すべての記録の指紋が現在の指紋と同じ ・ 求めるレベルに pass が1件以上ある。宣言の集合の終了基準は、すべてのテスト条件が合格 ・ 余りが0件 ・ 報告の誤りが0件、とする。集計はテストレベルごとに出す（開始基準と終了基準はテストレベルごとに定義するため）。時間や予算の都合で一部を残すときは、残すテスト条件と理由を宣言の側に「免除」として書き、承認（PR）を経たものだけを道具が「免除」と数える。免除は合格とは別に数え、テスト完了レポートの残存リスクとして出す。この終了基準は「宣言から導くテスト」だけのものであり、実装の定義から導く3種類（アダプターの契約試験など）の完了はこの道具では判定しない。

  8. 問い8：UC-1 と AGG-1 で、単位の一覧 ・ 報告 ・ 判定を確かめる

    下の「コードの例」に、テスト条件の一覧、報告の JSON、ドリフトの判定の3つを置く。判定の例では、6種のうち5種と警告1件が出る形にした。

注意

アンチパターンリスク代替案
位置のラベル（2a）を突き合わせの鍵にする手順を1つ足すだけで、関係の無いテストが欠けと余りに同時に出る。Fragile Test の Interface Sensitivity と同じ形で、テストの保守が増える表示のラベルと不変の ID を別の欄にし、ID は道具が要素を足した時点で振り、再利用しない
skip や古い指紋の pass を合格に数える終了基準の「計画したテストの実行」を満たしていないのに、テストが揃ったと判定するskip だけの条件は未実行、指紋が違う条件は古いとして、どちらも不合格に数える
1件のテストで多くのテスト条件を確かめ、報告を1行にまとめるEager Test ・ Assertion Roulette になり、どの条件が落ちたかを道具も人も特定できない報告は（条件 ・ テスト ・ case）ごとに1件にし、コンポーネントテストは Single Condition Tests に分ける
（推測）指紋に宣言の全体や表示の文を入れる関係の無い変更で多くの条件が古くなり、指紋の付け直しだけの作業が増えて High Test Maintenance Cost になる。付け直しが習慣になると、中身を見ずに指紋だけ書き換えるようになる指紋はテスト条件ごとに、期待する結果を決める欄だけから作る。範囲は宣言の種類ごとに道具の側で決め、試して直す
（推測）テスト条件の ID に、テストレベルや実装方法を埋め込む実装方法をドメインモデルからアクティブレコードへ変えただけで、すべての ID が変わり、トレーサビリティが切れるID は宣言の要素だけで決め、求めるレベルは実装の定義との対応表から道具が別に出す

差し戻し

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
usecase-advisor ・ 拡張のラベルを手順の位置から導く判断（前に出た指摘4）表示のラベルとしては問題ないが、テストの突き合わせの鍵にも使うと、手順の追加で関係の無いテストが壊れる。ラベルとは別に不変の ID を宣言に持たせてよいかを確かめる必要がある
ボード usecase-modeling-coding 論点7 ・ 宣言から導くテスト7種類にサーガを含める判断サーガを実装側へ移すなら、サーガの手順と補償の試験は「実装の定義から導くテスト」に移るはずで、宣言から導くのは拡張の最低保証の試験だけになる。7種類と3種類の分け方を見直す必要がある疑い
ボード usecase-modeling-coding 論点7 ・ 集約の条件の試験を「集約を直接作って操作する単体テスト」とした判断ドメインモデルのときだけ成り立つ。アクティブレコード ・ トランザクションスクリプトでは同じ条件 ID を別のレベルへ写す規則（実装方法との対応表）を足す必要がある
ddd-advisor ・ ドメインサービスの試験で模擬を使わない判断（前に出た指摘2）入力を値と直接作った集約に限るなら、ポートを要する処理はドメインサービスでない疑いがある。どこまでをドメインサービスに許すかは DDD の判断である
ACDR 0093 ・ 報告を results[] に {id, result} とした決定指紋 ・ テストの識別子 ・ レベル ・ skip の理由が無いので、古いテスト ・ レベル違い ・ 1件が複数条件を確かめる場合を判定できない。報告の形を広げる改訂が要る

次にすること

  • 宣言のスキーマの各要素に不変の id 欄を足し、2a などのラベルを表示専用の欄へ分ける。
  • 宣言の種類ごとに、指紋に入れる欄の一覧を決める。
  • 報告の JSON Schema を、必須5欄と skip の理由を持つ形へ改める。
  • 実装方法と宣言の種類からテストレベルを決める対応表を、実装の定義の側に書く。
  • 論点7 のテスト7種類からサーガを外すかを、ボード usecase-modeling-coding で決める。
  • UC-1 と AGG-1 の実物の宣言で、テスト条件の一覧と判定を試しに出して、指紋の範囲を確かめる。

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI がテストを直さずに、報告や定数の指紋だけを新しい値へ書き換えて「古い」を消す指紋の定数が変わったコミットで、同じテストの本体（準備 ・ 確認の行）に差分が無ければ、道具か CI が警告を出す。道具は旧と新の指紋に対応する宣言の差分を出し、レビューで照らす
AI が報告の condition を、表示のラベル（UC-1.2a）や、存在しない ID で書く道具が condition を現在の ID ・ 退役した ID の一覧と照合し、どちらにも無ければ「不明な ID」で不合格にする
AI が実装の難しいテストを skip にして、終了を宣言するskip だけの条件を未実行として不合格に数え、skip の reason を必須にする。免除は承認済みの宣言の欄にあるものだけを数える
AI がテストレベルを実際のテスト対象と違う値で報告する（system の試験を component と書く）推測：テストの識別子の置き場所（フォルダ）とレベルの対応を実装の定義に書き、報告の level とファイルの場所が合わなければ警告を出す
AI が1件のテストで条件を詰め込み、報告だけを条件ごとに分けるコンポーネントテストで、同じ test の識別子が2つ以上の condition に出たら警告を出す
