# 相談の材料：既存のプロダクトを宣言へ移した試しで、書けなかった4つ

## 前提（決着済み）
- 宣言は構造化データ。意味はすべて欄に持ち、文 ・ 例 ・ 境界値は道具が組む。要求のユースケースは内部に触れず、条件は用語集の語の並び（例 TERM-13.TERM-2）で書く。
- ユースケースの拡張は condition_kind（妥当性確認の失敗 ・ 業務ルールの拒否 ・ 支援アクターの失敗）と ending（「手順Nへ戻る」を表す STEP-N か「失敗」）を持つ。ステップは variations（varies と values）を持てる。
- 条件の形：{target, op(eq ・ ne ・ ge ・ le ・ empty ・ not_empty), value, agg(count ・ sum), if}。値オブジェクトの成分は invariants に同じ形の条件を持つ。
- 保証は success（成功時保証）と minimal（最低保証）に分け、それぞれ条件を持つ。

## 試した題材
fact-check の「原文を取得する」。書き手が出どころ（URL）を渡すと、システムは情報源のサーバーから原文を取得して保存し、取得の記録（取得した日 ・ sha256 ・ 行数）を残す。

## 書けなかった4つと、オーケストレーターの見立て
1. 試す順番 ── まず「出どころに .md を付けた先」を取り、取れなければ出どころそのものを取る。試しでは variations の値の並びで持ったので、順番がテスト条件にならなかった。
   見立て：主成功シナリオは「.md を付けた先から取得する」と書き、拡張「3a 情報源が .md を付けた先を返さない（支援アクターの失敗）：システムは出どころそのものから取得する。手順4へ進む」と書く。ending に「手順Nへ進む」（戻るのではなく、先へ進む）を足す。
2. 条件の付いた変化 ── 出どころが .md ・ .txt ・ .json で終わるときは、.md を付けた先を試さない。
   見立て：拡張に condition_kind「条件による分岐」を足し、条件の形で書く（{target: 出どころ, op: ends_with, value: [".md", ".txt", ".json"]}）。ending は「手順Nへ進む」。op に ends_with を足す。
3. 「してはならない」という品質 ── 取得した原文を変換しない（記法を剥がさない）。試しでは書けずに未決定事項へ置いた。
   見立て：欄は足さない。成功時保証「受け取ったまま残る」を、条件 {target: 保存した原文, op: eq, value: 受け取った中身} で書く。
4. 文字数の制限 ── 保存する名前は120字まで。試しでは数の大きさと区別できず note で補った。
   見立て：条件の agg に length（文字数）を足す。{target: CMP-1, agg: length, op: le, value: 120}。

## 聞きたいこと
A. 見立て1〜4は、ユースケースの書き方（拡張 ・ 変化 ・ 保証）と値オブジェクトの不変条件の概念の意味を変えていないか。置き場所の誤り ・ 不足はどれか。
B. 1 と 2 で、拡張を「失敗」ではない分岐（先へ進む）にも使うのは、拡張の概念に沿うか。変化（variations）の側に置くべきか。
C. 3 で「してはならない」を成功時保証の条件として書くのは、保証の概念に沿うか。ほかの要求（品質）の側に置くべきか。

判断基準からの引用を根拠にし、範囲外は「推測」と書く。新しい語を作らず、原典の語をそのまま使う。比喩を使わない。回答の文に書名 ・ 章 ・ 頁を書かない（根拠の出どころの欄に置く）。
