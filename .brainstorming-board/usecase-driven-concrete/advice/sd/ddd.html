ddd-advisor の回答 ・ 判断相談

中核以外の業務領域（補完 ・ 一般）を、プロダクトの仕様（ドメインの宣言）としてどう宣言するか。利用者の考え（A）、オーケストレーターの案1〜3（B）、一般を外部サービスで満たすときに書くこと ・ 書かないこと（C）、補完の宣言の重さ（D）、見本に当てはめた値（E）を、DDD の側から判定する

前置き

判定の前に確定させた前提と、その出所

前提内容出所
語判断基準は「業務領域」と書き、原典はサブドメインとも呼ぶ。この回答では宣言の名前に合わせて「サブドメイン」と書き、判断基準の引用は原文のままにするsubdomain の定義
宣言の最上位ドメインは企業の事業全体ではなく、作りたいプロダクトの宣言である。判断基準の「事業領域」とは範囲が違う相談の材料（前提）
宣言する区切られた文脈このプロダクトが持つものだけ。他のチーム ・ 外部のサービスの文脈は宣言せず、使う側の文脈の文脈の地図に、連係方法と変換（相手の項目 → こちらの語）か、そのまま使う語だけを書く相談の材料（前提）
ユースケースの書き方手順が外部の操作を指す書き方 ・ 拡張が失敗の種類を指す書き方は usecase-advisor の範囲である。この回答は、その指し先を文脈の地図の側にどう置くかだけを扱う依頼の範囲
宣言の欄の形宣言の種類と欄の名前は、見本（decls/*.json）にある形を前提にする。欄の名前の提案は「推測」として示す判断基準の範囲外
見本に補完を足すかの前提受け渡し以外の補完の候補（経理の突き合わせ）がプロダクトの範囲に入るかは、利用者が決めていない。未判定判断基準の範囲外

結論

条件付きで採る

利用者の考えは正しく、補完 ・ 一般もドメインの宣言で「どう実現するか」をまとめて書くべきだが、まとめ方は新しい欄を手で書くのではなく、サブドメイン ・ 区切られた文脈 ・ 文脈の地図の既存の欄から道具が組む表にし、宣言の重さはカテゴリーではなく業務ロジックから導いた実装方法で変える。

判断基準は「どの業務領域も事業には欠かせない」とし、カテゴリーごとに開発の方針（社内で開発 ・ 外部に委託 ・ 製品の購入 ・ 外部サービスの利用）と実装方法を選ぶとする一方、「業務領域は事業として何をするかを説明し、それをどのように実現するかは説明しない」ので、実現の仕方は区切られた文脈と文脈の地図の側に置き、ドメインはそれを集めて見せるだけにするのが判断基準の分け方に合う。実装方法は「業務領域のカテゴリーから、業務ロジックの実装方法、技術方式、テスト方針を順に選択する」流れで決まり、補完がドメインモデルを要する不一致は再検討の機会とされるので、宣言の重さは実装方法に合わせるほうが、カテゴリーの判断の誤りも検出できる。

比較した案

案何が起きるか採否
A：利用者の考え ── 補完 ・ 一般も、プロダクトの中でどう組み立てるかを仕様として書くどの業務領域も事業に欠かせないという判断基準に合う。今の見本は一般（SD-2）がどの外部サービスで満たされるかを、サブドメインの側から辿れない（BC-1 の文脈の地図の行に SD-2 への参照が無い）。この欠けを埋めると、カテゴリーごとの開発の方針が宣言から読める採る
案1：ドメインに「サブドメインの組み立て」を、新しい手書きの欄として置く実現の仕方 ・ どこで ・ 実装方法は、サブドメインの classification と business_logic、区切られた文脈の header.subdomains、文脈の地図の行から導ける。手で書けば同じ事実が2か所に在り、ずれる採らない
案1の修正：組み立ては道具が組む表にし、手で足すのは「文脈の地図の行 → 満たすサブドメイン」の参照と、実現の仕方の値「外部に委託する」だけにするサブドメイン → 文脈 ・ 外部サービス ・ 実装方法 ・ ユースケースの対応が、1か所の事実から組まれる。判断基準の補完の実装「社内で作るか、外部に委託する」と、一般の「製品を購入するか、外部サービスを利用する」の4つの値がそろう採る
案2：カテゴリーで宣言の重さを決める（中核＝集約まで ・ 補完＝文脈とユースケースと操作の事前 ・ 事後条件 ・ 一般＝連係の宣言だけ）多くの場合は正しい重さになるが、補完がドメインモデルを要する（または中核がトランザクションスクリプトで足りる）不一致を、宣言の形が隠す。また「補完は区切られた文脈を書く」とすると、補完を中核の文脈に含める判断基準の選択肢（中核の文脈には頻繁にやりとりする業務領域も含める）が書けない採らない
案2の修正：重さは実装方法で決め、カテゴリーとの不一致は検査で出す（ドメインモデル＝集約まで ・ アクティブレコード＝公開する操作の事前 ・ 事後条件とデータ構造 ・ トランザクションスクリプト＝公開する操作の事前 ・ 事後条件 ・ 外部サービスの一般＝使う側の文脈の地図の行に連係を書く）。補完の所属は、既存の文脈か自分の文脈かを選べるようにする判断基準の「カテゴリー → 実装方法 → 技術方式 → テスト方針」の流れと、「実装方法からカテゴリーを検証する」手順の両方が宣言に乗る採る
案3：見本に補完のサブドメイン「受け渡し」を出す受け渡しは注文の集約（AGG-1）のコマンド「渡す」で、同じデータを操作する。出しても所属は BC-1 のまま、実装は AGG-1 のコマンドのままで、補完の宣言の形（集約を書かない）を見せる見本にならない。補完の形に合わせて集約から外すと、1つの集約を分ける形になる採らない
案3の代わり：受け渡しは受注（SD-1）に残す。補完の見本が要るなら、自分のアクターとデータを持つもの（推測：経理が注文と入金を突き合わせる）を候補にし、範囲に入るかを利用者に確かめる補完の宣言の重さを、中核の集約と混ぜずに見せられる。候補が範囲に入るかは未判定採る

判断の道筋

  1. A：補完 ・ 一般も宣言で扱うべきか

    扱う。判断基準は、どの業務領域も事業に欠かせないとし、カテゴリーの特徴を使ってそれぞれを効率的に実装するとする。扱わないと、一般がどの外部サービスで満たされるか、補完をどこで誰が作るかが宣言から読めない

  2. A：「どう組み立てるか」をサブドメインの宣言そのものに書くか

    書かない。判断基準は、業務領域は何をするかを説明し、どのように実現するかは説明しないとし、業務領域は発見するもの、区切られた文脈は設計するものと分ける。実現の仕方は区切られた文脈と文脈の地図に置き、ドメインの組み立ての表はそこから組む

  3. B：案1の欄のうち、手で書く必要があるのはどれか

    カテゴリーと調達（sourcing）はサブドメインに既に在る。どこで（文脈）は区切られた文脈の header.subdomains から逆に引ける。実装方法は business_logic の3つの性質から設計の経験則の問いで導ける。足りないのは、外部サービスの行がどのサブドメインを満たすかの参照と、調達の値「外部に委託する」の2つだけである

  4. B：宣言の重さは、カテゴリーと実装方法のどちらで決めるか

    実装方法で決める。集約 ・ 値オブジェクト ・ ドメインサービスはドメインモデルの部品で、トランザクションスクリプトとアクティブレコードには無い。カテゴリーで決めると、補完がドメインモデルを要する不一致が宣言の形に隠れる。不一致は検査で出し、判断基準の表に沿って「要件を単純にする」か「競争優位の源泉になりうる」かを利用者に問う

  5. C：一般を外部サービスで満たすとき、どこに何を書くか

    サブドメインにはカテゴリー ・ 調達 ・ 分類の根拠だけを書く。使う側の文脈（BC-1）の文脈の地図の行に、連係方法とその理由、使う操作（こちらの語）、渡すもの ・ 受け取るもの（こちらの語）、変換（相手の項目 → こちらの語）、失敗の種類（こちらの語）を書く。モデル変換装置の目的は、自分の文脈に関係しない外部の概念を除外することなので、相手のモデルは書かない

  6. C：一般の business_logic の3つの性質は何を表すか

    外部サービスで満たす一般では、自分たちが書く業務ロジックは連係の部分だけである。判断基準は、外部サービスを導入した一般との連係にはトランザクションスクリプトかアクティブレコードが適するとする。一般そのものは「一般は単純ではない」ので、SD-2 の complex_rules: false を一般そのものの性質として読むと判断基準と食い違う。連係の性質であると欄の意味を決める

  7. D：補完は自分の区切られた文脈を持つか

    どちらもありうる。中核を含む文脈には頻繁にやりとりする業務領域も含め、そのカテゴリーは問わない。そのときは文脈の内部に業務領域ごとの論理的な境界（名前空間 ・ モジュール ・ パッケージ）を置く。別のチームが作る ・ 別のライフサイクル ・ 外部に委託するときは、自分の文脈（所有権の境界）を宣言する

  8. E：受け渡しを補完として見本に出すか

    出さない。受け渡しは注文の集約のコマンドで、同じデータを操作するユースケースの集まりを複数の文脈に分散させないという規則から BC-1 に残る。サブドメインだけ分けても、補完の宣言の形は見本に現れない

設計の手順

  1. サブドメインの組み立ての表を、道具が組む列で定める

    列は サブドメイン ・ カテゴリー ・ 調達 ・ どこで（自分の文脈 または 使う側の文脈の地図の行）・ 実装方法（導く）・ 使うユースケース。値はすべて既存の欄から組み、ドメインの宣言には手で書かない

  2. 調達の値を4つにそろえる

    社内で開発する ・ 外部に委託する ・ 製品を購入する（パッケージ製品 ・ オープンソース）・ 外部サービスを利用する。判断基準の3つのカテゴリーの表の「実装」の列にある値である

  3. 外部サービスの行に、満たすサブドメインを書く

    BC-1 の文脈の地図の行のうち、プロダクトのサブドメインを満たす行だけに書く。メニューのサービス ・ 顧客のサービスは範囲の外（scope.out のメニューの管理など）の相手で、プロダクトのサブドメインを満たさないので書かない

  4. 実装方法を、business_logic から設計の経験則の順で導く

    1 経緯を追う必要 → イベント履歴式ドメインモデル、2 業務ルールが複雑 → ドメインモデル、3 データ構造が複雑 → アクティブレコード、4 どれにも該当しない → トランザクションスクリプト。外部サービスの一般では、導いた実装方法は連係の部分に当てる

  5. 宣言の重さを実装方法で決め、カテゴリーとの不一致を検査にする

    中核なのにトランザクションスクリプト ・ アクティブレコード、補完なのにドメインモデルを、宣言の誤りではなく再検討の対象として出す

  6. 一般の連係の行に、使う側から見た約束を書く

    連係方法とその理由 ・ 使う操作 ・ 渡すもの ・ 受け取るもの ・ 変換 ・ 失敗の種類を、こちらの同じ言葉で書く。ユースケースの手順と拡張は、この行の操作と失敗の種類を指す（指し方は usecase-advisor の範囲）

判断基準引用

subdomainカテゴリー：補完 ・ 実装：社内で作るか、外部に委託する
subdomain業務領域は事業として何をするかを説明し、それをどのように実現するかは説明しない
subdomain一般は単純ではない。中核と同じく複雑なことが多いが、競争優位を生まないので、実績のある製品やサービスを使用する
subdomain条件：補完と一般の業務領域 ・ 対応：設計判断に影響する発見がなくなった時点で、分割をやめる ・ 理由：分割後のカテゴリーがすべて分割前と同じなら、その分割は不要である
subdomain条件：細分化をどこで止めるか迷うとき ・ 対応：同じアクター ・ 同じ外部システム ・ 密接に関係するデータを処理するユースケースの集まりで区切る ・ 理由：この定義を使うと停止する位置を判断しやすく、この定義による分割が境界として最も正確である

bounded-context対応：中核の業務領域を含む文脈には、それと頻繁にやりとりする業務領域も含める ・ 理由：中核の業務領域は変化しやすく不確実である。頻繁にやりとりする領域を同じ文脈に含めると、初期の予測しにくい変更に対応しやすい
bounded-context対応：同じデータを操作するユースケースの集まりを、複数の文脈に分散させない ・ 理由：誤った分割では、1つの変更要求のために複数の文脈を同時に修正し、同時に配置する調整が必要になる
bounded-context物理的な境界は1つだが、内部には業務領域ごとの論理的な境界（名前空間 ・ モジュール ・ パッケージ）が存在する
bounded-context区切り方：自殺行為となった境界 ・ 内容と結果：顧客管理の開発で、1つの集約を2つの区切られた文脈に分割した。絶対にしてはいけない
design-heuristics業務の複雑さと業務領域のカテゴリーは強く関係する。業務ルールが単純な補完的な業務領域と、パッケージ製品や外部サービスを導入した一般的な業務領域との連係には、トランザクションスクリプトかアクティブレコードが適する。業務ルールが複雑な中核の業務領域には、ドメインモデルかイベント履歴式ドメインモデルが適する。
design-heuristics判定方法は経験則であり、厳格なルールではない。どのルールにも例外があり、経験則は100%を保証しない。判定方法の一部を変更してもよく、独自の判定方法を作成してもよい
subdomain中核と判断したのにアクティブレコードやトランザクションスクリプトで足りる場合も、補完と判断したのにドメインモデルが必要な場合も、業務領域と事業活動についての判断を再検討する機会である。
anticorruption-layerモデルを作る観点では、変換によって、下流は自分の文脈に関係しない外部の概念を除外できる。その結果、下流の同じ言葉とモデルは単純で理解しやすくなる。
anticorruption-layer場合：下流の文脈が中核の業務領域を含む ・ 理由：中核の業務領域のモデル作りには細心の注意を必要とする。供給側のモデルの影響を受けると、中核の課題を表すモデルが歪む可能性がある
conformist条件：上流の契約が業界標準で、安定したモデルである ・ 対応：下流が上流のモデルを受け入れ、従属を選択できる
transaction-script対応：外部システムと連係するアダプターとして使用する ・ 理由：一般的な業務領域に導入した外部サービスとの連係や、モデル変換装置の一部として役立つ
transaction-script対応：補完的な業務領域に使用する ・ 理由：補完的な業務領域は、定義上、業務ロジックが単純である
transaction-scriptトランザクションスクリプト：システムが公開する業務処理（トランザクション）ごとに、データを参照 ・ 更新する手続きの一部として業務ロジックを記述する実装方法。公開された操作の集まりが、内部の手続きを隠蔽するカプセル化の境界になる。
transaction-script例：暗黙的な分散トランザクション ・ 実装：訪問回数を1増加させる UPDATE を実行し、成否を呼び出し元へ通知する ・ 発生する不整合：結果を通知する通信が失敗すると、呼び出し元が再実行し、訪問回数が2回増加する ・ 対処：この例に限れば、操作をべき等にするか、楽観的な排他制御を使用する（次の表）
active-record対応：補完的な業務領域か一般との連係で、データ構造が複雑な場合に選択する ・ 理由：データ構造が単純ならトランザクションスクリプトを、中核の業務領域ならドメインモデルかイベント履歴式ドメインモデルを選択する
separate-ways対応：互いに独立を選択するのは、補完的な業務領域か一般的な業務領域に限定する ・ 理由：中核の業務領域は、どちらか一方のチームが開発すべきである

注意

アンチパターンリスク代替案
組み立ての表を手で書く（同じ事実を2か所に置く）サブドメインの classification ・ 区切られた文脈の header.subdomains ・ 文脈の地図の行と、ドメインの組み立ての表がずれ、どちらが正しいかを毎回確かめることになる（推測）組み立ての表は道具が既存の欄から組む表示にし、手で足すのは文脈の地図の行の「満たすサブドメイン」の参照だけにする
一般の business_logic を、一般そのものの複雑さとして書く判断基準は「一般は単純ではない」とする。SD-2 の3つの性質が false のまま一般そのものの性質と読まれると、カテゴリーの分類（一般 ＝ 複雑）と食い違い、実装方法からカテゴリーを検証する手順で補完と判定される（推測）外部サービスで満たす一般では、business_logic は自分たちが書く連係の部分の性質であると欄の意味を決め、導いた実装方法を連係に当てる
補完の形に合わせて、中核の集約のコマンドを別のサブドメインへ切り出す受け渡し（AGG-1 のコマンド「渡す」）を補完として集約から外すと、同じデータを操作するユースケースが分かれ、判断基準が「絶対にしてはいけない」とする1つの集約の分割に近づく受け渡しは受注に残す。補完の見本は、自分のアクターとデータを持つものから選ぶ
外部サービスの相手のモデルを、使う側の同じ言葉へ持ち込む中核を含む BC-1 のモデルが、供給側のモデルの影響で歪むモデル変換装置で、相手の項目をこちらの語へ変換する行だけを書く。相手の操作名 ・ 項目名 ・ 失敗の符号は変換の左辺にだけ置く
外部サービスへの依頼を、べき等かどうかを決めずに再実行する（推測）UC-1 の拡張「決済代行が応答しなかった」は、結果を通知する通信だけが失敗した場合を含みうる。そのまま再実行すると、判断基準の暗黙的な分散トランザクションの例と同じく、承認が2回行われうる（推測）連係の行に、その操作がべき等か（再実行してよいか）を書き、応答が無かったときの扱いをその値から決める

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
補完のサブドメインを足すとき、中核と同じ形で集約 ・ 値オブジェクトまで書いてしまう各サブドメインの business_logic から導いた実装方法がドメインモデル以外なら、そのサブドメインだけに属する AGG 宣言が無いことを道具で検査する
一般の外部サービスの項目名を、使う側の同じ言葉の語として足してしまうBC-1 の translates の theirs の値が、ubiquitous_language.terms の word に現れないことを検査する
ドメインの組み立ての表を、既存の欄と別に手で書いて値をずらす組み立ての表の各行を、SD の classification ・ BC の header.subdomains ・ context_map の行から組み直し、差分が0件であることを検査する
カテゴリーと導いた実装方法の不一致を、宣言の誤りとして黙って直す中核 × トランザクションスクリプト ・ アクティブレコード、補完 × ドメインモデル ・ イベント履歴式ドメインモデルの組を一覧に出し、0件でなければ利用者に問う
