結論

条件付きで採る

ユースケースの側では、カテゴリーで書く量を変えるのではなく、主アクターの目的があるものはカテゴリーを問わずユースケースにし、外部サービスは支援アクターとして呼ぶ側のユースケースの手順と拡張に書き、サブドメインをまたいだ組み立ては一番外側の要約のユースケースで示す、という条件で案1〜3を採る。

判断基準は、ユースケースを書くかどうかを主アクターの目的と設計スコープで決め、使うだけのシステムは設計スコープの外の支援アクターとし、相互作用するシステムの要求はユースケースの外に書いてリンクする、としているからである。利用者の考え（A）は、要約のユースケースとアクター-目的リストで組み立てを示す点で正しいが、カテゴリーごとの記述の量の決め方は判断基準の範囲外である。

判断の道筋

  1. A：一般 ・ 補完も、プロダクトの中でどう組み立てるかを書く必要があるか

    ユースケースの側では、ある。一般のサブドメインを満たす外部サービスは、UC-1 の支援アクター（決済代行）として手順と拡張に現れ、その外部インタフェースとプロトコルはユースケースの外に必ず書く。サブドメインをまたいだ順序と文脈は、本来の主アクター（顧客）が外側にいる一番外側の設計スコープ（SCP-1 店）で要約のユースケースを書いて示す。今の見本はユーザー目的の UC-1 しかなく、この要約が無いので「中核に対してだけ」に見える

  2. 決済代行は、主アクター ・ 支援アクター ・ 設計スコープの内側のどれか

    対象システムから請求額の承認を頼まれて結果（承認番号）を返し、自分たちは設計せず使うだけなので、設計スコープの外の支援アクターである。決済サービスの中の振る舞いは書かない

  3. UC-1 の手順（STEP-4）は、決済サービスのどの操作かを書くべきか

    手順の文には書かない。手順は「システムは、決済代行に請求額の承認を依頼する」のまま、何を依頼し（請求額の承認）何を受け取るか（承認番号）を情報の別名で書く。どの操作か ・ 項目の対応 ・ プロトコルは、BC-1 の文脈の地図の決済代行の行に書き、STEP-4 から関連情報としてリンクする

  4. 拡張 5a は、失敗の種類を指すべきか

    拡張条件は、システムが検出できて、振る舞いが違うものごとに1つ置く。失敗の種類の一覧（連係の宣言の側）は細かくてよく、拡張はそれを振る舞いでまとめる。見本では「承認しなかった」と「応答が無い ・ 応答が正しくない」は振る舞いが違う（前者は承認が残らないことが分かっていて、後者は分からない）ので、2つの拡張に分ける。各拡張から、それがまとめた失敗の種類を指す

  5. 決済をサブユースケースとして独立させるか

    今は独立させない。呼び出すのは UC-1 の1か所だけで、UC-1 を読みにくくしてもいない。取り消し ・ 返金のように2つ目の呼び出し元が出たときに、サブ機能「請求額の承認を得る」（推測の名前）として切り出す

  6. 補完の業務は、カテゴリーで決めてユースケースにするか

    カテゴリーでは決めない。主アクターが対象システムに目的を持ち、システムがそのサービスを提供するなら、アクター-目的リストに載り、ユースケースになる。どこまで書くかは、精度の段階（アクターと目的 → 概要または主成功シナリオ → 失敗条件 → 失敗処理）と会話の密度で決める

  7. E：店頭の受け渡しはユースケースにするか。目的レベルは何か

    する。主アクターは店舗（SH-2。SCP-2 の外にいる）で、目的は注文を顧客に渡すこと。済ませたら満足して立ち去れ、今日いくつ渡したかが店舗の仕事の成果になり、SC-1 もこの件数で測るので、ユーザー目的とする。所要時間は「2〜20分程度」より短いので、レベルの判定にはこの問いを使わない（推測を含む判定）

設計の手順

  1. 企業スコープの要約のユースケースを1つ書く

    スコープ SCP-1（店）、主アクター 顧客、レベル 要約。1. 顧客は店に注文を確定させる（UC-1 を呼び出す） 2. 店は受け取り予定時刻までに調理する 3. 店舗は顧客に注文を渡す（「注文を渡す」を呼び出す）。これがサブドメインをまたいだ順序と目次を示す。名前は「約束した時刻に注文を受け取る」（推測）

  2. ユーザー目的のユースケース「注文を渡す」を書く

    スコープ SCP-2 ・ 文脈 BC-1、主アクター 店舗。1. 店舗はシステムに、渡す注文の注文番号を示す 2. システムは注文が確定済であることを確認する 3. システムは注文を受け渡し済にする（AGG-1.CMD-3、EVT-2 が SC-1 の測る業務イベント） 4. システムは店舗に、受け渡し済になったことを知らせる。成功時保証は「注文が受け渡し済で、渡した時刻が残る」。最低保証は「確定済でない注文を受け渡し済にしない」

  3. 「注文を渡す」の拡張条件を洗い出し、検出できるものに絞る

    1a. 注文番号の注文が見つからない： 2a. 注文が確定済でない（TERM-41 確定していない注文は渡せない）： 2b. 受け取り予定時刻を過ぎていた：（処理は未決定事項。UC-1 の open_issues と同じ問い）。「顧客が受け取りに来ない」はシステムが検出できないので拡張にせず、時間がきっかけの別のユースケースの候補にする。その主アクターは、その時間に動いてほしい利害関係者（店舗）

  4. UC-1 の STEP-4 を意図の文のまま残し、決済サービスの操作は関連情報としてリンクする

    STEP-4 の文 ・ data（TERM-34）・ reply（TERM-21）は変えない。決済サービスのどの操作か、authorization_id → 承認番号 ・ amount → 金額 の変換、プロトコルは BC-1 の文脈の地図の決済代行の行に置き、STEP-4 からそこを指す

  5. UC-1 の EXT-3 を、振る舞いが違う2つの拡張に分ける

    5a. 決済代行が支払いを承認しなかった： 5a1. システムは調理枠を戻す 5a2. システムは経過を記録する 5a3. システムは顧客に支払いが承認されなかったことを知らせる（別の支払い手段で STEP-4 に戻るかは未決定事項）。5b. 決済代行が応答しなかった、または正しくない応答を返した： 5b1. システムは調理枠を戻す 5b2. システムは経過を記録する 5b3. システムは顧客に、注文を確定できなかったことを知らせる。5b では TERM-47 を知らせない。承認が残った可能性の扱いは前置きの未判定に依存する

  6. 連係の宣言の失敗の種類と、拡張を対応づける

    失敗の種類（例：承認されなかった ・ 応答待ちのタイムアウト ・ 承認番号の無い応答）は連係の宣言に並べ、各拡張は自分がまとめる種類を指す。種類の一覧が増えても、振る舞いが同じなら拡張は増やさない

  7. アクター-目的リストに、カテゴリーを問わずユーザー目的を並べる

    顧客：注文を確定する（UC-1）。店舗：注文を渡す。決済代行は主アクターとしては載せない。補完のサブドメインが出たときも、そこに主アクターの目的があればこのリストに足し、まず概要（精度の段階2）まで書く

hub-and-spoke-model対応：ユースケースには、ステップで必要なデータを別名で挙げるだけにし、データ記述へリンクを張る ・ 理由：データ形式はユースケースの一部ではなく、フィールドの詳細はユースケースとは独立に変化する
hub-and-spoke-model対応：ユースケースに含めない要求も、要求文書のどこかで必ず文書化する ・ 理由：「その要求はどこにあるのか」と開発者が困らないようにする
supporting-actor対応：拡張条件をブレーンストーミングするときは、支援アクターからの応答が無い場合と、応答が正しくない場合を候補に入れる ・ 理由：そのときの振る舞いが要求に無いと、プログラマがその場で書ける程度の処理を書き込むことになる
extension問い：ほかの条件と、システムの振る舞いが同じにならないか ・ 何が分かるか：同じなら1つにまとめられる
extension問い：システムはその条件を検出できるか ・ 何が分かるか：検出できない出来事には反応できない。検出できる同等の条件に置き換えられないかも考える
extension対応：どの失敗処理でも、利害関係者の利益が守られ、ログや回復のための情報が残るかを確認する ・ 理由：書き手は途中で失敗が起きる場面を想定しないので、ログや回復の情報が抜けやすい
sub-use-case問い：その処理は、複数のユースケースや複数の場所から使われるか ・ 何が分かるか：独立させれば1か所で管理し保守できる。サブ機能のユースケースを作る理由は、理屈の上ではすべてこれである

goal-level対応：要約のユースケースは、ユーザー目的の文脈と目次を示す分だけ書く ・ 理由：要約からは機能要求を読み取れない
functional-scopeどのユースケースがあるかを決めることが、そのまま機能スコープを決めることになる。2つを別々の作業として進めない
primary-actor問い：システムに対して、システムが動くことで満たされる目的があるか ・ 何が分かるか：目的の無いもの（銀行のオーナーなど）は、利害関係者であっても主アクターではない
goal-level問い：社員なら、今日これをいくつ済ませたかが仕事の評価に響くか ・ 何が分かるか：仕事の単位として完結しているかが分かる
primary-actor問い：時間がきっかけで始まるなら、その時間に動いてほしいのは誰か ・ 何が分かるか：毎晩や月末にユースケースを起動する社員はいない。その時間に動いてほしい利害関係者を主アクターにする
precision対応：精度の低い段階で誤りを直してから、詳細を加える ・ 理由：低い段階で間違っていれば、その上で精度を上げる労力は何十人月分でも無駄になる

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
ユースケースの手順の文に、外部サービスの操作名や相手の項目名（authorization_id ・ amount）を書くUC の steps の data ・ reply が、BC-1 の ubiquitous_language の TERM だけを指しているかを検査する。相手の項目名は context_map.relations[].translates[].theirs にだけ現れることを検査する
連係の宣言の失敗の種類と、拡張を1対1で並べるcondition_kind が「支援アクターの失敗」の拡張どうしで、steps の並び（invokes ・ verb ・ data）が同じものが2つ以上ないかを検査する。同じなら1つにまとめる
拡張条件と、その処理で知らせる情報が食い違う（応答が無い拡張で「承認されなかった」を知らせる）支援アクターの失敗の拡張ごとに、知らせる data が、その拡張の条件で分かっていることだけを表すかを人が読んで確かめる
集約のコマンドのうち、どのユースケースからも呼ばれないものを残すAGG-*.commands[].id のそれぞれが、どれかの UC の steps[].invokes に現れるかを検査する（見本では AGG-1.CMD-3 が現れない）
