qa-advisor の回答 ・ 設計相談

既存のプロダクトから宣言を起こす（セマンティックマイグレーション）とき、既存の振る舞いとの一致をテストでどう確かめるか。(1) 既存のテストに記録の契約を後付けし、宣言のテスト条件と突き合わせる進め方、(2) テストが無い箇所の扱い（いまの振る舞いを写し取るテスト）、(3) 一部だけ宣言がある状態で、移した範囲の終了基準、(4) リグレッションテスト ・ 影響度分析 ・ メンテナンステストとの関係、(5) リスクに基づく移す順序。オーケストレーターの見立て3 ・ 4（と5のテストの側）を評価する

前置き

判定の前に確定させた前提と、その出所

前提内容出所
道具の位置と記録の契約道具はソースを読まない。テストの側から受けるのは、テストが走ったときに1行ずつ追記する記録（テスト条件の ID ・ ハッシュ値 ・ レベル。realsim では任意でテストの識別子 test も書く）だけで、合否を持たない。合否はテストの実行器が判定し、CI は concrete check ・ 実行器 ・ concrete match のどれか1つでも落ちれば落ちるACDR 0107 ・ sample/realsim/repo/ci.sh ・ tests/trace.py
前の回答との関係前の回答（advice/qa.json）の6種のうち、不合格と未実行は ACDR 0107 で実行器の判定へ移った。この回答は、道具の4種（欠け ・ 余り ・ 古い ・ レベル違い）と実行器の合否の2つで組む。テスト条件の単位、ID の形、求めるレベルの対応表、承認を経た「免除」だけを別に数える扱いは、前の回答のまま使うadvice/qa.json の問い1 ・ 問い6 ・ 問い7、ACDR 0107
「移行」という語判断基準のメンテナンステストのきっかけにある「移行」は、あるプラットフォームから別のプラットフォームへの移行を指す。宣言を起こす作業そのものはプロダクトのコードを変えないので、それだけではメンテナンステストのきっかけに当たらない。宣言で新しく決めたことに合わせてコードを直す段になって、きっかけの「改良」に当たる、と読む。この読み方は推測である判断基準の範囲外（推測）
いまの振る舞いを写し取るテスト相談の材料の語をそのまま使う。判断基準には、この種類のテストの名前と書き方は無い。判断基準が触れているのは「レガシーなコードに後からテストを付ける」のはより難しい、という点までである判断基準の範囲外
DDD ・ ユースケースの判断どのサブドメインが中核か、範囲をどの宣言の単位で切るか、元の文書に無い最低保証 ・ 拡張をどう決めるかは、DDD とコーバーンの判断であり、この回答の判断基準の範囲外である。触れるところは「推測」と書き、判定の根拠にしない判断基準の範囲外

結論

弱い

見立て3 ・ 4 の向き（既存のテストに記録を後付けし、テストが無い箇所は写し取るテストを先に書き、範囲を区切って移す）は採れるが、このままでは4つが欠ける ── 記録を足す前に、そのテストが条件の期待結果を確かめているかのレビュー、写し取るテストの合格が正しさを示さないことの扱い、範囲の外のリグレッションテストを流し続けること、範囲ごとの終了基準である。

トレーサビリティは「テストベースの各要素」と「テスト結果」との追跡できる対応関係なので、中身を確かめずに付けた記録の行は対応関係にならず、「欠陥ゼロ」の落とし穴は検証だけで正しいシステムを期待することを誤りとするので、いまの振る舞いとの一致は正しさを示さない。メンテナンステストは変更しない部分のリグレッションのチェックを含み、終了基準はテストレベルごとに定義するので、道具が検知しない範囲の外もテストは流し続け、範囲ごとに終了基準を決める。

設計の手順

  1. 問い1-a：範囲ごとに、既存のテストと宣言のテスト条件の対応表を作り、テストを4つに分ける

    道具で範囲の中のテスト条件（ID ・ ハッシュ値 ・ 求めるレベル）を出し、既存のテストを1件ずつ「どの条件の期待結果を確かめているか」で分ける。これはテスト分析に当たる（テストベースを分析し、テスト条件を定義する）。(a) 1つの条件を確かめている → 記録の行を1行足す候補にする。(b) 複数の条件を確かめている → 条件ごとに記録の行を書く候補にする。コンポーネントテストなら、前の回答のとおり Eager Test を避けて分けることを検討する。(c) どの条件にも当たらない → 人が決める。宣言の側に条件が足りない（読み取りの漏れ）、実装の定義から導くテスト（アダプターの契約試験など）、まだ範囲の外、もう要らない、のどれかである。宣言に条件が足りないときは、テストベースの欠陥として欠陥レポートに記録する。(d) 条件はあるのに既存のテストが無い → 問い2へ。対応表はテストウェアとして構成管理の下に置き、範囲の終了基準で使う（置き場所は推測）。

  2. 問い1-b：記録の行は、テストがその条件の期待結果を確かめているとレビューで確かめてから足す

    記録のハッシュ値は「このテストは、この版の条件を確かめた」という対応を表す。中身を見ずに今のハッシュ値を写すと、突き合わせは欠けを消すだけになり、以後の「古い」の検知も始めから誤った対応の上で動く。レビューでは、テストの確認の行（assert）と、条件の期待結果の欄（例：事前条件なら拒否されることと拒否の理由、事後条件なら変わった後の状態）を並べ、確かめていない欄があれば確認の行を足してから記録を足す。足せないなら、その条件には記録を足さず、欠けのまま残す。レベルはテスト対象で決めて正直に書く。既存のテストが駆動する側の入口から集約の条件を確かめているなら、記録は system と書き、道具はレベル違いを出す。レベル違いは誤りではなく、求めるレベルのテストを足すか、実装の定義の対応表を見直すかの、人の決定の候補である。記録の level を書き換えてレベル違いを消さない。

  3. 問い1-c：記録を足したテストを流し、不合格と検知を出どころで分けて人の決定へ回す

    既存のテストは以前合格していたので、記録の行を足しただけなら合否は変わらない。不合格になるのは、問い1-b で足した確認の行（宣言の期待結果）が、いまの振る舞いと違うときである。この不合格は、宣言の出どころで3つに分けられる：元の文書から起こした項目なら読み取りの誤りか元の文書と実装のずれ、既存のコードの振る舞いから推した項目なら推した結果の誤り、新しく決めた項目なら変更要求（コードを直すまで不合格になるのが正しい）。どれも不正として欠陥レポートに記録し、人が決める。判断基準も、報告した不正は本当の欠陥のこともあれば変更要求のこともある、としている。これは見立て5（移す途中の検知は既存のプロダクトにあったずれで、人の決定の候補）を、テストの側でも同じに扱うことに当たる。新しく決めた項目のテストで CI を止め続けないためには、前の回答の「免除」（承認を経た条件だけを別に数える）に、コードを直すまでの間だけ入れる（推測）。不合格を消すために、テストの期待結果をいまの振る舞いへ書き戻してはならない。

  4. 問い2：テストが無い条件には、いまの振る舞いを写し取るテストを、宣言のテスト条件の単位で書く

    書く前に、このテストが何を示すかを決めておく。いまの出力を期待結果にしたテストは、いまの振る舞いが変わらないことを示すが、いまの振る舞いが正しいことは示さない（「欠陥ゼロ」の落とし穴）。そこで次の4つを守る。(1) 写し取ったテストで確かめた条件は、宣言の出どころを「既存のコードの振る舞いから推した」にし、承認者が「その振る舞いを意図どおりとするか」を決めるまで承認済みにしない。検証に加えて妥当性確認を置く、ということである。(2) 写し取る単位は、宣言のテスト条件の期待結果の欄だけに絞る。出力の全体を文字列で比べる（Sensitive Equality）、内部の呼び出しの順まで確かめる（Overspecified Software）と、Behavior Sensitivity の Fragile Test になり、のちにコードを直したとき関係の無い所で落ちる。(3) 既存のコードが Hard-to-Test Code で部品を単独で動かせないときは、駆動する側の入口から system レベルで写し取り、求めるレベルとのレベル違いは人の決定の候補として残す。結合を断ってから求めるレベルのテストを足す（推測。後からテストを付ける技法は判断基準の範囲外）。(4) 範囲の全部を一度に書かず、問い5のリスクの順に書く。

  5. 問い3：範囲の終了基準を、テストレベルごとに7つの条件で決める

    範囲を「移した」と言えるのは、次をすべて満たしたときとする（判断基準の典型的な終了基準を、この道具に当てはめた案）。(1) concrete check：範囲の中の宣言どうしの検知が0件、または人の決定として記録済み。(2) concrete match：範囲の中の欠け ・ 余り ・ 古い ・ レベル違いが0件。承認を経た免除は合格と別に数える。(3) 実行器：範囲の中のテストがすべて合格し、範囲の外を含む既存のテストもすべて合格（リグレッション）。(4) 対応表で「どの条件にも当たらない」に分けたテストが、すべて人の決定済み。(5) 出どころが「既存のコードの振る舞いから推した」項目が、すべて承認済み。(6) 移す途中で記録した欠陥レポートが、すべてクローズか、延期として承認済み。(7) 範囲の中のテスト（写し取ったテストを含む）が、CI で自動で流れる。集計はテストレベルごとに出す。時間 ・ 予算で一部を残すときは、残すリスクをステークホルダーがレビューして受け入れた場合だけ終了とし、残したものをテスト完了レポートの未解決のリスクに書く。後の範囲を移す途中で前の範囲の宣言を変えたら、前の範囲の終了基準を評価し直す。

  6. 問い4-a：範囲の外は道具が検知しなくても、既存のテストはすべて流し続ける

    見立て4の「範囲の外は検知しない」は、道具の突き合わせの話であって、テストを止めてよいことにはならない。実行器は範囲の外のテストも判定するので、CI では既存のテストをすべて流し続け、これを移行の間のリグレッションテストとする。記録を後付けする作業でテストを分けたり書き直したりするのはテストウェアの変更なので、作業の前と後で、実行器が数えるテストの数と、記録の行に出るテストの識別子の数を比べ、テストが減っていないかを確かめる。書き直す前の古いテストは、新しいテストが合格するまで消さない（推測）。

  7. 問い4-b：宣言に合わせてコードを直す段からは、メンテナンステストとして変更の成功とリグレッションの両方を確かめる

    宣言を起こすだけの間は、コードは変わらないので、テストで確かめるのは宣言といまの振る舞いの一致である。新しく決めた項目に合わせてコードを直す段に入ると、メンテナンステストになる：変更の実装が成功したかの評価（その条件のテストの合格）と、変更しない部分のリグレッションのチェック（範囲の外を含む全体）の両方を含む。範囲の大きさは、変更のリスクの度合い ・ 既存システムの大きさ ・ 変更の大きさで決める。

  8. 問い4-c：影響度分析は、宣言の側と、範囲の外の側で別の手段を使う

    宣言の側：承認を経て宣言を変えたとき、ハッシュ値が変わった条件の一覧（concrete match の「古い」）が、範囲の中の影響度分析の結果になる。前の回答の問い3と同じである。範囲の外の側：判断基準は、変更の悪影響が変更したコンポーネントだけでなく、同じシステムの他のコンポーネントや接続している他システムにも及ぶ可能性があるとする。範囲の外には記録が無いので、道具はこの影響を出せない。範囲の外への影響度分析は、既存のテストとコードの依存から行い（推測）、範囲の外のリグレッションテストを省く根拠にしない。

  9. 問い5：移す順は、リスクレベル（可能性と影響）と依存で決める

    見立て4の「中核から先に」は、リスクの影響の側だけを見ている（どれが中核かは DDD の判断で、推測）。可能性の側として、(1) 欠陥の偏在：これまでの欠陥レポートや運用時の故障が集中しているコンポーネント、(2) テストの無さ：既存のテストが無い箇所は、宣言の読み取りの誤りを実行で確かめられない、(3) これからコードを直す予定があるか（推測）、を見る。サブドメイン ・ ユースケースごとに、可能性 ・ 影響 ・ テストの有無 ・ 依存をリスクレジスターに並べ、リスクレベルの高いものから範囲に入れる。ただし、優先度の高い範囲の条件が、優先度の低い宣言（ユースケースが参照する集約 ・ 値オブジェクトなど）に依存するなら、依存先を同じ範囲に入れるか先に移す。範囲の中の条件が範囲の外の宣言を参照したままだと、その参照先の条件は検知されない（推測）。テストが無くリスクも高い箇所は、写し取るテストを書く手間が大きいので、人と時間の都合で順を調整する。

  10. 問い6：例で、対応表の分け方と、記録を足してよいテストと避けるテストを確かめる

    下の「コードの例」に、realsim の ID を使った対応表、記録を足してよいテスト、避けるテスト、範囲の終了基準の判定表を置く。realsim の受注の文脈のテスト（tests/test_domain.py）を、既存のテストとみなした例である。

判定の拠りどころにした判断基準の記述

判断基準引用
test-processテスト活動：テスト分析 ・ 何をするか：テストベースを分析し、テスト可能なフィーチャーの識別、テスト条件の定義と優先順位付け、リスクとリスクレベルの分析を実施する

traceability対応：テストプロセスの全期間にわたって、トレーサビリティを確立し維持する ・ 理由：効果的なテストのモニタリングとコントロールの実装に重要である

testing-principles原則：「全数テストは不可能」 ・ 内容：ごく単純なソフトウェアを除き、すべてをテストすることは現実的でない
defect-management条件：テスト分析でテストベースの欠陥を識別し、直接修正しないとき ・ 対応：欠陥レポートを作成する
defect-management報告した不正は、本当の欠陥と判明する場合もあれば、偽陽性や変更要求など他の何かの場合もある
fragile-test原因：Overspecified Software（別名 Overcoupled Test） ・ 何か：ソフトウェアの構成や振る舞いについて、テストが言いすぎている ・ 4つの敏感さとの関係：Behavior Sensitivity の一形態
fragile-test原因：Sensitive Equality ・ 何か：検証するオブジェクトを文字列に変えて、期待する文字列と比べる
fragile-test確かめている機能が変わったせいで失敗するのは、この敏感さに当たらない。regression test は、まさにそのためにある
hard-to-test-code条件：レガシーなコードに後からテストを付ける ・ 対応：より難しい。技法は「Working Effectively with Legacy Code」が扱う
test-levelsテスト活動の重複を避けるため、テストレベルは次の代表的な属性で区別する。
entry-exit-criteria終了基準：活動の完了を宣言するために、何を達成しなければならないかを定義する基準。
entry-exit-criteria対応：開始基準と終了基準を、テストレベルごとに定義するべきである
entry-exit-criteria区分：終了基準 ・ 基準：完了基準 ・ 例：計画したテストの実行 ・ 静的テストの実行 ・ 発見したすべての欠陥のレポート ・ すべてのリグレッションテストの自動化
entry-exit-criteriaこれらを妥当な終了基準とみなすことがある。他の終了基準が未達でも、追加のテストをせずに本稼働させるリスクを、ステークホルダーがレビューして受け入れたなら、テストの終了は許容される
test-monitoring-and-control条件：再作業が発生した ・ 対応：テストアイテムによる開始基準と終了基準の充足を再評価する
test-monitoring-and-controlテスト完了：完了したテスト活動のデータを収集し、経験 ・ テストウェア ・ その他の関連情報を統合する活動。プロジェクトのマイルストーンで発生する。
confirmation-and-regression-testingリグレッションテスト：変更によって悪影響が生じていないことを確認するテスト。すでに確認テストを済ませた修正も、確認の対象に含む。
confirmation-and-regression-testing対応：リグレッションテストでは、まず影響度分析を行うことが望ましい
confirmation-and-regression-testing影響度分析は、変更の影響が及ぶソフトウェアの部分を示す。これにより、リグレッションテストの拡張を最適化する。
confirmation-and-regression-testing変更したコンポーネントだけでなく、同じシステム内の他のコンポーネントや、接続している他システムにも及ぶ可能性がある。テスト対象だけでなく、環境に関わる場合もある
maintenance-testingメンテナンステスト：本番稼働中のシステムに対する変更のテスト。変更の実装が成功したかの評価と、変更しない部分（通常はシステムの大部分）に起こりうるリグレッションのチェックの両方を含む。
maintenance-testing変更のリスクの度合い ・ 既存システムの大きさ ・ 変更の大きさ
risk-managementリスクレベル：リスクの可能性（顕在化する確率で、0より大きく1より小さい）と、リスクの影響（顕在化の結果）の2つが表す、リスクの尺度。高いほど、その処置が重要になる。
risk-management条件：欠陥の偏在を予測したとき、または観察したとき ・ 対応：その偏在を、リスクベースドテストの重要なインプットとして使用する ・ 理由：発見する欠陥や運用時の故障は、通常、その大部分が少数のシステムコンポーネントに集中する
risk-management条件：テスト実行の順番を決定するとき ・ 対応：リスク分析の結果に基づき、最も重要なリスクをカバーするテストケースから実行する ・ 理由：リスクに基づく優先順位付けは、最も一般的に使用される戦略の1つである
risk-management条件：テスト結果とリスクを関連付けたとき ・ 対応：そのトレーサビリティで、テスト対象の残存リスクのレベルを評価できる ・ 理由：トレーサビリティは、カバレッジの評価を支援する
test-case-prioritization対応：高い優先度のテストケースが低い優先度のものに依存する場合は、低いほうを先に実行する
test-case-prioritization対応：テストツール・テスト環境・特定の時間帯しか利用できない人など、リソースの可用性も考慮する
testware対応：適切な構成管理で、作業成果物の一貫性と整合性を確保する

アンチパターンリスク代替案
中身を確かめずに、今のハッシュ値を写して記録の行を足す欠けが消えるだけで、テストと条件の対応関係は実体を持たない。以後の「古い」の検知も誤った対応の上で動き、トレーサビリティでカバレッジを評価できなくなる確認の行と条件の期待結果の欄を並べてレビューし、確かめていると分かったテストにだけ記録を足す。足せない条件は欠けのまま残す
いまの出力の全体を期待結果として写し取るSensitive Equality ・ Overspecified Software になり、Behavior Sensitivity の Fragile Test として、宣言に合わせてコードを直すたびに関係の無いテストが落ちる写し取る単位を、宣言のテスト条件の期待結果の欄だけに絞る
いまの振る舞いと一致したことを、正しいことの確認とみなす「欠陥ゼロ」の落とし穴に当たる。既存の欠陥が、写し取ったテストの期待結果として固定され、宣言にも正しい振る舞いとして入る写し取ったテストで確かめた項目は出どころを「既存のコードの振る舞いから推した」にし、承認者が意図どおりかを決める（妥当性確認）まで承認済みにしない
範囲の外のテストを止める、または書き直しの途中で古いテストを消す道具は範囲の外を検知しないので、範囲の外へのリグレッションがどこにも出なくなる。変更の悪影響は、変更したコンポーネントの外や接続している他システムにも及びうる範囲の外を含む既存のテストをすべて CI で流し続け、テストの数を作業の前後で比べる
ごく単純なソフトウェアでないのに、すべてを一度に移し、すべてに写し取るテストを書こうとする全数テストは、ごく単純なソフトウェア以外では非現実的であるテスト技法 ・ テストケースの優先順位付け ・ リスクベースドテストを使用して、テストにかける労力を集中する。範囲をリスクレベルの順に区切る
（推測）不合格やレベル違いを、テストの期待結果や記録の level をいまの振る舞いへ書き戻して消す宣言と既存のプロダクトのずれ（人の決定の候補）が、記録にも欠陥レポートにも残らずに消える不合格と検知は欠陥レポートに記録し、出どころで分けて人が決める。新しく決めた項目は、コードを直すまで承認を経た免除で別に数える

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI が既存のテストの本体を見ずに、記録の行だけを一括で足して欠けを消す記録の行を足したコミットごとに、テストの識別子 ・ 条件の ID ・ 確かめている確認の行 ・ 条件の期待結果の欄を1行ずつ並べたレビュー表を AI に出させ、確認の行の欄が空の行があればレビューで差し戻す
AI がテストを条件ごとに分けたり書き直したりする途中で、既存のテストや確認の行を落とす作業の前と後で、実行器が数えるテストの数を比べ、減っていれば理由を対応表の決定に書かせる。記録の行に出るテストの識別子の数と、実行器のテストの数の差を、記録を持たないテストとして毎回出す
AI が写し取るテストで、いまの出力をそのまま期待値に貼る（repr ・ スナップショット ・ 文字列全体の比較）推測：写し取るテストの確認の行が、条件の期待結果の欄（状態 ・ 拒否の理由 ・ 業務イベント）以外を比べていないかをレビュー表で確かめる。スナップショットのファイルや repr との比較を grep で検出する
AI が不合格を消すために、テストの期待結果をいまの振る舞いへ書き戻す以前合格していたテストの確認の行を変えるコミットには、欠陥レポートか宣言の変更の承認への参照を必須にし、参照が無ければレビューで差し戻す
AI がレベル違いを消すために、記録の level を求めるレベルへ書き換える推測：テストのファイルの置き場所とレベルの対応を実装の定義に書き、記録の level とテストの識別子の置き場所が合わない行を道具か CI が警告する
