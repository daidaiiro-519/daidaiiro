# 相談の材料：セマンティックマイグレーション ── 既存のプロダクトの文書 ・ 仕様 ・ コード ・ テストから、宣言を起こす

## 前提（決着済み）
- 宣言は構造化データ（JSON Schema で型が決まる）。種類：ドメイン（プロダクトの宣言。課題 ・ 提供価値 ・ 利害関係者 ・ 範囲 ・ 達成の基準 ・ サブドメインの組み立て ・ 設計スコープ）・ サブドメイン ・ 区切られた文脈（このプロダクトが持つものだけ。外の相手とはこちら側の変換だけを書く）・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス。
- 意味はすべて欄に持ち、自由文は人が読む説明だけ。文 ・ 例 ・ 境界値は道具が組む。
- 道具は、宣言どうしのずれ（構造 ・ 対応の欄 ・ 上流の変更 ・ 人のレビュー）と、宣言とテストのずれ（テストが走ったときに書く記録の ID ・ ハッシュ値 ・ レベルとの突き合わせ。欠け ・ 余り ・ 古い ・ レベル違い）を検知する。道具はソースを読まない。
- 宣言のどの項目も、AI が起こし、人（承認者）が描画した画面で承認する（PR）。

## 利用者との合意（セマンティックマイグレーションの意味）
既存の文書や仕様を、ユースケース駆動の宣言へ「コンパイルするような感覚」で起こし直す作業。ただしコンパイルと違い、入力（自由文）の意味は決まっておらず、出力には元の文書に無い決定（最低保証 ・ 拡張 ・ 拒否の理由など）が入る。意味を移すより、既存の文書を手がかりに意味を決め直すことに近い。

## オーケストレーターの見立て（検証してほしい）
1. 段に分ける：読み取り（文書 ・ コード ・ テストからアクター ・ 目的 ・ 手順 ・ 規則 ・ 語の候補を取り出す。AI）→ 名前解決（語を区切られた文脈の同じ言葉に置く。同じ語の別の意味が見つかれば止めて人へ）→ 型検査（スキーマと宣言どうしの検査。道具）→ 人の決定（元の文書に無いこと）→ 出力。
2. 宣言の項目に「出どころ」の欄を持たせる：元の文書のどこから起こしたか（ファイルと位置）／元の文書に無く新しく決めた（人が決定）／既存のコードの振る舞いから推した。承認者は、出どころごとに見ること（読み取りの正しさ／決定の正しさ）を変える。
3. 既存の振る舞いとの一致は、既存のテストに記録の契約（ID ・ ハッシュ値 ・ レベルを1行追記）を後付けして、宣言のテスト条件と突き合わせて確かめる。テストが無い箇所は、いまの振る舞いを写し取るテストを先に書く。
4. 一度に全部は移さない。範囲（どのサブドメイン ・ 文脈 ・ ユースケースまで移したか）を宣言側に持ち、範囲の外は検知しない。中核から先に移す。
5. 移す途中で出る検知（宣言どうしのずれ）は、道具の誤りではなく既存のプロダクトにあったずれである。人の決定の候補として並べる。

## 聞きたいこと
A. 見立て1〜5 は、あなたの判断基準から見て正しいか。足りないもの ・ 多すぎるもの。
B. 既存のプロダクトから、何を手がかりに、どの順で宣言を起こすのが原典に沿うか。
C. 元の文書に無い決定と、元の文書から読み取ったものを、どう分けて承認させるか。
D. 移行の途中の状態（一部だけ宣言がある）を、どう扱うか。

判断基準からの引用を根拠にし、範囲外は「推測」と書く。新しい語を作らず、原典の語をそのまま使う。比喩を使わない。
