# 相談の材料：テスト仕様とテスト実装のドリフト検知のインタフェース

## 何を作っているか
- 仕様（モデリング側）は「宣言」と呼ぶ構造化データ（JSON、JSON Schema で型が決まる）。種類は7つ：ドメイン ・ サブドメイン ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス。宣言は人が描画した画面で承認する（PR で変更を承認、過去の版は git が持つ）。
- 実装（コーディング側）は、ポートとアダプターを外枠に、宣言からテストと実装を書く。技術スタックごとにテストの書き方は違う。
- スキーマ駆動の道具（ユースケース駆動の concrete）は、宣言の検証 ・ 描画 ・ 取得 ・ 更新に加えて、**テスト仕様とテスト実装のドリフト検知**を契約として持つ。ここが今回の対象のインタフェースである。道具はソースコードを読まない。テスト実装の側からは「報告」を受け取る。

## 宣言の中で、テスト仕様になる単位（現時点の整理。ID の形は未定）
| 宣言 | 単位 | 確かめること | 仮の ID |
|---|---|---|---|
| ユースケース | 主成功シナリオ | 成功時保証がすべて成り立つ | UC-1.M |
| ユースケース | 元の手順に戻る拡張（2a ・ 3a） | 戻ったあと成功時保証が成り立つ | UC-1.2a |
| ユースケース | 失敗で終わる拡張（4a） | 最低保証がすべて成り立ち、成功時保証は成り立たない | UC-1.4a |
| 集約 | 不変条件（違反する例つき） | 違反する操作が拒否される | AGG-1.INV-2 |
| 集約 | コマンドの事前条件（拒否の理由と例つき） | その理由で拒否される | AGG-1.CMD-1.PRE-1 |
| 集約 | コマンドの受け付ける例 | 事後条件と業務イベントが成り立つ | AGG-1.CMD-1 |
| 値オブジェクト | 不変条件（作れない値の例つき） | 作れない | VO-1.INV-1 |
| ドメインサービス | 操作の事後条件 | 結果が事後条件を満たす | DS-1.OP-1 |
| 区切られた文脈 | 公開された言葉（版つき） | 外へ出す形が版のとおり | BC-1.PL-1.v1 |
| ドメイン | 品質の要求（手順に付く） | 要求を満たす（例：2秒以内） | DOM-1.QR-1 |

## 宣言の組み方（意味の塊ごと）
- ユースケース：header（名前 ・ 目的レベル ・ スコープ ・ 主アクター ・ トリガー）／ preconditions ／ stakeholders ／ guarantees（minimal ・ success、それぞれ守る利害関係者）／ scenario.steps[]（番号 ・ 短い名前 ・ アクター ・ 相手 ・ 種類 ・ 文 ・ 戻りメッセージ ・ 呼び出す集約のコマンド ・ 品質の要求 ・ 守る利害関係者 ・ extensions[]（ラベル 2a ・ 名前 ・ 条件 ・ 条件の種類 ・ 処理の手順[] ・ 終わり方 ・ 成り立つ最低保証） ・ variations[]）。
- 集約：header ／ structure（状態 ・ 内側のエンティティ）／ invariants[]（条件の構造 ・ 違反する例）／ commands[]（引数 ・ 事前条件[]（拒否の理由 ・ 例）・ 事後条件[] ・ 出す業務イベント ・ 受け付ける例）。
- 条件は「前提条件 ・ 対象 ・ 集計 ・ 範囲 ・ 演算子 ・ 比較する値」の構造で書き、文はツールが生成する。

## 決まっていること（ボード usecase-modeling-coding 論点7、承認済み）
宣言から導くテストは7種類：ユースケースのシナリオの試験（成功で終わるものは成功時保証、失敗で終わるものは最低保証を検証。駆動する側から試験の道具で動かし、駆動される側を偽物に替える。準備は事前条件から作る）・ サーガの手順と補償の試験 ・ 集約の条件の試験（集約を直接作って操作する単体テスト。不変条件ごとに破ろうとして拒まれる例を1件以上）・ 値オブジェクトの条件の試験 ・ ドメインサービスの条件の試験（模擬を使わない）・ 公開された言葉の契約試験 ・ 品質の要求の試験。実装の定義から導くテストは3種類（駆動される側のアダプターの契約試験 ・ 駆動する側のアダプターの試験 ・ 通しの試験）。テストの厚さは業務ロジックの実装方法で決まる（ドメインモデル＝ピラミッド形、アクティブレコード＝ダイヤモンド形、トランザクションスクリプト＝逆ピラミッド形）。

## 前に出た指摘で、まだ決まっていないもの
1. 集約の条件の試験を単体テストとするのはドメインモデルのときだけ。アクティブレコード ・ トランザクションスクリプトのとき、同じ条件の ID をどのレベルのテストへ写すかの規則が無い（ddd-advisor）。
2. ドメインサービスの試験で模擬を使わないなら、入力は値に限られる（ddd-advisor）。
3. サーガの補償と拡張の処理の二重記述（usecase-advisor）。現在はサーガを実装側へ移す方向。
4. ユースケースの拡張のラベル（2a など）は手順の位置から付く。手順を足すと番号がずれ、テストの ID が変わる恐れがある（usecase-advisor は位置から導くとし、変わったら承認の差分に出すとした）。

## 前に出た案（作り直す前提の叩き台）
- テスト仕様の ID は「宣言の ID.項目の ID」。
- テスト実装は報告を JSON で出す：results[] に {id, result: pass|fail|skip}。報告の形は concrete が JSON Schema で持ち、報告を作る手段は技術スタックごとにコーディングの側が持つ。
- ドリフトは3種：仕様に在ってテストに無い ・ テストに在って仕様に無い ・ pass でない。
- 9月のボードでは「テストの側からは網羅したシナリオ ID の集合を1行1ID で受け取り、道具は引き算するだけ」だったのを、ACDR 0093 で上の JSON の報告へ改めた。

## 気にしていること（相談者のメモ）
- 仕様が変わったのにテストが古いまま、という食い違い（古いテスト）を検知できない。
- ID が安定しないと、突き合わせが壊れる。
- テスト1件が複数の仕様 ID を検証するとき、複数のテストが1つの仕様 ID を検証するとき。
- skip を通過と数えない。
- 完了の判定（いつ「テストが揃った」と言えるか）。
