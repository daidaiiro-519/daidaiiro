# 相談の材料：宣言どうしのドリフト（仕様と仕様のずれ）の検知

## 何を作っているか
- 仕様（モデリング側）は「宣言」と呼ぶ構造化データ（JSON、JSON Schema で型が決まる）。種類は7つ：ドメイン ・ サブドメイン ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス。1宣言1ファイル。人は描画した画面で承認し（PR）、AI は宣言を読んで実装とテストを書く。
- スキーマ駆動の道具（ユースケース駆動の concrete）は、宣言の検証 ・ 描画 ・ 取得 ・ 更新と、ドリフトの検知を契約として持つ。道具はソースコードを読まない。
- 宣言とテスト実装のドリフトは決めた（ボード論点4、回答待ち）：宣言からテスト条件を取り出し、変わらない ID（宣言ID.種類-連番。例 UC-1.EXT-3、AGG-1.CMD-1.PRE-2）と、期待する結果を決める欄のハッシュ値を付け、テスト実装の報告と突き合わせる。判定は欠け ・ 余り ・ 不合格 ・ 古い ・ 未実行 ・ レベル違い。
- 今回の相談：**宣言と宣言のあいだのドリフト**。利用者の指摘：「大事なのは仕様と実装のドリフトだけではない。仕様と仕様同士のドリフトもある。DDD とユースケースの観点で見ても関連する部分がある」。

## いま宣言どうしが持つ参照（ID で指す）
| 参照元 | 欄 | 参照先 |
|---|---|---|
| ドメイン | subdomains | サブドメイン |
| サブドメイン | serves_values | ドメインの提供価値 |
| サブドメイン | business_logic（経緯を追う必要 ・ 業務ルールが複雑 ・ データ構造が複雑） | 実装方法（ドメインモデル ・ アクティブレコード ・ トランザクションスクリプト）を導く。求めるテストレベルもここから決まる |
| 区切られた文脈 | subdomains ・ context_map.relations.with ・ published_language.from_event | サブドメイン ・ 他の文脈 ・ 業務イベント |

| 集約 ・ 値オブジェクト ・ ドメインサービス | context ・ name ・ 状態の型 ・ 引数の型 | 文脈 ・ 用語 ・ 値オブジェクト |
| 集約 | commands[].preconditions[].reject | 用語（拒否の理由） |

いまの検証は「ID が一意」「参照が解決する」だけ。

## 見本の宣言で実際に見つかったずれ（来店前注文）
UC-1「注文を確定する」：手順3 調理枠を確保する（invokes AGG-2.CMD-1 確保する）、手順4 支払いの承認を得る、手順5 注文を確定する（invokes AGG-1.CMD-1 確定する）。拡張 2a 価格が変わった（2へ戻る）、3a 調理の空きがない（3へ戻る）、4a 承認されない（失敗。4a1 で AGG-2.CMD-2 戻す を invokes。成り立つ最低保証 MG-1 承認なしで確定しない ・ MG-2 失敗したら何も残さない ・ MG-3 どこまで進んだかを残す）。事前条件 PRE-2「カートに1品以上」。
AGG-1「注文」CMD-1 確定する：PRE-1 注文の状態は下書き（拒否：確定済の注文は確定できない）、PRE-2 明細の件数は1以上（拒否：明細の無い注文は確定できない）。事後条件：状態が確定済、受け取り予定時刻が引数と同じ。業務イベント 注文確定済。
AGG-2「調理枠」CMD-1 確保する：引数 数量（VO-1）、PRE-1 空き ≥ 引数（拒否の理由が TERM-13「明細の無い注文は確定できない」を指している）。CMD-2 戻す：事後条件が CMD-1 と同じ「空きが空でない」。引数の「数量」の定義は「1つの明細で注文する商品の個数」で、調理枠の量とは意味が違う。
| 見つかったずれ | 種類（仮） |
|---|---|
| AGG-2.CMD-1 の拒否の理由が、AGG-1 の拒否の理由の語を指している | 参照は解決するが意味が違う |
| AGG-2.CMD-2 戻す の事後条件が、確保する と同じ | コマンドの事後条件が名前と合わない |
| AGG-2 の引数「数量」の用語の定義が、調理枠の文脈と合わない | 用語の意味のずれ |
| UC-1 手順3 が呼ぶ AGG-2.CMD-1 の拒否（空きが無い）に対応する拡張は 3a だが、宣言はそれを結んでいない | 拒否の理由と拡張の対応が無い |
| UC-1 の事前条件 PRE-2 が AGG-1.CMD-1.PRE-2 を満たすことは、文でしか分からない | 事前条件の対応が無い |
| 成功時保証 SG-1「確定済になる」と AGG-1.CMD-1 の事後条件の対応は、文でしか分からない | 保証と事後条件の対応が無い |
| 最低保証 MG-2「調理枠の確保が残らない」は、4a1 の AGG-2.CMD-2 でしか成り立たない。手順を消すと最低保証が嘘になる | 補償と最低保証の対応 |

## 聞きたいこと
1. 宣言どうしで、DDD（ユースケースの観点なら Cockburn）の判断基準から見て「ずれてはいけない関係」は何か。種類の組ごとに挙げ、それぞれ (a) 道具が構造だけで検査できる（参照 ・ 集合の包含 ・ 一致）、(b) 宣言に対応の欄を足せば検査できる、(c) 人のレビューでしか見られない、のどれかに分けてほしい。
2. (b) のとき、どの宣言のどの欄に、何への参照を足すのが原典に沿うか（例：拡張に handles＝集約の拒否の理由、成功時保証に established_by＝コマンドの事後条件）。足しすぎて AI が書く負担と、人が読む負担が増える点にも触れてほしい。
3. 上流の宣言が変わったとき、それを参照している下流の宣言を「確かめ直しが必要」と判定する仕組み（テストとのドリフトと同じ、ID とハッシュ値の考え方）が、DDD ・ ユースケースの観点で妥当か。どの参照で伝える ・ 伝えないか。
4. 上の見本のずれ7件を、あなたの判断基準でそれぞれどう判定するか。

回答は判断基準からの引用を根拠にし、判断基準の範囲外は「推測」と書く。新しい語を作らず、原典の語（DDD：中核 ・ 補完 ・ 一般、区切られた文脈、業務イベント、公開された言葉、集約、不変条件、ユビキタス言語。Cockburn：主アクター、利害関係者と利益、最低保証、成功時保証、拡張、事前条件、トリガー）をそのまま使う。「指紋」のような比喩を使わない。
