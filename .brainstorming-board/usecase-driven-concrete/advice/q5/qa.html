結論

条件付きで採る

宣言どうしの検査はテストベースに対する静的テストとして位置づけ、(a) 構造 ・ (b) 対応の欄は道具の静的解析、(c) はレビューに分け、上流の変更は「参照ごとに、確かめた時点の上流のハッシュ値」を道具が別の記録に持って下流へ伝え、その上流のハッシュ値をテスト条件のハッシュ値にも1段だけ含めて「古い」へつなぎ、宣言どうしのずれが未解決のあいだは終了基準を満たしたと数えない。

静的テストは「要件の欠陥」（一貫していないこと、矛盾、欠落など）を欠陥として直接発見する手段であり、終了基準の完了基準には「静的テストの実行」が、徹底度の測定には「未解決欠陥の数」が含まれる。宣言とテスト実装の突き合わせは宣言を正とする検証なので、宣言どうしのずれはそこでは見つからず、ずれた宣言から導いたテストは合格してしまう。条件付きなのは、どの参照で伝えるかが DDD ・ コーバーンの判断（範囲外）に依存するためである。

判断の道筋

  1. 問い1：宣言どうしの整合の検査は、テストの中のどれに当たるか

    テストベース（宣言）に対する静的テストに当たる。宣言は JSON Schema で型が決まった「正式な構文を持つテキスト」であり、モデルでもあるので、静的解析の対象になる。宣言どうしのずれは、静的テストで早期に見つけられる欠陥のうち「要件の欠陥」（一貫していないこと、曖昧さ、矛盾、欠落、不正確さ、重複）に当たる。相談の3分類はそのまま静的テストの2つの手段へ写せる：(a) 構造だけで検査できるもの＝いまの静的解析、(b) 対応の欄を足せば検査できるもの＝欄を足したあとの静的解析、(c) 人でしか見られないもの＝レビュー。さらにテスト分析は「テストベースとテスト対象を評価して欠陥を識別」する活動を含むので、道具がテスト条件を取り出す時点で (a) ・ (b) を同時に走らせるのが原典の活動の並びに沿う。

  2. 問い1の続き：(c) のレビューは、どう組むか

    レビューのチェックリストには (c) だけを載せ、(a) ・ (b) は道具へ移す。チェックリストの項目は「自動的にチェックできる項目は、含めない方がよい」とされ、また「各項目は、個別に直接チェックできるようにすべき」とされる。(c) の項目の例は、拒否の理由の語がそのコマンドの事前条件の意味と合っているか、コマンドの事後条件がコマンドの名前と受け付ける例に合っているか、用語の定義が使われている文脈と合っているか（どれも DDD の判断を含むので、項目の中身は推測）。レビューは PR の承認の場で行い、目的と測定可能な終了基準（例：(c) の項目に未解決の指摘が無い）を先に決める。

  3. 問い1の続き：宣言とテスト実装の突き合わせがあれば、宣言どうしの検査は要らないのではないか

    要る。宣言とテスト実装の突き合わせは、宣言を正としてテストがそれに合うかを見る検証であり、宣言そのものが誤っている・互いに矛盾していることは見つけない。検証だけで正しいシステムができると期待するのは「「欠陥ゼロ」の落とし穴」に当たる。また、初期の作業成果物の欠陥が検出されないと、後半の作業成果物の欠陥につながることが多い。この構成では AI が宣言から実装とテストの両方を書くので、宣言どうしのずれは実装とテストへ同じ形で写り、テストは合格する。宣言どうしの静的テストは、動的テストでは見つからないこの種の欠陥を見つける唯一の場所である。

  4. 問い2：上流の変更を ID とハッシュ値で下流へ伝える設計は妥当か

    妥当である（条件付き）。トレーサビリティの価値の1つは「変更の影響を判断できる」ことであり、構成管理は構成アイテムを他の構成アイテムと関連付けてトレーサビリティを維持する。宣言どうしの ID の参照は、その関連付けそのものである。ベースラインは承認された構成アイテムで、以後の変更は正式な変更コントロールプロセス（ここでは PR）を経る。影響度分析は「変更の影響が及ぶ」部分を示すもので、変更の前に行うことがある。したがって、PR の中で、変わった上流と、それを参照する下流の一覧を出すのは原典に沿う。条件は3つ：(1) 確かめた時点の上流のハッシュ値は宣言の外の記録に置き、道具の操作で更新する（案D）、(2) ハッシュ値は上流の要素のうち、下流の期待する結果を決める欄だけから作る、(3) どの参照で伝えるかを、テストの期待する結果に効くかどうかで決める。

  5. 問い2の続き：どの参照で伝え、どの参照で伝えないか（テストの観点）

    伝える：下流のテスト条件の期待する結果が、上流の中身で決まる参照。scenario.steps[].invokes（コマンドの事前条件 ・ 拒否の理由 ・ 事後条件 ・ 業務イベント）、extensions[].guarantees_hold（最低保証の文）、commands[].preconditions[].reject（用語の定義）、状態 ・ 引数の型（値オブジェクトの不変条件。境界値がここから決まる）、steps[].quality（品質の要求の値）、preconditions[].established_by（相手のユースケースの成功時保証）、サブドメインの business_logic（求めるテストレベルが変わるので、ハッシュ値ではなく求めるレベルの再計算として伝える）。伝えない：名前 ・ 説明 ・ 表示のラベルだけの変更、stakeholders ・ serves ・ satisfies ・ protects のように利害関係者を指すだけの参照（テストの期待する結果を決めないので、レビューの対象にとどめる）。区切られた文脈の context_map ・ published_language は、公開された言葉の契約試験が実装の定義の側にあるので、この道具の伝える範囲から外す（推測。ddd-advisor の判断）。

  6. 問い3：宣言どうしのずれを、6種の判定と終了基準にどうつなぐか

    6種は増やさず、2か所でつなぐ。(1) テスト条件のハッシュ値に、期待する結果を決める上流の要素のハッシュ値を1段だけ含める。これで上流が変わると、下流のテスト条件が既存の判定「古い」になり、確認テストとリグレッションテストの対象が影響度分析の結果として出る。(2) 終了基準に、宣言どうしのずれの件数を別に置く。終了基準の完了基準には「静的テストの実行」と「発見したすべての欠陥のレポート」が、徹底度の測定には「未解決欠陥の数」が含まれる。したがって、すべてのテスト条件が合格でも、(a) ・ (b) のずれ ・ 「確かめ直しが必要」の参照 ・ (c) の未解決の指摘が1件でも残っていれば、終了基準を満たしたとは言わない。例外は、ステークホルダーがリスクをレビューして受け入れた場合だけで、それは前回の「免除」と同じく宣言の側に理由を書いて PR で承認したものに限り、テスト完了レポートの残存リスクとして出す。

  7. 問い3の続き：テスト条件ごとに止めるか、全体で止めるか

    テスト条件ごとに数える。ずれが関わる宣言の要素から取り出したテスト条件は、テストの記録が pass でも、ずれが解決するまで「合格」に数えない（判定は6種のまま、集計の段で除く）。ずれと無関係のテスト条件の判定は止めない。開始基準を満たさないまま活動を進めると、より困難になり、リスクが高くなる可能性があるとされるので、全体を止めるのではなく、リスクのある所だけを合格から外す。宣言を直したら、テストコントロールとして、そのテスト条件の開始基準と終了基準の充足を評価し直す。

  8. 問い4：見本のずれ7件のうち、テストに影響するものはどれか

    7件すべてがテストに影響する。影響の形は2つに分かれる。期待する結果そのものが誤る（テストが誤った実装を合格にする）のは 1 ・ 2 ・ 3 の3件で、優先して直す。トレーサビリティが切れて、上流の変更がテストへ伝わらない ・ カバレッジを測れないのは 4 ・ 5 ・ 6 ・ 7 の4件である。1件ずつの判定は「具体例」の欄に置く。

設計の手順

  1. 宣言どうしの静的解析を、道具の検証に (a) から足す

    いまの「ID が一意」「参照が解決する」に、テストの期待結果を誤らせる (a) を足す：型の不変条件の範囲と、集約の不変条件 ・ 事前条件 ・ 例の値の食い違い（ずれ3）、同じ集約の2つのコマンドで事後条件が完全に一致（ずれ2）、どの条件にも使われない引数（ずれ2）、別の集約の事前条件が同じ拒否の理由を参照（ずれ1）。見つけたものは、静的テストの欠陥として、動的テストの欠陥と同じく ID と状態（未解決 ・ 解決済み ・ 免除）を持たせて報告する。

  2. 確認の記録を、宣言の外に置く

    参照1件ごとに（参照元の要素の ID ・ 参照先の要素の ID ・ 確かめた時点の参照先のハッシュ値）を持つ。道具は、現在の参照先のハッシュ値と違う参照を「確かめ直しが必要」として出す。記録の更新は道具の更新の操作で行い、PR の描画に参照先の差分と参照元を並べて出す。PR の承認で記録が新しいベースラインになり、以前のベースラインへは git で戻れる。AI に記録を直接書かせない。

  3. テスト条件のハッシュ値に、上流のハッシュ値を1段だけ含める

    UC-1.EXT-2 なら、UC-1 の自分の欄に加えて、invokes の先 AGG-2.CMD-1 の事前条件 ・ 拒否の理由 ・ 事後条件の欄のハッシュ値を含める。上流の要素のハッシュ値は、その要素の自分の欄だけから作ったものを使い、上流の上流は含めない。範囲は推測であり、見本で、1か所の変更で古くなるテスト条件の件数を数えて直す。

  4. 終了基準に、宣言どうしのずれを足す

    宣言の集合の終了基準を、前回の（すべてのテスト条件が合格 ・ 余り0件 ・ 報告の誤り0件）に、（宣言どうしの静的解析の未解決0件 ・ 確かめ直しが必要な参照0件 ・ レビューの未解決の指摘0件）を足したものにする。ずれが関わる宣言の要素から取り出したテスト条件は、ずれが解決するまで合格に数えない。残すときは免除として宣言の側に理由を書き、PR で承認したものだけを数えて、テスト完了レポートの残存リスクに出す。

具体例

  • ずれ1（AGG-2.CMD-1.PRE-1 の拒否の理由が TERM-13「明細の無い注文は確定できない」を指す）：テストに影響する（期待する結果が誤る）。テスト条件 AGG-2.CMD-1.PRE-1 は「その拒否の理由で拒否される」を確かめるので、AI が書くテストは TERM-13 で拒否されることを期待し、その誤った実装が合格する。UC-1 の 3a のシステムテストも、どの拒否を受けて分岐するかが誤る。分類は (a) で一部を検出できる：同じ拒否の理由の用語を、別の集約の事前条件が参照していれば警告にする（拒否の理由は事前条件ごとに固有、という規則を置くかは DDD の判断で推測）。意味の正しさは (c)
  • ずれ2（AGG-2.CMD-2 戻す の事後条件が、確保する と同じ「空きが空でない」）：テストに影響する（期待する結果が弱い）。事後条件から導くテストは、空きを戻さない実装でも合格する。受け付ける例 OK-1「空き3の枠へ2つ戻す → 空きが5になる」には正しい期待結果があるので、テストの期待結果は事後条件でなく例から取らせる。分類は (a) で検出できる：同じ集約の2つのコマンドの事後条件が完全に一致する、引数 ARG-1 がどの条件にも使われていない、の2つを道具の警告にする。最低保証 MG-2 はこのコマンドに依存するので、ずれ7と合わせて UC-1.EXT-3 のテストも誤った実装を通す
  • ずれ3（AGG-2 の引数「数量」TERM-3 の定義が「1つの明細で注文する商品の個数」）：テストに影響する（テストデータが誤る）。見本では、AGG-2 の状態「空き」の型も VO-1 であり、VO-1 は「1以上」「99以下」を不変条件に持つ。一方 AGG-2 の INV-1 は「空き ≥ 0」、CMD-1.PRE-1 の例は「空き0の枠から1つ確保する」である。境界値分析は型の不変条件から境界値（1 ・ 99）を取るので、空き0という拒否のテストの入力は VO-1 では作れず、INV-1 の境界0とも食い違う。この数値の食い違い（型の不変条件の範囲と、集約の不変条件 ・ 例の値）は (a) で道具が検出できる。用語の意味が調理枠の文脈に合わないことは (c)（DDD の判断で推測）
  • ずれ4（UC-1 手順3 が呼ぶ AGG-2.CMD-1 の拒否と、拡張 3a が結ばれていない）：テストに影響する（トレーサビリティが切れる）。いま UC-1.EXT-2 のハッシュ値は UC-1 の欄だけから作るので、AGG-2.CMD-1 の拒否が変わってもシステムテストは「古い」にならない。また「呼ぶコマンドの拒否の理由が、どれかの拡張で扱われている」をカバレッジとして測れない。(b) で検査できる：拡張に、扱う拒否の理由への参照を足す（欄の名前と置き場所は usecase-advisor ・ ddd-advisor の判断で推測）。足せば、拒否の理由ごとに拡張が1つ以上あるかを道具が数えられ、拒否が変わったときに 3a のテスト条件が「古い」になる
  • ずれ5（UC-1 の事前条件 PRE-2 と AGG-1.CMD-1.PRE-2 の対応が文だけ）：テストに影響する（テストレベルの重複を決められない）。ユースケースの事前条件はシステムテストでは成り立つ前提として置き、明細0件の拒否はコンポーネントテスト AGG-1.CMD-1.PRE-2 で確かめる、という分担を、対応が無いと道具が判定できない。AGG-1.CMD-1.PRE-2 が変わっても UC-1 側は「確かめ直しが必要」にならない。(b) の候補だが、テストの判定に使うのは「分担の記録」と「変更を伝える」だけなので、足すかどうかは ずれ4 より優先度が低い（事前条件をどう書くかはコーバーンの判断で推測）
  • ずれ6（成功時保証 SG-1 と AGG-1.CMD-1 の事後条件の対応が文だけ）：テストに影響する（トレーサビリティが切れる）。SG-1 は「確定済になる」と「確定した合計額だけが請求される」の2つを含み、AGG-1.CMD-1 の事後条件は前者しか持たない。対応が無いと、SG-1 のどの部分がコンポーネントテストで確かめ済みで、どの部分がシステムテストでしか確かめられないかを道具が出せない。(b) で一部を結べるが、成功時保証がすべて満たされるかは (c)
  • ずれ7（最低保証 MG-2 が 4a1 の AGG-2.CMD-2 でしか成り立たない）：テストに影響する。4a1 を消すと UC-1.EXT-3 のハッシュ値が変わるのでテストは「古い」になるが、テストを直すときに MG-2 の確かめ方まで直す保証は無い。さらに ずれ2 のため、CMD-2 が空きを戻さなくても MG-2 のテストが「調理枠の確保が残らない」を空きの値で確かめていなければ合格する。テストの側では、UC-1.EXT-3 のテストに MG-2 を空きの値で確かめることを求める。宣言の側では、最低保証を成り立たせる手順への参照を (b) で足せば、手順を消したときに道具が検出できる（どこに置くかはコーバーンの判断で推測）

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI が「確かめ直しが必要」を消すために、下流を読まずに確認の記録だけを更新する確認の記録の変更を含む PR では、記録が変わった参照ごとに参照元の要素の差分か、PR の承認のコメントがあるかを道具が数え、どちらも無い参照を警告にする
AI がテストの期待結果を、受け付ける例ではなく弱い事後条件（not_empty など）から書く事後条件の演算子が not_empty だけで引数を参照しないコマンドを道具が一覧にし、そのテスト条件の報告に case（受け付ける例の ID）があるかを突き合わせる
AI が境界値のテストデータを、集約の不変条件と型の不変条件の片方だけから作る状態 ・ 引数ごとに、型の不変条件の範囲と、集約の不変条件 ・ 事前条件 ・ 例の値を並べ、範囲の外の値を道具が検出する（見本では AGG-2 の空き0）
