ddd-advisor の回答 ・ 設計相談

宣言（ドメイン ・ サブドメイン ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス）どうしで、ずれてはいけない関係はどれか。どれを道具が構造で検査し、どれに対応の欄を足し、どれを人のレビューに残すか。参照される宣言が変わったときに、参照する宣言を「確かめ直しが必要」と判定する仕組みは妥当か。見本（来店前注文）で見つかったずれ7件をどう判定するか。

結論

採る

宣言どうしのずれは、(a) 同じ言葉が区切られた文脈の内側で1語1義になっているか、(b) ユースケースの手順が呼ぶコマンドの拒否 ・ 事後条件 ・ 補償がユースケースの拡張と保証に対応しているか、(c) 業務領域のカテゴリーと業務ロジックの実装方法が一致しているか、の3つの観点で検査し、確かめ直しは同じ区切られた文脈の内側では参照をたどって伝え、文脈をまたぐときは公開された言葉を通るものだけを伝える。

判断基準は、同じ言葉の一貫性を区切られた文脈の内側に限り、コマンドが業務ルールと不変条件に違反する状態を防ぎ（拒否される可能性がある）、複数の集約にまたがる業務プロセスは補償アクションで一貫性を確保するとし、下流への影響は公開された言葉を維持できるかで判断するとしている。この4つが、ずれてはいけない関係と、伝える範囲をそのまま決める。

判断の道筋

  1. ずれ1：AGG-2.CMD-1 の拒否の理由が、AGG-1 の拒否の理由の語（TERM-13「明細の無い注文は確定できない」）を指している

    (a) で検出できる誤りである。拒否の理由は、そのコマンドが守る業務ルールと不変条件に固有のもので、同じ拒否の理由の TERM を2つの集約のコマンドが指すことは、1つの用語に1つの意味の条件に反する兆候になる。道具は「同じ拒否の理由の TERM を別の集約から指していたら警告」を持つ。直し方は、BC-1 の同じ言葉に、調理枠の空きが足りないことを表す拒否の理由を足し、AGG-2.CMD-1.PRE-1 からそれを指す（語は業務エキスパートとの会話で決める）。

  2. ずれ2：AGG-2.CMD-2 戻す の事後条件が、確保する と同じ（空きが空でない）

    兆候は (a)、意味は (c) である。同じ集約の2つのコマンドの事後条件が同じで、どちらも引数を参照していないことは構造で警告できる。ただし本当の問題は、事後条件の書き方が「前の空きに引数を足した値」のような、コマンドを実行する前の状態を参照できないことにある（推測）。コマンドは業務ルールと不変条件に違反した状態を防ぐものなので、事後条件が名前と合わないと、補償（ずれ7）が成り立つかを誰も検査できない。条件式で実行前の状態の値を指せるようにすれば、確保する は「空き＝前の空き−引数」、戻す は「空き＝前の空き＋引数」と書け、2つが逆の変化であることも構造で検査できるようになる（推測）。

  3. ずれ3：AGG-2 の引数「数量」の用語の定義（1つの明細で注文する商品の個数）が、調理枠の文脈と合わない

    意味は (c) だが、その結果は (a) で出る。1つの文脈の中で「数量」を2つの意味（明細の個数と、調理枠から取る量）で使っており、1つの用語に1つの意味の条件に反する。さらに、同じ VO-1 を空きの型にも使ったため、VO-1 の不変条件（1以上）と AGG-2.INV-1（空き ≥ 0）が両立しなくなっている ── これは手順5の検査で構造として検出できる。直し方は、調理枠の量と空きを表す用語を同じ言葉に足し、それぞれの値オブジェクトを分けることである。AGG-2 の状態の名前（開始時刻 ・ 空き）が TERM を指さず文字で書かれていることも、(a) で検出すべきずれである。

  4. ずれ4：UC-1 手順3 が呼ぶ AGG-2.CMD-1 の拒否（空きが無い）に対応する拡張は 3a だが、宣言はそれを結んでいない

    (b) である。判断基準は、コマンドは「拒否される可能性がある」とする。手順が呼ぶコマンドの事前条件ごとに、それを扱う拡張か、起こらないとするユースケースの事前条件があるはずで、拡張の側にコマンドの事前条件の ID（AGG-2.CMD-1.PRE-1）を指す欄を足せば、扱われていない拒否を構造で出せる。指す先は拒否の理由の TERM ではなく、事前条件の ID にする ── TERM はずれ1のように別の集約と重なりうるが、事前条件の ID は1つのコマンドに固有である。

  5. ずれ5：UC-1 の事前条件 PRE-2（カートに1品以上）が AGG-1.CMD-1.PRE-2（明細の件数は1以上）を満たすことは、文でしか分からない

    (b) で、ずれ4と同じ欄の組で扱う。ユースケースの事前条件の側に、それが起こらないようにするコマンドの事前条件の ID を指す欄を足すと、「AGG-1.CMD-1 の PRE-1 ・ PRE-2 のどちらも、拡張でもユースケースの事前条件でも扱われているか」を1つの規則で検査できる。見本では AGG-1.CMD-1.PRE-1（注文の状態は下書き）を扱う拡張も事前条件も無い。あわせて、「カート」は BC-1 の同じ言葉に無く、AGG-1 の「明細」との関係が宣言から分からない。これは (c) で、同じ言葉に足すかを業務エキスパートと決める。

  6. ずれ6：成功時保証 SG-1（確定済になる）と AGG-1.CMD-1 の事後条件の対応は、文でしか分からない

    (b) である。成功時保証に、それを成り立たせるコマンドの事後条件の ID（AGG-1.CMD-1.POST-1）を指す欄を足す。足すと、成り立たせる事後条件が無い保証が構造で出る。見本では、SG-1 の「確定した合計額だけが請求される」、SG-3 の「承認番号と確定した合計額が注文に記録される」、手順5 の「承認番号と確定した合計額を注文に記録する」を成り立たせる引数 ・ 状態 ・ 事後条件が AGG-1 に無い。これは指す欄を足して初めて見えるずれで、AGG-1 に承認番号と合計額の状態を足すか、保証を別のコマンドで成り立たせるかは (c) である。

  7. ずれ7：最低保証 MG-2（調理枠の確保が残らない）は、4a1 の AGG-2.CMD-2 でしか成り立たない。手順を消すと最低保証が成り立たなくなる

    (b) で、判断基準のサーガの補償アクションにあたる。UC-1 は AGG-2（手順3）と AGG-1（手順5）を別々のトランザクションで変えるので、手順4 の失敗では、前に確保した調理枠を補償アクションで戻すしかない。集約の側では、戻すコマンドに「どのコマンドを補償するか」を指す欄（AGG-2.CMD-2 → AGG-2.CMD-1）を足す。すると「失敗で終わる拡張が MG-2 を成り立つと言うなら、それより前の手順で invokes した、補償するコマンドを持つコマンドが、すべて拡張の中で補償されている」を構造で検査でき、4a1 を消せば検出される。補償するコマンドの事後条件が逆の変化になっているかは、ずれ2の書き方を直すまで (c) である。MG-3（どこまで進んだかを残す）も、4a2 が何も invokes せず、AGG-1 に経過を持つ状態が無いので、成り立たせる宣言が無い。

  8. 追加1：AGG-2 の空き（型 VO-1）と、AGG-2.INV-1（空き ≥ 0）・ 例「空き0の枠」が両立しない

    (a) で検出できる。値オブジェクトの不変条件は、それを型に持つ集約の不変条件 ・ 事前条件と両立しなければならない。ずれ3と同じ原因で、空きに専用の値オブジェクトを置けば解消する。

  9. 追加2：DS-1 の入力「明細の数量の合計」が VO-1（99以下）で、AGG-1 の明細は20件まで持てる

    (a) で検出できる（範囲の比較）。VO-1 の操作「足す」も VO-1 を返すので、合計が99を超えると値オブジェクトの不変条件に反する。合計を表す用語と値オブジェクトを分けるかは (c) である。

  10. 追加3：AGG-2 の状態の名前（開始時刻 ・ 空き）が、同じ言葉の TERM を指さず文字で書かれている

    (a) で検出できる。集約 ・ フィールド ・ メソッド ・ 業務イベントの名前は区切られた文脈の同じ言葉で命名する、という判断基準に対し、同じ言葉に無い名前が集約に入っている。

  11. 追加4：SD-2（一般 ・ 外部サービス）の business_logic で needs_tracking が真

    (a) で不一致を出し、(c) で判定する。問いの順ではイベント履歴式ドメインモデルが導かれるが、一般の業務領域は外部サービスを使うので、自分たちが実装するのは連係の部分である。sourcing が外部サービスのサブドメインでは実装方法を導かない、という規則を道具に足すのがよい（推測）。

設計の手順

  1. (a) ドメイン ↔ サブドメインを構造で検査する

    ドメインの subdomains がすべてのサブドメインを含み、サブドメインの serves_values がドメインの提供価値を指すことを検査する（参照 ・ 集合の包含）。differentiator が真の提供価値を、中核でないサブドメインだけが担っているときは警告にする（判断基準の「差別化が大きい」と「中核」の対応から。判定は人のレビュー）。見本は VAL-1（差別化）を SD-1（中核）が担っており、合っている。

  2. (a)＋(c) サブドメインのカテゴリー ↔ business_logic ↔ 実装方法 ・ テスト方針を検査する

    business_logic の3つの値から、判断基準の問いの順（経緯を追う必要 → イベント履歴式ドメインモデル、業務ルールが複雑 → ドメインモデル、データ構造が複雑 → アクティブレコード、どれでもない → トランザクションスクリプト）で実装方法を道具が導き、テスト方針（ピラミッド形 ・ ダイヤモンド形 ・ 逆ピラミッド形）も導く（構造）。導いた実装方法とカテゴリーが合わないとき（中核なのにアクティブレコード以下、補完なのにドメインモデル以上）は、道具は不一致を出すだけにし、判定は人のレビューに渡す。判断基準は、この不一致を「業務領域と事業活動についての判断を再検討する機会」としており、どちらかを機械で直す対象にしていない。見本の SD-2（一般 ・ 外部サービス）は needs_tracking が真で、問いの順ではイベント履歴式ドメインモデルになる。外部サービスを使う一般の業務領域では、自分たちが実装するのは連係の部分なので、sourcing が外部サービスのときは実装方法を導かない、という規則を道具に持たせるのがよい（推測）。

  3. (a) サブドメイン ↔ 区切られた文脈を構造で検査する

    すべてのサブドメインが、少なくとも1つの区切られた文脈の subdomains に入っていることを検査する。一対一は検査しない ── 判断基準は、業務領域と区切られた文脈を一対一に限定することをアンチパターンとしている。中核のサブドメインを含む文脈の context_map.relations に「従属」があれば警告にする（中核を他の文脈と連係するときは、モデル変換装置か公開された言葉を使う）。「互いに独立」も、中核を含む文脈では警告にする。

  4. (a)＋(c) 区切られた文脈の同じ言葉 ↔ 各宣言の名前を検査する

    構造で検査できるもの：集約 ・ 値オブジェクト ・ ドメインサービス ・ コマンド ・ 業務イベント ・ 状態 ・ 引数 ・ 拒否の理由の名前が、その宣言の context が指す文脈の同じ言葉の TERM を指している（別の文脈の TERM を指したら誤り）。TERM の kind と、それを指す欄の種類が一致する（コマンドの name は kind がコマンドの TERM）。1つの文脈の中で同じ word が2回出ない（1つの用語に1つの意味）。avoid に挙げた語が、同じ文脈の宣言の文に出ない。使われていない TERM を出す。人のレビューでしか見られないもの：TERM の definition が、それを使う集約 ・ コマンドの中で同じ意味になっているか（見本のずれ3）。

  5. (a) 値オブジェクト ↔ 集約の不変条件 ・ 事前条件が両立するかを検査する

    状態 ・ 引数の型に値オブジェクトを指したとき、値オブジェクトの不変条件と、集約の不変条件 ・ 事前条件 ・ 受け入れの例が両立するかを、条件式どうしで検査する。条件が機械の読める形（target ・ op ・ value）で書かれているので、範囲の比較なら構造で検査できる。見本では、AGG-2 の空き（型は VO-1、VO-1 は1以上）と AGG-2.INV-1（空き ≥ 0）・ 例「空き0の枠」が両立しない。

  6. (a)＋(c) 集約の内側（不変条件 ・ コマンド ・ 業務イベント）を検査する

    構造で検査できるもの：emits[].fields[].from が自分の集約の状態を指す。同じ集約の2つのコマンドの事後条件が同じで、どちらも引数を参照していなければ警告にする（見本のずれ2の兆候）。同じ拒否の理由の TERM が、別の集約のコマンドから指されていたら警告にする（見本のずれ1）。他の集約は ID で指す（状態の型に別の集約の ID 以外を置かない）。人のレビューでしか見られないもの：コマンドの事後条件が、名前の表す状態の変化と合っているか。業務イベントの名前が過去形か（TERM の word を文字で検査する規則は置けるが、日本語では推測）。

  7. (a)＋(c) ドメインサービス ↔ 集約を検査する

    構造で検査できるもの：reads が同じ文脈の集約を指す。inputs の型が、読む集約の状態の型と合う。人のレビューでしか見られないもの：ドメインサービスが集約の状態を変えていないか（判断基準は、複数の集約を1つのトランザクションで変えることをアンチパターンとする）。見本の DS-1 は「明細の数量の合計」を VO-1（99以下）で受けるが、AGG-1 は明細を20件まで持てるので、合計が VO-1 の不変条件を超えうる（範囲の比較で構造でも検出できる）。

  8. (a) 区切られた文脈 ↔ 公開された言葉 ↔ 業務イベントを検査する

    published_language.from_event が、同じ文脈の集約が出す業務イベントを指すことを検査する。別の文脈の宣言は、相手の文脈の公開された言葉だけを指し、相手の同じ言葉の TERM や集約を直接指さないことを検査する。公開された言葉が内部の業務イベントをそのまま写しているか（判断基準のアンチパターン）は人のレビューに残す。

  9. (a) ユースケース ↔ 区切られた文脈を検査する

    手順の invokes が指すコマンドの集約が、ユースケースの scope.context と同じ文脈にあることを検査する。別の文脈のコマンドを直接 invokes していたら誤りにする（文脈をまたぐ連係は、文脈の地図の関係を通る）。支援アクター（見本の決済代行）と、それを受け持つ文脈（BC-2）の対応は、宣言にどちらの参照も無いので、いまは人のレビューでしか見られない（推測）。

  10. (b) ユースケース ↔ 集約に対応の欄を足して検査する

    集約の側から見て、ずれてはいけない対応は4つである。①手順が呼ぶコマンドの事前条件（拒否されうる条件）のそれぞれが、その手順の拡張で扱われるか、ユースケースの事前条件で起きないと決まっているか。②成功時保証のそれぞれが、どのコマンドの事後条件で成り立つか。③失敗で終わる拡張が成り立つと言う最低保証のうち、確保したものを残さないもの（見本の MG-2）について、それより前の手順で呼んだコマンドを補償するコマンドが拡張で呼ばれているか。④ユースケースの手順が「記録する」と言う値が、呼ぶコマンドの引数か事後条件にあるか。足す欄は記録案に書いた。

  11. 確かめ直しを伝える範囲を、参照の種類ごとに決める

    伝える：同じ言葉の TERM（word ・ definition）→ それを名前に持つ宣言。値オブジェクトの不変条件 → それを型に持つ集約 ・ ドメインサービス。コマンドの事前条件 ・ 事後条件 ・ 引数 → それを invokes する手順と、それを指す拡張 ・ 保証。サブドメインの business_logic とカテゴリー → 実装方法とテスト方針（テストとのドリフトのレベル違いの判定へ）。公開された言葉 → それを指す別の文脈の宣言。伝えない：集約の内部の状態 ・ 業務イベント ・ TERM の変更を、別の文脈の宣言へ直接伝えない（公開された言葉の値が変わったときだけ伝える）。ユースケースの変更を集約へ伝えない（参照の逆向き。足りないコマンドは参照が解決しないことで出る）。description ・ example ・ avoid の変更は伝えない（ハッシュ値の対象から外す。avoid は文の検査で足りる）。

アンチパターンリスク代替案
業務領域と区切られた文脈を一対一に限定する「サブドメイン1つに文脈1つ」を道具の検査にすると、1つの業務領域に複数の課題があっても別々のモデルを作れず、課題解決の柔軟性が失われる道具が検査するのは「すべてのサブドメインが、少なくとも1つの文脈に入っている」までにし、対応の数は検査しない
共用サービスを非同期メッセージングで実装するときに、内部モデルのオブジェクトや業務イベントを、そのまま公開された言葉として外部へ送信する区切られた文脈の内部モデルが外部に露出する。宣言では、別の文脈の宣言が相手の集約 ・ TERM を直接指し、内部の変更のたびに確かめ直しが文脈の外へ広がる業務イベントを横取りして公開された言葉へ変換し、内部イベントと公開イベントを区別する。宣言では、別の文脈からは公開された言葉の ID だけを指せるようにする
集約境界の設計が不適切なことを、サーガで補う集約の境界の外側のデータは結果的に整合するだけなので、強い一貫性を必要とする業務処理の要求を満たせない。UC-1 で注文の確定と調理枠の確保を補償でつなぐのは、両者が結果的に整合すればよいと判断したときだけ成り立つ強い一貫性が保証されたデータを必要とする業務処理は、同じ集約に所属させる。見本の SH-2「調理の空きを超えて注文を受けない」は AGG-2 の内側の不変条件で守られており、補償でつないでよい
（推測）対応の欄をすべての組に足すAI が宣言を書くたびに ID を大量に書き、人は描画でも対応の表を読み切れない。欄が多いほど、欄どうしのずれ（宣言どうしのドリフトそのもの）も増える足すのは、構造で検査する規則が1つ以上あるものに限る（記録案の4つ）。導けるもの（TERM の重なり ・ 不変条件の両立 ・ 実装方法）は欄を足さず、道具が導く。描画では、コマンドの事前条件ごとに「扱った拡張 ・ ユースケースの事前条件」の表を道具が組み、人は空いた行だけを見る
（推測）宣言のファイル全体のハッシュ値で確かめ直しを伝えるdescription や受け入れの例の書き直しだけで、参照するすべての宣言が確かめ直しの対象になり、本当に必要な確かめ直しが見落とされる参照される要素の ID ごとに、期待を決める欄（条件 ・ 拒否の理由 ・ 型 ・ TERM の word と definition）だけでハッシュ値を取る
