結論

採る

ユースケースの宣言は完全形式のテンプレートの欄をすべて構造化して持ち、手順を「主語 ・ 種類 ・ 文」の組に、拡張を「結び付く手順 ・ 条件の種類 ・ 条件 ・ 処理 ・ 終わり方」の組に固定し、終わり方の列挙値で、試験が成功時保証と最低保証のどちらを検証するかを一意に決める。

判断基準は、書き手に会話で確認できない状況では完全形式で厳密に書くこととし、主成功シナリオと拡張を同じアクションステップの規則で書き、拡張は主成功シナリオへ戻るか失敗するまで書くとしている。この規則を列挙値と構造へ移せば、AI の出力がぶれる範囲は1手順の文の中だけに狭まる（狭まるという見込みは推測）。

設計の手順

  1. 欄を完全形式のテンプレートに合わせて置き、必須を決める

    名前 ・ スコープ ・ レベル ・ 主アクター ・ 利害関係者と関心 ・ 事前条件 ・ 最低保証 ・ 成功時保証 ・ トリガー ・ 主成功シナリオ ・ 拡張 ・ 技術およびデータのバリエーション ・ 関連情報に、前提の3欄（寄与する達成の基準 ・ 書き換える集約 ・ サーガ）を加える。一覧と各欄の x-prompt.write は記録案の表が保持する。判断基準は、書き手に会話で確認できないときは完全形式で厳密に書き、利害関係者と利益 ・ 事前条件 ・ 最低保証に特に注意するとしている。

  2. x-prompt.write に書く順序を固定する

    利害関係者と関心 → 最低保証と成功時保証 → トリガーと事前条件 → 主成功シナリオ → 拡張の条件の一覧（処理は空のまま）→ 拡張の処理、の順に書かせる。判断基準は、主成功シナリオの前に保証を書くこと、処理を書く前に失敗条件のリストを書き上げることを求めている。承認も「条件の一覧」と「処理」の2段に分けると、条件の漏れを処理の量に隠されずに確認できる（2段の承認は推測）。

  3. 手順を「主語 ・ 種類 ・ 文」の組に固定する

    actor は主アクター ・ 支援アクターの名前 ・「システム」の列挙から選ばせ、text をその語で始めさせる。kind は判断基準の3種類（相互作用 ・ 妥当性確認 ・ 内部の状態変化）にサブユースケースの呼び出しを足した4値で、1手順に1つ（1手順1種類は推測。判断基準は4つの部品をまとめてもよいとするが、5つに分けた形を「各ステップを別々にテストできるので、形式を重んじる開発には向く」とする）。相互作用は to と data（情報の別名）、妥当性確認と内部の状態変化は serves（守る利害関係者）、内部の状態変化は aggregate、呼び出しは calls を持たせる。UI の操作 ・ if ・ 項目の一覧 ・ 技術の語を書かせない。

  4. サブユースケースの呼び出しを手順の種類として書かせる

    kind をサブユースケースの呼び出しにし、calls に UC の ID を入れ、text は「<主語>は、<呼び出す UC の名前>」の普通の文にする（「〜を使用する」と書かない）。主成功シナリオから呼んだら、condition_kind が「呼び出したユースケースの失敗」の拡張を必ず付ける。呼び出し側で成り立たせた条件は、呼ばれる側の事前条件に書き、呼ばれる側で確認し直さない。ユースケース同士の関係は呼び出しだけにし、拡張ユースケース（extend）を宣言に置かない。

  5. 拡張を「結び付く手順 ・ 条件の種類 ・ 条件 ・ 処理 ・ 終わり方」の組に固定する

    label は判断基準の番号の形（4a ・ 2-5a ・ *a、処理の手順は 4a1）にし、anchor は実在する手順番号を指させる。condition は検出されたことを表す句で、末尾をコロン（：）にする。condition_kind は判断基準のブレーンストーミングの8項目に「呼び出したユースケースの失敗」と「主アクターの取りやめ」を足した列挙（足した2つは推測。取りやめは判断基準のトリガーの例「ユーザーがキャンセルボタンを押す」が拡張条件であることに拠る）。処理は検出のあとから書き、主成功シナリオと同じ手順の規則で書く。ending は列挙［元の手順が成功した状態で合流する ・ 同じ手順へ戻る ・ 失敗する ・ 別の道筋で成功して終了する ・ 手順へ移る（to が必須）］を必須にする。判断基準は前2つで終わりを書かなくてよいとするが、宣言では欄に値を持たせ、描画で省く（推測）。入れ子は2段までとし、3段目が要るなら別のユースケースに切り出す。

  6. 失敗で終わる拡張を最低保証の試験にする

    ending が「失敗する」の拡張は、すべての最低保証を検証し、成功時保証が成り立たないことも検証する。それ以外の終わり方は、すべての成功時保証を検証する（成功時保証は「主成功シナリオを通っても、別の道筋を通って成功しても、同じく成り立つ」）。失敗で終わる拡張の処理には、記録の手順（進み具合を残す内部の状態変化）を置かせる。判断基準は、どの失敗処理でもログや回復のための情報が残るかを確認するよう求めている。

  7. 目的レベルごとに置く量を決める

    宣言の中心はユーザー目的に置く。サブ機能は「複数のユースケースから呼ばれる」か「呼び出し側を読みにくくする」のときだけ独立させ、reason_for_split に書かせる。要約は文脈の中で順序と目次を示す分だけ書き、手順をすべてサブユースケースの呼び出しにする。要約の試験は呼び出しの順序と、呼び出しが失敗したときの拡張だけを検証し、呼ばれる側の中身を試し直さない（試験の扱いは推測）。文脈をまたぐ要約は差し戻しに置く。

  8. 出力を安定させる範囲を決める

    自由文は、名前 ・ 各保証の文 ・ 事前条件の文 ・ トリガーの event ・ 手順の text ・ 拡張の condition ・ バリエーションの値だけにする。それ以外（レベル ・ トリガーの種類 ・ 手順の種類 ・ 主語 ・ 条件の種類 ・ 終わり方 ・ 結び付く手順 ・ 守る利害関係者 ・ 書き換える集約 ・ 呼び出す UC ・ サーガの手順）は列挙値か ID の参照にする。自由文にも文型（主語で始める ・ コロンで終える ・ 断定文）と禁止語（分岐の語 ・ UI の語 ・ 技術の語）を課し、機械で検査する。番号と ID は書き手に付けさせず、位置から導く（どれも推測）。

  9. 試験の ID と変換表を位置から導く

    シナリオの試験の ID は「UC の ID ＋ . ＋ 拡張のラベル」、主成功シナリオは M とする（例：UC-1.M ・ UC-1.2a ・ UC-1.2a2a）。準備は事前条件から、偽物は支援アクターと呼び出すサブユースケースから、偽物の振る舞いは condition_kind から決める（支援アクターの応答無し → 偽物が応答しない、呼び出したユースケースの失敗 → 呼ばれる側の偽物が失敗を返す、など）。範囲（2-5a）と任意の時点（*a）の拡張は、試験で条件を起こす手順が一意に決まらないので、test_at（手順番号）を必須にする。変換の規則はすべて推測であり、qa-advisor で照合する。

3. システムは在庫 API を呼び出し、stock テーブルを更新する ← 技術の語。宣言は技術を書かない

最低保証：残高不足のとき、ネットワーク停止のとき…  ← 失敗の仕方の列挙。拡張に書く
拡張 3：エラーなら適当に処理する                  ← 結び付く手順・条件の形・終わり方が無い

判断基準引用
use-case-format問い：チームが非常に大きい、各地に分散している、複数の会社で分担している、人命に関わる、のどれかに該当するか ・ 何が分かるか：該当するなら、品質の低い記述の影響が深刻になる。完全形式で厳密に書き、利害関係者と利益 ・ 事前条件 ・ 最低保証に特に注意する
use-case-format完全形式のユースケース：完全なテンプレートで、スコープ ・ レベル ・ 主アクター ・ 事前条件 ・ トリガーなどの欄をすべて記入し、プロジェクトの注釈も加えたユースケース。ステップには必ず番号を振る。
use-case-format欄：拡張 ・ 何を書くか：主成功シナリオのステップを参照し、条件と、そのときのアクションまたはサブユースケースを1つずつ書く
use-case-format観点：拡張の番号 ・ 書き方：ステップ番号のあとにアルファベットを付ける（2a、2a1、2a2 など）
use-case-format条件：分岐が2つ以上になるとき ・ 対応：if 文を使わず、代替の振る舞いを拡張として書く ・ 理由：2つ目で理解がずっと難しくなり、3つ目 ・ 4つ目や入れ子も現れて、ストーリーの筋を見失う
use-case-format対応：「ユースケースを書く」と決めるだけで済ませず、完全形式か略式か、必須の欄、書き手ごとの違いの許容範囲まで決める ・ 理由：あるプロジェクトで有効だったユースケースが、ほかでも有効とは限らない
design-scope対応：すべてのユースケースのスコープ欄に、対象システムの名前を書く ・ 理由：スコープは名前や主アクターからは読み取れないので、欄で示すしかない
use-case対応：機能要求として書くときは、対象システムをブラックボックスとして扱い、内部に触れない ・ 理由：要求は設計者の自由を奪ってはならない。よい設計を行うのは設計者の仕事である

goal-level対応：サブ機能は、何度も使うときか、切り出すと読みやすくなるときだけ独立させる ・ 理由：独立させた分だけ、保守の負担が増える
primary-actor対応：「顧客の代理の販売員」のように、操作する人と、誰の代わりかを並べて書く ・ 理由：UI やセキュリティ認証は操作する社員に合わせ、結果の良し悪しは本来の主アクターで判断する、という区別が伝わる

stakeholder対応：利益を満たすアクションとして、相互作用のほかに、妥当性確認と内部の状態変化を書く ・ 理由：相互作用だけでは目的へ進む流れしか表せず、その場にいない利害関係者を保護する振る舞いが抜ける
precondition問い：システムはそれが真であることを保証できるか ・ 何が分かるか：事前条件は、システムが真であると保証している事柄である。たいてい真でも、保証できないものは書かない
precondition問い：どのユースケースがその状態を作っているか ・ 何が分かるか：事前条件は、別のユースケースがすでに実行され、その条件を設定していることを表す
trigger問い：そのイベントでユースケースが始まるのか、実行中のユースケースの途中で起きるのか ・ 何が分かるか：始まるならトリガー、途中で起きるなら拡張条件として書く
minimal-guarantee対応：ユースケースが終了したときに必ず真になることを、いくつかの短い断定文で書く ・ 理由：この欄の目的は、システムが何を約束するかを示すことにある
minimal-guarantee対応：各文で、どの利害関係者のどの利益が満たされるかを表す ・ 理由：利害関係者ごとに守られる利益が読み取れれば、合意を取れる
minimal-guarantee対応：失敗の仕方を最低保証の欄に並べない ・ 理由：失敗の仕方は数えきれず、共通点もほとんど無い。拡張と二重に書くと、2つのリストをそろえる手間がかかり、食い違いも起きやすい
minimal-guarantee対応：主成功シナリオを書く前に保証を書く ・ 理由：必要な妥当性確認を先に思いつけるので、あとで見つけて本文を直す手戻りを避けられる
success-guarantee成功時保証：ユースケースが成功で終わったとき、つまり目的が達成されたときに満たされる利害関係者の利益。主成功シナリオを通っても、別の道筋を通って成功しても、同じく成り立つ。
success-guarantee欄：成功時保証 ・ いつ成り立つか：成功で終わったときに成り立つ ・ 何を書くか：最低保証に加えて満たされる利益。少なくとも、ユースケースのタイトルが示す目的を含む
main-success-scenarioステップ数が3から9の範囲か
main-success-scenario対応：分岐は本文から外し、成功を前提にした文にして、分岐は拡張に書く ・ 理由：成功前提の本文を読むと「そうならなかったら」と疑問がわき、読み手は拡張を探す。これでユースケースに一定のリズムが生まれる
main-success-scenario構成要素：本体 ・ 主成功シナリオ：アクションステップの並び ・ 拡張：アクションステップの並び（同じ規則で書く）
action-step対応：「主語 … 修飾語 … 目的語 … 述語」の単純な文にし、主語を省かない ・ 理由：主語を省くと、誰が動作を制御しているかが読み手に分からなくなる
action-step対応：どのステップも、動作を表す能動態の動詞を現在形で使い、アクターが目的を達成して処理を進める様子を書く
action-step対応：画面の表示やボタンのクリックではなく、ユーザーの意図と、アクター間で渡る情報を書く ・ 理由：UI の操作を書くと、長く、画面の小さな変更で成立しなくなり、UI 設計者の仕事を先取りする要求になる
action-step分け方：1つずつ分けた5ステップ ・ 評価：細かすぎてシナリオが長くなる。ただし各ステップを別々にテストできるので、形式を重んじる開発には向く
action-step「チェックする」ではなく「確認する」と記述しているか
data-requirement-precision対応：ステップには、アクターの意図を書き、渡されるデータは別名で書く ・ 理由：別名より詳しく書くと、要求の収集が長引き、ユースケースは長く読みにくく、データ要求が変わるたびに書き直す不安定なものになる
extension対応：条件は、検出されたことを表す句か文で書き、末尾にコロン（：）を付ける
extension対応：複数のステップで起こり得る条件は、「2-5a」のように範囲で書く ・ 理由：起こり得るステップごとに、同じ条件を書かずにすむ
extension対応：主成功シナリオと同じ規則で、主成功シナリオへ戻るか、ユースケースが失敗するまで書く ・ 理由：拡張は、拡張条件で始まる小さなユースケースであり、目的の達成か断念で終わる
extension対応：インデントが3段階ほどになったら、その拡張を別のユースケースに切り出す
extension対応：どの失敗処理でも、利害関係者の利益が守られ、ログや回復のための情報が残るかを確認する ・ 理由：書き手は途中で失敗が起きる場面を想定しないので、ログや回復の情報が抜けやすい
extension終わり方：ユースケース全体が失敗する ・ 拡張の最後に書くこと：「失敗する」だけ
extension項目：別の道筋での成功 ・ 主アクターの誤った振る舞い ・ 主アクターの活動の停止 ・ 支援アクターからの応答が無い、または誤っている ・ 設計対象システムの、通常の業務で起こる内部エラー ・ 予期しない異常な内部エラー ・ システムの性能上の重大な問題
extension問い：システムはその条件を検出できるか ・ 何が分かるか：検出できない出来事には反応できない。検出できる同等の条件に置き換えられないかも考える
extensionユースケースはそのまま機能テストの仕様になる。拡張はそれぞれ別の道筋なので、拡張ごとに少なくとも1つのテストケースを用意する
precision対応：第3段階では、処理を書く前に失敗条件のリストを書き上げる ・ 理由：処理を書くほうがずっと手間がかかる。見つけるたびに処理まで書くと、リストが完成する前に労力が尽きる
sub-use-case対応：呼び出し側は、サブユースケースが成功したか失敗したかだけを見て次へ移る ・ 理由：サブユースケースの中でどの道筋を通ったかは、呼び出し側には関係が無い
sub-use-case対応：主成功シナリオから呼んだなら失敗を拡張で処理し、拡張から呼んだなら成功と失敗をその拡張で処理する
sub-use-case対応：呼び出し側で成り立たせた条件はサブユースケースの事前条件に書き、中で確認し直さない
sub-use-case対応：ユースケース同士の関係には呼び出し（include）だけを使い、extend や specialize と混ぜない ・ 理由：include だけにすれば、書き手も読み手も混乱がずっと少ない
sub-use-case対応：本文に「〜を使用する」と書かず、呼び出すユースケース名に下線を引いた普通の文にする
extension-use-case対応：2つの場合のどちらでもなければ、拡張ユースケースを作らず、include を使う
supporting-actor対応：拡張条件をブレーンストーミングするときは、支援アクターからの応答が無い場合と、応答が正しくない場合を候補に入れる
technology-data-variation対応：条件やアクションステップは書かない ・ 理由：書いているなら、それはリストの使い方の誤りで、拡張に書くべきものである
technology-data-variation観点：主成功シナリオと何が異なるか ・ 拡張：システムが「何を」するか ・ 技術およびデータのバリエーション：同じことを「どのように」行うか
hub-and-spoke-model対応：優先度 ・ 発生頻度 ・ パフォーマンス要求 ・ 納品日 ・ 未決定事項などを、各ユースケースに紐づける
system-under-discussion対応：トリガーで始め、目的の達成か断念の後、対象システムがやりとりの責任を果たすまで書く
trigger種類：主アクターが直接始める ・ 中間の手段を介して始まる ・ 時間や状態で始まる

注意

アンチパターンリスク代替案
主成功シナリオの本文に「もし…ならば」で分岐を書く分岐が2つ出てくると筋書きを見失う。試験の道筋も文から読み取ることになり、一意に変換できない主成功シナリオは成功を前提に書き、分岐は結び付く手順の番号を持つ拡張に書く
画面 ・ クリック ・ 入力欄の操作を手順に書く要求文書ではなく操作の手引きになり、画面を少し変えるたびに宣言を書き直す特定の画面を決めずにユーザーの意図と渡す情報（別名）を書く
「口座残高が不足している」のような失敗条件を最低保証の欄に並べる拡張に書いた失敗条件と二重になり、2つのリストの食い違いが試験の期待値の食い違いになる失敗条件と処理は拡張に書き、最低保証には守られる利益だけを断定文で書く
システムが検出できない出来事を拡張の条件にするシステムはその条件に反応できず、試験でも条件を起こせない検出できる同等の条件（入力のタイムアウトなど）に置き換え、置き換えられなければ取り除く
サブユースケースを呼び出す手順に、呼び出した先の失敗の扱いを書かない目的が失敗したときの振る舞いと、利害関係者の利益の守り方が決まらない主成功シナリオから呼んだなら拡張に失敗の扱いを書き、拡張から呼んだならその拡張に成功と失敗の両方を書く
（推測）拡張の終わり方を文で書かせる「前の手順に戻る」「やり直す」「終了する」などの言い回しが書くたびに変わり、成功時保証と最低保証のどちらを試験するかが決まらない終わり方を列挙値の必須の欄にし、描画のときだけ判断基準の書き方（戻る場合は何も書かない）に直す
（推測）サーガの補償を拡張の手順へもう一度文で書く最低保証と拡張の二重記述と同じく、サーガの欄と拡張の手順が食い違い、サーガの試験とシナリオの試験の期待が分かれる補償の中身はサーガの欄にだけ書き、拡張の手順は compensates でサーガの手順の ID を指す
（推測）番号と ID を書き手（AI）に付けさせる書き直すたびに番号が振り直され、試験の ID が予告なく変わる手順番号と拡張のラベルは位置から導き、変わったときは承認の差分に試験の ID の変化として出す

欄：variations（技術およびデータのバリエーション）任意 ｜ 構造の並び {step、varies、values} ｜ write：手順で起きることは同じで手段やデータだけが違うものを、ドメインの語で並べる。条件と処理を書かない。技術の名前を書かない ｜ 根拠：technology-data-variation。技術の語を除くのは前提（技術を書かない）による
欄：saga（サーガ）writes_aggregates が2件以上のとき必須 ｜ 構造の並び {id：SAGA-<番号>、step、target、postcondition、compensation} ｜ write：書き換えの順に並べ、手順番号で主成功シナリオに結ぶ。補償を拡張の手順へ書き直さず compensates で指す ｜ 根拠：判断基準の範囲外（推測）
欄：annotations（繰り返し・順不同）任意 ｜ 構造の並び {kind：列挙［繰り返し ・ 順不同］、steps：範囲、until：文字列} ｜ write：手順の文に繰り返しや順番を書き込まず、この欄に置く ｜ 根拠：action-step（タイミング・繰り返し）。欄に出すのは推測
欄：links（関連情報）任意 ｜ 構造 {business_rules・data・quality：ID の並び、open_issues：文字列の並び} ｜ write：ビジネスルール・データの項目・品質の要求は本文に書かず ID で結ぶ。未決定事項は文で残す ｜ 根拠：hub-and-spoke-model ・ data-requirement-precision

差し戻し

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
ボード usecase-modeling-coding の決定「ユースケースは区切られた文脈の中に在る」判断基準は、主アクターごとに一番外側の設計スコープで最も高いレベル（要約）のユースケースを持つことを、書き終えたかの判定に含める。文脈をまたぐ要約のユースケースは、7種類の宣言のどこにも置き場が無い疑いがある。ドメインの宣言（サブドメインの一覧 ・ 範囲）に持たせるか、文脈の中の要約に限るかを決め直す必要がある
ボード usecase-modeling-coding の決定「モデリングの側は技術を書かない」判断基準の技術およびデータのバリエーションは、磁気カード ・ 網膜スキャン ・ 指紋のような技術の違いも含む。宣言ではドメインの語の手段とデータだけを残すとしたので、技術のバリエーション（コストと計画に影響するため追跡が要る）の置き場が実装の側に要る疑いがある
ボード usecase-modeling-coding の決定「サーガはユースケースの欄として持つ」判断基準は、失敗の仕方を最低保証と拡張に二重に書くと食い違うとする。サーガの補償と、拡張の処理の手順も同じ二重記述になり得る。この回答は compensates で指す形を推測で置いたが、サーガの試験とシナリオの試験の分担は qa-advisor の判断に拠る

次にすること

  • 記録案の表どおりに、ユースケースの器（JSON Schema）の欄と x-prompt.write を起こす
  • 手順の種類 ・ 拡張の条件の種類 ・ 拡張の終わり方の3つを、器の列挙値として定める
  • AI が作業するときの注意の検査を、宣言の validate に組み込む
  • 例の UC-1 を器へ書き写し、validate に通す
  • 拡張から試験の ID と検証する保証を導く変換の規則を、qa-advisor で照合する
  • 差し戻しの3件を、ボード usecase-modeling-coding の論点として起こす

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
手順の文に分岐を書く（「もし」「ならば」「場合は」「そうでなければ」「かどうか」）主成功シナリオと拡張のすべての text に、分岐の語の正規表現が当たらないことを validate で検査する
主語を省く、受け身で書く、主語と actor の欄が食い違うtext が actor の値と「は、」で始まり、末尾が「される」「られる」でないことを検査する
UI の操作や技術の語を書く（ボタン ・ クリック ・ 押す ・ 入力欄 ・ API ・ テーブルなど）禁止語の一覧（プロジェクトが保持する）を、手順 ・ 条件 ・ バリエーションの値に当てる
妥当性確認の手順に、確認できなかった場合の拡張を付けないkind が妥当性確認の手順ごとに、anchor がその手順を指す拡張が1件以上在ることを検査する
サブユースケースの呼び出しや支援アクターとの相互作用に、失敗 ・ 応答無しの拡張を付けないkind が呼び出しの手順には condition_kind が「呼び出したユースケースの失敗」の拡張が、to が支援アクターの相互作用には「支援アクターの応答無しまたは誤り」の拡張が在ることを検査する
利害関係者の関心を、保証にも手順にも反映しないstakeholders の各 ID が、最低保証か成功時保証の protects ・ satisfies と、いずれかの手順の serves に1回以上現れることを検査する
失敗で終わる拡張に、進み具合を残す手順を置かないending が「失敗する」の拡張ごとに、kind が内部の状態変化の手順が1件以上在ることを検査する
主成功シナリオの手順数が3〜9を外れる、拡張の入れ子が3段になる器の minItems ・ maxItems と、extensions の入れ子の深さを JSON Schema で制限する
拡張の anchor ・ test_at ・ 呼び出しの calls ・ 事前条件の established_by が、実在しない手順や UC を指す宣言の集合全体で参照を解決し、解決できない ID を validate の失敗にする
内部の状態変化の aggregate と writes_aggregates が一致しない、集約が2件以上なのにサーガが無い手順の aggregate の集合と writes_aggregates の集合を比べ、2件以上なら saga の必須を if-then で課す
バリエーションの値に条件や処理を書くvariations の値に「場合」「とき」と、主語で始まる文が無いことを検査する
