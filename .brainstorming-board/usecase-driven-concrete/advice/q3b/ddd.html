ddd-advisor の回答 ・ 設計相談

ユースケース以外の6種類の宣言（ドメイン ・ サブドメイン ・ 区切られた文脈 ・ 集約 ・ 値オブジェクト ・ ドメインサービス）に残る文字列の欄を、「欄から組める／欄を足せば組める／人が読む説明として残す」に分けるには、DDD の判断基準からどう組み立てるか。例（違反する例 ・ 拒否の例 ・ 受け付ける例 ・ 作れない値）を構造にする形と負担、測れる基準（品質の要求 ・ 達成の基準）の置き場所と参照先、見本で見つけたほかのずれも合わせて答える。

結論

採る

6種類の宣言の文字列の欄のうち、検知に使う意味を持つもの（集約の守る一貫性 ・ 4種類の例 ・ 状態と入力の名前と型 ・ 業務イベントの項目名 ・ 値の一覧 ・ 操作の説明 ・ ドメインサービスの理由 ・ 分類の答え ・ 関係の理由 ・ 競合との違い ・ 範囲の内側）は、既にある ID と条件の構造から組むか、真偽値 ・ 列挙 ・ ID の欄を足して組み、ドメインの課題 ・ 提供価値の文 ・ サブドメインの説明 ・ 文脈の目的 ・ 用語の定義 ・ 範囲の外側の語だけを人が読む説明として残す。

判断基準は、用語集では業務ルール ・ 前提条件 ・ 制約という振る舞いを表せず、それはコマンド ・ 不変条件 ・ 業務イベントが持つとし、分類は差別化と複雑さと問いの答えで決まり、連係方法には使う場合が決まっているとする。だから振る舞い ・ 分類 ・ 連係の意味は欄に持てて、業務エキスパートとの会話で形作る目的と定義だけが欄に置き換えられない。

設計の手順

  1. ドメイン（DOM）の文字列の欄を分ける

    【人が読む説明として残す】header.problem（q2b のとおり。モデルの目的を明確にするための文で、検知はこの文を読まない）・ value_proposition.values[].text（提供価値は業務エキスパートとの会話で形作る文。検知に要る対応は differentiator と、サブドメインの serves_values が持つ）・ scope.out[]（範囲の外側は宣言が無いものなので、ID で指せない。ただし語の照合にかける：どの文脈の用語集の語とも一致しないことを道具が確かめる）。【欄を足せば組める】competitors[].difference：競合に無い提供価値を VAL の ID で持つ欄（例：lacks: ["VAL-1"]）を足す。「他チェーンのモバイルオーダーには、受け取り時刻の約束が無い」を道具が組み、differentiator が true の価値が、どれかの競合の lacks に入っているかを照合する。「できあがりを通知するだけ」のように競合が何をするかの文は、任意の説明として残してよい。【欄から組める】scope.in[]：domain.subdomains（SD-1 受注 ・ SD-2 決済）の名前から組む。subdomains に対応しない項目（見本の「店頭での受け取り」）が残ったら、それはサブドメインが欠けている知らせであり、文字列で持ち続けない。【範囲外】stakeholders[].interest は、判断基準が触れていない。ユースケースの側の決定（自由文で残す）に合わせる

  2. サブドメイン（SD）の文字列の欄を分ける

    【人が読む説明として残す】header.description（q2b のとおり）。ただし判断基準は、業務領域は何をするかを説明し、どのように実現するかは説明しないとする。見本の「調理の空きに合わせて」は実現のしかたなので、人が読んで直すかを決める（道具は検知しない）。【欄を足せば組める】classification.answer：判断基準の分け方は「差別化 × 業務ロジックの複雑さ」の表と、迷ったときの3つの問いである。差別化は competitive_advantage と serves_values（differentiator が true の VAL）、複雑さは business_logic.complex_rules ・ complex_data が既に持つ。足すのは、問い「外部のサービスを導入するより、自分たちで作るほうが簡単で費用も少ないか」の真偽値と、「製品や外部サービスがあるか」の真偽値の2つである。これで category を表から導けるので、道具は category と答えの欄のずれを検知でき、答えの文（「VAL-1 受け取り時刻の約束が、競合との違いになる」）は欄から組む。sourcing も category から照合する（中核なら社内で開発する。見本の SD-1 は sourcing が無い）

  3. 区切られた文脈（BC）の文字列の欄を分ける

    【人が読む説明として残す】header.purpose（q2b のとおり）・ ubiquitous_language.terms[].definition（q2b のとおり。業務エキスパートの言い方を残す）。ただし定義が欄に無い意味を持っていたら欄へ移す：TERM-1 の「1人の顧客が1つの店舗で」は、AGG-1 の state に顧客と店舗を ID で指す欄が無いと検知できない。kind がコマンド ・ 状態の値 ・ 拒否の理由 ・ 業務イベントの用語は、定義と同じ意味を事前条件 ・ 事後条件 ・ 値の一覧が持つので、道具は欄から組んだ文を定義の横に並べ、人が2つを読み比べる。【欄を足せば組める】context_map.relations[].reason：判断基準は、モデル変換装置を使う場合を4つ（下流の文脈が中核の業務領域を含む ・ 上流のモデルが使いにくい ・ 供給側の契約が頻繁に変わる ・ 既存システムが下流に悪い影響を及ぼす）に分ける。この4つを列挙の欄（使う場合）にし、どちらが上流かの欄を足す。「下流の文脈が中核の業務領域を含む」は、header.subdomains のサブドメインの category から道具が導けるので、手で選ぶのは残りの3つだけになる。文脈の地図はシステム全体の関係なので、関係は片方の文脈の宣言に1回だけ書き、もう片方の画面には道具が逆向きを表示する（見本の BC-2 の relations が空なのは、これで解ける）

  4. 集約（AGG）の文字列の欄を分ける

    【欄から組める】header.description（守る一貫性）：判断基準は、集約の目標をデータの一貫性の保証とし、強い一貫性を必要とするデータだけを内側に置くとする。守る一貫性は「不変条件とコマンドの条件が target で指す state の集まり」なので、道具が「注文の状態 ・ 受け取り予定時刻 ・ 明細の一貫性を守る」と組む。どの条件からも指されない state（ID を除く）があれば、内側に置くかを問い直す知らせにする。emits[].fields[].name：from が指す state の name（TERM）から組めるので、name の欄をやめる（見本の「注文番号」は ST-1 の TERM-14 と同じ）。structure.state[].multiplicity：「0..20」の文字列を {min, max} の数にし、上限と下限の不変条件（INV-3）は多重度から道具が組む。2か所に同じ意味を手で書かない。【欄を足せば組める】entities[].state[].name ・ type：name は用語の ID（「商品」「数量」→ TERM。数量は TERM-3）、type は値オブジェクトの ID か、他の集約を指す ID の値オブジェクトにする。商品はこの文脈の外（scope.out のメニューの管理）にあるので、ID で参照する値オブジェクトを1つ足し、その用語を用語集に足す。4種類の例は次の手順で扱う

  5. 値オブジェクト（VO）の文字列の欄を分ける

    【欄を足せば組める】components[].digits：1つの欄に、桁（6桁）・ 精度（分まで）・ 数の種類（整数）・ 値の一覧（下書き ・ 確定済）が入っている。kind ごとに欄を分け、kind が列挙なら値の一覧を状態の値の用語の ID の配列（["TERM-10", "TERM-11"]）で持つ。これで条件の value（TERM-11）が値の一覧に在るかを道具が照合でき、TERM-5 の定義（下書きか確定済か）と同じ意味を道具が組める。operations[].text：操作に引数の欄（名前は用語の ID、型は VO）と、操作の名前を用語の ID で持つ欄を足す。「数量と数量を受け取り、数量を返す」までは欄から組め、「足した」という意味は名前の用語（業務エキスパートと決める）と、操作の受け付ける例（2 と 3 → 5）が持つ。結果が VO 自身の不変条件（99 以下）を破るときに拒否する事前条件も、操作に持たせる。【欄から組める】components[].invariants[].impossible（作れない値）：条件の境界から道具が組む（ge 1 → 0個、le 99 → 100個）

  6. ドメインサービス（DS）の文字列の欄を分ける

    【欄から組める】header.reason_text：判断基準の問いは「集約や値オブジェクトでは表現しにくいか」「複数の集約を参照する計算のロジックか」の2つで、reason の列挙がこれを持つ。「複数の集約にまたがる計算」なら、reads（AGG-1 ・ AGG-2）から「注文と調理枠の両方を読む」を道具が組み、reads が2つ未満なら知らせる。「どちらに置いても、もう一方の状態を持ち込む」は判断基準そのものの説明なので、宣言ごとに書かない。【欄を足せば組める】operations[].inputs[].name：入力を、reads の集約の state を指す欄で持つ。「明細の数量の合計」は条件の6項目の対象（AGG-1.ST-3）と集計（合計）を使い、「調理枠の空き」は AGG-2.ST-2 を指す。ただし見積もるにはどの時間の調理枠かを選ぶので、入力は1つの調理枠ではなく、調理枠の集まりにする。postconditions[].condition.value：「調理枠の開始時刻」を AGG-2.ST-1 で指し、target の「結果」は文字列でなく、操作の出力を指す決まった参照にする

  7. 4種類の例を、状態 ・ 引数 ・ 結果の組で持ち、否定の例は道具が条件の境界から組む

    形は1つにする：before（前の状態。state の ID と値、明細は集計の値でもよい）・ args（引数の ID と値）・ after（後の状態）・ emits（出る業務イベントの ID）・ reject（拒否の理由の用語の ID）。受け付ける例は before ・ args ・ after ・ emits を持ち、テスト条件 AGG-1.CMD-1.OK-1 の期待する結果は after と emits から組む。拒否の例は before ・ args と、事前条件の reject を持つ。違反する例は before だけ、作れない値は成分の値だけを持つ。負担を抑える決め方は2つ。①否定の例（違反する例 ・ 作れない値 ・ 拒否の例）は、条件の境界の値から道具が組む（INV-1：確定済で受け取り予定時刻が空、INV-3：明細21件、VO-1.INV-1：0個、PRE-1：確定済の注文を確定する）。引数と比べる条件（AGG-2.CMD-1.PRE-1：空き ≥ 数量）のように道具が組めないときだけ手で書く。②受け付ける例は手で書くが、before に書くのはコマンドの事前条件が指す state だけ、after に書くのは事後条件が指す state だけに限り、それ以外を書いたら道具が知らせる。足しすぎると、例が state を全部書き写すことになり、例を直す箇所が増える（推測）

  8. 測れる基準（達成の基準 ・ 品質の要求）は、置き場所を決め、参照する ID を欄で持つ

    【達成の基準 success_criteria】ドメインに置く（事業活動の基本目標を言う文なので、文脈の外にある。SC-2 の店頭の待ち列のように、システムの外で測るものもある）。持たせる欄は、何を数えるかを指す ID の配列である：SC-1 なら確定済（TERM-11）・ 受け取り予定時刻（TERM-4）・ 受け渡し（いまは用語が無い）。参照先の ID が宣言に無いとき（受け渡し）は、道具が知らせる。ユースケースの contributes_to はこの SC を指したままにする。【品質の要求 quality】1つのコマンドに対する要求（QR-1：注文の確定の応答）は、そのコマンドの ID（AGG-1.CMD-1）を指す欄を持たせ、そのコマンドの文脈（BC-1）に置く。判断基準は、区切られた文脈を、文脈ごとに要素技術を選べる物理的な境界とし、一部の機能だけスケールアウトが必要なら切り離すとするので、品質の要求がどの文脈に掛かるかを欄で引けると、境界の判断に使える。複数の文脈にまたがる要求だけをドメインに置く。ユースケースの手順の quality は QR の ID を指したままにする。【範囲外】「2秒以内」「95% 以上」「5分以内」の値の持ち方と測り方は判定しない（platform-advisor へ）

コードの例

良い例と、避ける例

受け付ける例（AGG-1.CMD-1.OK-1）を構造で持つ形の案。文「明細2件の下書きを、受け取り予定時刻 12:30 で確定する → 確定済になり、注文確定済を出す」は、道具がこの欄と用語から組む（推測）。

{
  "id": "OK-1",
  "before": { "ST-2": "TERM-10", "ST-3": { "agg": "count", "value": 2 } },
  "args":   { "ARG-1": "12:30" },
  "after":  { "ST-2": "TERM-11", "ST-4": "12:30" },
  "emits":  ["EVT-1"]
}

道具が組めないので手で書く拒否の例（AGG-2.CMD-1.PRE-1）。reject は事前条件の側にあるので、例には書かない。

{ "id": "NG-1", "before": { "ST-2": 0 }, "args": { "ARG-1": 1 } }

避ける例：同じ意味を2か所に手で書く形（見本の AGG-1）。multiplicity の「0..20」と INV-3 の le 20 は、片方を直してももう片方は直らない。

"state":      [{ "id": "ST-3", "name": "TERM-2", "type": "ENT-1", "multiplicity": "0..20" }],
"invariants": [{ "id": "INV-3", "condition": { "target": "ST-3", "agg": "count", "op": "le", "value": 20 }, "violation": "明細が21件" }]

根拠

判定の拠りどころにした判断基準の記述

判断基準引用
ubiquitous-language対応：用語集は、ユースケースや Gherkin のテストなど、振る舞いを表す手法と組み合わせる ・ 理由：用語集は名詞の整理に役立つが、業務ルール ・ 前提条件 ・ 制約という振る舞いを表現できない
ubiquitous-language対応：同じ言葉は、それを使っている業務エキスパートとの会話で形作る ・ 理由：会話によって、不正確な表現 ・ まちがった解釈 ・ 事業活動についての誤解を検出できる
ubiquitous-language条件：1つの用語に1つの意味 ・ 内容：あいまいな用語を残さない。意味を推測させない
ubiquitous-language条件：同義語を使用しない ・ 内容：2つの用語を同じ意味で使わない。言葉が違えば、ほとんどの場合、意図も違う
model対応：モデルで解決しようとしている課題、つまり目的を明確にする ・ 理由：役に立つモデルは、目的に合う内容だけを表す。目的の無いモデルは無い
business-domain競合している企業や製品は何かを問う
subdomain業務領域は事業として何をするかを説明し、それをどのように実現するかは説明しない
subdomain迷う組み合わせ：補完か一般か ・ 問い：外部のサービスを導入するより、自分たちで作るほうが簡単で費用も少ないか ・ 判定：そうであれば補完

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI が、否定の例（違反する例 ・ 作れない値 ・ 拒否の例）を、条件と食い違う値で手書きする例の before と成分の値を条件で評価し、違反する例と拒否の例が条件を満たしてしまったら validate が落とす。道具が境界から組める例を手書きしていたら知らせる
AI が、受け付ける例の before ・ after に、コマンドの条件が指さない state まで書き写すbefore のキーが事前条件の target の集まり、after のキーが事後条件の target の集まりに含まれるかを照合する
AI が、state ・ 入力 ・ 操作 ・ 業務イベントの項目の名前に、用語集の語に似た文字列を書く（見本の「商品」「空き」「明細の数量の合計」「足す」）名前の欄を TERM- の ID に限り、入力 ・ 条件の値を ST- ・ ARG- ・ OP- の ID に限る。文字列が来たら validate が落とす
AI が、分類の答え ・ 関係の理由を、列挙と真偽値から導ける内容と食い違う文で書くcategory を差別化 ・ 複雑さ ・ 問いの真偽値から導き、宣言の category と比べる。関係の使う場合「下流の文脈が中核の業務領域を含む」は、下流の文脈のサブドメインの category と照合する
