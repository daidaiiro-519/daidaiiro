platform-advisor の回答 ・ 設計相談

ドメインの宣言にある品質の要求（例：QR-1「注文の確定は、2秒以内に結果を返す」。ユースケースの手順が ID で指し、system レベルのテスト条件 UC-1.STEP-5.QR-1 になる）を、自由文ではなく測れる構造で持つには、どの欄が要るか。宣言（業務の仕様）と実装の定義・運用の境目はどこか。達成の基準（SC-1「確定した注文の 95% 以上を、受け取り予定時刻から5分以内に渡している」）は同じ形で持てるか

前置き

判定の前に確定させた前提と、その出所

前提内容出所
見本.brainstorming-board/usecase-driven-concrete/sample/decls/DOM-1.json の quality[]（QR-1）と success_criteria[]（SC-1 ・ SC-2）。どちらも id ・ name ・ text の3欄だけで、閾値 ・ 割合 ・ 負荷の条件は text の中にしか無い相談者の見本
宣言の原則検知に使う意味はすべて欄に持ち、自由文は人が読む説明だけにする。条件は6項目（前提条件 ・ 対象 ・ 集計 ・ 範囲 ・ 演算子 ・ 比較する値）の構造で書き、文は道具が組む相談者のボード（論点2 C）
対象のシステムの社会的影響未判定。来店前注文は1チェーンの顧客が使う B2C の受注で、モデルシステムの「社会的影響が限定されるシステム」に近いと仮に置く。順守率のレベルの例はこの仮定に依存する相談者に未確認（仮定）
どの宣言が品質の要求を持つか ・ ユースケースの手順が quality で指す形 ・ success_criteria を contributes_to で指す形宣言の種類の分け方と、ユースケースからの指し方の良し悪しは、DDD とユースケースの判断で決まる。この回答はそれを判定しない。回答の中でそこに触れた所は「推測」と書く判断基準の範囲外（推測）
宣言とインフラ構成の置き場所判断基準と水準は「宣言」という置き場所を持たない。境目は、水準が「業務の特性をふまえて合意する」とする項目と、Well-Architected が「要件に応えられるアーキテクチャとサービスを選ぶ」側に置く項目の分け方を、宣言とそれ以外に当てはめたものである判断基準と水準の当てはめ（置き場所そのものは推測）

結論

採る

品質の要求は、非機能要求グレードの小項目 ・ メトリクス ・ レベルを指す欄に、測る処理 ・ 閾値 ・ 順守率 ・ 時の区分（通常時 ・ ピーク時 ・ 縮退時）・ その区分の業務量の欄を足して持ち、宣言には業務の合意で決まる値だけを置き、達成の基準は同じ欄の組で持てるが、測る方法（性能テストか、運用中のモニタリングか）の欄で区別する。

水準は、オンラインレスポンスを「システム化する対象業務の特性をふまえ」て決め、「具体的にはレスポンスと順守率を数値で合意する」としているので、2秒という閾値だけでは測れる要求にならず、順守率と時の区分を欄に持つ必要がある。Well-Architected は KPI を「文書にし、しきい値を持たせ、監視するメトリクスに対応付ける」とし、達成の基準はこの KPI に当たる。

設計の手順

  1. 品質の要求1件に、非機能要求グレードの位置を指す欄を置く

    大項目（性能・拡張性）・ 中項目（B.2 性能目標値）・ 小項目（B.2.1 オンラインレスポンス）・ メトリクス（B.2.1.1 通常時レスポンス順守率 など）・ レベル（番号と内容の組。例：3：90%）を欄に持つ。水準は数値を「具体的な数値は特定の機能またはシステム分類毎に決めておくことが望ましい」とするので、レベルは目安として持ち、合意した数値は次の欄に置く。

  2. 測る対象を、処理の id と測る区間で書く

    対象 ＝ 測る処理（注文の確定。ユースケースの手順 UC-1.STEP-5 を ID で指す形は推測）、測る量 ＝ 応答時間（要求を受けてから結果を返すまで）。B.2.1 は「Webシステムの参照系/更新系/一覧系など」の分類ごとに決めるとするので、分類（更新系）も欄に持つ。測る区間の始点と終点（利用者の端末で測るか、サーバーの入口で測るか）は判断基準に定めが無く、欄として持つことは推測である。

  3. 閾値を、演算子 ・ 値 ・ 単位の3つの欄に分ける

    演算子 ＝ 以下、値 ＝ 2、単位 ＝ 秒。相談者の6項目の構造の「演算子」「比較する値」に当たる。Well-Architected は、しきい値を業界のベンチマークとエンドユーザーの期待の両方から決めるとするので、閾値の出所（利用者の期待か、業界の値か）を持つ欄も足せる（任意）。

  4. 割合を、集計の種類と値の欄で持つ

    集計 ＝ 順守率（測った処理のうち閾値を満たした数の割合）、値 ＝ 90%（社会的影響が限定されるシステムの選択レベル3）など。6項目の構造の「集計」に当たる。2秒だけを書いて順守率を持たないと、1件でも2秒を超えたら不合格なのか、が決まらない。パーセンタイルで書く（95パーセンタイルが2秒以下）形も同じ意味を持てるが、水準の語は順守率なので、順守率を使う。

  5. 条件として、時の区分と、その区分の業務量を持つ

    時の区分 ＝ 通常時 ・ ピーク時 ・ 縮退時（B.2.1 は区分ごとに順守率を決める）。業務量 ＝ オンラインリクエスト件数と単位時間（B.1.1.4 は「単位時間をはっきりさせて確かめる」）、同時アクセス数（B.1.1.2）。見本では、昼の混雑時がピーク時に当たり、その時間帯（例：11:30〜13:30）と件数の欄が要る。6項目の構造の「前提条件」「範囲」に当たる。区分ごとに値が違うときは、品質の要求を区分ごとに1件ずつ持つ。

  6. 測る方法の欄を置き、品質の要求と達成の基準を同じ形で持つ

    測る方法 ＝ 性能テスト（system レベルのテスト条件になる）か、運用中の測定（KPI のモニタリング）か。QR-1 は性能テスト、SC-1 は運用中の測定である。SC-1 も、対象 ＝ 確定した注文、測る量 ＝ 受け取り予定時刻から受け渡しまでの時間、演算子 ＝ 以下、値 ＝ 5、単位 ＝ 分、集計 ＝ 割合、値 ＝ 95% 以上、と同じ欄で書ける。違うのは、測る量が業務の出来事（受け渡し）を含むのでシステムの応答だけでは測れないことと、集計の期間（1日 ・ 1か月など）が要ることである。

  7. 宣言に置く欄と、宣言の外に置く欄を分ける

    宣言に置く：測る処理 ・ 閾値 ・ 順守率 ・ 時の区分 ・ 業務量（どれも業務の特性をふまえて合意する値）。宣言の外（実装の定義と運用）に置く：インフラ構成（インスタンスの種類 ・ キャッシュ ・ B.4.1 の帯域保証と HW リソース専有）・ 処理余裕率（B.2.3）・ 性能テストの測定頻度と確認範囲（B.4.2）・ アラームのしきい値と通知先。2秒は業務の要求であり、2秒を出すための構成は、要求を読んで選ぶ側の判断である。

  8. text の欄は道具が欄から組み、人が読む説明だけを自由文で残す

    「注文の確定は、ピーク時（11:30〜13:30、毎分 N 件）に、90% 以上を2秒以内に返す」の文を欄から組む。テスト条件のハッシュ値は、測る処理 ・ 閾値 ・ 順守率 ・ 時の区分 ・ 業務量の欄から取る（推測：ハッシュ値の取り方は相談者の道具の設計である）。

具体例

  • QR-1 を構造にした例：{ grade: { middle: "b-2", small: "B.2.1", metric: "B.2.1.2 ピーク時レスポンス順守率", level: "3：90%" }, target: { process: "注文の確定", class: "更新系", measure: "応答時間" }, threshold: { op: "<=", value: 2, unit: "秒" }, aggregate: { kind: "順守率", value: 90 }, condition: { period: "ピーク時", window: "11:30〜13:30", load: { metric: "B.1.1.4 オンラインリクエスト件数", value: N, per: "分" } }, measured_by: "性能テスト" }（欄の英語名は例。用語は相談者の用語集に合わせる）
  • SC-1 を同じ形にした例：{ target: { object: "確定した注文", measure: "受け取り予定時刻から受け渡しまでの時間" }, threshold: { op: "<=", value: 5, unit: "分" }, aggregate: { kind: "割合", value: 95, over: "1日" }, measured_by: "運用中の測定" }。grade は持たない（非機能要求グレードは業務の成果の割合をメトリクスに持たない）

水準引用

注意

アンチパターンリスク代替案
閾値だけを書き、順守率と時の区分を持たない（見本の QR-1）1件でも2秒を超えたら不合格なのか、ピーク時にも2秒を求めるのかが決まらず、テストの合否も、テスト条件のハッシュ値も、人が text を読んで決めることになる順守率（B.2.1.1〜B.2.1.3）と時の区分を欄に持ち、区分ごとに値が違えば区分ごとに1件にする
負荷の条件を持たない利用者が1人のときに2秒以内でも合格になり、昼の混雑時に要求を満たすかを性能テストで確かめられない時の区分ごとに、オンラインリクエスト件数と単位時間（B.1.1.4）・ 同時アクセス数（B.1.1.2）の欄を持つ
（推測）インフラ構成の値を宣言に書く構成を変えるたびに業務の仕様の宣言が変わり、業務の承認が要らない変更でも宣言どうしのずれとして検知される宣言には合意した閾値 ・ 順守率 ・ 業務量だけを置き、構成は宣言を読む実装の定義の側に置く
（推測）達成の基準を system レベルのテスト条件にする受け取り予定時刻から5分以内に渡したかは、店舗の調理と受け渡しの出来事を含むので、システムのテストでは合否が出ず、テスト条件が常に未実施のまま残る測る方法の欄を「運用中の測定」にし、テスト条件ではなく、運用中に KPI として測る項目として持つ

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI が QR-1 から性能テストを書くとき、1回の要求の応答時間だけを測り、順守率と負荷の条件を落とすテスト実装が、宣言の順守率 ・ 時の区分 ・ 業務量の欄の値を読んでいるかを、テスト条件 ID ごとに照らす。欄の値がテストの引数に現れなければ、ずれとして検出する
AI が 2秒を、宣言を読まずにインフラの設定（タイムアウトやアラームのしきい値）へ数値のまま写し、宣言が変わっても設定が残る設定に現れる閾値が、品質の要求の id を指して読んでいるかを検査し、id を持たない同じ数値を検出する
AI が達成の基準（SC-1）を品質の要求と同じく system レベルのテスト条件として起こす測る方法の欄が「運用中の測定」の項目からテスト条件 ID が作られていないかを検査する
