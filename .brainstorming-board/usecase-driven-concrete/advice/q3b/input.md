# 相談の材料：ユースケース以外の6種類の宣言から、意味を持つ自由文をなくす

## 前提
- 仕様は「宣言」という構造化データ（JSON Schema で型が決まる）。7種類：ドメイン ・ サブドメイン ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス。人は描画した画面で承認し、AI は宣言を読んで実装とテストを書く。道具は宣言どうしのずれと、宣言とテスト実装のずれを検知する（テスト条件 ID ＋ 期待する結果を決める欄のハッシュ値）。
- 決めた原則（ボード論点2 C）：「自由文の意味推論は機械的にできない。それをしないと検知できないなら構造化不足」。検知に使う意味はすべて欄に持ち、自由文は人が読む説明だけにする。条件は6項目の構造（前提条件 ・ 対象 ・ 集計 ・ 範囲 ・ 演算子 ・ 比較する値）で書き、文は道具が組む。式は「値オブジェクトの操作を1回呼ぶ形」と「事後条件で実行前の値を指す形」だけ足す。拒否の理由の語と業務イベントの名前は用語集の用語。ユースケースは手順 ・ 拡張 ・ 事前条件 ・ 保証も欄で書き、文は道具が組むと決めた。
- 自由文で残すと決めたもの（ユースケース側）：利害関係者の利益 ・ 未決定事項。DDD 側で ddd-advisor が残してよいとしたもの：用語の定義 ・ サブドメインの説明 ・ 文脈の目的 ・ ドメインの課題（道具は検知に使わず、用語集の使わない語の文字列照合だけかける）。

## 6種類の宣言に残っている文字列の欄（見本：来店前注文）
| 種類 | 欄 | 見本の値 |
|---|---|---|
| ドメイン | header.problem | 昼の混雑時、店頭で注文と会計の列に並ぶ客が多く、受け取りまで15分以上かかって帰ってしまう客がいる |
| ドメイン | value_proposition.values[].text（＋ differentiator: true/false） | 来店前に注文を確定でき、調理の空きに合わせた受け取り予定時刻を約束する |
| ドメイン | value_proposition.competitors[].difference | 受け取り時刻を約束せず、できあがりを通知するだけ |
| ドメイン | success_criteria[].text（達成の基準。ユースケースが contributes_to で指す） | 確定した注文の 95% 以上を、受け取り予定時刻から5分以内に渡している |
| ドメイン | scope.in[] ・ scope.out[] | 来店前の注文と支払い ／ ポイント |
| ドメイン | stakeholders[].interest | 待たずに、約束した時刻に受け取りたい |
| ドメイン | quality[].text（品質の要求。ユースケースの手順が quality で指し、テスト条件 UC-1.STEP-5.QR-1 になる。求めるレベルは system） | 注文の確定は、2秒以内に結果を返す |
| サブドメイン | header.description | 来店前の注文を受け付け、調理の空きに合わせて受け取り予定時刻を約束する |
| サブドメイン | classification.answer（＋ category enum ・ competitive_advantage bool ・ sourcing enum） | 受け取り時刻を約束できることが、競合店との違いになる |
| 区切られた文脈 | header.purpose | 受け取り予定時刻を約束した注文を、調理の空きを超えずに受け付ける |
| 区切られた文脈 | context_map.relations[].reason（＋ pattern enum） | 外部の決済サービスのモデルを、受注の言葉に持ち込まない |
| 区切られた文脈 | ubiquitous_language.terms[].definition（＋ kind enum ・ avoid） | 1人の顧客が1つの店舗で受け取る商品の一覧と、その受け取り予定時刻 |
| 集約 | header.description（守る一貫性） | 受け取り予定時刻の約束と、約束した明細の一貫性を守る |
| 集約 | invariants[].violation（違反する例） | 確定済なのに、受け取り予定時刻が空 |
| 集約 | commands[].preconditions[].example（拒否の例） | 確定済の注文を確定する |
| 集約 | commands[].accept_examples[].text（受け付ける例。テスト条件 AGG-1.CMD-1.OK-1） | 明細2件の下書きを、受け取り予定時刻 12:30 で確定する → 確定済になり、注文確定済を出す |
| 集約 | structure.entities[].state[].type ・ name | 商品の ID ／ 数量（用語の ID ではなく文字列） |
| 集約 | commands[].emits[].fields[].name | 注文番号（文字列） |
| 集約 | structure.state[].multiplicity | 0..20 |
| 値オブジェクト | components[].invariants[].impossible（作れない値の例） | 100個 |
| 値オブジェクト | operations[].text（操作の説明。name ・ result はある） | 2つの数量を足した数量を返す |
| 値オブジェクト | components[].digits（注文の状態の VO で値の一覧に使われている） | 下書き ・ 確定済 |
| ドメインサービス | header.reason（enum）＋ header.reason_text | 注文の明細と調理枠の空きの両方を使うので、どちらの集約に置いても、もう一方の状態を持ち込むことになる |
| ドメインサービス | operations[].inputs[].name | 明細の数量の合計（用語の ID ではない） |
| ドメインサービス | operations[].postconditions[].condition.value | 調理枠の開始時刻（文字列） |

## 聞きたいこと（共通）
1. 各欄を「欄から組める／欄を足せば組める（足す欄を示す）／人が読む説明として残す（検知に使わない理由）」に分けてほしい。
2. 例（違反する例 ・ 拒否の例 ・ 受け付ける例 ・ 作れない値）を構造にするなら、どんな形にするか（例：前の状態 ・ 引数 ・ 期待する結果 ・ 出る業務イベント）。足しすぎの負担にも触れる。
3. 測れる基準（品質の要求 ・ 達成の基準）を構造にするなら、どの欄が要るか。
4. 見本で見つけた、ほかのずれ。

判断基準からの引用を根拠にし、範囲外は「推測」と書く。新しい語を作らず、原典の語をそのまま使う。比喩を使わない。
