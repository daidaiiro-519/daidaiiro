qa-advisor の回答 ・ 設計相談

集約の違反する例 ・ 拒否の例 ・ 受け付ける例、値オブジェクトの作れない値（例）と、品質の要求 ・ 達成の基準（測れる基準）を、テストケースの入力と期待結果として機械的に使える構造にするには、どの欄をどう持たせればよいか。境界値との関係、例の数、テスト条件のハッシュ値に入れるか、品質の要求と達成の基準のどちらをテスト条件として扱うかを含めて

前置き

判定の前に確定させた前提と、その出所

前提内容出所
前回の回答との関係宣言はテストベース、宣言の単位はテスト条件、テスト条件の ID は不変で、ハッシュ値は「期待する結果を決める欄」だけから作る。報告の任意の欄 case で、同じテスト条件を確かめる複数のテストケース（境界値ごとなど）を区別する。受け付ける例は1件ずつテスト条件（AGG-1.CMD-1.OK-1）になる。品質の要求のテスト条件は UC-1.STEP-5.QR-1 で、求めるレベルは system。これらは変えず、その上に例と測れる基準の欄を足すadvice/qa.json ・ advice/q5/qa.json（前回の回答）

DDD の判断どのコマンドが不変条件を破る状態へ至り得るか、2つの事前条件が同時に破れたときにどちらの拒否の理由を返すか、受け渡しを表す業務イベントを置くかは、集約の設計の判断であり、この回答の判断基準の範囲外である。該当する箇所は「推測」と書き、判定の根拠にしない判断基準の範囲外
運用で測ること達成の基準を運用中にどう集めて測るか（監視の仕組み、集計の期間の運用）は、この回答の判断基準の範囲外である。テストの側から見た区別と、宣言に要る欄だけを示し、測り方は推測と書く判断基準の範囲外
ユースケースの判断品質の要求をどの手順に付けるか、達成の基準をどのユースケースが contributes_to で指すかはコーバーンの判断であり、範囲外である。今の参照の形をそのまま使う判断基準の範囲外

結論

採る

例は文ではなく Given/When/Then の構造（前の状態 ・ コマンドと引数 ・ 期待する結果＝状態の値か拒否の理由の用語、業務イベントの ID）で持ち、期待する結果に効く値だけを書かせ、テスト条件1件に例を1件だけ必須とし、境界値は条件の演算子と比較する値から道具が導いて case で区別し、例の構造はそのテスト条件のハッシュ値に入れる。品質の要求は非機能テストのテスト条件として「品質特性 ・ 測る対象 ・ 集計 ・ 演算子 ・ 比較する値 ・ 単位 ・ 測定の条件」を持たせて終了基準に数え、達成の基準はテスト条件にせず、同じ6項目の構造に「測る期間」と「データの出所（業務イベントか、システムの外か）」を足して、運用で測る指標として扱う。

テストケースは事前条件 ・ 入力 ・ 事後条件を含み、ATDD では実例とテストケースは同じものとされるので、例を構造にすれば宣言の例がそのままテストケースになる。同値分割法はパーティションごとに1つのテストで十分とし、境界値は順序性のあるパーティションの最小値と最大値なので、条件の構造から導ける。非機能テストは機能テストのテストケースから導いて指定時間内に動くかなどをチェックする「検証」だが、達成の基準は運用環境でステークホルダーのニーズを満たすかの「妥当性確認」に当たり、システムの外の要因も含むので、テストの合否にできない。

設計の手順

  1. 問い2-1：例を文から Given/When/Then の構造へ移す

    テストケースは「事前条件 ・ 入力 ・ 事後条件」を含むので、例は次の3つの欄で持つ。given（前の状態）＝集約の状態の ID ごとの値（列挙は状態の値の用語 ID、集まりは {"count": 2} のように集計で書いてよい）。when（入力）＝コマンドの ID と、引数の ID ごとの値。then（期待する結果）＝受け付けるなら状態の ID ごとの値と、出る業務イベントの ID、拒否するなら拒否の理由の用語 ID。値は値オブジェクトの成分の値（数は数、時刻は時刻の文字列）で書き、「明細2件」「100個」のような文にしない。人が読む文は、前回の決定どおり道具がこの構造から組む。受け入れ基準のルール指向の形式（入出力マッピングの表形式）に当たり、十分に定義され曖昧さが無ければ独自の形式を使ってよいとされるので、この形は原典の範囲に収まる。

  2. 問い2-2：例の種類ごとに、必須の欄と期待する結果を決める

    (1) 受け付ける例（accept_examples[]）：given ・ when ・ then.state ・ then.emits を必須にする。then の状態の値は、事後条件が引数から決まるもの（POST-2：受け取り予定時刻＝ARG-1）も書かせず、道具が事後条件から導く（Derived Values）。業務イベントの欄の値も emits[].fields[].from から道具が導くので、例には業務イベントの ID だけを書く。事後条件が値を決めないもの（AGG-2.CMD-1 の POST-1 は not_empty だけ）は、then に値を書かせる。これが前回の回答の「期待結果を弱い事後条件でなく受け付ける例から取る」を構造で保証する形である。(2) 拒否の例（preconditions[].example）：given ・ when を必須にし、期待する結果は「その事前条件の reject の用語で拒否され、状態は given のまま、業務イベントは出ない」と道具が決める。given と when は、対象の事前条件だけが偽で、ほかの事前条件はすべて真になる値にする（1つのテストケースで無効な遷移を1つだけテストする規則と同じ理由で、欠陥のマスキングを避ける）。(3) 違反する例（invariants[].violation）：違反する状態の値（state）を必須にし、それへ至る操作（via：コマンドの ID ・ given ・ when）を持たせる。via が無い不変条件は、テストケースの入力が決まらないので、道具が「テスト条件の入力が無い」と警告する（テスト分析の試験性のアセスメントに当たる）。via のデータが既存の拒否の例と同じになるとき（見本の INV-2 と CMD-1.PRE-2）は、拒否の例の ID を参照してよい。どのコマンドが違反へ至り得るかは DDD の判断である（推測）。(4) 作れない値（components[].invariants[].impossible）：成分の ID ごとの値（{"CMP-1": 100}）を必須にし、期待する結果は「生成を拒む」と道具が決める。

  3. 問い2-3：道具が例を静的に検査する

    例が構造になると、道具は例と条件を評価して、例そのものの誤りをソフトウェアを実行せずに見つけられる（静的テスト）。検査は4つ：受け付ける例の given ・ when がすべての事前条件を満たし、then がすべての事後条件と不変条件を満たす ／ 拒否の例で偽になる事前条件がちょうど1つで、それが例の付いた事前条件である ／ 違反する例の state で、その不変条件が偽になる ／ 作れない値で、その成分の不変条件が偽になり、値が型の範囲（VO の成分の種類 ・ 桁）に収まる。見本の PRE-1 の例「確定済の注文を確定する」は明細の件数を言っていないので、明細0件なら PRE-1 と PRE-2 の両方が偽になり、期待する拒否の理由が決まらない。構造にすれば given.ST-3 が無いことを道具が検出できる。2つの事前条件が同時に偽になるときにどちらの理由を返すかは、デシジョンテーブルの1列に当たり、宣言で決まっていなければ道具が「期待する結果の決まらない組み合わせ」として出す。決め方（事前条件の順序で決めるか）は DDD の判断である（推測）。

  4. 問い2-4：境界値は宣言に書かせず、条件から道具が導く

    境界値分析は順序性のあるパーティションにだけ使えるので、演算子が ge ・ gt ・ le ・ lt で、比較する値が数か時刻の条件から、道具が境界値と隣接値を導く（2値 BVA を既定にする）。VO-1 の INV-1（≥1）なら 1 と 0、INV-2（≤99）なら 99 と 100、AGG-1 の INV-3（明細の件数 ≤20）なら 20 と 21、PRE-2（件数 ≥1）なら 1 と 0 になる。導いた値は前回の回答の case（境界値ごとのテストケースの区別）にそのまま入れ、テスト条件の ID は増やさない。見本の作れない値（0個 ・ 100個）と違反する例（明細が21件）は、すでに無効側の隣接値と一致しているので、構造にしたあとは「例の値が導いた無効側の値と同じ」を道具が確かめるだけでよい。eq ・ 列挙のように順序の無い条件は、同値分割法で、有効パーティションと無効パーティションに1つずつ値があればよい。3値 BVA にするかは、リスクに応じてテスト計画で決める（推測）。

  5. 問い2-5：例の数を「テスト条件1件に例1件」に絞り、値も期待する結果に効くものだけにする

    必須は、受け付ける例はコマンドごとに1件以上、拒否の例は事前条件ごとに1件、違反する例は不変条件ごとに1件、作れない値は成分の不変条件ごとに1件である。同値パーティションの1つの値で欠陥を検出できるなら同じパーティションの他の値でも検出されるはずとされ、ATDD でも2つのテストケースに同じ特性を書かないので、同じパーティションに2件目の例を書かせない。受け付ける例を足すのは、結果が違うパーティション（例：受け取り予定時刻を受け付ける範囲が複数ある）を示すときだけで、そのときは OK-2 として別のテスト条件になる。境界値は道具が導くので、人と AI が書く数は増えない。given に書くのは、事前条件 ・ 事後条件 ・ 不変条件が参照する状態の ID だけにし、ほかの状態はテストの側の既定値（Creation Methods）に任せる。期待する結果に効かない値まで書かせると、Irrelevant Information ・ Hard-Coded Test Data の形が宣言に入り、ハッシュ値も無関係な変更で変わる。道具は、どの条件も参照しない状態の ID が given にあれば警告を出す。

  6. 問い2-6：例の構造を、そのテスト条件のハッシュ値に入れる

    入れる。例はテストケースの入力と期待結果そのものなので、例が変わればテストケースを直す必要があり、前回の回答の「期待する結果を決める欄」に当たる。入れる範囲は、受け付ける例なら given ・ when ・ then（OK-1 のテスト条件のハッシュ値）、拒否の例ならその事前条件のハッシュ値、違反する例（state ・ via）ならその不変条件のハッシュ値、作れない値ならその成分の不変条件のハッシュ値である。入れないのは、道具が組む文、表示のラベル、欄の並び順（正規化してから計算する）、道具が導いた境界値（条件から決まるので、条件のハッシュ値に含まれている）である。例の値を期待する結果に効くものに絞っておけば、例のハッシュ値は無関係な変更で変わらず、High Test Maintenance Cost を避けられる。

  7. 問い3-1：品質の要求はテスト条件として扱い、測れる欄を足す

    品質の要求（DOM-1 の QR-1「注文の確定は、2秒以内に結果を返す」）は、指定された要件をシステムが満たしているかの検証であり、非機能テスト（品質特性は性能効率性）に当たる。非機能テストは機能テストのテストケースから導くので、前回の回答どおり、手順の quality から UC-1.STEP-5.QR-1 を取り出し、求めるレベルは system とする。合否を機械で決めるには、文の「2秒以内」だけでは足りない。足す欄は7つ：characteristic（品質特性。ISO/IEC 25010 の7つの列挙）・ target（測る対象。例：応答時間）・ agg（集計。最大か、何パーセンタイルか）・ op（演算子）・ value（比較する値）・ unit（単位）・ preconditions（測定の条件。同時に処理する注文の数 ・ データの量などを6項目の条件で書く）。agg と測定の条件が無いと、同じ実装でも1回の遅い応答で合否が変わり、テストの結果が再現しない（推測）。本番相当の環境を要るかは environment（列挙）で持たせる。この欄のすべてを UC-1.STEP-5.QR-1 のハッシュ値に入れる。報告には、前回の必須5欄に加えて、任意の欄 measured（測った値と単位）を置き、プロダクト品質メトリクス（応答時間）として残す。

  8. 問い3-2：達成の基準はテスト条件にせず、運用で測る指標として欄を持たせる

    達成の基準（SC-1「確定した注文の 95% 以上を、受け取り予定時刻から5分以内に渡している」、SC-2「昼の時間帯の店頭の待ち列が、5人以下に収まっている」）は、運用環境でステークホルダーのニーズを満たしているかの妥当性確認に当たり、店の人手や客の数のようなシステムの外の要因でも変わる。テストの合否にすると、システムが正しくても不合格になり、終了基準が意味を失うので、テスト条件にせず、終了基準に数えない。トレーサビリティの「ビジネスゴールに照らしたプロジェクトの進捗を評価する情報」として、ユースケースの contributes_to から辿れるようにする。欄は品質の要求と同じ6項目（前提条件：確定した注文 ・ 対象 ・ 集計：割合 ・ 範囲 ・ 演算子 ・ 比較する値）に、window（測る期間）と source（データの出所：業務イベントの ID と欄、または「システムの外」）を足す。道具がテストの側で検査できるのは、source の業務イベントと欄が宣言に在ることだけである。見本の SC-1 は「渡した時刻」が要るが、宣言に受け渡しの業務イベントが無いので、運用で測れない。受け渡しを業務イベントとして置くかは DDD の判断である（推測）。SC-2 の待ち列はシステムが観測しないので source は「システムの外」となり、道具は構造だけを検査する。運用中の測り方は範囲外である（推測：platform-advisor の観測の設計へ渡す）。

  9. 問い3-3：2つを宣言のスキーマで区別できるようにする

    品質の要求と達成の基準を、欄の有無で区別する：テスト条件になるのは、手順から quality で指され、measured と比べられる target ・ agg ・ op ・ value ・ unit ・ 測定の条件を持つもの。運用で測るのは、window と source を持つもの。品質の要求に window を書いた場合や、達成の基準を手順の quality から指した場合は、道具が取り違えとして出す。品質の要求のうち、本番相当の環境でしか測れないもの（environment が本番相当）は、テスト条件のまま、求めるレベルを system にし、テスト環境の準備を開始基準に入れる（推測）。

具体例

  • AGG-1.CMD-1.OK-1（受け付ける例）：given {ST-2: TERM-10, ST-3: {count: 2}} ・ when {command: CMD-1, args: {ARG-1: "12:30"}} ・ then {state: {ST-2: TERM-11}, emits: [EVT-1]}。ST-4 が 12:30 になることと、EVT-1 の欄の値は、POST-2 と emits[].fields[].from から道具が導く
  • AGG-1.CMD-1.PRE-1（拒否の例）：given {ST-2: TERM-11, ST-3: {count: 2}} ・ when {command: CMD-1, args: {ARG-1: "12:30"}}。期待する結果は TERM-12 で拒否 ・ 状態は given のまま ・ 業務イベントなし。ST-3 を書かないと PRE-2 も偽になり得るので、道具が警告を出す
  • AGG-1.INV-1（違反する例）：state {ST-2: TERM-11, ST-4: null}。via が無ければ「テスト条件の入力が無い」の警告になる。CMD-1 の POST-2 が ST-4 を必ず埋めるなら、この状態へ至るコマンドは無い（推測：DDD の判断）
  • VO-1.INV-2（作れない値）：{CMP-1: 100}。道具が導く境界値は 99（有効）と 100（無効）で、例の値は無効側の隣接値と一致する
  • AGG-2.CMD-1.OK-1：事後条件が not_empty だけなので、then に {state: {ST-2: 3}} を書かせる。given {ST-2: 5} ・ when {ARG-1: 2}

注意

アンチパターンリスク代替案
例を文のまま残し、AI に読ませてテストデータを作らせるPRE-1 の例「確定済の注文を確定する」のように前の状態が欠けると、AI が明細0件で書いたときに PRE-2 も偽になり、どちらの拒否の理由を期待するかが実装ごとに変わる。例とテストのずれも、文のままでは道具が検出できない例を given ・ when ・ then の構造にし、偽になる事前条件がちょうど1つかを道具が静的に検査する
境界値や同じパーティションの値を、例として宣言に書き足す同じ特性を確かめる例が増え、AI が書く負担と人が描画で読む負担が増える。例はハッシュ値に入るので、1か所の変更で古くなるテスト条件も増え、High Test Maintenance Cost になる宣言の例はテスト条件1件に1件とし、境界値は条件の演算子と比較する値から道具が導いて、報告の case で区別する
例の given に、期待する結果に効かない状態まで書くIrrelevant Information ・ Hard-Coded Test Data の形が宣言とテストへ写り、どの値が結果に効くかが読めなくなる。効かない値の変更でもハッシュ値が変わるgiven は条件が参照する状態の ID だけにし、ほかはテストの側の Creation Methods の既定値に任せる。条件が参照しない状態の ID があれば道具が警告を出す
（推測）達成の基準をテスト条件にして、終了基準に数える店の人手や客の数のようなシステムの外の要因で不合格になり、システムが正しくても終了できない。逆に、テスト環境で作った数字で合格にすると、運用での達成を示したことにならない達成の基準はテスト条件にせず、window と source を持つ運用の指標として扱う。テストの側では source の業務イベントと欄が宣言に在ることだけを検査する
（推測）品質の要求を、集計と測定の条件なしの文のままテスト条件にする「2秒以内」が最大値か95パーセンタイルかが決まらず、AI が書くテストごとに合否の判定が変わる。測定の条件が無いと、結果が再現しない品質特性 ・ 測る対象 ・ 集計 ・ 演算子 ・ 比較する値 ・ 単位 ・ 測定の条件を欄で持ち、すべてをテスト条件のハッシュ値に入れる

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI が受け付ける例の then に、事後条件をそのまま写して具体的な値を書かない（AGG-2.CMD-1 の then を「空きが空でない」にする）事後条件が値を決めない（not_empty など）状態の ID について、then.state に値があるかを道具が検査し、無ければ不合格にする
AI が拒否の例の given を、複数の事前条件が同時に偽になる値で書く道具が例の given ・ when ですべての事前条件を評価し、偽になる事前条件がちょうど1つで、それが例の付いた事前条件であるかを検査する
AI がテストの中で、宣言の例と違う値（例：12:30 でなく 13:00）を使い、報告だけ OK-1 と書く推測：テストケースに例の値を直接書かせず、宣言から生成したテストデータ（例の ID で引く）を読み込ませる。生成したデータのハッシュ値を報告の hash と照合する
AI が品質の要求のテストを、測定の条件を満たさない環境や負荷で流して pass と報告する報告の measured を必須にし、測定の条件（同時に処理する注文の数など）も報告に載せさせ、宣言の preconditions と一致しなければ道具が不合格にする（推測）
