ddd-advisor の回答 ・ 設計相談

来店前注文の宣言（DOM-1 ・ SD-1/2 ・ BC-1/2 ・ AGG-1/2 ・ VO-1〜4 ・ DS-1 ・ UC-1）から自由文をなくし、道具が検知に使う意味をすべて欄に持たせるには、集約と同じ言葉の側から、どの欄をどう組み立てるか。条件の6項目の構造に式を足すか、拒否の理由 ・ 業務イベント ・ 用語の定義 ・ サブドメインの説明 ・ 文脈の目的を自由文のまま残してよいか、内部の状態変化の手順の文を invokes とコマンドから組めるか、組んだ文が同じ言葉で書かれたことになるか。

結論

良好

集約 ・ 値オブジェクト ・ 業務イベント ・ 拒否の理由が持つ意味はすべて ID と条件の構造へ移し、手順の文はコマンドと集約の用語から組み、用語の定義 ・ サブドメインの説明 ・ 文脈の目的 ・ 課題だけを人が読む自由文として残す ── この組み立てで、利用者の原則は判断基準と整合する。

判断基準は、振る舞い（業務ルール ・ 前提条件 ・ 制約）を用語集では表せず、コマンドと不変条件が持つものとし、ソースコードからテストまで同じ言葉を変換せずに使うことを求める。だから振る舞いの意味は構造に、言葉は用語の ID に持たせ、業務エキスパートとの会話で形作る定義と目的は人が読む文として残すのが合う。

判断の道筋

  1. 検知に使う意味は、用語集に置けるか

    置けない。判断基準は、用語集は名詞の整理に役立つが業務ルール ・ 前提条件 ・ 制約という振る舞いを表せないとする。振る舞いの意味は、集約のコマンド ・ 不変条件 ・ 業務イベントの欄に置く

  2. 用語の定義 ・ サブドメインの説明 ・ 文脈の目的 ・ 課題を、構造に置き換える必要はあるか

    無い。これらは業務エキスパートとの会話で形作り、育てるものであり、道具の検知はこれらの文を読まなくても成り立つ（検知に要る対応は、kind ・ avoid ・ subdomains ・ serves_values ・ 分類の真偽値 ・ 宣言の name の ID が持つ）。ただし定義の文に、検知に使う意味（どの集約の状態の値か等）を書き足し始めたら、その意味を欄に移す

  3. 拒否の理由は、条件から文を組めば足りるか

    足りない。拒否の理由の語は業務エキスパートが使う同じ言葉なので、条件から機械的に組んだ文で置き換えない。検知に要るのは「どの事前条件の拒否か」の対応であり、それを欄に持てば、見本の AGG-2.CMD-1.PRE-1 → TERM-13 のような取り違えを道具が検知できる

  4. 内部の状態変化の手順の文は、invokes とコマンドから組めるか

    組める。主語はシステム、動詞はコマンドの用語（TERM-15「確保する」）、目的語は集約の用語（TERM-9「調理枠」）で「システムは、調理枠を確保する」になる。ただし1手順に invokes が1つなので、見本の手順3（見積もる ＋ 確保する）は2つに分けるか、DS-1 の操作も invokes で指せるようにする必要がある

  5. 組んだ文は同じ言葉で書いたことになるか

    なる。用語の語を変換せずに並べるので、会話 ・ 文書 ・ テスト ・ ソースコードで同じ言葉を使う規則に合う。ただし、それが業務の理解として正しいかは、業務エキスパートが読んで確かめる。道具が組んだ文は会話のかわりにならない

設計の手順

  1. 用語の ID を、文字列で書いている欄へ通す

    AGG-2 の state の name（開始時刻 ・ 空き）、ENT-1 の state（商品 ・ 数量）、DS-1 の inputs の name と POST-2 の value（調理枠の開始時刻）を、用語集の TERM か宣言の ID（ST ・ ARG ・ AGG-2.ST-1 など）で指す。AGG-1 は既に state の name を TERM で持っているので、それに揃える。これで、文を組む語がすべて用語集から来る

  2. 拒否の理由を、事前条件と1対1で対応させる

    事前条件の reject は拒否の理由の TERM を指したまま、同じ TERM を2つの事前条件から指したら道具が知らせる（同じ語が2つの意味を持つことになるため）。見本では、AGG-2.CMD-1.PRE-1 用に新しい拒否の理由の用語（語は業務エキスパートと決める）を用語集に足す。拒否の理由の語は人が決める同じ言葉として残し、条件から組んだ文は画面で並べて見せるだけにする

  3. 業務イベントの fields と、コマンドの事後条件を対応させる

    業務イベントは出来事に関する必要なデータをすべて持つ。emits の fields の from が、そのコマンドの事後条件の target（AGG-1.CMD-1 なら ST-2 ・ ST-4）と、集約の ID（ST-1）を覆っているかを道具が照合する。業務イベントの用語の定義（「注文が確定済になったこと」）は人が読む文として残す。名前が過去形かは、語の末尾で検査する

  4. 条件の値に、値オブジェクトの操作の呼び出しを1段だけ許す

    6項目の「比較する値」に、定数 ・ ID に加えて「操作の ID と引数の ID の組」を許す。例：VO-1 に操作「足す」（既存の OP-1）を使い、PRE-1 の値を『OP-1(ARG-1, 予備の数量)』にする。事後条件では変更前の状態を指す印（例：ST-2 の変更前）を許し、AGG-2.CMD-1.POST-1 を『ST-2 eq 引く(変更前の ST-2, ARG-1)』にする。入れ子が要るときは、途中の値に用語（例：「必要な空き」「予備」）を付けて state か値オブジェクトの操作にする。操作自身にも事前 ・ 事後条件を持たせる（見本の VO-1 の足すは、和が 99 を超えると VO-1.INV-2 に違反する）

  5. 内部の状態変化の手順は、invokes を必須にし、文をコマンドと集約の用語から組む

    組み方は『システムは、<集約の語>を<コマンドの語>』。引数は invokes 先のコマンドの args から取れるので、内部の状態変化の手順には渡すデータの欄を足さない。invokes の無い内部の状態変化（見本の 4a2）は道具が知らせる。4a2 の「注文の経過」は、用語集に足して AGG-1 の state とコマンドを起こすか、手順を消すかを業務エキスパートと決める。手順5の「承認番号と確定した合計額を記録する」も、AGG-1.CMD-1 の引数 ・ 事後条件 ・ state に無いので、足すか文から外す（文を欄から組めば、このずれは文に現れない形で表に出る）

  6. 受け入れの例と拒否の例を、状態 ・ 引数 ・ 結果の組で持つ

    accept_examples の text（「空き5の枠から2つ確保する → 空きが3になる」）と事前条件の example を、前提の状態（ST-2 = 5）・ 引数（ARG-1 = 2）・ 結果（ST-2 = 3、または拒否の理由の TERM）の組にし、文は道具が用語から組む。テスト実装とのずれを検知するのに使うのはこの組であり、文ではない。違反の例（violation ・ impossible）も同じ形にできる

  7. 用語の定義 ・ サブドメインの説明 ・ 文脈の目的 ・ ドメインの課題は自由文のまま残し、検知に使わないことを宣言の形で示す

    これらの欄は、道具の照合の対象から外す（スキーマの欄の説明に「人が読むためだけ」と書く）。ただし、自由文の中に用語集の avoid にある語が出ていないかと、未登録の語が無いかの2つだけは検査してよい。これは意味の推論ではなく、語の照合である

注意

アンチパターンリスク代替案
1つの拒否の理由を、意味の違う2つの事前条件から指す（見本の AGG-2.CMD-1.PRE-1 → TERM-13）「明細の無い注文は確定できない」が、調理の空きの不足も表すことになり、1つの用語が2つの意味を持つ。拒否の理由を表示するテストも、空きの不足を明細の不足として扱う事前条件ごとに拒否の理由の用語を1つ持ち、同じ TERM を2つの事前条件から指したら道具が知らせる。空きの不足には、業務エキスパートと決めた語を新しく用語集に載せる
用語集の語と、別の宣言の語が少しずつ違う（TERM-8「受け取り時刻を見積もる」と TERM-4「受け取り予定時刻」）同じものを2つの語で呼ぶ同義語になり、AI が「受け取り時刻」を別の概念として実装する。avoid に「受け取り時間」はあるが「受け取り時刻」は無いので、今の検査では検知しない用語の語の中に別の値オブジェクト ・ 集約の語を含めるときは、その語をそのまま使う（TERM-8 は「受け取り予定時刻を見積もる」にする）。または TERM-4 の avoid に「受け取り時刻」を足す
（推測）自由な算術式を条件の値に書けるようにする「予備の1食」のような業務の概念が名前を持たずに式へ埋まり、同じ言葉に載らない。式の書き方が宣言ごとに分かれ、AI が書く負担と人が読む負担が増える値オブジェクトの操作を1回呼ぶ形だけを許し、途中の値には用語を付ける
（推測）用語の定義の文に、検知に使う意味を書き足していく定義の文が、どの集約の状態の値か、どのコマンドの拒否かといった対応を持ち始め、道具が読めない場所に検知の根拠が溜まる対応は宣言の側の ID（name ・ reject ・ emits ・ 状態の値を持つ値オブジェクト）に持たせ、定義の文には業務エキスパートの言い方だけを書く

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
AI が宣言を書くとき、用語の ID を通すべき欄（state の name ・ DS の inputs ・ 条件の value）に、用語集の語に似た文字列を直接書くスキーマでその欄を ID の形（TERM- ・ ST- ・ ARG- ・ OP- などの接頭辞）に限り、文字列が来たら validate が落とす
AI が、内部の状態変化の手順に invokes を付けずに文だけを書く（見本の 4a2）、または invokes 先のコマンドに無い変化を文に書く（見本の手順5）kind が内部の状態変化の手順に invokes を必須にし、文を道具が組むので、文の手書きを受け付けない。保証の established_by が invokes 先の事後条件を指しているかを照合する（SG-3 は指す先が無いと報告される）
AI が、事後条件を not_empty で済ませ、受け入れの例の結果と照合できない形にする（見本の AGG-2.CMD-1.POST-1）受け入れの例を前提の状態 ・ 引数 ・ 結果の組で持ち、結果の値が事後条件を満たすかを道具が評価する。事後条件が not_empty だけのコマンドで、例の結果が値を持つときは知らせる
AI が、組んだ文の中に用語集に無い語や avoid の語を混ぜる（自由文の欄で起きやすい）組んだ文と自由文の両方を、用語集の語と avoid の語で照合する（意味の推論ではなく文字列の照合）
