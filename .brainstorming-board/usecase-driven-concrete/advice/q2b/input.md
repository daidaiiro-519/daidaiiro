# 相談の材料：宣言の自由文をなくし、意味をすべて欄に持たせる書き方

## 前提
- 仕様は「宣言」という構造化データ（JSON Schema で型が決まる）。種類は7つ（ドメイン ・ サブドメイン ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 値オブジェクト ・ ドメインサービス）。人は描画した画面で承認し、AI は宣言を読んで実装とテストを書く。
- 道具は、宣言どうしのずれ（構造の検査 ・ 対応の欄の検査 ・ 上流の変更）と、宣言とテスト実装のずれを検知する。例：拡張の handles ＝ 呼び出すコマンドの事前条件の ID、事前条件の ensures、成功時保証の established_by ＝ コマンドの事後条件の ID、手順の keeps ＝ 最低保証の ID。
- 承認済みの書き方（ボード論点2）：
  - 条件（集約の不変条件 ・ 事前条件 ・ 事後条件、値オブジェクトの不変条件、ドメインサービスの事前 ・ 事後条件）は6項目の構造で書き、文はツールが組む。6項目＝前提条件（if、1段まで）・ 対象（項目の ID）・ 集計（count ・ sum ・ max ・ min）・ 範囲（all ・ any）・ 演算子（eq ・ ne ・ ge ・ le ・ not_empty など）・ 比較する値。1条件に演算子1つ。
  - ユースケースの手順と拡張は、主語（アクター）・ 種類（相互作用 ・ 妥当性確認 ・ 内部の状態変化 ・ サブユースケースの呼び出し）・ 参照（相手 ・ invokes ・ 守る利害関係者）を enum と ID で持ち、**文だけを自由に書く**（書式と NG ワードで検査）。拡張の条件も「〜だった：」で終わる自由文。
  - 使う語は区切られた文脈の用語集にあるものに限る。

## 利用者が出した原則
「自由文や意味推論までは機械的にできない。それを機械的にやらないと検知できないとすれば、それは構造化不足である」。つまり、道具が検知に使う意味はすべて欄に持ち、自由文は人が読むためだけにする（理想は欄から道具が組む文）。

## いま自由文で書いている箇所（見本：来店前注文 UC-1「注文を確定する」）
| 箇所 | 例 |
|---|---|
| 手順の文 text | 手順3「システムは、受け取り予定時刻を見積もり、その時刻の調理枠を確保する」（種類：内部の状態変化、invokes AGG-2.CMD-1）。手順1「顧客は、支払い手段を添えて、注文の確定をシステムに依頼する」（相互作用、相手 システム）。手順2「システムは、カートの商品の価格が提示した額から変わっていないことを確認する」（妥当性確認） |
| 拡張の条件 condition | 3a「希望の時間帯に調理の空きがなかった：」（handles AGG-2.CMD-1.PRE-1）、2a「提示した額から価格が変わった商品があった：」（妥当性確認の失敗。対応するコマンドは無い）、4a「決済代行が承認しなかった：」（支援アクターの応答無しまたは誤り） |
| 保証 | 成功時保証 SG-1「注文が確定済になり、確定した合計額だけが顧客に請求される」（established_by AGG-1.CMD-1.POST-1）、最低保証 MG-2「確定しなかった注文には、請求も調理枠の確保も残らない」 |
| ユースケースの事前条件 | PRE-2「カートに1品以上の商品が入っている」（ensures AGG-1.CMD-1.PRE-2） |
| 条件の値 | 「空き ≥ 引数と予備の1食の和」のような式が6項目では書けない |
| 説明の欄 | ドメインの解決する課題、サブドメインの説明、文脈の目的、利害関係者の利益、用語の定義 |

## 聞きたいこと
1. あなたの判断基準から見て、上の箇所のうち「欄から文を組めるもの」「欄を足せば組めるもの」「人が読むための説明として自由文のまま残してよいもの（検知に使わない）」はそれぞれどれか。残す自由文が検知に使われない理由も述べてほしい。
2. 欄から文を組むとき、どの欄を足すべきか（例：手順の「渡すデータ」、妥当性確認の「確かめる条件」を条件の構造で持つ、拡張の条件を「拒否の理由 ／ 妥当性確認の失敗 ／ 支援アクターの失敗」の種類と参照で持つ）。足しすぎて AI が書く負担と人が読む負担が増える点にも触れてほしい。
3. 条件の構造に式（足し算など）を足すべきか。足すならどこまでか。
4. 生成した文が、原典の書き方（ユースケースなら主語 ・ 動詞 ・ 目的語の単純な文、意図を書きUIを書かない。DDD なら同じ言葉で書く）に合うか。

判断基準からの引用を根拠にし、範囲外は「推測」と書く。新しい語を作らず、原典の語をそのまま使う。比喩を使わない。
