usecase-advisor の回答 ・ 設計相談

ユースケースの宣言（見本：来店前注文 UC-1「注文を確定する」）から自由文をなくし、道具が検知に使う意味をすべて欄に持たせるには、手順の文 ・ 拡張の条件 ・ 保証 ・ 事前条件 ・ 利害関係者と利益をどう組み立てるか。どの欄を足し、どの自由文を残してよいか。組んだ文は原典の書き方に合うか

前提内容出所

結論

良好

「検知に使う意味は欄に、自由文は読むためだけ」という原則は、判断基準の書き方とよく合う。手順の文 ・ 拡張の条件 ・ 事前条件 ・ トリガー ・ 保証の文は、手順の種類ごとの参照（相手 ・ 渡す情報の別名 ・ 確認する条件の ID ・ invokes）と、拡張の条件の種類から組める。利害関係者の利益は、人が妥当性確認と保証の漏れを見つけるための自由文として残してよい。式はユースケースに持たせず、条件の ID で参照する

判断基準は、ステップを3つの種類に分け、どの種類も利害関係者の利益に結び付けている。拡張条件は「システムが検出できるか」で残すかを決め、事前条件は「別のユースケースがすでに設定した状態」、保証は「どの利害関係者のどの利益か」で書く。どれも、参照先を ID で持てる事柄である。一方で、データの項目やチェック内容はユースケースに含めず別の場所へリンクせよとしているので、式はユースケースの外に置く。利害関係者の利益は、人がステップを読み直して漏れを見つけるための記述であり、検知は利益の文ではなく、利益を指す ID（serves ・ protects ・ satisfies）で行える

判断の道筋

  1. 手順の文（text）は欄から組めるか

    内部の状態変化は、いまの欄で組める。主語（actor）と invokes が指すコマンドの名前（用語）から「システムは、調理枠を確保する」となる。手順3の「受け取り予定時刻を見積もり」は2つ目の動作なので、invokes を2つ持たせるか手順を分ける。相互作用は欄を足せば組める ── 渡す情報の別名（用語集の語の ID）と、意図を表す述語（用語集の語）が要る。妥当性確認は「確認する条件」の ID を足せば「システムは、〈条件の名前〉ことを確認する」と組める。サブユースケースの呼び出しは、invokes が指すユースケースの名前で組める

  2. 拡張の条件（condition）は欄から組めるか

    組める。拡張条件は「システムがそれまでと違う振る舞いをする状況」で、システムが検出できるものだけを残す。検出できるなら、検出した事柄を指す参照がある。3a は handles が指すコマンドの事前条件の拒否（reject の用語）から「〜だった：」を組む。2a は、手順2の確認する条件の否定から組む（演算子と範囲を反転する）。4a は、手順4の支援アクターと、その応答の値（受け取れなかった ・ 承認しないという応答だった）から組む。参照を持てない条件は、システムが検出できない条件である疑いがある（推測）

  3. 事前条件とトリガーは欄から組めるか

    PRE-2 は、ensures が指す条件（AGG-1.CMD-1.PRE-2）の名前から組める。PRE-1 は established_by が UC-8 というユースケースしか指していないので、UC-8 の成功時保証の ID を指すように変えれば、その保証の文から組める。トリガーは、原典がステップ1と同じでよいとしているので、手順1から組める

  4. 保証は欄から組めるか

    欄を足せば組める。成功時保証は established_by が指す事後条件、最低保証は 6項目の条件（前提条件 if を1段使う）で持てば、短い断定文を組める。MG-2 は「注文が確定していなければ、請求が無い」「注文が確定していなければ、調理枠の確保が無い」の2条件になる。SG-3 は established_by が無いので、いまは検知できない

  5. 人が読むための自由文として残してよいのはどれか

    利害関係者の利益（interest）と、未決定事項（open_issues）である。利益の文は、人がステップを最初から読み、各ステップと保証に利益が入っているかを確かめるための記述である。検知は、利益の文ではなく、利益を指す ID（serves ・ protects ・ satisfies）がすべての利害関係者に付いているかで行う。手順の name ・ 保証の name は、組んだ文と重なるので、置くなら見出しとして読むだけにする

  6. 組んだ文は原典の書き方に合うか

    文の形を「主語は、相手に、別名を、述語」に固定すれば、主語 … 修飾語 … 目的語 … 述語の単純な文で、能動態 ・ 現在形になる。使う語が用語集の語に限られるので、UI の語が入る余地は小さい。合わなくなる点は2つある。1つは、条件を6項目のまま文にすると「空きが引数以上である」のようなチェック内容がステップに入ること。もう1つは、述語の enum を細かくしすぎて、意図ではなく操作を書く文になること。前者は条件の名前（用語の句）で文を組み、6項目はリンク先で見せれば避けられる

設計の手順

  1. 手順を種類ごとに、組む文の形と必須の欄を決める

    相互作用：主語 ・ 相手（to）・ 渡す情報の別名（data、用語集の語の ID の並び）・ 述語（用語集の語）→「顧客は、支払い手段を添えて、注文の確定をシステムに依頼する」。妥当性確認：主語 ・ 確認する条件（checks、条件の ID）→「システムは、〈条件の名前〉ことを確認する」。内部の状態変化：主語 ・ invokes（コマンドの ID）→「システムは、〈コマンドの名前〉」。サブユースケースの呼び出し：主語 ・ invokes（ユースケースの ID）。同じ方向に流れるデータは1つの手順にまとめ、data に複数の別名を並べる。どの種類にも serves（利害関係者の ID）を必須にする

  2. 妥当性確認の条件を、ユースケースの外の条件として持ち、ID で指す

    手順2「価格が提示した額から変わっていない」は、どのコマンドの事前条件でもないので、集約 ・ ドメインサービスの条件か、文脈のビジネスルールとして1か所に置き、checks で指す。条件には文を組むための名前（用語の句）を持たせる。妥当性確認が増えたら別の場所へ移すという判断基準の規則と同じ向きである

  3. 拡張の条件を、条件の種類と参照の組で持つ

    condition_kind は、判断基準がブレーンストーミングで考える項目として挙げる語をそのまま enum にする（別の道筋での成功 ・ 主アクターの誤った振る舞い ・ 主アクターの活動の停止 ・「システムは…を確認する」の失敗 ・ 支援アクターからの応答が無い、または誤っている ・ 設計対象システムの、通常の業務で起こる内部エラー ・ 予期しない異常な内部エラー ・ システムの性能上の重大な問題）。種類ごとに参照を必須にする ──「確認する」の失敗なら checks の条件か handles の事前条件、支援アクターなら手順と応答の値、活動の停止なら手順と時間の上限。文は「〜だった：」を道具が組む。終わり方（ending）は、原典の4つ（元のステップが成功した状態になる ・ 同じステップに戻る ・ 失敗する ・ ユースケースは終了する）の enum にする

  4. 事前条件の established_by を、状態を作る別のユースケースの成功時保証の ID にする

    事前条件は「別のユースケースがすでに実行され、その条件を設定している」ことを表す。ユースケースの ID だけでは、どの状態を前提にしたかを検知できない。保証の ID を指せば、文はその保証から組め、保証が変わったときに上流の変更として検知できる。ensures はいまのまま、コマンドの事前条件を指す

  5. 保証を、利害関係者の ID と、成り立たせる条件の参照で持つ

    成功時保証：satisfies と established_by（事後条件）を必須にする。最低保証：protects と、6項目の条件（失敗したときにも真になる状態）を持ち、それを守る手順が keeps で指す。文は条件の名前から短い断定文として組む。失敗の仕方（拡張の条件）を最低保証に並べない。成功時保証は「要求された額」ではなく「確定した合計額」のように、実際に起きたことを指す項目を対象にする

  6. 利害関係者の利益は自由文のまま残し、検知は ID の付き方で行う

    検知の例：どの利害関係者の ID も、少なくとも1つの手順の serves と、1つの保証の protects か satisfies に現れる。舞台裏のアクター（UC-1 では店舗 ・ 経理）の利益は、妥当性確認か内部の状態変化の手順で満たされている。利益の文が妥当かは、人が読んで判断する

  7. 欄を足しすぎないために、精度の段階ごとに必須の欄を分ける

    段階2（主成功シナリオ）では、主語 ・ 種類 ・ 相手 ・ data ・ serves までを必須にする。段階3（失敗条件）では、拡張の condition_kind と参照だけを必須にし、拡張の手順は空でよい。段階4（失敗処理）で、拡張の手順と ending を必須にする。data には別名だけを置き、項目の一覧やチェック内容はユースケースの外に置く。AI が書く欄は ID の参照が主になり、正しさは validate で確かめられる。人は欄ではなく組んだ文を読む

  8. 組んだ文を、アクションステップの問いで確かめる

    主語がアクターか ・ 能動態の現在形か ・ 受け渡す情報が分かるか ・ まったく別の UI を想定しても成り立つか ・「確認する」と書いた手順に、確認できなかった場合の拡張があるか。条件の6項目そのものを文に流し込まない

use-case-format書式：Occam スタイル ・ 特徴：代替 ・ 並列 ・ 選択的なシーケンスを簡単に書ける形式言語 ・ 著者の見方：形式的な記述モデルを作るならまず検討する価値があるが、拡張に必要な例外処理の書き方は著者も知らない。自然言語は、並列 ・ 非同期 ・ 例外を読みやすさを損なわずに表せる

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
妥当性確認の手順の checks に、そのユースケースの事前条件と同じ条件を指させる（事前条件を本文で再確認する）各手順の checks の ID が、同じユースケースの事前条件の ensures と established_by が指す条件に含まれないことを、宣言どうしの検査で確かめる
「確認する」の手順を書いて、確認できなかった場合の拡張を書かない種類が妥当性確認の手順ごとに、condition_kind が「システムは…を確認する」の失敗で、その手順の checks を参照する拡張が1つ以上あることを確かめる
data に、別名ではなく状態の項目（ST-x）や項目の一覧を並べるdata の参照先が用語集の語か値オブジェクトの ID であり、集約の状態の ID を指していないことを確かめる
舞台裏の利害関係者を、どの手順の serves にも、どの保証にも付けない利害関係者の ID ごとに、serves に現れる手順が1つ以上、protects か satisfies に現れる保証が1つ以上あることを確かめる
