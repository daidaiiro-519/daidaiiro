結論

採る

5種類の宣言は、判断基準が判定に使う問いの答え（分類の根拠 ・ 業務ロジックの性質 ・ 強い一貫性の要否 ・ 連係方法 ・ 置く理由）を列挙値で持ち、名前はすべて区切られた文脈の用語を ID で指し、条件は「前提 ・ 主語 ・ 集計 ・ 量化 ・ 述語（閉じた列挙）・ 対象」の6要素の構造と、破る例 ・ 受理する例を持たせて、1条件を1つのテストへ機械的に写す形にする。

判断基準は、カテゴリーと実装方法を業務ルール ・ データ構造の複雑さの問いで判定し（subdomain ・ design-heuristics）、集約の内側に置くかを強い一貫性の問いで判定し（aggregate）、用語は1つの意味だけを持ち同義語を使わない（ubiquitous-language）と定めるので、これらを自由文でなく問いの答えと用語の参照として持たせれば、AI の書き方の揺れが入る範囲が説明文だけに狭まる。

設計の手順

  1. ドメインの提供価値に ID と差別化の真偽を持たせ、サブドメインの一覧を ID で並べる

    分類はドメインに書かず、サブドメインの側が持つ（前提）。（推測）差別化が真の提供価値は、中核のサブドメインが1件以上「担う提供価値」で指す、を検査にする。根拠は subdomain の「中核：競合他社との違いを生み出す業務活動」である

  2. サブドメインごとに、分類と、分類を判定した問いの答えを列挙値で書く

    分類の根拠は subdomain の「カテゴリーの判断が難しいときの問い」の3行から1つを選ぶ。業務ロジックの性質は design-heuristics の実装方法を選ぶ問い1〜3の真偽で書く。実装方法の名前と技術名は書かない ── 実装方法は、コーディングの側が真偽から判断基準の表で導く

  3. 区切られた文脈ごとに、用語集を先に書き、それ以外の宣言の名前を用語の ID で指す

    用語は1つの意味だけを持ち、同義語を「使わない語」に挙げる。文脈の名前を付けた語（「受注の注文」）を作らない。集約 ・ 値オブジェクト ・ コマンド ・ 業務イベント ・ ドメインサービス ・ 拒否の理由も用語に載せる

  4. 他の区切られた文脈との関係を、連係方法の6つの列挙値と自分の立場で書く

    良きパートナー ・ モデルの共有 ・ 従属 ・ モデル変換装置 ・ 共用サービス ・ 互いに独立。中核のサブドメインを含む文脈は、下流なら従属を選ばない、互いに独立を選ばない、を検査にする

  5. 集約ごとに、状態 ・ 不変条件 ・ 操作（事前条件 ・ 事後条件 ・ 出す業務イベント）・ 業務イベント ・ 整合性の境界を書く

    状態の各項目は、それを必要とする条件の ID を「内側に置く理由」で指す。どの条件にも使われない状態は、集約の外へ出す候補として検出する。他の集約は識別子だけで指す

  6. 値オブジェクトごとに、構成する値 ・ 不変条件 ・ 等価の定義を書く

    等価は既定で「全構成値」。不変（変更できない）は欄にせず、値オブジェクトであることから常に真とする

  7. ドメインサービスごとに、置く理由を2つの列挙値から選び、操作の入力 ・ 出力を値オブジェクトの型で書く

    事後条件の主語は「結果」と入力に限る。集約の状態を変える事後条件を書けたら、それは集約の操作である

  8. すべての条件を6要素の構造で書き、破る例と受理する例を付ける

    1条件に1つの述語。「かつ」は条件を分けて書き、「または」は「のどれか」で1つの主語に書く。「〜なら」は前提に1段だけ書く。文は構造から生成し、AI が手で書かない

  9. 条件の ID からテストの ID を機械的に作り、宣言とテストの対応を検査する

    AGG-1.INV-2.例1 → 拒否の単体テスト1件、AGG-1.CMD-1.POST-1 → 受理する例の中の表明1件、というように1対1で写す。記録案の「条件からテストへの変換」の行に従う

サブドメインの説明や業務ロジックの性質に、実装方法の名前（ドメインモデル ・ トランザクションスクリプト）や技術名（データベース製品 ・ フレームワーク）を書く器の検査で、サブドメインの文字列の欄に実装方法の名前と技術名の禁止語の一覧が無いことを照合する

事後条件に「注文確定済を出す」と書き、出す業務イベントの欄と二重に持つ事後条件の主語が ST-n ／ 結果 ／ CMP-n だけであること、業務イベントの名前が事後条件の値に現れないことを検査する
