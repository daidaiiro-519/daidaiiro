アドバイザーから戻ってきた3つの指摘（実装方法の決め方 ・ 文脈をまたぐ要約 ・ 技術のバリエーション）を、宣言のどこで受け止めるか

B

3つの指摘を、次のように受け止める。

  1. 実装方法は、サブドメインの分類ではなく、業務ロジックの性質で決める
    サブドメインは、分類（中核 ・ 補完 ・ 一般）に加えて、判断基準の3つの質問への答えを true / false で持つ。質問は「金銭の追跡 ・ 監査ログ ・ 行動分析が必要か」「業務ルールは複雑か」「データ構造は複雑か」の3つ。宣言には実装方法の名前を書かず、コーディング側がこの答えから実装方法を選ぶ
  2. ユースケースのスコープは、区切られた文脈かドメインのどちらかにする
    ドメインをスコープにできるのは要約レベルだけで、手順はすべて文脈の中のユースケースの呼び出しになる。主アクターごとに、いちばん外側の要約を1つ以上用意する
  3. 技術のバリエーションは、実装側の定義に置く
    宣言のバリエーションには、ドメインの言葉で書ける手段とデータだけを並べる。技術の違い（接続先のサービス ・ 認証デバイスなど）は、実装側の定義がユースケースの手順を ID で参照して持ち、Driven アダプターのコントラクトテストで確認する

Q2

条件とシナリオを、AI が書いても出力がぶれず、テストに1対1で変換できる形にするには、どう書かせるか

ここで、宣言のどこに書き手のぶれが入るかが決まる。論点3（種類ごとの項目）と論点4（テストとのつなぎ方）は、この書き方が前提になる
B条件は、6つの項目に分けた構造で書く。集約の不変条件 ・ 事前条件 ・ 事後条件、値オブジェクトの不変条件、ドメインサービスの事前条件 ・ 事後条件が対象。
  • 6つの項目
    前提条件（if。1段まで）・ 対象（項目の ID）・ 集計（count ・ sum ・ max ・ min）・ 範囲（all ・ any）・ 演算子 ・ 比較する値
  • enum
    集計 ・ 範囲 ・ 演算子は enum の値だけを使う。足りない演算子は、自由文で逃げずに enum に追加する
  • 1条件に演算子1つ
    AND は条件を分け、OR は「いずれか」の演算子で書く
  • 例
    不変条件と事前条件には違反する例を、操作には成功する例を必ず付ける
  • 文章
    人が読む文章は、構造からツールが生成する。書き手は文章を書かない
シナリオの手順と拡張は、主語や種類を enum と ID で持ち、文章だけを自由に書く。
  • 手順の項目
    主語（アクターの enum）・ 種類（相互作用 ・ 妥当性確認 ・ 内部の状態変化 ・ サブユースケースの呼び出し）・ 参照（相手 ・ 集約 ・ 呼び出し先 ・ 関係する利害関係者）
  • 拡張の項目
    分岐元の手順 ・ 条件の種類 ・ 終了の種類（enum で必須）
  • 書式
    手順は主語から始まる能動態の1文。拡張の条件は「〜だった：」のように、検出したことをコロンで終わる形で書く
  • NG ワード
    分岐（もし ・ 場合は）・ UI 操作（ボタン ・ クリック）・ 技術用語（API ・ テーブル）を文章に書かない
どちらも、使う言葉は区切られた文脈の用語集にあるものに限る。名前 ・ 状態の値 ・ エラーの理由 ・ 手順で渡すデータは用語集と照らし合わせ、用語集の NG ワードに当たったらエラーにする。
