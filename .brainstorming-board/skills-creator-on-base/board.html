論点の一覧

完成した基盤 schema-driven の上で、どの AI ツールでも呼ばれて手順どおりに動く Skill を作れるように、skills-creator の役割 ・ 入口 ・ 配る手順 ・ 自身の作りと、完成の条件を決める。古い skills-creator のボードは過去の構成のものとして参照しない。

いま見るのは 5 件だけである


  1. アドバイザーが、完成の条件が上位目的（どの AI ツールでも動く）に届いていないと指摘した

  2. いまの scaffold と check が、tool.json と宣言したツールを前提にしている

  3. 入口を持つと決めたが、置き場所と呼び方が決まっていない

  4. 配る手順を skills-creator の持ち物と決めたが、中身が決まっていない

  5. いまのコードは基盤の CODING.md と違う形のまま

Q1

skills-creator は何を作り、何をどの段で検査するか

skills-creator は、新しい Skill の雛形を置く scaffold と、書いたその場（source）と配ったあと（dist）の2段で検査する check と、配る手順（dist）を持つ。tool.json はやめる。
  • scaffold は、まだ無いフォルダにだけ置く。置くのは SKILL.md の雛形、concrete スキーマの雛形（基盤の create で作る）、入口のソースの雛形（src/<Skill名>/）である
  • 既にある Skill を直すときは、scaffold を使わず、check の結果から直す
  • check は、どの項目も既定を「判定不能」にし、確かめた分岐からだけ合格を出す。不合格か判定不能が1件でもあれば、終了コードを0以外にする
  • source の段は、SKILL.md の型 ・ 記入欄が残っていない ・ concrete スキーマが1件以上ある ・ 基盤の check-schemas が通る、を見る
  • source の段は、入口のソースがビルドの印（Rust なら Cargo.toml）を持つことと、古い形のファイル（tool.json など）が無いことも見る
  • dist の段は、dist.json が型に合う ・ 記録したファイルの SHA-256 が合い記録に無いファイルも無い ・ target が一致する、を見る
  • dist の段は、入口とエンジンが --version で記録した版を答えることと、入口に渡した基盤の操作がエンジンを直に呼んだ結果と同じになることも見る
  • dist の段で前提（実行ファイル）が欠けていれば、対象外ではなく不合格にする
  • 共有のデザインシステムは、その Skill ができるまで、理由を付けた対象外として報告する
  • 「呼ばれるか」は check では判定しない。AI ツールで実際に確かめる（Q0）
  • 全 Skill で基盤の版が1つかは、1つのフォルダを見る check では比べる相手が無いので、check に入れない

Q3

上の Skill のフォルダに入口と基盤のエンジンの写しをどう入れ、何を記録し、失敗したらどうするか

配る手順は、入口をビルドし、基盤のエンジンを版を指して Release から取り、SHA-256 と証明を照合してから、入口 ・ エンジン ・ dist.json をまとめて置く。途中で失敗したら、フォルダを元のまま残す。
  • 呼び方は scripts/bin/skills-creator dist <Skill のフォルダ> --engine <基盤の版> [--target <target>]
  • 基盤の配布物は、schema-driven-v<版> の Release から取り、SHA256SUMS と証明（署名したワークフローと tag まで縛る）を照合する
  • 照合には gh の attestation を使う。gh が無いか古いときは、照合の前で止める。照合を飛ばす旗は作らない
  • 作業用のフォルダで全部をそろえて確かめてから、Skill のフォルダへ移す。途中で失敗したら、Skill のフォルダは元のまま残し、どの段で止まったかを返す
  • dist.json の型は skills-creator が持つ（skills-creator/dist@v1）。Skill の名前 ・ 版 ・ target ・ 入口の SHA-256 ・ 写しごとの名前と版と取得元の配布物の SHA-256 を記録する
  • 共有のデザインシステムは、その Skill ができるまで写さず、dist.json に「写していない」と理由を書く
  • 基盤の版を指定する1か所 ・ 全 Skill の版の一致 ・ 上の Skill の Release への公開と導入は、2件目の Skill を移すときに決める

Q4

skills-creator のコードをどう組み、自分の Skill のフォルダをどう作るか

src/skills-creator を基盤と同じ CODING.md ・ ヘキサゴナル（core と adapters）・ xtask の形で作り直す。xtask は skills-creator をビルドし、その配る手順で自分のフォルダを作る。
  • src/skills-creator/CODING.md を置き、基盤の CODING.md と同じ規則（層 ・ crate ・ 試験 ・ 検査の順）に従う
  • crate は core（domain ・ application ・ port）と adapters（CLI の受け口 ・ ファイル ・ 基盤のエンジンの呼び出し ・ Release の取得と照合）の2つ
  • xtask は cargo のビルドだけを行い、フォルダを作る仕事は skills-creator の dist を呼ぶ。配る手順を xtask と skills-creator の2か所に書かない
  • いまのコード（check.rs など）と、古い形との移り方の試験（migration.rs ・ baseline-v3）は残さずに作り直す
  • 雛形（SKILL.md ・ スキーマ ・ 入口のソース）と型のスキーマは、Skill のフォルダの assets/ に置く
