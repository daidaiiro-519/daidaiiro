Q1

skills-creator は何を作り、何を検査するか

skills-creator は、新しい Skill の雛形と基盤のエンジンを置く scaffold、エンジンを別の版に入れ替える engine、Skill のフォルダを検査する check を持つ。tool.json と、作った Skill を配る手順は持たない。
  • scaffold は、まだ無いフォルダにだけ置く。置くのは SKILL.md の雛形 ・ concrete スキーマの雛形（基盤の create で作る）・ scripts/ の入口の雛形 ・ 照合した基盤のエンジン（Q3）である
  • 既にある Skill を直すときは、scaffold を使わず、check の結果から直す
  • check は、どの項目も既定を「判定不能」にし、確かめた分岐からだけ合格を出す。不合格か判定不能が1件でもあれば、終了コードを0以外にする
  • check は、SKILL.md の型 ・ 記入欄が残っていない ・ concrete スキーマが1件以上ある ・ 基盤の check-schemas が通る、を見る
  • check は、エンジンが起動して版を答えること（別の OS 向けのエンジンは起動しないので、ここで見つかる）・ concrete スキーマが使う abstract の版（x-abstract）をエンジンが扱えること ・ 入口が基盤の操作をエンジンに渡せること、も見る
  • check は、古い形のファイル（tool.json など）が無いことも見る
  • 「呼ばれるか」は check では判定しない。AI ツールで実際に確かめる（Q0）
  • 作った Skill をどう配るかは、その Skill を作った人が決める。skills-creator は配る手順を持たない

Q2

作られる Skill の入口を、どこにどう置き、SKILL.md からどう呼び、どう基盤のエンジンを呼ぶか

入口は、拡張子の無い scripts/<Skill名> と、Windows で起動する scripts/<Skill名>.cmd の2つで1つの名前にし、SKILL.md は scripts/<Skill名> とだけ書く。
  • 入口の名前は、SKILL.md やドキュメントが言語に依存せずに参照するための、共通の窓口である。tool.json が持っていた役目を、入口のファイル自身が持つ
  • scripts/<Skill名> は、1行目で実行のしかた（#!/usr/bin/env python3 など）を指定した入口のソースで、作った人が持つ。macOS ・ Linux ・ WSL ・ Git Bash で動く
  • scripts/<Skill名>.cmd は、上の入口を Windows の実行環境で起動するだけの数行で、PowerShell と CMD で使われる
  • 入口を別の言語で書き直すときは、この2つを差し替えるだけで、SKILL.md もドキュメントも変わらない
  • 基盤のエンジン（実行ファイル）は scripts/bin/ に置く。入口は、作業ディレクトリでも PATH でもなく、自分のファイルの場所から Skill のフォルダとエンジンを決める
  • 基盤の操作は scripts/bin/schema-driven --skill <自分のフォルダ> へ渡し、終了コード ・ 標準出力 ・ 標準エラーを変えずに返す。Skill の能力は入口の中で行う
  • 自分の能力を持たない Skill は、入口を置かず、SKILL.md から scripts/bin/schema-driven を直接呼んでよい
  • scaffold が出す入口の雛形は、最初は Python の1つにする。ほかの言語の雛形は、必要になったときに足す

Q3

作られる Skill のフォルダに、基盤のエンジンをどう入れ、どう入れ替えるか

skills-creator は、基盤のエンジンを版を指して Release から取り、SHA-256 と証明を照合してから scripts/bin/ に入れる。記録のファイルは置かず、途中で失敗したらフォルダを元のまま残す。
  • scaffold が最初に入れ、engine <Skill のフォルダ> --version <版> [--target <target>] で入れ替える
  • target は、明示されなければ動かしている環境のものにする
  • 基盤の配布物は、schema-driven-v<版> の Release から取り、SHA256SUMS と証明（署名したワークフローと tag まで縛る）を照合する
  • 照合には gh の attestation を使う。gh が無いか古いときは、照合の前で止める。照合を飛ばす旗は作らない
  • 作業用のフォルダで照合してから scripts/bin/ へ移す。途中で失敗したら、Skill のフォルダは元のまま残し、どの段で止まったかを返す
  • 記録のファイルは置かない。版はエンジン自身が --version で答える
  • SHA-256 と証明の照合は、入れるときに1回だけ行う。呼ぶたび ・ 検査のたびには照合しない
  • 共有のデザインシステムの写しは、その Skill ができてから扱いを決める

skills-creator のコードをどう組み、実行ファイルをどう置き、どう公開するか

skills-creator は基盤と同じく、私たちがソースを管理して実行ファイル scripts/bin/skills-creator として置き、専用のワークフローで3つの OS 向けに証明付きで公開する。
  • src/skills-creator/CODING.md を置き、基盤の CODING.md と同じ規則（層 ・ crate ・ 試験 ・ 検査の順）に従う
  • crate は core（domain ・ application ・ port）と adapters（CLI の受け口 ・ ファイル ・ 基盤のエンジンの呼び出し ・ Release の取得と照合）の2つ
  • 版の正本は Cargo.toml の [workspace.package] の version の1か所にし、--version で答える
  • xtask は skills-creator をビルドして scripts/bin/skills-creator に置き、基盤のエンジンはビルドした skills-creator の engine で入れる。エンジンを入れる手順を2か所に書かない
  • SKILL.md は scripts/bin/skills-creator <操作> と書く。実行ファイルは言語に依存しないので、.cmd の窓口はいらない
  • 公開は、基盤のワークフローを写した .github/workflows/skills-creator.yml が行う
  • tag skills-creator-v<版> で、build ・ verify ・ publish ・ receive の4段を通す
  • 私たちが管理するものが3つになったら、公開のワークフローを共通の1本にまとめる
  • いまのコード（check.rs など）と、古い形との移り方の試験（migration.rs ・ baseline-v3）は残さずに作り直す
