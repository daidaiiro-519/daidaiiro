Q1

規則が無いまま作ると何が崩れるか。規則は、何を防ぐためにあるか

規則は、同じ役割が2か所以上にある ・ 依存が層を飛ばす ・ テストと実装の境界が崩れる ・ 名前と中身が食い違う、の4つの崩れを防ぐためにあり、どの規則もこのどれを防ぐかと、それを機械でどう見つけるかを持つ。
  • 4つの崩れは、規則が無いまま、別々の時期に、その場で決めた結果としていまの schema-driven に出ている（完成イメージの「コード」の一覧）
  • 規則の1件は、防ぐ崩れが4つのどれかを書く。どれも防がない規則は置かない
  • 規則の1件は、崩れを機械で見つける検査（clippy ・ crate の依存の向き ・ grep ・ 試験）を持つ。検査を持てない規則は置かない
  • 4つの崩れは言語に依らない。Rust の具体（crate ・ trait ・ #[cfg(test)]）は、規則の中身の側に書く

Q2

規則の正本をどこに、どんな形で持ち、人と AI はそれをどう読むか

規則の正本は、各リポジトリに1か所、コーディングの Skill の concrete スキーマに従う JSON として持つ。人には HTML と CODING.md を、AI の入口にはリポジトリの根の AGENTS.md を、正本から作って渡す。
  • 規則の型（何を書けるか）は、コーディングの Skill（use-case-driven-coding）の assets/ に concrete スキーマとして置く。基盤は持たない
  • 規則の中身（正本）は、各リポジトリの .coding-rules/rules.json に1か所だけ置く。このリポジトリの Rust のツールの規則も、その1つである
  • 人が読む HTML と CODING.md は、正本から描画する。手で書き換えない
  • AI の入口は、リポジトリの根の AGENTS.md にする。AGENTS.md には規則を書き写さず、正本と描画したものへの案内を書く
  • 規則の1件は、規則 ・ なぜ（防ぐ崩れ）・ 検査 ・ 出典を必ず持つ。JSON にするのは、この4つを欄として必ず書かせ、機械で読めるようにするためである
  • 型の欄の形は、規則の中身（構成 ・ trait ・ テスト）が出そろってから取り出して決める
  • 型は言語に依らない形にし、Rust の規則は中身として書く。いま書くのは Rust の規則だけにする
