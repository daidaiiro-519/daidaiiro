Q1

ページのデザインシステムと部品のカタログのうち、何を基盤の変わらない契約にし、何を concrete の中身にするか

基盤は、部品1つが守る形 ・ トークンが守る形とコントラストの下限 ・ 描画の仕組み ・ 検査だけを持ち、部品の一覧と見た目 ・ 操作と、トークンの値は concrete が持つ。
  • 基盤は、部品の名前もトークンの名前も持たない。concrete が部品を足しても、基盤は変わらない
  • カタログの契約は、部品1つの書き方の形（名前 ・ 入力の形 ・ 説明 ・ 状態ごとの振る舞い）の枠だけにする。部品12の名前と入力の形は、基盤から concrete へ移す
  • トークンの契約は、トークンが守る形の検査（形式 ・ 参照 ・ 循環）と、コントラストの下限（文字 4.5:1、部品の境界 3:1）だけにする。どの2色を比べるかは、concrete が宣言する。トークンの層の分け方は契約にしない
  • 描画の仕組みは、ページテンプレートと、concrete が渡すカタログからページを作る。基盤の中のカタログの実装は持たない
  • 文書の決まった見た目は持たない。ページテンプレートの指定が無い種類は、描かずに「指定が無い」と返す
  • 基盤の試験は、試験用の小さなカタログで描く
  • 移す順は、基盤の中でカタログをアダプタとして分け、基盤のコードが部品の名前を参照していないことを確かめてから、外へ移す

Q2

Q3

共有のデザインシステムと基盤のエンジンを、使う Skill へどう届け、版の食い違いをどう見つけるか

skills-creator の配布物を作る手順が、各 Skill のフォルダへ、入口 ・ 基盤のエンジンの写し ・ 共有のデザインシステムの写しを入れる。写しごとの版と SHA-256 を記録し、全 Skill の版が1つであることを検査する。
  • 配布物を作る手順は skills-creator が持つ。creator は Agent Skills としての形と、配る前の検査を持つと決めてある
  • 写しにするのは、基盤のエンジン（scripts/schema-driven）と、共有のデザインシステム（assets/design-system/）である。どちらも git では追跡せず、配布物の段で入れる
  • その Skill の正本（SKILL.md ・ スキーマ ・ ページテンプレート ・ その Skill だけが使う部品）は、Skill のフォルダで git で追跡する
  • 入口（その Skill だけの能力を中に持つ）は、ソースを src/<Skill>/ に置き、配布物の段でビルドして scripts/ に入れる。その Skill の実行ファイルは入口の1つだけである
  • 配布物の段で、写しごとの版と SHA-256 を、Skill のフォルダの dist.json に書く。check の配布物の段は、dist.json と中身が合うかを見る
  • リポジトリの全 Skill について、エンジンの版と共有のデザインシステムの版がそれぞれ1つであることを検査する
  • このリポジトリの中で使うときも、同じ手順で各 Skill のフォルダへ入れる。手で写さない
  • 呼ぶたびの SHA-256 の照合はしない。配るとき ・ 入れるときに1回だけ確かめる

Q4

AI が Skill を使うとき、何を呼ぶか。基盤の能力と、その Skill だけの能力を、どこから呼ぶか

各 Skill は自分の入口の実行ファイルを1つ持ち、SKILL.md の手順はその入口だけを呼ぶ。入口は、基盤の能力を自分のフォルダを渡して基盤へ渡し、その Skill だけの能力は自分で実行する。
  • 入口は scripts/<Skill の名前> に置く。--json で、できることの一覧を返す
  • 基盤の能力（作成 ・ 取得 ・ 更新 ・ 検査 ・ 承認 ・ 描画など）は、入口が scripts/schema-driven に、入口の1つ上のフォルダ（その Skill のフォルダ）を渡して呼ぶ
  • その Skill だけの能力（例：ブレストボードの advance ・ inspect ・ serve）は、入口が実行する。JSON の読み書きは基盤を呼ぶ
  • SKILL.md は基盤のコマンドを書かない。基盤の呼び方が変わっても、直すのは入口の中だけである
  • --skill は基盤の内部の引数として残す。呼ぶのは入口だけである
  • 基盤のエンジンは入口に取り込まず、別の実行ファイル（scripts/schema-driven）のまま呼ぶ。Skill を作る人が、入口をどの言語で書いてもよいようにするためである
  • 入口は、その Skill のコードで、言語は問わない。このリポジトリでは Rust で書き、ソースは src/<Skill>/ に置く。雛形は skills-creator の scaffold が置く
  • SKILL.md の手順が scripts/schema-driven を直接呼ぶ、という決まりは、この答えで改める

案採らなかった理由
SKILL.md の手順が、基盤（scripts/schema-driven）と Skill の実行ファイルを、それぞれ直接呼ぶ基盤の呼び方が変わるたびに、全 Skill の SKILL.md を書き直すことになる。AI が基盤の引数まで知ることになる
基盤が、Skill の能力も呼べる入口になる（やめた宣言したツールの形）入口の持ち主が基盤になり、Skill の能力の形を基盤が知ることになる
基盤のエンジンをライブラリとして入口に取り込み、実行ファイルを1つにする基盤は Rust で書いてあるので、取り込むと入口を Rust でしか書けなくなる。ほかの人がほかの言語で Skill を作れることを優先する。配るファイルが1つになり版が必ずそろう利点はあるが、版は配布物の段の検査でそろえられる
その Skill だけの能力を、入口とは別の実行ファイル（scripts/advance など）に分けるSKILL.md が呼ぶ先が増え、入口を1つにした意味が薄れる
エンジンが自分の置き場所から Skill のフォルダを決め、SKILL.md から直接呼ぶ引数は減るが、SKILL.md が基盤の CLI に依存したまま残る
