Q1

ブレストボードの論点は、何を持つか

論点は、問い ・ 答え ・ 完成イメージ ・ 根拠 ・ 採らなかった案の5つだけを持つ。
  • 答えは、1文の決定と、1文ずつの下位の決定で書く
  • 完成イメージは1つ以上置き、形は論点2で決める
  • 根拠は、何を支えるか ・ もとにしたこと ・ 種別 ・ 出どころの4つで書く
  • 採らなかった案は、案と、採らなかった理由で書く
  • 番号 ・ 名前 ・ 状態（待ち ・ 開いている ・ 決着）は、タブと回答欄のために残す
この答えの完成イメージ ── 図 ・ UI ・ コード

Q2

完成イメージは、どんな形で持ち、どう見せるか

完成イメージは、図 ・ コード ・ UI ・ 差分の4種類から論点ごとに1つ以上を置き、2つ以上なら切り替えで見せる。
  • 図は SVG で持つ。何で描いたかは問わず、ボードは受け取った SVG を検査して置くだけにする
  • コードは、言語の名前と本文で持つ
  • UI は、描画した HTML を持ち、ボードの中に埋め込んで表示する（ボードの見た目と混ざらないように分けて描画する）
  • 差分は、変更前と変更後で持つ

Q3

ボードの機能のうち、何を schema-driven に任せ、何をボードの Skill に残すか

ボードの Skill は schema-driven を転写して持ち、形の検査 ・ 描画 ・ 冪等性は基盤に任せ、ボードに固有の操作だけを ExtraTools として持つ。
  • ボードと回答は、それぞれ board.schema.json ・ answer.schema.json のインスタンスにする。スキーマは基盤の契約（meta-schema）に従い、検査は基盤の check と check-schemas が行う
  • 描画は基盤の render が行う。ボードはページテンプレートと Design を渡す。完成イメージの切り替えと UI の埋め込みは、ボードの Design の部品にする
  • ボードに固有の操作は ExtraTools にする：serve（配って回答を受け取る）・ freeze（回の基準を保存する）・ inspect（日本語の散文の検査）
  • いまの validate.rs ・ audit.rs ・ template.rs ・ tokens.rs のうち、基盤が果たすものは消し、残りはスキーマの制約か ExtraTools へ移す
この答えの完成イメージ ── 図 ・ コード ・ UI

Q4

画面から外した、反証の過程 ・ 覆しうる前提 ・ 扱わない範囲 ・ 経過は、どこに残すか

書き手の検証の記録は、同じ論点のインスタンスの中に書き手だけが使う欄として持ち、ページテンプレートは描画しない。
  • 欄は verification の1つにまとめ、通過した案 ・ 覆しうる前提 ・ 扱わない範囲 ・ 経過を持つ
  • 基盤の check は、この欄も形を検査する。描画するかどうかは、ページテンプレートだけが決める
  • 決定を正本へ適用するときは、ここから ACDR の「なぜ」と「比較した案」へ書き写す

Q5

ボードのデザインテンプレートが従うデザインシステム（トークン ・ 部品 ・ 部品ごとの状態の決まり）を、どう持つか

ボードの Design は、トークンの3層と、部品ごとの状態の決まりを持つデザインシステムに従い、状態の色は部品をまたいでそろえる。
  • トークンは、いまの tokens.json の3層（基礎 → 意味 → 部品）と明暗を引き継ぐ。デザインテンプレートと部品は、色 ・ 寸法 ・ 書体をすべてトークンから引き、直値を書かない
  • 部品の一覧に、部品ごとの状態（通常 ・ 押した ・ 焦点 ・ 無効）と、その状態で使う意味のトークンを書く
  • 押した状態は、どのボタンも同じ意味のトークン（key）で塗る。差し戻しであることは、ボタンの文字で分かる
  • キーボードの焦点は、どの部品も key の外枠で示す
  • 「デザインテンプレートを持つ具体は、デザインシステムを持つ」を、schema-driven の契約とガードレールにも入れる（ACDR で出す）
この答えの完成イメージ ── 図 ・ コード ・ UI
