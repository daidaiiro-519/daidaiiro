Q0

schema-driven が完成したと言えるのは、何が観測できたときか

新しく公開した schema-driven-v<版> を、受け取る側の手順で1回通せたときに完成とする。手順は、版を指して取得し、SHA-256 と証明を照合し、展開して置き、実行ファイルに版を答えさせて一致を確かめる、の4つである。
  • この4つを、基盤専用のワークフローの最後の段が、公開した Release に対して実際に行う。skills-creator を使わずに確かめる
  • まっさらな clone で cargo xtask skill を1回実行すると、Skill のフォルダ（scripts/ ・ assets/ ・ dist.json）がそろい、git で追跡しているファイルに差分が出ない
  • dist.json の SHA-256 は、xtask とは別の実装（sha256sum ・ certutil）で照合して全件一致する

  • 3つの OS で、ビルドしたのとは別のランナーで展開した場所から、--version ・ check-schemas ・ MCP の tools/list（9つの名前）が通る
  • 証明の照合は、正しい配布物で通り、1バイト変えた配布物で止まる
  • CODING.md の検査の順（fmt ・ clippy ・ cargo tree ・ grep ・ test）が、手順を足したあとも0件で通る

Q1

基盤の Skill のフォルダ（scripts/bin/ と assets/）を、ソースから作る手順を、どこに何で持つか

src/schema-driven の workspace に、製品に入らないツールの crate として xtask を置く。cargo xtask skill --out <Skill のフォルダ> が、ビルドから dist.json までを行う。
  • xtask は workspace の根の xtask/ に置く。crates/ の外なので、製品の crate（core と adapters）とは並びが分かれる
  • xtask の仕事は3つに分ける ── build（cargo build を呼ぶ。--target を渡せばその OS 向け）・ skill（置く ・ SHA-256 を取る ・ dist.json を書く）・ verify（展開した場所で起動を確かめる）
  • skill は、scripts/bin/ へ実行ファイル2つ、assets/ へ crates/core/schemas/ の写し、Skill のフォルダの根へ dist.json を置く。SKILL.md と LICENSE は git で追跡したまま触らない
  • 置き先は --out で受け取り、xtask の中に .claude/ への道を書かない
  • ビルドした実行ファイルは scripts/bin/ に置き、scripts/ の直下は人や AI が読める言語で書いたスクリプトのために空けておく。SKILL.md ・ .mcp.json の呼び先も scripts/bin/ へ直す
  • dist.json は、名前 ・ 版 ・ target ・ abstract スキーマの $id ・ ファイルごとの SHA-256 を持つ。形はスキーマ（xtask/dist.schema.json）で決める
  • verify は rmcp のクライアントで tools/list を呼ぶ。ワークフローに JSON-RPC を手で書かない
  • CODING.md の crate の規則を「製品の crate は core と adapters の2つ。xtask はツールの crate で、製品の crate は xtask に依存しない」へ直し、検査も合わせる
  • このリポジトリの中で使うときも、cargo xtask skill --out .claude/skills/schema-driven で作る。手で写さない

Q2

基盤の版を、どこで1か所に決め、どう確かめるか

版の正本は src/schema-driven/Cargo.toml の [workspace.package] version の1か所に置く。CLI の --version ・ MCP の serverInfo.version ・ dist.json はそこから取り、公開の前に出どころの違う4つの値を比べる。
  • CLI に --version を足す。MCP の serverInfo.version は、すでに CARGO_PKG_VERSION を返している
  • 公開の前に比べる4つ ── tag の名前 ・ cargo metadata で読んだ Cargo.toml の版 ・ ビルドした実行ファイルが答える --version ・ dist.json の version
  • 4つのどれかが違えば、公開の前にワークフローが止まる
  • エンジンの版と、abstract スキーマの $id の版（schema-driven/abstract@v1 など）は別の軸である。dist.json に両方を書く
  • 公開した版は配布物と tag を変えられない。誤りが見つかったら、版を上げて出し直す

Q3

3つの OS 向けにビルドし、署名を付けて公開する流れを、どこに持ち、受け取る側との境目をどこに置くか

基盤専用のワークフロー .github/workflows/schema-driven.yml が、tag schema-driven-v<版> で動く。中身は、3つの OS のビルド ・ 別のランナーでの確かめ ・ 証明を付けた公開 ・ 公開後の受け取りの確かめである。境目は、受け取る側ができる4つの行為で約束する。
  • build：3つの OS で cargo xtask build と skill を動かす。dist.json を別の実装（sha256sum ・ certutil）で照合する。macOS は lipo -archs で2つの側が入っていることを、Linux は静的リンクであることを、Windows は C の実行時ライブラリを取り込んで（+crt-static）ほかの DLL に依存しないことを確かめる
  • verify：ビルドしなかったランナーで配布物を展開し、cargo xtask verify で --version ・ check-schemas（assets/）・ MCP の tools/list を確かめる
  • publish：Q2 の4つの版を比べ、SHA256SUMS を作り、actions/attest で証明を付け、bundle を Release に並べて公開する。証明を付ける権限はこのジョブだけに渡す
  • receive：公開した Release から版を指して取り直す。gh attestation verify に --repo ・ --bundle ・ --signer-workflow（このワークフロー）・ --source-ref（この tag）を付けて照合する。1バイト変えた配布物で止まることも確かめる。展開して --version を比べる
  • workflow_dispatch でも動かせるようにし、そのときは publish と receive を飛ばす。tag を付ける前に build と verify を1回通す
  • 配布物の名前は schema-driven-<版>-<target>.tar.gz（Windows は .zip）にし、古い形の <名前>-<target> と重ならないようにする
  • 基盤が約束する4つの行為 ── 版を指して取得できる ・ SHA-256 と証明で照合できる（どのワークフローがどの tag で作ったかまで）・ 展開すればそのまま動く ・ --version で版を答える

# .github/workflows/schema-driven.yml
on:
  push:
    tags: ["schema-driven-v*"]
  workflow_dispatch: {}          # build と verify だけを通す

jobs:
  build:    # linux-musl ・ windows-msvc ・ macOS universal2
    run: cargo xtask build --target $T && cargo xtask skill --out dist/schema-driven
  verify:   # ビルドしなかったランナーで展開して確かめる
    run: cargo xtask verify --dir schema-driven
  publish:  # tag のときだけ。4つの版を比べ、SHA256SUMS と証明を付けて公開
    permissions: { contents: write, id-token: write, attestations: write }
  receive:  # 公開した Release から取り直して、受け取る側の手順を通す
    run: |
      gh attestation verify $FILE --repo daidaiiro-519/daidaiiro --bundle attestation.sigstore.json \
        --signer-workflow daidaiiro-519/daidaiiro/.github/workflows/schema-driven.yml \

Q4

古い形の release.yml ・ install スクリプト ・ 公開済みの v1.0.0 を、基盤の公開とどう切り分けるか

古い形は考慮しない。基盤の公開は、基盤専用のワークフローだけで行う。
  • 古い形を残すための手当て（tag の除外 ・ まとめ公開の対象から外す ・ 配布物の名前を分ける）はしない
  • ただし古い release.yml は tag の形 *-v* で動くので、残したまま schema-driven-v<版> を付けると、同じ tag の Release を2つのワークフローが作ろうとして片方が落ちる
  • この衝突は、古い release.yml を消して避ける。install スクリプトも古い形だけのものなので一緒に消し、新しい形の導入は skills-creator の作業で作る
