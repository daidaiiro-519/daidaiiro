Q1

Skill の型は何のためにあり、作られた Skill に何を必ず求めるか

型は、Skill を読む AI エージェントが正しいときに Skill を呼び、手順どおりに動けることを、書いたその場で確かめるためにある。SKILL.md は Agent Skills の公開の仕様に従う正本のまま手で書き、skills-creator の check が先頭の欄と節を読み取って、型のスキーマで検査する。
  • SKILL.md を読むのは、Agent Skills の仕様を読む AI エージェント（Claude Code ・ Codex ・ GitHub Copilot ・ Cursor ・ Gemini CLI など）である。人は書いてレビューし、直すのはその SKILL.md である
  • 型は JSON Schema（skills-creator/skill@v1）で持ち、欄ごとに誰が読むための条件か（AI エージェントか、エンジンと skills-creator か）を書く
  • どちらの読み手にもつながらない欄は、型に入れない。手順や決まりの文章そのものも、型に入れない
  • AI エージェントのための条件：先頭の欄は、Agent Skills の仕様の欄（name ・ description が必須。license ・ compatibility ・ metadata ・ allowed-tools が任意）だけを許し、ツール独自の欄を許さない
  • AI エージェントのための条件：name は64文字までの小文字 ・ 数字 ・ ハイフンでフォルダ名と同じ、description は1,024文字まで、SKILL.md は500行未満
  • AI エージェントのための条件：6つの節（目的 ・ 役割 ・ 入力の想定 ・ 実行手順 ・ 出力形式 ・ ガードレール）をこの順に持つ
  • AI エージェントのための条件：本文は特定の AI ・ ツールの名前を宛先にせず、置き場所（.claude/ など）とツール専用の変数を書かず、ファイルを Skill のフォルダからの相対パスで指す
  • エンジンと skills-creator のための条件：tool.json に使う abstract の版を書き、実行ファイルを Skill のフォルダからの相対パスで指す
  • MCP の登録と Skill の置き場所はツールごとに違うので、型に入れず、導入のときにツールごとに扱う
  • SKILL.md を読み取って JSON にする処理は、提供側の skills-creator の check が持つ。作られた Skill はコードを持たない

Q2

Skill を作る人が、どの AI ツールに置いてもそのまま呼ばれて動く Skill を作り始めるには、scaffold は何を置くか

scaffold は SKILL.md の雛形 ・ tool.json ・ スキーマの雛形だけを置き、ファイルは誰が読むか動かすかで scripts/ ・ assets/ ・ references/ に分ける。実行ファイルは置かない。
  • SKILL.md の雛形は、先頭の欄（name はフォルダ名、description は記入欄）と6つの節を持ち、記入する所を {{…}} で示す。check は {{…}} の残りを指摘する
  • tool.json には、使う abstract の版と、エンジンを指す相対パス scripts/schema-driven を書く
  • スキーマとページテンプレートは assets/ に置く。スキーマの雛形は x-abstract と名前（<Skill>/<種類>@v1）を持つ
  • ページテンプレート（assets/pages/）と固有のツールの宣言（tools.json）は、作る人が求めたときだけ置く
  • references/ は AI エージェントが必要なときに読む文書の置き場所で、文書が無ければ作らない。空のフォルダは作らない
  • エンジンの実行ファイルはソースに置かない。OS ごとの配布物を作る段で、scripts/ に1つだけ入れる
  • SKILL.md の手順は、エンジンを Skill のフォルダからの相対パス（scripts/schema-driven）で呼ぶ

Q3

skills-creator の check は何を検査し、何を基盤の check-schemas と check に任せるか

check は項目ごとに id と5つの結果（合格 ・ 不合格 ・ 警告 ・ 判定不能 ・ 対象外）を返し、不合格が0件かつ判定不能が0件のときだけ合格にする。項目は書いたその場と配布物の2つの段に分け、スキーマとツールの宣言は基盤の判定を返す。
  • 書いたその場で skills-creator が判定するのは、SKILL.md の先頭の欄 ・ 長さ ・ 6つの節 ・ {{…}} の残り ・ 本文のパスとリンクと、tool.json である
  • 項目ごとに、不合格になる場合を分けて書く。name は65文字以上 ・ a-z と 0-9 と - 以外の文字 ・ - で始まるか終わる ・ -- が続く ・ フォルダ名と違う、の5つである
  • 境界のある項目は、両側の値を項目に書く。name は64と65文字、description は1,024と1,025文字、compatibility は500と501文字、SKILL.md は499と500行である
  • 本文は、構文で決まるものだけを不合格にする。Skill の置き場所（.claude/skills/ のような、ツールのフォルダの下の skills/）・ ツール専用の変数（${…}）・ 絶対パスの3つである
  • AI ・ ツールの名前は、型の版に付く一覧と照らして警告だけを返す。名前が宛先になっているかは、レビューのチェックリストで人が見る
  • assets/ のスキーマは基盤の check-schemas の結果を、tools.json は基盤の --skill --json の結果を、項目 id を付けて返す。基盤が答えられないときは判定不能にする
  • 前提の項目が不合格なら、それに依存する項目は対象外にする。先頭の欄が無ければ、name ・ description などは見ない
  • 配布物の段は、書いたその場で合格し、実行ファイルが入ってから見る。実行ファイルが在る ・ SHA-256 が合う ・ 宣言したツールが一覧に出る、の3つである。入っていなければ対象外にする
  • 試験データは、型の版ごとに skills-creator の中に置く。合格例を1つと、合格例から1か所だけ変えた不合格例を、不合格になる場合ごとに1つずつ置く
  • 不合格例のフォルダ名で何を破るかを示し、落ちる項目 id の集合を並べて置く。試験は終了コードと項目 id の集合の両方を照らす。前の版の試験データも消さない
  • いまの17の Skill は試験データにしない。check を直したときに毎回検査して、結果の変化を見る
