3アーキテクチャと技術スタックを、宣言 ・ 規則 ・ Cargo のどこに書くか決着A
宣言には書かない。構成と向きは Cargo.toml の crate の依存が持ち、版は Cargo.lock が持つ。なぜその構成とその crate かは ACDR が持つ。実装から宣言の文脈を指す場所は、no-more-spaghetti に代わるコーディングの Skill の形として決める
4描画のページテンプレート（kind ごとに、どの値をどのコンポーネントで並べるか）を、どんな形で書くか決着A
ページテンプレートは、節の並びと、節ごとのコンポーネントと、値を取る JMESPath 式だけを書く。値の選び方 ・ 繰り返し ・ 絞り込み ・ 条件は、取得の契約と同じ JMESPath で書く。文にするのは x-view、見た目はコンポーネントが持つ。基盤は描画の文脈（this ・ schema ・ derived ・ links ・ referrers ・ instances）を用意する
5基盤の上に作る Skill（具体）は、基盤の能力をどう使い、自分に固有の能力と契約をどこに持つか決着C
具体は、自分のヘキサゴナル（契約 ・ ユースケース ・ アダプタ ・ CLI と MCP）を持ち、基盤の crate を転写して部品として呼ぶ。基盤のポートは、基盤のユースケースのうち具体ごとに変わるところにだけ置き、具体はそこへ実装を渡す（Functions ・ Design）。具体に固有の能力は具体の core に置き、基盤へ戻さない
6スキーマは具体が持つ。基盤は、さまざまな具体のスキーマを、どんな共通の決まりに従わせ、それを誰がどう検査するかいま見るD
