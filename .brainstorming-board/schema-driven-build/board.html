#論点状態いまの答え
1schema-driven の道具を、どの層とモジュールに分けて組むか決着A
ヘキサゴナル（ポートとアダプタ）で組む。core に domain ・ application ・ ports を置き、adapters に入ってくる側（CLI ・ MCP の受け口）と出ていく側（ファイルシステム ・ jmespath）を置く。業務の分け方は、domain と application の中の名前に出るだけである。中核の参照と導出値は domain のドメインモデル、ほかの3つは application のトランザクションスクリプトになる
2Rust で使う crate と、その版と設定をどうするか決着A
各 crate の最新の版を使い、ネットワークに出る機能を外す。版は正本の Cargo.lock の1か所で決め、転写した複製は lock ごと写す。JMESPath の crate は保守が細いので、取得の操作をポートの後ろに置き、契約の試験を当てる
3アーキテクチャと技術スタックを、宣言 ・ 規則 ・ Cargo のどこに書くか決着A
宣言には書かない。構成と向きは Cargo.toml の crate の依存が持ち、版は Cargo.lock が持つ。なぜその構成とその crate かは ACDR が持つ。実装から宣言の文脈を指す場所は、no-more-spaghetti に代わるコーディングの Skill の形として決める
4描画のページテンプレート（kind ごとに、どの値をどのコンポーネントで並べるか）を、どんな形で書くか決着A
ページテンプレートは、節の並びと、節ごとのコンポーネントと、値を取る JMESPath 式だけを書く。値の選び方 ・ 繰り返し ・ 絞り込み ・ 条件は、取得の契約と同じ JMESPath で書く。文にするのは x-view、見た目はコンポーネントが持つ。基盤は描画の文脈（this ・ schema ・ derived ・ links ・ referrers ・ instances）を用意する
5具体（ユースケース駆動 ・ acdr など）は、自分のコンポーネントと見た目を、どんな形で基盤に登録するかいま見るB
具体は、ポート Design を Rust で実装してコンポーネントを登録する。見た目は具体のデータ（部品の HTML ・ CSS ・ JS）が持ち、コンポーネントの Rust は部品の差し込み口に値を入れるだけにする。基盤は、ページテンプレートを読んで組む流れ ・ 式の評価 ・ 文字の逃がし ・ 差し込み口の過不足の検査 ・ 入力の形でのページテンプレートの検査を持つ
