現在地

論点の一覧

schema-driven を Rust で作るときの、アーキテクチャと技術スタックと、それをどこに書くかを決める。宣言は schema-driven-base/product/ にあり、実装の型はそこから導いた。

いま見るのは 2 件だけである


  1. 宣言から実装の型が導けた（参照と導出値＝ドメインモデル、ほか3つ＝トランザクションスクリプト）ので、コードのどこに置くかを決められる

  2. 使う crate の原文を crates.io から取得し、版とライセンスを照合した

残り 1 件は、上流が決まるまで動く。回答欄は無い。

#論点状態いまの答え
1schema-driven の道具を、どの層とモジュールに分けて組むかいま見るA
外側をポートとアダプタにし、中の実装の型を業務領域ごとに変える。中核の check はドメインモデルとしてドメインの crate に置き、readwrite ・ render ・ transcribe はトランザクションスクリプトとしてアプリケーションの crate に置く。ポートはアプリケーションの側が決め、アダプタがそれを実装する。向きは crate の依存で止める
2Rust で使う crate と、その版と設定をどうするかいま見るA
各 crate の最新の版を使い、ネットワークに出る機能を外す。版は正本の Cargo.lock の1か所で決め、転写した複製は lock ごと写す。JMESPath の crate は保守が細いので、取得の操作をポートの後ろに置き、契約の試験を当てる
3アーキテクチャと技術スタックを、宣言 ・ 規則 ・ Cargo のどこに書くか待ちA
宣言には書かない。構成と向きは Cargo.toml の crate の依存が持ち、版は Cargo.lock が持つ。なぜその構成とその crate かは ACDR が持つ。実装から宣言の文脈を指す場所は、no-more-spaghetti に代わるコーディングの Skill の形として決める
いま見る論点
論点1（アーキテクチャ）と論点2（技術スタック）を同時に開いた。2つは互いに依存しない。論点3（どこに書くか）は、1と2の答えを置く場所なので、そのあとに開く。論点1の前提：skills-creator の雛形がレイヤードなのは、「Skill の道具は手続き的な変換である」という前提で決めたからである（ACDR 0056 ・ 0058）。schema-driven は中核がドメインモデルなので、この前提に当たらない。no-more-spaghetti は廃止した。.coding-rules と inward には持ち主がいないので、向きは Rust と Cargo そのものの仕組みで止める。
