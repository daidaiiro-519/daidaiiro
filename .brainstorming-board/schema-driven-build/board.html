根拠（6件）
結論のどこを支えるかもとにしたことその出どころ
基盤が注釈の契約を持つこと基盤は7つの契約（作成 ・ 取得 ・ 更新 ・ 削除 ・ 検証 ・ 描画 ・ x-prompt）と、注釈 x-ref ・ x-derive を読むツールを持つ決まりボード schema-driven-base の論点1
具体が注釈を足せること基盤の注釈は title ・ x-view ・ x-prompt ・ x-generates ・ x-ref ・ x-derive の6つで、開発の concrete は x-test-spec を足す決まりボード schema-driven-base の論点2
具体の注釈も検査することconcrete の注釈2つを、concrete のメタスキーマで検査する決まりボード schema-driven-base の論点2の要求事項
x-prompt の契約の形案内を要求するのは、実体を生成するスキーマだけである（x-generates を持つもの）。案内は、値を書く単位ごとに持つ実測ボード usecase-driven-concrete の sample/schema/schema-meta.schema.json（2026-10-06 に読んだ）
検査の結果承認済みの契約（annotations.schema.json ・ view.schema.json）で、具体のスキーマ14件をすべての深さまで測った。x-view の文の型は JMESPath として読めるかと、古い絞りの書き方も数えた実測測るためだけの Rust のツール（schema-driven-core の Schema と jmespath 0.5.0。2026-10-06）
名前 meta-schema.jsonA schema that itself describes a schema is called a meta-schema.原典JSON Schema Core（draft 2020-12）json-schema-core:2057（https://json-schema.org/draft/2020-12/json-schema-core、2026-10-07 に取得し、fact-check で引用を照合）
採らなかった案（3件）
案採らなかった理由
契約を持たず、具体に任せる具体のスキーマが基盤の契約に従っているかを、誰も確かめられない。実測で、仕様に無い x-ref のキーが基盤の検査に無視されていた
基盤が共通の中身を持つ具体ごとに中身は違う（acdr の記録とユースケース）。利用者の指摘のとおり、スキーマは具体が持つ
具体の注釈を禁じる基盤のボードの論点2で、開発の具体が x-test-spec を足すと決めている
Q7

具体のスキーマもデザインテンプレートも無いとき、基盤の render は何を受け取り、どう描画するか

B ── 基盤は文書の契約（references/document.schema.json）と、その決まったデザインを持つ。AI は伝えたいことを、情報の種類ごとのブロック（14種類）でこの契約に合う JSON に書き、render は決まったデザインで描画する。具体がスキーマとデザインテンプレートを持つときは、具体のものを使う。どちらでもない種類は描画せずにエラーにする
