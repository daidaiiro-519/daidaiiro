Q1

抽象の基盤は、何を契約として持つか

この論点が、基盤と concrete の境目を決める。論点2〜4は、この線を前提にする
B″操作の契約は4つである。実体の JSON を作成 ・ 取得 ・ 更新 ・ 削除する。
  • 作成の契約
    スキーマから実体の JSON を作成する。置き場所はスキーマの x-generates が決める
  • 取得の契約
    実体から、JMESPath の式で値を取得する
  • 更新の契約
    実体を、JSON Patch（RFC 6902）で更新する。位置は JSON Pointer で指す
  • 削除の契約
    実体の項目を JSON Patch の remove で削除し、実体そのものはファイル単位で削除する
形の契約は3つである。どの実体にも同じ3つを課す。
  • スキーマ検証の契約
    実体を JSON Schema で検証する
  • 描画の契約
    実体を Markdown と HTML へ描画する。見出しはスキーマの title、見せ方は x-view が決める
  • 案内の契約
    項目ごとに x-prompt の read（読み取るとき）と write（値を書くとき）を持つ
更新と削除は、適用したあとの実体が検証の契約を通過したときだけ書き込む。作成した直後の実体は、未記入の項目があるので検証を通過しなくてよい。concrete も同じ7つの契約を持つ。違うのは表現だけである。ユースケース駆動の concrete は、人が確認して承認できる構造化データとして宣言を持ち、ドリフト検知の契約を足す。
  • テスト仕様
    ユースケースのシナリオと、集約 ・ ドメインサービスの条件。品質を担保する要素になる
  • テスト実装
    実装の側のテスト。仕様の各要素を指すテストが存在し、通っていることを実装の品質とする
  • ドリフト
    仕様に在ってテストに無いもの、テストに在って仕様に無いもの、テストが通らないもの
基盤は、宣言の形を認知しない。種類 ・ ID ・ 参照のような宣言の構造は、concrete のスキーマにだけ現れる。

Q2

ユースケース駆動の concrete は、7つの契約とドリフト検知を、どの形で満たすか

この論点が、concrete が基盤に何を渡し、テスト実装と何で接続するかを決める。論点3（描画の持ち方）は、この形を前提にする
Bconcrete が渡すものは、宣言の種類ごとの JSON Schema だけである。基盤の注釈（title ・ x-view ・ x-prompt ・ x-generates）に、concrete の注釈を2つ足す。
  • x-test-spec
    この欄の項目がテスト仕様である。ユースケースのシナリオと、集約 ・ ドメインサービスの条件に付ける
  • x-ref
    この欄の値が、指定した種類の宣言の ID を指す
欄の名前は Schema にだけ現れる。concrete のコードは注釈を読み、欄の名前を保持しない。検証は、宣言の集合に対して行う。
  • Schema
    宣言ごとに、$schema が指す Schema で検証する
  • ID の一意
    宣言の ID は集合の中で、項目の ID は宣言の中で一意である
  • 参照の解決
    x-ref の先の宣言が在り、種類が一致する
更新と削除は、適用したあとの集合が検証を通過したときだけ書き込む。論点1の規則を、集合へ広げたものである。参照されている宣言の削除は、参照の解決に違反するので拒否される。テスト仕様の ID は「宣言の ID.項目の ID」とする。例は UC-1.S-2 と AGG-1.INV-1 である。テストの報告は JSON で受ける。concrete が Schema（test-report.schema.json）を持ち、1件は id と result（pass ・ fail ・ skip）である。報告を作る手段は、技術スタックごとにコーディングの側が持つ。ドリフトは3種を報告する。仕様に在ってテストに無いもの、テストに在って仕様に無いもの、pass でないもの（fail と skip）である。

Q3

人が読む描画と、AI ツールが読む形を、基盤と concrete のどちらが持つか

この論点が、人と AI ツールがそれぞれ何を読むかを決める。論点4（配り方と名前）は、この分担を前提にする
B基盤が持つ描画は2つである。
  • 実体1件の描画
    title と x-view で、Markdown と HTML へ描画する。HTML は契約の版2 の view の型とトークンで組む
  • 違反の描画
    検証の違反を、欄の title と違反の種類と x-prompt.write で示す。違反の種類の語は基盤が持つ

基盤の描画は、値の見せ方を concrete が注入する口を1つ持つ。

concrete は、宣言の集合を頁の集まりに組む。
  • 頁の並び
    根（ドメイン）を先頭に、連鎖の浅い順に並べる
  • 目的の連鎖
    どの頁も先頭に、根からこの宣言までの連鎖を置く
  • 参照の名前
    参照の値を、ID と名前で描く。基盤の注入の口を使う
  • 逆参照
    この宣言を指す要素を、頁の末尾に置く
上位の目的は、x-ref に付ける注釈 x-purpose で申告する。
  • upward
    参照先が、この宣言の上位の目的である。例はユースケースの「寄与する達成の基準」
  • downward
    参照元が、参照先の上位の目的である。例はユースケースの「書き換える集約」
上位の目的を保持しない宣言は、集合の検証で検出する。根の種類だけを除く。AI ツールの形へは変換しない。AI ツールは CLI か MCP で、案内（x-prompt.read）と取得（JMESPath）を使って読む。9月の論点2の「実行の道具の形」の射影は置かない。
