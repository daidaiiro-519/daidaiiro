Q1

抽象の基盤は、何を契約として持つか

B⁗ ── 抽象の基盤は、AI が扱うデータを構造化して持つための基盤である。正本は構造化データ（JSON とスキーマ）で、Markdown と HTML は描画した結果である。基盤は7つの契約（作成 ・ 取得 ・ 更新 ・ 削除 ・ 検証 ・ 描画 ・ x-prompt）と、注釈 x-ref ・ x-derive を読む道具を持つ。テスト条件とドリフト検知は、開発の concrete が持つ
  • 作成の契約 ── スキーマからインスタンスを作成する。出力先のパスはスキーマの x-generates が決める
  • 取得の契約 ── インスタンスから、JMESPath の式で値を取得する
  • 更新の契約 ── インスタンスを、JSON Patch（RFC 6902）で更新する。位置は JSON Pointer で指す
  • 削除の契約 ── インスタンスの項目を JSON Patch の remove で削除し、インスタンスそのものはファイル単位で削除する
  • スキーマ検証の契約 ── インスタンスを JSON Schema で検証する
  • 描画の契約 ── インスタンスを Markdown と HTML へ描画する。見出しはスキーマの title、見せ方は x-view が決める
  • x-prompt の契約 ── 項目ごとに x-prompt の read（読み取るとき）と write（値を書くとき）を持つ
  • x-ref ── 指す先がある ・ 指す先の種類 ・ 指される数 ・ 承認のあとで指す先が変わった、を出す
  • x-derive ── 決まりに従って、答えから判定を出し、宣言した値と突き合わせる
  • 開発の concrete ── x-test-spec でテスト条件を申告し、テストの記録との突き合わせ（欠け ・ 余り ・ 古い ・ レベル違い）を持つ

━━ 8. ドリフト検知（concrete だけの契約）── テスト仕様とテスト実装を突き合わせる

テストに在って仕様に無い: ["UC-1.S-3"]
テストが通っていない:     ["UC-1.S-2"]

基盤は AI の構造化データ管理の基盤で、正本は構造化データ、Markdown と HTML は描画した結果である。テスト条件とテストの記録との突き合わせは、開発の concrete が基盤の注釈の上に持つ。

上位の目的を Schema の required だけで表す集約の上位の目的は、集約の中ではなく、それを書き換えるユースケースの側に在る。集約の Schema の required では表せず、試作の AGG-2 は集合を見て初めて検出できた
AI ツールごとの形へ変換する宣言の複製がツールの数だけ増え、複製と宣言のずれを管理することになる。x-prompt と取得で読めば、複製を作らずに必要な欄だけを読める
違反は検証器の文のまま出す検証器の文は英語で、欄の名前も書き方も示さない。欄の title と x-prompt.write は Schema に既に在る
Q4

基盤と concrete を、どの単位で配り、何と呼ぶか

A ── 基盤は、1つの Skill「schema-driven」として配る。この Skill が基盤の能力の正本（Rust の crate ・ コンポーネントのテンプレート ・ デザイントークン）を持ち、単独でも使える。基盤をもとに作るものには、作るときに正本の複製を転写し、基盤の差分の検査が、複製と正本の違いを報告する。concrete（ユースケース駆動）は基盤とは別に、use-case-driven-development の一式として配る
この答えの完成イメージ ── UI ・ コード ・ 図
.claude/skills/schema-driven/          ← 正本
  tool/  references/  bin/schema-driven

.claude/skills/use-case-driven-modeling/
  tool/base/        ← schema-driven から転写した複製（書き換えない）
  references/schemas/*.schema.json   ← この Skill の宣言のスキーマ
  references/pages/*.page.json       ← この Skill の頁の型

$ schema-driven check .claude/skills/use-case-driven-modeling
  複製と正本の違い：0件

schema-driven が正本を持ち、基盤をもとに作るものへ複製を転写する。差分の検査が、複製と正本の違いを報告する。右の2つの Skill の名前と持ち物は例で、役割の分担はボード usecase-modeling-coding で決める。

根拠（4件）
結論のどこを支えるかもとにしたことその出どころ
複製を転写すること基盤をもとに作るものには、基盤の能力の複製を転写する（skills-creator の雛形の契約と同じ形）決まり利用者の言明（2026-10-04）
Skill ごとに配ることRelease の公開の単位を Skill ごとにし、全部の Skill をまとめて公開する形はオプションとして残す決まりACDR 0042
基盤を単独で使える Skill にすること基盤は、開発に限らない AI の構造化データ管理の基盤である決まりこのボードの論点1（B⁗）
転写と差分の検査の形scaffold が各 Skill の references/ へ複製し、check が複製と正本の差を検査する決まりskills-creator の SKILL.md（references/view/ の項）
採らなかった案（3件）
案採らなかった理由
基盤を共有の依存（cargo の依存）として使う作ったものが基盤なしでは動かない。基盤をもとに作るものへ能力の複製を転写する、という前提（利用者の言明）に反する
基盤を skills-creator の雛形の中に置く基盤は開発に限らない構造化データ管理の基盤である（論点1）。Skill を作る道具の中に置くと、単独で使う形が無くなる
作るものごとに、基盤の能力を書く同じ概念の仕組みが別々に書かれ、形がずれる
