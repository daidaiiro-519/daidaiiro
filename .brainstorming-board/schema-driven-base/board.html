Q1

抽象の基盤は、何を契約として持つか

この論点が、基盤と concrete の境目を決める。論点2〜4は、この線を前提にする
B″操作の契約は4つである。実体の JSON を作成 ・ 取得 ・ 更新 ・ 削除する。
  • 作成の契約
    スキーマから実体の JSON を作成する。置き場所はスキーマの x-generates が決める
  • 取得の契約
    実体から、JMESPath の式で値を取得する
  • 更新の契約
    実体を、JSON Patch（RFC 6902）で更新する。位置は JSON Pointer で指す
  • 削除の契約
    実体の項目を JSON Patch の remove で削除し、実体そのものはファイル単位で削除する
形の契約は3つである。どの実体にも同じ3つを課す。
  • スキーマ検証の契約
    実体を JSON Schema で検証する
  • 描画の契約
    実体を Markdown と HTML へ描画する。見出しはスキーマの title、見せ方は x-view が決める
  • 案内の契約
    項目ごとに x-prompt の read（読み取るとき）と write（値を書くとき）を持つ
更新と削除は、適用したあとの実体が検証の契約を通過したときだけ書き込む。作成した直後の実体は、未記入の項目があるので検証を通過しなくてよい。concrete も同じ7つの契約を持つ。違うのは表現だけである。ユースケース駆動の concrete は、人が確認して承認できる構造化データとして宣言を持ち、ドリフト検知の契約を足す。
  • テスト仕様
    ユースケースのシナリオと、集約 ・ ドメインサービスの条件。品質を担保する要素になる
  • テスト実装
    実装の側のテスト。仕様の各要素を指すテストが存在し、通っていることを実装の品質とする
  • ドリフト
    仕様に在ってテストに無いもの、テストに在って仕様に無いもの、テストが通らないもの
基盤は、宣言の形を認知しない。種類 ・ ID ・ 参照のような宣言の構造は、concrete のスキーマにだけ現れる。
