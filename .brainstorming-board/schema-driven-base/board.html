Q1

抽象の基盤は、何を契約として持つか

この論点が、基盤と concrete の境目を決める。論点2〜4は、この線を前提にする
B′抽象の基盤の契約は3つである。どの構造化データにも、同じ3つを課す。
  • スキーマ検証の契約
    構造化データを JSON Schema で検証できる
  • 描画の契約
    構造化データを Markdown と HTML へ描画できる。見出しはスキーマの title、見せ方は x-view が決める
  • 案内の契約
    項目ごとに x-prompt の read（読み取るとき）と write（値を書くとき）を持つ
concrete も同じ3つの契約を持つ。違うのは表現だけである。ユースケース駆動の concrete は、人が確認して承認できる構造化データとして宣言を持つ。ユースケース駆動の concrete は、4つ目の契約を持つ。テスト仕様とテスト実装のドリフト検知である。
  • テスト仕様
    ユースケースのシナリオと、集約 ・ ドメインサービスの条件。品質を担保する要素になる
  • テスト実装
    実装の側のテスト。仕様の各要素を指すテストが存在し、通っていることを実装の品質とする
  • ドリフト
    仕様に在ってテストに無いもの、テストに在って仕様に無いもの、テストが通らないもの
基盤は、宣言の形を認知しない。種類 ・ ID ・ 参照のような宣言の構造は、concrete のスキーマにだけ現れる。
