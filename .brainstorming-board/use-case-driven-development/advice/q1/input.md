# 相談の材料：ユースケース駆動開発の、手法の構成と原典の概念の置き場所

## 前提（利用者の意図。手法の決定であり、変えない）
- この開発手法は、AI の時代に、作りたいものの目的を的確に定め、そこから抽象モデリングと抽象コーディングを進めるやり方である。
- 最上位には、作りたいプロダクトやサービスそのものを「ドメイン」として置く。ドメインは目的とビジョンを持つ。事業全体を最上位に置くと、スコープの取り方として広すぎる。
- そのドメインを、正しい目的レベルに分解してユースケースにする。ユースケースの集まりがドメインを構成し、最終的にプロダクトやサービスになる。
- 『ドメイン駆動設計をはじめよう』と『ユースケース実践ガイド』の2冊は、考え方 ・ 概念 ・ モデリング ・ 抽象設計の土台として採る。**概念の意味は2冊に忠実にし、ぶらさない。**ただし書籍をそのまま仕組みにするのではない。

## オーケストレーターの見立て（検証してほしい）
1. 構成は次の順に読む：ドメイン（プロダクト。目的 ・ ビジョン ・ 利害関係者と利益 ・ スコープの内外）→ 要約レベルのユースケース → ユーザー目的レベルのユースケース → サブ機能。ドメインの目的から要約、要約からユーザー目的へと、目的レベルの意味を変えずに分解する。
2. ドメインの目的とビジョンは、『ユースケース実践ガイド』のビジョン記述（3.4 ・ 17.6）と、要求アウトライン第1章（全体のスコープと目的 ・ 利害関係者 ・ スコープの内外）に当たる。
3. 業務領域（サブドメイン）は、プロダクトの中で「強く関連するユースケースの集まり」（『ドメイン駆動設計をはじめよう』1.2.3.2）として置く。中核 ・ 一般 ・ 補完の分類も、意味を変えずにプロダクトの中で使う。
4. 区切られた文脈は、プロダクトの中のモデルの境界として設計する。集約 ・ 値オブジェクト ・ 業務サービスは区切られた文脈の中に置き、ユースケースの手順から呼ばれる。
5. 『ドメイン駆動設計をはじめよう』の「事業領域」（企業が事業活動を展開する領域）と、この手法の「ドメイン」（作りたいプロダクト）は、スコープの取り方が違う。この違いは手法の決定として明記し、事業領域の語の意味は変えない。

## 聞きたいこと
A. 見立て1〜5 で、原典の概念の意味を変えてしまっているところはどこか。変えずに当てはめるにはどうするか。
B. プロダクトを最上位に置いたとき、原典のどの概念が、そのまま使えて、どれが使えない（または注意が要る）か。設計スコープ（企業 ・ システム）と目的レベル（要約 ・ ユーザー目的 ・ サブ機能）の当てはめを含めて。
C. 「ユースケースの集まりが業務領域を構成し、業務領域の集まりがドメイン（プロダクト）を構成する」という読み方は、原典の記述と両立するか。
D. 足りないもの（原典が必ずやるのに、見立てに無い作業や概念）。
