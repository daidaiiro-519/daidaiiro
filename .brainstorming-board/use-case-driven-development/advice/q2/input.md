# 相談の材料：原典の概念の置き場所と、要求と設計のつなぎ

## 前提（決着済み。ボード use-case-driven-development の論点1）
- 手法は「要求の側」と「設計の側」で構成する。要求の側：ドメイン（作りたいプロダクト。ビジョン記述 ・ 利害関係者と利益 ・ スコープの内外）→ アクター-目的リスト → ユースケース（要約 → ユーザー目的 → サブ機能。スコープ欄はプロダクト、レベル欄は別）→ ほかの要求（用語集 ・ ビジネスルール ・ 品質の要求。ユースケースの外に書いて結ぶ）。設計の側：業務領域（プロダクトが対象とするユースケースを、同じアクター ・ 外部システム ・ 密接なデータで束ねる。カテゴリーは競合との差別化）→ 実装の選択（実装方法 ・ 技術方式 ・ テスト方針）→ 区切られた文脈（業務領域と一対一に限らない）→ 集約など（ドメインモデルを選んだ業務領域だけ）。
- 要求の側のユースケースは、プロダクトの内部に触れない（ブラックボックス）。つなぎは設計の側が持ち、「この設計は、これらの振る舞い要求を満たす」として、どのユースケースを満たすかを指す。
- 手法の構成は利用者の意図で決まる。概念の意味は2冊に忠実にする。

## いまの宣言の問題
いまの宣言（別のボードで決めたもの）は、ユースケースの手順から集約のコマンドを直接指している：手順の invokes（呼ぶコマンド）、拡張の handles（扱うコマンドの業務ルールの拒否）、事前条件の ensures（防ぐ拒否）、成功時保証の established_by（成り立たせる状態の変更）。これは要求のユースケースが内部に触れる形である。道具は、これらの対応から「コマンドの拒否を、どの拡張も扱っていない」などのずれを検知している。

## オーケストレーターの見立て（検証してほしい）
1. つなぎは設計の側の「サービス層」（『ドメイン駆動設計をはじめよう』8章。アプリケーション層 ＝ ユースケース層）に持たせる。サービス層の操作1つが、満たすユースケース（ID）を指し、呼ぶ集約のコマンドと、ユースケースの各拡張がどのコマンドの業務ルールの拒否で起きるかを持つ。業務ロジックをトランザクションスクリプトで実装する業務領域では、トランザクションスクリプトの操作がこれを持つ（サービス層を置かない）。
2. ユースケースの側には、内部を指す欄を置かない。ずれの検知（拒否を扱う拡張が無い、など）は、設計の側の対応から道具が計算する。
3. 比較した案：(a) Cockburn のホワイトボックスのユースケースを設計の文書として書き、そこに内部を書く。(b) 集約のコマンドの側に、満たすユースケースを書く。(c) いまのまま、ユースケースから指す。
4. 概念の置き場所（意味を変えずに置く）：
   - 『ユースケース実践ガイド』：ビジョン記述 ・ In/Out リスト（ドメイン）／ 利害関係者と利益（ドメインの全体の一覧と、ユースケースごと）／ 設計スコープ（スコープ欄はプロダクト。企業スコープはビジネスユースケースだけ）／ アクター-目的リスト ・ 主アクター ・ 支援アクター ／ 目的レベル（レベル欄）／ 事前条件 ・ トリガー ・ 最低保証 ・ 成功時保証 ・ 主成功シナリオ ・ 拡張 ・ 技術およびデータのバリエーション ・ サブユースケース（ユースケースの中）／ 精度の段階（進め方）／ 用語集 ・ ビジネスルール ・ 品質の要求（要求アウトラインのほかの章）。
   - 『ドメイン駆動設計をはじめよう』：事業領域（使わない。プロダクトを取り巻く状況はビジネスユースケースで示す）／ 業務領域とカテゴリー ・ 業務エキスパート ／ 同じ言葉（区切られた文脈ごと。要求の側の用語集と結ぶ）／ 区切られた文脈 ・ 文脈の地図と連係の方法 ／ 実装方法（トランザクションスクリプト ・ アクティブレコード ・ ドメインモデル ・ イベント履歴式ドメインモデル）・ 技術方式（レイヤードアーキテクチャ ・ ポートとアダプター ・ CQRS）・ テスト方針 ／ サービス層 ／ 集約 ・ 値オブジェクト ・ 業務サービス ・ 業務イベント ／ サーガ ・ プロセスマネージャー（文脈をまたぐ流れ）／ イベントストーミング（任意の手法）。
