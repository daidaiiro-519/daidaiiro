結論

条件付きで採る

つなぎを設計の側に置き、設計の側から満たすユースケースを指す見立て1〜2は、原典の概念の意味を変えていないので条件付きで採る ── 条件は、設計の要素とユースケースを一対一に固定しないこと、事前条件に対応する拒否を拡張の欠けとして数えないこと、拡張条件をコマンドの名前ではなく検出された状況として書き続けることの3つである。

判断基準は、機能要求のユースケースでは対象システムをブラックボックスとして内部に触れないことと、ユースケースを次のレベルの設計が満たす振る舞い要求として扱い「この設計は、これらの振る舞い要求を満たす」と対応付けることを求めており、見立て1〜2はこの向きに合う。一方で、ユースケースを1つずつクラスやコンポーネントに対応づけることはアンチパターンであり、事前条件はユースケースの中で再確認しないものなので、この2点を守らない対応は原典の意味から外れる。

見立て1：設計の側の操作（サービス層の操作、またはトランザクションスクリプトの操作）が、満たすユースケースの ID を指し、呼ぶコマンドと、各拡張がどのコマンドの拒否で起きるかを持つ。ユースケースの側には内部を指す欄を置かない要求のユースケースはブラックボックスのまま残り、設計が変わっても要求を書き直さずに済む。対応の向きが「この設計は、これらの振る舞い要求を満たす」と一致する。ずれの検知は設計の側の対応から計算でき、要求の側の文書は検知のために内部の名前を持たない。ただし、操作とユースケースを一対一に固定すると、ユースケースをそのままクラスやコンポーネントに対応づけるアンチパターンに近づく。サービス層とトランザクションスクリプトを置き場所にすることの当否は判断基準の範囲外である採る

判断の道筋

  1. A-1. 要求のユースケースに内部を指す欄を置かない（見立て2）は、原典の意味を変えていないか

    変えていない。判断基準は、機能要求として書くときは対象システムをブラックボックスとして内部に触れないこと、これから作るシステムの要求では内部に触れないことを規則としている。invokes ・ handles ・ ensures ・ established_by を要求の側から外すことは、この規則に沿う。

  2. A-2. つなぎを設計の側に置き、設計からユースケースを指す（見立て1の向き）は、原典の意味を変えていないか

    変えていない。判断基準は、各レベルのユースケースを次のレベルの設計が満たす振る舞い要求として扱い、「この設計は、これらの振る舞い要求を満たす」という形で両者を対応付けるとする。要求の側が設計を知らず、設計の側が要求を指す向きは、この対応付けと一致する。ただし判断基準は、ユースケースを1つずつそのままクラスやコンポーネントに対応づけることをアンチパターンとしているので、1つの操作が複数のユースケースを満たすことも、1つのユースケースが複数の操作で満たされることも許す形にする。

  3. A-3. 設計の側が「各拡張がどのコマンドの拒否で起きるか」を持つことは、拡張の意味を変えていないか

    対応の置き場所としては変えていない。ただし拡張条件は、システムが検出できる状況を、検出されたことを表す句で書くものであり、別の道筋での成功 ・ 主アクターの活動の停止 ・ 支援アクターからの応答が無い ・ 性能上の問題など、コマンドの拒否から起きない条件も含む。したがって、道具が計算するずれは「拒否を扱う拡張が無い」の向きだけでなく「どの設計の要素にも対応しない拡張がある」の向きも数え、拒否に対応しない拡張を誤りとして扱わないこと。拡張条件の文はコマンドの名前ではなく、検出された状況で書き続ける。

  4. A-4. 事前条件 ・ 成功時保証と、コマンドの拒否 ・ 状態の変更の対応（いまの ensures ・ established_by）を設計の側に移したとき、意味は変わらないか

    事前条件は、システムが真であると保証している事柄で、ユースケースの中で再確認しないものである。コマンドの拒否が事前条件を守るためのものなら、それはユースケースの拡張ではない。道具がこの拒否を「扱う拡張が無い」と数えると、書き手は事前条件をユースケースの中で再確認する拡張を足すことになり、判断基準のアンチパターンに当たる。設計の側の対応で、拒否ごとに「拡張を起こす」か「事前条件を守る」かを区別し、後者を拡張の欠けに数えない。成功時保証は、ログや記録のような主アクター以外の利害関係者の利益も含むので、状態の変更との対応は、保証の一部にしか付かないことがある。対応が付かない保証を誤りとして数えない。

  5. A-5. サービス層を置き場所にしてよいか、トランザクションスクリプトの業務領域ではその操作が持つ、という扱いは正しいか

    判断基準の範囲外である。判断基準が言えるのは、設計の側の要素が「満たすユースケース」を指すこと、その単位はユーザー目的のユースケース（完結したトランザクション）に近いほうがよいこと（サブ機能は複数のクラスにまたがる）までである。サービス層の操作もトランザクションスクリプトの操作も、ユーザー目的のトランザクションを1つの操作として持つなら、この条件に合う（推測）。概念の当てはめは ddd-advisor に差し戻す。

  6. B. 案 a ・ b ・ c と比べて、見立て1は原典に照らしてどうか

    見立て1が最も原典に沿う。案 c はブラックボックスの規則に反する。案 a は、判断基準がホワイトボックスの用途を大規模システムの設計の記述とビジネスプロセスに挙げ、1つのシステムの中のサブシステムのスコープでは「書かない」と判定しているので、1つのプロダクトの中の集約の協力に使うと、同じ振る舞いの保守が二重になる。案 b は向きは前提に合うが、対応の単位がコマンドになり、ユースケースをクラスに直接対応づけるアンチパターンに近い。

  7. C-1. 見立て4で、意味を変えている置き場所はどれか

    3つある。①「企業スコープはビジネスユースケースだけ」── 判断基準は、企業スコープだからビジネスユースケースとは限らず、企業スコープで書いたシステムユースケースもある、とする。プロジェクトの決め事として企業スコープをビジネスユースケースに限るのはよいが、概念の定義として書かない。②「サブユースケース（ユースケースの中）」── サブユースケースはステップから呼び出される別のユースケースであり、ユースケースの中に在るのは呼び出し（下線を引いた名前）である。置き場所は「ユースケースの集合の中で、ステップから呼ばれる」と書く。③「ビジネスルール（ユースケースの外に書いて結ぶ）」── 判断基準は、複雑なビジネスルールを外の項目に置いてリンクする一方、利害関係者の代わりにシステムが実施するビジネスルールを妥当性確認のステップや拡張として書くことも求める。すべてを外に出すと、妥当性確認のステップが抜ける。

  8. C-2. 見立て4で、足りない概念はどれか

    ①データ要求の精度（情報の別名 ・ フィールド一覧 ・ フィールド詳細およびチェック内容）── ステップには別名だけを書き、残りはユースケースの外に書いてリンクする。要求アウトラインのほかの章として置く。②設計スコープの図 ── 判断基準は In/Out リスト ・ アクター-目的リスト ・ 設計スコープの図 ・ ビジョン記述の4つをスコープを定める成果物とする。見立て4にはスコープ欄だけがある。③要求アウトラインの残りの章（使われる技術 ・ 手動のサポート）と、ユースケースの関連情報（優先度 ・ 発生頻度 ・ 未決定事項など）。④ユースケースの書式（完全形式か略式か、必須の欄）をプロジェクトの標準として決めること。⑤ビジネスユースケースそのものの置き場所 ── 前提で「プロダクトを取り巻く状況はビジネスユースケースで示す」としているが、見立て4の要求の側の並びに、ビジネスユースケースとシステムユースケースの区別（スコープ欄とレベル欄で示す）が書かれていない。

  9. C-3. 見立て4で、置き場所を誤っている概念はあるか

    利害関係者と利益を「ドメインの全体の一覧と、ユースケースごと」に置くのは、ユースケースごとの一覧が在る限り判断基準に沿う。判断基準は、システム全体で1つの一覧を作って済ませないことを求めているので、全体の一覧は目標とスコープの章の材料にとどめ、ユースケースの欄を省かない。技術およびデータのバリエーションは要求の側のユースケースの欄に置くのが正しく、設計の側の技術方式と混ぜない。精度の段階を「進め方」に置くのは正しい。そのほかの置き場所（ビジョン記述 ・ In/Out リスト ・ アクター-目的リスト ・ 目的レベル ・ 事前条件 ・ トリガー ・ 保証 ・ 主成功シナリオ ・ 拡張 ・ 用語集）は判断基準と一致する。『ドメイン駆動設計をはじめよう』の側の置き場所は判断基準の範囲外である。

  10. D. 要求の側の用語集と、設計の側の同じ言葉（区切られた文脈ごと）を、どう結ぶと原典に沿うか

    判断基準が言えるのは、用語集が要求アウトラインの独立した章でユースケースの外に書くこと、ユースケースのステップは情報の別名を使いデータの詳細はリンクで結ぶことまでである。同じ言葉を区切られた文脈ごとに持つことは判断基準の範囲外である。そのうえで、つなぎの向きを見立て1と同じにし、設計の側の同じ言葉の各語が、対応する用語集の語を指す形にするのが、要求の側を設計から独立に保つという判断基準に最も近い（推測）。用語集の1つの語に、文脈ごとに別の語や別の意味が対応してよいかは ddd-advisor に差し戻す。

注意

アンチパターンリスク代替案
要求のユースケースに内部の名前を残す（案 c のまま進める）内部を推測して書いた要求は、読みにくく、設計が進むたびに書き直しになる。機能要求のブラックボックスの規則と、設計スコープの合否基準に反するinvokes ・ handles ・ ensures ・ established_by をユースケースの欄から外し、同じ対応を設計の側の操作に移す
設計の操作とユースケースを一対一に固定する要求の機能分解をそのまま反映しただけの設計になる。サブ機能のユースケースは、たいてい複数のクラスにまたがる部分的なメカニズムである操作が「満たすユースケース」を複数持てる形にし、対応の単位はユーザー目的のユースケースを基本にする。サブ機能のユースケースは、呼び出し側のユーザー目的のユースケースを通して満たされる形でもよい（推測）
事前条件を守る拒否を、扱う拡張が無いずれとして数える事前条件に書いた事柄をユースケースの中で再確認する拡張が増え、事前条件を書いた目的を果たせなくなる設計の側の対応で、拒否ごとに「拡張を起こす」か「事前条件を守る」かを持たせ、後者は拡張の欠けに数えない
（推測）拡張をコマンドの拒否の一覧として書く別の道筋での成功 ・ 主アクターの活動の停止 ・ 支援アクターの無応答 ・ 性能上の問題のような、拒否から起きない拡張条件が抜け、拡張条件の文が設計の名前に引きずられて内部に触れる拡張は判断基準のブレーンストーミングの項目でステップごとに洗い出し、検出された状況を表す句で書く。拒否との対応は設計の側だけに記録する
ビジネスルールをすべてユースケースの外へ出す利害関係者の代わりにシステムが実施する妥当性確認のステップと、それに対応する拡張がユースケースから抜ける妥当性確認のステップと拡張はユースケースに書き、シナリオの形に収まらない複雑なビジネスルールだけを外の項目に置いてリンクする

差し戻し

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
ddd-advisor ・ サービス層（アプリケーション層）をつなぎの置き場所にすることと、トランザクションスクリプトの業務領域ではその操作が持つという扱いサービス層 ・ トランザクションスクリプト ・ 集約 ・ コマンドは『ドメイン駆動設計をはじめよう』の概念であり、この判断基準は持たない。この回答が言えるのは、設計の側の要素がユーザー目的のトランザクションの単位で満たすユースケースを指せば判断基準に合う、というところまでである
ddd-advisor ・ 事業領域を使わず、プロダクトを取り巻く状況をビジネスユースケースで示すことビジネスユースケースで状況を示すことは判断基準に合うが、それが事業領域の代わりになるかは事業領域の意味に依存し、判断基準の範囲外である
ddd-advisor ・ 同じ言葉（区切られた文脈ごと）と用語集の対応の向きと多重度用語集を要求アウトラインの章としてユースケースの外に置くことまでは判断基準にあるが、1つの語が文脈ごとに別の意味を持つことの扱いは範囲外である

次にすること

  • ユースケースの宣言から invokes ・ handles ・ ensures ・ established_by を外す差分を、acdr で起こす
  • 設計の側の操作に、満たすユースケース ・ 呼ぶコマンド ・ 拒否ごとの「拡張を起こす／事前条件を守る」の区別を持たせる形を決める
  • ずれの検知を、拒否から拡張への向きと、拡張から設計への向きの両方で計算するように直す
  • 見立て4の要求の側に、データ要求の精度 ・ 設計スコープの図 ・ 要求アウトラインの残りの章 ・ ビジネスユースケースの置き場所を書き足す
  • 見立て4の「企業スコープはビジネスユースケースだけ」を、概念の定義ではなくプロジェクトの決め事として書き直す
  • サービス層 ・ トランザクションスクリプト ・ 同じ言葉の当てはめを ddd-advisor に問い合わせる

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
ユースケースの JSON を組み直すときに、invokes ・ handles ・ ensures ・ established_by や、集約 ・ コマンドの識別子をユースケースの欄に残す要求の側のユースケースのファイルを、この4つのキーと、設計の側で定義したコマンドの識別子の一覧で検索し、検出が0件であることを確認する
ずれの検知を移すときに、拒否から拡張への向きだけを計算し、事前条件を守る拒否も「扱う拡張が無い」と数える検知の試験に、事前条件を守る拒否だけを持つ操作の例を入れ、検出が0件になることを確かめる。あわせて、どの拒否にも対応しない拡張（例：支援アクターの無応答）を持つユースケースが誤りとして検出されないことを確かめる
設計の操作が指すユースケース ID を、存在しない ID や、要約レベルのユースケースに付ける操作が指す ID がすべて要求の側に存在し、レベル欄がユーザー目的またはサブ機能であることを、道具の検査に足す
