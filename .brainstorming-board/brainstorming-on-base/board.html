Q0

新しい brainstorming が完成したと言える条件を、何で判定するか

性質ごとに正しい場合と壊した場合を組にした18件の確かめがすべて合格したら完成とし、合否は残ったファイル ・ 画面 ・ 回答で決める。
  • 18件は、qa-advisor が出した15件に、meta-thinking-advisor の2件とチャットの1件を足したものである
  • 1件ごとに、合格する例と不合格になる例を1つ以上置く。何も検査しない実装が通らないようにするためである
  • 期待値を前もって計算できるもの（スキーマ ・ advance ・ inspect ・ 回答の形）は単体テストで見る
  • 本物の入出力が必要なもの（serve の書き込み ・ 入口からエンジンへの受け渡し）は作業用フォルダの試験と cargo xtask verify で見る
  • 人の操作と AI ツールでの実行は、受け入れとして手で数件だけ行い、合否は残ったファイルで決める
  • AI ツールでの受け入れは CI に入れない。同じ入力でも結果が変わり、落ちたときに欠陥か揺らぎかを決められないためである
  • 完成までを1つの目的として扱い、段に分けない

Q1

ボードの中身（concrete スキーマ）を、どの単位のインスタンスに分け、完成イメージの6種類をどんな形で持つか

1枚のボードを1つのインスタンスにして論点をその中に持ち、回答と回の記録は別のインスタンスとして追記だけで持ち、完成イメージは6種類の形をスキーマで決める。
  • ボードの本体は .brainstorming/<ボード>.json に置き、回の記録 ・ 回答 ・ 図は .brainstorming/<ボード>/ に置く。基盤の render を .brainstorming/ に1回当てると、全部のボードとダッシュボードが描ける
  • ボードは、題 ・ 状態 ・ 優先の印 ・ ほかのボードへのつながりを持つ。サイドバーとダッシュボードは、この3つから作る
  • ボードの状態は、いま答える ・ 進行中 ・ 保留 ・ 決着の4つである
  • 論点は、問い ・ 答え（1文と詳しい決まり）・ 完成イメージ ・ 根拠 ・ 採らなかった案と、描画しない書き手の検証を持つ
  • 回答は回の番号と論点の id を持つ別のインスタンスで、serve が書く。serve はボードを書かない
  • 回の記録 rounds/<n> は、advance が回を進めたときの写しで、書き換えない
  • この回で変わったところは、理由と一緒にボードの中に持ち、advance だけが書き換える
  • 図は SVG、画面は1枚の HTML を持つ
  • コードは言語 ・ 本文 ・ 強調する行を持つ
  • 差分はファイルの場所と変更前 ・ 変更後を持ち、統合か並べるかを選べる
  • フォルダ構成は、行ごとに場所 ・ 説明 ・ 印（足す ・ 消す ・ 変える）を持つ
  • 実行例は、コマンド ・ 出力 ・ 終了コードを持つ
  • 表は完成イメージに入れない。変化の要約は差分か図で見せる
  • チャットの記録は、ボードのフォルダの外に serve だけが書く（論点4）

Q3

brainstorming の Skill を、どのファイルで作り、どのコマンドで使い、データをどこに置くか

brainstorming は src/brainstorming/ の Rust で作り、advance ・ inspect ・ serve を自分の能力に持ち、データを .brainstorming/ に置く。
  • src/brainstorming/ は、skills-creator と同じく CODING.md ・ core ・ adapters ・ xtask の形にする
  • SKILL.md は scripts/bin/brainstorming だけを呼ぶ。言語に依存するコマンドを書かない
  • create ・ get ・ update ・ check などの基盤の操作は、scripts/bin/schema-driven へそのまま渡し、終了コードを変えずに返す
  • advance は回を進め、前の回と比べて変わったところを理由と一緒に書き、回の記録を残す
  • inspect は、1文の長さ ・ 前提にした論点の出どころ ・ 下流の行き先を検査する
  • serve は 127.0.0.1 で画面を配り、回答を受けてインスタンスとして書き、AI のチャットを中継する
  • ボードの置き場所は引数かボードの名前から決め、作業フォルダからは決めない
  • 3つの OS 向けに、証明付きで公開する（skills-creator と同じワークフローの形）

  • 会話の続きは、各 CLI のセッションの再開（Claude は --session-id と --resume、Codex は exec resume、Kiro は --resume-id）を使う
  • ボードの中身を写した context.json は作らない。AI がボードを直した時点で古くなるためである
  • 毎回の依頼の頭には、ボードのフォルダ ・ 回の番号 ・ 論点の id だけを付け、中身は AI が Skill のコマンドで読む

  • 子のプロセスの作業フォルダはリポジトリの根にし、標準入力から依頼を渡し、シェルを通さずに起動する
  • AI に許すのは Skill のコマンドの実行とボードのフォルダの書き換えだけで、権限を外す旗は使わない
  • serve は起動の前にボードのフォルダを写し、終わったら check と、ボードの外の変更の検査を自分で走らせる
  • 範囲の外の変更があれば差分を見せ、写しへ戻すかを利用者が選ぶ。黙って戻さない
  • 止めるときは子孫のプロセスまで止める（Linux ・ WSL はプロセスグループ、Windows はジョブオブジェクト）
  • 時間切れは、全体の時間と、出来事が来ない時間の2つで決める
  • チャットの記録（セッションの ID とやりとり）は、ボードのフォルダの外に serve だけが書く
  • 再開できないとき（別のマシン ・ 期限切れ）は新しいセッションで始め、チャットの記録とボードを読ませる
  • serve は 127.0.0.1 だけで待ち受け、起動ごとの合言葉を最初の1回で cookie へ移し、Host と Origin を検査する
  • 出来事の名前は CLI ごとに違うので、serve が共通の形（文字 ・ 読んだ ・ 直した ・ 検査 ・ 終わり ・ 失敗）に直す
