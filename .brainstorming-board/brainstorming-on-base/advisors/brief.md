# 相談の材料：ブレインストーミングの Skill を、新しい形の基盤の上で作り直す

## 背景
- 基盤 schema-driven（0.1.1 公開済み）は、abstract スキーマとエンジン（共通ツール：create ・ get ・ update ・ delete ・ prompt ・ check ・ check-schemas ・ approve ・ render）を持つ。3つの層：①abstract（基盤）②concrete スキーマ（Skill が持つ）③インスタンス。render は、Skill が持つページテンプレートと部品のカタログ（assets/catalog/：catalog.schema.json ・ parts.html ・ design-system.json ・ catalog.css ・ catalog.js）でページを作る。基盤はカタログの中身を持たず、形とコントラストの下限（文字 4.5:1、部品の境界 3:1）を検査する。
- skills-creator（0.1.0 公開済み）は、新しい Skill の雛形と照合した基盤のエンジンを置く scaffold、エンジンを入れ替える engine、9項目の check を持つ。作られる Skill はソースを scripts/ に持ち、入口は scripts/<名前>（拡張子なし）と scripts/<名前>.cmd、SKILL.md は入口だけを呼ぶ。私たちがソースを管理する Skill（基盤と skills-creator）は src/<名前>/ に Rust で置き、実行ファイルを scripts/bin/ に置き、3つの OS 向けに証明付きで公開する。
- ブレストボードは、決めることがある問いに論点を立て、AI が案を出して反証し、残った1つを答えとして出し、利用者は承認 ・ 差し戻し ・ 書き足しだけをする対話の Skill である。根幹の判断はすべてこれを通す。いまの Skill（brainstorming-board）は古い形（tool/ と bin/、自前の描画とトークン）で、.brainstorming-board/ に40枚ほどのボードがある。
- 利用者の決定（2026-10-16）：
  - 名前を brainstorming に変える。新しいボードは新しい形だけで作り、新しいフォルダ（.brainstorming/）に置く。古いボードは移さず、過去の記録として残す。古いボードの中身（決まったこと）は材料として使う。
  - 共有のデザインシステムの Skill は作らない。見た目は ux-advisor が設計相談で完成イメージとしてデザインシステム（スタイルタイル ・ Design Tokens 形式のトークン ・ パターンの一覧）を出し、各 Skill がそれを持つ。
  - 完成イメージは6種類：図（SVG）・ 画面（触れる HTML）・ コード（言語 ・ 行番号 ・ 色付け）・ 差分（Git の差分の形、並べる表示も可）・ フォルダ構成（ツリーと説明の列、足す ・ 消す ・ 変えるの印）・ 実行例（コマンド ・ 出力 ・ 終了コード）。在る種類だけをタブにする。表は入れない（変化の要約は差分か図で見せる）。いままで「コード」に、フォルダ構成や実行例をべた書きしていて見にくかった。
- 古いボードで決めた中身（材料。今の決定と食い違う所はそのまま採らない）：
  - 判断の目的：AI が作ったもののうち自分の意図からずれた所だけを早く見つけて正す。承認する人の問いは「この答えを、このまま進めてよいか」の1つ。見る順は 現在地 → 問いと答えの1文 → この回で変わったところ → 完成イメージ → 置いた前提 → 確かめてほしい箇所 → 裏づけ → 回答。
  - 画面（触れる試作あり）：いま答える論点が最初から開いている。現在地は1行のチップ。問いと答えは1つの枠、答えは1文、詳しい決まりと裏づけは閉じる。この回で変わったところは1行の帯で、押すと移って光る。置いた前提は番号付き。確かめてほしい箇所は3件まで。裏づけは主張ごとに束ねる。知らない語に ⓘ。回答は「このまま進める」「差し戻す（どこが違うかが必須）」。
  - デザインシステム（スタイルタイルとトークンあり）：トークンは基礎と意味（ライト ・ ダーク）の2層、意味の層は19（面5 ・ 文字6 ・ 主役1 ・ 線4 ・ 状態3）。主役の色は青緑 #0d5c55（苔緑と見比べ）。書体は Zen Kaku Gothic New ・ Shippori Mincho ・ JetBrains Mono。状態は6つ。
  - 論点の形：問い ・ 答え（1文と下位の決定）・ 完成イメージ ・ 根拠（何を支えるか ・ もとにしたこと ・ 種別 ・ 出どころ）・ 採らなかった案（案と理由）。書き手の検証の記録（通過した案 ・ 覆しうる前提 ・ 扱わない範囲 ・ 経過）は同じ論点に持ち、描画しない。
  - 固有の能力：回を進める advance（前の回と比べて変わったところを書く）・ 本文を読む inspect（1文の長さ ・ 前提にした論点の出どころ ・ 下流の行き先）・ 回答を受ける serve（127.0.0.1 で配り、回答をインスタンスとして書く）。

## 決めたいこと
0. 新しい brainstorming が完成したと言える条件。
1. ボードの中身（concrete スキーマ）：論点の形、完成イメージの6種類の形、回と「この回で変わったところ」、回答の形、書き手の検証の記録。
2. 画面とデザインシステム：試作を土台にした画面、ux-advisor が出すデザインシステムの取り込み方、カタログの部品（完成イメージの6種類の部品を含む）、基盤のデザインシステムの契約（design-system@v1）とトークンの形（Design Tokens 形式）の合わせ方。
3. Skill の作り：入口が持つ能力（advance ・ inspect ・ serve と、基盤の操作の渡し方）、ソースの置き場所（私たちが src/ で Rust で管理するか、作られる Skill と同じく scripts/ にソースを持つか。ほかの14の Skill の扱いもこれに従う）、データの置き場所 .brainstorming/。

## いまの見解（反証してほしい）
- 0：新しい brainstorming で、このボード自身の続き（または次の agents creator のボード）を1枚作り、回を2回進めて「変わったところ」が出て、利用者が画面で承認 ・ 差し戻しを送り、その回答がインスタンスとして残り、Claude Code と Codex の両方で SKILL.md の手順どおりに動いたら完成とする。
- 1：古い board-on-schema-driven の論点の形を引き継ぎ、完成イメージを6種類にする。回は rounds/ にインスタンスとして残し、advance が前の回と比べる。
- 2：試作の画面とスタイルタイルを ux-advisor に渡して設計相談にし、返ったデザインシステムを brainstorming の assets/catalog/ に置く。トークンの形は基盤の design-system@v1 に合わせ、Design Tokens 形式からの変換が要るなら、基盤の契約を Design Tokens 形式に寄せるかを別に決める。
- 3：brainstorming は私たちがソースを管理する側（src/brainstorming/ に Rust、scripts/bin/brainstorming）。入口は基盤の操作を scripts/bin/schema-driven へ渡し、advance ・ inspect ・ serve は入口の中で行う。データは .brainstorming/<ボードの名前>/。ほかの14の Skill も、私たちが管理するものは同じ形にする。
