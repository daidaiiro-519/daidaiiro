Q1

abstract スキーマ ・ concrete スキーマ ・ エンティティのインスタンスのそれぞれについて、中身をだれが書き、基盤が何を出すか。concrete スキーマはどんな契約を守り、どんな責務を持つか

基盤は②（concrete スキーマ）の中身も③（エンティティ）の値も作らず、どちらにも同じ共通ツールで、枠 ・ 書き方の案内 ・ 契約の検査だけを出す。②は abstract の契約を守り、何を表し ・ 持ち ・ どう書かせ ・ どう見せるかを自分で決める。
  • ①abstract スキーマは基盤が持つ。②の契約そのものである
  • ②concrete スキーマは①のインスタンスで、中身は concrete の側（Skill を作る人）が書く
  • ③エンティティのインスタンスは②のインスタンスで、値は concrete の側（使う人 ・ AI）が書く
  • 基盤は、②にも③にも、同じ共通ツールで枠 ・ 書き方の案内（x-prompt）・ 契約の検査を出す。中身の意味は知らない
  • concrete の側は、中身（スキーマ ・ ページテンプレート ・ 固有のツール）を持つ。呼ぶ側は中身に依存せず、同じ操作で扱える
  • ②の契約と責務は、完成イメージの「コード」の一覧のとおりにする
  • インスタンスの $schema 欄を自分の名前の const で持つことを、abstract の決まりに足す。いまは skills-creator の雛形にしか無い
この答えの完成イメージ ── 図 ・ コード

3つの層と、だれが何を持つか。

concrete スキーマ（②）の契約 ── abstract が決め、②が守る

  $schema        JSON Schema の dialect を書く
  x-abstract     従う abstract の版を書く
  $id            <Skill>/<種類>@v<n>。一度使った名前を別の中身に使い回さない
  title          何のインスタンスかを名詞で書く
  description    何のインスタンスかと、書かないものを書く
  x-generates    インスタンスを作るスキーマだけが書く。書いたら $id と properties.kind の const を持つ
  各プロパティ   description と x-prompt（読み方と書き方の決まり）を持つ
  注釈           参照は x-ref、導出値は x-derive、見せ方は x-view。独自の注釈は x-annotations で申告する

②の責務 ── concrete の側にしか決められない

  何を表すか        title ・ description
  何を持つか        properties ・ required
  どう書かせるか    x-prompt
  何とつながるか    x-ref
  何から決まるか    x-derive
  どう見せるか      x-view とページテンプレート
  ほかに何ができるか  tools.json

Q2

concrete スキーマ（②）を、エンティティのインスタンス（③）と同じ「スキーマのインスタンス」として、同じ共通ツール ・ 同じ引数で、枠 ・ 案内 ・ 書き進め ・ 検査ができるようにするか

する。エンジンに、x-abstract を持つ文書はその abstract を自分のスキーマとして扱う、という規則を1つ持たせる。②は create ・ prompt ・ update ・ get ・ delete ・ check-schemas で、③と同じように扱う。
  • create に abstract の名前を渡すと、②の枠を作る。$schema には dialect を、x-abstract には abstract の版を書く
  • prompt ・ update ・ get ・ delete は、②にも③と同じ引数で使える
  • ②の検査は check-schemas が持つ。③の検査の check と承認の approve と描画の render は③だけを扱い、②に対応するのは check-schemas と公開の記録 published.json である
  • ②のためだけの引数 ・ 手順 ・ ツールを足さない
  • skills-creator は、スキーマ ・ ページテンプレート ・ tools.json の雛形を持たない。②の枠は基盤の create から作る

いまのエンジン（2026-10-12）
  create --schema <abstract のファイル>   枠はできるが、$schema に「schema-driven/abstract@v1」が入る
  create --schema schema-driven/abstract@v1   断る（ファイルのパスしか受け付けない）
  update（②）                         断る（$schema が dialect なので「スキーマの名前でない」）

試作：規則1つ（$schema が dialect で x-abstract を持つ文書は、その abstract を自分のスキーマとして扱う）
  create --schema schema-driven/abstract@v1 --path demo/assets/term.schema.json
    → {"$schema": "https://json-schema.org/draft/2020-12/schema", "x-abstract": "schema-driven/abstract@v1"}
      未記入：/title ・ /description（x-prompt 付き）
  prompt --schema schema-driven/abstract@v1 --property /title   → 書き方の案内が返る
  update（title ・ description ・ $id ・ x-generates ・ properties.kind）  → 合格
  check-schemas --dir demo/assets                                   → 指摘 0件
  --skill demo create --schema demo/assets/term.schema.json --path terms/a.json
    → {"$schema": "demo/term@v1"}、未記入 /kind（②に書いた x-prompt 付き）
