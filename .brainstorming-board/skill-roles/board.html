Q1

このプロダクト（基盤と2つの creator）で、使う人に何を達成するか

使う人が、どの Skill ・ Agent にもスキーマとインスタンスを持たせ、concrete スキーマを基盤に手を入れずに育てられ、その振る舞いを abstract スキーマの版ごとに当てにできる状態にする。
  • どの Skill ・ Agent も、必ず concrete スキーマとインスタンスを持つ
  • abstract スキーマ（meta-schema ・ x-prompt の形 ・ 注釈）は、提供側が版を付けて厳格に保証する契約である
  • abstract スキーマの版ごとのツールの振る舞いは、提供側が保証する
  • concrete スキーマ（各スキーマ ・ x-prompt の中身 ・ デザイン）は、使う人が契約の範囲で定義して育てる
  • skills-creator と agents creator が、abstract スキーマを配る能力を持つ
  • 確かめ方1：使う人が concrete スキーマを変えても、エンジンを変えずに済むか
  • 確かめ方2：エンジンの版を上げても、版 N の契約に従う concrete スキーマに対する振る舞いが、版 N の定義どおりか

Q2

schema-driven ・ skills-creator ・ agents creator ・ 作られた Skill と Agent は、それぞれ何を持つか

abstract スキーマは schema-driven が版付きで1か所に持ち、2つの creator はその版を変えずに同梱し、作られた Skill ・ Agent は使う版を記録して concrete スキーマを持つ。
  • schema-driven：abstract スキーマ、エンジン、汎用の検査（契約への適合 ・ 注釈）、版を並べて出す方針、版を上げる手順、版付きの配布物
  • skills-creator ・ agents creator：schema-driven の配布物を、版を指定して変えずに同梱する
  • skills-creator ・ agents creator：Skill ・ Agent の形を作り、形に固有の検査だけを持つ。汎用の検査は schema-driven を呼ぶ
  • Skill の型は skills-creator が、Agent の型は agents creator が持ち、abstract スキーマと同じように版を付ける
  • 型が決めるのは必ず書く項目と項目の並びで、各項目の中身は使う人が書く
  • skills-creator が持つ Skill の型は1つで、作業型と助言型のような区別を持たない
  • 助言型は、Agent の型として agents creator が持つ
  • 使う人は項目を足せるが、型が決めた項目は消せない。型の検査は、必ず書く項目が全部あるかを見る
  • 作られた Skill ・ Agent：使う abstract スキーマの版を記録し、concrete スキーマ ・ インスタンス ・ 固有のツールを持つ
  • 版を上げるかどうかは、使う人が選ぶ
  • skills-creator と agents creator も、自分の concrete スキーマ（Skill の形 ・ Agent の形）を持つ基盤の上の Skill である
  • 確かめ方：変えたいことごとに、直すのが1か所だけで済むか（完成イメージの表）

変えたいことごとに、どこを直すか。直すのはどの行も1か所だけで、ほかは配り直すか、版を上げるかを選ぶだけになる。

Q3

新しい Skill ・ Agent に、abstract スキーマとエンジンをどう配り、固有のツールをどう足すか

基盤は署名付きの実行ファイルとして GitHub Release で配り、作った Skill ・ Agent は宣言と concrete スキーマだけを持ち、固有のツールは宣言か、宣言した別の実行ファイルで足す。
  • 配る経路の正本は GitHub Release とし、install スクリプトは入れる前に SHA-256 と署名を照合する
  • pnpm のパッケージは、使う人の多くが Node を持つと分かってから、Release と同じ配布物を包む2つ目の経路として足す
  • 基盤のソースを各 Skill へコピーするのをやめ、schema-driven を OS ごとの実行ファイル1つとして版付きで配る
  • 固有のツールはまず宣言で書き、宣言で書けないものだけを別の実行ファイルにする。別の実行ファイルの言語は問わない
  • 別の実行ファイルとの入出力の形 ・ 呼べるコマンドの範囲 ・ 制限時間 ・ 失敗の返し方は abstract スキーマの版に含め、基盤が呼ぶ前と後に検査する
  • 別の実行ファイルの中で何が正しいかは、提供側の保証に入れない
  • 使う abstract スキーマの版は concrete スキーマの $schema に、型の版は tool.json の contract に書き、同じ版を2か所に書かない
  • 複製は防がない。提供側が保証するのは、署名が合う基盤と、記録した版が基盤の版と合う組だけである
  • 署名の方式と制限時間の値は、作るときに原典と実測で決める

Q4

共通ツールと検査で、abstract スキーマと型の版ごとの振る舞いを、誰が何で保証するか

共通ツールは同梱した基盤が同じ名前で出し、振る舞いは abstract スキーマと型の版ごとの試験データで提供側が固定し、creator の check は型 ・ 宣言 ・ 一覧を見て、汎用の検査は基盤に任せる。
  • 共通ツールは create ・ get ・ update ・ delete ・ prompt ・ check ・ check-schemas ・ approve ・ render の9つで、基盤が CLI と MCP に同じ一覧で出す
  • 版3 の get は get に、validate は check-schemas と check に、view は render に置き換え、import は使う Skill だけが固有のツールとして宣言する
  • 共通ツールの振る舞いは、abstract スキーマの版ごとの試験データ（入力 ・ 期待する出力 ・ 比べる欄）で固定し、公開した版の試験データは書き換えずに足すだけにする
  • エンジンの新しい版は、扱う全部の版の試験データを 3 OS で実行し、全部合格してから公開する
  • 別の実行ファイルの境界は、違反を1つずつ返す見本の実行ファイルを試験データに入れ、基盤が拒否することで固定する
  • skills-creator の check は、型の必ず書く項目と並び ・ tool.json の欄と型の版 ・ 宣言した別の実行ファイルの SHA-256 ・ 宣言したツールが一覧に出るかを見る
  • $schema の版を扱えるかと、concrete スキーマとインスタンスの検査は基盤だけが判定し、creator の check はその結果を返す
  • 型の版ごとにも試験データ（合格する例と、必ず書く項目を消して不合格になる例）を creator が持つ
  • 使う人が足した項目と固有のツールの振る舞いは使う人が試験を持ち、基盤の check がその試験データを実行する
  • ソースを読む検査は check から外し、提供側のソースの静的解析は提供側の CI で行う
  • 移し終わるまでは tool.json の contract で版3 の check と新しい check を切り替え、最後の版3 の Skill を移したら版3 の check を外す

インスタンスは書いた時点のスキーマの版を「<Skill の名前>/<種類>@<版>」の名前で持ち、エンジンは --skill の Skill と自分が持つ abstract だけから引く。
  • 名前を持つのは、書いた時点の版で検査し続けるためである。置き場所だけなら、呼ぶ側の --skill と種類で決まる
  • concrete スキーマの根の $id に「<Skill の名前>/<種類>@<版>」を書き、インスタンスの $schema に同じ名前を書く
  • スキーマの $schema には標準の 2020-12 の URI を書き、従う abstract の版は x-abstract に書く
  • abstract の名前は schema-driven/abstract@v1、宣言の形は schema-driven/tools@v1 にし、無効な urn:schema-driven を置き換える
  • エンジンは、--skill の Skill の references にある *.schema.json の $id と、自分が持つ abstract だけから名前を引く
  • ほかの Skill の名前が来たら、どの Skill のスキーマかを返して止める。その Skill を --skill に渡して検査し直す
  • 同じ名前のスキーマが2つあれば、エンジンが登録の前に数えてエラーにする
  • 公開した版のスキーマは消さず書き換えず、新しい版は新しい名前（@v2）で足す

  • エンジンは公開した abstract の版をすべて持ち続け、知らない版にはエンジンが古いと返して止める
