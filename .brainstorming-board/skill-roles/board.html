Q1

skills-creator と schema-driven の立ち位置を決め直して、何を達成するか

データとツールの決まりの正本を schema-driven の1つにし、skills-creator はそれを使って Skill を生み、検査する状態にする。
  • 決まりの正本：いまは skills-creator の契約の版3 と schema-driven の2つ。これを schema-driven の1つにする
  • 基盤の上へ移した Skill に skills-creator の check で検査して、検出が0件になる
  • 確かめ方：新しい型や言語の組を足すときに、直す Skill が skills-creator の1つで済むか

Q2

2つの Skill の責務を、どこで分けるか

skills-creator は Skill という単位の外側の形を持ち、データとツールの中身は schema-driven が持つ。
  • skills-creator：要件の確認 ・ 型（作業型 ・ 生成型 ・ 助言型）・ SKILL.md の雛形 ・ フォルダの構成
  • skills-creator：CLI と MCP の呼び方（tool.json ・ mcp.json）・ check と accept ・ 配布
  • schema-driven：スキーマの契約（meta-schema）・ インスタンスの作成 ・ 取得 ・ 更新 ・ 検査 ・ 描画 ・ 承認 ・ 転写
  • 具体の Skill：自分のスキーマ ・ Design とデザインシステム ・ 固有のツール（ExtraTools）
  • skills-creator はツールの中身を自分では持たず、Skill を生むときに schema-driven を転写する

Q3

scaffold は、新しい Skill のツールをどう生むか。いまの4層のリファレンス実装をどうするか

scaffold は schema-driven を転写し、具体の crate（Design と ExtraTools の雛形）と cli ・ mcp を置く。4層のリファレンス実装は、すべての Skill を移し終えたら消す。
  • Rust の Skill：schema-driven transcribe で tool/schema-driven/ を置き、具体の crate に Design と ExtraTools の雛形を置く
  • ほかの言語の Skill：いまと同じく枠だけを置き、schema-driven のツールの振る舞いを、契約のテストケースに合わせて移植する
  • 助言型の雛形は、ボード advisor-answer で回答の形が決まってから、schema-driven の上の形に作り直す
  • 4層のリファレンス実装（data_access ・ business_logic ・ service と refs.rs）は、移し終えるまで残す。新しく生む Skill には使わない

Q4

すべての Skill に求める共通ツール（get ・ validate ・ view ・ import）と check の2段目を、schema-driven の上の Skill に合わせてどう変えるか

共通ツールを schema-driven のツールの一覧に置き換えて契約の版4 とし、check は tool.json の contract が 4 の Skill に、転写の記録 ・ 基盤との差 ・ スキーマの契約を検査する。
  • get <kind> [id] → get（ファイルと JMESPath の式）。validate → check と check-schemas。view → render（ページテンプレートと具体の Design）
  • import は共通から外し、Markdown の原文を取り込む Skill（fact-check と助言型）だけが ExtraTools で持つ
  • 基盤にだけあるもの（create ・ update ・ delete ・ prompt ・ approve ・ transcribe ・ check-copy）も、共通ツールとして契約のテストケースで振る舞いを決める
  • 版4 の check の2段目：transcription.json がある ・ check-copy の差が0件 ・ references の具体のスキーマが check-schemas を通る。refs.rs と見た目の正本の複製は求めない
  • 版3 の Skill には、移し終えるまでいまの check を当てる。移した Skill は tool.json を 4 にする
