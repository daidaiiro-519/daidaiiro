# 反証：Semantic Schema Core の集約の切り方（案A ・ 案B）

役割は反証役である。どちらの案にも肩入れせず、壊れる場面を実物の断片で示す。判断基準は ddd-advisor の criteria（aggregate ・ entity ・ value-object ・ domain-model ・ domain-service ・ subdomain）で、引用は原文のままである。

## 1. 実物から分かったこと（brainstorming の描画の材料）

### 1.1 数

| 物 | 1つの文脈にいくつあるか | 実物 |
|---|---|---|
| ページテンプレート | kind ごとに1つ（いまは2つ） | `assets/pages/board.page.json` ・ `assets/pages/dashboard.page.json` |
| 部品のカタログ | 文脈に1つ。中身は4ファイルで1組、部品は35個 | `catalog.schema.json`（`$defs` 35個）・ `parts.html`（部品ごとに `<template>` 1つ）・ `catalog.css` ・ `catalog.js` |
| デザインシステム | 文脈に1つ。正本2つから作る派生物1つ | `light.tokens.json` ・ `dark.tokens.json` → `design-system.json` |
| Concrete | kind ごとに1つ | `board.schema.json` ・ `dashboard.schema.json` など |
| glossary | 文脈に1つ（決まっていること） | ― |

数の食い違いが要点になる。**ページテンプレートと Concrete は kind ごと、カタログ ・ デザインシステム ・ glossary は文脈ごと**である。

### 1.2 互いをどう参照するか

| 参照する側 → される側 | 何で参照するか | 誰が確かめるか |
|---|---|---|
| ページ → カタログ | 部品の名前（`"component": "board-head"`、board.page.json:53） | render が描画の前に断る（schema-driven SKILL.md:190「カタログに無い部品 ・ 入力の欠け … 1ページも書かずに」） |
| ページ → Concrete（instance の欄） | JMESPath 式（`"intro": "this.intro \|\| ''"` board.page.json:56、`"answer": "answer.text"` 同:106） | **誰も確かめない**。欄の名前が変わると `\|\| ''` で空になり、黙って描かれる |
| カタログ（catalog.css）→ デザインシステム | トークンの名前（`var(--color-surface-block)` catalog.css:123） | **誰も確かめない**。基盤が見るのは「カタログの CSS に色の値を直接書いていないこと」だけ（schema-driven SKILL.md:178） |
| デザインシステムの `contrast` → 自分のトークン | `"foreground": "color-text-warn", "background": "color-surface-notice"` | 基盤が明暗の両方で比を見る |
| カタログ（`$defs`）↔ parts.html | 部品の名前とプレースホルダー | 抽象の規則 `one-name-one-template` ・ `inputs-are-placeholders` |

版付きの id は、いまの実物では成り立っていない。`catalog.schema.json` は `"$id": "brainstorming/catalog@v1"` を持つが、**それを指すファイルは無い**。`design-system.json` とページテンプレートは `$id` を持たない。render は `--skill` のフォルダから「描画のたびにカタログを読む」（schema-driven SKILL.md:160）ので、参照は「いまフォルダにある1組」である。

### 1.3 いつ一緒に変わるか

| 変更 | 一緒に変えないと何が起きるか | 検出 |
|---|---|---|
| カタログから部品を外す（例：`basis-tag`） | それを呼ぶページがあると、render が**全ページの描画を止める** | 描画の時に検出（止まる側に倒れる） |
| ページに新しい部品を置く | カタログに先に足していないと、同じく全停止 | 同上 |
| デザインシステムのトークン名を変える（例：`color-surface-notice` → `color-surface-warn`） | catalog.css の `var(--color-surface-notice)` が未定義になり、背景が無いまま描かれる | **検出されない** |
| カタログに「文字色 × 背景色」の新しい組を足す（例：`.notice` に `color-text-source`） | その組が `contrast` に無いと、比の検査を通らない組が出荷される | **検出されない**（基盤は `contrast` に書いた組だけを見る） |
| tokens（light/dark）を直す | `design-system.json` を作り直さないと、正本と派生がずれる | 作り直しの手順しだい |
| Concrete の欄の名前を変える（例：`intro` → `purpose`） | ページの `this.intro` が空になる | **検出されない** |

まとめ：**カタログとデザインシステムは「名前の一致」と「コントラストの組」の2つの不変条件を共有し、片方だけ変えると黙って壊れる。ページとカタログは片方だけ変えると止まる（安全側）。ページと Concrete は片方だけ変えると黙って壊れる。**

## 2. 判断基準（原文）

| 項 | 原文 |
|---|---|
| aggregate・判定の問い | 「集約の業務ロジックが、その情報に強い一貫性を必要とするか」→「集約の内側に置く」／「結果的に整合していればよい情報か」→「境界の外側（例：別の集約）に置き、ID で参照する」 |
| aggregate・境界 | 「1つのトランザクションで変更する集約は1つにし、複数の集約の状態は集約ごとに別々にコミットする」 |
| aggregate・境界 | 「他の集約は、オブジェクトそのものではなく ID で参照する」 |
| aggregate・境界 | 「一貫性を保証する対象を、集約の業務ロジックが必要とするデータだけに限定し、集約をできるだけ小さく設計する」 |
| aggregate・アンチパターン | 「複数の集約への変更を、1つのトランザクションとしてコミットしようとする」→「トランザクションの境界、つまり集約の境界が誤っている兆候である」 |
| aggregate・アンチパターン | 「要求事項に出てくる名詞（…）をすべて集約として表現し」→「トランザクションの境界とずれ、業務ロジックもほぼ持たない、名前だけの「集約」になる」 |
| aggregate・アンチパターン | 「集約の境界の設計が不適切なことを、サーガで補う」→「データが強く整合していると想定できるのは集約の境界の内側だけであり、サーガの下ではデータは結果的に整合するだけである」 |
| entity | 「エンティティを単独で実装せず、集約の実装の一部にする」 |
| value-object | 「不変。値を変えるときは別のインスタンスを生成する」 |
| domain-service・アンチパターン | 「業務サービスを使って、複数の集約のインスタンスを1つのデータベーストランザクションで変更する」→「集約のインスタンス1つにトランザクション1つ、という原則に反する」 |
| domain-model・アンチパターン | 「顧客管理のように、補完的な業務領域をドメインモデルで実装する」→「無駄な努力になる」 |
| subdomain・補完 | 「高速開発を重視したフレームワークで、単純な業務ロジックを実装する」 |

## 3. 案A（集約5つ）への反証

| # | 壊れる場面 | 断片 | 当たる基準 |
|---|---|---|---|
| A-1 | **glossary を Concrete の一部にできない。** glossary は文脈に1つ、Concrete は kind ごとに1つである。brainstorming なら board ・ answer ・ round ・ dashboard ・ chat の5つの Concrete が1つの glossary を指す。どれか1つの Concrete の内側に置くと、残り4つは他の集約の内部へ直接手を入れる。全部に複製すると、同じ term が5か所で別々に変わる | `assets/board.schema.json` ・ `answer.schema.json` ・ `round.schema.json` ・ `dashboard.schema.json` ・ `chat.schema.json`（SKILL.md:137-141） | 「他の集約は、オブジェクトそのものではなく ID で参照する」 |
| A-2 | **変更の記録と instance を同じコミットにすると、2つの集約を1つのトランザクションで変える。** 変更の記録の対象は Concrete ・ instance ・ 判定の記録の3種なので、instance の内側にも置けない。別の集約のまま同じコミットに縛るのは、基準がいう境界の誤りの兆候そのものである | 決まっていること「変更の項目（対象は Concrete ・ instance ・ 判定の記録）」 | 「複数の集約への変更を、1つのトランザクションとしてコミットしようとする」 |
| A-3 | **A 自身の決定と矛盾する。** 「ずれは CI とレビューで後から検出する」と決めた時点で、ずれが存在しうる、つまり結果整合を認めている。同じコミットを不変条件にするなら「記録に無い」は検出の対象ではなく起きない状態になり、例外の判断の対象が消える | 決まっていること「記録に無い ・ 変更の無い記録などの変更の例外」 | 「結果的に整合していればよい情報か」→外側 |
| A-4 | **「描画の3つを集約にしない」の行き先が決まっていない。** 集約でないなら、どの集約の内側か、それともドメインモデルの外か。Concrete の内側に置くと、文脈に1つのカタログ ・ デザインシステムを kind ごとの Concrete が抱え、A-1 と同じ形で壊れる | §1.1 の数 | 「エンティティを単独で実装せず、集約の実装の一部にする」 |
| A-5 | 1.3 の「黙って壊れる」2本（トークン名 ・ Concrete の欄名）を、A はどこでも守らない | catalog.css:123、board.page.json:56 | ― |

**A を救う読み方**：描画の3つは「ドメインモデルの外の補完の部品で、render が門で確かめる」と明記すれば A-4 は閉じる。A-1 ・ A-2 は案の形を変えないと閉じない。

## 4. 案B（集約9つ）への反証

| # | 壊れる場面 | 断片 | 当たる基準 |
|---|---|---|---|
| B-1 | **カタログとデザインシステムを別の集約にすると、黙って壊れる窓ができる。** デザインシステムだけ `color-surface-notice` を改名して公開 → カタログは旧名の `var(--color-surface-notice)` のまま → 背景の無い画面が出る。版付き id で旧版を指していても、カタログの新版を出すときに新版のデザインシステムへ同時に移れなければ、同じ窓が開く。さらに `contrast` の組はカタログの CSS が「どの文字をどの背景に置くか」で決まるので、カタログの変更がデザインシステムの変更を要求する | catalog.css:6 `background: var(--color-surface-page)`、design-system.json の `contrast` | 「集約の業務ロジックが、その情報に強い一貫性を必要とするか」→内側 |
| B-2 | **版付き id で参照する、が実物に無い。** カタログの `$id` を指す者はおらず、デザインシステムとページは `$id` を持たない。render はフォルダの「いまの1組」を読む。旧版を残さない限り、ページが `catalog@v1` を指しても v1 は消えている。旧版を残すなら、保存と版の管理（一般の業務領域）の仕事が、描画の材料の数だけ増える | schema-driven SKILL.md:160「描画のたびにカタログを読む」 | 「他の集約は … ID で参照する」は、参照先が存在し続けることを前提にする |
| B-3 | **補完の業務領域の名詞を4つ集約にしている。** 描画は補完で、業務ロジックはプレースホルダーへの差し込みと名前の一致だけである。カタログの35部品の `properties` は `"description": "answer"` のように型を持たず、守る業務ルールがほぼ無い | catalog.schema.json:14-16 | 「要求事項に出てくる名詞 … をすべて集約として表現し」／「補完的な業務領域をドメインモデルで実装する」 |
| B-4 | **変更の記録の結果整合は、中核の「変更の確かめと例外の判断」の入力を揺らす。** instance を直したコミットと記録のコミットの間で CI が走ると、「記録に無い変更」を正しく検出したのか、まだ届いていないだけなのかを区別できない。区別する点（公開の単位）を決めないと、例外の判断が誤報を出す | 決まっていること「CI とレビューで後から検出」 | 「サーガの下ではデータは結果的に整合するだけである」 |
| B-5 | B でも、ページ → Concrete の JMESPath の結合は ID 参照ではなく、他の集約の内部構造（欄の名前）への直接の依存である。B の切り方はこれを扱わない | board.page.json:106 `"answer": "answer.text"` | 「他の集約は … ID で参照する」 |

**B が守れること**：glossary の独立は壊れない。term は「出した版を変えない」ので、版付きの term は不変の値として Concrete から指せる。新しい欄は「term を出す → Concrete を出す」の2回のコミットで足り、片方だけの状態でも壊れない（Concrete は旧版の term を指したまま有効）。壊れるのは term を版を上げずに書き換えたときだけで、それは決まりが禁じている。

## 5. 第3の切り方（案C）

| 集約 | 数（文脈ごと） | 境界の理由 |
|---|---|---|
| Semantic Abstract Schema | Core に版ごと | 版は不変。Concrete は id@版で指す |
| Semantic Concrete Schema | kind ごと | ― |
| glossary | 1 | B と同じ。term の版は不変の値 |
| instance | 1件ごと | ― |
| 判定の記録 | 1件ごと | 読んだ値を写して持つので、相手の後の変更に左右されない |
| 変更の記録 | 1件ごと | B と同じく結果整合。**ただし整合を求める点を「公開の単位（マージ）」と決め、例外の判断はその点でだけ行う** |
| **表示の組（カタログ ＋ デザインシステム）** | 1 | B-1 の2つの不変条件（トークン名の一致 ・ contrast の組）を内側で守る |
| ページテンプレート | kind ごと | 表示の組と Concrete を id で指す。部品の追加はカタログが先、削除はページが先、の順で2回のコミットに分けられる（片方だけでも render が止まる側に倒れる） |

C の条件：(1) 表示の組の内側の検査として「catalog.css の `var(--x)` がすべてトークンにある」を足す（いまは無い）。(2) ページの JMESPath が指す欄が Concrete にあるかを render の前に確かめる（いまは無い）。この2つが無いと、C も B と同じく黙って壊れる。

C の弱み：表示の組 ・ ページの2つも補完であり、B-3 の批判は半分残る。より引いた形は「描画の材料は集約にせず、補完のモジュールとして render の門で確かめる」（A-4 を閉じた A）で、この場合も上の (1)(2) の検査は要る。

## 6. 結論

| 案 | 結論 | 決め手の壊れる場面 |
|---|---|---|
| 案A | **採れない** | A-1：文脈に1つの glossary を kind ごとの Concrete の内側に置けない。A-2：変更の記録と instance の同時コミットは2集約を1トランザクションで変える |
| 案B | **条件付き** | B-1：カタログとデザインシステムを分けると、トークン名の改名で背景が消える画面が検出されずに出る。条件は (1) カタログとデザインシステムを1つの集約にまとめる（＝案C）か、分けるなら名前の一致と contrast の組をまたいで検査する、(2) 変更の記録の整合を求める点を公開の単位と定め、例外の判断をその点に限る、(3) 版付き id を使うなら旧版を残す（B-2） |
| 案C | **条件付き** | 表示の組の内側に `var(--x)` の検査、ページ → Concrete の欄の検査を足すこと。足さなければ B と同じく黙って壊れる |

どの案にも残る穴：**ページテンプレートと Concrete の結合（JMESPath の欄名）**は、どの切り方でも ID 参照にならない。集約の切り方ではなく、render の前の検査で閉じるしかない。
