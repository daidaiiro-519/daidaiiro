2　ドメインサービスとは

問い答え出どころ
定義「When a significant process or transformation in the domain is not a natural responsibility of an entity or value object, add an operation to the model as a standalone interface declared as a service.」Evans DDD Reference p.14 Services
何に属するか「State these assertions in the ubiquitous language of a specific bounded context.」── 区切られた文脈に属する。業務領域（subdomain）に属するとは書いていない同上
基盤では基盤の内側は1つの区切られた文脈（Q9 #11）。crate は、model.json が各ドメインサービスに付けた業務領域で置く。ドメインサービスは4つ（Resolver ・ Validator ・ Renderer ・ Session Selector）で、ほかは集約の操作 ・ ファクトリ ・ 値オブジェクトが持つ（ドメインサービスの分け直しの頁）premises/board-answers.json:293 ・ model.json domain_services

3　外の情報を使うドメインサービス

ドメインサービス外の情報の受け取り方前提
Semantic Schema Resolverapplication が文脈のリポジトリの契約 ・ glossary と、閉じた一覧にある公開された言葉の版を先に読んで渡す。Resolver は渡された中だけで解決し、無いものは断るQ4 #9「検証の途中で、$ref が指す外のスキーマを取りに行かない」

4　駆動される側のポート（13。application の ports/）

ポート最初のアダプター
契約を読む ・ 書く（Concrete の文書 ・ glossary ・ ビュー ・ デザインシステム。公開する部分を含む）文脈のリポジトリのファイル
インスタンスを読む ・ 書く文脈のリポジトリのファイル（正本。関係の索引は、遅いと測れてから、ファイルから作り直せる手元の DB を同じポートの後ろに置く）
判定の記録を読む ・ 書くrule の判定は文脈のリポジトリのファイル（最初のアダプターは1件1ファイル）。意図の判定は作業した人の手元の DB（確定しない）
変更の記録を読む ・ 書く作業した人の手元の DB（最初のアダプターは SQLite。セッションと同じファイル。確定しない）
セッションと手元のセッションの索引を読む ・ 書く作業した人の手元（最初のアダプターは SQLite 1ファイル。置き場所は起動の設定で渡し、Git のアダプターを使うときの既定はすべての worktree が共有する場所。確定しない。不変条件は一意の索引とトリガーで断り、接続の設定に依らない。登録は書き込みのトランザクションを先に取ってから読む）
変更のまとめを読む ・ 書く文脈のリポジトリのファイル（コミットごとに1件）
変更の仕組みとやりとりする（①前後：前の姿の参照と後の姿の参照から対象ごとの前後。無いと届かないを分ける ②単位の中身：前の姿 ・ 後の姿 ・ 出した者と時刻（出どころ付き）③確定する：対象のファイルの一覧と変更のまとめから単位の参照。変わったものが無いことを失敗と分ける）Git ・ スナップショット（前と後のディレクトリ）など。参照は基盤が解釈しない文字列
公開された言葉を取りに行く（ほかの文脈の公開する部分の版）ほかのリポジトリ ・ 配布の仕組み（$id の閉じた一覧で確かめる）
rule の判定を依頼する（AI）Claude Code ・ Codex などの CLI
描画したものを書き出すHTML ・ Markdown のファイル
外のツールを呼ぶ（Concrete が宣言した validator）Concrete の x- の定義に名前がある外のツール
AI ツールのセッションを問う（再開できるか ・ キャッシュの有効時間（不明もある）・ 最後に使った時刻 ・ 履歴の割合）Claude Code ・ Codex ・ Copilot ・ Gemini ・ Kiro などの CLI
設定を読む（利用者 ・ プロジェクト ・ 手元）ファイル

5　駆動する側の入口（12。inbound）

入口使う場面
意味を宣言する（create ・ patch ・ release。AI は semantic-create ・ semantic-write の procedure に従う。セッション ID と意図を一緒に受け取る）U1 ・ U2 ・ U3 ・ U23 ・ U24
インスタンスを書く（create ・ patch ・ import。AI は semantic-create ・ semantic-write ・ semantic-import の procedure に従う。消すコマンドは無く、不要なものは superseded にして残す。セッション ID と意図を一緒に受け取る）U5 ・ U6 ・ U7 ・ U11 ・ U17
検証する ・ 変更を見せる（validate。検査は2回：①入力が入力のスキーマに合うか（外れたら断り、状態に触れない）②適用した後の出力が形 ・ 機械の rule ・ AI の rule に合うか（外れても保存し violated で返す Q8）。AI の rule は needs で返し、semantic-judge の答えを validate がまとめる）U8 ・ U10 ・ U18 ・ U25
判定する（judge。人の判定だけ。本人が意図を承認したら、まとめを作ってコミットできる）U16
探して取り出す ・ 案内する（search ・ get。AI は semantic-search ・ semantic-read の procedure に従う）U1 ・ U5 ・ U6 ・ U12 ・ U24 ・ U26 ・ U28
描画する（render。Abstract のファイルは基盤が同梱した既定のビューで描く）U12 ・ U16
Abstract の版を出す ・ 移す（release ・ migrate。機械で直せない欄は semantic-migrate の procedure で AI が直し、patch で適用する）U3 ・ U4
経緯をたどる（history。対象ごと ・ 目的ごとは変更のまとめから。作業した本人の手元ではセッションごとに変更の記録から）U13
セッションを決める ・ 立てる ・ 閉じる（session。目的の参照 ・ 親 ・ 役割を受け取り、AI ツールの起動の前に、再開する ID か「新しく立てる」を返す。新しく立てたら、AI ツールが発行した ID を受け取って登録する）U27
変更を記録する（record。意図と目的の参照を受け取り、最後に確定した姿 → いまの前後から変更の記録を手元の DB に作る）U2 ・ U5 ・ U6 ・ U7
まとめを作る（コミットの前に、前回のコミットからの差し引きと例外を、手元の変更の記録から変更のまとめにする。記録と変更の前後を両方向で突き合わせる。AI は書かない）U25 ・ U13
セマンティックの手順を返す（semantic-search ・ semantic-read ・ semantic-create ・ semantic-write ・ semantic-judge ・ semantic-import ・ semantic-migrate。AI が行う操作ごとに procedure（手順 ・ 入力のスキーマ ・ 出力のスキーマ）を返す。処理はせず、AI を起動しない）U1 ・ U2 ・ U3 ・ U5 ・ U6 ・ U7 ・ U10 ・ U16 ・ U17 ・ U28

AI が行う操作は、入口のセマンティックのコマンドが procedure（手順 ・ 入力のスキーマ ・ 出力のスキーマ）を返し、AI が生成した入力を機械的なコマンドが適用する。消すコマンドは無い
