Semantic Read と Semantic Write

利用者「Semantic Read と Semantic Write というのはx-promptを読み、aiが読み書きを人間の都度の指示がなくてもループ的にできるようにしたもの」「手順とその操作における入力と出力をschemaの形式で成型するのがAIができたとしたら」。決まった内容は ACDR 0201（正本：model.json ・ ボード）。例の名前は架空

semantic-read と semantic-write は、AI が行う操作のセマンティックのコマンドで、procedure（手順 ・ 入力のスキーマ ・ 出力のスキーマ）を返す。AI は手順に従って入力（JSON Patch）だけを生成し、適用と検査は機械的なコマンド（get ・ patch）がする。検査は入力と出力の2回で、出力が外れても保存して violated を返す

1　対象

対象semantic-readsemantic-write
欄（いちばん細かい単位）その欄の x-prompt ・ 値 ・ 版その欄の write の rule ・ 使える op
インスタンス欄ごとの means と読み進め方欄ごとの write の rule（複数の欄を1つの Patch で書く）
スキーマ（Concrete ・ glossary ・ published）$ref を解いた形と欄ごとの meansx-prompt と拡張の書き方（Abstract に照らす）
ドキュメント（Markdown ・ ソース）読み方の案内だけ。本文は AI が読み、基盤は中身を解釈しない──（AI が直し、record で変更の記録を作る）
文脈（settings）──探す範囲 ・ validator の書き方

まだ無いものを作るときは semantic-create（雛形と書く順を返す）→ create。ほかのセマンティックのコマンドは semantic-search ・ semantic-judge ・ semantic-import ・ semantic-migrate（7つ）

2　事前状態 → 入力 → 事後状態

semantic-read：欄 owner を読む

状態を変えない。事後状態は事前状態と同じで、出力（値 ・ x-prompt ・ 版）だけが増える

事前状態
{
  "$schema": "urn:semantic-agent-schema:sample:record:v1",
  "id": "r-12",
  "subject": "AI の許可",
  "owner": "team-a"
}
procedure
{
  "手順": "read の means に従って読む",
  "入力のスキーマ": "procedure#/$defs/read-request（id ・ JSON Pointer）",
  "出力のスキーマ": "procedure#/$defs/read-result（値 ・ x-prompt ・ 版）"
}
AI が生成した入力
{
  "kind": "urn:semantic-agent-schema:sample:record:v1",
  "id": "r-12",
  "pointer": "/owner"
}
事後状態
{
  "$schema": "urn:semantic-agent-schema:sample:record:v1",
  "id": "r-12",
  "subject": "AI の許可",
  "owner": "team-a"
}
出力
{
  "値": "team-a",
  "x-prompt": {
    "read": {
      "means": "この記録の決定に責任を持つ人"
    },
    "write": [
      {
        "id": "owner-is-person",
        "rule": "人の名前を書く。チーム名は書かない",
        "by": "ai"
      }
    ]
  },
  "results": [
    {
      "rule": "owner-is-person",
      "value": "violated"
    }
  ],
  "版": 3
}

semantic-write → patch：owner を直す

test でいまの値を確かめてから replace する。版の食い違いは patch が断る。状態は violated → unverified（AI の rule は needs で返る）

事前状態
{
  "$schema": "urn:semantic-agent-schema:sample:record:v1",
  "id": "r-12",
  "subject": "AI の許可",
  "owner": "team-a",
  "状態": "violated"
}
procedure
{
  "手順": "write の rule に従って書く。test でいまの値を確かめてから replace",
  "入力のスキーマ": "JSON Patch（test ・ add ・ replace ・ remove。対象の欄だけ）",
  "出力のスキーマ": "record@1 と change"
}
AI が生成した入力
[
  {
    "op": "test",
    "path": "/owner",
    "value": "team-a"
  },
  {
    "op": "replace",
    "path": "/owner",
    "value": "yamada"
  }
]
事後状態
{
  "$schema": "urn:semantic-agent-schema:sample:record:v1",
  "id": "r-12",
  "subject": "AI の許可",
  "owner": "yamada",
  "状態": "unverified（owner-is-person の判定待ち）"
}
出力
{
  "applied": true,
  "stop": true,
  "needs": [
    {
      "rule": "owner-is-person",
      "why": "AI の判定を親が依頼する（semantic-judge）"
    }
  ]
}

semantic-write → patch：x-prompt の rule を直す（Concrete への書き込み）

Concrete は Abstract のインスタンスなので、同じ semantic-write で x-prompt の rule を足す ・ 変える ・ 取り除く。rule は添字ではなく test で id を確かめてから指す。この欄の前の AI の判定は効かなくなる（U2）

事前状態
{
  "$schema": "urn:semantic-agent-schema:base:abstract:v1",
  "$id": "urn:semantic-agent-schema:sample:record:v1",
  "owner の rule": "人の名前を書く。チーム名は書かない"
}
procedure
{
  "手順": "rule を id で指す。test で id を確かめる",
  "入力のスキーマ": "JSON Patch（x-prompt の欄だけ）",
  "出力のスキーマ": "Abstract に合う Concrete と change"
}
AI が生成した入力
[
  {
    "op": "test",
    "path": "/properties/owner/x-prompt/write/0/id",
    "value": "owner-is-person"
  },
  {
    "op": "replace",
    "path": "/properties/owner/x-prompt/write/0/rule",
    "value": "人の名前を書く。チーム名と役職名は書かない"
  }
]
事後状態
{
  "$schema": "urn:semantic-agent-schema:base:abstract:v1",
  "$id": "urn:semantic-agent-schema:sample:record:v1",
  "owner の rule": "人の名前を書く。チーム名と役職名は書かない"
}
出力
{
  "applied": true,
  "stop": true,
  "note": "r-12 の owner の AI の判定は効かなくなり、unverified に戻る"
}

3　検査

検査外れたもの扱い
① 入力（適用する前）op が1つでも当たらない断る。何も適用しない（RFC 6902「application of the entire patch document SHALL NOT be deemed successful」）
読んだ版といまの版が違う断る（同じインスタンスを書くほかの任せる先と重ならないように）
id ・ $schema ・ 文書全体（path が空）を変える断る。種類を変えるのは作り直しで、不要になったものは superseded にして残す
move ・ copy断る（使える op は test ・ add ・ replace ・ remove。欄を取り除くのは remove）
② 出力（適用した後）形 ・ 機械の rule に違反する値断らずに保存し、violated を返す（Q8）
人が決める欄を AI が変えた断らずに保存し、rule human-entry-only の結果を返す。needs に出す（Q7 ・ I21）
AI の ruleunverified で返し、needs に出す。親が semantic-judge で依頼し、validate が答えをまとめる

4　止める条件

結果繰り返しの中での扱い
機械の rule の violated0 になるまで AI が直す
error（validator が答えない など）止めて needs で返す。書く操作は再試行しない（Q3）
AI の rule（by: ai）止めて needs で返す。機械の rule が0になってから親が semantic-judge で依頼する
人が決める欄止めて needs で返す。人の入口で直す
前の回と同じ姿になった止めて needs で返す（同じ状態のくり返し）
オーケストレーターのセッション（親がいない）needs の代わりに、判断待ちのまま止める

5　変更の記録

もの置き場所いつ
変更の記録（意図 ・ 目的の参照 ・ 変えた欄）手元の DB止めたあとに record が意図1つにつき1件作る。semantic-write は意図を受け取らない
意図の判定（I33 ・ 人の承認）手元の DB変更の中で判定する
まとめ（change-summary）コミットするコミットの前に、基盤が前回のコミットからの差し引きと例外を機械的に作る（AI は書かない）
rule の判定コミットするほかの人の手元と CI が verified を決める材料

名前は英語と日本語の対で持つ（Q5）：Semantic Read（セマンティックリード）・ Semantic Write（セマンティックライト）。x-prompt の read ・ write のキーと紛れないよう、単独の Read ・ Write とは呼ばない
