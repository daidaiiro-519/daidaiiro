基盤のテスト計画

利用者の問い「テスト計画としてはどのようなテストをする予定ですかね？？テスト規約はどうなるんだろうか。テストピラミッド的に何をどうするのがいいでしょうか。」への答え。qa-advisor の計画（arch/reviews/qa-test-plan.html）を、結論を渡さない反証役に通し、前提に照らして1つにした。arch.html はまだ直していない

単体テストを最も厚くし、domain の値の関数を決定表と状態遷移で確かめる。バイナリを通すシステムテストは、核で作った70場面のうち、バイナリでしか確かめられない約21場面だけにする。残りの場面は、それを守る側のテストへ移す

2　テストの規約（CODING.md のテストの節に置く）

規約中身根拠
単体テストの置き場所確かめるコードと同じファイルの #[cfg(test)] mod testsRust Book ch11-03「The convention is to create a module named tests in each file to contain the test functions and to annotate the module with cfg(test).」
統合テストの置き場所crate ごとに tests/ のファイル1つにし、中をモジュールに分けるCargo「you may want to consider creating a single integration test, and split the tests into multiple modules」（cargo-targets:285）
テストダブルtests/ と dev-dependencies の中だけに置く。本番のバイナリに切り替えの分岐を入れない。名前を grep する検査は持たないCargo「Dev-dependencies are not used when compiling a package for building, but are used for compiling tests, examples, and benchmarks.」・ qa：Test Logic in Production
決定性時刻 ・ id ・ 乱数は値で渡す。domain での生成は clippy の forbid で止める（arch.html 6節と同じ仕組み）。テストごとに新しい前提の状態を作るQ0 #14「同じ入力から同じ結果を返し」
基盤が作る値の期待ULID やコミットの参照を決まった文字列で期待しない。「記録と索引で同じ値」「ULID の形」のように値の関係で期待するI37「書いた時に1回だけ、ほかの書き手と打ち合わせずに一意に決まる値」
1テストに1つ1つのテストは1つの振る舞いを確かめる。テストの中に分岐を書かない。比べるときは何を確かめたかの文を付けるqa：Conditional Test Logic ・ Assertion Roulette
名前テスト関数の名前は確かめる振る舞いを書く。使う場面と不変条件への結びつきは test-suite/ の traces と、単体テストのモジュールの説明に1か所だけ書く反証役：結びつけを2か所に持たない
テストデータの正本test-suite/*.json を正本にし、手で直す。核の build.py ・ ref/ ・ coverage.json は移さないqa：正本を2つにしない

3　完了基準と CI

完了基準中身
テストが通る静的テスト ・ cargo test --workspace ・ crate ごとの単独のビルドとテスト（arch.html 6節の -p の段と1つにまとめる）
同じ入力から同じ結果検証の操作（I13 の範囲）は2回実行して出力が同じ。git と snapshot で出力が一致する
確かめるテストが抜けていない不変条件46と使う場面の事後 ・ 失敗時の全行に、それを確かめるテストがある。いま核では90行のうち65行が「確かめない」（参照実装の範囲外）なので、実装の段でそのテストを書く

CI は毎回の push で、静的 → 単体とコンポーネント統合 → システムの順に全部を回す。本物の AI ツールは呼ばない

4　外したもの

外したもの理由
テストダブルの名前 ・ 環境変数を grep する検査dev-dependencies と tests/ の crate が本番のバイナリに入らないので、Cargo の仕組みで足りる
場面の件数を固定する検査確かめるテストの無い65行に場面を足すたびに CI が落ちる
全部の場面を2回実行して1バイトも同じULID とコミットの参照で必ず違う。I13 が同じ結果を求めるのは検証の操作だけ
使う場面ごとに呼び出しの順を確かめる Mock Object のテスト実装を直すたびに落ちる（qa：Overspecified Software）
inbound/cli の単体テスト起動と結びつけだけ。ただし I37（id を1回だけ決める）を確かめるのは、sqlite のテストと ULID の外の crate だと表に書く
行のカバレッジの数値目標不変条件と使う場面からテストへの対応表（完了基準の3つ目）で足りる

5　前提の扱いを直したこと

変更前変更後指摘
「試験は、入力と期待結果の JSON の組で持ち…」「core は入出力に触らない」「ほかの言語の Concrete も、バイナリを呼んで…」を決着した前提として引いていたどれも Q4（待ち）の下書き。決着しているのは Q0 #14「同じ入力から同じ結果を返し、別の言語の実装が使える適合の試験を持つ」。ポートを application に置く決定は、この Q0 #14 とあなたの承認で成り立つ反証役：board-answers.json の Q3 は open、Q4 は waiting

6　決めてほしいこと

決めてほしいこと私の見解
このピラミッドと、核の70場面の移し替え（システムテストは約21場面）採る。あなたの「基盤側で作りこむ内容ではない」にも沿い、テストのためだけの入口を必要としない
