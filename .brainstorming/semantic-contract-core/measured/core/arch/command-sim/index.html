コマンドのシミュレーション

AI が行う操作は、すべてセマンティック。セマンティックのコマンドは procedure（手順 ・ 入力のスキーマ ・ 出力のスキーマ）を返す。AI が生成するのは入力だけで、出力は機械的なコマンドが作り、型どおりかを validate が見る

問い答え
出力は機械的に作るか作る。AI は入力（Patch ・ 条件 ・ 判定）だけを生成し、状態に適用するのは機械的なコマンド
入力を機械的に適用したら、出力は型どおりかそうとは限らない。だから検査が2回ある ── ①入力が入力のスキーマに合うか（適用する前）②出力が形 ・ 機械の rule ・ AI の rule に合うか（適用した後。AI の rule は unverified で返る）
検査で外れたら①で外れた入力は断り、状態に触れない。②で新しく持ち込んだ機械の rule の違反があれば、書き込みを断る（data.saved:false、exit 1）。前からある違反 ・ AI と人の rule は断らず、状態として返す
状態を変える操作の入力は何か事前状態に足す ・ 変える ・ 取り除く分だけ（Patch の add ・ replace ・ remove）。作るは新しい文書の値、判定は判定1件が入力になる
状態を変えない操作（探す ・ 読む）は事後状態は事前状態と同じ。出力（結果）だけが増え、それも出力のスキーマで検査する

2　目的に沿った流れ：「依存の向きの検査ツールを作る」

5　決めたこと

決めたこと理由
AI が行う操作は、すべてセマンティックのコマンドにするAI が関わるかどうかで、セマンティックと機械的を分ける
セマンティックのコマンドは procedure（手順 ・ 入力のスキーマ ・ 出力のスキーマ）を返す。procedure は Abstract のファイルに足すAI が生成する入力と、機械的に作る出力を、どちらも型で検査できる
セマンティックは、入力のスキーマが違う操作ごとに別のコマンドにする（7つ。semantic-judge を残すかは未決）返す型は同じ procedure でも、入力が操作ごとに違う。意図は record が --intent で受け取り、Patch では書かない
検査は2回。①適用する前に入力を見る ②適用した後に出力を見る①で外れた入力は断り、状態に触れない。②で新しく持ち込んだ機械の rule の違反は書き込みを断る（data.saved:false）。前からある違反 ・ AI と人の rule は断らない
AI の rule の判定は、基盤が coding-agents のアダプターで判定ごとに新しいセッションの AI を起動して依頼し、答えを Validator の2段目に渡す（ステップ4）。judge は人の判定だけdomain は AI を起動しない。起動はポート「rule の判定を依頼する（AI）」のアダプターに置く（CODING.md）
楽観ロックは ETag。get が data.etag を返し、patch --if-match で渡す。JSON Patch の op は add ・ replace ・ remove だけETag は文書の SHA-256 の先頭20字で、保存しない
消すを無くす。不要になったものは superseded にして残す。項目を消すのは変える（Patch の remove）消すでしか済まない場面が無く、消すと指している記録が壊れる
確定していない変更の取り消しは Git の側でする。基盤は戻った姿を validate するだけ基盤は変更の仕組みを持たない

U11（不要になったインスタンスを置き換えて残す）・ I11（superseded のインスタンスに結び付いた判定の記録は効かない）・ U28（Semantic Search）・ boundary の query ・ procedure は、ACDR 0201 で model.json に適用済み。query ・ procedure の Abstract のファイルはまだ無い。0150 ・ 0160 ・ 0120 ・ 0210 は架空。セマンティックのコマンド（procedure を返す）・ search ・ import ・ migrate ・ render ・ session ・ release はまだ実装に無い。2節のカードの decision-record@1 ・ abstract@1 は略記で、URN は urn:semantic-agent-schema:acdr:decision-record:v1 など。3節の出力の例は、実装の試験のシナリオを基盤のコマンドで流した出力から取った
