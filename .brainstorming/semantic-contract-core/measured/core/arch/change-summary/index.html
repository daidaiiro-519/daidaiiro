変更のまとめのシミュレーション

1件ずつの変更の記録は、作業者がセッションの中で確かめるために手元の DB に置く。コミットするのは、目的ごとのまとめ（ACDR のように確かめやすい形）と、ほかの人が verified を決めるのに使う rule の判定。まとめは基盤が記録から機械的に作り、AI は書かない

5　決めたこと

決めたこと根拠
変更の記録と意図の判定は、手元の DB に置く意図の判定の対象は変更の記録で、インスタンスの状態の導出には使わない（I33 ・ I17）。作業者の手元にあれば足りる
まとめはコミットごとに1件。中身は前回のコミットからの差し引きと例外。id は打ち合わせなしで一意な値コミットの差分とまとめが1対1になり、CI が「まとめに無い書き換え」を機械的に出せる
まとめは基盤が機械的に作る。AI が書く欄は持たない意図の文が説明になっている。AI の欄を足すと、その欄の rule と判定を必要とする
rule の判定はコミットに残す状態は変更に入れた判定の記録だけから導く（I17）。残さないと、ほかの人の手元と CI では unverified になる
同じ目的を引き継ぐときは、引き継ぐ前にコミットする手元の DB はほかの人に見えない

0185 ・ C-1〜C-4 ・ J-1〜J-4 は例。まとめのファイル名 changes/01JB7….json は、打ち合わせなしで一意な id の例
