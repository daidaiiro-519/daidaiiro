結論

条件付きで採る

セマンティックな検索は、ドメインサービスではなく、AI のセッションが Search ・ Semantic Read で探して読み、答えのインスタンスを作って検証を受ける使う場面として、中核「意味で探す」に置く。AI の自然な言葉の理解だけが一般「AI と外のツールによる判定」で、基盤が足すのは値オブジェクト「出どころ」と、それを確かめる rule だけにする。基盤が AI を起動して全体を回す案は採らない。

業務領域は同じアクター ・ 同じ外部システム ・ 密接に関係するデータを処理するユースケースの集まりで区切るので、同じインスタンスと索引を読む検索は1つの業務領域に入り、AI は外の上流としてモデル変換装置の向こうに置く。基盤が AI を起動して繰り返しを持つと、状態を持って次のステップを決める仕組み（プロセスマネージャー）が基盤に入り、Q8 が外に置いた「直すループを回す」と、親が任せる先を呼ぶという決定の両方に違反する。

判断の道筋

  1. 1-1　ドメインサービスか、使う場面か、任せる先か

    使う場面である。ドメインサービスは状態を持たず計算をまとめるもので、外の AI に選ばせて書かせる手順の並びはそこに入らない。手順の各段（Search ・ Semantic Read ・ インスタンスを作る ・ 検証）はすでにある使う場面とドメインサービスで、新しいのはその並びと「出どころ」だけである。AI の部分は任せる先（working）か目的のセッションそのもので、答えの判定は任せる先（judging）である

  2. 1-2　「意味で探す」（中核）か「AI と外のツールによる判定」（一般）か

    使う場面と出どころの決まりは中核「意味で探す」に置く。読むデータ（インスタンス ・ 関係の索引 ・ 探した範囲）が機械的な Search と同じなので、同じ業務領域に入れる。自然な言葉を理解して候補を選ぶ部分は、Claude Code ・ Codex などの製品で済む一般で、Agents 契約（モデル変換装置）の向こうに置く。Q9 の「埋め込みの検索の製品を使うとしても、それはアダプターの側」と同じ分け方である

  3. 1-3　必要か

    必要である。呼ぶ側が kind ・ term ・ id を知らない場面（自然な言葉の問いしか無い）に、機械的な Search は答えられない。ただし使う場面の行（U28）として、アクター ・ 目的 ・ 成功時の保証 ・ 最低保証を先に書く。最低保証の候補：出どころの無い答えの欄は verified にならない ・ 探した範囲が付き、範囲の外は探していないと返る ・ 出どころの値が変わったら前の判定は効かない

  4. 2　名前をどう分けるか

    英語と日本語の対で、機械的なものを Search（サーチ）、AI が伴うものを Semantic Search（セマンティックサーチ）にする。利用者の定義（AI が伴うか）を、操作の名前に付く Semantic の意味として glossary に書く：Semantic Read ・ Semantic Write ・ Semantic Search は、x-prompt を AI が読んで行う操作である。crate の名前 search は機械的な Search のまま変えない。業務領域の名前「意味で探す」は両方を含む

  5. 3-1　答えのスキーマは何か

    Semantic Concrete Schema である。答えの形は問いを出す文脈ごとに違い、欄ごとの x-prompt（読み方と書くときの rule）と rule を持つので、文脈が持つ Concrete に当たる。Abstract のファイルにはしない。Abstract は版を出したら変えない基盤の契約で、呼ぶ側ごとの答えの形を持てない

  6. 3-2　出どころをどう持つか

    値オブジェクト「出どころ」を Abstract の $defs に置き（Q6 の値オブジェクトに1つ足す）、答えの Concrete は欄から $ref で使う。中身は、答えの欄の位置（instanceLocation）ごとに、読んだインスタンスの id ・ kind（Concrete の $id）・ instanceLocation ・ 読んだ版の並び。新しい Abstract のファイルにはしない（保存の単位ではないため）。確かめる rule は2つ：機械の rule（指す id ・ 位置 ・ 版がある。Resolver が解決する）と AI の rule（答えの欄の値が、出どころの値に支えられているか。I14 と同じく根拠が渡した値に無ければ unverified）

  7. 3-3　出どころの値が後で変わったら

    新しい仕組みは足さない。AI の rule の判定した値に出どころの値の写しが入るので、出どころのインスタンスが変わると入力が変わり、前の判定は効かなくなる（I16 ・ U10）。出どころのインスタンスを消すと、答えは参照の壊れとして violated になる（U11）。そのために、出どころは関係の索引に「指す側 → 指される側」として入れ、Search の incoming で引けるようにする

  8. 4　crate と依存の向き

    crate は8つのまま増やさず、依存の向きも変えない。出どころの型は instance の crate（declaration だけに依存）に置き、resolver ・ validation ・ search はすでに instance に依存しているのでそのまま使える。出どころの rule の検査は validation、指す先の解決は resolver、incoming で引くのは search。使う場面 Semantic Search はアプリケーション層に置く。AI との受け渡しは adapters の Agents 契約で、working の AI にツールを渡す契約が必要かは Q3 で決める

Semantic Search を実装するときに、基盤のコマンドの中から AI ツールの CLI を起動して繰り返しを書くdomain と application の crate に、AI ツールのアダプターを呼ぶ繰り返し（loop ・ while）が無いことを、Agents 契約のポートを呼ぶ箇所の grep で確かめる。呼んでよいのは Validator の判定の依頼を値で返す箇所だけ
答えの Concrete を作るときに、出どころの欄を $ref で Abstract の値オブジェクトへつながず、自前の形で書く答えの Concrete の各欄に、Abstract の出どころの $defs への $ref があるかを、Concrete を照らす検査（Abstract に従うか）の rule にする
答えを Semantic Write の入力（id と読んだ版の付いた Patch）で作ろうとするシミュレーションで、存在しない id への Semantic Write が断られ、作成はファクトリを通ることを期待する振る舞いに入れる
