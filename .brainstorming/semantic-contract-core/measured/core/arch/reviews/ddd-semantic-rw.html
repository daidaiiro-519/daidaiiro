結論

条件付きで採る

Semantic Read ・ Semantic Write は、駆動する側のポートの操作（使う場面）の名前として採り、JSON Patch は「1つの文書を1回で変える」コマンドの入力として採る。ただし、根が断る条件 ・ 決定権の定義 ・ 変更の記録を書く時点 ・ search の値の条件の付け先の4つを先に決める。

集約の状態はコマンドでだけ変わり、コマンドは不変条件に違反した状態を防ぐ。汎用の Patch でもこの2つは成り立つが、根が断る条件を決めないと、Patch は外から状態を直接書き換える入口になる。2つの語は複数の集約と Resolver ・ Validator をまとめるので、ドメインの操作ではなく使う場面の名前である。

判断の道筋

  1. 問1：2つの語は同じ言葉として成り立つか

    成り立つ。業務エキスパート（利用者）の語で、意味も1つに書ける。ただし「Read ・ Write」は、駆動される側のポートの「読む ・ 書く」と、x-prompt の read ・ write のキーの2つと重なる。Semantic Read が x-prompt の write（rule の並び）も返すことを用語の定義に書き、「案内する」「インスタンスを書く」は同義語になるので使わなくする

  2. 問1：使う場面の名前か、ドメインの操作か

    使う場面の名前である。Read は複数の集約と Resolver の結果をまとめて返す問い合わせ、Write は1つの集約のコマンドと Validator の呼び出しを並べる手順で、どちらも1つの集約の中で閉じない

  3. 問1：駆動する側のポート10とどう対応させるか

    「探して取り出す ・ 案内する」を「search」と「Semantic Read」に分ける。「インスタンスを書く」の更新を「Semantic Write」にし、対象を Concrete にも広げる（x-prompt の作成 ・ 更新 ・ 削除はここ）。作成（雛形のファクトリ）・ 削除 ・ 取り込むは別のコマンドに残す。「意味を宣言する」は 照らす ・ 公開する部分の版を出す などに縮める。ポートは11になる

  4. 問2：繰り返しは誰が持つか

    目的のセッション（AI）が持つ。基盤の Semantic Write は1回ごとに、根のコマンド → 保存 → Validator → 結果の返却 だけをする（集約の判断基準のアプリケーション層の役割と同じ）。止める条件は「violated と error が0」で、unverified ・ unsupported と決定権の欄は needs で親に返す

  5. 問2：AI の rule の判定は繰り返しのどこで動くか

    Validator は AI の rule では call を返し、依頼するのは使う場面である。毎回の Write で AI に判定させると費用が繰り返しの回数だけ増えるので、機械の rule の violated が0になってから依頼する順にする案を決める。判定した値がいまと同じなら使い直す（I16）

  6. 問2：決定権との関係

    Semantic Write（MCP の入口）からは、決定権が人の欄を変える op を根が断る。人の入口（CLI ・ 画面）からの同じコマンドは通す。入口の種類は呼ぶ側の引数ではなくアダプターが決める。これを採るなら、値オブジェクト「決定権」の「AI が書き写すのはよい」を直す。I21 は基盤を通らない書き換えを見つける検査として残る

  7. 問2：I33 との関係

    I33 の判定の対象は変更の記録で、変更の中でだけ判定する。インスタンスの rule ではないので、繰り返しの止める条件に入れない。変更の記録は書き換えない（I32）ので、Write のたびに記録を書くと意図1つに記録が何件もできる。変更の記録は、繰り返しが止まってから「変更を記録する」で意図1つにつき1回書く案を採る

  8. 問3：JSON Patch で根は不変条件を守れるか

    根が断る条件を決めれば守れる。断るのは ① 1つでも op が失敗したら何も当てない ② id ・ $schema（移すは別のコマンド）・ 決定権が人の欄を path か from に含む op ③ 文書全体（path が空文字）を指す op ④ 読んだ版といまの版が違う、の4つ。rule の違反は断らず、結果として返す（状態「下書き」）

  9. 問3：Concrete に当てるときに増えること

    Concrete の中で閉じる不変条件（I4 rule の id が一意）を根が見る。公開した版の中身を変える op（$id の never-reuse）も断る。Concrete を変えたあとの全インスタンスの検証（U2）は Write の返り値に含めず、「検証する ・ 変更を見せる」で出す。x-prompt を変えた欄の AI の判定は、判定した値に読んだ x-prompt の文があるので I16 で効かなくなる

  10. 問4：search の欄の値の条件を JSON Schema で書いてよいか

    条件付きで採る。値の条件は、種類と Concrete の欄の位置（または term）に付けた先の値にだけ当てる。結果の位置は、付けた欄の位置をインスタンスの中の位置に解いたもので、JSON Schema の出力からは取らない。索引は id ・ kind ・ x-relationship だけなので、値の条件は全件を読む。遅いと測れてから索引を足す

  11. 問4：位置の名前

    下書きの「schemaLocation」は JSON Schema 2020-12 のキーに無い。出力の keywordLocation は $ref を通った keyword の道筋で、Concrete の文書の中の欄の位置とは別物である。「Concrete の中の欄の位置（JSON Pointer）」と名前で書き、出力のキーの名前を借りない

アンチパターンリスク代替案
汎用の setter としての Patch（判断基準の setter をプライベートにする手順が避けるもの）根が断る条件が無いと、Patch は id ・ $schema ・ 決定権の欄を外から直接書き換える入口になる。どこで状態が変わったかを根の1か所で追えない（推測）根のコマンド「Patch を当てる」に、断る4条件（全部か無しか ・ 守る位置 ・ 文書全体 ・ 読んだ版）を持たせる。守る位置は、Resolver が Concrete からインスタンスの中の位置へ解いて求める
同じ言葉の同義語（Semantic Write と インスタンスを書く、Semantic Read と 案内する）同じ操作に語が2つ残ると、利用者と AI が別の操作だと読み、ポートやコマンドが2つ作られる（推測）model.json の ports と use_cases の文から「案内する」「インスタンスを書く」を消し、語を1つにそろえる。定義を naming か用語の表に足す
1つの語に2つの意味（Read ・ Write）駆動される側のポート「インスタンスを読む ・ 書く」（保存）と、x-prompt の read ・ write（読み方と書き方の決まり）と、Semantic Read ・ Write（AI の読み書き）の3つが同じ語になる。Semantic Read が x-prompt の write も返すことが読み違えられる（推測）語は Semantic Read ・ Semantic Write の全体でだけ使い、単独の Read ・ Write を使わない。定義に「Semantic Read は x-prompt の read と write の両方を返す」と書く
1つのトランザクションで複数の集約を変えるU7（契約の変更で violated になったインスタンスを直す）を1つの Patch で複数の文書に当てると、1つのトランザクションで複数の集約を変えることになる1回の Semantic Write は1つの文書に限る。複数のインスタンスは文書ごとに書き、x-relationship の整合はそれまで violated として見える（結果整合）
必要になる前の CQRSsearch の値の条件の速さのために、読み取り用の索引を先に作ると、永続化モデルが2つになる値の条件は全件を読む。関係の索引と同じく、遅いと測れてから、正本のファイルから作り直せる索引を同じポートの後ろに置く

model.json の aggregates（インスタンス ・ Semantic Concrete Schema の commands）コマンド「Patch を当てる」：入力は JSON Patch と読んだ版と入口の種類。断る条件は4つ（全部か無しか ・ 守る位置 ・ 文書全体を指す op ・ 版の不一致）。rule の違反は断らずに結果で返す
model.json の value_objects「決定権」「AI が書き写すのはよい」を直すかを決める。直すなら「決定権が人の欄は、人の入口から来たコマンドでだけ変わる。AI は値の案を needs で親に返す」
model.json の invariants（新しい行）「1回の Semantic Write は1つの文書だけを変え、1つでも op が成り立たなければ何も変えない」「Semantic Read は状態を変えない（判定の記録も書かない）」
用語（naming か glossary）Semantic Read：文書の id と欄の位置から、その欄の x-prompt（read と write）・ いまの値 ・ 版 ・ reads が指す欄の値 ・ rule ごとのいまの結果を返す操作。Semantic Write：読んだ版と JSON Patch を受け取り、1つの文書を変えて rule ごとの結果を返す操作

差し戻し

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
ボード Q1（決着）の値オブジェクト「決定権」「AI が書き写すのはよい」は、書いた者が AI のときに値の出どころを基盤が確かめる方法を持たない。下書きの「断る」と両立せず、どちらかを上流で決め直す必要がある疑い
Q4（protocol、待ち）Semantic Read ・ Write の入出力の形（版 ・ rule ごとの結果 ・ call の返し方）は protocol が持つ。ここで形を決めると、待っている Q4 を下流から決めることになる疑い

次にすること

  • 決定権の定義（AI が書き写すのはよいか）を利用者に確かめる
  • 根が断る条件と、断らずに violated として返す条件の表を、インスタンスと Concrete の2つの集約について作る
  • Semantic Write のたびに変更の記録を書くか、意図1つにつき1回書くかを決める
  • AI の rule の判定を繰り返しのどこで依頼するか（機械の rule の violated が0になってから）を決める
  • 版（Semantic Read が返す値）を何から作るかを決める
  • search の値の条件を、種類と欄の位置か term に付ける形で、search の完成イメージの頁に足す
  • 下書きの「schemaLocation」を「Concrete の中の欄の位置」に直す
  • ports.inbound の対応表を changes.py に足して model.json を作り直す

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
Patch の path だけを見て、move ・ copy の from を見ずに決定権の欄の検査を通す根のコマンドの単体テストに、from が守る位置を指す move と、path が守る位置へ写す copy の2件を入れ、どちらも断られることを確かめる
rule の violated を理由に Semantic Write を断り、下書きを保存しないviolated になる Patch を当てたテストで、ファイルが書かれ、結果に violated と根拠が返り、状態が「下書き」になることを確かめる
Write のたびに変更の記録を書き、意図1つに記録が何件もできる同じ意図で Write を3回したあとの変更の記録の件数が、決めた数（意図1つにつき1件なら1）と同じかを数える
search の結果の位置を JSON Schema の出力の instanceLocation から取るcontains を使う値の条件で、結果の位置が条件を付けた欄の位置と同じかを確かめる
