結論

採る

ドメインサービスは3つ（Semantic Schema Resolver ・ Validator ・ Renderer）である。再開か新規かを決めるはセッションの集約の操作で、利用者の「4つ」は1つ多い。残りの10は、集約の操作4 ・ 値オブジェクトの操作2 ・ ファクトリ3 ・ 使う場面（application）1に分かれる。

Evans は、エンティティにも値オブジェクトにも自然に属さない処理だけをサービスにする。判断基準（domain-service）も、集約や値オブジェクトで表現しにくいとき、または複数の集約を参照して計算するときに業務サービスに書くとする。13のうち、2つ以上の集約を読み、どの集約も変えず、どの集約の不変条件にも属さない計算は、Resolver ・ Validator ・ Renderer の3つだけである。ほかの10は、変える集約が1つ（その集約のコマンド）、作る物が1つ（ファクトリ）、1種類の値から計算する（値オブジェクト）、読む ・ 並べる ・ 書くの順序を決める（使う場面）のどれかに当たる。再開か新規かを決めるが読む ・ 変える集約はセッション1つだけで、AI ツールの答えと設定は値として渡る。原文の「An entity is responsible for tracking its state and the rules regulating its lifecycle.」のとおり、開いたまま続けるか閉じるかはセッション自身のライフサイクルの決まりである。

判断の道筋

  1. その処理は集約を変えるか。変えるなら、いくつか

    1つだけを変えるなら、その集約のコマンドにする（Concrete を照らす ・ 移す ・ 公開された言葉の版を出す ・ 再開か新規かを決める）。2つ以上を1回で変える処理は13の中に無い

  2. 集約か複雑な値を丸ごと1つ作るか

    作るならファクトリにする（作成する ・ 取り込む ・ 変更を見せるの後半）

  3. 1種類の値だけから計算するか

    そうなら値オブジェクトの操作にする（状態を導く ・ 例外をまとめる）

  4. 読む ・ 問い合わせる ・ 書くの順序を決めているだけか

    そうなら使う場面にする（意味で探して取り出す。変更を見せるの前半と取り込むの一覧も）

  5. 残ったものは、2つ以上の集約を読み、どの集約の不変条件にも属さない計算か

    Resolver ・ Validator ・ Renderer の3つが当たる。これがドメインサービスである

  6. 再開か新規かを決めるは、エンティティにも値オブジェクトにも自然に属さないか

    属する。読む集約はセッション1つ（I46 で枠に1つまで）で、AI ツールの答え ・ 設定 ・ 時刻は値で渡る。閉じる（I45）もセッションのコマンドである

設計の手順

  1. 13を分類する

    下の表「13の分類」のとおり。各行に、読む ・ 変える集約と、守る不変条件を書いた

  2. domain の各 crate の中を組み直す

    aggregates/ に集約のコマンドを、factories/ にファクトリを、src/ の直下に値オブジェクトを置き、services/ は validation と render だけに残す。migration と publish の crate は消し、search の crate は値オブジェクト（探した範囲）だけにする

  3. model.json の書き換え案を changes.py に足す

    下の表「model.json の書き換え案」を C61 以降の変更として書き、apply.py で model.json を作り直す

判定の拠りどころにした判断基準の記述

判断基準引用
domain-service業務サービス（英語は Services）：業務ロジックだけを書き、自分の状態は持たないステートレスなオブジェクト。集約や値オブジェクトの中では不自然になる業務ロジックの置き場所で、ほとんどの場合、いろいろなコンポーネントの呼び出しをまとめて何かの計算や分析をする。
domain-service問い：その業務ロジックは、集約や値オブジェクトでは表現しにくいか ・ 「はい」なら：業務サービスに記述する
domain-service問い：複数の集約を参照する計算のロジックか ・ 「はい」なら：業務サービスで記述すると、わかりやすくなる
domain-service業務サービスが有効なのは、いくつもの集約を参照して計算するロジックである。集約の変更とデータベーストランザクションの関係は、常に意識する
aggregate構成するもの：コマンド ・ 役割：集約が公開する状態変更のメソッド。外部から渡された内容を検証し、業務ルールと不変条件に違反した状態になることを防ぐ。集約の状態は、コマンドを実行したときにだけ変わる
aggregate対応：集約の状態は集約内部の業務ロジックだけが変更できるようにし、外部には参照だけを許可する ・ 理由：関連する業務ロジックを、すべて集約自身の1か所に実装できる
aggregate業務ロジックを集約に集めると、アプリケーション層の役割は、集約の生成 ・ 操作の実行 ・ 永続化 ・ 結果の返却だけになる。
value-object性質：データとロジック ・ 内容：メソッドは値を操作し、その結果を新しい値オブジェクトとして返す
value-object性質：業務の概念の表現 ・ 内容：値の妥当性の検査にとどまらず、その値を使う業務ロジックを1箇所に集め、ソースコードに同じ言葉を語らせる
entity対応：エンティティを単独で実装せず、集約の実装の一部にする

注意

アンチパターンリスク代替案
要求事項に出てくる名詞をすべて集約として表現し、業務ロジックを巨大なサービス層に書く（いまの13はこの形に近い）トランザクションの境界とずれ、業務ロジックもほぼ持たない、名前だけの「集約」になる。業務ロジックはすべて巨大なサービス層に書かれるサービス層のクラスを減らして業務ロジックを適切な集約へ移動する。ここでは10の処理を、集約のコマンド ・ 値オブジェクト ・ ファクトリ ・ 使う場面へ移す
業務サービスを使って、複数の集約のインスタンスを1つのデータベーストランザクションで変更する集約のインスタンス1つにトランザクション1つ、という原則に反する。業務サービスは、この原則の例外にはならない再開か新規かを決めるは、開いていたセッションを閉じるだけ（1つ）にし、新しいセッションの登録は AI ツールが ID を発行したあとの別の操作にする。どちらも application が1回ずつコミットする
（推測）集約のコマンドを、集約の型と別の crate（migration ・ publish）に置こうとするRust はある型のメソッドを、その型を定義した crate の外に書けない。別の crate に置くには trait を足すか自由な関数にすることになり、コマンドが集約の外に出る移す ・ 公開する部分の版を出すは declaration の集約の型に置き、migration と publish の crate を消す。使う場面（release.rs）は application に残す
