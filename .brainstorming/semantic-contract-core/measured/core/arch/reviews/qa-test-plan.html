判断の道筋

  1. タスク1. テストレベルごとに、どの crate の何を、どのテストダブルで確かめるか

    静的テスト＝ワークスペース全体（arch.html 6節 ・ fmt ・ clippy ・ JSON の検査）。単体テスト＝crates/domain/* の集約 ・ ドメインサービス ・ 値オブジェクトと、agents-contract の形の変換 ・ ai-cli の argv の生成と出力の読み取り（値の関数の部分）。Test Double は使わない。コンポーネント統合テスト＝crates/application（ポート12を Fake ・ Test Stub に替える）と crates/outbound/*（本物の fs ・ git ・ sqlite ・ 外のツールを一時ディレクトリで。Test Double は使わない）。システムテスト＝crates/inbound/cli/tests/test_suite.rs が test-suite/ の56場面でバイナリを起動する。inbound/cli の main.rs ・ compose.rs には単体テストを書かない。詳細は「設計の手順」の1〜4

  2. タスク2. ピラミッドの配分と、56場面との重なりをどう扱うか

    採るのは案 B。厚い順に 単体（domain）＞ コンポーネント統合（application の失敗の経路 ・ outbound のポートの op ごと）＞ システム（56場面）。重なりの決まりは1つ：使う場面の事後 ・ 失敗時のうち、protocol の外から見える結果は test-suite/ の場面が持ち、単体テストは同じ結果をもう一度確かめず、場面が並べない組み合わせ（決定表の列 ・ 無効な遷移 ・ 不変条件の境目）だけを持つ。application のテストは、場面で起こせないポートの失敗（届かない ・ 起動できない ・ 変わったものが無い）だけを持つ

  3. タスク3. テストの規約

    置き場所 ・ 名前 ・ 1テストに1つのテスト条件 ・ 分岐の無いテスト本体 ・ Test Double の置き場所 ・ 決定性 ・ テストデータの正本 ・ AI ツールを呼ぶアダプターの試し方の8つを CODING.md のテストの節に持つ。中身は「記録案」の CODING.md の行

  4. タスク4. 完了基準と CI

    完了基準は5つ：静的テストが全部通る ／ cargo test --workspace が全部通る ／ crate ごとに -p で単独に test が通る ／ 不変条件46と使う場面の事後 ・ 失敗時の全行が、少なくとも1つのテストに結び付いている（確かめない行が0件か、残す行を利用者が承認している）／ 56場面を2回実行して出力が同じ。CI は 静的テスト → 単体とコンポーネント統合 → システムテスト の順に、毎回の push で全部回す。arch.html 6節の検査は CI の静的テストの段そのものであり、動的テストの代わりにはしない

  5. タスク5. 外せるもの

    inbound/cli の単体テスト ・ application の使う場面ごとの Mock Object によるテスト ・ 場面と同じ事後条件を確かめる単体テスト ・ 本物の AI ツールを CI で呼ぶテスト ・ ports の trait の定義だけを確かめるテスト ・ 行のカバレッジの数値目標 ・ coverage.json を実装のリポジトリで回す仕組み ・ doctest（推測：crates.io へ出さないため）。どれも外しても前提 162 ・ 164 ・ Q0 原則5 は満たされる。詳細は「設計の手順」の5

設計の手順

  1. 1. 静的テストの段を決める（ワークスペース全体）

    arch.html 6節の6つ（辺の種類ごとの突き合わせ ・ feature の統合 ・ pub use ・ clippy forbid ・ domain に trait のポートを置かない ・ 外の crate の許可）に、テストのための4つを足す：(a) test-suite/*.json を場面の JSON Schema（test-suite/scenario.schema.json。推測：名前は未決）で検査する、(b) test-suite/ に when.op が sql の場面が0件、traces が全場面で1件以上、(c) crates/*/src/ の #[cfg(test)] mod tests の外に Fake ・ Stub ・ Mock の型と cfg(test) の分岐が0件、(d) crates/domain/ と crates/application/src/ に SystemTime::now ・ ULID の生成 ・ 乱数の呼び出しが0件（時刻と id は inbound から値で渡す）。arch.html 6節は dev の辺も数えるので、application の dev-dependencies に outbound/* を足すことも止まる

  2. 2. 単体（コンポーネント）テスト：crates/domain/* と、アダプターの値の関数

    対象：集約9の不変条件 ・ ドメインサービス13 ・ 値オブジェクト（URN ・ target ・ change_id ・ session_id など）。Test Double は使わない（domain は値の関数で、ポートを持たない）。技法：状態を導く（I19）は決定表の実行可能な列をすべて1テストずつ、セッションの開いている → 閉じた（I45）とインスタンスの4状態は状態遷移で、無効な遷移を1テストに1つ。Semantic Schema Validator は「依頼の一覧を返す」と「答えを5つの値にまとめる」を別々に、割れた答え ・ 根拠の無い答え → unverified（I14）を1テストずつ。Resolver は渡された材料に無い $id を断ること（I2）。agents-contract の呼び出しの形への変換 ・ 答えの形の読み取りと、ai-cli の argv の生成 ・ 出力の読み取りも、値の関数に切り出してここで確かめる。schemas/v1 は本物を build.rs で取り込んだまま使い、替えない

  3. 3. コンポーネント統合テスト：crates/application と crates/outbound/*

    application/tests/：ポート12を tests/common/mod.rs に置く Test Double に替える。保存のポート（contracts ・ instances ・ judgments ・ change_records ・ sessions ・ rendered）は Vec や HashMap に読み書きする Fake、judge ・ ai_sessions ・ tools ・ settings ・ published ・ changes は決まった答えを返す Test Stub。確かめるのは、場面で起こせない失敗の経路（changes が unreachable を返す ・ 確定で変わったものが無い ・ judge が起動できない → unsupported（I15 ・ I39）・ 書き込みの途中の失敗で何も書かない）と、Fake の中身で見える状態（呼び出しの順と回数は確かめない）。outbound/*/tests/：Test Double を使わず、本物の外の技術を一時ディレクトリで動かす。ports.json の op ごとに、out の oneOf の各分岐（items と unreachable など）を1テストずつ出し、出力を ports.json の Schema で検査する。changes を実装する git と fs/snapshot には同じテスト関数を当てる。sqlite/tests/ は SQL の14場面（一意の索引とトリガーで I46 を断る）を DDL に直に実行する。tools は固定の答えを返す小さなプログラムを起動して確かめる

  4. 4. システムテスト：test-suite/ の56場面を、本番と同じバイナリで回す

    crates/inbound/cli/tests/test_suite.rs を [[test]] harness = false のデータ駆動テストにし、CARGO_BIN_EXE_<name> のバイナリを場面ごとに起動して標準入出力で回す。1場面 × 1アダプターを1件として報告し、落ちたら場面の id ・ アダプター ・ then の id と message を出す（message が Assertion Message の役をする）。同じ場面を2回実行し、出力が同じことを確かめる（Q0 原則5 ・ I13）。場面ごとに新しい一時ディレクトリを作り（Fresh Fixture）、並列に実行してよい形にする。未判定1 ・ 2 が決まるまで、given.judge ・ given.ai と基盤が作る値の literal の期待（S-REC-1 E4 など）を持つ場面は、バイナリにテスト用の入口を足して通さない。期待を「ULID の形で、記録と索引で同じ値」のような関係に書き直すか、その条件だけを application のテストへ移すかを先に決める

  5. 5. 外せるものを外す

    (a) inbound/cli の main.rs ・ compose.rs の単体テスト：lib.rs が無く tests/ から use できない。結びつけの誤りは56場面が落ちるので見つかる。(b) application の使う場面10ごとの Mock Object による呼び出しの順のテスト：内部の順に結び付き Fragile Test になる。事後条件は場面が持つ。(c) 場面と同じ事後条件を確かめる単体テスト：レベルの目的が重なる。(d) 本物の AI ツールを CI で呼ぶテスト：答えが毎回変わり、CI の環境に AI ツールの認証が必要になる（Erratic Test の Nondeterministic Test と Resource Optimism）。AI ツールの版を上げたときに手で実行し、得た出力を ai-cli の単体テストの入力ファイルに足す。(e) ports の trait の定義そのもののテスト（処理を持たない）。(f) 行のカバレッジの数値目標：前提が求めるのは不変条件と使う場面への結び付きで、行の割合ではない。(g) coverage.json を実装で回す仕組み：前回の判定どおりボードに残す。(h) doctest（推測：crates.io へ出さないので、公開の API の文書の例を確かめる必要が無い）

  6. 6. 完了基準と CI を、テスト計画書として CODING.md と CI の設定に書く

    完了基準：①静的テストの段が全部通る ②cargo test --workspace が通る ③crate ごとに cargo test -p が単独で通る（feature の統合に頼っていないこと）④不変条件 I1〜I46 と使う場面の事後 ・ 失敗時の全行が、場面の traces かテスト関数の名前で少なくとも1つのテストに結び付く。結び付かない行が残るなら、行ごとに残す理由を利用者が承認する ⑤56場面を2回実行して出力が同じ。CI：毎回の push で 静的テスト（数秒）→ 単体 ・ コンポーネント統合（cargo test --workspace）→ システムテスト（test_suite）の順に全部回す。テストの数が増えて遅くなっても、どのテストも定期的に回ることを守る

test-first-development対応：テストレベルごとに、そのレベル特有の異なる目的を持たせる ・ 理由：冗長性を避けながら、適切に包括したテストを実施できる
test-pyramid観点：妥当なカバレッジに必要なテストの数 ・ 最下位のレイヤー：通常、多い ・ 最上位のレイヤー：通常、ほんの数個
test-pyramid条件：レイヤーが高くなる ・ 対応：テストの粒度は粗くなり、テストの分離は少なくなり、テスト実行時間は遅くなる
test-pyramidモデル：一般的なモデル ・ 定義するレイヤー：ユニット（コンポーネント）テスト ・ 統合（コンポーネント統合）テスト ・ エンドツーエンドテスト
test-levelsテストレベル：コンポーネントテスト（ユニットテスト） ・ 焦点：コンポーネントを単独でテストすること ・ 特記事項：テストハーネスやユニットテストフレームワークなどの特定のサポートを必要とする場合が多い。実施するのは、通常、開発担当者で、場所は開発環境である
test-levelsテストレベル：コンポーネント統合テスト（ユニット統合テスト） ・ 焦点：コンポーネント間のインターフェースと相互処理 ・ 特記事項：ボトムアップ ・ トップダウン ・ ビッグバンなどの統合戦略のアプローチに大きく依存する
test-levelsテストレベル：システムテスト ・ 焦点：システムやプロダクト全体の振る舞いと能力の全般。多くの場合、エンドツーエンドのタスクの機能テストと、品質特性の非機能テストである ・ 特記事項：一部の非機能品質特性（例：使用性）は、本番相当のテスト環境で、完全なシステムを対象にテストするのが望ましい。サブシステムのシミュレーションも使用できる。システムの仕様に関連し、独立したテストチームが実施することがある
hard-to-test-code原因：Highly Coupled Code ・ 場面：テストのために結合を断つ ・ 直し方：Test Double を使う。より具体的には Test Stubs や Mock Objects である
hard-to-test-code原因：Asynchronous Code ・ 場面：どの場合も ・ 直し方：処理（logic）を、非同期のアクセスの仕組みから分ける
test-logic-in-production原因：Test Hook ・ 場面：どの場合も ・ 直し方：テストのための処理を製品のコードに書き込まず、差し替えのきく依存（substitutable dependency）の側へ移す
test-logic-in-production原因：Test Dependency in Production ・ 場面：どの場合も ・ 直し方：型の定義のように害の無さそうなものでも、製品のコードがテストコードを当てにしないよう、依存を気を付けて管理しなければならない
fragile-test敏感さ：Context Sensitivity ・ 直し方：テストを決定的にするため、SUT のすべての入力を制御する。
fragile-test原因：Overspecified Software（別名 Overcoupled Test） ・ 何か：ソフトウェアをどう構成し、どう振る舞うべきかについて、テストが言いすぎている。Test Double で部分を切り離す unit test に慣れていないことが、この形で出ることもある ・ Fragile Test や敏感さとの関係：Behavior Sensitivity の一形態で、Mock Object を多用して layer-crossing test を作る Behavior Verification の流儀にともなう
erratic-test原因：Nondeterministic Test ・ 直し方：Conditional Test Logic を取り除き、ランダムな値を決定的な値に置き換える（下の手順）
conditional-test-logic原因：Multiple Test Conditions ・ 場面：値の組が大量にある ・ 直し方：Data-Driven Test に切り替えるほうが、よりよい解決になるかもしれない
conditional-test-logic原因：Multiple Test Conditions ・ 場面：Defect Localization が得られない ・ 直し方：テスト条件ごとに別々の Test Methods を作り、そこから Parameterized Test を呼ぶ
assertion-roulette条件：1つのテストで同じ種類の Assertion Method を2回以上呼ぶ ・ 対応：最小限でよいので Assertion Message を付ける
obscure-test原因：Mystery Guest ・ 場面：ファイルなどの外部リソースを使わざるを得ない ・ 直し方：そのためだけのフォルダやディレクトリに置き、名前を見ればどんなデータが入っているかが分かるようにする
decision-table-testing項目：100%の条件 ・ 内容：これらの列を、テストケースですべて通過する
state-transition-testing条件：全遷移カバレッジで無効な遷移をテストする ・ 対応：1つのテストケースで無効な遷移を1つだけテストし、欠陥のマスキングを回避する
testware対応：適切な構成管理で、作業成果物の一貫性と整合性を確保する
test-automation条件：第一象限（コンポーネントテスト ・ コンポーネント統合テスト） ・ 対応：自動化して CI プロセスに含めるべきである
static-testing場面：シフトレフト ・ 静的テストの扱い：仕様書をテストの観点でレビューする。ソースコードの静的解析は、動的テストより前か、自動化したプロセスの中で完了させる
entry-exit-criteria対応：開始基準と終了基準を、テストレベルごとに定義するべきである
entry-exit-criteria区分：終了基準 ・ 基準：完了基準 ・ 例：計画したテストの実行 ・ 静的テストの実行 ・ 発見したすべての欠陥のレポート ・ すべてのリグレッションテストの自動化
confirmation-and-regression-testing対応：リグレッションテストケースの自動化を、プロジェクトの早期に開始する
slow-tests原因：Too Many Tests ・ 見え方：テストがとても多く、1つ1つがいくら速くても、実行に長くかかるのは避けられない ・ 根本の原因：明らかな原因はテストの数そのもので、システムが本当に大きいか、テストの重なりが多すぎるかのどちらかである。見えにくい原因は、多すぎるテストを頻繁に実行しすぎていることである ・ 直し方：テストを毎回すべて実行しなくてよい。大事なのは、どのテストも定期的に実行されるようにすることである（下の規則）

アンチパターンリスク代替案
Test Logic in Production（Test Hook）：compose.rs に環境変数 ・ 引数 ・ feature で模擬の判定や固定の時刻 ・ id へ切り替える分岐を足すテストと本番で違う動きをするバイナリになり、56場面が通っても本番の結びつけを確かめていないことになる。誤った設定1つで本番でも固定の値が使われうる模擬は本番と同じ経路（Concrete の x-delegates の argv など、利用者も使う設定）でだけ渡す。経路が無い期待は、場面の期待を値の関係に書き直すか、application のテストへ移す（未判定1 ・ 2）
Test Dependency in Production：Test Double を置く crate を作り、本番の crate の [dependencies] から使う本番のバイナリにテストのコードが入る。arch.html 6節の辺の検査に無い crate が増えるTest Double は使う crate の tests/common/mod.rs に置く。2つ以上の crate が同じ Test Double を使うようになったら、（推測）publish = false のテスト用 crate を作り、architecture.json に dev の辺だけを許す行として足す
Overspecified Software：application のテストで Mock Object に呼び出しの順と回数を期待する使う場面の中の順（読む → ドメインサービス → 書く）を直すたびに、振る舞いが同じでもテストが落ちる（Fragile Test）Fake に書かれた中身と戻り値で確かめる。呼ばれたこと自体が外から見える結果のとき（確定を呼ばないことなど）だけ、呼ばれた回数を確かめる
Multiple Test Conditions ・ Assertion Roulette：56場面を1つの #[test] のループで回す最初に落ちた場面で止まり、どの場面 ・ どのアダプター ・ どの期待で落ちたかが出ないharness = false のデータ駆動テストで場面 × アダプターごとに1件として報告し、then の id と message を失敗の文に出す
Erratic Test（Interacting Tests ・ Nondeterministic Test）：libtest が並列に実行するテストが、同じ一時ディレクトリ ・ 同じ SQLite のファイル ・ 実時刻を共有する実行の順と時刻によって落ちたり通ったりする。I46 の concurrent_register の場面は特に、実時刻と実行の順に左右されやすいテストごとに新しい一時ディレクトリと DB のファイルを作り（Fresh Fixture）、時刻と id はテストが値で決める。git のアダプターのテストは作者と日時を固定する（推測：GIT_AUTHOR_DATE などの環境変数で固定できるかは原文で照合していない）
（推測）レベルの目的の重なり：場面の事後条件を単体テストへ写し、さらに場面にも組み合わせを足す同じ欠陥で2つのレベルが落ち、場面を直すたびに単体テストも直すことになる。最上位が太ってピラミッドが逆になる外から見える結果は場面、組み合わせは単体、ポートの失敗は application、と行き先を1つに決め、レビューで確かめる

差し戻し

原因が上流の判断に在る疑い。断定せず、疑いとして示す

疑われる上流（advisor ・ 判断）疑う理由
場面の期待の書き方（behaviors/build.py で作った then の equals）S-REC-1 E4 などは基盤が作る ULID を literal で期待しており、参照の実装では given.ids を渡せたが、本番のバイナリで同じ期待を満たすにはテストのためだけの入口が必要になる疑いがある。前提 164 の「どのインターフェースも同じ試験」を守るなら、期待を値の関係（形と、記録と索引で同じ値）に直す必要があるかもしれない
ports.json と arch.html 5節のポート12（AI ツールの起動と時刻 ・ id の作り方）時刻と id は compose.rs が作る、としているが、それを外から決める正規の経路が protocol に無い。システムテストの決定性をどこで担うかは、platform-advisor ・ ddd-advisor の判断（protocol に入れるか、入れないか）に依る疑いがある

次にすること

  • 未判定2（基盤が作る ULID と時刻を場面がどう期待するか）を利用者に確かめる
  • 未判定1（模擬の判定と模擬の AI をバイナリの外から渡す経路）を、未判定2 と一緒に決める

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
テストを通すために、compose.rs や application に環境変数 ・ 引数 ・ feature による模擬への切り替えを足すcrates/*/src/ を grep し、#[cfg(test)] mod tests の外に cfg(test) ・ Fake ・ Stub ・ Mock ・ test_ で始まる環境変数の読み取りが0件であることを CI の静的テストで確かめる
domain や application の中で SystemTime::now ・ ULID の生成 ・ 乱数を呼ぶcrates/domain/ と crates/application/src/ に SystemTime ・ Ulid::new ・ rand の呼び出しが0件であることを grep する（arch.html 6節の外の crate の許可表で rand ・ ulid の生成の feature を domain に許さないことでも止める）
場面と同じ事後条件を単体テストに写す、または 56場面を Rust の #[test] に書き直すtest-suite/ の場面の数と traces を CI で数え、56件と、全場面の traces が1件以上であることを確かめる。単体テストに場面の id（S-…）の文字列が無いことを grep する
56場面を1つの #[test] でループして回すcrates/inbound/cli/Cargo.toml の [[test]] name = "test_suite" に harness = false があり、出力の件数が場面 × アダプターの数と一致することを CI で確かめる
本物の AI ツールを呼ぶテストを CI に入れる、または #[ignore] のテストを黙って増やすCI の設定に AI ツールの認証の秘密が無いことと、#[ignore] の件数を CI で数えて、増えたら落とす
