結論

条件付きで採る

70場面は基盤自身のシステムテストのテストケース（テストウェア）であり、前提 164 を守るために JSON のまま持ち込む。ただし、そのままは移さず、インターフェースに依らない56場面と SQLite のアダプターだけの14場面に分け、coverage.json ・ build.py ・ ref/ はボードに残し、受け入れテストの名前をやめる

前提 164 が JSON の組を試験の形と決めているので、Rust のテストに書き直すとほかのインターフェースと言語の実装が同じ試験を通せなくなる。一方で、判断基準の受け入れテストは想定ユーザーがビジネスニーズを確かめるテストレベルであり、機械が基盤の操作を確かめるこの場面の集まりには当たらないので、名前と置き場所をシステムテストとして決め直す

判断の道筋

  1. 1. この場面の集まりは何か（製品の機能か、基盤自身の試験のデータか、設計の検証の材料か）

    製品の機能ではない（基盤が利用者へ出すものではない）。基盤自身の試験のテストケースとテストデータであり、判断基準のテストウェアに当たる。核の段では、ドメインモデル ・ スキーマ ・ DB が食い違わないことを参照の実装で回して確かめる設計の検証の材料も兼ねていた。実装の段では、前者の役目だけが残る

  2. 2. 受け入れテスト駆動の考え方が混ざっているか

    形は混ざっている。コードより先に、使う場面の事後条件 ・ 失敗時と不変条件から、題を自然言語で書いた Given/When/Then の場面を作っており、テストファーストで受け入れ基準のシナリオ指向の形式に当たる。しかし受け入れテスト（UAT）ではない。判断基準の受け入れテストは想定ユーザーがビジネスニーズを確かめるもので、この場面は機械がプロトコルの操作と結果の JSON ポインタを比べる。テストレベルとしてはシステムテスト（SQL の14場面はアダプター単体のテスト）に当たる。よって、利用者の「UAT を基盤で作り込むものではない」は正しく、直すのは名前（acceptance ・ 受け入れの試験）であって、場面を持つこと自体ではない

  3. 3. 実装で必要か

    必要。理由は2つ。前提 164 が「どのインターフェースとどの言語の実装も同じ試験を通す」と決めており、その試験の実体がこの JSON である。また、判断基準はテストファーストで作ったテストケースを自動テストとして維持し、リファクタリングのときのコード品質の確保に使うとしている。Rust のテストへ書き直す案は前提 164 を破るので採らない

  4. 4. coverage.json と traces は持ち込むか

    traces は持ち込む。判断基準は、トレーサビリティをテストプロセスの全期間で確立し維持し、変更の影響の判断に使うとしており、1場面に1行の id で済む。coverage.json は持ち込まない。中身が参照の実装の段の進み具合（確かめない65行の move_when）で、核の段のテスト完了の記録としてボードに残す。Rust の実装で対応表を回すかは、model.json を実装へ移すか（未判定）が決まってから、終了基準として決め直す

  5. 5. どこに、何という名前で置くか

    Cargo の慣習で決まるのは「統合テストは tests ディレクトリ」と「main.rs だけの binary crate は tests/ から use できない」まで。データの JSON の置き場所を Cargo は決めない。よって、(a) 56場面は複数の crate とほかの言語の実装が読むので、ワークスペースの根に置く。名前は、判断基準のテスト実装の作業成果物の語「テストスイート」から test-suite/ とする（推測：名前は判断基準も Cargo も決めていない。behaviors/ より中身が伝わる語として選んだ）。(b) 回す側は crates/inbound/cli/tests/ の統合テストにし、CARGO_BIN_EXE_<name> でバイナリを起動して標準入出力で回す。ファイル名は acceptance.rs をやめ、test_suite.rs などにする（推測）。(c) SQL の14場面は crates/outbound/sqlite/tests/ に移す（SQLite のアダプターだけが持つ約束なので、共通の test-suite/ に入れない）

具体例

  • S-REC-1「AI が Markdown とコードを直し、意図だけを渡して記録する」：when は record_change、then は /result/change/purpose_ref が ACDR 0197 であること。どのインターフェースでも同じ結果を期待するので test-suite/ へ移す
  • S-DB-1「オーケストレーターの入れ子を断る」：when は INSERT INTO sessions … の SQL を直に流す。SQLite の DDL の約束なので crates/outbound/sqlite/tests/ へ移す
  • S-ST-bad-2「argv のシェルの記号を断る」：Abstract に照らして ACDR の Concrete を検証し valid が false であること。検証器の振る舞いなのでインターフェースに依らず、test-suite/ へ移す

注意

アンチパターンリスク代替案
受け入れテストでないものを受け入れテストと呼ぶ（acceptance.rs ・ 受け入れの試験）利用者が感じたとおり、基盤が UAT を作り込んでいるように読める。テストレベルごとの目的が混ざり、本当に想定ユーザーが行う受け入れ（Concrete の作者が基盤を使って確かめること）を別に置く余地が見えなくなるシステムテストとして名前を付け直す（test-suite/ ・ test_suite.rs）。受け入れテストは、想定ユーザーが行うものとして別に扱う
テスト用の差し替えを CLI のバイナリに入れる（Test Logic in Production）場面の given.judge ・ given.ai は模擬の判定と模擬の AI ツールを前提にしている。CLI を起動して回すために、本番のバイナリへ模擬へ切り替える引数や設定を足すと、テストと本番で違う動きをするシステムになる（推測）模擬はバイナリの外からポートの正規の経路で渡す。例えば判定は、x-delegates の argv を持つ judging として、固定の答えを返す試験用のプログラムを指す。経路が無いものは、場面の側を直すか、その場面を application の crate の tests/ で回す
生成元の build.py と生成物の JSON を両方の正本にするPython の関数（GIVEN ・ REC）を直すと JSON がずれ、JSON を直すと次の生成で上書きされる。実装のリポジトリに Python の依存も入る持ち込む時点で JSON を正本にし、build.py はボードに残して以後は使わない
すべての場面が同じ given（GIVEN の FILES ・ 2つのセッション ・ 3つの ULID）を使う（General Fixture）どの値が期待結果を左右するのかが場面から読み取りにくく、Tests as Documentation にならない（推測）持ち込んだ後に、場面ごとに使わない given の欄を削る。今回の判定の条件にはしない
