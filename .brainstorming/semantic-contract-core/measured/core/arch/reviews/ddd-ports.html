結論

条件付きで採る

混在にする。ドメインサービスが計算の途中で、自分の計算の結果を引数にして呼ぶ3つの読む口（契約を読む ・ インスタンスを読む ・ 判定の記録を読む）だけを domain に置き、残り9つと3つの書く口は application に置く。

trait は呼ぶ側から見える crate に置かなければならず、Rust の依存は application → domain の1方向なので、domain が呼ぶものだけが domain に要る。判断基準の業務サービスの例も Cockburn の Discounter も、計算の途中でリポジトリを呼んでおり、そうでないもの（取りに行く ・ AI に聞く ・ 書く ・ 確定する）は application が前後で呼べば、ドメインサービスは値だけを受け取る関数になり、同じ入力から同じ結果（Q0 #14）を守れる。

判断の道筋

  1. ドメインサービスとは何か（Evans の原文）

    Evans p.14 Services：「When a significant process or transformation in the domain is not a natural responsibility of an entity or value object, add an operation to the model as a standalone interface declared as a service.」「State these assertions in the ubiquitous language of a specific bounded context. Give the service a name, which also becomes part of the ubiquitous language.」。判断基準では「業務ロジックだけを書き、自分の状態は持たないステートレスなオブジェクト」で、「いろいろなコンポーネントの呼び出しをまとめて何かの計算や分析をする」

  2. ポートの trait をどこに置くかを、何で決めるか

    呼ぶ側で決める。Rust の crate は依存する先の項目しか使えず、許す辺は application → domain なので、ドメインサービスが呼ぶ trait は domain（呼ぶ crate か、その crate が依存する crate）に要る。問いは1つ ──「ドメインサービスが、自分の計算の途中で得た値を引数にして呼ぶ必要があるか」。はいなら domain、いいえなら application が前後で呼び、ドメインサービスには値で渡す

  3. 判断基準の例は、ドメインサービスが計算の途中でポートを呼ぶことを認めるか

    認める。業務サービスの例は、部門の方針を取り出し、その方針の最大応答時間を範囲にして勤務予定を取り出す。2回目の呼び出しの引数が1回目の結果で決まる。Cockburn の Discounter も「double rate = rateRepository.getRate( amount ); return amount * rate;」（1923〜1926行）と、計算の途中で RateRepository を呼ぶ

  4. ポート12それぞれは、誰が呼ぶ必要があるか

    下の「コードの例」の表に12行で示す。domain が呼ぶ必要があるのは、契約を読む ・ インスタンスを読む ・ 判定の記録を読むの読む側だけで、残り9つと3つの書く側は application が前後で呼べば足りる

  5. 判断基準の「ポートは業務ロジック層が定義する」と、Cockburn の「application の境界にポート」は食い違うか

    食い違わない。Cockburn の application は内側の六角形の全体である ──「the use cases should generally be written at the application boundary (the inner hexagon)」（2025〜2026行）・「there is an application on the inside communicating over some number of ports with things on the outside」（1498〜1500行）。判断基準のアプリケーション層は、その内側の中の業務ロジック層のファサードである。どちらも「内側が定義し、外側（アダプター）が実装する」ことを言い、内側の中のどの crate に置くかは決めていない。Cockburn の例も RateRepository を package repository に置き、Discounter が import する（1910行）だけである

  6. application に置くことは、判断基準に違反しないか

    判断基準の文面（ポートは業務ロジック層が定義する）は、application だけが呼ぶポートについて触れていないので、ここは判断基準の範囲外である。判断基準の DIP（上位のモジュールを下位のモジュールに依存させない）は、アダプターが application と domain に依存する向きである限り守られる。Evans の Layered Architecture（p.10）は「eliminate any dependency on infrastructure, user interface, or even application logic that is not business logic」と書く。AI に聞く ・ 取りに行く ・ 確定する順番は application logic なので、domain から外すほうが原文に沿う

  7. ドメインサービスは業務領域に属するのか、区切られた文脈に属するのか

    区切られた文脈に属する。Evans p.14 は service contract を「the ubiquitous language of a specific bounded context」で書けと言い、業務領域（subdomain）には触れない。業務領域は文脈の中を分ける単位で、Evans p.15 Modules は「Choose modules that tell the story of the system and contain a cohesive set of concepts.」、p.41 Generic Subdomains は「Identify cohesive subdomains that are not the motivation for your project. Factor out generic models of these subdomains and place them in separate modules.」と書く。ドメインサービスを業務領域のモジュールに置くのは、文脈の中の置き場所の決定である

  8. いまの「業務領域ごとに crate」は適切か

    適切である。基盤は1つの区切られた文脈（Q9 #11）で、判断基準は「内部には業務領域ごとの論理的な境界（名前空間 ・ モジュール ・ パッケージ）が存在する」とする。crate はその論理的な境界をビルドで守る手段で、文脈を分けていない。ただし、一般の業務領域2つ（AI と外のツールによる判定 ・ 保存と版の管理）は domain の crate を持たず、ポートとアダプターだけで表れる。model.json はポートごとに業務領域を付けているので、ポートを中核の crate の ports.rs に置くと、一般の業務領域の口が中核の crate の中に入る。application に移すと、この混ざりも消える

根拠

判定の拠りどころにした判断基準の記述

判断基準引用
domain-service業務サービス（英語は Services）：業務ロジックだけを書き、自分の状態は持たないステートレスなオブジェクト。集約や値オブジェクトの中では不自然になる業務ロジックの置き場所で、ほとんどの場合、いろいろなコンポーネントの呼び出しをまとめて何かの計算や分析をする。
domain-service処理の流れは、担当者の部門の方針を取り出す → 優先度に応じた最大の対応時間を得る → エスカレートしていれば方針の係数を掛ける → 方針の最大応答時間の範囲で担当者の今後の勤務予定を取り出す → 対応時間と勤務予定から目標時刻を計算する、である。
ports-and-adaptersポート：業務ロジック層が定義する抽象的なインターフェースで、インフラストラクチャ層が実装する。業務ロジック層は、基盤のコンポーネントを直接には参照せず、ポートを介して連係する。
ports-and-adapters依存関係逆転の原則（DIP）：業務ロジックを実装する上位のモジュールを、下位のモジュールに依存させないとする原則。従来のレイヤードアーキテクチャでは、業務ロジック層がインフラストラクチャ層に依存しており、この原則に反する。
ports-and-adaptersポート（インターフェース）は業務ロジック層に、アダプター（実装）はインフラストラクチャ層に属する。
layered-architectureサービス層：プレゼンテーション層と業務ロジック層を仲介する追加の層。ファウラーは、アプリケーションの境界を定め、使える操作と各操作の応答をまとめる層とする。下位の層の振る舞いをカプセル化する。別の呼び方はアプリケーション層である。
aggregate対応：1つのトランザクションで変更する集約は1つにし、複数の集約の状態は集約ごとに別々にコミットする ・ 理由：一貫性を維持する境界の定義が、正しいことを保証する
subdomain業務領域は事業方針から決まり、発見するものである。区切られた文脈はソフトウェア技術者が設計するものである。両者を一対一に限定しない
bounded-context物理的な境界は1つだが、内部には業務領域ごとの論理的な境界（名前空間 ・ モジュール ・ パッケージ）が存在する

注意

アンチパターンリスク代替案
ドメインサービスの中で AI ・ 外のツール ・ 公開された言葉の取得を呼ぶ（いまの validation/ports.rs の形）検証の途中で外へ取りに行くことを型で止められず、Q4 #9 に違反できる。ドメインサービスの結果が AI の答えの揺れで変わり、domain の試験で同じ入力から同じ結果を確かめられない（推測）Validator を「依頼の一覧を返す」と「答えをまとめる」の2つの関数に分け、AI と外のツールは application が間で呼ぶ。公開された言葉は application が閉じた一覧で先に取り、値で渡す
ドメインサービスが値だけで決まると書きながら、その crate にポートを置く（session の crate）4節の依存の表と5節のディレクトリが別のことを言い、どちらが正しいかを毎回確かめることになる。トランザクションの中で読む ・ 決める ・ 書くを、domain と application のどちらが囲むかが決まらない（推測）session の crate からポートを外し、application の use_cases/session.rs がトランザクションを取り、索引 ・ AI ツール ・ 設定を呼んで値を渡す
読む口を domain に置くとき、書く口も一緒に domain に置くドメインサービスから書けるようになり、1回に変える集約は1つという決まりを application の外で破れる（推測）Rust の trait を読む口と書く口に分け、domain には読む口だけを置く。書く口は application に置く

違反しやすい点検査する方法
AI が domain の crate の Cargo.toml や ports.rs に、AI ・ 外のツール ・ 取りに行く ・ セッションのポートを足し直すcrates/domain/*/src/ports.rs に定義された trait の名前を architecture.json の「domain に置いてよい読む口」の一覧と突き合わせ、一覧に無い trait が0件であることを CI で確かめる
