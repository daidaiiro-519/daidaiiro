ux-advisor の回答 ・ 設計相談

Semantic Agent Schema が同梱する既定のビュー3つ（session ・ change-summary ・ judgment）の体験と完成イメージ（ワイヤーフレームとデザインシステム）をどう組み立てるか

前置き

判定の前に確定させた前提と、その出所

前提内容出所
作るもの基盤の Renderer が出す静的な HTML。サーバーを持たず、ファイルを開くか PR に添えて読む。明暗の両方に対応する相談者
見る人作業者（AI と作業し、手元の DB を持つ人）・ PR を見る人 ・ あとから経緯をたどる人の3者。調査で確かめた像ではなく、相談者から聞いた像である（未判定）相談者
既定のビューの位置文脈が同じ対象向けのビュー（ACDR のような形）を持てばそちらで描く。既定のビューは、何も用意していないときの最低限相談者
既にある見た目の決まりbrainstorming の catalog の light.tokens.json（Design Tokens の形式）。基礎の色はここから取る相談者
操作の範囲静的な HTML なので、承認 ・ 取り直し ・ 戻すは画面の中で実行できない。次にすることは、実行するコマンドと、移る先のリンクで示す相談者の前提から導いた制約
比べる相手利用者がふだん使う PR の画面（チェックの結果の一覧と、ファイルごとの差分）に寄せる、という見立ては調べていない仮定である判断基準の範囲外（比べる相手そのものは判断基準が決めない）

結論

採る

3つのビューを、どれも「答えの帯 → 次にすることの帯 → 要対応の項目 → 畳んだ残り」の同じ並びにし、例外 ・ 判定 ・ インスタンスをリンクでつなぎ、状態を記号と語と色の3つで示す。

画面に載せる内容の優先順位を見る人の主な目的を支える順に決め（aesthetic-and-minimalist-design）、状態をはっきり伝えて次にすることを判断できるようにし（visibility-of-system-status）、色だけで伝えない（distinguishable の 1.4.1）ためである。いまの試作はデータの並びが先に来るので、問いへの答えと次の行動が後ろに埋もれている。

比較した案

案何が起きるか採否
案 A：件数のタイルを並べるダッシュボード型全体の量はすぐ分かるが、どの変更のどの欄かを読むには一覧へ移る必要がある。1件だけの例外が件数の中に埋もれる採らない
案 B：上から読む文書型（いまの試作）PR に添えて読む形には合うが、データの並びが先に来て、答えと次の行動が後ろに埋もれる採らない
案 C：文書型の先頭に、答えの帯 ・ 次にすることの帯 ・ 要対応の項目を置き、残りを畳むPR に添えて上から読める形を保ったまま、1画面目で問いに答え、次の行動へ移れる。静的な HTML の details で畳めるので、スクリプトが無くても読める採る

設計の手順

  1. 1. ゴールを決める ── 見る人ごとの問いと次の行動を1行にする

    ① session：作業者「コミットの前に、私が片付けることは何か」→ 承認する ・ 意図に無い変更を戻す ・ 開いたままの子のセッションを閉じる。② change-summary：PR を見る人「この変更は意図どおりか。意図に無い変更はあるか」→ 例外を確かめて承認する ・ 差し戻す。経緯をたどる人「この欄の値は、何の目的で、なぜ変わったか」→ 目的の記録（文脈のビュー）と前後のコミットへ移る。③ judgment：作業者「どの rule が violated ・ unverified で、何をすれば verified になるか」→ 直す ・ 取り直す。PR を見る人「機械でなく AI や人が判定した所はどこで、その根拠に納得できるか」→ 根拠を読んで承認する ・ 差し戻す

  2. 2. シナリオを書く（who ・ why ・ where ・ what ・ how）

    PR を見る人：レビューの依頼を受け（why）、PR の画面から添付のまとめを開き（where）、意図に無い変更が無いかを確かめ（what）、例外の一覧 → 判定の行 → 対象の差分の順にたどる（how）。作業者：AI との作業の区切りで（why）、手元で session を開き（where）、コミットできる状態かを知り（what）、次にすることの帯のコマンドを写して実行する（how）。経緯をたどる人：ある欄の値に疑問を持ち、まとめの意図のカードからその欄を探し、目的の記録へ移る

  3. 3. タスクフローを描く（利用者の手順とシステムの手順の両方）

    利用者：開く → 答えの帯を読む → 要対応を開く → 根拠へ移る → コマンドを実行するか承認する。システム（Renderer）：DB と Git から集める → 判定の結果で並べ替える（violated → unverified → 承認待ち → verified）→ 件数と答えの文を作る → 次にすることを1つ選ぶ → 0件の欄も「0件」と書く。分かれ目は「要対応が0件か」で、0件なら答えの帯は「片付けることは無い」と書き、次にすることの帯は次の工程（まとめを作る ・ 承認する）を示す

  4. 4. 案を広げて1つに絞る（比較した案の表）

    ダッシュボード型 ・ 文書型 ・ 文書型の先頭に答えを置く型の3つを比べ、案 C を採る。この案件だけの原則を4つ置き、以後の決定はこれで判定する ── (1) 答えを先に、データは後に：各頁の最初の帯が、見る人の問いに1文で答える。(2) 状態は記号 ・ 語 ・ 色の3つで示す。(3) 例外から根拠まで、リンクを2回たどれば着く（覚えて運ばせない）。(4) 何も無いことも書く：例外 0件 ・ 記録に無い書き換え 0件を省かない

  5. 5. 1画面目に出すものと畳むものを決める

    共通：頁の題（<h1> は1つで、ビューの名前と目的の名前）・ 現在地の行（目的 ＞ 対象）・ 答えの帯 ・ 次にすることの帯を1画面目に出す。① session：出す＝violated と承認待ちの変更（対象 ・ 欄 ・ 意図 ・ 判定の札）。畳む＝欄ごとの差分 ・ verified で承認済みの変更 ・ セッションの木 ・ tool と id ・ 単発の子の数。② change-summary：出す＝例外の一覧（0件でも出す）・ 意図のカード（意図 ・ 判定の札 ・ 対象 ・ 欄の名前）。畳む＝欄ごとの差分 ・ 判定の理由の全文 ・ コミットの id と描いた版。③ judgment：出す＝インスタンスの状態と rule ごとの件数 ・ violated と unverified の行（判定した値 ・ 理由 ・ 判定した者 ・ rule の版）。畳む＝verified の行（件数だけ見せる）・ rule の文（x-prompt）の全文 ・ 形（JSON Schema）の検査

  6. 6. 動線をリンクで決める

    まとめの例外の各行は、judgment の「インスタンス × rule」の行へのアンカー付きリンクと、対象の差分へのリンクを持つ（GOV.UK のエラーサマリーと同じく、1件ずつリンクし、文言を行き先と同じにする）。session の violated の変更も同じ行へリンクする。judgment の各行は、対象のインスタンス（文脈のビューがあればそちら、無ければ Git の差分）へリンクする。どの頁も現在地の行から1つ上へ戻れる。リンクの文は「判定を見る」「差分を見る」のように行き先を言い、「こちら」と書かない

  7. 7. ワイヤーフレームを描く（デザインシステムの欄の3枚）

    構造 ・ 配置 ・ 階層だけを示し、色とフォントは載せない。幅 358px で1列になる前提で、横に並べるのは札と件数だけにする。表（欄 ／ 変更前 ／ 変更後）は横スクロールを許す部分として扱う

  8. 8. デザインシステムを組む（スタイルタイル ・ トークン ・ 部品）

    基礎の色は既存の catalog から取り、意味の層（status ・ exception ・ diff ・ judge ・ next ・ focus ・ link）を alias で重ねる。部品は意味の層だけを参照する。色の組はすべて WCAG 2.2 の 1.4.3（文字 4.5:1）と 1.4.11（状態を見分ける枠 3:1）で計算した

  9. 9. 原則で点検し、残りを利用者で確かめる

    点検の表と、利用者で確かめることの表をデザインシステムの欄の最後に置く。原則で決まらないのは、札の語（verified のままか日本語か）・ 差分の色（PR の画面と同じ赤 ・ 緑に寄せるか）・ 経緯をたどる人の入口の3つである

デザインシステム

完成イメージとして渡すデザインシステム。見た目の方向（スタイルタイル）・トークン（Design Tokens Format Module の形式の JSON）・パターンの一覧（部品 ・ 振る舞い ・ 使う理由）を置く。新しく作るものの設計相談で置く

見た目の方向（スタイルタイル）：「静かな報告書」。地は白系統、文字は濃い墨。色を使うのは状態 ・ 例外 ・ 差分 ・ 次にすることの4か所だけにし、それ以外は線と余白で区切る。頁に強い色の面は1つ（次にすることの帯）だけ置く。id ・ 欄の経路 ・ 値 ・ コマンドは等幅の字で書き、文と見分ける。

部品振る舞い使う理由
答えの帯頁の題の直後に置き、見る人の問いへの答えを1文で書く。件数は記号付きで並べる（✓ 4 ・ ✕ 0 ・ ？ 1）主な目的を支える情報を最初に置く
次にすることの帯頁に1つ。行為を1文で書き、実行するコマンドを等幅の字で添え、コピーのボタンを置く（スクリプトが無いときはコマンドの文字だけ）。要対応が0件なら次の工程を書く静的な HTML では操作できないので、次の行動を見て分かる形で渡す
状態の札記号 ＋ 語（✓ verified ・ ✕ violated ・ ？ unverified）。地の色と 2px の枠。語は CLI の出力と同じ識別子にする色だけで伝えない。CLI と頁で同じ語にする
判定した者の札語（機械 ・ AI ・ 人）を枠だけの札で示す。色で分けない。AI と人の判定には根拠のリンクを必ず付ける誰が判定したかは、色の意味を増やさずに語で足りる
例外の一覧まとめの main の先頭に置く。見出し「例外（n件）」、0件なら「例外は無い」と書く。各行は判定の行と差分へ1件ずつリンクし、文言を行き先の判定の理由と同じにするGOV.UK のエラーサマリーと同じ型。見落としを防ぐ
意図のカード意図1件を1枚にし、意図の文 ・ 判定の札 ・ 判定した者（AI ・ 人）・ 対象 ・ 欄の名前を出す。差分と理由は details で畳む変更を意図の単位で読ませる
差分の表示欄（等幅）・ 変更前（−）・ 変更後（＋）の3列。無い値は「（無い）」と書き、空欄にしない。ファイルの差分は Git の行の差分で出す。狭い幅では表を横スクロールにする変更前と変更後を列の題と記号で見分けられる
判定の行rule の名前と版 ・ 判定した値 ・ 結果の札 ・ 判定した者の札 ・ 根拠。各行に「インスタンス × rule」のアンカーを持たせるまとめと session から1行へ直接移れる
セッションの木入れ子の一覧（ul）。子ごとに役割 ・ 引き継ぐか ・ open/closed ・ 最後に使った時刻。open を先に並べる親子の関係を構造で示し、読み上げでも分かる
現在地の行目的 ＞ 対象 ＞ 頁。各段はリンク。<title> は「頁の題 - 目的の名前」どこにいるかを示し、1つ上へ戻れるようにする
畳みdetails と summary。summary に件数を書く（「verified（4件）」）。開いた状態は印刷とページ内検索でも読めるスクリプト無しで動き、余分な情報を後ろへ回せる

注意

アンチパターンリスク代替案
データの並びを頁の先頭に置く（いまの試作）余分な情報の1つ1つが、本当に必要な情報と競い合い、例外や violated が相対的に目立たなくなる答えの帯 ・ 次にすることの帯 ・ 要対応の項目を先頭に置き、id ・ tool ・ verified の行を畳む
状態を色だけで示す（緑 ・ 赤 ・ 黄の塗りだけ）色を見分けにくい人と、白黒で印刷した人に状態が伝わらない（1.4.1）札を記号 ＋ 語 ＋ 色にし、件数にも記号を付ける
（推測）差分の色に、状態と同じ緑 ・ 赤を使う「変更後（緑）」と「verified（緑）」、「変更前（赤）」と「violated（赤）」が同じ意味に見え、internal consistency が崩れる差分は砂色 ・ 青緑の別の色相にし、列の題と − ・ ＋ を添える。PR の画面の赤 ・ 緑に寄せるかは利用者で確かめる
（推測）0件の欄を省く「例外が無い」のか「例外を調べていない」のかを、読む人が区別できない例外 ・ 突き合わせは0件でも欄を出し、「例外は無い」と書く

次にすること

  • 既存の試作（default-views/index.html）を、3枚のワイヤーフレームの並びで組み直す。
  • トークンを、明るい地と暗い地の2つの tokens.json として書き起こす。
  • 幅 358px ・ 明 ・ 暗の3通りで描画し、目視で確かめる。
  • 比べる相手として、利用者がふだん使う PR の画面を2〜3つ選び、同じ観点で評価する。
  • 札の語と差分の色について、PR を見る人3〜5人に考えを声に出す形のテストを行う。
  • 4つの原則をボードに置き、以後の決定を原則で判定する。

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
Renderer を実装するとき、部品の CSS に基礎の色（#a3262a など）を直接書き、意味のトークンを経由しない部品の CSS を検索し、color.base の値（16進の色）が意味の層の定義の外に出てこないことを、ビルドの検査で確かめる
状態の札を、記号か語を落として色だけで描く描画した HTML の状態の札の要素すべてについて、テキストに ✓ ・ ✕ ・ ？ のいずれかと verified ・ violated ・ unverified のいずれかが入っていることを検査する
例外の一覧のリンクの文と、行き先の判定の理由の文がずれる例外の各行のリンク先のアンカーが judgment の頁に在り、両方の理由の文字列が一致することを検査する
0件の例外 ・ 突き合わせの欄を出し忘れる例外 0件のまとめを入力にした描画の試験で、「例外は無い」の文が出ることを確かめる
暗い地で、明るい地と別のトークンの名前を使う明暗の2つのトークンのファイルで、名前の集合が一致することを検査し、各組のコントラスト比を計算して 4.5:1 ・ 3:1 を下回れば失敗にする
