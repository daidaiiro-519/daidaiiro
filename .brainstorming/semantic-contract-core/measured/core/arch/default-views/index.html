既定のビューのデザインシステムと完成イメージ

3つのビューは、どれも「答えの帯 → 次にすることの帯 → 要対応 → 畳んだ残り」の順で、見る人の問いに最初の画面で答え、次の行動をコマンドで渡す。状態は記号 ・ 語 ・ 色の3つで示し、例外 ・ 判定 ・ まとめはリンクで行き来する

1　見る人 ・ 問い ・ 次の行動

見る人この頁で答えを得たい問い次にする行動最初に開くビュー
作業者コミットの前に、私が片付けることは何か承認する ・ 意図に無い変更を戻す ・ 子のセッションを閉じる① session
作業者どの rule が violated ・ unverified で、何をすれば verified になるか直す ・ 取り直す③ judgment（session から）
PR を見る人この変更は意図どおりか。意図に無い変更はあるか例外を確かめて承認する ・ 差し戻す② change-summary
PR を見る人AI や人が判定した所はどこで、根拠に納得できるか根拠を読んで承認する ・ 差し戻す③ judgment（まとめの例外から）
経緯をたどる人この欄の値は、何の目的で、なぜ変わったか目的の記録と前後のコミットへ移る② change-summary（Git の履歴から）

2　動線

入口は2つ：PR からは変更のまとめ、作業者の CLI からはセッション。静的な HTML なので、操作は「次にすることの帯」のコマンドで渡す

部品振る舞い使う理由
答えの帯頁の題の直後に置き、見る人の問いへの答えを1文で書く。件数は記号付きで並べる（✓ 4 ・ ✕ 0 ・ ？ 1）主な目的を支える情報を最初に置く
次にすることの帯頁に1つ。行為を1文で書き、実行するコマンドを等幅の字で添え、コピーのボタンを置く（スクリプトが無いときはコマンドの文字だけ）。要対応が0件なら次の工程を書く静的な HTML では操作できないので、次の行動を見て分かる形で渡す
状態のバッジ記号 ＋ 語（✓ verified ・ ✕ violated ・ ？ unverified）。地の色と 2px の枠。語は CLI の出力と同じ識別子にする色だけで伝えない。CLI と頁で同じ語にする
判定した者のバッジ語（機械 ・ AI ・ 人）を枠だけのバッジで示す。色で分けない。AI と人の判定には根拠のリンクを必ず付ける誰が判定したかは、色の意味を増やさずに語で足りる
例外の一覧まとめの main の先頭に置く。見出し「例外（n件）」、0件なら「例外は無い」と書く。各行は判定の行と差分へ1件ずつリンクし、文言を行き先の判定の理由と同じにするGOV.UK のエラーサマリーと同じ型。見落としを防ぐ
意図のカード意図1件を1枚にし、意図の文 ・ 判定のバッジ ・ 判定した者（AI ・ 人）・ 対象 ・ 欄の名前を出す。差分と理由は details で畳む変更を意図の単位で読ませる
差分の表示欄（等幅）・ 変更前（−）・ 変更後（＋）の3列。無い値は「（無い）」と書き、空欄にしない。ファイルの差分は Git の行の差分で出す。狭い幅では表を横スクロールにする変更前と変更後を列の題と記号で区別できる
判定の行rule の名前と版 ・ 判定した値 ・ 結果のバッジ ・ 判定した者のバッジ ・ 根拠。各行に「インスタンス × rule」のアンカーを持たせるまとめと session から1行へ直接移れる
セッションの木入れ子の一覧（ul）。子ごとに役割 ・ 引き継ぐか ・ open/closed ・ 最後に使った時刻。open を先に並べる親子の関係を構造で示し、読み上げでも分かる
現在地の行目的 ＞ 対象 ＞ 頁。各段はリンク。<title> は「頁の題 - 目的の名前」どこにいるかを示し、1つ上へ戻れるようにする
畳みdetails と summary。summary に件数を書く（「verified（4件）」）。開いた状態は印刷とページ内検索でも読めるスクリプト無しで動き、余分な情報を後ろへ回せる

6　原則での点検

原則点検した項目結果
Nielsen：Visibility of System Status各頁の状態（片付けることの件数 ・ インスタンスの状態）が1画面目にあるか答えの帯で満たす
Nielsen：Recognition Rather than Recall例外の内容を覚えて別の頁へ運ばせていないか例外の行から判定の行へ直接リンクし、判定の行にも対象と欄を書き直す
Nielsen：Aesthetic and Minimalist Designまれにしか使わない情報（id ・ tool ・ 描いた版）が1画面目にあるか畳みへ移した
Nielsen：Consistency and Standards3つの頁で、同じ部品が同じ位置 ・ 同じ語か同じ並びと同じバッジにした。CLI の語とも合わせた
Nielsen：Help Users Recognize, Diagnose, and Recover from Errorsviolated の行が、何が問題で、どう直すかを言っているか理由の文と次にすることの帯（コマンド）で満たす
WCAG 1.4.1 ・ 1.3.3状態 ・ 例外 ・ 差分を色だけで伝えていないか記号 ・ 語 ・ 列の題を必ず添える
WCAG 1.4.3 ・ 1.4.11文字 4.5:1 ・ 状態の枠 3:1明暗とも満たす（トークンの表）
WCAG 1.4.10幅 320px 相当で横スクロールが出ないか1列に落とす。差分の表だけはデータテーブルとして横スクロールを許す
WCAG 1.3.1 ・ 2.4.6見出し ・ 一覧 ・ 表を構造で書いているかh1 は1つ、帯と節は h2、木は ul、差分は table
WCAG 2.4.2 ・ 2.4.8 ・ 2.4.7頁の題 ・ 現在地 ・ フォーカスの輪現在地の行と color.focus の 2px の輪
GOV.UK：Writing for user interfaces答えの帯 ・ 次にすることの帯が短い1文か。リンクの文が行き先を言うか「判定を見る」「差分を見る」と書き、「こちら」を使わない。「緑のバッジ」のような色での指示を書かない

7　利用者で確かめること

原則で決まらないこと誰に確かめ方
バッジの語を識別子（verified など）のままにするか、日本語の語にするかPR を見る人（CLI を使わない人を含む）ワイヤーフレームの2案を見せ、バッジだけを見て意味を言ってもらう（考えを声に出す形のテスト）
差分の色を、PR の画面と同じ赤 ・ 緑に寄せるか、状態の色と分けた砂色 ・ 青緑にするかPR を日常的に見る人同じまとめを2つの配色で見せ、例外の見落としと読む時間を比べる
経緯をたどる人が、Git の履歴からまとめに着けるかあとから経緯をたどる人「この欄はなぜこの値か」を課題にして、入口から目的の記録まで着けるかを観察する
答えの帯の1文で、承認してよいかを決められるかPR を見る人答えの帯だけを見せて判断を聞き、そのあと全体を見せて判断が変わるかを見る
