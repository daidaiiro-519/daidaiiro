実装計画

Semantic Agent Schema の基盤を、目的ごとの段で作る。各段は1つの目的のセッションで、題材の Concrete（ACDR）を使った受け入れ（利用者が実際に動かす）とシステムテストで終える。ACDR で全段を通したあと、2つ目の題材（Brainstorming のボード）で入れ子と規模を確かめる

1　題材の Concrete

ACDR（最初の題材）Brainstorming のボード（2つ目）
実物記録 178件（古い版の記録を含む）。スキーマは20の欄で、配列の入れ子は2段まで。x-prompt は0件ボード5枚。スキーマは入れ子（定義7）。x-prompt 110件
試せることConcrete を一から書く（U1 ・ U23）・ 欄の書き換えと検証 ・ AI の rule（理由が決定を説明しているか）・ superseded と置き換えの参照 ・ 実データの取り込みと探す（U17 ・ U28）入れ子と配列の深い欄 ・ 多い x-prompt ・ 回と回答の参照 ・ 規模
なぜこの順形が軽く、宣言 → インスタンス → 記録の順を最初から最後まで通せる。x-prompt が0件なので、Concrete を一から書くことになる。実データがある毎日使っていて使い勝手の試験としての価値は高いが、形が重い（入れ子 ・ x-prompt 110件 ・ serve）。ACDR で土台が動いてから確かめる
置き場所test-suite/fixtures/acdr/。題材は例であって基盤の中身ではないので、crates/ に題材の語を入れない（grep で検査）test-suite/fixtures/brainstorming/

2　段の並び

段0 検査の土台を作る → 段1 意味を宣言する：Abstract と Concrete → 段2 インスタンスを書いて検証する（機械の rule） → 段3a 変更を記録する（手元の DB） → 段3b まとめをコミットし、ほかの変更を取り込む → 段4 AI と外のツールに rule を判定させる → 段5 AI が手順に従って書く：セマンティックのコマンドと MCP → 段6 既存のファイルを取り込み、探す → 段7a 置き換えて残す → 段7b 版を出す ・ 移す ・ 公開された言葉 → 段8 人が読む：描画と既定のビュー → 段9 目的ごとのセッション → 段10 通しの受け入れ → 段11 2つ目の題材：Brainstorming のボード

依存の順：宣言（段1）→ インスタンス（段2）→ 記録（段3a）→ まとめ（段3b）→ AI の判定（段4）→ セマンティックと MCP（段5）。段6 〜 9 は段5 のあと、互いに独立（7b は 7a のあと）。段10 は全段のあと、段11 は最後。Abstract の13ファイルとポート13は、どれも作る段が1つ決まっている

4　どの段にも共通の進め方

ことどうするか
1段 ＝ 1つの目的段ごとに目的のセッションを立てる。段の中で決めることがあれば、その段の ACDR に変更前と変更後を出してから実装する
試験から書くdomain の値と集約は単体テスト（決定表 ・ 状態遷移）から書く。段の受け入れの流れを test-suite の場面にして、先に落ちることを確かめる
終わりの条件CODING.md の8段の検査が0件で通る ・ untested.json の行が減っている ・ 利用者が ACDR での受け入れを動かして確かめた
受け入れ（UAT）段の終わりに、利用者が実際に CLI（段10 からは MCP も）で題材を動かす。手順と期待はこの頁の表のとおり
AI の扱いシステムテストでは代役の AI を使い、本物の AI ツールは呼ばない。本物は受け入れのときだけ使う
