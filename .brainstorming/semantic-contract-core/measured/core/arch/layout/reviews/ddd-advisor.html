Rust のワークスペース semantic-agent-schema/ で、承認済みのドメインモデル（model.json：集約9 ・ ドメインサービス4 ・ ファクトリ3 ・ 値オブジェクト32 ・ 不変条件46 ・ ポート）を、domain の8つの crate と application の中のモジュールとファイルへどう置くか。①型の種類で分けるか集約ごとに分けるか ②2つ以上の crate で使う値オブジェクトの置き場所 ③application の使う場面とポートのファイルの分け方 ④英語の型名の決め方と対応表の置き場所 ⑤置き方の誤りを機械で検査する方法

結論

採る

domain の crate の中は型の種類ではなく集約ごとのモジュールで分け、値オブジェクトはその語を持つ業務領域の crate に置いて共有の crate を作らず、application は model.json のポートの行と1対1のファイルにし、英語名は model.json に1か所だけ持たせて、コードとの食い違いを architecture-lint ・ clippy ・ model.json を読む試験の3つで止める。

判断基準は、集約の状態を集約内部の業務ロジックだけが変えられること、エンティティを集約の実装の一部にすること、妥当性の検証を値オブジェクト自身に持たせることを求める。Rust ではこれをモジュールの可視性で強制できるので、モジュールの境目を集約の境目に合わせると、コンパイラがそのまま検査になる。

C：2つ以上の crate で使う値オブジェクトを、共有の crate（common など）に集める検証結果 ・ 状態 ・ 出どころ ・ procedure の持ち主の業務領域が消え、それを使う規則が共有の crate と持ち主の crate に分かれる。共有の crate はどの crate からも依存されるので、変更のたびに8つ全部が作り直しになる採らない
D：値オブジェクトを、その語の規則を持つ業務領域の crate に置き、使う側はいまの辺で依存する。辺の無い組だけを個別に解く32のうち30はいまの辺のまま置ける。残る2つ（目的の参照 ・ 手元のセッションの索引）と、出どころを validate が確かめる1件だけを、辺を1本足すか application に置くかで解く採る

設計の手順

  1. domain の各 crate の src を、集約1つにモジュール1つで組む

    集約がエンティティか専用の値オブジェクトを持つならフォルダ（例：declaration/src/concrete_schema/mod.rs ・ rule.rs ・ delegate.rs ・ template.rs）、持たないなら1ファイル（例：declaration/src/glossary.rs）。ルートの構造体は pub、欄は private、読むのは pub fn、状態を変えるのはコマンドの pub fn だけ。エンティティ（rule ・ 任せる先）の欄も private にし、変えるのはルートのコマンドから。aggregates/ ・ factories/ ・ services/ のフォルダは作らない

  2. ファクトリを、作る型のモジュールの中に置く

    Concrete の雛形 → declaration/src/concrete_schema/template.rs、インスタンス（作る ・ 取り込む）→ instance/src/instance/factory.rs（または instance.rs の関連関数）、変更のまとめ → change/src/summary/ の中。private の欄を組めるのは同じモジュールだけなので、ファクトリが集約のコマンドを迂回する道を作らない

  3. 値オブジェクトの置き場所を、使う範囲で決める

    1つの集約の中だけで使うなら、その集約のモジュールの中。集約の外（同じ crate のほかの集約 ・ ドメインサービス ・ ほかの crate ・ application）から型の名前で使うなら、crate の直下に1型1ファイル。どちらも欄は private で、作る関数が妥当性を検証する

  4. ドメインサービスを、1つ1ファイルで crate の直下に置く

    resolver/src/resolver.rs（Semantic Schema Resolver）・ validation/src/validator.rs（Semantic Schema Validator）・ render/src/renderer.rs（Semantic Schema Renderer）・ session/src/selector.rs（Session Selector）。状態を持たない構造体か自由関数にし、集約を変えるコマンドを呼ばない（値を読んで値を返すだけ）

  5. 値オブジェクト32を、その語の規則を持つ crate に割り当てる

    割り当ては下の「コードの例」の表。いまの辺で置けないのは3件：①目的の参照（session と change の両方が持ち、2つの間に辺が無い）→ declaration に置き、session → declaration の辺を1本足す ②手元のセッションの索引（セッション ID と変更の記録の id の組）→ domain のどの crate にも置けないので application/ports/sessions.rs の型にする ③出どころを validate が評価し直す → validation から search への辺は足さず、application の validate の使う場面が search の関数で評価し直し、結果を値で Validator に渡す

  6. ほかの集約は ID の値オブジェクトで指す

    変更の記録 ・ 判定の記録はインスタンスを、declaration の「対象」（id と kind、またはパス）で指す。change は instance の crate に依存しない（4節の辺のまま）。インスタンスの id の型は declaration の対象の中に置き、instance はそれを使う

  7. 不変条件を、それを守る関数に I 番号で結びつける

    守るのが集約のコマンドなら集約のモジュール、値の制約なら値オブジェクトの作る関数、集約をまたぐ計算ならドメインサービス、手元の DB の一意 ・ トリガー（I46 など）なら outbound/sqlite、入口の受け付け（I38 など）なら application。守る関数の doc コメントに「不変条件 I44」を書き、単体試験の名前を i44_… で始める。46行の置き場所の表は別に作らず、コードの印を正本にして試験で数える

  8. application を model.json のポートの行と1対1のファイルにする

    use_cases/ は ports.inbound の12行に1ファイルずつ（意味を宣言する ・ インスタンスを書く ・ 検証する ・ 判定する ・ 探して取り出す ・ 描画する ・ 版を出す ・ 経緯 ・ セッション ・ 変更を記録する ・ まとめを作る ・ セマンティックの手順を返す）。1つの関数は、読む → 集約1つのコマンドかドメインサービス → 書く、で終え、2つの集約を1回で書かない。ports/ は ports.outbound の13行に1ファイルずつ trait を1つ。ポートの引数と戻り値に出る domain の型は application が pub use し、outbound は application だけに依存したまま使う

  9. 英語の型名を model.json に足し、それを唯一の対応表にする

    changes.py に行を足して、aggregates ・ entities ・ value_objects ・ domain_services ・ ファクトリ ・ ports の各項目に en（型名 ・ モジュール名 ・ crate 名）を持たせる。決まっている英語名（Semantic Schema Resolver など）はそのまま使う。型の doc コメントの1行目に model.json の日本語名を書く。CODING.md には対応表を写さず、model.json の場所だけを書く

  10. 置き方の誤りを3つの道具で止める

    ①architecture-lint check --rules architecture.json --cargo .：crate の辺（session → declaration を足すならここにも足す）②clippy：domain の crate で入出力 ・ 時刻 ・ 乱数を禁じる（4節のまま）③model.json を読む試験（xtask の検査。製品の crate には入れない）：en の型が割り当てた crate に pub で1回だけ定義されている ・ 集約とエンティティの構造体に pub の欄が0件 ・ I1〜I46 の印がどれも1回以上あり、model.json に無い I 番号が0件 ・ use_cases/ と ports/ のファイルの数と名前が ports の行と一致

根拠

判定の拠りどころにした判断基準の記述

判断基準引用
aggregate対応：集約の状態は集約内部の業務ロジックだけが変更できるようにし、外部には参照だけを許可する ・ 理由：関連する業務ロジックを、すべて集約自身の1か所に実装できる
aggregate構成するもの：集約のルート ・ 役割：外部に公開するインターフェース役のエンティティ。1つにする。内部のエンティティの状態は、ルートを経由してだけ変更できる
entity対応：エンティティを単独で実装せず、集約の実装の一部にする
value-object対応：妥当性を検証するロジックを、値オブジェクト自身に持たせる ・ 理由：値を設定するたびに、使う側で妥当性を検証する必要がなくなる
value-object対応：状態区分やパスワードなど、対象領域に固有の概念を値オブジェクトで表す ・ 理由：同一性を値の比較で判定でき、明示的な ID フィールドを必要としない
aggregate対応：他の集約は、オブジェクトそのものではなく ID で参照する ・ 理由：境界の外側であることを明確に表現し、集約ごとに固有のトランザクション境界を持たせる
aggregate対応：1つのトランザクションで変更する集約は1つにし、複数の集約の状態は集約ごとに別々にコミットする ・ 理由：一貫性を維持する境界の定義が、正しいことを保証する
domain-service業務サービス（英語は Services）：業務ロジックだけを書き、自分の状態は持たないステートレスなオブジェクト。集約や値オブジェクトの中では不自然になる業務ロジックの置き場所で、ほとんどの場合、いろいろなコンポーネントの呼び出しをまとめて何かの計算や分析をする。
bounded-context物理的な境界は1つだが、内部には業務領域ごとの論理的な境界（名前空間 ・ モジュール ・ パッケージ）が存在する
domain-model対応：データベースの操作や外部との通信といった技術的な関心事を、ドメインモデルから完全に分離する ・ 理由：業務ロジックは本質的に複雑なので、それ以上の不必要な複雑さを持ち込まない
ports-and-adaptersポートとアダプターの結びつけは、依存性注入か、アプリケーションの起動時の設定で実施する。
aggregate対応：集約 ・ フィールド ・ メソッド ・ 業務イベントの名前を、区切られた文脈の同じ言葉で命名する ・ 理由：ソースコードは、開発者どうしや業務エキスパートとの会話で使う同じ言葉に基づいて書く。複雑な業務ロジックでは特に重要である
ubiquitous-languageカスタマーやオーダーのようなカタカナの用語なら、対応する英単語をソースコードに使える。業務エキスパートが「顧客」「注文」と言うなら、同じ言葉は本来それに合わせる。次善の策は、クラス名を英単語にして、日本語名をドキュメンテーションコメントに書き添えることである
ubiquitous-language対応：用語がソースコードで正しく使われているかは、NDepend のような道具で検査できる ・ 理由：NDepend は C# のソースコードを解析し、記述の一貫性や依存の複雑さを報告する。ただし補助手段である
testing-strategy方針：ピラミッド形 ・ 最も適する実装方法：ドメインモデル、イベント履歴式ドメインモデル ・ 理由：集約と値オブジェクトの単体テストが、業務ロジックのテストとして最も効果的である

注意

アンチパターンリスク代替案
ドメインモデルを作るつもりで、業務ロジックをほとんど持たない「集約」を置き、業務ロジックを巨大なサービス層に記述する（貧血ドメインモデル）型の種類で分けて欄を pub(crate) にすると、不変条件のチェックが application の使う場面に書かれ、集約はデータ構造だけになる。結局はアクティブレコードになる集約ごとのモジュールにして欄を private にし、不変条件の I 番号を集約のコマンドか値オブジェクトの作る関数に付ける。application の関数は、読む → コマンド → 書く だけにする
業務サービスを使って、複数の集約のインスタンスを1つのデータベーストランザクションで変更する集約のインスタンス1つにトランザクション1つ、という原則に反する。Session Selector の決定を索引へ書くときや、まとめを作るときに、セッションと変更の記録を1回で書くと起きるドメインサービスは値を返すだけにし、書くのは application の使う場面が集約ごとに行う
（推測）2つ以上の crate で使う値オブジェクトを、共有の crate（common ・ shared など）に集める値オブジェクトの持ち主の業務領域が消え、その値の規則が共有の crate と使う側に分かれる。すべての crate が共有の crate に依存し、4節の辺の表が意味を失うその語の規則を持つ crate に置き、使う側はいまの辺で依存する。辺の無い組だけを、辺を1本足すか application に置くかで個別に解く
顧客管理のように、補完的な業務領域をドメインモデルで実装するinstance（インスタンスの作成と変更）と render（描画）は model.json で補完である。集約ごとのモジュールの形を守るために、ここで型や層を増やすと無駄な努力になるinstance と render の crate は、集約1つを1ファイルにした最小の形に留め、モジュールを分けるのは中核の crate（declaration ・ change ・ validation ・ search ・ session）から始める

ACDR 0201 の crate の辺（arch.html 4節）目的の参照を session と change の両方が持つのに2つの間に辺が無く、出どころを validate が確かめるのに validation から search への辺が無い。辺の表を作ったときに、値オブジェクトの持ち主までは突き合わせていない疑いがある

次にすること

  • session → declaration の辺を足して目的の参照を declaration に置くか、application で変換するかを利用者に決めてもらう。
  • changes.py に、各項目へ en と crate を足す行を書き、apply.py で model.json に適用する。
  • arch_tree.py の DOMAIN を集約ごとのモジュールの形に書き直し、arch.html 5節を作り直す。
  • 不変条件46行それぞれを、守る型（集約 ・ 値オブジェクト ・ ドメインサービス ・ application ・ outbound）に振り分けた表を下書きし、試験が許す例外の番号を決める。
  • model.json を読む xtask の検査の項目（型の定義 ・ pub の欄 ・ I 番号 ・ ポートの行）を CODING.md の規則の案として書く。
  • 以上の決定と差分を ACDR に起こし、承認を得る。
