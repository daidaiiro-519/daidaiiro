結論

採る

テストを置く場所でテストレベルを決め、使う場面と不変条件への追跡はテストの側に1か所だけ書き、区分は書かずに置いた場所から導き、CI は静的 → 単体 → 統合 → システムの順で、どの段でも0件で止める。

トレーサビリティはテストプロセスの全期間で確立し維持してカバレッジの評価に使うものであり、終了基準はテストレベルごとに定義するべきとされる。置き場所＝レベルにすると、追跡と終了基準の両方を機械で判定できる。

設計の手順

  1. 1-a 単体テストを、確かめるコードと同じファイルの #[cfg(test)] mod tests に置く

    domain の集約の操作 ・ ファクトリ ・ ドメインサービス ・ 値オブジェクトはすべてここ。テストダブルは使わない（値を渡して値を比べる）。#[cfg(test)] は mod tests にだけ付け、製品のコードにテストのためだけの関数 ・ 分岐 ・ pub を足さない。application の use_cases の単体テストも置かない（ポートを使うのでコンポーネント統合へ）

  2. 1-b コンポーネント統合テストを、crate ごとに tests/<crate の短い名前>/main.rs の1つのテストのターゲットにまとめ、中をモジュールに分ける

    application：tests/use_cases/main.rs と、src/use_cases/ と同じ名前のモジュール（patch.rs ・ validate.rs ・ record.rs …）。outbound：tests/sqlite/main.rs ・ tests/git/main.rs のように crate ごと。git と snapshot は同じモジュールの同じテストを両方の実装に当てる（K5）。schemas：declaration の tests/schemas/main.rs で schemas/v1 の13ファイルに正しいインスタンスと誤ったインスタンスを通す

  3. 1-c テストダブルを、application の tests/use_cases/doubles/ にポート1つ1ファイルで置き、型の名前で種類を示す

    保存のポート（contracts ・ instances ・ judgments ・ change_records ・ sessions ・ change_summaries）は FakeXxx（メモリ上で本当に保存する）、外から答えを受け取るポート（judge ・ ai_sessions ・ tools ・ settings ・ published）は StubXxx（テストが値を決めて返す）。Mock Object で呼び出しの順は確かめない。前提の状態を作る Creation Method は tests/use_cases/support.rs の1か所にまとめる。dev 専用の crate は作らない（使うのが application だけで、architecture.json に辺が増えるため）

  4. 1-d テストの関数の名前を、英語の snake_case で「条件_期待」の形にする

    例：closed_session_is_not_reopened ・ input_outside_schema_is_refused_without_state_change ・ split_answers_become_unverified。決定表の列なら列の条件を名前にし、1列に1つのテスト。状態遷移は1テストに無効な遷移1つ。テストの本体に if ・ for ・ while ・ match を書かず、同じ種類の assert を2回以上書くときは assert_eq!(…, "何を確かめたか") を付ける

  5. 2-a 使う場面と不変条件への追跡を、テストの関数の doc コメントの1行 `/// traces: I45, U27:事後` に書く（システムテストは test-suite の traces）

    テスト計画は「単体テストのモジュールの説明」としていたが、モジュール単位ではどのテストが落ちたらどの行のリスクが残るかを引けないので、関数に寄せる。書く場所は1テストにつき1か所で、ほかに対応表を持たない

  6. 2-b coverage.json の区分は持ち込まず、traces が見つかった場所から区分を導く

    src/ の mod tests → 単体、crates/*/tests/ → 統合、test-suite/ → システム、architecture.json ・ clippy.toml ・ schemas の検査 → 静的（静的は test-suite/static.json に「どの検査が守るか」を traces 付きで1行ずつ書く）。まだテストが無い行だけを test-suite/untested.json に why ・ move_when 付きで置く。同じ行が traces と untested の両方にある ・ どちらにも無い ・ model.json に無い id を traces に書いた、の3つを追跡の検査が落とす

  7. 2-c model.json を semantic-agent-schema/ に置き、追跡の検査を inbound/cli の tests/system/ の中のモジュール traces に1つ置く

    検査は model.json の use_cases ×｛事後, 失敗時｝と invariants の id を並べ、test-suite/*.json の traces と crates/**/*.rs の `/// traces:` 行を集めて突き合わせる。件数は固定しない（テスト計画の「場面の件数を固定する検査」を外した理由と同じ）。xtask の crate は足さない

  8. 3-a test-suite/<区分>.json を、場面の配列にし、1場面＝前提のコマンド列 ・ 操作1つ ・ 期待にする

    欄：id（S-REC-1 の形）・ title ・ traces ・ given.files（作業の木に置くファイル）・ given.steps（前提を作る protocol のコマンドの列。手元の DB を直接書かない）・ when（コマンド1つ：args ・ stdin）・ then（id ・ at（JSON Pointer。/exit ・ /stdout/… ・ /after/<名前>/…）・ message ・ 期待の種類1つ）・ after（操作の後に状態を読む protocol のコマンド。名前付き）・ unchanged（操作の前後で同じであるべき after の名前）。期待の種類は equals ・ contains ・ count ・ exists ・ matches（ULID の形などの正規表現）・ same_as（別の at と同じ値）。ULID ・ コミットの参照 ・ 時刻を equals で書かない。形は test-suite/scenario.schema.json が持ち、段5で検査する

  9. 3-b system テストを harness = false のテストのターゲットにし、場面1つを1件のテストとして登録して走らせる

    crates/inbound/cli/tests/system/main.rs が test-suite/*.json を読み、場面ごとに一時ディレクトリを作り（git init ・ HOME と XDG の各ディレクトリもその下に向ける）、CARGO_BIN_EXE_<名前> のバイナリを Command で起動する。1つの #[test] の中で全場面をループしない。`cargo test -p semantic-agent-schema-cli --test system S-REC-1` で1場面だけ走らせられるようにする。本物の AI ツールは呼ばず、needs への答えは場面の steps がコマンドで渡す

  10. 4-a 1つの変更の完了基準を、図の1〜8がすべて0件で通ることにする

    加えて：追跡の検査で untested.json の行が増えていない（減るのはよい）・ 欠陥を直した変更は、直す前に落ちる確認テストを1件足してある ・ 直した使う場面 ・ 不変条件の行に traces がある。行のカバレッジの数値は基準にしない

  11. 4-b CI を毎回の push で、図の順に別々の段として回す

    fmt → architecture-lint → clippy --workspace --all-targets --locked -D warnings → cargo build -p <crate>（全 crate）と cargo tree -e features → 追跡と test-suite の形 → cargo test --workspace --lib --locked → cargo test --workspace --test '*' --exclude semantic-agent-schema-cli --locked → cargo test -p semantic-agent-schema-cli --test system --locked。段を分けるのは、落ちた段でレベルが分かるようにするため。夜間に、system の場面を逆順で走らせる段を1つ足す（核の run.py の --reverse を引き継ぐ）

  12. 5-a needs の往復をシステムテストに入れる

    validate → needs（AI の rule ごとの依頼）が出る → 場面が semantic-judge の答えをコマンドで渡す → validate が5つの値にまとめる、を1場面にする。単体（validator の②）では、割れた答え ・ 根拠が空 ・ 読んだ値に無い根拠 → unverified（I14）を決定表の列で1つずつ。needs の各項目が procedure の出力のスキーマに合うかを then の1つにする

  13. 5-b 検査①②を、境界の両側の組で確かめる

    ①：入力のスキーマに合わない入力 → 断る ・ unchanged（作業の木 ・ 変更の記録 ・ セッションの索引）を after のコマンドで読んで前後同じ。②：機械の rule に外れた出力 → 保存し violated、AI の rule → needs。①が外れたら②まで進まないことも1場面。セマンティックの7コマンドが返す procedure が schemas/v1 の procedure に合い、AI を起動しないことは統合（application）で確かめる

  14. 5-c 手元の DB とまとめのコミットに、抜けている観点を足す

    sqlite の統合：schema.sql の一意の索引 ・ トリガー（14場面）に加えて、前の版のバイナリが作った DB を開ける（メンテナンステスト）・ DB が無い ・ 壊れているときの振る舞い。同時の登録（S-SES-10）は2つの接続を順に使って決定的に書き、sleep で待たない。まとめ：record で記録と変更の前後を両方向に突き合わせ（I31）、記録の無い書き換えが例外に出る ・ 同じ記録から作ったまとめが ULID とコミットの参照を除いて同じ ・ git と snapshot で一致 ・ コミットごとに1件（I35）

  15. 5-d ai-cli の記録した出力を、本物の AI ツールの出力の変化と別に管理する

    記録は crates/outbound/ai-cli/tests/ai_cli/recorded/ に置き、CI では本物を呼ばない。本物の出力の形が変わったことは CI で見つからないので、記録を取り直す手順と頻度を CODING.md に書く（手動の確認として残す）

根拠

判定の拠りどころにした判断基準の記述

判断基準引用
traceability対応：テストプロセスの全期間にわたって、トレーサビリティを確立し維持する ・ 理由：効果的なテストのモニタリングとコントロールの実装に重要である
traceabilityトレーサビリティ：テストケースと要件 ・ 評価できること：要件がテストケースでカバーされていること
test-levelsテストレベル：コンポーネント統合テスト（ユニット統合テスト） ・ 焦点：コンポーネント間のインターフェースと相互処理
test-pyramid条件：レイヤーが高くなる ・ 対応：テストの粒度は粗くなり、テストの分離は少なくなり、テスト実行時間は遅くなる
entry-exit-criteria対応：開始基準と終了基準を、テストレベルごとに定義するべきである
entry-exit-criteria区分：終了基準 ・ 基準：完了基準 ・ 例：計画したテストの実行 ・ 静的テストの実行 ・ 発見したすべての欠陥のレポート ・ すべてのリグレッションテストの自動化
static-testing場面：シフトレフト ・ 静的テストの扱い：仕様書をテストの観点でレビューする。ソースコードの静的解析は、動的テストより前か、自動化したプロセスの中で完了させる
devops-and-testingテスト活動：静的解析 ・ CI ・ DevOps パイプラインとの関係：CI フレームワークへ組み込む例が多い
test-automation条件：第一象限（コンポーネントテスト ・ コンポーネント統合テスト） ・ 対応：自動化して CI プロセスに含めるべきである
decision-table-testing項目：カバレッジアイテム ・ 内容：実行可能な条件の組み合わせを含む列
state-transition-testing条件：全遷移カバレッジで無効な遷移をテストする ・ 対応：1つのテストケースで無効な遷移を1つだけテストし、欠陥のマスキングを回避する
conditional-test-logic原因：Multiple Test Conditions ・ 場面：Defect Localization が得られない ・ 直し方：テスト条件ごとに別々の Test Methods を作り、そこから Parameterized Test を呼ぶ
conditional-test-logic原因：Multiple Test Conditions ・ 場面：値の組が大量にある ・ 直し方：Data-Driven Test に切り替えるほうが、よりよい解決になるかもしれない
assertion-roulette条件：1つのテストで同じ種類の Assertion Method を2回以上呼ぶ ・ 対応：最小限でよいので Assertion Message を付ける ・ 理由：Equality Assertion は期待値と実際の値の両方を表示するのがふつうだが、似た期待値が並ぶか表示が分かりにくいと、失敗したものを見分けにくい
test-logic-in-production原因：For Tests Only ・ 何が起きているか：SUT の中に、テストだけが使うためのコードがある ・ 見え方：SUT のメソッドのうち、テストからしか呼ばれないものがある。private のはずの属性のいくつかが public になっている
test-code-duplication原因：Cut-and-Paste Code Reuse ・ 場面：重複がフィクスチャの準備の処理 ・ 直し方：取り出した結果は、Creation Methods か Finder Methods（Test Utility Method の一種）になる
erratic-test原因：Resource Optimism ・ 直し方：できれば fixture setup の段階でリソースを作り、Fresh Fixture にする。これでどこで実行してもリソースがある。SUT をどこで動かしてもファイルシステムの決まった場所があるように、ファイルを相対的な場所で指すことになるかもしれない。外部のリソースを使わざるを得ないなら、ソースコードの Repository に登録し、すべての Test Runner を同じ環境で実行させる
erratic-test条件：互いに依存するテストがあるか確かめたい ・ 対応：ふだんと違う順でテストを実行する。スイート全体を逆順に実行するとよく見つかる ・ 理由：これを定期的にすれば、Interacting Tests を気付かずに作り込むことを防ぎやすい
erratic-test条件：データベースに保存するオブジェクトの一意のキー ・ 対応：Distinct Generated Value を使ってよい ・ 理由：これが、実行ごとに違う値を使う正当な使い方である
fragile-test敏感さ：Context Sensitivity ・ 直し方：テストを決定的にするため、SUT のすべての入力を制御する。ほかのシステムからの入力は、テストが値を決めて差し込む Test Stub で制御する。時刻か日付に固有の処理があれば、システムクロックを Virtual Clock に差し替え、テストが開始の時刻か日付を決め、ことによると時間の経過もまねられるようにする
slow-tests原因：Asynchronous Test ・ 直し方：処理を同期的にテストし、テストの非同期性を避ける。そのために Extract Testable Component のリファクタリングで Humble Executible を作る必要があるかもしれない
confirmation-and-regression-testing確認テスト：元の欠陥が、正常に修正されたことを確認するテスト。デバッグで原因を修正した後に、修正によって問題が解決されたかを確認する。
testware対応：適切な構成管理で、作業成果物の一貫性と整合性を確保する

注意

アンチパターンリスク代替案
Conditional Test Logic（1つの #[test] で全場面をループ）どの場面が落ちたかが出力から分からず、最初の失敗で残りが走らない（Defect Localization が得られない）harness = false で場面1つを1件のテストとして登録する（Data-Driven Test）。単体は決定表の1列に1つの #[test]
Erratic Test（Resource Optimism）：システムテストが利用者の HOME の設定や手元の DB を読むsettings の3段のうち user の段が開発者ごとに違い、手元と CI で結果が変わる場面ごとに一時ディレクトリを作り、HOME ・ XDG の各ディレクトリ ・ 作業の木 ・ DB をすべてその下に向けて子のプロセスに渡す（Fresh Fixture）
Fragile Test（Context Sensitivity）：ULID ・ コミットの参照 ・ 時刻を equals で期待する実行のたびに値が変わり、毎回落ちるか、期待を書き換え続けることになる単体では時刻と id を値で渡す。システムでは matches（形）と same_as（記録と索引で同じ値）で値の関係を期待する
（推測）追跡を2か所に持つ（coverage.json の区分とテストの traces）片方だけ直したときに食い違い、どちらが正しいかを毎回確かめることになるtraces はテストの側だけに書き、区分は置いた場所から導く。テストの無い行だけ untested.json に理由付きで置く
Slow Tests（Asynchronous Test）：同時の登録やセッションの再開を sleep で待つ待ちの時間が場面の数だけ積み上がり、時間の足りない CI では時々落ちる2つの接続を順に使うなど同期的に書く。待ちが要る処理は、処理を非同期の仕組みから分けて単体で確かめる
Test Logic in Production（For Tests Only）：テストのために domain の型にコンストラクタや pub を足すテストだけが使う公開 API が配る実行ファイルに入り、本当の呼び出し側を迷わせるテストは公開のファクトリと集約の操作で前提を作り、Creation Method はテストのモジュールの中に置く
