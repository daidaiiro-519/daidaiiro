Semantic Search と用語

利用者「処理自体は多分全部機械的…整形する部分がaiが行う部分で、それを整形する部分の契約としてjsonスキーマがある」「サーチする対象はこの項目だけではなく、どっちかというとインスタンスもあるし、Schemaもあるし、なんならJsonではないような普通のドキュメントやソースだって対象」「返す方はschemaで定義した型」。決まった内容は ACDR 0201（正本：model.json ・ ボード）。例の名前は架空

Semantic Search は、自然な言葉の問いに答えのスキーマで答える使う場面（U28）。semantic-search は procedure（手順 ・ 入力のスキーマ ・ 出力のスキーマ）を返し、AI は問いを条件（query#/$defs/request）に、結果（query#/$defs/result）を答えに整形するだけ。探す ・ 確かめるは機械的なコマンドで、出どころに式と版を残すので、答えは何度でも同じ結果で確かめられる。状態は変えない

1　コマンドと用語

コマンド種類返すもの
semantic-searchセマンティック（procedure を返す）手順 ・ 入力のスキーマ（query#/$defs/request）・ 出力のスキーマ（答えのスキーマ）・ 書き方の rule ・ kind と term の候補
semantic-read ・ semantic-write ・ semantic-create ・ semantic-judge ・ semantic-import ・ semantic-migrateセマンティック（procedure を返す）AI が行うほかの操作の手順と入出力のスキーマ（Semantic Read と Write の頁）
search機械的検査①のあと、インスタンス ・ スキーマごとに JMESPath の where を評価し、query#/$defs/result（id ・ 版 ・ 式 ・ select の値 ・ 探した範囲）を返す
get機械的欄 ・ インスタンス ・ スキーマの値 ・ x-prompt ・ 版。スキーマは $ref を解いた形
validate機械的検査②。渡した値を保存せずに検証する。出どころの式をその版で評価し直して一致を確かめる

AI が行う操作はすべてセマンティックのコマンドで、procedure を返す。AI は手順に従って入力を生成し、機械的なコマンドを呼ぶ

2　探す対象

対象探し方返す型
インスタンスJMESPath の where ・ select をインスタンス1件ずつに評価するquery#/$defs/result
スキーマ（Concrete ・ glossary ・ published）同じ（スキーマも JSON）。例：ある rule を使っている Concretequery#/$defs/result
ドキュメント（Markdown ・ ソース）本文は基盤が探さない。変更の記録とまとめ（JSON）から、意図 ・ 目的で変えたファイルのパスを引く。本文は AI が読むquery#/$defs/result（パス）
集まり（文脈 ・ 探す範囲）contexts と、文脈の settings の探す範囲結果の scope

3　送る JSON と返る JSON

状態を変えない操作なので、事後状態は事前状態と同じ。増えるのは出力だけ

① semantic-search に問う
{
  "for": "semantic-search",
  "question": "AI に何を許すかを決めた記録と、その責任者は？",
  "answer_schema": "urn:semantic-agent-schema:sample:answer-owner:v1"
}
procedure が返る
{
  "手順": [
    "問いを入力のスキーマ（query の request）の形に整形する",
    "search を呼ぶ",
    "結果を答えのスキーマの形に整形し、出どころを付ける",
    "validate を呼ぶ"
  ],
  "入力のスキーマ": "urn:semantic-agent-schema:base:query:v1#/$defs/request",
  "出力のスキーマ": "urn:semantic-agent-schema:sample:answer-owner:v1",
  "使ってよいコマンド": [
    "search",
    "get",
    "validate"
  ],
  "rules": [
    {
      "id": "where-is-jmespath",
      "rule": "where はインスタンス1件に評価する JMESPath の式。JMESPath の真偽の決まり（false ・ null ・ 空の文字列 ・ 空の配列 ・ 空のオブジェクト以外が真）で真のものを選ぶ"
    }
  ],
  "候補": {
    "kind": [
      "urn:semantic-agent-schema:sample:record:v1"
    ],
    "term": [
      "urn:semantic-agent-schema:sample:glossary:v1#permission"
    ]
  }
}
② AI が生成した入力 → ③ search（検査①）
{
  "kind": [
    "urn:semantic-agent-schema:sample:record:v1"
  ],
  "where": "contains(subject, 'AI') && decision != `null`",
  "select": {
    "owner": "owner",
    "decision": "decision"
  },
  "contexts": [
    "sample"
  ]
}
出力：query#/$defs/result
{
  "$schema": "urn:semantic-agent-schema:base:query:v1#/$defs/result",
  "query": {
    "kind": [
      "urn:semantic-agent-schema:sample:record:v1"
    ],
    "where": "contains(subject, 'AI') && decision != `null`",
    "select": {
      "owner": "owner",
      "decision": "decision"
    },
    "contexts": [
      "sample"
    ]
  },
  "items": [
    {
      "id": "r-12",
      "kind": "urn:semantic-agent-schema:sample:record:v1",
      "version": "<読んだ版>",
      "values": {
        "owner": "yamada",
        "decision": "許可は各ツールの設定に任せる"
      }
    }
  ],
  "scope": {
    "contexts": [
      "sample"
    ],
    "index_of": "<正本の版>"
  }
}
④ AI が整形した答え → ⑤ validate（検査②）
{
  "$schema": "urn:semantic-agent-schema:sample:answer-owner:v1",
  "items": [
    {
      "record": "r-12",
      "owner": "yamada",
      "provenance": {
        "id": "r-12",
        "kind": "urn:semantic-agent-schema:sample:record:v1",
        "version": "<読んだ版>",
        "where": "contains(subject, 'AI') && decision != `null`",
        "select": "owner"
      }
    }
  ]
}
validate の結果（保存しない）
[
  {
    "rule": "provenance-reproduces",
    "by": "machine",
    "value": "verified",
    "why": "その版で where が真になり、select の owner を評価し直すと yamada"
  }
]

select は「出す名前 → JMESPath の式」の対応で、values のキーはその名前（呼ぶ側が決める）。出どころの select はその名前を指す。JMESPath は選ぶ（where）と取り出す（select）にだけ使い、それ以外の返す形は基盤が決める。読んだ版がいまの正本と違えば、validate は violated を返し、AI が読み直す。写した値でない要約 ・ 組み合わせを答えに入れたときだけ、AI の rule（根拠の判定）が必要になり、semantic-judge で依頼する

4　呼ぶ側

呼ぶ側種類使うコマンド
AI ツール（Claude Code ・ Codex ・ Copilot ・ Kiro）と、それを動かす harnessAI が伴うsemantic-* で procedure を受け取り、機械的なコマンドを呼ぶ
CIAI が伴わない機械的なコマンド（search ・ validate など）を直接呼ぶ

5　AI をどこで動かすか

形セッションキャッシュ使う場面
A　いまのセッションで行う（基本）増えないいまの会話のまま効く問う者が AI のとき
B　文脈を引き継ぎ、残さない fork残らないClaude Code の fork：効く（原典「its first request reads the parent's cache」）。Codex の fork --ephemeral：効く（実測 64%、再開と同じ）いまの会話から切り離して1回だけ整形させたいとき

fork は呼ぶ側の AI ツールの機能で、基盤は関わらない（基盤は AI を起動しない）。子のセッションの4つの型と、ツールごとの手段は「子のセッションの型」の頁が持つ
