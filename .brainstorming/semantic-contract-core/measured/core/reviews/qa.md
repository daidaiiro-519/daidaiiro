# qa-advisor の回答（設計相談）

## 相談

Semantic Agent Schema の基盤の核（ドメインモデル ・ スキーマ ・ ポートの契約 ・ DB ・ 期待する振る舞い）を、参照の実装で場面を実行して合否で確かめるとき、期待する振る舞いの書き方 ・ 観点の抜け ・ 完了基準 ・ 外せるものをどう設計するか

## 結論

**判定：採る**

期待する振る舞いは、使う場面と不変条件の id を持つ「場面」の JSON 1件に、前提（fixture）・ 1つの操作 ・ 期待値の並びを書き、ランナーが全アダプターで実行して合否を返す形にし、id の対応表が全行埋まり、全場面が2回 ・ 逆順 ・ 2つのアダプターで同じ結果になったら核ができたと判定する。

**なぜ**：受け入れ基準は事前条件 ・ 入力 ・ 事後条件で書くテスト条件であり、テストベース（v2 の id）との対応が取れていれば、カバレッジを数で判定できる。いまの dbcheck.py と selfcheck.py は結果を人が読んで判断するので、self-checking に直すのが先である。

## 図で確認する

場面の JSON が、v2 の id とアダプターをつなぎ、結果が対応表に戻る

- v2 の使う場面22件 ・ 不変条件46行（＋合意済み ・ A1〜A9） → 対応表（id ごとに 場面 ・ 静的 ・ 確かめない）（全 id を区分する）
- 対応表（id ごとに 場面 ・ 静的 ・ 確かめない） → 場面の JSON（前提 ・ 操作 ・ 期待値）（「場面」の行は1件以上の場面を持つ）
- 場面の JSON（前提 ・ 操作 ・ 期待値） → ランナー（入口のポートだけを呼ぶ）（読む）
- ランナー（入口のポートだけを呼ぶ） → Git のアダプター（変更の前後を受け取る）
- ランナー（入口のポートだけを呼ぶ） → スナップショットのアダプター（変更の前後を受け取る）
- ランナー（入口のポートだけを呼ぶ） → SQLite のアダプター（セッションと索引）
- ランナー（入口のポートだけを呼ぶ） → 判定する AI の模擬（返す答えを場面が決める）（rule の判定（AI））
- ランナー（入口のポートだけを呼ぶ） → 合否（期待値の id ごと）と、アダプター間の差（出す）
- 合否（期待値の id ごと）と、アダプター間の差 → 対応表（id ごとに 場面 ・ 静的 ・ 確かめない）（id ごとの合否を戻す）（点線）

## 設計の手順

### 1. 場面の書式を決める（タスク1）

1件の場面は1つの JSON で、欄は次の7つ。(a) id ・ 題、(b) traces：使う場面の id と区分（事後条件 ・ 失敗時）、不変条件の id、依存する A の id、(c) adapters：実行するアダプター（git ・ snapshot ・ sqlite のうち当てはまるもの全部）、(d) given：前提の姿をデータで書く（リポジトリのファイル ・ 確定済みの単位の並び ・ DB の行 ・ 模擬の AI が rule ごとに返す答え ・ 時刻）、(e) when：入口のポートの操作を1つだけ（操作名と引数）、(f) then：期待値の並び。各期待値は id ・ 何を見るか（入口のポートの出力の JSON Pointer か、出口のポートの先の状態）・ 期待する値 ・ 失敗したときの文を持つ、(g) unchanged：操作の前後で変わってはいけないもの（契約 ・ インスタンス ・ 記録のハッシュ）。使う場面の「失敗時」は、1つの場面を「失敗させる前提＋同じ操作」で書き、事後条件の場面と対で置く。不変条件は、それを破る操作を when に置く否定の場面で確かめる（1場面に破る操作は1つ）。同じ特性を、使う場面の側と不変条件の側で2回書かない。1場面の traces に両方の id を並べる

### 2. 書式の例を1件書く

U25 の失敗時「意図の無い変更と、基盤を通らずに変えた欄は、そうだと分かる」と I31 ・ I36 を1場面で確かめる。下の「コードの例」に置いた。期待値は描画した HTML でなく、基盤が成型した JSON（例外の一覧 ・ 対象ごとの欄の前後）で比べる

### 3. 観点を、場面の前提の型として足す（タスク2）

観点ごとに「前提をどう作るか」と「何を期待するか」を決め、下の 3-1〜3-8 を場面の群にする。どれも新しい仕組みを足さず、given の書き方で表す

### 3-1. アダプターを替えても同じ結果

adapters に git と snapshot を両方書いた場面は、ランナーが両方で実行し、成型した出力が1バイトも違わないことを1つの期待値にする。ポートの操作 (2) 出した者 ・ (3) 対象の履歴 ・ (4) 消した ID の履歴は、スナップショットでは答えられない。答えられない操作は、場面ごとに飛ばすのでなく、アダプターが「この操作を持たない」と返すことを期待値にする（期待値はまだ決まっていない。I39 と同じ扱いにするかを決める）。境界の前提として、追加（前が null）・ 削除（後が null）・ 名前の変更 ・ UTF-8 でないファイル ・ 最初のコミット（親が無い）・ マージコミット（親が2つ）を足す。changeview.py の Git のアダプターは ref^ を自分で求めるので、A3 の「前の姿の参照と後の姿の参照を受け取る」と入出力が合わない。合わせてから等しさを確かめる

### 3-2. DB が消えたとき（I40 ・ A6）

given で DB のファイルを置かない場面を作る。期待値：目的 ・ 対象で変更を見せると、コミット済みの記録から同じ出力になる。セッションで引くと「手元の索引が無い」と返り、0件として返らない（I42 の考え方を当てる）。同じ目的のセッションを決めると「新しく立てる」が返る。索引に行があるのにポートの前後で記録が見つからない行は「確定しなかった」と出る（A6）

### 3-3. 同時に開くとき（I46 ・ U27）

時間に頼る並行の実行はしない。1つのプロセスで DB の接続を2つ持ち、操作の順を場面が決める（接続1が「決める」→ 接続2が「決める」→ 接続1が「登録」→ 接続2が「登録」）。期待値：2つ目の登録は断られ、再開する ID が返る。ここで「決める」と「登録」のあいだに AI ツールが ID を発行し終えているので、断られた側のセッションをどう扱うかが期待値として決まっていない。U27 の失敗時に足す必要がある。worktree を2つ作り、同じ DB を読む場面も置く

### 3-4. 単位がまとめられたとき（A8 ・ I33 ・ I37）

given で、記録を1件ずつ持つ単位を2つ作り、squash した単位を1つ作る。期待値：単位の変更すべてに両方の意図が付く。例外「単位がまとめられた」が件数と一緒に先頭に出る。意図ごとの変更は I33 の判定の記録の「判定した値」から引ける。I33 の判定の記録が無いときは「意図ごとに分けられない」と出る（期待値は未決）。別のブランチで足した記録どうしを合流しても衝突しない（I37）。rebase で前の姿が変わったとき、判定した値が変わり判定が効かなくなるか（I16）も場面にする

### 3-5. AI の判定が入る場面と、模擬に替える範囲

替えるのは出口のポート「rule の判定を頼む（AI）」の先の CLI のプロセスだけ。読む値の写しを作る処理 ・ 答えの形と根拠の確かめ ・ 5つの値へのまとめ ・ 判定の記録への書き込みは基盤の側なので替えない。模擬は given で rule ごとに返す答えを持ち（verified ・ violated ・ 形の誤り ・ 根拠が空 ・ 根拠が読んだ値に無い ・ 答えない ・ 割れた答え）、受け取った入力を記録する。期待値に「模擬が受け取ったのは読む欄 ・ term ・ 参照先の値の写しだけ」（I14 ・ I29）と「CI の場面では模擬が1回も呼ばれない」（I17）を置く。本物の AI を呼ぶ確かめは、結果が回ごとに変わるので完了基準に入れない

### 3-6. 決定表と状態遷移で網羅を決める

インスタンスの4つの状態（I19）は、rule の結果の組み合わせ（violated ・ error ・ unverified ・ unsupported の有無）を条件にした決定表にし、実行できる列をすべて場面にする。セッションの2つの状態（開いている ・ 閉じた）は状態表にし、有効な遷移をすべて通し、無効な遷移（閉じた → 開いている、id ・ 目的 ・ 親 ・ 役割の書き換え）を1場面に1つずつ試す

### 3-7. 基盤を通らない書き換え

given で、基盤の入口を通さずにインスタンス ・ 変更の記録 ・ 判定の記録をファイルとして書き換えた姿を作る。期待値：「記録に無い」「変更の無い記録」「記録の書き換え」が出る（I31 ・ I32）。いまの changeview.py の shape() は、書き換えた記録を新しい記録と区別せず、消した記録を見ない

### 3-8. 結果が実行の順と回数に依存しないこと

場面ごとに一時ディレクトリの Git リポジトリと新しい DB を作り、場面のあいだで何も共有しない。全場面を通常の順 ・ 逆順で1回ずつ、ローカルの設定と CI の設定で1回ずつ回し、結果が同じことを確かめる（I13）。時刻と id はランナーが渡す値で決める

### 4. v2 の id を3つに区分する（タスク3）

区分の決め方：(場面) 入口のポートの出力か出口のポートの先の状態で見えて、期待値が決まっているもの。(静的) スキーマ ・ 文書の形についての決まりで、操作を実行しなくても検査できるもの。(確かめない) 期待値が未決の論点に依存するか、確かめるための入力がまだ存在しないもの。理由と、場面へ移る条件を必ず書く。下の表が案

### 4-1. 使う場面22件の区分（案）

場面（18件）：U0（全体の流れの1場面）・ U1 ・ U2 ・ U5 ・ U6 ・ U7 ・ U8 ・ U10 ・ U11（同じ文脈の中）・ U12 ・ U13 ・ U14（validator は模擬）・ U16 ・ U17 ・ U18（Git のアダプターだけ。スナップショットには合流が無い）・ U25 ・ U26 ・ U27。一部だけ場面（1件）：U23（Abstract の拡張項目とぶつかる定義が違反になることだけ。x- の定義の形は Q7 が未決）。確かめない（3件）：U3 ・ U4（Abstract の新しい版がまだ無く、移す入力が存在しない。2つ目の版を出すときに場面へ移す）・ U24（Q6-pub が未決で、ほかのリポジトリから取りに行くポートの参照の実装が無い）

### 4-2. 不変条件46行の区分（案）

静的（2行）：I1（出した版のハッシュの一覧と照合）・ I3（selfcheck.py の型の検査）。確かめない（3行）：I7（Q6-pub）・ I27（新しい版が無い）・ I30（Q7）。一部だけ場面（3行）：I5（結果を5つの値でまとめる部分だけ。作法は Q7）・ I29（渡す値は模擬で確かめる。「道具を持たせずに起動する」は CLI の引数の配列を記録して見るまでで、CLI の中の振る舞いは確かめない）・ I43（同じリポジトリの中の文脈どうしだけ。リポジトリをまたぐのは Q6-pub）。場面（38行）：残りすべて。I4 ・ I6 は静的にも検査できるが、U1 ・ U23 の失敗時の場面で、取り込めない理由として出ることまで確かめる

### 5. 完了基準を合否で書く

次の9つがすべて合格なら「核ができた」と判定する。

- C1：v2 の use_cases の22件 × {事後条件, 失敗時} と invariants の46行のすべてが、対応表で 場面 ・ 静的 ・ 一部 ・ 確かめない のどれかに区分されている（区分の無い id が0件。ドメインモデルの JSON と対応表を機械で突き合わせる）。
- C2：「場面」と「一部」の id はすべて1件以上の場面から traces で指されている。どの id も指さない場面が0件。
- C3：「場面」の不変条件は、すべて1件以上の否定の場面を持つ。
- C4：インスタンスの状態の決定表の実行できる列と、セッションの状態表の有効 ・ 無効な遷移を、すべて場面が通る。
- C5：全場面が、traces に書いたすべてのアダプターで合格する。git と snapshot の両方を書いた場面は、成型した出力が一致する。
- C6：全場面を通常の順 ・ 逆順 ・ ローカルの設定 ・ CI の設定で回した4回の結果が一致し、CI の設定で AI の模擬の呼び出しが0回。
- C7：ランナーは不合格が1件でもあれば0以外で終わり、出力は期待値の id ごとの合否で、人が読み比べる出力が無い。
- C8：静的の行がすべて合格する（Abstract の本体が自分自身で、Concrete が本体で、インスタンスが Concrete で検査を通り、DB の DDL が一員のスキーマから導いたものと一致する）。
- C9：「確かめない」と「一部」の行は、理由と「場面へ移る条件」を持ち、traces が指す A の id がすべて合意済みである

### 6. 外せるものを外す（タスク4）

下の「注意」の表のとおり、dbcheck.py の生の SQL の確かめ ・ 人が読む出力 ・ HTML での比較 ・ 本物の AI の呼び出し ・ 使う場面と不変条件で同じ特性を2回書くこと を外す。場面のランナー1つが、dbcheck.py と selfcheck.py の動的な部分を置き換える。新しく足すのはランナーと場面の JSON だけにする

## コードの例

場面の書式の例（U25 の失敗時 ・ I31 ・ I36）。期待値は成型した JSON で比べ、HTML を比べない。

```
    "change_records": [],
    "judge": {}
  },
  "when": {"port": "検証する ・ 変更を見せる", "op": "show", "args": {"by": "unit"}},
```

```
#   期待（通る／断る）がデータに無く、終了コードも常に 0
```


## 根拠

| 判断基準 | 引用 |
|---|---|
| acceptance-criteria | 形式：シナリオ指向 ・ 例：BDD で使用する Given/When/Then 形式 |
| atdd | 対応：典型的には、必要な事前条件（もしあれば）・ 入力 ・ 事後条件を、自然言語の文章で含める |
| atdd | 対応：2つのテストケースに、ユーザーストーリーの同じ特性を記述すべきではない |
| traceability | トレーサビリティ：テストケースと要件 ・ 評価できること：要件がテストケースでカバーされていること |
| entry-exit-criteria | 区分：終了基準 ・ 基準：徹底度の測定 ・ 例：達成されたカバレッジレベル ・ 未解決欠陥の数 ・ 欠陥密度 ・ 不合格になったテストケースの数 |
| decision-table-testing | 項目：カバレッジアイテム ・ 内容：実行可能な条件の組み合わせを含む列 |
| state-transition-testing | 条件：全遷移カバレッジで無効な遷移をテストする ・ 対応：1つのテストケースで無効な遷移を1つだけテストし、欠陥のマスキングを回避する |
| manual-intervention | 原因：Manual Result Verification ・ 直し方：Test Method に、Assertion Method の呼び出しなどの結果の検証の処理を入れ、すべてのテストを self-checking にする |
| manual-intervention | 条件：SUT がほかの部分からの同期の応答として受け取る ・ 対応：SUT の一部を Test Stub に置き換え、その状況をまねて indirect input を制御する |
| erratic-test | 条件：互いに依存するテストがあるか確かめたい ・ 対応：ふだんと違う順でテストを実行する。スイート全体を逆順に実行するとよく見つかる ・ 理由：これを定期的にすれば、Interacting Tests を気付かずに作り込むことを防ぎやすい |
| assertion-roulette | 条件：1つのテストで同じ種類の Assertion Method を2回以上呼ぶ ・ 対応：最小限でよいので Assertion Message を付ける |
| test-logic-in-production | 原因：Test Hook ・ 場面：どの場合も ・ 直し方：テストのための処理を製品のコードに書き込まず、差し替えのきく依存（substitutable dependency）の側へ移す |
| testing-principles | 条件：検証を実施した ・ 対応：検証に加えて、妥当性確認も実施する |

## 注意

| アンチパターン | リスク | 代替案 |
|---|---|---|
| Manual Result Verification（dbcheck.py ・ selfcheck.py） | 期待が表示名の括弧にしか無く、終了コードが常に0なので、断るはずの操作が通っても合格に見える | 期待（通る ・ 断る ・ 断る理由）を場面の then に書き、ランナーが判定する。dbcheck.py は場面へ移して外す |
| 名前と中身が合わない確かめ（dbcheck.py の「閉じたオーケストレーターのあとに、新しく開く」） | その状況（閉じてから開く）が確かめられていないのに、確かめた扱いになる | （推測）given で 0a9d を閉じた姿を作り、when で新しいオーケストレーターを開く場面にする |
| アダプターの内側の SQL を直に叩く確かめ | A5 で DDL はアダプターの実装と決めたので、DDL を変えるたびに確かめが壊れる（Fragile Test）。ポートの振る舞いを確かめていない | （推測）入口のポート「セッションを決める ・ 立てる ・ 閉じる」を通す場面にする。DDL のトリガーと一意の索引は、ポートの場面が通れば足り、別に確かめない |
| HTML を比べてアダプターの等しさを見る | 描画の都合（アダプターの名前の表示など）で差が出て、等しさの判定が崩れる | （推測）基盤が成型した JSON（対象 ・ 欄の前後 ・ 例外）を比べる。HTML は人が読む合否のページとして結果から1枚作るだけにする |
| 本物の AI を完了基準の場面で呼ぶ | 回ごとに答えが変わり、同じ場面が通ったり落ちたりする（Erratic Test の Nondeterministic Test） | 判定する AI を Test Stub に替え、答えを場面のデータで決める。本物の AI の確かめは完了基準の外に置く |
| 基盤の中に模擬へ切り替える分岐を入れる | テストのときだけ動く処理が基盤に残り、本番で誤って動く（Test Logic in Production の Test Hook） | 模擬は出口のポートのアダプターの実装として渡し、基盤の中に「テスト中なら」の分岐を置かない |
| v2 の文と合意済みがずれた行をそのまま期待値にする | I44「子の目的の参照は親と同じ」は、目的の無いオーケストレーターを親に持つ目的のセッション（dbcheck.py の 7c1e）と両立しない。I46 も合意済みの「同じ目的は1つ」と範囲が違う。どちらで書いても片方に反する場面になる | （推測）場面を書く前に、ずれた行を v2 へ適用する差分に入れ、期待値の出所を1つにする |

## 差し戻し

| 疑われる上流（advisor ・ 判断） | 疑う理由 |
|---|---|
| ドメインモデル（ddd-advisor）・ I44 | 「子の目的の参照は親と同じ」が、オーケストレーターの子（目的のセッション）に当てはまらない。合意済みの「オーケストレーターは目的を持たない」と合わせた文が必要と疑う |
| 使う場面 U27 の失敗時（usecase-advisor） | 「決める」が「新しく立てる」を2か所へ返したあと、片方の登録が断られたとき、すでに AI ツールが発行したセッションをどうするかが書かれていない |
| A3 のポートの操作 (2)〜(4)（platform-advisor） | スナップショットのアダプターは出した者 ・ 対象の履歴 ・ 消した ID の履歴を答えられない。持たない操作をどう返すかが決まっていないと、アダプターの等しさの期待値が書けない |

## 次にすること

1. v2 と合意済みがずれる行（I44 ・ I46 ・ I31 ・ I35）の期待値の出所を1つに決める。
2. v2 の id を読んで対応表の JSON を作り、22件 × 2 と46行に区分を付ける。
3. 場面の JSON の形を JSON Schema で書く。
4. dbcheck.py の確かめを、ポートを通す場面へ書き直してから dbcheck.py を外す。
5. changeview.py の Git のアダプターを、A3 の「前の参照と後の参照を受け取る」入出力に合わせる。
6. AI の判定の模擬を、出口のポートのアダプターとして1つ作る。
7. ランナーを作り、C1〜C9 を1回の実行で判定させる。

## AI が作業するときの注意

| 違反しやすい点 | 検査する方法 |
|---|---|
| 場面を書く AI が、期待値を参照の実装を走らせた出力から写す（実装の誤りが期待値になる） | 場面の then の各値に、出所の id（U ・ I ・ A）を traces で持たせ、traces が空の期待値を持つ場面を対応表の突き合わせで不合格にする |
| 失敗する場面を「既知の失敗」として外して全件合格にする | ランナーが飛ばした場面の数を出力し、C2 の判定で、飛ばした場面だけに指される id を「場面が無い」と数える |
| 1つの場面に破る操作を2つ以上入れる | 場面の JSON Schema で when を1つの操作に限る（配列にしない） |
