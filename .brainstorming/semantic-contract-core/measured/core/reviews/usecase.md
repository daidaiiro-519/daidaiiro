# 相談

9件の答え（A1〜A9）を適用したあとも、変更の記録 ・ 判定の記録 ・ セッションに関わる使う場面（U5 ・ U6 ・ U7 ・ U13 ・ U16 ・ U18 ・ U25 ・ U27）の事後条件と失敗時は成り立つか。シミュレーションで流すシナリオをどう起こすか

相談種別：設計相談

## 前置き

| 前提 | 内容 | 出所 |
|---|---|---|
| 対象システム（スコープ） | Semantic Agent Schema の基盤（Core）。変更の仕組み（Git など）は設計スコープの外の支援アクターで、ポート「変更の前後を受け取る」の向こう側に居る | domain-model-v2.json の ports ・ answers.json A3 |
| 事後条件と失敗時 | use_cases の4つ目の欄を成功時保証、5つ目の欄を最低保証として読む | domain-model-v2.json の use_cases の並び |
| コミット ・ 作業ツリーの語の在りか | 8件の使う場面の文そのものには「コミット」「作業ツリー」は無い。在るのは、これらの場面が引く集約「変更の記録」・ 値オブジェクト「判定した値」「まとめ方」・ 不変条件 I20 ・ I34 ・ I40 の文である | domain-model-v2.json を語で検索した結果 |
| 確定する操作の持ち主 | 未判定。A3 のポートの4つの操作はどれも読むだけで、確定させる操作が無い。確定は基盤の外（変更の仕組み）で起きる、と読んで判定した | answers.json A1 ・ A3 |
| 契約の変更と直しの意図 | 未判定。U2 の契約の変更と U7 の直しを1つの意図にするか、別の意図にするかで、U7 の直す文が変わる。推奨は1つの意図（A8 の「単位がまとめられた」を通常の作業で起こさないため） | answers.json A1 ・ A8 からの推論。判断基準の範囲外 |

## 結論

**判定：弱い**

8件とも直しが要る。A1（1単位＝1意図）・ A3（未確定）・ A4（最後の判定だけ確定）・ A6 ・ A8 の例外を保証へ写し、変更の仕組みの無応答の拡張を足し、U27 は要約レベルに直す。

**なぜ**：成功時保証は実際に起きたことを基準に書くので、確定の前に終わる U5 ・ U6 ・ U7 ・ U16 が「残る」と約束すると、確定しなかった場合と食い違う。変更の仕組みは支援アクターなので、応答が無い場合と正しくない場合を拡張に入れる必要がある。

## 図で確認する

使う場面と、確定の単位 ・ 支援アクターの関係。基盤が書くのは未確定の変更までで、確定は変更の仕組みが行う

- AI の Agent（U5 ・ U6 ・ U7） → 基盤（Core）（書く（意図 ・ 目的））
- 作業した本人（U16） → 基盤（Core）（判定する（人の入口））
- 基盤（Core） → 未確定の変更（インスタンス ・ 変更の記録 ・ 判定の記録）（置く）
- 基盤（Core） → 手元の索引（セッション → 変更の記録）（行を足す）
- 作業した本人（U16） → 変更の仕組み（Git ・ スナップショット）（意図を承認して確定させる）　※基盤の外
- 変更の仕組み（Git ・ スナップショット） → 確定の単位（1単位＝1意図）（確定する）
- 変更を見る人 ・ 監査する人（U25 ・ U13 ・ U18） → 基盤（Core）（見せる ・ たどる）
- 基盤（Core） → 変更の仕組み（Git ・ スナップショット）（前後 ・ 出した者 ・ 対象の履歴）

## 設計の手順

1. **保証を先に直す** ── 記録案の対のとおり、8件の成功時保証 ・ 最低保証を直してから、シナリオを起こす。確定より前に終わる場面（U5 ・ U6 ・ U7 ・ U16）は「未確定の変更に置かれる」までを約束し、「残る」と書かない
2. **スコープとレベルを各場面の頭に書く** ── スコープは全件「基盤（Core）」。レベルは U27 だけ要約、ほかはユーザー目的。変更の仕組みと手元の索引のアダプターは、場面の文に出さず、支援アクターと技術のバリエーションに置く
3. **主シナリオを3〜9ステップで書く** ── 1ステップは1行で「主語 ・ 操作（意図）・ 受け渡す情報」。主語は 主アクター ・ 基盤 ・ 変更の仕組み のどれか。分岐を本文に書かない
4. **拡張条件を、基盤が検出できる形で出し切る** ── 候補は4つの型から必ず出す ── 変更の仕組みが答えない ・ 誤った形で答える／記録と前後が食い違う（記録に無い ・ 変更の無い記録 ・ 確定しなかった ・ 単位がまとめられた）／validator の error ・ unsupported／人の入口を通らない書き換え
5. **拡張ごとに終わり方と最低保証の文を結ぶ** ── 各拡張は「主シナリオの n へ戻る」か「失敗で終わる」で閉じ、失敗で終わるものは、確かめる最低保証の文を1つ指す
6. **1経路を1回のシミュレーションにする** ── 主シナリオ1本と拡張ごとに1本。各回は事前の状態（ファイル ・ 索引 ・ 確定済みの単位）を自分で用意し、前の回の結果に頼らない
7. **技術の違いは同じ経路を2回流して確かめる** ── Git とスナップショットを別のシナリオにせず、同じ経路をアダプターだけ替えて流し、事後の状態が同じになるかを見る

## 具体例

### シミュレーションの1行の書式

| 欄 | 中身 | build.py の場面との対応 |
|---|---|---|
| uc ・ path ・ no | 使う場面 ・ 経路（主 か 拡張の番号）・ ステップ番号（例：4c1） | `a` を置き換える |
| actor | ステップの主語（主アクター ・ 基盤 ・ 変更の仕組み） | `actor` |
| op | 意図の動詞句と、受け渡す情報 | `op` |
| pre | 事前の状態（ファイル ・ 手元の索引 ・ 確定済みの単位） | `pre` |
| post | 事後の状態 | `post` |
| checks | この行で確かめる保証の文（成功時保証か最低保証の1文） | 新しく足す |
| variation | 技術の違い（Git ・ スナップショット）。経路は増やさない | 新しく足す |
| files | 前後のファイル | `files` |

経路の規則：主シナリオは3〜9行で分岐を書かない。拡張は「基盤が検出した条件：」で始め、「主シナリオの n へ戻る」か「失敗で終わる」で閉じる。1経路が1回のシミュレーションで、各回は自分の事前の状態を用意する。

トリガー：変更を見る人が、条件とまとめ方を付けて「変更を見せる」を頼む

**主シナリオ**

### 例の要約（回答の JSON の examples）

- U25 の主シナリオ：1. 変更を見る人は、条件（目的 ・ 対象 ・ セッション）とまとめ方（単位の並び）を基盤に渡す。2. 基盤は、単位ごとの前の姿と後の姿を変更の仕組みに頼み、対象ごとの前後を受け取る。3. 基盤は、前後を成型し、対象ごと ・ 欄ごとの変更を導く。4. 基盤は、条件に紐づく変更の記録と判定の記録（I33 ・ 人）を読み、変更と突き合わせる。5. 基盤は、まとめた後の姿で全インスタンスを検証する。6. 基盤は、例外を件数と一緒に先頭に置き、目的 → 意図 → 意味 → 検証結果の差分 → 描画の差分の順で見る人に示す
- U25 の拡張：*a 変更の仕組みが答えない ・ 誤った形で答える：基盤は error として返し、変更を見せたことにしない（失敗で終わる）／1a 手元に無いセッション ID で引いた：基盤は、そのセッションでは探していないと返し、目的 ・ 対象の条件だけで続ける（2 へ戻る）／4a 変更の記録の無い書き換えがある：基盤は「記録に無い」とする（5 へ戻る）／4b 書き換えの無い記録がある：「変更の無い記録」とする／4c 手元の索引に在る記録が、前後のどこにも無い：「確定しなかった」とする（A6）／4d 1単位に変更の記録が2つ以上ある：入った意図すべての変更として並べ、意図ごとの変更を I33 の判定した値から引き、「単位がまとめられた」とする（A8）／4e I33 の判定した値がいまと違う：I33 を判断待ちとする／5a validator が答えない：その rule を error とし、verified に数えない
- U25 の技術のバリエーション：2. 変更の仕組みは Git（commit の親と commit）／スナップショット（前と後のディレクトリ）／後の姿は未確定の変更でもよい

## 根拠

| 判断基準 | 引用 |
|---|---|
| success-guarantee | 対応：実際に起きたことを基準に書き、失敗条件と食い違う言い回しを避ける ・ 理由：ATM なら、要求額どおりに出金されない失敗条件があるので、要求された金額ではなく引き出した額で書く |
| minimal-guarantee | 対応：失敗の仕方を最低保証の欄に並べない ・ 理由：失敗の仕方は数えきれず、共通点もほとんど無い。失敗条件と処理は拡張に書くので、2つのリストをそろえる手間がかかり、食い違いも起きやすい |
| supporting-actor | 対応：拡張条件をブレーンストーミングするときは、支援アクターからの応答が無い場合と、応答が正しくない場合を候補に入れる ・ 理由：そのときの振る舞いが要求に無いと、プログラマがその場で書ける程度の処理を書き込むことになる |
| technology-data-variation | 観点：主成功シナリオと何が異なるか ・ 拡張：システムが「何を」するか ・ 技術およびデータのバリエーション：同じことを「どのように」行うか |
| design-scope | 問い：スコープ欄のシステムの内部（コンポーネント）に触れているか ・ どう判断するか：触れていればホワイトボックスである。システムの要求文書なら、触れないブラックボックスで書く |
| goal-level | 対応：一番外側（要約）のユースケースを、ほかのユースケースの文脈を示す分だけ書く ・ 理由：作業をまとめるのに大変便利で、強く勧められる。ただし、作るシステムの機能要求はここからは分からない |
| extension | 問い：システムはその条件を検出できるか ・ どう判断するか：検出できない出来事には反応できない。検出できる同等の条件に置き換えられないかも考える |
| extension | 対応：どの失敗処理でも、利害関係者の利益が守られ、ログや回復のための情報が残るかを確認する ・ 理由：書き手は途中で失敗が起きる場面を想定しないので、ログや回復の情報が抜けやすい |
| main-success-scenario | 対応：分岐は本文から外し、成功を前提にした文にして、分岐は拡張に書く ・ 理由：成功前提の本文を読むと「そうならなかったら」と疑問がわき、読み手は拡張を探す。ユースケースに一貫したリズムが生まれ、読みやすくレビューしやすくなる |
| action-step | 対応：「主語 … 修飾語 … 目的語 … 述語」の単純な文にし、主語を省かない ・ 理由：主語を省くと、誰が動作を制御しているかが分からなくなる。例：システムは … 残高から … 金額を … 差し引く |
| use-case-to-test-case | ユースケースを番号を付けたテスト項目に分け、異なるパスを通すための設定を1つずつ見分けた計画を作る |
| sub-use-case | 対応：サブユースケースの成功時保証 ・ 最低保証 ・ 拡張を、特に丁寧に書く ・ 理由：何を返すかが、呼び出し側にとって重要だからである |

## 注意

| アンチパターン | リスク | 代替案 |
|---|---|---|
| 確定より前に終わる場面で、記録が「残る」と約束する（U5 ・ U6 ・ U7 ・ U16 ・ U27） | A1 で確定は人が意図を承認したときに起きるので、承認されずに捨てられた場合（A6 の「確定しなかった」）と保証が食い違う | 「未確定の変更に置かれる」までを成功時保証にし、確定しなかった場合は U25 ・ U13 の例外で分かる、と書く |
| 成功時保証に基盤の内部の置き場を書く（「書いたセッションの ID が手元の索引に残る」） | ブラックボックスで書くべきシステムの要求に、索引という内部の部品が入り、SQLite のアダプターを替えると保証の文まで直すことになる | 利害関係者の利益で書く ──「作業した本人は、その記録を書いたセッションで引ける」。置き場は I38 ・ I40 が持つ |
| 最低保証に失敗の仕方を並べる（U5 の「必須の欄が空なら…」） | 拡張の条件と2か所になり、片方だけ直したときに食い違う | 「必須の欄が空」は拡張の条件にし、最低保証には「確定済みの姿は変わらない」のような守られる利益だけを書く |
| 変更の仕組みが答えない ・ 誤った形で答える拡張が無い（U13 ・ U18 ・ U25） | A3 で前後 ・ 出した者 ・ 履歴をすべて変更の仕組みから受け取るようになったので、応答が無いときの振る舞いが要求に無いと、実装の側でその場の処理が書き込まれる | *a として「変更の仕組みが答えない ・ 誤った形で答える：基盤は error として返し、見せたことにしない」を各場面に置く |
| 技術の違いを場面やシナリオに書く（Git ではブランチと PR、PR で承認する人） | 変更の仕組みを替えると使う場面の文が変わり、A3 の「変更の仕組みの語を使わない」に反する | 技術およびデータのバリエーションとして、ステップ番号に Git ・ スナップショットを並べる |
| 要約レベルの場面をユーザー目的として書く（U27） | 「目的のあいだは同じセッションが続く」は何日にもまたがる目的で、中に U5 ・ U6 ・ U16 ・ U25 がステップとして入る。ユーザー目的として流すと、シミュレーションの1回が目的のすべてを抱える | U27 を要約レベルにし、ステップを「目的のセッションを立てる → U5 / U6 → U16 → 意図を承認して確定させる → U25」のように他の場面への呼び出しで書く |

## 差し戻し

| 疑われる上流 | 疑う理由 |
|---|---|
| A1 と A3（ddd-advisor） | A1 は人が承認した意図1つぶんを確定すると決めたが、A3 のポートは読む操作だけで確定させる操作を持たない。確定を基盤の外に置くなら、U16 の後に「変更の仕組みで確定させる」ステップの主語が人になり、確定しなかった場合は A6 でしか分からない。この読み方でよいかを確かめる必要がある |
| I40 の「コミット」（利用者の決定 第70回 ・ 第73回） | A3 は変更の仕組みの語をポートから外したが、保存の決まり（extension_contract.storage ・ I40）は「コミットするファイル」を決定の語として持つ。保存の決まりまで中立の語にするかは、A3 の範囲を超える |
| U7 を U2 の拡張へ移すか（ddd-advisor） | A1 と A8 の下では、契約の変更と直しを別の意図にすると、途中の単位の後の姿に violated が残るか、まとめたときに「単位がまとめられた」が通常の作業で出る。1つの意図にするなら U7 は U2 のステップになる |
