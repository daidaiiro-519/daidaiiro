## 判断の道筋

1. **A1 確定の単位は、集約の境界と合うか**  
   変更の記録とインスタンスは別の集約で、一致は結果整合（I31）である。同じ単位で確定するのは外の変更の仕組みの都合で、基盤のトランザクションではない。1単位＝1意図を基盤の不変条件にすると、外が破ったときに基盤の不変条件が破れるので、期待する確定の仕方として書き、破れたら A8 の例外にする。また、差し戻した意図を同じ単位の中で直すと、I32 の「新しい記録を足す」で1単位に記録が2つ入る。確定する前の記録は書き換えてよく、置き換える意図の id は確定した記録だけを指す、と1文足す
2. **A1 同じ言葉は保たれるか**  
   v2 の I20 は「変更（変更の仕組みの単位。Git ではブランチと PR）」と書く。A1 の「単位」は1コミットの側である。変更（単位の並び）と確定の単位を別の語として定義し、I20 の Git の語も A3 と同じくアダプターの説明へ移す
3. **A2 変更の項目は、変更の記録の業務ロジックが強い一貫性を必要とするデータか**  
   必要とする。I31 は記録と前後を両方向で突き合わせ、「記録に無い」書き換えを欄の単位で出す。そのためには、入口が書いた欄を、前後とは別に記録しておく必要がある。前後から導けるのは「何が変わったか」で、「入口を通って変わったか」は導けない。導ける値を持たないことは自由度を減らすが、変更の項目は導ける値ではない
4. **A2 1単位＝1意図なら、変更の項目は要らなくならないか**  
   単位の粒度では「記録の無い単位」は分かる。分からなくなるのは、記録のある単位の中で入口を通らずに別の欄も書き換えた場合で、その欄は意図の変更として数えられる。I33 の AI の判定が「意図が合わない」と出すこともあるが、確かな検出ではない。U25 の失敗条件「基盤を通らずに変えた欄は、そうだと分かる」を残すなら、変更の項目は外せない
5. **A2 欄の粒度は保たれるか**  
   A2 の「JSON の対象は欄（JSON Pointer）の単位」は、配列の添字まで下がるかが書かれていない。v2 の「x-prompt を持つ書く単位まで、配列の添字までは下げない」（Q1 #30）を、成型の規則にもそのまま書く。判定の単位と変更の単位がずれないようにするため
6. **A3 ポートを変更の仕組みの語なしで書けば、モデル変換装置として足りるか**  
   形は足りる。ポートは基盤が定義し、Git の語はアダプターが持ち、参照は解釈しない文字列なので、下流（基盤）が上流（変更の仕組み）のモデルを自分の言葉へ変換している。足りないのは1点で、操作 (1) は「前の姿の参照」を受け取るが、ある単位の前の姿の参照を得る操作が無い。Git では単位（コミット）と姿（コミット）が同じ参照なので気づかないが、これは Git の前提がポートに残っている状態である。操作 (2) を「単位の中身：前の姿 ・ 後の姿 ・ 出した者 ・ 時刻」に置き換え、前の姿は1つと決める。合流の単位で親が2つあるときにどちらを前の姿にするかは、アダプターの説明に書く
7. **A3 操作 (3) は消した対象にも効くか**  
   U11 ・ U13 で、消したインスタンスの経緯を引く。操作 (3) の契約に「いま無い対象のパスでも、それを変えた単位を返す」と書く
8. **A4 外れた判定を確定に入れないことは、どこで守るか**  
   v2 は判定の記録のルートを「対象 × rule の記録」としている。これはエンティティの識別が対象 × rule であることを意味し、識別が同じなら記録は1つである。下書きの judgment.schema.json は ULID の id と {id}.json の置き場所を持ち、同じ対象 × rule の記録が複数作れる。識別を対象 × rule にし、置き場所を対象と rule から作れば、上書きで最後の判定だけが残り、A4 は手順を足さずに成り立つ。両側で同じ対象 × rule を判定した取り込みは同じファイルの衝突になり、I22 も変更の仕組みの衝突として成り立つ
9. **A5 I46 は、1つのセッションの集約の中で守れるか**  
   守れない。I46 は「目的 ・ 親 ・ 役割が同じで開いているのは1つまで」で、ほかのセッションの状態に依存する。業務ルールがほかの状態に依存するなら同じ集約に入れる、が判断基準の答えで、I46 を強く守る単位は「1つの手元のセッションの集まり」である。DDL の一意の索引がこの集まりを1つのトランザクションで守っているので、モデルにもそう書く：I46 は一員 session の集合への rule（by: machine）で、守るのはアダプターの一意の索引。I45 ・ 不変条件①は1行の中で守れるので、一員の rule とトリガーで足りる
10. **A5 一員の形を Abstract に、DDL をアダプターに置く分け方は、ポートとアダプターに合うか**  
   合う。行の形と rule がポートの契約、DDL がそれを SQLite で実装したアダプターである。v2 の第79回の決定（行の形は Abstract、DDL と DB の版は SQLite アダプター）とも同じ。直すのは2点。セッション ID は値オブジェクト（tool と文字列の組）なので、上の欄も親と同じ {tool, id} の1つの値にそろえる。DDL は手で書くと rule とずれるので、rule ごとに対応する制約を表にし、違反を1件ずつ入れて拒まれるかをシミュレーションで確かめる
11. **A5 session-change はどの集約に属するか**  
   v2 の値オブジェクト「手元のセッションの索引」の行である。変更の記録（コミットするファイル）とは別の置き場所なので、1つのトランザクションでは書けず、結果整合になる。セッションを外部キーで指すのは同じ DB の中なのでよく、change_id は変更の記録を ID で指すだけで、記録の在ることを索引の側で保証しない。保証しないことを A6 が受け持つ
12. **A6 確定しなかった記録の索引の行は、どう扱うか**  
   索引の行は見せるための索引で、正しさの判定に使わない（I34 と同じ）。見せる時に、ポートの前後（確定した姿と未確定の姿の両方）で記録が見つからない行を「確定しなかった」と出せば、基盤を通った捨て方も通らない捨て方も同じ結果になる。基盤を通る捨て方のコマンドは要らないので外す
13. **A7 対象ごとの経緯は、基盤が履歴を持たずに引けるか**  
   引ける。操作 (3) で単位の並びを受け取り、操作 (2) の直した形で各単位の前の姿 ・ 後の姿を得て、記録と判定を読む。変更の記録 ・ 判定の記録のファイルも対象なので、同じ操作で記録の経緯も引ける。全件を読むのが遅いと測れてから索引を足す（v2 の方針のまま）
14. **A8 まとめられた単位で、意図ごとの変更は引けるか**  
   案のままでは引けない場合がある。I33 の判定した値の前の値は「その記録が入った単位の前の姿」から取る（A3 の書き換え）。まとめると、2つめ以降の意図の前の姿が単位の前の姿と違うので、I16 により判定が効かなくなる。直し方：単位に記録が2つ以上あるときは、I33 の判定した値の前後が意図の順に単位の前の姿から後の姿まで途切れずにつながるか（1つめの前＝単位の前、各意図の後＝次の意図の前、最後の後＝単位の後）を基盤が確かめ、つながるときだけ効くものとして意図ごとに分けて見せる。つながらない、または I33 の判定の記録が無い意図があれば、その単位は分けられないとして例外「単位がまとめられた」に出す。変更の例外の値オブジェクトの一覧にこの1つを足す（推測：この規則は判断基準には無く、I16 と A3 の書き換えから導いた）
15. **A9 例外の書き方は、同じ言葉を崩さないか**  
   #7：本体の欄が持つ x-prompt は、Concrete の欄の x-prompt と同じ $defs/prompt の形で、同じ意味である。1つの用語に1つの意味を保つので足してよい。#22：ビューを任意にすると、I26 とビューの集約の「1つの kind に向くビューは1つ」と食い違う。「1つまで」に直す。既定の描き方は Semantic Schema Renderer の振る舞いとして書く
16. **適用したあと、担い手が消える使う場面は無いか（変更の記録の側：U2 ・ U5 ・ U6 ・ U7 ・ U13 ・ U25）**  
   A2 を案のまま適用すると、U25 の失敗条件「基盤を通らずに変えた欄は、そうだと分かる」と I31 の「記録の無い書き換え」の欄の単位の担い手が無くなる。A2 を直した形（変更の項目を残す）なら担い手は v2 と同じ。U13 の「どの欄を変えたか」は、操作 (1) ・ (2) ・ (3) と「変更を見せる」が持ち、まとめられた単位では A8 の直した形の I33 の判定の記録が持つ
17. **担い手の確認（取り込み：U18）**  
   I22 の「同じ対象の同じ欄を両方で変えた」は、v2 から変更の仕組みの衝突に任せている。A3 で合流点がアダプターへ移り、ポートには合流点を得る操作が無い。1つの欄が複数行にまたがると、Git は両側の変更を衝突なしに合わせることがある（判断基準の範囲外）。これは A2 〜 A3 で新しく生じた穴ではないが、担い手が変更の仕組みだけであることを I22 に明記するか、欄の単位で確かめるなら、まとめ方で受け取る前後に合流点を足す。どちらにするかは利用者の判断
18. **担い手の確認（判定 ・ セッション ・ 描画：U0 ・ U8 ・ U10 ・ U12 ・ U16 ・ U27）**  
   U8 ・ U10 ・ U16 は判定の記録が持ち、A4 の直した形で識別が対象 × rule になっても担い手は変わらない。U27 はセッションの集約が持ち、A5 で I46 の守り手がアダプターの一意の索引と明記される。U12 はビューが任意になっても Renderer の既定の描き方が持つ。U0 は状態を導くが持ち、I33 を使わないことは変わらない。消える担い手は無い
19. **外せるもの（足す前に引く）**  
   (1) A6 の基盤を通る捨て方のコマンド。(2) 判定の記録の ULID の id（識別を対象 × rule にすれば要らない。I37 の打ち合わせずに一意な id は変更の記録にだけ要る）。(3) A4 を独立の規則として書くこと（識別から導かれる）。(4) A3 の操作 (2) を単位の中身へ置き換え、操作を増やさない。変更の項目は外せるものに入れない

## 根拠

| 判断基準 | 引用 |
|---|---|
| aggregate | 対応：一貫性を保証する対象を、集約の業務ロジックが必要とするデータだけに限定し、集約をできるだけ小さく設計する ・ 理由：集約の全体が1つのトランザクションの単位なので、大きくすると不必要に複雑になり、性能やスケーラビリティが低下しやすい |
| aggregate | 問い：集約の業務ロジックが、その情報に強い一貫性を必要とするか ・ 「はい」なら：集約の内側に置く |
| aggregate | 問い：結果的に整合していればよい情報か ・ 「はい」なら：境界の外側（例：別の集約）に置き、ID で参照する |
| aggregate | 場面：業務ルールが他の状態に依存する ・ 内容：あるオブジェクトの業務ルールが、別のオブジェクトの状態に依存している |
| aggregate | 対応：1つのトランザクションで変更する集約は1つにし、複数の集約の状態は集約ごとに別々にコミットする ・ 理由：一貫性を維持する境界の定義が、正しいことを保証する |

## 注意

| アンチパターン | リスク | 代替案 |
|---|---|---|
| 複数の集約への変更を、1つのトランザクションとしてコミットしようとする | A1 の「変更の記録はその単位に入る」を、変更の記録とインスタンスを1つの集約として強く整合させる意味に読むと、I31 の結果整合と取り込み時の突き合わせが要らないように見え、突き合わせを外す誤りにつながる | 同じ単位で確定するのは外の変更の仕組みの都合と書き、変更の記録とインスタンスは別の集約のまま、取り込みの時点で両方向に突き合わせる |
| （推測）外の仕組みの前提をポートの契約に残す | 単位の参照と姿の参照を同じものとして扱うと、スナップショットのアダプターで操作 (1) の前の姿が得られず、ポートが Git でしか実装できない | 単位の中身（前の姿 ・ 後の姿 ・ 出した者 ・ 時刻）を返す操作をポートに置き、単位と姿を別の参照として扱う |
| （推測）外が破りうる約束を基盤の不変条件にする | 1単位＝1意図を不変条件にすると、squash ・ 手作業のコミットで基盤の不変条件が破れ、基盤の側で直せない | 期待する確定の仕方として書き、破れたら変更の例外「単位がまとめられた」に出す |
| （推測）導けない値を、導ける値と見なして外す | 変更の項目を前後から導けると見なして外すと、入口を通らずに変えた欄が意図の変更として数えられ、U25 の失敗条件が守れない | 変更の項目を「入口がその呼び出しで書いた対象と欄」として残し、前後の値は持たない |

## 差し戻し

| 疑われる上流（advisor ・ 判断） | 疑う理由 |
|---|---|
| usecase-advisor（U25 の失敗条件） | A2 を適用するかは、U25 の「基盤を通らずに変えた欄は、そうだと分かる」を欄の単位で保証し続けるかで決まる。保証を単位の粒度へ下げてよいなら、先に U25 を直してから A2 を適用できる |
| platform-advisor（U18 ・ I22 と Git の merge） | 1つの欄が複数行にまたがると、両側の変更が衝突なしに合わさることがある。I22 を変更の仕組みの衝突だけで受け持てるかは、ファイルの書き方（1欄1行か）と合わせて確かめる必要がある |

## 次にすること

- A2 を適用するかを、U25 の失敗条件を欄の単位で残すかと一緒に利用者に聞く
- A3 の操作 (2) を「単位の中身」に置き換えて、ポートの契約を書き直す
- 判定の記録の識別を対象 × rule にし、judgment.schema.json の id と置き場所を直す
- I46 を集合への rule として一員 session に書き、DDL の一意の索引との対応表を作る
- A8 のつながりの規則を、squash したシミュレーションの場面で確かめる
- I26 とビューの集約を「1つまで」に直す
