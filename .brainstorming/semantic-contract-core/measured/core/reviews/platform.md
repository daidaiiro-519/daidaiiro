## 結論
| 判定 | 結論 | なぜ |
|---|---|---|
| 条件付きで採る | 置き場所の分け方と、DB の一意の索引で I46 を守る設計は成り立つ。ただし A3 ・ A8 ・ db.sql に、満たしていない条件が7つあり（6つは実測、1つは推測）、それを契約に書き足すか外すまでは採らない。 | REL 9 の「バックアップするか、ソースから作り直せるようにする」に対し、正本はコミットするファイル、手元の DB は失ってよいと決めてあるので、置き場所は成り立つ。一方で、浅い clone では対象の履歴と消した ID の履歴が0件で返る ・ 未確定の後の姿に新しいファイルが入らない ・ squash で後ろの意図の判定の記録が効かなくなる ・ 決めてから登録までの間に2つ目の AI ツールが立つ、を実測し、これらは REL 4 のべき等と同時実行コントロールの基準を満たしていない。 |

## 図で確認する
正本（コミットするファイル）と手元の DB と、変更の仕組みへのポートの関係。破線は、失ってよい ・ 作り直さない流れ

- 基盤 → コミットするファイル（インスタンス ・ 変更の記録 ・ 判定の記録）（読む ・ 書く）
- 基盤 → 手元の SQLite（セッション ・ 手元のセッションの索引）（読む ・ 書く（正しさの判定に使わない））　［破線］
- 基盤 → ポート：変更の前後を受け取る（4操作）（前後 ・ 出した者 ・ 対象の履歴 ・ 消した ID の履歴）
- ポート：変更の前後を受け取る（4操作） → Git アダプター（実装）
- ポート：変更の前後を受け取る（4操作） → スナップショットのアダプター（実装）
- 確定（1単位＝1意図） → コミットするファイル（インスタンス ・ 変更の記録 ・ 判定の記録）（4操作のどれでもない書く操作）　［破線］

## 判断の道筋
| 問い | 答え |
|---|---|
| 1. A3 の4操作は、Git 以外でもアダプターだけで満たせるか | 条件付きで満たせる。(1) 前後：Git では未確定の後の姿に新しいファイルを入れる必要がある（実測：git diff HEAD --name-only は inst/a.json だけを返し、新しい変更の記録 rec/c1.json を返さない。git status --porcelain --untracked-files=all は ?? rec/c1.json を返す）。スナップショットでも、前の姿を保存してあれば満たせる（推測）。(2) 出した者：Git の author は書いた者の申告で、別名でコミットできる（実測：author=someone-else、署名=N）。スナップショットには出した者が無い。返す値に「変更の仕組みが約束していない」を置かないと、I18 を守れない。(3) 対象の履歴 ・ (4) 消した ID の履歴：浅い clone では0件で返る（実測：depth 1 で git log -- inst/a.json と --diff-filter=D がどちらも空、完全な clone では4件と1件）。スナップショットでは、すべての姿を消さずに持つことが条件になる（推測）。満たせないのは、4操作の外にある「確定する」（A1 が単位を作る書く操作）で、スナップショットの仕組みでは誰が単位を作るかが決まらない |
| 2. 手元の DB の一意の索引で I46 を守る設計は妥当か | 行の不変条件としては妥当。2つのプロセスが同時に登録すると、一意の索引が1つだけを通す（実測：T2 成功、T1 は UNIQUE constraint failed）。ただし「決める」と「登録」の間に AI ツールの起動が入るので、2つの端末が両方とも「新しく立てる」を受け取り、負けた側の AI ツールが登録されないまま動く（同じ実測）。DB の外のこの状態は、索引では防げない |
| 3. db.sql に、不変条件を迂回できる操作があるか | ある。閉じた行を DELETE して同じ ID を open で入れ直すと、I45 の no_reopen を通る（実測：両方通った）。子の目的を親と違えても通る（I44 の後半は未実装。実測）。PRAGMA foreign_keys を ON にしない接続では、無いセッションへの索引の行も無い親も入る（実測）。同じ値で purpose_ref を UPDATE しても fixed_at_creation が断る（実測）ので、アダプターは全列の UPDATE を出せない |
| 4. 同時に書く ・ 壊れた ・ 消えたときの振る舞いは決まっているか | 同時に書く：WAL で読みは書き込み中も通る（実測）。書きは待ち時間 0 なら database is locked で即座に失敗する（実測）ので、待ち時間を決めて書く必要がある。消えた：I40 が「作り直さず新しく立てる、コミットした記録は失わない」と決めており、A6 が索引を正しさの判定に使わないので成り立つ。壊れた：決まっていない。開くときに壊れを検出したら、消えたときと同じ扱いにする手順を必要とする（推測） |
| 5. A1（承認ごとに1単位）は、失敗と再実行に耐えるか | 1単位の確定は Git ではアトミックなので、REL 8 の「うまく終わるか何も変わらないか」を満たす。再実行への備えは書かれていない。I37 の変更の記録の id を、確定の重複を検出する一意の識別子に使えば、新しい仕組みを足さずに済む |
| 6. squash ・ rebase で単位が変わっても成り立つか | rebase：単位の参照は変わる（実測：6cbf2b0… → b621537…）が、A3 で参照は基盤が解釈しない文字列になり、判定した値は参照ではなく値を持つので、記録は壊れない。読んだ欄の前の値が変わったときだけ判定が効かなくなり、聞き直す。squash：2つの変更の記録が1単位に入る（実測：rec/c1.json と rec/c2.json が1コミット）。A3 で「判定した値」の前の値を「その記録が入った単位の前の姿」と書き換えると、2つ目以降の意図の I33 の判定の記録は、前の値が単位の前の姿と合わず効かなくなる。A8 に、まとめられた単位での比べ方を足す必要がある |
| 7. 外せるものはあるか | 3つある。A6 の前半（基盤を通って捨てたら索引の行も消す）：後半の「見せる時に見つからない行を確定しなかったとして出す」だけで同じ結果になる。I38 の最後の節（セッション ID を受け取らなければ、セッションが無いと索引に残す）：db.sql の session_changes は tool ・ id が NOT NULL で sessions を参照するので書けず、目的の参照はコミットする記録が持つので必要としない。dbcheck.py の「閉じたオーケストレーターのあとに、新しく開く」の場面は closed の行を入れているだけで、新しく開く場面を確かめていないので、open の行に直すか外す |

## 根拠
| 判断基準 | 引用 |
|---|---|
| rel-09 | ベストプラクティス：「バックアップが必要なすべてのデータを特定してバックアップする、またはソースからデータを再現する」 ・ 望ましい成果：データソースを見つけて重要度で分け、RPO をもとにデータの復旧戦略を決める。戦略は、データソースをバックアップするか、ほかのソースから作り直せるようにするかのどちらかを含む。データを失ったら、その戦略で、決めた RPO と RTO の範囲でデータを復旧するか作り直す |
| rel-09 | バックアップが必要か、ほかのソースから作り直せるかを評価していない |
| rel-04 | ベストプラクティス：「変更操作をべき等にする」 ・ 何をするか：べき等なサービスは、各リクエストを1回だけ処理すると約束する。同じリクエストが何度届いても、効き目は1回分だけである。間違って二重三重に処理されるおそれが無いので、クライアントは気軽に再試行できる |
| rel-04 | 必要なら、同時実行コントロール（ロック、トランザクション、オプティミスティック同時実行コントロールなど）で、一貫性と原子性を保つ。トークンを記録する操作と、そのリクエストに関わる変更操作をひとまとめにする |
| rel-04 | 一意の識別子を使う。べき等にするオペレーションのリクエストに、一意のトークンを、リクエストそのものか、HTTP ヘッダーのようなメタデータとして入れる。トークンによく使うのは UUID（「Universally Unique Identifiers」）と KSUID（「K-Sortable Unique Identifiers」）である |
| rel-04 | タイムスタンプをべき等性のキーにする |
| rel-08 | ベストプラクティス：「イミュータブルなインフラストラクチャを使用してデプロイする」 ・ メリット：デプロイは、うまく終わるか何も変わらないかのどちらかになり、信頼できるアトミックデプロイになる |
| ops-06 | ベストプラクティス：「変更の失敗に備える」 ・ 望ましい成果：失敗したときのために、変更ごとに細かな復旧計画を持っている。ほかのワークロードコンポーネントへの影響を抑えるため、リリースを小さくする。そうして、失敗で起きうるダウンタイムが縮み、復旧の時間に融通が利き効率も上がり、ビジネスへの影響が軽くなる |

## 注意
| アンチパターン | リスク | 代替案 |
|---|---|---|
| ポートが「探していない」を0件で返す（浅い clone ・ 消したスナップショット） | I11 の「消した ID は使い直さない」と対象の履歴（U13）が、CI の浅い clone で黙って0件になり、使い直しを取り込む（実測：depth 1 で --diff-filter=D が空） | （推測）操作 (3) ・ (4) は、探した範囲（履歴の始まりの参照、または「履歴が足りない」）を一緒に返す。範囲が足りなければ基盤は unsupported として人が見るものに出す。I42 の「0件を無いと返さない」を、このポートにも当てる |
| 未確定の後の姿を、変更の仕組みが追っているファイルだけで作る | 新しく書いた変更の記録とインスタンスが前後に入らず、I31 の突き合わせで「記録に無い」「変更の無い記録」が誤って出る（実測：git diff HEAD は新しいファイルを返さない） | （推測）操作 (1) の契約に「後の姿が未確定のとき、変更の仕組みがまだ追っていないファイルも含む」と書き、Git アダプターは作業ツリーを読む |
| 出した者を、変更の仕組みが約束していないのに約束した値として返す | Git の author は申告なので、AI が人の名前で人の判定を足せる（実測：別名で author を書けた。署名は N）。I18 の境界が名前だけになる | （推測）操作 (2) は、出した者と一緒に「約束の出どころ」（署名の検証 ・ ホスティングの合流の記録 ・ 約束なし）を返す。約束なしなら、I18 の人の判定は足せないとして取り込めない理由に出す |
| squash でまとめられた単位で、各意図の判定した値を単位の前の姿と比べる | 2つ目以降の意図の I33 の判定の記録が毎回効かなくなり、取り込んだ main で判断待ちが出続ける | （推測）A8 に、まとめられた単位では、変更の記録の前の値と後の値を値どうしでつないだ並び（ある記録の後の値＝次の記録の前の値）が、単位の前の姿から後の姿までつながれば効いている、と足す。つながらない ・ 2通りにつながるときは例外に出す。並びを時刻で決めない（REL 4 のアンチパターン「タイムスタンプをべき等性のキーにする」） |
| 「決める」と「登録」の間に AI ツールを起動する | 2つの端末が両方とも「新しく立てる」を受け取り、負けた側の AI ツールのセッションが登録されないまま動く（実測）。そのセッションで書いた変更の記録は、手元に無いセッション ID として I38 で断られる | （推測）登録が一意の索引で断られたら、立てる操作は勝った側の ID を返し、呼ぶ側に新しく起動したセッションを閉じさせる。予約の表などは足さない |
| 閉じないまま止まったセッションが、一意の索引を持ち続ける | AI ツールが落ちて再開できないと、オーケストレーターも同じ目的のセッションも新しく立てられない（推測） | （推測）「決める」は開いている行と last_used_at を返し、人の操作で閉じられるようにする。自動で閉じる時間は決めない |
| DDL の外の操作で不変条件を迂回する | DELETE と入れ直しで I45 を通る、子の目的が親と違っても通る、foreign_keys が OFF の接続では参照が壊れる（いずれも実測） | （推測）sessions への DELETE を断るトリガーと、子の purpose_ref が親と同じでなければ断るトリガーを足す。アダプターは接続ごとに foreign_keys を ON にし、busy_timeout を決める |

## 記録案
| 記録先 | 記録する内容 |
|---|---|
| A3（ポートの契約） | 操作 (1)：後の姿が未確定のとき、変更の仕組みがまだ追っていないファイルを含む。操作 (2)：出した者と約束の出どころを返し、約束が無いことを返せる。操作 (3) ・ (4)：探した範囲を返し、履歴が足りなければそう返す。(3) の並びの順は、合流のある履歴では変更の仕組みの順とし、基盤は全順序を前提にしない |
| A1（確定） | 確定は4操作の外にある書く操作で、だれが行うか（基盤か、人 ・ AI が変更の仕組みのツールで行うか）を書く。確定を繰り返しても単位が2つにならないことを、変更の記録の id（I37）で検出する |
| A8（単位がまとめられたとき） | まとめられた単位で I33 の判定の記録が効いているかは、前の値と後の値を値でつないだ並びで決める |
| SQLite アダプター（db.sql） | 置き場所の決め方（Git では git rev-parse --git-common-dir が返すフォルダ。実測で worktree からも本体の .git を返した）を、変更の仕組みのアダプターから受け取る。接続ごとに foreign_keys=ON ・ busy_timeout。DB の版は user_version。開くときに壊れを検出したら、ファイルを脇へ移して新しく作り、消えたときと同じに扱う |
| 合意済みの「セッション」（agreed.json） | 「オーケストレーターはリポジトリに1つ」の「リポジトリ」は、1つの clone（すべての worktree を含む手元）を指す。別の clone ・ 別の機械では別に数える |

## 差し戻し
| 疑われる上流（advisor ・ 判断） | 疑う理由 |
|---|---|
| A3 の書き換え（判定した値の前の値を「その記録が入った単位の前の姿」にする） | squash を前提にすると、記録ごとの前の値と単位の前の姿が一致しないので、A3 と A8 の両方を同時に直さないと I16 の「いまの値と等しければ聞き直さない」が成り立たない疑いがある |
| I38 の最後の節（セッションが無いと索引に残す） | db.sql の形で表せず、目的の参照はコミットする記録が持つので、ドメインモデルの側で必要としなくなっている疑いがある |

## 次にすること
- A3 の4操作の契約に、未確定の後の姿 ・ 約束の出どころ ・ 探した範囲の3つを書き足す。
- A8 に、まとめられた単位での判定した値の比べ方を書き足す。
- A1 に、確定を行う者と、変更の記録の id で再実行を検出することを書き足す。
- db.sql に、DELETE を断るトリガーと、子の目的を親と同じにするトリガーを足す。
- 立てる操作が一意の索引で断られたときに、勝った側の ID を返す振る舞いを、期待する振る舞いの場面に足す。
- A6 の前半と I38 の最後の節を外すかを、利用者に確かめる。
- dbcheck.py に、この回答で実測した迂回の場面（DELETE と入れ直し ・ 子の目的の違い ・ foreign_keys が OFF ・ 浅い clone）を足す。
