基盤のアーキテクチャ（案）

核（ドメインモデル ・ ポート）と Rust の原典から決め、ddd ・ platform ・ 反証役のレビュー（前提の束つき）を統合した。ポートの置き場所は、利用者の問いを受けて ddd ・ 反証役にもう一度通し、承認を得た（arch/ports/）。schema-driven と ctxtrace の実装は手本にしていない。全文 arch/reviews/

ポートとアダプター。コードを crates/ にまとめ、業務領域ごとの crate（crates/domain/）・ 使う場面とポートの application ・ 駆動される側の outbound ・ 入口の inbound に分け、許す辺を1つの表に持つ。
domain は値を受け取って値を返す関数だけを持ち、入出力は application がポートを通して行う。依存の向きは Cargo の辺と循環の禁止で止め、Cargo が止めない書き方（dev の辺 ・ feature の統合 ・ pub use ・ allow）は検査で止める。

1　なぜポートとアダプターか

核の事実構成への帰結
変更の仕組み ・ AI ツール ・ 保存を差し替えられる（利用者「アダプターが変わったとしても機能するように」）application がポート（trait）を持ち、outbound が実装する。依存は外から中への1方向
同じ入力から同じ結果（Q0 #14）・「core は入出力に触らないので変えない（Q3）」domain は値を受け取って値を返す。読む ・ 書く ・ AI への依頼は application がポートで行い、時刻と id は inbound から値で渡す
入口が複数（CLI ・ MCP ・ CI ・ 人の入口）駆動する側も業務の外に置く
中核5つは集約9 ・ 不変条件46 ・ 決定表を持つドメインモデル（ddd：ports-and-adapters「業務ロジックがドメインモデルならポートとアダプターを選択する」）中核はポートとアダプターで作る
補完（描画 ・ 移す ・ 公開）は形と参照の検査が中心（Q1 #23）移す ・ 公開は集約を持たず、ドメインサービスの関数だけ。描画とインスタンスは、モデルの集約（ビュー ・ デザインシステム ・ インスタンス）だけを持つ
基盤の内側は1つの区切られた文脈（Q9 #11）crate は文脈を分けるものではなく、業務領域の論理的な境界をビルドで守る手段。名前に contexts を使わない

6　決定的にする検査

Cargo が止めない書き方（platform が試作で実測）止める検査
dev-dependencies は循環を許す（change → fs → change が通った）cargo metadata の辺を種類（normal ・ dev ・ build）ごとに architecture.json と突き合わせる。domain から application ・ outbound ・ inbound への辺は種類を問わず0件
workspace のビルドで feature が統合される（jsonschema の取りに行く機能が入った）jsonschema は [workspace.dependencies] に default-features = false で1か所。cargo tree -e features で確かめ、業務の crate を -p で1つずつ単独にビルドする
pub use した外の crate を、書いていない crate が使えたdomain の crate からの外の crate の pub use を grep で0件
clippy の disallowed は #[allow] で外せるdomain/ の clippy を forbid にする（E0453 で止まることを実測）。主な守りは、crate ごとに許す外の crate の表
trait を通した入出力は clippy で止まらないdomain/ に trait のポートを置かない。ポートは application/src/ports/ だけに置き、domain/ の公開の関数が引数に dyn ・ impl の trait を取らないことを検査する
（設計）表に無い外の crate を足すarchitecture.json の外の crate の許可と cargo metadata を突き合わせる
