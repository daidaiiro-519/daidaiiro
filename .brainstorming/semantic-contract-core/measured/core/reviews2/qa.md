# qa-advisor の回答（設計相談）

## 相談

いま想定しているドメインモデル ・ DB ・ JSON Schema の3つは、シミュレーションで「期待する振る舞いができる」ことを合否で確かめられる形になっているか。確かめる方針と完了基準をどう設計するか。

## 前置き

| 前提 | 内容 | 出所 |
|---|---|---|
| 評価の対象 | domain-model-v2.json に decisions-in-session.md と answers-v2.json を当てたもの。abstract-draft の abstract.json ・ change.schema.json ・ judgment.schema.json ・ concrete.json ・ instances.json ・ records.example.json ・ db.sql | common.txt |
| 前提の優先順 | 利用者の指示の原文 ＞ この会話の決定（新しいほう）＞ ボードの決着の原文 ＞ domain-model-v2.json | core/premises/README.md |

## 結論

**判定：弱い**

3つはまだ、期待する振る舞いを合否で確かめられる形になっていない。検証の出力の形 ・ セッションの一員の schema ・ 判定の記録の I33 の欄が無く、記録や文書をまたぐ machine の決まりは検査するエンジンが無い（schema の書き換え8件のうち6件が素通りした）。前提どうしの食い違いが1件、前提と案の食い違いが3件ある。

**なぜ**：受け入れ基準は事前条件 ・ 入力 ・ 事後条件で書くテスト条件で、入力と出力の形が決まっていない行からはテストケースを作れない。いまの3つの検査は結果を人が読み比べるので、self-checking に直してから核の検査に使う。

### 2. 場面の書式を決める（タスク2）

1件の場面は JSON 1件で、7つの欄を持つ。Q4 #10「試験は、入力と期待結果の JSON の組で持ち」と同じ形にする。

| 欄 | 中身 |
|---|---|
| id ・ title | S-<出どころ>-<番号> と、期待する振る舞いの1文 |
| traces | 出どころの id：U<n>:事後 か U<n>:失敗時、I<n>、A<n>、会話の決定の行。空の場面は不合格 |
| adapters | 実行するアダプター（git ・ snapshot ・ sqlite と、AI の判定の Test Stub） |
| given | 前提をデータで書く：ファイル ・ 確定済みの単位 ・ 未確定の変更 ・ DB の行 ・ Test Stub が rule ごとに返す答え ・ いまの時刻 ・ 有効時間 ・ 払い出す id の並び |
| when | 入口のポートの操作を1つだけ（配列にしない） |
| then | 期待値の並び。各期待値は id ・ at（出力の JSON Pointer か、出口のポートの先の状態）・ 期待する値 ・ 外れたときの文 |
| unchanged | 操作の前後で変わってはいけないもの（契約 ・ インスタンス ・ 記録） |

起こし方は5つの規則にする。

| 出どころ | 起こす場面 | 同じ特性を2回書かない |
|---|---|---|
| 使う場面の事後条件 | 正の場面1件。事後条件の文を、1つの主張ごとに then の期待値1件へ分ける | — |
| 使う場面の失敗時 | 負の場面1件。失敗させる前提を given に1つだけ置き、when は正の場面と同じ操作 | 不変条件が同じ特性なら、この場面の traces に I を足すだけにする |
| 不変条件 | 破る操作を when に1つだけ置く負の場面。状態の不変条件は状態表の無効な遷移ごとに1件 | 使う場面の失敗時で済んでいれば作らない |
| 状態（インスタンスの4つ ・ セッションの2つ） | インスタンスは rule の結果の組を条件にした決定表の実行できる列ごと、セッションは状態表の有効と無効な遷移ごとに1件 | — |
| 実行全体の性質（I13 ・ I15 ・ Q0 #14） | 場面にしない。ランナーの実行の条件として K6 で確かめる | — |

|---|---|---|---|
| selfcheck.py | 本体 0件 ・ Concrete 0件 ・ インスタンス3件とも0件 ・ docs を消した accepted を検出。終了コードは常に0 | JSON Schema の実装に任せる部分の静的の検査（K7）として残す | 結果を人が読む出力を、期待との比較と0以外の終了に直す。change ・ judgment ・ records.example を対象に足す（probe.py ではどれも0件だった）。machine の rule ごとの悪い例を足す。annotations の仮の定義を正本の一員に替える |
| dbcheck.py | 名前に書いた期待どおりに10件とも通る ・ 断る。終了コードは常に0。「閉じたオーケストレーターのあとに、新しく開く」は closed の行を足すだけで、名前の状況を作っていない | 10件の操作は、SQLite のアダプターの試験（コンポーネントテスト）の材料にする。A5 で断るのはアダプターなので、この層の試験を必要とする | 期待を名前の括弧から then に移し、R2〜R6 の5件を足す。セッションの振る舞い（決める ・ 立てる ・ 閉じる）は、入口のポートを通す場面に移す |
| changeview.py | スナップショットでは動いた。最初のコミットでは「HEAD^」が無く終了コード1。未確定の変更は扱えない。意図2件の単位では、両方の意図が全対象に付いた。変更の項目（items）を読まない | GitAdapter と SnapshotAdapter を、ポート「変更の前後を受け取る」の参照のアダプターの元にする | 入力を「単位の参照」から A3 の「前の姿の参照と後の姿の参照」に替える。後の姿に未確定の変更（新しいファイルを含む）を許す。shape() と render() は外し、成型した JSON を出力にする |
| build.py ・ simulation.html | 10場面とも成功の流れで、失敗時の場面が無い。判定の記録に「効いているか」を持つ（C4）。場面7の事後条件「目的のセッションが閉じた」は、表（7c1e は open、b52a が closed）と合わない | 場面の並びは、正の場面の given と when の元にする | 合否の判定には使わない。場面の JSON から人が読むページを作る向きに替える |

### 5. 外せるもの（タスク4）

| 外すもの | 理由 |
|---|---|
| HTML を比べてアダプターの等しさを見ること | 描画の差で等しさが崩れる。成型した JSON を比べる |
| 完了基準の場面での本物の AI の呼び出し | 答えが回ごとに変わる。出口のポート「rule の判定を頼む」の先を Test Stub にし、答えを given で決める |
| 判定の記録に保存した「効いているか」 | schema の description と I16 が「導く」と決めている（C4） |
| changeview.py の 1単位＝1意図の成型 | A1 が不変条件にしないと決めた（C3） |
| dbcheck.py の生の SQL でセッションの振る舞いを確かめること | 振る舞いは入口のポートの場面に移し、SQL はアダプターの試験だけに残す |
| 核の完了基準から外す行：U3 ・ U4 ・ U24 ・ U26 ・ 関係の索引 | 移す ・ 公開された言葉 ・ 文脈の地図は Q4 と Q6 の公開の扱いに依存する。関係の索引は「遅いと測れてから足す」（Q1 #34）。対応表で「確かめない」にし、場面へ移る条件を書く |
| abstract.settled.json との比較 | 核の合否に関わらない。比べる元としてだけ残す |

## 注意

| アンチパターン | リスク | 代替案 |

| Manual Result Verification（selfcheck.py ・ dbcheck.py） | 終了コードが常に0で、断るはずの操作が通っても合格に見える | 期待を場面の then に持たせ、ランナーが不合格で0以外を返す |

## 差し戻し

| 疑われる上流（advisor ・ 判断） | 疑う理由 |
|---|---|
| Q11 の規則と I46（ddd-advisor ・ usecase-advisor） | 有効時間が切れたときに「新しく立てる」と「開いているのは1つまで」が両立しない（C1）。古い行を閉じる者と時点を必要とする |
| 人の入口の判定（I18 ・ I21）（ddd-advisor ・ platform-advisor） | 残る記録に入口を区別する入力が無い（R7）。CI で判定できるのか、手元でだけ判定するのかが決まっていない |
| change.schema.json の from-session（platform-advisor） | 手元の DB を読む machine の rule は、CI で同じ結果にならない（R8）。I13 と両立させる書き方を必要とする |
| A4 と judgment.schema.json | 判定の記録の識別が「対象 × rule」と ULID の id の2つになっている（C2） |

## AI が作業するときの注意

| 違反しやすい点 | 検査する方法 |
|---|---|
| 場面の期待値を、参照の実装を走らせた出力から写す | then の各期待値の traces が U ・ I ・ A ・ 会話の決定のどれかを指すかを、対応表との突き合わせで確かめ、指さない期待値を不合格にする |
| v2 の文（I44 ・ I46 ・ core）から期待値を書き、会話の決定を落とす | 対応表の各行に「期待値の出どころ」を持たせ、decisions-in-session.md に同じ id の決定がある行で v2 を指していたら不合格にする |
| 1つの場面に破る操作を2つ以上入れる | 場面の schema で when を1つのオブジェクトに限る（配列を許さない） |
| 「確かめない」に区分して全件合格にする | 「確かめない」の行が、理由と場面へ移る条件を持つかを K1 の検査で確かめ、件数を出力の先頭に出す |
