# ddd-advisor の回答：いまのドメインモデル ・ JSON Schema ・ DB は、ドメインモデルとして問題ないか

相談種別：判断相談（judgment）。回答の JSON は validate に合格した（scratchpad の ddd/reviews2/answer.json）。

## 相談

いま想定しているドメインモデル（domain-model-v2.json ＋ この会話の決定 ＋ answers-v2.json）と、それを写した JSON Schema（abstract.json ・ change.schema.json ・ judgment.schema.json ・ concrete.json）と DDL（db.sql）は、ドメインモデルとして問題ないか

## 結論

- 判定：条件付きで採る
- 結論：集約9つの境界と ID での参照は保てているが、セッションの種類 ・ 承認の記録 ・ 人の入口の記録 ・ I33 の判定した値が型として無く、JSON Schema と DDL は A4 ・ A5 と利用者の指示をまだ写していないので、直してから核にする。
- なぜ：集約の内側に置くべき情報（変更の項目 ・ 判定した値の x-prompt の文 ・ セッションの種類）が外の前後や NULL の組に任されていて、結果整合の外部を参照して不正な状態になる場面がある。名前も role ・ 親 ・ オーケストレーター ・ 変更の単位で、1つの語に2つの意味が残っている。

## 判断の道筋

1. **集約の境界は保てているか** ── 保てている。9つの集約は互いを ID（目的の参照 ・ 対象 ・ change_id ・ セッション ID）で指し、1回の書き込みで変える集約は1つである。I46 は複数のセッションをまたぐ規則で、アダプターの一意の索引が守る（A5）。dbcheck.py で、I45 ・ I46 ・ 不変条件① ・ 外部キーが断られることを確かめた
2. **値オブジェクトにすべき概念が型になっているか** ── なっていない。セッションの種類（3つの呼び名）が NULL の組でしか表されない。任せる先の参照 ・ 判定の記録の ID（対象 × rule）・ 確定の単位の参照も型が無い（F2 ・ F4 ・ F9）
3. **集約の内側に置くべき情報が外に出ていないか** ── 出ている。I33 の判定した値（前後の値 ・ 読んだ x-prompt の文 ・ 渡した引き継ぎ）と意味の欄が judgment.schema.json に無い。承認（A1）と人の入口の通過（I21）を記録する欄も無い（F6 ・ F7 ・ F10）
4. **同じ言葉か** ── role ・ 親のセッション ・ オーケストレーター ・ 変更／変更の単位／確定の単位 が、1つの語に2つの意味か、1つの意味に2つの語になっている（F3 ・ F22〜F25）
5. **スキーマと DDL は過不足なく写しているか** ── 写していない。本体の一員は3つだけで、Q6 の10ファイルのうち7つが見つからない。judgment は A4 と食い違う。ACDR の x-instance-path の {slug} は欄に無い（F9 ・ F15 ・ F16）
6. **A2 はどちらか** ── 案 X を直したものを採る（上の比較）

## 根拠

| 判断基準 | 引用 |
|---|---|
| aggregate | 問い：業務ロジックが、結果整合性だけが保証される外部のエンティティを参照すると、不正な状態になる危険があるか ・ 「はい」なら：そのエンティティを集約の内側で管理する |
| aggregate | 問い：集約の業務ロジックが、その情報に強い一貫性を必要とするか ・ 「はい」なら：集約の内側に置く |
| aggregate | 対応：他の集約は、オブジェクトそのものではなく ID で参照する ・ 理由：境界の外側であることを明確に表現し、集約ごとに固有のトランザクション境界を持たせる |
| aggregate | 対応：1つのトランザクションで変更する集約は1つにし、複数の集約の状態は集約ごとに別々にコミットする ・ 理由：一貫性を維持する境界の定義が、正しいことを保証する |
| aggregate | 対応：集約 ・ フィールド ・ メソッド ・ 業務イベントの名前を、区切られた文脈の同じ言葉で命名する ・ 理由：ソースコードは、開発者どうしや業務エキスパートとの会話で使う同じ言葉に基づいて書く。複雑な業務ロジックでは特に重要である |
| entity | 対応：ID の内部には、GUID ・ 整数 ・ 文字列や、保険証番号のような対象領域に固有の値を使える |
| entity | 対応：ID の型は値オブジェクト（例：PersonId）にする |
| value-object | 対応：状態区分やパスワードなど、対象領域に固有の概念を値オブジェクトで表す ・ 理由：同一性を値の比較で判定でき、明示的な ID フィールドを必要としない |
| value-object | 対応：妥当性を検証するロジックを、値オブジェクト自身に持たせる ・ 理由：値を設定するたびに、使う側で妥当性を検証する必要がなくなる |
| ubiquitous-language | 条件：1つの用語に1つの意味 ・ 内容：あいまいな用語を残さない。人どうしの会話なら前後関係でどちらの意味か分かるが、ソフトウェアはあいまいさをうまく扱えない |
| ubiquitous-language | 条件：同義語を使用しない ・ 内容：2つの用語を同じ意味で使わない。同義語は最初は問題に見えないが、言葉が違えば、ほとんどの場合、意図も違う |
| ports-and-adapters | ポート：業務ロジック層が定義する抽象的なインターフェースで、インフラストラクチャ層が実装する。業務ロジック層は、基盤のコンポーネントを直接には参照せず、ポートを介して連係する。 |
| domain-service | 問い：複数の集約を参照する計算のロジックか ・ 「はい」なら：業務サービスで記述すると、わかりやすくなる |

## 注意

| アンチパターン | リスク | 代替案 |
|---|---|---|
| セッションの種類を NULL の組で暗に表す（基本データ型への執着） | どの種類でもない行 ・ 親の無い目的のセッション ・ 目的のセッションの入れ子 ・ 目的の違う任せる先のセッションが DDL を通る（probe で確かめた） | セッションの種類（オーケストレーター ・ 目的 ・ 任せる先）を値オブジェクトにし、行に kind を持たせて種類ごとの CHECK と、親の種類 ・ 親の目的を見るトリガーを置く |
