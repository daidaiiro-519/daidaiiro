## 結論
| 判定 | 結論 | なぜ |
|---|---|---|
| 条件付きで採る | 置き場所の分け方と A3 の4操作は Git とスナップショットのどちらのアダプターでも満たせるが、db.sql は I44 ・ I45 ・ I46 と「入れ子にしない」を6つの経路で守れておらず（実測）、キャッシュ切れの再開の規則が一意の索引とぶつかる（実測）ので、DDL を直し前提の食い違いを決めるまでは採らない。 | REL 4 は同時実行コントロールで一貫性と原子性を保つことを求めるが、いまの DDL は DELETE と入れ直し ・ INSERT OR REPLACE ・ 外部キーを切った接続で不変条件を通し、登録はトランザクションの始め方によって database is locked で失敗する。REL 9 の「作り直せるか」は、I40 が手元の DB を失ってよいと決めているので満たす。 |

## 図で確認する
セッションの3つの種類と、親として許す向き（実線）。破線は、いまの db.sql が断らずに通した向き（実測）

- オーケストレーターのセッション（目的なし ・ 親なし） → 目的のセッション（目的あり ・ 役割なし）（親）
- 目的のセッション（目的あり ・ 役割なし） → 任せる先のセッション（目的は親と同じ ・ 役割あり）（親（目的が同じ））
- オーケストレーターのセッション（目的なし ・ 親なし） → オーケストレーターのセッション（目的なし ・ 親なし）（入れ子）　［破線］
- オーケストレーターのセッション（目的なし ・ 親なし） → 任せる先のセッション（目的は親と同じ ・ 役割あり）（任せる先の親がオーケストレーター）　［破線］
- 任せる先のセッション（目的は親と同じ ・ 役割あり） → 任せる先のセッション（目的は親と同じ ・ 役割あり）（任せる先が任せる）　［破線］
- 目的のセッション（目的あり ・ 役割なし） → 目的のセッション（目的あり ・ 役割なし）（目的のセッションの入れ子）　［破線］
- 目的のセッション（目的あり ・ 役割なし） → 変更の記録の id（session_changes）（索引）

## 判断の道筋
| 問い | 答え |
|---|---|
| 1. db.sql は「オーケストレーターは手元の DB で1つ ・ 入れ子にしない」を守れるか | 1つは守る（実測：2つ目の開いているオーケストレーターは one_open_orchestrator_session で断った）。入れ子は守れない（実測：目的なし ・ 親あり ・ 役割なしの行は3つの一意の索引のどれにも当たらず、2行とも通った）。CHECK (purpose_ref IS NOT NULL OR parent_id IS NULL) で断れる（実測）。依拠：decisions-in-session.md「その後に決めたこと」の「オーケストレーターのセッションは、手元の DB（＝リポジトリ。worktree をまたいで1つ）で開いているのは1つ。入れ子にしない。」 |
| 2. I44（任せる先の目的は親と同じ）と、任せる先の I46 を守れるか | 守れない（実測）。目的が親と違う任せる先、目的が NULL の任せる先が通る。目的が NULL だと一意の索引が NULL を別の値として扱うので、同じ親 ・ 同じ役割の任せる先が2つ開く。親の種類も確かめないので、親がオーケストレーター ・ 親が任せる先 ・ 目的のセッションの親が目的のセッション、がどれも通る。INSERT の前に親の行を引くトリガー1つで全部断れる（実測）。依拠：answers-v2.json A5「I44（任せる先の目的は親と同じ）」、decisions-in-session.md「呼ばれた子はほかの agent を呼ばず」「目的のセッション（親はオーケストレーターのセッション）」 |
| 3. I45 と不変条件①（立てた時に決めて変えない）を迂回する操作は残っているか | 残っている（実測）。開いている行も閉じた行も DELETE して別の目的で入れ直せる。INSERT OR REPLACE で閉じた行を開いた行に置き換えられる。A5 の「閉じた行の削除を断る」を DELETE のトリガーで書いても、INSERT OR REPLACE は recursive_triggers が OFF（既定）の接続ではそのトリガーを通らず開き直せた（実測：OFF で通り、ON で断った）。sessions の DELETE をすべて断るトリガーと、同じ (tool, id) が在れば INSERT を断るトリガーなら、接続の設定に依らず断る（実測）。依拠：domain-model-v2.json I45「閉じたセッションは開き直さない。」・ I44「セッション ID ・ 目的の参照 ・ 親 ・ 役割は立てた時に決めて変えない。」 |
| 4. A5 の「アダプターは外部キーを必ず有効にし」は成り立つか | 接続ごとの設定なので、sqlite3 の CLI など基盤のアダプターを通らない接続では効かない（実測：foreign_keys を設定しない接続で、無いセッションへの索引の行と無い親の行が入った）。親の行を引くトリガーは接続の設定に依らず働き、無い親を断った（実測）。session_changes にも同じトリガーを置けば、接続ごとの約束は要らない（推測：session_changes のトリガーは試していない）。依拠：answers-v2.json A5「アダプターは外部キーを必ず有効にし、閉じた行の削除も断る。」 |
| 5. Q11 の規則（キャッシュが切れたら新しく立てる）と I46 の一意の索引は両立するか | 両立しない（実測）。開いている目的のセッションが在るまま新しく立てると UNIQUE constraint failed で断られる。オーケストレーターも同じ。古い行を閉じれば立てられるが、Q11 #2 は閉じる契機を3つに限っており、キャッシュ切れは入っていない。前提どうしの食い違いなので、差し戻しに書いた。依拠：board-answers.json Q11 #2「閉じるのは、利用者か親が閉じると決めたときと、AI ツールが「そのセッションは無い」と答えたときだけ」・ #3「そうでなければ新しく立てる」 |
| 6. A5 の「登録の競合」（断られた側は先に登録された ID で再開し直す）は成り立つか | 登録を1つのトランザクションにし、BEGIN IMMEDIATE で始めれば成り立つ（実測：2つの端末が同時に登録すると、後の側は待ってから先の ID を読み、再開を返した）。BEGIN（DEFERRED）で読んでから書くと、待ち時間を5秒にしても後の側は database is locked で即座に失敗した（実測）。登録は「決める」が見た開いている行（または無し）を一緒に受け取り、いまの開いている行と違えば書かずにいまの ID を返す形にすると、競合とキャッシュ切れの両方を同じ比べ方で扱える（推測）。依拠：answers-v2.json A5「『決める』と『登録』の間に2つ目が立ったら、断られた側は先に登録された ID で再開し直す。」 |
| 7. 「worktree をまたいで1つ」の手元の DB は、どこに置けば成り立つか | Git では git rev-parse --git-common-dir が worktree からも本体の .git を返した（実測）ので、そこに置けば worktree をまたいで1つになる。ただし A3 の4操作には置き場所を返す操作が無く、「worktree」は Git の語である。置き場所は基盤を起動するときの設定で SQLite アダプターに渡し、Git のアダプターを使うときの既定値を common dir にすれば、ポートに5つ目の操作を足さずに済む（推測）。依拠：user-instructions.md「Gitと同じようなことはしてほしくないからね？」、answers-v2.json G1「v2 から Git の語を外す」 |
| 8. A3 の (1) 前後を、Git とスナップショットで満たせるか | 満たせる。Git：未確定の後の姿の新しいファイルは git status --porcelain --untracked-files=all が ?? で返した（実測）。前の姿に無いファイルは git show が fatal で返る（実測）ので、アダプターは「無い（null）」と「参照に届かない（浅い clone で HEAD~1 が Not a valid object name。実測）」を分けて返す必要がある。スナップショット：diff -rq は新しいフォルダを「Only in s2: rec」とフォルダで返した（実測）ので、アダプターはファイルまで下りて組む。依拠：answers-v2.json A3「(1) 前後：…（無いものは null）」「答えられない範囲（浅い clone など）は『探していない』と返し、0件として返さない。」 |
| 9. A3 の (2) 単位の中身と (3) 消した ID の履歴を満たせるか | (2)：Git の出した者と時刻はどちらも申告で、別の名前と2001年の日付でコミットでき、署名は N だった（実測）。A3 は出した者に出どころを付けたが、時刻には付けていない。スナップショットのファイルにはファイルの持ち主と更新時刻しか無い（実測）ので、出どころは「約束なし」になる（推測）。(3)：浅い clone では git rev-parse --is-shallow-repository が true で、--diff-filter=D は空を返した（実測）。深さ N の clone では一部だけが返るので、「探していない」の真偽だけでなく探した範囲（どの単位から）を返す必要がある（推測）。依拠：answers-v2.json A3「(2) 単位の中身：単位の参照 → 前の姿 ・ 後の姿 ・ 出した者（と、その出どころ）・ 時刻。」、domain-model-v2.json I42「0件を「無い」と返さない。」 |
| 10. A3 の (4) 確定するを満たせるか | 条件付きで満たせる（実測）。対象の一覧に未追跡のファイルがあると git commit --only は pathspec … did not match で失敗し、先に git add が要る。素の git commit は、ほかの作業でステージ済みのファイルを巻き込んだ（other.txt が入った）。git add のあと git commit --only なら一覧のファイルだけが入り、ほかはステージに残った。変わっていないファイルで繰り返すと nothing to commit で終了コード1になる。基盤が (4) を再試行するとき、「変わったものが無い」と「失敗」を区別して返さないと、成功済みの確定を失敗と取り違える。スナップショット：後の姿を新しいフォルダへ写し、その名前を単位の参照にすれば満たせる（推測）。依拠：answers-v2.json A3「(4) 確定する：対象のファイルの一覧と説明 → 単位の参照。」・ A1「承認したら、基盤がポートの『確定する』を呼ぶ。」 |
| 11. 外せるものはあるか | 4つある。(a) A5 の「アダプターは外部キーを必ず有効にし」：トリガーをスキーマに置けば、接続ごとの約束が要らない。(b) A5 の「閉じた行の削除も断る」：「行を消さない ・ 同じ ID を入れ直さない」の2つに置き換えると、閉じた行だけの特別扱いが要らない。(c) one_open_delegate_session の purpose_ref の列：I44 をトリガーで守れば、目的は親で決まるので、一意の索引は (parent_tool, parent_id, role) で足りる（推測：試していない）。(d) fixed_at_creation の「同じ値の UPDATE も断る」振る舞い：WHEN OLD.x IS NOT NEW.x を付けると、行の全体を書くアダプターも通り、変える書き込みだけを断る（実測）。外せないもの：last_used_at（Q11 #3 の規則が使う）・ 閉じた行（I45 のため ID を使い直さない）・ (3) 消した ID の履歴（I11） |

## 根拠
| 判断基準 | 引用 |
|---|---|
| rel-04 | 必要なら、同時実行コントロール（ロック、トランザクション、オプティミスティック同時実行コントロールなど）で、一貫性と原子性を保つ。トークンを記録する操作と、そのリクエストに関わる変更操作をひとまとめにする |
| rel-04 | ベストプラクティス：「変更操作をべき等にする」 ・ 何をするか：べき等なサービスは、各リクエストを1回だけ処理すると約束する。同じリクエストが何度届いても、効き目は1回分だけである。間違って二重三重に処理されるおそれが無いので、クライアントは気軽に再試行できる |
| rel-05 | べき等でないサービスの呼び出しを再試行する |
| rel-09 | ベストプラクティス：「バックアップが必要なすべてのデータを特定してバックアップする、またはソースからデータを再現する」 ・ 望ましい成果：データソースを見つけて重要度で分け、RPO をもとにデータの復旧戦略を決める。戦略は、データソースをバックアップするか、ほかのソースから作り直せるようにするかのどちらかを含む。データを失ったら、その戦略で、決めた RPO と RTO の範囲でデータを復旧するか作り直す |

## 注意
| アンチパターン | リスク | 代替案 |
|---|---|---|
| 不変条件を、接続ごとの設定（foreign_keys ・ recursive_triggers）に頼って守る | 設定しない接続で、無い親 ・ 無いセッションへの索引の行が入り、INSERT OR REPLACE で閉じた行が開き直る（実測）。依拠：answers-v2.json A5「アダプターは外部キーを必ず有効にし、閉じた行の削除も断る。」 | （推測）スキーマに置くトリガー（行を消さない ・ 同じ ID の INSERT を断る ・ 親の種類と目的を確かめる ・ session_changes のセッションが在るかを確かめる）で守る。設定に依らず働くことは、session_changes を除いて実測した |
| 一意の索引の列に、NULL になりうる列を入れる | 目的が NULL の任せる先が、同じ親 ・ 同じ役割で2つ開く（実測）。依拠：decisions-in-session.md「任せる先のセッションは目的 ・ 親 ・ 役割が同じで1つ。」 | （推測）任せる先の目的を親と同じにするトリガーで NULL を断つか、索引の列を NOT NULL の列（親 ・ 役割）だけにする |
| 読んでから書く登録を BEGIN（DEFERRED）で始める | 2つの端末が同時に登録すると、待ち時間を決めても後の側が database is locked で失敗し、AI ツールのセッションだけが残る（実測）。依拠：answers-v2.json A5「断られた側は先に登録された ID で再開し直す。」 | （推測）登録は BEGIN IMMEDIATE で始め、「決める」が見た開いている行と、いまの開いている行を比べてから書く。違えば書かずにいまの ID を返す |
| (4) 確定するを、変わったものが無いときに失敗として返す | 確定のあとで基盤が落ちて再試行すると、Git は nothing to commit で終了コード1を返し（実測）、成功済みの確定を失敗と取り違える。REL 5 のアンチパターン「べき等でないサービスの呼び出しを再試行する」に当たる。依拠：answers-v2.json A1「承認したら、基盤がポートの『確定する』を呼ぶ。」 | （推測）(4) は「変わったものが無い」を失敗と別の値で返す。Git のアダプターは git add のあと git commit --only で一覧のファイルだけを入れる |
| (3) 消した ID の履歴で、探したかどうかだけを返す | 深さ N の clone では一部の履歴だけを探し、その外の使い直しを見落とす（推測。深さ1では空を返したことを実測）。依拠：domain-model-v2.json I42「探した結果には探した範囲（…）を付け、範囲の外は探していないと返す。」 | （推測）(3) は探した範囲（どの単位までさかのぼったか）を一緒に返し、範囲が足りなければ基盤は unsupported として人が見るものに出す |

### 前提の外の指摘
| アンチパターン | リスク | 代替案 |
|---|---|---|
| 2つの端末が、同じオーケストレーターのセッションを同時に再開する | （推測）AI ツールが同じ会話に2つのプロセスから書くと、会話の中身が分かれるか、片方の書き込みが失われる。前提は「同じ ID で再開する」とだけ決めている | （推測）AI ツールのアダプターごとに、同じ ID を同時に再開してよいかを確かめ、だめなツールでは「決める」が使っている最中かを返す。基盤の DB には仕組みを足さない |
| 手元の DB を、ネットワーク上のファイルシステム（WSL の /mnt/c など）に置く | （推測）SQLite のロックが効かず、一意の索引の比べ方が成り立たない | （推測）置き場所の設定で、ローカルのファイルシステムかを起動時に確かめる |

| A5（セッションと索引の行の形） | 登録は BEGIN IMMEDIATE の1つのトランザクションで、「決める」が見た開いている行と比べてから書く。違えば書かずにいまの ID を返す。「外部キーを必ず有効」「閉じた行の削除を断る」はスキーマのトリガーに置き換える |
| A3（ポートの契約） | (1)：「無い（null）」と「参照に届かない（探していない）」を分ける。(2)：時刻にも出どころを付ける。(3)：探した範囲を返す。(4)：未追跡のファイルを含めて一覧のファイルだけを確定し、ほかのステージ済みのファイルを入れない。「変わったものが無い」を失敗と別に返す |
| dbcheck.py | この回答で実測した経路（入れ子のオーケストレーター ・ 目的の違う任せる先 ・ 目的が NULL の任せる先2つ ・ 親の種類 ・ DELETE と入れ直し ・ INSERT OR REPLACE ・ foreign_keys を設定しない接続 ・ キャッシュ切れの新しく立てる ・ 同時の登録）を場面に足す。「閉じたオーケストレーターのあとに、新しく開く」は closed の行を入れているので、閉じてから open の行を入れる場面に直す |

## 差し戻し
| 疑われる上流（advisor ・ 判断） | 疑う理由 |
|---|---|
| board-answers.json Q11 #2 と #3、decisions-in-session.md の I46（前提どうしの食い違い） | #3「そうでなければ新しく立てる」には、古い開いている行を閉じることが要る（実測：閉じなければ一意の索引が断る）。#2「閉じるのは、利用者か親が閉じると決めたときと、AI ツールが「そのセッションは無い」と答えたときだけ」はキャッシュ切れを契機に入れていない。立てる操作が古い行を同じトランザクションで閉じると決めるか、#3 を変えるかを決める必要がある。オーケストレーターにもこの規則を当てるかも決まっていない（利用者「他のターミナルで開きたくなったらそのsessionIDでResumeすればいい」） |
| domain-model-v2.json I46 と、decisions-in-session.md の I46（前提どうしの食い違い） | v2 の I46「目的の参照 ・ 親 ・ 役割が同じで開いているセッションは1つまで」と、決定「同じ目的は親が違っても1つ」が違う。優先順で決定が勝ち、db.sql も決定に従っているが、G1 の書き換えの一覧に I46 が無い |
| decisions-in-session.md「Q11 の不変条件①は任せる先のセッションにだけ当てる」と domain-model-v2.json I44（前提どうしの食い違い） | ①は「ID ・ 目的 ・ 親 ・ 役割は立てた時に決めて変えない。子の目的は親と同じ」の2つを含む。決定を文のとおり読むと、目的のセッションとオーケストレーターは ID ・ 目的を変えてよいことになる。answers-v2.json A5 は「I44（任せる先の目的は親と同じ）」と後半だけに読んでおり、db.sql は前半をすべての行に当てている。どちらに読むかを決める必要がある |
| decisions-in-session.md「目的のセッション（親はオーケストレーターのセッション）」と「親のセッションは人 ・ harness が立てても基盤が立ててもよい」（前提の欠け） | 目的のセッションが親を持たずに立てるのを許すかが決まっていない。db.sql は通す（実測）。利用者の「最上位のセッションはでもオーケストレーターではあるよね」に従うなら、親の無い目的のセッションを断る |
| domain-model-v2.json I38（前提の欠け） | 「そのセッションの目的の参照を、その呼び出しで書くすべての変更の記録に写し」は、目的を持たないオーケストレーターのセッション ID を受け取ったときの振る舞いを決めていない。閉じたセッションの ID を受け取ったときに書いてよいかも決まっていない |

## AI が作業するときの注意
| 違反しやすい点 | 検査する方法 |
|---|---|
| DDL を直すとき、DELETE のトリガーだけで I45 を守ったつもりになり、INSERT OR REPLACE の経路を残す | recursive_triggers を設定しない接続で、閉じた行に INSERT OR REPLACE で open の行を入れ、断られるかを dbcheck.py で確かめる |
| dbcheck.py を PRAGMA foreign_keys=ON の接続だけで走らせ、設定しない接続の経路を見落とす | 同じ場面を foreign_keys を設定しない接続でも走らせ、結果が同じかを比べる |
| 登録のコードを、ライブラリの既定（BEGIN DEFERRED）のトランザクションで書く | 2つのプロセスから同時に登録する試験を置き、片方が database is locked で終わらず、先の ID を返すかを確かめる |
| Git のアダプターの (4) を素の git commit で書き、ステージ済みのほかのファイルを確定に入れる | 一覧に無いファイルをステージしてから (4) を呼び、確定した単位にそのファイルが無く、ステージに残るかを試験で確かめる |
