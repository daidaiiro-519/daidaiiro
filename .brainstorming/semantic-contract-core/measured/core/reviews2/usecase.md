# 相談

いま想定しているドメインモデル（domain-model-v2.json に decisions-in-session.md と answers-v2.json を適用したもの）・ JSON Schema（abstract-draft の change ・ judgment ・ abstract ・ concrete）・ DB（db.sql）で、変更の記録 ・ 判定の記録 ・ セッションに関わる使う場面（U2 ・ U5 ・ U6 ・ U7 ・ U13 ・ U16 ・ U18 ・ U25 ・ U27）の事後条件と失敗時は成り立つか。build.py の場面の並びをどの経路に対応づけ、シミュレーションのシナリオをどう起こすか。A2 の2案で U13 ・ U25 はどう変わるか。何を外せるか

## 結論

**判定：弱い**

9件のうち、いまの3つ（ドメインモデル ・ スキーマ ・ DB）だけで事後条件と失敗時が成り立つものは無い。一番大きい穴は、判定の記録のスキーマが A4 ・ Q1 #49〜#51 に追いついていないことと、記録から確定の単位を引く操作がポートに無いことで、U2 ・ U13 ・ U18 ・ U25 がここで止まる

**なぜ**：成功時保証は実際に起きたことを基準に書き、最低保証はどう終わっても真になる文で書く。判定の記録が ULID のファイル名（U18 の衝突が起きない）で、読んだ x-prompt の文 ・ 前後の値 ・ 意味の欄を持たない（U2 ・ U25 の判定ができない）いまの形では、文を書いても保証にならない。

## 設計の手順

1. **保証の文を先に直す** ── 記録案の対（変更前 → 変更後）を当ててから経路を起こす。直すのはスキーマ ・ DB の欄が足りないもの（判定の記録 ・ change.schema の items）と、使う場面の文が決定に追いついていないもの（U7 の「同じ変更」・ U27 の主アクター）の2種類
2. **build.py の10場面を、主シナリオの鎖として残す** ── 場面の並びは U1 → U27 → U5 → U16 の主シナリオに対応する（具体例の表）。場面ごとに uc ・ 経路（主か拡張の番号）・ checks（確かめる保証の1文）を足す。場面10のあとに「基盤が確定する」（A1）の場面を足し、主シナリオを成功時保証まで届かせる
3. **足りない経路を拡張として起こす** ── 拡張条件は基盤が検出できる句に「：」を付けて書く（例「確定が断られた：」「キャッシュの有効時間が切れていた：」）。候補は4つの型から必ず出す ── 支援アクター（変更の仕組み ・ AI ツール ・ 手元の DB）が答えない ・ 誤った形で答える／記録と前後が食い違う（7種類の例外 ・ A6 の確定しなかった記録 ・ A8 のまとめられた単位）／validator の error ・ unsupported／人の入口を通らない書き換え
4. **拡張を、分岐元の場面の事後から始める1回にする** ── 各拡張は「主シナリオの n へ戻る」か「失敗で終わる」で閉じる。事前は分岐元の場面の事後（ファイル ・ DB の行 ・ 確定済みの単位）を写して用意し、ほかの拡張の結果に頼らない。1経路が1回のシミュレーションで、checks の文が事後の状態で真かを機械で見る
5. **A2 を決めてから U13 ・ U18 ・ U25 の経路を流す** ── 2案で checks の文が変わる（比較した案）。決める前に流すなら、同じ経路を案 X と案 Y で2回流し、どの checks が落ちるかを並べて利用者に見せる
6. **技術のバリエーションは同じ経路をアダプターだけ替えて流す** ── 変更の仕組み（Git とスナップショット）で U25 ・ U13 ・ U18 の経路を2回流し、事後の状態と見せる出力が同じかを見る（state-image.html の「Git と同じ画面が出た」を経路の単位で確かめる）

## 根拠

| 判断基準 | 引用 |
|---|---|
| success-guarantee | 対応：実際に起きたことを基準に書き、失敗条件と食い違う言い回しを避ける ・ 理由：ATM なら、要求額どおりに出金されない失敗条件があるので、要求された金額ではなく引き出した額で書く |
| success-guarantee | 成功時保証は、主成功シナリオが行き着く先を表す。主成功シナリオは、トリガーから始まって成功時保証を達成するところまで進まなければならない |
| success-guarantee | 条件：ほかのユースケースから呼び出されるユースケースのとき ・ 対応：成功時保証には特に気を付ける ・ 理由：成功時保証 ・ 最低保証 ・ 拡張は、呼び出し側にとって重要である |
| minimal-guarantee | 対応：処理がどこまで進んだかをログに残すことを、候補として必ず検討する ・ 理由：最もよく見られる最低保証である。回復したシステムはログで取引を再開し、利害関係者はログでトラブルを解く |
| minimal-guarantee | 対応：失敗の仕方を最低保証の欄に並べない ・ 理由：失敗の仕方は数えきれず、共通点もほとんど無い。失敗条件と処理は拡張に書くので、2つのリストをそろえる手間がかかり、食い違いも起きやすい |
| extension | 対応：条件は、検出されたことを表す句か文で書き、末尾にコロン（：）を付ける ・ 理由：「暗証番号が正しくない：」「ネットワークが停止している：」のように書けばアクションステップと区別でき、多くの誤りを防げる。できれば（必須ではない）過去形にする |
| extension | 対応：どの失敗処理でも、利害関係者の利益が守られ、ログや回復のための情報が残るかを確認する ・ 理由：書き手は途中で失敗が起きる場面を想定しないので、ログや回復の情報が抜けやすい |
| extension | ユースケースはそのまま機能テストの仕様になり、テストの一式は要求を決める時点で手に入る。拡張はそれぞれ別の道筋なので、拡張ごとに少なくとも1つのテストケースを用意し、網羅的なテストではデータの値のためにさらにテストケースを足す |
| supporting-actor | 対応：拡張条件をブレーンストーミングするときは、支援アクターからの応答が無い場合と、応答が正しくない場合を候補に入れる ・ 理由：そのときの振る舞いが要求に無いと、プログラマがその場で書ける程度の処理を書き込むことになる |
| use-case-to-test-case | ユースケースを番号を付けたテスト項目に分け、異なるパスを通すための設定を1つずつ見分けた計画を作る |
| main-success-scenario | 対応：分岐は本文から外し、成功を前提にした文にして、分岐は拡張に書く ・ 理由：成功前提の本文を読むと「そうならなかったら」と疑問がわき、読み手は拡張を探す。ユースケースに一貫したリズムが生まれ、読みやすくレビューしやすくなる |
| design-scope | 対応：すべてのユースケースのスコープ欄に、対象システムの名前を書く ・ 理由：スコープは名前や主アクターからは読み取れないので、欄で示すしかない |
| goal-level | 対応：レベルを上げたいときは、「主アクターは本当は何を望んでいるのか」と問う ・ 理由：答えが、より高いレベルの目的になる |

| アンチパターン | リスク | 代替案 |
|---|---|---|
| 確定の前に終わる場面（U2 ・ U5 ・ U6 ・ U7）の成功時保証に「変更の記録が残る」と書く | 承認されず確定しなかったとき（A6）と食い違い、保証を確かめるシミュレーションの checks が「残る」の意味（ファイルか単位か）で割れる | 「未確定の変更に置かれる」までを約束し、確定は U16 の成功時保証に書く |

- judgment.schema の judged_values に prompts ・ handoff ・ before ・ after を足し、I33 の記録だけに meaning を必須にする
- change.schema に I33 の rule を足し、items の field を任意にする
- db.sql に、任せる先の目的 ・ 任せる先の親 ・ 閉じた行の削除のトリガーを足す
- Q11 #2 ・ #3 とドメインサービスに、キャッシュが切れたときと親が替わったときの扱いを書き足す
- build.py の場面10のあとに、基盤が確定する場面を足す
- 具体例の「足りない経路」を拡張として起こし、分岐元の場面の事後から1回ずつ流す

## 関連する基準

| 判断基準 | 関係 |
|---|---|
| success-guarantee | 確定の前に終わる場面の成功時保証を「未確定の変更に置かれる」までにする判定に使った |
| minimal-guarantee | U13 ・ U16 ・ U27 の最低保証に足す文（探していない ・ 未確定の変更に残る）の判定に使った |
| extension | 足りない経路を、検出できる条件で始まる拡張として起こす手順に使った |
| supporting-actor | 変更の仕組み ・ AI ツール ・ 手元の DB の無応答と誤った応答を拡張に入れる根拠にした |
| use-case-to-test-case | 1経路を1回のシミュレーションにする起こし方の根拠にした |

## AI が作業するときの注意

| 違反しやすい点 | 検査する方法 |
|---|---|
| 判定の記録を書く実装やシミュレーションが、ファイル名に ULID を使い、同じ対象 × rule の判定を2つのファイルに残す | selfcheck.py で、judgment の x-instance-path に {id} が無いことと、同じ target と rule の組を持つファイルが2つ以上無いことを検査する |
| 変更の記録の items の field に配列の添字まで書く（build.py の CH2 の /shift/0/to） | field の JSON Pointer を Concrete に照らし、指す先が x-prompt を持つ欄かを検査する（unit-field の rule を selfcheck で実行する） |
| シミュレーションの拡張の回が、ほかの回の事後に頼って事前を用意する | 各回の事前（ファイル ・ DB の行 ・ 確定済みの単位）をその回のデータに持たせ、回の順を入れ替えて流しても checks の結果が変わらないかを見る |
| 使う場面の文に「コミット」「作業ツリー」「HEAD」など変更の仕組みの語が戻る | domain-model の use_cases ・ invariants ・ aggregates をこれらの語で検索し、0件であることを確かめる（G1） |
