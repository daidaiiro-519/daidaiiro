案どう記録するかこの場面で起きること
宣言の入口を足す（私の見解）変更の項目は残す。入口で書いた JSON は基盤が対象と欄を入れる。それ以外は AI が「意図と、書いたファイルの一覧」を宣言し、基盤が前後に出ているかを確かめて項目に入れるSKILL.md ・ agent.rs は 0197 の意図に、CLAUDE.md は 0198 の意図に付く。どちらも宣言しなかった変更は「記録に無い」

2　決めてほしいこと②：再開できないセッションを、どうするか

場面：A　目的のセッション（ACDR 0197）がキャッシュの有効時間を過ぎて開いたまま。B　端末1で Claude Code のオーケストレーターが開いたまま、端末2で Codex を始める。C　オーケストレーターが閉じたあと、その子の目的のセッションが開いたまま

いまの決着（Q11 #2 ・ #3 ＋ この会話の I46）私の見解：1つの規則にする
規則同じ目的 ・ 親 ・ 役割で開いていて有効時間内なら再開、そうでなければ新しく立てる。閉じるのは利用者か親が決めたときと、AI ツールが「無い」と答えたときだけ同じ枠（オーケストレーター ・ 同じ目的 ・ 同じ親と役割の任せる先）に開いているものがあり、このツールで有効時間内に再開できるなら再開する。できないなら、それを閉じて新しく立てる（同じトランザクション）
A新しく立てようとして、一意の索引に断られて止まる（qa ・ platform が実測）古い 0197 を閉じ、新しく立てる
BCodex は Claude Code の ID で再開できず、2つ目も立てられないClaude Code のオーケストレーターを閉じ、Codex で新しく立てる（リポジトリに1つは保つ）
C新しいオーケストレーターから見ると親が違うので「新しく立てる」になり、同じ目的は1つで断られる目的のセッションは親を問わず同じ目的なら再開する（親は立てた時のまま変えない）。有効時間を過ぎていれば A と同じ
直す決着Q11 #2 の閉じる契機に「再開できないので新しく立てるとき」を足す。#3 の「親」を、目的のセッションでは比べない
