1　点検の結果

どこ決着済みのドメインモデル私の直近の案判定
変更の記録の「変更の項目」（対象 ・ 欄）持つ。U13「どの欄を変えたか」を記録から引く外した決着に反する
変更の前後の受け取り方まとめ方：前の姿の参照と後の姿の参照の組（PR なら範囲）変更の単位1つの参照狭めた
1つの変更に入る意図の数I33 の意味は「同じ欄を2つの意図が変えた」場合を持つ1単位＝1意図新しい制約。決め直しを必要とする
判定した値の「前の値」「変更の記録を足したコミットの親（コミット前の手元なら HEAD）から取る」—決着の文そのものが Git の語
変更の記録の置き方「作業ツリーに置き、インスタンスと同じ変更でコミットされる」同じ決着の文そのものが Git の語
ポート「変更の前後を受け取る」の操作前の姿 ・ 後の姿 ・ 出した者 ・ 消した ID の履歴前後だけ「対象ごと」の経緯（U13）が必要とする操作が未決
セッション ・ 手元のセッションの索引の行の形「行の形は Abstract の一員」DDL（SQLite）だけ。一員のスキーマが無い抽象が無く、アダプターだけある
確定しなかった変更の記録—session_changes の行が残る未決
change_commits無い（索引は遅いと測れてから）足して、外した決着どおりに戻った

2　抽象設計としての穴

層在るべきものいま
ドメイン（Abstract の一員）変更の記録 ・ 判定の記録 ・ セッション ・ 手元のセッションの索引の行の形変更の記録と判定の記録の下書きだけ。セッションと索引の行の形が無い
駆動される側のポート変更の仕組みに求める操作を、変更の仕組みの語を使わずに書く操作の名前だけ。入出力の形が無く、決着の文に「コミット」「HEAD」「作業ツリー」が残る
アダプターGit ・ SQLite がポートを満たすSQLite の DDL と、Git を直接読む試作が先にできている

順番が逆になっていた：アダプター（DDL ・ 試作）を先に作り、ドメインとポートを後から合わせようとしていた

3　次にすること（私の見解）

順すること
