何が DB で、何がファイル（JSON）か

前提にしているのは、決着済みの Q1 の正本（domain-model-v2.json）と、ボードの Q1 の ER 図。私が足したものは無い

ファイル（JSON）＝ 正本。コミットして共有する

  • Semantic Concrete Schema
  • インスタンス
  • glossary ・ ビュー ・ デザインシステム
  • 変更の記録
  • 判定の記録

理由：PR と一緒にチームへ渡り、レビューされ、取り込まれる。変更の記録は「変更（PR）と一緒に共有する」（Q1 #32）。承認と取り込みは変更の仕組み（Git）に任せる（Q10）

手元の DB（SQLite）＝ その人の手元だけ。コミットしない

  • セッション
  • 手元のセッションの索引（セッション → 変更の記録の id）
  • 関係の索引（ファイルから作り直せる）

理由：セッション ID は AI ツールが手元で発行したもので、ほかの人には意味が無い。コミットする記録にセッション ID を入れない（I34）

I40インスタンス ・ glossary ・ ビュー ・ デザインシステム ・ 変更の記録 ・ 判定の記録の正本はコミットするファイルで、Concrete は保存の形を宣言しない。セッションと索引は基盤が持つ手元の DB に置き、コミットしない。関係の索引は正本から作り直せる
Q1 #28変更の記録：1件が意図1つ。…を、セッション ID の無い形で作業ツリーに置く
集約「変更の記録」書いた時に作業ツリーに置き、インスタンスと同じ変更でコミットされる
境界の表索引（手元のセッションの索引 ・ 関係の索引）は基盤が持つ。行の形は Abstract の一員、DB のスキーマ（DDL）と DB の版は基盤の SQLite アダプターが持つ

つながり：ファイルと DB をまたぐ線は1本だけ

変更の記録（ファイル）はセッション ID を持たない。どのセッションで書いたかは、手元の DB の索引（session_changes）だけが知っている。だから、チームの人は「どの目的 ・ どの意図の変更か」は分かるが、「だれのどのセッションか」は分からない（作業した本人だけが引ける。I35）。

ボードの Q1 の ER 図

変更とセッションのデータモデル：手元の DB ・ リポジトリ ・ 外に分け、集約ごとにルートと値オブジェクトを表の形で書いた。

スキーマとインスタンスのデータモデル：集約ごとに、ルート（濃い箱）と値オブジェクト（薄い箱）を表の形で書いた。ID は識別子、参照はほかを指す欄。
