結論

採る

目的を先に1文で固め、論点は「規則の形 → 言語との境目 → 出力と終了コード → 置き場所と配り方と名前」の4件に絞り、既知の違反の扱いは外す

「アーキテクチャに寄らない抽象レイヤー」は手段であり、目的（許していない辺を止める）から論点を並べないと汎用性そのものが目的になって範囲が広がる。良い抽象かどうかは、2つ目の具体（Rust 以外の読み取り、または別の構成の規則）を当てたときに仕組みを変えずに済むかで判定する

設計の手順

  1. 目的を1文にしてボードの最初に置く

    目的：ビルド道具が「辺があるか」と「循環」しか止めない言語で、リポジトリの開発者（人と AI ツール）と CI が、規則の表に無い依存の辺を、言語やアーキテクチャに依らない1つの規則の形で検出して止められるようにする。論点ではなく前提として置き、利用者の承認だけをもらう（利用者の発言から読み取れるので、案を比べる対象にしない）

  2. 論点1「規則の形」を立てる（依存の先：目的）

    問い：規則を「許す辺の表」で書くか、「層の並び」で書くか、層の並びから辺を導く書き方を持つか。辺の種類（通常 ・ dev ・ build）と、表に無い外の依存を規則に含めるか。規則が言語の語（crate ・ Cargo.toml）を持たずに書けるか。目指すこと：最初の利用者の arch.html 4節の表を、意味を落とさずにこの形へ書き写せ、「書いていない組は禁止」が規則の形だけで言える。決まると、論点2が依存グラフに持たせる属性が決まる

  3. 論点2「言語との境目」を立てる（依存の先：論点1）

    問い：判定の核が受け取る依存グラフの形（節点 ・ 辺 ・ 辺の種類 ・ 外か内か）と、言語ごとの読み取りアダプターの契約（入力は何か、グラフをどの形で返すか）。目指すこと：判定の核は依存グラフと規則だけを受け取り、cargo metadata のキーを1つも持たない。2つ目の具体（Rust 以外の言語の読み取り）を紙の上で当てて、規則と判定を変えずに足せることを確かめる。最初の版で実装する読み取りは cargo metadata の1つ

  4. 論点3「出力と終了コード」を立てる（依存の先：論点1・2）

    問い：違反をどう報告するか（どの辺が ・ どの種類で ・ 規則のどこに無いか）、機械が読む形（JSON）と人が読む形をどう持つか、終了コードを何通りにするか（違反あり ・ 規則やグラフが読めない を分けるか）。目指すこと：CI が終了コードだけで止められ、人と AI ツールが出力を読んで直す場所（Cargo.toml の行か、規則の表か）を決められる

  5. 論点4「置き場所と配り方と名前」を立てる（依存の先：論点3）

    問い：独立したフォルダの中の構成、規則のファイルを利用者のリポジトリのどこに置くか、実行ファイルとして配るか、ツールの名前。目指すこと：semantic-agent-schema が自分の CI から外のツールとして呼べ、特定の AI ツールの置き場所や変数を契約に入れずに済む。名前は目的（依存の向きの検査）を表し、最初の利用者の名前や Rust の語を含めない

  6. 既知の違反の扱いを論点から外す

    理由：最初の利用者は新しく作るので違反0件から始められる。既知の違反の記録は、一度「ある」になると「ない」へ戻りにくく、許す辺の表の外にもう1つの許可の置き場所を作る。違反0件で始められない利用者が現れたときに論点として立てる

  7. 最初の版に入れないもの（範囲の外）をボードに並べる

    ① Rust 以外の読み取りアダプターの実装（契約は論点2で決め、紙の上で当てるだけ）② 既知の違反の記録 ③ 1つの crate の中のモジュールどうしの向き（arch.html は crate を単位に向きを守ると決めている）④ domain の入出力 ・ 時刻 ・ 乱数と feature の統合の検査（clippy と cargo build -p が既に持つ）⑤ 依存グラフの図の描画 ⑥ いまのグラフから規則を作る機能と、違反の自動修正

  8. 論点1の答えが出たら、最初の利用者の表を書き写した具体を早く見せる

    規則の形は抽象のままだと判断しにくい。arch.html 4節の表をその形で書いた1枚と、わざと1辺を足したときの出力の例を、論点1と論点3の完成イメージとして並べる

注意

アンチパターンリスク代替案
手段の目的化（汎用性そのものを目的にする）「どの言語 ・ どのアーキテクチャにも」を目指して、モジュール単位の解析や複数言語の読み取りまで最初の版に入れ、最初の利用者の検査が遅れる目的の1文を各論点の判定に使い、最初の利用者の表を書き写せることを受け入れの条件にする。汎用性は2つ目の具体を紙の上で当てて確かめる
抽象なき具体化（最初の利用者の語をそのまま規則にする）domain ・ application ・ outbound ・ inbound のような層の名前や crate ・ Cargo.toml の語が規則の形に入り、ほかの構成で使えなくなる規則の形は節点の名前と辺だけで書き、層の名前は利用者の規則ファイルの中の値にする
（推測）既知の違反の記録を最初から入れる許す辺の表と別の許可の置き場所ができ、一度入った違反が減らない違反0件で始める利用者だけを最初の版の対象にし、必要になった時点で論点を立てる

次にすること

  • 目的の1文をボードの前提として利用者に承認してもらう
  • 論点1から論点4をこの順でボードに立て、各論点に「目指すこと」を書く
  • 既知の違反の扱いを外した理由と、範囲の外の6件をボードに書く
  • 論点1の候補を、arch.html 4節の表を書き写した具体で比べる
  • 論点2の答えを、Rust 以外の言語の読み取りを1つ紙の上で当てて反証する

AI が作業するときの注意

この回答の結論に、AI の作業が違反しやすい点と、それを検査する方法。工程を問わない

違反しやすい点検査する方法
論点の答えや規則のスキーマに、semantic-agent-schema の crate 名 ・ 層の名前や cargo metadata のキー（packages ・ resolve ・ dep_kinds など）が残る規則のスキーマと判定の核のソースを、最初の利用者の crate 名 ・ 層の名前 ・ cargo metadata のキーで検索し、読み取りアダプターの外で0件であることを確かめる
反証で穴が出るたびに、既知の違反 ・ 例外の注記 ・ 自動修正などの仕組みを足す足す前に範囲の外の一覧と照らし、その仕事を Cargo ・ clippy ・ Git ・ コードレビューが既に持っていないかを1行で書く
