良好

設計の手順

  1. タスク1：ツールの言葉を1つの区切られた文脈の同じ言葉として確かめ、語をそろえる

    判定：おおむね過不足ない。ただし次の4点を直す。①同義語：下書きは本文で「要素」、グラフの JSON で `nodes` と書く。同じものなので node（Cargo「Array of nodes within the dependency graph」Q153、deptrac「Collectors decide if a node」Q101）にそろえ、本文もノードと書く。②集まりの名前：group を component にする（比較した案の表）。③違反の理由：`not-allowed` は dependency-cruiser の既存の語 `not-in-allowed`（Q31）に、`ungrouped` は group を改めると成り立たないので deptrac の uncovered（Q95「--fail-on-uncovered」）にする。④欠けている語：Q3 の「一度も使われなかった allow」に名前が無い。import-linter「unmatched expressions」（Q8）・ cargo-deny「no longer matches」（Q169）・ deptrac「was not matched」（Q96）がそろって使う unmatched にする。そのまま採る語：allow（dependency-cruiser `allowed` Q31 ・ cargo-deny `allow` Q162）・ from と to（Q33）・ edge と dependency graph（Q153）・ kind（Cargo `kind` Q150）・ violation（deptrac Q93 ・ ArchUnit Q67）。採らない語：layer ・ tag ・ contract（比較した案の表）

  2. タスク2：判定の中心と読み取りの境目を、腐敗防止層と公開された言葉として確かめる

    判定：境目の切り方は正しい。①Cargo の読み取りは、上流（Cargo）のモデル packages ・ resolve ・ dep_kinds ・ workspace_members を node ・ edge ・ kind へ直すモデル変換装置で、変換は下流（このツール）の側に属する。Cargo は「It is recommended to include the --format-version flag to future-proof your code」（Q157）と出力の形の変わりうることを自分で書いており、「供給側の契約が頻繁に変更される」場合に当たる。②グラフの JSON を公開された言葉にする判断は適切。ほかの言語の読み取りは中心のモデルを変えずにこの形へ合わせる（中心から見ると、読み取りは公開された言葉に従う側）。③直すこと：公開された言葉を中心の内部の型と分ける。中心の型に serde を付けてそのまま JSON にすると、中心の型の変更がそのまま公開された言葉の変更になる。グラフと規則の JSON Schema に版（例：`"version": 1`）を持たせ、JSON から中心の型への変換は入口（または公開された言葉の型だけを持つ部品）で行う。④`kind` を中心が解釈しない決め方は、モデルを目的（許していない辺を止める）に絞る判断として適切。辺の種類で許し分ける規則を足す日が来たら、kind の値は読み取りごとの語なので、規則の側に読み取りの語が入る。足すときは、kind の値の一覧を読み取りごとに公開された言葉へ書いてから足す

  3. タスク2の続き：モデルに欠けた2つの決め事を足す

    ①node の id の決め方：規則のパターンは node の id と照合するので、id の付け方は読み取りと規則の両方が知る公開された言葉の一部になる。Cargo の読み取りは package の name を id にする（resolve.nodes の id は「path+file:///…#name@version」の形で、規則に書けない）。同じ name の外の crate が版違いで2つあれば1つの node にまとめる。id の決め方は読み取りごとに、グラフの JSON Schema の説明に書く。②1つの node が2つの component のパターンに当たるとき：下書きに決め事が無い。1語1意味にそろえるため、規則の誤り（終了コード 2）にする。deptrac は1つの要素を複数の layer に入れられる（Q90, Q101）が、最初の利用者に使う場面が無い

  4. タスク3：最初の利用者の表を規則の形へ書き写し、落ちる意味を挙げる

    判定：4節の表の内側の辺は、意味を落とさず書ける（コードの例に実物）。outbound/agents-contract → ai-cli は、ai-cli を自分だけの component にすれば書ける（ai-cli を git ・ fs と同じ component に入れると agents-contract → fs まで許してしまう）。外の crate は、crate ごとに許す先が違う所で component を分ければ書ける（sqlite → rusqlite を許すと、sqlite を fs と同じ component に置けない）。書けない、または未判定の所は3つ。①辺の種類ごとの許可：「この外の crate は dev（または build）としてだけ許す」は、kind を区別しない規則では書けない。architecture.json の「辺の種類」の欄がこれを意味するかは未判定。②外の crate の許可の値：arch.html に一覧が無く、jsonschema と rusqlite 以外は書き写せない（規則の形の欠けではなく、利用者の側の値の欠け）。③パターンの末尾の `*`：package の name は全部 semantic-agent-schema- で始まるので、outbound/* のようなフォルダの層をパターンで書けず、name を全部並べる。意味は落ちない。なお dev の辺の循環は、どの種類の辺も allow に無ければ違反で、allow 自体の循環を規則の誤りにするので、kind を区別しなくても止まる

  5. タスク4：ツール自身の内部構成を、中心 ・ 公開された言葉 ・ 読み取り ・ 入口の4つに分ける

    判定：下書きの3つ（中心 ・ 読み取り ・ 入口）は正しいが、公開された言葉の型を置く所が無い。読み取りが中心の型を使うと、Rust の読み取りだけが公開された言葉を通らずに中心へ入れるので、ほかの言語の読み取りと同じ条件で試されない。①core：node ・ edge ・ component ・ allow ・ violation の型と判定の関数。入出力をしない。外の crate に依存しない。判定はパターンの照合と許す辺の表引きと allow の循環の検査だけで、業務ルールは単純なので、集約もポート（trait）も作らない。②公開された言葉（グラフと規則の JSON の型と JSON Schema）：serde だけに依存する。③Cargo の読み取り：cargo metadata を起動し、②の形のグラフを返す。core に依存しない。④入口（CLI）：ファイルと標準入力を読み、②を core の型へ直して core を呼び、出力と終了コードを決める。ツール自身の規則ファイルでこの4つの辺（入口 → core ・ 公開された言葉 ・ 読み取り、読み取り → 公開された言葉）だけを許し、自分を検査する

根拠

判定の拠りどころにした判断基準の記述

判断基準引用
bounded-context区切られた文脈：1つの同じ言葉を小さな複数の同じ言葉へ分割し、各々を、それが通用する明確な文脈へ配分したもの。同じ言葉の一貫性を維持するための境界であり、用語の意味 ・ 業務方針 ・ 業務ルールが一貫するのは、その内側に限られる。
ubiquitous-language条件：同義語を使用しない ・ 内容：2つの用語を同じ意味で使わない。同義語は最初は問題に見えないが、言葉が違えば、ほとんどの場合、意図も違う
ubiquitous-language条件：1つの用語に1つの意味 ・ 内容：あいまいな用語を残さない。人どうしの会話なら前後関係でどちらの意味か分かるが、ソフトウェアはあいまいさをうまく扱えない
anticorruption-layer場合：供給側の契約が頻繁に変更される ・ 理由：頻繁な変更から自分のモデルを保護し、供給側の変更が影響する範囲を限定できる
anticorruption-layerモデルを作る観点では、変換によって、下流は自分の文脈に関係しない外部の概念を除外できる。その結果、下流の同じ言葉とモデルは単純で理解しやすくなる。
open-host-service公開された言葉（英語は Published Language）：共用サービスが外部に提供する通信規約（プロトコル）。内部で使用する同じ言葉には一致させず、連係の用途に特化した言葉として定義し、利用する側が使用しやすい形にする。
open-host-service対応：外部に公開するインターフェースを、内部のモデルから分離する ・ 理由：上流のモデルを変更しても下流に影響しない。公開するモデルと内部の実装を、別々の時期に変更できる
model-translation内部モデルのオブジェクトや業務イベントを、そのまま公開された言葉として外へ出すのはありがちな誤りである。区切られた文脈の内部モデルを外部に見せてしまう
conformist条件：上流の提供内容が、下流のニーズを十分に満たす ・ 対応：下流が上流のモデルを受け入れ、従属を選択できる
model対応：モデルで解決しようとしている課題、つまり目的を明確にする ・ 理由：役に立つモデルは、目的に合う内容だけを表す。目的の無いモデルは無い
transaction-script対応：外部システムと連係するアダプターとして使用する ・ 理由：一般的な業務領域で入れた外部サービスとつなぐときや、区切られた文脈どうしをつなぐモデル変換装置の一部として役立つ
transaction-script対応：業務ロジックが手続き的なデータ操作だけの、単純な問題に使用する ・ 理由：例は、データソースから抽出し、形式を変換し、出力先へ格納する ETL の操作である
ports-and-adapters条件：業務ロジックがトランザクションスクリプトかアクティブレコード ・ 対応：レイヤードアーキテクチャを選択する ・ 理由：業務ロジック層とデータアクセス層の依存関係が、これらの実装方法に適する
subdomain迷う組み合わせ：補完か一般か ・ 問い：外部のサービスを導入するより、自分たちで作るほうが簡単で費用も少ないか ・ 判定：そうであれば補完
