# 相談の材料：AI がコードの大半を書く前提での、開発プロセスの形

## 背景（2026-10-17 時点の事実）

原典は Anthropic の公開記事3本で、原文を `.brainstorming/ai-driven-process/sources/` に置いてある（2026-10-17 10:14 取得、fact-check で引用を照合済み）。

- A：How the Claude Code team does code review（claude.dev、2026-10-15）
- B：Best practices for Claude Code（code.claude.com/docs/en/best-practices）
- C：Redesigning source control at Anthropic（anthropic.com/engineering、2026-10-13）

A から読み取れる事実：

- Claude が Claude Code のコードの約90%を書く。6月〜9月に、マージした PR は2倍を超え、revert した割合は40%を超えて下がった。
- 目標は「revert と障害を増やさずに、人の時間を最小にする」。revert と障害の率をガードレールにしている。
- 7つの層がある。①人が見る前に AI が検証する（動かせる検査を渡し、出力を見せさせる。新しい文脈のサブエージェントが差分を見る）②PR ごとの AI レビュー（複数のエージェントが探し、別の組が投票）③止められるセキュリティレビュー ④CI ⑤危険度に応じた人の承認（変更が段階を決める。エージェントの承認は人の承認に数えない。頼んだ人が責任を持つ）⑥マージキュー ・ フラグ ・ 段階的なリリース ⑦すぐ見つけ、すぐ戻す。
- 人に残した判断は5つ：そもそも作るべきか ・ 危険なコード ・ 他が真似する設計 ・ 証拠を読む ・ 結果の責任。
- 変更は人が Claude に頼むところから始まる。PR を開き、意図とテンプレートを埋めるのは Claude で、人が確かめる。
- 記事には spec ・ requirement ・ acceptance ・ use case ・ performance の語が1つも出てこない（原文の HTML 全体で照合）。
- レビューは収束しなかった（1つの PR が一晩で50回を超えた。約59%は最初のレビューの時点から在ったコードへの指摘）。回数の上限 ・ 差分だけの再レビュー ・ バグの種類で指摘 ・ 重複しない、で直した。
- 障害を評価セットにし、見逃しは CLAUDE.md ・ skill ・ 新しい検査へ戻す。
- 指標が動いたときに承認を自動で厳しくする仕組みは、まだ無い。

B から：検証の手段を渡す（Claude は「終わったように見えた」ところで止まる）／ 探索 → 計画 → 実装 → コミット ／ 大きな機能は Claude に聞き取りをさせて仕様を書かせる（使える仕様は、関わるファイルとインターフェースを挙げ、範囲外を書き、エンドツーエンドの検証で終わる）／ 新しい文脈でのレビュー ／ 指摘を全部追うと過剰設計になるので、正しさと要求に関わるものに絞る。

C から：コードを書くことはもうボトルネックではない／ Claude に書き直させたら、メモリ20分の1 ・ 4倍速いものが出た（暗黙の不変条件を保ったと書いてある）／ エンジニアの役目はしばしば Claude に「no」と言うこと／ 敵対的レビューは過剰設計を招くことがある／ 人は1行ずつではなく変更の意図を見る／ Anthropic のトークンの使い方はふつうの会社と違う。

## 利用者がこれまでに決めた方向（前提として固定）

1. ATDD を土台にする。受け入れ基準はユースケースから起こす（利用者はこれを UATDD と呼んでいる）。ユースケースにするのは、目的レベルを前提に置いて振る舞いを明確にするため。
2. 受け入れ基準は、合否が一意に決まるところまで具体にし、どう作るかは抽象のまま残す。
3. 仕様の境界は、ユースケース ・ 受け入れ基準 ・ 概念モデル（DDD の高さ：語彙 ・ 集約と不変条件 ・ コンテキストの境界）・ 非機能要求まで。技術の制約は設計、クラスと関数は実装で、仕様の外。
4. 非機能要求は ATDD の中に存在させる。変更ごとに判定できるものは検査に、運用しないと測れないものは指標にする。

## いまの見解（反証してほしい）

- Q1 プロセスの骨組み：アジャイル／ウォーターフォールのどちらかを選ぶのではなく、3つのループに分ける。ループ1 妥当性確認（validation：正しいものを作っているか。人と利用者。ユースケースを立て、目的が確かでなければ AI に安い試作を2〜3案作らせて選び、選んだ振る舞いから受け入れ基準を起こす）。ループ2 検証（verification：作ったものが正しいか。ほぼ AI。受け入れ基準を検査にし、AI が全検査を通るまで実装し、新しい文脈でレビューし、基準を満たしたら止める）。ループ3 学習（見逃し ・ 障害 ・ 運用の指標を、仕様のどの層が足りなかったかで分けて戻す）。根拠：書くのが安くなり、高く残るのは「何を作るかを決める」「正しいと確かめる」「人の注意」の3つになった。
- Q2 残すものと作り直せるもの：残して育てる（人がレビューする）のは、ユースケース ・ 受け入れ基準 ・ 概念モデル ・ 非機能要求 ・ 技術の制約 ・ 検査そのもの ・ 見逃しの記録。クラスと関数は作り直せるものとして AI に任せる。ただし作り直せるのは検査が十分に強いときだけ。
- Q3 検査の強さ：品質の要は検査の強さ。AI が書いた受け入れテストが受け入れ基準どおりかを人が確かめる（人が一番時間を使う場所）。ミューテーションテストなどで検査の強さを測る。AI が書いた検査を AI が確かめると同じ思い込みが重なるおそれがある。
- Q4 ダイヤル：アジャイルとウォーターフォールは、「ループ1でまとめて決める量（ユースケース1つずつ〜リリース分を先に）」と「ループ2の後の守り（戻しやすいならフラグ ・ 段階リリース ・ すぐ戻す、戻せないなら受け入れテストの工程と厚い承認）」の2つの設定の位置として扱う。
- Q5 大きさのつなぎ方：ユースケース1つは大きいが、記事の仕組みは小さな変更を前提にしている。ユースケースの拡張やシナリオの段ごとに変更を分ける案がある。

## 聞きたいこと

上の見解 Q1〜Q5 を、あなたの専門の判断基準で反証し、採ってよいか、足りない所、別の案を出してほしい。特に担当として指定した論点を深く見てほしい。
