文脈の境界の手がかり

「判定」が2つの意味で使われている。rule の判定（インスタンスと rule の組ごとに1件、コミットするファイル）と、意図の判定（変更の記録ごとに1件、手元の表）。同じ意味か別の意味かを確かめると、意味の検証と変更の確かめのあいだに境界を引くかが決まる。

集約「変更の記録」（変更の確かめと例外の判断）

1回の変更について、意図 ・ 目的の参照 ・ 変えた欄を持ち、まとめに入るまで未確定のまま手元に残る記録。

守る条件出どころ

I2 書いた記録は消さない。書いたセッションが error で終わっても残す原文（目的のセッションを立て、ID で再開して進める（役割ごとに子のセッションに任せることを含む）（U27） ・ 役割ごとに子のセッションに任せる（N3） の最低限の保証）

I4 まとめに入った記録は、ほかのまとめに入らない推測

置かない指示：記録を消す（I2 に反する）、意図を書き換える（I3 に反する）。状態は「未確定」から「まとめに入った」へ進み、戻らない。目的のセッション ・ 変更のまとめ ・ 意図の判定は外に置き、ID で参照する。

データ（ER 図）

案どこで決めるか：基盤が用意するスキーマ の承認

Abstract の本体（型）から利用者が Concrete（スキーマ）を作り、Concrete からインスタンスを作る。この図は、承認待ちの「基盤が用意するスキーマ」の案を入れた形。SQLite の表は手元の内部の形で、JSON Schema を持たない。

矢印の数字は対応の数（N:1 なら、矢印の元が複数で先が1つ）。

call から呼ばれるものと、できるもの

call は ER 図の要素ではなく、基盤が任せる先を起動するコマンド。できるものは、どれもスキーマに従うインスタンス。決めきれず返す点だけは、インスタンスにならず呼んだ主体へ返る。

公開する契約は「任せる先の入出力」「コミットするファイル」「CLI の出力」「Concrete を書く型」の4種類だけにする。schemas/v1 は8つから7つにする。

ディレクトリ

仮どこで決めるか：区切られた文脈が決まったあと、ACDR でコードへ移す

土台のディレクトリの決まり（業務領域の下に domain と application、外側は inbound と outbound）を適用したもの。文脈が決まると根の置き方が変わる。いまのコードはまだこの形に移していない。

置き方の決まり（この事業での適用）
  • core/<業務領域>/ の下に domain（概念）と application（use_cases ・ ports）の2つの crate。1つにすると業務領域どうしの依存が循環する
  • ポートは、その会話を受け持つ業務領域の application に置く。共有の置き場は作らない
  • 外側は inbound（入口）と outbound（外の技術）。HTTP の API を足すときは inbound に足す
  • Cargo の勧め（平らに並べる）から外れることと理由は CODING.md に書き、フォルダと crate 名の一致は検査で守る
  • schemas/v1/call.schema.json は、スキーマの案では消す

実際のディレクトリ構成

図の形をファイルまで下ろしたもの。左のファイルを押すと、役割 ・ 担うこと ・ コードのイメージが出る。コードは形を伝えるための抜粋で、そのまま動くものではない。いまのコードはまだこの形に移していない（ACDR で移す）。
