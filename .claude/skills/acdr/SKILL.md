# 意思決定を、変更前と変更後の差分ごと記録するSkill：acdr

**ACDR は Any Change Decision Record である。** 分野を限定しない ── 何を決めたときでも、変更前と変更後の差分ごと残す。

## 目的

何かを決めたとき、**決定と、その差分と、なぜそう決めたかを1枚へ保存する**ために使用する。文書・コード・設計・方針のいずれでもよい。分野を問わない ── この Skill は、対象が何の仕事に属するかを認知しない。

**人は、変更前と変更後が見えていると判定が速い。** 差分が無いまま承認を求めると、「この決定は何を土台にして決まったのか」を読む側が毎回復元することになる。成熟した環境では、決定の大半が既存のものへの変更である。だから差分を既定にし、**新規のときだけ差分が空になる**。

**残すのは、承認の前と後で同じ1枚である。** 状態が `proposed` から `accepted` へ変わるだけで、記録の形は変化しない。リポジトリに置くので、差分に載り、変更の理由がPRに出力される。

---

## 役割

- 決定を、節（決定 ・ なぜ ・ 形の変化 ・ 実現の形 ・ 適用先 ・ 比較した案 ・ 承認の状態 ・ 承認後に実施すること）にする
- 変更を1件ずつ、**どこ・何から何に・なぜ**の3つ組にする
- 対象の文書を描画し、変更箇所を押すと変更前と理由が開く形にする
- **理由が欠けている変更を、記録に包含しない**
- 正本へ適用する前に見せ、承認を得てから適用する
- 承認が下りたら状態を `accepted` にして、リポジトリへ保存する

---

## 処理対象と成果物

### 処理対象

これから決めようとしていること。多くは既存の文書・コード・設計への変更で、新規のこともある。

### 成果物

**記録1件は、フォルダ1つである。**

```
.acdr/<番号>-<短い名詞句>/
  acdr.json    ← 正本。節と、変更の3つ組を保持する
  flow.svg     ← 図（組ませた相手が返す。無い場合は配置しない）
  index.html   ← 組成した成果物。acdr.json から導出される
```

**`acdr.json` が正本で、`index.html` は導出されるものである。** 同じ `acdr.json` から、実行場所に依存せず同一の `index.html` が出力される。

**中身を複製しない。** 変更後の全文は対象の文書が保持している。記録が保持するのは、節と、対象のパスと、3つ組だけである。

**`index.html` を手で直さない。** 正本は `acdr.json` である ── 手で直すと、次に組成した時点で失われる。

**承認済みの記録は封印される。** 承認後の最初の組成で、対象の文書の `sha256` が `acdr.json` へ保存される。以降、対象の文書が変化した状態で組み直そうとすると**拒否する** ── 組み直すと承認時点の姿が失われる。`--check` はその場合に「承認時点の姿である」と報告する。意図して組み直す場合は `--force` を渡す。

## 入力の想定

| 受け取る情報 | 解釈・既定値 |
|---|---|
| 決めようとしていること | 明示されなければ、直前の会話から決定を書き起こす。推測で補完しない |
| 対象の文書 | 明示されなければ、変更しようとしている文書すべてを対象とする。無ければ新規として扱う |
| 変更前の内容 | **正本の現在の中身をそのまま取る**。適用済みなら、gitの作業ツリーとHEADの差から取る |
| なぜ | 明示されなければ、そのとき何と食い違っていて何に一致させたかを書き起こす |
| 除外した案 | 明示されなければ、検討した案と、それぞれ何が成立しないかを記述する |

## 実行手順

### Step 1: 何を出す文書かを、外から取る

その文書が何を出すべきかは、その文書の中には無い。中から取ると、旧路線の記述が旧路線を残す根拠になる。成果物を決めている親文書・定義票・仕様の記述から取り、**見出しの並びだけ**で出すものが出るかを判定する。出していなければ、本文の校正に入らず骨格の案を先に出す。

### Step 2: 対象の全文を読む

頭から終わりまで確認する。検索で見当を付けて周辺のみを確認する方法を採用しない ── 置換のすり抜け、説明なしで残った旧い値、見出しと中身の食い違いは、どれも検索では検出されない。

### Step 3: 節を記入する

| 節 | 鍵 | 中身 |
|---|---|---|
| 決定 | `decision` | **決めてほしいこと1件**。能動態の完全な文で、**手段を記述しない** |
| 形の変化 | `shift` | **抽象の側の変更前と変更後**。`what` ・ `from` ・ `to` の3列 |
| 図で確認する | `figure` ・ `figure_caption` | 形の変化を図にしたもの。**この Skill は描画しない** ── 受け取るのは SVG の文字列のみである |
| 実現の形 | `how` | その決定をどう実現するか。手段はここへ配置する |
| 適用先 | `applies_to` | どの正本が変わるか |
| なぜ、いま決めるのか | `why` | 何と食い違っていて、何に一致させたか |
| 比較した案 | `alternatives` | `option` と、**`why_not`**。反証を通過しなかった案であり、未解決の懸念ではない |
| 承認の状態 | `status` | `proposed` ／ `accepted` ／ `superseded` |
| 承認後に実施すること | `after_approval` | 承認が成立したあとに実施する作業 |
| 置き換えた記録 | `supersedes` | この決定が置き換えた記録の番号 |

**鍵は ASCII で、値は人が読む日本語である。** 機械が分岐するもの（鍵 ・ `status`）と、
人が読むもの（本文）を、同じ文字体系に混在させない。

**`decision` ・ `applies_to` ・ `why` の3つは、欠けたら道具が停止する。** 欠けた記録は、あとから誰も補完できない。

### Step 4: 変更を3つ組にする

1件ずつ、**どこ**（読み手がその場所を開ける粒度）・**何から何に**（変更前の原文をそのまま。要約しない）・**なぜ**を完備させる。書けない変更は記録に含めない ── 書けないのは、変更の意図が自分でも掴めていないということである。削除も1件として扱い、消えた場所に印を配置する。

**「変更前」と「なぜ」は平文である。** タグを書いても文字として出る ── 「変更前」は原文をそのまま出す欄なので、タグを解釈してはならない。節（決定 ・ 対象 ・ なぜ）のほうは HTML を受ける。

**「どこ」は、描画したあとの本文に現れる文字列で指定する。** マークダウンの記法を含めると一致しない ── 描画後は `<b>` や `<code>` になっている。


### Step 5: 作業コピーへ適用して、1枚を組む

正本は触らない。作業コピーへ適用してから組成する。**操作は3つだけである。**

```
python3 scripts/cli.py new .acdr/0007-<短い名詞句> "題"    起こす（雛形から）
python3 scripts/cli.py validate .acdr/0007-<短い名詞句>    入力を検査する
python3 scripts/cli.py render .acdr/0007-<短い名詞句>      組む
python3 scripts/cli.py render .acdr/0007-<短い名詞句> --check 1   差が無いかを検査する
```

**入口は1つである。** どの操作も `--json` を付けると機械が読む形で出て、終了コードは `0` 正常 ／ `1` 検出あり ／ `2` 誤用である。

`acdr.json` の形は `references/acdr.schema.json` が決め、雛形は `references/spec-template.json` が保持する。**生成物ではなく、入力を検査する** ── 生成物の検査からは、複製が正しく生成されたことしか判明しない。しかも不合格の時点で HTML は既に出ている。**不合格なら HTML を1バイトも出さない** ── 検査は4系統で、形（スキーマ）・欄の完備（節と3つ組）・散文（1つの欄への主張の同居 ・ 1文の長さ ・ 段の要素の混入。引用と原文は除外する）・参照の解決（図と対象の文書の実在）である。

**面の中身は、拡張子で決まる。**

| 拡張子 | 置き方 |
|---|---|
| `.md` | 描画した見た目。印は語の単位で付く |
| **コード**（`.py` ・ `.js` ・ `.json` ・ `.go` ・ `.rs` ・ `.rb` ・ `.sh` ・ `.sql` ・ `.yaml` ・ `.toml` ・ `.css` ・ `.xml` ほか） | **Git の統合差分**。旧と新の行番号 ・ `+` / `-` ・ 文脈3行。**印は行の単位で付く** |
| それ以外（`.html` など） | そのままの見た目。CSS を隔てるので `iframe` へ流し込み、届かなければ Shadow DOM へ切り替える |

`docs` が空なら、節だけの1枚になる。

**新しい種別の枠を追加する場合は、タブの押す処理の配線と、枠の挿入先の2点を確認する。** どちらが欠けても印は開かない ── 面の種別を増やす操作は、配線と挿入先の2か所へ同時に及ぶ。

**Git は差分を出すが、なぜ変えたかを出さない。** そこを補完するのがこの道具である ── まとまりごとに理由を添え、印を押すと開く。**変更前は `-` の行が示す**ので、`before` の記述は省略してよい。

**変更前は `git show <rev>:<パス>` で取得する。** 記録へ複製しない。`rev` の既定は `HEAD` で、`docs` の項目に書くと変更できる。取得できない場合と差分が無い場合は、全文を置く。

**理由が付いていないまとまりは、組成の検査が件数を出す。** 差分の見出しにも表示する ── **0件にしてから提示する**。

**コードの印は行の単位である。** 語の単位で付けると、色付けが挿入した要素と交差してどちらかが壊れる ── コードの変更は行の単位で読むものなので、行で足りる。

**色付けは近似である。** 構文解析を実施せず、行ごとに正規表現を適用する ── 文字列の中の予約語のような事例は取り違える。読解の補助であり、判定の根拠にしない。

**冪等である。** `docs` のパスはリポジトリの根から解決するので、どこから実行しても同一のものが出力される。`--check` は組み直した結果と `index.html` を比較し、差が在れば 1 を返す。


### Step 6: 開いて閉じることを確認する

描画して、実際に押す。1度押すと変更前と理由が出て、2度押すと閉じる。「すべて開く／閉じる」も両方向とも動作する。**印が内側のタブに隠れることがある** ── タブの先頭の一覧から、押してその印まで運べることを確認する。

### Step 7: 理由の欠けを確認する

「なぜ」が「一致させるため」だけになっていないか（何と何を一致させたかを書く）。変更内容の言い換えになっていないか。変更前が要約になっていないか。

### Step 8: 見せて、承認を得てから適用する

1枚を渡し、返事を待つ。**「適用しました。確認してください」と記述しない** ── それは承認ではなく追認を求めている。

承認が下りたら、状態を `accepted` にして組み直し、正本へ適用し、`.acdr/` の1枚と索引をコミットする。差し戻されたら3つ組を直して Step 3 から再実行する。止められた場合は適用しない。

後の決定が、この決定を置き換えたときは、古いほうの状態を `superseded` にし、置き換えた記録を指す ── **消さない**。

## 出力形式

**1枚のHTMLである。** 先頭に節、その下に対象の文書が並ぶ。チャットには次のみを記述する。

| 書くこと | 書き方 |
|---|---|
| 何件直したか | 数と、いちばん影響の大きい1件 |
| いちばん影響の大きい1件 | どこで、何が食い違っていて、何に一致させたか |
| 直していない箇所 | 理由が書けなくて保留にしたものが在れば、そう書く |
| 何と照らしたか | Step 1 で外から取った先。照らしていないなら、そう書く |
| 全文を読んだか | 読んだと書く。読んでいないなら、読んでいないと書く |
| 正本の状態 | **まだ適用していないこと**と、適用してよいかを聞く |

**変更の一覧をチャットに並べない。** それは1枚の役目である。

## ガードレール

- **中身を複製しない。** 変更後の全文は対象の文書が保持する。記録が保持するのは節と3つ組だけである
- **対象が何の仕事に属するかを、この Skill が認知しない。** 特定の分野の語彙・規則・スキーマを持ち込まない ── 使う側がこの Skill を呼ぶのであって、この Skill が使う側を知ることはない
- **何を出す文書かを、外から取得してから改訂する。** 文書の中の記述を、その文書を直す根拠にしない
- **骨格が合っていなければ、本文を直さない。** 先に骨格の合意を取る
- **対象の全文を読んでから直す。** 検索で見当を付けて周辺のみを確認する方法を採用しない
- **正本へ適用する前に見せる。** 適用してから提示しない
- **理由が欠けている変更を包含しない。** 推測で理由を補完しない
- **変更前を要約しない。** 原文をそのまま保持させる
- **比較した案を削除しない。** 案と、採らなかった理由を保存する
- **節の語を負の側へ偏向させない。** 「除外」「負担」ではなく「比較した案」「承認後に実施すること」と記述する ── 負の語が残ると、未解決の懸念が存在すると読解され、承認の判定が遅延する
- **抽象の側の変更前と変更後を記述する。** 枠が保持するのは具体の差分である ── 抽象の対比が欠けると、下に並ぶ差分が何のためかを読み手が復元することになる
- **図を省略しない。** 形の変化を図で確認できる形式にする。描画はこの Skill が実施せず、SVG の文字列を受け取るのみである
- **状態を自由文にしない。** `proposed` ／ `accepted` ／ `superseded` の3つ以外を書かない ── 自由文にすると、承認されているかを読む側が判定することになる
- **置き換えられた記録を削除しない。** `superseded` にして、置き換えた記録を指す
- **新規を例外として区別しない。** 差分が存在しない決定も同一の形式で、`docs` を空欄とする
- **描画して押すまで出さない。** 開閉が動作することを目視で確認する
- **色・寸法を直書きしない。** 見た目は `references/tokens.json` が保持するトークンから引く ── 直書きすると、配色を替えたときにそこだけ取り残される。**トークンの正本は1つである** ── 2か所に書くと、どちらが正しいかを毎回確認することになる
- **入力の検査を、組み立てと同じ場所に置かない。** 組み立てが検査を兼ねると、不合格の判明が生成物のあとになる ── **不合格なら HTML を1バイトも出さない**
- **決定の文に手段を混在させない。** 決定は「何を採るか」で、手段は実現の形が保持する ── 手段だけを上に置くと、下の差分が何のためかを読み手が復元することになる
- **差し色を1つに限定する。** 状態の札（承認済み）以外に別の色を使わない ── 1本だけ違う色の線が在ると、意味が在るものとして読解される
- **題を二重に出さない。** 題は節が持ち、枠の見出しには出さない
- **生成物に文字コードを宣言する。** `<meta charset="utf-8">` を先頭に置く ── 無いとHTTPで配ったときに推測になり、化ける
- **承認済みの記録を組み直さない。** 記録は承認時点の姿である ── 後に対象の文書が変化しても、記録はその時点を保持する
- 外部のCDNやスクリプトを参照しない。**1枚で完結させる**

## 参照

### 入口と契約

- `scripts/cli.py`: **唯一の入口。** `new` ・ `validate` ・ `render` ・ `tokens` を持つ ── どれも `--json` で機械が読む形が出る
- `scripts/tools.py`: 道具の宣言。**能力の正本**であり、CLI と MCP はここから組む。**部品は載せない** ── `tabs.py` ・ `code.py` ・ `render.py` は読み込まれるものであり、入口を保持しない
- `scripts/mcp.py` ・ `mcp.json`: MCP サーバー。**実装が無い環境では立たず、CLI だけが動く**

### 正本と組み立て

- `references/acdr.template.html`: **出来上がりの形の正本。** 節 ・ タブと枠 ・ 印 ・ 差分の部品を持ち、組み立ては値を差し込むだけである ── **形をコードの中の文字列に散らさない**
- `scripts/lib/template.py`: 型を読み、部品を組む。**差し込む場所の過不足を、その場で例外にする** ── 埋め忘れも、余分な値も、出てから気づく形にしない
- `references/acdr.schema.json`: **入力の契約。** `acdr.json` の形を決める。**鍵は ASCII である**（`decision` ・ `why` ・ `applies_to` ・ `shift` ・ `alternatives` ・ `after_approval` …）── 日本語のまま残るのは、人が読む本文だけである
- `references/tokens.json`: **デザイントークンの単一の正本。3段である** ── 基礎（原始値）→ 意味（役割）→ 部品。意味の段は基礎の鍵だけを参照し、部品の段は意味か基礎の鍵だけを参照する。**明暗は1つの表から3つの選択子を生成する** ── 手で3か所へ記述すると、1つの鍵が片側から脱落しても誰も検出しない
- `references/tokens.schema.json`: トークンの形の契約。段を跨いだ直値と、明暗の鍵集合の不一致を弾く
- `scripts/lib/tokens.py`: トークンを読み、CSS のカスタムプロパティへ組む。**iframe と Shadow の中へ流し込む側は、`:host` でも解決する形で組む** ── Shadow の中に `:root` は無く、寄せないと印が色を失う
- `scripts/lib/validate_input.py`: **入力を検査する。** 形（スキーマ）・欄の完備（節と3つ組）・散文・参照の解決（図と対象の文書）の4系統である。**原文（`before`）と照合する文字列（`find`）は、散文として検査しない** ── 原典の形を変えないためである
- `references/acdr.css`: **見た目の正本。** セレクタと規則だけを保持し、**直値を1つも書かない** ── 色も寸法も字寸も `tokens.json` の段を参照する。以前は `scripts/lib/` の中の Python 文字列に141行在った ── そこに置くと、型とトークンを直すべき変更が、Python の中の文字列を直す作業になる。塊の境目は `/* == 名前 == */` が示す（BASE ・ CODE ・ MARK ・ SECTION）
- `scripts/lib/acdr_css.py`: 正本を読み、塊へ割る（36行）。**境目をこの側で決めない** ── 決めると、正本を割り直したときに気づけない
- `scripts/lib/render_acdr.py`: 節と差分を1枚へ組む。入力の検査で1件でも検出したら、HTML を1バイトも出さない
- `scripts/lib/panes.py`: 対象の文書を描画し、変更箇所に印を付け、複数なら1枚へまとめる。拡張子で置き方を決める
- `scripts/lib/code_diff.py`: コードを Git の統合差分へ組む。まとまりごとに理由を添え、**理由が付いた数を返す**ので、欠けを検査へ出せる。対応する拡張子は `LANGS` が保持する ── **ここに無い拡張子は、コードとして扱わない**
- `scripts/lib/markdown.py`: マークダウンを描画し、変更箇所に印を付ける。**位置は差し込む前に全部決める**（差し込みながら探すと、印が前の印の属性の中へ入る）
- `scripts/tests/test_markdown.py`: 印の付き方を事例で検証する。`python3 scripts/tests/test_markdown.py` で実行する
- `references/acdr.schema.json`: `acdr.json` の形を検査するJSON Schema
- `references/spec-template.json`: `acdr.json` の雛形。`new` が複製する
- `scripts/tests/test_render_acdr.py`: 雛形から起こせるか ・ 欠けた欄で止まるか ・ **同じ入力から同じ出力が出るか** ・ 実行場所に依存しないか ・ 承認済みの記録が封印されるか ・ コードが Git の差分になるか ・ 理由の欠けを検出するかを検証する。`python3 scripts/tests/test_render_acdr.py` で実行する（17件）
- `scripts/tests/test_template.py`: 型が満たすことを検証する ── 部品を組めるか ・ 差し込みの過不足で例外になるか ・ 組み立ての側に構造を作る文字列が残っていないか（19件）
