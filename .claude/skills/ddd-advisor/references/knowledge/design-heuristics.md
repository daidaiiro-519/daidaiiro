# 設計の経験則を扱う概念：design-heuristics

## 概要

### この概念が答える判断

- 区切られた文脈はどれくらいの大きさで区切ればよいか
- 業務ロジックをどの方法で実装すればよいか
- 実装方法が決まったとき、技術方式とテスト方針はどう決まるか
- 業務領域のカテゴリー判断と実装方法の選択が食い違うとき、何を疑うべきか
- 経験則をどこまで厳格な規則として扱ってよいか

区切られた文脈の大きさ・業務ロジックの実装方法・技術方式・テスト方針を、業務領域のカテゴリーから連鎖的に決めていくための経験則。前段の判断が後段の判断の前提になるので、後段で違和感が出たときは前段を疑い直す手がかりにもなる。

## 設計の経験則

### 経験則とは何か

100%正しいと証明された定理ではなく、完全性は保証されないが実務で役に立つおおまかなやり方。大量の手がかりが生む雑音を遮り、複雑さの根源が生む重要な手がかりへ焦点を合わせるための、実践的な問題の解き方である。この章の経験則が焦点を合わせるのは2つ——さまざまな事業活動に共通する本質的な特性と、設計判断そのものが抱える本質的な難しさ。

### 4つの判断は連鎖する

区切られた文脈の大きさ・業務ロジックの実装方法・技術方式・テスト方針は独立していない。前の判断が後の判断の前提になるので、後段で迷ったときは前段を疑い直すのが近道になる。

4つの判断が連鎖しており、後段の違和感は前段を疑う合図になることを示す

4つの判断は前から順に前提になり、最後まで行って合わなければ出発点へ戻る。

```mermaid
flowchart LR

    n1["区切られた文脈の大きさ"]
    n2["業務ロジックの実装方法"]
    n3["技術方式"]
    n4["テスト方針"]
    n0 --> n1
    n1 --> n2
    n2 --> n3
    n3 --> n4
    n4 -->|"食い違ったら戻って疑う"| n0
```

| どこの話か | 図に載せきれないこと |
|---|---|
| 4本の矢印 | 時間の順序ではなく、前提の順序である。4つを同時に考えてもよいが、左が決まらないと右は決められない、という依存を表している。 |
| 業務領域のカテゴリー | 節点は5つあるが、判断として数えるのは右の4つである。左端のこれは、この連鎖の中で決めるものではなく、外から持ち込む前提にあたる。 |
| テスト方針から業務領域のカテゴリー | 繰り返しを表していない。テスト方針が現場の実感と合わないときにだけ通る例外の経路であり、そのとき直す先はテスト方針ではなく出発点のカテゴリー判断である。この線があるために、この図は手順書ではなく、食い違いの原因をどこに探すかの地図として読める。 |

### 区切られた文脈の大きさ

大きさそのものに一般解は無い。モデルを作った結果として大きさが決まる。

#### 最適な大きさはない

大きさは、設計の手がかりとしてもっとも役に立たないものの一つである。先に大きさを決めてモデルを当てはめるのではなく、モデルを作ってから区切られた文脈の大きさを決める。順序は逆にしない。

#### 最初は広い範囲で区切る

複数の区切られた文脈にまたがる変更は、調整に多くの時間と労力を要する。一度引いた境界を引き直すのはとてもたいへんで、ほとんどの場合そのまま放置される。したがって広い範囲を境界とするところから始め、業務知識が増えるのに合わせて必要なら小さく切り分ける。

#### 中核を含むときは、よくやりとりする相手も同じ側に置く

中核の業務領域を含む区切られた文脈を設計するときは、その業務領域と頻繁にやりとりする他の業務領域を同じ区切られた文脈に含めておく。含める相手は中核・補完・一般のいずれでもよい。初期段階では予測しにくい変更に対応しやすくなるためである。適切な垂直の境界を定義しておけば、一枚岩になった区切られた文脈をモジュールに割ることができ、大きな泥団子になるのを防げる。その垂直の論理的な境界を、後から物理的な境界へ引き直すこともできる。

### 業務ロジックの実装方法

業務領域のカテゴリーとデータ構造の複雑さで決まる。

業務ロジックの実装方法を、業務領域のカテゴリーとデータの複雑さから決める

業務領域のカテゴリーとデータの複雑さという2つの問いだけで、4つの実装方法のどれかに行き着く。

```mermaid
flowchart TD
    n0["業務領域のカテゴリーは"]
    n1["データ構造は複雑か"]
    n2["金銭処理・一貫した監査記録・深い行動分析が要るか"]
    n3["アクティブレコード"]
    n4["トランザクションスクリプト"]
    n5["イベント履歴式ドメインモデル"]
    n6["ドメインモデル"]
    n0 -->|"補完・一般・連係"| n1
    n0 -->|"中核"| n2
    n1 -->|"はい"| n3
    n1 -->|"いいえ"| n4
    n2 -->|"はい"| n5
    n2 -->|"いいえ"| n6
```

| どこの話か | 図に載せきれないこと |
|---|---|
| 業務領域のカテゴリーは | ここで分類をやり直すのではない。すでに済んでいる分類の結果を持ち込むだけの入口である。 |
| データ構造は複雑か | 業務ルールの複雑さではなく、データの形の複雑さを問う。業務ルールの複雑さは中核かどうかの側に織り込まれているので、ここで二重に問わない。 |
| 金銭処理・一貫した監査記録・深い行動分析が要るか | 3つのうち1つでも当てはまれば「はい」へ進む。3つとも必要という意味ではない。 |
| 4つの終点 | 排他だが、それは1つの業務領域についての話である。同じ区切られた文脈の中に業務領域が複数あるなら、それぞれ別の終点になってよい。 |

#### 複雑さをどう判定するか

複雑な業務ロジックとは、入り組んだ業務ルール・不変条件・最適化の手続きを含むもの。単純な業務ロジックとは、入力データの検証が中心のもの。同じ言葉そのものの複雑さも判断材料になる——主に登録・参照・更新・削除を説明しているなら業務ロジックは単純であり、入り組んだ業務の流れと複雑な業務ルールを説明しているなら複雑である。

#### カテゴリー判断と実装方法の食い違いを見つける

中核と判断したのに実装方法がアクティブレコードやトランザクションスクリプトになる、補完と判断したのに実装方法がドメインモデルやイベント履歴式になる——こうした食い違いは要注意である。ただしこれは実装方法を選び直せという合図ではなく、業務領域や事業活動についての自分たちの判断を見直す絶好の機会だと捉える。

### 技術方式

業務ロジックの実装方法が決まれば、技術方式はほぼ一意に決まる。

技術方式が、業務ロジックの実装方法から一意に決まることを示す

実装方法が決まれば技術方式も決まる。選び直す余地はほとんど無い。

```mermaid
flowchart LR
    n0["イベント履歴式ドメインモデル"]
    n1["ドメインモデル"]
    n2["アクティブレコード"]
    n3["トランザクションスクリプト"]
    n4["永続化モデルは複数か"]
    n5[CQRS]
    n6["ポートとアダプター"]
    n7["レイヤードアーキテクチャ（4層）"]
    n8["レイヤードアーキテクチャ（3層）"]
    n0 --> n5
    n1 --> n6
    n2 --> n7
    n3 --> n8
    n4 -->|"はい（実装方法によらず加わる）"| n5
```

| どこの話か | 図に載せきれないこと |
|---|---|
| イベント履歴式ドメインモデルからCQRS／ドメインモデルからポートとアダプター／アクティブレコードからレイヤードアーキテクチャ（4層）／トランザクションスクリプトからレイヤードアーキテクチャ（3層） | この4本は選択ではなく帰結である。4本を見比べて好きなものを選ぶための図ではない。 |
| 永続化モデルは複数か | 左の4つから切り離して描いてあるのは、これが実装方法によらない独立した問いだからである。どの実装方法から来てもこの問いには当たる。 |
| 永続化モデルは複数かからCQRS | イベント履歴式から伸びる線とは意味が違う。こちらは元の技術方式の上に重ねる追加であり、イベント履歴式からの線は、CQRSでなければ成立しないという必然である。 |

#### そうなる理由

対応は取り決めではなく、実装方法が抱える制約から導かれている。

実装方法ごとに、なぜその技術方式になるのかを並べる

対応は恣意的ではなく、実装方法が抱える制約から導かれている。理由の側を読むと、例外を認めてよい場面かどうかを自分で判断できる。

| 実装方法 | 技術方式 | そうなる理由 |
|---|---|---|
| イベント履歴式ドメインモデル | CQRS | CQRSが無いと、集約の状態にもとづく参照が極端に制限される |
| ドメインモデル | ポートとアダプター | レイヤードアーキテクチャでは、集約と値オブジェクトを永続化から引き離しにくい |
| アクティブレコード | レイヤードアーキテクチャ（4層） | 追加したサービス層が、アクティブレコードを制御する |
| トランザクションスクリプト | レイヤードアーキテクチャ（3層） | 最小の層構成で足りる |

#### 永続化モデルが複数なら CQRS を加える

CQRSは、業務ロジックの実装方法がイベント履歴式ドメインモデルでなくても、複数の永続化モデルでデータを表現したい場合には役に立つ可能性がある。これは上の対応表に対する例外として扱う。

### テストの基本方針

業務ロジックの実装方法と技術方式が決まれば、テスト方針も決まる。

テスト方針が、業務ロジックの実装方法から決まることを示す

実装方法が決まればテスト方針も決まり、2つの実装方法は同じ方針へ行き着く。

```mermaid
flowchart LR
    n0["トランザクションスクリプト"]
    n1["アクティブレコード"]
    n2["ドメインモデル"]
    n3["イベント履歴式ドメインモデル"]
    n4["逆ピラミッド形"]
    n5["ダイヤモンド形"]
    n6["ピラミッド形"]
    n0 --> n4
    n1 --> n5
    n2 --> n6
    n3 --> n6
```

| どこの話か | 図に載せきれないこと |
|---|---|
| 4本の線 | 「その種類のテストだけを書く」ではなく、どこに重心を置くかを表す。ピラミッド形でも統合テストは書くし、逆ピラミッド形でも単体テストは書く。 |
| ドメインモデルからピラミッド形／イベント履歴式ドメインモデルからピラミッド形 | 実装方法が違うのに同じ終点になるのは、方針を決めているのが実装方法の名前ではなく、業務ロジックがどの層に置かれるかだからである。どちらも1つの層に集まっている。 |

#### 3つの方針の対比

重心の置きどころが3通りある。

3つのテスト方針を、重心と向いている実装方法で対比する

重心がどの層に寄るかは、業務ロジックがどの層に置かれるかで決まる。業務ロジックが層をまたぐほど、重心は上へ移る。

| 方針 | 重心 | 向いている実装方法 |
|---|---|---|
| ピラミッド形 | 単体テストを厚く。統合は少なく、端から端までのテストはさらに少ない | ドメインモデル・イベント履歴式ドメインモデル |
| ダイヤモンド形 | 統合テストに寄せる | アクティブレコード（業務ロジックがサービス層と業務ロジック層にまたがる） |
| 逆ピラミッド形 | 端から端までのテストを最重視し、処理の流れを通しで確かめる | トランザクションスクリプト（業務ロジックが単純で層が少ない） |

### 総合的な判定

カテゴリーの判断から、実装方法・技術方式・テスト方針までを一続きで辿る。

業務領域のカテゴリーから、実装方法・技術方式・テスト方針までを一続きで決める

業務領域のカテゴリーという1つの入口から、実装方法・技術方式・テスト方針が順に決まる。

| どこの話か | 図に載せきれないこと |
|---|---|

#### この判定方法の使い方

あくまで経験則であり、厳格な規則ではない。設計判断は文脈に依存する。この判定方法を部分的に変えたり、独自の判定方法を作ったりするのは自由である。そのうえで守るべき指針は2つ——できるだけ単純な手段を選ぶこと、そして複雑な手段（ドメインモデル・イベント履歴式・CQRS）は、本当に必要なときの最後の手段として使うこと。

### アンチパターン

設計の経験則を使うときによく起きる誤り。

#### 大きさから区切られた文脈を決める

「細かく分ける方式だから小さく」「一枚にまとめる方式だから大きく」のように、実装形態の方針を先に決めてからモデルを当てはめるのは順序が逆である。モデルが先で、大きさは結果として出る。

#### すべての業務領域に同じ実装方法を使う

チームがイベント履歴式ドメインモデルに習熟していても、全業務領域へ一律に適用するより、経験則で使い分けるほうが効率的である。

#### 補完的な業務領域にドメインモデルを使う

業務ロジックが単純な補完領域に手の込んだ設計を持ち込むと、複雑さに見合わない保守の負担だけが残る。

#### カテゴリー判断と実装方法の食い違いを放置する

食い違いに気づいても放置すると、後段の技術方式・テスト方針の選択もつられて不適切になる。気づいた時点で、業務領域のカテゴリー判断そのものを疑い直す。
