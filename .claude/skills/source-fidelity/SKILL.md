## 目的

**調査対象を、要約を経由せずに読む。**

**識別子は説明ではなく鍵である。**
`compact_summary` を `compact_text` と書き換えたら、その鍵で引く実装は**必ず空を返す**。
**しかも壊れ方が静かで、「その事象は起きなかった」と読めてしまう。**
土台の項目名が違えば、その上に作った道具は何も取れない。

**主張は、要約すると別のものになる。**
「〜の場合に出る」から条件を落とせば、無条件で出ると書いたことになる。
**しかも識別子と違って、照合には1件も掛からない。**
名前がすべて原文どおりの文書が、原典と違うことを述べる。

**識別子の照合は、原典への忠実さのうち、文字列で当てられる一部である。**
**残りは、主張を原文の引用に結びつけて確かめる。**

**このスキルが禁じるのは1つ——「要約された原典」を根拠にすることである。**
公式リファレンスも、OSS の実装も、規格も、実測データも、
**扱いは同じである**。どれも「正しいとされる情報源」であり、
**勝手に言い換えた時点で、実体と別のものになる。**

---

## 役割

- 情報源の**原文**を落とし、落とした日と `sha256` を残す
- 文書へ書く識別子を、**原文の文字列で1つずつ照合する**
- 照合できなかった識別子を、**原典の名前として書かない**
- 「原典にこう書いてある」と書くときは、**どのファイルの何行目かを言えるようにする**
- **原典の記述として書く主張を、原文の引用へ1件ずつ結びつける**
- **引用を添えられない主張を、原典の記述として書かない**
- **要約・言い換え・意訳を、識別子にも主張にも行わない**

## 処理対象と成果物

### 処理対象

**外にある情報源である。**

| 種類 | 例 |
|---|---|
| 公式リファレンス | フックの事象と入力項目、API のスキーマ、設定ファイルの形式 |
| OSS の実装 | 型定義、アダプタの契約、保存先のパス |
| 規格・論文 | RFC、semantic conventions、原典の数値 |
| 実測データ | 自分で取った記録。**これも「情報源」として同じ扱いをする** |

### 成果物

**原文のファイルと、2種類の照合の結果である。**
原文は保存する。**識別子は原文の文字列で照合し、主張は原文の引用へ結びつけて**から文書へ書く。

---

## 入力の想定

| 受け取る情報 | 解釈・既定値 |
|---|---|
| 調べる対象 | 明示されなければ、話に出ている仕様・実装のすべてを対象にする |
| 保存先 | **呼び出す側から受け取る**（`--dir`）。渡されなければ、いま作業しているフォルダの下の `sources/` |
| 何を照合するか | 明示されなければ、**文書へ書こうとしている識別子すべてと、原典の記述として書こうとしている主張すべて** |

## 実行手順

### Step 1: 原文を落とす

```
python3 <skill>/scripts/source.py fetch <URL>
```

`<skill>` は、このスキルを置いた場所である。

**まず `<URL>.md` を試し、無ければ本体を取る。**
主要な文書サイトは `.md` で原文を返す（実測：Anthropic ・ Cursor ・ OpenAI ・ GitHub の4社とも返した）。

落としたものは、`sha256` ・ バイト数 ・ 行数 ・ 落とした日と一緒に保存される。
**「いつ・どの版を読んだか」が言えなければ、根拠にならない。**

| 対象 | どう落とすか |
|---|---|
| 公式リファレンス | `fetch <URL>`。`.md` が返ればそれが原文である |
| OSS の実装 | `git clone --depth 1`。**読んだ commit を記録する** |
| 論文 | PDF を置き、本文の文字列で確認する |
| 実測データ | 自分で取ったファイルをそのまま置く |

**HTML しか返らない頁も、そのまま原文として残る。**
タグは剥がさない ── 剥がすのは加工であり、剥がし方で文字列が変わると
「原文と1文字ずつ同じ」が言えなくなる。

### Step 2: 識別子を書き出す

**文書・設計・実装へ書こうとしている識別子を、1行1個で並べる。**

対象になるのは、**名前がそのまま鍵として使われるもの**である。

- 項目名・フィールド名（`compact_summary` ・ `tool_use_id`）
- パラメータ名・フラグ（`--permission-mode` ・ `permission_prompts`）
- 事象名・関数名・型名（`PostToolUse` ・ `LoadedEntry`）
- ファイル名・パス（`~/.codex/sessions/` ・ `state.vscdb`）
- 設定の鍵（`github.copilot.chat.otel.enabled`）

### Step 3: 原文と照合する

```
python3 <skill>/scripts/source.py verify <原文> --as identifier <識別子>...
python3 <skill>/scripts/source.py verify <原文> --as identifier --from names.txt
```

**当て方を渡さなければ止まる。**
道具の側で「たぶん識別子だろう」と決めない。

| 当て方 | 何を見るか |
|---|---|
| `identifier` | **語として当てる**。前後が語の文字なら、それは別の名前である |
| `quote` | **引用として当てる**。空白の畳み方だけ揃え、語は1文字も変えない |
| `text` | **そのまま探す**。探索のための種類で、**照合した証しにはならない** |

**語の区切りは、当てる語自身が決める。**
英数と `_` `-` は常に語の内側で、それ以外の区切り（`.` `/` `:` など）は、
**当てる語がそれを含んでいるときだけ**内側になる。
だから `otel.enabled` は鍵の切れ端として落ち、`compact_summary` は英文の文末でも当たる。

**読めた範囲に無い識別子が1つでもあれば、そこで止まる。**

| 見つからない原因 | どうするか |
|---|---|
| 名前を言い換えた | **直す**。原文の綴りをそのまま使う |
| 別のページに在る | **そのページを落として照合し直す** |
| **読めなかった範囲に在る** | **読めるようにして、当て直す**。0件を結論にしない |
| 本当に無い | **「無い」と書く**。推測で埋めない |

**アンカーを渡すと、文脈まで見る。**

```
python3 <skill>/scripts/source.py verify <原文> --as identifier compact_summary \
        --near "PostCompact input" --within 25
```

**名前が在ることと、その名前がそこで使われることは別である。**
`trigger` は原文に 24 か所あるが、それが `PostCompact` のものとは限らない。
**別の事象の項目を、その事象のものとして書く**——これが次に起きる誤りである。

### この検査で見えるもの・見えないもの

**これは文字列の検査であって、意味の検査ではない。**

| 見える | 例 |
|---|---|
| **識別子を言い換えた** | `config_source` と書いたが、原文には無い |
| 綴り・大文字小文字・区切りの違い | `toolResult` を `tool_result` と書いた |
| **アンカーを渡せば、文脈違い** | `trigger` は在るが `PostCompact` の節に無い |

| 見えない | どう防ぐか |
|---|---|
| **名前は合っているが、説明が違う** | **Step 4 で、主張を引用に結びつける** |
| **原文に在るのに、こちらが拾っていない** | **Step 6 で逆側から当てる** |
| 数値・件数の誤り | **数値も、原文の文字列で確認する**。自分で計算した値を、原典の値のように書かない |
| 版が古い | 落とした日を残し、**同じ URL でも中身が変わる**前提で扱う |

**「0件だから正しい」ではない。「書いた名前は、読めた範囲に実在する」だけである。**

**読めなかったファイルは、結果に「読めなかった範囲」として出る。**
1つでも在れば、0件は「無い」ではなく「**読めた範囲には**無い」としか言えない。
**黙って飛ばして0件と報告するのは、道具の側が推測で断定することである。**

### Step 4: 主張を、引用に結びつける

**原典の記述として書こうとしている主張を、1件ずつ書き出す。**
識別子と同じ扱いをする。**違うのは、当てる先が名前ではなく、原文の一続きの範囲だという1点である。**

**1件ごとに、根拠にした原文の行をそのまま添える。**
行番号は `grep -n` で取る。

```
主張      PostCompact は、自動の圧縮でも手動の圧縮でも走る
引用      | `trigger` | `"manual"` \| `"auto"` | 圧縮の起こし方 |
出どころ  claude-code-hooks.md:412
```

**引用を添えられない主張は、原典の記述として書かない。**

| 引用を添えられない | どうするか |
|---|---|
| 原文に在るはずだが、まだ探していない | **探す**。見つけた行を添える |
| 原文には無く、自分の推論である | **「推測」と印を付ける**。または落とす |
| 離れた複数の箇所を繋いで導いた | **繋いだと書く**。引いた箇所を全部添える |

**要約して意味が変わる形は、4つある。**

| 崩れ方 | 原文 | 書いてしまう内容 |
|---|---|---|
| **条件の脱落** | 「〜の場合に出る」 | 「出る」 |
| **範囲の拡大** | 1つの実装・1つの版の話 | 「一般にこうである」 |
| **因果の捏造** | 並べて書いてあるだけ | 「A だから B になる」 |
| **欠落の補完** | 何も書いていない | 通念で埋め、「原典にこうある」と書く |

**4つとも、Step 3 の照合では0件になる。**
名前を1つも言い換えていないためである。

**引用が原文と1文字ずつ同じかは、`verify` で確かめられる。**

```
python3 <skill>/scripts/source.py verify <原文> --as quote --from quotes.txt
```

**引用は1行ずつ渡す。**
行をまたぐ引用も当たる（空白の畳み方だけ揃えるため）が、
渡すときの1件は1行にする。

**引用を、読みやすくするために整えない。**
整えた時点で、引用ではなくなる。

### Step 5: 書けることと、書けないことを分ける

**原文で照合できたことだけを、原典の記述として書く。**

| 書けること | 書き方 |
|---|---|
| 原文に在る識別子と、その説明 | そのまま引く。**言い換えない** |
| 原文に無い | 「原文に無い」と書く |
| 自分で測った値 | 「実測」と印を付け、**測った条件も書く** |
| 第三者の実装が主張していること | 「第三者」と印を付け、**どのリポジトリの何 commit かを書く** |

**「原典に書いてある」と「実際にそうなる」は別である。**
公式に書いてあっても、条件が揃わないと出ない項目がある。
**出せることを確かめたなら、そのための条件も書く。**

### Step 6: 逆側からも当てる

**原文に在るのに、こちらが拾えていない識別子を探す。**

Step 3 は「こちらが書いたものが原文に在るか」を見る。
それだけでは**取りこぼし**が残る。原文を頭から読み、
**見出しの一覧と、こちらが持っている一覧を突き合わせる。**

**識別子だけでなく、条件・例外・限定も同じように探す。**
原文が付けている「ただし」を拾い落とせば、書いたものは Step 4 の**条件の脱落**と同じ形になる。

## 出力形式

**調べた結果を報告するとき、次を必ず添える。**

| 報告する内容 | 書き方 |
|---|---|
| 何を読んだか | **URL と、落とした日と、行数**。「公式ドキュメント」とだけ書かない |
| どう読んだか | **原文を落として文字列で照合した**、と書く。していないならそう書く |
| 照合した識別子の数 | 何個当てて、何個が原文に在ったか |
| **主張の根拠** | **原典の記述として書いた主張ごとに、引いた行と出どころを添える。添えられないものは「推測」と印を付ける** |
| **どの当て方で当てたか** | **`identifier` ・ `quote` ・ `text` のどれか。`text` は照合した証しにならないと添える** |
| 読めた範囲に無かったもの | **一覧で出す。1つでも隠さない** |
| **読めなかった範囲** | **在れば一覧で出し、0件を結論にしない。無ければ「全部読めた」と書く** |
| 実測と原典の区別 | 行ごと・値ごとに印を付ける |

## ガードレール

- **要約を経由して原典を読まない**。要約する道具の出力を、原典の記述として引用しない
- **識別子を言い換えない**。大文字小文字・区切り記号・単複まで原文どおりにする
- **原文に無い識別子を、原典の名前として書かない**
- **引用を添えられない主張を、原典の記述として書かない**。推測として書くか、書かない
- **引用を整えない**。読みやすさのために語を足さない。条件・範囲・限定を落とさない
- **照合が0件でも、意味が合っているとは限らない**。主張は Step 4 で別に確かめる
- **0件を「無い」と結論しない**。読めなかった範囲が1つでも在れば、「読めた範囲には無い」と書く
- **`--as text` の結果を、照合した証しにしない**。探索のための種類である
- **「公式にはこう書いてある」と書くなら、原文のどこかを言えるようにする**
- **原典が誤っていると結論する前に、自分の読み方を疑う。**
  実際に「公式が間違っている」と結論し、**誤っていたのは読み方だった**
- **落とした日と版を残す**。同じ URL でも中身は変わる
- **OSS は読んだ commit を記録する**。「そのリポジトリではこうなっている」は版に依存する
- **第三者の実装の主張を、公式の記述として書かない**。印を分ける
- **原文で照合していない調査結果で、正本を書き換えない**
- **原文の置き場所を、このスキルの側で決めない**。呼び出す側から受け取る
- **このスキルの外を指す参照を持たない**。他のスキル・特定のフォルダの並びを前提にしない
