## 目的

**技術文書としても学術文書としても違和感のない日本語を書く。**

| 満たすこと | |
|---|---|
| **論** | 意味が通り、論が成立している |
| **構造** | 情報が、その型に合った形で置かれている |
| **文調** | 人が読んで、一度で意味が取れる |
| **語彙** | 同じ文脈では、同じものが同じ語で呼ばれている |

**判断の材料は10の概念である。**
**どれも公開された規格・指針から導いており、出どころを最後の節に置く。**

**出すには、2つのゲートを実行する。**

| ゲート | 何を検査するか | 誰が決めるか |
|---|---|---|
| **1** | 0件にできるものが、0件であること | **機械** |
| **2** | 10の判定すべてに、結果が1行ずつあること | **書き手** |

**ゲート2が保証するのは、判定を適用したことだけである。**
何を直すかは、書き手の判断に残る。

## 役割

- 書いたものに、10の概念から導いた判定を適用する
- 判定を、**読む人がその場でできる1つの操作**に降ろす
- **原典から導けない決めは、そう書く**
- 適用しなかった判定を、報告に書く

## 処理対象と成果物

### 処理対象

**これから書く日本語の文書、または既に書いてある日本語の文書である。**

### 成果物

**10の判定を適用し、直したか残したかを明示する文書である。**

## 入力の想定

| 受け取る情報 | 解釈・既定値 |
|---|---|
| 読み手 | 明示されなければ、その文書を初めて開く人とする |
| 用語の定め | 対象フォルダに用語を定めた文書があれば、それに従う |
| 文脈の境界 | 明示されなければ、文書1本を1つの文脈とする |

## 実行手順

### Step 1: 読み手と用語を決める

**書き始める前に、読み手を1つに決める。**
読み手が決まらないと、選ぶ語も構成も決まらない（概念8）。
対象フォルダに用語の定めがあれば、先に読む。

### Step 2: 10の判定を適用する

**上から順に適用する。**
前の概念が成立していなければ、後の判定は意味を保持しない。

| # | 概念 | 規則 | 判定 |
|---|---|---|---|
| 1 | 読み手が意味を復元する作業を、書き手が負担する | 1文の中で、読み手に計算をさせない。**名詞句には、指し先を文書の中に置く** | **名詞句を1つずつ抜き出し、「何の」「どこの」「どっちの」「誰が」を問う。文書の中の文字列で答えられない名詞句が1つでもあれば、その文は書けていない**。**「読み返して不自然か」で判定しない**——書き手は指し先を知っているので、不自然に見えない |
| 2 | 情報の型が、置く形を決める | 対比・条件・手順・分岐を、散文に置かない | **その段落を、表か図に置き直せるかを試す** |
| 3 | 数が増えたら、形を変える | 並べるものが3つ以上なら、箇条書きか表にする | **数える** |
| 4 | 見出しは、本文を読まずに全体を掴ませる | 見出しの階層を飛ばさない。**見出しを追えば全体の内容がつかめるようにし、見出しを目立たせる**。**番号は付けても付けなくてもよい** ── 統一されているかだけを確認する | **見出しだけを抜き出して、順に読む。そのうえで、どの本文がどの見出しに属すかが見た目で分かるかを確認する** |
| 5 | 結論を先に置き、根拠を後ろに置く | 節の最初の一文を結論にする | **各節の先頭文だけを並べて読む** |
| 6 | 読み手は、形の違いを意味の違いとして読む | 同じ立場のものは同じ形で書く。文体は文書の中で1つにする | **並んでいるものの語尾を見比べる** |
| 7 | 語の意味は、文脈の中で定まる | 同じ文脈では、1つの意味に1つの語だけを対応づける。文脈が変わるなら、変わることを書く | **用語を列挙し、同じ意味の別の語が無いかを確認する** |
| 8 | 読み手が誰かで、選ぶ語と構成が変わる | 読み手を先に決める。**語は、読み手の世界にすでにある語から選ぶ**。**分野で定着した専門用語はそのまま使い**、自分が作った語・訳した語は使わない。使うなら、新しい語だと書いて定義する。**名前のあるものを、描写で呼ばない** | **語の出どころを提示できるかを確認する**。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する。**そのうえで、書いた操作や物に、分野で通っている名前があるかを1つずつ問う**。あるなら、描写ではなくその名前を書く——「均す」ではなく**正規化する**、「流す」ではなく**実行する**、「鵜呑みにしない」ではなく**そのまま信じない**。**ふつうの日本語の語も、この判定に掛ける**。作った語でも訳した語でもないので、出どころだけを確認すると通り抜ける。**読み手が分野の外の人でも、描写に置き換えてはならない**。言い換えてよいのは、**日常語で意味が表せるものだけ**である（頻回→頻繁に）。日常語で表せないものは、**その名前のまま使い、説明を添える** |
| 9 | 読み手が一度に扱える量には限りがある | 1文は短くする。段落は3行から7行にする。文書の限度を決める | **数える** |
| 10 | 比喩と定型句は、読み手によって解けない | 比喩は、例として明示するときだけ使う | **その比喩を字義どおりに読んで、意味が通るかを試す** |

**名詞句で終わることは、それ自体では欠陥ではない。**
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
**判定1が見るのは、文の中で読み手が戻るかどうかである。**

### Step 3: 直したか、残したかを明示する

**判定に該当した箇所を、直すか、理由を付けて残すかのどちらかにする。**
**理由が書けないなら、それは直す対象である。**

### Step 4: 2つのゲートを実行する

**ゲート1は機械が決める。**

```
doc-writing-skills check <ファイル...>
doc-writing-skills check <ファイル...> --synonyms 用語.tsv
```

| 検査 | 拠って立つもの |
|---|---|
| 見出しの階層が飛んでいる | 概念4 |
| 文体が混ざっている | 概念6 |
| 並んだ項目の語尾が統一されていない | 概念6 |
| 文字で図や表を描いている | 概念2 |
| 同じ意味の語が2つある（対を渡したとき） | 概念7 |
| 強調が描画されない | **媒体の決め** |

**最後の1つだけ、概念から導けない。**
マークダウンの記法に拠るもので、5つの原典はどれも描画について書いていない。
**別枠であることを、`--list` と名簿に書いてある。**

**概念3と概念9は、ゲートに入らない。**
数は数えられるが、**いくつで形を変えるかは文脈で変わる**ので、0件にできない。
判定として、書き手が適用する。

**利用者への応答には、`reply` を適用する。**
応答で使用した語は、そのまま文書へ流入するので、文書と同じ語彙表で照合する。
適用するのは廃語の1つだけで、見出しや文体の判定は適用しない。

```
doc-writing-skills reply --message <本文>   # 本文を直接渡す（MCP も同じ）
doc-writing-skills reply                    # Claude Code の Stop フックの入力を標準入力から読む
```

検出があれば、Stop フックが読む `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":…}}` を出力する。
**`decision: "block"` を使わない** ── Claude Code はそれを hook error として表示する。`additionalContext` なら会話は同じく続き、
表示は `Stop hook feedback` になる（code.claude.com/docs/en/hooks :2620・2631、2026-09-27 取得）。
**Stop フックは応答を表示したあとに走る** ── 表示を止めることはできず、修正した全文を続けて出させる。

**語の単位で判定できない不自然さは、`review` でモデルに審査させる。**
造語 ・ 比喩 ・ 主述の不整合 ・ 含意の不一致 ・ 幼い語り口 ・ 回りくどさは、語彙表では検出できない。
`review` は、判定基準（`references/review-criteria.json`）・手順（`references/document.json` の `review-instruction`）・
事例（プロジェクトの `.doc-writing/review-examples.json`）を1つの依頼文にまとめる。判定はモデルが実施する。

```
doc-writing-skills review --message <本文>                 # 文書（全部の基準を適用する）
doc-writing-skills review --message <本文> --scope reply   # 前後の文脈を保持しない本文（文脈を要する基準を外す）
```

**適用するのは、文書を出す前だけである。会話の応答には、応答のたびに適用しない** ──
審査のたびにモデルのトークンを消費し、得られる判定は確率的である。会話の応答には、
トークンを消費しない `reply`（語彙表の照合）だけを適用する。

**判定は確率的である。ゲート1の代わりにしない。** 実測（指摘された文15件 ・ 指摘の無い文15件）で、
ゲート1と併用して検出13〜14件 ・ 誤検出2件だった。

**ゲート2は書き手が判定する。**
報告に、10の判定すべての結果を1行ずつ書く。**1つでも欠けていれば、通っていない。**

| 報告する内容 | 書き方 |
|---|---|
| 直した箇所 | 概念の番号ごとに、どこを何から何へ直したかを表で出す |
| 残した箇所 | 場所と、残す理由を書く |

## ガードレール

- **運用の覚書の書き方を、どの文書にも使わない**。書いた本人が読み返すための略した書き方は、読み手のための書き方ではない。**`CLAUDE.md` と Skill も例外にしない** ── 例外にすると、そこで書いた語がそのまま本文へ流れる。どの文書でも、操作の名前で書く
- **名前のあるものを、描写で呼ばない**。その操作に分野の名前があるなら、自分の言葉で言い換えない
- **比喩で言い換えない**。対象を別の物へ置き換えた語を使わない ── **指し先が読み手の側で決まらない**（文書か、欄か、クラスかを、読み手が推測することになる）。**利用者への応答も同じである** ── 応答で使用した語は、そのまま文書へ流入する。対象の名前で書く。**検出する語は廃語の一覧が保持する** ── 散文で例を並べると、その例が本文へ流入する。**ただし、普通の語の一部になる語は一覧へ入れられない** ── 部分一致で正しい語まで検出するためである（「段」は段階 ・ 段落 ・ 手段 ・ 段組みの一部である）。その種の語は機械で検出できないので、書く時点で遵守する
- **文語寄りの語を使わない**。「営み」「所以」「〜ねばならない」のように、書き言葉のためだけに選んだ語は、ふだん話す語へ替える。**判定は、同じことを口で説明するときにその語を使うか** ── 使わないなら、読み手にとっては飾りであって、意味を1つも足していない
- **廃語を使用しない**。一度破棄した語の一覧は**このSkillの外**にある ── いつ何を破棄したかはプロジェクトごとに相違するので、ここへ書くと書いたプロジェクトでしか使えない検査になる。既定では `.doc-writing/retired-words.json` を、対象のファイルから上へたどって探す。**無ければこの検査は走らない**（失敗にしない）
- **名前を言い換えない**。**原典の訳語と、分野で定着した技術用語は、そのまま使う**。和語にも漢語にも置き換えない ── 置き換えると**必ず新しい語になり**（メタデータ→「頭」、出典→「指す先」）、読み手が意味を決められない。**判定は2つ ── その語を検索して同じ意味が出てくるか。原典か分野で、その語が使われているか**
- **述部は、ふだん使う動詞で書く**。ふだん使わない漢語（「保持する」「認知する」「委譲する」）にも、ふだん使わない和語（「起こす」「組み立てる」「止める」「突き合わせる」）にも置き換えない。**分野に名前のある操作は、その名前で書く**（ビルドする ・ コミットする ・ 照合する ・ エラーにする）。**判定は、同じことを口で説明するときにその語を使うか**。意味の範囲が広すぎて操作が特定できないときも、分野で使われている具体的な語を選ぶ
- **指し先の無い名詞句を書かない**。「ずれ」「外を指す名前」のように、それが何を指すかを文書の中に書いていない語を使わない。**見出しに置く語は、見出しだけで指し先が分かる形にする**（「ずれた34件」ではなく「仕様と実装のずれ34件」）
- **散文で書けることを、散文で書かない**。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- **桁を空白で整列させて、表に見せない**。表はマークダウンの表で書く
- **ASCII で図を描かない**。図は mermaid か SVG で書く
- **同じ文脈で、同じ意味に2つの語を対応づけない**。文脈が変わるなら、変わることを書く
- **訂正の記録を本文に残さない**。文書には現行の正しい内容だけを書く。履歴は git が持つ
- **数値は原典の文字列で確認してから書く**。要約を経由して引かない
- **確認していない内容を、確認したように書かない**。推測は推測と分かる形で書く
- **原典から導けない決めを、原典の記述として書かない**。こちらの決めだと書く
- **ゲートを実行していないものを、出さない**。実行していないなら、そう書く

**規約の文言を参照するときは、`references/source.json` の原文を開いて文字列で照合する。記憶で書かない。**

**概念8の「名前のあるものを、描写で呼ばない」は、DDD Reference の次の行から取っている。**

> Translation blunts communication and makes knowledge crunching anemic.

> Within a bounded context, use the same language in diagrams, writing, and especially speech.

**見出しの番号は、規則にしない。**

> Don't use numbers in headings to indicate a sequence of sections.
> ── Google developer documentation style guide, headings

**公用文は番号に触れず、見え方だけを求めている**（Ⅲ－２ 標題・見出しの付け方）。

> エ　見出しを追えば全体の内容がつかめるようにする。
> カ　見出しを目立たせるよう工夫する。

**したがって、番号の有無は検査しない**。見出しだけで内容がつかめるか、
どの本文がどの見出しに属すかが見た目で分かるか ── 見るのはそちらである。

**漢語と和語は、正確さと親しみやすさで選び分ける。**

> ウ　重厚さや正確さを高めるには、述部に漢語を用いる
> 語の意味を**より正確に表現したいとき**に、漢語を用いることが有効である場合がある。
> 例）性質が変わる → 性質が変化する　　プログラムが変わる → プログラムが変更される
>
> エ　分かりやすさや親しみやすさを高めるには、述部に訓読みの動詞を用いる
> ── 公用文作成の考え方 Ⅲ－４

**エには但し書きが付いている。**

> ただし、**訓読みの動詞は意味の範囲が広いため、厳密に意味を特定しなければならないときには
> 不向き**なこともあることに留意する。
> 例）作業が進捗する → 作業がはかどる、作業が順調に進む、作業が予定どおりに運ぶ

**「進捗する」1語が、和語では3通りに散る。**

**このリポジトリは、ウ と エ を選び分ける。**
述部はふだん使う動詞で書き、意味の範囲が広すぎて操作が特定できないときだけ、分野で使われている具体的な語を選ぶ（ACDR 0095）。名前は言い換えない。

**専門用語への対応は3つあり、言い換えはそのうち1つである。**

> ア　言い換える。　例）頻回 → 頻繁に、何回も　　埋蔵文化財包蔵地 → 遺跡
> イ　説明を付けて使う。
> ウ　普及を図るべき用語は、工夫してそのまま用いる。
> ── 公用文作成の考え方 Ⅱ－２

> 日常語では言い換えることができない専門用語も多く、その中には専門的な知識を持たない人々に
> とって重要な意味を持つものもある。そうした場合は、**専門用語を使った上で、分かりやすい説明を
> 添える工夫が望まれる**。

**アが適用されるのは「その用語でなくても意味が表せるもの」だけである。**

> 専門家同士で使っている用語で、**その用語でなくても意味が表せるもの**は、一般的な言葉に
> 言い換えることが求められる

**日常語で表せないものを描写に置き換えると、誰にとっても新しい語になる。**
専門家は名前と結び付け直す手間を負い、分野の外の人は何を指すのか分からない。
どちらにも得が無い ── だから、読み手が誰であっても描写にはしない。

**公用文は、同じ問いに逆の答えを置いている**（Ⅱ－２ 専門用語の扱い ア）。

> 専門家同士で使っている用語で、その用語でなくても意味が表せるものは、一般的な言葉に言い換えることが求められる

**2つは矛盾していない。読み手が違う。**
**公用文が想定するのは分野の外の読み手、DDD が想定するのは分野の中の読み手である。**
**だから概念8は、読み手を決めてからでないと適用できない。**

### 述部を漢語にする規則は、外した

**原典は禁止も強制もしていない。** 公用文作成の考え方 Ⅲ－４ には、ウ と エ が対称に置かれている。

> ウ　重厚さや正確さを高めるには、述部に漢語を用いる
> （`references/source.json` の `kobun-sakusei-no-kangaekata`）

> エ　分かりやすさや親しみやすさを高めるには、述部に訓読みの動詞を用いる
> （同）

**原典の強度は「効果が得られることがある」── 推奨である。**
このリポジトリは、ゲート1 で「述部が和語である」を検出し、ウ を必須にしていた（ACDR 0003 で、原典の規定ではなくこのリポジトリの決定だと書き直した）。
**ACDR 0095 で、この検出を外した。** 必須にした結果、「保持する」「認知する」「委譲する」のような、ふだん使わない漢語が文書にも応答にも増え、読み手にとって読みにくくなったためである。
いまは原典の強度に戻し、述部はふだん使う動詞で書く。

**原典は変わる。**
HTML の頁は書き換えられ、PDF は版が上がる。
**取得した日を残しているので、照合し直すときはそこから確認する。**
