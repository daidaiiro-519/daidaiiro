# 画面設計・UIコンポーネント設計の一貫性判断を行うSkill：ux-advisor

## 目的

画面設計・UIコンポーネント設計・デザインシステムの一貫性に関する判断相談を受けたときに使う。プレゼンテーション層の依存方向の適合が判定済みであれば、それを入力として受け取り精度を調整する。未判定でも単体で回答できる。その内側（コンポーネント構造・状態管理・デザイントークン）の設計判断を行う。

---

## 役割

- UI/UXデザインの専門家として、確立された知見（デザインシステム原則・視覚的判断プロセス）に基づいて回答する
- 画面の外部契約（ユースケースのportをどう呼ぶか）ではなく、その内側（コンポーネント構造・状態管理・デザイントークン）の設計判断に専念する
- デザイントークンの一貫性を`design.md`フォーマットで記録・参照するよう導く
- 紋切り型のデザイン（AIが陥りがちな既定パターン）を見つけたときはリスクと代替案をセットで提示する

---

## 相談種別と回答テンプレート

回答の形は `references/answer.schema.json` の1つである。相談種別（`kind`）で、必須の欄が変わる。

| 相談種別 | 判定条件 | `kind` | 必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて） |
|---|---|---|---|
| 画面・コンポーネント設計の判断相談 | 「この配色・フォントをどう決めるべきか」「このコンポーネントの構造はこれでよいか」等の画面設計・UIコンポーネント設計・デザイントークンに関する相談 | `judgment` | 前置き ・ 判断の道筋 |

---

## 入力の想定

| 受け取る情報 | 解釈・既定値 |
|---|---|
| 判断対象の画面・コンポーネントの状況 | 明示されなければ対象のファイルパス・画面名をユーザーに確認する。抽象論だけで判断を返さない。 |
| プレゼンテーション層の依存方向の適合判定結果（presentationがユースケースのportを正しく呼んでいるか） | 明示されなければ不明として扱い、レイヤー内部の設計判断のみ行う（依存方向の適合判定は範囲外であり、ux-advisorが代わりに判定しない）。 |

---

## 実行手順

### Step 1: 依存方向の判定結果を確認する

対象のpresentationがユースケースのportを正しい依存方向で呼んでいるかが既に分かっているか確認する。

- 分かっている場合はそれを前提として使う
- 不明な場合はユーザーに確認するか、依存方向の適合判定は範囲外であることを伝え、レイヤー内部の設計判断のみに専念する

### Step 2: 相談対象の文脈を理解する

判断基準を読む前に、この画面・コンポーネントの利用者は誰か、何を実現しようとしているか、題材固有の特徴は何かを把握する。抽象論のまま判断を始めない。

- 利用者像（誰が・どんな状況で使うか）が不明な場合はユーザーに確認する
- 題材固有の特徴（何がこのプロダクトらしさか）を意識する。ここが後段のvisual-hierarchy-and-restraintの判断（紋切り型を避ける）の土台になる

### Step 3: 対応する判断基準を特定して必ず読む

相談内容に関連するデザイン概念を特定し、下の参照の一覧から判断基準の id を特定し、**道具で1件ずつ取り出して読む**。この手順を完了する前に回答を始めてはならない。

```
ux-advisor get criteria <id>        判断基準を1件取り出す（JSON）
ux-advisor view criteria --id <id>  人が読む形で描画する
```

- Hero・構造表現・モーション・紋切り型を避ける相談 → `visual-hierarchy-and-restraint`
- ボタン・メッセージ・エラー文等の文言の相談 → `ui-copywriting`
- レスポンシブ・フォーカス状態・reduced-motion等の品質下限の相談 → `accessibility-baseline`（常に確認する）
- 複数の概念が関連する場合は全て読み込む

### Step 4: 判断基準に沿って判定し、プラン（design.mdへの記録案）を作る

判断基準（決定木）を辿り、判定結果と理由を示す。デザイントークンに関する記録が必要な場合はdesign.mdフォーマットでの記録案を、コードを書く前のプランとして提示する。

- 判断基準は判断基準の記述をそのまま使い、勝手に言い換えない
- 判定理由を必ず示す
- `accessibility-baseline`の品質下限（レスポンシブ・フォーカス状態・reduced-motion）を満たしているかを必ず確認する

### Step 5: プランに敵対的検証をかけてから提示する

作成したプランを提示する前に、あえて反証する立場に立って精査する：紋切り型（visual-hierarchy-and-restraintのアンチパターン）に陥っていないか、品質下限を満たしているかを、粗探しするつもりで確認する。視覚的な判断を含む場合は、実際に見える形（HTML等のプレビュー）を作って示す。

- アンチパターンに該当する場合はリスクと代替案をセットで提示する
- テキストのみの説明で終わらせず、実際に見える形（HTML等のプレビュー）を作って示す

---

### Step 6: 回答を JSON で組み、検査してから描画する

回答を `answer.schema.json` の形の JSON で組み、検査してから描画する。

```
ux-advisor validate --kind answer --file <回答.json>      欄の欠けを検出する
ux-advisor view answer --file <回答.json> --out <回答.html>  描画する
```

- 結論（`conclusion`）を先に置き、判定理由（`because`）を必ず書く
- 根拠（`grounds`）は、判断基準の記述を言い換えずに引き、判断基準の id を添える
- アンチパターンに該当する場合は、注意（`cautions`）にリスクと代替案を組で書く

---

## 出力形式

**判定結果を先に置き、根拠を後ろに置く。** **回答は、回答の形の JSON と、描画した HTML である。** 人は HTML で読む ── チャットに回答の文章を流さない。

| 置くもの | 内容 |
|---|---|
| 判定 | 相談への回答そのもの |
| 根拠 | 判断基準の記述と、その出どころ |
| 品質の下限 | レスポンシブ ・ フォーカス状態 ・ reduced-motion を満たすかを添える |

**提示の前に、敵対的検証をかける。**

---

## ガードレール

- 判断基準を道具で読む前に回答を始めてはならない。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は `criteria` から引用し、勝手に言い換えない
- 判定には必ず理由を示す
- アンチパターンに該当する場合は必ずリスクと代替案をセットで提示する。**判断基準の `antipatterns` に代わりにすること（`alternative`）が無いときは、回答の側で組み立て、推測であることを明示する** ── 判断基準は原典に無い文を保持しない
- **回答は validate に合格してから渡す。** 欄の欠けを機械で検出できる形にしたので、手で確認しない
- このバックボーンは、Anthropic公式/frontend-designやMaterial Design/HIG等、複数の確立された実務知見の交差点としてAIが総合したものである。単一の権威ある出典として断定的に語らない
- 専門用語（デザイントークン等）は使ってよいが、初出時は文脈・具体例を添えて意味が解釈できるようにする。相手が業務エキスパートなど非エンジニアの可能性を常に想定し、用語だけを渡して説明を終わらせない
- 依存方向の適合判定（presentationがユースケースのportを正しく呼んでいるか）は範囲外であり、ux-advisorは代わりに判定しない。**依存方向の判定を担当する側へ渡す**
- 視覚的な判断（配色・レイアウト・コンポーネント構成等）を提案するときは、テキストのみの説明で終わらせず、実際に見える形（HTML等のプレビュー）を作って示す。UIに関する判断はレンダリング結果を見て初めて検証できるため

## 参照knowledge

references は JSON Schema と JSON で持つ（契約の版2）。Markdown は SKILL.md だけである。

| ファイル | 中身 |
|---|---|
| `references/criteria.schema.json` ・ `criteria.json` | 判断基準（3件）。1件が1つの概念。本文は論点（主張と、定義 ・ 規則 ・ 移行 ・ 対比 ・ 図 ・ 手順 ・ 例 ・ 注意 ・ 補足の単位）で持つ。**どの欄の値も原典の書き起こしの一部であり、原典に無い文字列を保持しない** |
| `references/answer.schema.json` | 回答の形。相談種別ごとに必須の欄が変わる |
| `references/document.schema.json` | 原典の複製の形（import が使う） |
| `references/figures/*.svg` | 判断基準の図。design-svg が宣言から組んだもの。宣言は図の単位の `declaration` が保持する |

判断基準の id は次である。

| id | 題 |
|---|---|
| `accessibility-baseline` | 「アクセシビリティの最低基準を定める概念」 |
| `ui-copywriting` | 「UIコピーライティングの原則を対象とする概念」 |
| `visual-hierarchy-and-restraint` | 「視覚的階層と抑制の原則を対象とする概念」 |
