## 2026-10-31 の語の決まりと位置づけ
- 「要件定義」「要求仕様」をやめた（usecase-advisor、scratchpad の term-uc）。段階名は「要求を書く」（4段階：要求を書く → 見つける → 設計する → 確かめる）、成果物は「要求文書」。Q2＝要求の書き方、Q6＝要求文書のインスタンスと項目、Q7＝要求文書の画面。ボード（round 8、artifact 版8）とシミュレーション（版4）は直した。「機能要求」「データ要求」などはそのまま。
- レベルの印（＋ ！ －）は分かりにくいと利用者が指摘 → 「要約」「ユーザー目的」「サブ機能」の言葉の札にした（render2・found3）。土台（docs/foundation）の印は Q8 の「土台を分ける」ACDR で直す。
- 位置づけ（現在地のページ P9c3… の節にまとめた）：Semantic Agent Schema は事業領域（プロダクト全体）。以前は土台の図で事業領域でありながら「基盤の文脈（1つ）」としてプロダクト全体を1つの文脈にしていた → 10-30 に取り消し。業務領域は事業領域を分解して見つけるもの（問題の側）、区切られた文脈は設計するもの（解決の側）で、対応は設計判断・1対1に限らない（土台の概念、決まり）。文脈を決める手順は Q3（回答待ち）、実際の文脈は未決。Q3 の「最も広い1つの文脈から始める」は「事業領域＝1文脈」と読まれうるので、Q3 を決めるとき書き方を直す。
- 10-29 に合意した「境界はトップダウンで先に広く（区切られた文脈＝意味の境界と公開する契約）、中身（集約・値・ルール）はユースケースから後で育てる」は有効のまま（利用者が 10-31 に確認）。無効なのは「広く」を「事業全体で1つ」と当てたことだけ。Q3 を開くとき、「部品を探す前に、用語集で同じ語が同じ意味で通じる範囲を引く」を答えに入れる（advisor と反証を通す）。シミュレーションの「判定」が2つの意味で使われていることが実例。
