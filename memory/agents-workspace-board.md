## SAS のセッションと操作の契約をどう使うか（2026-10-31 夜、利用者と話した見解）
- 訂正：SAS のセッションは単発だけではない（「単発」は SAS の範囲の版5 の古い記憶だった）。基盤は親＝呼び出し元のセッション（sessions）を前提にし、操作はすべてそこにぶら下がる。`-p` でも同じ `--session` を渡せば同じセッションに積まれる。SAS がセッションを立てる（launched_sessions、caller_session_id で親を持ち continuing も可）のは別のコンテキストで動かしたいときだけ。
- 利用者の判断：基盤で十分 AW に使える。ただし目的の表は AW が作る。そこにセッション ID を入れておきたい。
- 外部キーはファイルをまたげない：SQLite の `REFERENCES foreign-table` に schema-name を書く所が無い（sqlite.org の CREATE TABLE の頁で確認）。ATTACH なら JOIN はできる。→ セッション ID は値として持つ（文脈をまたぐ参照は ID で持つのが普通）。
- 持ち方の案（訂正後）：使う側は SAS の DB を間借りしない（DDL は非公開・trigger の決まり・物置になる・コミットしないので消えて困る物を置けない）。置き場所は3つ ── 残すもの（目的 ・ ワークフローの定義 ・ 承認の記録）は Concrete のインスタンスとして SAS で書いて Git にコミット／SAS の操作の経緯は SAS の DB を CLI で読むだけ／動いている間だけの状態（どのワークツリーでどのセッションが動いているか）は AW が自分で持ち、Git から作り直せる形に。目的とセッションの結びつきの正本は目的のインスタンス（セッション ID を値で）。`--caller purpose/<id>` → caller_ref は経緯を引く手がかり。利用者の問い「Concrete で DB やセッションが絡むものは SAS のセッション DB を間借りするのか、運用が回るか」への答え。Q1 の論点にする（ddd ・ platform ＋ fork）。
- DB の置き場所：利用者「コミットしないのでリポジトリ内に持つ必要はない」。案は利用者のデータの置き場所（例 `~/.local/share/sas/<リポジトリの識別>/sas.db`）。識別は `git rev-parse --git-common-dir` の絶対パスならワークツリーをまたいで同じになり、ワークツリーごとに DB が分かれる問題も消える。今の実装は `<作業ディレクトリ>/.sas/sas.db` 固定、設計は設定の db_path。既定を SAS の作り直しで決め直す。
- 今のセッションの表：実装（0001-validate.sql）は id ・ actor（human/tool）・ tool_ref（--session、重複不可）・ started_at ・ ended_at だけで caller_ref はまだ無い。人のセッションは開いているものを使い回す。設計は caller_ref ・ adapter ・ last_used_at ・ ended_as を足し、launched_sessions と session_turns を持つ。
- 引っかかり：開いている人のセッションは1つだけ（sessions_open_human）で、開いている間は caller_ref を変えられない。人が目的 A → B と続けて承認すると B の操作も A の参照になる。見解は「caller_ref を操作1件ごとに持たせる」（SAS の契約の変更）。もう1つの手は承認ごとに人のセッションを開き直す（AW だけで済む）。
- 結合度（利用者の問い「SAS の DB のセッション情報を AW でも使う、結合度の高い運用で回るか」）：見立ては、表を直接読むのは回らない、CLI が返す公開のスキーマ（session ・ operation-result、schemas/v1、版を持つ）にだけ依存するなら回る（公開された言葉に合わせる側、向きは AW → SAS の一方）。条件3つ ── セッション ID は AW が起動した側として自分で知っている／SAS の情報が無くても主な流れ（Git の差分で承認）が止まらず、SAS の経緯は意図を添えるだけ／読むのは公開のスキーマの出力だけ。
- SAS のセッション管理を軽くする意見を、アドバイザーと反証に通して [[sas-light-sessions-opinion]] に置いた（SAS のセッションへ渡す。未承認）。
- 上の2つ（caller_ref の持ち方、DB の既定の置き場所）は SAS に関わるので、ボードの Q1「SAS との境目」の論点にする。

## SAS の最終の形を受けて（2026-11-01）
- SAS の形は [[sas-light-sessions-opinion]] の冒頭（薄い sessions、caller_ref と --caller は無し、親が子の ID を --continue で渡す）。これで前の「caller_ref を操作ごとに」「人のセッションが1つで参照が混ざる」の引っかかりは消えた。
- AW での扱い：親＝ワークツリーで動く AI のセッション（ID は環境変数から SAS が取る。AW は --session を渡さなくてよい）。目的とセッションの結びつきは、目的のインスタンスに親のセッション ID を値で書く（AW は自分で起動するので ID を知っている。起動し直したら ID を足す）。SAS の記録は parent_session_id で引く。書く子 ・ 確かめる子の ID は親が持ち、AW は持たなくてよい。確かめる子が書く子と別なのは、AW の AI レビューの独立と合う。
- 残る論点：AW の承認のボタンが Claude Code の中から sas を呼ぶと環境変数で AI と見なされる → 人の操作は環境変数を外した起動で呼ぶ。逆に AI が環境変数を外せば人に見える（人の入口の確かさ）。Q1 の論点。

- DB を分けるか（2026-11-01、利用者「DB ファイルが分かれるのは運用がむずい。sas.db に入れてもいいけど悩ましい。マイグレーション SQL があればいつでも作れればいい」）：見立ては「AW は正本の DB を持たない」。目的 ・ ワークフローの定義 ・ 承認 ・ 目的とセッション ID の結びつきはインスタンスで Git に、計画表の状態は Git（ワークツリー ・ ブランチ ・ タグ）から導く、誰が何を変えたかは SAS の CLI で親のセッション ID から引く。sas.db に同居させない（SAS が作り直すデータと決め、マイグレーションも SAS が持つ）。表示が遅くなったら作り直せる控え（例 `<git-common-dir>/agents-workspace/cache.db`）だけ足す。Q1 の答えの案に入れる。
