# Semantic Agent Schema

JSON Schema を Semantic に拡張し、その型（Abstract → Concrete → インスタンス）で作成・更新・削除・検証・描画・検索する基盤。

| 置き場所 | 何か |
|---|---|
| このフォルダ | 製品 Semantic Agent Schema のリポジトリ。区切られた文脈ではない（事業領域は「AI のエージェントが扱う構造化データを、スキーマに従って書き、検証すること」） |
| `schemas-and-instances/` | 区切られた文脈「スキーマとインスタンス」。中の作り方はポートとアダプター |
| `schemas-and-instances/published-language/v1/` | 公開された言葉（使う側が従い、読む通信規約）の9つ：Concrete を書く型（abstract ・ vocabulary ・ dialect）・ CLI の出力（command-result）・ 打ったセッションへの手順（procedure）と、そのセッションが --answer で渡す答えの形（judgment-answer ・ search-answer）・ 受け取りの型（design-system ・ template-language） |
| `schemas-and-instances/writing/` ・ `validation/` ・ `search/` ・ `recording/` ・ `rendering/` | writing と validation は業務領域「書いて検証する」（中核）を作る2つのモジュール（domain と application）。search は業務領域「検索」、recording は業務領域「記録」、rendering は業務領域「描画」（どれも補完）のモジュール（application だけ）。集約は writing/domain |
| `schemas-and-instances/adapters/` | 入口（inbound/cli、sas）と外の技術（outbound/filesystem ・ git ・ jsonschema ・ sqlite ・ templates ・ javascript） |
| `schemas-and-instances/system-tests/` | システムテストの場面（`scenarios/`）と材料（`fixtures/`）、保証 ・ 拡張との突き合わせ（`trace.json` ・ `untested.json`） |
| `docs/foundation/` | 土台。どの事業にも使う共通の概念 |
| `docs/design/` | Semantic Agent Schema に適用した設計。仮説と、探索の記録 |

作り方は、ユースケースから探索してドメインモデルと構成を育てる進め方による。いまできるコマンドは `sas validate [--session <名前>] [--stale] (<経路>... | --all)`（UC4。形の検査と組み込みの検査。rule は --answer で判定を渡さなければ unsupported）・ `sas create <経路> --concrete <URN> --value <JSON>`（UC1）・ `sas update <経路> --patch <JSON Patch> [--if-match <ハッシュ>]`（UC2）。create と update は `--reason` ・ `--session` ・ `--request-id` も受け取る。`sas delete <経路> --reason <理由>`（UC3）は対象だけを消し、ほかの文書は書き換えない（Concrete は従うインスタンスがあれば止める）。update と delete は、--if-match を省くと、いまの中身が SAS の記録のどれかの事後かを確かめ、違えば書かずに間に入った変更を返す。打ったセッションの ID は `--session` → AI のツールの環境変数（`adapters/inbound/cli/callers.json`）→ このフォルダで `sas init [--session <ID>]` が最後に登録したセッションの順で決まり、どれも無ければ人とみなす。最初に sas を打ったときに、そのセッションを sessions に1行足す。記録は `<git-common-dir>/sas/sas.db`（ワークツリーで1つ。コミットしない）に置き、断った操作は記録しない。SAS を通らない変更は、`sas create <経路> --adopt`（記録に無い既存のファイル）と `sas update <経路> --adopt --reason <理由>`（SAS が書いたあとに外で直されたファイル）で、ファイルを書かずに記録へ取り込む。`sas validate --stale` は、前の判定が読んだ所（rule の reads を含む）が変わった rule だけを判定し直す（--semantic と一緒なら、前に判定できなかった rule も手順に入れる）。`sas render <経路>... --design-system <経路> --out <書き出す先>`（UC5）は、使う側が渡すデザインシステムのテンプレート（Mustache。Concrete の根の x-view で選ぶ。無ければ page）に、インスタンスの値（value ・ json）とデザイントークン（tokens ・ css）を入れて描く。テンプレートが表現するロジックと UI ・ UX はテンプレートの JS が持ち、SAS は持たない。テンプレートの書き方は published-language/v1/template-language.json が契約で、`sas validate <デザインシステム>` で型 ・ トークン ・ テンプレート ・ JS を契約に照らせる（テンプレートが置く名前と、JS が値の入口 sas-data から読む欄が、Concrete にあるか）。外れたデザインシステムでは描かない。同じ入力からは同じページになり、描いたページは記録もコミットもしない。SAS はエージェントを起動しない。`sas validate <経路>... --semantic`（UC4 の変形「意味の判定」）は、機械の検証のうえで、x-prompt の rule × 当たる所ごとに1ステップの判定の手順（published-language/v1/procedure.schema.json）を標準出力へ出す（記録しない。意味の rule が無ければ機械の検証を記録して返す）。手順の steps はレビューのまとまり（所のまとまり：pointer ・ before ・ current ・ changes ・ rules と、文書全体のまとまり：changed ・ changes ・ rules。changes は前の判定のあとの変更の操作で、--reason で渡した理由が入る）で、根の review に前の判定（since）と範囲（scope：changed ・ all-rules ・ first）を持つ。判定済みの対象では、前の判定のあとに記録された変更（取り込みを含む）の所と重なる rule ・ その所を reads で読む rule ・ 文書全体に当たる rule ・ 文が変わった rule だけを入れ（`--all-rules` と初めての対象はすべて）、ほかの所は前の判定を引き継いで記録する。rule の全文は手順の rules に1回だけ書く。判定は書いたときとは別の文脈で行うよう、手順の constraints で求める。手順にはいまの中身と rule と rule の reads の値だけを入れる（前の判定は入れない）。打ったセッションが判定し、`sas validate <経路> --answer <ファイル | ->` で判定の JSON（published-language/v1/judgment-answer.schema.json。hash 必須）を渡すと、SAS は答えの形 → ハッシュ → step ・ rule ・ pointer の順に確かめて記録する。形か突き合わせが違えば invalid_answer、ハッシュが違えば conflict（手順の取り直しを案内する）。`sas create <経路> --concrete <URN> --semantic [--task <依頼>] [--ref <資料>]...` と `sas update <経路> --semantic --task <依頼> …`（UC1 ・ UC2 の意味で書く変形）は、Concrete の rule から書く手順を組み（rule の reads で書く順を決め、--ref は SAS が読んで中身を入れる）、標準出力へ出すだけで記録しない。手順の command に書くコマンド（作成は `sas create … --value <値の JSON>`、更新は `sas update … --patch <JSON Patch> --if-match <手順のハッシュ>`）が入り、打ったセッションがそれで書く。断られたら理由を読んで直し、打ち直す。人が決める欄は書かせない。手順の answer.schema には、書いた文書が従うスキーマの本体（Concrete を書くときは Abstract、インスタンスを書くときは Concrete。$ref で指すほかの文書は $defs に入れる）が入る。`sas log [<経路>...] [--by <セッション ID>] [--folder <フォルダ>] [--since <時刻>] [--limit <件数>]`（UC7）は、記録にある操作（変更と検証）を新しい順に1行1件（kind operation）で返し、`sas log --operation <ID>` は1件の中身を書いたとき ・ 検証したときと同じ change ・ validation の形で返す（無い ID は not_found）。読むだけで、セッションの行も足さない。`sas search (<経路>... | --concrete <URN> | --all) --where <JSON Pointer>=<値>`（UC6。値が JSON として読めなければ文字列）は、範囲のうち条件のすべてに一致した所と値を、探した範囲（経路とハッシュ）と一緒に返す。`sas search <範囲> --semantic --question <問い>` は範囲の文書ごとに1ステップの手順を返し（範囲の中身の合計が 64KB を超えたら range_too_large）、打ったセッションが `sas search <範囲> --answer <ファイル | ->` で答えと出どころ（経路 ・ 所 ・ ハッシュ。published-language/v1/search-answer.schema.json）を渡すと、SAS は出どころが範囲の中か ・ ハッシュがいまと同じか ・ 所があるかを確かめ、その所のいまの値と一緒に返す。検索は記録しない。ステップごとの記録は `docs/design/exploration/` にある。前の実装は `archive/semantic-agent-schema-2026-10-31/`（タグ `semantic-agent-schema-archive-2026-10-31`）に残してある。
