抽象概念の土台

全体像

事業を設計 ・ 実装するための抽象概念。基盤自身にも、基盤で作るものにも使う。3つの層を分けて持ち、どの形を選んでも13の境界を守る。

層1 業務領域事業領域を分解して見つける。線は「分解」
層2 目的レベルユースケースの高さ。線は「呼び出し」
層3 区切られた文脈意味の境界として設計する。線は「連係」

目的は、あとから「この文脈で分けたのは間違いだった」と作り直さないこと。そのために、意味の境界を先に広く引き、中身はユースケースから後で育てる。

Semantic Agent Schema に適用した結果（業務領域 ・ 文脈 ・ ドメインモデル ・ ER ・ スキーマ構成 ・ ディレクトリ）は docs/design/ にまとめる。この頁はどの事業にも使う概念だけを持つ。

3つの層

業務領域は見つけるもの、文脈は設計するもの。対応は設計判断で、中に入る関係でも1対1でもない。

事業領域 → 業務領域（問題の側）作るプロダクト全体が事業領域。それを事業活動の単位に分解して、業務領域を見つける。区分（中核 ・ 補完 ・ 一般）は業務領域の属性で、変わりうる
区切られた文脈（解決の側）1つのモデルと言葉が同じ意味で通じる範囲を、設計で引く。業務領域を手がかりに引く。1つの文脈が複数の業務領域を受け持つことも、1つの業務領域を複数の文脈で扱うこともある。事業領域そのものを1つの文脈とみなさない
下へ：どのように？目的を手順へ分ける
上へ：なぜ？手順をまとめて1つ上の目的へ
外へ：設計の範囲一番外側に要約を書く（別の軸）
詳しい表
層何を表すか線の意味決め方
層1　業務領域事業活動を細かく分けたもの。何をするかを表す。見つける（問題の側）分解：事業活動を細かく分けるユースケースの3条件（同じアクター ・ 同じ外部システム ・ 密接なデータ）でまとまるまで分ける。補完 ・ 一般は分けても区分が変わらなければ止め、中核はできる限り正確に区切る
層2　目的レベル主体の目的の高さ。要約 ・ ユーザー目的 ・ サブ機能呼び出し：なぜ？で上、どのように？で下目的レベルと設計の範囲は別の軸として持つ
層3　区切られた文脈1つのモデルと言葉が通じる範囲。設計する（解決の側）連係：上流 ・ 下流と、その方法言葉の一貫と、同じデータを扱うユースケースの集まりで線を引く

意味の境界を先に、中身はあとで

区切られた文脈（意味の境界）と公開する契約は、部品を探す前に先に引く。中身（集約 ・ 値 ・ 共通のルール）は、ユースケースと実際の重複から後で育てる。

先に引く：意味の境界と公開する契約あとで変えると、パッケージの分割 ・ データの分離 ・ 依存の付け替え ・ 相手との取り決めが必要になり、高くつくただし広く引く。業務知識が乏しいほど広くし、知識が増えてから小さな文脈を切り出す「広く」は「事業全体で1つ」ではない。範囲は、用語集で同じ語が同じ意味で通じるかで決める
後で育てる：集約 ・ 値 ・ 共通のルール初めに描いた中身は外れやすい。ユースケースを書き、実際に重複したルールを見てから引き上げる引き上げるかは「同じ理由で一緒に変わるか」で決める。見た目が同じでも変わる理由が違えば、まとめない

意味の境界が無いと起きること

同じ語が2つの意味で使われていると、その2つが1つの部品に混ざる。たとえば「記録」という語が、ある所では「1件ごとに置き換える値」、別の所では「消さずに積み上げる出来事」を指すとき、境界を引く前に部品を探すと、その記録を値オブジェクトにするか業務イベントにするかが決まらない。先に、語の意味が1つに通じる範囲を引いてから、その中で部品を探す。

13の境界

パターンは選ぶもの、境界は守るもの。どの境界も、防ぐ失敗を1つ持つ。

防ぐ失敗と出どころ
#境界防ぐ失敗出どころ
1業務領域は事業活動に届くもので、まとまりはユースケースの3条件で決める。都合で入れない業務領域の中身が目的と関係なく増え、あとで業務領域を分け直すことになるddd-advisor ・ あなたの「分解」
2呼び出しの親子には「なぜ？」で届く目的だけを入れる。サブ機能は、複数から使われるか呼び出し側が読みにくくなるときに切り出し、親を1つに決めない。ユーザー目的から別のユーザー目的を呼んでもよいどの目的のための手順かを辿れなくなり、サブ機能が乱立するusecase-advisor
3目的レベル ・ 設計の範囲 ・ 業務領域は別々の分類として持つ。区分（中核 ・ 補完 ・ 一般）でディレクトリの置き場所を決めない（区分は実装方法と連係の選び方を決める）1つの分類から他を決めつけ、置き場所や実装を誤る。区分が変わるたびに組み替えるusecase-advisor ・ ddd-advisor
4どのユースケースにもレベル欄とスコープ欄を持たせる高さの違うユースケースを、印なしで同じ並びに置いてしまうusecase-advisor
5低すぎる目的はユースケースにせず、呼ぶ側の手順に含める細かすぎるユースケースが増え、追跡とテストの手間が増えるusecase-advisor
6ユースケースを1つずつクラスやフォルダに対応づけないユースケースを足すたびに、コードの構造を組み替えることになるusecase-advisor
7同じデータを扱うユースケースの集まりを、文脈の線で割らない同じデータを扱う処理が2つの文脈に分かれ、一貫性が壊れるddd-advisor
81つの文脈に、競合するモデルを入れない1つの文脈の中で言葉の意味が割れるddd-advisor
9文脈どうしは連係方法を明示して選ぶ。中核を含む下流は従属しないつなぎ方が暗黙になり、上流の変更で中核が壊れるddd-advisor
101つの文脈は1つのチームだけが持つ（AI のセッションをチームとみなすかは事業ごとに決める）1つの文脈を複数で直し、変更がぶつかるddd-advisor
111つの集約を2つの文脈に分けない1つの集約の不変条件を2か所で守ることになり、破れるddd-advisor
12集約の状態は、集約の中の業務ロジックだけが変える。外には参照だけ外から状態が変えられ、不変条件が守れないddd-advisor
131つのトランザクションで変える集約は1つ1回の変更で複数の集約を書き、一部だけ失敗したときに整合が崩れるddd-advisor

ユースケース

単位はユーザー目的。コマンドはそれを呼ぶ入口で、ユースケースではない。

文脈

型は4つ。業務知識が乏しいうちは型1から始め、言葉が分かれた所で切り出す。どの型でも、事業領域そのものを1つの文脈とみなさない。

型ごとのディレクトリ
型選ぶときディレクトリ
型1　広い1つの文脈理解が浅い ・ 変更が多い ・ 小さいチーム ・ 言葉を共有しているリポジトリの根の直下に文脈のフォルダを1つ置き、その中を業務領域を作るモジュールで分ける
型2　1対1業務領域ごとに言葉や変わる速さが違う ・ チームが分かれているリポジトリの根の直下に業務領域ごとの文脈のフォルダを並べ、それぞれがポートとアダプターと外へ出す言葉を持つ
型3　まとめて分ける言葉を共有する業務領域とそうでないものがはっきりしているリポジトリの根の直下に束ねた文脈のフォルダを置き、その中に業務領域を作るモジュール
型4　1つの業務領域を複数の文脈で扱う課題ごとにモデルが違うとき。割らないのは、同じデータのユースケースの集まりと集約同じ業務領域が、モデルごとに別の文脈に入る

セッション

AI で仕事を進めるときのセッションの形。セッションは1つのフォルダに1つ。ふだんはセッション1つで進め、目的を分けるときはフォルダ（ワークツリーなど）を用意してセッションを1つ立てる。道具のコマンドはセッションを増やさない。

概念何をするか
いま動いているセッション利用者と話す。ふだんはこれ1つで進める。目的を分けるときは、ほかのフォルダのセッションを立て、様子を見て、最後の答えを集める
ほかのフォルダのセッション目的ごとのフォルダに1つ。画面は無くプロセスとして動き、そのフォルダで再開すれば画面で開ける。ツールと許可は、立てた側と同じ条件
立ち上げる作業を進める側が、フォルダとセッションを1つずつ用意する。セッションがもうあるフォルダには立てない
続きを頼む同じ目的なら、新しく作らず同じセッションを再開する
道具のコマンド打ったセッションの操作として記録するだけ。セッションもプロセスも増やさない。道具が知っているのは、どのセッションが打ったかだけ
様子を見る各セッションの出力と、どのセッションが何をしたかの記録で追う
記録を始める道具は、セッションが最初に打ったときに、そのフォルダでの記録を始める。セッションの ID が取れないツールのために、明示して登録する入口も持つ
確かめる書いたものを別のセッションに確かめさせるか、どこに置くか（同じセッションのサブエージェント、またはコミットを取り出した別のフォルダ）は、作業を進める側が決める。道具は判定の手順を返し、判定を記録するだけ
外した形と理由
外した形理由
道具が、操作のたびに AI のセッションを新しく起動する画面の無いプロセスが操作の数だけ増え、何が起きているか誰にも見えない。続きのはずの仕事が、前のやりとりを持たないセッションで始まる
道具が AI の答えを受け取り、直させる中継をする目的のセッションが道具の出力を読み、自分で直して打ち直せば足りる

ヘキサゴナル

文脈の中はポートとアダプターで作る。コアは domain と application で、ポートは、それを使うユースケースを持つモジュールの application が宣言する。

ユースケース目的を果たす手順と判断（application の use_cases）
ドメイン値を受け取り値を返す。複数のモジュールが使う判断と値もここに置く（domain）
ポート外に依頼する1回の約束。DB の表や外の仕組みの側からではなく、ユースケースから見つける（application の ports）
アダプターその1回を技術で実現する（outbound）。1つのアダプターが複数のモジュールのポートを実装してよい
入口誰が呼んだかのような外からの入力を読み取り、値でユースケースに渡す（inbound）

業務ロジックの置き場所は、上から決めて下から確かめる。守る条件がすでに書けている所（決定 ・ 規則 ・ 試験の場面）は初めから domain に置き、それ以外は use_cases にトランザクションスクリプトで書いて、同じ理由で変わると確かめたものだけを domain へ引き上げる。

どのモジュールがどのポートを宣言するかは、事業ごとに決める（Semantic Agent Schema では docs/design/）。

ディレクトリ

文脈の根は、リポジトリの根の直下の、文脈の名前のフォルダ。その中に、業務領域を作るモジュールごとの domain と application、外側に adapters/ の inbound と outbound。

置き方の決まり
  • 文脈の根：リポジトリの根の直下の <文脈の名前>/。文脈が1つでも同じ。リポジトリの根は製品の置き場で、文脈の根にしない
  • 文脈の根の下に、業務領域を作るモジュールごとの <モジュール>/{domain, application}。文脈の根に domain を置かない。domain は集約 ・ 値 ・ ドメインサービスでポートを知らず、守る条件が確かめられたモジュールだけが持つ。application は use_cases と ports
  • ポートは、それを使うユースケースを持つモジュールが、自分の application に、使うメソッドだけで宣言する。同じ形のポートもモジュールごとに宣言し、1つのアダプターがそれらを実装してよい。共有の置き場は作らない
  • モジュールの application は、ほかのモジュールの application（ポートもユースケースも）に依存しない。複数のモジュールが使う判断と値は domain に置く
  • 誰が呼んだかのような外からの入力は、入口のアダプターが読み取り、値でユースケースに渡す。ユースケースは自分で調べない
  • ユースケースは1つにつき1ファイルにしない（境界6）。目的レベルでフォルダを分けない（境界3）。区分でも分けない
  • 外側は adapters/ の inbound（入口）と outbound（外の技術）。入口を足すときは inbound に足す

言語やビルドのツールに合わせた置き方（crate の分け方など）は、事業ごとの具体に書く。
