抽象概念の土台

全体像

Semantic Agent Schema を設計 ・ 実装するための抽象概念。3つの層を分けて持ち、どの形を選んでも13の境界を守る。

層1 業務領域見つける。線は「分解」
層2 目的レベルユースケースの高さ。線は「呼び出し」
層3 区切られた文脈設計する。線は「連係」

この土台は、基盤自身を設計するときにも、基盤で何かを設計するときにも同じ概念として使う。目的は、あとから「この文脈で分けたのは間違いだった」と作り直さないこと。

3つの層

業務領域は見つけるもの、文脈は設計するもの。対応は1対1に限らない。

下へ：どのように？目的を手順へ分ける
上へ：なぜ？手順をまとめて1つ上の目的へ
外へ：設計の範囲一番外側に要約を書く（別の軸）
詳しい表
層何を表すか線の意味決め方
層1　業務領域事業活動を細かく分けたもの。何をするかを表す。見つける（問題の側）分解：事業活動を細かく分けるユースケースの3条件（同じアクター ・ 同じ外部システム ・ 密接なデータ）でまとまるまで分ける。補完 ・ 一般は分けても区分が変わらなければ止め、中核はできる限り正確に区切る
層2　目的レベル主体の目的の高さ。要約（＋）・ ユーザー目的（！）・ サブ機能（－）呼び出し：なぜ？で上、どのように？で下目的レベルと設計の範囲は別の軸として持つ
層3　区切られた文脈1つのモデルと言葉が通じる範囲。設計する（解決の側）連係：上流 ・ 下流と、その方法言葉の一貫と、同じデータを扱うユースケースの集まりで線を引く

パターン

層ごとに選ぶ。文脈は「広い1つ」から始める。

詳しい表
層パターン選ぶとき
層1細分化事業活動を、3条件でまとまるまで分ける。中核はできる限り正確に
層2要約 → ユーザー目的 → サブ機能サブ機能は、読みやすくするときか、ほかから何度も使うときだけ書く

層2一番外側に要約を書く設計の範囲の軸。主体が外にいる一番外側の範囲で、いつも書くことを勧める

13の境界

パターンは選ぶもの、境界は守るもの。どの境界も、防ぐ失敗を1つ持つ。

防ぐ失敗と出どころ
#境界防ぐ失敗出どころ
1業務領域は事業活動に届くもので、まとまりはユースケースの3条件で決める。都合で入れない業務領域の中身が目的と関係なく増え、あとで業務領域を分け直すことになるddd-advisor ・ あなたの「分解」
2呼び出しの親子には「なぜ？」で届く目的だけを入れる。サブ機能は、複数から使われるか呼び出し側が読みにくくなるときに切り出し、親を1つに決めない。ユーザー目的から別のユーザー目的を呼んでもよいどの目的のための手順かを辿れなくなり、サブ機能が乱立するusecase-advisor
3目的レベル ・ 設計の範囲 ・ 業務領域は別々の分類として持つ。区分（中核 ・ 補完 ・ 一般）でディレクトリの置き場所を決めない（区分は実装方法と連係の選び方を決める）1つの分類から他を決めつけ、置き場所や実装を誤る。区分が変わるたびに組み替えるusecase-advisor ・ ddd-advisor
4どのユースケースにもレベル欄とスコープ欄を持たせる高さの違うユースケースを、印なしで同じ並びに置いてしまうusecase-advisor
5低すぎる目的はユースケースにせず、呼ぶ側の手順に含める細かすぎるユースケースが増え、追跡とテストの手間が増えるusecase-advisor
6ユースケースを1つずつクラスやフォルダに対応づけないユースケースを足すたびに、コードの構造を組み替えることになるusecase-advisor
7同じデータを扱うユースケースの集まりを、文脈の線で割らない同じデータを扱う処理が2つの文脈に分かれ、一貫性が壊れるddd-advisor
81つの文脈に、競合するモデルを入れない1つの文脈の中で言葉の意味が割れるddd-advisor
9文脈どうしは連係方法を明示して選ぶ。中核を含む下流は従属しないつなぎ方が暗黙になり、上流の変更で中核が壊れるddd-advisor
101つの文脈は1つのチームだけが持つ（AI の子のセッションに当てはめるかは推測）1つの文脈を複数で直し、変更がぶつかるddd-advisor
111つの集約を2つの文脈に分けない1つの集約の不変条件を2か所で守ることになり、破れるddd-advisor
12集約の状態は、集約の中の業務ロジックだけが変える。外には参照だけ外から状態が変えられ、不変条件が守れないddd-advisor
131つのトランザクションで変える集約は1つ1回の変更で複数の集約を書き、一部だけ失敗したときに整合が崩れるddd-advisor

単位はユーザー目的。validate は入口のコマンドで、ユースケースではない。

文脈

この基盤は型1（広い1つの文脈）。言葉が分かれたら切り出す。

型ごとのディレクトリ
型選ぶときディレクトリ
型1　広い1つの文脈理解が浅い ・ 変更が多い ・ 小さいチーム ・ 言葉を共有しているrepo ＝ 文脈。中を業務領域の論理的な境界で分ける
型2　1対1業務領域ごとに言葉や変わる速さが違う ・ チームが分かれているcontexts/<業務領域>/ がそれぞれ六角形と外へ出す言葉を持つ
型3　まとめて分ける言葉を共有する業務領域とそうでないものがはっきりしているcontexts/<束ねた文脈>/ の中に業務領域
型4　1つの業務領域を複数の文脈で扱う課題ごとにモデルが違うとき。割らないのは、同じデータのユースケースの集まりと集約同じ業務領域が、モデルごとに別の文脈に入る

ディレクトリ

業務領域が上、その下に domain と application。モジュラーモノリスと同じ形。

置き方の決まり
  • core/<業務領域>/ の下に domain（概念）と application（use_cases ・ ports）の2つの crate。1つにすると業務領域どうしの依存が循環する
  • ポートは、その会話を受け持つ業務領域の application に置く。共有の置き場は作らない
  • ユースケースは1つにつき1ファイルにしない（境界6）。目的レベルでフォルダを分けない（境界3）
  • 外側は inbound（入口）と outbound（外の技術）。HTTP の API を足すときは inbound に足す
  • Cargo の勧め（平らに並べる）から外れることと理由は CODING.md に書き、フォルダと crate 名の一致は検査で守る

ファイルの中身と役割は「実装の完成イメージ」のページで見られる。

基盤との対応

いまの基盤にある語と、この土台の概念の対応。

この土台で、次に設計すること

  1. U0〜U28 にレベル欄とスコープ欄を足し、境界に照らして直す
  2. ポートとディレクトリの形を、ACDR で実装へ移す
  3. この概念を基盤がどこまで持つか（語彙 ・ 一緒に配るもの ・ 使う側の宣言）を、直したユースケースから決める
