Semantic Agent Schema ・ 本質の像

抽象モデリング概念

技術に依らない「何を ・ なぜ」のモデル。ユースケースとドメインの言葉の粒度で書く。どう作るかは、具体モデリング概念が持つ。

「根拠」の欄の 本質 W1 は本質（essence.json）の id（W は利用者の言葉、C は概念モデル、E は本質、R は受け取り方、P は設計の進め方）、subdomain のような英字は DDD の判断基準（ddd-advisor の criteria.json）の id。UC2-4 ・ D3 ・ S4 などは、具体モデリング概念と試験がこのページの行を指す id。用語は 4 のユビキタス言語の表の語だけを使う。

本質：JSON Schema と、AI が読む拡張項目

  1. 根幹は JSON Schema。そこに、AI が読むことを前提にした拡張項目（x-prompt ・ x-decided-by ・ x-view）を持つ 本質 W9 ・ W1 ・ W3
  2. AI が引数と JSON ドキュメントを作る。Semantic Agent Schema はそれを機械的に検証し、違反なら、AI が次のアクションを取れる rejected を返す 本質 W3 ・ R2–R5
  3. 意味的な検証は、x-prompt から prompt を作って返すだけ。判定と生成は AI が行い、AI の response は機械的に検証する 本質 W1
  4. 操作の記録に追記する。前回の検証の JSON ドキュメントを残し、次に変更点を求める基準にする 本質 W1 ・ W3 ・ E5
機械的な検証と意味的な検証をするって部分を両方やってるって感じだよね。
それにプラスして意味的な検証をソースコード内でエージェントを呼ぶような部分まで担わせるのではなく、それを実施するための手順を返す。
これがもう本質なんだよね。

1Abstract と Concrete の関係、依存の注入の条件

何かSemantic Agent Schema との関係
AbstractSemantic Agent Schema のメタスキーマ。作法（拡張項目と x-prompt の書き方）を書いたもの。Abstract 自身も x-prompt を持ち、Concrete を作成 ・ 検証するときの rule になる 本質 W4 ・ C1Semantic Agent Schema が持つ。能力はこの作法に基づく
ConcreteAbstract の拡張項目を継承し、用途ごとに拡張したスキーマ 本質 W4 ・ C2依存しない。用途ごとのプロパティや rule を知らない
インスタンスConcrete に従う JSON ドキュメント 本質 C3作法に基づいて扱う
  • 能力：スキーマとインスタンスに対する操作 ・ 描画 ・ 検証 ・ 更新 ・ 作成 本質 W4 ・ C4
  • Concrete も「Abstract に従う JSON ドキュメント」として、インスタンスと同じ作法で作成 ・ 検証する
  • 依存の注入は、Semantic Agent Schema が決めた契約の依存だけを受け入れる。例はデザインシステム：契約（デザインシステムの形とテンプレートの記法）は Semantic Agent Schema が決め、内容は使う側が渡す 本質 W4 ・ C6

2責務の範囲と、入力 ・ 出力の契約

考え方なぜ根拠
入力と出力の形は JSON Schema で決める形と値を、契約で機械的に検証できる本質 W3 ・ R1
入力を作るのは AIどの JSON ドキュメント ・ スキーマ ・ 範囲かは AI が決める。中で探すより、探すものを渡すほうが軽い本質 W3 ・ R2
中で引くのは、入力から機械的に導けるものだけ自分の操作の記録 ・ Git の事実 ・ 渡された schemas の中の $id なら、同じ入力から同じ結果になる本質 W3 ・ R4
入力の曖昧さを補わない足りなければ、rejected で AI に次のアクションを示す本質 W3 ・ R5
出力はすべてログイベントで、読むのは AIAI がログイベントを読んで次のアクションを取れる本質 W5 ・ W1 ・ R2

5機械的な検証と意味的な検証

検証何で担保するか根拠
機械的な検証JSON Schema：入力 ・ 出力 ・ JSON ドキュメントの形と値。既存の JSON Schema の実装で検証し、format も違反として検証する。
ドメインモデル：JSON Schema で書けない不変条件と、拡張項目のバリデーター ・ レンダラー		本質 W1 ・ W8 ・ W10 ・ E1
意味的な検証ドメインモデル：変更点に適用される rule を集め、生成 ・ 判定の prompt を作って返す。
AI：prompt に従って判定 ・ 生成する。結果の response は機械的に検証する		本質 W1 ・ E2
  • ドメインモデルは、機械的な検証と意味的な検証の両方にある
  • JSON Schema で書けるものは JSON Schema に寄せる。ドメインモデルは、JSON Schema で書けない不変条件だけを持つ
  • ファイルの読み書き ・ 操作の記録への追記 ・ 描画は検証ではない。処理（アダプター）として分ける

6ユースケース

作成 ・ 更新 ・ 意味的な検証 ・ 検索は、どれもこの往復で進む。

設計スコープは Semantic Agent Schema。主アクターの AI は、利用者の代理で動く。各アクションステップの担保は、機械的（JSON Schema） ・ 機械的（ドメインモデル） ・ 意味的（ドメインモデル） ・ 意味的（AI） ・ 処理 のどれか1つ。拡張はどれも、rejected で AI に指示と next を返して終わる。

UC2 更新 中核

目的
JSON ドキュメント（インスタンスか Concrete）を JSON Patch で書き換える
利害関係者
同じ JSON ドキュメントを更新するほかの AI：コマンドが読んでから書くまでの変更を上書きされず、ほかの位置への変更は残る ／ 利用者：x-decided-by: human の値を AI に変えられない ／ Concrete を書く人：Concrete を更新しても、範囲のインスタンスが違反しない
成功時保証
書いた JSON ドキュメントは Concrete と不変条件を満たす。change が操作の記録に残る。Concrete を更新したときは、範囲のインスタンスもすべて新しい Concrete を満たした
最低保証
コマンドが読んでから書くまでに変わった JSON ドキュメントを上書きしない。rejected のときは、ファイルも操作の記録も変えない。不完全なファイルを残さない
主成功シナリオ
1AI が、path ・ schemas を渡し、更新の prompt を依頼する機械的（JSON Schema）：引数
2x-prompt から更新の prompt を作って返す意味的（ドメインモデル）：S2 ・ S3

8変更点の求め方

  • 基準は、直前の意味的な検証（judged）で残した JSON ドキュメント。機械的な検証（validated）では基準を動かさない。比べるのは、その JSON ドキュメントと、いまの内容の2つだけ。JSON Pointer ごとに値を比べ、違う instance location を変更点とする
  • Concrete のハッシュが前回と違うとき、または前回の検証が無いときは、すべての instance location を対象にする
  • 変更点を instance location か related_fields に含む rule だけを prompt に入れる。ほかの AI の judgment は、前回の検証から引き継いで残す
  • Semantic Agent Schema を通さずに変わった JSON ドキュメントも変更点に出るだけなので、取り込みの仕組みは持たない

根拠：本質 W1 ・ E5–E6 ・ R4

9rejected の考え方

出力はすべてログイベントで、読むのは AI。rejected は、AI が次のアクションを取れるように、次の6つを持つ 本質 W5 ・ W1 ・ R2 ・ R5。

持つもの何か出どころ
codeどのルールに違反したかを示す決まった名前rejected の種類ごとに決める
instance location違反したインスタンスの中の位置JSON Schema の実装の出力か、不変条件
absolute keyword location違反したキーワードの位置JSON Schema の実装の出力
message違反の内容の文JSON Schema の実装の出力か、不変条件
指示AI への直し方の文code ごとの定型文に、instance location と値を入れる
next次に実行するコマンド行。AI が埋める部分だけを <…> で空けておく受け取った引数を引き継ぐ

JSON Schema の違反は、JSON Schema の実装の出力をこの形に変換するだけで、独自の判定を足さない。JSON として読めない入力も、rejected で返す。violated の judgment がある検証の結果は rejected ではないが、同じく指示と next を持つ。
