Semantic Agent Schema ・ 本質の像

抽象モデリング概念

技術に依らない「何を ・ なぜ」のモデル。作り方の技術は、具体モデリング概念が持つ。

本質：機械的な検証と、x-prompt による意味的な検証

層何で担保するか
機械的な検証JSON Schema による決定論的な検証と、x- の項目に対する独自のバリデーター ・ レンダラー（ドメインモデルに持つ）
意味的な検証中でエージェントを呼ばず、手順を返す。手順は Markdown ではなく、スキーマとして定義した x-prompt から決まった形で生成する
機械的な検証と意味的な検証をするって部分を両方やってるって感じだよね。
それにプラスして意味的な検証をソースコード内でエージェントを呼ぶような部分まで担わせるのではなく、それを実施するための手順を返す。
これがもう本質なんだよね。

1概念モデル：Abstract ・ Concrete ・ インスタンス

何かSemantic Agent Schema との関係
Abstract スキーマ中核のスキーマ。Semantic Agent Schema のメタで、作法（x- の項目と x-prompt の書き方）を書いたものSemantic Agent Schema が持つ。能力はこの作法に基づく
Concrete スキーマAbstract の x- の項目などを継承して具体にしたもの。作法に沿って用途ごとに拡張して使う依存しない。用途ごとの項目や決まりを知らない
インスタンスConcrete に従う JSON作法に基づいて扱う
  • 能力：JSON Schema とインスタンスの JSON に対する操作 ・ 描画 ・ 検証 ・ 更新 ・ 作成
  • 依存の注入は、Semantic Agent Schema が決めた契約の依存だけを受け入れる。一例はデザインシステム（契約は Semantic Agent Schema が決め、中身は使う側が渡す）
セマンティックエージェントスキーマはその作法に基づく能力は提供する。
しかしconcrateに関する具体内容までは依存しないです。
しかし依存の注入は受け入れるような形です。ただその条件はあくまでセマンティックエージェントスキーマが決めた契約の依存のみです。

2受け持つ所と、入力の契約

誰が受け持つこと
Semantic Agent Schema入力の形と値を契約で確かめ、決まった手順で処理する。結果 ・ 手順 ・ 断る理由を返す
AI のセッション（外）入力と JSON を作る。どの対象 ・ スキーマ ・ 範囲かを考える。意味を判定する
人（外）承認する。人だけが決める欄を決める

入力の契約

考え方なぜ
入力と出力の形は JSON Schema で決める形と値の正しさを、契約で機械的に確かめられる
入力を作るのは AI何を見るかは AI が考える。中で探すより、探すものを渡すほうが軽い
中で引くのは、入力から決定論的に導けるものだけ自分の操作の記録 ・ 版の管理の事実 ・ 渡された置き場所の中の名前なら、同じ入力から同じ結果になる
足りなければ断る曖昧さを補うと、結果が入力で決まらなくなる
入力と出力の契約ができていれば、あとはそれを受け取って処理するだけですよね。
もちろんdbとかから、探すみたいな話もさ結局コマンドないで決定論的に導かれるものとかならいいんだよね。

3ユースケース

意味の部分がある作る ・ 直す ・ 意味の判定 ・ 探すは、どれもこの往復で進む。

保証の範囲は、渡された入力と記録にあるものまで。緑の枠は意味の部分を持つもの。

作る

目的
Concrete に従う新しいインスタンス（または新しい Concrete）を作る
アクター
AI のセッション ・ 人
主な流れ
対象と依頼を渡す → x-prompt から生成した手順を返す → AI が値を作って渡す → 確かめて書き、項目ごとに記録する
保証
書いた値は、渡された Concrete の形と x- の決まりに合う。意味が合うかは、意味の判定で確かめる

直す

目的
あるインスタンス（または Concrete）を書き換える
アクター
AI のセッション ・ 人
主な流れ
読んだ時のハッシュと差分を渡す → 中身が読んだ時と同じで、形と x- が合うときだけ書く → 項目ごとの前後を記録する。外で変えたものは、理由を付けて取り込む
保証
ほかの変更を上書きしない。人だけが決める欄は、人からの変更だけを受ける。Concrete を直すときは、渡された範囲と記録で、従わなくなるインスタンスが無いかを確かめる。何を見たかを結果に返す。範囲が渡されなければ断る

消す

目的
渡された対象（インスタンスか Concrete）を消す
アクター
AI のセッション ・ 人
主な流れ
対象と理由を渡す → 対象だけを消し、消す前の状態を記録する。参照している所は、AI が「直す」で直す
保証
渡された対象のほかは変えない。Concrete を消すときは、渡された範囲と記録に従うインスタンスが無いことを確かめてから消す。何を見たかを結果に返す。範囲が渡されなければ断る

確かめる

目的
渡された対象が、形と x- の決まりに合うかを知る
アクター
AI のセッション ・ 人
主な流れ
対象を渡す → 機械的に検証し、判定の区分ごとの数を返して記録する。記録に無い変更があれば知らせる
保証
渡された対象について、記録にある操作をもとに決める

意味の判定 確かめるの変形

目的
x-prompt の rule に照らして、意味が合うかを判定する
アクター
AI のセッション
主な流れ
判定の手順を依頼する → 前の判定のあと変わった所と当たる rule だけで手順を返す（判定する所が0件でも、空の手順を返す）→ AI が書いたときとは別の文脈で判定して渡す（0件なら空の判定）→ 突き合わせて記録する
保証
どの所を、どの rule で、誰が判定したかが記録に残る。判定の中身は AI の答えのまま。判定できない答えは「守られている」に数えない

描く

目的
インスタンスを、人が読めるページにする
アクター
人（読み手）・ AI のセッション
主な流れ
インスタンスと、契約に従うデザインシステムを渡す → x-view の種類のテンプレートに値を置いて返す
保証
同じ入力から同じページになる。インスタンスは書き換えない

探す

目的
渡された範囲から、問いへの答えを得る
アクター
AI のセッション ・ 人
主な流れ
範囲と問いを渡す → 構造で絞った結果か、意味で探す手順を返す → AI が答えと出どころを渡す → 出どころが範囲の中にあり、ハッシュが合うかを確かめて返す
保証
範囲の外は探していない、と返す。記録しない

記録を読む

目的
誰が、いつ、何をしたかを知る
アクター
人（レビューする人）・ AI のセッション
主な流れ
絞る条件を渡す → 記録を新しい順に返す
保証
読むだけで、何も変えない。無いものは無いと返す

4ドメインモデル

業務領域と区分

業務領域と区分なぜその区分か
書いて確かめる
中核		本質（x- の決まりと x-prompt による意味的な検証）を担う。モデリングを必要とし、ほかに無い価値になる
記録
補完		変わった所を選ぶ元として必要だが、追記して読むだけで、業務の判断を持たない
描く
補完		値を置いて返すだけ。見た目は注入されたデザインシステムが決める
探す
補完		範囲の中で絞るか、手順を返して出どころを確かめるだけ
版の管理 ・ JSON Schema の検証 ・ テンプレートの処理
一般		どこでも同じ仕組み。作らずに使い、受け取る契約だけを Semantic Agent Schema が決める

集約と不変条件

集約不変条件なぜ
Concrete申告する Abstract の版が、閉じた一覧にある作法に従っていることを、版で確かめる
Concrete公開した欄（x-published）は、同じ版のあいだ変えない同じ版を使う側の前提を壊さない
Concrete作法に従う。x- は閉じた一覧で、JSON Schema で書けない作法は組み込みの検査で確かめる能力は作法に基づくので、作法から外れたものは扱えない
インスタンスid を変えない記録と参照が同じものを指し続ける
インスタンス人だけが決める欄（x-decided-by）は、人からだけ変える承認は人が持つ
インスタンスConcrete の形と x- の決まりに合う機械的な検証を通らない値を書かない
インスタンス中身が読んだ時と同じときだけ書くほかの変更を上書きしない

1回の操作で書く集約は1つ。

値

値何か
ハッシュ中身から決まる値。読んだ時といまの中身が同じかを決める
差分項目（JSON Pointer）ごとの前と後
書く条件の外れ書かずに断った理由（中身が変わっていた ・ 形が合わない ・ 人の欄 など）
判定の区分5つ：守られている ・ 破られている ・ 判定できない ・ 判定に失敗した ・ まだ判定していない。「守られている」に数えるのは、守られているだけ
誰が判定したか機械（形の検査 ・ 組み込みの検査）か、AI（x-prompt の rule）か
誰が打ったかセッション。入力で受け取り、推さない
対象の種類Concrete かインスタンスか

ドメインサービス

サービスすること
x- の項目のバリデーターJSON Schema で書けない作法（$schema と $id が合う ・ rule の id が重ならない ・ 例の related は related_fields の所だけ）と、人の欄 ・ 公開した欄を確かめる
x- の項目のレンダラーx-view の種類に、デザインシステムのテンプレートを当てて値を置く
x-prompt から手順を生成する決まり項目の title ・ description ・ x-prompt（meaning ・ when ・ rules）と当たる rule から、決まった形の手順を生成する。同じ入力なら同じ手順。入れ子の深さで切らず、$ref の先の rule は置かれた所ごとに1回だけ入れる
変わった所を選ぶ決まり前の判定のあとの項目ごとの前後と、判定が読んだ所のハッシュから、判定し直す所を選ぶ。選ばれなかった所は前の判定を引き継ぐ

記録の概念

記録何を残すか担う価値
セッション誰が打ったか。1つのセッションに1つ誰が何をしたかを読む
変更の操作対象 ・ 前後のハッシュ ・ 理由 ・ 通したか外の変更の取り込みか記録に無い変更を見つける
項目ごとの前後JSON Pointer ごとの前の値と後の値価値3：変わった所だけを検証する
検証の操作対象 ・ その時のハッシュ ・ 判定の区分ごとの数いつの中身を確かめたかを残す
項目ごとの判定rule ・ JSON Pointer ・ 区分 ・ 誰が判定したか ・ 理由 ・ 読んだ所のハッシュ価値4：変更点を決定論的に集める

どれも追記だけ。断った操作は記録しない。

5境界：してはならないこと

してはならないことなぜ
どのファイルを見るかを推し量る見るものを決めるのは、入力を作る AI。推し量ると、渡していないもので結果が変わる
入力の曖昧さを補う補うと、同じ入力から同じ結果にならない。足りなければ断る
中でエージェントを呼ぶ意味的な検証は、手順を返して担う。判定は外の AI が行う
Concrete の具体に依存する能力は作法に基づく。受け入れるのは、決めた契約の依存の注入だけ
後方互換のためのコードを残すいまの契約だけを持つ。残すと契約が2つになり、どちらで確かめるかが決まらない
もっとシンプルでいいし、入力の曖昧さをアルゴリズムで強引に実現しようとしなくてもある程度入力を作成するaiに頼ってもいいと思う。
