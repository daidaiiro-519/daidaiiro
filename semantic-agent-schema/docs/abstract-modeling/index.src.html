Semantic Agent Schema ・ 本質の像

抽象モデリング概念

技術に依らない「何を ・ なぜ」のモデル。ユースケースとドメインの言葉の粒度で書く。どう作るかは、具体モデリング概念が持つ。

「根拠」の欄の 本質 W1 は本質（essence.json）の id（W は利用者の言葉、C は概念モデル、E は本質、R は受け取り方、P は設計の進め方）、subdomain のような英字は DDD の判断基準（ddd-advisor の criteria.json）の id。UC2-4 ・ D3 ・ S4 などは、具体モデリング概念と試験がこのページの行を指す id。用語は 4 のユビキタス言語の表の語だけを使う。

本質：JSON Schema と、AI が読む拡張項目

{{essence}}
  1. 根幹は JSON Schema。そこに、AI が読むことを前提にした拡張項目（x-prompt ・ x-decided-by ・ x-view）を持つ 本質 W9 ・ W1 ・ W3
  2. AI が引数と JSON ドキュメントを作る。Semantic Agent Schema はそれを機械的に検証し、違反なら、AI が次のアクションを取れる error を返す 本質 W3 ・ R2–R5
  3. 意味的な検証は、x-prompt から procedure を作って返すだけ。判定と生成は AI が行い、AI の answer は機械的に検証する 本質 W1
  4. 操作の記録に追記する。前回の検証の JSON ドキュメントを残し、次に変更点を求める基準にする 本質 W1 ・ W3 ・ E5
機械的な検証と意味的な検証をするって部分を両方やってるって感じだよね。
それにプラスして意味的な検証をソースコード内でエージェントを呼ぶような部分まで担わせるのではなく、それを実施するための手順を返す。
これがもう本質なんだよね。

1Abstract と Concrete の関係、依存の注入の条件

{{concept}}
何かSemantic Agent Schema との関係
AbstractSemantic Agent Schema のメタスキーマ。作法（拡張項目と x-prompt の書き方）を書いたもの。Abstract 自身も x-prompt を持ち、Concrete を作成 ・ 検証するときの rule になる 本質 W4 ・ C1Semantic Agent Schema が持つ。能力はこの作法に基づく
ConcreteAbstract の拡張項目を継承し、用途ごとに拡張したスキーマ 本質 W4 ・ C2依存しない。用途ごとのプロパティや rule を知らない
インスタンスConcrete に従う JSON ドキュメント 本質 C3作法に基づいて扱う
  • 能力：スキーマとインスタンスに対する操作 ・ 描画 ・ 検証 ・ 更新 ・ 作成 本質 W4 ・ C4
  • Concrete も「Abstract に従う JSON ドキュメント」として、インスタンスと同じ作法で作成 ・ 検証する
  • 依存の注入は、Semantic Agent Schema が決めた契約の依存だけを受け入れる。例はデザインシステム：契約（デザインシステムの形とテンプレートの記法）は Semantic Agent Schema が決め、内容は使う側が渡す 本質 W4 ・ C6

5機械的な検証と意味的な検証

検証何で担保するか根拠
機械的な検証JSON Schema：入力 ・ 出力 ・ JSON ドキュメントの形と値。既存の JSON Schema の実装で検証し、format も違反として検証する。
ドメインモデル：JSON Schema で書けない不変条件と、拡張項目のバリデーター ・ レンダラー		本質 W1 ・ W8 ・ W10 ・ E1
意味的な検証ドメインモデル：変更点に適用される rule を集め、生成 ・ 判定の procedure を作って返す。
AI：procedure に従って判定 ・ 生成する。結果の answer は機械的に検証する		本質 W1 ・ E2
  • ドメインモデルは、機械的な検証と意味的な検証の両方にある
  • JSON Schema で書けるものは JSON Schema に寄せる。ドメインモデルは、JSON Schema で書けない不変条件だけを持つ
  • ファイルの読み書き ・ 操作の記録への追記 ・ 描画は検証ではない。処理（アダプター）として分ける

8変更点の求め方

{{diff}}
  • 比べるのは、前回の検証で残した JSON ドキュメントと、いまの内容の2つだけ。JSON Pointer ごとに値を比べ、違う instance location を変更点とする
  • Concrete のハッシュが前回と違うとき、または前回の検証が無いときは、すべての instance location を対象にする
  • 変更点を instance location か related_fields に含む rule だけを procedure に入れる。ほかの AI の judgment は、前回の検証から引き継いで残す
  • Semantic Agent Schema を通さずに変わった JSON ドキュメントも変更点に出るだけなので、取り込みの仕組みは持たない

根拠：本質 W1 ・ E5–E6 ・ R4

9error の考え方

出力はすべてログイベントで、読むのは AI。error は、AI が次のアクションを取れるように、次の6つを持つ 本質 W5 ・ W1 ・ R2 ・ R5。

持つもの何か出どころ
codeどのルールに違反したかを示す決まった名前error の種類ごとに決める
instance location違反したインスタンスの中の位置JSON Schema の実装の出力か、不変条件
absolute keyword location違反したキーワードの位置JSON Schema の実装の出力
message違反の内容の文JSON Schema の実装の出力か、不変条件
指示AI への直し方の文code ごとの定型文に、instance location と値を入れる
next次に実行するコマンド行。AI が埋める部分だけを <…> で空けておく受け取った引数を引き継ぐ

JSON Schema の違反は、JSON Schema の実装の出力をこの形に変換するだけで、独自の判定を足さない。JSON として読めない入力も、error で返す。violated の judgment がある検証の結果は error ではないが、同じく指示と next を持つ。

10境界：持たないもの

持たないものなぜ根拠
どの JSON ドキュメントを見るかを推し量ること見るものは、入力を作る AI が決める本質 R2 ・ R4
入力の曖昧さをアルゴリズムで補うこと補うと、同じ入力から同じ結果にならない本質 W3 ・ R5
中でエージェントを呼ぶこと意味的な検証は、procedure を返して担う本質 W1 ・ E2
Concrete の具体への依存受け入れるのは、決めた契約の依存の注入だけ本質 W4 ・ C5
操作とセッション（coding agent の会話）の結び付けどの会話の操作かを結び付けるのは、使う側の責務。Semantic Agent Schema が残すのは主アクター（ai か human）だけ本質 W11 ・ P7
変更の履歴をたどる仕組み ・ 外の変更の取り込み前回の検証と比べれば変更点が出る本質 W1 ・ W3
Concrete の中の $ref と、参照先をたどる仕組みConcrete は1つの JSON ドキュメントで閉じる。$ref は Abstract が禁じ、書けば機械的な検証の違反になる本質 W3 ・ R4
テンプレートの中を解析して Concrete と照らすことテンプレートは契約の記法で書き、描画はその処理系に任せる本質 W4
もっとシンプルでいいし、入力の曖昧さをアルゴリズムで強引に実現しようとしなくてもある程度入力を作成するaiに頼ってもいいと思う。
