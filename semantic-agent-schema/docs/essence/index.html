1概念モデル：Abstract と Concrete

何かSemantic Agent Schema との関係
C1Abstract中核のスキーマ。Semantic Agent Schema のメタスキーマであり、作法（拡張項目と x-prompt の書き方）を書いたものSemantic Agent Schema が持つ。能力はこの作法に基づく
C2ConcreteAbstract の拡張項目などを継承して具体にしたスキーマ。作法に沿って用途ごとに拡張して使う依存しない。内容（用途ごとのプロパティや rule）を知らない
C3インスタンスConcrete に従う JSON ドキュメント作法に基づいて扱う
  • C4Semantic Agent Schema は、作法に基づく能力を提供する：スキーマとインスタンスに対する操作 ・ 描画 ・ 検証 ・ 更新 ・ 作成
  • C5Concrete の具体の内容には依存しない
  • C6依存の注入は受け入れる。ただし、Semantic Agent Schema が決めた契約の依存だけである。デザインシステムは、この形をイメージしやすくするための具体の一例である（契約は Semantic Agent Schema が決め、内容は使う側が渡す）

2本質

検証何で担保するか
E1機械的な検証JSON Schema による検証と、拡張項目に対する独自のバリデーター ・ レンダラー（集約 ・ ドメインサービス ・ 値オブジェクトとしてドメインモデルに持つ）
E2意味的な検証ソースコードの中でエージェントを呼ばず、実施する procedure を返す。procedure は Markdown ではなく、スキーマとして定義した x-prompt から決まった形で出す

x-prompt が担う価値

  • E3意味的な推論による生成と、生成した値のレビュー ・ 検証を、同じ x-prompt で担保する
  • E4サブスキーマごとに x-prompt が振られているので、JSON Pointer で instance location と rule を特定できる
  • E5操作の記録が instance location ごとの change を持つので、変更点だけを検証できる
  • E6変更点の収集は、procedure を返すコマンドが機械的に行う。AI はそれを見て動く

3受け取り方

  • R1入力と出力の形は JSON Schema で決める。JSON の引数は、それを検証するスキーマをコマンドで渡す
  • R2入力を作るのは AI である。どの JSON ドキュメント ・ どのスキーマ ・ どの範囲かを、AI が考えて引数にする
  • R3Semantic Agent Schema は、受け取った入力の形と値を機械的に検証し、決まった処理をする
  • R4中で引いてよいのは、入力から機械的に導けるもの（自分の操作の記録 ・ Git の事実 ・ 渡された schemas の中の名前）だけである
  • R5入力の曖昧さをアルゴリズムで補わない。足りなければ error を返す

4設計の進め方

  • P1本質の外側に、アーキテクチャ（ポートとアダプター）を置く。中心は、ユースケースからドメインモデルへのモデリングで、ポートとアダプターの中心として設計する
  • P2本質（機械的な検証 ・ x-prompt による意味的な検証）
  • P3ユースケース（作成 ・ 更新 ・ 検証 ・ 意味的な検証 ・ 承認 ・ 描画 ・ 検索 ・ 操作の記録の参照）
  • P4ドメインモデル（拡張項目のバリデーター ・ レンダラー、x-prompt から procedure を作る決まり、instance location ごとの change の記録）
  • P5ポート（中心が外へ依頼するインターフェース）
  • P6アダプター（CLI ・ 渡された path のファイル ・ 操作の記録の DB ・ Git の事実 ・ JSON Schema の実装 ・ テンプレート）
  • P7外：AI（引数と JSON ドキュメントを作り、意味を判定する）・ 人（承認する）
