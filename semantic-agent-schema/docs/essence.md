## 概念モデル：Abstract と Concrete

| | 何か | Semantic Agent Schema との関係 |
|---|---|---|
| Abstract スキーマ | 中核のスキーマ。Semantic Agent Schema のメタであり、作法（`x-` の項目と `x-prompt` の書き方）を書いたもの | Semantic Agent Schema が持つ。能力はこの作法に基づく |
| Concrete スキーマ | Abstract の `x-` の項目などを継承して具体にしたスキーマ。作法に沿って用途ごとに拡張して使う | 依存しない。中身（用途ごとの項目や決まり）を知らない |
| インスタンス | Concrete に従う JSON | 作法に基づいて扱う |

- Semantic Agent Schema は、作法に基づく能力を提供する：JSON Schema とインスタンスの JSON に対する操作 ・ 描画 ・ 検証 ・ 更新 ・ 作成
- Concrete の具体の内容には依存しない
- 依存の注入は受け入れる。ただし、Semantic Agent Schema が決めた契約の依存だけである。デザインシステムは、この形をイメージしやすくするための具体の一例である（契約は Semantic Agent Schema が決め、中身は使う側が渡す）

## 本質

| 層 | 何で担保するか |
|---|---|
| 機械的な検証 | JSON Schema による決定論的な検証と、`x-` の項目に対する独自のバリデーター ・ レンダラー（集約 ・ ドメインサービス ・ 値オブジェクトとしてドメインに持つ） |
| 意味的な検証 | ソースコードの中でエージェントを呼ばず、実施する手順を返す。手順は Markdown ではなく、スキーマとして定義した `x-prompt` から決まった形で出す |

`x-prompt` が担う価値：

1. 意味的な推論による生成と、生成した値のレビュー ・ 検証を、同じ `x-prompt` で担保する
2. 項目ごとに `x-prompt` が振られているので、JSON Pointer で項目と決まりを特定できる
3. 操作の記録が項目ごとの変更を持つので、変更した所だけを検証できる
4. 変更点の収集は、手順を返すコマンドが決定論的に行う。AI はそれを見て動く

## 受け取り方

- 入力と出力の形は JSON Schema で決める。JSON の引数は、それを検証するスキーマをコマンドで渡す
- 入力を作るのは AI である。どのファイル ・ どのスキーマ ・ どの範囲かを、AI が考えて引数にする
- Semantic Agent Schema は、受け取った入力の形と値の正しさを確かめ、決まった手順で処理する
- 中で引いてよいのは、入力から決定論的に導けるもの（自分の操作の記録 ・ Git の事実 ・ 渡された置き場所の中の名前）だけである
- 入力の曖昧さをアルゴリズムで補わない。足りなければ断る

## 設計の進め方

本質の外側に、アーキテクチャ（ポートとアダプター）を置く。中心は、ユースケースからドメインモデルへのモデリングで、ヘキサゴナルの中心として設計する。

```
本質（機械的な検証 ・ x-prompt による意味的な検証）
  └ ユースケース（作る ・ 直す ・ 確かめる ・ 意味の判定 ・ 描く ・ 探す ・ 記録を読む）
      └ ドメインモデル（x- のバリデーター ・ レンダラー、x-prompt から手順を組む決まり、項目ごとの変更の記録）
          └ ポート（中心が外に頼む約束）
              └ アダプター（CLI ・ 渡された経路のファイル ・ 記録の DB ・ Git の事実 ・ JSON Schema の検証器 ・ テンプレート）
外：AI（引数と JSON を作る、意味を判定する）・ 人（承認する）
```

技術に依らない「何を ・ なぜ」は抽象モデリング概念（`abstract-modeling/index.html`）、どう作るかは具体モデリング概念（`concrete-modeling/index.html`）が持つ。
