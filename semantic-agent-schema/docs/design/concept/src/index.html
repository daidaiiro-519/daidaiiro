SAS の責務と能力

Semantic Agent Schema が何をし、何を記録し、どう使われるかを、ボードとは別に一から整理したもの。版5（2026-10-31）：SAS が立てるセッションの型（単発・引き継がない）・書き方・失敗の扱いを決め、ER 図の sessions と使われ方の場面 e を足した。

決めたこと

10-31 に決めたこと中身版2 から

書くのは SAS だけエージェントはファイルを直接書かず、決めた形の JSON を返す。SAS は機械の検証と指紋の確認を通ったときだけまとめて書き、1つの操作として残す足した

1. SAS とは何か

JSON Schema を Semantic に拡張し、その型で作成・更新・削除・検証・描画・検索する基盤。どんな Concrete を作るかは使う側が決める。

2. 6つの能力と、機械と意味

どの能力も Concrete にもインスタンスにも働く。意味の側（エージェント）があるのは作成・更新・検証・検索。

能力機械で意味で（エージェント）操作として残るか
作成人や道具が値を書くエージェントが x-prompt を指示として読み、値を書く残る（create）
更新人や道具が値を書き換えるエージェントが x-prompt を指示として読み、書き換える残る（update）
削除参照している所の記載も一緒に消す―残る（delete と、参照元の update）
検証JSON Schema の項目と by: machine の ruleby: ai の rule をエージェントが判定する残る（validate と rule ごとの結果）
描画デザインテンプレートとトークンを注入して、その場で描く―残らない（描画したものはコミットしない）
検索構造で絞る意味で探す（中核）残らない（意味で探すために立てたセッションは残る）

3. 内と外

目的の2つの読み置き場所
意味の一部としての目的（rule・欄・Concrete が何のためにあるか、1件の操作の意図）SAS の中：rule.why・reading.when・根の description・operations.intent
進め方としての目的（目的ごとのセッション・親子・承認・コミット）使う側

4. ER 図（手元の DB）

DB はリポジトリごとに1つで、SAS の中だけで使う。使う側に共通のモデルとして使わせず、使う側が受け取るのはセッション ID と、読む CLI の出力だけ。

5. セッションの2種類

呼び出し元のセッション（kind = caller）SAS が立てたセッション（kind = sas）
誰のセッションかいま CLI を実行している AI のエージェントか人SAS が意味の操作のためにエージェントを起動したもの
いつできるかその呼び出し元から初めて CLI が実行されたとき意味の作成・更新・検証・検索を始めたとき
ID の取り方アダプターがツールのセッション ID を取る。取れなければ --session で渡す。人なら SAS が人のセッションを立てるSAS が振る。親は呼び出し元のセッション
持つ操作SAS を通した作成・更新・削除・機械の検証エージェントが行った作成・更新・検証

SAS が立てるセッションの型：単発・引き継がない

意味の作成・更新・検証・検索のどれも、1つの対象への1件の操作ごとに新しくセッションを立て、再開しない。呼び出し元の会話は引き継がない。

理由：インスタンス1件を1つのまとまりとして扱い、1回に変えるのは1件だけにする。こうすると、結果を決めるのは手順のプロンプトとモデルだけになり、失敗した件だけを取り直せる。費用は、手順のプロンプトの決まった前置き（Concrete・rule）を先頭に置けば、前置きのキャッシュが毎回効き、件数に比例するだけで済む（キャッシュが前置きに効くことは、ツールごとに実測で確かめる）。

場面どう扱うか
1つのインスタンスの複数の欄を書く1つのセッション・1つの操作で書く。欄ごとの前後は field_changes に残る
複数のインスタンスを続けて作るインスタンスごとに別のセッションを立てる。順番・中断・やり直しの段取りは使う側が持つ。同時に動かす数には上限を設ける
別のインスタンスを読む必要がある（x-relationship）SAS が参照先の値を手順のプロンプトに入れて渡す。参照先は書き換えない
呼び出し元の会話で決めたことを反映させたい会話は引き継がず、呼び出し元が --intent と --brief で文として渡す。文で渡すので記録に残り、あとで意味で探せる
同じ入力で同じ条件にしたい引き継がないので、条件は手順のプロンプトとモデルだけで決まる。input_hash・prompt_hash・model で同じ条件だったかを確かめる。AI の答えの揺れまでは無くせない
答えの形が誤っている同じセッションの中で形だけ直させる（2回まで）。超えたら invalid_output で閉じ、書かない
時間内に答えないtimeout で閉じ、同じ request_id・次の attempt で新しいセッションを立てる（2回まで、間隔を広げる）。止まったセッションは再開しない
書く前に対象が変わっていた開始時の input_hash といまの指紋が違えば書かずに conflict で閉じる。最新を読んで立て直す

外した案

外した案理由
作成・更新を継続にして、続けて同じセッションで書く前のインスタンスの会話が次の結果に効き、扱う順で結果が変わる。履歴を毎回送るので費用は件数の2乗に比例して増える
呼び出し元の会話を引き継ぐ（fork）なぜその値になったかが記録に残らず、結果が呼び出し元の会話とツールに左右される。決めたことは文で渡せば足りる
1つのセッションで複数のインスタンスをまとめて書く途中で失敗すると一部だけ書かれた状態になり、どこから取り直すかが決まらない
rule 1件ごとにセッションを立てる同じインスタンスの rule は同じ入力を見るので、分けても再現性は上がらず、起動の待ち時間と費用だけが増える
エージェントに対象のファイルを直接書かせる一部だけ書けたファイルが見え、SAS を通らない変更と区別できない

sessions の決まり

  1. kind = sas なら parent は必須で、親の kind は caller。SAS が立てたセッションの下に子を立てない。
  2. kind = caller なら parent・operation・prompt_hash・brief・request_id・attempt は空。
  3. kind = sas の操作は、create・update・validate なら1件、search なら0件。
  4. ended_at が埋まったセッションに操作を足さない（再開しない）。
  5. create・update で ended_as が completed 以外なら操作は0件（書いていない）。validate は判定できた rule の結果を残し、残りは unverified。
  6. validate の操作は before = after = input_hash。
  7. 同じ request_id で操作が残るのは1回だけ（やり直しで二重に記録しない）。

以前の SAS のボード Q11 で決めた、単発・継続 × 引き継ぐ・引き継がないの4つの型、役割ごとの登録、再開か新規かの規則（キャッシュの有効時間・履歴の割合）は、呼び出し元のセッションを持つ使う側（目的のセッション）の決まりへ移した。SAS は判断の材料（開始と終了の時刻・tokens）を CLI で読める形で返すだけにする。

6. 使われ方（5つの場面）

どの場面も、誰が・どのコマンドを実行し・SAS が何を返し・DB に何の行が入るかを順に示す。ID とハッシュは例。

場面 a：AI のエージェントがユースケース U10「入力が変わって効かなくなった判定を取り直す」を作り、意味の検証をする

1
AI のエージェント（codex のセッション cx-7f3a）

ユースケースの Concrete に従って U10 を作る。SAS はアダプターでツールのセッション ID を取り、呼び出し元のセッションとして記録する。

実行するコマンド

  --concrete urn:example:usecase:v1 \
  --intent "U10 を精度4まで書く"

SAS が返すもの

  "session": "s-0007",
  "operation": "o-0031",
  "result": "created",
  "machine": { "verified": 12, "violated": 0 }
}

表行

結果を人に見せ、OK かを決める。by: human の rule は、人がこのセッションの中で判断する。SAS はコミットも承認もしない。

7. 意味の検証の流れ

判定はその時のもの。結果は呼び出し元に返り、OK かはそこで決める。SAS は、どのセッションで何をなぜ判定したかを残すだけで、コミットしない。

8. 使う側とのつなぎ方

使う側の「目的のセッション」の Concrete は、自分の欄（目的・親子・状態・コミット）を持ち、CLI が返した SAS のセッション ID を記録する。SAS の DB は手元にあるので、ID を引けるのは同じリポジトリの手元。

{
  "$schema": "urn:example:purpose-session:v1",
  "id": "ps-2026-10-31-01",
  "purpose": "ユースケースの頁を仕上げる",
  "parent": null,
  "status": "進行中",
  "sas_sessions": [ "s-0007", "s-0008" ],
  "commit": null
}

9. ユースケース

ユースケース機械／意味主アクター
UC0 その型で成果物を作り、検証された状態で使い続ける（要約）―使う側
UC1 作成する機械と意味人・AI のエージェント・オーケストレーター
UC2 更新する（SAS を通らない変更の取り込みを含む）機械と意味同上

#承認してほしい決定決めた形
1SAS が立てるセッションの型4つの操作とも単発・引き継がない。1件の操作ごとに新しく立て、再開しない（5 節）
2書くのは SAS だけエージェントは決めた形の JSON を返し、SAS が機械の検証と指紋の確認を通ったときだけ書く。形の誤りは同じセッションで2回まで直させ、時間切れは新しいセッションで2回までやり直す
3sessions に足す欄request_id・attempt・prompt_hash・brief・tokens。ended_as は completed・timeout・invalid_output・conflict・failed・cancelled
4SAS を通らない変更の見つけ方と取り込み方ファイルのいまの指紋と、最後の操作の事後の指紋を比べる。取り込むときは --adopt と意図を付け、前の値は最後の操作の事後のファイル（Git の該当コミット）から取る
5人のセッションをいつ立て、いつ閉じるか人が CLI を初めて実行したときに立てる。閉じるのは sas session end か、一定の時間 CLI が実行されなかったとき
6呼び出し元のセッション ID の取り方アダプターがツールの持つセッション ID を取る。取れないツールでは --session で渡す。どちらも無ければ人のセッションとして扱う
