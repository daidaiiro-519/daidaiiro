Semantic Agent Schema の概念

Semantic Agent Schema が何をし、何を記録し、どう使われるか。要求を書く（全体像〜ユースケース）→ 見つける（事業領域と文脈）→ 設計する（ドメインモデル〜スキーマと DB）の順に並べた。

全体像

JSON Schema を Semantic に拡張し、その型で作成・更新・削除・検証・描画・検索する基盤。どんな Concrete を作るかは使う側が決める。

SAS は能力・記録（動いているセッションを回すため）・公開する形と、一般の能力のポートと受け取りの型まで。製品は作らずに渡す。目的ごとに進める営みは使う側。

SAS の中能力6つ・記録・公開する形・意味としての目的・一般の能力のポートと受け取りの型
使う側目的のセッション・承認・まとめ・コミット・PR
一般の製品Git・バリデーター・テンプレートの処理系はアダプターとして渡す。コーディングエージェントは semantic-agent-schema を打つ側で、SAS は起動しない

目的の読み置き場所
意味の一部（rule・欄・Concrete が何のためにあるか、1件の操作の意図）SAS の中：rule.why・x-prompt の when・根の description・changes.reason
進め方（目的ごとのセッション・親子・承認・コミット）使う側

事業領域と文脈

事業領域（AI のエージェントが扱う構造化データを、スキーマに従って書き、検証すること）を分解して業務領域を見つけ、SAS 自身の4つを、意味の境界の内側の広い1つの文脈「スキーマとインスタンス」に置く。一般の4つと使う側は外の文脈。

業務領域は見つけるもの、文脈は設計するもの。区分は仮で、確かめるときに実装の方法から逆に判定する。

中核を含む文脈「スキーマとインスタンス」は、ツールにはセッション ID の環境変数（callers.json）だけで従属し、エージェントを起動しない。Git と JSON Schema にも従属する。使う側へは共用サービスとして、公開された言葉（Abstract と CLI の出力）だけを出す。

ドメインモデル

集約は2つ。Concrete・インスタンスで、書くのモジュール（writing/domain）に置く。検証のモジュールは集約を読んで rule に照らす。上から決め、下から確かめて同じ形になったものだけを domain に置く。

writing-domain は何にも依存しない。validation-domain は集約を読む。意味（x-prompt の rule・x-prompt の欄を書く）は検証・書くの中にあり、業務領域にしない。記録・描画・検索はドメインモデルを持たない（業務ロジックは use_cases のトランザクションスクリプト）。点線の箱は use_cases に残すもの。

ファイルの中身は Git。記録は集約にせず、追記する行のまま。

確かめる

上から決めた構成を、ユースケースの手続きから下から確かめた（版14 の記録）。業務領域ごとの実装の方法と3つの集約は一致し、構成は妥当。食い違い6件は上からの設計を直した。いまの集約は2つ（Concrete・インスタンス）。

言語に依存しない決まり
  • リポジトリの根は製品 Semantic Agent Schema の置き場で、文脈の根にしない。文脈の根は、文脈の名前のフォルダ（リポジトリの根の直下。ここでは schemas-and-instances/）。その中は業務領域を作るモジュール（writing・validation・recording・rendering・search）と adapters で、文脈の根に domain を置かない。名前はその文脈の言葉（スキーマ・インスタンス・書く・検証・記録）から付け、製品の名前を使わない。文脈の中はポートとアダプターで作り、外とのやりとりはすべて application の ports を adapters が実装する（呼び出し元を決めるポートは inbound/cli、ほかは outbound）。本ではポートは業務ロジック層が定義するが、記録と描画はドメインモデルを持たないので application に置く
  • 業務ロジックの置き方は、上から決めて下から確かめる。守る条件がすでに決定・Abstract の rule・試験の場面に書けている所は初めから domain に置き、それ以外は use_cases にトランザクションスクリプトで書く。引き上げの表で判別し、突き合わせで確かめたものだけを domain に置く
  • domain の中は部品の種類でフォルダを分ける：aggregates/（集約ごと）・values/・services/。購読する手続きが無いうちは events/ を作らない
  • application の中は use_cases/ と ports/。use_cases/ のファイルは集約か手順のまとまりごとに分け、ユースケースごとのファイルやフォルダは作らない（土台の境界6）
  • domain を持つのは、突き合わせで集約・値・サービスが確かめられたモジュールだけ（いまは書く・検証）。集約は書くのモジュール、検証のモジュールは集約を読んで rule に照らすサービスと判定の値を持つ。記録・描画・検索は application だけ
  • ポートは、それを使うユースケースを持つモジュールが、自分の application/ports に、使うメソッドだけで宣言する。共有の置き場を作らない。同じ形のポート（document_store ・ schema_validator）もモジュールごとに宣言し、1つのアダプターがそれらを実装する。記録のポートも追記するモジュールが宣言する（書く change_log、検証と描画 validation_log。検索は持たない）
  • モジュールの application は、ほかのモジュールの application（ポートもユースケースも）に依存しない。依存してよいのは domain の crate だけ（validation-domain → writing-domain の一方向）。複数のモジュールが使う判断と値は domain に置く
  • 誰が打ったか（Caller）は入口が決めて sessions に登録し、値でユースケースへ渡す。決める手続きは記録のモジュールに置き、入口だけが呼ぶ
  • 断る理由の型（Refused）は各モジュールが持つ。出力の形（kind = error）は inbound/cli が持ち、各モジュールの Refused を移す
  • 外のライブラリ（rusqlite・2020-12 のバリデーター・テンプレートの処理系）は、それを使う outbound の crate だけが依存する
  • コンポジションルート（アダプターをポートへ渡す）は入口の1か所だけ
  • 公開された言葉（Abstract の本体・語彙・方言と CLI の入出力・手順と答えの形）は文脈の根の published-language/<版>/ に置き、出した版は変えない
Rust の決まり（一次情報の頁と行）
  • 依存の向きを強制したい境界と、外のライブラリを閉じ込めたい所だけを crate にし、それ以外はモジュールで分ける。crate の数の基準は原典に無い（Book ch07-01:186・ch14-03:187（基準の記述が無い）・ch07-03:296・Reference visibility:476）
  • domain はモジュールごとに crate を分ける（いまは writing-domain と validation-domain。検証が集約を読む向きを crate で強制する）。1つの crate の中では子モジュールが祖先の項目を使えるので、集約の間の向きはモジュールでは止められない（Book ch07-03:296・ch14-03:299）
  • 根の Cargo.toml は virtual manifest。[workspace] に members と resolver = "3" を書く（Cargo workspaces:241・258、Book ch14-03:207〜211）
  • 外のライブラリの版は [workspace.dependencies] に置き、各 crate は workspace = true で継承する（optional にはできない）。SAS の中の crate どうしは path dependencies（Cargo workspaces:359・363、specifying-dependencies:425）
  • crate が使えるのは自分の Cargo.toml に書いた crate だけ。これで domain の無依存と、ライブラリの閉じ込めを強制する（Book ch14-03:299・390）
  • domain の lib.rs は pub mod aggregates; pub mod values; pub mod services;（集約の無い validation-domain は values と services だけ。events は作らない）。crate の中だけで使う部品は pub(crate)（Book ch07-02:273、Reference visibility:390・476）
  • mod.rs を使わない。src/aggregates.rs と src/aggregates/concrete.rs・instance.rs の形にする（Book ch07-05:251・265・268）
  • adapters は、実装するポートの application と、ポートで受け渡す型を持つ domain の crate に依存する（outbound/sqlite は記録の行の型のため writing-domain ・ validation-domain にも）。application は domain の型を再公開しない
  • コンポジションルートは cli の main.rs。outbound の crate に依存してよいのは cli だけ（Book ch14-03:299（推論：実装の型の名前を書くので依存が必要））
  • ポートは trait で、どれも dyn で使う。dyn compatible に保つ：型引数のあるメソッド・async fn・関連定数を持たず、Self を receiver 以外で使わない。sealed にしない（Reference traits:412・429・445・459、API Guidelines C-OBJECT:322・324・321、C-SEALED:169）
  • 集約の欄は private、メソッドだけ pub。ID・ハッシュは newtype で区別する（Book ch07-03:477、API Guidelines C-STRUCT-PRIVATE:218・C-NEWTYPE:169）
  • adapters で外の trait（rusqlite・serde など）を domain の型に実装しない（orphan rule）。sqlite の crate は自分の行の型を持って変換する（Book ch10-02:302・309・313、Reference implementations:658・659・669）
  • 依存のグラフは循環させない（Cargo resolver:568・585）

自分の $id を持つリソースにするか、$defs の部品にするか

問いはいいいえ
1. その形を1つの文書として名指しする相手がいるか（$schema で示す ・ 別の文書の欄から URN で指す ・ 外のツールへ文書で渡す）2へ使うリソースの $defs に置く。複数で使うなら意味の持ち主の $defs に置き、ほかは $id#/$defs/名前 で指す
2. すでにあるリソースと、読み手も変わる理由も同じか同じリソースに置く自分の $id を持つリソース（ファイル）にする

ファイルは運ぶ単位で、線はリソース（$id）にある（JSON Schema 2020-12 Core 8.2.4 ・ 9.3）。手順（procedure）は打ったセッションが行う指示で、結果を返す command-result と役目が違うので別のリソース。Concrete を書く人への作法は Abstract の rule：one-document-kind（1つの Concrete に1種類の文書）・ no-shape-only-concrete（properties に $schema のほかの欄を1つ以上持たせる）・ shape-in-defs（インスタンスの根にならない形は $defs）・ ref-not-copy（ほかの Concrete の形は写さず $ref）。

JSON で表したい・型で制御したい・意味を持たせたい・決まった型で返したい、のどれかに当たる境界だけをスキーマにする。DB の表と版の管理・バリデーター・テンプレートの処理系はプロセスの外へ JSON が出ないのでスキーマにしない。
