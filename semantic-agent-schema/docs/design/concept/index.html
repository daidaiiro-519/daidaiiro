全体像

JSON Schema を Semantic に拡張し、その型で作成・更新・削除・検証・描画・検索する基盤。どんな Concrete を作るかは使う側が決める。

SAS は能力・記録（動いているセッションを回すため）・公開する形と、一般の能力のポートと受け取りの型まで。製品は作らずに渡す。目的ごとに進める営みは使う側。

SAS の中能力6つ・記録・公開する形・意味としての目的・一般の能力のポートと受け取りの型

一般の製品Git・コーディングエージェント・バリデーター・テンプレートの処理系。アダプターとして渡す

目的の読み置き場所
意味の一部（rule・欄・Concrete が何のためにあるか、1件の操作の意図）SAS の中：rule.why・reading.when・根の description・changes.intent
進め方（目的ごとのセッション・親子・承認・コミット）使う側

事業領域と文脈

事業領域（AI のエージェントが扱う構造化データを、スキーマに従って書き、検証すること）を分解して業務領域を見つけ、SAS 自身の4つを、意味の境界の内側の広い1つの文脈「スキーマとインスタンス」に置く。一般の4つと使う側は外の文脈。9519cffa で「セッション」を理由に2つに分けたが、版16 で1つに戻した。

業務領域は見つけるもの、文脈は設計するもの。区分は仮で、確かめるときに実装の方法から逆に判定する。

中核を含む文脈「スキーマとインスタンス」は、変わりやすいツールにモデル変換装置を置き、Git と JSON Schema には従属する。使う側へは共用サービスとして、公開された言葉（Abstract と CLI の出力）だけを出す。

意味の境界ツールのセッションの寿命と再開・Git の「コミット」・使う側の「目的のセッション」は文脈「スキーマとインスタンス」の語と意味が違う
ポートと製品一般の能力は、ポートと受け取りの型を SAS が持ち、製品はアダプターとして渡す

ドメインモデル

集約は2つ。Concrete・インスタンスで、書くのモジュール（writing/domain）に置く。検証のモジュールは集約を読んで rule に照らす。SAS が立てたセッションの集約は版16 でやめた（子の状態を持たない）。上から決め、下から確かめて同じ形になったものだけを domain に置く。

writing-domain は何にも依存しない。validation-domain は集約を読む。意味（by: ai の rule・x-prompt の欄を書く）は検証・書くの中にあり、業務領域にしない。記録と描画はドメインモデルを持たない（業務ロジックは use_cases のトランザクションスクリプト）。点線の箱は use_cases に残すもの。

ファイルの中身は Git。記録は集約にせず、追記する行のまま。

確かめる

上から決めた構成を、ユースケースの手続きから下から確かめた（版14 の記録）。業務領域ごとの実装の方法と3つの集約は一致し、構成は妥当。食い違い6件は上からの設計を直した。版16 で SAS が立てたセッションの集約はやめたので、いまの集約は2つ。

段階3でユースケースの手続きをそのまま書き、段階4で何になるかを判別する。似たものも、同じ意味・同じ理由で変わると確かめるまで引き上げない。

Rust の決まり（一次情報の頁と行）
  • 依存の向きを強制したい境界と、外のライブラリを閉じ込めたい所だけを crate にし、それ以外はモジュールで分ける。crate の数の基準は原典に無い（Book ch07-01:186・ch14-03:187（基準の記述が無い）・ch07-03:296・Reference visibility:476）
  • domain はモジュールごとに crate を分ける（いまは writing-domain と validation-domain。検証が集約を読む向きを crate で強制する）。1つの crate の中では子のモジュールが祖先の項目を使えるので、集約の間の向きはモジュールでは止められない（Book ch07-03:296・ch14-03:299）
  • 根の Cargo.toml は virtual manifest。[workspace] に members と resolver = "3" を書く（Cargo workspaces:241・258、Book ch14-03:207〜211）
  • 外のライブラリの版は [workspace.dependencies] に置き、各 crate は workspace = true で継承する（optional にはできない）。SAS の中の crate どうしは path dependencies（Cargo workspaces:359・363、specifying-dependencies:425）
  • crate が使えるのは自分の Cargo.toml に書いた crate だけ。これで domain の無依存と、ライブラリの閉じ込めを強制する（Book ch14-03:299・390）
  • domain の lib.rs は pub mod aggregates; pub mod values; pub mod services;（集約の無い validation-domain は values と services だけ。events は作らない）。crate の中だけで使う部品は pub(crate)（Book ch07-02:273、Reference visibility:390・476）
  • mod.rs を使わない。src/aggregates.rs と src/aggregates/concrete.rs・instance.rs の形にする（Book ch07-05:251・265・268）
  • application の ports.rs が、ポートで使う domain の型を pub use で再公開する。adapters は application だけに依存する（Book ch07-04:392、Reference visibility:564）
  • コンポジションルートは cli の main.rs。outbound の crate に依存してよいのは cli だけ（Book ch14-03:299（推論：実装の型の名前を書くので依存が必要））
  • ポートは trait で、8つとも dyn で使う。dyn compatible に保つ：型引数のあるメソッド・async fn・関連定数を持たず、Self を receiver 以外で使わない。sealed にしない（Reference traits:412・429・445・459、API Guidelines C-OBJECT:322・324・321、C-SEALED:169）
  • 集約の欄は private、メソッドだけ pub。ID・指紋は newtype で区別する（Book ch07-03:477、API Guidelines C-STRUCT-PRIVATE:218・C-NEWTYPE:169）
  • adapters で外の trait（rusqlite・serde など）を domain の型に実装しない（orphan rule）。sqlite の crate は自分の行の型を持って変換する（Book ch10-02:302・309・313、Reference implementations:658・659・669）
  • 依存のグラフは循環させない（Cargo resolver:568・585）
