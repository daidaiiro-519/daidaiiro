Semantic Agent Schema ・ 本質の像

具体モデリング概念

抽象モデリング概念を Go でどう作るか。ファイル ・ 型 ・ 列 ・ 引数の粒度で書く。何を ・ なぜは抽象モデリング概念が持ち、ここでは繰り返さない。

UC2-4 ・ D3 ・ S4 などは抽象モデリング概念の行の id。対象の OS は Linux と macOS。原文の行は、取得した原文のファイルの行番号。

2ポートとアダプター

ポートは、使う側の application が ports.go に、自分のユースケースが使うメソッドだけで宣言する。外部（ファイル ・ 操作の記録 ・ ライブラリ）の分だけ作り、試験の代役のためには作らない。

ポート宣言する package とメソッドアダプター
Documentsauthoring：Read ・ Write（一時ファイルに書いて置き換える）／ rendering ・ search：Read（search の application のポートは読むだけ。値の比べ方はドメインサービス「検索の比較」S6）files
Schemasauthoring ・ rendering：Lookup（$id で Concrete を引き、domain へ渡す。Concrete は $ref を持たないので、引くのは1つだけ。S2）files

Patcherauthoring：Apply（JSON Patch を適用する。適用できなければ、その operation の path を返す）patching
Recordsauthoring：WithLock ・ AppendChange（作成と更新の両方。command と before_hash を記録する）・ AppendValidation ・ LastJudged（直前の意味的な検証 judged の JSON ドキュメントと judgment。S4。validated では基準を動かさない）／ record：Operations（新しい順の一覧）・ Operation（1件）recordstore。読むだけのときは読み取り専用で開き、ファイルが無ければ作らずに空として扱う
Rendererrendering：References（テンプレートの .Value… ・ .Tokens… と、<script> の中の JS の参照を集める）・ Render（受け取る Page は authoring/domain に置く。全部描けてから書き出す）templates

working tree と Git の共通ディレクトリは、入口が repository で一度だけ引き、各アダプターに渡す。application は Git を知らない。

4コマンドと引数

引数は pflag で読み、JSON にして arguments.schema.json で検証する（UC1-1 など）。違反は arguments_invalid の rejected になる。

コマンドは2つの層に分ける。semantic <ユースケース> は意味的な操作で、prompt を返し、AI が作る ・ 判定する。<ユースケース>（semantic なし）は機械的な操作で、AI が作ったものを受け取り、機械的に検証して書く ・ 記録する。意味的な操作の next は、同じユースケースの機械的なコマンド。

ユースケース意味的な操作（prompt を返す）機械的な操作（受け取って検証する）
UC1 作成semantic create <path> --schemas … --schema <$id> → generation_requestedcreate <path> --schemas … --json <JSON | -> → created
UC2 更新semantic update <path> --schemas …（Concrete なら --range <path>）→ update_requestedupdate <path> --schemas … --patch <JSON | ->（Concrete なら --range <path>。値なしの --range で「従うインスタンスは無い」と明示できる）→ updated
UC3 検証 ・ UC4 意味的な検証semantic validate <path> --schemas … [--all] → judgment_requested（判定する組が0なら validated。instruction が、意味的な検証を必要としないことを示し、next は付けない）。--all は、変更点だけでなく、すべての rule とすべての instance location を判定するvalidate <path>... --schemas … → validated ／ validate <path> --schemas … --judgments <JSON | -> → judged
UC7 検索semantic search <path>... --question <問い> → search_requestedsearch <path>... --where <JSON Pointer>=<JSON>（繰り返せる。最初の = で分ける）→ found ／ search <path>... --matches <JSON | ->（範囲を確かめるため path も渡す。next が引き継ぐ）→ found。検索は --schemas を取らない
UC6 描画—render <path>... --schemas … --design-system <path> --out <ディレクトリ> → rendered（インスタンス1つにつき1つ。path と out を持つ）。書き出すファイルは <--out>/<元の path から .json を除いたもの>.html。全部を描いてから一時ファイルに書いて置き換え、描けないものが1つでもあれば何も書き出さない
UC8 操作の記録の参照—log [<path>...] [--limit <1以上>]（--limit が無ければ全部）、または log --operation <create|update|validate>:<id>（path ・ --limit とは一緒に渡せない）→ listed。--schemas は取らない

--help（semantic-agent-schema --help、コマンドごとに <command> --help ・ semantic <command> --help）で、コマンドと引数の一覧を返す。説明は arguments.schema.json の description から作る。出力はログイベント help で、commands（command ・ description ・ arguments（name ・ description ・ required））を持つ。--help ・ -h で全部、<command> --help ・ semantic <command> --help でそのコマンドだけ。

値を2つ以上渡す引数（--schemas ・ --range ・ --where）は繰り返す。- は標準入力から読む。終了コードは、rejected か violated の judgment があれば 1、ほかは 0。

  • 人かどうかの確かめと、セッションとの結び付けは使う側の責務。Semantic Agent Schema は、実行したのが人か AI かを受け取らない ・ 残さない

next への引き継ぎ

created と updated の next は semantic validate <path> --schemas …（意味的な検証の依頼）。prompt の next は同じユースケースの機械的なコマンド。prompt と rejected の next には、受け取った --schemas ・ --range ・ --schema を入れる。AI は <…> の部分だけを埋めて実行する。

種類ファイル役目
Concrete を書く型abstract.schema.json ・ vocabulary.schema.json ・ dialect.schema.json拡張項目の形と閉じた一覧。x-view はルートだけ（入れ子では false）と、Concrete に $ref を書かないことも、ここで JSON Schema にする。Concrete に書いてよい format の名前は CODING.md が持つ。rule の related_fields は、インスタンスのルートからの絶対の JSON Pointer で書く。x-prompt は、値を書く所（ルート ・ properties ・ patternProperties ・ additionalProperties ・ unevaluatedProperties ・ items ・ prefixItems ・ unevaluatedItems のサブスキーマ）と、分岐の枝（oneOf ・ anyOf の各枝 ・ then ・ else ・ dependentSchemas の枝）に必ず書く。const か要素1つの enum だけで値が決まる所は省ける。if ・ allOf の枝 ・ not ・ contains ・ propertyNames には書かなくてよい。値を書く所のサブスキーマは true にせずオブジェクトにし、type が object なら additionalProperties か unevaluatedProperties、array なら items ・ prefixItems ・ unevaluatedItems のどれかを書く（分岐の中でキーを定義するときは、additionalProperties: false がそのキーを弾くので unevaluatedProperties: false を使う）。これらは abstract.schema.json の $defs/writing ・ valueSchema ・ branchSchema ・ shape で JSON Schema にし、ドメインのコードで同じことを確かめない。$defs は Concrete に書かせない（$ref を禁じているので使われない）
引数arguments.schema.jsonコマンドごとの引数の JSON の形。必須 ・ 組み合わせ ・ path とハッシュの pattern。各引数の description は --help の説明になる
出力event.schema.jsonログイベントの1行。event の名前は、ユースケースで起きたことの過去形（下の表）
promptprompt.schema.jsonsemantic <ユースケース> が返す prompt。*_requested のログイベント。JSON ドキュメントの内容は貼らず、path で渡す。path ・ hash（判定のとき、内容のハッシュ。judgments の JSON に写す）・ instruction（判定と更新のとき。path のファイルを読み、判定では step ごとに判定し、更新では violations の reason に従って step の位置を直す手順）・ steps ・ subschemas ・ violations ・ response ・ next。検索は question と documents（path とハッシュだけ）。
steps：作成は、サブスキーマごとの keywordLocation ・ title ・ description ・ x-prompt。更新は instanceLocation と keywordLocation だけで、violations があれば、その instance location ごとの step にする（keywordLocation は、その位置か、たどれる一番深い親のサブスキーマ）。判定はそれに rule の id（rule）を足したものだけ。どれも配列の要素までたどる。
subschemas：更新と判定で、steps の keywordLocation が指すサブスキーマ。x-prompt は、ここに keyword location ごとに1回だけ、スキーマに書いた順のまま置く。

response：$id ではなく、JSON Schema の中身（作成は Concrete、更新は JSON Patch のスキーマ、判定は judgment-response、検索は search-response）。
next：同じユースケースの機械的なコマンド。Concrete の更新では --range を引き継ぐ。

受け取りの型design-system.schema.json ・ template-language.json ・ design-tokens.schema.jsondesign-system.schema.json は、templateLanguage（template-language.json を参照）・ templates（x-view の名前から、テンプレートのファイルへの path。デザインシステムのファイルからの相対で、working tree の中だけ）・ tokens（design-tokens.schema.json を参照）を持ち、どれも必須。design-tokens.schema.json は、W3C Design Tokens Community Group の Design Tokens Format Module 2025.10 と Color Module 2025.10 に従う。扱う型は color（colorSpace ・ components ・ alpha ・ hex）・ dimension（px ・ rem）・ fontFamily ・ fontWeight ・ duration（ms ・ s）・ cubicBezier ・ number。合成の型（shadow など）・ $ref ・ $extends は扱わず、JSON Schema で拒む。render は translation tool の役を担い、別名を解いた値の各トークンに、型から作る CSS の文字列 css を足して .Tokens で渡す（dimension は 10px、duration は 200ms、color は hex か CSS Color 4 の関数、fontFamily は引用符と , でつないだもの、cubicBezier は cubic-bezier(…)、fontWeight と number は数）。テンプレートは .Tokens.space.radius.css のように読む。.Tokens の各トークンは、どれも css を持つオブジェクト。color ・ dimension ・ duration は値のオブジェクトに css を足し、number ・ fontWeight ・ fontFamily ・ cubicBezier は {"value": 値, "css": …} にする。alpha が 1 でない色は、hex があっても CSS Color 4 の関数にする。根拠は Design Tokens Format Module 2025.10 の 3.6 Type「A translation tool might reference a token's type to convert the source value into the correct platform-specific format.」（原文 L501）。template-language.json は {"name":"html/template","version":"go1.27"} を const で宣言する JSON Schema。テンプレートに渡すのは .Value（インスタンス）と .Tokens（デザイントークン）だけ。JS はテンプレートの中にだけ書き、JS への入口は <script> の中の {{.Value}} ・ {{.Tokens}} だけ（html/template が JS として安全な JSON にして埋め込む）
エラーの定型error-codes.jsoncode ごとの instruction の定型文と、コマンドごとの next の定型（意味的な操作と機械的な操作で分ける）。prompt の instruction（semantic validate と semantic update）と next の定型（semantic update を含む）も持つ。引数の JSON（--json ・ --patch ・ --judgments ・ --matches）の違反には、argumentInstruction（渡した引数の JSON の位置を直すよう示す。{argument} はその引数の名前）を使う。定型に埋める項目は {schemaId} ・ {range} ・ {limit} ・ {operation} ・ {designSystem} ・ {out} ・ {line} などで書く。instance location は "{instanceLocation}" と引用符で囲む（ルートは "" と出る）。violated の judgment がある validated ・ judged の instruction は {violations}（rule の id と instance location の並び）を持ち、機械的な検証の違反の next は Concrete なら {range} で --range を足す。not_judged は、violated が無く not-judged がある validated の instruction と、semantic validate の next。no_judgment_targets は、判定する組が無い semantic validate の validated の instruction

どれでもrejected断った。理由は code

rejected

rejected は、テンプレートの違反のとき line（テンプレートのファイルの行）の欄も持つ。

{"event": "rejected",
 "code": "schema_violation",
 "instanceLocation": "/items/0/price",
 "absoluteKeywordLocation": "urn:example:order:v1#/properties/items/items/properties/price/minimum",
 "message": "0 より小さい",
 "instruction": "\"/items/0/price\" を 0 以上の数にして、もう一度 update を実行する",
 "next": "semantic-agent-schema update order.json --schemas schemas --patch '<JSON Patch>'"}

schema_violation は、schemacheck が ValidationError の葉ごとに InstanceLocation を instanceLocation、キーワードの絶対の位置を absoluteKeywordLocation にして1行ずつ出す。独自の判定は足さない。message は、ライブラリの文に「（description）」を続ける。description は、違反したキーワードを直接持つサブスキーマのものだけで、親のサブスキーマへは上らない。無ければ何も足さない。Abstract のサブスキーマでも Concrete のサブスキーマでも同じで、スキーマの作者の文のまま出す。

violated の judgment があるときの validated

validated のログイベントは rejected ではないが、violated の judgment があるときは instruction と next を付ける。instruction は違反の instance location を直すよう示し、next は update <path> --schemas … --patch '<violated の instance location を直す JSON Patch>'。機械的な検証の違反は位置と理由が分かっているので、AI が JSON Patch で直接直せば1回で済む。AI の judgment の violated（judged）の next は semantic update <path> --schemas …。

6操作の記録

ファイルは <git-common-dir>/semantic-agent-schema/records.sqlite。形は adapters/outbound/recordstore/records.sql が決める。

表列抽象の行
changesid（PK）・ path ・ schema_id ・ command（create ・ update）・ before_hash ・ after_hash ・ atUC1 ・ UC2
field_changeschange_id（FK）・ instance_location ・ op（add ・ remove ・ replace）・ before ・ after。作成では、ルートを含むすべての instance location を add で1行ずつD3
validationsid（PK）・ event（validated ・ judged）・ path ・ schema_id ・ concrete_hash ・ content（検証した JSON ドキュメント）・ content_hash ・ at。変更点の基準は、event が judged の最新の行V1 ・ S4
judgmentsvalidation_id（FK）・ rule_id ・ instance_location ・ by（machine ・ ai）・ verdict（verified ・ violated ・ unverified ・ not-judged）・ reasonV3
ビュー operationschanges と validations を UNION ALL し、at の順に並べる。列は id ・ command ・ path ・ atUC8
  • どの表も追記だけ。UPDATE と DELETE は trigger で拒否する
  • ID は INTEGER の主キー。ビューでは command と組にして指す（--operation <command>:<id>）
  • 書く操作は Records.WithLock の中で行う：BEGIN IMMEDIATE → ハッシュの確認（D2。最初に読んだときのハッシュと同じか）→ 追記 → Documents.Write → COMMIT。書き込みに失敗したら ROLLBACK で追記も取り消すので、rejected のときはファイルも操作の記録も変わらない
  • at は RFC 3339 で、秒の小数を9桁にそろえて書く（文字列の順が時刻の順になる）
  • 表の形の版は user_version の 5。版が違えば開かず、log_unavailable で records.sqlite の削除を示す。前の版との互換は作らない

7処理の流れ

1回の流れ。入力の検証で違反なら rejected、通過すればドメインモデルで検証し、意味的な検証なら prompt を返す。

UC2 の prompt による更新から、UC4 の意味的な検証まで。

エラーのとき：AI は instruction に従い、next を実行する。

9試験と完成の条件

試験の正解は、本質と2枚のページだけ。Rust 版の出力は正解にしない。識別子は変わっていくので、試験とページの行を識別子で対応させることはしない。

決まり内容
試験の名前振る舞いの名前で書く（例：TestUpdateRejectsChangedFileBeforeWrite ・ TestValidateReturnsNextForViolatedJudgment）
期待値実装より先に、ページの振る舞いから書く。出力から写さない。ハッシュは試験の中でバイト列から求める
比べ方出力は JSON Pointer と値の組で比べ、差は cmp.Diff で出す。message の文は比べない。全部の出力を event.schema.json（prompt は prompt.schema.json）で検証する
環境試験ごとに新しい一時ディレクトリで git init し、本物のアダプター（一時ファイルの SQLite）を使う。子プロセスの環境は空から作る
