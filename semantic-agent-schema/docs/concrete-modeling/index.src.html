Semantic Agent Schema ・ 本質の像

具体モデリング概念

抽象モデリング概念（技術に依らない何を ・ なぜ）を、どう作るか。構成 ・ ポート ・ コマンドの引数 ・ 公開された言葉 ・ 記録 ・ 処理の流れ ・ 書き方の決まりの7つで書く。

軸：入力は契約で受け取り、決まった手順で処理する

  • 入力を作るのは AI。どのファイル ・ どのスキーマ ・ どの範囲かを、AI が考えて引数にする
  • Semantic Agent Schema は、入力の形と値を確かめ、決まった手順で処理する
  • 中で引くのは、自分の操作の記録 ・ Git の事実 ・ 渡された置き場所の中の名前だけ
  • 足りなければ補わずに断る

元：semantic-agent-schema/docs/essence.md の「受け取り方」と「設計の進め方」

モジュール層持つもの

  • 外のライブラリは、許したアダプターだけが使う（rusqlite は sqlite、jsonschema は jsonschema、boa は javascript）

3コマンドと引数

コマンド必須任意
validate<経路>... ・ --schemas <置き場所>...--semantic ・ --all-rules（--semantic ・ --answer と）・ --answer <ファイル | ->（経路は1つ）
create<経路> ・ --schemas、次のどれか1つ：--concrete <$id> --value <JSON> ／ --concrete <$id> --semantic ／ --adopt--reason
update<経路> ・ --schemas、次のどれか1つ：--patch <JSON Patch> --if-match <ハッシュ> ／ --semantic ／ --adopt --reason。Concrete を直すときは（--semantic でも）--range <経路>...--reason ・ --base <コミット>（--adopt と）
delete<経路> ・ --schemas ・ --reason ・ --if-match <ハッシュ>。Concrete を消すときは --range <経路>...なし
render<経路>... ・ --design-system <経路> ・ --out <書き出す先> ・ --schemasなし
search<経路>...（範囲）・ --schemas、次のどれか1つ：--where <JSON Pointer>=<JSON> ／ --semantic --question ／ --answer--where を重ねる
logなし（--operation <ID> で1件）<経路>... ・ --by ・ --folder ・ --since ・ --limit
initなし（新しい ID を作り、tool はほかのコマンドと同じく環境変数から決めて登録し、返す）なし

記録をつけるコマンド（validate ・ create ・ update ・ delete）は、どれも --session <ID> か --human を取る。--semantic は手順を返すだけで、記録は読むだけ（セッションの行も足さず、記録が無ければ作らない）。search ・ render ・ デザインシステムの validate は誰が打ったかを取らず、記録を開かない。

AI が考えて付ける引数

何を引数無いとき
対象<経路>断る
スキーマの置き場所--schemas <置き場所>...断る。置き場所に $id が無くても断る
範囲<経路>... の並び（validate ・ search）・ --range（Concrete を直す ・ 消す）断る。既定の範囲は持たない
読んだ時の中身--if-match <ハッシュ>（update ・ delete）断る。いまの中身のハッシュと違えば、書かずに間に入った変更を返す
取り込む前の中身--base <コミット>（update --adopt）前の値の無い差分（before_unavailable）で取り込む。次の意味の判定は、前の判定を使えないので全部の所になる
セッション--session <ID>。人は --humanツールの環境変数で決まらなければ断る（Gemini CLI ・ Cursor は毎回付ける。ID は init で作れる）。ツールの環境変数があるところでは --human を受け取らない

引数の決まりは、上のコマンドの表と --help ・ 使い方の文が持つ。足りなければ、出力の kind = error で何が足りないかを言って断る。

終了コードいつ
0violated が無い（書けた ・ 返せた）
1violated がある ・ 断った
2使い方の誤り（code = usage）

4公開された言葉

published-language/v1/ に置く。AI と使う側が読む契約。

種類ファイル役目
Concrete を書く型abstract.schema.json ・ vocabulary.schema.json ・ dialect.schema.jsonConcrete が従う作法。x- の3つ（x-prompt ・ x-decided-by ・ x-view）の形と閉じた一覧。Abstract 自身も x-prompt を持ち、Concrete を書く ・ 判定するときの rule になる

5記録

{{records}}

形は adapters/outbound/sqlite/sql/records.sql の1つで決め、版は SHAPE が持つ。

表1行は何か結び付き
sessions打ったセッションchanges ・ validations の session_id が指す。人と明示した操作は NULL
changes書いた変更（create ・ update ・ delete）source は semantic-agent-schema（通した変更）か outside（取り込み）。worktree は書いたワークツリー
field_changes変わった項目（pointer ごと）change_id で changes を指す
validations検証ID は changes と同じ採番
rule_resultsrule と項目ごとの判定validation_id で validations を指す
ビュー operations変更と検証を記録した順にUC7 が読む
  • 置き場所は入口の db_path の1か所で決める（<git-common-dir>/semantic-agent-schema/records.sqlite）。Git のリポジトリの外では断る
  • 表の形の版が違う記録は開かない。記録はコミットしない作り直せるデータなので、そのファイルを消して打ち直すと空で作り直す（ファイルを消すかは利用者が決める）
  • 削除のあとは、前の判定を引き継がない（作り直した文書に前の判定を当てない）
  • target_path は Git の根からの相対。どこで打っても同じ経路になる
  • どの表も追記だけ。断った操作は記録しない

6処理の流れ

{{flow-validate}}

validate 1件。入口が引数を確かめ、モジュールがポートを通してアダプターを呼び出す。

{{flow-semantic}}

update --semantic → --patch --if-match、validate --semantic → --answer。validate --semantic はいつも手順を返し（判定する所が0件なら steps が空）、記録は --answer のときだけ。どのコマンドも、入口が引数を確かめてから呼び、結果を1行で返す。

7書き方の決まり

決まり中身
外の変更の検出validate と取り込みは、いまの中身を、このワークツリーで記録した最後の事後と比べる（まだ書いていなければ、記録のどれかの中身と）。違えば知らせ、取り込みの前提にする。update ・ delete は --if-match だけと比べる
x- の作法x-view は Concrete の根だけ。json-schema などの組み込みの検査の名前は rule の id に使えない（予約）
デザインシステムの検証validate にデザインシステムを渡すと、受け取りの型 ・ トークン ・ テンプレートの書き方 ・ --schemas の Concrete との合い方を契約に照らして返す。ほかの対象や --semantic と混ぜたら断る。記録しない
描くときに断るConcrete は描かない。書き出すページが入力のファイルと重なれば断る。欠けたテンプレートの種類は全部を返して断る。Git の外と、根の外を指す経路では描かない
書きかけを残さない文書は一時ファイルに書いてから置き換える。JSON Patch は全部当てるか、1つも当てない。描画は全部のページを書けてから置き換える
ページに入れないもの判定 ・ 記録 ・ ハッシュはページに入れない。テンプレートに渡すのは template-language.json の x-names（value ・ json ・ tokens ・ css）だけで、値の入口は x-data-entry（semantic-agent-schema-data）
