Semantic Agent Schema ・ 本質の像

具体モデリング概念

抽象モデリング概念を Go でどう作るか。ファイル ・ 型 ・ 列 ・ 引数の粒度で書く。何を ・ なぜは抽象モデリング概念が持ち、ここでは繰り返さない。

UC2-4 ・ D3 ・ S4 などは抽象モデリング概念の行の id。対象の OS は Linux と macOS。原文の行は、取得した原文のファイルの行番号。

2ポートとアダプター

ポートは、使う側の application が ports.go に、自分のユースケースが使うメソッドだけで宣言する。外部（ファイル ・ 操作の記録 ・ ライブラリ）の分だけ作り、試験の代役のためには作らない。

ポート宣言する package とメソッドアダプター
Documentsauthoring：Read ・ Write（一時ファイルに書いて置き換える）／ rendering ・ search：Readfiles
Schemasauthoring ・ rendering：Lookup（$id で Concrete を引く。$ref の先も先に引いて domain へ渡す。S2）files
Validator全部の application：Check（JSON をスキーマで検証し、違反を返す）schemacheck
Patcherauthoring：Applypatching
Recordsauthoring：WithLock ・ AppendChange ・ AppendValidation ・ LastValidation（前回の検証の JSON ドキュメントと judgment。S4）／ record：Operations ・ Operationrecords
Rendererrendering：Render（全部描けてから書き出す）templates

working tree と Git の共通ディレクトリは、入口が repository で一度だけ引き、各アダプターに渡す。application は Git を知らない。

4コマンドと引数

引数は pflag で読み、JSON にして arguments.schema.json で検証する（UC1-1 など）。違反は arguments_invalid の error になる。

コマンド引数UC
create<path> --schemas <ディレクトリ>、次のどちらか：--semantic --schema-id <$id> ／ --value <JSON | ->UC1
update<path> --schemas、次のどちらか：--semantic ／ --patch <JSON | -> --if-match <ハッシュ>。Concrete を更新するときは --range <path>UC2 ・ UC5（--human）
validate<path>... --schemas。意味的な検証は --semantic（--scope changed が既定で変更点だけ。--scope all で全部の instance location。値はこの2つだけで、procedure の scope と同じ）か --answer <JSON | ->（path は1つ）UC3 ・ UC4
render<path>... --schemas --design-system <path> --out <ディレクトリ>UC6
search<path>...、次のどれか：--where <JSON Pointer>=<JSON>（繰り返せる）／ --semantic --question <問い> ／ --answer <JSON | ->UC7
log[<path>...] [--by <ai | human>] [--limit <数>]、または --operation <command>:<id>UC8

値を2つ以上渡す引数（--schemas ・ --range ・ --where）は繰り返す。- は標準入力から読む。終了コードは、error か violated の judgment があれば 1、ほかは 0。

主アクター

  • 操作の記録に追記するコマンド（create ・ update ・ validate）は、主アクターを actor に残す。--human があれば human、無ければ ai
  • --human は、coding agent の環境変数があるところでは human_in_coding_agent の error で拒否する（D5）。見るのは次の名前の環境変数があるかだけで、値は読まない：CLAUDE_CODE_SESSION_ID（env-vars L381）・ CODEX_SESSION_ID（exec_env.rs L42）・ COPILOT_AGENT_SESSION_ID（changelog.md L2026）
  • セッションとの結び付けは使う側の責務で、Semantic Agent Schema はセッションの ID を受け取らない ・ 残さない

next への引き継ぎ

procedure と error の next には、受け取った --schemas ・ --range ・ --schema-id ・ --human と、いまのハッシュ（--if-match）を入れる。AI は <…> の部分だけを埋めて実行する。

6操作の記録

{{er}}

ファイルは <git-common-dir>/semantic-agent-schema/records.sqlite。形は adapters/outbound/recordstore/records.sql が決める。

表列抽象の行
changesid（PK）・ actor（ai ・ human）・ path ・ schema_id ・ command（create ・ update）・ before_hash ・ after_hash ・ atUC1 ・ UC2 ・ UC5
field_changeschange_id（FK）・ instance_location ・ op（add ・ remove ・ replace）・ before ・ afterD4
validationsid（PK）・ actor ・ path ・ schema_id ・ concrete_hash ・ content（検証した JSON ドキュメント）・ content_hash ・ atV1 ・ S4
judgmentsvalidation_id（FK）・ rule_id ・ instance_location ・ by（machine ・ ai）・ verdict（verified ・ violated ・ unverified ・ not-judged）・ reasonV3
ビュー operationschanges と validations を UNION ALL し、at の順に並べる。列は id ・ command ・ actor ・ path ・ atUC8
  • どの表も追記だけ。UPDATE と DELETE は trigger で拒否する
  • ID は INTEGER の主キー。ビューでは command と組にして指す（--operation <command>:<id>）
  • 書く操作は Records.WithLock の中で行う：BEGIN IMMEDIATE → ハッシュの確認（D3）→ Documents.Write → 追記 → COMMIT。追記に失敗しても、次の S4 の変更点が増えるだけ
  • 表の形の版（user_version）が違えば開かず、log_unavailable で records.sqlite の削除を示す。前の版との互換は作らない

決まり内容原文 ・ なぜ
package の名前短い小文字の1語。util ・ common ・ misc ・ api ・ types ・ interfaces を作らない。層は domain ・ application の名前で示すCodeReviewComments L797、blog/package-names L587

9試験と完成の条件

試験の正解は、本質と2枚のページだけ。Rust 版の出力は正解にしない。

決まり内容
ページの行の idどの試験も、確かめる行の id（UC2-6a ・ D3 ・ S4 など）を持つ。go test が、試験の id とページの id を比べ、片方にしか無い id があれば落とす
期待値実装より先に、ページの行から書く。出力から写さない。ハッシュは試験の中でバイト列から求める
比べ方出力は JSON Pointer と値の組で比べ、message の文は比べない。全部の出力を event.schema.json（procedure は procedure.schema.json）で検証する
環境試験ごとに新しい一時ディレクトリで git init し、本物のアダプター（一時ファイルの SQLite）を使う。子プロセスの環境は空から作る
試験の入口バイナリと application の手続きと、domain の公開の関数から実行する。非公開の関数を直に試さない
レベルdomain はコンポーネントテスト（S4 と主アクターの決まりはデシジョンテーブル、値オブジェクトと S1 は同値分割法）。application とアダプターはコンポーネント統合テスト。UC の拡張1つを1場面にするシステムテスト

完成の条件

条件測り方合格
1 実装 → ページpackage ・ 型 ・ 関数 ・ 引数 ・ 列 ・ code を go list ・ go doc ・ pflag の定義 ・ records.sql ・ error-codes.json から機械で並べ、作成者の会話を引き継がない Agent が、どれもページの行に結び付くかを判定する結び付かない行が0件
2 ページ → 実装ページの行の id ごとに、それを満たすコードを、同じく新しい Agent が探す満たすコードが無い行が0件
3 独立した書き起こしコードだけを渡した新しい Agent がページの行の形で書き起こし、別の Agent がページと比べる（無い ・ 余分 ・ 違う）。2回行う2回とも0件
4 受け入れ新しい Agent が --help とログイベントだけを見て、一時のリポジトリで UC0 と UC6〜UC8 を行う。UC5 は人として実行する人の助け無しで終える。エラーのときは instruction と next だけで直せた
5 振る舞い試験を全部実行する。go vet ・ gofmt -l ・ architecture_test.go ・ exhaustive も含む。deadcode ./cmd/semantic-agent-schema（-test を付けない）全部通る。id の対応表の片側にしか無い id が0件。main から届かない関数が0件
