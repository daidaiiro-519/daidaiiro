# semantic-agent-schema の実装レビューの観点

実装が、本質と、抽象 ・ 具体のモデリングから外れていないかを見るときの観点である。どの観点にも、照らすもの（正本）を付ける。

## 1 この文書の使い方

| 読む人 | いつ | 何をする |
|---|---|---|
| レビューする AI と人 | 実装を変えたあと、コミットの前 | 2 の観点ごとに、正本と実装を突き合わせ、外れを観点の ID（`R01` など）で指す |
| 実装する AI | 実装を始める前 | 自分の変更が触れる観点を読み、外れない形で書く |
| 実装を報告する AI | 実装を報告するとき | 変えた理由 ・ 守った契約 ・ 確かめたこと ・ 確かめていないことを書く。確かめていないことを、確かめたことにして報告しない |

### 1.1 正本

| 正本 | 何を決めているか |
|---|---|
| `docs/essence/essence.json` | 本質。利用者の言葉（W1〜）。ほかの正本より先に照らす |
| `docs/abstract-modeling/index.src.html` | 抽象：責務の範囲 ・ ユビキタス言語 ・ 機械的な検証と意味的な検証 ・ ユースケース ・ ドメインモデル ・ 変更点 ・ rejected ・ 境界 |
| `docs/concrete-modeling/index.src.html` | 具体：構成 ・ ポートとアダプター ・ ライブラリ ・ コマンドと引数 ・ 公開された言葉 ・ 操作の記録 ・ 処理の流れ ・ 書き方 ・ 試験 |
| `DESIGN-MODELING.md` | ユースケースからドメインモデルへの設計の手順と、ヘキサゴナルの置き方 |
| `CODING.md` | Go のコードと試験の決まり（K ・ T ・ L の ID） |

### 1.2 外れを見つけたときの書き方

| 欄 | 書くこと |
|---|---|
| 観点 | `R01` など |
| 実装 | ファイルと行 |
| 正本 | ページの節、または規則の ID |
| 外れ | 正本が何と言い、実装が何をしているか（1文ずつ） |
| どちらを直すか | 実装を直すか、正本が古いか。正本が古いときは、利用者の決定（essence ・ コミット）を根拠に書く |

## 2 観点

### 2.1 本質と責務

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|
| R01 | 責務の割り当てが1か所か：形の検証とサブスキーマと値の対応は JSON Schema の実装、JSON Schema で書けない不変条件と prompt の生成はドメインモデル、rule に照らした判定は AI | 本質 ・ 抽象 5節 ・ 7節 | 同じ責務を2か所でしていないか（JSON Schema の実装の結果をドメインがたどり直していないか）をコードで探す |
| R02 | ツールは AI を呼ばず、意味的な操作は prompt（手順）を返すだけか | 本質 ・ 抽象 2節 ・ 5節 | AI を呼ぶコード、AI の答えを推し量って補うコードが無いか |
| R03 | 持たないと決めたものを持っていないか（セッション ・ 主アクター ・ 人かどうかの確かめ ・ 入力の補い ・ 消すユースケース） | 抽象 10節 ・ 本質 W11 | その語や仕組みがコード ・ 引数 ・ 記録に無いか |
| R04 | 入力から機械的に導けないものを、中で引いていないか | 抽象 2節（責務の範囲と、外） | 中で引いてよいのは、自分の操作の記録 ・ Git の事実 ・ 渡された schemas の中の $id だけ |

### 2.2 ユースケースと CLI

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|
| R10 | 7つのユースケースが、コマンドとオプションで表されているか（semantic で prompt を返す層と、受け取って機械的に検証する層） | 抽象 6節 ・ 具体 4節 | ページのコマンドと引数の表と、`--help` の出力と、cli のコードが一致するか |
| R11 | ユースケースごとの主成功シナリオと拡張が、application の usecase_*.go の流れと一致するか | 抽象 6節 ・ 具体 7節 | 手順の並び ・ 拡張の条件 ・ 返すイベントを突き合わせる |
| R12 | 出力がすべてログイベントで、形が event.schema.json に従い、instruction と next が error-codes.json の定型から作られているか | 抽象 9節 ・ 具体 5節 | 文をコードに直に書いていないか。定型に無い文が出ないか |
| R13 | 入力（引数 ・ AI の response）が、すべて JSON Schema で機械的に検証されているか | 本質 ・ 具体 5節 | arguments ・ judgment-response ・ patch ・ search-response を通さない入力が無いか |

### 2.3 ドメインモデル

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|
| R20 | 集約（JSON ドキュメント ・ 検証）の不変条件が、ページの表どおりにドメインにあり、ほかの層に漏れていないか | 抽象 7節 | 不変条件ごとに、それを守るコードの場所を1つ挙げる。application や adapter で守っていないか。slice ・ map ・ ポインタ（`json.RawMessage` を含む）を持つ値を返す所と受け取る所で、外から中身を変えられないか（別名参照）。操作の記録や AI の response の JSON から値を戻す入口が、作る関数を通っているか（[CODING K77 ・ K78](CODING.md#26-値オブジェクトと空の値)） |
| R21 | 値オブジェクトとドメインサービスの表と、domain の型 ・ 関数が対応しているか（名前と責務） | 抽象 7節 | 表に無い型や関数、型や関数の無い表の行を挙げる |
| R22 | 変更点の求め方がページどおりか（前回の判定の記録との差、related_fields、引き継ぎ） | 抽象 8節 | changes.go と判定の prompt の作り方を突き合わせる |
| R23 | コードの語が、ユビキタス言語の表と一致するか（x-prompt と prompt、response、変更点、instance location、keyword location など） | 抽象 4節 | 型名 ・ 関数名 ・ コメント ・ ログイベントの欄名に、表に無い語や表と違う意味の語が無いか |

### 2.4 ポートとアダプター

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|
| R30 | 依存の向きが、cmd → adapters → application → domain、publishedlanguage は誰からも読める、で守られているか | 具体 1節 ・ 2節 ・ DESIGN-MODELING.md | architecture_test.go が通るだけでなく、試験が見ていない向きが無いか |
| R31 | ポートの表（名前 ・ メソッド ・ どのユースケースが使うか）と、ports.go が一致するか | 具体 2節 | 表に無いメソッド、使われていないメソッドを挙げる |
| R32 | ライブラリ（JSON Schema ・ JSON Patch ・ SQLite ・ テンプレート ・ JS の解析）が、それぞれ1つのアダプターに閉じているか | 具体 3節 | domain ・ application がライブラリを import していないか |
| R33 | 操作の記録の表 ・ 列 ・ ビュー ・ user_version が、ページと SQL で一致するか | 具体 6節 | recordstore の SQL と、ページの ER 図 ・ 表を突き合わせる |

### 2.5 公開された言葉

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|

### 2.6 書き方と試験

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|
| R50 | CODING.md の決まりに外れていないか | CODING.md | 外れを規則の ID で挙げる |
| R51 | コメントと試験に、UC などの識別子を書いていないか。コメントは具体モデリングの言葉で設計を書いているか | CODING.md ・ 具体 8節 | grep と目視 |
| R52 | 後方互換の残し ・ 使われないコード ・ 「前は」の記述が無いか | CODING.md（deadcode） | deadcode ・ grep |
| R53 | 試験の場面が、ページの完成の条件とユースケースの拡張を押さえているか | 具体 9節 ・ 抽象 6節 | 拡張ごとに場面があるか |
| R54 | 試験の期待を変える ・ 試験を skip する ・ 検査を止める（`nolint` など）変更が、設計を直したのか、検査を通しただけなのかを分けているか | 本質 ・ 抽象 ・ 具体 ・ コミット | これらの変更だけを別に取り出して見る。期待を変えた理由が、正本（ページ ・ 本質 ・ コミット）で説明できるか。説明できない変更は、実装を直す |

### 2.7 文書と実装の一致

| ID | 観点 | 照らすもの | 確かめ方 |
|---|---|---|---|
| R60 | ページに書いてあって、実装に無いもの | 抽象 ・ 具体の全節 | 節ごとに、実装の場所を1つ挙げる |
| R61 | 実装にあって、ページに無いもの | 抽象 ・ 具体の全節 | コマンド ・ イベント ・ code ・ ポート ・ ドメインの型ごとに、ページの場所を1つ挙げる |
