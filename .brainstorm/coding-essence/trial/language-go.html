Go の規則

決まった形で実際に書き、欄が足りるかを確かめるための試作である。
置き場所はまだ決めていない。

この文書が持つのは、メタデータと規則の並びだけである（論点4）。
どの規則をなぜ選んだかは、ここには書かない ── 書くと、規則が外から何が来るかを
知ってしまう。

載せる基準は、何を見れば守れたと言えるかを書けることである（論点5）。
書けないものは載せない ── 読む人は原典を読めばよい。
この文書が原典に足すのは、検証方法である。

要求レベルは、原文の語から決める。
原文が should なら推奨、do not や never なら必須である。原文より強くしない。

規則

1　名前

1-1　頭字語は、大文字か小文字かで揃える

要求レベル必須
検証方法機械が見る。 識別子を語へ分け、URL HTTP XML ID API などの頭字語が Url Http のような形で現れないことを見る

規定
頭字語は、URL か url のどちらかで書かなければならない。Url と書いてはならない。
ID も同じで、appId ではなく appID と書く。
プロトコルバッファの生成したコードは、この規則の外に置く。

出典

Words in names that are initialisms or acronyms (e.g. "URL" or "NATO") have a consistent
case. For example, "URL" should appear as "URL" or "url" (as in "urlPony", or "URLPony"),
never as "Url". As an example: ServeHTTP not ServeHttp.
This rule also applies to "ID" when it is short for "identifier" ... so write "appID"
instead of "appId".
Code generated by the protocol buffer compiler is exempt from this rule.

1-2　語の区切りを、大文字で表す

要求レベル必須
検証方法機械が見る。 識別子に _ が含まれないこと、全て大文字の識別子が無いことを見る（頭字語だけのものを除く）

規定
公開しない定数は maxLength と書く。MaxLength や MAX_LENGTH と書いてはならない。
ほかの言語の慣習がどうであっても、この書き方に従う。

出典

This applies even when it breaks conventions in other languages. For example an unexported
constant is maxLength not MaxLength or MAX_LENGTH.

1-3　パッケージの名前に、意味の無い語を避ける。型の名前でパッケージ名を繰り返さない

要求レベル推奨
検証方法機械が見る。 パッケージ名が util common misc api types interfaces のいずれでもないこと、型の名前がそのパッケージ名で始まっていないことを見る

規定
util common misc api types interfaces のような、意味の無いパッケージ名は避ける。
利用側はパッケージ名を付けて書くので、型の名前でパッケージ名を繰り返さないほうがよい。
chubby パッケージの型は ChubbyFile ではなく File にする。

出典

All references to names in your package will be done using the package name, so you can
omit that name from the identifiers. For example, if you are in package chubby, you don't
need type ChubbyFile, which clients will write as chubby.ChubbyFile. Instead, name the
type File, which clients will write as chubby.File. Avoid meaningless package names
like util, common, misc, api, types, and interfaces.

1-4　変数の名前は、宣言から遠いほど詳しくする

要求レベル推奨
検証方法人が見る。 機械は名前の長さしか見られない。宣言からどれだけ離れて使われるかに見合っているかは、人が決める

規定
変数の名前は、長いより短いほうがよい。範囲の狭い局所変数ではとくにそうで、
lineCount より c、sliceIndex より i を選ぶ。
宣言から遠いところで使う名前ほど、詳しくする。
繰り返しの添字や読み手のような、よくあるものは1文字でよい。

出典

Variable names in Go should be short rather than long. This is especially true for local
variables with limited scope. Prefer c to lineCount. Prefer i to sliceIndex.
The basic rule: the further from its declaration that a name is used, the more descriptive
the name must be.

1-5　受け手の名前は、型の1文字か2文字の略にする

要求レベル必須（me this self の禁止と、型の中で揃えること）／推奨（長さ）
検証方法機械が見る。 受け手の名前が me this self でないこと、同じ型のすべてのメソッドで同じ名前であることを見る

規定
メソッドの受け手の名前は、その型を表す1文字か2文字の略にするとよい
（Client なら c や cl）。
me this self のような名前を使ってはならない。
1つの型の中で、受け手の名前を揃えなければならない。

出典

The name of a method's receiver should be a reflection of its identity; often a one or two
letter abbreviation of its type suffices (such as "c" or "cl" for "Client"). Don't use
generic names such as "me", "this" or "self" ...
Be consistent, too: if you call the receiver "c" in one method, don't call it "cl" in another.

2　失敗

2-1　エラーの文字列を、大文字で始めない。末尾に句読点を置かない

要求レベル推奨
検証方法機械が見る。 errors.New( と fmt.Errorf( の第一引数の文字列リテラルを集め、先頭が大文字でないこと、末尾が . ! ? でないことを見る。先頭が固有名詞または頭字語のものは対象から外す

規定
errors.New と fmt.Errorf へ渡す文字列は、小文字で始めるとよい。
固有名詞と頭字語で始まるものを除く。末尾に . ! ? を置かない。
ほかの文脈に続けて表示されるからである。

出典

Error strings should not be capitalized (unless beginning with proper nouns or acronyms)
or end with punctuation, since they are usually printed following other context.
That is, use fmt.Errorf("something bad") not fmt.Errorf("Something bad")

2-2　error を、_ で捨てない

要求レベル必須
検証方法機械が見る。 戻り値に error を持つ関数の呼び出しを集め、その戻り値が _ へ束ねられていないことを見る

規定
error を返す関数の戻り値を、_ で捨ててはならない。
受け取ったうえで、扱うか、返すか、例外的な場合にかぎり panic する。

出典

Do not discard errors using _ variables. If a function returns an error, check it to
make sure the function succeeded. Handle the error, return it, or, in truly exceptional
situations, panic.

2-3　通常の失敗に、panic を使わない

要求レベル必須
検証方法機械が見る。 panic( の呼び出しを集める。人が見る。 それが例外的な場合に当たるかは、人が決める

規定
通常の失敗の扱いに panic を使ってはならない。
error と複数の戻り値を使う。

出典

Don't use panic for normal error handling. Use error and multiple return values.

2-4　失敗を、戻り値の中に紛れ込ませない

要求レベル推奨
検証方法人が見る。 機械は、-1 や "" を返す関数を集めるところまでしか言えない。それがその関数にとって正しい結果かどうかは、人が決める

規定
-1 や "" を返して失敗を知らせるのではなく、
ほかの戻り値が有効かどうかを示す値を、もう1つ返すとよい。
それは error でも、説明が要らないなら真偽値でもよい。最後の戻り値に置く。
nil "" 0 -1 が、その関数にとって正しい結果であるときは、そのまま返してよい。

出典

Instead of requiring clients to check for an in-band error value, a function should return
an additional value to indicate whether its other return values are valid. This return
value may be an error, or a boolean when no explanation is needed. It should be the final
return value.
Return values like nil, "", 0, and -1 are fine when they are valid results for a function,
that is, when the caller need not handle them differently from other values.

2-5　正常の道を、いちばん浅い字下げに置く

要求レベル推奨
検証方法機械が見る。 if err != nil の else の側に正常の処理が置かれていないことを見る

規定
正常の道はいちばん浅い字下げに置き、失敗の扱いを先に書いて字下げするとよい。
if err != nil { ... } else { 正常の処理 } と書かない。
if err != nil { ...; return } と書いて抜け、そのあとに正常の処理を続ける。

出典

Try to keep the normal code path at a minimal indentation, and indent the error handling,
dealing with it first. This improves the readability of the code by permitting visually
scanning the normal path quickly.

3　境界

3-1　interface は、使う側のパッケージで宣言する

要求レベル推奨（ただし「模擬のために実装側へ置く」は禁止）
検証方法人が見る。 機械は、interface の宣言と同じパッケージにその実装が在ることまでしか言えない。それが違反かどうかは人が決める

規定
interface は、その値を使う側のパッケージで宣言するとよい。
実装する側のパッケージは、具体の型を返す。
模擬のために、実装側へ interface を置いてはならない。

出典

Go interfaces generally belong in the package that uses values of the interface type,
not the package that implements those values. The implementing package should return
concrete (usually pointer or struct) types: that way, new methods can be added to
implementations without requiring extensive refactoring.

3-2　受け手の型を、1つの型の中で混ぜない

要求レベル必須
検証方法機械が見る。 同じ型のメソッドが、値と指し手の両方を受け手に持っていないことを見る

規定
1つの型のメソッドで、値の受け手と指し手の受け手を混ぜてはならない。
迷うなら指し手にする。
受け手を書き換えるなら、指し手でなければならない。
sync.Mutex のような同期の欄を持つ構造体も、写しを作らないために指し手でなければならない。

出典

Don't mix receiver types. Choose either pointers or struct types for all available methods.
If the method needs to mutate the receiver, the receiver must be a pointer.
If the receiver is a struct that contains a sync.Mutex or similar synchronizing field,
the receiver must be a pointer to avoid copying.

3-3　context.Context を、第一引数に置く

要求レベル推奨
検証方法機械が見る。 context.Context を引数に持つ関数の署名を集め、その位置が先頭であることを見る

規定
context.Context を受け取る関数は、それを第一引数にするとよい。

出典　（取得日 2026-09-06）

Most functions that use a Context should accept it as their first parameter:
func F(ctx context.Context, /* other arguments */) {}

4　並行

4-1　goroutine が、いつ終わるかを分かるようにする

要求レベル必須
検証方法人が見る。 機械は go の呼び出しを集めるところまでしか言えない。終わる条件が読み取れるかは、人が決める

規定
goroutine を起こすときは、それがいつ終わるのか、あるいは終わらないのかを
分かるようにしなければならない。
並行の処理は、終わりが読み取れる程度に単純に保つ。
それが難しいときは、いつなぜ終わるのかを書き残さなければならない。

出典

When you spawn goroutines, make it clear when - or whether - they exit.
Try to keep concurrent code simple enough that goroutine lifetimes are obvious.
If that just isn't feasible, document when and why the goroutines exit.

5　テストと説明

5-1　テストの失敗は、入力と実際と期待を示す

要求レベル推奨
検証方法人が見る。 機械は t.Errorf の書式に引数が3つ以上あることまでしか言えない。読んで分かるかは、人が決める

規定
テストは、何がどの入力で、実際にどうなり、何を期待していたのかを示して落ちるとよい。
t.Errorf("Foo(%q) = %d; want %d", tt.in, got, tt.want) の形にする。
並びは実際・期待の順にし、文もその順で書く。

出典

Tests should fail with helpful messages saying what was wrong, with what inputs, what was
actually got, and what was expected.
Note that the order here is actual != expected, and the message uses that order too.
Some test frameworks encourage writing these backwards: 0 != x, "expected 0, got x",
and so on. Go does not.

5-2　公開する名前に、説明を付ける

要求レベル推奨
検証方法機械が見る。 公開している最上位の名前に、説明の注記が付いていることを見る

規定
公開している最上位の名前には、説明の注記を付けるとよい。
公開しない型と関数も、内容が単純でないなら付けるとよい。

出典

All top-level, exported names should have doc comments, as should non-trivial unexported
type or function declarations.
