道具が、射影を出す試作で動く

道具 ／ 雛形は concrete が持つ

同じ宣言から、人が承認する HTML と、実行系が読む形が出る。出す先は 宣言 × 変換機 で決まり、ここでは 39 件出た。

$ schema render --as 承認
<h1>出荷指示（集約）</h1>
<h2>不変条件</h2>
<ul>
<li>明細の合計は、引当済の数量を超えない
    <code>sum(lines.qty) <= allocatedQty</code></li>
</ul>
<h2>操作</h2>
<li><b>確定する</b> ── 事前 ["status == 準備中",
    "lines.length > 0"］／ 事後 ["status == 確定済"]</li>
$ cat .codex/agents/AGG-01J7Q4K.toml
name = "AGG-01J7Q4K"
description = "出荷指示"
model = "gpt-5.6-luna"
sandbox_mode = "read-only"
developer_instructions = """
明細の合計は、引当済の数量を超えない を保つこと。

雛形は concrete が持つので、出す先を1つ足すのは雛形1枚と宣言1件である（Rust は0行）。

AI が、要る分だけ取る試作で動く

AI ／ 取る操作 3つ

仕様を全部は渡さない。索引を取り、参照をたどり、実装する宣言だけを取る。括弧の数はトークンで、実在の仕様を数えた値である。

> list　　　　　　　　　　　　　　　　　　　# 索引（299／17行）
BD-01J8D0P 宅配のサービス <business-domain>
BC-01J8B7C 受注の文脈 <bounded-context>
SD-01J8C1A 配送手配 <subdomain>
AGG-01J7Q4K 出荷指示 <aggregate>
UC-01J7Q8Q 出荷を確定する <usecase>
…（17行）
> refs AGG-01J7Q4K　　　　　　　　　　　　 # 参照をたどる（38）
指している　 BC-01J8B7C　SD-01J8C1A
指されている （無し）
> get AGG-01J7Q4K　　　　　　　　　　　　　# 宣言1件（360。中央値は108）
{ "kind":"aggregate", "id":"AGG-01J7Q4K", "name":"出荷指示",
  "rules":[{"name":"明細の合計は、引当済の数量を超えない",
            "predicate":"sum(lines.qty) <= allocatedQty"}],
  "ops":[{"name":"確定する",
          "pre":["status == 準備中","lines.length > 0"],
          "post":["status == 確定済"],
          "writes":["出荷指示","出荷明細"]}],
  "nodes":[{"id":"SC-01J7Q4M","name":"明細が0件のとき、確定できない",
            "then":{"fails":true,"checks":["status == 準備中"]}}] }

実測 ── この3つで 697（索引299 ＋ 参照38 ＋ 宣言360）。全部を詰めて渡すと 2,674 なので 26% である。釣り合う点は取る宣言の大きさで動く ── 中央値の宣言なら12.6件、いちばん大きい宣言なら5.6件で並ぶ。

AI の文脈に載るものこれから

AI ／ 読まれ方

取った結果に、concrete の schema が持つ x-prompt が付く。読み方も利用者が書く ── 道具は「x-prompt が在れば頭に出す」しか知らない。

# aggregate 読む: 状態と不変条件を持つ単位
# aggregate 書く: 操作を呼ぶ前に事前条件を取り直す。書き換える先も宣言に在る
# scenario 書く: 期待（given / when / then）はテストの元である。作り替えない

AGG-01J7Q4K 出荷指示 <aggregate>
  不変条件　明細の合計は、引当済の数量を超えない
  　　　　　sum(lines.qty) <= allocatedQty
  操作　　　確定する
  　　　　　事前 status == 準備中 ／ lines.length > 0
  　　　　　事後 status == 確定済
  　　　　　書き換える 出荷指示 ・ 出荷明細
  シナリオ　SC-01J7Q4M 明細が0件のとき、確定できない
  　　　　　期待 失敗する（status == 準備中）

同じ宣言を --as 承認 で取れば HTML が出る。操作と射影は直交する ── 何を取るかと、どの形で受け取るかは別である。

AI が書く試作で動く

AI ／ 受ける操作 2つ

書く先は3つある。実装とテストはふつうにファイルへ書く ── 道具はソースを1行も読まない。道具へ入るのは対応表の1行だけである。

① 実装とテストを、ファイルへ書く
src/出荷指示.rs
tests/出荷指示.rs
  #[test] fn 明細が0件のとき確定できない() { … }
② 結んだと申告する ── 道具へ入るのはここだけ
> bind(node="SC-01J7Q4M", external="usecase::tests::明細が0件のとき確定できない")
対応表へ1行入った
③ 仕様を直すときは、ファイルへ書いて validate で受ける
> validate
× spec/宅配のサービス/usecases/all.json
    UC-01J9B2B/body: 欄 context が無い
見つかったこと 1 件

道具に、仕様を書き換える操作は持たせない。書き換えられると、承認を経ない変更の経路ができる ── 仕様の変更は PR を通る（論点8）。書くのは AI だが、通すのは人である。

9

壊すと、別の行で出る試作で動く

道具 ／ 4通りの壊れ方 
① シナリオを足して、テストをまだ書いていない
対応の無い節： SC-01J9C1A  ／ 承認の境目でゼロ
② 誰も宣言していないテストが在る
結ばれていない識別子： usecase::tests::こっそり足した  ／ 常時ゼロ（落とす）
③ テストの名前を変えた
切れた対応： usecase::tests::明細が1件あれば確定できる ── 外に無い  ／ 承認の境目でゼロ
④ 宣言していない Skill を、手で置いた
結ばれていない識別子： .claude/skills/手で置いた/SKILL.md  ／ 常時ゼロ（落とす）

「常時ゼロ」は落とす行で、「承認の境目でゼロ」は人が承認するまで残ってよい行である。直す手は2つしかない ── 仕様へ入れるか、成果物を消すか。
