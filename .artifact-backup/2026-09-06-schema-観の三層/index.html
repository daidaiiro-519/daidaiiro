10名前の実体は、どこに置くか

宣言が指すのは名前であり、その名前が何に解決されるかは実装側の話である。 ただし置き場所は2つに分かれる ── 検査が集約の境界の内側で閉じるかどうかで決まる。

検査答えを出すのに要るもの名前の実体を置く場所
VALIDATED なら検証結果の置き場所を持つその文書だけ集約（不変条件）
節の対が揃っているその文書だけ集約（不変条件）
参照が実在する節に届く他の文書ドメインサービス
schema の版がそろう他の文書 ＋ schemaドメインサービス
シナリオと実装がずれていないソースの木ぜんぶドメインサービス
出典の文字列が原典に在る落とした原文ドメインサービス

集約にまたぐ検査を持たせると、集約が内側から他の集約を引くことになる ── そこで集約は一貫性の境界ではなくなり、何でも入る箱になる。

置き方そう置く理由
検査は「コマンド」と呼ばないコマンドは状態を変える意図を指す。検査は状態を変えず判定を返すので、仕様か問い合わせのサービスである
モデルが「自分の構造契約はこの schema」と持つschema がモデルを知ると、構造契約が実装に依存する。向きはモデル → 仕様である
名前の実在は、schema 自身が閉じる未実装を落とすコンパイラがいない。名簿に無い名前を規則が指せないことで閉じる

論点 7

どこまで書いたら、人に見せるか

書くのは節、承認するのは文書 ── このずれが Human On The Loop の境界そのものである。論点6・8 の決着が、ここへ 材料を落とした ── 規則は「まだ確かめていない」を数えられるようになり、差分は意味として持てるようになった。

1決まり

B

承認は、意思決定が起きる境目（ブレスト→spec、spec→実装）でだけ行う。その間は決められた構造と規約が値を埋め、検査が守る。②で人が見るのは差分と、未検の一覧である

なぜそう言えるか

結論のどこを支えるかもとにしたことその出どころ
境目に絞ること承認は意思決定に対して行うものであり、値が埋まったことに対して行うものではない前提承認点をブレスト→spec と spec→実装 に置く、という置き方
間を人が見ないことその間は決められた構造と knowledge と規約に従って値が埋まるだけである前提同上
間を検査で守ること宣言された規則は「まだ確かめていない」を数えられる決まり論点6 の決まり（述語 ＋ 確かめることの名前）

合成した文字列は保存されない。渡すときに作られ、渡し終われば消える ── だからどの形を選んでも、正本の schema は変わらない。 人が読むのは保存の形（説明と指示が別の欄に分かれたもの）のままである。

だから3つの差は2つしかない ── 分解できるかどうかと、かさである。 読みにくさが問題になるのは案B（description に直接書く）を採ったときで、案Cには当たらない。

どの階層に置けるか

description は「その schema が記述するインスタンスの目的の説明」である（原典の言い方）── だから欄だけでなく、塊（オブジェクト）の schema にも付く。配列の要素にも、$defs の中にも付く。

指示の中に意味の境界があるなら、それは文字列の中ではなく欄で表す。 いまは「振る舞いを述べる一文。実装名を含めない。例：…」のように句読点が境界を兼ねているが、 句点の打ち方が変われば、境界も動いてしまう。

これは壊す変更だが、いまは受け入れる。 x-prompt-write を文字列からオブジェクトへ変えると、既存の schema はそのままでは通らない ── いまが段1・段2 の再定義そのものなので、ここは一度で変える。 新しい欄を足して古い文字列を残す、という迂回はしない ── 迂回すると、 再定義が終わった時点で、使わない欄が最初から残っていることになる。

残る問いは1つ ── どの形がいちばん効くか。 同じ節を、合成なし ／ 散文 ／ ラベル行 ／ JSON 文字列の4通りで埋めさせ、 規則に違反した件数を比べる。Waffle は自分自身が対象なので、この測定はいつでもできる。

論点 11

論点 13

節を引く仕様を、どう決めるか

いまは JMESPath の式1つで引いている。式は JSON の構造に対するもので、schema が持つ意味（印・型・軸）を知らない ── そこが、この論点である。そして schema が形を固定している以上、その型をどう引くかも型ごとに決まっているはずである ── 引き方は、取得する側が毎回考えるものではない。

C

  • 領域は見つけるもの、文脈は決めるものである。領域は事業方針によって決まる構造で、文脈はプロジェクトの目的と制約に合わせて技術者が決定できる ── だから文脈がソフトウェアの設計境界だという読みは正しい。ただしそれは「ある領域の中の境界」とは限らない
  • 1つの文脈が複数の領域を含むとき、領域の境界は名前空間 ・ モジュール ・ パッケージとして現れる ── 実装の側の話になる（物理的には単一の境界、論理的には複数の境界）
  • 「層で切る」だけでは足りない。CodingSkills も同じ場面を通り、雛形の単位まで下ろして初めて形が定まった ── spec でも同じ段が要る
  • 切る基準は「1つの文書として閉じるか」である。閉じない単位を種にすると、中身が他の文書へこぼれる ── 一貫性の境界より小さく切れないのは、そのためである
  • 業務 × 接点が2つに割れた。約束は 能力 × 接点 の組ごとだが、順序は複数の約束をまたぐ ── 画面の遷移や対話の流れが、どの約束にも属さない

  • 言葉（用語集）を、文脈の中に入れるか別の単位にするかは決めていない ── 文脈の定義そのものが言葉なので、いまは文脈に含めている
  • 「つながりの順序」が、本当に接点をまたぐかは確かめていない ── 画面の遷移は UI の中の話かもしれない

8形が変わるとき、何が起きるか

同時に別の形が並ぶことは、問題にならない。 対応は文書ごとの宣言なので、ある文脈は2つの領域をまたぎ、別の文脈は1対1、が同じリポジトリで成り立つ。

問題になるのは、形が変わるときである ── 1つだった文脈を2つに割ると、 その中の集約やユースケースがどちらの文脈に属するかを決め直すことになる。

文脈を割ったときに起きること
並べる形文書を移し、対応の宣言を書き換える。 フォルダの規則は変わらない（領域は1本ずつ、文脈は1つずつ）
入れ子の形階層ごと組み替える。領域の下に文脈があるなら、 割れた文脈の片方は別の領域の下へ移る ── 置き場所の規則そのものが動く

そして参照は壊れない ── 文書どうしは印で指している（論点3）。 名前やパスで指していたら、移した瞬間に全部が切れる。 移動が「移動」で済むのは、印で指しているからである。

残るのは、割った結果として中身を分ける作業である。 これは言葉が割れたことの帰結なので、どんな置き方を選んでも避けられない ── 置き方で変えられるのは、それに加えて構造の組み替えまで要るかどうかだけである。

9フォルダは、schema の中に書かない

置き方は、schema が宣言することではない。 どの節がどの型かは schema が決めるが、その文書がどこに置かれるかは、人が読むための投影である（論点8）── schema に置き場所を書くと、構造の契約に投影が混ざる。

何がどこに属するか
軸 ・ 種 ・ 欄concrete schema（構造の契約）
この文書はどのフォルダに置くかschema の外 ── 投影の規則（道具の設定）
置き場所が規則どおりか検査（名前で指す ── 論点6）

CodingSkills も同じ形を通っている ── ディレクトリ構成は 「アーキテクチャの層」ではなく「言語 × アーキテクチャの層」が決めると切り分けた。 置き場所は、いつも一段具体の側にある。
