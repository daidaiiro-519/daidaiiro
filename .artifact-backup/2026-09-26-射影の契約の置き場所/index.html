射影の契約の置き場所

abstract schema / concrete

射影の契約は、基盤が持つ

concrete は利用者の側に在り、能力の契約は道具の側に在る。射影も、対応表も、テストの一覧も、何であるかを定めるのは契約である ── だから利用者が自分の concrete を置いても、道具は検査できる。

3層である。道具が配るのは下の2段だけで、実体は利用者のリポジトリに在る。破線は利用者が置くもの、実線は道具が同梱するものである。

縦の2組が、対応している

concrete宣言の schema（6種類） 事業領域 ・ 業務領域 ・ 区切られた文脈 ・ ユースケース ・ 集約 ・ 業務サービス。何を1件にするかは方法論が決める。
abstract schema宣言の契約 基盤が知るのは「ID を持つ節である」ことだけで、中身を認知しない。ここは既に成立している。
concrete射影の実体 雛形と、穴へ入れる値。HTML ・ MD ・ JSON ・ TOML の形は、出す先ごとに違う。
abstract schema射影の契約欠けている 入力は宣言1件 ／ 雛形は1枚 ／ 穴の過不足は例外 ／ 出力の種類を申告する。いまは名前と閉包の対応表しか無い。

いま、基盤は射影について何も検査できない

試作は r.render("render.aggregate", |d| …) の形で、基盤が持つのは名前と閉包の対応だけである。閉包の中身は基盤から見えないので、返り値が文字列であること以外に契約が存在しない。結果として、次の3つが出ない。

01雛形の穴の埋め忘れ ── いまは format! なので、宣言に欄を足しても射影に出ないだけで、誰も気づかない
02射影を持たない宣言の種類 ── 決まりとしては在るが、閉包が不透明なので検査が書けない
03承認用の射影が2本ある登録 ── 出力の種類を申告しないので、判定できない

完成イメージ ── concrete 側に置くもの

射影が Rust から出て、ファイルになる ── 1件が雛形1枚と宣言1件である。既定の concrete のぶんは道具が同梱し、利用者が足すぶんは利用者のリポジトリに置く。どちらも同じ契約を守るので、道具は両方を同じに扱う。

道具（配布するもの） abstract schema/ 能力の契約 concrete/usecase/ 既定の concrete。差し替えられる subdomain.html 雛形 subdomain.render.json 射影の宣言 context.html context.render.json 利用者のリポジトリ .<道具名>/ spec/宅配のサービス/ 仕様の JSON ── 成果物である bindings.json 対応表 tests.txt テストの一覧 concrete/ 自前の concrete（置いてもよい）

同じ射影（区切られた文脈）を、いまと完成後で並べる。

記法は3つで止める ── {{経路}} 穴 ／ {{#each}} 繰り返し ／ {{#if}} 条件。値の加工は持たせない。

模擬の結果 ── 試作の射影2件を、実際に置き換えた

試作 trial/spike/ の写しで、実在の宣言7件（業務領域4 ・ 区切られた文脈3）を雛形と宣言だけで出し直し、いまの Rust が出すものと照合した。模擬では仕様も雛形も crate の中に置いてある ── 試作の都合であって、上の境目とは違う。

出力が変わらないか7件とも一致1バイトずつ同じ。雛形と宣言だけで、いまと同じ HTML が出る
A 欄を足して出し忘れる止まったどの射影にも出ない欄 ["businessDomain", "owner"]
C 欄名を改名して直し忘れる止まった経路が解けない: body.asOf

模擬で出た綻び2件

01Aの検査が、参照の欄まで拾った ── businessDomain は射影に出さない欄で、引き算が参照として使う。検査の条件を「どの射影にも出ず、どの参照にも使われない欄」に直す必要がある
02集約の射影は、まだ置き換えられない ── 期待の行（成否と確認する点を ・ で連結する）が値の加工である。記法に持たせないと決めるなら、基盤が名前つきの変換を持つか、宣言の側が加工済みの値を持つかを決めることになる

深さは、この境目から決まる

concrete が利用者の側に在るなら、射影を Rust では書けない。雛形と宣言でしか書けない ── 道具を分岐して組み直させることになるからである。契約が道具の側に無ければ、利用者が置いた雛形を検査する根拠も無い。

残っているのは、記法をどこで止めるかだけである。

模擬で当たった綻び②（期待の行 ＝ 値の加工）が、そのまま利用者の側の問題になる。利用者が加工を必要としたとき、Rust を書けない以上、逃げ道が要る。

道具が、名前つきの変換を一式持つ（連結 ・ 既定値 ・ 大小など）。利用者は選ぶだけで、作れない。足りなければ道具へ1件足す判断になり、承認を通る。

宣言の側に、加工済みの値を持たせる。道具は素通しにする。記法は穴 ・ 繰り返し ・ 条件の3つで止まる。
