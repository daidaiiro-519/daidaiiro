語の単位で判定できない不自然さの審査

提案まだ承認を得ていない。適用してはならない2026-09-27
決めること ── 承認か差し戻しを返すのは、この1件である
語彙表では判定できない日本語の不自然さ（造語 ・ 比喩 ・ 主述の不整合 ・ 含意の不一致 ・ 幼い語り口 ・ 回りくどさ）を、判定基準に基づいてモデルに審査させる。

なぜ、いま決めるのか

層1（語彙表の照合）は語の単位でしか判定できない。利用者が指摘してきた不自然さの多くは、登録済みの語を含まない。例は「3言語は覆った」「締めを流す日」「実行の担い手が走る」である。指摘は過去の会話で約80件あり、同じ型の指摘が繰り返されている。判定基準は、その指摘から型を抽出して作成した。

形の変化

何がいまの形これからの形
検出できる不自然さ語彙表に登録した語（和語の述部 ・ 廃語）だけ語彙表の語に加えて、判定基準8件の型に当てはまる表現
判定基準と手順の置き場所無いSkill の references（review-criteria.json ・ review-instruction.md）。事例はプロジェクトの .doc-writing/review-examples.json
会話の応答への適用層1（reply）だけ層1に加えて、agent 型の Stop フックが手順のファイルを読んで審査する
CLI と MCP─review が、同じ正本から判定の依頼文を組む。判定はモデルが実施する

図で確認する

実現の形

判定基準8件を JSON で定義し、文脈を要する基準（指し先の欠落）には needs_context を付ける。手順を Markdown で定義する。宣言に review を追加する。Stop フックには、手順のファイルを読ませる agent 型のフックを追加する。設定の prompt は手順のファイルの場所だけを持ち、判定基準を複製しない。層1には「揃う」と「代償」を追加し、「言い回し」の誤検出を解消する。

適用先

doc-writing-skills の references に判定基準と手順を追加し、宣言（rs/declare/src/lib.rs）と SKILL.md を変更する。和語の一覧（predicates.json）と廃語の一覧（.doc-writing/retired-words.json）に語を追加する。事例（.doc-writing/review-examples.json）を追加する。承認後に .claude/settings.json へ agent 型の Stop フックを追加する。

比較した案

どれも反証を通過しなかった案である ── 未解決のまま残っているものではない。

案採らなかった理由
prompt 型のフックに判定基準を書くprompt 型はファイルを読めない。判定基準を設定へ複製することになり、Skill の正本とずれる
command 型のフックから claude -p を実行する入れ子のセッションが同じ Stop フックを起動する。道具が claude の CLI に依存する
Sonnet で判定する実測で、事例なしの Sonnet は検出12件 ・ 誤検出3件だった。事例付きの Haiku（検出12件 ・ 誤検出2件）より良くない
指し先の欠落も会話の応答に適用する実測で、指摘の無い文15件のうち11件を違反と判定した。応答は前後の文脈を保持しない

承認後に実施すること

  • 状態を accepted にして組み直し、変更と記録をコミットする
  • Stop フックに agent 型のフックを追加する。モデルは haiku、prompt は「会話の応答を審査する。.claude/skills/doc-writing-skills/references/review-instruction.md を Read で読み、その手順に従う。本文は、次の入力の last_assistant_message である。$ARGUMENTS」とする
  • 運用で誤検出と見逃しを記録し、事例（.doc-writing/review-examples.json）へ追加する

日本語の審査の手順

あなたは日本語の技術文書の校閲者である。本文に、判定基準への違反が在るかを判定する。

手順

1. 判定基準を用意する。この依頼文に「判定基準」の節が在れば、それを使う。無ければ .claude/skills/doc-writing-skills/references/review-criteria.json を読む
2. 事例を用意する。この依頼文に「事例」の節が在れば、それを使う。無ければ .doc-writing/review-examples.json を読む。そのファイルも無ければ、事例なしで進む
3. 本文へ判定基準を適用する
- 会話の応答を審査するときは、needs_context が true の基準を適用しない。 応答は前後の文脈を保持しないので、指し先が本文の中に無いことを違反としない
- 事例は、基準の適用の仕方の参考である。本文に同じ語が無くても、同じ型の違反を検出する
- 鉤括弧（「」）の中とコード（バッククォートの中）は、他人の言葉か識別子なので審査しない
4. 結果を、JSON 1行で出力する

出力の形

違反が1つでも在れば、次の形で出力する。

{"ok": false, "reason": "<基準の id>：<本文の該当箇所> → <言い換えの案>"}

違反が複数在れば、reason に「 ／ 」で区切って並べる。違反が無ければ {"ok": true} だけを出力する。

判定を誤りやすい点

- 主題の「は」で始まり、動作の主体を省いた文（「図は、描画してから提示する」）は、日本語として成立している。predicate-fit の違反としない
- 専門用語は、分野で定着していれば造語ではない

name: doc-writing-skills
description: 日本語のテクニカルライティング文書を書く・直すときに必ず使うスキル。設計文書・仕様・報告・README・学術文書など、人が読む文書を書き起こす前と、書いたあとに使う。「文書」「まとめて」「書いて」「ドキュメント」と言われたとき、および既存のmdやHTMLの本文を直すときに必ず使う。
version: 1.0.0

目的

技術文書としても学術文書としても違和感のない日本語を書く。

満たすこと
論意味が通り、論が成立している
構造情報が、その型に合った形で置かれている
文調人が読んで、一度で意味が取れる
語彙同じ文脈では、同じものが同じ語で呼ばれている

判断の材料は10の概念である。
どれも公開された規格・指針から導いており、出どころを最後の節に置く。

出すには、2つのゲートを実行する。

ゲート何を検査するか誰が決めるか
10件にできるものが、0件であること機械
210の判定すべてに、結果が1行ずつあること書き手

ゲート2が保証するのは、判定を適用したことだけである。
何を直すかは、書き手の判断に残る。

役割

- 書いたものに、10の概念から導いた判定を適用する
- 判定を、読む人がその場でできる1つの操作に降ろす
- 原典から導けない決めは、そう書く
- 適用しなかった判定を、報告に書く

処理対象と成果物

処理対象

これから書く日本語の文書、または既に書いてある日本語の文書である。

成果物

10の判定を適用し、直したか残したかを明示する文書である。

入力の想定

受け取る情報解釈・既定値
読み手明示されなければ、その文書を初めて開く人とする
用語の定め対象フォルダに用語を定めた文書があれば、それに従う
文脈の境界明示されなければ、文書1本を1つの文脈とする

実行手順

Step 1: 読み手と用語を決める

書き始める前に、読み手を1つに決める。
読み手が決まらないと、選ぶ語も構成も決まらない（概念8）。
対象フォルダに用語の定めがあれば、先に読む。

Step 2: 10の判定を適用する

上から順に適用する。
前の概念が成立していなければ、後の判定は意味を保持しない。

#概念規則判定
1読み手が組み立て直す作業を、書き手が負担する1文の中で、読み手に計算をさせない。名詞句には、指し先を文書の中に置く名詞句を1つずつ抜き出し、「何の」「どこの」「どっちの」「誰が」を問う。文書の中の文字列で答えられない名詞句が1つでもあれば、その文は書けていない。「読み返して不自然か」で判定しない——書き手は指し先を知っているので、不自然に見えない
2情報の型が、置く形を決める対比・条件・手順・分岐を、散文に置かないその段落を、表か図に置き直せるかを試す
3数が増えたら、形を変える並べるものが3つ以上なら、箇条書きか表にする数える
4見出しは、本文を読まずに全体を掴ませる見出しの階層を飛ばさない。見出しを追えば全体の内容がつかめるようにし、見出しを目立たせる。番号は付けても付けなくてもよい ── 統一されているかだけを確認する見出しだけを抜き出して、順に読む。そのうえで、どの本文がどの見出しに属すかが見た目で分かるかを確認する
5結論を先に置き、根拠を後ろに置く節の最初の一文を結論にする各節の先頭文だけを並べて読む
6読み手は、形の違いを意味の違いとして読む同じ立場のものは同じ形で書く。文体は文書の中で1つにする並んでいるものの語尾を見比べる
7語の意味は、文脈の中で定まる同じ文脈では、1つの意味に1つの語だけを対応づける。文脈が変わるなら、変わることを書く用語を列挙し、同じ意味の別の語が無いかを確認する
8読み手が誰かで、選ぶ語と構成が変わる読み手を先に決める。語は、読み手の世界にすでにある語から選ぶ。分野で定着した専門用語はそのまま使い、自分が作った語・訳した語は使わない。使うなら、新しい語だと書いて定義する。名前のあるものを、描写で呼ばない語の出どころを提示できるかを確認する。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する。そのうえで、書いた操作や物に、分野で通っている名前があるかを1つずつ問う。あるなら、描写ではなくその名前を書く——「均す」ではなく正規化する、「流す」ではなく実行する、「鵜呑みにしない」ではなくそのまま信じない。ふつうの日本語の語も、この判定に掛ける。作った語でも訳した語でもないので、出どころだけを確認すると通り抜ける。読み手が分野の外の人でも、描写に置き換えてはならない。言い換えてよいのは、日常語で意味が表せるものだけである（頻回→頻繁に）。日常語で表せないものは、その名前のまま使い、説明を添える
9読み手が一度に扱える量には限りがある1文は短くする。段落は3行から7行にする。文書の限度を決める数える
10比喩と定型句は、読み手によって解けない比喩は、例として明示するときだけ使うその比喩を字義どおりに読んで、意味が通るかを試す

名詞句で終わることは、それ自体では欠陥ではない。
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
判定1が見るのは、文の中で読み手が戻るかどうかである。

Step 3: 直したか、残したかを明示する

判定に該当した箇所を、直すか、理由を付けて残すかのどちらかにする。
理由が書けないなら、それは直す対象である。

Step 4: 2つのゲートを実行する

ゲート1は機械が決める。

doc-writing-skills check <ファイル...>
doc-writing-skills check <ファイル...> --synonyms 用語.tsv
検査拠って立つもの
見出しの階層が飛んでいる概念4
文体が混ざっている概念6
並んだ項目の語尾が統一されていない概念6
文字で図や表を描いている概念2
同じ意味の語が2つある（対を渡したとき）概念7
強調が描画されない媒体の決め

最後の1つだけ、概念から導けない。
マークダウンの記法に拠るもので、5つの原典はどれも描画について書いていない。
別枠であることを、--list と名簿に書いてある。

概念3と概念9は、ゲートに入らない。
数は数えられるが、いくつで形を変えるかは文脈で変わるので、0件にできない。
判定として、書き手が適用する。

利用者への応答には、reply を適用する。
応答で使用した語は、そのまま文書へ流入するので、文書と同じ語彙表で照合する。
適用するのは和語の述部と廃語の2つだけで、見出しや文体の判定は適用しない。

doc-writing-skills reply --message <本文>   # 本文を直接渡す（MCP も同じ）
doc-writing-skills reply                    # Claude Code の Stop フックの入力を標準入力から読む

検出があれば、Stop フックが読む {"decision":"block","reason":…} を出力する。
Stop フックは応答を表示したあとに走る ── 表示を止めることはできず、修正した全文を続けて出させる。

語の単位で判定できない不自然さは、review でモデルに審査させる。
造語 ・ 比喩 ・ 主述の不整合 ・ 含意の不一致 ・ 幼い語り口 ・ 回りくどさは、語彙表では検出できない。
review は、判定基準（references/review-criteria.json）・手順（references/review-instruction.md）・
事例（プロジェクトの .doc-writing/review-examples.json）を1つの依頼文へ組む。判定はモデルが実施する。

doc-writing-skills review --message <本文>                   # 会話の応答（文脈を要する基準を外す）
doc-writing-skills review --message <本文> --scope document  # 文書（全部の基準を適用する）

判定は確率的である。ゲート1の代わりにしない。 実測（指摘された文15件 ・ 指摘の無い文15件）で、
ゲート1と併用して検出13〜14件 ・ 誤検出2件だった。

ゲート2は書き手が判定する。
報告に、10の判定すべての結果を1行ずつ書く。1つでも欠けていれば、通っていない。

出力形式

報告する内容書き方
直した箇所概念の番号ごとに、どこを何から何へ直したかを表で出す
残した箇所場所と、残す理由を書く
ゲート1の結果通ったか、通っていないか。件数を書く
適用しなかった判定番号で書く。全部適用したなら、そう書く。1つでも欠ければゲート2は通っていない
確認していないこと確認していないことを、確認したと書かない

ガードレール

- 運用の覚書の書き方を、どの文書にも使わない。ゲート1の「述部が和語である」が検出する語は、書いた本人が読み返すための書き方であって、読み手のための書き方ではない。CLAUDE.md と Skill も例外にしない ── 例外にすると、そこで書いた語がそのまま本文へ流れる。どの文書でも、操作の名前で書く
- 名前のあるものを、描写で呼ばない。その操作に分野の名前があるなら、自分の言葉で言い換えない
- 比喩で言い換えない。対象を別の物へ置き換えた語を使わない ── 指し先が読み手の側で決まらない（文書か、欄か、クラスかを、読み手が推測することになる）。利用者への応答も同じである ── 応答で使用した語は、そのまま文書へ流入する。対象の名前で書く。検出する語は廃語の一覧が保持する ── 散文で例を並べると、その例が本文へ流入する。ただし、普通の語の一部になる語は一覧へ入れられない ── 部分一致で正しい語まで検出するためである（「段」は段階 ・ 段落 ・ 手段 ・ 段組みの一部である）。その種の語は機械で検出できないので、書く時点で遵守する
- 文語寄りの語を使わない。「営み」「所以」「〜ねばならない」のように、書き言葉のためだけに選んだ語は、ふだん話す語へ替える。判定は、同じことを口で説明するときにその語を使うか ── 使わないなら、読み手にとっては飾りであって、意味を1つも足していない
- 廃語を使用しない。一度破棄した語の一覧はこのSkillの外にある ── いつ何を破棄したかはプロジェクトごとに相違するので、ここへ書くと書いたプロジェクトでしか使えない検査になる。既定では .doc-writing/retired-words.json を、対象のファイルから上へたどって探す。無ければこの検査は走らない（失敗にしない）
- 和語へ言い換えない。名前も、述部もである。原典が和語を勧めるのは広報・解説であって、事務的・専門的な文書ではない。名前を和語にすると必ず新語になり（メタデータ→「頭」、出典→「指す先」）、述部を和語にすると意味の範囲が広がる（適用される ・ 有効である ・ 作用する が、1語にまとまってしまう）。判定は2つ ── その語を検索して同じ意味が出てくるか。意味を特定できる漢語が在るか

言い換え先は、references/predicates.json が定義する。
ゲート1の「述部が和語である」はその定義で検出し、検出した1件ごとに言い換え先を出力する。
この文書は定義を複製しない ── 複製は本体とずれ、どちらが正しいかを毎回確認することになる。
- 指し先の無い名詞句を書かない。「ずれ」「外を指す名前」のように、それが何を指すかを文書の中に書いていない語を使わない。見出しに置く語は、見出しだけで指し先が分かる形にする（「ずれた34件」ではなく「仕様と実装のずれ34件」）
- 散文で書けることを、散文で書かない。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- 桁を空白で整列させて、表に見せない。表はマークダウンの表で書く
- ASCII で図を描かない。図は mermaid か SVG で書く
- 同じ文脈で、同じ意味に2つの語を対応づけない。文脈が変わるなら、変わることを書く
- 訂正の記録を本文に残さない。文書には現行の正しい内容だけを書く。履歴は git が持つ
- 数値は原典の文字列で確認してから書く。要約を経由して引かない
- 確認していない内容を、確認したように書かない。推測は推測と分かる形で書く
- 原典から導けない決めを、原典の記述として書かない。こちらの決めだと書く
- ゲートを実行していないものを、出さない。実行していないなら、そう書く

「基本動詞は対象外」という区分も、原典に無い。 原典が持つのは和語の動詞という語種の区分だけで、
使う ・ 読む ・ 示す ・ 伝える ・ 決める も全て和語である。
語彙表に入れる・入れないの判定は、このリポジトリが実施している。

原典は変わる。
HTML の頁は書き換えられ、PDF は版が上がる。
取得した日を残しているので、照合し直すときはそこから確認する。

参照

- rs/cli/: 唯一の入口。check ・ checks ・ tails ・ reply ・ review ・ sources を持つ ── どれも --json で機械が読む形が出る。終了コードは 0 指摘なし ／ 1 指摘あり ／ 2 誤用。宣言に無い旗は断る
- rs/declare/src/lib.rs: 道具の宣言。能力の正本であり、CLI と MCP はここから組む
- rs/parts/src/gate.rs: ゲート1の実行。拠って立つものは checks で見られる
- rs/parts/src/checks.rs: 8つの判定の実体
- rs/parts/src/unit.rs: 本文を判定の単位へ割る。引用と記号で囲んだ中を、書き手の文として数えない
- rs/parts/src/tails.rs: 語彙表を使わずに句の末尾を全部収集して並べる。ゲート1 の和語の検査は語彙表で照合するので、表に無い和語は通過する ── この道具で洗い出し、確定したものを references/predicates.json へ追加する
- rs/parts/tests/: 事例（28件）。8つの判定と、単位の割り方を固定してある
- references/predicates.json: 和語の述部と言い換え先の正本（59件）。出典と、その立場を持つ
- rs/mcp/: MCP の面。同じ宣言から組む ── 能力を1行も複製しない
