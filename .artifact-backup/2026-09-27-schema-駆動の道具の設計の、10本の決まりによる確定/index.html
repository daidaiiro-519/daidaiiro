ユースケース駆動と、それを支える schema 駆動の道具の設計を、10本の決まりで確定する。

なぜ、いま決めるのか

決着はブレストボードが保持するが、そこに在るのは答えだけである。なぜその答えになったかは、回ごとの反証に散在している。承認が成立した時点で「なぜ」が消失すると、あとからその決定を改訂してよいかを判定できない。論点10と11が 2026-09-27 に決着し、10本すべてが決着した。試作は10本すべてを1度通過し、試験67件が成功したので、実装へ移る前に確定する。

形の変化

何がいまの形これからの形
論点1　道具の範囲実装とビルドまで含むかが未定である仕様を出し、契約を定め、突き合わせるまでとする。契約はソースの外に置き、道具はソースを読まない
論点2　方法論の注入道具が方法論を保持する前提である基盤は方法論も AI ツールも認知しない。注入点は2つで、射影は承認の HTML と、変換機が出すツールごとの形である
論点3　仕様の外に出られなくする手段実行時に見張るか、突き合わせるかが未定である単位は宣言とシナリオとする。引き算は3系統で、置き場所は事業領域で切ったフォルダの根から決まる
論点6　宣言の種類と多重度何を1件の宣言とするかが未定である宣言を6種類とする。多重度は4本を1で固定し、業務領域と文脈の対応は導出する
論点4　振る舞いの持ち方6種類のどれが操作を持つかが未定である振る舞いを持つのは、集約 ・ ユースケース ・ 業務サービスの3つとする。シナリオはテストと結ぶ単位である
論点5　人が承認するもの何を何回承認するかが未定である承認は人が PR のレビューで1回とする。人が読むのはシナリオの射影だけである
論点8　宣言が変わったときの扱い版と承認の指紋を道具が保持する案である道具は何も足さない。変更の担保は PR が持ち、改名と削除は既存の3系統で出る
論点9　文脈をまたぐ業務7種類目の宣言を立てる案である7種類目を立てない。またがる業務は調整する側の文脈の集約として書き、地図は導出する
論点10　concrete の注入形式注入の形式を Rust の型で書く前提である二段にする。既定は宣言での注入（JSON Schema ・ 雛形 ・ 射影の宣言）で、Rust の注入点も残す。どちらの注入点も、雛形と「読む経路」の申告を要求する
論点11　仕様の取り方と、網羅されたシナリオ仕様を全部読ませ、テストとの結び付きは名前で照合する案である操作は4つ（list ・ refs ・ get ・ validate）とする。道具は、仕様が必要とするシナリオの集合と、テストが記録したシナリオの集合の差を計算するだけである。テストの側の作法は本体が持ち、get の応答で渡す

比較した案

どれも反証を通過しなかった案である ── 未解決のまま残っているものではない。

案採らなかった理由
10本を1件ずつ、10の記録に分ける10本は上から下へ前提が連鎖している。1件ずつに割ると、どの答えがどの答えを前提にしたかが記録の外へ出る
ブレストボードを、そのまま記録とするブレストボードは決着の一覧を保持するが、承認の状態を保持しない。承認が成立したかを、読む側が毎回判定することになる
実装が終了してから記録する適用してから提示すると、承認ではなく追認になる

承認後に実施すること

  • ブレストボードの「次にすること」の最後の1件を、実施済みにする
  • 試作の形を正本へ起こし、基盤と concrete の置き場所と、道具の名前を決める
  • no-more-spaghetti の規則ファイルへ、起こした層を追加する
  • 論点10と11の「まだ弱いところ」（後で決める6件）を、実装の中で測って決める

対象の文書に変更が無い決定である ── 差分は出ない。
