schema 駆動の手引き

はじめて使う人のための手引き ／ 試作段階

仕様に書いたシナリオを、
テストが全部網羅しているかを検査する道具

AI にコードを書かせると、仕様に書いたことと、実際にテストされていることが、いつの間にか食い違う。この道具は、その食い違いを CI で毎回検出する。人が行うのは、AI が書いた仕様を読んで承認することだけである。

試作段階道具の名前はまだ決まっていない。この手引きでは、コマンド名を仮に schema と書く。

この手引きの構成

  1. この道具でできること
  2. 人 ・ AI ・ 道具 ・ CI の分担
  3. 仕様を書いてから CI が止めるまでの流れ
  4. リポジトリに置くファイル
  5. テストの書き方 ── シナリオID を記録する1行
  6. コマンドの一覧
  7. 検出の結果と、直し方
  8. この道具が検査しないこと
  9. 決まっていないこと
  10. 用語

この道具でできること

できることは3つである。どれも、仕様を1か所に置き、そこから外れたものを検出するための機能である。

1 ── 仕様を1か所に置く

業務の決まりを、決まった形のファイル（JSON）へ書く。このファイルが正本で、コードやテストよりも先に在る。形が方法論の決めと合っていなければ、道具が検出する。

2 ── 人が読む形と、AI ツールが読む形を出す

同じ仕様から、人が承認のときに読む HTML と、AI ツールが読む設定ファイル（Claude Code ・ Codex ・ Kiro の形）を出力する。手で転記しない。

3 ── シナリオのテストが在るかを検査する

仕様に書いたシナリオ（期待する振る舞い）の1つ1つについて、それを検査するテストが実際に走ったかを CI で確認する。無ければ CI が停止する。

人 ・ AI ・ 道具 ・ CI の分担

人が行うのは承認だけである。仕様もテストも実装も AI が書き、つながりの検査は道具が、テストの合否は CI が担当する。

担当行うこと行わないこと
人AI が書いた仕様を、HTML で読んで承認する（プルリクエストのレビューで1回）仕様の JSON を直接読む ・ 書く
AI仕様を書く。仕様からシナリオを取得し、テストと実装を書く承認する
道具仕様の形を検査する。射影を出力する。シナリオのテストが在るかを検査するソースコードを読む ・ テストの中身を判定する
CIテストを走らせる。道具を呼び、検出があれば停止させる──

仕様を書いてから CI が止めるまでの流れ

1回の開発は、次の6段で進む。人が関わるのは3段目だけである。

  1. AI仕様を書く

    業務の決まりとシナリオを、仕様のファイルへ書く。書いたら schema validate で形を検査する。

  2. 道具射影を出力する

    射影とは、仕様から道具が出力する別の形のことである。schema emit が、承認用の HTML と、AI ツールが読む設定ファイルを出力する。

  3. 人承認する

    プルリクエストで HTML を読み、シナリオがやりたいことを表しているかを判断する。承認はこの1回だけである。

  4. AIテストと実装を書く

    schema get <ID> で必要な宣言だけを取得し、シナリオごとにテストを書く。テストの中で、どのシナリオを検査するかを1行で記録する（次の次の節）。

  5. CIテストを走らせる

    いつものテストの実行器を、環境変数 SCENARIO_TRACE を付けて走らせる。走ったテストが、記録したシナリオID をファイルへ1行ずつ書き出す。

  6. 道具シナリオのテストが在るかを検査する

    schema covered が、仕様のシナリオと、テストが記録したシナリオを照合する。欠けがあれば終了コード 1 を返し、CI が停止する。

リポジトリに置くファイル

道具が使うファイルは、リポジトリの .<道具名>/ の下にまとめて置く。正本は spec/ だけである。

場所中身誰が書くか版に入れるか
spec/<事業領域>/仕様の本体。宣言を JSON で書くAI入れる
schema/方法論を差し替えるときの定義（宣言の形 ・ 射影の雛形）。既定の方法論を使うなら空のまま利用者入れる
out/承認用の HTML など、道具が毎回出力するもの道具入れない

AI ツールが読む設定ファイルは、それぞれのツールが決めた場所（.claude/ ・ .codex/ ・ .kiro/）へ道具が出力する。手で書き換えない ── 仕様に無い振る舞いが混入する。

テストの書き方 ── シナリオID を記録する1行

テストの中で scenario("シナリオID") を1回呼ぶ。これだけで、道具はそのシナリオのテストが走ったことを把握する。

テストがあるシナリオを検査することを、この手引きでは網羅する（カバーする）と呼ぶ。道具が扱うのは、次の2つの集合だけである。

破線はリポジトリの側、実線は道具の側。道具は2つの集合の差を取るだけで、テストの言語も、テストの実行器も、テストの書き方も扱わない。

記録する1行を入れたテスト（Go の例）

func TestConfirm(t *testing.T) {
	t.Run("明細が0件なら確定できない", func(t *testing.T) {
		scenario("SC-01J7Q4M")   // ← このテストが検査するシナリオを記録する
		o := &Order{Status: "準備中"}
		if o.Confirm() == nil {
			t.Fatal("確定できてしまった")
		}
	})
}

scenario の中身 ── 言語ごとに1つ置く

SCENARIO_TRACE が指すファイルへ、ID を1行追記するだけである。どの言語も標準ライブラリだけで書ける。

言語中身（要点）
Goos.OpenFile(p, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0o644) へ id + "\n"
Pythonopen(os.environ["SCENARIO_TRACE"], "a").write(id + "\n")
TypeScript ／ JavaScriptappendFileSync(process.env.SCENARIO_TRACE, id + "\n")
JavaFiles.writeString(Path.of(p), id + "\n", CREATE, APPEND)
RubyFile.open(ENV["SCENARIO_TRACE"], "a") { |f| f.puts id }
PHPfile_put_contents(getenv("SCENARIO_TRACE"), $id . "\n", FILE_APPEND)
RustOpenOptions::new().append(true).create(true).open(p) へ writeln!

7言語とも、表駆動のテスト ・ 引数付きのテスト ・ 入れ子のテストの中で記録させて、同じ結果になることを確認している（2026-09-27）。

遵守すること

  • 1つのテストで、検査するシナリオを記録する。1つのシナリオを複数のテストで検査してよい（境界値ごとに分けるなど）
  • テストの先頭で記録する。飛ばした（skip した）テストは記録しないので、網羅したことにならない
  • 記録してよいのは、そのテストが実際に検査するシナリオだけである。関係の無い ID を記録すると、道具は「在る」と判定してしまう

コマンドの一覧

コマンドは6つである。名前はすべて仮で、試作では同じ処理が別の名前で動いている。

コマンド行うこと主に使う人
schema validate仕様の形を検査する。方法論が決めた欄が欠けていないか ・ 知らない欄が無いかを検査するAI ・ CI
schema emit仕様から射影（承認用の HTML と、AI ツールが読む設定ファイル）を出力するCI
schema list宣言の索引（ID ・ 名前 ・ 種類）を出力するAI
schema refs <ID>その宣言が参照している ID と、その宣言を参照している ID を出力するAI
schema get <ID> [--as 射影]宣言を1件出力する。射影の名前を渡すと、その形で出力するAI
schema covered <記録> [宣言ID]テストが記録したシナリオと、仕様のシナリオを照合する。宣言ID を渡すと、その宣言のシナリオだけを対象にするCI

AI は list ・ refs ・ get を MCP から呼ぶ。仕様を全部読み込まず、必要な宣言だけを取得する ── 試作の仕様（宣言17件）では、全部を渡すと 2,674 トークン、索引と参照と宣言1件で 697 トークンだった。

CI に書く内容の例

schema validate                                  # 仕様の形
schema emit                                      # 射影の出力
SCENARIO_TRACE=covered.txt go test ./...         # いつものテスト
schema covered covered.txt                       # シナリオのテストが在るか

検出の結果と、直し方

検出はどれも「仕様の外に在るもの」か「仕様に在るのに無いもの」である。直し方は、仕様を直すか、実装側を直すかの2つしかない。

schema covered の出力の例

○ SC-01J7Q4M　明細が0件のとき、確定できない
× SC-01J7Q4N　明細が1件あれば、確定できる　── テストが無い
× SC-01J7Q4X　── 仕様に無いシナリオを記録している
網羅 1/2 ／ 見つかったこと 2 件
出力起きていること直し方
テストが無いそのシナリオを記録するテストが走っていない。書いていない ・ 記録する1行を入れ忘れた ・ テストを飛ばした、のどれかテストを書くか、scenario(...) を入れるか、skip を外す
仕様に無いシナリオを記録しているテストが記録した ID が、仕様に無い。多くは ID の書き間違いID を仕様のものに直す
形の検査に通らない（validate）宣言に、方法論が決めた欄が欠けている ・ 知らない欄がある仕様を直す
宣言していない成果物が在る道具が出力していない設定ファイルが、手で置かれている消すか、仕様へ入れて道具に出力させる

道具の検出は、必ず「無い」の側に帰着する。記録の入れ忘れ ・ skip ・ ID の書き間違いは、どれも「テストが無い」として出る。テストが無いのに「在る」と出るのは、関係の無いテストが実在する ID を記録したときだけである。

この道具が検査しないこと

道具が検査するのはつながりが在るかどうかだけである。次の4つは、道具ではなく別の担当が担当する。

検査しないこと担当するもの
シナリオが、やりたいことを表しているか人（承認）
テストが、そのシナリオを正しく検査しているか（中身が空のテストでも、記録すれば「在る」になる）コーディングの規則と、プルリクエストのレビュー
テストが通るかCI（テストの実行器の終了コード）
実装の品質コーディングの規則

道具がソースコードを読まないのは、言語に依存しないためである。ソースを読むと、言語ごとに解析の仕組みが要り、言語が増えるたびに道具が変わる。

決まっていないこと

この道具は試作段階である。仕組みは試作で動いているが、次の点はまだ決まっていない。

項目いまの状態
道具の名前 ・ コマンドの名前未定。この手引きの schema は仮の名前である
方法論を差し替えるときの書き方（JSON Schema ・ 雛形 ・ 射影の宣言）試作で動作を確認済み。承認待ち
取得のコマンド4つと、シナリオID を記録する方式試作で動作を確認済み（7言語）。承認待ち
MCP の1回の呼び出しに掛かるトークン測定していない
宣言が1,000件を超えるときの索引の絞り込み決めていない

用語

この手引きで使う語は、次の8つである。同じものは、いつも同じ語で呼ぶ。

仕様
業務の決まりを書いたファイルの集まり。spec/ に置き、これが正本である。
宣言
仕様の中の1件。ID を持ち、種類（集約 ・ ユースケースなど）が決まっている。
シナリオ
宣言が持つ、期待する振る舞いの1つ。「明細が0件のとき、確定できない」のように書く。テストと1対1ではなく、1つのシナリオを複数のテストで検査してよい。
シナリオID
シナリオに付いた識別子。SC-01J7Q4M の形をしている。
射影
仕様から道具が出力する、別の形。人が読む HTML と、AI ツールが読む設定ファイルがある。射影は毎回出力し直すもので、手で書き換えない。
承認
人が射影の HTML を読み、シナリオがやりたいことを表しているかを判断すること。プルリクエストのレビューで1回行う。
網羅する
テストが、あるシナリオを検査すること（カバーすること）。テストが走ったときに記録したシナリオを、「網羅したシナリオ」と呼ぶ。
方法論
宣言の種類と、その形を決めたもの。既定はユースケース駆動で、利用者が差し替えてよい。
