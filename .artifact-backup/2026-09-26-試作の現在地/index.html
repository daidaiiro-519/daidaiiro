  1. 受注で、宣言3件とシナリオ4件を書く

    書いたとおりには通らなかった。道具が3つ検出した ── 業務サービスに書き換えを持たせた／業務領域にユースケースが1件も無い／操作を関門へ登録していない。

    在庫引当は業務サービスではなく、集約だった。 論点9 の判定（状態を持つものは集約）を、道具が独立に指した。

  2. またがる業務と、文脈の関係を書く

    確定の進行（集約）を調整する側へ置き、受注の文脈へ上流を2件宣言した。 関係の引き算を道具へ足した ── 宣言していない文脈を挙げると出る。

  3. 期待の書き方を決める

    fails と check の1組では足りなかった。 1つのシナリオが2つのことを言う（確定しない／引当を戻す）。 しかも期待を除外しても実体の無い検査を書いても、49件すべてが通った ── 誰も見ていなかった。

    いまの形（1つの成否 ＋ 確認する点の列）

            ── 失敗する（check.precondition ・ check.allocationReturned）

    形の検査は注入する側が持つ ── 基盤は節の中身を見ない（論点2）。

  4. テストの一覧の形と、フックの契機を決める

    実行系の生の出力を渡すと「結ばれていない識別子」が6件出て、CI が失敗した。 Rust の --list は関数名だけを出し、crate の道を出さない。

    測ったもの結果

    一覧は1行1識別子のテキスト（空行と # を無視）。 契機は保存時で成り立つ ── 500宣言でも14ms である。

  5. 埋められないキーの扱いを決める

    Codex の model は、宣言のどこにも無い値を要求する（原文で照合した）。 宣言へ足すと方法論の語彙へ AI ツールの語が入る ── 論点2 に違反する。

    表に無いキーを変換機が直に書くと、検査で出る
出どころの分からないキー： {"approval_policy"}

    既定値は注入する側が表で持ち、何を充填したかを毎回申告する。

いま困っていること

道具の外側である
  • 止まる

    呼び出し口が1つも無い

    論点1 は MCP ・ CLI ・ フックの3つを決めたが、実装は0である。 いま動かせるのは cargo run だけで、他所のリポジトリから呼べない。仕様はもうバイナリの外に在るので、残るのは口だけである。

  • 止まる

    対応表が Rust のコードに直書きである

    契約3本のうち1本（対応表）が、bindings() という関数の中に在る。 AI が MCP で申告して、道具が書く形になっていない。

  • 片付いた

    仕様の焼き込みは、外した

    include_str! をやめ、基盤が仕様の木を根から読むようにした （read_spec_tree）。走査する場所は根1つだけで、JSON だけを読む。 置き場所の契約が、手で打った文字列ではなく実在の木に当たるようになった ── 根の外へ事業領域を置いた木で、2行出ることを確かめた。

  • 未決

    承認の画面の形が決まっていない

    HTML の文字列は出るが、PR のレビューへどう出すかは未定である（論点8 の保留）。 人が押せる形にはなっていない。

  • 設計どおり

    意味は、機械に見えない

    テストの中身がシナリオと違っていても、名前が一致すれば通る（論点5 の保留）。 AI が担保し、人が承認のときに判定すると決めてある ── 道具の穴ではない。
