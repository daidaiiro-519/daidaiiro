検証の Rust の組み立ての出力先を、1か所で共有する

決めたこと

提供者の検証（verify）は、Rust の組み立ての出力を、生成した Skill ごとではなく1か所の共有の出力先へ集める。

なぜ決める必要があるか

verify は1回の実行で約 2.5G を使用していた（実測 2026-10-01）。内訳のほぼ全部は、Rust の2つの型（work ・ advisor）の tool/target/ である。同じ依存（jsonschema ・ rmcp ・ tokio など）を、型ごとに release と debug の2回コンパイルしていた。作業場所は実行ごとに run-<番号> を新しく作るので、容量は実行の回数に比例して増加し、/tmp（tmpfs 7.7G）に置いた試験では容量が不足した。利用者から「2.5ギガも何に使うの？」と問われ、無駄が多いなら直すよう指示された。

どう変わるか

変更前と変更後

何が変更前変更後
Rust の組み立ての出力先生成した Skill ごとの tool/target/（1回の実行ごとに約 2.5G が増加する）skills-creator の tool/target/verify-cargo の1か所（1.4G で、2回目以降は増加しない）
1回の実行の作業場所約 2.5G222M（5言語 × 2型）
利用者の手順scaffold が案内する組み立てのコマンド変化しない。検証が起動するときだけ --target-dir の値を置換する

比較した案と、採らなかった理由

案採らなかった理由
データアクセス層の process::run に、環境変数を渡す引数を追加するprocess.rs は10の Skill が同一の内容で複製して保持するファイルである。検証だけのために10か所の複製を変更することになる
Rust の言語の組の組み立てのコマンドから --target-dir を削除する利用者の手順が変化する。tool/target/ に出力を集める現在の配置（.gitignore が除外する場所）が成立しなくなる
実行が終了するたびに、生成した Skill の tool/target/ を削除する容量は減少するが、その都度すべての依存をコンパイルし直すので時間は短縮しない。共有すれば2回目以降の実行は依存をコンパイルしない（Rust だけの実行で 40秒 → 18秒）

下に並ぶのは、この決定を採ったときに何がどう変わるかである ── 上の決定の具体である。
