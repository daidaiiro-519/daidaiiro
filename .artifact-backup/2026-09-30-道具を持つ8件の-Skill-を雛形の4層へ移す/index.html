道具を持つ8件の Skill を雛形の4層へ移す

決めたこと

道具を持つ8件の Skill を、skills-creator の雛形の4層の構成へ移し、その構成を規則で保つ。

なぜ決める必要があるか

ACDR 0058 で雛形を4層（入出力をデータアクセス層だけが持つ）にしたが、構成は契約ではない（ACDR 0059）ので、既存の Skill は移していなかった。8件は、業務ロジック層とサービス層が入出力を直接扱い、雛形の構成の検査で合計232件を検出していた。利用者の指示で、advisor 以外の道具を持つ Skill をこの構成へ移した。移すときは判定を書き換えず、入出力の呼び出しをデータアクセス層へ移すことに徹した。8件とも事例の件数を減らさずに合格し、組み直す前と後の実行ファイルで出力を比べて一致を確かめた。8件は acdr ・ brainstorming-board ・ design-svg ・ doc-writing-skills である。残りは fact-check ・ narration ・ no-more-spaghetti ・ slide-deck である。雛形の process::run へ起動を移した Skill は、制限時間を元の値か十分な値にした。narration の合成は300秒、slide-deck は300秒、acdr の git は60秒、fact-check の curl は90秒である。no-more-spaghetti だけは、道具の出力の扱いを保つために固有の起動（logfile）を残した。

どう変わるか

変更前と変更後

何が変更前変更後
8件の道具の層業務ロジック層 ・ サービス層 ・ プレゼンテーション層の3層（入出力は各層に散在）データアクセス層を足した4層（入出力はデータアクセス層だけ）
雛形の構成の検査（check --layout 1）8件で合計232件を検出8件とも0件
雛形の構成の規則skills-creator だけskills-creator と8件
acdr の references の実装（refs.rs）雛形と違う雛形と一致
design-svg の cli ・ mcp の crate の名前bb_cli ・ bb_mcp（別の Skill の接頭辞）ds_cli ・ ds_mcp

比較した案と、採らなかった理由

案採らなかった理由
8件を3層のまま残す（構成は契約ではないので、移さなくても check は合格する）利用者の指示である。入出力が各層に散っていると、Skill ごとに読み方が違い、1つを読んで得た理解が次の Skill で通用しない
no-more-spaghetti の起動も雛形の process::run へ移すprocess::run は標準出力と標準エラーを分けて最大16MB ずつメモリに受け取る。規則の道具の出力を出た順のまま1本のファイルへ書く振る舞いと、道具が見つからないことの判定が保てない
データアクセス層の files と process に、各 Skill が要る関数（通信 ・ 標準入力 ・ フォルダの複製など）を足すfiles と process は雛形の複製で、Skill をまたいで同一に保つ。Skill に固有の入出力は別の module に置く（雛形の lib.rs の注記どおり）
advisor の5件も同時に移すadvisor は別のセッションが作り直している途中で、道具も助言型の雛形へ揃えている（usecase-advisor は ACDR 0068 で4層へ移した）
