道具の入出力をデータアクセス層へ集める

決めたこと

道具のファイル ・ 外部の道具 ・ 通信の入出力を、データアクセス層だけに持たせる。道具の層は、サービス層を挟んだレイヤードアーキテクチャの4層（プレゼンテーション層 ・ サービス層 ・ 業務ロジック層 ・ データアクセス層）とする。

なぜ決める必要があるか

0056 で道具の層をレイヤードアーキテクチャの正式名で呼ぶと決めた。しかし、判断基準のレイヤードが持つデータアクセス層が無く、業務ロジック層がファイルと外部の道具を直接扱っていた（14件で、ファイル操作 約200か所 ・ 外部の道具 10か所 ・ 通信 5か所）。全 Skill 共通の references の実装も同じである。利用者から「今後データを扱うのが増えた時に辛い」と指摘された。雛形がこの形のまま複製され続けると、データを処理する Skill が増えるほど、後で分ける量が増える。いま決めるのは、6つの言語の組の雛形をこれから起こすからである。3つの形を ddd-advisor の判断基準と原典で比べた（下の比較した案）。道具の処理は手続き的な変換であり、判断基準はこれにレイヤードを対応づける。あわせて、SKILL.md が存在しないファイル（placeholder-definitions.md）を参照し、Step 4 と矛盾していた点と、汎用の Skill に固有名 Waffle が残っていた点を直す。

比較した案と、採らなかった理由

案採らなかった理由
ヘキサゴナル（コアがポートを定義し、アダプタが実装する）判断基準は、ポートとアダプターをドメインモデル（集約と不変条件を持つ業務）向けとしている。道具にはその前提が無く、入出力の種類ごとに trait と注入が増える。ドメインモデルを必要とする Skill が現れたら、その Skill だけを移せばよい（判断基準は業務領域ごとに方式を混ぜてよいとする）
関数型コア＋命令型シェル（サービス層が入出力を行い、業務ロジック層は純粋な関数だけにする）「読んだ内容で次に読むものが決まる」処理（references の参照の解決、外部の道具の結果による分岐）で、シェルとコアの往復が増える。Bernhardt 自身も「If this became more complex, then I would become afraid」（FCIS 字幕:933）と限定している
データアクセス層を分けず、契約に「分けない」と明記するデータを処理する Skill が増えるたびに、業務ロジックが保存先の都合を知る。雛形の references の実装が入出力を持つので、複製するたびに分ける対象が増える
入出力の禁止を業務ロジック層だけに当てるサービス層が雛形のファイルを直接読んでいた。サービス層の入出力を許すと、データアクセス層を飛ばす経路が残る

道具の契約：tool-contract

目的

Skill が道具（実行ファイル）を伴うとき、呼ぶ側に形を推測させないために使用する。

道具ごとに呼び出し方の形が違うと、呼ぶ側は呼ぶたびに本文を読み直す。
契約は、呼び方を1つに固定する。

契約は、呼ぶ側から観察できるものだけを規定する（ACDR 0036）。道具を書く言語と、
配布するかどうかは、利用者に委ねる。言語ごとの実装の形は言語の組が持ち
（いまは references/profiles/rust.md だけ）、配布は任意の機能として
references/distribution.md が持つ。

置く先中身
契約（この文書）CLI と MCP の2つのプレゼンテーション層と起動のコマンド ・ CLI の規約 ・ 1つの道具の一覧から CLI と MCP を組む ・ MCP の規約 ・ Skill のフォルダの求め方 ・ 外部の道具 ・ 層と依存の向き ・ 1段目の検査
言語の組実行ファイルの置き場所 ・ ソースの構成 ・ 雛形 ・ 組み立てのコマンド ・ 2段目の検査
配布（任意）配布物 ・ 導入スクリプト ・ 組み立ての定義

言語の組を作ってよい言語の条件は、公式の MCP の SDK が在ることだけである。
組が持つのは、雛形 ・ 組み立てのコマンド ・ ソースの検査の3つである。

原則

能力は1つ、呼び出し方は複数である。

能力をサービス層の道具の一覧に1度だけ書き、CLI と MCP はその一覧から組む。
能力を2か所に書くと、片方だけが古くなる。

呼び出し方が欠けても、能力は欠けない。
MCP の実装が無い環境では、MCP サーバーは立たず、CLI だけが動く。

標準入出力の規約 ── 原典

modelcontextprotocol.io/specification/2025-06-18/basic/transports（2026-09-24 取得 ・ 297行）から引用する。

行原文
27The server reads JSON-RPC messages from its standard input (stdin) and sends messages to its standard output (stdout).
31The server MAY write UTF-8 strings to its standard error (stderr) for logging purposes.
33The server MUST NOT write anything to its stdout that is not a valid MCP message.

だから、道具の中で標準出力へ書くと MCP サーバーが壊れる ── 子プロセスの標準出力も同じである（パイプかファイルで受ける）。

誤りの返し方 ── 原典

原典は2つを分けている（specification/2025-06-18/server/tools:389、2026-09-24 取得）。

種類原文この契約での対応
Protocol ErrorsStandard JSON-RPC errors for issues like: Unknown tools, Invalid arguments引数の不足 ・ 知らない動詞。SDK が返す
Tool Execution ErrorsReported in tool results with isError: trueok が偽のとき（読めない ・ 誤用）

findings は誤りではない。 検出が在っても isError は偽のままにする ── 違反の検出は、道具が正しく動作した結果である。

予期した失敗は、道具の結果として返す。 ok が偽なら CallToolResult の is_error を立て、こちらの文言を content に載せる ── 異常終了（panic）させると、呼ぶ側には理由が届かない。言語の組の雛形がこの形を持つ。

型は緩く受ける。 呼ぶ側は JSON の値を渡すので、数を文字列で包むことを強制しない（実測: timeout に 30 を渡すと、検証が不合格になっていた）。まとめて受ける引数は配列も受ける。

層と依存の向き

道具のソースは、サービス層を挟んだレイヤードアーキテクチャで組む。 層は4つである。
依存は上から下へだけ向け、層を飛ばさない。

層置くもの依存してよい先入出力
プレゼンテーション層（CLI ・ MCP）呼び出し方。引数を受け、結果を印字し、終了コードを返すサービス層標準入出力と引数だけ
サービス層道具の一覧（名前 ・ 引数 ・ 説明）と、業務ロジック層の関数との対応。外部の道具を tool.json から読み、業務ロジック層へ渡す業務ロジック層持たない（例外は契約の実体 contract.rs が読む起動の設定だけ）
業務ロジック層判定と変換 ── 組み立て ・ 描画 ・ トークン ・ 検査などデータアクセス層持たない
データアクセス層ファイル ・ 外部の道具 ・ 通信の入出力無しここだけが持つ

サービス層を置くのは、プレゼンテーション層が2つ在るからである。 CLI と MCP の違いから業務ロジックを隔離し、道具の一覧を1か所に保つ。

データアクセス層を置くのは、入出力を1か所に集めるためである（ACDR 0058）。業務ロジック層は、読んだ値を受けて判定するだけになる ── データを処理する Skill が増えても、変わるのはデータアクセス層だけである。データアクセス層に判定を置かない ── 何を読み、読んだものをどう扱うかは業務ロジック層が決める。子プロセスの規律（上の節）は、データアクセス層が1回だけ実装する。

業務ロジック層に、集約 ・ エンティティ ・ リポジトリの型を作らない。 この層が置くのは、業務の状態を保持しない変換の関数である ── 層の名前から連想してドメインモデルの型を導入すると、使わない抽象が増える。

この構成を、ヘキサゴナルアーキテクチャともクリーンアーキテクチャとも称さない。 両者の核心は依存の向きを逆にすること（内側が抽象を定義し、外側が実装する）であり、この構成はそれを保持しない ── 業務ロジック層がデータアクセス層を直接呼ぶ。称すると、備えていない性質を名前で主張することになる。

ポートを導入するのは、業務ロジック層が使う外部を差し替える必要が生じたときに限る。 それまでは、実装が1つしかない抽象を作らない。ドメインモデルを必要とする Skill が現れたら、その Skill の道具だけをポートとアダプターへ移す ── 方式は Skill ごとに選んでよい。

どう守らせるかは、言語の組が決める（Rust は crate の境界に置き、各 Cargo.toml が依存の向きを宣言する。入出力の混入は2段目の検査が検出する）。

生成物を持つ Skill は、3つで組む

入力の契約 ・ 出力の型 ・ 組み立ての3つに分ける。 どれか1つに形が混ざると、
同じ Skill が出す成果物どうしで形が違ってくる（実際に、節の1つだけ別の入れ物で組まれていた）。

何を持つか置き場所
入力の契約何を書けるか。JSON Schemareferences/<名前>.schema.json
出力の型どう並ぶか。差し込む場所（{{名前}}）を持つreferences/<名前>.template.html
組み立て値を差し込むだけ。構造を作る文字列を保持しない業務ロジック層（型のファイルの読み込みはデータアクセス層が実行する）
JSON Schema  →  実体の JSON（値を埋める）  →  型（HTML）へ差し込む  →  生成物

差し込む場所の過不足は、その場で例外にする ── 埋め忘れも、余分な値も、出てから気づく形にしない。
型を読んで部品を組むのは、業務ロジック層の組み立てである。

検証で、組み立て側に構造を作る文字列が残っていないことを検査する ── 規定だけでは戻る。

ガードレール

- 節の構成を、対応する雛形と一致させる。助言の Skill は advisor-creator の雛形、それ以外は
こちらの雛形を満たす ── どちらを適用するかは節の有無で決まる（名前で分岐すると、Skill が
増えるたびに検査を直すことになる）
- 道具を持つ Skill には、道具の契約を適用させる（references/tool-contract.md）── 呼び出し方の形が道具ごとに違うと、呼ぶ側は呼ぶたびに本文を読み直すことになる
- 同じ概念の仕組みは、同じ実装の形にさせる。入力の契約（スキーマ）・トークンの正本・入力の検査・置き場所を、Skill ごとに違う形で実装させない ── 概念が同じで形が違うと、1つを読んで得た理解が、次の Skill で通用しない
- 能力を2か所へ記述させない。CLI と MCP は、サービス層の道具の一覧から組ませる ── 同じ能力を2度書くと、片方だけが古くなる
- 業務ロジック層の関数に呼び出し方を付けさせない。業務ロジック層の関数は道具の一覧に載せない ── 載せると、同じ能力に呼び方が2つできる
- 道具の層を、サービス層を挟んだレイヤードアーキテクチャの4層にさせる（プレゼンテーション層 ・ サービス層 ・ 業務ロジック層 ・ データアクセス層）。依存は上から下へだけ向け、層を飛ばさせない ── 飛ばすと、道具の一覧を経ない呼び出し方ができる。業務ロジック層に集約 ・ エンティティ ・ リポジトリの型を作らせない
- 入出力をデータアクセス層だけに持たせる。業務ロジック層とサービス層に、ファイル ・ 外部の道具 ・ 通信を直接扱わせない ── 入出力が散らばると、データを処理する Skill が増えたときに、変更が業務ロジックまで及ぶ
- 道具に印字させない。戻り値は {ok, findings, data} とし、印字と終了コードはプレゼンテーション層が持つ ── 道具が印字すると、MCP から呼んだときに戻り値が空になる
- ガードレールと手順を、不変条件で記述させる。1回の出来事・特定の語・特定の形を規則にしない ── 規則が事例の形を取ると、その形だけが規制され、他の形は通過する。規則が禁じるのは性質であって、その性質が現れた1つの形ではない
- 例を規則本体へ混ぜさせない。例を添えるなら「例」と明示し、規則の文とは分離する ── 混ざると、読み手は例の範囲を規則の範囲として解釈する
- SKILL.md は必ずスキルフォルダのルートに置く。サブフォルダには置かない
- テンプレートファイルは assets/ ではなく references/ に置く
- 不要なフォルダは作らない。使うものだけ作る
- プレースホルダーは、references/skill-template.md の各 {{…}} に書かれた指示に従って記入する。指示を読まずに推測で記入しない
- スキル名は英小文字・ハイフン区切りに統一する（スペース・アンダースコア不可）
- ユーザーが要件を明確にしていない場合は作成を開始しない。必ずヒアリングを先に完了させる
- 新しいSkillに、特定の外部ツール・システム（特定の CLI ・ MCP など）の存在を自ら判定して振る舞いを変えるロジックを持たせない。汎用のSkillが具体的な実装の有無を参照するのは依存性の方向違反であり、正しい向きは「具体的なシステムの側が汎用Skillを自分の中に注入・統合する」（composition-rootの原則）。特定システムとの統合が必要な場合は、そのSkill自体は単一の環境非依存な実装のままにし、統合はSkillの外側（呼び出し側・Orchestrator側）に置く設計を選ぶ
