Windows で基盤の Skill のスキーマを名前で引けるようにする

決めたこと

基盤は、Windows でも --skill の Skill のスキーマを名前で引いて検査できるようにし、版 0.1.1 として公開し直す。skills-creator は 0.1.1 のエンジンを入れる。

なぜ決める必要があるか

skills-creator の公開のワークフロー（run 38898991107）で、Windows の verify だけが落ちた。skills-creator の check は、SKILL.md の型を判定させるために基盤のエンジンを --skill 付きで呼ぶ。基盤は、スキーマのファイル名を経路の / だけで区切って取っていたので、Windows では file:///schemas/assets\skill.schema.json という不正な URI を作り、「スキーマが壊れている」で止まった。同じ書き方が core の5か所にあった。基盤の公開の確かめは --skill の道を通っていなかったので、0.1.0 の公開では見つからなかった。

どう変わるか

変更前と変更後

何が変更前変更後
スキーマのファイル名の取り方経路を / だけで区切る（core の5か所）/ と \ の両方で区切る関数（domain/path.rs）を1つ置き、5か所がそれを使う
基盤の公開の確かめ（xtask verify）--skill の道を通らない作業用の Skill のフォルダにスキーマを置き、--skill でスキーマを名前で引いてインスタンスを検査する。3つの OS で通す
基盤の版0.1.00.1.1（不具合の修正）
skills-creator が入れるエンジンの版0.1.00.1.1

比較した案と、採らなかった理由

案採らなかった理由
skills-creator の側で、--skill に渡す経路の区切りを / に直してから呼ぶ基盤の不具合を上の Skill が回り込むことになる。ほかの上の Skill も同じ回り込みを書くことになる
経路を Path で扱うように core を書き直すcore はファイルに触らず、経路を文字列として受け取る。ファイル名を取るだけなので、区切りを2つ見る関数で足りる
版を 0.1.0 のまま直す公開した版は配布物を変えられない。0.1.0 の配布物は Windows で壊れたまま残る
