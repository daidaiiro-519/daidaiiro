文脈の根とモジュールのポートを直す

決めたこと

抽象概念の土台が示す文脈の中の形を、リポジトリの根の直下の文脈のフォルダの中で、各モジュールが自分のユースケースが使うポートを宣言する形にする。

なぜ決める必要があるか

土台は、文脈の根を「文脈が1つならリポジトリの根」とし、ポートを「その会話を受け持つ業務領域の application が持つ」としていた。Semantic Agent Schema の版30（コミット 32268b31）で、この決まりに従って作った形を直した。検索はポートを持たずに検証のユースケースの中身を借り、記録のポートは DB の表の側から作った1つの trait を全モジュールが借り、誰が呼んだかを各ユースケースが調べていた。土台の文を、直したあとの CODING.md ・ architecture.json と、概念のページのアーキテクチャのタブ（TREE ・ RULES_ANY）に合わせる。0216 の直し（core/ をやめる ・ 型4 を書く）は、この記録へ引き継ぐ。

どう変わるか

変更前と変更後

何が変更前変更後
文脈の根文脈が1つならリポジトリの根、複数なら contexts/<文脈>/。リポジトリの根の直下の、文脈の名前のフォルダ。リポジトリの根は製品の置き場で、文脈の根にしない。
文脈の中のフォルダcore/<業務領域>/{domain, application} と、外側の inbound ・ outbound。業務領域を作るモジュールごとの <モジュール>/{domain, application} と adapters/{inbound, outbound}。domain の無いモジュールもある。
ポートを宣言するものその会話を受け持つ業務領域の application。それを使うユースケースを持つモジュールの application。ユースケースから見つけ、使うメソッドだけで宣言する。
モジュールの間の依存決まりが無い。application どうしは依存しない。複数のモジュールが使う判断と値は domain に置く。
外からの入力決まりが無い。入口のアダプターが読み取り、値でユースケースに渡す。
業務ロジックの置き場所決まりが無い。上から決めて下から確かめる。
文脈の引き方業務領域を単位に引く。業務領域を手がかりに引く。1つの業務領域を複数の文脈で扱うこともある。

比較した案と、採らなかった理由

案採らなかった理由
0216 のまま適用する（core/ をやめて業務領域のフォルダと adapters/ にし、ポートはそれを使うユースケースのモジュールに置く）。文脈の根がリポジトリの根のままで、モジュールの application の間の依存と外からの入力の扱いを決めていないので、版30 で直した借り方を防げない。
文脈が1つのときは、リポジトリの根を文脈の根にしたままにする。製品全体のもの（ビルドの設定 ・ 設計の文書）と文脈の中身が同じ所に並び、製品と文脈を同じものとして扱う。文脈が増えたときに置き場所が変わる。
同じ形のポートを、共有の置き場に1つだけ置く。どのモジュールも使わないメソッドにまで依存し、ポートを置いたモジュールの application への依存が残る。版30 の記録のポートがこの形だった。
誰が呼んだかを、ユースケースの中で決める。外からの入力を読むのは入口のアダプターの責務で、ユースケースごとに同じ調べ方が重なる。版30 の前の形がこれだった。
Semantic Agent Schema のモジュールの名前と crate の分け方も、土台に書く。土台はどの事業にも使う概念だけを持つ（ACDR 0215）。具体は docs/design/ が持つ。
