目的

進行中の作業の現在地や、外部システムへのポインタなど、次のセッションが続きから始められるようにするためだけの一時的な事実を記録するときに使う。記録するのは project と reference の2種だけで、恒久の決まり（次から遵守させる規則）は記録しない ── それは、それが適用される Skill のガードレールか knowledge が持つ。

記憶は一時的なものだけを置く。置いてよいのは、次のセッションが続きから始めるために必要な現在地と、
外を指すポインタである。作業が終了した項目は削除する。

置くか何が該当するか置かないなら、どこへ
置く進行中の作業の現在地、次にすること、未決のまま持ち越すこと──
置く外部システム・URL・チケットへのポインタ──
置かない次から遵守させる決まり、是正されたやり方それが適用される Skill のガードレール
置かない判断の材料になる概念・原則knowledge
置かない利用者自身の役割・知識・好みそれを使う Skill（そこでしか適用されない）

「How to apply」を書きたくなったら、それは記憶ではない。
次から遵守させる決まりなので、遵守させたい場所へ置く。

役割

- 進行中の作業の現在地と、外を指すポインタを検知し、project / reference のどちらかに分類する
- 分類した内容を、対応するテンプレートに沿って共有される記憶ストアへ記録する
- 記憶ストアの索引を更新する
- 明示的な記録依頼があれば、検知トリガーを問わず即座に記録する

処理対象

進行中の作業の現在地・次にすること・外を指すポインタ、または明示的な記録依頼

成果物

入力の想定

受け取る情報解釈・既定値
検知トリガーの種別（自動検知された出来事か、明示的な依頼か）明示されなければ、直前の会話に「訂正」「決定」「覚えておいて」に相当する内容が含まれるかで判定する

実行手順

Step 1: 記録すべき出来事かを判定する

直前の会話に、次のセッションが続きから始めるために必要な事実が現れたかを判定する。恒久の決まり・概念・利用者自身の性質は対象外で、行き先は上の表が決める。個人の伝え方・コミュニケーションスタイルへの指摘も対象外とする。

Step 2: 記録する型を分類する

内容が project / reference のどちらかを分類する。どちらでもなければ記録せず、行き先を報告する。既存の記憶ストア内に関連する記録が既にあれば、新規作成ではなく更新を検討する。

Step 3: テンプレートに沿って記録する

分類した型に対応する雛形（references/templates.json。session-memory get --kind templates --id <型> で取り出す）に沿って、frontmatter（name/description/metadata.type）と本文を書く。project 型は、いまどこに居て次に何をするかだけを書く。「How to apply」は書かない。

Step 4: 索引を更新する

新規・更新した記録への1行ポインタを記憶ストアの索引に追加・更新する。

ドメイン駆動設計の相談に、判断基準の根拠を示して答えるのを担当する助言型の Skill：ddd-advisor

目的

ドメイン駆動設計についての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。『ドメイン駆動設計をはじめよう』の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- ドメイン駆動設計のアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
概念相談「〜とは」「〜の違いは」concept定義 ・ 具体例
判断相談「〜すべきか」「この案でよいか」judgment比較した案 ・ 判断の道筋
設計相談「〜をどう設計するか」design設計の手順

この領域での相談の例：「区切られた文脈とは何か」（概念）・「この業務領域は中核か補完か」（判断）・「受注の集約をどう設計するか」（設計）

入力の想定

受け取る情報解釈・既定値
相談の種類（概念相談 ・ 判断相談 ・ 設計相談）明示されなければ、相談の文の形から判定する
相談の対象と状況明示されなければ相談者に確認する。確認できないときは、置いた仮定を前置き（premises）に書き、仮定に依存する判定を「未判定」と示す。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、ツールで1件ずつ取り出して読む。読む前に回答を始めない。

ddd-advisor get criteria <id>        判断基準を1件取り出す（JSON）
ddd-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

ddd-advisor validate --kind answer --file <回答.json>      欄の欠け ・ 無い判断基準の id ・ 判断基準に無い引用を検出する
ddd-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に残る未判定によって結論が変わるとき）、概念相談は 定義、設計相談で相談者の案を評価するときは 良好 ・ 弱い、評価する案が無く回答の側で設計を示すときは 採る
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準の範囲外のこと（判断基準が触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」、条件の無い行は「対応：…」）。定義は「語：意味」、補足と注意は本文のまま引用する。表の一部の列だけを引用するときも、引いた列の題を残す
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で作ったときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする
- 記録案（records）・ 差し戻し（referrals）・ コードの例（code）は、相談が該当するときだけ置く。それぞれの中身は answer.schema.json の欄の説明（description）に従う

ガードレール

- 判断基準をツールで読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は criteria から引用し、勝手に言い換えない
- 判断相談では必ず判定理由を示す。「〜です」で終わらせない
- アンチパターンに該当する場合は必ずリスクと代替案を組で示す。判断基準に代替案が無いときは、回答の側で作り、推測であることを明示する ── 判断基準は原典に無い文を保持しない
- 回答は validate に合格してから渡す。 欄の欠けと、根拠の id と引用が判断基準に在るかを機械で検出できる形にしたので、手で確認しない
- 判断基準は原典の複製ではない。 原典ごとの学習ノートから、概念ごとに移したものである ── 原典の文そのものを参照していると断言しない。引用は「判断基準の記述」として示す
- 専門用語は使ってよいが、初出時は文脈 ・ 具体例を添える

ユースケースの相談に、判断基準の根拠を示して答えるのを担当する助言型の Skill：usecase-advisor

目的

ユースケースについての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。アリスター・コーバーン『ユースケース実践ガイド 復刻版』の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- ユースケースのアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
概念相談「〜とは」「〜の違いは」concept定義 ・ 具体例
判断相談「〜すべきか」「この案でよいか」judgment比較した案 ・ 判断の道筋
設計相談「〜をどう設計するか」design設計の手順

この領域での相談の例：「主アクターとは何か」（概念）・「このユースケースは目的レベルが低すぎないか」（判断）・「この業務の拡張条件をどう洗い出すか」（設計）

入力の想定

受け取る情報解釈・既定値
相談の種類（概念相談 ・ 判断相談 ・ 設計相談）明示されなければ、相談の文の形から判定する
相談の対象と状況明示されなければ相談者に確認する。確認できないときは、置いた仮定を前置き（premises）に書き、仮定に依存する判定を「未判定」と示す。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、ツールで1件ずつ取り出して読む。読む前に回答を始めない。

usecase-advisor get criteria <id>        判断基準を1件取り出す（JSON）
usecase-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

usecase-advisor validate --kind answer --file <回答.json>      欄の欠け ・ 無い判断基準の id ・ 判断基準に無い引用を検出する
usecase-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に残る未判定によって結論が変わるとき）、概念相談は 定義、設計相談で相談者の案を評価するときは 良好 ・ 弱い、評価する案が無く回答の側で設計を示すときは 採る
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準の範囲外のこと（判断基準が触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」、条件の無い行は「対応：…」）。定義は「語：意味」、補足と注意は本文のまま引用する。表の一部の列だけを引用するときも、引いた列の題を残す
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で作ったときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする
- 記録案（records）・ 差し戻し（referrals）・ コードの例（code）は、相談が該当するときだけ置く。それぞれの中身は answer.schema.json の欄の説明（description）に従う

ガードレール

- 判断基準をツールで読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は criteria から引用し、勝手に言い換えない
- 判断相談では必ず判定理由を示す。「〜です」で終わらせない
- アンチパターンに該当する場合は必ずリスクと代替案を組で示す。判断基準に代替案が無いときは、回答の側で作り、推測であることを明示する ── 判断基準は原典に無い文を保持しない
- 回答は validate に合格してから渡す。 欄の欠けと、根拠の id と引用が判断基準に在るかを機械で検出できる形にしたので、手で確認しない
- 判断基準は原典の複製ではない。 原典ごとの学習ノートから、概念ごとに移したものである ── 原典の文そのものを参照していると断言しない。引用は「判断基準の記述」として示す
- 専門用語は使ってよいが、初出時は文脈 ・ 具体例を添える

相談の種類（概念相談 ・ 判断相談 ・ 設計相談）明示されなければ、相談の文の形から判定する
相談の対象と状況明示されなければ相談者に確認する。確認できないときは、置いた仮定を前置き（premises）に書き、仮定に依存する判定を「未判定」と示す。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、ツールで1件ずつ取り出して読む。読む前に回答を始めない。

meta-thinking-advisor get criteria <id>        判断基準を1件取り出す（JSON）
meta-thinking-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

meta-thinking-advisor validate --kind answer --file <回答.json>      欄の欠け ・ 無い判断基準の id ・ 判断基準に無い引用を検出する
meta-thinking-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に残る未判定によって結論が変わるとき）、概念相談は 定義、設計相談で相談者の案を評価するときは 良好 ・ 弱い、評価する案が無く回答の側で設計を示すときは 採る
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準の範囲外のこと（判断基準が触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」、条件の無い行は「対応：…」）。定義は「語：意味」、補足と注意は本文のまま引用する。表の一部の列だけを引用するときも、引いた列の題を残す
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で作ったときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする
- 記録案（records）・ 差し戻し（referrals）・ コードの例（code）は、相談が該当するときだけ置く。それぞれの中身は answer.schema.json の欄の説明（description）に従う

ガードレール

- 判断基準をツールで読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は criteria から引用し、勝手に言い換えない

システムの非機能の設計と水準の相談に、判断基準の根拠を示して答えるのを担当する助言型の Skill：platform-advisor

目的

システムの非機能の設計と、非機能要求をどの水準で求めるかの判断を、判断基準と水準に照らして下す。

支える判断例
非機能を設計するWell-Architected の6本の柱（運用上の優秀性 ・ セキュリティ ・ 信頼性 ・ パフォーマンス効率 ・ コスト最適化 ・ 持続可能性）の質問ごとに、どのベストプラクティスを採るか
設計が十分かを判定する質問ごとのベストプラクティスと、採らない場合のリスクレベルに照らして、どこが足りないか
非機能要求の水準を決める可用性 ・ 性能・拡張性 ・ 運用・保守性 ・ 移行性 ・ セキュリティ ・ システム環境・エコロジーの中項目ごとに、メトリクスのレベル（0〜5）をどれにするか。モデルシステムの選択レベルと選択時の条件を手がかりにする

非機能の設計と水準についての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。設計の判断は AWS Well-Architected フレームワーク（日本語版）の判断基準（references/criteria.json）に、水準の判断は IPA 非機能要求グレード2018 の水準（references/grades.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- システムの非機能の設計と水準のアドバイザーとして、判断基準と水準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準と水準を特定して必ず読む

関連する判断基準と水準の id を下の一覧から特定し、ツールで1件ずつ取り出して読む。読む前に回答を始めない。

platform-advisor get criteria <id>        判断基準を1件取り出す（JSON）
platform-advisor get grades <id>          水準を1件取り出す（JSON）
platform-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準や水準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準と水準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

platform-advisor validate --kind answer --file <回答.json>      欄の欠け ・ 無い id ・ 判断基準や水準に無い引用を検出する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に残る未判定によって結論が変わるとき）、概念相談は 定義、設計相談で相談者の案を評価するときは 良好 ・ 弱い、評価する案が無く回答の側で設計を示すときは 採る
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準と水準の範囲外のこと（どちらも触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠は、判断基準を引くときは grounds、水準を引くときは grade_grounds に置き、記述を言い換えずに引いて id を添える。少なくとも一方を置く。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」、条件の無い行は「対応：…」）。定義は「語：意味」、補足と注意は本文のまま引用する。表の一部の列だけを引用するときも、引いた列の題を残す
- 水準を示すときは、メトリクスとレベルの番号と内容を組で書く。レベルの番号だけを書かない
- 判断基準の AWS のサービス名は例である。相談者が AWS を使わないときは、サービス名ではなく設計の考え方を根拠にする
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で作ったときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする
- 記録案（records）・ 差し戻し（referrals）・ コードの例（code）は、相談が該当するときだけ置く。それぞれの中身は answer.schema.json の欄の説明（description）に従う

ソフトウェアテストについての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。『テスト技術者資格制度 Foundation Level シラバス』（JSTQB 日本語版）と、テストの臭い（Gerard Meszaros の xunitpatterns.com）の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- ソフトウェアテストのアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
概念相談「〜とは」「〜の違いは」concept定義 ・ 具体例
判断相談「〜すべきか」「この案でよいか」judgment比較した案 ・ 判断の道筋
設計相談「〜をどう設計するか」design設計の手順

この領域での相談の例：「境界値分析とは何か」（概念）・「この修正にリグレッションテストを実施すべきか」（判断）・「リスクベースドテストのテスト計画書をどう作るか」（設計）・「このテストが時々落ちる原因と直し方は何か」（判断）

入力の想定

受け取る情報解釈・既定値

相談の対象と状況明示されなければ相談者に確認する。確認できないときは、置いた仮定を前置き（premises）に書き、仮定に依存する判定を「未判定」と示す。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、ツールで1件ずつ取り出して読む。読む前に回答を始めない。

qa-advisor get criteria <id>        判断基準を1件取り出す（JSON）
qa-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

qa-advisor validate --kind answer --file <回答.json>      欄の欠け ・ 無い判断基準の id ・ 判断基準に無い引用を検出する
qa-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に残る未判定によって結論が変わるとき）、概念相談は 定義、設計相談で相談者の案を評価するときは 良好 ・ 弱い、評価する案が無く回答の側で設計を示すときは 採る
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準の範囲外のこと（判断基準が触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」、条件の無い行は「対応：…」）。定義は「語：意味」、補足と注意は本文のまま引用する。表の一部の列だけを引用するときも、引いた列の題を残す
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で作ったときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする
- 記録案（records）・ 差し戻し（referrals）・ コードの例（code）は、相談が該当するときだけ置く。それぞれの中身は answer.schema.json の欄の説明（description）に従う

#概念規則判定
1読み手が意味を復元する作業を、書き手が負担する1文の中で、読み手に計算をさせない。名詞句には、指し先を文書の中に置く名詞句を1つずつ抜き出し、「何の」「どこの」「どっちの」「誰が」を問う。文書の中の文字列で答えられない名詞句が1つでもあれば、その文は書けていない。「読み返して不自然か」で判定しない——書き手は指し先を知っているので、不自然に見えない
2情報の型が、置く形を決める対比・条件・手順・分岐を、散文に置かないその段落を、表か図に置き直せるかを試す
3数が増えたら、形を変える並べるものが3つ以上なら、箇条書きか表にする数える
4見出しは、本文を読まずに全体を掴ませる見出しの階層を飛ばさない。見出しを追えば全体の内容がつかめるようにし、見出しを目立たせる。番号は付けても付けなくてもよい ── 統一されているかだけを確認する見出しだけを抜き出して、順に読む。そのうえで、どの本文がどの見出しに属すかが見た目で分かるかを確認する
5結論を先に置き、根拠を後ろに置く節の最初の一文を結論にする各節の先頭文だけを並べて読む
6読み手は、形の違いを意味の違いとして読む同じ立場のものは同じ形で書く。文体は文書の中で1つにする並んでいるものの語尾を見比べる
7語の意味は、文脈の中で定まる同じ文脈では、1つの意味に1つの語だけを対応づける。文脈が変わるなら、変わることを書く用語を列挙し、同じ意味の別の語が無いかを確認する
8読み手が誰かで、選ぶ語と構成が変わる読み手を先に決める。語は、読み手の世界にすでにある語から選ぶ。分野で定着した専門用語はそのまま使い、自分が作った語・訳した語は使わない。使うなら、新しい語だと書いて定義する。名前のあるものを、描写で呼ばない語の出どころを提示できるかを確認する。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する。そのうえで、書いた操作や物に、分野で通っている名前があるかを1つずつ問う。あるなら、描写ではなくその名前を書く——「均す」ではなく正規化する、「流す」ではなく実行する、「鵜呑みにしない」ではなくそのまま信じない。ふつうの日本語の語も、この判定に掛ける。作った語でも訳した語でもないので、出どころだけを確認すると通り抜ける。読み手が分野の外の人でも、描写に置き換えてはならない。言い換えてよいのは、日常語で意味が表せるものだけである（頻回→頻繁に）。日常語で表せないものは、その名前のまま使い、説明を添える
9読み手が一度に扱える量には限りがある1文は短くする。段落は3行から7行にする。文書の限度を決める数える
10比喩と定型句は、読み手によって解けない比喩は、例として明示するときだけ使うその比喩を字義どおりに読んで、意味が通るかを試す

名詞句で終わることは、それ自体では欠陥ではない。
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
判定1が見るのは、文の中で読み手が戻るかどうかである。

ガードレール

- 運用の覚書の書き方を、どの文書にも使わない。書いた本人が読み返すための略した書き方は、読み手のための書き方ではない。CLAUDE.md と Skill も例外にしない ── 例外にすると、そこで書いた語がそのまま本文へ流れる。どの文書でも、操作の名前で書く
- 名前のあるものを、描写で呼ばない。その操作に分野の名前があるなら、自分の言葉で言い換えない
- 比喩で言い換えない。対象を別の物へ置き換えた語を使わない ── 指し先が読み手の側で決まらない（文書か、欄か、クラスかを、読み手が推測することになる）。利用者への応答も同じである ── 応答で使用した語は、そのまま文書へ流入する。対象の名前で書く。検出する語は廃語の一覧が保持する ── 散文で例を並べると、その例が本文へ流入する。ただし、普通の語の一部になる語は一覧へ入れられない ── 部分一致で正しい語まで検出するためである（「段」は段階 ・ 段落 ・ 手段 ・ 段組みの一部である）。その種の語は機械で検出できないので、書く時点で遵守する
- 文語寄りの語を使わない。「営み」「所以」「〜ねばならない」のように、書き言葉のためだけに選んだ語は、ふだん話す語へ替える。判定は、同じことを口で説明するときにその語を使うか ── 使わないなら、読み手にとっては飾りであって、意味を1つも足していない
- 廃語を使用しない。一度破棄した語の一覧はこのSkillの外にある ── いつ何を破棄したかはプロジェクトごとに相違するので、ここへ書くと書いたプロジェクトでしか使えない検査になる。既定では .doc-writing/retired-words.json を、対象のファイルから上へたどって探す。無ければこの検査は走らない（失敗にしない）
- 名前を言い換えない。原典の訳語と、分野で定着した技術用語は、そのまま使う。和語にも漢語にも置き換えない ── 置き換えると必ず新しい語になり（メタデータ→「頭」、出典→「指す先」）、読み手が意味を決められない。判定は2つ ── その語を検索して同じ意味が出てくるか。原典か分野で、その語が使われているか
- 述部は、ふだん使う動詞で書く。ふだん使わない漢語（「保持する」「認知する」「委譲する」）にも、ふだん使わない和語（「起こす」「組み立てる」「止める」「突き合わせる」）にも置き換えない。分野に名前のある操作は、その名前で書く（ビルドする ・ コミットする ・ 照合する ・ エラーにする）。判定は、同じことを口で説明するときにその語を使うか。意味の範囲が広すぎて操作が特定できないときも、分野で使われている具体的な語を選ぶ
- 指し先の無い名詞句を書かない。「ずれ」「外を指す名前」のように、それが何を指すかを文書の中に書いていない語を使わない。見出しに置く語は、見出しだけで指し先が分かる形にする（「ずれた34件」ではなく「仕様と実装のずれ34件」）
- 散文で書けることを、散文で書かない。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- 桁を空白で整列させて、表に見せない。表はマークダウンの表で書く
- ASCII で図を描かない。図は mermaid か SVG で書く
- 同じ文脈で、同じ意味に2つの語を対応づけない。文脈が変わるなら、変わることを書く
- 訂正の記録を本文に残さない。文書には現行の正しい内容だけを書く。履歴は git が持つ
- 数値は原典の文字列で確認してから書く。要約を経由して引かない
- 確認していない内容を、確認したように書かない。推測は推測と分かる形で書く
- 原典から導けない決めを、原典の記述として書かない。こちらの決めだと書く
- ゲートを実行していないものを、出さない。実行していないなら、そう書く

このSkillが保持する知識は、声・読み方・合成の条件だけである。 スライドの並び方、
画像の置き場、動画の解像度は保持しない ── 保持すると、同じ知識が2か所に存在する。

役割

- 枚ごとの読み上げる文から、音声と、語と文の時刻を作る
- 音声の長さを測り、結合する側が画面を切るための尺として返す
- 文・声・エンジンからキーを作り、キーが在る枚を再合成せずに取り出す
- 読みの補正を辞書へ集約し、原稿と入力を書き換えない
- 手元での実行と、AWS側での実行の両方を、同じ命令で成立させる

処理対象と成果物

処理対象

枚の識別子と、読み上げる文を持つ入力（narration.json）。識別子は、スライドを保持する側が
出したものをそのまま使う ── このSkillは採番しない。

成果物

枚ごとの音声（mp3）と、語と文の時刻（marks）、および両者の場所と長さを持つ出力
（narration.out.json）。音声はキーの名前で置くので、名前そのものが再合成の判定になる。

入力の想定

受け取る情報解釈・既定値
narration.json を置いたフォルダ明示されなければ、いま作業しているフォルダを対象とする
声明示されなければ narration.json の指定を使う。指定が無ければ Takumi（日本語・ニューラル）
読みの辞書明示されなければ適用しない。narration.json の lexicons が名前を持つ
音声の置き場明示されなければ、入力のフォルダの下の cache とする

実行手順

Step 1: 入力を確認する

枚の識別子が、スライドを保持する側の識別子と一致するかを確認する。読み上げる文に読み仮名が
書かれていないかを確認する ── 読みの補正は辞書が持つ。

slide-deck-speech plan <フォルダ>

合成せずに、どの枚が合成になり、どの枚が取り出しになるかが出る。

Step 2: 合成する

slide-deck-speech synth <フォルダ> [声]

キーが在る枚は取り出し、無い枚だけを合成する。出力に、音声・時刻・長さを書く。

Step 3: 尺を確認する

出力の durationMs が、音声の長さと一致することを確認する。

slide-deck-speech measure <音声のファイル>

durationMs は音声の長さである。 語と文の時刻の最後の印は、最後の語が始まる時刻であって、
音声の終わりではない ── 最後の印を長さとして扱うと、枚ごとに早く切り替わる。

Step 4: 読みを直す

読み間違いが在れば、辞書へ登録する。原稿と入力は書き換えない。

登録した名前を narration.json の lexicons へ書くと、合成の前に適用される。

Step 5: 結合する側へ渡す

出力の枚の識別子で、スライドの画像と突き合わせる。映像の長さは durationMs で固定し、
通しは再符号化して繋ぐ ── 無変換で繋ぐと、時刻の差が累積する。

- 枚の識別子を、このSkillが採番してはならない。 採番すると、枚の増減で識別子が他の枚へ移り、違う枚に音声が付く。しかもその誤りは機械では検出できず、動画を再生するまで判明しない

- 環境を先に作ってはならない。同時に、環境の作り方を保持しない状態にしてもならない。 既定は手元で実行し、AWS側で実行するための構成はテンプレートとして同梱する ── 先に作ると使っていない設備を保守することになり、作り方が無いと端末の状態に依存し続ける

目的

ある作業を1つのSkillだけでは終えられないとき、どのSkillを一緒に呼ぶかを配線表を参照して決める際に使う。Orchestratorが作業の途中で必要な回数だけ呼び、呼んだSkillから返ってきた結果を、その作業への入力として渡す。配線表が持つのは「何を、誰に頼むか」だけで、「いつ呼ぶか（作業の前に材料を集めるのか、作業のあとに十分かを確認するのか、両方か）」はOrchestratorが決める。skill-router自身はタイミングを保持しない。

この文書が持つのは、配線表の読み方だけである。配線そのものは保持しない。 配線はプロジェクトごとに違う。ここに書けば、書いたプロジェクトでしか使えないSkillになる。

どんなSkillを呼んでよいかも、この文書は決めない。 それはプロジェクトごとの決め事なので、配線表のファイルに書く。

役割

- 1つのSkillだけでは終えられない作業を、外にある配線表を参照して識別する
- 何を依頼するか・誰を呼ぶか・その相手が居ないときどうするかを返す
- 呼ぶSkillを、それぞれ独立した目的・役割・タスク・成果物・受け入れ基準を持たせて並列に呼び出せるよう、呼ぶSkillの名前の一覧を返す
- 作業側のSkillと呼ばれる側のSkillが互いを呼び合う形を避け、Orchestratorに代わって窓口になる
- ユーザーから配線の追加・修正・削除を依頼されたときは、対話しながら配線表のファイルを書き換える（判定だけを依頼されたときは書き換えない）

name: fact-check
description: 外にある情報源を調べて、その内容を文書・設計・実装へ取り込むときに必ず使うスキル。公式リファレンス・API仕様・OSSの実装・論文・規格が対象。「調べて」「調査して」「仕様を確認して」「どうなっている？」と言われたとき、および識別子（項目名・パラメータ名・関数名・スキーマのキー）を文書へ書き写すときに必ず使う。要約を経由して原典を読むことを禁じ、原文の文字列で照合させる。
version: 2.0.0

目的

調査対象を、要約を経由せずに読む。

真偽そのものは判定しない ── 見るのは、書こうとしている識別子と主張が取得した原文の中に在るかである。原文が誤っている場合は、誤っているまま照合が通る。

識別子は説明ではなくキーである。
compact_summary を compact_text と書き換えたら、そのキーで参照する実装は必ず空を返す。
しかも壊れ方が静かで、「その事象は起きなかった」と読めてしまう。
土台の項目名が違えば、その上に作ったツールは何も取れない。

主張は、要約すると別のものになる。
「〜の場合に出る」から条件を除けば、無条件で出ると書いたことになる。
しかも識別子と違って、照合には1件も掛からない。
名前がすべて原文どおりの文書が、原典と違うことを述べる。

識別子の照合は、原典への忠実さのうち、文字列で照合できる一部である。
残りは、主張を原文の引用に結びつけて検証する。

このスキルが禁じるのは1つ——「要約された原典」を根拠にすることである。
公式リファレンスも、OSS の実装も、規格も、実測データも、
扱いは同じである。どれも「正しいとされる情報源」であり、
勝手に言い換えた時点で、実体と別のものになる。

役割

- 情報源の原文を取得し、取得した日と sha256 を残す
- 文書へ書く識別子を、原文の文字列で1つずつ照合する
- 照合できなかった識別子を、原典の名前として書かない
- 「原典にこう書いてある」と書くときは、どのファイルの何行目かを提示できるようにする
- 原典の記述として書く主張を、原文の引用へ1件ずつ結びつける
- 引用を添えられない主張を、原典の記述として書かない
- 要約・言い換え・意訳を、識別子にも主張にも行わない

処理対象

外にある情報源である。

種類例

OSS の実装型定義、アダプタの契約、保存先のパス
規格・論文RFC、semantic conventions、原典の数値
実測データ自分で取った記録。これも「情報源」として同じ扱いをする

成果物

原文のファイルと、2種類の照合の結果である。
原文は保存する。識別子は原文の文字列で照合し、主張は原文の引用へ結びつけてから文書へ書く。

入力の想定

受け取る情報解釈・既定値

実行手順

Step 1: 原文を取得する

fact-check fetch <URL> [--dir <置き場所>]

まず <URL>.md を試し、無ければ本体を取る。
主要な文書サイトは .md で原文を返す（実測：Anthropic ・ Cursor ・ OpenAI ・ GitHub の4社とも返した）。

取得したものは、sha256 ・ バイト数 ・ 行数 ・ 取得した日と一緒に保存される。
「いつ・どの版を読んだか」が提示できなければ、根拠にならない。

対象どう取得するか
公式リファレンスfetch <URL>。.md が返ればそれが原文である
OSS の実装git clone --depth 1。読んだ commit を記録する
論文PDF を置き、本文の文字列で確認する
実測データ自分で取ったファイルをそのまま置く

HTML しか返らない頁も、そのまま原文として残る。
タグは剥がさない ── 剥がすのは加工であり、剥がし方で文字列が変わると
「原文と1文字ずつ同じ」が主張できなくなる。

Step 2: 識別子を列挙する

文書・設計・実装へ書こうとしている識別子を、1行1個で並べる。

対象になるのは、名前がそのままキーとして使われるものである。

- 項目名・フィールド名（compact_summary ・ tool_use_id）
- パラメータ名・フラグ（--permission-mode ・ permission_prompts）
- 事象名・関数名・型名（PostToolUse ・ LoadedEntry）
- ファイル名・パス（~/.codex/sessions/ ・ state.vscdb）
- 設定のキー（github.copilot.chat.otel.enabled）

Step 3: 原文と照合する

fact-check verify <原文> <識別子>... --as identifier
fact-check verify <原文> --as identifier --from names.txt

照合の種類を渡さなければ止まる。
ツールの側で「たぶん識別子だろう」と決めない。

照合の種類何を照合するか
identifier語として照合する。前後が語の文字なら、それは別の名前である
quote引用として照合する。空白の圧縮規則だけ統一し、語は1文字も変えない
textそのまま探す。探索のための種類で、照合した証しにはならない

語の区切りは、照合する語自身が決める。
英数と _ - は常に語の内側で、それ以外の区切り（. / : など）は、
照合する語がそれを含んでいるときだけ内側になる。
だから otel.enabled はキーの切れ端として一致せず、compact_summary は英文の文末でも一致する。

読めた範囲に無い識別子が1つでもあれば、そこで止まる。

見つからない原因どうするか
名前を言い換えた直す。原文の綴りをそのまま使う
別のページに在るそのページを取得して照合し直す
読めなかった範囲に在る読めるようにして、照合し直す。0件を結論にしない
本当に無い「無い」と書く。推測で補完しない

アンカーを渡すと、文脈まで検査する。

fact-check verify <原文> compact_summary --as identifier \
           --near "PostCompact input" --within 25

名前が在ることと、その名前がそこで使われることは別である。
trigger は原文に 24 か所あるが、それが PostCompact のものとは限らない。
別の事象の項目を、その事象のものとして書く——これが次に起きる誤りである。

この検査で見えるもの・見えないもの

これは文字列の検査であって、意味の検査ではない。

見える例
識別子を言い換えたconfig_source と書いたが、原文には無い
綴り・大文字小文字・区切りの違いtoolResult を tool_result と書いた
アンカーを渡せば、文脈違いtrigger は在るが PostCompact の節に無い
見えないどう防ぐか
名前は合っているが、説明が違うStep 4 で、主張を引用に結びつける
原文に在るのに、こちらが取りこぼしているStep 6 で逆側から照合する
数値・件数の誤り数値も、原文の文字列で確認する。自分で計算した値を、原典の値のように書かない
版が古い取得した日を保存し、同じ URL でも中身が変化する前提で処理する

「0件だから正しい」ではない。「書いた名前は、読めた範囲に実在する」だけである。

読めなかったファイルは、結果に「読めなかった範囲」として出る。
1つでも在れば、0件は「無い」ではなく「読めた範囲には無い」としか判定できない。
黙って飛ばして0件と報告するのは、ツールの側が推測で断定することである。

Step 4: 主張を、引用に結びつける

原典の記述として書こうとしている主張を、1件ずつ書き出す。
識別子と同じ扱いをする。違うのは、照合する先が名前ではなく、原文の一続きの範囲だという1点である。

1件ごとに、根拠にした原文の行をそのまま添える。
行番号は grep -n で取る。

主張      PostCompact は、自動の圧縮でも手動の圧縮でも走る
引用      | `trigger` | `"manual"` \| `"auto"` | 圧縮の起こし方 |
出どころ  claude-code-hooks.md:412

引用を添えられない主張は、原典の記述として書かない。

引用を添えられないどうするか
原文に在るはずだが、まだ探していない探す。見つけた行を添える
原文には無く、自分の推論である「推測」と印を付ける。または除外する
離れた複数の箇所を繋いで導いた繋いだと書く。参照した箇所を全部添える

要約して意味が変わる形は、4つある。

変わり方原文書いてしまう内容
条件の脱落「〜の場合に出る」「出る」
範囲の拡大1つの実装・1つの版の話「一般にこうである」
因果の捏造並べて書いてあるだけ「A だから B になる」
欠落の補完何も書いていない通念で埋め、「原典にこうある」と書く

4つとも、Step 3 の照合では0件になる。
名前を1つも言い換えていないためである。

引用が原文と1文字ずつ同じかは、verify で検証できる。

fact-check verify <原文> --as quote --from quotes.txt

引用は1行ずつ渡す。
行をまたぐ引用も一致する（空白の圧縮規則だけ統一するため）が、
渡すときの1件は1行にする。

引用を、読みやすくするために整えない。
整えた時点で、引用ではなくなる。

Step 5: 書けることと、書けないことを分ける

原文で照合できたことだけを、原典の記述として書く。

書けること書き方
原文に在る識別子と、その説明そのまま引用する。言い換えない
原文に無い「原文に無い」と書く
自分で測った値「実測」と印を付け、測った条件も書く
第三者の実装が主張していること「第三者」と印を付け、どのリポジトリの何 commit かを書く

「原典に書いてある」と「実際にそうなる」は別である。
公式に書いてあっても、条件が充足しないと出ない項目がある。
出せることを確認したなら、そのための条件も書く。

Step 6: 逆側からも照合する

原文に在るのに、こちらが取りこぼしている識別子を探す。

Step 3 は「こちらが書いたものが原文に在るか」を検査する。
それだけでは取りこぼしが残る。原文を頭から読み、
見出しの一覧と、こちらが持っている一覧を突き合わせる。

識別子だけでなく、条件・例外・限定も同じように探す。
原文が付けている「ただし」を看過すれば、書いたものは Step 4 の条件の脱落と同じ形になる。

出力形式

調べた結果を報告するとき、次を必ず添える。

報告する内容書き方
何を読んだかURL と、取得した日と、行数。「公式ドキュメント」とだけ書かない
どう読んだか原文を取得して文字列で照合した、と書く。していないならそう書く
照合した識別子の数何個照合して、何個が原文に在ったか
主張の根拠原典の記述として書いた主張ごとに、引いた行と出どころを添える。添えられないものは「推測」と印を付ける
どの種類で照合したかidentifier ・ quote ・ text のどれか。text は照合した証しにならないと添える
読めた範囲に無かったもの一覧で出す。1つでも隠さない
読めなかった範囲在れば一覧で出し、0件を結論にしない。無ければ「全部読めた」と書く
実測と原典の区別行ごと・値ごとに印を付ける

ガードレール

- 要約を経由して原典を読まない。要約するツールの出力を、原典の記述として引用しない
- 識別子を言い換えない。大文字小文字・区切り記号・単複まで原文どおりにする
- 原文に無い識別子を、原典の名前として書かない
- 引用を添えられない主張を、原典の記述として書かない。推測として書くか、書かない
- 引用を整えない。読みやすさのために語を足さない。条件・範囲・限定を除かない
- 照合が0件でも、意味が合っているとは限らない。主張は Step 4 で別に検証する
- 0件を「無い」と結論しない。読めなかった範囲が1つでも在れば、「読めた範囲には無い」と書く
- --as text の結果を、照合した証しにしない。探索のための種類である
- 「公式にはこう書いてある」と書くなら、原文のどこかを提示できるようにする
- 原典が誤っていると結論する前に、自分の読み方を疑う。
原典の誤りと読み方の誤りは、同じ観測を生む ── 観測だけでは区別できないので、
検証の負荷が小さい側（自分の読み方）から先に検証する
- 取得した日と版を残す。同じ URL でも中身は変わる
- OSS は読んだ commit を記録する。「そのリポジトリではこうなっている」は版に依存する
- 第三者の実装の主張を、公式の記述として書かない。印を分ける
- 原文で照合していない調査結果で、正本を書き換えない
- 原文の置き場所を、このスキルの側で決めない。呼び出す側から受け取る
- このスキルの外を指す参照を保持しない。他のスキル・特定のフォルダの並びを前提にしない

構造化データからSVGを生成するSkill：design-svg

目的

図を、手で座標を置くのではなく構造化データの宣言から生成するときに使う。何をどう並べるかを
宣言し、見た目はトークンで決め、座標は配置戦略に解かせる。紹介ページの主画像・概念の説明図・
仕組みの内訳図・量を示す図のいずれも、単体で完結するインラインSVGとして得られる。

この Skill が持つ描画エンジン（tool/business_logic/）が実体である。CLI は1つの実行ファイル design-svg で、
宣言を JSON のファイルで受け取る ── 呼ぶ側は台本を書かず、宣言だけで同じ図を生成し直せる。

cargo install --path tool/cli --root . --target-dir tool/target   # bin/design-svg ができる
cargo install --path tool/mcp --root . --target-dir tool/target   # bin/design-svg-mcp ができる

以下の design-svg は、この実行ファイルを指す。

役割

- 描きたいものを、節点・辺・囲みの宣言へ変換する
- どの部品で描くか・どの配置戦略で解くかを選ぶ
- 見た目をテーマ（トークン）と役割で決める。色や寸法を直接書かない
- 描いた画像を必ず見る。幾何の検査が通ることと、絵として成立していることは別である

処理対象と成果物

処理対象

図にしたい構造（つながり・階層・包含・並び順・量・対応など）。

成果物

単体で完結するインラインSVG文字列。外部ホストにも実行時のライブラリにも依存しない。

入力の想定

受け取る情報解釈・既定値
何を描きたいか（構造そのもの、または描きたい内容の説明）説明で渡された場合は、まず節点・辺・囲みの宣言へ変換する。変換できない場合は「量を描く部品」側で表せないかを確認する
見た目の指定（明暗・配色・大きさ）明示されなければ既定のテーマを使う。指定があればテーマを差し替えるか、役割を足す
置き場所（ファイルへ書くか、埋め込むか）明示されなければ文字列として返し、書き出しは呼び出し側に委ねる

実行手順

Step 1: 何を受け取れるかを目録で確認する

design-svg catalog               # 目録をJSONで出す
design-svg catalog catalog.json  # ファイルへ書き出す

目録は、どの部品があり、それぞれがどんな値を読み、どんなトークンで見た目が決まり、
どの配置戦略が選べるかを持つ。手で書かれたものではなく、部品の実装から導かれているので、
実物とずれない。各部品には最小の動く入力（見本）も載っている。

Step 2: 構造を宣言へ変換する

つながり・階層・包含は、節点と辺と囲みで書く。宣言は JSON のファイルに置く。

{"nodes": [{"id": "a", "label": "受付"},
           {"id": "b", "label": "検証", "role": "focus"}],
 "edges": [{"from": "a", "to": "b", "label": "渡す"}],
 "groups": [{"label": "束ね", "members": ["a", "b"]}],
 "direction": "TB"}
design-svg figure 宣言.json --out 図.svg

groups は省ける。direction は TB か LR である。

- nodes は id が必須。label / role / style / figure は任意
- edges は from と to が必須。label / dashed / arrow は任意
- groups は members が必須。label は任意
- 節点に figure を持たせると、その節点の中身が別の図になる（入れ子。深さの上限はトークン）

量を描くもの（内訳・大小・並び順・区間・分布・2軸上の点・流量・位置）は、部品を1つ選んで描く。

design-svg chart bars データ.json --out 図.svg

データ.json は {"bars": [{"name": "文書", "value": 13}]} のように、その部品が読む値を持つ。

意匠そのものを作るとき（面 ・ 文字 ・ 人 ・ 絵 ・ 任意の曲線）は、画布へ直に置く。

{"width": 600, "height": 200, "layers": [
  {"kind": "panel", "x": 20, "y": 20, "props": {"width": 240, "height": 120}},
  {"kind": "text", "x": 40, "y": 44,
   "props": {"text": ["見出し", "説明の行"], "size": 18, "weight": "bold"}},
  {"kind": "icon", "x": 320, "y": 40, "props": {"name": "person", "size": 64}},
  {"kind": "icon", "x": 420, "y": 48, "props": {"name": "doc", "size": 32}},
  {"kind": "path", "x": 460, "y": 40,
   "props": {"d": "M0,0 a30 30 0 0 1 60,0", "filled": false}}]}
design-svg canvas 層.json --out 図.svg

- text ── 任意の位置の文字。行の並び ・ 大きさ ・ 太さ ・ 濃さ ・ 寄せを渡す。中央へ置くのは呼ぶ側の仕事である（部品は自分の原点を基準に描く。幅の測り方は tool/business_logic/src/text.rs が持つ）
- panel ── 塗りと枠だけの面。囲み（frame）とは別である ── 囲みは「ここは領域の内側」を示す破線の注記で、面は意匠そのものである
- icon ── 絵記号（人も含む）。どれも 0..24 の同じ枠で描くので、並べたときに大きさが一致する。拡大しても線は太らない ── 枠ごと拡大すると、大きい絵だけ重くなる
- path ── SVG のパスの文法をそのまま受ける（M/L/H/V/C/S/Q/T/A/Z を絶対でも相対でも）。座標は書き換えない ── 外接矩形ぶんの平行移動で置く
- 色は濃さの呼び名で渡す（ink ・ soft ・ faint ・ accent ・ accent-bg ・ on-accent ・ fill ・ line）。直値を渡さない

好きな位置へ重ねたいときも画布を使う。層の並びだけを渡すなら、大きさは引数で渡す ──
design-svg canvas 層.json --width 400 --height 200。

Step 3: 配置戦略を選ぶ

座標の解き方は差し替えられる。主張が違えば配置も違う ── 閉じていることを見せたい図を
縦一列に並べて最後から最初へ長い辺を戻すと、閉じていることが図から読めない。

戦略何を根拠に置くか
graph（既定。層状）辺の向きから層を決める。つながり・階層に使う
radial輪の上に置く。並びが閉じていることを見せる
tree中心から枝分かれさせる
grid宣言が持つ座標のとおりに置く。縦横の交点が意味を持つとき

宣言の layout に名前を書く（--layout でも渡せるが、宣言が勝つ）。

{"layout": "radial", "nodes": [...], "edges": [...]}

格子は座標を必要とするので、宣言の grid に置く。cols と rows は並びを外から決めるときだけ書く。

{"layout": "grid", "nodes": [...], "edges": [...],
 "grid": {"at": {"a": ["左", "上"], "b": ["右", "下"]},
          "cols": ["左", "右"], "rows": ["上", "下"],
          "elbow": [["a", "b", "vertical"]]}}

辺を鍵線にしたいときは elbow に [始点, 終点, 置き方] を書く ── "vertical" は真下（真上）へ降りてから横へ折れ、"horizontal" はその逆である。格子は最上位の図だけに適用する ── 入れ子の図は層状で解く。

同じ2点を往復する2本の辺は、どちらにも同じ置き方を書くと、別の角を通る（往路は始点の列 ・ 終点の行で、復路はその逆で折れる）。書かないと2本が同じ直線に重なり、注記も重なる。

箱の幅は size.box-max-w までで、超えるラベルは箱の中で折り返す。 1行のまま箱を広げると、横に並んだ図が枠の幅に合わせて縮小され、文字が読めなくなる。行頭に閉じ括弧 ・ 句読点を置かない（行頭の禁則）。宣言の側で改行を入れない ── 折り返す位置は幅から決まる。

自分へ戻る辺（from と to が同じ）は、節点の脇に輪を作る。 同じ節点に2本以上あれば、2本目以降は別の辺へ出す ── 流れの上流の側の辺（LR では左、TB では上）は、入ってくる辺が集まるので最後に使用する。輪の注記は、輪の頂点の外側へ置く。

囲み（groups）を持つ図は、囲みごとに段を分けて配置する。 囲みは __g<番号>（groups の並び順、0から）を名前として at に座標を持ち、囲みの内側の節点の座標は、その囲みの中の格子として解く。鍵線は、その辺が在る段で適用する ── 宣言に無い辺を指す鍵線は、図全体で照合して断る。

Step 4: 見た目を決める

見た目の上書きは、宣言の中で渡す。 theme に差分だけを書けばよく、既定のテーマへ重なる。layout と direction も宣言が持てる ── 引数でしか渡せないものを作らない。宣言だけで同じ図を生成し直せなければ、呼ぶ側は台本を書くことになり、その台本は成果物の隣に残らない。

{"nodes": [...], "edges": [...], "direction": "LR",
 "theme": {"color.box-fill": "var(--card)", "color.ink": "var(--ink)"}}

知らないトークンの名前は、その場で誤用（終了コード 2）として返る ── 目録に在る名前だけを使う。

色・寸法・書体を直接書かない。必ずトークンから引く。3層で解決される
── テーマの既定値 → 役割による上書き → その場の上書き。

{"nodes": [...], "edges": [...],
 "theme": {"color.box-fill": "#1C222C", "color.ink": "#E7ECF3"}}

既定のテーマの正本は references/theme.json である ── トークン ・ 値の範囲 ・ 色の濃さの呼び名を持つ。

役割（強調・控えめ等）もテーマが持つので、新しい役割はテーマへ行を足すだけで増える。

{"nodes": [{"id": "a", "label": "停止", "role": "危険"}],
 "theme": {"role.危険.color.box-stroke": "color.warn",
           "role.危険.color.text": "color.warn"}}

役割の行も名前を検査する ── role.<役割>.<名前> の <名前> は、既定のトークンか、既存の役割が使っている名前
（color.text など。目録の roles に在る）でなければ断る。綴りの誤りを、その場で止めるためである。

焼き上がったSVGは、生成後の外部CSSでも上書きできる（.svg-box rect { fill: ... }）。
明暗の切り替えは、テーマを2組焼き分けるか、CSSで適用するかのどちらでもよい。

Step 5: 破綻していないかを機械で検査する

figure ・ chart ・ canvas は、描いた直後に3種の検査を自動で適用し、検出を返す（終了コード 1）。
書き出した SVG を単独で検査するときは verify を使う。

design-svg verify 図.svg

見るのは、文字どうしの重なり・画布からのはみ出し・箱どうしの重なり・辺が箱を突っ切ること・
辺の端点がインクに乗っていること。この検査が見ないものが3つある ── 極端な縦横比、
配置戦略の選び違い（幾何は無傷でも主張が読めない）、詰まり・読みにくさ・配色の良し悪し。

この検査は、見つけるが直さない。辺が箱を突っ切ることは検出できるが、
それを避けて経路を描く戦略は無い。出たときに消す手は、宣言の手直しではなく配置の選び直しである。

Step 6: 描いた画像を目視で確認する

座標が正しいことと、絵として成立していることは別である。検査が全部通っていても、
余白の偏り・意図しない強調・読めない重なりは目視でしか分からない。出す前に必ず画像を目視で確認する。

Step 7: 部品が足りなければ足す

部品は、tool/business_logic/src/shapes*.rs の関数1つと、そのファイルの register() への1行で増える。核は変化しない。

fn bookmark(p: &Props, style: &Style) -> Result<Fragment, String> {
    let (w, h) = (style.num("size.box-min-w")?, style.num("size.box-h")?);
    let fill = style.text("color.accent-bg")?;
    Ok(Fragment::own(format!("<path d=\"...\" fill=\"{fill}\"/>"), w, h))
}
// register() の並びへ ("しおり", bookmark) を足す

足すときの規約は references/document.json の svg-engine-discipline にある（design-svg get --kind document --id svg-engine-discipline で取得する）。新しいファイルは
tool/business_logic/src/lib.rs の components() へ足すこと ── 足さないと台帳に載らない。
目録の表（catalog.rs の PARTS）にも1行足す ── 部品が読むキーと表が食い違えば、事例が失敗する。

出力形式

インラインSVGの文字列を返す。 ファイルへの書き出しは、呼ぶ側が決める。

返すもの形
図<svg> から始まる単体の文字列。外部ホストにも実行時のライブラリにも依存しない
目録JSON（design-svg catalog）── 部品 ・ トークン ・ 役割 ・ 配置戦略
検査の結果破綻の一覧。0件なら空である

描いた画像を目視で確認してから渡す ── 幾何の検査が通ることと、絵として成立していることは別である。

ガードレール

- 描いた画像を目視で確認する前に提示してはならない。最優先。例外なし
- 描けないという判断を、既定の配置だけで下さない。位置を決めるものは戦略ごとに違う
（辺・宣言の座標・順序・階層・呼ぶ側）。既定は選べるうちの1つであって、能力の上限ではない。
目録は部品の実装から導かれているので、そこに無いことを確認してから言う
- 図の破綻を、宣言の書き直しで直さない。辺が箱を貫く・線が長い斜めになる・経路が外を回り込む
── どれも描きたい主張と、位置を決めるものが食い違っている印である。
直す先は節点や辺ではなく、どの配置に解かせるかである
- 囲みは、配置が終了したあとに付与される外接矩形である。外から引く辺は中の節点の中心を狙うので、
囲みは辺の相手にならない。囲みの中の1つへつなぎたいときは、囲みではなく入れ子の図にする
- 辺をどこから出すかは、宣言では決まらない。次の点へ向かう向きで決まる。だから
鍵線は、配置が曲がり角を1つ挟むことで出る（格子なら elbow=）。斜めの1本になったのを
見て「この向きには引けない」と決めない ── 決めているのは辺ではなく配置である
- 色・寸法・書体を直接書かない。必ずトークンから引く（テーマを差し替えても取り残されるため）
- 勘で置いた数値を残さない。コードに現れる数は、設計上の選択（トークンから注入）か
データから決まる量（毎回計算）のどちらかである。3種目は存在してはいけない
- 1枚に2つ以上の訴求を載せない
- 部品はSVGの断片だけを返す。<svg> ルートを作るのは最上位の合成だけ
- 部品は決定的であること。乱数・現在時刻を使わない
- 利用側の語彙をエンジンへ持ち込まない。このSkillが知ってよいのは節点・辺・囲みという
一般名詞と、部品・トークン・配置戦略だけである。固有の記法を持つ側から使うときは、
その語彙からこの宣言へ直す変換を呼ぶ側に置く

name: slide-deck
description: 発表資料・スライドデッキを新しく作る、または既存の枚を直すときに使うスキル。「スライド」「デッキ」「発表資料」「プレゼン」「登壇資料」「LT」と言われたとき、HTMLで1枚ずつめくる資料を扱うとき、および原稿（読み上げの台本）を持つデッキ・教材動画のスライドを1枚ずつ照合して直すときに必ず使う。
version: 1.3.0

目的

HTMLのスライドデッキを、1枚1主張・量の上限・描画確認の3つを遵守して作る。
配色は選ぶ ── references/themes/ の1本を適用する。図は生成させて、返った SVG をそのまま置く。
規則が立っている考え方は references/document.json の visual-design-for-slide-decks にある。
新しくデッキを起こすとき、既存の枚を直すとき、短い版に集約するときに使う。

原稿を持つデッキは、スライドと原稿を1枚ずつ照合して直す。
変更前と変更後を並べた比較ページで1枚ずつ確認し、全枚が済んだら、台本 ・ 確認記録 ・ 観点ごとの結果の3つをHTMLとPDFで出す。
工程と観点は references/document.json の review が保持する。

役割

- 枚ごとに「言い切る1文」を先に決め、それが立つ構成を選ぶ
- どの配色で作るかを先に決める。色を1つずつ選ばない
- 図は部品を並べて作る。文字を枠で囲んだだけのものを図と呼ばない
- 通った枚から取り出した3つの型（列挙と図解／数値2つの対／種類を分ける）のどれかを適用する
- 大きい要素の数と、根拠の置き方を、枚をまたいで統一する
- 描画して目視で確認してから出す。測ってはみ出しを確認する
- 数値を原典の文字列で確認してから載せる
- 図・表・数値の対のいずれかを、必ず1つ置く。文字だけの枚を作らない
- 色と大きさを均等に配らない。支配する色を1つ決め、際立たせる色を1つだけ置く
- 繰り返すのは目印と列の役割で、変えるのは枚の組み方である
- 既定値のままにしない。見出しの下の線・色の帯・縁の縞を置かない
- 枚の追加・削除・並べ替えを先に済ませ、中身は後で書く
- 描画した画像を、作った本人とは別の目で確認する。確認の順序を決めておく
- 描画されたテキストを抜き出して、入れ忘れと置き忘れを探す
- 直す前に1度検査して件数を控え、増えたぶんだけを自分の壊れとして扱う
- 原稿を持つデッキでは、原稿を枚の一部として扱う。スライドと原稿を同じ枚の中で照合する
- 微調整の前に、図の形が主張を示しているかを判定する
- 1枚を直したら、前後の枚との論とストーリーを確認する
- 1枚ごとに比較ページへ反映し、承認を得てから次の枚へ移る

実行手順

Step 1: この枚で言い切ることを1文にする

枚を書き始める前に、主張を1文で書く。1文にならないなら、その枚は2枚に割れている。

- 見出しは、その1文を断定形で書いたものにする
- 問いの形にしない。体言止めで逃げない

Step 2: 設計規則を読み込む

references/document.json の design-rules を読み、量の上限と3つの型を把握してから構成を選ぶ。

- 大きい要素は2つか3つ。4つ以上あると、どれが主張か消える
- 各要素の下は 条件1行 → 但し書き1〜2行 → 出典1行 の順を崩さない
- 強調は枚に1か所だけ

型を選ぶ

中身に合う型を選ぶ。形から入らない。

- 左で数を宣言でき、右をその図にできる → 型A 列挙と図解
- 2つの実測を突き合わせる → 型B 数値2つの対
- 情報量が多く、左右で種類を分けられる → 型C 種類を分ける

列に役割を対応づける

同じ系統の枚では、列の役割を固定する。
例えば「左＝いま起きていること、右＝提案」と決めたら、全枚で固定する。

- 幅いっぱいの帯で横断させない。どちらの話か分からなくなる
- 対比を語る枚は、左右で同じ部品・同じ個数にし、色だけを変える
- 同形式にすると決めたら、見出しの行数・根拠の数・補足の行数まで統一する

Step 3: 配色を選ぶ

references/document.json の themes を読み、references/themes/ の1本を選ぶ。

テーマ地強調いつ選ぶか
warm-paper生成り赤茶線画を多く置くとき。明るい地なので細い線が持ちこたえる
deep-navy濃紺青緑暗い会場で投影するとき。細い線は沈むので、面で見せる
cool-paper明るい灰青藍赤茶が題材と合わない技術寄りの回。強調が叫ばない
print-mono白深い赤PDFにして刷る・配るとき。階層は2つまで

選ぶのは人ではなく、出力先である。
投影なら会場の明るさが、配布なら紙が決める。題材の雰囲気で選ばない。

出力先が分からないときは聞く。こちらからは会場も配布の形も見えない。

Step 4: 入力を書き、生成させる

3つで生成する。 中身は入力（JSON）が、形は型が、配色はテーマが持つ。

形      references/slide-deck.template.html   出来上がりの形。部品と差し込む場所
中身    <デッキ>.json                          枚と要素。形は slide-deck.schema.json が決める
配色    references/themes/<名前>.css           色の正本
slide-deck new <デッキ>.json --theme <テーマの名前> --title <題>
slide-deck render <デッキ>.json <出力.html>

同じ入力からは、同じ1枚が出る ── 日付も乱数も読まない。--check を渡すと、
生成し直さずに差が在るかだけを検査する。

- HTML を手で書かない。 枚を直すのは入力であり、形を直すのは型である
- 要素は14種類である。text ・ lede ・ card ・ flow ・ stat ・ boxes ・
pair ・ recap ・ punch ・ caveat ・ figure ・ table ・ list ・ who
- 種類を足すときは、型と schema の両方へ足す ── 片方だけに足すと、入力が通って出力が空になる
- 色を1つずつ直さない。 直すならテーマの側を直す
- 固定ステージと拡大縮小のしくみは型が持つ。枚の側で書き換えない

Step 5: 図を生成させる

この Skill は図を描かない。描き方も、描くツールも保持しない。 渡すのは配色と、何を描くかである ── 生成させる相手は配線表が決める。

slide-deck theme <テーマの名前> --out theme.json   # 配色を複製して渡す

- 配色を図の側へ書かない。 正本は references/themes/<名前>.css の1か所である
- 幅は 1112px に統一する。枚ごとに変えない
- 何を示す図かを1文で書く。書けないなら、その図はまだ決まっていない
- 新しい分類色を足す前に、位置・ラベル・線の違いで区別できるかを判定する
- 描く側の幾何の検査を実行し、そのうえで描画して目視する

渡し方と色の対応は references/document.json の figures が持つ。

Step 6: 数値を原典で確認する

要約経由で引かない。原典の文字列を開いて確認する。

- 自分で計算した値を、原典の値のように書かない
- 範囲で書かない。条件付きの1つの値を、条件とともに書く
- 割合には母集団を添える

Step 7: 描画して目視で確認する

references/document.json の render-check の手順で画像にし、実際に目視で確認する。

- 変更した枚を必ず描画する
- 全枚の下端を測り、620を超える枚を把握する
- 縦長と横長の両方で、はみ出しが無いことを確認する

高さが一致しないときの直し方

余白で押し広げない。中身を減らすか、置き方を変える。

- 縦に長い要素を、横に広い帯へ置き直す
- 要素の数を減らす
- 別の枚に分ける

Step 8: 日本語を声に出して読む

references/document.json の design-rules の §7 に照らして、枚に置いた文をすべて読み直す。

- 語尾や助詞を、鉤括弧で括って名詞のように使っていないか
- 見出しと導入文を、主語・目的語・述語の3つに分解できるか
- 曖昧語を使っていないか

Step 9: 締めの前に確認する

- 主張を1文で表現できるか
- 大きい要素は2〜3個か
- 出典は要素の直下にあるか
- 強調は1か所か
- 列の役割は他の枚と同じか
- 同じ意味の語を、別の語で書いていないか
- 見出しと直下の1文が、同じことを2回言っていないか
- 英語の識別子・術語が、日本語より大きい文字になっていないか
- 枚数・ラベル数・通し番号の3つが一致しているか
- テーマを貼り替えただけで、色の直書きが残っていないか
- 図のどれかが、文字を枠で囲んだだけになっていないか

ガードレール

- 描画していない枚を出さない。HTMLを書いただけで公開しない
- 1枚ずつ直す。指示された枚だけを直し、他の枚へ勝手に広げない

- margin-top:auto で高さを揃えない。不自然な余白が空く
- 定義していない抽象語を使わない。その語が何を指すかを読み手が復元できること
- 同じものを指す語を増やさない。一度決めた語を使い続ける
- 色をテーマの外に書かない。枚のCSSにも、図のコードにも直書きしない ── 正本は references/themes/ の1本である
- テーマを混在させない。1つのデッキへ適用するテーマは1本だけ
- テーマを増やす前に、既にある4本のどれでも足りない理由を言う
- 文字だけの図を置かない。枠と文字しか無いものは、図ではなく表である
- 原典で確認していない数値を載せない
- 語尾や助詞を、鉤括弧で括って名詞のように使わない。声に出して読んで意味が通る文だけを置く
- 原稿を持つデッキを、スライドだけ ・ 原稿だけで直さない。食い違いは、片方だけを読む限り検出できない

- 図の形を判定する前に、余白や文字の大きさの調整へ入らない。形が誤っていれば、調整は無駄になる
- 図に置いた具体を、原稿から外さない。原稿で説明した要素を、図から外さない

意思決定を、変更前と変更後の差分ごと記録するSkill：acdr

ACDR は Any Change Decision Record である。 分野を限定しない ── 何を決めたときでも、変更前と変更後の差分ごと残す。

目的

何かを決めたとき、決定と、その差分と、なぜそう決めたかを1枚へ保存するために使用する。文書・コード・設計・方針のいずれでもよい。分野を問わない ── この Skill は、対象が何の仕事に属するかを認知しない。

人は、変更前と変更後が見えていると判定が速い。 差分が無いまま承認を求めると、「この決定は何を土台にして決まったのか」を読む側が毎回復元することになる。成熟した環境では、決定の大半が既存のものへの変更である。だから差分を既定にし、新規のときだけ差分が空になる。

残すのは、承認の前と後で同じ1枚である。 状態が proposed から accepted へ変わるだけで、記録の形は変化しない。リポジトリに置くので、差分に載り、変更の理由がPRに出力される。

役割

- 決定を、4つの節（決めたこと ・ なぜ決める必要があるか ・ どう変わるか ・ 比較した案と採らなかった理由）にする
- 変更を1件ずつ、どこ・何から何に・なぜの3つ組にする
- 対象の文書を描画し、変更箇所を押すと変更前と理由が開く形にする
- 理由が欠けている変更を、記録に包含しない
- 正本へ適用する前に見せ、承認を得てから適用する
- 承認が下りたら状態を accepted にして、リポジトリへ保存する

処理対象と成果物

処理対象

これから決めようとしていること。多くは既存の文書・コード・設計への変更で、新規のこともある。

成果物

記録1件は、フォルダ1つである。

.acdr/<番号>-<短い名詞句>/
  acdr.json    ← 正本。節と、変更の3つ組を保持する
  flow.svg     ← 図（組ませた相手が返す。無い場合は配置しない）
  index.html   ← 組成した成果物。acdr.json から導出される

acdr.json が正本で、index.html は導出されるものである。 同じ acdr.json から、実行場所に依存せず同一の index.html が出力される。

中身を複製しない。 変更後の全文は対象の文書が保持している。記録が保持するのは、節と、対象のパスと、3つ組だけである。

index.html を手で直さない。 正本は acdr.json である ── 手で直すと、次に組成した時点で失われる。

承認済みの記録は封印される。 承認後の最初の組成で、対象の文書の sha256 が acdr.json へ保存される。以降、対象の文書が変化した状態で生成し直そうとすると拒否する ── 生成し直すと承認時点の姿が失われる。--check はその場合に「承認時点の姿である」と報告する。意図して生成し直す場合は --force を渡す。

入力の想定

受け取る情報解釈・既定値
決めようとしていること明示されなければ、直前の会話から決定を書き起こす。推測で補完しない
対象の文書明示されなければ、変更しようとしている文書すべてを対象とする。無ければ新規として扱う
変更前の内容正本の現在の中身をそのまま取る。適用済みなら、gitの作業ツリーとHEADの差から取る
なぜ明示されなければ、そのとき何と食い違っていて何に一致させたかを書き起こす
除外した案明示されなければ、検討した案と、それぞれ何が成立しないかを記述する

実行手順

Step 1: 何を出す文書かを、外から取る

その文書が何を出すべきかは、その文書の中には無い。中から取ると、旧路線の記述が旧路線を残す根拠になる。成果物を決めている親文書・定義票・仕様の記述から取り、見出しの並びだけで出すものが出るかを判定する。出していなければ、本文の校正に入らず構造の案を先に出す。

Step 2: 対象の全文を読む

頭から終わりまで確認する。検索で見当を付けて周辺のみを確認する方法を採用しない ── 置換のすり抜け、説明なしで残った旧い値、見出しと中身の食い違いは、どれも検索では検出されない。

Step 3: 節を記入する

上部の節は4つだけである（ACDR 0045）── 読み手は、決めたこと ・ なぜ ・ どう変わるか ・ 何と比べたかだけで判定できる。
具体の変更箇所と理由は、下のファイルごとの差分が持つ。

節キー中身
決めたことdecision決めてほしいこと1件。能動態の完全な文で、手段を記述しない
なぜ決める必要があるかwhy何と食い違っていて、何に一致させたか
どう変わるかfigure ・ figure_caption ・ shift図と、抽象の側の変更前と変更後（what ・ from ・ to）。この Skill は描画しない ── 図は design-svg が生成する
比較した案と、採らなかった理由alternativesoption と why_not。反証を通過しなかった案であり、未解決の懸念ではない
状態（見出しのバッジ）statusproposed ／ accepted ／ superseded
置き換えた記録supersedesこの決定が置き換えた記録の番号

how ・ applies_to ・ after_approval は、過去の記録のために形に残してあるが、描画しない。新しい記録に書かない ──
手段と適用先は、下のファイルごとの差分の変更箇所と理由が示す。

キーは ASCII で、値は人が読む日本語である。 機械が分岐するもの（キー ・ status）と、
人が読むもの（本文）を、同じ文字体系に混在させない。

decision ・ why ・ alternatives の3つは、欠けたらツールが停止する。 欠けた記録は、あとから誰も補完できない。比較した案が無いことと書き忘れは、読み手には同じに見える。

Step 4: 変更を3つ組にする

1件ずつ、どこ（読み手がその場所を開ける粒度）・何から何に（変更前の原文をそのまま。要約しない）・なぜを完備させる。書けない変更は記録に含めない ── 書けないのは、変更の意図が自分でも掴めていないということである。削除も1件として扱い、消えた場所に印を配置する。

「変更前」と「なぜ」は平文である。 タグを書いても文字として出る ── 「変更前」は原文をそのまま出す欄なので、タグを解釈してはならない。節（決定 ・ 対象 ・ なぜ）のほうは HTML を受ける。

「どこ」は、描画したあとの本文に現れる文字列で指定する。 マークダウンの記法を含めると一致しない ── 描画後は <b> や <code> になっている。

Step 5: 作業コピーへ適用して、1枚を生成する

正本は触らない。作業コピーへ適用してから組成する。操作は3つだけである。

acdr new .acdr/0007-<短い名詞句> "題"    起こす（雛形から）
acdr inspect .acdr/0007-<短い名詞句>     入力を検査する
acdr render .acdr/0007-<短い名詞句>      組む
acdr render .acdr/0007-<短い名詞句> --check 1   差が無いかを検査する

CLI は1つである。 どの操作も --json を付けると機械が読む形で出て、終了コードは 0 正常 ／ 1 検出あり ／ 2 誤用である。

acdr.json の形は references/acdr.schema.json が決め、雛形は references/spec-template.json が保持する。生成物ではなく、入力を検査する ── 生成物の検査からは、複製が正しく生成されたことしか判明しない。しかも不合格の時点で HTML は既に出ている。不合格なら HTML を1バイトも出さない ── 検査は4系統で、形（スキーマ）・欄の完備（節と3つ組）・散文（1つの欄への主張の同居 ・ 1文の長さ ・ 見出しや表の混入。引用と原文は除外する）・参照の解決（図と対象の文書の実在）である。

ファイルの差分の見せ方は、拡張子で決まる。

拡張子置き方
.md描画した見た目。印は語の単位で付く
コード（.py ・ .js ・ .json ・ .go ・ .cs ・ .rs ・ .rb ・ .sh ・ .sql ・ .yaml ・ .toml ・ .css ・ .xml ほか）Git の統合差分。旧と新の行番号 ・ + / - ・ 文脈3行。印は行の単位で付く
それ以外（.html など）そのままの見た目。CSS を隔てるので iframe へ流し込み、届かなければ Shadow DOM へ切り替える

docs が空なら、節だけの1枚になる。

新しい種別の枠を追加する場合は、タブの押す処理の配線と、枠の挿入先の2点を確認する。 どちらが欠けても印は開かない ── ファイルの種別を増やす操作は、配線と挿入先の2か所へ同時に及ぶ。

Git は差分を出すが、なぜ変えたかを出さない。 そこを補完するのがこのツールである ── まとまりごとに理由を添え、印を押すと開く。変更前は - の行が示すので、before の記述は省略してよい。

変更前は git show <rev>:<パス> で取得する。 記録へ複製しない。rev の既定は HEAD で、docs の項目に書くと変更できる。取得できない場合と差分が無い場合は、全文を置く。

理由が付いていないまとまりは、組成の検査が件数を出す。 差分の見出しにも表示する ── 0件にしてから提示する。

コードの印は行の単位である。 語の単位で付けると、色付けが挿入した要素と交差してどちらかが壊れる ── コードの変更は行の単位で読むものなので、行で足りる。

色付けは近似である。 構文解析を実施せず、行ごとに正規表現を適用する ── 文字列の中の予約語のような事例は取り違える。読解の補助であり、判定の根拠にしない。

冪等である。 docs のパスはリポジトリの根から解決するので、どこから実行しても同一のものが出力される。--check は生成し直した結果と index.html を比較し、差が在れば 1 を返す。

Step 6: 開いて閉じることを確認する

描画して、実際に押す。1度押すと変更前と理由が出て、2度押すと閉じる。「すべて開く／閉じる」も両方向とも動作する。印が内側のタブに隠れることがある ── タブの先頭の一覧から、押してその印まで運べることを確認する。

Step 7: 理由の欠けを確認する

「なぜ」が「一致させるため」だけになっていないか（何と何を一致させたかを書く）。変更内容の言い換えになっていないか。変更前が要約になっていないか。

Step 8: 見せて、承認を得てから適用する

1枚を渡し、返事を待つ。「適用しました。確認してください」と記述しない ── それは承認ではなく追認を求めている。

承認が下りたら、状態を accepted にして生成し直し、正本へ適用し、.acdr/ の1枚と索引をコミットする。差し戻されたら3つ組を直して Step 3 から再実行する。止められた場合は適用しない。

後の決定が、この決定を置き換えたときは、古いほうの状態を superseded にし、置き換えた記録を指す ── 消さない。

出力形式

1枚のHTMLである。 先頭に節、その下に対象の文書が並ぶ。チャットには次のみを記述する。

ガードレール

- 中身を複製しない。 変更後の全文は対象の文書が保持する。記録が保持するのは節と3つ組だけである
- 対象が何の仕事に属するかを、この Skill が認知しない。 特定の分野の語彙・規則・スキーマを持ち込まない ── 使う側がこの Skill を呼ぶのであって、この Skill が使う側を知ることはない
- 何を出す文書かを、外から取得してから改訂する。 文書の中の記述を、その文書を直す根拠にしない
- 構造が合っていなければ、本文を直さない。 先に構造の合意を取る
- 対象の全文を読んでから直す。 検索で見当を付けて周辺のみを確認する方法を採用しない
- 正本へ適用する前に見せる。 適用してから提示しない
- 理由が欠けている変更を包含しない。 推測で理由を補完しない
- 変更前を要約しない。 原文をそのまま保持させる
- 比較した案を削除しない。 案と、採らなかった理由を保存する
- 節の語を負の側へ偏向させない。 「除外」「負担」ではなく「比較した案」と記述する ── 負の語が残ると、未解決の懸念が存在すると読解され、承認の判定が遅延する
- 抽象の側の変更前と変更後を記述する。 枠が保持するのは具体の差分である ── 抽象の対比が欠けると、下に並ぶ差分が何のためかを読み手が復元することになる
- 図を省略しない。 形の変化を図で確認できる形式にする。描画はこの Skill が実施せず、SVG の文字列を受け取るのみである
- 状態を自由文にしない。 proposed ／ accepted ／ superseded の3つ以外を書かない ── 自由文にすると、承認されているかを読む側が判定することになる
- 置き換えられた記録を削除しない。 superseded にして、置き換えた記録を指す
- 新規を例外として区別しない。 差分が存在しない決定も同一の形式で、docs を空欄とする
- 描画して押すまで出さない。 開閉が動作することを目視で確認する
- 正本から生成される生成物があるときは、描画した生成物を先頭の面に置く。 正本（JSON など）の差分だけでは、画面でどう変わるかを読み手が頭の中で再現することになる ── 正本の差分は2つ目の面に残す
- 変更箇所は、初めから開いて出す。 印に地の色を付け、印を囲む畳まれた節も開く ── 閉じて出すと、どこが変わったかを1件ずつ押して探すことになる
- 畳まれた節の中の印も、一覧から開ける形にする。 見えているかを offsetParent で判定しない ── 閉じた <details> の中でも値を返す
- 色・寸法を直書きしない。 見た目は references/tokens.json が保持するトークンから引く ── 直書きすると、配色を替えたときにそこだけ取り残される。トークンの正本は1つである ── 2か所に書くと、どちらが正しいかを毎回確認することになる
- 入力の検査を、生成と同じ場所に置かない。 生成が検査を兼ねると、不合格の判明が生成物のあとになる ── 不合格なら HTML を1バイトも出さない
- 決定の文に手段を混在させない。 決定は「何を採るか」で、手段は下のファイルごとの差分の変更箇所と理由が示す ── 手段だけを上に置くと、下の差分が何のためかを読み手が復元することになる
- 差し色を1つに限定する。 状態のラベル（承認済み）以外に別の色を使わない ── 1本だけ違う色の線が在ると、意味が在るものとして読解される
- 題を二重に出さない。 題は節が持ち、枠の見出しには出さない
- 生成物に文字コードを宣言する。 <meta charset="utf-8"> を先頭に置く ── 無いとHTTPで配ったときに推測になり、化ける
- 承認済みの記録を生成し直さない。 記録は承認時点の姿である ── 後に対象の文書が変化しても、記録はその時点を保持する
- 外部のCDNやスクリプトを参照しない。1枚で完結させる

目的

決めることがある問いに論点を立て、案を出し、提示の前に自分で反証して1つに絞り、承認だけで決められるブレストボードを1枚作る。

進捗は決着である。 案の数でも論点の数でもない。論点に答えが付いていても、1件も決着していないなら進んでいない ── 未決のまま相互に依存する論点が増えるほど、1つ動かすと全部を再確認することになる。

役割

- 論点を3〜5件立て、依存の順序を自分で持ち、いま見る論点を示す
- 案を複数出し、提示の前に反証して1つに限定する
- 答えの直下に完成イメージを置き、裏づけを開閉式で添える
- 事実は自分で調べる ── 利用者へ渡すのは決定だけである
- 承認・差し戻し・書き足しを受け取り、決着まで進める

処理対象と成果物

処理対象

決めることがある問い。方針・設計・構成をまだ決めていない状態。

成果物

ブレストボード1枚（HTML）。先頭に現在地のタブ、そのあとに論点ごとのタブが並び、開いている論点だけが回答欄を持つ。

承認の画面を別に作らない。 別ページにすると、開いている論点の中身が2か所になる。

置き場所は .brainstorming-board/<ブレストボードの名前>/ である。1つのブレストボードが、生成のもとになる雛形 ・ 図 ・
取得した原文の取り直し方 ・ 回答の蓄積先を、同じ1つのフォルダに持つ。

入力の想定

受け取る情報解釈・既定値
テーマ1〜2文で確認してから始める。論点はこちらで立てる
回答（承認 ／ 差し戻しの理由 ／ 書き足し）論点ごとに1件。論点に対して決定は1つだからである

実行手順

Step 1: ブレストボードの置き場所を作る

雛形は、契約の全部の欄を持って出る。 使わない欄は消せばよいが、そこに何が置けるかは雛形が示す ── 示さないと、欄が在ることを誰も知らないまま書き始める。

brainstorming-board init <ブレストボードの名前> [--title <題>]

.brainstorming-board/<名前>/ に、入力の board.json と figures/ ・ rounds/ ・ sources/ ・ answers/ を置く。この下に生成の実装を置かない ── 生成するのは Skill 側の tool/business_logic/src/render.rs である。

既に在る名前は作り直さない。上書きすると、書いた論点が消える。

Step 2: 論点を立て、依存を自分で持つ

3〜5件立てる。どれがどれに依存するかを自分の側で整理し、利用者へ渡さない ── 順番の管理は承認する側の仕事ではない。

Step 3: 案を出し、提示の前に反証して1つに限定する

複数考え、見せる前にそれぞれを攻める。除外した案は捨てず、名前と「何が壊れるか」を残す。残った1つが答えになる。

反証の過程で論点の軸そのものが変わることがある。変わったら、そのことも書く。

案が最初から1つなら、論点の立て方が誤っている。 絞るのは反証の結果である。

Step 4: 出す直前に、論点をまたいだ整合を検査する

型何を確認するか
基準の違反自分で立てた基準（回避条件・必要条件）を、下流の論点の答えが充足しているか
条件の違反決めた条件に、下流の答えが違反していないか
置き場所の重複同じものを2か所へ置いていないか

入力へ型の契約を適用する。 tool/business_logic/src/validate.rs が、1つの欄に主張が同居している状態 ・ 長すぎる1文 ・ 見出しや表の混入 ・ 解決しない参照を検出する ── 不合格なら HTML を1バイトも出さない。

論点ごとの反証では、これは検出できない。 反証は1つの論点の中で閉じているので、前の論点の結論に下流が違反している状態は見えない。

Step 5: 出す直前に、承認者の目で全文を点検する

書き手は判断の根拠を保持しているので、読み手の判断を妨げる表記を検出できない。
書いた文を、承認者の判断基準で解釈し直してから出す。

承認者の判断は1つの問いで進む ── それは、この決定を覆すか。
点検は、その問いに回答できる状態かを検証する。

点検する不変条件破れている状態
語の含意が、対象の性質と一致する否定の含意を持つ語が、否定でない対象に付いている
節の名前と、中身の対象が一致する名前が示す範囲と、中身が求める行為が食い違う
各項目が、承認者の問いに答えている覆すか否かを、読み手が推測することになる
1つの欄に、1つのことだけが入る1つの欄・1文に、主張と説明が同居する
ふだん使う言葉で書いている原典の訳語や技術用語を言い換えている。ふだん使わない和語 ・ 漢語や、作った語がある

Step 6: ブレストボードを生成して出す

前提が片付いた問いだけを並べる。依存が開いている問いは、この回には出さない。

現在地に「いま見る論点」を置く。 deck() へ queue を渡すと、いま見る論点だけが回答欄を持ち、待ちの論点はタブが薄くなる ── どれに答えるかを利用者に判定させない。 依存を自分で持つことと、示すことは別である。

答えの直下に完成イメージ（図、実例、または変更前後の差分）を置く。節の見出しはツールが作る（生成した文言を後から照合して書き換えない ── 文言を1字直した瞬間に、書き換えが無言で不成立になる） ── 「この答えの完成イメージ ── 図2枚と、実例」のように、中に何が在るかをツールが数えて書く。手で見出しを書かない ── 書くとボードごとに形が変わる（入力の検査が検出する）。語を1つ導入したら、その実例を置く ── 上流の論点で決着した語を、説明せずに下流で使わない。実例は Topic.example が持ち、図と同じ扱いにする ── 開閉式にすると、実例を探索しながら結論を読解することになる。折り畳む対象は、裏づけだけである ── 完成イメージは開いたまま出す。<b>実際に、裏づけと同じ折り畳みへ入れていたので、「図と完成イメージから全くイメージがわかない」と差し戻された。</b>置くのはできあがるものだけで、判断の過程（判定の基準 ・ 論証 ・ なぜそう決めたか）は裏づけへ移す。過程が混ざると、読み手は結論を探しながら読むことになる。

裏づけは4つの節にまとめる ── この答えが残った理由（反証を通過した案と除外した案）／ 前提（根拠）／ この答えが扱わない範囲（と、在れば未修正の誤り） ／ 経過（道筋・反証で分かったこと・要求事項）。結論は1つ目の節だけから出る。他は前提・危険・履歴であって、論証ではない。開閉式にしてよいが、無くしてはならない ── 根拠を見ないまま押した承認は、承認になっていない。

同じことを2つの節に書かない。 節を増やすと、どれが論証かを読み手が開いて判定することになる。

Step 7: 回答を受け取る

送信では、こちらのターンは始まらない。 送ったあと利用者に一言もらう必要があることを、画面にも書く。

Step 8: 差し戻されたら、まず既存の答えを直せるかを確認する

収まらないときだけ論点を足し、そのときは利用者に確認する。 差し戻し1件ごとに論点を足すと、決着しないまま相互に依存する論点が蓄積する。

答えを作り直すときは、案を並べ直すのではなく直した答えを1つ出す。前の答えは消さず、閉じた状態で当時の完成イメージと差し戻しの理由（利用者の言葉そのまま）を付けて残す ── 前の答えのほうがよかったとなったときに戻れなくなる。

答えが動いていない節は書き直さない。 1行の変更に全節を書き直すのは、変更の費用を測っていない状態である。

Step 9: 決着させ、次に答えられる問いを選び直す

決着にしてよいのは、その答えが実際に使われた場合だけである。 使うのは下流の論点か、外の作業（試作・実装）である ── 末端の論点には下流が無いので、そこでは外の作業が試す相手になる。 自分でやる反証は、自分の想像力の範囲までしか届かない ── 本物の試験は、下流が使って違反が出るときに起きる。

決着したことで答えられるようになった問いが次の回になる。なぜいま開いたのかも一緒に示す。

Step 10: まとめる

答えられる問いが尽きたら、決まりの一覧・次にすること・保留を現在地へ並べる。保留は正当な着地点である。

現在地は3つで作る。

欄何を置くか
introボードが何を決めるかの1文。決まったことの一覧をここへ置かない ── 論点の一覧と重なる
queueいま見る論点と、なぜいま開いたか
panels集約した論点の行き先など、論点に属さない補足

出力形式

ブレストボード1枚。ツールが要求する形は次のとおりである。

- 出どころには種別を付ける ── 実測 ／ 原典 ／ 決まり ／ 前提 ／ 未確認。どの種別にも該当しないものは、根拠として置かない
- 原典の種別は、原文を取得しているときだけ付ける。 取得の依頼が配線されていればそれを委譲し、無ければ自分で取得して残す ── 取得していない原典に種別だけ付けると、その種別は何も指さない
- 根拠は3つを備える ── 答えのどこを支えるか ／ もとにしたこと ／ その出どころ
- 情報の型が、表現の形を決める ── 根拠は表、道筋は番号を打った連鎖、除外した案は表、図は図。分かったことと要求事項も表である（何が分かったか ／ だから何が決まったか）
- 1つの欄に2つのことを詰めない ── 「主張 ── 説明」と書いたものは、ツールが2行へ割る。上が主張、下が説明で、読む順が欄の中でも統一される。引用は割らない（原文の形を変えない）
- 閉じた前の答えは3行の表にする ── 前の答え ／ なぜ作り直したか ／ 利用者の言葉（そのまま）。prev() が作る
- 答えや軸が変わった箇所は印にする。 押すと変更前と理由が開く
- この回で変わったところを、ブレストボードが自分で示す ── 前の回の生成物を snapshot() で保存し、次に生成するとき deck(prev=…) へ渡す。保存は、回を進めるときだけ行う ── 比較の基準が生成し直しのたびに前進すると、差分が常に空になる。変わった欄だけが色づき、押すと前の回の中身が開く ── どこを直したかを、書き手が文章で言うのは仕組みではない
- 変更の一覧は、どの画面からでも開ける ── 画面の端につまみを置き、押すと引き出しが出る。行を押すとその論点へ跳び、印まで運ぶ。現在地の節だけに置かない ── 他の論点を見ているあいだ、何も見えなくなる
- 差し戻しの理由と書き足しは自由文にする。 よく使う理由をボタンで入力できるようにしてよいが、値そのものは限定しない ── 限定した値の集合は、差し戻しの理由の集合を包含しない

ガードレール

- 案を並べて選ばせない。選ばせるのは判断の移譲であって、承認ではない
- 事実を利用者に聞かない。調べれば分かることは自分で調べ、直して報告する
- 除外した案を黙って消さない。消すと、選択肢を潰したことに誰も気づけない
- 決着した論点を別のページへ移さない。後の論点は、前の決着を前提にしている
- 記載を2か所に持たない。散文の記録とブレストボードの両方に同じ論点を持つと、片方だけが動いたときに誰も気づけない
- 反証しうるものを「扱わない範囲」へ置かない。そこに在ってよいのは、<b>反証を通過した後に残存したもの</b>だけである ── 反証しうるものが発見されたら、それは欠陥ではなく反証が未了の証左なので、完了してから提示する。完了不能なら、それは依存であって、その論点は提示しない
- 扱わない範囲に扱いを付与せずに、承認を求めない。対象外 ／ 後続で決定 ／ 解消済 のどれかを1件ずつ添える
- 扱いは、承認者の問いに答える語にする。承認者の問いは「<b>それはこの決定を覆すか</b>」の1つである ── 答えを読み手に推測させない。節の先頭に、覆さないという判定そのものを置く
- 語の含意を、対象の性質に一致させる。否定の含意を持つ語は、否定の対象にだけ使う ── 一致しないと、読み手は対象の性質そのものを誤って解釈する。性質の異なるものは、節を分離する（制約は weaknesses、誤りは defects）
- 図を省かない。文字だけで説明すると、読み手が頭の中で像を作り、そこで解釈がぶれる
- 図は、描いたツールの検査を実行してから、描画して目視する。検査はツールごとに違う ── 生成させた相手が持つ検査と、絶対座標で描いた図を検査する figures である。どちらの検査も、注記が主張として読まれることや、配置の選び違いは検出しない
- 決まりが変わったら、図も一緒に直す。文だけ直すと、ブレストボードの中で食い違う
- 図は、この Skill が描かない。受け取るのは SVG の文字列だけで、どう描いたかを認知しない。描くのは呼ぶ側である
- 散文のガードレールは破れる。機械で見られるものは機械に見させる ── この文書の規定のうち6件は tool/business_logic/src/audit.rs が検査する
- 承認者の目で全文を点検してから出す（Step 5）。書き手は判断の根拠を保持しているので、読み手の判断を妨げる表記を検出できない
- 合意を急かさない。差し戻しは失敗ではなく、正常な使い方である
