schema-driven を新しい契約だけの基盤にする

決めたこと

schema-driven を、新しい契約だけを持つ基盤にする。正本はすべてソースの側に置き、Skill には配布物を作る段で入れる。

なぜ決める必要があるか

schema-driven は、すべての Skill の土台になる基盤である。ACDR 0165 ・ 0166 で、エンジンは名前でスキーマを引く形になった。一方で Skill のフォルダは、契約の版3（tool.json の contract 3、bin/、mcp.json、references/、Skill の中の tool/）のままだった。エンジンにも、名前でない $schema をファイルからの相対パスとして読む分岐が残っていた。新しい契約の形はまだ一度も配っていないので、古い形を読む理由が無い。土台が古い形のままだと、その上に Skill を移す作業が始められない。ソースを Skill の外の src/<Skill>/ に置き、実行ファイルを配布物の段で scripts/ に入れる形は、ボード skills-creator-rebuild の論点4で決めた。基盤のスキーマとカタログは、エンジンがビルドのときに取り込むソースの一部で、実行するときに Skill の assets/ を読む者はいない。だから正本をソースの側に置き、Skill へは配布物の段で同梱する。tool.json は、skills-creator が作る Skill が、使う abstract の版とエンジンの場所を書く宣言で、型も skills-creator が持つ。schema-driven はそのエンジン自身で、skills-creator が作るものではないので、tool.json を持たない。基盤のスキーマを references/ に置くとしたボード schema-driven-build の論点6 ・ 7は、この決定で改める。基盤の実装は Rust だけで、署名付きの実行ファイル1つで配る（ボード skill-roles の論点3）。エンジンを別の言語で作り直す前提が無いので、言語を替えるための試験データの JSON と implementation.json も残さない。

構造化データを正本として持つ基盤の Skill：schema-driven

目的

AI が扱うデータを、JSON Schema とそのインスタンスで持つときに使う。Markdown の文書は、書いたものが形を満たしているかを機械で確かめられない。スキーマとインスタンスなら、書いたその場で検証でき、参照と導出値も検査できる。

この Skill は基盤である。何のデータを持つかは決めない。

誰が何を持つか
基盤（この Skill）abstract スキーマ（assets/ の契約）と、それを版ごとに守るエンジン（共通ツール9つ）
使う側（基盤の上に作る Skill ・ Agent）concrete スキーマ ・ インスタンス ・ ページテンプレート ・ 固有のツールの宣言（tools.json、任意）

使う側はコードを持たない。 見た目と操作は基盤の部品のカタログが持ち、固有の処理は宣言した別の実行ファイルが持つ。abstract スキーマを書き換えると、エンジンが扱えなくなる。

役割

- concrete スキーマが abstract スキーマの版に従っているかを検査する
- スキーマからインスタンスを作成し、未記入のプロパティと、その x-prompt を返す
- JMESPath 式で値を取得し、JSON Patch で更新する。更新は、検証エラーが無いときだけ書く
- ディレクトリのインスタンスを検証し、x-ref（参照）と x-derive（導出値）を検査する
- 検査を通ったインスタンスのパスとハッシュ値を、承認記録へ書く
- 検証を通ったインスタンスを、ページテンプレートと部品のカタログでページへ描画する
- 使う側が宣言したツールを、決められた境界の中で起動する

処理対象と成果物

処理対象

concrete スキーマと、それに従うインスタンスのディレクトリ。スキーマは x-abstract に従う abstract の版を、$id に自分の名前を書く。インスタンスは $schema に、そのスキーマの名前を書く。

成果物

成果物どこに書くか
インスタンス渡したパス
検証と検査の結果標準出力（JSON）
承認記録検査したディレクトリの approval.json
ページ渡した出力のディレクトリ（インスタンス1件につき HTML 1枚）

入力の想定

受け取る情報解釈・既定値
スキーマ ・ インスタンス ・ ディレクトリのパス明示されなければ受け付けない。相対パスは、CLI を起動した場所から解決する
ページテンプレートのディレクトリ（render の --pages）明示されなければ、kind が document のインスタンスだけを描画できる
読んだ時点のハッシュ値（update の --hash）明示されなければ、update が読んだ時点のハッシュ値で書く。ほかの更新と重なりうるときは渡す
Skill のフォルダ（--skill）明示されなければ、共通ツールだけを出し、スキーマの名前はエンジンが持つものだけを引く。渡すと、そのフォルダの tools.json で宣言したツールも出し、その Skill のスキーマを名前で引く

実行手順

ツールは、CLI の実行ファイル scripts/schema-driven と、MCP のサーバー scripts/schema-driven-mcp の両方から、同じ名前と引数で呼べる。MCP の登録はツールごとに形が違うので、導入するときに行う。一覧は次で取れる。

scripts/schema-driven --json

Step 1: concrete スキーマを書き、abstract に従っているかを検査する

スキーマの根に、次の3つを書く。書き方の決まりは assets/meta-schema.json が持つ。

欄書くもの
$schemaJSON Schema の標準の dialect https://json-schema.org/draft/2020-12/schema
x-abstract従う abstract の版 schema-driven/abstract@v1
$idこのスキーマの名前「<Skill の名前>/<種類>@<版>」。インスタンスを作るスキーマ（x-generates を持つもの）は必ず書く

プロパティごとに description と x-prompt（read と write）を書き、参照には x-ref、導出値には x-derive を付ける（assets/annotations.schema.json）。

ほかのスキーマの定義を使うときは、$ref をファイル名ではなく名前で書く。同じ Skill のスキーマなら、$id を基準に JSON Schema の規則で解けるので、「<種類>@<版>」だけでよい（例：term@v1#/$defs/short）。ファイル名を変えても、参照は切れない。

scripts/schema-driven check-schemas --dir <スキーマのディレクトリ>

findings が空なら、契約に従っている。版を書いていないスキーマと、エンジンが扱わない版のスキーマは、検査せずに指摘する。

スキーマのフォルダに公開の記録 published.json（assets/published.schema.json）があれば、check-schemas は公開した版の指紋といまの中身を比べる。

状態check-schemas の返し方
公開した版の中身が変わったfindings に「公開した版が書き換えられている」
公開した版が消えたfindings に「公開した版が無い」
まだ記録に無い名前unpublished に名前と指紋。公開するときに、そのまま記録へ足す

指紋は、キーの順と空白に左右されない SHA-256 である。名前（$id）を持つ JSON は、ファイル名が .schema.json で終わらなくても対象になる。

Step 2: インスタンスを作成し、x-prompt を読む

scripts/schema-driven create --schema <スキーマ> --path <インスタンス>
scripts/schema-driven prompt --schema <スキーマ> --property /<プロパティ>

create は、必須のプロパティを空のままにしてインスタンスを作り、未記入のプロパティを x-prompt と一緒に返す。インスタンスの $schema には、スキーマの名前を書く。x-prompt の write の決まりに従って値を決める。

インスタンスを読むツールは、$schema の名前から次の順にスキーマを引く。

名前引く先
schema-driven/…エンジンが持つスキーマ（文書 ・ ページテンプレート ・ カタログ ・ 宣言など）。--skill を渡さなくても引ける
--skill の Skill の名前で始まるものその Skill の assets の下の *.schema.json のうち、$id が同じもの
ほかの Skill の名前で始まるものどの Skill のスキーマかを返して止める。その Skill を --skill に渡して検査し直す
名前の形でない値断って「スキーマの名前でない」を返す。パスでは引かない

同じ名前のスキーマが2つあれば、どちらも使わずに止める。

Step 3: JSON Patch で更新する

scripts/schema-driven update --path <インスタンス> --patch '<JSON Patch>' [--hash <読んだ時点のハッシュ値>]

未記入以外の検証エラーがあれば、書かずに errors を返す。直して、もう一度送る。未記入が残っているときは書いて、残りを x-prompt と一緒に返す。

値を読むときは get を使う。

scripts/schema-driven get --path <インスタンス> --query '<JMESPath 式>'

Step 4: ディレクトリを検査する

scripts/schema-driven check --dir <インスタンスのディレクトリ>

終了コード 0 は、検査を最後まで実行できたことだけを示す。 合格かどうかは、instances の errors と unfilled、findings の status（合格 ・ ずれ ・ 確かめ直し など）で見る。

Step 5: ページテンプレートを書き、描画する

ページテンプレートは、節の並びと、節ごとに置く部品と、値を取る JMESPath 式だけを書いた JSON である（assets/page.schema.json）。部品は、部品のカタログ（assets/catalog.schema.json）の名前で呼ぶ。HTML ・ CSS ・ JS は書かない。

scripts/schema-driven render --dir <インスタンスのディレクトリ> --out <出力> [--pages <ページテンプレートのディレクトリ>]
インスタンスの kind描画のしかた
document基盤の文書の契約（assets/document.schema.json）を、カタログの部品 document で描く
そのほかの種類その種類のページテンプレート（--pages）が並べた部品で描く
ページテンプレートが無い種類1ページも書かずに失敗する

カタログに無い部品や、部品の入力の欠けがあれば、1ページも書かずに失敗する。検証エラーが1件でもあれば描画しない。内容が変わったページだけを書くので、同じ入力から何度描画しても結果は変わらない。

インスタンスの値は、HTML を含んでいても文字として出る。別の文書をその見た目のまま見せるときは部品 embed を使い、script の動かない枠に入れる。

Step 6: 承認を記録する

scripts/schema-driven approve --dir <インスタンスのディレクトリ>

検証エラー ・ ずれ ・ 未記入が1件でもあれば、承認記録を書かない。

Step 7: 固有のツールを宣言する

共通ツールで足りない処理だけを、Skill のフォルダの tools.json（assets/tools.schema.json）で宣言する。宣言する前に、x-derive ・ x-view ・ ページテンプレートで書けないかを確かめる。

scripts/schema-driven --skill <Skill のフォルダ> --json
scripts/schema-driven --skill <Skill のフォルダ> <ツールの名前> --<引数> <値>

宣言したツールは、Skill のフォルダの中の別の実行ファイルである。言語は問わない。エンジンは次の境界を守って起動する。

境界決まり
起動の前実行ファイルの SHA-256 が宣言と合うこと。パスは Skill のフォルダの中の相対パスだけで、シェルを通さない
渡すもの標準入力に {"tool": …, "args": {…}} の JSON。環境変数は宣言した名前だけ
受け取るもの標準出力に、真偽の ok を持つ JSON を1つ。1 MiB まで
制限時間既定 30 秒、宣言で 300 秒まで。超えたら止めて失敗にする
終了コード0 ・ 1 ・ 2 だけ。それ以外は失敗にする

宣言したツールの中身が正しいかは、基盤は保証しない。使う側が自分の試験で確かめる。

出力形式

どのツールも、標準出力へ JSON を1つ書く。

終了コード意味出力
0実行できた{"ok": true, …}。中身はツールごとに違う
1拒否した ・ 失敗した{"ok": false, "reason": …, "detail": …, "errors": […]}
2使い方が違う{"ok": false, "reason": "使い方が違う", "detail": …, "tools": […]}

動詞なしの --json だけは、ツールの一覧を {"ok": true, "findings": [], "data": {"tools": […]}} で返す。

ガードレール

- abstract スキーマを、使う側で書き換えない。エンジンは、版ごとの abstract スキーマに対する振る舞いだけを保証する
- 公開した版のスキーマを、消さず書き換えない。中身を変えるときは、版を上げた新しい名前（@v2）で足す。同じ名前で中身が変わると、前に書いたインスタンスが別のスキーマで検査される。公開するときは、その版の指紋を published.json に記録し、配る前の検査で確かめる
- インスタンスの $schema に、Skill の置き場所へのパスを書かない。名前で指す。配った先では、Skill は別の場所に置かれる
- ファイルを手で書き換えて、update を通さずにインスタンスを直さない。update を通さないと、書いたその場の検証が行われない。手で直したときは、check で確かめ直す
- check の終了コードだけで合格と判断しない。0 は実行できたことだけを示す
- 検証エラーのあるインスタンスを、描画や承認で先へ進めない。基盤はどちらも止める
- ページの見た目と操作を、使う側で持たない。足りない部品は基盤のカタログに足す。同じ働きの部品が Skill ごとに違う形になると、読み手はページを替えるたびに見方を覚え直す
- 部品のカタログは、デザインシステムに従う。トークン（基礎 → 意味 → 部品の3層と明暗）と、部品ごとの状態（通常 ・ 押した ・ 焦点 ・ 無効 など）の決まりを持ち、CSS に色の直値を書かない
- 使う側の種類を、基盤の文書の契約へ押し込まない。決まった並びがあるものは、使う側がスキーマとページテンプレートを持つ
- 基盤の中心は、ファイルを直接扱わない。入出力はポートを通す
- 基盤はネットワークに出ない。依存の版は1か所で決める
