依存の向きの検査ツールを内作する

決めたこと

許していない依存の辺を検出して止める検査ツール dependency-rules を、アーキテクチャに寄らない形で内作し、リポジトリ直下に CLI として置く。

なぜ決める必要があるか

Cargo は書いていない crate の使用と通常の依存の循環は止めるが、その辺を Cargo.toml に書いてよいかは知らない。semantic-agent-schema のアーキテクチャは許す辺の表を持つと決めたので、表と依存を突き合わせる検査が必要になった。第三者の cargo-deny も候補だったが、利用者が内作を選んだ。

どう変わるか

変更前と変更後

何が変更前変更後
依存の向きを止めるものCargo だけ。許していない辺はビルドを通るCargo と dependency-rules check。規則に無い辺は終了コード 1 で止まる
規則の形無い（アーキテクチャの頁の表を人が読むだけ）component と allow（任意の kinds ・ description）の許可リスト型。rules.schema.json（版つき）で公開する
言語との境目無い判定の中心は node と edge のグラフだけを受け取る。グラフの JSON は graph.schema.json（版つき）で公開し、cargo の読み取りもこれを通る

比較した案と、採らなかった理由

案採らなかった理由
cargo-deny の bans の wrappers で書く第三者のツールで、利用者が公式でないことを理由に内作を選んだ。ワークスペースの中の crate と dev の辺に効くかも確かめていなかった
cargo metadata と表を突き合わせる小さなスクリプトを semantic-agent-schema の中に書くアーキテクチャに寄らない検査にならず、ほかの利用者が使えない
層の並びだけで規則を書く（import-linter layers ・ ArchUnit layeredArchitecture）semantic-agent-schema の domain の中は並びにならず、search → validation を許してしまう
グラフの JSON を受け付けず、2つ目の言語が現れてから形を決める利用者が公開する前提で設計と実装をすると決めた

対象の文書に変更が無い決定である ── 差分は出ない。
