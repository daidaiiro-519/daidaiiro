道具の中の構成を契約から外す

決めたこと

skills-creator の契約と check が既定で守らせるのは、呼ぶ側から観察できるもの（呼び方と成果物の形）だけとする。道具の中の構成（層 ・ 依存の向き ・ 入出力の置き場所）は契約から外し、雛形が採る推奨の構成とする。

なぜ決める必要があるか

利用者から、skills-creator が依存の向きを強制しようとしていることに驚いた、と指摘された。利用者が多言語にしたい理由は、利用者が使いやすい言語で、skills-creator が作る Skill の道具と成果物の構成の契約が守られることである。Skill ごとに実現したいことは違うので、業務ロジックは同じにならない。契約は同じでも、中身までは指定しない。一方、check の2段目は、2026-09-26（コミット edd3499）から crate の分け方と依存の向きを不合格の条件にしていた。0056 と 0058 がそれをさらに強めた（4層 ・ 入出力の置き場所）。skills-creator-language の論点1で「層と許可辺」を契約に置いた決定も、同じ混同に立っていた。そこで、呼ぶ側から見えない規則を契約から外す。0058 の構成そのものは、雛形が採る推奨の構成として残す。雛形から生んだ Skill は、直後から動く出発点になる。構成を保ちたいリポジトリは、check に --layout 1 を渡して自分で有効にする。このリポジトリは、4層へ移した skills-creator にだけ、これを当てる。

道具の契約：tool-contract

目的

Skill が道具（実行ファイル）を伴うとき、呼ぶ側に形を推測させないために使用する。

道具ごとに呼び出し方の形が違うと、呼ぶ側は呼ぶたびに本文を読み直す。
契約は、呼び方を1つに固定する。

契約は、呼ぶ側から観察できるものだけを規定する（ACDR 0036）。道具を書く言語と、
配布するかどうかは、利用者に委ねる。言語ごとの実装の形は言語の組が持ち
（いまは references/profiles/rust.md だけ）、配布は任意の機能として
references/distribution.md が持つ。

置く先中身
契約（この文書）CLI と MCP の2つのプレゼンテーション層と起動のコマンド ・ CLI の規約 ・ 1つの道具の一覧から CLI と MCP を組む ・ MCP の規約 ・ Skill のフォルダの求め方 ・ 外部の道具 ・ 1段目の検査
言語の組実行ファイルの置き場所 ・ 雛形とその構成（推奨） ・ 組み立てのコマンド ・ 2段目の検査
配布（任意）配布物 ・ 導入スクリプト ・ 組み立ての定義

言語の組を作ってよい言語の条件は、公式の MCP の SDK が在ることだけである。
組が持つのは、雛形 ・ 組み立てのコマンド ・ ソースの検査の3つである。

原則

能力は1つ、呼び出し方は複数である。

能力を1つの道具の一覧に1度だけ書き、CLI と MCP はその一覧から組む。
能力を2か所に書くと、片方だけが古くなる。

呼び出し方が欠けても、能力は欠けない。
MCP の実装が無い環境では、MCP サーバーは立たず、CLI だけが動く。

modelcontextprotocol.io/specification/2025-06-18/basic/transports（2026-09-24 取得 ・ 297行）から引用する。

誤りの返し方 ── 原典

原典は2つを分けている（specification/2025-06-18/server/tools:389、2026-09-24 取得）。

種類原文この契約での対応
Protocol ErrorsStandard JSON-RPC errors for issues like: Unknown tools, Invalid arguments引数の不足 ・ 知らない動詞。SDK が返す
Tool Execution ErrorsReported in tool results with isError: trueok が偽のとき（読めない ・ 誤用）

findings は誤りではない。 検出が在っても isError は偽のままにする ── 違反の検出は、道具が正しく動作した結果である。

予期した失敗は、道具の結果として返す。 ok が偽なら CallToolResult の is_error を立て、こちらの文言を content に載せる ── 異常終了（panic）させると、呼ぶ側には理由が届かない。言語の組の雛形がこの形を持つ。

型は緩く受ける。 呼ぶ側は JSON の値を渡すので、数を文字列で包むことを強制しない（実測: timeout に 30 を渡すと、検証が不合格になっていた）。まとめて受ける引数は配列も受ける。

雛形が採る構成（推奨 ・ 契約ではない）

この節は契約ではない（ACDR 0059）。言語の組の雛形が、生んだ直後から動く出発点として採る構成である。
利用者は構成を変更してよく、skills-creator check は既定ではこの構成を検査しない。
雛形の構成を保つと決めたリポジトリは、check に --layout 1 を渡して検査を有効にする。

雛形は、サービス層を挟んだレイヤードアーキテクチャの4層で組む。依存は上から下へだけ向け、層を飛ばさない。

層置くもの依存してよい先入出力
プレゼンテーション層（CLI ・ MCP）呼び出し方。引数を受け、結果を印字し、終了コードを返すサービス層標準入出力と引数だけ
サービス層道具の一覧（名前 ・ 引数 ・ 説明）と、業務ロジック層の関数との対応。外部の道具を tool.json から読み、業務ロジック層へ渡す業務ロジック層持たない（例外は契約の実体 contract.rs が読む起動の設定だけ）
業務ロジック層判定と変換 ── 組み立て ・ 描画 ・ トークン ・ 検査などデータアクセス層持たない
データアクセス層ファイル ・ 外部の道具 ・ 通信の入出力無しここだけが持つ

サービス層を置くのは、プレゼンテーション層が2つ在るからである。 CLI と MCP の違いから業務ロジックを隔離し、道具の一覧を1か所に保つ。

データアクセス層を置くのは、入出力を1か所に集めるためである（ACDR 0058）。業務ロジック層は、読んだ値を受けて判定するだけになる ── データを処理する Skill が増えても、変わるのはデータアクセス層だけである。データアクセス層に判定を置かない ── 何を読み、読んだものをどう扱うかは業務ロジック層が決める。子プロセスの規律（上の節）は、データアクセス層が1回だけ実装する。

業務ロジック層に、集約 ・ エンティティ ・ リポジトリの型を作らない。 この層が置くのは、業務の状態を保持しない変換の関数である ── 層の名前から連想してドメインモデルの型を導入すると、使わない抽象が増える。

この構成を、ヘキサゴナルアーキテクチャともクリーンアーキテクチャとも称さない。 両者の核心は依存の向きを逆にすること（内側が抽象を定義し、外側が実装する）であり、この構成はそれを保持しない ── 業務ロジック層がデータアクセス層を直接呼ぶ。称すると、備えていない性質を名前で主張することになる。

ポートを導入するのは、業務ロジック層が使う外部を差し替える必要が生じたときに限る。 それまでは、実装が1つしかない抽象を作らない。ドメインモデルを必要とする Skill が現れたら、その Skill の道具だけをポートとアダプターへ移す ── 方式は Skill ごとに選んでよい。

どう保つかは、言語の組が決める（Rust は crate の境界に置き、各 Cargo.toml が依存の向きを宣言する。入出力の混入は --layout 1 の2段目が検出する）。

生成物を持つ Skill は、3つで組む

入力の契約 ・ 出力の型 ・ 組み立ての3つに分ける。 どれか1つに形が混ざると、
同じ Skill が出す成果物どうしで形が違ってくる（実際に、節の1つだけ別の入れ物で組まれていた）。

何を持つか置き場所
入力の契約何を書けるか。JSON Schemareferences/<名前>.schema.json
出力の型どう並ぶか。差し込む場所（{{名前}}）を持つreferences/<名前>.template.html
組み立て値を差し込むだけ。構造を作る文字列を保持しない業務ロジック層（型のファイルの読み込みはデータアクセス層が実行する）
JSON Schema  →  実体の JSON（値を埋める）  →  型（HTML）へ差し込む  →  生成物

差し込む場所の過不足は、その場で例外にする ── 埋め忘れも、余分な値も、出てから気づく形にしない。
型を読んで部品を組むのは、業務ロジック層の組み立てである。

検証で、組み立て側に構造を作る文字列が残っていないことを検査する ── 規定だけでは戻る。

- 例を規則本体へ混ぜさせない。例を添えるなら「例」と明示し、規則の文とは分離する ── 混ざると、読み手は例の範囲を規則の範囲として解釈する

- テンプレートファイルは assets/ ではなく references/ に置く
- 不要なフォルダは作らない。使うものだけ作る
- プレースホルダーは、references/skill-template.md の各 {{…}} に書かれた指示に従って記入する。指示を読まずに推測で記入しない
