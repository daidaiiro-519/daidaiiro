意思決定の記録 ・ ACDR 0038 ・ 2026-09-29 ・ 承認

8つの Skill へ、言語に依存しない道具の契約を適用する

決めたこと

道具を持つ残りの8つの Skill を、ACDR 0037 で改訂した道具の契約（tool.json ・ 宣言の JSON ・ 外部の道具の注入）に従う形へ移す。

なぜ決める必要があるか

ACDR 0037 で skills-creator の check を2段にした。残りの8つの Skill は、tool.json が無く、動詞なしの --json で宣言を返さないので、1段目に合格しない。acdr ・ fact-check ・ narration は、外部の道具の名前を部品に直書きしているので、2段目にも合格しない。このリポジトリの書いた後の検査は、この8件で不合格になっている。

どう変わるか

変更前と変更後

何が変更前変更後
外部の道具の宣言各 Skill の宣言の Rust の定数 EXTERNAL各 Skill の tool.json の external（名前 ・ 起動するコマンド ・ 理由）
外部の道具の起動部品が git ・ curl ・ aws の名前を直書きする（4か所）宣言の層が tool.json から読み、部品へ引数で渡す
動詞なしの --json人が読む一覧を出し、終了コード2宣言（道具 ・ 引数 ・ skill_root）を JSON で返す
Skill のフォルダの判定references/ が在る場所SKILL.md が在る場所

比較した案と、採らなかった理由

案採らなかった理由
外部の道具の注入をせず、tool.json と宣言の JSON だけを適用するacdr ・ fact-check ・ narration が2段目に合格しない。利用者が呼ぶコマンドを差し替えられないままである
fact-check に references/ を置いて、Skill のフォルダの判定を変えないreferences/ を保持しない Skill を作るたびに、同じ不合格が起きる。SKILL.md はどの Skill も持つ

意思決定を、変更前と変更後の差分ごと記録するSkill：acdr

ACDR は Any Change Decision Record である。 分野を限定しない ── 何を決めたときでも、変更前と変更後の差分ごと残す。

目的

何かを決めたとき、決定と、その差分と、なぜそう決めたかを1枚へ保存するために使用する。文書・コード・設計・方針のいずれでもよい。分野を問わない ── この Skill は、対象が何の仕事に属するかを認知しない。

人は、変更前と変更後が見えていると判定が速い。 差分が無いまま承認を求めると、「この決定は何を土台にして決まったのか」を読む側が毎回復元することになる。成熟した環境では、決定の大半が既存のものへの変更である。だから差分を既定にし、新規のときだけ差分が空になる。

残すのは、承認の前と後で同じ1枚である。 状態が proposed から accepted へ変わるだけで、記録の形は変化しない。リポジトリに置くので、差分に載り、変更の理由がPRに出力される。

役割

- 決定を、節（決定 ・ なぜ ・ 形の変化 ・ 実現の形 ・ 適用先 ・ 比較した案 ・ 承認の状態 ・ 承認後に実施すること）にする
- 変更を1件ずつ、どこ・何から何に・なぜの3つ組にする
- 対象の文書を描画し、変更箇所を押すと変更前と理由が開く形にする
- 理由が欠けている変更を、記録に包含しない
- 正本へ適用する前に見せ、承認を得てから適用する
- 承認が下りたら状態を accepted にして、リポジトリへ保存する

処理対象と成果物

処理対象

これから決めようとしていること。多くは既存の文書・コード・設計への変更で、新規のこともある。

成果物

記録1件は、フォルダ1つである。

.acdr/<番号>-<短い名詞句>/
  acdr.json    ← 正本。節と、変更の3つ組を保持する
  flow.svg     ← 図（組ませた相手が返す。無い場合は配置しない）
  index.html   ← 組成した成果物。acdr.json から導出される

acdr.json が正本で、index.html は導出されるものである。 同じ acdr.json から、実行場所に依存せず同一の index.html が出力される。

中身を複製しない。 変更後の全文は対象の文書が保持している。記録が保持するのは、節と、対象のパスと、3つ組だけである。

index.html を手で直さない。 正本は acdr.json である ── 手で直すと、次に組成した時点で失われる。

承認済みの記録は封印される。 承認後の最初の組成で、対象の文書の sha256 が acdr.json へ保存される。以降、対象の文書が変化した状態で組み直そうとすると拒否する ── 組み直すと承認時点の姿が失われる。--check はその場合に「承認時点の姿である」と報告する。意図して組み直す場合は --force を渡す。

入力の想定

受け取る情報解釈・既定値
決めようとしていること明示されなければ、直前の会話から決定を書き起こす。推測で補完しない
対象の文書明示されなければ、変更しようとしている文書すべてを対象とする。無ければ新規として扱う
変更前の内容正本の現在の中身をそのまま取る。適用済みなら、gitの作業ツリーとHEADの差から取る
なぜ明示されなければ、そのとき何と食い違っていて何に一致させたかを書き起こす
除外した案明示されなければ、検討した案と、それぞれ何が成立しないかを記述する

実行手順

Step 1: 何を出す文書かを、外から取る

その文書が何を出すべきかは、その文書の中には無い。中から取ると、旧路線の記述が旧路線を残す根拠になる。成果物を決めている親文書・定義票・仕様の記述から取り、見出しの並びだけで出すものが出るかを判定する。出していなければ、本文の校正に入らず構造の案を先に出す。

Step 2: 対象の全文を読む

頭から終わりまで確認する。検索で見当を付けて周辺のみを確認する方法を採用しない ── 置換のすり抜け、説明なしで残った旧い値、見出しと中身の食い違いは、どれも検索では検出されない。

Step 3: 節を記入する

節キー中身
決定decision決めてほしいこと1件。能動態の完全な文で、手段を記述しない
形の変化shift抽象の側の変更前と変更後。what ・ from ・ to の3列
図で確認するfigure ・ figure_caption形の変化を図にしたもの。この Skill は描画しない ── 受け取るのは SVG の文字列のみである
実現の形howその決定をどう実現するか。手段はここへ配置する
適用先applies_toどの正本が変わるか
なぜ、いま決めるのかwhy何と食い違っていて、何に一致させたか
比較した案alternativesoption と、why_not。反証を通過しなかった案であり、未解決の懸念ではない
承認の状態statusproposed ／ accepted ／ superseded
承認後に実施することafter_approval承認が成立したあとに実施する作業
置き換えた記録supersedesこの決定が置き換えた記録の番号

キーは ASCII で、値は人が読む日本語である。 機械が分岐するもの（キー ・ status）と、
人が読むもの（本文）を、同じ文字体系に混在させない。

decision ・ applies_to ・ why の3つは、欠けたら道具が停止する。 欠けた記録は、あとから誰も補完できない。

Step 4: 変更を3つ組にする

1件ずつ、どこ（読み手がその場所を開ける粒度）・何から何に（変更前の原文をそのまま。要約しない）・なぜを完備させる。書けない変更は記録に含めない ── 書けないのは、変更の意図が自分でも掴めていないということである。削除も1件として扱い、消えた場所に印を配置する。

「変更前」と「なぜ」は平文である。 タグを書いても文字として出る ── 「変更前」は原文をそのまま出す欄なので、タグを解釈してはならない。節（決定 ・ 対象 ・ なぜ）のほうは HTML を受ける。

「どこ」は、描画したあとの本文に現れる文字列で指定する。 マークダウンの記法を含めると一致しない ── 描画後は <b> や <code> になっている。

Step 5: 作業コピーへ適用して、1枚を組む

正本は触らない。作業コピーへ適用してから組成する。操作は3つだけである。

acdr new .acdr/0007-<短い名詞句> "題"    起こす（雛形から）
acdr validate .acdr/0007-<短い名詞句>    入力を検査する
acdr render .acdr/0007-<短い名詞句>      組む
acdr render .acdr/0007-<短い名詞句> --check 1   差が無いかを検査する

入口は1つである。 どの操作も --json を付けると機械が読む形で出て、終了コードは 0 正常 ／ 1 検出あり ／ 2 誤用である。

acdr.json の形は references/acdr.schema.json が決め、雛形は references/spec-template.json が保持する。生成物ではなく、入力を検査する ── 生成物の検査からは、複製が正しく生成されたことしか判明しない。しかも不合格の時点で HTML は既に出ている。不合格なら HTML を1バイトも出さない ── 検査は4系統で、形（スキーマ）・欄の完備（節と3つ組）・散文（1つの欄への主張の同居 ・ 1文の長さ ・ 見出しや表の混入。引用と原文は除外する）・参照の解決（図と対象の文書の実在）である。

拡張子置き方
.md描画した見た目。印は語の単位で付く
コード（.py ・ .js ・ .json ・ .go ・ .rs ・ .rb ・ .sh ・ .sql ・ .yaml ・ .toml ・ .css ・ .xml ほか）Git の統合差分。旧と新の行番号 ・ + / - ・ 文脈3行。印は行の単位で付く
それ以外（.html など）そのままの見た目。CSS を隔てるので iframe へ流し込み、届かなければ Shadow DOM へ切り替える

docs が空なら、節だけの1枚になる。

新しい種別の枠を追加する場合は、タブの押す処理の配線と、枠の挿入先の2点を確認する。 どちらが欠けても印は開かない ── 面の種別を増やす操作は、配線と挿入先の2か所へ同時に及ぶ。

Git は差分を出すが、なぜ変えたかを出さない。 そこを補完するのがこの道具である ── まとまりごとに理由を添え、印を押すと開く。変更前は - の行が示すので、before の記述は省略してよい。

変更前は git show <rev>:<パス> で取得する。 記録へ複製しない。rev の既定は HEAD で、docs の項目に書くと変更できる。取得できない場合と差分が無い場合は、全文を置く。

理由が付いていないまとまりは、組成の検査が件数を出す。 差分の見出しにも表示する ── 0件にしてから提示する。

コードの印は行の単位である。 語の単位で付けると、色付けが挿入した要素と交差してどちらかが壊れる ── コードの変更は行の単位で読むものなので、行で足りる。

色付けは近似である。 構文解析を実施せず、行ごとに正規表現を適用する ── 文字列の中の予約語のような事例は取り違える。読解の補助であり、判定の根拠にしない。

冪等である。 docs のパスはリポジトリの根から解決するので、どこから実行しても同一のものが出力される。--check は組み直した結果と index.html を比較し、差が在れば 1 を返す。

Step 6: 開いて閉じることを確認する

描画して、実際に押す。1度押すと変更前と理由が出て、2度押すと閉じる。「すべて開く／閉じる」も両方向とも動作する。印が内側のタブに隠れることがある ── タブの先頭の一覧から、押してその印まで運べることを確認する。

Step 7: 理由の欠けを確認する

「なぜ」が「一致させるため」だけになっていないか（何と何を一致させたかを書く）。変更内容の言い換えになっていないか。変更前が要約になっていないか。

Step 8: 見せて、承認を得てから適用する

1枚を渡し、返事を待つ。「適用しました。確認してください」と記述しない ── それは承認ではなく追認を求めている。

承認が下りたら、状態を accepted にして組み直し、正本へ適用し、.acdr/ の1枚と索引をコミットする。差し戻されたら3つ組を直して Step 3 から再実行する。止められた場合は適用しない。

後の決定が、この決定を置き換えたときは、古いほうの状態を superseded にし、置き換えた記録を指す ── 消さない。

1枚のHTMLである。 先頭に節、その下に対象の文書が並ぶ。チャットには次のみを記述する。

正本の状態まだ適用していないことと、適用してよいかを聞く

変更の一覧をチャットに並べない。 それは1枚の役目である。

ガードレール

- 中身を複製しない。 変更後の全文は対象の文書が保持する。記録が保持するのは節と3つ組だけである
- 対象が何の仕事に属するかを、この Skill が認知しない。 特定の分野の語彙・規則・スキーマを持ち込まない ── 使う側がこの Skill を呼ぶのであって、この Skill が使う側を知ることはない
- 何を出す文書かを、外から取得してから改訂する。 文書の中の記述を、その文書を直す根拠にしない
- 構造が合っていなければ、本文を直さない。 先に構造の合意を取る
- 対象の全文を読んでから直す。 検索で見当を付けて周辺のみを確認する方法を採用しない
- 正本へ適用する前に見せる。 適用してから提示しない
- 理由が欠けている変更を包含しない。 推測で理由を補完しない
- 変更前を要約しない。 原文をそのまま保持させる
- 比較した案を削除しない。 案と、採らなかった理由を保存する
- 節の語を負の側へ偏向させない。 「除外」「負担」ではなく「比較した案」「承認後に実施すること」と記述する ── 負の語が残ると、未解決の懸念が存在すると読解され、承認の判定が遅延する
- 抽象の側の変更前と変更後を記述する。 枠が保持するのは具体の差分である ── 抽象の対比が欠けると、下に並ぶ差分が何のためかを読み手が復元することになる
- 図を省略しない。 形の変化を図で確認できる形式にする。描画はこの Skill が実施せず、SVG の文字列を受け取るのみである
- 状態を自由文にしない。 proposed ／ accepted ／ superseded の3つ以外を書かない ── 自由文にすると、承認されているかを読む側が判定することになる
- 置き換えられた記録を削除しない。 superseded にして、置き換えた記録を指す
- 新規を例外として区別しない。 差分が存在しない決定も同一の形式で、docs を空欄とする
- 描画して押すまで出さない。 開閉が動作することを目視で確認する
- 色・寸法を直書きしない。 見た目は references/tokens.json が保持するトークンから引く ── 直書きすると、配色を替えたときにそこだけ取り残される。トークンの正本は1つである ── 2か所に書くと、どちらが正しいかを毎回確認することになる
- 入力の検査を、組み立てと同じ場所に置かない。 組み立てが検査を兼ねると、不合格の判明が生成物のあとになる ── 不合格なら HTML を1バイトも出さない
- 決定の文に手段を混在させない。 決定は「何を採るか」で、手段は実現の形が保持する ── 手段だけを上に置くと、下の差分が何のためかを読み手が復元することになる
- 差し色を1つに限定する。 状態のラベル（承認済み）以外に別の色を使わない ── 1本だけ違う色の線が在ると、意味が在るものとして読解される
- 題を二重に出さない。 題は節が持ち、枠の見出しには出さない
- 生成物に文字コードを宣言する。 <meta charset="utf-8"> を先頭に置く ── 無いとHTTPで配ったときに推測になり、化ける
- 承認済みの記録を組み直さない。 記録は承認時点の姿である ── 後に対象の文書が変化しても、記録はその時点を保持する
- 外部のCDNやスクリプトを参照しない。1枚で完結させる

name: fact-check
description: 外にある情報源を調べて、その内容を文書・設計・実装へ取り込むときに必ず使うスキル。公式リファレンス・API仕様・OSSの実装・論文・規格が対象。「調べて」「調査して」「仕様を確認して」「どうなっている？」と言われたとき、および識別子（項目名・パラメータ名・関数名・スキーマのキー）を文書へ書き写すときに必ず使う。要約を経由して原典を読むことを禁じ、原文の文字列で照合させる。
version: 2.0.0

目的

調査対象を、要約を経由せずに読む。

真偽そのものは判定しない ── 見るのは、書こうとしている識別子と主張が取得した原文の中に在るかである。原文が誤っている場合は、誤っているまま照合が通る。

識別子は説明ではなくキーである。
compact_summary を compact_text と書き換えたら、そのキーで参照する実装は必ず空を返す。
しかも壊れ方が静かで、「その事象は起きなかった」と読めてしまう。
土台の項目名が違えば、その上に作った道具は何も取れない。

主張は、要約すると別のものになる。
「〜の場合に出る」から条件を除けば、無条件で出ると書いたことになる。
しかも識別子と違って、照合には1件も掛からない。
名前がすべて原文どおりの文書が、原典と違うことを述べる。

識別子の照合は、原典への忠実さのうち、文字列で照合できる一部である。
残りは、主張を原文の引用に結びつけて検証する。

このスキルが禁じるのは1つ——「要約された原典」を根拠にすることである。
公式リファレンスも、OSS の実装も、規格も、実測データも、
扱いは同じである。どれも「正しいとされる情報源」であり、
勝手に言い換えた時点で、実体と別のものになる。

役割

- 情報源の原文を取得し、取得した日と sha256 を残す
- 文書へ書く識別子を、原文の文字列で1つずつ照合する
- 照合できなかった識別子を、原典の名前として書かない
- 「原典にこう書いてある」と書くときは、どのファイルの何行目かを提示できるようにする
- 原典の記述として書く主張を、原文の引用へ1件ずつ結びつける
- 引用を添えられない主張を、原典の記述として書かない
- 要約・言い換え・意訳を、識別子にも主張にも行わない

実行手順

Step 1: 原文を取得する

fact-check fetch <URL> [--dir <置き場所>]

まず <URL>.md を試し、無ければ本体を取る。
主要な文書サイトは .md で原文を返す（実測：Anthropic ・ Cursor ・ OpenAI ・ GitHub の4社とも返した）。

取得したものは、sha256 ・ バイト数 ・ 行数 ・ 取得した日と一緒に保存される。
「いつ・どの版を読んだか」が提示できなければ、根拠にならない。

対象どう取得するか
公式リファレンスfetch <URL>。.md が返ればそれが原文である
OSS の実装git clone --depth 1。読んだ commit を記録する
論文PDF を置き、本文の文字列で確認する
実測データ自分で取ったファイルをそのまま置く

HTML しか返らない頁も、そのまま原文として残る。
タグは剥がさない ── 剥がすのは加工であり、剥がし方で文字列が変わると
「原文と1文字ずつ同じ」が主張できなくなる。

Step 2: 識別子を列挙する

文書・設計・実装へ書こうとしている識別子を、1行1個で並べる。

対象になるのは、名前がそのままキーとして使われるものである。

- 項目名・フィールド名（compact_summary ・ tool_use_id）
- パラメータ名・フラグ（--permission-mode ・ permission_prompts）
- 事象名・関数名・型名（PostToolUse ・ LoadedEntry）
- ファイル名・パス（~/.codex/sessions/ ・ state.vscdb）
- 設定のキー（github.copilot.chat.otel.enabled）

Step 3: 原文と照合する

fact-check verify <原文> <識別子>... --as identifier
fact-check verify <原文> --as identifier --from names.txt

照合の種類を渡さなければ止まる。
道具の側で「たぶん識別子だろう」と決めない。

照合の種類何を照合するか
identifier語として照合する。前後が語の文字なら、それは別の名前である
quote引用として照合する。空白の圧縮規則だけ統一し、語は1文字も変えない
textそのまま探す。探索のための種類で、照合した証しにはならない

語の区切りは、照合する語自身が決める。
英数と _ - は常に語の内側で、それ以外の区切り（. / : など）は、
照合する語がそれを含んでいるときだけ内側になる。
だから otel.enabled はキーの切れ端として一致せず、compact_summary は英文の文末でも一致する。

読めた範囲に無い識別子が1つでもあれば、そこで止まる。

見つからない原因どうするか
名前を言い換えた直す。原文の綴りをそのまま使う
別のページに在るそのページを取得して照合し直す
読めなかった範囲に在る読めるようにして、照合し直す。0件を結論にしない
本当に無い「無い」と書く。推測で補完しない

アンカーを渡すと、文脈まで検査する。

fact-check verify <原文> compact_summary --as identifier \
           --near "PostCompact input" --within 25

名前が在ることと、その名前がそこで使われることは別である。
trigger は原文に 24 か所あるが、それが PostCompact のものとは限らない。
別の事象の項目を、その事象のものとして書く——これが次に起きる誤りである。

この検査で見えるもの・見えないもの

これは文字列の検査であって、意味の検査ではない。

見える例
識別子を言い換えたconfig_source と書いたが、原文には無い
綴り・大文字小文字・区切りの違いtoolResult を tool_result と書いた
アンカーを渡せば、文脈違いtrigger は在るが PostCompact の節に無い
見えないどう防ぐか
名前は合っているが、説明が違うStep 4 で、主張を引用に結びつける
原文に在るのに、こちらが取りこぼしているStep 6 で逆側から照合する
数値・件数の誤り数値も、原文の文字列で確認する。自分で計算した値を、原典の値のように書かない
版が古い取得した日を保存し、同じ URL でも中身が変化する前提で処理する

「0件だから正しい」ではない。「書いた名前は、読めた範囲に実在する」だけである。

読めなかったファイルは、結果に「読めなかった範囲」として出る。
1つでも在れば、0件は「無い」ではなく「読めた範囲には無い」としか判定できない。
黙って飛ばして0件と報告するのは、道具の側が推測で断定することである。

Step 4: 主張を、引用に結びつける

原典の記述として書こうとしている主張を、1件ずつ書き出す。
識別子と同じ扱いをする。違うのは、照合する先が名前ではなく、原文の一続きの範囲だという1点である。

1件ごとに、根拠にした原文の行をそのまま添える。
行番号は grep -n で取る。

主張      PostCompact は、自動の圧縮でも手動の圧縮でも走る
引用      | `trigger` | `"manual"` \| `"auto"` | 圧縮の起こし方 |
出どころ  claude-code-hooks.md:412

引用を添えられない主張は、原典の記述として書かない。

引用を添えられないどうするか
原文に在るはずだが、まだ探していない探す。見つけた行を添える
原文には無く、自分の推論である「推測」と印を付ける。または除外する
離れた複数の箇所を繋いで導いた繋いだと書く。参照した箇所を全部添える

要約して意味が変わる形は、4つある。

変わり方原文書いてしまう内容
条件の脱落「〜の場合に出る」「出る」
範囲の拡大1つの実装・1つの版の話「一般にこうである」
因果の捏造並べて書いてあるだけ「A だから B になる」
欠落の補完何も書いていない通念で埋め、「原典にこうある」と書く

4つとも、Step 3 の照合では0件になる。
名前を1つも言い換えていないためである。

引用が原文と1文字ずつ同じかは、verify で検証できる。

fact-check verify <原文> --as quote --from quotes.txt

引用は1行ずつ渡す。
行をまたぐ引用も一致する（空白の圧縮規則だけ統一するため）が、
渡すときの1件は1行にする。

引用を、読みやすくするために整えない。
整えた時点で、引用ではなくなる。

Step 5: 書けることと、書けないことを分ける

原文で照合できたことだけを、原典の記述として書く。

書けること書き方
原文に在る識別子と、その説明そのまま引用する。言い換えない
原文に無い「原文に無い」と書く
自分で測った値「実測」と印を付け、測った条件も書く
第三者の実装が主張していること「第三者」と印を付け、どのリポジトリの何 commit かを書く

「原典に書いてある」と「実際にそうなる」は別である。
公式に書いてあっても、条件が充足しないと出ない項目がある。
出せることを確認したなら、そのための条件も書く。

Step 6: 逆側からも照合する

原文に在るのに、こちらが取りこぼしている識別子を探す。

Step 3 は「こちらが書いたものが原文に在るか」を検査する。
それだけでは取りこぼしが残る。原文を頭から読み、
見出しの一覧と、こちらが持っている一覧を突き合わせる。

識別子だけでなく、条件・例外・限定も同じように探す。
原文が付けている「ただし」を看過すれば、書いたものは Step 4 の条件の脱落と同じ形になる。

出力形式

調べた結果を報告するとき、次を必ず添える。

報告する内容書き方
何を読んだかURL と、取得した日と、行数。「公式ドキュメント」とだけ書かない
どう読んだか原文を取得して文字列で照合した、と書く。していないならそう書く
照合した識別子の数何個照合して、何個が原文に在ったか
主張の根拠原典の記述として書いた主張ごとに、引いた行と出どころを添える。添えられないものは「推測」と印を付ける
どの種類で照合したかidentifier ・ quote ・ text のどれか。text は照合した証しにならないと添える
読めた範囲に無かったもの一覧で出す。1つでも隠さない
読めなかった範囲在れば一覧で出し、0件を結論にしない。無ければ「全部読めた」と書く
実測と原典の区別行ごと・値ごとに印を付ける

ガードレール

- 要約を経由して原典を読まない。要約する道具の出力を、原典の記述として引用しない
- 識別子を言い換えない。大文字小文字・区切り記号・単複まで原文どおりにする
- 原文に無い識別子を、原典の名前として書かない
- 引用を添えられない主張を、原典の記述として書かない。推測として書くか、書かない
- 引用を整えない。読みやすさのために語を足さない。条件・範囲・限定を除かない
- 照合が0件でも、意味が合っているとは限らない。主張は Step 4 で別に検証する
- 0件を「無い」と結論しない。読めなかった範囲が1つでも在れば、「読めた範囲には無い」と書く
- --as text の結果を、照合した証しにしない。探索のための種類である
- 「公式にはこう書いてある」と書くなら、原文のどこかを提示できるようにする
- 原典が誤っていると結論する前に、自分の読み方を疑う。
原典の誤りと読み方の誤りは、同じ観測を生む ── 観測だけでは区別できないので、
検証の負荷が小さい側（自分の読み方）から先に検証する
- 取得した日と版を残す。同じ URL でも中身は変わる
- OSS は読んだ commit を記録する。「そのリポジトリではこうなっている」は版に依存する
- 第三者の実装の主張を、公式の記述として書かない。印を分ける
- 原文で照合していない調査結果で、正本を書き換えない
- 原文の置き場所を、このスキルの側で決めない。呼び出す側から受け取る
- このスキルの外を指す参照を保持しない。他のスキル・特定のフォルダの並びを前提にしない
