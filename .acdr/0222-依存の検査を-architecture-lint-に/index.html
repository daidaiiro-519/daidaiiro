依存の向きの検査を architecture-lint に任せる

決めたこと

SAS と agents-skills-creator の依存の向きは、architecture-lint の規則の形で architecture.json に書く。確かめるのは、試験から呼ぶ architecture-lint である。

なぜ決める必要があるか

依存の向きの検査の道具 architecture-lint（ACDR 0200）があるのに、SAS と creator は独自の形の architecture.json と、検査の写し（architecture.rs）で確かめていた。architecture.json は architecture-lint の規則のファイルなので（利用者の指摘）、形と検査の持ち主を architecture-lint に一致させ、写しを外す。

どう変わるか

変更前と変更後

何が変更前変更後
architecture.json の形製品ごとの独自の形（context ・ crates ・ allow ・ libraries ・ dev_only など）。形の schema は無い。architecture-lint の規則の形（components ・ allow ・ kinds）。$schema で urn:architecture-lint:rules:v1 を指す。
依存の向きの検査製品ごとに写した Rust の検査（architecture.rs）。試験が architecture-lint check を呼ぶ。名前の付け方の検査（製品ごとに違う）と、規則に残った消えた crate の検査だけを試験に残す。
試験だけで使う依存dev_only の欄で test-support を区別し、dev の依存は止めなかった。test-support へ向かう辺を allow に書かないので、dev の依存も止まる。要る辺だけを kinds dev で許す（前より強い）。
規則でない説明（文脈の地図 ・ 名前の付け方 ・ モジュール）architecture.json の中。SAS は arch-v15.json と CODING.md（既に同じ中身がある）、creator は docs/design/structure.json（schema を持つ）。crate の役目は component の description。
architecture-lint の規則の形$schema の欄を受けない（追加の欄を禁止）。$schema を任意の欄で受け、urn:architecture-lint:rules:v1 以外なら終了コード 2。

比較した案と、採らなかった理由

案採らなかった理由
architecture.json に製品ごとの schema を新しく作る（ACDR 0221 の版1 の案）形の持ち主が architecture-lint と製品の2人になり、規則の書き方が食い違う。
architecture-lint を使わず、検査の写しを残す同じ検査を製品の数だけ持ち、直すときに写し漏れる。architecture-lint を作った目的（ACDR 0200）と食い違う。

architecture-lint

許していない依存の辺を、規則で検出して止める CLI。アーキテクチャに寄らない。

Cargo は「Cargo.toml に書いていない crate を使う」と「通常の依存の循環」を止める。ただし、その辺を Cargo.toml に書いてよいかは知らない。architecture-lint は、規則（component と allow）に無い辺を見つけ、終了コード 1 で CI を止める。

決めた経緯はブレストボード .brainstorming/dependency-rules.json と ACDR 0199 と 0200（名前）にある。

規則の書き方

形は rules.schema.json が決める。例は examples/semantic-agent-schema.json。

{
  "$schema": "urn:architecture-lint:rules:v1",
  "version": 1,
  "components": [
    {"name": "domain", "nodes": ["myapp-domain-*"]},
    {"name": "app", "nodes": ["myapp-app"]},
    {"name": "tempfile", "nodes": ["tempfile"]}
  ],
  "allow": [
    {"from": "app", "to": ["domain"]},
    {"from": "domain", "to": ["tempfile"], "kinds": ["dev"], "description": "テストの一時ディレクトリだけ"}
  ]
}
欄決まり
$schemaこの形の名前 urn:architecture-lint:rules:v1（rules.schema.json の $id）。任意。書くなら、この値でなければ規則の誤り（終了コード 2）
componentsnode の名前の集まり。nodes は完全一致か、末尾の * で前方一致。1つの node が2つ以上の component に当たると規則の誤り（終了コード 2）
allow許す辺。from の component から to の component へ。書いていない辺はすべて禁止で、同じ component の中の辺も書かなければ禁止
kinds許す辺の種類。省けばすべての種類を許す
descriptionなぜ許すか。任意

違反は2種類ある。

違反意味
not-in-allowedallow に無い辺（種類が kinds に無い辺を含む）
uncoveredどの component にも入らない node。外の依存も、規則に書かなければこれになる

グラフの読み取り

判定の中心は、node と edge のグラフ（形は graph.schema.json）と規則だけを受け取る。言語ごとの読み取りがグラフを作る。

読み取りnode の名前kind の値
Rust（--cargo）package の name。依存では dependencies の name で、rename の名前は使わないnormal ・ dev ・ build

Rust の読み取りは cargo metadata --no-deps --format-version 1 を起動し、workspace の member が Cargo.toml に書いた依存を辺にする。optional の依存も feature に依らず入る。target（プラットフォームの条件）は見ない。外の node は、member の直接の依存だけである。

ほかの言語は、graph.schema.json の形のグラフを出すプログラムを書き、check --graph に渡す。

版

rules.schema.json ・ graph.schema.json ・ result.schema.json は version を持つ。欄を足すだけなら同じ版、意味を変えるなら版を上げる。読めない版は終了コード 2 になる。

決まり理由
リポジトリの根は製品の置き場。区切られた文脈は、根の直下の文脈の名前のフォルダ（いまは schemas-and-instances/）製品と文脈を同じものとして扱わない。事業領域は問題の側の言葉なので、置き場所の名前にしない
文脈の中はポートとアダプターで作る。外とのやりとりは application の ports を adapters が実装する（呼び出し元を決めるポートは inbound/cli、ほかは outbound）。本ではポートは業務ロジック層が定義するが、記録と描画はドメインモデルを持たないので application に置く。各モジュールの application は、自分のユースケースが使うポート（と、そのうち使うメソッド）だけを自分の ports.rs に宣言する。ほかのモジュールと同じ形のポート（DocumentStore ・ SchemaValidator）も、それぞれのモジュールに同じ名前で宣言し、1つのアダプターが複数のモジュールのポートを実装する外の技術を業務ロジックから切り離す。ポートは使う側が「自分に何が要るか」として宣言するもので、形が同じでも変わる理由はモジュールごと
モジュールの application は、ほかのモジュールの application（ports ・ use_cases）を使わない。使ってよいのは domain の crate と、同じモジュールの中だけで、例外は無い。複数のモジュールが使う判断と値は domain に置く：文書が Concrete かインスタンスかの見分け（TargetKind）・ リポジトリの文書の一覧（Corpus）・ スキーマの所に当たる欄の定義（field_schema）・ 誰が打ったか（Caller）・ 記録にある書いた変更の行（ChangeRow ・ WriteRecord など）と SAS を通らない変更の見分け（unrecorded_since）は writing-domain、当たる rule と判定が読んだ所のハッシュ（reads_hash）・ 記録にある検証と判定の行（ValidateRow ・ RuleRow ・ Judgment）は validation-domain。答えの JSON の読み方（```json の囲みを外す）やコマンドの1行の組み方のような小さな道具は、使うモジュールごとに置く依存の向きを crate の境界で強制し、あるモジュールの手続きを変えてもほかのモジュールが壊れないようにする
誰が打ったか（人か、名乗ったセッションか）は入口が決めて、値（writing-domain の Caller）でユースケースへ渡す。決める材料（--session ・ ツールの環境変数 ・ sas init の登録）を読むのも、記録をつけるコマンドで sessions に1行足すのも入口で、その手続き（identify ・ register ・ sas init の register_session）は記録のモジュールの use case に置き、CLI からだけ呼ぶ。ユースケースは誰が打ったかを自分で決めない外からの入力を読むのは入口のアダプターの責務。誰が打ったかは x-decided-by の欄を変えてよいかを決めるドメインの概念で、記録のモジュールの型にしない
記録のポートは、使うモジュールが自分の ports.rs に、そのモジュールのユースケースが使うメソッドだけで宣言する（書く ChangeLog ＝ append_change ・ find_request ・ writes ・ last_judgments、検証 ValidationLog ＝ append_validate ・ writes ・ last_judgments、描画 ValidationLog ＝ append_validate）。検索は記録しないので持たない。記録のモジュールに残るのは、記録を読む UC7（OperationReader）と、入口が使う SessionLog ・ IdentifyCaller。sqlite のアダプター（SqliteLog）は1つで、手続きを自分のメソッドに持ち、すべての記録のポートをそれで実装する表の側から作った1つの大きな trait にすると、どのモジュールも使わないメソッドにまで依存し、記録のモジュールの application への依存が残る
理由を表す欄は reason の1語にする。何の理由かは、付いている物で決まる（変更の reason は変えた理由、判定の reason は判定の理由）。CLI の引数も --reason同じことを表す語が intent ・ why ・ reason と分かれると、読む人と AI が別のものと読む
x-prompt の形は、直下に meaning（値を何として読むか）・ when（いつ、何のために読むか）・ rules（書くときの決まりの並び）を並べる。rule は id ・ rule ・ why ・ check ・ bad ・ good（bad ・ good は1つ以上の例の並びで必須。例は value ・ related ・ note のオブジェクトで、Abstract の $defs/example が形を持ち、bad の例は note も必須）と、任意の related_fields（判定で一緒に読む欄）を持つ。例の related のキーは related_fields にある所だけ（組み込みの検査 example-related）。手順の中でも同じ名前で渡す（meaning ・ when ・ related_fields）read と reads が1字違いで取り違え、write ・ interpret は動詞で欄の中身が分からなかった。例の無い rule は、判定する AI と人とで違反の境目を別に読む
断った理由の型（Refused）は、各モジュールの use_cases が、そのモジュールが断るときに使う欄だけで持つ。出力の形（command-result の kind = error）は inbound/cli の output が持ち、各モジュールの Refused を From で移すCLI の出力の形は入口の事情で、モジュールが互いの断る理由の欄を知らなくてよくする
文脈の中のフォルダは、業務領域を作るモジュール（writing/ ・ validation/ ・ recording/、ステップ5 で rendering/、ステップ8 で search/）と adapters/。名前はユースケースと場面で実際に使う言葉から付ける。文脈の根に domain を置かない業務領域ごとの手続きの置き場所を、言葉から引けるようにする（名前の見直し）
