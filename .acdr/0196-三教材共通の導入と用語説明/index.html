49def _cuts(text):
50 """改行してよい位置。読点の後と、ひらがなから漢字 ・ カタカナ ・ 英数へ移る位置（語の切れ目の近似）。"""
51 hira = lambda c: &#x27;\u3041' <= c <= '\u309f'
52 out = []
53 for i in range(1, len(text)):
54 p, c = text[i - 1], text[i]
55 if p in &#x27;、。' or (hira(p) and not hira(c) and c not in '、。」』）'):
56 out.append(i)
57 return out

60def _wrap(text):
61 """1行がおよそ LINE 字に収まるよう、2行のうち長いほうが最も短くなる位置で改行する。"""
62 if len(text) <= LINE:
63 return [text]
64 cuts = _cuts(text) or [len(text) // 2]
65 # 読点の後を優先し、行の長さの差が大きくならない範囲で選ぶ
66 best = min(cuts, key=lambda i: (max(i, len(text) - i) + (0 if text[i - 1] == &#x27;、' else 3)))
67 return [text[:best], text[best:]]

70def _split(text, start, end):
71 """2行に収まらない文は、読点か語の切れ目で分け、時間を文字数で按分する。"""
72 if len(text) <= LINE * 2:
73 return [(text, start, end)]
74 a, b = _wrap(text)
75 mid = start + (end - start) * len(a) // len(text)
76 return _split(a, start, mid) + _split(b, mid, end)

79def subtitles(ids, dur, pacing=None):
80 """枚ごとの文の時刻を、通しの時刻へずらして WebVTT にする。"""
81 cues, offset = [], 0
82 for sid in ids:
83 item = dur[sid]
84 gap = (pacing or {}).get(&#x27;slides', {}).get(sid, {})
85 leading = gap.get(&#x27;beforeMs', 0)
86 trailing = gap.get(&#x27;afterMs', 0)
87 marks = [json.loads(l) for l in (NARR / item[&#x27;marks']).read_text().splitlines() if l.strip()]
88 sents = [m for m in marks if m[&#x27;type'] == 'sentence']
89 for k, m in enumerate(sents):
90 end = sents[k + 1][&#x27;time'] if k + 1 < len(sents) else item['durationMs']
91 for text, a, b in _split(m[&#x27;value'], m['time'], end - 80):
92 cues.append((offset + leading + a, offset + leading + b, &#x27;\n'.join(_wrap(text))))
93 offset += leading + item[&#x27;durationMs'] + trailing
94 body = &#x27;\n'.join(f'{n}\n{_ts(a)} --> {_ts(b)}\n{t}\n' for n, (a, b, t) in enumerate(cues, 1))
95 return &#x27;WEBVTT\n\n' + body

01　仕事の目的を、AIで達成できるようになるためのワークショップです

AIを使うことで、これまで難しかったことも、自分で実現できるようになってきました。この力を、皆さんが仕事で実現したいことに合わせて使えるようになるために、今回のワークショップを企画しました。

学ぶのは、AIの使い方と、その前提となる考え方です。何を実現したいのか。そのために何が必要なのかを考え、AIに説明します。そして、AgentsやSkillsを使って実行し、結果を確かめるところまで、自分の仕事で実践していきます。

目指すのは、皆さんが自分の仕事の目的を、AIで達成できるようになることです。ここでは、そのために何を学び、どのように実践するのかをご紹介します。

まずは、AIによって私たちの仕事がどう変わったかを考えてみましょう。

02　AIで成果物を作りやすくなりました。仕事全体の生産性も上がっていますか？

資料やツール、アプリなどを、以前より手軽に作れるようになりました。作成にかかる時間が短くなっただけでなく、これまで自分では作れなかったものも試せるようになっています。皆さんにも、こうした実感があるのではないでしょうか。

では、その変化は、自分の作業を終えるまでの工数や、案件が進む速さにも、期待したほどつながっているでしょうか。

作成が速くなったことと、仕事全体が速く進むこと。その関係を考えるために、まず、普段の作業のどこをAIが担うようになったかを見てみます。

03　あなたの仕事のどこでAIを使い、作業はどう変わりましたか？

例えば、計画書や説明資料、報告資料を作る仕事です。図の左では、人が情報を整理し、文章にしています。開発でも、要件をもとに設計書を書き、コードやテストを作成していました。

右は、その作成の一部をAIが担う例です。一つの案を作るだけでなく、複数の案を比較したり、関連する資料を追加したりすることも、以前より手軽になりました。重ねた資料は、短時間で作れるものの種類や量が増えたことを表しています。

皆さんの仕事でも、資料の案を作ったり、設計や実装の方法を試したりしやすくなっていませんか。

ただ、成果物ができた時点で、仕事のすべてが終わるわけではありません。実際に使うには、その内容を確認し、必要なら修正する作業があります。

04　作成は速くなった。確認や修正まで含めると、どうでしょうか？

例えば資料なら、元の情報と合っているか、仕事に必要な内容が含まれているかを確認します。開発では、設計書やコード、テストが要件や仕様を満たしているかを確かめます。成果物どうしで内容が食い違っていないかも、確認が必要ですね。

不足があれば修正し、修正した内容をもう一度確認します。図の下の矢印は、この流れを示しています。

AIで作成しやすくなると、資料のページ数やコードの量に加え、成果物の種類や数が増えることもあります。その分、読んだり、要件や記録と照らし合わせたりする対象も増えます。作成の時間が短くなっても、確認や修正まで含む時間が、同じように減るとは限りません。

必要なレビューやテストは、これからも大切です。そのうえで、確認したい内容を探すだけで時間がかかったり、何を基準に問題ないと判断するか迷ったりすることはないでしょうか。確認の負担を考えるには、成果物の量だけでなく、内容と示し方にも目を向ける必要があります。

05　その成果物は、確認・判断ができる形になっていますか？

図の左のように、資料ごとに形式や詳しさが違うと、確認したい内容を探すところから始めなければなりません。形式を決めていても、情報量が多ければ、読むだけで時間がかかります。欄が埋まっていても、必要な内容を把握し、判断できるとは限らないわけです。

そこで考えたいのが、その成果物を何のために使い、何を確かめたいのかです。目的に合わせて、含める内容、対象の範囲、必要な詳しさ、示し方を決めます。

右は、承認に使う資料の例です。何を決めるのか、その根拠は何か、満たす条件や未確認の点は何かを確認でき、必要なら詳細も調べられる形です。設計書やコード、テストでも、要件との対応や確認すべき点が分かることが大切ですね。

ただ短くしたり、すべてを同じ形式にしたりすればよいわけではありません。判断に必要な情報を残し、人が確認できる内容と示し方にすることが大切です。

では、何のために、何をどこまで作り、何を確かめればよいのか。皆さん自身が説明し、AIにも伝えられるでしょうか。このワークショップでは、それを言葉にするところから、AIで実行し、繰り返し使えるようにするところまでを学びます。

06　AIで必要な成果物を作り、条件と手順を再利用・改善する

このワークショップで学ぶのは、AIで必要な成果物を作り、そのための条件と手順を、繰り返し使いながら改善する方法です。図は、その使い方を表しています。

まず、何のために、何を作り、何を確かめるのかを考えます。中央の下にあるSkillは、AIが使う条件や手順の記録です。繰り返し使う内容を、ここに記録します。Agentは、作業を実行するAIです。Skillに記録した条件や手順と、その作業に必要な情報を使い、成果物を作ります。

左にあるのは、作業のたびに必要になる情報です。例えば、資料を作るための元の記録や、開発で使う要件や仕様などです。使う情報は、何をするかによって変わります。右には成果物の例を並べていますが、毎回すべてを作るという意味ではありません。その仕事に必要なものを作ります。

人は、出力が目的や条件に合っているかを確かめて使います。合わないところがあれば出力を修正し、必要に応じてSkillの条件や手順も改善します。下の矢印が、その流れです。

同じ種類の作業では、記録した条件や手順を再利用し、そのときに必要な情報や変更点を伝えます。目的や条件が変われば、記録した内容も見直します。毎回すべてを説明し直すのではなく、使いながら改善していくわけです。

こうしたAIの使い方を、自分の仕事で実現するために、三つの教材で順に学びます。

07　3つの教材で、AIを自分の仕事に合わせて使う方法を学びます

一つ目は、目的の把握です。何のための作業で、何をどこまで作る必要があるかを考えます。成果物を増やすこと自体を目的にせず、仕事で使うために必要な内容や条件を説明できるようにします。

二つ目は、言葉の定義です。必要な内容や条件を表す言葉が、何を指しているかを明確にします。同じ言葉でも、人や業務によって意味が違うことがあります。自分の仕事で使う意味を定義し、チームで使う場合は、その違いも確かめます。

この二つで考えた目的や内容、言葉の意味、確認条件が、図の下にあるSkillに記録する前提になります。

三つ目は、仕組みの構築です。AgentsやSkillsなどの使い方を学び、決めた条件や手順を使ってAIが作業を進めるようにします。実際に使い、出力を確かめて改善する方法も扱います。

使い方とあわせて、何を記録し、何を確かめるかを、自分の仕事に合わせて考えられるようになることが大切です。教材では、身近な一つの作業を例に学びます。題材の詳しい説明は教材の「はじめに」で行いますので、ここでは、皆さんの仕事にどう活かせるかを見てみましょう。

08　学んだ方法を、資料作成や開発の仕事で使えるようになる

例えば、資料を作る仕事です。誰が何の判断に使うのかを考え、そのために必要な内容や詳しさをAIに伝えます。出力も、必要な情報があるか、根拠は確かか、詳細を確認できるかという観点で確かめます。見た目や形式に加えて、仕事で使える内容かどうかを判断できるようにするわけです。

設計や開発なら、変更の目的や対象範囲、満たす要件や仕様、品質の条件を説明してAIに伝えます。そして、設計書、コード、テストがその条件に対応しているか、成果物どうしで内容が合っているかを確認します。

どちらも、何が必要かを考え、AIに伝え、結果を確かめるという点は共通です。繰り返し使う条件や手順はSkillなどに記録し、同じ種類の作業で使います。その作業に必要な情報を伝え、Agentが記録した内容を使って作業を進めるようにし、合わないところは改善します。

特定の作業のやり方だけでなく、自分の仕事に合わせて考え、実行し、改善する方法を身につけていただきたいと考えています。そのために、教材ではAIの操作方法とあわせて、仕事の目的や言葉の意味を考える方法も扱います。この考え方の参考にしたのが、次の三冊です。

01　経費精算システムの刷新案件で、AIを活用して開発を進めます

既存システムを知るメンバーに、新しく開発者が加わりました。チームには、開発、レビュー、テストの担当者と、案件を管理するPMやPLがいます。役割は説明のために分けていますが、一人が複数の役割を担当する場合もあります。

この案件では、チームとしてAIを活用して開発を進める方針です。コードを作る場面だけでなく、レビューやテスト、進捗を把握する作業でもAIを使います。

仕様書や開発手順は、すでにあります。新しく参加した開発者も、それらの資料と担当するタスクの説明をもとに作業を進めます。

教材では、このチームの一つの不具合対応を例に、各担当者がAIを使う仕事が、案件全体の成果にどうつながるかを考えます。

02　同じ案件でも、各担当者がAIに伝えている前提は異なります

先ほどのチームで、各担当者がAIに伝えている内容を見てみましょう。この案件には、担当機能の仕様書と、承認状態による操作制限などを説明した共通仕様があります。

既存メンバーは、担当機能の仕様とタスク説明に加えて、関連する共通仕様も参照します。経験から、今回の作業にはどの共通仕様が関係するかを知っており、その参照先と適用する条件をAIにも伝えています。

一方、新しく参加した開発者は、提供された担当機能の仕様とタスク説明をもとにAIで作業を進めます。関連する共通仕様も参照する必要があるとは分からず、AIにもその内容を参照させていなかった設定です。

今回不足していたのは、仕様そのものではなく、どの仕様を今回の作業に当てはめるかという情報です。経験のある人が補っている参照先と適用関係を、初めて参加した人が同じように把握できるとは限りません。

その結果、同じ案件でAIを使っていても、AIが参照する前提は異なることがあります。AIツールを共通にするだけでなく、参照すべき関連仕様と、今回適用する条件を分かるようにする必要があります。

では、この参照範囲の違いが、実際の実装にどう関係したのでしょうか。次は、経費申請の変更機能を例に見ていきます。

03　新しく参加した開発者が、申請の変更機能をAIで実装します

ここからは、刷新する経費精算システムの、申請内容を変更する機能を例に考えます。新しく参加した開発者が、この機能の実装を担当します。

担当機能の仕様書には、申請内容を変更して保存する機能の説明があります。一方、承認状態に応じた操作制限は、別の共通仕様に記載されています。そこでは、申請者が承認済みの申請内容を直接変更できない条件を定めています。既存コードにも、その制御があります。

既存メンバーは、この機能を実装するときに共通仕様も確認する必要を知っています。しかし、新しく参加した開発者が作業で参照したのは、担当機能の仕様書とタスク説明でした。関連する共通仕様を確認する必要があるとは分からず、AIにも参照させていませんでした。

図の中央が、今回の実装に使った情報です。その結果、右側の画面のように、承認済みの申請も金額を1万2千円から1万8千円に変更して保存できてしまいました。変更と保存は実装できましたが、共通仕様にある承認後の変更制御は抜けました。

仕様がどこにもなかった、という話ではありません。関連する仕様は存在していても、今回の作業に必要な情報として参照されていなかった、という設定です。

では、この開発者が実装完了と報告し、AIと人によるレビューを受けるとどうなったのでしょうか。次は、共通仕様の条件が反映されていないことが見つかる場面へ進みます。

04　AIでレビューも行いましたが、確認する前提が不足していました

新しく参加した開発者は、AIで申請の変更機能と単体テストを作り、AIによるレビューも行いました。レビューには、新しいコードと、実装に使った担当機能の仕様書を参照させています。

この例では、AIレビューでも承認済み申請の制約について指摘が出ず、開発者は実装と単体テストを終えたとして、変更を確認してもらうためのPRを作りました。PRは、コードなどの変更内容を確認し、取り込むかどうかを判断するためのものです。

PRには、コード、テスト、変更の説明、AIのレビュー結果があります。ただし、どの条件を確かめたのか、何が未確認なのか、重要な条件と変更箇所がどう対応するのかは、整理されていません。

既存メンバーも、このPRを確認します。AIのレビュー結果を読むだけで終えるわけではありません。差分を読み、関連する共通仕様と既存コードに照らして、確認すべきことを調べ直します。

その過程で、承認済み申請の変更制御が抜けていると気づきました。共通仕様の該当箇所と既存コードをAIにも参照させ、承認済み申請は変更不可という条件に照らして再確認し、人が指摘と該当箇所を確かめます。開発者は制御とテストを追加し、再びレビューとテストを受けることになります。

ここで伝えたいのは、AIでレビューすれば必ず見つかる、あるいは前提がなければ絶対に見つからない、ということではありません。実装にもレビューにも、何に照らして確認するかという前提が必要だということです。

コードやテスト、レビュー結果を早く作れても、人が重要な条件と該当箇所を探し直していては、確認の負担は残ります。次は、PRを確認する人の立場から、この負担を見てみましょう。

05　作成は速くなっても、確認に必要な情報を探す負担が残ります

先ほどのPRを、確認する人の立場から見てみましょう。コードとテストに加えて、変更の説明やAIのレビュー結果もあります。AIで作成が進むと、一度に確認する変更や説明が多くなる場合があります。

ただし、量が多いことだけが問題ではありません。今回のPRでは、何のための変更か、どこに影響するか、何を確認済みで何が未確認かが、変更箇所と対応して示されていませんでした。

図の右側は、レビュー担当者が確かめたいことです。承認済みの申請を変更できない条件について、どのコードで制御し、どのテストで確かめたのか。変更の影響はどこまであるのか。これらの根拠を、左側のPRの中から探します。その対応が分からなければ、差分やテストを読み、既存コードや仕様と照合して調べる必要があります。

説明文が長くても、テストが多くても、その条件を確認した根拠が見つかるとは限りません。AIのレビュー結果についても、何を参照し、どの条件を確認した結果なのかを確かめる必要があります。

こうして、人が確認観点と該当箇所を探し直し、不足があれば説明を求め、修正後にもう一度確認します。コードの作成時間が短くなっても、この負担が残っていれば、案件全体が同じように速く進むとは限りません。

ここで目指したいのは、単に文章や変更量を減らすことではありません。次の担当者が必要な判断をできるように、目的に合う成果物と、確認の根拠になる情報を用意することです。

では、何を達成するための作業で、そのために何を作り、何を確かめる必要があるのでしょうか。次の教材1の説明では、この目的から考えていきます。

06　教材1では、今回の修正から、別の機能にも使う進め方を考えます

ここまでの例では、承認済み申請の変更制御が抜け、追加の修正と確認が必要になりました。今回の制御とテストを追加すれば、この不具合には対応できます。ただ、それだけでは、別の機能でも必要な条件を参照できるとは限りません。

では、別の機能でも同じように、引き継ぐべき条件が抜けることを防ぐには、どうすればよいでしょうか。教材1では、この問いから、作業の目的を捉え直します。

図の1番は、今回の修正です。図の画面は修正後の状態です。承認済みの申請を変更できないようにし、金額が1万2千円のまま変わらないことをテストで確かめます。「今回の不具合を直す」という目的なら、承認後の変更制御とテストを追加する対応が考えられます。そこで、2番の共通する目的へ戻ります。複数の機能に共通する進め方を考えたいなら、「刷新で引き継ぐ業務制約を確認し、実装と検証に反映する」という目的で仕事を捉えます。

その目的から、3番の具体的な仕事へ戻ります。今回の制御を追加することだけでなく、毎回どんな確認が必要かを考えられます。例えば、関連する既存の仕様やコード、業務ルールを確認し、引き継ぐ条件と不明な点を明確にします。その条件を実装と検証に反映し、どの条件をどう確かめたかを記録します。図の右下では、この進め方を承認機能やデータ取込機能にも使う関係を示しています。それぞれで引き継ぐ条件を確かめ、実装と検証に反映するという進め方は共通です。

今回の修正という具体的な対応から、複数の機能に共通する目的へ戻り、その目的に必要な仕事を再び具体的に考えます。この往復を、教材1で練習します。

目的は大きくするほどよい、ということではありません。今回の不具合を直したいのか、今後の開発にも使う方法を考えたいのかによって、必要な目的の大きさは変わります。

また、目的を捉え直しただけで、必要な業務知識まで分かるわけではありません。どんな条件を引き継ぐかは、既存資料やコード、業務を知る人に確かめる必要があります。続く教材2では、「既存と同じ」「変更不可」「確認済み」といった言葉が、この業務で何を指し、どこまで当てはまるのかを明確にします。

07　教材2では、業務で使う言葉の意味と適用範囲を明確にします

教材1では、今回の修正から、刷新で引き継ぐ業務制約を実装と検証へ反映するという目的へ戻りました。では、その引き継ぐ条件を、どう説明すればよいでしょうか。教材2では、業務で使う言葉の意味と適用範囲を明確にします。

例えば、共通仕様にある承認状態による操作制限です。既存メンバーが短く「承認後は変更不可」と説明しても、今回の機能にどう適用するかは、この一文だけでは判断できない部分が残ります。

今回の例で確かめたのは、申請者が承認済みの申請内容を直接変更できない、という条件です。図の右側では、誰の操作か、どの状態の申請か、どんな変更を制限するかを分けて示しています。

ただし、さらに確認が必要な点もあります。複数の承認段階がある場合、どの段階を終えた状態を承認後と呼んでいるのでしょうか。対象は金額だけか、ほかの申請項目も含むのでしょうか。差戻し後に修正する手続きや、画面以外の更新経路はどう扱うのでしょうか。

これらは、関連する仕様を読んで確かめる観点です。共通仕様と関連する機能仕様、既存コードを照合して確認します。資料だけでは判断できない部分は、業務を知る人に確かめます。既存コードが実際にしていることと、業務として引き継ぐべきことが同じかどうかも確認します。

そうして、短い説明に含まれていた意味と、その条件が当てはまる範囲を具体的にします。ほかの機能を扱うときも、そこで使う言葉が何を指し、どこまで当てはまるかを確かめる、という考え方は共通です。

目的を捉え直すだけでは、こうした条件の中身までは分かりません。続く教材3では、教材2で明確にした前提を各担当者のAIも参照できるようにし、役割ごとの手順で実行する仕組みにしていきます。

08　教材3では、共通の前提と役割ごとの手順をAIが使える形にします

教材2では、関連する共通仕様を確認し、今回の機能に当てはまる条件を明確にしました。教材3では、その前提を各担当者のAIも参照し、仕事の中で使えるようにします。

今回の例では、関連する共通仕様があっても、実装とAIレビューで参照されていませんでした。そこで、どの仕様を参照し、どんな条件を適用するかを、担当者が毎回思い出して補う方法から、実行手順の中で確認する方法へ変えます。

図の上は、案件で共通して使う参照情報です。共通仕様の参照先と、適用する条件を確認できるようにします。その情報を、開発、レビュー、テストのそれぞれの仕事で使います。

役割ごとの手順は、Skillに記録します。この教材では、参照先、確認する条件、仕事の進め方、出力に含める内容を記録し、Agentがそれを使って実行する形を扱います。Agentは、仕事を実行するAIです。

例えば、開発では関連条件を確認して実装し、どの条件を反映したかを報告します。レビューでは共通仕様と差分を照合し、指摘と根拠を示します。テストでは適用する条件から確認項目を考え、実行結果を記録します。参照する前提は共通でも、各役割の手順と出力は異なります。

人は、参照先や条件が適切か、出力に必要な根拠があるかを確認します。Skillを用意しただけで、参照漏れや考慮漏れがなくなるという説明ではありません。実行結果を確かめ、必要な前提や手順を改善していきます。

このように、教材1で目的を捉え、教材2で意味と範囲を明確にした内容を、実際に使えるAIの手順にするのが教材3です。次は、別の機能でも試し、どう改善していくかを見てみましょう。

09　別の機能でも試し、AIが参照する条件と手順を改善します

教材3で用意した手順は、別の機能でも試してみます。今回の変更機能で使えたからといって、そのまま別の機能でも十分に使えるとは限りません。

例えば、同じ経費精算システムの承認機能で、開発、レビュー、テストに使います。その機能に関係する共通仕様を参照できたか、必要な条件を実装と検証に反映できたかを、出力と実行結果から確かめます。

ここでは、不具合の有無だけでなく、人が確認しやすい情報が出ているかも見ます。どの条件をどのコードやテストで確認したのか。その対応が分からなければ、また人が探し直すことになるからです。

足りないものがあったら、どこを直す必要があるかを考えます。関連する共通仕様を見つけられなかったのであれば、共通の参照情報や、適用する条件の説明を見直します。参照はできていても確認結果の根拠が出ていなければ、その役割のSkillに、確認の手順や報告に含める内容を足します。ここで直すのは、仕様の参照方法やAIの手順です。既存の業務ルールを、この試行の中で勝手に変更するわけではありません。

修正したら、もう一度実行して確かめます。必要な条件が反映されたか、根拠を確認しやすくなったか、人が探し直す負担は減ったか。このように結果を見ながら、チームで使う参照情報と、それぞれの役割の手順を改善していきます。

三つの教材では、目的を捉え、言葉の意味と範囲を明確にし、AIで実行して結果から改善します。この流れを、自分の仕事でも実践できるようにしていきます。

10　自分の担当業務から、チームで成果を出すAI活用を考えます

ここまで、経費精算システムの刷新案件を例に、三つの教材で何を学ぶかを紹介しました。

この案件では、共通仕様も開発の手順もありました。それでも、関連する仕様を実装とAIレビューで参照できず、必要な制御が抜けました。作成は速くなっても、人が条件や根拠を探し直し、修正と再確認をする時間が残ったわけです。

教材1では、今回の修正だけで終わらず、別の機能でも必要な業務制約を反映するには、どのような目的で作業を考えるかを学びます。教材2では、その目的に必要な言葉の意味と範囲を明確にします。教材3では、明確にした前提と手順を、AgentやSkillを使って実行し、結果から改善する方法を学びます。

学ぶときには、皆さん自身の担当業務も思い浮かべてみてください。開発なら実装や検証、レビューなら条件と変更内容の確認、PMやPLなら進捗や残作業の把握など、AIを使う作業は異なります。それぞれの仕事で、何のためにAIを使い、どの前提を参照し、何を確かめればよいのかを考えます。

そして、自分の成果物を作るところで終わらず、その内容をチームが確認し、判断できるかまで見ていきます。例えば、実装した条件とテスト結果の対応が分かれば、レビュー担当者は確認すべき根拠を探しやすくなります。PMやPLも、何が確認済みで、何が残っているのかを把握しやすくなります。

目指すのは、必要な条件をAIの作業に反映し、その結果を人が確認できるようにすることです。自分の作業の速さに加えて、確認や修正を含むチーム全体の仕事を改善するために、三つの教材を使っていきましょう。
