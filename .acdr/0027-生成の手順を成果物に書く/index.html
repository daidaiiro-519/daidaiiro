ACDR 0027

生成の手順を成果物に書き、依存の向きを測る直前に実行する

承認承認を得た。適用してよい2026-09-28
決めること ── 承認か差し戻しを返すのは、この1件である
no-more-spaghetti の規則ファイルで、生成物を持つ成果物に生成の手順を書けるようにし、check がその成果物の依存の向きを測る直前に実行する。

なぜ、いま決めるのか

no-more-spaghetti のブレストボード（.brainstorming-board/no-more-spaghetti/）の論点13 の要求事項に「生成の手順は、規則ファイルの成果物（units）に書く ── check が inward の前に実行する」とある。ACDR 0026（.acdr/0026-規則ファイルを成果物ごとの形へ移す/）で units の形へ変更したが、生成の手順を書く欄はまだ無い。生成物を持つ成果物では、生成物を指す参照が「参照先が実在しない」と報告され、実際の違反と区別できない。

形の変化

何がいまの形これからの形
生成の手順の置き場所書く欄が無い成果物の generate に、コマンドの配列の並びで書く。コマンドはシェルを経由しない
生成物を指す参照参照先が実在しないと報告する依存の向きを測る直前に、成果物の根で生成するので、実在するモジュールとして判定する
生成が失敗したとき該当なし（生成を実行しない）生成の手順を不合格として報告し、その成果物の依存の向きは実行しないとする

図で確認する

実現の形

no-more-spaghetti の手順で実施した。モデルと3つの仮定（失敗したら依存の向きを実行しない ・ 成果物ごとに1回だけ実行する ・ 依存の向きの直前だけに実行する）は、実装の前に提示して承認を得た。失敗する試験を5件書いてから実装し、試験は69件すべて成功した。clippy の警告は0件である。書いた後の検査は104件が合格し、不合格の2件は design-svg と brainstorming-board の SKILL.md の廃語で、この変更の対象外である。.coding-rules/rules.json の15の成果物は生成物を保持しないので、書き換えは発生しない。

比較した案

どれも反証を通過しなかった案である ── 未解決のまま残っているものではない。

案採らなかった理由
生成が失敗しても、依存の向きを測る生成物が無いまま測ると、実在しない参照先が大量に報告され、実際の違反と区別できない
生成の手順を、すべての規則の前に実行する論点13 の要求事項は「inward の前に」である。整形や静的解析の道具は、それぞれ自身で生成を処理する（cargo の build.rs など）
生成の手順を、規則の1件として書く規則は並びの順に実行されるので、依存の向きより前に並べる責任が書く側に移る。成果物に書けば、どの規則の前に実行するかを Skill が決める
生成の道具を Skill が保持する同じボードの論点2 で、Skill は検査する言語の外の道具を保持しないと決めた

アーキテクチャを決め・保ち・測りながらコーディングするSkill：no-more-spaghetti

目的

実装を書くときに使用する。遵守するのはアーキテクチャである ── 名前も整形も後から直せるが、
構造だけは絡まってから直すと全部が動く。

アーキテクチャは3つの面を持つ。

面何をするか
モデル構造を決める ── 変更理由が同じものをまとめ、違うものを分ける
依存の向き構造を保つ ── 規則1件と既存の道具で検査する
テスト構造を測る ── 先に書く。書きにくさは設計の報告である

テストは2つ目の原則ではない。 構造を測る道具である ── 模擬だらけになる、準備が長い、
1つ直すと大量に失敗する。どれも境界の置き方の報告である。

役割

- 与えられた仕様から、実装のモデルを起こす ── 仕様そのものは決めない
- 失敗するテストから書き、通してから、書いた後の検査を実行する
- 層の場所の規則を1件持ち、依存の向きを検査する
- 規則に書いたコマンドを実行し、終了コードだけを読む。出力は道具のまま渡す

道具は2種類あり、持ち主が違う。

種類誰が持つか例
検査する言語の道具プロジェクトが持ち、規則が名指しする。 この Skill は認知しない整形器 ・ 静的解析器 ・ 試験の実行器
この Skill の能力の実装この Skill が持つ規則を実行する機構 ・ 依存の向きの検査 ・ 契約の検査 ・ 雛形

区別する基準は、持ち運びである。 Skill を別のリポジトリへ移したとき、無いと
能力が欠けるものは Skill が持つ ── 依存の向きの検査をリポジトリ側へ置くと、
移した先で向きを検査できない（実測 ── 一度そう置いて、規則が Skill の外の経路を
指す状態になった）。

処理対象と成果物

処理対象

これから書く実装。仕様は利用者が持つ。

成果物

コードとテストである。規則の判定を添える。

文書置き場所単位
手順（この文書）SKILL.mdこの Skill に1つ
概念と契約references/この Skill に1つ
モデル成果物の中成果物ごと
規則（内を指すものも、外を指すものも）.coding-rules/（リポジトリに1つ）成果物ごとに1ファイル

規則を、この Skill の中に置かない。 層の名前と識別子は成果物ごとに違うので、
ここへ置くと2つ目の成果物で衝突する ── 内と外は出典の向きであって、置き場所の
区別ではない。

この Skill は、1つのリポジトリの中で完結する。 検査する場所は必ず1つの根で、
その外を指す対象は実行しない ── 他のリポジトリへ渡すのは規則ファイルであって、
実行が跨ぐことはない。

.coding-rules/ は、リポジトリに1つである。 成果物ごとにフォルダを作ると、実装が
増えるたびに各所へ生える ── 成果物が2つ以上あるなら、1つのファイルの units に
成果物を並べ、規則は適用する成果物の名前を持つ。

.coding-rules/rules.json      **規則ファイル1つ**（リポジトリに1つ）
.coding-rules/sources/<領域>/  外を指す規則の原文（取り直して照合するため）

管理する対象を1つにする。 成果物が複数在るときは、units に成果物ごとの根 ・ 言語 ・
層の並びを書き、規則は成果物の名前で指す ── ファイルを分けると、索引 ・ 区分 ・
名前の解決という仕組みが必要になる（実測 2026-09-26、41件を全部実行して5秒である）。
層の並びは、成果物の中でだけ意味を持つ ── 無関係な成果物の層を1列に並べない。

他のリポジトリのための置き場を保持しない。 規則は、その規則が実行される
リポジトリで作る ── 取り込むと、道具の版が上がったときに古い引用のまま残る。

規則ファイルを平らに並べない。 成果物と言語が増えるたびに一覧が読めなくなる ──
名前から経路へ解決する層を1つ挟み、呼ぶ側は名前だけを知る。

原文の置き場所も、規則と同じ側である ── 別の場所（調査の記録など）へ置くと、
規則を読む側が原文へ到達できない。

入力の想定

受け取る情報解釈・既定値
仕様何を作るか ・ どう振る舞うか ・ 何を拒むか。明示されなければ問う ── 推測で補完しない
規則ファイルの場所明示されなければ .coding-rules/ を読む。無ければ、モデルと一緒に起こす
採用するアーキテクチャ明示されなければポートとアダプタを採る（references/concepts.json）。他を採るなら、採ると書いて採る

実行手順

Step 1: モデルを起こす（分け方に迷うときだけ）

変更理由が同じものをまとめ、違うものを分ける。 名前はその単位に付け、
層は依存してよい先が決定する ── 層名を先に決定し、そこへ概念を配置しない。

この分け方の出典は references/concepts.json が保持する ── この文書は、
アーキテクチャの知識を散文で保持しない。

書くのは3つだけである ── 概念 ・ 持ち物 ・ 依存してよい先。実装の前に見せる。

書く書かない
新しい概念が増える ・ どの単位に入れるかが決まらない ・ 層をまたぐ既存の関数に1行足す ・ 純粋な計算を1つ足す ・ 整形や命名の変更

表し方は固定しない ── 変換なら入力と出力の型、画面なら状態と遷移になる。

Step 2: 規則を作る（規則ファイルが無いときだけ）

雛形は init が出す。 層の名前と識別子と言語を渡すと、.coding-rules/rules.json を置く。

no-more-spaghetti init <成果物の場所> --language go --layer core=internal/core --layer app=internal/app

雛形は、契約に対して不合格で出る ── 道具と出典が空だからである。その不合格の一覧が、
そのまま充填する欄の一覧になる。

出典の向きで作り方が変わる。

種類作り方
内を指す規則（層の場所 ・ 依存の向き）モデルから書き出す。 照合する相手が存在しない ── 出典はこちら側の決定である
外を指す規則（言語 ・ 道具の規約）4つの条件を満たしてから書く ── ①原文を取得する ②引用を原文の文字列で照合する ③取得した日と版を残す ④原典の立場を書く。③と④は契約が要求する（source.fetched ・ source.authority）
作らないもの無くても構造が外れないもの ・ コマンドで検査できないもの

依存の向きは、この Skill の inward で検査する。 規則は check: { inward: true } と書き、
言語と層の並びは成果物（units）から来る ── 層の並びを規則の引数へ複製しない。
units に * と書くと、層を持つ成果物すべてを指す。

生成物を持つ成果物は、生成の手順を generate に書く。 check は、その成果物の
依存の向きを測る直前に、成果物の根で1回だけ実行する。生成が失敗したら、その成果物の
依存の向きは「実行しない」になる ── 生成物が無いまま測ると、実在しない参照先が
実際の違反と区別できない。生成の道具も、この Skill は保持しない ── 成果物の側が書く。

言語の仕組み検査
依存の宣言をコンパイルで強制する（Cargo.toml ・ go.mod）inward に加えて、その言語の道具（cargo build ・ go build）を追加の保証として置いてよい
強制しないinward だけが検査する

解決の範囲を広げる設定が、依存の宣言を無効にすることがある。 宣言に無い依存まで
解決するようになると、コンパイルによる保証が効かない ── その設定を置かない。
どの設定が該当するかは、成果物の側が規則の採用範囲へ書く。

照合する実装は、この Skill が持たない。 どの道具で取得するかは問わず、
持つのは条件だけである ── ①と②は機械で検査できない（原文を取りに行くことになり、
外部の情報源への依存が生じる）。③と④は契約が検査する。

原典の立場を、規則の側に書く（source.authority）。公式かどうかは、URL を見ても
判定できない ── 言語の提供元が出す文書にも、振る舞いの定義と勧めが混在する。

値何を指すか外してよいか
spec提供元が出す振る舞いの定義（終了コード ・ lint が何を検出するか）外すと事実と食い違う
recommendation提供元が出す勧め（規約集 ・ 入門書）外してよい。理由を記録する
third-party提供元の外（別の組織が維持する道具）版と維持の主体がこちら側の管理外である

規則の内容の強さで決めない。 決めるのは原典の立場だけである ── 内容で決めると、
同じ原典を指す2件が別の値を持つ。

書く順番が決まっている。 3番目を飛ばして4番目は書けない ── 道具は識別子の形で規則を書く。

順番決めるもの言語に依存するか
1モデル（概念 ・ 持ち物 ・ 依存してよい先）しない
2概念の層（名前と、内から外への並び）しない
3その言語での識別子する
4内を指す規則する
5外を指す規則する

何を書くかは、契約が案内する。 references/rules.schema.json の各項目が3つの
案内を持つ ── description（概要）・ x-prompt.read（読み取り）・
x-prompt.write（値を充填するとき）。項目の一覧を、この文書に複製しない。

キーは ASCII である（units ・ root ・ language ・ layers ・ where ・ marks ・
rules ・ rule ・ source ・ scope ・ check ・ tool ・ inward ・ target ・ authority）。機械が分岐する値も同様で（pass ・ fail ・ skip ・
spec ・ recommendation ・ third-party）、
画面へ出す語は、読む側の対応表が持つ ── 1つの語が識別子と表示を兼ねると、
表示を直した瞬間に分岐が壊れる。実装の識別子も、引数の名前も同じである ──
日本語を置くのは、docstring ・ 検出の文 ・ 画面へ出す語だけにする。

Step 3: 決まっていることを読み直す

実装へ入る前に、その決定の本文を読む。 決めた語と、これから書くものを1つずつ
照合する ── 決定と実装の食い違いは、機械で検査できない（どのコマンドも、
「答えの語と実装が一致するか」を測らない）。だから、この工程を飛ばすと誰も検出しない。

照合するもの何を確認するか
決定の本文に在る語置き場所 ・ 単位 ・ 名前を、そのまま採る
決定に語が2つ在るときどちらかを選ばずに、両立する形を探す ── 片方を破棄した時点で、決定の半分に違反している
一般の慣習同じ種類の道具がどこへ置くかを確認する（設定は根に置く、など）

実測 2026-09-24 ── 論点5の答えは「リポジトリの .coding-rules/ へ」だったのに、
成果物ごとに .coding-rules/ を置いた。決定には「リポジトリの」と「成果物に1つ」の2つの語が
在り、フォルダを増やす方向で解決した ── ファイルを増やす方向なら両立した。

Step 4: 失敗するテストを書く

実装が無い状態で実行し、失敗することを確認する。
失敗しなければ、そのテストは何も検査していない。

Step 5: 実装する

テストが通る最小の実装を書く。

Step 6: 通す

テストが通ることを確認する。通っていない状態で次の工程へ進まない
── 後の検査が、壊れた対象を検査することになる。

Step 7: 書いた後の検査

何を実行するかを先に見せ、それから実行する。

no-more-spaghetti plan  <成果物の場所> <規則ファイルのパス>   # 実行しない
no-more-spaghetti check <成果物の場所> <規則ファイルのパス> [--json]

出力が長いときは、続きを同じ入口から読む ── 道具は実行し直さない。

no-more-spaghetti output <成果物の場所> <実行の識別子> <規則の名前> [位置] [量]

工程の中は順序が任意である ── 整形 ・ 静的解析 ・ ビルド ・ 依存の向きは、
どの順でも判定が同じである。

出力形式

check は、規則ごとの判定を返す。判定は3つである。

判定条件
合格終了コードが0
不合格終了コードが非0。道具の出力をそのまま添える
実行しない道具が見つからない ・ 検証方法に道具が無い ・ 制限時間で終わらない

「実行しない」を合格として扱わない ── 道具が消えた瞬間に、全部が通る。

保持するのは直近の1回だけである。 check は前回の保存を消し、実行の識別子を返す ──
合わない識別子には明示して断る。別の実行の中身を返すと、読む側はそれを今回の結果として
受け取る。

この判定で区別できないものが2つある。

区別できないものどう現れるか
道具の誤用と、本物の違反引数を誤った道具は非0を返すので、不合格として出る。出力を読むと判明する
実行する環境の差道具が PATH に無ければ「実行しない」になる。同じ規則ファイルでも、環境が違えば判定が変わる

規則が0件のファイルは、合格ではない。 1件も検査していない状態なので、検出として
返す ── 呼ぶ側が終了コードだけを読むと、検査した結果として受け取るためである。

既にコードが在るリポジトリへ導入すると、不合格が大量に出る。 それが観測の結果で
あり、改修が発生する。一度に直せないときは check.target に範囲を書いて狭める ──
規則を緩めるのではなく、見ている範囲を書く。広げるときは、その1行を書き換える。

--json を付けると、ok ・ findings ・ data の形で返る。
findings を確認すると、どれが不合格かが判明する ── 出力を確認するのは、不合格の1件だけである。

出力が長いときは、先頭と末尾を返し、真ん中を除外する。除外した旨と全文の場所を
output_file に添えるので、足りなければ読む側が開く。

ガードレール

- 仕様を決めない。何を作るか ・ どう振る舞うか ・ 何を拒むかは利用者が持つ。
仕様に無いことが必要なときは、問うか、仮定として明示して承認を得る
- 既存のコードを手本にしない。既存は観測した事実であって、正しさの根拠ではない ──
モデルと食い違っていれば、合わせずに食い違いを報告する
- 抽象を飛ばして具体から書かない。近くのコードへ寄せた結果は、こちら側で正しさを判定していない
- 層名を先に決めない。層はモデルから導出される
- 層の識別子を、ファイルの場所として検査しない。言語ごとに形が違い、経路とは限らない ──
値が正しいかは、道具が実行できるかで判明する
- 不合格を0件にするために、層の宣言を書き換えない。既存の構成に合わせると、
違反がそのまま規則になり、以後その検査は何も検出しない
- 違反の件数を基準値にしない。件数を数えるには、道具の出力を解析することになる
- 工程を飛ばさない。実装から書き始めない
- 決定の本文を読み直してから実装へ入る。決定と実装の食い違いは機械で検査できない ──
決定に語が2つ在るときは、片方を破棄せずに両立する形を探す
- テストが書きにくいときは、構造を疑う。模擬を増やして通さない
- 検査の道具を実装しない。既存の道具を呼ぶ ── 自作すると言語ごとに書くことになり、
既存の道具と結果が食い違ったときに、どちらが正しいかを判定できない
- 道具の出力を解析しない。検出は道具の仕事で、意味の解釈はこちら側が実施する ──
解析すると、道具ごとに違う書式へ依存する
- 道具の出力を、まとめて受け取らない。ファイルへ流し、上限までしか読まない ──
受け取ると、道具が出した量がそのままこの側の記憶に載る
- 除外してよいのは真ん中だけである。先頭と末尾の両方を返し、全文の場所を添える ──
読む側は、この出力で次の手を決める。翻訳器は先頭に、試験の実行器は末尾に
必要なものを置く
- 道具は配列で書く。シェルを経由すると、引数の展開が実行するシェルに依存する
- 判定を終了コードで返す呼び方を選ぶ。同じ道具に、判定を返す呼び方と返さない
呼び方がある ── 違反を並べながら終了コード0を返す呼び方が実在する。
選び違えると、検査は黙って通る
- 規則を立てる条件は2つで、両方を満たすものだけを書く ── 無ければ外すか、
コマンドで検査できるか。コマンドを伴わない心得を書かない（読みやすく書く ・
適切に命名する）── 件数が増えると、本当に見るべき数件が埋没する
- 実行する内容を、実行の前に提示できるようにする。承認はホストが持つ ──
原典は拒否の義務を Applications SHOULD の並びに置いている
（specification/2025-06-18/server/tools:30、2026-09-24 取得）
- 成果物の場所の外を指す対象を実行しない。解決してから、成果物の場所の中かを確認する
- 規則ファイルが信用の境界である。書き換えられる者は、その成果物で任意のコマンドを
実行できる立場に在る ── 隠さずに、道具の説明へ書く
- ポートを作る条件は2つで、どちらかを満たすときだけ作る ── 実装が2つ以上あり得るか、
テストで差し替えるか。全部の外部接触にポートを作ると、実装が1つのままの抽象が増える

参照

- references/concepts.json: 手順が依拠する概念の出典。 3件（変更理由で分ける ・
依存の向き ・ ポートとアダプタ）が、引用と、取り直すための4つの値（url ・ 日 ・
sha256 ・ 行）を持つ。原文は同梱しない ── 引用が原文と一致するかは、取り直して
照合する側が判定する。この Skill は、他の Skill を名指しで呼ばない
- references/concepts.schema.json: 概念の出典の契約
- references/schema-meta.schema.json: 案内の契約。 スキーマ自身を実体として
検証する ── 案内を要求するのは、最上位に x-generates を持つスキーマだけである
- references/rules.schema.json: 規則ファイルの契約。 規則1件が3要素（出典 ・ 採用範囲 ・
検証方法）を持ち、適用する成果物（units）の名前を持つ。成果物は根 ・ 言語 ・ 層の並びを持つ。層の名前は原典に無い ──
domain も usecase も、ヘキサゴナルとクリーンのどちらの原文にも無い（2026-09-22 に照合）
- rs/parts/src/init.rs: 規則ファイルの雛形を組む。道具の名前を1つも持たない ──
雛形は契約の形から組み、何を充填するかは x-prompt.write が案内する
- rs/parts/src/rules.rs: 規則ファイルを読み、規則を成果物ごとの実行1件へ展開する。
実行する場所は「成果物の根 ＋ check.target」である。生成の手順は、成果物ごとに
最初の依存の向きの実行の直前へ挿入する
- rs/parts/src/run.rs: 規則のコマンドを実行し、終了コードで判定する。
依存の向きの規則は、別の process を立てずに inward で測る ── MCP から呼んだときに、
実行する binary が CLI ではないためである。
標準入力を閉じて実行する ── 入力を待つ道具が、制限時間まで止まる。
出力は上限で切る ── 道具が出した量が、そのままこの側の記憶に載る。
道具の名前を保持しない ── 実行するものは規則から来るので、この Skill の依存は0件である
- rs/parts/src/validate.rs: 規則ファイルの形と、層の宣言の構造と、概念の出典と、案内を検査する
- rs/parts/src/inward/: 依存の向きを、原文の構文木で測る。 検査は4段（モジュール ・ 依存 ・
モジュール解決 ・ 向きの判定）である。syntax.rs が言語の表を持ち、各言語が契約の欄
（bridge ・ dynamic ・ branches ・ naming）を宣言する。names.rs が別名と検索パスを
設定ファイル（Cargo.toml ・ go.mod ・ package.json ・ tsconfig ・ pyproject ・ gemspec ・ CMake）から読み、
judge.rs が層の並びから許可辺を導いて突き合わせる。判定は言語を認知しない ──
受け取るのは層の並び ・ 依存 ・ モジュールの一覧 ・ 名前の区切り方だけである。
測り方の限界は、検出と分けて返す ── 混ぜると、解決しなかった参照が違反として出る。
報告するのは、参照元が層に属す依存だけである ── 層の外のファイルは、向きの規則を課されない
- rs/declare/src/lib.rs: 道具の宣言。能力の正本であり、CLI と MCP はここから組む
- rs/cli/: 唯一の入口。 check ・ init ・ plan ・ output ・ validate ・ inward を持つ ──
どれも --json で機械が読む形が出る。終了コードは 0 正常 ／ 1 検出あり ／ 2 誤用。
validate は、渡されたファイルの種類（規則 ・ 概念 ・ スキーマ）で適用する契約を替える。
宣言に無い旗は断る
- rs/mcp/: MCP の面。同じ宣言から組む ── 能力を1行も複製しない
- rs/parts/tests/: 事例（66件）。実行と判定 ・ 契約の検査 ・ 雛形 ・ 禁じた辺 ・
10言語の読み込みの抽出 ・ 言語に依存しない2つの義務 ・ 成果物ごとの展開 ・ 生成の手順を固定してある
- rs/declare/tests/contract.rs: 依存の向きの契約を、言語の表のすべての言語へ課す（7つの義務）。
表に言語を足すと、この試験がその言語にも課される ── 試験データが無ければ失敗する
