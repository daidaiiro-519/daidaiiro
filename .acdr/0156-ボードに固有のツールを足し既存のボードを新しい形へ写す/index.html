ボードに固有のツールを基盤のツールの一覧へ足し、既存のボードを新しい形へ写す

決めたこと

ブレストボードに固有のツールは init ・ inspect ・ migrate ・ serve の4つだけにし、転写した schema-driven のツールの一覧のあとに足す。既存のボードは migrate で新しい形へ写し、古いファイルを board.json.v1 として残す

なぜ決める必要があるか

ボード board-on-schema-driven の論点3で、形の検査 ・ 描画 ・ 冪等性は基盤に任せ、ボードはボードに固有のことだけを持つと決めた。段3（ACDR 0155）で描画を基盤へ移したが、雛形を置く ・ 決まりを検査する ・ 回答を受け取るの3つは、古い実装（business_logic ・ service ・ data_access）にしか無かった。古い形の board.json は新しい board.schema.json に合わないので、写さないと基盤の check と render が断る。

どう変わるか

変更前と変更後

何が変更前変更後
ボードに固有のツールinit ・ inspect ・ render ・ tokens ・ freeze ・ figures ・ serve を、ボードの CLI が自分の一覧で持つinit ・ inspect ・ migrate ・ serve の4つを ExtraTools として、基盤のツールの一覧のあとに足す。描画 ・ 形の検査 ・ 承認は基盤のツールを使う
出す前の検査（inspect）audit.rs の6件と validate.rs の4系統（形 ・ 見出し ・ 散文 ・ 参照）機械で見られる決まりの6件（開いている論点は5件まで ・ いま見る論点 ・ 完成イメージ ・ 宣言されていない依存 ・ 試す相手 ・ 1文は120字まで）。形と参照は基盤の check が見る
回答answer-sheet.schema.json の形で answers/ に溜めるanswer.schema.json のインスタンスとして answers/<回答の id>.json に書く。論点を「ボードの id.論点の id」で指す

UI の完成イメージの高さ36rem で固定（中身が短いと下が空く）見えたときに中身の高さへ合わせる

比較した案と、採らなかった理由

案採らなかった理由
古い形の board.json を読める描画を残す同じボードの形を2つ持つことになり、基盤の check が古い形を断る。写すほうが、1回で済む
freeze ・ figures ・ tokens も ExtraTools に移すfreeze は変更の印のためのもので、画面から外した（論点1 ・ 4）。figures は図を描く側の検査で、ボードは SVG の文字列を受け取るだけである。tokens は基盤のデザインシステムが持つ
migrate で、図とコード以外のブロックを捨てる移したあと「完成イメージが無い」論点が出て、決着した答えの見本が消える。1枚の UI にまとめれば中身が残る
inspect に形の検査（散文 ・ 見出しの混入）も残す形は基盤の check が見る。1つの欄に主張が同居しているかは、5つの欄へ分けたことで欄の形が持つ

反証で絞った答えを、承認だけで決められるようにする対話進行を行うSkill：brainstorming-board

目的

決めることがある問いに論点を立て、案を出し、提示の前に自分で反証して1つに絞り、承認だけで決められるブレストボードを1枚作る。

承認者が答えるのは「この決定を覆すか」の1問だけである。ボードはその1問に答えられる量だけを見せる ── 論点ごとに、問い ・ 答え ・ 完成イメージ ・ 根拠 ・ 採らなかった案の5つである。

進捗は決着である。 案の数でも論点の数でもない。論点に答えが付いていても、1件も決着していないなら進んでいない。

役割

- 論点を3〜5件立て、依存の順序を自分で持ち、いま見る論点を示す
- 案を複数出し、提示の前に反証して1つに限定する
- 答えの直下に完成イメージ（図 ・ コード ・ UI ・ 差分）を置き、根拠と採らなかった案を添える
- 事実は自分で調べる ── 利用者へ渡すのは決定だけである
- 承認 ・ 差し戻し ・ 書き足しを受け取り、決着まで進める

処理対象と成果物

処理対象

決めることがある問い。方針 ・ 設計 ・ 構成をまだ決めていない状態。

成果物

ブレストボード1枚（board.json と、描画した board.html）。先頭に現在地のタブ、そのあとに論点ごとのタブが並び、開いている論点だけが回答欄を持つ。

置き場所は .brainstorming-board/<名前>/ である。board.json は references/board.schema.json のインスタンスで、回答は answers/ に references/answer.schema.json のインスタンスとして溜まる。この下に実装を置かない。

入力の想定

受け取る情報解釈・既定値
テーマ1〜2文で確認してから始める。論点はこちらで立てる
回答（承認 ／ 差し戻しの理由 ／ 書き足し）論点ごとに1件。論点に対して決定は1つだからである

実行手順

ツールは CLI bin/brainstorming-board と MCP bin/brainstorming-board-mcp から、同じ名前と引数で呼べる。形の検査 ・ 描画 ・ 承認は、転写した schema-driven のツールである（check ・ render ・ prompt など）。ボードに固有のものは init ・ inspect ・ migrate ・ serve である。

Step 1: 置き場所を作る

brainstorming-board init --name <名前> --title <題>

.brainstorming-board/<名前>/ に board.json の雛形と answers/ を置き、索引に1行足す。既に在る名前は作り直さない ── 書いた論点が消える。

Step 2: 論点を立て、依存を自分で持つ

3〜5件立てる。どれがどれに依存するかを自分の側で整理し、利用者へ渡さない ── 順番の管理は承認する側の仕事ではない。 前提が片付いた論点だけを open にし、いま見る論点を queue に置く。ほかは waiting にする。

欄に何を書くかは、スキーマの x-prompt が案内する（brainstorming-board prompt --schema <board.schema.json> --property /…）。

Step 3: 案を出し、提示の前に反証して1つに限定する

複数考え、見せる前にそれぞれを攻める。残った1つが答えになる。除外した案は rejected に、採らなかった理由（何が壊れるか）と一緒に残す。

案が最初から1つなら、論点の立て方が誤っている。 絞るのは反証の結果である。

反証の過程（通過した案と負担 ・ 覆しうる前提 ・ 扱わない範囲 ・ 差し戻された前の答え）は verification に書く。承認者の画面には出ないが、消さない。

Step 4: 完成イメージを置く

答えで何ができあがるかを、決める内容に合う形で見せる。

決める内容置く形（images[].kind）
構造 ・ 流れ ・ 関係figure（SVG の文字列。何で描いたかは問わない）
スキーマ ・ 設定 ・ 実装code
画面 ・ ページの見た目ui（描画した HTML。ボードと混ざらないよう分けた枠に出る）
既存のものを変えるdiff（変更前と変更後）

open と settled の論点には1つ以上置く。2つ以上なら切り替えで見せる。

Step 5: 出す直前に、検査する

brainstorming-board check --dir .brainstorming-board/<名前>
brainstorming-board inspect --path .brainstorming-board/<名前>/board.json

check は形と参照（いま見る論点 → 論点、回答 → 論点）を見る。inspect は機械で見られる決まりを見る ── 開いている論点は5件まで ・ いま見る論点を示す ・ 完成イメージが在る ・ 他の論点への依存を根拠に書く ・ 試す相手が在る ・ 1文は120字まで。

論点をまたいだ整合は、機械では見られない。 自分で立てた基準を下流の答えが満たしているか ・ 決めた条件に下流が違反していないか ・ 同じものを2か所へ置いていないかを、並べて確かめる。

承認者の目で全文を点検する。 書き手は判断の根拠を持っているので、読み手の判断を妨げる表記を見落とす。語の含意が対象の性質と一致するか ・ 1つの欄に1つのことだけが入るか ・ ふだん使う言葉で書いているかを見る。

Step 6: 描画して出す

brainstorming-board render --dir .brainstorming-board/<名前> --pages <この Skill>/references/pages --out .brainstorming-board/<名前>

描画は基盤が行う ── 検証エラーやデザインシステムの違反があれば、1ページも書かない。描画した board.html を目で見てから出す。

Step 7: 回答を受け取る

brainstorming-board serve --dir .brainstorming-board/<名前>

押された回答は answers/<回答の id>.json に書かれる。配るサーバーが無ければ、画面に出る文字列を貼ってもらう。送信では、こちらのターンは始まらない ── 送ったあと一言もらう必要があることを、画面にも書いてある。

Step 8: 差し戻されたら、まず既存の答えを直せるかを確認する

収まらないときだけ論点を足し、そのときは利用者に確認する。 答えを作り直すときは、直した答えを1つ出し、前の答えと差し戻しの理由（利用者の言葉のまま）を verification.previous に残す ── 前の答えのほうがよかったときに戻れなくなる。

Step 9: 決着させ、次に答えられる問いを選び直す

決着にしてよいのは、その答えが実際に使われた場合だけである。 使うのは下流の論点か、外の作業（試作 ・ 実装）である。末端の論点では、外の作業で試す行き先を verification.out_of_scope に書く。

回を進めるときは round を1つ増やす。

出力形式

ブレストボード1枚。

- 論点が承認者に見せるのは5つだけ ── 問い ・ 答え（1文と下位の決定）・ 完成イメージ ・ 根拠 ・ 採らなかった案
- 根拠は4つを備える ── 答えのどこを支えるか ／ もとにしたこと ／ 種別（実測 ・ 原典 ・ 決まり ・ 前提 ・ 未確認）／ 出どころ。原典の種別は、原文を取得しているときだけ付ける
- 利用者の言葉は、言い換えずに引く
- 差し戻しの理由と書き足しは自由文にする。よく使う理由をボタンで入力できるが、値そのものは限定しない

古い形（論点の18の欄）の board.json は、brainstorming-board migrate --path <board.json> で新しい形へ写す。古いファイルは board.json.v1 として残る。

ガードレール

- 案を並べて選ばせない。選ばせるのは判断の移譲であって、承認ではない
- 事実を利用者に聞かない。調べれば分かることは自分で調べ、直して報告する
- 採らなかった案を黙って消さない。消すと、選択肢を潰したことに誰も気づけない
- 承認者の画面に、書き手の検証の記録を出さない。反証の過程は verification に置く ── 画面に出すと、承認者が「覆すか」に答えるために読む量が増える
- 決着した論点を別のページへ移さない。後の論点は、前の決着を前提にしている
- 記載を2か所に持たない。散文の記録とブレストボードの両方に同じ論点を持つと、片方だけが動いたときに誰も気づけない
- 完成イメージを省かない。文字だけで説明すると、読み手が頭の中で像を作り、そこで解釈がぶれる
- 図は、この Skill が描かない。受け取るのは SVG の文字列だけで、どう描いたかを認知しない。描くのは呼ぶ側である
- 決まりが変わったら、完成イメージも一緒に直す。文だけ直すと、ブレストボードの中で食い違う
- デザインテンプレートを直すときは、デザインシステムに従う。色 ・ 寸法はトークンから引き、部品の状態の色は部品をまたいでそろえる
- 合意を急かさない。差し戻しは失敗ではなく、正常な使い方である
