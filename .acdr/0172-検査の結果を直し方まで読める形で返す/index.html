検査の結果を、直し方まで読める形で返す

決めたこと

検査の結果は、何がどれだけ契約を外れたかと、直し方の案内まで返す。

なぜ決める必要があるか

基盤の check は、配列の要素が maxContains を超えたときも、contains に合う要素が無いと返していた。JSON Schema を検証する crate（jsonschema）が、どちらの誤りも同じ種類で返すためである。要素が多すぎるのに無いと言われると、読んだ人も AI も逆の向きに直す。check-schemas の指摘も、どこが何かだけで、直し方は別に prompt を引かないと分からなかった。ボード concrete-schema-roles で、指摘から案内まで引けるかは作るときに確かめるとしていた。書き方の作法の正本は meta-schema の x-prompt なので、指摘にその案内を添える。

どう変わるか

変更前と変更後

何が変更前変更後
contains の誤りの文要素が多すぎても少なすぎても「contains のスキーマに合う要素が無い」合う要素を数え直し、maxContains を超えた ・ minContains より少ない ・ 1つも無い、を言い分ける
check-schemas の指摘schema ・ at ・ rule ・ message だけを返す欠けた欄や誤った値の指摘には、meta-schema のその欄の x-prompt を prompt として添える

比較した案と、採らなかった理由

案採らなかった理由
jsonschema が返す誤りの場所（maxContains か minContains か）だけで文を分けるmaxContains だけを書いたスキーマでは、合う要素が0個のときも同じ場所で返る。場所だけでは、多すぎるか無いかを言い分けられない
指摘に案内を添えず、prompt ツールで引いてもらう指摘のたびに、どの欄の案内を引くかを読み手が決めることになる。案内の正本は同じ meta-schema なので、添えても二重にならない
エンジンの検査の決まり（x-ref の指す先など）の指摘にも案内を添えるその作法は meta-schema の根の x-prompt にまとめて書いてあり、どの1件かを指摘から決められない。いまは欄の指摘だけに添える
