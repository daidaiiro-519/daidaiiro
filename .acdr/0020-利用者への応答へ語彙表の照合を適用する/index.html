利用者への応答への語彙表の照合

承認承認を得た。適用してよい2026-09-27

利用者への応答に、文書と同じ語彙表の照合（和語の述部と廃語）を適用する能力を、doc-writing-skills の道具として持たせる。

なぜ、いま決めるのか

直近40件の応答を実測したところ、和語の述部が104件、廃語が28件在った。上位の語はいずれも語彙表に登録済みで、語彙表は機能していた。欠けていたのは、会話の応答へ照合を適用する経路である。応答で使用した語は、そのまま文書へ流入する。能力は Skill の道具が持ち、CLI と MCP の両方から呼べる形にする。Stop フックはその呼び出し元の1つである。

形の変化

何がいまの形これからの形
照合の対象ファイルに書いた文書だけ文書と、利用者への応答の両方
応答の照合の実行無い（書き手の注意に依存する）応答が完了するたびに Stop フックが reply を実行し、検出があれば修正した全文を出し直させる
能力の置き場所─doc-writing-skills の宣言。CLI（reply）と MCP（reply）の両方から呼べる

図で確認する

実現の形

ゲートに、ファイルを経由せず文字列へ判定を適用する入口（inspect_text）を追加する。宣言に reply を追加する。reply は本文を message で受けるか、Stop フックの入力（JSON）を標準入力から読む。検出があれば decision と reason の JSON を出力し、無ければ何も出力しない。フックの登録（.claude/settings.json）は、利用者が配置する。

適用先

doc-writing-skills のゲート（rs/parts/src/gate.rs）と宣言（rs/declare/src/lib.rs）が変わる。検査（rs/declare/tests/reply.rs）と SKILL.md の記述も変わる。フックの登録先は .claude/settings.json である。

比較した案

どれも反証を通過しなかった案である ── 未解決のまま残っているものではない。

案採らなかった理由
フックのスクリプトを Python で .claude/hooks/ に置く能力が Skill の外に出て、CLI と MCP から呼べない。このリポジトリの道具は Rust へ移しており、言語も分岐する
応答にも、文書と同じ8つの判定をすべて適用する見出しの階層や表の判定は、会話の応答の形には適合しない。語彙表で決まる2つだけが、応答から文書へ流入する語を捕捉する
応答を表示する前に差し止めるStop フックは応答が完了したあとに実行される（公式文書 hooks の Stop の節）。表示前に差し止める経路は無い

name: doc-writing-skills
description: 日本語のテクニカルライティング文書を書く・直すときに必ず使うスキル。設計文書・仕様・報告・README・学術文書など、人が読む文書を書き起こす前と、書いたあとに使う。「文書」「まとめて」「書いて」「ドキュメント」と言われたとき、および既存のmdやHTMLの本文を直すときに必ず使う。
version: 1.0.0

目的

技術文書としても学術文書としても違和感のない日本語を書く。

満たすこと
論意味が通り、論が成立している
構造情報が、その型に合った形で置かれている
文調人が読んで、一度で意味が取れる
語彙同じ文脈では、同じものが同じ語で呼ばれている

判断の材料は10の概念である。
どれも公開された規格・指針から導いており、出どころを最後の節に置く。

出すには、2つのゲートを実行する。

ゲート何を検査するか誰が決めるか
10件にできるものが、0件であること機械
210の判定すべてに、結果が1行ずつあること書き手

ゲート2が保証するのは、判定を適用したことだけである。
何を直すかは、書き手の判断に残る。

役割

- 書いたものに、10の概念から導いた判定を適用する
- 判定を、読む人がその場でできる1つの操作に降ろす
- 原典から導けない決めは、そう書く
- 適用しなかった判定を、報告に書く

処理対象と成果物

処理対象

これから書く日本語の文書、または既に書いてある日本語の文書である。

成果物

10の判定を適用し、直したか残したかを明示する文書である。

入力の想定

受け取る情報解釈・既定値
読み手明示されなければ、その文書を初めて開く人とする
用語の定め対象フォルダに用語を定めた文書があれば、それに従う
文脈の境界明示されなければ、文書1本を1つの文脈とする

実行手順

Step 1: 読み手と用語を決める

書き始める前に、読み手を1つに決める。
読み手が決まらないと、選ぶ語も構成も決まらない（概念8）。
対象フォルダに用語の定めがあれば、先に読む。

Step 2: 10の判定を適用する

上から順に適用する。
前の概念が成立していなければ、後の判定は意味を保持しない。

#概念規則判定
1読み手が組み立て直す作業を、書き手が負担する1文の中で、読み手に計算をさせない。名詞句には、指し先を文書の中に置く名詞句を1つずつ抜き出し、「何の」「どこの」「どっちの」「誰が」を問う。文書の中の文字列で答えられない名詞句が1つでもあれば、その文は書けていない。「読み返して不自然か」で判定しない——書き手は指し先を知っているので、不自然に見えない
2情報の型が、置く形を決める対比・条件・手順・分岐を、散文に置かないその段落を、表か図に置き直せるかを試す
3数が増えたら、形を変える並べるものが3つ以上なら、箇条書きか表にする数える
4見出しは、本文を読まずに全体を掴ませる見出しの階層を飛ばさない。見出しを追えば全体の内容がつかめるようにし、見出しを目立たせる。番号は付けても付けなくてもよい ── 統一されているかだけを確認する見出しだけを抜き出して、順に読む。そのうえで、どの本文がどの見出しに属すかが見た目で分かるかを確認する
5結論を先に置き、根拠を後ろに置く節の最初の一文を結論にする各節の先頭文だけを並べて読む
6読み手は、形の違いを意味の違いとして読む同じ立場のものは同じ形で書く。文体は文書の中で1つにする並んでいるものの語尾を見比べる
7語の意味は、文脈の中で定まる同じ文脈では、1つの意味に1つの語だけを対応づける。文脈が変わるなら、変わることを書く用語を列挙し、同じ意味の別の語が無いかを確認する
8読み手が誰かで、選ぶ語と構成が変わる読み手を先に決める。語は、読み手の世界にすでにある語から選ぶ。分野で定着した専門用語はそのまま使い、自分が作った語・訳した語は使わない。使うなら、新しい語だと書いて定義する。名前のあるものを、描写で呼ばない語の出どころを提示できるかを確認する。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する。そのうえで、書いた操作や物に、分野で通っている名前があるかを1つずつ問う。あるなら、描写ではなくその名前を書く——「均す」ではなく正規化する、「流す」ではなく実行する、「鵜呑みにしない」ではなくそのまま信じない。ふつうの日本語の語も、この判定に掛ける。作った語でも訳した語でもないので、出どころだけを確認すると通り抜ける。読み手が分野の外の人でも、描写に置き換えてはならない。言い換えてよいのは、日常語で意味が表せるものだけである（頻回→頻繁に）。日常語で表せないものは、その名前のまま使い、説明を添える
9読み手が一度に扱える量には限りがある1文は短くする。段落は3行から7行にする。文書の限度を決める数える
10比喩と定型句は、読み手によって解けない比喩は、例として明示するときだけ使うその比喩を字義どおりに読んで、意味が通るかを試す

名詞句で終わることは、それ自体では欠陥ではない。
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
判定1が見るのは、文の中で読み手が戻るかどうかである。

Step 3: 直したか、残したかを明示する

判定に該当した箇所を、直すか、理由を付けて残すかのどちらかにする。
理由が書けないなら、それは直す対象である。

Step 4: 2つのゲートを実行する

ゲート1は機械が決める。

最後の1つだけ、概念から導けない。
マークダウンの記法に拠るもので、5つの原典はどれも描画について書いていない。
別枠であることを、--list と名簿に書いてある。

概念3と概念9は、ゲートに入らない。
数は数えられるが、いくつで形を変えるかは文脈で変わるので、0件にできない。
判定として、書き手が適用する。

応答で使用した語は、そのまま文書へ流入するので、文書と同じ語彙表で照合する。

Stop フックは応答を表示したあとに走る ── 表示を止めることはできず、修正した全文を続けて出させる。

ゲート1の結果通ったか、通っていないか。件数を書く
適用しなかった判定番号で書く。全部適用したなら、そう書く。1つでも欠ければゲート2は通っていない
確認していないこと確認していないことを、確認したと書かない

ガードレール

- 運用の覚書の書き方を、どの文書にも使わない。ゲート1の「述部が和語である」が検出する語は、書いた本人が読み返すための書き方であって、読み手のための書き方ではない。CLAUDE.md と Skill も例外にしない ── 例外にすると、そこで書いた語がそのまま本文へ流れる。どの文書でも、操作の名前で書く
- 名前のあるものを、描写で呼ばない。その操作に分野の名前があるなら、自分の言葉で言い換えない
- 比喩で言い換えない。対象を別の物へ置き換えた語を使わない ── 指し先が読み手の側で決まらない（文書か、欄か、クラスかを、読み手が推測することになる）。利用者への応答も同じである ── 応答で使用した語は、そのまま文書へ流入する。対象の名前で書く。検出する語は廃語の一覧が保持する ── 散文で例を並べると、その例が本文へ流入する。ただし、普通の語の一部になる語は一覧へ入れられない ── 部分一致で正しい語まで検出するためである（「段」は段階 ・ 段落 ・ 手段 ・ 段組みの一部である）。その種の語は機械で検出できないので、書く時点で遵守する
- 文語寄りの語を使わない。「営み」「所以」「〜ねばならない」のように、書き言葉のためだけに選んだ語は、ふだん話す語へ替える。判定は、同じことを口で説明するときにその語を使うか ── 使わないなら、読み手にとっては飾りであって、意味を1つも足していない
- 廃語を使用しない。一度破棄した語の一覧はこのSkillの外にある ── いつ何を破棄したかはプロジェクトごとに相違するので、ここへ書くと書いたプロジェクトでしか使えない検査になる。既定では .doc-writing/retired-words.json を、対象のファイルから上へたどって探す。無ければこの検査は走らない（失敗にしない）
- 和語へ言い換えない。名前も、述部もである。原典が和語を勧めるのは広報・解説であって、事務的・専門的な文書ではない。名前を和語にすると必ず新語になり（メタデータ→「頭」、出典→「指す先」）、述部を和語にすると意味の範囲が広がる（適用される ・ 有効である ・ 作用する が、1語にまとまってしまう）。判定は2つ ── その語を検索して同じ意味が出てくるか。意味を特定できる漢語が在るか

言い換え先は、references/predicates.json が定義する。
ゲート1の「述部が和語である」はその定義で検出し、検出した1件ごとに言い換え先を出力する。
この文書は定義を複製しない ── 複製は本体とずれ、どちらが正しいかを毎回確認することになる。
- 指し先の無い名詞句を書かない。「ずれ」「外を指す名前」のように、それが何を指すかを文書の中に書いていない語を使わない。見出しに置く語は、見出しだけで指し先が分かる形にする（「ずれた34件」ではなく「仕様と実装のずれ34件」）
- 散文で書けることを、散文で書かない。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- 桁を空白で整列させて、表に見せない。表はマークダウンの表で書く
- ASCII で図を描かない。図は mermaid か SVG で書く
- 同じ文脈で、同じ意味に2つの語を対応づけない。文脈が変わるなら、変わることを書く
- 訂正の記録を本文に残さない。文書には現行の正しい内容だけを書く。履歴は git が持つ
- 数値は原典の文字列で確認してから書く。要約を経由して引かない
- 確認していない内容を、確認したように書かない。推測は推測と分かる形で書く
- 原典から導けない決めを、原典の記述として書かない。こちらの決めだと書く
- ゲートを実行していないものを、出さない。実行していないなら、そう書く
