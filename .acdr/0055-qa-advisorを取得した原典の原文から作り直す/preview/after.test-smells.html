Obscure Test（Meszaros、2006年12月20日更新）

補足

分類: コードの臭い

別名: Long Test ・ Complex Test ・ Verbose Test

書籍版: p.186

定義

Obscure Test

It is difficult to understand the test at a glance.

補足

自動テストには少なくとも2つの目的がある

SUT がどう振る舞うべきかの文書になる（Tests as Documentation）

自己検証する実行可能な仕様になる

補足

この2つはしばしば相反する。実行可能にするのに必要な詳細さが、テストを理解しにくいほど冗長にする

補足

Symptoms（兆候）

テストがどの振る舞いを検証しているのか理解しにくい

補足

Impact（影響）

1つ目: テストを理解しにくくなり、したがって保守しにくくなる。Tests as Documentation をほぼ確実に妨げ、High Test Maintenance Cost につながりうる

補足

2つ目: Obscure Test に隠れたテストのコーディング誤りのために、バグをすり抜けさせうる → Buggy Tests

さらに、Eager Test の1つのアサーションの失敗が、実行されない多くの誤りを隠し、テストのデバッグ情報を失わせる

補足

Causes（原因）

逆説的に、Test Method の中の情報が多すぎても少なすぎても起きる

少なすぎる例: Mystery Guest

多すぎる例: Eager Test ・ Irrelevant Information

補足

根本原因: テストコードを清潔で単純に保つことへの注意の不足。テストコードも本番コードと同じく重要で、同じ頻度でリファクタリングが必要になる

大きな要因は「とりあえずインラインで書く」という姿勢。インラインで書くと Test Method が大きく複雑になる

定義

原因: Eager Test

Eager Test

The test is verifying too much functionality in a single Test Method.

補足

Symptoms: テストが延々と「あれもこれも何もかも」検証する。どこがフィクスチャの準備で、どこが SUT の実行なのか識別しにくい

例（testFlightMileage_asKm2）: コンストラクタの実行と検証 → 距離の設定 → km への換算の実行と検証 → 欠航にして例外を検証、を1つのメソッドで行う

補足

Root Cause: 手動でテストするときは、準備の手間を減らすために論理的に別のテスト条件を1つのテストケースにつなげるのが理にかなう。人（liveware）が実行し、続けるか中止するかをその場で判断できるから

規則
  • Possible Solution: 自動化したテストでは、独立した Single Condition Tests の集まりにするほうがよい。はるかに良い Defect Localization を与える
定義

原因: Mystery Guest

Mystery Guest

The test reader is not able to see the cause and effect between fixture and verification logic because part of it is done outside the Test Method.

補足

Symptoms

Four-Phase Test の fixture setup と exercise SUT の段で使うデータが SUT の事前条件を決め、verify outcome の段で Assertion Method に渡すデータが事後条件（期待結果）を表す

準備または検証がテストの中に見えない情報に依存し、読み手が外部の情報を探して調べないと振る舞いを理解できないとき、Mystery Guest である

例: loadAirportsAndFlightsFromFile("test-flights.csv") で読み込み、"YYC" 発の便が1件で出発都市が "Calgary" であることを検証する。フィクスチャの中身が見えず、期待結果と事前条件を結び付けられない

補足

Impact

フィクスチャ（事前条件）と期待結果の因果関係が見えにくい。Tests as Documentation の役を果たさない

さらに、外部のリソースを、テストへの影響に気づかずに誰かが変更 ・ 削除しうる。この振る舞いの臭いには Resource Optimism（Erratic Test）という名前がある

Mystery Guest が Shared Fixture の場合、他のテストがそれを変更すると Erratic Test につながりうる

補足

Root Cause: テストが謎の外部リソースに依存する。形はさまざま

既存の外部ファイルの名前を SUT のメソッドに渡し、その中身が SUT の振る舞いを決める

リテラルのキーで特定したデータベースのレコードの中身を読み込み、テストで使う、または SUT に渡す

ファイルの中身を読み、Assertion Method の呼び出しで期待結果の検証に使う

Setup Decorator で Shared Fixture を作り、検証ロジックの中で変数を介してフィクスチャのオブジェクトを参照する

Implicit Setup で General Fixture を作り、Test Method がインスタンス変数やクラス変数でそれにアクセスする

共通の結果: 関係するデータがテストの中に見えない。データの中身が、それを持つ変数 ・ ファイルに付けた名前で明確に表されていなければ Mystery Guest である

規則

Possible Solution

明白な解決は、Inline Setup で構築する Fresh Fixture

  • ファイルの例では、ファイルの中身をテストの中で文字列として作って見えるようにし、ファイルシステムへ書き出す（Setup External Resource リファクタリング）か、ファイルシステムの Test Stub に入れる（Inline Resource リファクタリング）
  • Irrelevant Information を避けるため、構築の詳細を、内容を想起させる名前の Creation Method に隠してよい
規則
  • Shared Fixture や Implicit Setup を使わざるを得ないなら、内容を想起させる名前の Finder Method でフィクスチャのオブジェクトにアクセスする
  • ファイルなどの外部リソースを使わざるを得ないなら、専用のフォルダに置き、どんなデータを持つかが明らかな名前を付ける
定義

原因: General Fixture

General Fixture

The test is building or referencing a larger fixture than is needed to verify the functionality in question.

補足

Symptoms

どのテストにも必要と思われる以上の大量のフィクスチャが構築されているように見える。フィクスチャ ・ 実行する SUT の部分 ・ 期待結果の「因果関係」が理解しにくい

例: 出発便1件のテストと2件のテストが、実行と検証の部分からは全く違うフィクスチャを必要としそうなのに、どちらも setupStandardAirportsAndFlights を呼ぶ。メソッド名が手がかりになる典型的で識別しやすい例

より診断しにくいのは、各テストが Standard Fixture をインラインで作る場合や、それぞれ少しずつ違うが各テストに必要な分より多くを含むフィクスチャを作る場合

Slow Tests や Fragile Fixture が同時に起きていることもある

補足

Root Cause: 多くのテストを支えるよう設計したフィクスチャを使うこと。例: フィクスチャの要件が違う多くのテストで Implicit Setup や Shared Fixture を使う。フィクスチャが大きく理解しにくくなり、時とともに大きくなりうる。根本は、使うすべてのテストの要件を満たさねばならない Standard Fixture を使うこと。テストの要件が多様なほど General Fixture になりやすい

Impact: 各テストがフィクスチャをどう使うか理解しにくい。Tests as Documentation の可能性を下げ、新しいテストのためにフィクスチャを変えるにつれ Fragile Fixture を生みうる。Slow Tests も生みうる

規則

Possible Solution

  • Minimal Fixture へ移る。最善は各テストで Fresh Fixture を使うこと
  • Shared Fixture を使わざるを得ないなら、Make Resource Unique リファクタリングで各テスト用の仮想的な Database Sandbox を作ることを考える
  • 注意: Immutable Shared Fixture に切り替えても核心は解決しない。各テストがフィクスチャのどの部分を必要とするかは分からず、変更する部分しか特定されないため
定義

原因: Irrelevant Information

Irrelevant Information

The test is exposing a lot of irrelevant details about the fixture that distract the test reader from what really affects the behavior of the SUT.

補足

Symptoms

読み手として、オブジェクトに渡した値のどれが期待結果に実際に影響するのか判断しにくい

例: 請求先 ・ 配送先の住所、顧客の番号 ・ 氏名、商品番号 ・ 商品名などをすべて指定して請求書を作り、数量5を追加して明細を検証する

補足

多くの関連オブジェクトを編み合わせるフィクスチャの準備が長く複雑に見え、読み手が事前条件を理解できないため、何を検証しているか分からない（例: 期待する便の DTO を項目ごとに組み立てる）

期待結果を検証するコードも複雑すぎて理解できないことがある（例: 明細の件数を検証し、1件目と2件目を項目ごとに assertEquals する）

補足

Root Cause

テストが Literal Value や変数として多くのデータを持つ。Hard-Coded Test Data や General Fixture と一緒に起きることが多いが、テストを理解するのに必要なデータでなく、実行に必要なすべてのデータを見せることでも起きる

テストを書くとき、最も抵抗の少ない道は、手元のメソッドを使い、関係の有無にかかわらず全引数を充填すること

もう1つの原因: はるかに簡潔な「宣言的」な指定でなく、Procedural State Verification で検証のコードをすべて書くこと

補足

Impact: 事前条件と事後条件を明確に結ばない無作為に見える断片が多いと、Tests as Documentation を実現しにくい。多くの準備 ・ 検証の手順をかき分けることは High Test Maintenance Cost を生み、Production Bugs や Buggy Tests の確率を上げうる

規則

Possible Solution

  • 準備ロジックでは、コンストラクタや Factory Method の直接の呼び出しを、関係する情報だけを引数に取る Parameterized Creation Method の呼び出しに置き換える
  • 期待結果に影響しない値は、Creation Method の中で既定値にするか Dummy Object に置き換える。こうして読み手に「見えない値は期待結果に影響しない」と伝える
  • 準備と検証の両方に現れる値は、Fresh Fixture を使っている限り、適切に初期化した名前付き定数に置き換えてよい
  • 検証ロジックでは、個々のフィールドでなく Expected Object 全体に対してアサートし、複雑な手続き的検証を隠す Custom Assertion を作る
定義

原因: Hard-Coded Test Data

Hard-Coded Test Data

Data values in the fixture, assertions or arguments of the SUT are hard-coded in the Test Method obscuring cause-effect relationships between inputs and expected outputs.

補足

Symptoms

読み手として、テスト中のハードコードされた（リテラルの）値どうしがどう関係し、どれが SUT の振る舞いに影響すべきか判断しにくい。Erratic Test のような振る舞いの臭いが見えていることもある

例: 割引30の顧客 ・ 単価19.99の商品で数量5を追加し、合計69.96を期待する。リテラルは少ないが、暗算が得意でなければ単価 ・ 数量 ・ 割引 ・ 合計の関係を看過しうる

補足

Root Cause

テストが、互いに無関係に見える多くの Literal Value を持つときに起きる。（Mystery Guest と同じく、準備と実行の段のデータが事前条件を決め、検証の段のデータが事後条件を表す）

最も抵抗の少ない道は、関係の有無にかかわらず全引数を値で充填すること

テストのロジックを「コピー＆ペースト」で再利用すると、すべてのリテラル値が派生したテストへ複製される

補足

Impact

事前条件と事後条件を明確に結ばない断片が多いと Tests as Documentation を実現しにくい。リテラルが少なければ理解の手間はさほど増えないが、数が増えるとはるかに理解しにくくなる。大半の値がテストに無関係で信号対雑音比が低いときは特にそう

2つ目の影響: テストが同じ値を使うことによるテスト間の衝突。これは Shared Fixture を使うときにだけ起きる。Fresh Fixture は後続のテストが衝突するオブジェクトを残さないはずだから

規則

Possible Solution

  • リテラルの定数を別のものに置き換える。どのシナリオを実行するかを決める値（型コードなど）はリテラルのまま残してよい唯一のものだろうが、それも名前付き定数にできる
  • 期待結果に影響しない値は Creation Method の中で既定値にする（「見えない値は期待結果に影響しない」と伝える）。準備と検証の両方に現れる値は、Fresh Fixture の限り名前付き定数にする
  • 準備の値や SUT の引数に基づく検証側の値は Derived Value に置き換え、計算を読み手に明らかにする
  • Shared Fixture のどの変種を使う場合も、Distinct Generated Value で実行ごとに違う値を使う。データベースの一意キーに使うフィールドでは特に重要。この処理は Anonymous Creation Method で包むのが一般的
定義

原因: Indirect Testing

Indirect Testing

The Test Method is interacting with the SUT indirectly via another object thereby making the interactions more complex.

補足

Symptoms: テストが、振る舞いを検証すると称するオブジェクト以外と主にやり取りする。SUT そのものでなく、SUT への参照を持つオブジェクトを構築してやり取りする。プレゼンテーション層を経由してビジネスロジックをテストするのが典型例

例: 乗り継ぎ時間が規定未満の接続を作り、getFlightConnectionAsHtmlFragment の返す HTML 文字列を、期待する HTML を組み立てて比較する

補足

Impact

中間のオブジェクトを経由しては SUT の「壊れうるものすべて」をテストできないことがあり、テストは明確でも理解しやすくもなりにくい。Tests as Documentation にならない

中間のオブジェクトの変更でテストの修正が必要になり、Fragile Tests を生みうる

補足

Root Cause

SUT が、テストからアクセスに使うクラスに対して「private」であることがある。コンストラクタが private で SUT を直接作れないこともある。これはソフトウェアがテスト容易性を考えて設計されていない兆候の1つ

SUT を実行した実際の結果を直接観察できず、中間のオブジェクトを経由して期待結果を検証せざるを得ないこともある

規則

Possible Solution

SUT のテスト容易性の設計を改善する必要があるかもしれない。Extract Component リファクタリング（Extract Class の変種）で SUT をテストに直接さらせるかもしれない。その結果、テストできない Humble Object と、ロジックのほとんど ・ すべてを持つテストしやすいオブジェクトに分かれうる

  • 例: facade を Mock で差し替え、FlightConnAnalyzer の getConn の結果に対して isLegal() を検証する（ビジネス層のテスト）
規則

コードをリファクタリングできず間接的にやり取りせざるを得ない場合は、Indirect Testing が強いる複雑なロジックを、適切な名前の Test Utility Method の後ろに包む。準備は Creation Method、検証は Verification Method に隠す。どちらも SUT API Encapsulation の例

  • 例: 検証を assertConnectionIsIllegal(illegalConn, actualHtml) にまとめる
  • この Custom Assertion は Extract Method で作ったが、期待する文字列全体を組み立てて一度に比べるより、HTML の中でキーになる文字列を探すほうが頑健になる。HTML の整形を検証する Presentation Layer Test も別にあるだろう
規則

Solution Patterns（解決のパターン）

  • 良いテスト戦略はテストコードを理解しやすく保つ助けになるが、「最初の接敵を生き延びる作戦はない」のと同様、どのテスト基盤もすべてのテストの必要を予見できない。ソフトウェアが成熟し自動化の技能が向上するにつれ、テスト基盤を進化させることを見込む
  • 複数のシナリオでのテストロジックの再利用は、複数のテストから Test Utility Method または共通の Parameterized Test を呼び、構築済みのフィクスチャ ・ Expected Object を渡して行う
規則

「outside-in」で書くと、後でリファクタリングが必要な Obscure Test を作らずに済む

  • まだ存在しない Test Utility Method の呼び出しで Four-Phase Test の雛形を書く → テストに満足したら、実行に必要なユーティリティメソッドを書く
  • 先にテストを書くことで、テストをできるだけ単純にするためにユーティリティメソッドが何をすべきかがよく分かる
  • 「test-infected」な人は、Utility Method を書く前に Test Utility Test を書く

Conditional Test Logic（Meszaros、2006年10月31日更新）

補足

分類: コードの臭い

別名: Indented Test Code

書籍版: p.200

定義

Conditional Test Logic

A test contains code that may or may not be executed

補足

Fully Automated Test は、他のコードの振る舞いを検証するコードにすぎない。このコードが複雑なら、それが正しく動くことをどう検証するのか。テストのテストを書けるが、その再帰はいつ止まるのか。簡単な答えは、Test Method はテストが必要としないほど単純でなければならない

Conditional Test Logic は、テストを本来より複雑にする要因の1つ

補足

Symptoms（兆候）

コードの臭いなので振る舞いの兆候は必要としないが、読み手には十分明らかなはず

Test Method の中の制御構造はすべて、きわめて疑ってかかるべき

補足

読み手は、どのコードパスが実行されているのか疑問に思うこともある

例（ループと if を含む）: 便の一覧をイテレータで反復し、便番号が一致したら assertEquals して break する

補足

このコードは「このテストコードは何をしていて、それを正しく行っているとどう分かるのか」という問いを招く

やや振る舞い寄りの兆候として、関連するプロジェクトの臭い High Test Maintenance Cost がある（Conditional Test Logic がもたらす複雑さが原因になりうる）

補足

Impact（影響）

テストが、本当に重要なときに何をするのか正確に知りにくい

実行パスが1つだけのコードは常に同じように実行される。複数の実行パスを持つコードは、はるかに確信しにくい

補足

本番コードへの確信を高めるため Self-Checking Test を書く。では、実行するたびに違う動きをするテストコードへの確信はどう高めるのか。テストが検証したい振る舞いを検証していると知る（証明する）のは難しい

分岐やループを持つテスト、実行ごとに違う値を使うテストは、完全に決定的でないためデバッグがとても難しい

関連する問題として、テストを正しく書くのも難しくなる。テストは容易にテストできないので、捕まえるはずのバグを実際に検出するとどう分かるのか（これは Obscure Test 一般の問題で、単純なコードより Buggy Tests になりやすい）

原因: Flexible Test

Flexible Test

Test code verifies different functionality depending on when or where it is run.

補足

Symptoms: 現在の環境によって違うことをする条件ロジックを持つ。最もよくあるのは、テストの外の要因に基づいて期待結果の別の版を作る形

例（testDisplayCurrentTime_whenever）: 現在時刻を取得し、0時0〜1分なら "Midnight"、12時0分なら "Noon"、それ以外は "h:mm a" 形式、と期待値を分岐して組み立てる

補足

Root Cause: 環境を制御できないこと。自動化担当者は SUT を依存から切り離せず、環境の状態に応じてテストロジックを適応させることにしたのだろう

補足

Impact

1つ目: テストを理解しにくく、したがって保守しにくくする

2つ目: どのシナリオが実際に実行されているのか、すべてのシナリオが定期的に実行されているのか分からない。例では、真夜中のシナリオはほぼ実行されない（ちょうど真夜中に実行する必要があり、夜間ビルドを真夜中にまたがらせても起こりにくい）

規則
  • Possible Solution: テストを柔軟にさせた依存から SUT を切り離す。SUT をリファクタリングして substitutable dependency を支え、依存を Test Double（Test Stub や Mock Object）に置き換え、Flexible Test が扱っていた状況ごとに別のテストを書く
補足

原因: Conditional Verification Logic

期待結果の検証に Conditional Test Logic を使うこと。SUT が正しいオブジェクトを返さないときにアサーションの実行を防ぎたい場合や、SUT が返すコレクションの中身をループで検証する場合に起きる

  • fail の呼び出しへ実行を向ける if は、実行させたくないコードに至る前にテストを失敗させる Guard Assertion に置き換える。ただし Expected Exception Test の場合は、その xUnit と言語の標準のコーディングイディオムを使う
  • 複雑なオブジェクトの検証のための条件ロジックは、Expected Object に対する Equality Assertion に置き換える。本番コードの equals が厳しすぎるなら、Custom Assertion でテスト固有の等価性を定義する
  • 検証ロジックのループは、Custom Assertion Test で振る舞いを検証できる Custom Assertion へ移す
  • 複数のテストでテストロジックを再利用するには、Test Utility Method または共通の Parameterized Test を呼び、構築済みのフィクスチャ ・ Expected Object を渡す
補足

原因: Production Logic in Test

Symptoms: 条件ロジックのいくつかの形は、検証の部分に現れる

補足

Root Cause: 1つの Test Method で複数のテスト条件を検証したいことの直接の結果。入力が複数あれば期待結果も複数必要になる。多くの組み合わせを入れ子のループで渡すと入力ごとの期待結果を列挙しにくく、よくある解決は入力に基づく Calculated Value（Derived Value）を使うこと。問題になるのは、SUT が持つはずのロジックをテストの中に複製して期待値を計算してしまうこと

規則

Possible Solution: 可能なら、あらかじめ計算した値の組を列挙してテストするほうがよい

  • 例（testMultipleValueSets）: (1,2,3) ・ (2,3,5) ・ (3,4,8)（特殊ケース） ・ (4,5,9) の値の組の配列を反復して検証する
補足

原因: Complex Teardown

Symptoms: 複雑なフィクスチャの後始末のコードは、正しく片付けずにテスト環境を壊したままにしやすい。正しく書けているか検証しにくく、後でこのテストや他のテストを理由なく失敗させる「データ漏れ」を起こしやすい

例: 空港2つと便1つを作り、finally の中に try/finally を入れ子にして便 ・ 空港を順に削除する

補足

Root Cause: 後始末は通常、ガベージコレクションの届かない永続リソースを使うときだけ必要になる。1つの Test Method で多くのそうしたリソースを使うと Complex Teardown になる

規則

Possible Solution

  • 複雑な後始末ロジックは、再利用 ・ テストできるようにする Implicit Teardown、または自動化した単体テストで検証できる Automated Teardown で避ける
  • Fresh Fixture 戦略を使う、テストで永続オブジェクトを避ける（何らかの Test Double に置き換える）ことで、後始末の必要自体をなくせる
補足

原因: Multiple Test Conditions

Symptoms: 同じテストロジックを、それぞれ期待結果を持つ多くの入力値の組に適用しようとする

例: 上の testMultipleValueSets（値の組のコレクションを反復して各組にテストロジックを適用する）

補足

Root Cause: 1つの Test Method で、同じテストロジックを使って多くのテスト条件をテストしようとする。この例はかなり単純な条件ロジックだが、入れ子のループや、期待値の場合分けを計算する if があると、はるかに悪くなる

規則

Possible Solution

  • Conditional Test Logic の原因のうち、Multiple Test Conditions はおそらく最も害が少ない。読み手を怖がらせる以外の主な影響は、最初の失敗で実行が停止し、バグを入れたときに Defect Localization を与えないこと
  • 読みやすさ: Extract Method でループの中から呼ぶ Parameterized Test を作る
  • Defect Localization の欠如: テスト条件ごとに別の Test Method から Parameterized Test を呼ぶ
  • 値の組が大きいときは Data-Driven Test のほうがよい解決かもしれない

Hard-to-Test Code（Meszaros、2007年6月11日更新）

補足

分類: コードの臭い

書籍版: p.209

定義

Hard-to-Test Code

Code is difficult to test.

補足

自動テストは、大きなコードベースを保守するようになっても速く開発する助けになるが、その利点はコードの大半に Fully Automated Test があるときだけ得られる

補足

テストを書く手間は、検証する製品コードを書く手間に上乗せされる。だから自動テストを書くのを容易にしたい

（この費用は別のところで手間を減らして取り戻したい。最善の方法は、テストを先に書いて Defect Localization を実現し、Frequent Debugging を避けること）

補足

Hard-to-Test Code は、完全で正しい自動テストを費用効率よく書くのを難しくする要因の1つ

補足

Symptoms（兆候）

テストしにくい種類のコードがある。すぐ思い浮かぶのは GUI コンポーネント ・ マルチスレッドのコード ・ テストコード

テストから見えないため、テスト対象のコードに届きにくいことがある

他のクラスと強く結合しているため、テストをコンパイルしにくいことがある

コンストラクタが存在しない ・ private である ・ 他のオブジェクトを引数に多く取るため、オブジェクトのインスタンスを作りにくいことがある

補足

Impact（影響）

Hard-to-Test Code があるときは常に、品質を自動で容易に検証できないコードがある

手動の品質評価はたいてい可能だが、規模を広げにくい。コードを変えるたびに行う手間のため、たいてい行われない

大きなテスト文書の費用なしには、繰り返し可能でもない

規則

Solution Patterns（解決のパターン）

  • よりよい解決は、コードをテストになじみやすくすること。これは1章を要する大きな話題なので、ここでは要点をいくつか扱う
補足

Causes（原因）

Hard-to-Test Code の理由は多いが、最もよくある原因は次のとおり。

補足

原因: Highly Coupled Code

別名: Hard-Coded Dependency

Symptoms: クラスを、他のいくつかのクラスも一緒にテストせずにはテストできない

Impact: 他のコードと強く結合したコードは、分離して実行できないため、単体テストがとても難しい

Root Cause: 貧弱な設計 ・ オブジェクト指向設計の経験不足 ・ 結合を減らすことを促す報酬の仕組みの欠如、など多くの要因

規則

Possible Solution

  • 鍵は結合を断つこと。テスト駆動開発では自然にそうなる
  • テストのために結合を断つ技法としてよく使うのは Test Double、特に Test Stub や Mock Object（詳しくは「Using Test Doubles」の章）
  • 既存のコード、特にレガシーコードに後からテストを付けるときはより難しい。Michael Feathers がそのための技法の本『Working Effectively with Legacy Code』を書いた
補足

原因: Asynchronous Code

Symptoms: クラスを直接のメソッド呼び出しでテストできない。テストが実行体（スレッド ・ プロセス ・ アプリケーション）を起動し、起動し終わるまで待ってからやり取りしなければならない

Impact: テストの実行を SUT の実行と調整する必要があり、テストがかなり複雑になり、実行時間もはるかに長くなる。後者は、開発者が頻繁に実行するようきわめて速く走らなければならない単体テストにとって大きな問題

Root Cause: 結合の特定の形。テストしたいアルゴリズムを実装するコードが、通常それを実行する能動オブジェクトと強く結合している

規則
  • Possible Solution: 鍵はロジックを非同期のアクセス機構から分離すること。設計のためのテスト容易性パターン Humble Object（Humble Dialog ・ Humble Executable を含む）は、非同期のコードを同期的にテストできるよう組み直すよい例
補足

原因: Untestable Test Code

Symptoms: Test Method の本体が十分に分かりにくい（Obscure Test）か、Conditional Test Logic を十分に含んでいて、テストが正しいのか疑問に思う

Impact: Test Method の中の Conditional Test Logic は Buggy Tests になる確率が高く、High Test Maintenance Cost を生みやすい。本体のコードが多すぎると、テストが理解しにくく、正しく書きにくい

Root Cause: Test Method の本体のコードは、本質的に Self-Checking Test でテストしにくい。テストしたい誤りを注入する Test Double で SUT を置き換え、そのテストメソッドを別の Expected Exception Test の中で実行する必要があり、ごく特殊な状況以外では手間がかかりすぎる

規則
  • Possible Solution: Test Method の本体をきわめて単純にし、Conditional Test Logic を、Self-Checking Test を容易に書ける Test Utility Method へ移すことで、本体をテストする必要をなくす

Test Code Duplication（Meszaros、2007年2月18日更新）

補足

分類: コードの臭い

書籍版: p.213

定義

Test Code Duplication

The same test code is repeated many times.

補足

スイートの多くのテストは似たことをする必要がある。テストはしばしば1つの主題の変奏であるシナリオを実行する。似たフィクスチャの準備や検証のロジックを要することがある。SUT の実行の段さえ自明でないロジックを含む場合がある

テストが似たことをする必要が、しばしば Test Code Duplication を生む

補足

Symptoms（兆候）

複数のテストにまたがる重複: いくつかのテストが、本質的に同じ文の共通部分を含む

例: testInvoice_addOneLineItem_quantity1_b と testRemoveLineItemsForProduct_oneOfTwo が、明細の件数の確認と、明細1件の請求書 ・ 商品 ・ 数量の assertEquals を同じ形で持つ

補足

1つのテストの中の重複: 似た文のまとまりが繰り返される

例: testInvoice_addTwoLineItems_sameProduct が、1件目と2件目の明細に対して同じ3つの assertEquals を繰り返す

補足

上の2例は気づきやすい。別の Testcase Class にある Test Method にまたがる重複は気づきにくい

補足

Impact（影響）

「カット＆ペースト」はしばしば同じコードの多くの複製を生む

このコードは、SUT のメソッドの意味（引数の数 ・ 引数の属性 ・ 返すオブジェクトの属性 ・ 呼び出しの順序）に影響する変更のたびに保守しなければならない

影響を受けるコードの複製を持つすべてのテストを更新する手間のため、新しい機能を入れる費用が大きく増えうる（High Test Maintenance Cost）

補足

原因: Cut-and-Paste Code Reuse

「カット＆ペースト」はコードを速く書く強力な道具だが、並行して保守しなければならない同じコードの複製を多く生む

補足

Root Cause

ロジックを再利用する既定の方法になりがち。「どう」行うかの詳細に集中する開発者は、テストの全体像（意図）に集中できない（または時間をかけない）ため、同じコードを何度も繰り返す

寄与する要因: リファクタリングの技能や経験の不足で、書いた詳細なコードから全体像を抜き出せない。単に時間の圧力でリファクタリングが起きないこともある。結果として、テストコードは時とともに単純になるどころか複雑になる

規則

Possible Solution

重複が起きたら、最善は Extract Method で例の1つから Test Utility Method を作り、各複製を扱えるよう一般化すること

  • 準備のロジックなら Creation Method や Finder Method になる
  • 検証のロジックなら Custom Assertion や Verification Method になる
規則
  • Introduce Parameter で、抽出したメソッドの中のリテラル定数を引数にし、呼ぶテストごとに振る舞いを変えられるようにする
  • Test Method を意図に集中して「outside in」で書けば、重複を大いに避けられる。数行を要することをするときは、まだ存在しない Test Utility Method を呼ぶ。テストをすべてそう書いてから、コンパイル ・ 実行できるよう Test Utility Method の実装を記述する（最近の IDE はメソッドの雛形の自動生成でこれを容易にした）
補足

原因: Reinventing the Wheel

Cut and Paste Code Reuse がテストを書く手間を減らすため意図的に複製を作るのに対し、これは誤って同じ文の並びを別のテストに書くこと

Root Cause: 主に、どんな Test Utility Method があるかを認知していないこと。他人の書いたコードを再利用するより自分で書こうとする傾向によることもある

規則
  • Possible Solution: 技術的な解決は Cut and Paste Code Reuse とほぼ同じだが、進め方の解決が少し違う。自動化担当者は、車輪を再発明する（新しいコードを書く）前に、どんな Test Utility Method があるかを十分に調査する必要がある
補足

Test Logic in Production（Meszaros、2007年2月18日更新）

補足

分類: コードの臭い

書籍版: p.217

定義

Test Logic in Production

The code that is put into production contains logic that should be exercised only during tests.

補足

SUT が、テスト環境で実行できないロジックを含むことがある。テストが、完全なカバレッジのために SUT に特定の振る舞いを求めることもある

補足

Symptoms（兆候）

SUT の中に、テストを支えるためだけにあるロジックがある

準備や検証のために、テストがアプリケーションの内部状態にアクセスするための「余分なもの」であることがある

テストされていることを検知したときに、システムのロジックを変えるものであることもある

補足

Impact（影響）

SUT をより複雑にし、なくて済むはずの種類のバグへの扉を開く

テストの場と本番で全く違う振る舞いをするシステムは、災難のもと

補足

原因: Test Hook

SUT の中の条件ロジックが、「本物」のコードとテスト固有のロジックのどちらを実行するかを決める

Symptoms: コードの臭いなので振る舞いの兆候が全く無いこともあれば、本番で何かがおかしくなることもある。SUT の中に if (testing) { return hardCodedCannedData; } else { ... return gatheredData; } のような断片が見える

補足

Impact

本番で動くよう設計されておらず、本番環境で正しく動くと検証されていないコードが、誤って本番で実行され、深刻な問題を起こしうる

例: Ariane 5 ロケットの初飛行は離陸37秒後に爆発した。地上でだけ使うコードが飛行の最初の40秒間動き続け、横方向の速度を表す64ビットの数を16ビットのフィールドに代入しようとし、航法コンピュータに誤った方向へ進んでいると判断させた

テストコードが本番で実行されることは決してないと信じていても、こうした賭けを本当にしたいか

補足

Root Cause

既知の（ハードコードした）値を返して SUT の振る舞いをより決定的にするために持ち込まれることがある

テスト環境で実行できないコードの実行を避けるために持ち込まれることもある。残念ながら、何かの設定を誤ると、本番環境でもそのコードを実行しないことになりうる

テストが、本来は依存先のコンポーネントが実行するコードを SUT に実行させることを要する場合もある。例: データベースを Fake Database に置き換えるとデータベースのトリガーから実行されるコードが実行されないので、同等のロジックを SUT のどこかから実行させる必要がある

規則

Possible Solution

本番コードに直接テストロジックを加える代わりに、ロジックを substitutable dependency へ移す

  • 本番でだけ実行すべきコードは、既定で組み込まれ、テストでは Null Object に置き換える Strategy オブジェクトに入れる
  • テスト中にだけ実行すべきコードは、既定では Null Object として構成する Strategy オブジェクトに入れ、テスト中に余分なコードを実行させたいときにテスト固有の版に置き換える
  • Strategy への参照を持つ変数が、テストで上書きされないときに正しく初期化されることを検証する Constructor Test を用意する
規則
  • 回避したい本番ロジックが上書き可能なメソッドにうまく局所化されていれば、Test-Specific Subclass で SUT の特定のメソッドを上書きできることもある。これは Self-Calls によって可能になる
補足

原因: For Tests Only

SUT の中に、厳密にテストのためだけのコードがある

Symptoms: SUT のメソッドのいくつかがテストからしか使われない。本来 private であるべき属性が public になっている

Impact: SUT をより複雑にする。テスト以外のコードが使うことを意図しないメソッドを加え、ソフトウェアのインターフェースの利用者を混乱させうる。このコードはごく特定の状況でしかテストされておらず、実際の利用者の典型的な使い方では動かないかもしれない

補足

Root Cause

自動化担当者が、テストに必要な情報を公開するため、または初期化をより制御するため（Test Double の組み込みなど）にメソッドを加えることがある。テスト駆動開発では、利用者が本当は必要としないのにこうしたメソッドが作られる

レガシーコードに後からテストを付けるとき、公開されていない情報や機能へのアクセスが必要になることがある

実際には非対称に使われる SUT によっても起きる。自動テスト（特に往復テスト）はより対称的にソフトウェアを使うので、実際の利用者が必要としないメソッドを必要としうる

規則

Possible Solution

  • 必要な属性や初期化ロジックを公開するメソッドを持つ SUT の Test-Specific Subclass を作り、テストに private な情報へのアクセスを与える。そのためには、テストが SUT のクラスでなくサブクラスのインスタンスを作れる必要がある
  • 何かの理由で余分なメソッドを Test-Specific Subclass へ移せないなら、For Tests Only と明示する。名前を "FTO_" で始めるなどの命名規約を採る
補足

原因: Test Dependency in Production

本番の実行体がテストの実行体に依存する

Symptoms: 本番コードだけをビルドできない。本番コードをコンパイルするためにテストコードをビルドに含める必要がある。またはテストの実行体が無いと本番コードを実行できない

Impact: 本番のモジュールにテストコードが無くても、本番のモジュールがテストのモジュールに依存すれば問題が起きうる。少なくとも、テストコードを本番で全く使わなくても実行体が大きくなる。本番中にテストコードが誤って実行される扉も開く

Root Cause: 通常、モジュール間の依存への注意の不足。組み込みの自己テストが、結果を報告するために Test Utility Method や Test Automation Framework などのテスト自動化の基盤へのアクセスを要することによる場合もある

規則

Possible Solution

  • 型の定義のような無害なものであっても、本番コードがテストコードに依存しないよう、依存を注意深く管理する
  • テストと本番の両方が必要なものは、両方からアクセスできる本番のモジュールやクラスに置く
補足

原因: Equality Pollution

SUT の equals メソッドに、テスト固有の等価性を実装すること

Symptoms: 起きてしまうと見つけにくい。注目すべきは、SUT が実は equals の実装を必要としていないこと。振る舞いの兆候が出る場合もある。テスト固有の必要に合わせて equals を変えたときや、新しい機能 ・ ユーザーストーリーの一部として SUT の中で equals の定義を変えたときに、テストが失敗し始める

補足

Impact

テストを満たすためだけに不要な equals を書くことになりうる。または、業務上の要件を満たさなくなるよう equals の定義を変えてしまいうる

別のテストのためのテスト固有の等価性として equals がすでにあると、新しい要件が定める equals のロジックを入れにくくなりうる

補足

Root Cause: テスト固有の等価性という概念を認知していないこと。動的な Mock Object 生成ツールの初期の版には、SUT の equals の定義を使わせるものがあり、Equality Pollution を招いた

規則

Possible Solution

  • テストがテスト固有の等価性を要するときは、組み込みの Equality Assertion を使えるよう equals を変えるのでなく、Custom Assertion を使う
  • 動的な Mock Object 生成ツールを使うときは、SUT の equals に頼らず Comparator を使う
  • Expected Object の Test-Specific Subclass に equals を実装し、本番のクラスに直接加えるのを避けることもできる
補足

Further Reading（参考）

For Tests Only と Equality Pollution は XP2001 の論文 "Refactoring Test Code" [RTC] で初めて紹介された

Assertion Roulette（Meszaros、2006年10月31日更新）

補足

分類: 振る舞いの臭い

書籍版: p.224

定義

Assertion Roulette

It is hard to tell which of several assertions within the same test method caused a test failure.

補足

Symptoms（兆候）

テストが失敗する。Test Runner の出力を調べても、どのアサーションが失敗したのか正確に判断できない

補足

Impact（影響）

自動化した Integration Build の中でテストが失敗したとき、どのアサーションが失敗したのか正確に分かりにくい

開発者の手元で問題を再現できない場合（環境の問題や Resource Optimism が原因の場合など）、修正が難しく時間がかかりうる

定義

原因: Eager Test

Eager Test

A single test verifies too much functionality.

補足

Symptoms

テストが SUT のいくつかのメソッドを実行する、または同じメソッドを、フィクスチャの準備とアサーションを挟みながら何度も呼ぶ

例: Obscure Test と同じ testFlightMileage_asKm2

補足

別の兆候: 自動化担当者が、残りのアサーションも実行できるよう、アサーションの失敗後も続行するように Test Automation Framework を改造したがる

補足

Root Cause

単体テストの数を（意識的にせよ無意識にせよ）最小にしようとして、1つの Test Method で多くのテスト条件を検証することによることが多い。これは、「liveware」が結果を解釈しその場でテストを調整する手動のテストではよい実践だが、Fully Automated Test ではうまくいかない

もう1つのよくある原因: 多くの手順を要する顧客テストを xUnit で自動化し、各テストで SUT の多くの側面を検証すること。こうしたテストは単体テストより必然的に長くなるが、できるだけ短く（ただし短すぎず）保つよう注意する

規則

Possible Solution

単体テストでは、Eager Test をほぐして Single Condition Tests の集まりに分ける

  • Extract Method で独立した部分をそれぞれの Test Method へ引き出せることがある
  • テスト条件ごとにテストを複製し、各 Test Method からその条件に不要なコードを除いて整理するほうが容易なこともある
  • フィクスチャの準備や SUT を正しい開始状態にするコードは Creation Method へ抽出できる。良い IDE やコンパイラが、使われなくなった変数を見つける助けになる
規則

顧客テストを xUnit で自動化していて、ワークフローが複雑なフィクスチャの準備を要するため各テストの手順が多いなら、テストの後半のフィクスチャを別の方法で準備することを考える

  • Back Door Setup（Back Door Manipulation）でテストの後半のフィクスチャを前半と独立に作れれば、1つのテストを2つにでき、Defect Localization が向上する
  • テストが一目で読めるほど短くなり、意図を明確に伝える（Communicate Intent）まで、これを必要なだけ繰り返す
補足

原因: Missing Assertion Message

Symptoms: テストが失敗する。Test Runner の出力を調べても、どのアサーションが失敗したのか正確に判断できない

補足

Root Cause

同じ ・ または欠けた Assertion Message で Assertion Method を呼ぶことによる。IDE やエディタと統合されていない Test Runner（Command-Line Test Runner など）でテストを実行するときに最もよく問題になる

例（testInvoice_addLineItem7）: 期待する明細と実際の明細を、請求書 ・ 商品 ・ 数量の3つの Equality Assertion で比べる

Equality Assertion は通常、期待値と実際の値を両方出力するが、期待値どうしが似ていたり出力が分かりにくかったりすると、どれが失敗したのか分かりにくい

経験則: 同じ種類の Assertion Method を2回以上呼ぶときは、少なくとも最小限の Assertion Message を入れる

規則

Possible Solution

  • IDE と統合された Graphical Test Runner で起きたなら、スタックトレースの該当行をクリックして失敗したアサーションを IDE に強調させられるはず。だめなら、デバッガで1ステップずつ実行して失敗する文を特定する
  • Command-Line Test Runner で起きたなら、IDE と統合された Graphical Test Runner で実行して該当のアサーションを特定してみる。それもだめなら、行番号（あれば）を使うか、消去法で絞り込む
  • もちろん、覚悟を決めて、各 Assertion Method の呼び出しに一意の Assertion Message（番号だけでもよい）を付けることもできる
補足

Further Reading（参考）

Assertion Roulette と Eager Test は XP2001 の論文 "Refactoring Test Code" [RTC] で初めて記述された

Erratic Test（Meszaros、2007年2月4日更新）

補足

分類: 振る舞いの臭い

書籍版: p.228

定義

Erratic Test

One or more tests are behaving erratically; sometimes they pass and sometimes they fail.

補足

Symptoms（兆候）

実行したときや実行した人によって結果が違うテストがある

ある開発者が実行すると一貫して同じ結果になるのに、別の人や別の環境で実行すると失敗する場合がある

同じ Test Runner から実行しても違う結果になる場合もある

補足

Impact（影響）

「バーを緑に保つ」ために失敗するテストをスイートから外したくなるが、それは（意図的な）Lost Test（Production Bugs）になる

失敗を承知でスイートに保持すると、既知の失敗が、同じテストが検出した別の問題などを隠蔽しうる

1つのテストが失敗しているだけで他の失敗を看過しうる。緑から赤への変化に気づくほうが、予期した1件ではなく2件が失敗していることに気づくよりはるかに容易なため

規則

Trouble-Shooting Advice（調査の助言）

  • 原因が多いので、調査はかなり難しい
規則

原因を容易に特定できなければ、一定期間、体系的にデータを集める価値がある

  • どこで（どの環境で）通り、どこで失敗したか
  • すべてのテストを実行していたか、一部だけか
  • スイートを続けて何度か実行したとき振る舞いは変わったか
  • 複数の Test Runner から同時に実行したときは
規則
  • データがあれば、観察した兆候を各原因の兆候と突き合わせ、候補を数個に絞りやすい。次に、候補の原因どうしの兆候の違いに焦点を絞ってさらにデータを収集する
  • 原典は、どの原因かを特定する手順をフローチャート（Erratic Test Trouble-Shooting）で示す（画像のため本ノートでは読み取れない）
補足

Causes（原因）

テストが不安定になる理由は多い。根底の原因は通常、テストがいつどのように失敗するかのパターンに注意し、粘り強く調べれば特定できる。よくある原因には名前と具体的な対処の助言を付ける

補足

原因: Interacting Tests

テストが何らかの形で互いに依存する。Interacting Test Suites と Lonely Test は Interacting Tests の特定の変種

補足

Symptoms: 単独では動くテストが、次のとき突然失敗する

別のテストがスイートに追加された（または外された）

スイートの別のテストが失敗した（または通るようになった）

そのテスト（または別のテスト）がソースファイルの中で名前を変えられた ・ 移動された

Test Runner の新しい版が入れられた

補足

Root Cause

通常、Shared Fixture を使うテストで、あるテストが別のテストの結果に何らかの形で依存することによる

2つの観点で記述できる: 相互作用の仕組みと相互作用の理由

補足

仕組み: SUT がデータベースを含むといった明白なものも、より微妙なものもある。テストの寿命より長く生きるものは何でも相互作用を生みうる

static 変数は Interacting Tests を確実に生むので、SUT でも Test Automation Framework でも避けるべき（後者の例はサイドバー There's Always an Exception）

Singleton や Registry は SUT でできるだけ避けるべきものの良い例。使わざるを得ないなら、各テストの開始時に変数を再初期化する仕組みを入れる

補足

理由（設計によるもの、偶然によるもの）

別のテストのフィクスチャ準備の段で構築したフィクスチャに依存する

別のテストの SUT 実行の段で SUT に加えた変更に依存する

同じテスト実行の中の2つのテスト間の、互いに排他的な動作による衝突（上のどちらかでもありうる）

補足

依存先のテストが次のとき、依存が突然満たされなくなりうる

スイートから外された

SUT の状態を変えないよう変更された

SUT の状態を変えるのに失敗した

問題のテストより後に実行された（名前を変えられた、別の Testcase Class へ移された）

補足

衝突は、衝突するテストが次のとき起き始めうる

スイートに追加された

初めて通った

依存するテストより前に実行された

補足

多くの場合、複数のテストが失敗する。一部は正当な理由（SUT がすべきことをしていない）で失敗しているかもしれないが、依存するテストは誤った理由（他のテストの成功に依存するよう書かれている）で失敗し、偽の失敗（原文は「false negative」、false failure）を示しているかもしれない（原文の表記のまま）

一般に、テストの実行順序に依存するのは良くない。ほとんどの xUnit の変種は、スイートの中のテストの実行順序を保証しない（TestNG はテスト間の依存を管理する機能を与え、依存を促す例）

規則

Possible Solution

  • Fresh Fixture が望ましい解決で、ほぼ確実に問題を解決する
  • Shared Fixture を使わざるを得ないなら、Immutable Shared Fixture を考える。テストが変更するつもりのフィクスチャの部分を一から作ることで、フィクスチャの変更を通じた相互作用を防ぐ
  • 満たされない依存が、別のテストが期待するオブジェクトやデータベースのデータを作っていないことによるなら、Lazy Setup で両方のテストでそれを作り、先に実行したほうが両方のために作るようにする。重複を避けるため準備のコードを Creation Method に入れる。テストが別の Testcase Class にあるなら Test Helper へ移す
  • 衝突が、テストで作って片付けていないオブジェクトやデータベースのデータによるなら、Automated Fixture Teardown で安全かつ効率よく取り除く
  • 互いに依存するテストがあるかを手早く調べるには、通常と違う順序でテストを実行する。スイート全体を逆順で実行するのがよい。これを定期的に行えば、Interacting Tests の偶発的な混入を避けやすい
補足

原因: Interacting Test Suites

Interacting Tests の特殊な場合で、テストが別のテストスイートにある

補足

Symptoms: 自分のスイートで実行すると通るが、Suite of Suites の中で実行すると失敗する

例: Suite1 単独 → 緑、Suite2 単独 → 緑、Suite(Suite1, Suite2) → Suite2 のテスト C が失敗

補足

Root Cause

通常、別のスイートのテストが同じリソースを作ろうとすることによる。同じスイートで実行すると、1つ目は成功し、2つ目はリソースの作成で失敗する

失敗や失敗した Test Method を読むだけで明らかなこともある。そうでなければ、（失敗していない）スイートから他のテストを1つずつ外してみる。失敗が停止したら、最後に外したテストに相互作用を起こしうる振る舞いが無いか調べる。特に Shared Fixture に関わるもの、クラス変数を初期化するすべての場所（Test Method ・ setUp ・ 呼ばれる Test Utility Method）を調査する

警告: スイートの中で相互作用するテストの組は1つとは限らない。実際の Test Method どうしでなく、複数の Testcase Class の SuiteFixture Setup や Setup Decorator の衝突が原因のこともある

Testcase Class Discovery を使う xUnit の変種（NUnit など）はテストスイートを使わないように見えるが、実は使っている。自動化担当者が Test Suite Factory で Test Runner にスイートを示すことを想定していないだけ

規則

Possible Solution

  • Fresh Fixture で問題を完全になくせる。それが範囲外なら、Immutable Shared Fixture で相互作用を防いでみる
  • あるテストが作った残りのオブジェクトやデータベースの行が後のテストのフィクスチャと衝突するなら、誤りやすい片付けのコードを書く必要をなくす Automated Teardown を考える
補足

原因: Lonely Test

Interacting Tests の特殊な場合。スイートの一部としては実行できるが、単独では実行できない。別のテスト（Chained Tests など）やスイート単位の準備ロジック（Setup Decorator など）が作った Shared Fixture の何かに依存するため

規則
  • 対処: テストを Fresh Fixture を使うよう変える、または Lonely Test に Lazy Setup のロジックを加えて単独で実行できるようにする
補足

原因: Resource Leakage

テストや SUT が有限のリソースを消費している

Symptoms: テストがだんだん遅くなる、または突然失敗し始める。Test Runner ・ SUT ・ Database Sandbox を再初期化すると解消するが、時とともに再発する

補足

Root Cause: テストや SUT がリソースを確保して解放しない。テストが遅くなりうる。やがてすべてのリソースが使い尽くされ、それに依存するテストが失敗し始める。2種類のバグのどちらか

SUT がリソースを正しく片付けていない。早く検出するほど早く突き止めて直せる

テストが、フィクスチャの準備でリソースを確保し、後始末で片付けていない

規則

Possible Solution

  • 問題が SUT にあれば、テストは役目を果たしたので、バグを直せばよい
  • テストが漏れを起こしているなら、漏れの源を取り除く。テストが失敗したときに正しく片付けないことによるなら、すべてのテストで Guaranteed Inline Teardown を行うか、Automated Teardown に変える
  • 一般に、すべてのリソースプールの大きさを1にするのがよい。テストがはるかに早く失敗し、どのテストが漏れを起こしているかを速く特定できる
補足

原因: Resource Optimism

外部リソースに依存するテストが、いつ ・ どこで実行するかによって非決定的な結果になる

Symptoms: ある環境で実行すると通り、別の環境で実行すると失敗する

Root Cause: ある環境で使えるリソースが別の環境で使えない

規則

Possible Solution

  • 可能なら、テストのフィクスチャ準備の段でリソースを作ることで Fresh Fixture に変える。どこで実行してもリソースが存在するようになる。SUT がどこで実行されてもファイルシステムの特定の場所が存在するよう、ファイルの相対アドレス指定が必要なかもしれない
  • 外部リソースを使わざるを得ないなら、ソースコードの Repository に登録し、すべての Test Runner が同じ環境で実行するようにする
補足

原因: Unrepeatable Test

テストが、初回の実行と以降の実行とで違う振る舞いをする

補足

Symptoms: 初回は通って以降すべて失敗する（Pass-Fail-Fail）、または初回は失敗して以降すべて通る（Fail-Pass-Pass）

Pass-Fail-Fail の例: 緑 → テスト C 失敗 → テスト C 失敗 →（利用者が何かをリセット）→ 緑 → テスト C 失敗

Fail-Pass-Pass の例: テスト C 失敗 → 緑 → 緑 →（リセット）→ テスト C 失敗 → 緑

スイートに Unrepeatable Test が複数あると、例えば C 失敗 → X 失敗 → X 失敗 →（リセット）→ C 失敗 → X 失敗、のように見える。C が Fail-Pass-Pass、X が Pass-Fail-Fail を同時に示している。毎回赤いバーになるので、どのテストが失敗しているかをよく見ないと違いに気づかず、看過しやすい

補足

Root Cause

最もよくある原因は、意図的か偶然かを問わず Shared Fixture を使うこと。テストがフィクスチャを変更し、次のスイートの実行時にフィクスチャが別の状態になっている

Prebuilt Fixture で最もよく起きるが、本当の前提条件はフィクスチャがテストの実行より長く残ることだけ

Database Sandbox は他の開発者のテストからは分離するが、自分が実行するテストどうしの衝突は防がない

フィクスチャを保持するクラス変数を Lazy Setup で初期化すると、同じスイートの以降の実行でフィクスチャが再初期化されないことがある。実質的に、同じ Test Runner から始めたすべての実行でフィクスチャを共有している

規則

Possible Solution

  • 永続する Shared Fixture が前提条件なので、各テストで Fresh Fixture を使えばなくせる
  • テストを完全に分離するには、個々のテストの寿命を超えて残る共有リソース（Database Sandbox など）が無いようにする必要がある。選択肢の1つはデータベースを Fake Database に置き換えること
  • 永続するデータストアを使わざるを得ないなら、すべてのデータベースキーに Distinct Generated Value を使い、テストごと ・ 実行ごとに違うオブジェクトを作る
  • もう1つの選択肢は、Automated Teardown で新しく作ったオブジェクト ・ 行をすべて安全かつ効率よく取り除くこと
補足

原因: Test Run War

複数の人が同時にテストを実行すると、テストの失敗がランダムに起きる

Symptoms: データベースなどの共有の外部リソースに依存するテストを実行している。1人から見ると、テスト3失敗 → テスト2失敗 → すべて通る → テスト1失敗、のように見える。チームに話すと、同じ時に同じ問題が起きていると分かる。1人だけが実行するとすべて通る

Impact: とてもいら立たしい。コードの締め切りが近づくほど起きる確率が上がるため。締め切りが近づくと、より小さな変更をより頻繁にコミットする傾向があり（「土壇場のバグ修正」）、他の人が同時にスイートを実行している可能性が上がり、同時の実行間の衝突の可能性が上がる

補足

Root Cause

さまざまなテストがアクセスし時に変更する全体で共有された Shared Fixture があるときにだけ起きる。テストや SUT が開く ・ 読むファイルのこともあれば、テスト用データベースのレコードのこともある

補足

データベースの競合の原因

別のテストが更新しているレコードを更新 ・ 削除しようとする

別のテストが読み取りロック（悲観的ロック）をかけているレコードを更新 ・ 削除しようとする

補足

ファイルの競合: 別の Test Runner から実行している別のインスタンスがすでに開いているファイルにアクセスしようとする

規則

Possible Solution

  • Fresh Fixture が望ましい解決
  • より簡単な解決は、各 Test Runner に専用の Database Sandbox を与えること。テストの変更は必要とせず、Test Run War の可能性を完全になくす。ただし、テストは Shared Fixture（Database Sandbox）を通じて相互作用しうるので、他の Erratic Test の源はなくならない
  • もう1つの選択肢は、各テストが変更するつもりのときに新しいオブジェクトを作ることで Immutable Shared Fixture に切り替えること。Test Method の変更が必要になる
  • あるテストが作った残りのオブジェクトやデータベースの行が後のテストのフィクスチャを汚しているなら、Automated Teardown で各テストの後に片付ける。これだけで Test Run War を完全になくすことはまずないが、頻度を減らせるかもしれない
補足

原因: Nondeterministic Test

1つの Test Runner だけがテストを実行していても、テストの失敗がランダムに起きる

補足

Symptoms

実行するたびに結果が変わる。例: テスト3失敗 → テスト3クラッシュ → すべて通る → テスト3失敗

チームと突き合わせ、自分しか実行していない、またはフィクスチャを利用者 ・ コンピュータ間で共有していないことから Test Run War を除外する

Unrepeatable Test と同様、同じスイートに Nondeterministic Test が複数あると、1つのテストの結果が変わるのでなく違うテストが失敗しているように見え、失敗 ・ エラーのパターンが見えにくい

補足

Impact: コードが毎回違う実行をするので、デバッグにとても時間がかかりいら立たしい。失敗の再現が難しく、何が失敗を起こすのか特定するのに何度も試行を要しうる。（特定できれば、ランダムな値を問題を起こすと分かっている値に置き換えるのはたいてい簡単）

補足

Root Cause

テストを実行するたびに違う値を使うことによる

毎回違う値を使うのがよい場合もある。正当な使い方は、データベースに保存するオブジェクトの一意キーとして Distinct Generated Value を使うこと

補足

値によって SUT の振る舞いが変わると期待されるアルゴリズムの入力に生成した値を使うと、Nondeterministic Test になりうる。例:

負（またはゼロ）の値が別扱いされる、または最大許容値がある整数値。ランダムに生成すると、ある実行では失敗し別の実行では通りうる

長さに最小 ・ 最大の許容値がある文字列。ランダムまたは一意の数値を生成し、長さを一定に保つ明示的な書式なしに文字列に変換するとき、偶然最もよく起きる

補足

ランダムな値はテストカバレッジを上げるのでよい考えに思えるかもしれないが、残念ながらテストカバレッジの理解とテストの繰り返し可能性を下げる（原則 Repeatable Test を参照）

もう1つの原因は、テストでの Conditional Test Logic の使用。実行ごとに違うコードパスが実行され、テストが非決定的になる。よくある「理由」は Flexible Test

テストを完全に決定的でなくするものは何であれ悪い考え

手順

Possible Solution

  1. まず、Conditional Test Logic を取り除き、テストが完全に直線的に実行されるようにして、テストを繰り返し可能にする

  2. 次に、ランダムな値を決定的な値に置き換える

  3. その結果テストカバレッジが乏しくなれば、扱えていない興味深いケースのテストを追加する。最善の入力値の組を決めるよい方法は、同値クラスの境界値を使うこと

  4. その結果 Test Code Duplication が多くなれば、Parameterized Test を抽出するか、入力値と期待結果をファイルに入れて Data-Driven Test で読む

補足

分類: 振る舞いの臭い

書籍版: p.239

定義

Fragile Test

A test fails to compile or run when the system under test (SUT) is changed in ways that do not affect the part the test is exercising.

補足

Symptoms（兆候）

以前は実行して通っていたテストが、コンパイルや実行に失敗する、または実行すると失敗する

当該の SUT の振る舞いを変えたのなら、テスト結果の変化は予期どおり

変更が失敗しているテストに影響するはずがないと思うとき、または本番コードもテストも変えていないときは、Fragile Test

補足

過去の自動テストの取り組みは、しばしば自動テストの「4つの感度」（four sensitivities）に阻まれてきた

以前通っていた Fully Automated Test を突然失敗させ始めるのはこれらの感度

テストが失敗する根本原因は、おおよそこの4つのどれかに分類できる

各感度はさまざまな具体的なテストの書き方から生じうるが、感度そのものを理解するのが有用

補足

Impact（影響）

システムの機能やフィクスチャを変えるたびに、はるかに多くのテストを再確認させ、テストの保守費用を上げる

高度にインクリメンタルな納品を行うプロジェクト（eXtreme Programming など）では特に致命的

規則

Trouble-Shooting Advice（調査の助言）

  • テストがどう失敗するかのパターンを探す。「壊れたテストすべてに共通するものは何か」と問う。これで、テストが SUT とどう結合しているかが分かるはず。次に、その結合を最小にする方法を探す

定義

原因: Interface Sensitivity

Interface Sensitivity

Interface Sensitivity is when a test fails to compile or run because some part of the interface of the SUT that is uses has changed.

補足

Symptoms

静的型付け言語では通常コンパイルの失敗として、動的型付け言語ではテストを実行したときだけ現れる

動的型付け言語のテストは、変更された API（メソッド名やシグネチャの変更）を呼ぶとテストエラーになりうる

ユーザーインターフェースを介して SUT とやり取りするテストが、必要な UI 要素を見つけられないことがある。UI を経由してやり取りする Recorded Tests（「スクリーンスクレイピング」）は特にこの問題を起こしやすい

規則

Possible Solution

  • 原因はたいてい十分明らか。テストが（コンパイル ・ 実行に）失敗する箇所が問題の場所を示す。変更そのものがテストエラーを起こすので、テストが変更点を越えて実行し続けることはまれ
規則

インターフェースが内部（組織やアプリケーションの中）と自動テストからだけ使われるなら、SUT API Encapsulation が最善の解決。API の変更の費用と影響を減らし、必要な変更を妨げない

  • よくある実装は、テストを表現する Higher Level Language の定義。テスト言語の動詞をカプセル化の層が適切なメソッド呼び出しに翻訳し、インターフェースがある程度後方互換な形で変わったときに修正が必要なのはその層だけになる
  • 「テスト言語」は、SUT の API をテストから隠す Creation Method や Verification Method などの Test Utility Method の形で実装できる
規則

Interface Sensitivity を避ける他の唯一の現実的な代替は、インターフェースを厳格な変更管理の下に置くこと

  • インターフェースの利用者が外部で匿名の場合（Windows の DLL の利用者など）、これが唯一の代替かもしれない
  • その場合、通常は変更の手順がある: すべての変更は後方互換でなければならない、古い版のメソッドを外す前に非推奨にしなければならない、非推奨のメソッドは最低限のリリース数または期間存在しなければならない
定義

原因: Behavior Sensitivity

Behavior Sensitivity

Behavior Sensitivity is when changes to the SUT cause other tests to fail.

補足

Symptoms: 以前通っていたテストが、SUT に新しい機能を追加したときやバグを直したときに突然失敗し始める

補足

Root Cause

テストが検証している機能自体が変更されたために失敗するのは Behavior Sensitivity ではない。それが回帰テストを持つ理由そのもの

補足

次の場合が Behavior Sensitivity

テスト前の SUT の状態を準備するのに使う機能が変更された

テスト後の SUT の状態を検証するのに使う機能が変更された

フィクスチャの後始末に使うコードが変わった

補足

変わったコードが検証している SUT の一部でなければ Context Sensitivity。大きすぎる SUT をテストしているのかもしれず、検証する部分とそれが依存するコンポーネントに分ける必要がある

規則

Possible Solution

  • 準備で使う SUT の振る舞いについての、新たに誤りになった前提は Creation Method の後ろにカプセル化できる
  • テスト後の SUT の状態の詳細についての前提は Custom Assertion や Verification Method にカプセル化できる
  • 前提が変わったときにテストコードの更新が必要になることはなくならないが、変更が必要なテストコードの量は確実に減る
定義

原因: Data Sensitivity

Data Sensitivity

Data Sensitivity occurs when a test fails because the data being used to test the SUT has been modified.

補足

テスト用データベースの中身が変わるときに最もよく起きる

補足

Symptoms: 以前通っていたテストが次のとき突然失敗し始める

SUT のテスト前の状態を持つリポジトリ（データベース）にデータが追加された

リポジトリのレコードが変更 ・ 削除された

Standard Fixture を準備するコードが変更された

Shared Fixture が、それを使う最初のテストの前に変更された

いずれの場合も、Standard Fixture（共有データベースや Prebuilt Fixture などの Shared Fixture）を使っているはず

補足

Root Cause

検証ロジックが、リポジトリにもう無いデータを探している、または新しく追加されたレコードを偶然含む検索条件を使っている

SUT が、欠けた ・ 変更されたデータを参照する入力で実行され、違う振る舞いをする

いずれの場合も、テストがデータベースにどんなデータがある ・ 無いかについて前提を置き、その前提が破られた

規則

Possible Solution

  • SUT の実行の段で失敗するなら、実行するロジックの事前条件を見て、最近のデータベースの変更に影響されていないか確認する
  • ほとんどの場合、失敗は検証の段で起きる。検証ロジックが、どんなデータがあるかについて不合理な前提を置いていないか調べ、置いていれば検証ロジックを変える
  • SUT の入力が存在しない ・ 変更されたデータを参照していることが問題でも、失敗は検証ロジックで起きうる。SUT の（期待と違う）「後」の状態を調べ、なぜ期待と違うのかをたどる必要があるかもしれない。これで、SUT の入力とテスト開始前に存在したデータの不一致が明らかになるはず
  • 最善の解決は、テストを既存のデータベースの中身から独立させること（Fresh Fixture）
  • それができなければ、何らかの Database Partitioning Scheme（Database Sandbox）で、あるテストのために変更したデータが他のテストが使うデータと重ならないようにする（例はサイドバー Why Do We Need 100 Customers?）
  • もう1つの解決は、データに正しい変更が加えられたことを検証すること。Delta Assertion はデータの前後の「スナップショット」を比べ、変わっていないデータを無視する。フィクスチャ全体の知識を検証の段にハードコードする必要がなくなる
定義

原因: Context Sensitivity

Context Sensitivity

Context Sensitivity occurs when a test fails because the state or behavior of the context in which the SUT executes has changed in some way.

補足

Symptoms: 以前通っていたテストが謎の理由で突然失敗し始める。Erratic Test と違い、短い間に繰り返し実行すると一貫した結果になる。違うのは、どう実行しても一貫して失敗するようになったこと

補足

Root Cause

テストが失敗しうる理由

検証している機能が何らかの形で時刻や日付に依存する

SUT が依存する他のコードやシステムの振る舞いが変わった

補足

大きな源は、検証しようとしている SUT が何かについての混乱。SUT は検証しようとしているソフトウェアの部分であり、単体テストでは、システムやアプリケーション全体のごく小さな部分であるべき

特定の単位（クラスやメソッド）を分離できないと、多すぎるソフトウェアを一度にテストすることになり、Context Sensitivity を必ず生む

テストが制御すべき間接入力が成り行きに任され、誰かが依存先のコンポーネント（DOC）を変えるとテストが失敗する

補足

解消するには、SUT のどの間接入力がなぜ変わったかを突き止める

日付や時刻に関わるロジックがあれば、月の長さなどが原因でないか見る

他のシステムからの入力に依存するなら、最近何か変わっていないか調べる。他のシステムとの過去のやり取りのログは、失敗時のログと比べるのにとても役立つ

問題が出たり消えたりするなら、通るときと失敗するときのパターンを探す（詳しくは Erratic Test）

規則

Possible Solution

  • テストを決定的にするには、SUT のすべての入力を制御する必要がある
  • 他のシステムからの入力に依存するなら、テストが構成して組み込む Test Stub で制御する必要があるかもしれない
  • 時刻 ・ 日付に固有のロジックがあれば、テストの一部としてシステムクロックを制御できる必要がある。開始の日時を設定し、時間の経過を模擬する手段をテストに与える Virtual Clock でシステムクロックを差し替える必要があるかもしれない
補足

原因: Overspecified Software

別名: Overcoupled Test

テストが、ソフトウェアがどう構造化され振る舞うべきかについて言いすぎる

Behavior Verification というテストのスタイルに伴う Behavior Sensitivity の一形態。Mock Object を多用して層をまたぐテストを組むのが特徴

主な問題は、テストがソフトウェアが何を達成すべきかでなく、どう行うべきかを記述すること。ソフトウェアが特定の方法で実装されたときにだけテストが通る

可能な限り原則 Use the Front Door First を適用し、SUT の実装についての知識をテストに多く埋め込むのを避けることで回避できる

補足

原因: Sensitive Equality

検証するオブジェクトを文字列に変換し、期待する文字列と比べる

テストが、検証する役目にない振る舞いに敏感になるので Behavior Sensitivity の例。インターフェースの意味が変わった Interface Sensitivity の例とも考えられる

いずれにせよ問題はテストの書き方にある。オブジェクトの文字列表現を使って期待値と照合するのは端的に誤り

補足

原因: Fragile Fixture

新しいテストに合わせて Standard Fixture を変更すると、他のいくつかのテストが失敗する

Data Sensitivity または Context Sensitivity の別名

Frequent Debugging（Meszaros、更新日の記載なし）

補足

分類: 振る舞いの臭い

別名: Manual Debugging

書籍版: p.248

定義

Frequent Debugging

Manual debugging is required to determine the cause of most test failures.

補足

Symptoms（兆候）

テストを実行するとテストの失敗やエラーになる。Test Runner の出力では問題を判断できず、対話的なデバッガ（またはコード中にばらまいた print 文）でどこがおかしいかを判断しなければならない

これが例外的なら心配は不要だが、ほとんどのテストの失敗でこの種のデバッグが必要なら Frequent Debugging

補足

Causes（原因）

自動テストのスイートに Defect Localization が欠けていることによる

補足

失敗したテストは、個々の失敗メッセージ（Assertion Message）か、テストの失敗のパターンによって、何がおかしいかを教えるべき。そうでなければ

個々のクラスの中の論理誤りを指摘するはずの、詳細な単体テストが欠けているかもしれない

補足

クラスの集まり（コンポーネント）について、個々のクラス間の統合の誤りを指摘するはずのコンポーネントテストが欠けているかもしれない

これは、依存先のオブジェクトを置き換えるために Mock Object を多用し、依存先のオブジェクトの単体テストが Mock Object に設定した振る舞いと一致しないときに起きうる

補足

著者がこの問題に最もよく出会ったのは、上位（機能やコンポーネントの）テストは書いたが、個々のメソッドの単体テストをすべては書かなかったとき

（この手法を、すべてのコードが失敗する単体テストに引き出されて生まれるテスト駆動開発と区別して、テストファースト開発と呼ぶ人もいる）

補足

Infrequently Run Tests（Production Bugs）でも起きうる。小さな変更のたびにテストを実行すれば、前回の実行から何を変えたかを覚えている。テストが失敗しても、バグの場所を探して長く調べる必要はない。入れたのを覚えているので場所が分かる

補足

Impact（影響）

手動のデバッグは遅く退屈な作業。問題の微妙な兆候を看過しやすく、1つの論理誤りを追うのに何時間も費やしうる

生産性を下げ、開発のスケジュールをはるかに予測しにくくする。1回の手動のデバッグで、ソフトウェアの開発に要する時間が半日以上延びうる

規則

Solution Patterns（解決のパターン）

ある機能の顧客テストが欠けていて、自動テストが明らかにしなかった問題を手動の利用者テストが明らかにしたなら、おそらく Untested Requirement（Production Bugs）

  • どんな自動テストがあればその手動デバッグを防げたかを自問する
  • さらに良いのは、問題を特定したら、それを明らかにするテストを書くこと。その失敗するテストでテスト駆動のバグ修正を行う
  • 広範な問題だと疑うなら、明らかになった不足を補完するのに必要な追加のテストを特定して書く開発タスクを作る
規則

本当のテスト駆動開発を行うことが、Frequent Debugging を生む状況を避ける最善の方法

  • アプリケーションの外皮にできるだけ近いところから始め、ストーリーテスト駆動開発を行う
  • 個々のクラスの単体テストと、関連するクラスの集まりのコンポーネントテストを書き、良い Defect Localization を確保する

Manual Intervention（Meszaros、更新日の記載なし）

補足

分類: 振る舞いの臭い

書籍版: p.250

定義

Manual Intervention

A test requires a person to perform some manual action each time it is run.

補足

Symptoms（兆候）

テストを実行する人が、テストの前か途中で何かを手動で行わなければテストが失敗する

人がテストの結果を手動で検証する必要があることもある

補足

Impact（影響）

自動テストの要点は、ソフトウェアに持ち込まれた問題について早いフィードバックを得ること

そのフィードバックを得る費用が Manual Intervention の形で高すぎると、テストをあまり実行しなくなり、フィードバックをあまり得られなくなる

フィードバックがあまり得られないと、テストの実行の間に多くの問題を混入させ、Frequent Debugging と High Test Maintenance Cost につながる

完全に自動化した Integration Build と回帰テストの工程を非現実的にする

補足

Causes（原因）

原因は、ソフトウェアが行う ・ 出会うことの種類と同じほど多様。以下は、Manual Intervention を要するものの一般的な分類で、網羅的ではない

補足

原因: Manual Fixture Setup

Symptoms: 自動テストを実行できるようにするには、人が手動でテスト環境を準備しなければならない。サーバーの設定、サーバープロセスの起動、Prebuilt Fixture を準備するスクリプトの実行などの形をとる

Root Cause: 通常、テストのフィクスチャ準備の段の自動化への注意の不足。SUT のコンポーネント間の過剰な結合で、システムのコードの大部分を開発環境の中でテストできないことによる場合もある

規則
  • Possible Solution: Prebuilt Fixture を使うときは、Unrepeatable Test（Erratic Test）にならないよう、フィクスチャの何も変更しないことが重要。これを Immutable Shared Fixture と呼ぶ
補足

原因: Manual Result Verification

Symptoms: テストを実行できるが、SUT が正しい結果を返していないと分かっているときでも、ほぼ常に通る

Root Cause: 書いたテストが Self-Checking Test でなければ、エラーや例外が投げられたときにしかテストが失敗しないので、誤った安心感を与えられうる

規則
  • Possible Solution: Test Method に Assertion Method の呼び出しなどの結果検証ロジックを入れ、すべてのテストを自己検証にする
補足

原因: Manual Event Injection

Symptoms: テストが進めるようになる前に、実行中に人が介入して手動の操作をしなければならない

Root Cause: SUT の多くのイベントは、プログラムの制御で生成しにくい。例: ネットワークケーブルを抜く、データベース接続を切断する、ユーザーインターフェースのボタンを押す

Impact: 人が何かを手動で行う必要があると、テストを実行する手間が増え、無人で実行できなくなる。完全に自動化したビルドとテストのサイクルの試みを台無しにする

規則

Possible Solution

  • 最善の解決は、本物の人が手動の操作をせずに済むテスト方法を見つけること
  • イベントが非同期のイベントで SUT に通知されるなら、Test Method から模擬したイベントオブジェクトを渡して SUT を直接呼べる
  • SUT がその状況をシステムの他の部分からの同期的な応答として経験するなら、SUT の一部を、さらしたい状況を模擬する Test Stub に置き換えて間接入力を制御できる
補足

Further Reading（参考）

SUT の間接入力を制御する方法の詳しい説明は「Using Test Doubles」の章を参照

Slow Tests（Meszaros、2006年10月11日更新）

補足

分類: 振る舞いの臭い

書籍版: p.253

定義

Slow Tests

The tests take too long to run.

補足

Symptoms（兆候）

テストの実行に時間がかかり、開発者が SUT を変えるたびには実行しない

次のコーヒーブレークや他の中断まで実行を待つ。または実行するたびに、席を離れて他のメンバーと雑談する（Doom をしたりネットを閲覧したり…）

補足

Impact（影響）

直接の費用: テストを実行する人の生産性を下げる。テスト駆動でコードを書くときは実行のたびに貴重な秒を無駄にし、変更をコミットする前にすべてのテストを実行するときはさらに大きな待ち時間になる

補足

多くの間接の費用

変更をすべてマージした後にテストの実行を待つ必要があり、「統合トークン」を長く持つことによるボトルネック

テストの実行を待つ人に他の人が気を取られる時間

前回テストを実行した後のいつかに入れた問題を、デバッガで探す時間。前回から時間が経つほど、何をしてテストを壊したか覚えていない可能性が高い。自動単体テストが与える素早いフィードバックの崩壊の結果

補足

Slow Tests へのよくある反応は、すぐ Shared Fixture に向かうこと。だがこれはほぼ常に Erratic Tests などの他の問題を生む

よりよい解決は、Fake Object で遅いコンポーネント（データベースなど）をより速いものに置き換えること

他のすべてが失敗して何らかの Shared Fixture を使わざるを得ないなら、できる限り不変にするよう試みる

規則

Trouble-Shooting Advice（調査の助言）

  • Slow Tests は、SUT の構築 ・ テストのしかたからも、テストの設計のしかたからも起きうる
  • テストを実行して緑のバーが伸びるのを見ているだけで問題が明らかなこともある。実行に明らかな停止があったり、Test Method に明示的な遅延が書かれていたりする
  • 原因が明らかでなければ、テストの異なる部分集合（サブスイート）を実行して、どれが速くどれが長いかを確認する
規則

プロファイリングツールは時間の使いどころを確認するのに便利だが、xUnit で簡単な自作のミニプロファイラを作れる

  • Testcase Superclass の setUp と tearDown を編集し、Testcase Class と Test Method の名前とともに開始 ・ 終了時刻または所要時間をログファイルに出力する
  • ファイルを表計算に取り込み、所要時間で並べ替えれば、原因が見つかる
  • 実行時間が最も長いテストが、最も労力を注ぐ価値のあるテスト
補足

Causes（原因）

具体的な原因は、SUT の構築のしかたにも、テスト自体の書き方にもありうる

SUT の構築のしかたが、遅くなる書き方をテストに強いることもある。これはレガシーコードや「テストを後で」書いたコードで特に問題

補足

原因: Slow Component Usage

SUT のコンポーネントの遅延が大きい

Root Cause: Slow Tests の最もよくある単一の原因は、多くのテストでのデータベースとのやり取り。フィクスチャ準備のためにデータベースに書き、結果検証のためにデータベースを読む（Back Door Manipulation の一形態）テストは、メモリ上のデータ構造に対して実行する同じテストより約50倍長くかかる。これは遅いコンポーネントを使うという、より一般的な問題の特殊な場合

規則
  • Possible Solution: 遅いコンポーネントを、ほぼ即座に応答する Test Double に置き換えれば、はるかに速くなる。遅いコンポーネントがデータベースなら、Fake Database で平均50倍速くなりうる。他の方法はサイドバー Faster Tests Without Shared Fixtures を参照
補足

原因: General Fixture

Symptoms: 各テストが同じフィクスチャを構築するため、テストが一貫して遅い

Root Cause: 各テストが、Fresh Fixture を構築するたびに大きな General Fixture を構築している。General Fixture は Minimal Fixture よりはるかに多くのオブジェクトを含むので、構築に時間がかかる。Fresh Fixture は Testcase Object ごとに新しいフィクスチャを準備するので、「長い」をテストの数だけ掛ければ減速の大きさが分かる

規則
  • Possible Solution: 最初の傾向は、テストごとの再構築を避けるため General Fixture を Shared Fixture にすることだが、Shared Fixture を不変にできない限り Erratic Tests につながりやすいので避けるべき。よりよい解決は、各テストが準備するフィクスチャの量を減らすこと
補足

原因: Asynchronous Test

Symptoms: いくつかのテストの実行が異常に長い。それらのテストは明示的な遅延を含む

補足

Root Cause

Test Method に含めた遅延は、実行をかなり遅くする

テストするソフトウェアがスレッドやプロセスを起動し（Asynchronous Code、Hard-to-Test Code）、テストがその起動 ・ 実行を待ち、期待した副作用を検証する必要があるとき、必要になりうる

プロセスなどの起動にかかる時間のばらつきのため、一貫して通るよう、通常「念のため」のかなり長い遅延を入れる必要がある

例（RequestHandlerThreadTest）: スレッドを起動し Thread.sleep(TWO_SECONDS) で待ってから、初期化の成功や処理した要求の数を検証する（定数名は TWO_SECONDS だが値は3000）

補足

Impact: 2秒の遅延は大したことがないように思えるかもしれないが、そうしたテストが1ダースあると実行にほぼ30秒かかる。通常のテストなら1秒に数百実行できる

規則
  • Possible Solution: 最善は、ロジックを同期的にテストしてテストの非同期性を避けること。Extract Testable Component リファクタリングで Humble Executable（Humble Object）を実装する必要があるかもしれない
補足

原因: Too Many Tests

Symptoms: テストが多すぎて、個々がどれほど速くても実行に長くかかる

補足

Root Cause

明らかな原因はテストが多いこと。本当にそれだけのテストがある大きなシステムだからかもしれないし、テスト間の重複が多すぎるからかもしれない

あまり明らかでない原因は、多すぎるテストを頻繁に実行しすぎていること

規則

Possible Solution

すべてのテストを常に実行する必要はない。鍵は、すべてのテストが定期的に実行されるようにすること

  • スイート全体が長すぎるなら、適切な断面のテストを持つ Subset Suite（Named Test Suite）を作り、コミットのたびにそれを実行する
  • 残りのテストは、夜間など都合のよい時間に予定して、頻度は低いが定期的に実行する。これを「ビルドパイプライン」と呼ぶ人もいる（他の考えはサイドバー Faster Tests Without Shared Fixtures）
規則

システムが大きいなら、かなり独立したサブシステムやコンポーネントに分けるとよい

  • 各コンポーネントのチームが独立に作業し、自分のコンポーネントのテストだけを実行できる
  • そのテストの一部は、他のコンポーネントがこのコンポーネントをどう使うかの代理として働くべきで、インターフェースの契約が変わったら最新に保つ必要がある（「Tests as Documentation、いいね！」）
  • すべてのコンポーネントを一緒に実行するエンドツーエンドのテスト（おそらくストーリーテストの一形態）もあるが、コミット前のスイートに含める必要はない

Buggy Tests（Meszaros、更新日の記載なし）

補足

分類: プロジェクトの臭い

書籍版: p.260

定義

Buggy Tests

Bugs are regularly found in the automated tests.

補足

Fully Automated Tests は、反復的な開発を行うチームの「安全網」の役を果たすはず。だが、安全網が実際に機能するとどうして確信できるのか

Buggy Tests は、自動テストがうまくいっていないかもしれないことを示すプロジェクト単位の兆候

補足

Symptoms（兆候）

ビルドが失敗し、失敗したテストが原因とされる。よく調べると、テスト対象のコードは正しく動いていて、テストが壊れていると示していた

バグが見つかった特定のシナリオを検証するテストがあったのに Production Bugs に出会った。根本原因の分析で、テストにバグがあり本番コードの誤りを捕まえられなかったと分かる

補足

Impact（影響）

誤った結果を出すテストは危険

通るべきでないのに通るテスト（原文は「false negative」、「ここには何も問題がない」の意）は誤った安心感を与える

失敗すべきでないのに失敗するテスト（原文は「false positive」）はテストの信用を失わせる。「オオカミが来た」と叫ぶ少年のように、何度か起きると無視する傾向が生まれる

補足

Causes（原因）

多くのことが原因になりうる。そのほとんどはコードや振る舞いの臭いとしても現れるが、プロジェクトマネージャーとしては、特に探しに行かない限りそうした根底の臭いを確認することはまずない

補足

原因: Fragile Test

Buggy Tests は Fragile Test のプロジェクト単位の兆候にすぎないかもしれない

偽陽性のテスト失敗については、「4つの感度」（Interface ・ Behavior ・ Data ・ Context Sensitivity）から始めるとよい。それぞれが、テストを失敗させた変更でありうる

Test Double とリファクタリングで感度を取り除くのは難しいこともあるが、最終的にテストをはるかに頼りになるものにする

補足

原因: Obscure Test

偽陰性（通るべきでないのに通る）のよくある原因は、正しく書くのが難しい Obscure Test。特に、自分の変更で壊れた既存のテストを修正しているとき

自動テストはテストしにくいので、修正したテストが当初捕まえるよう設計したバグをまだすべて捕まえるか、あまり検証しない。緑のバーが出れば「大丈夫」と思うが、決して失敗しないテストを作ってしまったかもしれない

Obscure Test は、テストの読み手を重視したテストのリファクタリングで対処するのが最善。本当の目標は Tests as Documentation で、それに満たないものは Buggy Tests の可能性を上げる

補足

原因: Hard to Test Code

もう1つのよくある原因は、特に「レガシーソフトウェア」（ここでは、完全な自動テストのスイートを保持しないソフトウェアと定義する）で、ソフトウェアの設計が自動テストに向いていないこと

この Hard-to-Test Code は Indirect Testing を強いることがあり、それが Fragile Test や Fragile Fixture を生みうる

Hard-to-Test Code をテストしやすくする唯一の方法は、テスト容易性を上げるようリファクタリングすること（「Test Automation Strategy」と「Using Test Doubles」の章）

それができなければ、SUT API Encapsulation（Test Utility Method）で、変更に影響されるテストコードの量を減らせるかもしれない

規則

Trouble-Shooting Advice（調査の助言）

  • Buggy Tests があると聞いたら、さらに質問することが重要
  • 「5回のなぜ」[TPS] を問うて突き詰め、どのコード ・ 振る舞いの臭いが原因なのかを正確に特定し、それぞれの根本原因を見つける
規則

Solution Patterns（解決のパターン）

  • 解決は、Buggy Tests がなぜ起きたかに大きく依存する。根底の振る舞い ・ コードの臭いの解決を参照する
規則

すべての「プロジェクトの臭い」と同様、プロジェクト単位の原因を探すべき。それには、開発者に次のための十分な時間を与えないことが含まれる

  • テストを正しく書くことを学ぶ
  • テストの自動化をより容易 ・ 頑健にするため、レガシーコードをリファクタリングする
  • テストを先に書く
規則
  • こうしたプロジェクト単位の原因に対処しなければ、問題は近いうちに必ず再発する

Developers Not Writing Tests（Meszaros、2006年10月9日更新）

補足

分類: プロジェクトの臭い

書籍版: p.263

定義

Developers Not Writing Tests

Developers aren't writing automated tests.

補足

Symptoms（兆候）

開発者がテストを書いていないと耳にする

または Production Bugs を観察し、「なぜこんなに多くのバグがすり抜けるのか」と尋ねたら「そこの部分をカバーするテストを書いていないから」と言われた

補足

Impact（影響）

チームが「壊れうる」すべてのソフトウェアの自動テストを書いていないなら、未来を抵当に入れている

補足

システムがテスト負債を内包するので、現在のペースは長期的に持続できない

新しい機能を加えるのにどんどん長くかかる

設計を改善するコードのリファクタリングが危険に満ちる（だからだんだん行われなくなる）

補足

これは、伝統的で疑心暗鬼な非アジャイル開発への「滑りやすい坂道」の始まり。そこを目指すならこのままでよいが、そうでないなら行動する時

補足

原因: Not Enough Time

ありそうな原因は、与えられた開発時間の中でテストを書くのに苦労していること

開発スケジュールが厳しすぎる

上司やチームリーダーから「テストを書いて時間を無駄にするな」と言われている

テストを効率よく書く技能が無く、学習曲線を上る時間も与えられていない

補足

時間が必要なら、プロジェクトのスケジュールを調整して時間を与える

これは、テストをより速く書けるようにする技能とテスト自動化の基盤を身に付ける間の一時的な調整でよいはず

著者らの経験では、開発者がこの工程を身に付ければ、以前コードを書いてデバッグするだけにかかっていたのと同じ時間でテストとコードを書ける。テストを書く時間は、デバッガで費やさずに済む時間で十分に埋め合わされる

補足

原因: Hard to Test Code

特に「レガシーソフトウェア」（完全な自動テストのスイートを保持しないソフトウェア）で、ソフトウェアの設計が自動テストに向いていないこと

詳しくは臭い Hard-to-Test Code の節

補足

原因: Wrong Test Automation Strategy

テスト環境やテスト自動化の戦略が、書くのに時間がかかりすぎる Fragile Tests や Obscure Tests を生んでいることもある

「5回のなぜ」[TPS] を問うて根本原因を見つけ、その原因に対処して軌道に戻す

規則

Trouble-Shooting Advice（調査の助言）

  • Developers Not Writing Tests のようなプロジェクト単位の臭いは、開発者よりもプロジェクトマネージャー ・ スクラムマスター ・ チームリーダーが検出しやすい
規則

マネージャーとして直し方を認知していなくてもよい。重要なのは気づき、認識すること

  • それにより、開発チームに、なぜテストを書かないのか、どんな状況でか、書くときはどれくらい時間がかかるのかを質問できる
  • そして、テストをすべて書けるよう根本原因に対処する方法を考え出すことを励まし、権限を与える
規則

チームが考え出した改善計画を実行するのを全面的に支援する

  • 支援には、必要な技能を学ぶ時間と、必要なテスト基盤を構築 ・ 準備する時間を含める
  • 一夜で好転するとは期待しない
規則

反復ごとに工程改善の目標を置いてもよい（例: 「テストされていないコードを20%減らす」「コードカバレッジを20%改善する」）

  • 目標は合理的で、数字を良く見せるだけでなく正しい行動を促す十分に高いレベルのものにする
  • （「テストを205件多く書く」という目標は、テストを小さく分けたり複製したりするだけで、テストカバレッジを少しも上げずに達成できてしまう）

High Test Maintenance Cost（Meszaros、更新日の記載なし）

補足

分類: プロジェクトの臭い

書籍版: p.265

定義

High Test Maintenance Cost

Too much effort is spent maintaining existing tests.

補足

テストコードは、検証する本番コードとともに保守する必要がある。アプリケーションを進化させるにつれ、検証するクラスが機能追加やリファクタリングで変わるので、テストを定期的に再確認することになる

High Test Maintenance Cost は、テストが理解しにくく保守しにくくなったときに起きる

補足

Symptoms（兆候）

新しい機能の開発が遅くなっている。新しい機能を加えるたびに、既存のテストに大規模な変更が必要になる

開発者やテスターが、プロジェクトマネージャーやコーチに「テストのリファクタリング ・ 片付けの反復」が必要なと言っているかもしれない

新しいテストを書く時間と既存のテストを変える時間を、テストを成功させるためのコードを実装する時間と分けて計測していれば、時間のほとんどが既存のテストの変更に費やされていると気づく

補足

テストの保守性の問題のほとんどには、他の臭いが伴う

Fragile Tests: テストが SUT に密に結合しすぎていることを示す兆候

Fragile Fixture: 同じフィクスチャの設計（Standard Fixture）に依存するテストが多すぎ、それが High Test Maintenance Cost を生んでいる兆候

Erratic Test: Shared Fixture が大きな悩みの種になっている兆候かもしれない

補足

Impact（影響）

テストの保守に大きな手間がかかるため、チームの生産性が大きく低下する

開発者が「見切りをつける」（影響を受けるテストをスイートから外す）よう求めて騒ぐかもしれない。本番コードを書くことは必須だが、テストの保守は（事情を認知していない人にとっては）完全に任意

何もしなければ、チームや経営陣がテストの自動化は「うまくいかない」と判断してテストを放棄し、テスト自動化の取り組み全体が無駄になるかもしれない

補足

Causes（原因）

根本原因は、「Principles of Test Automation」に記述したさまざまな原則に注意を払わないこと

より直接の原因は、しばしば多すぎる Test Code Duplication と、SUT の API に密に結合しすぎたテスト

High Test Maintenance Cost は多くのことが原因になりうる

補足

原因: Fragile Test

SUT に小さな変更を加えたために失敗するテストが Fragile Tests。本来影響すべきでないあらゆる小さな変更の後に再確認して「揺すって直す」必要があるので、High Test Maintenance Cost を生む

失敗の根本原因は「4つの感度」のどれでもありうる（Interface ・ Behavior ・ Data ・ Context Sensitivity）

Test Double を使い、システムを個別にテストできる小さなコンポーネントとクラスにリファクタリングすることで、テストをできるだけ多くの感度に鈍感にし、High Test Maintenance Cost を減らせる

補足

原因: Obscure Test

Obscure Tests は、見るたびに理解に時間がかかるので、High Test Maintenance Cost の大きな要因

変更が必要なときは、調整に手間がかかり、「一度で動く」可能性がはるかに低く、テストのデバッグが増える

意図した条件を捕まえられなくなる可能性も高く、Buggy Tests につながりうる

テストの読み手を重視したリファクタリングで対処するのが最善。本当の目標は Tests as Documentation で、それに満たないものは High Test Maintenance Cost の可能性を上げる

補足

原因: Hard to Test Code

「レガシーソフトウェア」（完全な自動テストのスイートを保持しないソフトウェア）は、通常テストを「最後に」（ソフトウェアがすでに存在した後に）書くので、テストしにくいことがある

ソフトウェアの設計が自動テストに向いていないと、多くの偶有的な複雑さを伴う扱いにくいインターフェースを介した Indirect Testing を強いられ、Fragile Tests や Fragile Fixture になりうる

テスト容易性を上げるリファクタリングには時間と手間がかかるが、High Test Maintenance Cost をなくすならその時間は有効に使われる

補足

リファクタリングができなければ、Test Utility Method による SUT API Encapsulation で、変更に影響されるテストコードの量を減らせるかもしれない

例: Creation Method はコンストラクタをカプセル化し、コンストラクタのシグネチャや意味の変更にテストを影響されにくくする

規則

Trouble-Shooting Advice（調査の助言）

  • プロジェクト単位の臭いとして、High Test Maintenance Cost は、開発者と同じくらいプロジェクトマネージャー ・ スクラムマスター ・ チームリーダーにも検出されやすい
規則

問題を調べて直す技術的な深さが無くても、気づいていることが重要

  • それにより、開発チームに、テストの保守にどれくらい時間がかかっているか、どのくらいの頻度で起きるか、なぜ必要なのかを質問できる
  • そして、そんなに高い保守費用にならないより良い方法を見つけるよう求められる
規則

チームが考え出した改善計画の実行には、もちろん支援が必要になる

  • 支援には、調査（スパイク）の時間、学習 ・ 訓練の時間、実際の作業の時間を含める
  • 時間は、「テストのリファクタリングのストーリー」を持つ、顧客に約束する新機能を減らすようベロシティを調整する、などの方法で作れる
規則
  • どう行うにせよ、今開発チームに問題を直す資源を与えなければ、問題は悪化し、テストが倍になった将来にはさらに直しにくくなることを忘れてはならない

Production Bugs（Meszaros、2007年2月18日更新）

補足

分類: プロジェクトの臭い

書籍版: p.268

定義

Production Bugs

We find too many bugs during formal test or in production.

補足

Symptoms（兆候）

自動テストを書くのにこれだけ労力をかけたのに、正式な（システム）テストや本番で見つかるバグの数が多すぎる

補足

Impact（影響）

正式なテストで見つかったバグは開発中に見つかったものより調査と修正に時間がかかり、本番で見つかったものはさらにかかる

バグ修正と再テストの時間を取るため、製品の出荷や本番投入を遅らせざるを得なくなりうる

この時間と手間はそのまま金銭的費用になり、製品に機能を加えたり他の製品を作ったりに使えたはずの資源を消費する

遅れは顧客の目から見た組織の信用に影響しうる

品質の低さは、提供する製品 ・ サービスの価値を下げるという間接の費用も持つ

補足

Causes（原因）

バグが本番まで通り抜ける理由はいくつかある: Infrequently Run Tests、または Untested Code。後者は Missing Unit Tests や Lost Tests によりうる

補足

「十分なテスト」とは、数ではなくテストカバレッジのこと

Untested Code への変更は、問題を入れたときに開発者に知らせる自動テストが無いので、Production Bugs を生みやすい

Untested Requirements は、テストの実行のたびに検証されていないので、動いているか確かには分からない

どちらも Developers Not Writing Tests に関係する

補足

原因: Infrequently Run Tests

Symptoms

開発者があまりテストを実行していないと耳にする。質問してみると、テストの実行に時間がかかりすぎる（Slow Tests）、または無関係な失敗が多すぎる（Buggy Tests）と分かる

毎日の Integration Build でテストの失敗が見られる。掘り下げると、開発者が自分の手元でテストを実行せずにコードをコミットしていることが多いと分かる

補足

Root Cause

自動テストという安全網で作業する利点を知れば、ほとんどの開発者は、何かが邪魔しない限り続ける

最もよくある障害は、統合を遅くする Slow Tests と、テスト環境の再起動やテスト前の Manual Intervention を強いる Unrepeatable Tests（Erratic Test）

規則

Possible Solution

  • 根本原因が Unrepeatable Tests なら、Fresh Fixture 戦略に切り替えてテストをより決定的にしてみる
  • 原因が Slow Tests なら、テストの実行を速くすることにより労力をかける必要がある
補足

原因: Lost Test

Symptoms

スイートで実行されるテストの数が減った（または期待ほど増えていない）

テストの数に注意を払っていれば直接気づける。または、あるはずのテストが捕まえるべきだったバグを見つけ、調べてみるとテストが無効化されていたと分かる

補足

テストが誤ってスイートから漏れる（一度も実行されない）経路

Test Method に [test] 属性を付け忘れる、または Test Discovery の命名規約に合わない名前を使う

Test Enumeration しか支えない Test Automation Framework で、Test Method を Test Suite Object に加える suite.addTest の呼び出しを書き忘れる

手続き型言語の xUnit の変種で、Test Suite Procedure に Test Method の明示的な呼び出しを書き忘れる

スイートを Suite of Suites に加え忘れる、または Testcase Class に [Test Fixture] 属性を付け忘れる

補足

以前は実行されていたテストが無効化される経路

Test Method の名前を、Test Discovery がスイートに含めるパターンに合わないよう変える（例: "test..." で始まるメソッド名）

メソッド属性で Test Method を示す xUnit の変種で [Ignore] 属性を加える

テスト（またはスイート）を明示的にスイートに加えるコードをコメントアウト（または削除）する

補足

Root Cause: Test Method または Testcase Class が無効化された、または AllTests Suite（Named Test Suite）に一度も加えられなかったことによる

典型的には、テストが失敗していて、他のテストを実行するときに失敗をかき分けずに済むよう誰かが無効化したときに起きる。偶然起きることもある

規則

Possible Solution: Lost Tests を持ち込まない方法はいくつかある

  • 失敗する ・ 遅いテストを無効化する代わりに、Single Test Suite（Named Test Suite）で1つの Test Method だけを実行する。Test Tree Explorer（Test Runner）でスイートの中を掘り下げて1つのテストを実行することもできる。どちらも Chained Tests（意図的な Interacting Tests）があると難しくなるので、Chained Tests を避ける理由がまた1つ増える
  • xUnit の変種が支えていれば、用意された仕組みでテストを ignore する（例: NUnit の [Ignore] 属性）。通常、実行されていないテストの数を知らせるので、再有効化を忘れない。「ignore」されたテストの数が閾値を超えたらビルドを失敗させるよう CI ツールを設定することもできる
  • チェックイン後のテストの数を、統合を始める直前のブランチの数と比べ、追加したテストの数だけ増えていることを確認する
  • プログラミング言語がリフレクションを支えていれば、Test Discovery を実装または活用する
  • Integration Build で実行するテストを見つける別の戦略を使う。Ant などのビルドツールは名前のパターン（"Test" で終わるなど）に合うファイルをすべて見つけられる。これですべてのテストを拾えば、スイートごと失うことはない
補足

原因: Missing Unit Test

Symptoms: すべての単体テストは通るが、顧客テストがまだ失敗している。ある時点で顧客テストは通るようになったが、個々のクラスの振る舞いを検証する単体テストが書かれなかった。その後のコードの変更がクラスの1つの振る舞いを変え、機能を壊した

補足

Root Cause

チームが顧客テストを書くことに集中し、単体テストを使うテスト駆動開発を行わないときによく起きる。顧客テストを成功させるのに十分な機能は作ったが、その後のリファクタリングがそれを壊した。単体テストがあれば、そのコードの変更が Integration Build に入るのをおそらく防げた

テスト駆動開発の最中でも、誰かが先走って、導く失敗するテストなしにコードを書くと起きる

規則
  • Possible Solution: 陳腐な答えは「単体テストをもっと書く」だが、言うは易く行うは難く、常に効果的でもない。本当のテスト駆動開発を行うことが、テストの数を増やすためだけの不要なテストを書かずに Missing Unit Tests を避ける最善の方法
補足

原因: Untested Code

Symptoms: SUT のあるコードがどのテストにも実行されていないと、ただ「分かって」いることがある。実行されるのを確認したことがないから、またはコードカバレッジツールで疑いなく証明したから

例: getCurrentTimeAsHtmlFragment で、timeProvider が例外を投げたときに正しく処理されることを、どうテストするのか

補足

Root Cause

最もよくある原因は、SUT が、依存先のコンポーネントの特定の振る舞いに反応するコードパスを持ち、そのパスを実行する方法が見つかっていないこと。依存先は通常同期的に呼ばれ、特定の値を返すか例外を投げる。通常のテストでは、間接入力の可能な同値クラスの一部にしか実際には出会わない

もう1つのよくある原因は、SUT のインターフェースが公開する機能の特徴付けが不完全なことによる、テストスイートの不完全さ

規則

Possible Solution

  • SUT の間接入力を制御できないことが原因なら、最もよくある解決は Test Stub でさまざまな間接入力を SUT に与え、すべてのコードパスを網羅すること
  • そうでなければ、SUT を完全にテストするのに必要なさまざまな間接入力を返すよう、依存先のコンポーネントを設定するだけで足りることもある
補足

原因: Untested Requirement

Symptoms

ある機能がテストされていないと、ただ「分かって」いることがある。または、テストしようとしているソフトウェアに、公開インターフェースを経由してテストできる目に見える機能が存在しない。書いたテストはすべて通る

補足

テスト駆動開発では、要件を処理するコードを加える必要があると分かっていても、動作をログに記録するコードの必要性を Fully Automated Test で表す方法が見つからない

例: testRemoveFlight は、便を削除した後に便が存在しないことだけを検証し、正しいログ動作を検証しない。ログが正しく実装されていてもいなくても通る

検証対象のコードでは、removeFlight が logMessage("CreateFlight", flightNumber) と誤ったログを出している（「Bug!」）。これは SUT の間接出力で、正しく実装されていない

補足

本番でアプリケーションを保守するときに logMessage が記録する情報に頼るつもりなら、それが正しいとどう保証するのか。この機能の自動テストがあるのが明らかに望ましい

補足

Impact

SUT に求められる振る舞いの一部が、どのテストも失敗させずに誤って無効化されうる

バグのあるソフトウェアが顧客に納品されうる

バグを入れる恐れが、容赦ないリファクタリングや不要（死んでいる）と疑われるコードの削除を妨げうる

補足

Root Cause

最もよくある原因は、SUT が公開インターフェースを経由して観察できない振る舞いを持つこと。テストが直接観察できない期待される「副作用」（ファイルやレコードの書き出し、別のオブジェクトやコンポーネントのメソッドの呼び出しなど）を持つことがある。こうした副作用を間接出力と呼ぶ

SUT がアプリケーション全体の場合、目に見える振る舞いのすべての面を検証する完全な顧客テストのスイートが無いことによることもある

規則

Possible Solution

  • 顧客テストが欠けていることが問題なら、すべてのコンポーネントが正しく統合されていることを確認するのに少なくとも十分な顧客テストを書く。プレゼンテーション層をビジネスロジック層から分けて、アプリケーションのテスト容易性の設計を改善する必要があるかもしれない
  • 検証する必要がある間接出力があるときは、Mock Object を使って Behavior Verification を行う。間接出力のテストは「Using Test Doubles」の章が解説する
補足

原因: Neverfail Test

Symptoms: ある機能が動いていないと、ただ「分かって」いるのに、その機能のテストは通っている。テスト駆動開発で、まだ書いていない機能のテストを加えたのに、失敗させられない

Impact: 機能を実装するコードが存在しなくても失敗しないテストは、Defect Localization にどれほど役立つのか（ほとんど役立たない）

補足

Root Cause

assertEquals(aVariable, true) の代わりに assertTrue(aVariable, true) と書くような、不適切に書かれたアサーション

より悪質な原因: 非同期のテストでは、別のスレッドやプロセスで投げられた失敗が Test Runner に見えない ・ 報告されないことがある

規則
  • Possible Solution: 非同期のテストが確実に失敗するよう、スレッドをまたぐ失敗検出の仕組みを実装できる。だが、よりよい解決は、Humble Executable（Humble Object）を支えるようコードをリファクタリングすること
補足

原典が誤り ・ 注意として明示しているもの。

アンチパターン

誤り起きること
テストメソッドの中に制御構造を置く「Any control structures within a Test Method should be viewed with extreme suspicion!」（Conditional Test Logic）
テストを完全に決定的でなくするもの全般「Anything that makes the tests less than completely deterministic is a bad idea!」（Erratic Test ・ Nondeterministic Test）
テストの実行順序に依存するほとんどの xUnit は順序を保証しない（Erratic Test ・ Interacting Tests）
SUT や Test Automation Framework で static 変数を使う、SUT で Singleton ・ Registry を使うInteracting Tests を生む（Erratic Test）
オブジェクトを文字列に変換して期待する文字列と比べる「just plain wrong」（Fragile Test ・ Sensitive Equality）
Slow Tests への反応としてすぐ Shared Fixture に向かうほぼ常に Erratic Tests などを生む（Slow Tests）
「バーを緑に保つ」ために失敗するテストを外す ・ 無効化するLost Test になる（Erratic Test ・ Production Bugs）
テストの自動化で手動テストと同じく多くのテスト条件を1つのテストにつなげるEager Test（Obscure Test ・ Assertion Roulette）
テストの数を目標にするテストを分けたり複製したりするだけでカバレッジを上げずに達成できる（Developers Not Writing Tests）
本番コードにテストのための分岐 ・ メソッド ・ 依存 ・ equals を入れるTest Hook ・ For Tests Only ・ Test Dependency in Production ・ Equality Pollution（Test Logic in Production）
プロジェクト単位の原因（学ぶ ・ レガシーコードをリファクタリングする ・ テストを先に書く時間の不足）に対処しない問題は近いうちに再発する（Buggy Tests）
