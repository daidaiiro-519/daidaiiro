テスト駆動開発（Canon TDD）

概要

テスト駆動開発（TDD）の定義を、手順の形で示す。何がTDDで、何がTDDでないかを区別し、各手順で起きやすい誤りを挙げる。

この基準が答える判断

  • Canon TDD（Kent Beck、2023）

概要

補足

使う原典

「Canon TDD」（Kent Beck、2023年12月11日、Software Design: Tidy First?）── 全文を扱った

Canon TDD（Kent Beck、2023）

補足

冒頭の断り書きと5つの手順

以下は「TDDをこうすべきだ」という指示ではない。自分の仕事の品質には、どんな方法でもよいので、実際に責任を持つこと

以下は「TDDはダメだ、なぜなら<TDDでない何か>だから」という批判への応答である。よくある例は「コードを書く前にテストを全部書くのが嫌だから」

補足

If you're going to critique something, critique the actual thing.

規則
  • 批判するなら、実物を批判すること
手順

5つの手順

  1. カバーしたいテストシナリオのリストを書く

  2. リストの項目をちょうど1つ、実際に動く具体的なテストにする

  3. コードを変更して、そのテスト（とそれまでのすべてのテスト）を通す（途中で見つけた項目はリストに足す）

  4. 任意でリファクタリングして、実装の設計を改善する

  5. リストが空になるまで、2へ戻る

図
補足

Intro（導入）

最近TDDについて説明し直すなかで、TDDの定義について人々の意見が一致していないことに驚いた。著書ではできるだけ明確にしたつもりだったが、そうではなかった

以下の流れと違うことをしていて、それがうまくいっているなら結構。それは Canon TDD ではないが、構わない。手順どおりに従っても褒美は無い

TDDを批判するつもりで、以下の流れを批判していないなら、それはわら人形を批判している。この記事の目的は、わら人形を先回りして防ぐことである

プログラミングの方法を指示しているのではない

この記事は簡潔で否定的な書き方になる（「人はここを間違える。実物はこうだ」）。他人の流れを批判する意図ではなく、Canon TDD の理解を研ぎ澄ますためである

補足

Overview（全体像）

Test-driven development is a programming workflow.

定義

TDD

プログラミングの作業の流れである

補足

プログラマーは、システム（今は空かもしれない）の振る舞いを変える必要がある

補足

TDDは、プログラマーが次の状態のシステムを作るのを助けることを意図している

以前動いていたものが、すべてまだ動く

新しい振る舞いが、期待どおりに動く

システムが次の変更に備えている

プログラマーと同僚が、上の3点に自信を持てる

表

Interface/Implementation Split（インターフェースと実装の分離）

最初の誤解は、設計をすべて一緒くたにすることである。設計には2種類ある

種類内容
インターフェースある振る舞いがどう呼び出されるか
実装システムがその振る舞いをどう実現するか
補足

著者の学生時代には、これを論理設計と物理設計と呼び、決して混ぜるなと教わったが、どうすればよいかは誰も説明しなかった

補足

The Steps（手順）

人間は下手なコンピュータである。以下はプログラムのように見えるが、プログラムではない。プログラムに慣れた人に効果的に伝えるための書き方である

規則

1. Test List（テストリスト）

  • システムと望む振る舞いの変更が与えられたら、最初に、新しい振る舞いの期待される変種をすべて列挙する
  • 振る舞いの変更が既存の振る舞いを壊すべきでない点を思いついたら、それもリストに入れる
補足

例：「基本のケースがあって、このサービスがタイムアウトしたら、キーがまだデータベースに無かったら……」

これは分析だが、振る舞いの分析である。振る舞いの変更が機能すべきさまざまなケースを考える

誤り：実装設計の判断を混ぜる。 内部をどうするかを決める時間は後でたっぷりある。リストを作ることだけに集中したほうが、よいリストになる（実装のスケッチが必要ならナプキンに描いてもよいが、本当は要らないかもしれない。試してみること）

著書のこの手順は見落とされているようだ。「TDDはいきなりコーディングに入る。いつ終わるのか分からない」── そうではない

規則

2. Write a Test（テストを書く）

  • テストは1つ。セットアップ・呼び出し・アサーションを持つ、本当に自動化されたテスト
  • 助言：アサーションから逆向きに書いてみるとよい
補足

このテストを書くなかで設計の判断を始めるが、それは主にインターフェースの判断である。実装の判断が漏れ出ることもあるが、次第に避けられるようになる

補足

誤り：コードカバレッジを得るためだけに、アサーションの無いテストを書く

補足

誤り：テストリストの項目をすべて具体的なテストに変換してから、1つずつ通す

最初のテストを通したことで、その推測で書いたテストすべてに影響する判断を見直すことになったら → 手戻り

テスト#6まで来て、まだ1つも通っていなかったら → 落胆や退屈

補足

次のテストを選ぶのは重要な技能で、経験によってしか身につかない。テストの順序は、プログラミングの体験と最終結果の両方に大きく影響しうる（未解決の問い：コードは初期条件に敏感か）

規則

3. Make it Pass（通す）

  • 失敗するテストができたら、システムを変更してテストを通す
  • レッドからグリーンへ進む途中で新しいテストが必要だと分かったら、テストリストに足す
  • テストが通ったら、リストから消す
補足

誤り：アサーションを消して、通ったふりをさせる。 本当に通すこと

誤り：実際に計算された値をコピーして、テストの期待値に貼り付ける。 これは二重チェックを無効にする。TDDの検証の価値の多くは二重チェックから生まれる

誤り：テストを通すことにリファクタリングを混ぜる。 「2つの帽子をかぶる」問題。まず動かし、それから正しくする

規則

そのテストが既にした作業を無効にする場合（「空のフォルダの場合を扱う方法が無い」）は、押し進めるか、やり直すかを決める

  • 助言：やり直す。ただし、テストを実装する順序を変える
規則

4. Optionally Refactor（任意でリファクタリング）

  • ここで初めて実装の設計判断をする
補足

誤り：この回に必要な範囲を超えてリファクタリングする。 片付けるのは気持ちがよい。次のテスト、特に通し方が分からないテストに向き合うのは怖いこともある

補足

誤り：早すぎる抽象化。

Duplication is a hint, not a command.

重複は手がかりであって、命令ではない

規則

5. Until the Test List is Empty, Go To 2.（テストリストが空になるまで2へ）

  • コードの振る舞いに対する恐れが退屈に変わるまで、テストとコーディングを続ける
補足

History（経緯）

著者がTDDを「再発見」した時期について

SUnit を書いたのは1994年（コンサルティングの顧客のため）なので、それより前ではない

1995年10月、オースティンの OOPSLA で Ward Cunningham に TDD を実演したので、それより後ではない

当時の刊行物での言及は見つからない

補足

『TDD By Example』の執筆を長く止めていたので先を越されるのを心配したが、結局うまくいった

表

アンチパターン

原典が「Mistake」として挙げているもの。

手順誤り
1. テストリスト実装設計の判断を混ぜる
2. テストを書くカバレッジのためだけに、アサーションの無いテストを書く
2. テストを書くリストの項目をすべてテストにしてから、1つずつ通す
3. 通すアサーションを消して、通ったふりをさせる
3. 通す計算された実際の値を、期待値へコピーする（二重チェックの無効化）
3. 通すテストを通すことにリファクタリングを混ぜる
4. リファクタリングこの回に必要な範囲を超えてリファクタリングする
4. リファクタリング早すぎる抽象化
補足

あわせて、原典は「コードを書く前にテストを全部書く」ことを TDD と取り違えた批判を、TDD の批判ではないとしている
