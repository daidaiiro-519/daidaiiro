schema-driven が名前を引く場所を assets にする

決めたこと

エンジンは、インスタンスの $schema に書いたスキーマの名前（「<Skill の名前>/<種類>@<版>」）を、--skill の Skill の assets/ の下で $id が同じスキーマから引く。

なぜ決める必要があるか

スキーマの名前は、ボード skill-roles の Q7 で決めた「<Skill の名前>/<種類>@<版>」の形の文字列で、スキーマの $id に書き、インスタンスは $schema に同じ名前を書いて指す。エンジンは、その名前と $id が同じスキーマのファイルを Skill のフォルダから探す。Agent Skills の仕様（agentskills.io/specification、2026-10-10 取得）は、Skill のフォルダを、中のファイルを誰がどう使うかで分けている。references/ は「Contains additional documentation that agents can read when needed」で、AI エージェントが必要なときに読む文書の置き場所である（:227）。仕様は続けて「Agents load these on demand, so smaller files mean less use of context.」と書き、ここに置いたものは AI の文脈に読み込まれる（:233）。assets/ は「Contains static resources」で、その例に「Data files (lookup tables, schemas)」とスキーマを名指ししている（:237、:241）。エンジンが名前で引くスキーマは、AI が読む文書ではなく、エンジンがインスタンスを検査するためのデータである。だから assets/ に当たり、ボード skills-creator-rebuild の論点2でもここに置くと決めた。ところがエンジンは references/ から名前を引くので、新しい skills-creator の型のスキーマを名前で引けない。いま Skill の名前で引いているインスタンスはリポジトリに無いので、移す期間を設けずに引く場所を替える。

どう変わるか

変更前と変更後

何が変更前変更後
エンジンが、インスタンスの $schema の名前（例 glossary-keeper/term@v1）と $id が同じスキーマを探す場所--skill の Skill の references/ の下の *.schema.json--skill の Skill の assets/ の下の *.schema.json
references/ に置いたスキーマ$schema の名前で引ける$schema の名前では引けない。見つからないと返し、assets/ を探したことを書く

比較した案と、採らなかった理由

案採らなかった理由
references/ のまま引き、スキーマを references/ に置く仕様の references/ は AI エージェントが必要なときに読む文書の置き場所で、置いたものは AI の文脈に読み込まれる。仕様は references/ の例に「FORMS.md - Form templates or structured data formats」も挙げるが、これは AI が読む Markdown の文書であり、エンジンが検査に使うスキーマの例は assets/ の「Data files (lookup tables, schemas)」である
references/ と assets/ の両方から引く名前で引くインスタンスがまだ無いので、両方を読む期間は何も守らない。両方を読むと、同じ名前が2か所に置かれる形を許すことになる

name: schema-driven
description: AI が扱うデータを、Markdown ではなく JSON Schema とそのインスタンスで持つときに使う基盤の Skill。abstract スキーマ（版ごとに振る舞いを保証する契約）とエンジンを持つ。Skill ・ Agent は、abstract に従う concrete スキーマ ・ インスタンス ・ ページテンプレート ・ 固有のツールの宣言だけを持ち、エンジンの共通ツールで作成 ・ 取得 ・ 更新 ・ 検査 ・ 承認 ・ 描画する。
version: 0.1.0

構造化データを正本として持つ基盤の Skill：schema-driven

目的

AI が扱うデータを、JSON Schema とそのインスタンスで持つときに使う。Markdown の文書は、書いたものが形を満たしているかを機械で確かめられない。スキーマとインスタンスなら、書いたその場で検証でき、参照と導出値も検査できる。

この Skill は基盤である。何のデータを持つかは決めない。

誰が何を持つか
基盤（この Skill）abstract スキーマ（references/ の契約）と、それを版ごとに守るエンジン（共通ツール9つ）と、版ごとの試験データ
使う側（基盤の上に作る Skill ・ Agent）concrete スキーマ ・ インスタンス ・ ページテンプレート ・ 固有のツールの宣言（tools.json、任意）

使う側はコードを持たない。 見た目と操作は基盤の部品のカタログが持ち、固有の処理は宣言した別の実行ファイルが持つ。abstract スキーマを書き換えると、エンジンが扱えなくなる。

役割

- concrete スキーマが abstract スキーマの版に従っているかを検査する
- スキーマからインスタンスを作成し、未記入のプロパティと、その x-prompt を返す
- JMESPath 式で値を取得し、JSON Patch で更新する。更新は、検証エラーが無いときだけ書く
- ディレクトリのインスタンスを検証し、x-ref（参照）と x-derive（導出値）を検査する
- 検査を通ったインスタンスのパスとハッシュ値を、承認記録へ書く
- 検証を通ったインスタンスを、ページテンプレートと部品のカタログでページへ描画する
- 使う側が宣言したツールを、決められた境界の中で起動する

処理対象と成果物

処理対象

concrete スキーマと、それに従うインスタンスのディレクトリ。スキーマは x-abstract に従う abstract の版を、$id に自分の名前を書く。インスタンスは $schema に、そのスキーマの名前を書く。

成果物

成果物どこに書くか
インスタンス渡したパス
検証と検査の結果標準出力（JSON）
承認記録検査したディレクトリの approval.json
ページ渡した出力のディレクトリ（インスタンス1件につき HTML 1枚）

入力の想定

受け取る情報解釈・既定値
スキーマ ・ インスタンス ・ ディレクトリのパス明示されなければ受け付けない。相対パスは、CLI を起動した場所から解決する
ページテンプレートのディレクトリ（render の --pages）明示されなければ、kind が document のインスタンスだけを描画できる
読んだ時点のハッシュ値（update の --hash）明示されなければ、update が読んだ時点のハッシュ値で書く。ほかの更新と重なりうるときは渡す
Skill のフォルダ（--skill）明示されなければ、共通ツールだけを出し、スキーマの名前はエンジンが持つものだけを引く。渡すと、そのフォルダの tools.json で宣言したツールも出し、その Skill のスキーマを名前で引く

実行手順

ツールは、CLI と MCP の両方から、同じ名前と引数で呼べる。起動のしかたは tool.json と mcp.json が持つ。一覧は次で取れる。

schema-driven --json

Step 1: concrete スキーマを書き、abstract に従っているかを検査する

スキーマの根に、次の3つを書く。書き方の決まりは references/meta-schema.json が持つ。

欄書くもの
$schemaJSON Schema の標準の dialect https://json-schema.org/draft/2020-12/schema
x-abstract従う abstract の版 schema-driven/abstract@v1
$idこのスキーマの名前「<Skill の名前>/<種類>@<版>」。インスタンスを作るスキーマ（x-generates を持つもの）は必ず書く

プロパティごとに description と x-prompt（read と write）を書き、参照には x-ref、導出値には x-derive を付ける（references/annotations.schema.json）。

ほかのスキーマの定義を使うときは、$ref をファイル名ではなく名前で書く。同じ Skill のスキーマなら、$id を基準に JSON Schema の規則で解けるので、「<種類>@<版>」だけでよい（例：term@v1#/$defs/short）。ファイル名を変えても、参照は切れない。

schema-driven check-schemas --dir <スキーマのディレクトリ>

findings が空なら、契約に従っている。版を書いていないスキーマと、エンジンが扱わない版のスキーマは、検査せずに指摘する。

スキーマのフォルダに公開の記録 published.json（references/published.schema.json）があれば、check-schemas は公開した版の指紋といまの中身を比べる。

状態check-schemas の返し方
公開した版の中身が変わったfindings に「公開した版が書き換えられている」
公開した版が消えたfindings に「公開した版が無い」
まだ記録に無い名前unpublished に名前と指紋。公開するときに、そのまま記録へ足す

指紋は、キーの順と空白に左右されない SHA-256 である。名前（$id）を持つ JSON は、ファイル名が .schema.json で終わらなくても対象になる。

Step 2: インスタンスを作成し、x-prompt を読む

schema-driven create --schema <スキーマ> --path <インスタンス>
schema-driven prompt --schema <スキーマ> --property /<プロパティ>

create は、必須のプロパティを空のままにしてインスタンスを作り、未記入のプロパティを x-prompt と一緒に返す。インスタンスの $schema には、スキーマの名前を書く。x-prompt の write の決まりに従って値を決める。

インスタンスを読むツールは、$schema の名前から次の順にスキーマを引く。

名前引く先
schema-driven/…エンジンが持つスキーマ（文書 ・ ページテンプレート ・ カタログ ・ 宣言など）。--skill を渡さなくても引ける
--skill の Skill の名前で始まるものその Skill の assets の下の *.schema.json のうち、$id が同じもの
ほかの Skill の名前で始まるものどの Skill のスキーマかを返して止める。その Skill を --skill に渡して検査し直す
名前の形でない値インスタンスのファイルからの相対パス。名前で指す形にする前に、承認時のスキーマの写しを指していた記録のため

同じ名前のスキーマが2つあれば、どちらも使わずに止める。

Step 3: JSON Patch で更新する

schema-driven update --path <インスタンス> --patch '<JSON Patch>' [--hash <読んだ時点のハッシュ値>]

未記入以外の検証エラーがあれば、書かずに errors を返す。直して、もう一度送る。未記入が残っているときは書いて、残りを x-prompt と一緒に返す。

値を読むときは get を使う。

schema-driven get --path <インスタンス> --query '<JMESPath 式>'

Step 4: ディレクトリを検査する

schema-driven check --dir <インスタンスのディレクトリ>

終了コード 0 は、検査を最後まで実行できたことだけを示す。 合格かどうかは、instances の errors と unfilled、findings の status（合格 ・ ずれ ・ 確かめ直し など）で見る。

Step 5: ページテンプレートを書き、描画する

ページテンプレートは、節の並びと、節ごとに置く部品と、値を取る JMESPath 式だけを書いた JSON である（references/page.schema.json）。部品は、部品のカタログ（references/catalog.schema.json）の名前で呼ぶ。HTML ・ CSS ・ JS は書かない。

schema-driven render --dir <インスタンスのディレクトリ> --out <出力> [--pages <ページテンプレートのディレクトリ>]
インスタンスの kind描画のしかた
document基盤の文書の契約（references/document.schema.json）を、カタログの部品 document で描く
そのほかの種類その種類のページテンプレート（--pages）が並べた部品で描く
ページテンプレートが無い種類1ページも書かずに失敗する

カタログに無い部品や、部品の入力の欠けがあれば、1ページも書かずに失敗する。検証エラーが1件でもあれば描画しない。内容が変わったページだけを書くので、同じ入力から何度描画しても結果は変わらない。

インスタンスの値は、HTML を含んでいても文字として出る。別の文書をその見た目のまま見せるときは部品 embed を使い、script の動かない枠に入れる。

Step 6: 承認を記録する

schema-driven approve --dir <インスタンスのディレクトリ>

検証エラー ・ ずれ ・ 未記入が1件でもあれば、承認記録を書かない。

Step 7: 固有のツールを宣言する

共通ツールで足りない処理だけを、Skill のフォルダの tools.json（references/tools.schema.json）で宣言する。宣言する前に、x-derive ・ x-view ・ ページテンプレートで書けないかを確かめる。

schema-driven --skill <Skill のフォルダ> --json
schema-driven --skill <Skill のフォルダ> <ツールの名前> --<引数> <値>

宣言したツールは、Skill のフォルダの中の別の実行ファイルである。言語は問わない。エンジンは次の境界を守って起動する。

境界決まり
起動の前実行ファイルの SHA-256 が宣言と合うこと。パスは Skill のフォルダの中の相対パスだけで、シェルを通さない
渡すもの標準入力に {"tool": …, "args": {…}} の JSON。環境変数は宣言した名前だけ
受け取るもの標準出力に、真偽の ok を持つ JSON を1つ。1 MiB まで
制限時間既定 30 秒、宣言で 300 秒まで。超えたら止めて失敗にする
終了コード0 ・ 1 ・ 2 だけ。それ以外は失敗にする

宣言したツールの中身が正しいかは、基盤は保証しない。使う側が自分の試験で確かめる。

Step 8: 既存の Skill を基盤の上へ移すとき、段階の順に作業する

自前の実装を持つ Skill を基盤の上へ移すことは、1つの目的である。決定の記録は1件にし、承認を受けたら、その記録と適用の差分を1つのコミットに入れる。 作業は次の段階の順に進め、段階ごとに「確かめること」を通してから次へ進む。

段階すること確かめること
1concrete スキーマを、abstract の版に従う形で書くcheck-schemas の指摘が0件。見本のインスタンスで、通すものと断るものの両方を確かめる
2ページテンプレートを、カタログの部品で書き、render で描画するいまの画面と並べて描画し、目で見比べる。カタログに無い部品が必要なら、基盤のカタログに足すことを先に決める
3固有の処理を tools.json で宣言し、古い実装を消し、SKILL.md を書き直す--skill を渡したツールの一覧に、共通ツールと宣言したツールが並ぶ。古い形のインスタンスが残るなら、新しいツールでその状態を変えて描画できる

既存のインスタンスは、性質で扱いを分ける。

インスタンス扱い
書き換えてよいもの移行のツールで新しい形へ写す。古いファイルは残さない。戻すときは、写す前のコミットから取り出す
承認時点の姿を保持するもの写さない。古い形のスキーマを残し、新しいスキーマは根の kind の有無で古いものと区別する。新しいツールは古い形も読み、状態の変更と描画を受け持つ

出力形式

どのツールも、標準出力へ JSON を1つ書く。

終了コード意味出力
0実行できた{"ok": true, …}。中身はツールごとに違う
1拒否した ・ 失敗した{"ok": false, "reason": …, "detail": …, "errors": […]}
2使い方が違う{"ok": false, "reason": "使い方が違う", "detail": …, "tools": […]}

動詞なしの --json だけは、ツールの一覧を {"ok": true, "findings": [], "data": {"tools": […], "skill_root": …}} で返す。

ガードレール

- abstract スキーマを、使う側で書き換えない。エンジンは、版ごとの abstract スキーマに対する振る舞いだけを保証する
- 公開した版のスキーマを、消さず書き換えない。中身を変えるときは、版を上げた新しい名前（@v2）で足す。同じ名前で中身が変わると、前に書いたインスタンスが別のスキーマで検査される。公開するときは、その版の指紋を published.json に記録し、配る前の検査で確かめる
- インスタンスの $schema に、Skill の置き場所へのパスを書かない。名前で指す。配った先では、Skill は別の場所に置かれる
- ファイルを手で書き換えて、update を通さずにインスタンスを直さない。update を通さないと、書いたその場の検証が行われない。手で直したときは、check で確かめ直す
- check の終了コードだけで合格と判断しない。0 は実行できたことだけを示す
- 検証エラーのあるインスタンスを、描画や承認で先へ進めない。基盤はどちらも止める
- ページの見た目と操作を、使う側で持たない。足りない部品は基盤のカタログに足す。同じ働きの部品が Skill ごとに違う形になると、読み手はページを替えるたびに見方を覚え直す
- 部品のカタログは、デザインシステムに従う。トークン（基礎 → 意味 → 部品の3層と明暗）と、部品ごとの状態（通常 ・ 押した ・ 焦点 ・ 無効 など）の決まりを持ち、CSS に色の直値を書かない
- 使う側の種類を、基盤の文書の契約へ押し込まない。決まった並びがあるものは、使う側がスキーマとページテンプレートを持つ
- 公開した版の試験データを書き換えない。足すだけにする。書き換えると、古い版の振る舞いが変わっても試験が検出しない
- 移しているあいだ、古い実装が読むスキーマのファイルを書き換えない。新しいスキーマは別のファイルにする ── 書き換えると、移し終わるまで古い実装でインスタンスを作れなくなる
- 同じ目的の変更を、段階ごとの記録に分けない。承認する側が、1つの目的を何度にも分けて判断することになる
- 基盤の中心は、ファイルを直接扱わない。入出力はポートを通す。どう禁じるかは references/implementation.json が持つ
- 基盤はネットワークに出ない。依存の版は1か所で決める
