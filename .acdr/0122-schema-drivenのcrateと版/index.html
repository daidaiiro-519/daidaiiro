schema-driven の crate と版

決めたこと

schema-driven は各 crate の最新の版を使い、ネットワークに出る機能を外し、版を正本の Cargo.lock の1か所で決める

なぜ決める必要があるか

crates.io の原文を 2026-10-05 に取得し、版とライセンスと既定の features を原文の文字列で照合した（ボード schema-driven-build の sources/）。いまの Skill は jsonschema 0.34 ・ rmcp 0.9 ・ sha2 0.10 を使うが、Skill ごとに workspace が分かれているので、そろえても共有されるものが無い。platform-advisor の判断基準は、依存を最新のパッチを当てた版に保つことと、見直すきっかけを決めることを求める。schema-driven は手元のファイルだけを扱うので、ネットワークに出る機能は使わない。転写した複製が正本と同じ版で動くように、版を決める場所を1か所にする。決めた過程はボード schema-driven-build の論点2にある

どう変わるか

変更前と変更後

何が変更前変更後
版Skill ごとに決める（jsonschema 0.34 ・ rmcp 0.9 ・ sha2 0.10）serde_json 1.0.151 ・ jsonschema 0.58.5 ・ jmespath 0.5.0 ・ json-patch 4.2.0 ・ sha2 0.11.0 ・ rmcp 3.5.0 ・ tokio 1.53.2
ネットワークに出る機能既定の features のままjsonschema ・ rmcp は default-features = false。tokio に net を入れない。CI の cargo tree の検査と、通信を断ったテストで確かめる
複製の版決めていない正本の Cargo.lock ごと写し、複製の側では cargo update をしない。差分の検査に lock のハッシュ値を含める

比較した案と、採らなかった理由

案採らなかった理由
いまの Skill と同じ版にそろえるSkill ごとに workspace が分かれているので、そろえても得るものが無い。古い版を残す費用が増える
JMESPath をやめて JSONPath（RFC 9535）の crate にする基盤の論点1の決定を変えることになり、その crate の保守が太いという材料も無い

対象の文書に変更が無い決定である ── 差分は出ない。
