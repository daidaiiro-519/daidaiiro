schema-driven のコーディング規則を CODING.md に置く

決めたこと

schema-driven のコードは、src/schema-driven/CODING.md に書いたアーキテクチャ ・ crate とフォルダ ・ trait ・ テスト ・ 検査の順の規則に従う。

なぜ決める必要があるか

schema-driven のコードには、ヘキサゴナルで作るという大枠（ボード schema-driven-build の論点1）しか無かった。規則を書く場所は、コーディングの Skill の形として先送りしていた。その Skill は無く、実装の決まりを書いた implementation.json も ACDR 0169 で消した。規則が無いまま別々の時期に作った結果、受け口と起動時の結合が2か所に分かれ、入ってくる側が出ていく側を直に呼び、テストの中に実装（5,500行のうち MCP のクライアントや cargo build）が入った。利用者は、コーディングの Skill より先に、CODING.md だけを作って schema-driven の規則を書き、型（スキーマ）は後で定義して移す、と決めた。CODING.md を置いたフォルダより下がそれに従い、近いものが優先する。AGENTS.md と同じ決まり方である。規則の中身は、原文と照合した原典（The Rust Programming Language ・ The Cargo Book ・ Rust API Guidelines）から書いた。ddd-advisor と qa-advisor の回答も使った。どの規則も、なぜ（守らないと何が起きるか）と、機械で見る検査を持つ。

比較した案と、採らなかった理由

案採らなかった理由
コーディングの Skill と規則の型（スキーマ）を先に作るSkill は基盤（schema-driven）の上に作るので、基盤が規則に従っていない間は作れない。型は後から定義して、CODING.md の中身を移せばよい
言語ごとの規則（Rust の書き方）にする規則は作るもののアーキテクチャと技術スタックで決まり、言語では決まらない。同じ Rust でも、基盤と使い捨ての変換では規則が違う
層ごとに crate を分ける（domain ・ application ・ 各アダプタ）ヘキサゴナルが求めるのは論理的な境界で、層を物理的に分ける理由にならない（ddd-advisor の回答、layered-architecture）。crate は依存の向きを Cargo で強制できる core と adapters の2つで足りる
取り込みの crate（files）を残す業務の知識（スキーマ）と表示の部品（カタログ）を1つの crate に混ぜ、core がそれに頼る。取り込みは、使う層の crate の build.rs が持つ。フォルダから一覧を作って名前で引く仕組み（ACDR 0171）はそのまま移す
MCP を起動して確かめるとき、JSON-RPC を手で書いたクライアントを使い続けるテストの中にプロトコルの実装を持つことになる。rmcp 3.5.0 は client と transport-child-process の feature を持つ（取得していない依存 tokio-stream と process-wrap を、規則に従わせる作業のときに取得する）

schema-driven のコーディング規則

このファイルを置いたフォルダ（src/schema-driven/）より下のコードは、この規則に従う。下のフォルダに別の CODING.md があれば、近いほうに従う。

規則の1件は、なぜ（守らないと何が起きるか） と 検査（機械で見る方法） を持つ。どちらも書けない規則は置かない。

アーキテクチャ

ポートとアダプタ（ヘキサゴナル）で作る。中心は domain と application で、外側との境界は port の trait である。

層持つもの依存してよい先
domain業務の規則（スキーマの契約 ・ 検証 ・ 参照 ・ 導出値 ・ 公開の記録 ・ デザインシステムの検査）無し
applicationユースケース（作る ・ 取る ・ 更新する ・ 消す ・ 検査する ・ 承認する ・ 描画する ・ 宣言したツールを起動する）domain ・ port
port出ていく側の trait。application が定義し、adapters が実装するdomain
inbound adapterCLI と MCP の受け口と、ツールの一覧と振り分けapplication
outbound adapterport の実装（ファイル ・ JMESPath ・ 部品のカタログ ・ 別の実行ファイルの起動）port ・ domain
起動時の結合outbound adapter を application へ渡し、受け口に渡すadapters の中のすべて
規則なぜ検査
port と呼ぶのは、application が定義して adapters が実装する、出ていく側の trait だけにするcore が自分で実装する trait まで port と呼ぶと、どれが外との境界なのかがコードから読めなくなるcore の中に、port の trait への impl … for が0件
application が自分で実装するものは trait にせず、型と関数として公開する。差し替える実装が2つ以上あるときだけ trait にする実装が1つしかない trait は、読む人に「差し替えがある」と思わせ、呼び出しを追う手間だけが増えるcore の中で定義と実装が core にある trait が0件
業務の規則は domain と application に置く。宣言したツールの SHA-256 の照合 ・ 制限時間 ・ 出力の形の確認も application が持ち、起動そのものだけを port の向こうに置く同じ判定がアダプタにもあると、片方だけ直したときに CLI と MCP で結果が食い違う。判定がアダプタにあると、代役を渡して単体テストで確かめられないadapters の中に、同じ規則の判定（SHA-256 の比較 ・ 時間の上限）が0件
inbound adapter は application だけを呼ぶ。outbound adapter を直に呼ばない受け口が出ていく側を直に呼ぶと、業務の規則（SHA-256 の照合など）が application を通らなくなるadapters/src/inbound/ に outbound:: が0件
起動時の結合は、adapters の1か所（compose）に置く。CLI と MCP の実行ファイルは、それを呼ぶ結合が2か所にあると、片方だけ直したときに CLI と MCP で振る舞いが食い違う結合を書いた関数が1つだけ
domain と application は、ファイル ・ 通信 ・ 時刻に直接触らない中心が入出力に触ると、入出力の代役を渡して単体テストで確かめられなくなるcrates/core/clippy.toml が std::fs ・ std::net ・ std::process ・ std::time::SystemTime を禁じ、clippy が0件

crate とフォルダ

The Rust Programming Language 11.3 は「Rust projects that provide a binary have a straightforward src/main.rs file that calls logic that lives in the src/lib.rs file」と書く。The Cargo Book（Workspaces）は、メンバーを crates/ の平らなフォルダに置くことを勧める。

src/schema-driven/
  Cargo.toml          ワークスペース（メンバーは crates/*）
  Cargo.lock          依存の版の1か所
  CODING.md           この規則
  crates/
    core/             domain ・ application ・ port（ライブラリ）
      schemas/        基盤のスキーマ。build.rs が取り込み、名前（$id）で引く
      build.rs
      clippy.toml
      src/
        lib.rs
        domain/
        application/
        ports.rs
    adapters/         inbound ・ outbound ・ 起動時の結合（ライブラリ）と実行ファイル
      catalog/        部品のカタログ。build.rs が取り込み、ファイル名で引く
      build.rs
      src/
        lib.rs
        compose.rs
        inbound/      tools.rs ・ cli.rs ・ mcp.rs
        outbound/     fs.rs ・ jmespath.rs ・ catalog.rs ・ process.rs
        bin/          schema-driven.rs ・ schema-driven-mcp.rs
      tests/          結合テストと、少数の端から端までのテスト
        support/      テストの補助（作業用のフォルダ ・ 値の表を回す関数）
    probe/            宣言したツールの境界を試す見本の実行ファイルと、その試験（配らない）
規則なぜ検査
crate は core と adapters の2つと、配らない probe だけにする。層ごとに crate を分けない層ごとに crate を分けても、守りたい依存の向きは core と adapters の境界で Cargo が強制できる。crate が増えると、同じ設定と依存の宣言を何か所にも書くことになるワークスペースのメンバーが3つ
実行ファイル（src/bin/）は、compose と受け口を呼ぶだけにする。impl も分岐も書かない実行ファイルに処理を書くと、結合テストから呼べず（The Book 11.3 :237）、CLI と MCP で同じ処理を2回書くことになるsrc/bin/ に impl ・ match ・ if が0件
取り込むファイルは、それを使う層の crate が持つ。スキーマは core、カタログは adapters。build.rs がフォルダから一覧を作り、コードはファイルの場所を書かないファイルの場所を相対パスで書くと、ソースのファイルを動かしただけで壊れる。使わない層の crate が持つと、core が表示の部品まで抱えることになるinclude_str! と include_bytes! が build.rs の出力の外に0件。../ を含む文字列のパスが0件
core は、adapters ・ rmcp ・ tokio ・ jmespath に依存しないcore が外の技術に依存すると、その技術を替えるときに業務の規則まで直すことになるcargo tree -p schema-driven-core にそれらが現れない
配る crate は probe とテストの補助に依存しない配る実行ファイルに、テストのためのものが入るcore と adapters の [dependencies] に probe が無い

trait とジェネリクス

Rust API Guidelines（flexibility）は「When designing a trait, decide early on whether the trait will be used as an object or as a bound on generics.」と書く。The Rust Programming Language 18.2 は、型の集まりが同じならジェネリクスと trait の境界を、利用者が型を足せるようにしたいなら trait object を勧める。

規則なぜ検査
port の trait は、定義するときに、ジェネリクスの境界として使うか dyn で使うかを決め、doc コメントの1行目に書く後から dyn とジェネリクスを混ぜて使うと、同じ trait の呼び方が場所によって変わり、読み手が毎回確かめることになるport の trait の doc コメントに「ジェネリクスで使う」か「dyn で使う」がある
1つの実行ファイルの中で実装が1つに決まる port（ファイル ・ スキーマの読み込み ・ JMESPath ・ 別の実行ファイルの起動）は、ジェネリクスの境界で使う実装が1つに決まるのに dyn で渡すと、実行時に呼び先を探す負荷がかかり、型の上でも実装が1つだと読めない（The Book 18.2 :119）該当する port が dyn で使われていない
外から実装を足す port（部品のカタログ）と、その引数（描画の部品）だけを dyn で使う実装を足していくものは、型が実行時に決まるので dyn が合う（The Book 18.2 :15）dyn の使用が、その2つの trait だけ
値の制約は型で表す（newtype）。bool や Option で意味を運ばない（API Guidelines の C-NEWTYPE ・ C-CUSTOM-TYPE）bool や Option で意味を運ぶと、呼ぶ側が値の意味を取り違えてもコンパイラが止めないレビューで見る（機械の検査は無い）

最後の規則は機械で見られないので、レビューでだけ見る。この1件だけを例外にする。

テスト

The Rust Programming Language 11.3 は、単体テストを「in the src directory in each file with the code that they're testing」に置き、結合テストを tests に置いて「using only the public interface」で使う、と書く。

層テストの型置き場所
domain単体テスト。入力と、前もって計算した期待値の表で確かめる同じファイルの #[cfg(test)] mod tests
application単体テスト。port をメモリ上で実装した代役を渡して確かめる同じファイルの #[cfg(test)] mod tests
outbound adapter本物の入出力を使う単体テスト（作業用のフォルダ）同じファイルの #[cfg(test)] mod tests
inbound adapterCLI と MCP の変換（引数 ↔ 呼び出し、結果 ↔ 出力）の単体テスト。同じ表で両方を確かめる同じファイルの #[cfg(test)] mod tests
共通ツールの約束公開 API の振り分け（Toolbox::dispatch）を、値の表で1回ずつ確かめる結合テストcrates/adapters/tests/
実行ファイル起動して確かめる端から端までのテスト。CLI と MCP で代表の数件だけcrates/adapters/tests/
宣言したツールの境界probe を宣言したツールとして起動し、SHA-256 ・ 制限時間 ・ 出力の上限を確かめるcrates/probe/tests/
規則なぜ検査
テストの本体に、分岐 ・ ループ ・ 確かめる対象と同じ計算を書かない。期待値は前もって計算した値を並べるテストの中に処理があると、そのテスト自体の正しさを別に確かめることになる#[test] の関数の本体に if ・ for ・ while ・ match が0件
テストの中で、ビルド（cargo build）・ 外部コマンド（sha256sum ・ certutil）を起動しない。実行ファイルの場所は CARGO_BIN_EXE_<名前> を使うテストの結果が、ビルドのやり方や OS ごとのコマンドの有無に左右されるtests/ と mod tests に env!("CARGO") ・ sha256sum ・ certutil が0件
プロトコルのクライアントを手で書かない。MCP を起動して確かめるときは、使っている MCP のライブラリのクライアントを使う手で書いたクライアントは、製品の MCP と同じ間違いをしても見つけられない。テストの中にプロトコルの実装が1つ増えるtests/ に JSON-RPC の文字列（"jsonrpc"）が0件
テストの補助は tests/support/ の1か所に置く。同じ補助を2か所に書かない同じ補助が2か所にあると、片方だけ直したときにテストどうしで前提が食い違うstruct Scratch などの補助の定義が1つだけ
製品のコードに、テストのためだけの関数 ・ 分岐 ・ pub を足さない。#[cfg(test)] は mod tests にだけ付けるテストのためのコードが配る実行ファイルに入り、テストの都合で製品の公開 API が広がる#[cfg(test)] が mod tests の外に0件
結合テストから core の domain と application を直に呼ばない。結合テストは公開 API（振り分け）だけを使う結合テストが中の型に結びつくと、中を直すたびに結合テストまで壊れる。中の確かめは単体テストが持つcrates/adapters/tests/ に schema_driven_core::domain ・ schema_driven_core::application が0件
