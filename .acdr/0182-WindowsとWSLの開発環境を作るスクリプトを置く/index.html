Windows と WSL の開発環境を作るスクリプトを置く

決めたこと

Windows と WSL（Ubuntu 26.04）の開発環境を、このリポジトリに置いたスクリプトから、同じ構成で作れるようにする。

なぜ決める必要があるか

2026-10-16 に、WSL と同じ開発環境を Windows に手で入れた。その手順は会話の記録と、セッションの一時フォルダの ps1 にしか無く、WSL の側は手順の記録がそもそも無い。2つの環境は別々に決めたので、Java の版の指定 ・ Rust と uv を mise の一覧に載せるか ・ Kotlin を入れるかが食い違っている。作り直すときに会話を読み返して手で再現するのをやめ、リポジトリのスクリプトを実行すれば同じ構成になる状態に一致させる。

どう変わるか

変更前と変更後

何が変更前変更後
開発環境の作り方の置き場所会話の記録と、手で入れた結果だけリポジトリの dev-env/wsl/setup.sh と dev-env/windows/setup.ps1
2つの環境の言語の指定WSL は Java を corretto-25.0.4.8.1 に固定し Kotlin を入れる。Windows は corretto-25 で、Rust と uv も mise の一覧に載せるどちらも mise の node@24 ・ go ・ java@corretto-25 ・ ruby ・ dotnet ・ uv ・ rust@stable。Rust の中身は公式の rustup
入れるツールの出どころそのときどきで選んだ各開発元の公式の配布物（winget ・ 公式の apt リポジトリ ・ 公式のインストーラー）。原典の取得と照合の記録は sources/ に置く

比較した案と、採らなかった理由

案採らなかった理由
手順を docs/ に文書として書く読んだ人が手で写すので、写し間違いと抜けが起きる。スクリプトなら、空の Ubuntu のコンテナで最初から最後まで実行して確かめられる
dotfiles などの別のリポジトリに置く入れるものは、このリポジトリの作業（Skill のビルド ・ 図の描画 ・ AI の CLI）のための環境である。別のリポジトリに置くと、このリポジトリの変更と一緒に直されない
1本のスクリプトで Windows と WSL の両方を作るWindows は PowerShell と winget、WSL は bash と apt で、実行する場所も言語も違う。1本にすると、分岐が本体の大半になる
Dev Container や Nix で環境を宣言するWindows の側で必要とするのは、Build Tools ・ Docker Desktop ・ PowerShell 7 のような、Windows に直接入れるものである。コンテナの中の環境では作れない
