意思決定の記録 ・ ACDR 0093 ・ 2026-10-03 ・ 承認

9月のボードの論点8と論点11を、スキーマ駆動の基盤のボードに合わせて改める

決めたこと

ボード usecase-schema-driven の決まりの表のうち、論点8と論点11の2行を、ボード schema-driven-base の論点1と論点2の決定に合わせて改める。

なぜ決める必要があるか

ボード schema-driven-base で、スキーマ駆動の道具の基盤の契約を7つ（作成 ・ 取得 ・ 更新 ・ 削除 ・ 検証 ・ 描画 ・ 案内）に決めた。続けて、ユースケース駆動の concrete の契約（注釈 ・ 集合の検証 ・ テストの報告 ・ ドリフト検知）を決めた。9月のボードの論点11は、操作を list ・ refs ・ get ・ validate の4つとし、テストの側からは記録した ID の集合だけを受けると書いている。論点8は、削除は引き算で後から出ると書いている。このままだと、2つのボードが同じ事柄について別のことを言う。決まりの表を新しい決定に合わせ、各論点のタブは決着した当時の答えとして残す。試作（trial/spike）の改修は、試作を正本へ起こすときに行う。

どう変わるか

変更前と変更後

何が変更前変更後
道具の操作list ・ refs ・ get ・ validate基盤の操作の4つ（作成 ・ 取得 ・ 更新 ・ 削除）。取得は JMESPath、更新と削除は JSON Patch
テストの側から受けるもの記録した ID の集合テストの報告（JSON。1件は id と result）
検出するものID の集合の差欠け ・ 余り ・ pass でないもの
参照されている宣言の削除削除したあとに、引き算で出る適用したあとの集合が検証を通過しないので、拒否される

比較した案と、採らなかった理由

案採らなかった理由
9月のボードの論点11のタブの答えまで書き換える各論点のタブは、決着した当時の論証と一体である。答えだけを書き換えると、論証と答えが食い違う。ACDR 0092 と同じく、決まりの表を現在の決まりにし、タブは当時の記録として残す
9月のボードは変えず、新しいボードだけを正とする9月のボードの決まりの表が古いまま残り、2つのボードが同じ事柄について別のことを言う。読む人がどちらが正かを毎回確認することになる
論点11だけを改め、論点8は残す論点8の「削除は引き算で後から出る」は、参照されている宣言の削除を拒否するという新しい決定と食い違う。片方だけ直すと、表の中で2行が別のことを言う

下に並ぶのは、この決定を採ったときに何がどう変わるかである ── 上の決定の具体である。

この面の変更 3 件
  1. ACDR 0093 でさらに改めた
    論点8と論点11の行を改めたことと、各論点のタブは当時の答えのまま残したことを、表の前置きに書く。書かないと、表とタブが食い違って見える
  2. 道具は変更の追跡を足さない
    新しいボードの論点2で、更新と削除は適用したあとの宣言の集合が検証（Schema ・ ID の一意 ・ 参照の解決）を通過したときだけ書き込むと決めた。参照されている宣言の削除は後から出るのではなく、その場で拒否される。変更の追跡を足さないという趣旨は保った
  3. 基盤の操作は4つ
    新しいボードの論点1で、基盤の操作を作成 ・ 取得（JMESPath）・ 更新 ・ 削除（JSON Patch）の4つに決めた。論点2で、テストの側からは ID の集合ではなく結果を持つ JSON の報告を受け、欠け ・ 余り ・ pass でないものを報告すると決めた。結果を受けないと、テストが通っていることを担保できない。報告を作る手段は、技術スタックごとにコーディングの側が持つ
