画面の AI に許すツールを、設定ファイルから読む

決めたこと

画面の「AI に聞く」で起動する AI に許すツールを、コードではなく設定ファイル（brainstorming/agents@v1）に持たせ、serve が依頼のたびに読む。

なぜ決める必要があるか

許可を足すたびに Rust のコードを直し、ビルドして入れ直していた（WebSearch と fact-check を足したときも同じだった）。しかも許可がどのリポジトリでも同じになり、fact-check の経路のようにリポジトリの並びに依存するものまでコードが探していた。利用者が「許可リストは外出しのファイルを読む形にしないと回らない」と指摘した。許可は利用者が決めるものなので、利用者が書くファイルに一致させる。

どう変わるか

変更前と変更後

何が変更前変更後
許可の置き場所brainstorming のコード（agent.rs）に、Claude Code の許すツール ・ Codex の sandbox ・ Kiro の信頼するツールを書いている.brainstorming/.settings/agents.json に書く。無ければ Skill の assets/defaults/agents.json を使う（混ぜない）
許可を変える手順コードを直し、テストし、ビルドして入れ直し、serve を起動し直すファイルを書き換える。次の依頼から効く
危ない値の止め方コードに書かないことと、テストで旗の名前を探すことで止めているスキーマが止める（sandbox を外す値 ・ dangerously と bypass を含む値 ・ Kiro のシェル ・ ボードを直すツールが無い一覧）。serve は読むたびに基盤の check で確かめ、通らなければ AI を起動しない
形の持ち主形が無く、許可の並びがコードに埋め込まれているいまは brainstorming（Concrete）が形を持つ。一時の置き場所であり、基盤の Agents 契約が決まったら形を基盤（Abstract）へ移し、brainstorming には値だけを残す

比較した案と、採らなかった理由

案採らなかった理由
Skill の既定とリポジトリの設定を項目ごとに混ぜるどの許可が効いているかを、2つのファイルから組み立てて読むことになる
設定ファイルを .brainstorming/agents.json に置くrender が置き場所の直下の JSON をページにしようとして止まる（実際に止まった）。ドットで始まるフォルダはページにしない
起動の旗をそのまま設定に書けるようにする権限を外す旗（--dangerously-skip-permissions など）も書けてしまう。設定に書けるのは、ツールの名前と sandbox の値だけにする
既定の許可をコードに残し、設定は足す分だけにする許可の一部がコードに残り、何が許されているかを読むのにコードとファイルの両方が要る
基盤の Agents 契約（ボード semantic-contract-core の Q3）が決まるまで待つ画面のチャットは今日も動いていて、許可を変えるたびにコードを直す状態が続く。形を基盤へ移すときは、この設定の値をそのまま持ち込める

license: MIT

反証で絞った答えを、承認だけで決められるボードにする Skill：brainstorming

目的

決めることがある問いに論点を立て、案を出し、提示の前に自分で反証して1つに絞り、利用者が承認だけで決められるボードを作る。利用者の判断の目的は、AI が作ったもののうち自分の意図からずれた所だけを早く見つけて正すことである。承認する人の問いは「この答えを、このまま進めてよいか」の1つだけにする。

進み具合は決着の数で測る。 案の数でも論点の数でもない。

役割

- 論点を3〜5件立て、依存の順を自分で持ち、いま見る論点を示す
- 案を複数出し、提示の前に反証して1つに絞る。外した案は理由と一緒に残す
- 答えの直下に完成イメージ（図 ・ 画面 ・ コード ・ 差分 ・ フォルダ構成 ・ 実行例）を置く
- 事実は自分で調べ、根拠に出どころを付ける。利用者に渡すのは決定だけである
- 回答を受けて回を進め、前の回から変わったところを理由と一緒に示す

入力の想定

受け取る情報解釈 ・ 既定値
テーマ1〜2文で確かめてから始める。論点はこちらで立てる
回答（承認 ・ 差し戻し ・ 書き足し）画面の「送る」でボードごとにまとめて届き、.brainstorming/<ボード>/answers/ に1件ずつ残る。送られると serve が AI を起動し、Step 5 を行わせる
データの置き場所リポジトリの根の .brainstorming/。ボードの本体は .brainstorming/<ボード>.json

実行手順

使うのは、この Skill のフォルダの実行ファイル scripts/bin/brainstorming だけである。ボードの JSON は手で書き換えず、update で直す（書いたその場でスキーマの検査が走る）。どの操作も JSON を1つ返し、終了コードは 0 正常 ／ 1 不合格 ・ 失敗 ／ 2 使い方の誤りである。

1枚のボードで AI が動くのは1つだけである。update と advance はボードのロック（.brainstorming/.serve/locks/<ボード>.json）を取り、ほかの AI が動いていれば断る。ターミナルから取ったロックは advance で外れる。advance をせずにやめるときは unlock --board .brainstorming/<ボード>.json で外す。

scripts/bin/brainstorming            操作の一覧
scripts/bin/brainstorming --version  版

Step 1: ボードを作る

ボードの名前（小文字の英数字とハイフン）を決め、スキーマから作る。

scripts/bin/brainstorming create --schema brainstorming/board@v1 --path .brainstorming/<ボード>.json

未記入の欄が x-prompt と一緒に返る。欄の書き方は prompt で読み、その決まりに従って値を決める。

scripts/bin/brainstorming prompt --schema brainstorming/board@v1 --property /topics

Step 2: 論点を立て、案を反証して答えを1つにする

論点ごとに、問い ・ 答え（1文と詳しい決まり）・ 完成イメージ ・ 置いた前提 ・ 確かめてほしい箇所（3件まで）・ 根拠 ・ 採らなかった案を書く。前提にした論点は depends に書く。書き手の検証の記録（通過した案 ・ 扱わない範囲 ・ 外の作業）は verification に書く。画面には出ない。

scripts/bin/brainstorming update --path .brainstorming/<ボード>.json --patch '<JSON Patch>'

- 案が最初から1つなら、論点の立て方が誤っている。複数出して反証し、残った1つを答えにする
- 根拠には、答えのどこを支えるか ・ もとにしたこと ・ 出どころの3つを書く。原典の引用は原文のまま書く
- 完成イメージは、在る種類だけがタブになる。表は入れない。変化の要約は差分か図で見せる
- 図の SVG は、書いた側で検査してから入れる

Step 3: 出す前に検査する

scripts/bin/brainstorming inspect --board .brainstorming/<ボード>.json
scripts/bin/brainstorming check --dir .brainstorming

inspect は形では見られない決まり（1文は120字まで ・ 答えが指す論点は depends に書く ・ 回答待ちの論点には完成イメージと試す行き先がある ・ いま見る論点は前提が決着している ・ 一度に開く論点は5件まで）を見る。check は形と参照を見る。どちらも0件にしてから出す。check の終了コード 0 は実行できたことだけを示すので、instances の errors と findings で合否を見る。

Step 4: 回として出し、画面で見せる

scripts/bin/brainstorming advance --board .brainstorming/<ボード>.json
scripts/bin/brainstorming render --dir .brainstorming
scripts/bin/brainstorming serve --dir .brainstorming --port 0

advance は回の記録 rounds/<回>.json を残す（書き換えない）。2回目からは、前の回と欄ごとに比べて変わったところ（画面では「前の更新から変わったところ」）を書き、差し戻しの言葉を理由に入れる。前の回で承認された論点は決着になる。render は全部のボードとダッシュボードを .brainstorming/site/ に描く。serve は出力の url を利用者に渡す（合言葉付きの URL で、最初の1回だけ使う）。合言葉は .serve/key に残るので、serve を起動し直しても同じ URL のまま使える。

Step 5: 回答を受けて、直して、次の回を出す

回答は .brainstorming/<ボード>/answers/ にあり、いまの回への回答を読む。

回答すること
承認（approve）その論点の status を settled にする。前提がすべて決着した論点を open にし、queue に、なぜいま開いたかと一緒に並べる
差し戻し（return）まず既存の答えを直せるかを確かめ、「どこが違うか」の所だけを直す。答えが動いていない欄は書き直さない
選ばれなかった論点その論点は変えない（回答待ちのまま残る）

直したら Step 3 から繰り返す。advance は、承認と差し戻しの言葉を読んで、この回で変わったところに理由を付ける。

Step 6: 決着させる

答えが下流の論点か外の作業で使われたら決着にしてよい。論点がすべて決着すると、ボードのステータスは決着になる。ボードのステータスは論点の状態と保留とロックから導くので、ボードに status を書かない。保留は利用者が画面で決める（hold に日付が入る）。保留は正当な着地点である。

出力形式

ボード1枚（.brainstorming/<ボード>.json）と、描いた画面（.brainstorming/site/<ボード>.html ・ dashboard.html）。利用者には次を伝える。

伝えること書き方
画面の場所serve の url、または site/<ボード>.html
回答待ちの論点論点の id と名前、なぜいま開いたか
前の更新から変わったところ何か所か。中身は画面が示すので、チャットに並べない
検査inspect と check が0件だったこと

回の番号（第N回）は、記録と比べるための内部の数え方なので、利用者に伝えない。

ガードレール

- 案を並べて選ばせない。選ばせるのは判断を利用者に移すことで、承認ではない
- 事実を利用者に聞かない。調べれば分かることは調べて根拠に書く
- 外した案を黙って消さない。rejected に案と何が壊れるかを残す
- ボードの JSON を手で書き換えない。update で直す。手で直すと、書いたその場の検査が行われない
- 回の記録 rounds/ と回答 answers/ を書き換えない。比べる相手と利用者の言葉が変わる
- ボードのフォルダの外を書き換えない。画面の「AI に聞く」から呼ばれたときは、serve が作業の前後を比べて、外の変更を利用者に知らせる。比べ方では変えた者を区別できないので、AI の作業の記録に出てくるもの ・ ほかのボード ・ 記録に無いものに分けて知らせる
- AI の「検査した」で合格としない。inspect と check の結果で決める
- ボードに status を書かない。ステータスは論点の状態 ・ 保留 ・ ロックから導く。手で書くと、回答したのに回答待ちのまま見えるような食い違いが出る
- ロックを残したまま作業をやめない。advance か unlock で外す。残すと、画面の「送る」と「AI に聞く」が止まったままになる
- 画面の AI に聞くで、Kiro は読むだけにする。手元の Kiro はシェルのコマンドを絞れないので、ボードを直すのは Claude Code と Codex だけである
- 画面の AI に許すツールを、コードに書かない。許可の設定（.brainstorming/.settings/agents.json。無ければ assets/defaults/agents.json）に書く。serve は依頼のたびに読んで基盤の check で確かめ、合格しなければ AI を起動しない。AI はこのファイルを書き換えない
- 扱わない範囲に扱いを付けずに承認を求めない。verification.out_of_scope に、対象外 ・ 後で決める ・ 解消済みのどれかを付ける
