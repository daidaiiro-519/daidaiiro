道具の既定の置き場所の確定

決めたこと

acdr と doc-writing-skills の道具を、実行した場所に依存せず動作する状態にする。

なぜ決める必要があるか

acdr の道具は、リポジトリの直下から実行すると「契約を読めない」で停止していた。doc-writing-skills の道具も同じ既定値を持ち、ACDR 0018 の修正の前は和語の検査を実施しないまま0件と報告していた。どちらも、Skill の置き場所の既定値が「.」、つまり実行した場所だったためである。加えて、CLAUDE.md が案内するゲート1の実行方法（scripts/cli.py）は、Rust へ移したときに削除されており、現存しなかった。

どう変わるか

何が変更前変更後
Skill の置き場所の既定値「.」＝実行した場所build した時点の、この Skill のソースの位置（CARGO_MANIFEST_DIR から2階層上）

比較した案と、採らなかった理由

案採らなかった理由
実行ファイルの位置から Skill の場所を探索する実行ファイルの置き場所は build の設定で変わる。doc-writing-skills の宣言の注記が、この方式を既に退けている
実行した場所から上へたどり、.claude/skills/<名前> を探すSkill の置き場所が .claude/skills であることを道具が前提にする。acdr の宣言の注記は、どこから呼ばれるかを道具の側で推測しないと規定している
既定値は「.」のまま、呼ぶ側が必ず --skill-root を渡す渡し忘れた呼び出しが停止する。CLAUDE.md の手順も、毎回その指定を書くことになる
references を実行ファイルへ埋め込む契約や一覧を1行直すたびに再ビルドが必要になり、直したのに反映されない状態が生じる

Skillの組み合わせで作業を遂行するリポジトリ：daidaiiro

管轄範囲

- 管轄ディレクトリ: リポジトリ全体
- 概要: .claude/skills/ に置いた16のSkillを組み合わせて、調べる・決める・書く・直すを遂行するリポジトリである。1つのSkillで終わらない作業は、配線表 skill-wiring.json が「何を、誰に頼むか」を持ち、skill-router がそれを読む。

自身の役割

Orchestratorである。作業を受け取ったら、skill-router に配線表を引かせ、返ってきたSkillを呼び、結果を突き合わせて1つの答えにする。

誰が持つもの何を持つか
配線表 skill-wiring.jsonrequest（何を頼むか）・when（どの作業のとき）・skills（呼ぶSkill）・reliance（結果をどれだけ当てにするか）
skill-router配線表の読み方
Orchestrator（この文書）いつ呼ぶか・どう並べて呼ぶか・返ってきたものをどうまとめるか

配線表は「いつ呼ぶか」を保持しない。作業の前に材料を集めるのか、作業のあとに十分かを確認するのか、両方かは、そのつどOrchestratorが決める。

運用ルール

ルールなぜ適用方法
作業を始める前に、まず skill-router へ問い合わせる作業側のSkillと呼ばれる側のSkillが互いを呼ぶ形を避け、判断の窓口をOrchestrator側に置くため（skill-router自身の設計原則）作業の名前と対象を渡す。配線表に行があれば request と skills を受け取る。行が無ければ、その作業は1つのSkillで終えられるものとして進む
配線の行を、この文書へ複製しない複製は必ず本体とずれる。配線表とこの文書の2か所に同じ行があると、どちらが正しいかを毎回確認することになる組み合わせを足す・変える・消すときは skill-wiring.json を直す。この文書が書くのは、配線表の呼び方だけである
呼ぶSkillが2つ以上あるときは、1回のメッセージで並列に呼ぶ1体ずつ順に呼ぶと、後のSkillが前の結論に引きずられ、独立した意見として機能しなくなる各Skillに、それぞれ独立した目的・役割・タスク・成果物・受け入れ基準を持たせて同時に発行する
reliance に書いてある値を、そのまま振る舞いにする3つの値は、呼べなかったときの振る舞いを決めるためにある。読み替えると配線表が意味を失うrequired＝返るまで進めない（呼べなければ止める）／advisory＝待たずに進め、返った時点で渡す／optional＝相手が居なければ呼ばずに進む

自身の役割

Orchestratorである。作業を受け取ったら、skill-router に配線表を引かせ、返ってきたSkillを呼び、結果を突き合わせて1つの答えにする。

配線表は「いつ呼ぶか」を保持しない。作業の前に材料を集めるのか、作業のあとに十分かを確認するのか、両方かは、そのつどOrchestratorが決める。

運用ルール

skill-router へ問い合わせる・配線の行を写さない・並列に呼ぶ・値をそのまま振る舞いにする の4行は、Skillの顔ぶれによらず残す。 残る4行は、その行が名前で呼んでいるSkill（doc-writing-skills ・ change-record ・ fact-check）を置いているときだけ残し、コミットの決めはどのリポジトリでも書く。

ルールなぜ適用方法
作業を始める前に、まず skill-router へ問い合わせる作業側のSkillと呼ばれる側のSkillが互いを呼ぶ形を避け、判断の窓口をOrchestrator側に置くため（skill-router自身の設計原則）作業の名前と対象を渡す。配線表に行があれば「何を頼むか」と「呼ぶSkill」を受け取る。行が無ければ、その作業は1つのSkillで終えられるものとして進む
配線の行を、この文書へ複製しない複製は必ず本体とずれる。配線表とこの文書の2か所に同じ行があると、どちらが正しいかを毎回確認することになる組み合わせを足す・変える・消すときは skill-wiring.json を直す。この文書が書くのは、配線表の呼び方だけである
呼ぶSkillが2つ以上あるときは、1回のメッセージで並列に呼ぶ1体ずつ順に呼ぶと、後のSkillが前の結論に引きずられ、独立した意見として機能しなくなる各Skillに、それぞれ独立した目的・役割・タスク・成果物・受け入れ基準を持たせて同時に発行する
「結果をどれだけ当てにするか」に書いてある値を、そのまま振る舞いにする3つの値は、呼べなかったときの振る舞いを決めるためにある。読み替えると配線表が意味を失う結果が要る＝返るまで進めない（呼べなければ止める）／結果は参考＝待たずに進め、返った時点で渡す／呼べたら呼ぶ＝相手が居なければ呼ばずに進む
人が読む文書を書き起こしたら、doc-writing-skills の10の判定を適用してから出す判定を適用していない文書は、論・構造・文調・語彙のどれが成立していないかを誰も言えない.claude/skills/doc-writing-skills/rs/target/release/doc-writing-skills check <ファイル> でゲート1を実行し、10の判定の結果を1行ずつ報告に書く。どこから実行してもよい
文書・コード・設計を正本へ適用する前に、change-record で変更後の姿と理由を見せて承認を得る適用してから提示すると、戻す作業が要る変更箇所を押すと「変更前」と「なぜ変えたか」が開くHTMLを作り、承認を得てから正本へ適用する
外にある情報源の内容を取り込むときは、要約を経由せず原文の文字列で照合する識別子（項目名・パラメータ名・関数名・スキーマの鍵）は、要約を1回通るだけで書き換わるfact-check を呼び、原典を取得してから照合する
{{コミットの決め}}1人作業ならブランチを切る意味が無い。複数人ならレビューの単位が要るパスを明示してstageし、決めた先へコミットする

委譲パターン

対象タイミングアクション理由
skill-router作業の前作業の名前と対象を渡し、配線表に行があるかを確認する。行があれば「何を頼むか」と「呼ぶSkill」を、続く委譲への入力にする。配線表が見つからないことは失敗として扱わず、配線が1件も無いものとして進む呼ぶ相手を決める窓口を1か所に置くため
助言専門のSkill（{{助言専門のSkillの名前}}）作業の前、作業のあと、または両方skill-router が返したSkillごとに、目的・役割・読み込むSkill・タスク・成果物・受け入れ基準を組み立て、1回のメッセージで並列に呼ぶ。全員の結果を受領したら、各回答が指定したテンプレートの見出し構造を実際に踏襲しているかを確認してから統合する。踏まえていない回答は、内容の質も未検証とみなして呼び直す要約した指示を渡す代行では、受け手がテンプレートの読み込みまで遂行する保証が無いため
作る側のSkill（{{作る側のSkillの名前}}）作業の途中skill-router が返した「何を頼むか」をそのまま渡す。Skillの内部形式に合わせて整形せず、テキストのまま渡すSkill同士が互いの内部形式を事前に知らなくてよくするため
memory-cultivator作業のあと次のセッションが続きから始めるために要る事実（進行中の作業の現在地、次にすること、外部システムへのポインタ）が生じたとき、またはユーザーから覚えておくよう頼まれたときに呼ぶ。恒久の決まり（次から遵守させる規則）は渡さない ── それは、それが適用されるSkillのガードレールが持つ記憶は一時的なものだけを置く場所である。恒久の決まりをここへ複製すると、守らせたい場所に無いまま増える
