具体が使ってよい面だけを、基盤の crate の外へ出す

決めたこと

基盤の crate は、具体が使ってよいもの（ポート ・ ユースケースと結果 ・ 結果とポートに出てくる値）だけを外へ出し、ドメインの部品とユースケースの中の部品は crate の中だけにする

なぜ決める必要があるか

ACDR 0143 で、転写した複製は具体の持ち物になり、基盤の新しい版へ更新できるようになった。ところが基盤の crate はすべてのモジュールが pub で、具体は内部（検査の graph ・ ViewEngine ・ Schema など）も import できた。実際に試しの具体から内部を import すると、ビルドが通った。具体が内部を使っていると、基盤が内部を直した版へ更新したときに、具体のビルドが壊れる。更新しても壊れないと約束できるのは、具体が使ってよい面を決めて、それ以外をコンパイラが止める場合だけである。

どう変わるか

変更前と変更後

何が変更前変更後
具体から見える基盤の crateすべてのモジュール（domain の6つ ・ application の8つ ・ ports）ports と、application の4つのユースケース（instances ・ checks ・ renders ・ transcriptions）と結果
具体から見える値domain::values の値オブジェクトすべてと、domain::check ・ schema_rules の型domain の直下の8つ（Finding ・ SchemaFinding ・ Hash ・ Html ・ JsonValue ・ Status ・ Unfilled ・ ValidationError）
具体が内部を使ったときビルドが通り、基盤を更新したときに初めて壊れるコンパイラが止める（E0603：module is private）
基盤のテスト内部をそのまま import するfeature internals で内部を開く。core と cli のテストだけが有効にする
アダプタ値を domain::values ・ domain::check から取る具体と同じ面（domain の直下）から取る
テストからしか使っていないものViewEngine::name ・ ApprovalRecord::directory ・ instances ・ Instance::path ・ schema ・ JsonPatch::as_str消す。VO-3 参照だけは宣言にあるので残し、別に決める

比較した案と、採らなかった理由

案採らなかった理由
すべて pub のまま、使ってよい面を SKILL.md に書く具体が内部を使っても、ビルドは通る。破ったことが分かるのは、基盤を更新して具体のビルドが壊れたときである
内部に #[doc(hidden)] を付ける文書から隠れるだけで、import はできる。コンパイラが止めない
基盤のテストを、ユースケースを通すテストへ書き直すドメインの部品を直接確かめる66件（値 ・ 検査 ・ 承認記録 ・ 描画の文脈 ・ x-view ・ ページ ・ スキーマの検査）を、ページ全体やディレクトリ全体を通す形へ書き直すことになる。どの部品で失敗したかが分からなくなる
内部のテストを、モジュールの中の単体テスト（#[cfg(test)]）へ移すx-view とページのテストは jmespath のアダプタを使うので、core の中には置けない（core はアダプタに依存しない）
crate の根に pub use で面を並べ、モジュールはすべて非公開にする基盤のテストが内部を見られなくなり、上の2つの案と同じことになる。面の入口はユースケースのモジュールのままにし、値だけを domain の直下から出す
