semantic-agent-schema のディレクトリ構成とコーディング規則

決めたこと

domain の crate の中を values/ ・ aggregates/ ・ services/ に分け、集約の欄をその集約のフォルダの中にだけ見せ、コーディング規則を CODING.md に置く。

なぜ決める必要があるか

ACDR 0201 の構成は、ファクトリを crate の直下の factories/ に置いていた。Rust の private はモジュールの親子で効くので、その位置からは集約の欄を pub(crate) にしないと作れず、crate のどこからでも欄を書き換えられた（実測 E0451）。集約のフォルダの中にだけ見せる形なら、別の集約や services/ からの書き換えをコンパイラが止める（実測 E0616 ・ E0624）。あわせて、ボード Q3 の MCP の入口と、目的の参照による session の依存を足し、実装の前に規則を決める。

1. アーキテクチャと依存の向き

ポートとアダプター。中心は crates/domain/ の8つの crate で、crates/application/ が使う場面とポートを持ち、crates/outbound/ と crates/inbound/ が外側である。

規則なぜ検査
crate の依存は architecture.json が許す辺だけにする依存の向きが外から中心へ揃っていないと、中心の変更理由が外の技術に引きずられるarchitecture-lint check --rules architecture.json --cargo . が0件
domain の crate は値を受け取り値を返す。ファイル ・ 通信 ・ プロセス ・ 時刻に触らない中心が入出力に触ると、代役なしの単体テストで確かめられなくなるcrates/domain/clippy.toml の disallowed-methods ・ disallowed-types（std::fs ・ std::net ・ std::process ・ std::time::SystemTime）に clippy が0件
基盤は AI を起動しない。AI が判定する rule は Semantic Schema Validator が依頼の一覧（needs）として返し、使う場面がポート（rule の判定を依頼する）で依頼して、答えを Validator の2段目に渡すAI の起動が domain や Validator の中に入ると、判定の入力と出力が値として残らず、決定的な試験ができないdomain の crate に outbound の crate への辺が無い（architecture-lint）。Validator の公開関数が値だけを受け取る（単体テスト）
起動時の結合は crates/inbound/cli/src/compose.rs の1か所に置く。main.rs（CLI）と src/bin/mcp.rs（MCP）は、引数を受け取って compose を呼ぶだけにする結合が2か所にあると、片方だけ直したときに振る舞いが食い違う。原典：「Rust projects that provide a binary have a straightforward _src/main.rs_ file that calls logic that lives in the _src/lib.rs_ file」（The Rust Programming Language 11.3）① outbound の外から outbound の crate に依存するのは cli だけ。outbound どうしの辺は architecture.json のとおり（architecture-lint）② cli の中で outbound の crate を use するのは compose.rs だけ（追跡の検査の grep）

2. ワークスペースと crate

規則なぜ検査
ワークスペースは virtual manifest にし、メンバーを crates/ の下に層ごとのフォルダで置く（members = ["crates/domain/*", "crates/application", "crates/outbound/*", "crates/inbound/*"]）。resolver を明示する原典は「Keep all member packages in a flat directory (commonly crates/)」と平らを勧める。ここでは層（domain ・ outbound ・ inbound）をフォルダで見せるために、原典から外して2段にする（ACDR 0201 で承認した形）。原典：「resolver must be set explicitly in virtual workspaces」（Cargo Book Workspaces）cargo metadata --no-deps のメンバーが crates/ の下だけ
版 ・ edition ・ rust-version（1.97 以上。build.warnings が使える版）・ license と依存の版は [workspace.package] と [workspace.dependencies] の1か所に置き、メンバーは workspace = true で受け継ぐ版が2か所にあると、片方だけ上がって食い違うメンバーの Cargo.toml に版の数字が0件
lint の段階は [workspace.lints] に置き、メンバーは [lints] workspace = true だけを書く。lint の設定値は根の clippy.toml（試験のコードでの unwrap ・ expect ・ panic を許す allow-unwrap-in-tests など）に置き、domain の入出力の禁止は crates/domain/clippy.toml に置く（根の設定値も写す。Clippy は近いほうの1つだけを読む）lint の段階が crate ごとに違うと、同じ書き方が crate によって通ったり落ちたりする。workspace = true と自分の [lints] を両方書くと Cargo が止まる（Cargo の実装 commit b5786332 のエラー「cannot override workspace.lints in lints」。Cargo Book には無い）メンバーの Cargo.toml すべてに [lints] workspace = true があり、ほかの lint の行が0件
共有の crate（common ・ shared ・ utils）を作らない。2つ以上の crate が使う値は、その語の規則を持つ crate に置く共有の crate は持ち主の無い型の置き場になり、依存の辺が中心から外れるcrates/ の下に common ・ shared ・ utils の名前のフォルダが0件（追跡の検査の grep）
crate の名前は semantic-agent-schema-<名前>（例：semantic-agent-schema-declaration）。フォルダの名前は <名前>ACDR 0201 で承認した名前。原典：「Crate names should not use -rs or -rust as a suffix or prefix」（Rust API Guidelines C-CASE）。フォルダで層が分かるので、フォルダに接頭辞は必要ないarchitecture.json の components と Cargo.toml の name が一致

3. domain の crate の中

規則なぜ検査
domain の crate の中は values/（値オブジェクト）・ aggregates/（集約）・ services/（ドメインサービス）に分ける。エンティティかファクトリを持つ集約は、集約の名前のフォルダ aggregates/<集約>/ に entities/ と factories/ を置き、集約とエンティティの欄 ・ エンティティを作る関数を pub(in crate::aggregates::<集約>) にする。2つ以上の集約が持つエンティティだけ aggregates/entities/ に置き pub(in crate::aggregates) にする原典：「pub(in path) makes an item visible within the provided path」「If an item is private, it may be accessed by the current module and its descendants.」（The Rust Reference, Visibility and privacy）。集約のフォルダの中にだけ見せれば、ファクトリは欄で集約を作れ、別の集約や services/ からは書き換えられない（実測：E0616 ・ E0624）。crate の直下の factories/ からは pub(crate) にしないと作れず、crate のどこからでも書き換えられる（実測 E0451）集約とエンティティの struct の欄に pub ・ pub(crate) ・ pub(in crate::aggregates)（共有のエンティティを除く）が0件（追跡の検査。syn でソースを解析する）
集約の状態を変えるのは、集約のコマンド（メソッド）だけにする。欄は private で、読むのは借用を返すメソッド（get_ を付けない）で行う原典：「the get_ prefix is not used for getters」（C-GETTER）。欄を開くと、どこからでも不変条件を壊せる上と同じ
2つ以上の集約が持つエンティティ（aggregates/entities/）の欄は、持ち主の集約のコマンドからだけ書き換えるこのエンティティだけは見せる範囲が aggregates/ 全体で、コンパイラが止めないレビュー
ドメインサービスは services/ に1つ1ファイルで置く（resolver.rs ・ validator.rs ・ renderer.rs ・ selector.rs）ドメインサービスは集約をまたぐ処理で、集約を作るときは集約の公開の関数を使うこの4つのファイルが割り当てた crate の services/ にある（追跡の検査の grep）
値オブジェクトは values/ に1つ1ファイルで置き、中身は private にして new で作る値オブジェクトは自分で正しさを守り、ほかから中身に触らない値オブジェクトの struct の欄に pub が0件（追跡の検査。syn）
モジュールのファイルの形を foo.rs と foo/ の1つにそろえ、foo/mod.rs の形を混ぜないRust はどちらの形も受け付けるが、foo.rs と foo/mod.rs を両方置くことはできない。原典：「It is encouraged to use the new naming convention as it is more consistent, and avoids having many files named mod.rs within a project.」（The Rust Reference, Modules）。mod.rs が禁止されているわけではないcrates/ の下に mod.rs が0件
不変条件を守る関数の doc コメントに 不変条件 I番号 を書くどの不変条件をどの関数が守るかを、コードからたどれるようにするtest-suite/trace.json の不変条件の id が、それぞれ doc コメントか試験の traces に1回以上ある（追跡の検査）

6. 失敗と panic

規則なぜ検査
ライブラリの crate で unwrap ・ expect ・ panic! を使わない。失敗は Result で返すpanic すると CLI が値（JSON の結果と終了コード）を返さずに落ち、呼ぶ側の AI と CI が理由を受け取れない[workspace.lints.clippy] の unwrap_used ・ expect_used ・ panic を deny。試験のコードは根の clippy.toml の allow-unwrap-in-tests ・ allow-expect-in-tests ・ allow-panic-in-tests で許す
Result を返す公開関数は、doc コメントに # Errors の節を書く原典：「Error conditions should be documented in an "Errors" section」（C-FAILURE）clippy の missing_errors_doc を deny
外から受け取る値の検査①（入力が入力のスキーマに合うか）で外れたら断り、状態に触れない。検査②（出力が形と rule に合うか）で外れても保存し、violated で返すACDR 0201 と Q8（保存は断らない）システムテスト（①は unchanged、②は violated を期待する場面）
