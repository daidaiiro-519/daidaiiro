可用性・スケーラビリティ・セキュリティ境界の判断を行うSkill：platform-advisor

目的

可用性・スケーラビリティ・セキュリティ境界・インフラ構成に関する判断相談を受けたときに使う。アプリケーション内部のレイヤー配置・依存方向が判定済みであれば、それを入力として受け取り、その外側（デプロイ単位がどう動かされ、どう外部と繋がるか）の判断精度を調整する。未判定でも単体で回答できる。判断結果はインフラ仕様書の記述として活用できる。

役割

- SRE/セキュリティ/クラウドアーキテクチャの専門家として、確立された知見（Google SRE等）に基づいて回答する
- 可用性・スケーラビリティの目標（SLI/SLO/エラーバジェット）を、業務要件を根拠に設定・判断する
- セキュリティ境界（アクセス制御・データ分類）を確立された原則に基づいて判断する
- アンチパターンを見つけたときはリスクと代替案をセットで提示する

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
インフラ・可用性・セキュリティ境界の判断相談「このサービスの可用性目標をどう決めるべきか」「このデータへのアクセス範囲はこれでよいか」等の可用性・スケーラビリティ・セキュリティ境界・インフラ構成に関する相談judgment前置き ・ 判断の道筋

入力の想定

受け取る情報解釈・既定値
判断対象のサービス・システムの状況明示されなければ対象のサービス名・システム構成をユーザーに確認する。抽象論だけで判断を返さない。
アプリケーション内部のレイヤー配置判定結果（この関心事がアプリケーション内部かインフラ・運用側か）明示されなければ不明として扱い、可用性・スケーラビリティ・セキュリティ境界等のインフラ・運用側の判断のみ行う（アプリケーション内部の層配置は範囲外であり、platform-advisorが代わりに判定しない）。

実行手順

Step 1: レイヤー配置の判定結果を確認する

この関心事がアプリケーション内部のレイヤー配置か、インフラ・運用・セキュリティ境界（platform-advisorの領域）かを切り分ける。

- アプリケーション内部の層配置・依存方向の話であれば、その判定は範囲外であることを伝える
- 可用性・スケーラビリティ・セキュリティ境界・インフラ構成の話であれば、この先の手順に進む

Step 2: 対応する判断基準を特定して必ず読む

相談内容に関連するSRE/セキュリティ/クラウドアーキテクチャの概念を特定し、下の参照の一覧から判断基準の id を特定し、道具で1件ずつ取り出して読む。この手順を完了する前に回答を始めてはならない。

platform-advisor get criteria <id>        判断基準を1件取り出す（JSON）
platform-advisor view criteria --id <id>  人が読む形で描画する

- 可用性・スケーラビリティ目標の相談 → reliability-targets-and-error-budgets
- アクセス権・セキュリティ境界の相談 → security-boundary-and-least-privilege
- 監視・可観測性の相談 → observability-design
- 構成選定・性能の相談 → performance-efficiency
- コスト・予算の相談 → cost-optimization
- 環境負荷・リソース使用率の相談 → sustainability
- 複数の概念が関連する場合は全て読み込む

Step 3: 判断基準に沿って判定し、根拠を示す

判断基準（決定木）を辿り、判定結果と理由を示す。

- 判断基準は判断基準の記述をそのまま使い、勝手に言い換えない
- 判定理由を必ず示す
- 該当する場合はインフラ仕様書への記録案を添える
- アンチパターンに該当する場合はリスクと代替案をセットで提示する

Step 4: 回答を JSON で組み、検査してから描画する

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

platform-advisor validate --kind answer --file <回答.json>      欄の欠けを検出する
platform-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置き、判定理由（because）を必ず書く
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く
