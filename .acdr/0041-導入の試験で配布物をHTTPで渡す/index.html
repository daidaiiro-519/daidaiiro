ACDR 0041

導入の試験で、配布物を HTTP で渡す

承認承認を得た。適用してよい2026-09-29
決めること ── 承認か差し戻しを返すのは、この1件である
配布の CI の導入の試験で、配布物を試験の中の HTTP サーバーから導入スクリプトへ渡す。

なぜ、いま決めるのか

tag v1.0.0 を付け直した CI（run 36525094562）は、3つの OS で組み立てが完了し、Linux ・ macOS で導入の試験に合格した。Windows の導入の試験だけが失敗し、公開まで進まなかった。試験は配布物の場所を file:///d/a/… の形で渡していた。この経路は Git Bash の書き方であり、Windows の PowerShell の install.ps1 は照合の一覧を取得できなかった。

形の変化

何がいまの形これからの形
導入の試験で配布物を渡す方法file:// の経路試験の中で立てた HTTP サーバー（http://127.0.0.1:8765）

図で確認する

実現の形

試験の中で Python の http.server を配布物の置き場所で起動し、応答するまで待ってから導入スクリプトを実行する。release.yml と、その雛形の2か所を同じ内容に修正した。手元の Linux で、直した試験の手順を CI と同じシェルの設定（-e -o pipefail）で実行し、3つの Skill を導入できた。Windows での動作は、CI を再実行するまで確認できない。

適用先

変更する正本は、このリポジトリの .github/workflows/release.yml と、skills-creator の release.yml の雛形である。

比較した案

どれも反証を通過しなかった案である ── 未解決のまま残っているものではない。

案採らなかった理由
Windows だけ、経路を Windows の書き方（D:/a/…）に変換して渡すOS ごとに試験の手順が分岐する。PowerShell の Invoke-WebRequest が file:// に対応するかも確認できていない
Windows の導入の試験を削除するinstall.ps1 が動くかを、公開の前に確認できなくなる

承認後に実施すること

  • 状態を accepted にして組み直し、.acdr/README.md へ行を加え、main へコミットする
  • tag v1.0.0 を直したコミットへ付け直して push し、CI を再実行する（Release はまだ作られていない）
