x-view の文の型を普通の JMESPath で書く

決めたこと

x-view の文の型を schema-driven の references/view.schema.json として持ち、{…} の中は普通の JMESPath と基盤の9つの関数で書く。キーは text ・ cases ・ parts ・ maps ・ label ・ hidden の6つにする

なぜ決める必要があるか

3回目（描画）で x-view を Rust で実装する。見本の x-view は、15種類のキーと30種類の絞り（|name ・ |map: ・ |clause など）を持つ独自の書き方で、仕様が無かった。このまま実装すると、試作を仕様の代わりに読むことになる。取得の契約とページテンプレートはすでに JMESPath で書くと決めた（ボード schema-driven-build の論点4、ACDR 0128）。x-view も同じ JMESPath に寄せれば、書き方は1つで済む。省略の書き方（パイプの後ろの関数で @ を省く）も比べたが、方言になり、誤りの文が書いた式と食い違い、外の道具で確かめられないので、採らなかった（利用者と合意した）

どう変わるか

変更前と変更後

何が変更前変更後
x-view のキー15種類（text ・ cases ・ ops ・ by_value ・ by_key ・ by_type ・ post ・ maps ・ hidden ・ form_default ・ short ・ reply など）6つ（text ・ cases ・ parts ・ maps ・ label ・ hidden）
文の型の {…} の中独自の道と30種類の絞り（{lacks|name|quote1|join:}）普通の JMESPath（{lacks | name(@) | quote(@) | join('', @)}）
基盤が足す関数無い（絞りが見本の道具の中にあった）name ・ label ・ map ・ view ・ part ・ quote ・ clause ・ neg ・ fill の9つ。配列は要素ごとに処理する
参照の名前x-ref の label と、見本の道具の中の決まり参照される側の形の x-view の label（JMESPath 式）。name() はそれで名前を返す

比較した案と、採らなかった理由

案採らなかった理由
見本の独自の書き方を、キーと絞りを減らして残す取得とページテンプレートの JMESPath とは別に、2つ目の式の書き方が残る
パイプの後ろの関数で @ を省略できる方言にする書く量は関数ごとに3文字減るだけで、省略してよい関数を覚える規則 ・ 誤りの文と書いた式の食い違い ・ 外の道具で確かめられないこと、の費用が毎回かかる
日本語の言い回しの関数（clause ・ neg ・ fill）を基盤に置かない条件の文の「なら、」、拡張の条件の否定、用語集の動詞の型（「〜に〜を依頼する」）が組めない。基盤は日本語の文を組むことを前提にする
