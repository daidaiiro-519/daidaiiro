述部を、ふだん使わない和語にも置き換えない

決めたこと

述部は、ふだん使わない漢語にも、ふだん使わない和語にも置き換えず、分野に名前のある操作はその名前で書く

なぜ決める必要があるか

doc-writing-skills の規則は、名前（名詞）は和語にも漢語にも置き換えないと決めていたが、述部は漢語へ置き換えることだけを禁じていた。そのため、技術の操作を和語の言い回しで書く応答が続いた（「一から起こした」「組み立てが通った」「clippy が誤りとして止めた」「突き合わせ」）。利用者から「和語が多い」「馴染みのない語彙ばっかり」と指摘された。名詞の規則と同じく、述部も両方の側を禁じ、分野の名前がある操作はその名前で書くことに一致させる

どう変わるか

変更前と変更後

何が変更前変更後
述部の規則ふだん使わない漢語へ置き換えない（和語については書いていない）ふだん使わない漢語にも和語にも置き換えない。分野に名前のある操作は、その名前で書く

比較した案と、採らなかった理由

案採らなかった理由
記憶（自動メモリ）に、和語を使わないと書く記憶は一時的な事実だけを置く場所で、恒久の決まりは、それが適用される Skill のガードレールが持つ（CLAUDE.md）
和語の言い回しを廃語の一覧（retired-words.json）へ入れる「起こす」「止める」は普通の語でもあり、部分一致で正しい使い方まで検出する

name: doc-writing-skills
description: 日本語のテクニカルライティング文書を書く・直すときに必ず使うスキル。設計文書・仕様・報告・README・学術文書など、人が読む文書を書き起こす前と、書いたあとに使う。「文書」「まとめて」「書いて」「ドキュメント」と言われたとき、および既存のmdやHTMLの本文を直すときに必ず使う。
version: 1.0.0

目的

技術文書としても学術文書としても違和感のない日本語を書く。

満たすこと
論意味が通り、論が成立している
構造情報が、その型に合った形で置かれている
文調人が読んで、一度で意味が取れる
語彙同じ文脈では、同じものが同じ語で呼ばれている

判断の材料は10の概念である。
どれも公開された規格・指針から導いており、出どころを最後の節に置く。

出すには、2つのゲートを実行する。

ゲート何を検査するか誰が決めるか
10件にできるものが、0件であること機械
210の判定すべてに、結果が1行ずつあること書き手

ゲート2が保証するのは、判定を適用したことだけである。
何を直すかは、書き手の判断に残る。

役割

- 書いたものに、10の概念から導いた判定を適用する
- 判定を、読む人がその場でできる1つの操作に降ろす
- 原典から導けない決めは、そう書く
- 適用しなかった判定を、報告に書く

処理対象と成果物

処理対象

これから書く日本語の文書、または既に書いてある日本語の文書である。

成果物

10の判定を適用し、直したか残したかを明示する文書である。

入力の想定

受け取る情報解釈・既定値
読み手明示されなければ、その文書を初めて開く人とする
用語の定め対象フォルダに用語を定めた文書があれば、それに従う
文脈の境界明示されなければ、文書1本を1つの文脈とする

実行手順

Step 1: 読み手と用語を決める

書き始める前に、読み手を1つに決める。
読み手が決まらないと、選ぶ語も構成も決まらない（概念8）。
対象フォルダに用語の定めがあれば、先に読む。

Step 2: 10の判定を適用する

上から順に適用する。
前の概念が成立していなければ、後の判定は意味を保持しない。

#概念規則判定
1読み手が組み立て直す作業を、書き手が負担する1文の中で、読み手に計算をさせない。名詞句には、指し先を文書の中に置く名詞句を1つずつ抜き出し、「何の」「どこの」「どっちの」「誰が」を問う。文書の中の文字列で答えられない名詞句が1つでもあれば、その文は書けていない。「読み返して不自然か」で判定しない——書き手は指し先を知っているので、不自然に見えない
2情報の型が、置く形を決める対比・条件・手順・分岐を、散文に置かないその段落を、表か図に置き直せるかを試す
3数が増えたら、形を変える並べるものが3つ以上なら、箇条書きか表にする数える
4見出しは、本文を読まずに全体を掴ませる見出しの階層を飛ばさない。見出しを追えば全体の内容がつかめるようにし、見出しを目立たせる。番号は付けても付けなくてもよい ── 統一されているかだけを確認する見出しだけを抜き出して、順に読む。そのうえで、どの本文がどの見出しに属すかが見た目で分かるかを確認する
5結論を先に置き、根拠を後ろに置く節の最初の一文を結論にする各節の先頭文だけを並べて読む
6読み手は、形の違いを意味の違いとして読む同じ立場のものは同じ形で書く。文体は文書の中で1つにする並んでいるものの語尾を見比べる
7語の意味は、文脈の中で定まる同じ文脈では、1つの意味に1つの語だけを対応づける。文脈が変わるなら、変わることを書く用語を列挙し、同じ意味の別の語が無いかを確認する
8読み手が誰かで、選ぶ語と構成が変わる読み手を先に決める。語は、読み手の世界にすでにある語から選ぶ。分野で定着した専門用語はそのまま使い、自分が作った語・訳した語は使わない。使うなら、新しい語だと書いて定義する。名前のあるものを、描写で呼ばない語の出どころを提示できるかを確認する。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する。そのうえで、書いた操作や物に、分野で通っている名前があるかを1つずつ問う。あるなら、描写ではなくその名前を書く——「均す」ではなく正規化する、「流す」ではなく実行する、「鵜呑みにしない」ではなくそのまま信じない。ふつうの日本語の語も、この判定に掛ける。作った語でも訳した語でもないので、出どころだけを確認すると通り抜ける。読み手が分野の外の人でも、描写に置き換えてはならない。言い換えてよいのは、日常語で意味が表せるものだけである（頻回→頻繁に）。日常語で表せないものは、その名前のまま使い、説明を添える
9読み手が一度に扱える量には限りがある1文は短くする。段落は3行から7行にする。文書の限度を決める数える
10比喩と定型句は、読み手によって解けない比喩は、例として明示するときだけ使うその比喩を字義どおりに読んで、意味が通るかを試す

名詞句で終わることは、それ自体では欠陥ではない。
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
判定1が見るのは、文の中で読み手が戻るかどうかである。

Step 3: 直したか、残したかを明示する

判定に該当した箇所を、直すか、理由を付けて残すかのどちらかにする。
理由が書けないなら、それは直す対象である。

Step 4: 2つのゲートを実行する

ゲート1は機械が決める。

doc-writing-skills check <ファイル...>
doc-writing-skills check <ファイル...> --synonyms 用語.tsv
検査拠って立つもの
見出しの階層が飛んでいる概念4
文体が混ざっている概念6
並んだ項目の語尾が統一されていない概念6
文字で図や表を描いている概念2
同じ意味の語が2つある（対を渡したとき）概念7
強調が描画されない媒体の決め

最後の1つだけ、概念から導けない。
マークダウンの記法に拠るもので、5つの原典はどれも描画について書いていない。
別枠であることを、--list と名簿に書いてある。

概念3と概念9は、ゲートに入らない。
数は数えられるが、いくつで形を変えるかは文脈で変わるので、0件にできない。
判定として、書き手が適用する。

利用者への応答には、reply を適用する。
応答で使用した語は、そのまま文書へ流入するので、文書と同じ語彙表で照合する。
適用するのは廃語の1つだけで、見出しや文体の判定は適用しない。

doc-writing-skills reply --message <本文>   # 本文を直接渡す（MCP も同じ）
doc-writing-skills reply                    # Claude Code の Stop フックの入力を標準入力から読む

検出があれば、Stop フックが読む {"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":…}} を出力する。
decision: "block" を使わない ── Claude Code はそれを hook error として表示する。additionalContext なら会話は同じく続き、
表示は Stop hook feedback になる（code.claude.com/docs/en/hooks :2620・2631、2026-09-27 取得）。
Stop フックは応答を表示したあとに走る ── 表示を止めることはできず、修正した全文を続けて出させる。

語の単位で判定できない不自然さは、review でモデルに審査させる。
造語 ・ 比喩 ・ 主述の不整合 ・ 含意の不一致 ・ 幼い語り口 ・ 回りくどさは、語彙表では検出できない。
review は、判定基準（references/review-criteria.json）・手順（references/document.json の review-instruction）・
事例（プロジェクトの .doc-writing/review-examples.json）を1つの依頼文へ組む。判定はモデルが実施する。

doc-writing-skills review --message <本文>                 # 文書（全部の基準を適用する）
doc-writing-skills review --message <本文> --scope reply   # 前後の文脈を保持しない本文（文脈を要する基準を外す）

適用するのは、文書を出す前だけである。会話の応答には、応答のたびに適用しない ──
審査のたびにモデルのトークンを消費し、得られる判定は確率的である。会話の応答には、
トークンを消費しない reply（語彙表の照合）だけを適用する。

判定は確率的である。ゲート1の代わりにしない。 実測（指摘された文15件 ・ 指摘の無い文15件）で、
ゲート1と併用して検出13〜14件 ・ 誤検出2件だった。

ゲート2は書き手が判定する。
報告に、10の判定すべての結果を1行ずつ書く。1つでも欠けていれば、通っていない。

出力形式

報告する内容書き方
直した箇所概念の番号ごとに、どこを何から何へ直したかを表で出す
残した箇所場所と、残す理由を書く
ゲート1の結果通ったか、通っていないか。件数を書く
適用しなかった判定番号で書く。全部適用したなら、そう書く。1つでも欠ければゲート2は通っていない
確認していないこと確認していないことを、確認したと書かない

ガードレール

- 運用の覚書の書き方を、どの文書にも使わない。書いた本人が読み返すための略した書き方は、読み手のための書き方ではない。CLAUDE.md と Skill も例外にしない ── 例外にすると、そこで書いた語がそのまま本文へ流れる。どの文書でも、操作の名前で書く
- 名前のあるものを、描写で呼ばない。その操作に分野の名前があるなら、自分の言葉で言い換えない
- 比喩で言い換えない。対象を別の物へ置き換えた語を使わない ── 指し先が読み手の側で決まらない（文書か、欄か、クラスかを、読み手が推測することになる）。利用者への応答も同じである ── 応答で使用した語は、そのまま文書へ流入する。対象の名前で書く。検出する語は廃語の一覧が保持する ── 散文で例を並べると、その例が本文へ流入する。ただし、普通の語の一部になる語は一覧へ入れられない ── 部分一致で正しい語まで検出するためである（「段」は段階 ・ 段落 ・ 手段 ・ 段組みの一部である）。その種の語は機械で検出できないので、書く時点で遵守する
- 文語寄りの語を使わない。「営み」「所以」「〜ねばならない」のように、書き言葉のためだけに選んだ語は、ふだん話す語へ替える。判定は、同じことを口で説明するときにその語を使うか ── 使わないなら、読み手にとっては飾りであって、意味を1つも足していない
- 廃語を使用しない。一度破棄した語の一覧はこのSkillの外にある ── いつ何を破棄したかはプロジェクトごとに相違するので、ここへ書くと書いたプロジェクトでしか使えない検査になる。既定では .doc-writing/retired-words.json を、対象のファイルから上へたどって探す。無ければこの検査は走らない（失敗にしない）
- 名前を言い換えない。原典の訳語と、分野で定着した技術用語は、そのまま使う。和語にも漢語にも置き換えない ── 置き換えると必ず新しい語になり（メタデータ→「頭」、出典→「指す先」）、読み手が意味を決められない。判定は2つ ── その語を検索して同じ意味が出てくるか。原典か分野で、その語が使われているか
- 述部は、ふだん使う動詞で書く。ふだん使わない漢語（「保持する」「認知する」「委譲する」）にも、ふだん使わない和語（「起こす」「組み立てる」「止める」「突き合わせる」）にも置き換えない。分野に名前のある操作は、その名前で書く（ビルドする ・ コミットする ・ 照合する ・ エラーにする）。判定は、同じことを口で説明するときにその語を使うか。意味の範囲が広すぎて操作が特定できないときも、分野で使われている具体的な語を選ぶ
- 指し先の無い名詞句を書かない。「ずれ」「外を指す名前」のように、それが何を指すかを文書の中に書いていない語を使わない。見出しに置く語は、見出しだけで指し先が分かる形にする（「ずれた34件」ではなく「仕様と実装のずれ34件」）
- 散文で書けることを、散文で書かない。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- 桁を空白で整列させて、表に見せない。表はマークダウンの表で書く
- ASCII で図を描かない。図は mermaid か SVG で書く
- 同じ文脈で、同じ意味に2つの語を対応づけない。文脈が変わるなら、変わることを書く
- 訂正の記録を本文に残さない。文書には現行の正しい内容だけを書く。履歴は git が持つ
- 数値は原典の文字列で確認してから書く。要約を経由して引かない
- 確認していない内容を、確認したように書かない。推測は推測と分かる形で書く
- 原典から導けない決めを、原典の記述として書かない。こちらの決めだと書く
- ゲートを実行していないものを、出さない。実行していないなら、そう書く

概念8の「名前のあるものを、描写で呼ばない」は、DDD Reference の次の行から取っている。

Translation blunts communication and makes knowledge crunching anemic.
Within a bounded context, use the same language in diagrams, writing, and especially speech.

見出しの番号は、規則にしない。

Don't use numbers in headings to indicate a sequence of sections.
── Google developer documentation style guide, headings

公用文は番号に触れず、見え方だけを求めている（Ⅲ－２ 標題・見出しの付け方）。

エ　見出しを追えば全体の内容がつかめるようにする。
カ　見出しを目立たせるよう工夫する。

したがって、番号の有無は検査しない。見出しだけで内容がつかめるか、
どの本文がどの見出しに属すかが見た目で分かるか ── 見るのはそちらである。

漢語と和語は、正確さと親しみやすさで選び分ける。

ウ　重厚さや正確さを高めるには、述部に漢語を用いる
語の意味をより正確に表現したいときに、漢語を用いることが有効である場合がある。
例）性質が変わる → 性質が変化する　　プログラムが変わる → プログラムが変更される

エ　分かりやすさや親しみやすさを高めるには、述部に訓読みの動詞を用いる
── 公用文作成の考え方 Ⅲ－４

エには但し書きが付いている。

ただし、訓読みの動詞は意味の範囲が広いため、厳密に意味を特定しなければならないときには
不向きなこともあることに留意する。
例）作業が進捗する → 作業がはかどる、作業が順調に進む、作業が予定どおりに運ぶ

「進捗する」1語が、和語では3通りに散る。

このリポジトリは、ウ と エ を選び分ける。
述部はふだん使う動詞で書き、意味の範囲が広すぎて操作が特定できないときだけ、分野で使われている具体的な語を選ぶ（ACDR 0095）。名前は言い換えない。

専門用語への対応は3つあり、言い換えはそのうち1つである。

ア　言い換える。　例）頻回 → 頻繁に、何回も　　埋蔵文化財包蔵地 → 遺跡
イ　説明を付けて使う。
ウ　普及を図るべき用語は、工夫してそのまま用いる。

アが適用されるのは「その用語でなくても意味が表せるもの」だけである。

原典は禁止も強制もしていない。 公用文作成の考え方 Ⅲ－４ には、ウ と エ が対称に置かれている。

ウ　重厚さや正確さを高めるには、述部に漢語を用いる
（references/source.json の kobun-sakusei-no-kangaekata）
エ　分かりやすさや親しみやすさを高めるには、述部に訓読みの動詞を用いる
（同）

原典の強度は「効果が得られることがある」── 推奨である。
このリポジトリは、ゲート1 で「述部が和語である」を検出し、ウ を必須にしていた（ACDR 0003 で、原典の規定ではなくこのリポジトリの決定だと書き直した）。
ACDR 0095 で、この検出を外した。 必須にした結果、「保持する」「認知する」「委譲する」のような、ふだん使わない漢語が文書にも応答にも増え、読み手にとって読みにくくなったためである。
いまは原典の強度に戻し、述部はふだん使う動詞で書く。

参照

- tool/cli/: 唯一の CLI。check ・ checks ・ reply ・ review と、references の4つの道具 get ・ validate ・ view ・ import を持つ ── どれも --json で機械が読む形が出る。終了コードは 0 指摘なし ／ 1 指摘あり ／ 2 誤用。道具の一覧に無い旗は断る
- tool/service/src/lib.rs: サービス層の道具の一覧。能力の正本であり、CLI と MCP はここから組む
- tool/business_logic/src/gate.rs: ゲート1の実行。拠って立つものは checks で見られる
- tool/business_logic/src/checks.rs: 7つの判定の実体
- tool/business_logic/src/unit.rs: 本文を判定の単位へ割る。引用と記号で囲んだ中を、書き手の文として数えない。HTML の頁は要素で割る（split_html）── タグを本文として読まず、コードの要素（pre ・ code）の中は記号で囲んだ中と同じ扱いにする。Markdown として読むと、閉じの の直後のタグを文字と数え、表に並べたコードの行を本文として判定する
- tool/business_logic/src/input.rs: reply ・ review が読む入力（フックの入力 ・ 判定基準 ・ 事例）。サービス層は入出力を保持しないので、ここが読み込む
- tool/data_access/: データアクセス層。ファイルと標準入力の入出力だけを持つ ── 業務ロジック層はここを経由して読み込む。files.rs ・ process.rs は skills-creator の雛形の複製、stdin.rs はこの Skill に固有である
- tool/business_logic/tests/: 事例（38件）。7つの判定と、単位の割り方（HTML の頁を含む）と、手順の変換を固定してある
- references/review-criteria.json: review が依頼文へ組む判定基準（8件）。形は references/review-criteria.schema.json が定義する
- references/document.json: review の手順（review-instruction）。形は references/document.schema.json が定義する
- references/source.json: 外部の原典の複製（git で追跡しない）。形は references/source.schema.json が定義する。取得し直すときは sources/MANIFEST.json の URL から原文を取得し、import で取り込んだ項目を source.json へ移す
- tool/business_logic/src/refs.rs ・ tool/service/src/refs.rs: references の4つの道具の実体。skills-creator の雛形の複製である
- tool/business_logic/src/instruction.rs: document の1件を、review の依頼文へ入れる本文へ変換する
- tool/mcp/: MCP の面（プレゼンテーション層）。同じ道具の一覧から組む** ── 能力を1行も複製しない
