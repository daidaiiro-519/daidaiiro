既存の Skill に契約の版3 を当てる

決めたこと

道具を持つ13の Skill の tool.json を契約の版3 にし、skills-creator の check が版3 を求め、契約の文書を references/contract/ の JSON を正本とする形に書き直す。

なぜ決める必要があるか

ACDR 0097 で、組み立て ・ テスト ・ フォーマットのコマンドを言語ごとの定義から tool.json へ移した（契約の版3）。いまの Skill の tool.json は版2 のままで、これらのコマンドを持たない。このままだと accept の試験と提供者の検証が、既存の Skill でコマンドを見つけられない。契約の文書（references/document.json の tool-contract）も、版2 と5言語の組を前提に書いてある。この ACDR はボード skills-creator-contract の移行の手順の C である。

どう変わるか

変更前と変更後

何が変更前変更後
13の Skill の tool.json契約の版2 ── cli と external だけ契約の版3 ── build ・ test ・ format を足す
check が求める版版2 以上版3。build ・ test ・ format の形も検査する
契約の文書の正本references/document.json の tool-contract の散文references/contract/ の JSON。tool-contract は理由と MCP の規約を持つ

比較した案と、採らなかった理由

案採らなかった理由
版2 の Skill も受け入れ、build ・ test ・ format が無ければ言語ごとの既定を使う既定を持つには、言語ごとの定義をまた持つことになる。ACDR 0097 で言語ごとの定義を無くした
platform-advisor と ux-advisor を、この ACDR でリファレンス実装から作り直す2件はデータアクセス層を持たない古い構成で、references の実装だけを複製し直しても組み立てられない。作り直しは advisor の作り直しの作業として、この後に行う（ボードの論点5）

下に並ぶのは、この決定を採ったときに何がどう変わるかである ── 上の決定の具体である。
