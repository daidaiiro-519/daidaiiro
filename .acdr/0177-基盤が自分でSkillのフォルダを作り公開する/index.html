基盤が自分で Skill のフォルダを作り公開する

決めたこと

基盤 schema-driven は、自分のソースから自分の Skill のフォルダを作り、自分のワークフローで3つの OS 向けに証明を付けて公開し、受け取る側の手順を公開した Release で通せたときに完成とする。

なぜ決める必要があるか

ボード schema-driven-release の論点0〜4で決めた。いままで基盤の Skill のフォルダの scripts/ と assets/ は、作業のたびに手で写していた。エンジンは版を答えず、公開の仕組み（release.yml と install スクリプト）は、skills-creator の dist が置いた古い形のままで、新しい形の基盤を公開できなかった。基盤の公開が上の Skill の置いた仕組みに乗っていたことは、上の Skill が基盤を使うという依存の向きとも逆だった。論点3の「基盤のエンジンの写し」を、上の Skill が版を指して受け取れる形にするのが、schema-driven の完成の残りである。

どう変わるか

変更前と変更後

何が変更前変更後
基盤の Skill のフォルダscripts/ と assets/ を手で写す。手順はどこにも無いcargo xtask skill --out <フォルダ> が、ビルドから scripts/bin/ ・ assets/ ・ dist.json までを作る
実行ファイルの置き場所scripts/schema-driven ・ scripts/schema-driven-mcpscripts/bin/schema-driven ・ scripts/bin/schema-driven-mcp。scripts/ の直下は読めるスクリプトのために空ける
版エンジンは版を答えない（--version は誤用）Cargo.toml の [workspace.package] の version の1か所。--version ・ serverInfo ・ dist.json がそこから取り、公開の前に tag と合わせて比べる
公開skills-creator の dist が置いた release.yml が、古い形（tool/ と bin/）を前提に全 Skill を公開する基盤専用の .github/workflows/schema-driven.yml が、tag schema-driven-v<版> で build ・ verify ・ publish ・ receive を行う
受け取る側との境目決まっていない版を指して取得できる ・ SHA-256 と証明で照合できる（ワークフローと tag まで）・ 展開すればそのまま動く ・ --version で版を答える、の4つの行為
古い形の公開の仕組みrelease.yml ・ install.sh ・ install.ps1消す。新しい形の導入は skills-creator の作業で作る

比較した案と、採らなかった理由

案採らなかった理由
skills-creator の配る手順で基盤も公開する基盤の公開が上の Skill に依存する。基盤は上の Skill を知らない、という向きに反する
シェルスクリプトか Makefile で Skill のフォルダを作るWindows で別に書くことになり、ツールは Rust だけで書く決まりにも反する
ワークフローの中だけに手順を書く手元では手で写す作業が残り、CI と手元で手順が分かれる
エンジンの実行ファイルに、配る仕事を足す利用者に配る実行ファイルに、配る側だけが使うコードが入る
古い release.yml に、基盤の tag の除外と、まとめ公開からの除外を足して残す古い形はまだ配布していないので、残すための手当てをしなくてよい。残すと基盤の tag でも動き、同じ tag の Release を2つのワークフローが作ろうとする
SHA256SUMS だけで照合する同じ Release から取るので、来歴（どのワークフローが作ったか）を確かめない

構造化データを正本として持つ基盤の Skill：schema-driven

目的

AI が扱うデータを、JSON Schema とそのインスタンスで持つときに使う。Markdown の文書は、書いたものが形を満たしているかを機械で確かめられない。スキーマとインスタンスなら、書いたその場で検証でき、参照と導出値も検査できる。

この Skill は基盤である。何のデータを持つかは決めない。

誰が何を持つか
基盤（この Skill）abstract スキーマ（assets/ の契約）と、それを版ごとに守るエンジン（共通ツール9つ）
使う側（基盤の上に作る Skill ・ Agent）concrete スキーマ ・ インスタンス ・ ページテンプレート ・ 部品のカタログ（assets/catalog/）・ 自分の能力を持つ実行ファイル（任意）

使う側は、基盤の能力をそのまま使い、自分の能力は自分の実行ファイルとして持つ。 基盤は使う側の実行ファイルを起動しない。使う側が、自分の実行ファイルを直接呼ぶ。ページの見た目と操作は、使う側の Skill のフォルダにある部品のカタログが持つ。基盤はカタログの中身を持たず、カタログとデザインシステムが守る形だけを持つ。abstract スキーマを書き換えると、エンジンが扱えなくなる。

役割

- concrete スキーマが abstract スキーマの版に従っているかを検査する
- スキーマからインスタンスを作成し、未記入のプロパティと、その x-prompt を返す
- JMESPath 式で値を取得し、JSON Patch で更新する。更新は、検証エラーが無いときだけ書く
- ディレクトリのインスタンスを検証し、x-ref（参照）と x-derive（導出値）を検査する
- 検査を通ったインスタンスのパスとハッシュ値を、承認記録へ書く
- 検証を通ったインスタンスを、ページテンプレートと、使う側の Skill のフォルダの部品のカタログでページへ描画する

Step 1: concrete スキーマを書き、abstract に従っているかを検査する

concrete スキーマは、abstract スキーマのインスタンスである。インスタンスと同じ共通ツールで作り、書き進める。中身（何を持つか）は、作る側が決める。

scripts/bin/schema-driven create --schema schema-driven/abstract@v1 --path <Skill のフォルダ>/assets/<種類>.schema.json
scripts/bin/schema-driven prompt --schema schema-driven/abstract@v1 --property /<欄>
scripts/bin/schema-driven update --path <スキーマ> --patch '<JSON Patch>'

create は、根に $schema と x-abstract を書いて枠を作り、未記入の欄を x-prompt と一緒に返す。根に置く3つの欄は次のとおりで、書き方の決まりは assets/meta-schema.json が持つ。

欄書くもの
$schemaJSON Schema の標準の dialect https://json-schema.org/draft/2020-12/schema
x-abstract従う abstract の版 schema-driven/abstract@v1
$idこのスキーマの名前「<Skill の名前>/<種類>@<版>」。インスタンスを作るスキーマ（x-generates を持つもの）は必ず書く

$id は create のあとに書く。インスタンスを作るスキーマは、根の properties に kind と $schema を置き、$schema の const に自分の $id を書く。

プロパティごとに description と x-prompt（read と write）を書き、参照には x-ref、導出値には x-derive を付ける（assets/annotations.schema.json）。

ほかのスキーマの定義を使うときは、$ref をファイル名ではなく名前で書く。同じ Skill のスキーマなら、$id を基準に JSON Schema の規則で解けるので、「<種類>@<版>」だけでよい（例：term@v1#/$defs/short）。ファイル名を変えても、参照は切れない。

scripts/bin/schema-driven check-schemas --dir <スキーマのディレクトリ>

findings が空なら、契約に従っている。版を書いていないスキーマと、エンジンが扱わない版のスキーマは、検査せずに指摘する。

スキーマのフォルダに公開の記録 published.json（assets/published.schema.json）があれば、check-schemas は公開した版の指紋といまの中身を比べる。

状態check-schemas の返し方
公開した版の中身が変わったfindings に「公開した版が書き換えられている」
公開した版が消えたfindings に「公開した版が無い」
まだ記録に無い名前unpublished に名前と指紋。公開するときに、そのまま記録へ足す

指紋は、キーの順と空白に左右されない SHA-256 である。名前（$id）を持つ JSON は、ファイル名が .schema.json で終わらなくても対象になる。

Step 2: インスタンスを作成し、x-prompt を読む

scripts/bin/schema-driven create --schema <スキーマ> --path <インスタンス>
scripts/bin/schema-driven prompt --schema <スキーマ> --property /<プロパティ>

create は、必須のプロパティを空のままにしてインスタンスを作り、未記入のプロパティを x-prompt と一緒に返す。インスタンスの $schema には、スキーマの名前を書く。x-prompt の write の決まりに従って値を決める。

インスタンスを読むツールは、$schema の名前から次の順にスキーマを引く。

名前引く先
schema-driven/…エンジンが持つスキーマ（ページテンプレート ・ カタログの枠 ・ デザインシステムなど）。--skill を渡さなくても引ける
--skill の Skill の名前で始まるものその Skill の assets の下の *.schema.json のうち、$id が同じもの
ほかの Skill の名前で始まるものどの Skill のスキーマかを返して止める。その Skill を --skill に渡して検査し直す
JSON Schema の dialect（concrete スキーマ）x-abstract に書いた abstract スキーマ。エンジンが持つので、--skill を渡さなくても引ける
名前の形でない値断って「スキーマの名前でない」を返す。パスでは引かない

同じ名前のスキーマが2つあれば、どちらも使わずに止める。

Step 3: JSON Patch で更新する

scripts/bin/schema-driven update --path <インスタンス> --patch '<JSON Patch>' [--hash <読んだ時点のハッシュ値>]

未記入以外の検証エラーがあれば、書かずに errors を返す。直して、もう一度送る。未記入が残っているときは書いて、残りを x-prompt と一緒に返す。

値を読むときは get を使う。

scripts/bin/schema-driven get --path <インスタンス> --query '<JMESPath 式>'

Step 4: ディレクトリを検査する

scripts/bin/schema-driven check --dir <インスタンスのディレクトリ>

終了コード 0 は、検査を最後まで実行できたことだけを示す。 合格かどうかは、instances の errors と unfilled、findings の status（合格 ・ ずれ ・ 確かめ直し など）で見る。

Step 5: カタログを置き、ページテンプレートを書き、描画する

ページの見た目と操作は、使う側の Skill のフォルダの assets/catalog/ に置く部品のカタログが持つ。基盤はカタログの中身（部品の名前 ・ HTML ・ CSS ・ JS ・ トークンの値）を持たない。render は、--skill に渡した Skill のフォルダから、描画のたびにカタログを読む。

ファイル中身守る形
assets/catalog/catalog.schema.json部品の一覧。$defs のキーが部品の名前で、値が入力の形 ・ 説明 ・ 状態ごとの振る舞い（x-states）assets/catalog.schema.json（schema-driven/catalog@v1）
assets/catalog/parts.html部品の HTML。部品ごとに <template id="部品の名前"> を1つ置き、ほかにページの page と節の section を置くプレースホルダーは {{名前}}
assets/catalog/design-system.jsonトークンの値と、コントラストを確かめる色の組assets/design-system.schema.json（schema-driven/design-system@v1）
assets/catalog/catalog.css部品の見た目。無くてもよい色の値を直接書かず、var(--トークンの名前) で引く
assets/catalog/catalog.js部品の操作。無くてもよい―

基盤は、テンプレートのプレースホルダーへ次の値を入れる。

テンプレート基盤が入れる値
page{{title}}（インスタンスの名前）・ {{tokens}}（トークンから作った CSS の変数）・ {{style}}（catalog.css）・ {{script}}（catalog.js）・ {{sections}}（節）。ほかのプレースホルダーには、ページテンプレートの head の同じ名前の値
section{{heading}}（見出し）・ {{help}}（説明）・ {{body}}（節の要素）
部品ページテンプレートに書いた入力の値を、同じ名前のプレースホルダーへ入れる。文字はエスケープする。入力の形の contentMediaType が image/svg+xml の入力だけは、検査した SVG をそのまま入れる

デザインシステムについて基盤が確かめるのは、形式 ・ 参照（{名前} の指す先があるか）・ 参照が循環しないこと ・ contrast に書いた組のコントラスト（文字 4.5:1、部品の境界 3:1。明と暗の両方）と、カタログの CSS に色の値を直接書いていないことだけである。トークンの名前と層の分け方は、使う側が決める。

ページテンプレートは、節の並びと、節ごとに置く部品と、値を取る JMESPath 式だけを書いた JSON である（assets/page.schema.json）。部品は、カタログの部品の名前で呼ぶ。HTML ・ CSS ・ JS は書かない。

scripts/bin/schema-driven --skill <Skill のフォルダ> render --dir <インスタンスのディレクトリ> --pages <ページテンプレートのディレクトリ> --out <出力>
状態render の返し方
カタログが無い1ページも書かずに「部品のカタログを読めない」
カタログが枠かデザインシステムの契約を満たさない1ページも書かずに「部品のカタログが契約を満たさない」
ページテンプレートに、カタログに無い部品 ・ 入力の欠け ・ page に無い head の名前がある1ページも書かずに「ページテンプレートが契約を通過しない」
ページテンプレートの指定が無い種類がある1ページも書かずに「ページテンプレートの指定が無い種類がある」
検証エラーのあるインスタンスがある1ページも書かずに「検証を通過しないインスタンスがある」

内容が変わったページだけを書くので、同じ入力から何度描画しても結果は変わらない。インスタンスの値は、HTML を含んでいても文字として出る。

Step 6: 承認を記録する

scripts/bin/schema-driven approve --dir <インスタンスのディレクトリ>

検証エラー ・ ずれ ・ 未記入が1件でもあれば、承認記録を書かない。

出力形式

どのツールも、標準出力へ JSON を1つ書く。

終了コード意味出力
0実行できた{"ok": true, …}。中身はツールごとに違う
1拒否した ・ 失敗した{"ok": false, "reason": …, "detail": …, "errors": […]}
2使い方が違う{"ok": false, "reason": "使い方が違う", "detail": …, "tools": […]}

動詞なしの --json だけは、ツールの一覧を {"ok": true, "findings": [], "data": {"tools": […]}} で返す。

ガードレール

- abstract スキーマを、使う側で書き換えない。エンジンは、版ごとの abstract スキーマに対する振る舞いだけを保証する
- 公開した版のスキーマを、消さず書き換えない。中身を変えるときは、版を上げた新しい名前（@v2）で足す。同じ名前で中身が変わると、前に書いたインスタンスが別のスキーマで検査される。公開するときは、その版の指紋を published.json に記録し、配る前の検査で確かめる
- インスタンスの $schema に、Skill の置き場所へのパスを書かない。名前で指す。配った先では、Skill は別の場所に置かれる
- ファイルを手で書き換えて、update を通さずにインスタンスを直さない。update を通さないと、書いたその場の検証が行われない。手で直したときは、check で確かめ直す
- check の終了コードだけで合格と判断しない。0 は実行できたことだけを示す
- 検証エラーのあるインスタンスを、描画や承認で先へ進めない。基盤はどちらも止める
- ページテンプレートに、HTML ・ CSS ・ 色の値を書かない。見た目と操作は、Skill のフォルダのカタログ（assets/catalog/）だけが持つ。ページテンプレートに書くと、カタログを替えても見た目が揃わない
- 部品のカタログは、枠とデザインシステムに従う。部品ごとに名前 ・ 入力の形 ・ 説明 ・ 状態ごとの振る舞いを書き、CSS に色の値を直接書かず、文字と背景 ・ 部品の境界と背景の組を contrast に書く
- 基盤の中心は、ファイルを直接扱わない。入出力はポートを通す
- 基盤はネットワークに出ない。依存の版は1か所で決める
