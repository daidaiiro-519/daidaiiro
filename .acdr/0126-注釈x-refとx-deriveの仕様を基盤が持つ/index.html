注釈 x-ref と x-derive の仕様を基盤が持つ

決めたこと

注釈 x-ref と x-derive の形と意味を、schema-driven が references/annotations.schema.json として持ち、検査はこの仕様だけに従って実装する

なぜ決める必要があるか

2回目で、x-ref と x-derive による検査を Rust で実装する。仕様はボード schema-driven-base の論点2の表にあったが、要約だった。ユースケース駆動のスキーマが実際に使うキーと比べると、only ・ label ・ where_derive ・ expect ・ title が表に無く、意味が決まっていないキーもあった。さらに、meaning ・ meanings ・ meaning_key は用語集の語を指すための作りで、「基盤は宣言の形を認知しない」（論点1）と食い違っていた。このまま実装すると、意味を推測で埋めるか、試作のコードを仕様の代わりに読むことになる。そこで、キーごとの型と意味を JSON Schema として基盤に置き、用語集に寄ったキーは、指す先の任意の場所を確かめる accept にまとめる

どう変わるか

変更前と変更後

何が変更前変更後
x-ref と x-derive の仕様ボードの論点2の表（要約）と、試作のコードschema-driven の references/annotations.schema.json。キーごとに型 ・ 説明 ・ x-prompt を持つ
各キーの x-promptキーが何かを一言で書く指示として書く。read は値の解釈の仕方と、道具が何を検査して何を出すか。write はいつ書くか ・ 値の形 ・ 決め方の手順 ・ 例 ・ よくある誤り。各キーに examples も持つ
指す先の種類を確かめるキーmeaning ・ meanings ・ meaning_key（用語集の形を前提にする）accept（at：指す先の項目の中の場所、in：許す値）
ユースケース駆動のスキーマmeaning ・ meanings ・ meaning_key を使う段3（concrete を本物の基盤の上に作り直す）で accept に書き直す。それまでは今のまま

比較した案と、採らなかった理由

案採らなかった理由
ボードの論点2の表を仕様として、そのまま実装する表が要約で、実際に使うキーの一部と、各キーの細かい意味が無い。実装の側で推測することになる
試作（Python の base7.py）の振る舞いを仕様にする試作は検討のための見本で、仕様ではない。試作の誤りもそのまま写る
meaning ・ meanings ・ meaning_key をそのまま基盤のキーにする用語集の形（語が意味の一覧を持ち、意味が種類を持つ）を基盤が前提にすることになり、論点1と食い違う
