Python の組を契約の版1で起こす

決めたこと

skills-creator に Python の組を加え、契約の版1 を満たす作業型の Skill を Python で生めるようにする。

なぜ決める必要があるか

利用者は、skills-creator を配布し、利用者が使いやすい言語の組から Skill を作れる状態を目標にした。いまの組は Rust だけで、Rust を書かない利用者は Skill の道具を作れない。対象の言語は Rust ・ Go ・ Python ・ TypeScript ・ C# と決め、Python から起こすと決めた（案A の承認）。契約が規定するのは呼び方と成果物の形だけである（ACDR 0059）。そこで Python の組は、Rust の組と同じ振る舞いを別の言語で満たす雛形を持つ。中の構成は指定しない。起動は uv が依存を揃えてから行う形にした。検査の道具は、処理系を介して起動する形の引数の中の経路を解けなかった。この経路を解くようにした。

どう変わるか

比較した案と、採らなかった理由

案採らなかった理由
Python の組も契約の版2（references の4つの道具）で起こす版2 の実体（refs.rs）は JSON Schema の検査と HTML の描画を持ち、移すと雛形が大きくなる。版1 で作業型を先に通し、版2 は後の ACDR で足す（案A の承認）
FastMCP（デコレータで道具を宣言する高水準の API）で MCP の面を組む道具をその場で宣言するので、能力の正本が CLI の一覧と2か所になる。Rust の組が #[tool] マクロを使わないのと同じ理由である

目的

新しいSkillsを作成したいとき、Skillのテンプレートが欲しいとき、「スキルを作って」「Skills作成」「新しいスキル」と言われたとき、またはベストプラクティスに従ったSkillフォルダ構成を生成したいときに使う。

役割

- スキル設計のコンサルタントとして要件をヒアリングする
- ベストプラクティスのフォルダ構成を遵守した実装者として動く
- SKILL.mdの各セクション（目的・役割・実行手順・ガードレール）を適切に記入するファシリテーターとして振る舞う
- 作成後はスキルの動作確認方法をユーザーに伝える

処理対象と成果物

処理対象

新規Skillの要件（スキル名・トリガー条件・スコープ・テンプレートの要否・追加フォルダの要否）。

成果物

ベストプラクティスに従ったフォルダ構成とSKILL.mdを備えた新しいSkill（プレースホルダー付きスケルトンから量産）。

入力の想定

受け取る情報解釈・既定値
新規Skillの要件（スキル名・トリガー条件・スコープ・テンプレートの要否・追加フォルダの要否）要件が明確でない場合は作成を開始せず、先にヒアリングを完了させる。

Skill の型

skills-creator は、Skill を型と言語の組の組み合わせで生む（ACDR 0060 ・ 0061）。型は、その Skill を使うときに誰が何を作るかで決まる。

型定義生み方
作業型（work）エージェントが成果物を作る作業の手順を持ち、途中で検査や生成の道具を使う共通の一式に、見本の道具を置く
生成型（generate）他から入力を渡され、道具が成果物を組んで返す。作業の手順は保持しない入力と出力のスキーマ ・ 入力の検査 ・ 組む道具（雛形はまだ無い）
助言型（advisor）相談を受け、原典の判断基準に照らして答える雛形を丸ごと固定する（判断基準と回答のスキーマ ・ 回答の道具 ・ 試験）

助言型は、references/types/advisor/procedure.md の9段の手順で作り、skills-creator accept <フォルダ> の受け入れの検査（機械の7件）を実行する。 判断基準は、原典が名前を付けて立てている概念を1件の単位にし、学習ノートの言葉だけで書く。

道具を持つ Skill は、道具の契約に従わせる。
契約は references/tool-contract.md が規定する ── 呼び方を1つに固定し、
能力をサービス層の道具の一覧に1度だけ書かせて、CLI と MCP をその一覧から組ませる。

契約が規定するのは、呼ぶ側から観察できるものだけである（ACDR 0036）。

道具の契約：tool-contract

目的

Skill が道具（実行ファイル）を伴うとき、呼ぶ側に形を推測させないために使用する。

道具ごとに呼び出し方の形が違うと、呼ぶ側は呼ぶたびに本文を読み直す。
契約は、呼び方を1つに固定する。

契約は、呼ぶ側から観察できるものだけを規定する（ACDR 0036）。道具を書く言語と、
配布するかどうかは、利用者に委ねる。言語ごとの実装の形は言語の組が持ち
（いまは Rust と Python。references/profiles/<言語>.md）、配布は任意の機能として
references/distribution.md が持つ。

置く先中身
契約（この文書）CLI と MCP の2つのプレゼンテーション層と起動のコマンド ・ CLI の規約 ・ 1つの道具の一覧から CLI と MCP を組む ・ MCP の規約 ・ Skill のフォルダの求め方 ・ 外部の道具 ・ 1段目の検査
言語の組組の定義（references/profiles/<言語>.profile.json）・ 実行ファイルの置き場所 ・ 雛形とその構成（推奨） ・ 組み立てのコマンド ・ 2段目の検査
配布（任意）配布物 ・ 導入スクリプト ・ 組み立ての定義

言語の組を作ってよい言語の条件は、公式の MCP の SDK が在ることだけである。
組が持つのは、雛形 ・ 組み立てのコマンド ・ ソースの検査の3つである。

原則

能力は1つ、呼び出し方は複数である。

能力を1つの道具の一覧に1度だけ書き、CLI と MCP はその一覧から組む。
能力を2か所に書くと、片方だけが古くなる。

呼び出し方が欠けても、能力は欠けない。
MCP の実装が無い環境では、MCP サーバーは立たず、CLI だけが動く。

findings は誤りではない。 検出が在っても isError は偽のままにする ── 違反の検出は、道具が正しく動作した結果である。

サービス層を置くのは、プレゼンテーション層が2つ在るからである。 CLI と MCP の違いから業務ロジックを隔離し、道具の一覧を1か所に保つ。

データアクセス層を置くのは、入出力を1か所に集めるためである（ACDR 0058）。業務ロジック層は、読んだ値を受けて判定するだけになる ── データを処理する Skill が増えても、変わるのはデータアクセス層だけである。データアクセス層に判定を置かない ── 何を読み、読んだものをどう扱うかは業務ロジック層が決める。子プロセスの規律（上の節）は、データアクセス層が1回だけ実装する。

業務ロジック層に、集約 ・ エンティティ ・ リポジトリの型を作らない。 この層が置くのは、業務の状態を保持しない変換の関数である ── 層の名前から連想してドメインモデルの型を導入すると、使わない抽象が増える。

この構成を、ヘキサゴナルアーキテクチャともクリーンアーキテクチャとも称さない。 両者の核心は依存の向きを逆にすること（内側が抽象を定義し、外側が実装する）であり、この構成はそれを保持しない ── 業務ロジック層がデータアクセス層を直接呼ぶ。称すると、備えていない性質を名前で主張することになる。

ポートを導入するのは、業務ロジック層が使う外部を差し替える必要が生じたときに限る。 それまでは、実装が1つしかない抽象を作らない。ドメインモデルを必要とする Skill が現れたら、その Skill の道具だけをポートとアダプターへ移す ── 方式は Skill ごとに選んでよい。

どう保つかは、言語の組が決める（Rust は crate の境界に置き、各 Cargo.toml が依存の向きを宣言する。入出力の混入は --layout 1 の2段目が検出する）。
