抽象概念の土台と Semantic Agent Schema の設計を分ける

決めたこと

抽象概念の土台を、どの事業にも使う一般の概念だけを持つページにし、Semantic Agent Schema に当てた結果は新しい「Semantic Agent Schema の設計」のページに1か所でまとめる。

なぜ決める必要があるか

土台が一般の概念と、Semantic Agent Schema に当てた結果（「この基盤は型1」・ポートの持ち主の表・layout.json・基盤との対応）を同じページに持っていた。そのため事業の設計判断が概念として読まれ、「文脈は1つ」の誤り（10-30 に利用者が取り消し）が起きた。具体（ディレクトリ・ドメインモデル・ER 図・スキーマの構成）は承認待ちのページを含めて6か所以上に分かれ、利用者から「いろんなところを見ないといけないのがしんどい」と言われた。ガイドのボードの Q8（土台とガイドの分け方と往復）の答えに合わせる。

どう変わるか

変更前と変更後

何が変更前変更後
概念の置き場所抽象概念の土台に、一般の概念と Semantic Agent Schema に当てた結果が混ざる。抽象概念の土台は一般の概念だけ。例は事業の名前の無い「業務領域 A〜E」で書く。
具体の置き場所ER 図・スキーマの案・エンジンの部品の案・ポート表・ディレクトリが別々のページにある。docs/design/ の1ページに9つのタブでまとめ、タブごとに状態（決まった・案・候補・仮・未決）と決める場所を書く。
意味の境界の扱い「文脈は広い1つから始める」とだけ書き、事業全体を1つの文脈と読めた。「意味の境界を先に、中身はあとで」を概念として書き、広く引くのは事業全体ではなく、同じ語が同じ意味で通じる範囲までとする。
まだ決まっていない概念どこにも書かれていない。土台の「育てている所」に問いと、決めるボードの論点を並べる。

比較した案と、採らなかった理由

案採らなかった理由
当てた結果を、土台の中の別のタブに置く。1つの正本と1つの build.py に2つのモデルが残り、文脈を決めるたびに土台を直すことになる。
「この基盤は型1」の1文だけを直す。ポートの表と layout.json が土台に残り、文脈が決まるたびに土台が変わり続ける。具体が分かれている問題も残る。
「意味の境界を先に」をガイドの Q3 の手順に移す。利用者が「これは抽象概念の話」と判断した。手順に置くと、ガイドを使わない設計からは見えない。
具体のページを作らず、承認待ちのページへのリンク集にする。見る場所の数が減らず、どれが決まりでどれが案かがページごとに違う書き方のまま残る。
