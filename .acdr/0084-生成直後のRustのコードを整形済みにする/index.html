雛形から生成した直後の Rust のコードを、整形済みにする

決めたこと

skills-creator が生成した直後の Rust の Skill は、整形の検査（cargo fmt --check）に合格する。

なぜ決める必要があるか

利用者から「現在は skills-creator の契約通りに作成できてるんですかね？」と問われ、usecase-advisor を同じ名前で雛形から生成し直して現物と比べた。差は2点だった。1点目は、雛形から生成した直後の Rust のコードが cargo fmt --check に7か所で不合格になることである。リポジトリの規則（.coding-rules の「整形されている」）にその場で不合格になるので、usecase-advisor は手で整形していた（6e0a4c4e）。これから作り直す ddd ・ qa ・ platform ・ ux も同じ手作業になる。提供者の検証も整形を検査していなかったので、検出できなかった。2点目は、usecase-advisor の SKILL.md が archive の置き場所を旧い書き方（コードの記法）のまま保持していたことである。ACDR 0076 で雛形の書き方を改めたが、反映していなかった。

どう変わるか

変更前と変更後

何が変更前変更後
生成した直後の Rust のコードcargo fmt --check に7か所で不合格（work 型 4ファイル ・ advisor 型 3ファイル）合格する
MCP の面の use の並びSkill の crate の use を外部の crate と同じ組に置く（接頭辞の文字で並びが変化する）別の組に置く。接頭辞に依存せず、並びが一定になる
言語の組の定義組み立てと試験のコマンドだけを保持する整形の検査のコマンド（format）も保持できる。Rust は cargo fmt --check
提供者の検証組み立て ・ 試験 ・ check ・ accept加えて、組が format を保持するときは整形を検査する
usecase-advisorMCP の面の use の並びと、SKILL.md の archive の書き方が雛形と相違する雛形から生成したものと、差し込み場所の中身以外は一致する

比較した案と、採らなかった理由

案採らなかった理由
scaffold が生成したあとに rustfmt を実行するscaffold が Rust の処理系の道具に依存し、言語の組ごとの整形の道具を知ることになる。雛形そのものが整形済みなら、追加の道具は必要ない
生成した Skill を、その都度手で整形する作り直す4件で同じ作業を繰り返す。雛形と生成物の差も毎回生じ、契約どおりかの比較が成立しない
5言語すべての整形の検査を同時に加える各言語の整形の道具（gofmt ・ ruff ・ prettier ・ dotnet format）を提供者の環境に準備する作業が必要になる。欄を用意したので、組ごとに追加できる

下に並ぶのは、この決定を採ったときに何がどう変わるかである ── 上の決定の具体である。

cargo install --path tool/cli --root . --target-dir tool/target
cargo run -q --release --manifest-path tool/Cargo.toml -p sc_cli --example provider -- verify --skill_root . [--work <作業場所>] [--json]

name: "usecase-advisor"
description: "ユースケースについての概念相談(「〜とは」)・判断相談(「〜すべきか」)・設計相談(「〜をどう組み立てるか」)を受けたときに使う。アリスター・コーバーン『ユースケース実践ガイド 復刻版』の判断基準に根拠を示して回答し、回答は構造化した JSON で組んで HTML で渡す。"

ユースケースの相談に、判断基準の根拠を示して答えるのを担当する助言型の Skill：usecase-advisor

目的

ユースケースについての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。アリスター・コーバーン『ユースケース実践ガイド 復刻版』の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- ユースケースのアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
概念相談「〜とは」「〜の違いは」concept定義 ・ 具体例
判断相談「〜すべきか」「この案でよいか」judgment比較した案 ・ 判断の道筋
設計相談「〜をどう組み立てるか」design設計の手順

この領域での相談の例：「主アクターとは何か」（概念）・「このユースケースは目的レベルが低すぎないか」（判断）・「この業務の拡張条件をどう洗い出すか」（設計）

入力の想定

受け取る情報解釈・既定値
相談の種類（概念相談 ・ 判断相談 ・ 設計相談）明示されなければ、相談の文の形から判定する
相談の対象と状況明示されなければ相談者に確認する。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、道具で1件ずつ取り出して読む。読む前に回答を始めない。

usecase-advisor get criteria <id>        判断基準を1件取り出す（JSON）
usecase-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

usecase-advisor validate --kind answer --file <回答.json>      欄の欠けを検出する
usecase-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く
- 図（figure）は節点と辺で宣言する。SVG は任意である
- AI が作業するときの注意（ai_cautions）は、一般論ではなく、違反しやすい点と検査する方法の組で書く

出力形式

回答の JSON と、描画した HTML である。 人は HTML で読む ── チャットに回答の文章を流さない。

置くもの内容
結論判定と1文の結論。最初に読む
図 ・ 比較 ・ 道筋 ・ 手順結論に至った構造。種別で必須の欄が変わる
根拠判断基準の id と、その記述の引用
次にすること動詞で始まる行動

ガードレール

- 判断基準を道具で読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は criteria から引用し、勝手に言い換えない
- 判断相談では必ず判定理由を示す。「〜です」で終わらせない
- アンチパターンに該当する場合は必ずリスクと代替案を組で示す。判断基準に代替案が無いときは、回答の側で組み立て、推測であることを明示する ── 判断基準は原典に無い文を保持しない
- 回答は validate に合格してから渡す。 欄の欠けを機械で検出できる形にしたので、手で確認しない
- 判断基準は原典の複製ではない。 原典ごとの学習ノートから、概念ごとに移したものである ── 原典の文そのものを参照していると断言しない。引用は「判断基準の記述」として示す
- 専門用語は使ってよいが、初出時は文脈 ・ 具体例を添える
