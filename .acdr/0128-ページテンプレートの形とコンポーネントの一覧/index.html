ページテンプレートの形とコンポーネントの一覧

決めたこと

ページテンプレートの形を schema-driven の references/page.schema.json として持ち、ページテンプレートは節 ・ コンポーネント ・ JMESPath 式だけで書く。コンポーネントは19種類にし、見本の60の部品はその内側で使う

なぜ決める必要があるか

ボード schema-driven-build の論点4で、ページテンプレートは節の並び ・ コンポーネント ・ JMESPath 式だけを書くと決めた。その要求事項として、page.schema.json とコンポーネントの一覧を ACDR で決める。見本の60の部品には、th ・ tr ・ td ・ kv-row のように、書き手が選ぶ必要のない細かい部品が多い。書き手が選ぶものを意味の単位のコンポーネントにまとめると、同じ意味のものが同じ見た目になる。ページテンプレートも JSON のインスタンスなので、schema-driven 自身の作成 ・ 検証 ・ x-prompt で書ける（実際に作成と更新を試し、未記入と x-prompt が返り、誤った入力が拒まれた）

どう変わるか

変更前と変更後

何が変更前変更後
ページテンプレートの形見本の独自の書き方（92 種類のキー。独自の道 ・ 条件 ・ 繰り返し）kind ・ tones ・ head ・ sections と、要素ごとの component ・ show ・ each。値は JMESPath 式、決まった文字は {"text": …}
書き手が選ぶもの60の部品（p と s で HTML の部品を直接選ぶ）19のコンポーネントから選び、部品はその内側で使う。文の中に置くものは text ・ strong ・ sentence ・ pill ・ ref ・ missing ・ yes-no ・ code ・ note。ブロックとして置くものは paragraph ・ subheading ・ kv ・ table ・ filter-table ・ cards ・ list ・ fold ・ steps ・ json
基盤に置かないもの見本の tchip ・ design-only（テスト条件の札）と図開発の concrete の側（テスト条件と、図の入力の組み立ては開発の側の機能）

比較した案と、採らなかった理由

案採らなかった理由
60の部品をそのまま書き手に選ばせるth ・ td のような細かい部品まで書き手が組むことになり、同じ意味のものがページごとに違う組み方になる
コンポーネントを kind ごとに作る（ユースケースの手順用 ・ 用語集用など）基盤が宣言の形を知ることになる。steps のように、意味の単位（手順と分かれ道）で一般的に作る
