なぜ決める必要があるか

道具の契約：tool-contract

目的

Skill が道具（実行ファイル）を伴うとき、呼ぶ側に形を推測させないために使用する。

道具ごとに入口の形が違うと、呼ぶ側は呼ぶたびに本文を読み直す。
契約は、呼び方を1つに固定する。

原則

能力は1つ、呼び出し方は複数である。

能力を宣言に1度だけ書き、CLI と MCP はその宣言から組む。
能力を2か所に書くと、片方だけが古くなる。

呼び出し方が欠けても、能力は欠けない。
MCP の実装が無い環境では、MCP サーバーは立たず、CLI だけが動く。

規定するもの

規定中身

置き場所役割ごとに階層を分ける（下の表）── 中身を開かずに、どれが入口かを判定できる形にする
宣言tool/declare/ の tools()。名前 ・ 引数 ・ 説明 ・ 実体 ・ 人が読む形
入口tool/cli/ が唯一。<Skill の名前> <動詞> [対象…] [--json]

標準入出力の規約 ── 原典

modelcontextprotocol.io/specification/2025-06-18/basic/transports（2026-09-24 取得 ・ 297行）から引用する。

行原文
27The server reads JSON-RPC messages from its standard input (stdin) and sends messages to its standard output (stdout).
31The server MAY write UTF-8 strings to its standard error (stderr) for logging purposes.
33The server MUST NOT write anything to its stdout that is not a valid MCP message.

だから、道具の中で println! を使うと MCP サーバーが壊れる ── 子プロセスの標準出力も同じである（Stdio::piped() かファイルで受ける）。

誤りの返し方 ── 原典

原典は2つを分けている（specification/2025-06-18/server/tools:389、2026-09-24 取得）。

種類原文この契約での対応
Protocol ErrorsStandard JSON-RPC errors for issues like: Unknown tools, Invalid arguments引数の不足 ・ 知らない動詞。SDK が返す
Tool Execution ErrorsReported in tool results with isError: trueok が偽のとき（読めない ・ 誤用）

findings は誤りではない。 検出が在っても isError は偽のままにする ── 違反の検出は、道具が正しく動作した結果である。

予期した失敗は、道具の結果として返す。 ok が偽なら CallToolResult の is_error を立て、こちらの文言を content に載せる ── 異常終了（panic）させると、呼ぶ側には理由が届かない。雛形の mcp.main.rs.tmpl がこの形を持つ。

型は緩く受ける。 呼ぶ側は JSON の値を渡すので、数を文字列で包むことを強制しない（実測: timeout に 30 を渡すと、検証が不合格になっていた）。まとめて受ける引数は配列も受ける。

戻り値は、構造としても乗せる

原典が両方を求めている（server/tools:296・298、2026-09-24 取得）。

Structured content is returned as a JSON object in the structuredContent field of a result.
For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block.

{ok, findings, data} は JSON なので、そのまま structuredContent に乗る。雛形の MCP の面は、同じ値を structured_content と、文字列にした content の両方へ載せる。

子プロセスを起こすときの規律

道具が外のコマンドを実行するなら、3つを必ず指定する。どれも実測で欠陥が出た項目である（2026-09-24、9つの Skill で6か所）。

指定欠けると何が起きるか
.stdin(Stdio::null())入力を待つ道具が、制限時間まで停止する（実測 5秒の設定で5.1秒）
制限時間（try_wait で待ち、過ぎたら kill）停止した子プロセスを、永久に待つ
.stdout(…) ・ .stderr(…) の指定子プロセスの出力が、こちらの標準出力へ流れる ── MCP サーバーでは JSON-RPC の流れへ混入する

出力をまとめて受け取らない。 ファイルへ書き出し、上限までしか読まない ── 受け取ると、道具が出した量がそのままこちらの記憶に載る（実測: 100MB の出力で最大常駐が 306MB、ファイルへ書き出すと 24KB）。

新規Skillのテンプレート生成を行うSkill：skills-creator

目的

新しいSkillsを作成したいとき、Skillのテンプレートが欲しいとき、「スキルを作って」「Skills作成」「新しいスキル」と言われたとき、またはベストプラクティスに従ったSkillフォルダ構成を生成したいときに使う。

役割

- スキル設計のコンサルタントとして要件をヒアリングする
- ベストプラクティスのフォルダ構成を遵守した実装者として動く
- SKILL.mdの各セクション（目的・役割・実行手順・ガードレール）を適切に記入するファシリテーターとして振る舞う
- 作成後はスキルの動作確認方法をユーザーに伝える

処理対象と成果物

処理対象

新規Skillの要件（スキル名・トリガー条件・スコープ・テンプレートの要否・追加フォルダの要否）。

成果物

ベストプラクティスに従ったフォルダ構成とSKILL.mdを備えた新しいSkill（プレースフォルダー付きスケルトンから量産）。

入力の想定

受け取る情報解釈・既定値
新規Skillの要件（スキル名・トリガー条件・スコープ・テンプレートの要否・追加フォルダの要否）要件が明確でない場合は作成を開始せず、先にヒアリングを完了させる。

実行手順

Step 1: 要件のヒアリング

スキル名・トリガー条件・スコープ（プロジェクト専用/グローバル）・テンプレートの要否・追加フォルダの要否を確認する。不明な項目はユーザーに質問する。

Step 2: フォルダ構成を決定する

folder-structure.mdを参照し、ヒアリング内容に応じてミニマム構成かフル構成かを選ぶ。

Step 3: フォルダ構成を作成する

決定した構成に従い、SKILL.mdと必要ならreferences/等のフォルダを作成する。

Step 4: SKILL.mdを生成する

references/skill-template.mdを読み込む。各{{...}}プレースホルダーは、そこに書かれた指示を読めばそのまま記入できる自己完結の形式になっているため、別途定義票を参照する必要はない。ヒアリング内容に従って全プレースホルダーを記入し、{{スコープ}}/skills/{{スキル名}}/SKILL.mdとして保存する。

Step 5: テンプレートファイルを生成する（必要な場合のみ）

出力ドキュメントを生成するスキルの場合、プレースホルダー付きのスケルトンテンプレートを{{スコープ}}/skills/{{スキル名}}/references/template.mdとして作成する。

Step 6: 完成確認

作成したファイル一覧を表示し、スキルの呼び出し方をユーザーに伝える。

出力形式

作成したファイル一覧を表示し、スキルの呼び出し方をユーザーに伝える。

道具を伴う Skill

道具を持つ Skill は、道具の契約に従わせる。
契約は references/tool-contract.md が規定する ── 呼び方を1つに固定し、
能力を1度だけ宣言させて、CLI と MCP をその宣言から組ませる。

skills-creator scaffold <Skill の名前>   # 契約一式を置く
skills-creator check <Skill のフォルダ>  # 契約と節の構成を検査する
skills-creator dist --repo <所有者/リポジトリ>  # 配布元に、導入スクリプトと組み立ての定義を置く

層を crate に分けて置く。 1つの crate の中の module では、内側が外側を参照しても
コンパイラが通す ── 層の境界を crate の境界に置いて初めて、宣言に無い依存が解決
しなくなる。許可辺は各 Cargo.toml が宣言する。

置くもの役割参照してよい先
tool/parts/部品。実体はここに在る無し（依存を1件も宣言しない）
tool/declare/能力の正本。名前 ・ 引数 ・ 説明 ・ 実体の対応部品
tool/cli/唯一の入口宣言
tool/mcp/MCP の面。同じ宣言から組む宣言
tool/parts/tests/事例部品
bin/組み立てた実行ファイル。配布物だけが持ち、git で追跡しない──
mcp.json登録。ホストごとの差は、ここだけが吸収する。絶対パスを書かない──

生んだものが、そのまま契約を満たす。 満たさないと、新しい Skill は必ず不合格の
状態で生まれる ── 実測で、契約だけを変えて雛形を差し替えなかったとき、そうなった。

入口 ・ 部品 ・ 検証を、同じ階層へ並べない。 並べると、
どれを起動してよいかが、中身を開くまで判定できない ── 検査はこの置き場所も見る。

MCP の実装が無い環境では、MCP サーバーは立たず、CLI だけが動く ──
呼び出し方が欠けても、能力は欠けない。

利用者の環境に Rust が無くても動く形で配る。 組み立てた実行ファイルを OS ごとの配布物にし、
導入スクリプトが利用者の環境を判別して置く ── 利用者は、どの実行ファイルかを選ばない。
配布の規定は references/tool-contract.md の「配布」の節が持つ。

ガードレール

- 節の構成を、対応する雛形と一致させる。助言の Skill は advisor-creator の雛形、それ以外は
こちらの雛形を満たす ── どちらを適用するかは節の有無で決まる（名前で分岐すると、Skill が
増えるたびに検査を直すことになる）
- 道具を持つ Skill には、道具の契約を適用させる（references/tool-contract.md）── 入口の形が道具ごとに違うと、呼ぶ側は呼ぶたびに本文を読み直すことになる
- 同じ概念の仕組みは、同じ実装の形にさせる。入力の契約（スキーマ）・トークンの正本・入力の検査・置き場所を、Skill ごとに違う形で実装させない ── 概念が同じで形が違うと、1つを読んで得た理解が、次の Skill で通用しない
- 能力を2か所へ記述させない。CLI と MCP は、宣言から組ませる ── 同じ能力を2度書くと、片方だけが古くなる
- 部品に入口を付けさせない。import される部品は宣言に載せない ── 載せると、同じ能力に呼び方が2つできる
- 道具に印字させない。戻り値は {ok, findings, data} とし、印字と終了コードは入口が持つ ── 道具が印字すると、MCP から呼んだときに戻り値が空になる
- ガードレールと手順を、不変条件で記述させる。1回の出来事・特定の語・特定の形を規則にしない ── 規則が事例の形を取ると、その形だけが規制され、他の形は通過する。規則が禁じるのは性質であって、その性質が現れた1つの形ではない
- 例を規則本体へ混ぜさせない。例を添えるなら「例」と明示し、規則の文とは分離する ── 混ざると、読み手は例の範囲を規則の範囲として解釈する
- SKILL.md は必ずスキルフォルダのルートに置く。サブフォルダには置かない
- テンプレートファイルは assets/ ではなく references/ に置く
- 不要なフォルダは作らない。使うものだけ作る
- プレースフォルダーを記入する前に必ずreferences/placeholder-definitions.mdを参照する。定義票なしで記入しない
- スキル名は英小文字・ハイフン区切りに統一する（スペース・アンダースコア不可）
- ユーザーが要件を明確にしていない場合は作成を開始しない。必ずヒアリングを先に完了させる
- 新しいSkillに、特定の外部ツール・システム（Waffle、特定のCLI/MCP等）の存在を自ら判定して振る舞いを変えるロジックを持たせない。汎用のSkillが具体的な実装の有無を参照するのは依存性の方向違反であり、正しい向きは「具体的なシステムの側が汎用Skillを自分の中に注入・統合する」（composition-rootの原則）。特定システムとの統合が必要な場合は、そのSkill自体は単一の環境非依存な実装のままにし、統合はSkillの外側（呼び出し側・Orchestrator側）に置く設計を選ぶ

意思決定を、変更前と変更後の差分ごと記録するSkill：acdr

ACDR は Any Change Decision Record である。 分野を限定しない ── 何を決めたときでも、変更前と変更後の差分ごと残す。

目的

何かを決めたとき、決定と、その差分と、なぜそう決めたかを1枚へ保存するために使用する。文書・コード・設計・方針のいずれでもよい。分野を問わない ── この Skill は、対象が何の仕事に属するかを認知しない。

人は、変更前と変更後が見えていると判定が速い。 差分が無いまま承認を求めると、「この決定は何を土台にして決まったのか」を読む側が毎回復元することになる。成熟した環境では、決定の大半が既存のものへの変更である。だから差分を既定にし、新規のときだけ差分が空になる。

残すのは、承認の前と後で同じ1枚である。 状態が proposed から accepted へ変わるだけで、記録の形は変化しない。リポジトリに置くので、差分に載り、変更の理由がPRに出力される。

役割

- 決定を、節（決定 ・ なぜ ・ 形の変化 ・ 実現の形 ・ 適用先 ・ 比較した案 ・ 承認の状態 ・ 承認後に実施すること）にする
- 変更を1件ずつ、どこ・何から何に・なぜの3つ組にする
- 対象の文書を描画し、変更箇所を押すと変更前と理由が開く形にする
- 理由が欠けている変更を、記録に包含しない
- 正本へ適用する前に見せ、承認を得てから適用する
- 承認が下りたら状態を accepted にして、リポジトリへ保存する

処理対象と成果物

処理対象

これから決めようとしていること。多くは既存の文書・コード・設計への変更で、新規のこともある。

成果物

記録1件は、フォルダ1つである。

.acdr/<番号>-<短い名詞句>/
  acdr.json    ← 正本。節と、変更の3つ組を保持する
  flow.svg     ← 図（組ませた相手が返す。無い場合は配置しない）
  index.html   ← 組成した成果物。acdr.json から導出される

acdr.json が正本で、index.html は導出されるものである。 同じ acdr.json から、実行場所に依存せず同一の index.html が出力される。

中身を複製しない。 変更後の全文は対象の文書が保持している。記録が保持するのは、節と、対象のパスと、3つ組だけである。

index.html を手で直さない。 正本は acdr.json である ── 手で直すと、次に組成した時点で失われる。

承認済みの記録は封印される。 承認後の最初の組成で、対象の文書の sha256 が acdr.json へ保存される。以降、対象の文書が変化した状態で組み直そうとすると拒否する ── 組み直すと承認時点の姿が失われる。--check はその場合に「承認時点の姿である」と報告する。意図して組み直す場合は --force を渡す。

入力の想定

受け取る情報解釈・既定値
決めようとしていること明示されなければ、直前の会話から決定を書き起こす。推測で補完しない
対象の文書明示されなければ、変更しようとしている文書すべてを対象とする。無ければ新規として扱う
変更前の内容正本の現在の中身をそのまま取る。適用済みなら、gitの作業ツリーとHEADの差から取る
なぜ明示されなければ、そのとき何と食い違っていて何に一致させたかを書き起こす
除外した案明示されなければ、検討した案と、それぞれ何が成立しないかを記述する

実行手順

Step 1: 何を出す文書かを、外から取る

その文書が何を出すべきかは、その文書の中には無い。中から取ると、旧路線の記述が旧路線を残す根拠になる。成果物を決めている親文書・定義票・仕様の記述から取り、見出しの並びだけで出すものが出るかを判定する。出していなければ、本文の校正に入らず構造の案を先に出す。

Step 2: 対象の全文を読む

頭から終わりまで確認する。検索で見当を付けて周辺のみを確認する方法を採用しない ── 置換のすり抜け、説明なしで残った旧い値、見出しと中身の食い違いは、どれも検索では検出されない。

Step 3: 節を記入する

図で確認するfigure ・ figure_caption形の変化を図にしたもの。この Skill は描画しない ── 受け取るのは SVG の文字列のみである

比較した案alternativesoption と、why_not。反証を通過しなかった案であり、未解決の懸念ではない

承認後に実施することafter_approval承認が成立したあとに実施する作業
置き換えた記録supersedesこの決定が置き換えた記録の番号

キーは ASCII で、値は人が読む日本語である。 機械が分岐するもの（キー ・ status）と、
人が読むもの（本文）を、同じ文字体系に混在させない。

decision ・ applies_to ・ why の3つは、欠けたら道具が停止する。 欠けた記録は、あとから誰も補完できない。

Step 4: 変更を3つ組にする

1件ずつ、どこ（読み手がその場所を開ける粒度）・何から何に（変更前の原文をそのまま。要約しない）・なぜを完備させる。書けない変更は記録に含めない ── 書けないのは、変更の意図が自分でも掴めていないということである。削除も1件として扱い、消えた場所に印を配置する。

「変更前」と「なぜ」は平文である。 タグを書いても文字として出る ── 「変更前」は原文をそのまま出す欄なので、タグを解釈してはならない。節（決定 ・ 対象 ・ なぜ）のほうは HTML を受ける。

「どこ」は、描画したあとの本文に現れる文字列で指定する。 マークダウンの記法を含めると一致しない ── 描画後は <b> や <code> になっている。

Step 5: 作業コピーへ適用して、1枚を組む

正本は触らない。作業コピーへ適用してから組成する。操作は3つだけである。

acdr new .acdr/0007-<短い名詞句> "題"    起こす（雛形から）
acdr validate .acdr/0007-<短い名詞句>    入力を検査する
acdr render .acdr/0007-<短い名詞句>      組む
acdr render .acdr/0007-<短い名詞句> --check 1   差が無いかを検査する

入口は1つである。 どの操作も --json を付けると機械が読む形で出て、終了コードは 0 正常 ／ 1 検出あり ／ 2 誤用である。

acdr.json の形は references/acdr.schema.json が決め、雛形は references/spec-template.json が保持する。生成物ではなく、入力を検査する ── 生成物の検査からは、複製が正しく生成されたことしか判明しない。しかも不合格の時点で HTML は既に出ている。不合格なら HTML を1バイトも出さない ── 検査は4系統で、形（スキーマ）・欄の完備（節と3つ組）・散文（1つの欄への主張の同居 ・ 1文の長さ ・ 見出しや表の混入。引用と原文は除外する）・参照の解決（図と対象の文書の実在）である。

それ以外（.html など）そのままの見た目。CSS を隔てるので iframe へ流し込み、届かなければ Shadow DOM へ切り替える

docs が空なら、節だけの1枚になる。

新しい種別の枠を追加する場合は、タブの押す処理の配線と、枠の挿入先の2点を確認する。 どちらが欠けても印は開かない ── 面の種別を増やす操作は、配線と挿入先の2か所へ同時に及ぶ。

Git は差分を出すが、なぜ変えたかを出さない。 そこを補完するのがこの道具である ── まとまりごとに理由を添え、印を押すと開く。変更前は - の行が示すので、before の記述は省略してよい。

変更前は git show <rev>:<パス> で取得する。 記録へ複製しない。rev の既定は HEAD で、docs の項目に書くと変更できる。取得できない場合と差分が無い場合は、全文を置く。

理由が付いていないまとまりは、組成の検査が件数を出す。 差分の見出しにも表示する ── 0件にしてから提示する。

コードの印は行の単位である。 語の単位で付けると、色付けが挿入した要素と交差してどちらかが壊れる ── コードの変更は行の単位で読むものなので、行で足りる。

色付けは近似である。 構文解析を実施せず、行ごとに正規表現を適用する ── 文字列の中の予約語のような事例は取り違える。読解の補助であり、判定の根拠にしない。

冪等である。 docs のパスはリポジトリの根から解決するので、どこから実行しても同一のものが出力される。--check は組み直した結果と index.html を比較し、差が在れば 1 を返す。

Step 6: 開いて閉じることを確認する

描画して、実際に押す。1度押すと変更前と理由が出て、2度押すと閉じる。「すべて開く／閉じる」も両方向とも動作する。印が内側のタブに隠れることがある ── タブの先頭の一覧から、押してその印まで運べることを確認する。

Step 7: 理由の欠けを確認する

「なぜ」が「一致させるため」だけになっていないか（何と何を一致させたかを書く）。変更内容の言い換えになっていないか。変更前が要約になっていないか。

Step 8: 見せて、承認を得てから適用する

1枚を渡し、返事を待つ。「適用しました。確認してください」と記述しない ── それは承認ではなく追認を求めている。

承認が下りたら、状態を accepted にして組み直し、正本へ適用し、.acdr/ の1枚と索引をコミットする。差し戻されたら3つ組を直して Step 3 から再実行する。止められた場合は適用しない。

後の決定が、この決定を置き換えたときは、古いほうの状態を superseded にし、置き換えた記録を指す ── 消さない。

ガードレール

- 中身を複製しない。 変更後の全文は対象の文書が保持する。記録が保持するのは節と3つ組だけである
- 対象が何の仕事に属するかを、この Skill が認知しない。 特定の分野の語彙・規則・スキーマを持ち込まない ── 使う側がこの Skill を呼ぶのであって、この Skill が使う側を知ることはない
- 何を出す文書かを、外から取得してから改訂する。 文書の中の記述を、その文書を直す根拠にしない
- 構造が合っていなければ、本文を直さない。 先に構造の合意を取る
- 対象の全文を読んでから直す。 検索で見当を付けて周辺のみを確認する方法を採用しない
- 正本へ適用する前に見せる。 適用してから提示しない
- 理由が欠けている変更を包含しない。 推測で理由を補完しない
- 変更前を要約しない。 原文をそのまま保持させる
- 比較した案を削除しない。 案と、採らなかった理由を保存する
- 節の語を負の側へ偏向させない。 「除外」「負担」ではなく「比較した案」「承認後に実施すること」と記述する ── 負の語が残ると、未解決の懸念が存在すると読解され、承認の判定が遅延する
- 抽象の側の変更前と変更後を記述する。 枠が保持するのは具体の差分である ── 抽象の対比が欠けると、下に並ぶ差分が何のためかを読み手が復元することになる
- 図を省略しない。 形の変化を図で確認できる形式にする。描画はこの Skill が実施せず、SVG の文字列を受け取るのみである
- 状態を自由文にしない。 proposed ／ accepted ／ superseded の3つ以外を書かない ── 自由文にすると、承認されているかを読む側が判定することになる
- 置き換えられた記録を削除しない。 superseded にして、置き換えた記録を指す
- 新規を例外として区別しない。 差分が存在しない決定も同一の形式で、docs を空欄とする
- 描画して押すまで出さない。 開閉が動作することを目視で確認する
- 色・寸法を直書きしない。 見た目は references/tokens.json が保持するトークンから引く ── 直書きすると、配色を替えたときにそこだけ取り残される。トークンの正本は1つである ── 2か所に書くと、どちらが正しいかを毎回確認することになる
- 入力の検査を、組み立てと同じ場所に置かない。 組み立てが検査を兼ねると、不合格の判明が生成物のあとになる ── 不合格なら HTML を1バイトも出さない
- 決定の文に手段を混在させない。 決定は「何を採るか」で、手段は実現の形が保持する ── 手段だけを上に置くと、下の差分が何のためかを読み手が復元することになる
- 差し色を1つに限定する。 状態のラベル（承認済み）以外に別の色を使わない ── 1本だけ違う色の線が在ると、意味が在るものとして読解される
- 題を二重に出さない。 題は節が持ち、枠の見出しには出さない
- 生成物に文字コードを宣言する。 <meta charset="utf-8"> を先頭に置く ── 無いとHTTPで配ったときに推測になり、化ける
- 承認済みの記録を組み直さない。 記録は承認時点の姿である ── 後に対象の文書が変化しても、記録はその時点を保持する
- 外部のCDNやスクリプトを参照しない。1枚で完結させる

- rs/parts/src/tokens.rs: トークンを読み、CSS のカスタムプロパティへ組む。iframe と Shadow の中へ流し込む側は、:host でも解決する形で組む ── Shadow の中に :root は無く、寄せないと印が色を失う
- rs/parts/src/validate.rs: 入力を検査する。 形（スキーマ）・欄の完備（節と3つ組）・散文・参照の解決（図と対象の文書）の4系統である。原文（before）と照合する文字列（find）は、散文として検査しない ── 原典の形を変えないためである
- references/acdr.css: 見た目の正本。 セレクタと規則だけを保持し、直値を1つも書かない ── 色も寸法も字寸も tokens.json の層を参照する。以前は組み立ての中の文字列に141行在った ── そこに置くと、型とトークンを直すべき変更が、実装の中の文字列を直す作業になる。塊の境目は /* == 名前 == */ が示す（BASE ・ CODE ・ MARK ・ SECTION）
- references/acdr.js: 動きの正本。 印を押せるようにし、面を iframe か Shadow DOM へ立て、一覧から印まで運ぶ。これも組み立ての外に置く ── 置かないと、200行の script が実装の中の文字列になる
- rs/parts/src/style.rs: 見た目と動きの正本を読み、塊へ割る。境目をこの側で決めない ── 決めると、正本を割り直したときに気づけない
- rs/parts/src/record.rs: 節と差分を1枚へ組む。入力の検査で1件でも検出したら、HTML を1バイトも出さない
- rs/parts/src/panes.rs: 対象の文書を描画し、変更箇所に印を付け、複数なら1枚へまとめる。拡張子で置き方を決める
- rs/parts/src/code.rs: コードを Git の統合差分へ組む。まとまりごとに理由を添え、理由が付いた数を返すので、欠けを検査へ出せる。対応する拡張子は LANGS が保持する ── ここに無い拡張子は、コードとして扱わない
- rs/parts/src/markdown.rs: マークダウンを描画し、変更箇所に印を付ける。位置は差し込む前に全部決める（差し込みながら探すと、印が前の印の属性の中へ入る）
- references/acdr.schema.json: acdr.json の形を検査するJSON Schema
- references/spec-template.json: acdr.json の雛形。new が複製する
- rs/parts/tests/: 事例（81件）。型（差し込みの過不足 ・ 入れ子の <template> ・ 組み立ての側に構造を作る文字列が残っていないこと）・ 印の付き方（属性の中へ入らないこと ・ 重なりの除外 ・ 渡す順に依存しないこと）・ 差分（まとまりの切れ目 ・ 理由の欠け）・ 表（縦線の文字 ・ 表の枠）・ 入力の検査（欠けた欄 ・ 1つの欄の主張の数 ・ 参照の解決）・ 記録（同じ入力から同じ出力 ・ 承認済みの記録の封印 ・ 対象が変化したときの拒否）を固定してある
