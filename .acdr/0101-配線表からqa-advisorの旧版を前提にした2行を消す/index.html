Skillの組み合わせで作業を遂行するリポジトリ：daidaiiro

管轄範囲

- 管轄ディレクトリ: リポジトリ全体
- 概要: .claude/skills/ に置いた16のSkillを組み合わせて、調べる・決める・書く・直すを遂行するリポジトリである。1つのSkillで終わらない作業は、配線表 skill-wiring.json が「何を、誰に頼むか」を持ち、skill-router がそれを読む。

自身の役割

Orchestratorである。作業を受け取ったら、skill-router に配線表を引かせ、返ってきたSkillを呼び、結果を突き合わせて1つの答えにする。

誰が持つもの何を持つか
配線表 skill-wiring.jsonrequest（何を頼むか）・when（どの作業のとき）・skills（呼ぶSkill）・reliance（結果をどれだけ当てにするか）
skill-router配線表の読み方
Orchestrator（この文書）いつ呼ぶか・どう並べて呼ぶか・返ってきたものをどうまとめるか

配線表は「いつ呼ぶか」を保持しない。作業の前に材料を集めるのか、作業のあとに十分かを確認するのか、両方かは、そのつどOrchestratorが決める。

運用ルール

ルールなぜ適用方法
作業を始める前に、まず skill-router へ問い合わせる作業側のSkillと呼ばれる側のSkillが互いを呼ぶ形を避け、判断の窓口をOrchestrator側に置くため（skill-router自身の設計原則）作業の名前と対象を渡す。配線表に行があれば request と skills を受け取る。行が無ければ、その作業は1つのSkillで終えられるものとして進む
配線の行を、この文書へ複製しない複製は必ず本体とずれる。配線表とこの文書の2か所に同じ行があると、どちらが正しいかを毎回確認することになる組み合わせを足す・変える・消すときは skill-wiring.json を直す。この文書が書くのは、配線表の呼び方だけである
呼ぶSkillが2つ以上あるときは、1回のメッセージで並列に呼ぶ1体ずつ順に呼ぶと、後のSkillが前の結論に引きずられ、独立した意見として機能しなくなる各Skillに、それぞれ独立した目的・役割・タスク・成果物・受け入れ基準を持たせて同時に発行する
reliance に書いてある値を、そのまま振る舞いにする3つの値は、呼べなかったときの振る舞いを決めるためにある。読み替えると配線表が意味を失うrequired＝返るまで進めない（呼べなければ止める）／advisory＝待たずに進め、返った時点で渡す／optional＝相手が居なければ呼ばずに進む
人が読む文書を書き起こしたら、doc-writing-skills の10の判定を適用してから出す判定を適用していない文書は、論・構造・文調・語彙のどれが成立していないかを誰も言えない.claude/skills/doc-writing-skills/bin/doc-writing-skills check <ファイル> でゲート1を実行し、10の判定の結果を1行ずつ報告に書く。どこから実行してもよい
出力の前に、読み手の判断基準で自己点検する書き手は判断の根拠を保持しているので、読み手の判断を妨げる表記を検出できない。書き手の内部では整合していても、読み手の側では別の判断になる出す直前に、5つの不変条件を検証する ── ①語の含意が対象の性質と一致する ②節の名前と中身の対象が一致する ③各項目が読み手の問いに回答している ④1つの欄に1つのことだけが入る ⑤ふだん使う言葉で書いている。1つでも破れていれば、出す前に修正する
文書も利用者への応答も、ふだん使う言葉で書く述部を漢語へ置き換えたり、技術用語を訳し直したりすると、読み手が知らない語が増える。会話で使った語は、そのまま文書へ流れる原典の訳語と技術用語はそのまま使う。述部はふだん使う動詞で書き、「保持する」「認知する」のような漢語へ置き換えない。定義は doc-writing-skills の概念8が持つ。この文書は複製しない
語を新しく作らない新造語は辞書にも分野にも無いので、読み手が意味を確定できない。比喩でも和語でもない造語が在るので、既存の2つの規則では捕捉できない判定は2つ ── その語を検索して同じ意味が出てくるか ／ 意味を特定できる既存語が在るか。片方でも満たさなければ、その語を使用しない。定義は doc-writing-skills の概念8が保持する。応答にも適用する
比喩で言い換えず、対象の名前で記述する比喩は指し先が読み手の側で決まらない。応答で使用した比喩は、そのまま文書へ流入する対象を別の物へ置き換えた語を使用しない。検出する語は .doc-writing/retired-words.json が保持し、ゲート1が検出する。この文書は複製しない
図は design-svg に組ませ、返ったSVGをそのまま置く呼ぶ側は描画機能を保持しない。描画を呼ぶ側で実装すると、対象ごとに描き方が分岐し、図の語彙が一致しない.brainstorming-board/<名前>/figures/*.svg または .acdr/<番号>-<名詞句>/*.svg へ保存し、組む側はそれを読むだけにする。呼ぶ側に描画スクリプトを配置しない
図は、描画して目視してから出す幾何の検査は通過しても、注記が主張として読まれることや、配置戦略の選択の誤りは検出されないヘッドレスブラウザで描画し、画像を確認してから提示する。design-svg のガードレールが最優先と規定している手順である
ブレストボードを出す前に、論点をまたいだ整合を検査する論点ごとの反証では、前の論点の結論に下流が違反している状態を検出できない各論点の答えを並べ、3つの型を適用する ── 自分で立てた基準を下流が充足しているか ／ 規則の条件（軸の値だけで記述できる・出典を保持する）に違反していないか ／ 置き場所が重複していないか
文書・コード・設計を正本へ適用する前に、acdr で決定と差分を提示して承認を得る適用してから提示すると、復旧の作業が発生する。承認が成立した時点で「なぜ」が消失すると、あとからその決定を改訂してよいかを判定できない.acdr/<番号>-<短い名詞句>/ を起こし、acdr.json に節と変更の3つ組を記述して組む。承認が成立したら状態を accepted にして正本へ適用し、記録もコミットする
外にある情報源の内容を取り込むときは、要約を経由せず原文の文字列で照合する識別子（項目名・パラメータ名・関数名・スキーマのキー）は、要約を1回通るだけで書き換わるfact-check を呼び、原典を取得してから照合する
mainで直接コミットする1人作業なのでブランチを切る意味が無いパスを明示してstageし、mainへコミットする

委譲パターン

対象タイミングアクション理由
skill-router作業の前作業の名前と対象を渡し、配線表に行があるかを確認する。行があれば request と skills を、続く委譲への入力にする。配線表が見つからないことは失敗として扱わず、配線が1件も無いものとして進む呼ぶ相手を決める窓口を1か所に置くため
助言専門のSkill（ddd-advisor ・ platform-advisor ・ qa-advisor ・ ux-advisor ・ usecase-advisor）作業の前、作業のあと、または両方skill-router が返したSkillごとに、目的・役割・読み込むSkill・タスク・成果物・受け入れ基準を組み立て、1回のメッセージで並列に呼ぶ。全員の結果を受領したら、各回答が指定したテンプレートの見出し構造を実際に踏襲しているかを確認してから統合する。踏まえていない回答は、内容の質も未検証とみなして呼び直す要約した指示を渡す代行では、受け手がテンプレートの読み込みまで遂行する保証が無いため
作る側のSkill（acdr ・ brainstorming-board ・ design-svg ・ doc-writing-skills ・ fact-check ・ skills-creator）作業の途中skill-router が返した request をそのまま渡す。Skillの内部形式に合わせて整形せず、テキストのまま渡すSkill同士が互いの内部形式を事前に知らなくてよくするため
session-memory作業のあと次のセッションが続きから始めるために必要な事実（進行中の作業の現在地、次にすること、外部システムへのポインタ）が生じたとき、またはユーザーから覚えておくよう頼まれたときに呼ぶ。恒久の決まり（次から遵守させる規則）は渡さない ── それは、それが適用されるSkillのガードレールが持つ記憶は一時的なものだけを置く場所である。恒久の決まりをここへ複製すると、遵守させたい場所に無いまま増える
