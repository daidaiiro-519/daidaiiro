ユースケースの判断基準

名前の付いた3つの目的レベル

概要

シナリオの目的と相互作用は、より粒度の細かい目的や相互作用へどんどん展開できる。日常生活では当たり前のことだが、ユースケースを書くときには「1文ごとに、どのレベルの目的を書けばよいのか」という疑問が生じる。この章は、目的レベルに名前とアイコン（メタファー）を付け、どの目的レベルを使えばよいかを判断する方法を説明する。

この基準が答える判断

  • ユーザー目的（青、海面）（5.1）
  • 要約レベル（白、雲／凧）（5.2）
  • サブ機能（藍／黒、水中／貝）（5.3）
  • 図形のアイコンを使って目的レベルを強調する（5.4）
  • 適切な目的レベルを見つける（5.5）
  • 長めの記述例: 複数のレベルの「保険金支払い請求を処理する」（5.6）
  • 練習（5.7）

概要

この章は、目的レベルに名前とアイコン（メタファー）を付け、どの目的レベルを使えばよいかを判断する方法を説明する。

補足

例として挙げられている目的の連鎖

販売契約を結びたい → マネージャを昼食に誘う → 現金が要る → ATMでお金を引き出す → IDを確認させる → カードを入れる → 挿入口を見つける

Tabキーを探す ← 住所欄にカーソルを移すため ← 住所を入力するため ← 見積もりソフトに個人情報を入れるため ← 見積もりを取るため ← 自動車保険に入るため ← ナンバーを取るため ← 運転するため

3つの名前付きレベル: 要約（白） ・ ユーザー目的（青） ・ サブ機能（藍／黒）

図

図5.1 ユースケースのレベル（「はてしない展開の物語」）

ユースケースの集合から、目的の階層が見えてくる。

図の右側のアイコン: 雲（白）・凧（白）・波（青＝ユーザー目的、海面）・魚（藍）・貝（黒）

ユーザー目的（青、海面）（5.1）

ユーザー目的は、最も重要なものです。

定義

ユーザー目的

最も重要なものです。これは、主アクターが仕事を完了させるために持つ目的であり、システムを使っているユーザーが持つ目的です。

補足

ビジネスプロセスエンジニアリングの「基本ビジネスプロセス」にあたる

判定の問い: 「主アクターはこれを実行したあとで満足して立ち去れるか」

社員の場合: 「今日これらをいくつ実行できるかが仕事の出来に影響するか」

コーヒーブレークテスト: 「これが終わったらコーヒーブレークにしよう」と言えるか

対比

例

多くの場合、1人の人が中断なしで行える（2分から20分程度）もの

目的ユーザー目的か理由
ネットオークションでの購入を完了する通常ならない何日もかかり、「中断なしで」の点で不合格
ログインする通常ならない42回続けて行っても、仕事の責務やシステムを使う目的を満たさない
新しい顧客を登録するおそらくなる42人登録することは販売代理店にとって重要な意味がある
本を購入するおそらくなる中断なしで完了できる
補足

色と海面のメタファー

色は白 → 青 → 藍 → 黒と変化する（本書ではグレーの濃淡で表す）

定義

青

ユーザー目的

定義

白

より長い時間のかかる、よりレベルの高い目的（例: ネットオークションを完了する、自動車事故の保険支払いを求める）

定義

藍

より時間の短い、より低いレベルの目的

定義

黒

目的のレベルが低すぎて、ユースケースとして記述するのは間違いであることを示す（例: Tabキーを押す）

補足

海面: 空と海が接するのは海面のレベルだけ。ユーザー目的の上にも下にも多くの目的レベルがあるが、記述しなければならない重要なものはユーザー目的

雲・凧 = 海面より高い、魚・貝 = 海面より低い

システムが意義を持つのは、海面レベルの目的をサポートしているとき

例: 電話を受けた社員が、コンピュータを操作して顧客と会話し目的Gを達成する。Gは青（海面）。Gの達成にはいくつかの藍の目的が要る。電話をかけてきた人の、より高い目的は白

システムがサポートするユーザー目的のリスト = システム機能の非常に簡単なまとめ。これを基礎に、優先度付け・納品・チーム分け・見積もり・開発を行う

膨大な数の低レベルの目的やユースケースは「海中」と考えるとよい（本当は書いたり読んだりしたくないことを暗示する）

補足

コラム: ちょっとした実話

100ページ以上の、すべて藍色（海中）のユースケースの要求文書は、長く退屈で読み手にも書き手にも役立たなかった

同じ人が代わりに送ってきた海面レベルの6つのユースケースのほうが、皆にとって理解しやすく扱いやすかった

補足

青の2つのレベル

通常、青のユースケースの上には1つの白、下にはいくつかの藍がある。しかし青から別の青を参照する状況もある（著者はただ1つの状況でしか見たことがないが、繰り返し現れる）

補足

例（レンタルビデオ店）

通りがかりに会員登録する（青）→ 翌週にビデオを借りる（青）: 2つのユーザー目的を別の日に行う

ビデオを借りに入り、会員でないので店員が手続きの一環として会員として登録する: 会員登録するはビデオを借りるの中の1ステップだが、両方とも青

「通りがかりの人を登録する」が、青の中に別の青が入っている唯一の状況

両方とも海面レベルだが、ビデオを借りるは図5.1の波の頂点、会員登録するは波の谷に相当する

要約レベル（白、雲／凧）（5.2）

要約レベルの目的には、複数のユーザー目的が含まれる。

対比
システム記述上の3つの役割
ユーザー目的が実行されるコンテキストを表す
関連する目的群について、ライフサイクルにおける実行順序を表す
より低いレベルのユースケース（白と青の両方）の目次となる
補足

注: 以前の著作では「戦略的」と「要約」の両方を使っていたが、「要約」のほうが混乱しにくいとして本書では「要約」を使う

要約レベルのユースケースは白。白のステップには、白や青、場合によっては藍（例: 白に現れることがある「ログインする」）が含まれる

白の中で複数のレベルを区別しても意味がないと著者は考えるが、「雲の上の白だ」と言う人もいる。海面のメタファーでは、ほとんどは「凧のように海面の少し上」、ほかは「雲の上」

実行時間は通常、数時間・数日・数週間・数か月、時には数年

補足

例: ユースケース18「保険を利用する＋」（雲）

主アクター: 顧客／スコープ: 保険会社（MyInsCo社）／レベル: 要約（白）

手順

ステップは4つで、それぞれが下位ユースケースへの参照（下線）

  1. 見積もりを取る

  2. 保険を契約する

  3. 保険金の支払いを請求する

  4. 保険を解約する

補足

要点

何年にもわたってばらばらに行われる青のユースケースをまとめることが目的

会社をブラックボックスとして捉え、目的レベルは真っ白（雲の上）であることがアイコンで強調される

名前の後ろの「＋」は要約レベルであることを示す（5.4節）

この章のほかの白のユースケース: 19「保険金支払い請求を処理する（ビジネス）」・20「労災の請求を審査する」・21「保険金支払い請求を処理する（システム）」

手順

一番外側のユースケース（再考）

第3章で推奨した「一番外側のユースケース」を見つけるための、より詳しい手順。

  1. ユーザー目的から開始する

  2. 「この目的はどの（おそらく組織外の）主アクター（AA）のためのものか」を考える。AAは集めようとしているユースケースの本来の主アクター

  3. 一番外側の設計スコープSを探す。AAはSの外側にいなければならない。Sに名前を付ける。典型は3つ

  4. 本来の主アクターがAAで、設計スコープがSであるすべてのユーザー目的を洗い出す

  5. AAがSに対して持つ要約レベルの目的GGをじっくり考える

  6. GGについて要約レベルのユースケースを記述する。これは複数の海面レベルのユースケースを結び付ける

対比
一番外側の設計スコープS
会社
組み合わされた複数のソフトウェアシステム
設計対象の特定のソフトウェアシステム
補足

非常に大規模なシステムでも、一番上位のユースケース（GG）は普通4つか5つ程度。3つか4つの本来の主アクターの利益を要約したもの

対比
本来の主アクター
顧客（会社に対して）
マーケティング部門（組み合わされた複数のソフトウェアシステムに対して）
セキュリティ部門（ソフトウェアシステム自体に対して）
規則
  • 一番外側のユースケースは作業を取りまとめるうえで大変便利で、記述を強く推奨する
注意
どこの話か注意
機能要求ただし構築するシステムの機能要求を明らかにするものではない。機能要求はユーザー目的（青）のユースケースに含まれる

サブ機能（藍／黒、水中／貝）（5.3）

サブ機能レベルの目的は、ユーザー目的を達成するのに必要な目的です。

定義

サブ機能レベルの目的

ユーザー目的を達成するのに必要な目的です。

規則
条件対応
必要になるのは、読みやすくするためか、ほかの目的から何度も使用される場合必要な場合だけ記述に含める
補足

例: 商品を検索する、顧客を検索する、ファイルに保存する。あまり見かけない藍の例は、5.6節のユースケース23「何かを検索する（問題記述）」

水中にあり藍色。海底に沈んでいるものは黒と呼ぶ

黒 = 「あまりに低いレベルなのでユースケースにまでふくらませないでくれ」という意味（「泳ぎさえもしない…貝じゃないか」）

特別な名前を付けておくと、誰かが記述したときに、記述すべきでなく別のユースケースに含めるべきだと伝えられる

青には藍のステップが含まれ、藍にはさらに濃い藍のステップが含まれる（図5.2）。より高いレベルの目的は「アクターはなぜこれを行うのか」で見つかる（5.5節）

最も低いサブ機能のユースケースにも、システムの外側の主アクターが存在する

サブ機能もユースケースの決まりにすべて従う

サブ機能のアクターは、それを参照するより高いレベルのユースケースのアクターとおそらく同じ

規則

目的レベルのまとめ

対応理由
海面レベルのユースケースを見つけることに多くの労力を割くこれらが重要なユースケースである
ほかのユースケースのコンテキストを示すために、一番外側のユースケースを多少なりとも記述する
システム要求の文章内のお気に入りのフレーズが、ユースケースのタイトルとして「認められる」かどうかで騒ぎ立てないタイトルになったから「一番重要な要求」とは限らず、ならなかったから「重要でない」わけでもない
補足

目的レベルを明確にすると、複雑なテキストを独立したユースケースにしたり、些細なユースケースを高いレベルの一部に入れたりすることが比較的容易になる

文はすべて目的として記述され、その目的はすべて1つの独立したユースケースに展開できる。記述を見ただけでは、どの文が展開されているかはわからない（リンクをたどる場合を除く）。これにより、ちょっとした変更でも記述の整合性が保たれる

それ自身がユースケースになることを保証されているのは、青の目的だけ

図形のアイコンを使って目的レベルを強調する（5.4）

補足

3.2節の設計スコープのアイコンはタイトルの左側。目的レベルのアイコンはタイトルの右側に付ける（テンプレートの欄に書き込むのとは別に）

対比

海面からの距離で5つの高さに分類

著者の経験では、レベルを知るための手段は多いに越したことはない

ほとんどの場合、使うのは真ん中の3つ

レベルアイコンアイコンが使えないとき使いどころ
非常に粗く要約した（真っ白）雲名前の後ろに「＋」非常にまれ。ステップ自体が白のユースケースになっている場合
要約（白）凧名前の後ろに「＋」ほとんどの要約ユースケース。ステップは青
ユーザー目的（青、海面）波何も付けないか「！」—
サブ機能（藍）魚名前の後ろに「－」藍のユースケースのほとんど
一部のサブ機能（黒）貝—記述してはいけない。呼び出しているユースケースに含めるべきことを示す
補足

ツールベンダーがサポートすれば、UMLのユースケース図にも設計スコープと目的レベルの印を付けられる

＋／－／！の記号は今すぐ使える。テンプレートに設計スコープや目的レベルの欄があっても重複して付けると便利。欄がなければ追加する

適切な目的レベルを見つける（5.5）

適切な目的レベルを見つけるのは、ユースケースを扱ううえで最も難しいことの1つ。

規則

ガイドライン

  • ユーザー目的を見つける
  • ユースケースごとのステップ数を3から10にする
補足

ユーザー目的を見つける

問い: システムを使う誰かがこのシステムから今何かを得ようとしていて、得たあとは続けてほかのことを実行できる。その人が今このシステムに望んでいることは何か

どこの話か注意
最初のドラフト最初のドラフトではほとんど答えは「違う」

手順

より高いレベルを見つける問い

  1. 主アクターは本当は何を望んでいるのか？

  2. このアクターはなぜこれを行っているのか？

規則
  • 確信が持てるまで質問を繰り返す
補足

基準は主観的だが、次第に意見は一致する。経験者は驚くほど似た答えを出す（ユーザー目的は安定した概念のよう）

補足

目的レベルを上下させる

ステップ = 処理がどのように行われるか、ユースケース名 = なぜその処理が重要なのか。この「どのように／なぜ」の関係でステップの目的レベルを調べられる（図5.2）

規則
  • 1つ以上レベルを上げるには「アクターはなぜこれを行っているのか」を考える
図

その答えが1つ高いレベルの目的

（図5.2「『なぜ』と問いかけてレベルを上げる」: ユースケースの目的の下にステップの目的が並び、「なぜ？」で上へ、「どのように？」で下へ移る）

補足

ユースケースの長さも判定方法の1つ

適切に書かれたユースケースのステップ数は、ほとんどの場合3から8

著者が見た11ステップ以上のユースケースはどれも短くしたほうがよかった

推測: 人は中間のステップが10以上もあるプロセスを容認したり考えたりしない

ステップが10以上なら、詳細なUIまで含めているか、アクションのステップを低すぎるレベルで書いていることが多い

手順

対処

  1. UIの詳細を取り除く — アクターの動きではなく意図を表現する

  2. 目的レベルを上げる — 「なぜ」と問いかけて1つ上の段階を見つける

  3. ステップ同士を統合する

  4. 5.6節や第19章「問題点の修正」の記述例と比較する

長めの記述例: 複数のレベルの「保険金支払い請求を処理する」（5.6）

補足

ユースケース19〜23は、Fireman's Fund Insurance Corporation社（カリフォルニア州Novato）の許可を得た掲載

現場で請求処理をしているプロフェッショナルが、IT部門のビジネスアナリストや技術開発スタッフと協力して書いた

現場スタッフはITスタッフには考えもつかない見識を持ち、ITスタッフは正確に記述するための助言をした

ソフトウェアの基礎知識を持たない利用者側の専門家が、ITスタッフと協力して要求を記述できることを立証した

設計スコープと目的レベルの例として5つのユースケースを挙げる。ステップや拡張を記述するスタイルの優れた例でもある。各ユースケースの前に注釈がある

読みどころ: 目的がどのように低いレベルへ展開されるか、スコープが「会社の業務活動」→「全コンピュータシステム」→「設計対象のシステム」へどう小さくなるか。下線は別のユースケースへの参照。主成功シナリオを先頭近くに置くようテンプレートを少し変更している

ユースケース19についての注釈と要点

対象システムは会社の業務活動で、コンピュータシステムには触れていない

構成の要点

使用時のコンテキスト: アジャスター（事故調査から保険金の算定、契約者との調整までを行う専門職）が請求を処理する

事前条件: 損害が生じた／トリガー: 保険会社に請求が報告される

主成功シナリオ: 事故報告者が損害情報を登録 → 社員がアジャスターに請求を割り当て → アジャスターが調査・見積もり・準備金・協議・解決・終了を行う（いずれも下位ユースケースへの参照）

拡張は「今後記述する」、最低保証は「なし」

利害関係者は6者（保険商品を販売した部署、顧客、市場行動を設定する保険部、請求者、請求部門、見込み顧客）

補足

ユースケース20についての注釈と要点

ビジネスユースケースで対象はやはり会社の業務活動だが、目的レベルはユースケース19より低い

数日から数か月を要するアジャスターの仕事を表し、中断なしで行うアクティビティを複数含むため、凧のレベルの要約ユースケース

コンピュータには直接言及せず、アジャスターの目的だけを書いている。どの部分でコンピュータが役立つかを考え出すための材料となる

ステップ7は保険部のために付け加えたもの

構成の要点: 主成功シナリオは9ステップ（診断書の評価、永続障害の度合いの評価、和解金の範囲の決定、準備金のチェック、権限を越える場合の許可要求、資料の文書化など）。発生頻度（1日に5、6回）、成功時保証、最低保証、利害関係者ごとの利益（請求者は和解金を多く、アジャスター・保険会社は法の範囲内で少なく、保険部と州の役所は公平さと手続きの厳守）、未決定事項（司法上の問題の考慮）を持つ

補足

ユースケース21についての注釈と要点

多くの人には漠然として使いようがなく見えるが、時間をかけて記述した意味がある

複数のユーザー目的のユースケースをつなぎ合わせ、ビジネスのガイドラインのどこに組み込まれるかを表す。請求の完了・削除・アーカイブといった、多くの人にとって謎だった部分が記述されている

最後の3つのステップはプログラマの作業に関係ないが、ストーリーの一部であり、あらゆる読み手に有意義なコンテキスト情報を与える

一部の人しか知らなかったビジネスルールを公式な記録として残せる（チームは前日にこのルールの推測に3時間費やした）

初めて読む人（重役から新入社員まで）にとって概論や目次の役割を果たす。重役は重要なプロセスの漏れを確認でき、新入社員はユーザー目的のユースケースまで下りていける

拡張*a1は失敗処理のユースケースを呼び出している。これはアジャスターには書けないが、技術グループは必ず書かなければならない

構成の要点: 主アクターは顧客、主成功シナリオは10ステップ（請求 → 社員による契約検索・損害情報登録・アジャスター任命 → 調査・更新・経過メモ・金額確保・請求書入力・評価と交渉の記録 → 支払いと完了 → 完了後6か月で削除 → 一定期間後にアーカイブ）。拡張はシステムダウン（*a）、提出データ不十分（1a、さらに期限内に提供されない場合の1a2a）、有効な保険に入っていない（2a）、対応できる代理人がいない（3a、対処は未記入）、別の請求作業の通知（8a）。未決定事項は「アーカイブする期限」

補足

ユースケース22についての注釈と要点

著者が経験した中で最も複雑なユースケース。なぜユースケースを自然言語の文章（散文）で書かなければならないかがわかる

複雑にしている最大の原因は順番

混乱状態の顧客と電話で話す社員は、標準的な質問の順序に従いながら、どのような順番でも情報を入力できなければならない

コンピュータは情報が入力されたそばから、できるだけの処理（顧客のレコードを取り出す、請求番号とアジャスターを割り振る等）を行う

明確にするため・通常の作業順序を表すため・非同期に動くコンピュータを示すため、全体を通して少なくとも4回書き直した。これ以上はそれほど改善されないと判断してこの版で止めた

「（何か）を検索する」を何度も呼び出すが、そのたびに検索対象も基準も異なる。チームが検索の標準ステップ（リストのマッチング、ソート、再ソート、探索、見つからない等）を何度も書き直さずに済むよう考えた独創的な解決方法（練習5.4で同じことを行う）

拡張「*a. 電源が落ちる」から、作業途中での保存という新しい要求が生じた

保存するなら、あとで社員が検索できなければならない → 一時的に保存された損害情報の格納と検索の問題

失敗条件6b（一時保存した損害情報のタイムアウト）は、「確認できていない一時入力の損害についてのビジネスルールはどうなるか。重要な情報が欠けているのでコミットできず、最小限の入力基準はクリアしているので削除もできない」という細かい質問を突きつけた

チームは、作業途中で保存せずに損害情報を削除する案も考えたが、許容できない選択肢だった

拡張1cは「失敗の中での失敗」。独立したユースケースにしてもよかったが、ユースケースの集合が複雑になりすぎる（新しいユースケースは追跡・レビュー・維持が必要）ため、拡張の拡張として記述した。ほとんどの人が混乱せず使えるのはこのレベルが限度で、それ以上なら独立したユースケースにする

拡張2-5aは柔軟性を示す。条件はステップ2から5のどこでも起きうる。起きうるステップごとに毎回書くのは労力の無駄なので、単に「2-5a」「2-5b」とした。これで読む側に十分意味が伝わる

補足

構成の要点

主アクター: 社員（冒頭には請求データを取り込むコンピュータシステムも記載）／レベル: 青／事前条件: 社員がログイン済み／トリガー: 損害情報の入力を開始している

成功時保証: 損害情報が入力され保存される／最低保証: 何も起こらない

主成功シナリオの前置き: 社員の能率のため、システムは必要なデータが入力されたらすぐに非同期で処理する。社員は好きな順番で入力できる。以下は一番起きそうな順番を想定したもの

主成功シナリオは6ステップ（契約の特定と合致確認 → 基本情報入力と重複確認・請求番号割り振り → 請求種別に特有の情報 → 担保情報の取り出し要求 → アジャスター割り当て → 完了確認と保存・代理人への通知）

拡張は多階層（*a電源断、*b処理対象外の請求、1a〜1d、2-5a／2-5b、2c重複の可能性、2d、2e途中保存、4-5a、6a最低限の情報不足、6bタイムアウト）

ビジネスルール・使用されるデータ記述・UIリンク・オーナー・レビュー主担当者・未決定事項（自動保存の頻度、代理人への通知状の印刷時期と方法）の欄を持つ

補足

「何かを検索する」の汎用化とユースケース23

チームは「顧客を検索する」「製品を検索する」など、ほとんど同じユースケースを記述するのは意味がないと判断し、すべての記述チームが使える汎用のメカニズムを作った

「…を検索する」という文は、ユースケース「何かを検索する」が呼ばれることを表す。「何か」は暗黙に特定の単語に置き換えられる

各ユースケースで独自の検索・ソート・表示の基準が要るので、データや検索の制約はハイパーリンクでつながれた別のシートに記述する（例: 「顧客の詳細検索を使って顧客を検索する」）

利点: 何かを検索するの具体的な手続きを一度だけ記述し、異なるコンテキストで使える。開発側も同じメカニズムで検索されるとわかり、共通のものを1つだけ開発すればよい

解決法は練習5.4のあと、14.2節「パラメタライズドユースケース」で説明

ユースケース23「何かを検索する（問題記述）」（魚）は本文では「練習で作成する」とだけ示される

練習（5.7）

手順

目的レベル

  1. 5.1 ATMの前で暗証番号を入力し終え確認ボタンを探しているジェニーにとっての、白・青・藍の目的を挙げる

  2. 5.2 ATMのさまざまな主アクターがATMに対して持つ目的を少なくとも10個挙げ、目的レベルを指定する

  3. 5.3 練習4.4の金融取引プログラムについて、すべての主アクターの要約目的とユーザー目的を挙げる。一番レベルが高く一番外側にあるアクター・スコープ・目的の組み合わせはどれか

  4. 5.4 何かを検索する ユーザーが何かを探したいと思ったことをトリガーに始まるユースケースを記述する

規則
  • ユーザーは検索およびソート用の情報を入力できなければならない
  • 起きる可能性のある状況にすべて対応できなければならない
  • 成功した場合、コンピュータによって「何か」が識別され、呼び出し側のユースケースで指定された次の用途に使えるようになっていなければならない

アンチパターン

誤り起きること代わりにすること
水中（藍）のユースケースだけで要求文書を作る100ページ以上のすべて藍色のユースケースは長く退屈で役に立たなかった。海面レベルの6つのほうが理解しやすく扱いやすかった。
海面レベルのつもりで水中のユースケースを書く初心者に多い「主アクターは本当は何を望んでいるのか」「なぜこれを行っているのか」と問い、目的レベルを上げる。
黒（貝）のユースケースを記述する「Tabキーを押す」のような低すぎる目的はユースケースにせず、呼び出し側のユースケースに含める。
ステップが10以上あるUIの詳細を含めているか、ステップのレベルが低すぎるUIの詳細を除き、目的レベルを上げ、ステップを統合する。
お気に入りのフレーズがユースケースのタイトルになるかで騒ぎ立てるタイトルになるかどうかは重要度と無関係。それ自身がユースケースになることを保証されているのは青の目的だけ。
一番外側のユースケースから機能要求を読み取ろうとする一番外側のユースケースは作業の取りまとめ用で、機能要求はユーザー目的（青）のユースケースに含まれる。
