usecase-advisor を、『ユースケース実践ガイド』の判断基準で起こす

決めたこと

アリスター・コーバーン『ユースケース実践ガイド』を原典とする advisor（usecase-advisor）を、ddd-advisor と同じ形で置く。

なぜ決める必要があるか

利用者の決まりで、advisor の原典は公式情報 ・ 書籍 ・ 確立された方法論に限る。ユースケース駆動の作業には、その原点となる書籍を原典とする advisor が無かった。ddd-advisor で確立した形（章ごとの書籍のノート、原文に無い文字列0件の照合、論点と9種類の単位、design-svg の図、契約の版2 の道具）をそのまま適用し、この経験を advisor-creator の作り直しへ戻す。

どう変わるか

変更前と変更後

何が変更前変更後
原典ユースケースを扱う advisor が無い『ユースケース実践ガイド 復刻版』（翔泳社）。スキャンと章ごとの学習ノート26本は手元だけに置き、git の管理の外にする

案採らなかった理由
原典を一言一句書き写して archive に置き、そこから判断基準を作る利用者の決まりは ddd-advisor と同じ粒度の構造化したノートであり、書き写しは求められていない。著作物の全文の複製にもなる
advisor-creator を先に作り直し、その道具で usecase-advisor を作るadvisor-creator の作り直しは、判断基準の形と手順が固まってから行うと決めている。usecase-advisor を先に作り、その経験を作り直しへ戻す
章を分けずに、概念ごと（アクター ・ スコープ ・ 目的レベル …）に判断基準を立て直す章をまたいで文を集めると、ノートに無いつなぎの文が要る。章の単位ならノートの見出しをそのまま論点にでき、原文に無い文字列を0件に保てる
答える問い（answers）を、ノートに無い問いの形の文で書く原文に無い文字列を足すことになる。各章の節の見出しを、そのまま答える問いに使う

ユースケースの概念質問・判断・記述に根拠を示して答えるのを担当するadvisor Skill：usecase-advisor

目的

ユースケースについての概念質問・判断相談・記述相談を受けたときに使う。アリスター・コーバーン『ユースケース実践ガイド』の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む（ACDR 0043）。

役割

- ユースケースのアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、利用者が書いているユースケースに当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
概念質問「〜とは」「〜の違いは」等の質問形式concept定義 ・ 具体例
判断相談「〜すべきか」「この記述でよいか」等の質問形式。書いたユースケースの点検も含むjudgment比較した案 ・ 判断の道筋
記述相談「〜はどう書くか」「〜の書式は」等の質問形式writing記述の手順

入力の想定

受け取る情報解釈・既定値
質問の種類(概念質問/判断相談/記述相談)明示されなければ質問文の形式から判定する
相談対象のシステム ・ ユースケースの記述明示されなければ利用者に確認する。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

質問を「概念質問」「判断相談」「記述相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、道具で1件ずつ取り出して読む。読む前に回答を始めない。

usecase-advisor get criteria <id>        判断基準を1件取り出す（JSON）
usecase-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 語の意味を確認するときは、用語集（glossary）も読む

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

usecase-advisor validate --kind answer --file <回答.json>      欄の欠けを検出する
usecase-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く
- 図（figure）は節点と辺で宣言し、design-svg が組んだ SVG を svg の欄に置く
- AI が作業するときの注意（ai_cautions）は、一般論ではなく、違反しやすい点と検査する方法の組で書く

出力形式

回答の JSON と、描画した HTML である。 人は HTML で読む ── チャットに回答の文章を流さない。

置くもの内容
結論判定と1文の結論。最初に読む
図 ・ 比較 ・ 道筋 ・ 手順結論に至った構造。種別で必須の欄が変わる
根拠判断基準の id と、その記述の引用
次にすること動詞で始まる行動

ガードレール

- 判断基準を道具で読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 定義文 ・ 判断基準は criteria から引用し、勝手に言い換えない
- 判断相談では必ず判定理由を示す。「〜です」で終わらせない
- アンチパターンに該当する場合は必ずリスクと代替案を組で示す。判断基準の antipatterns に代わりにすること（alternative）が無いときは、回答の側で組み立て、推測であることを明示する ── 判断基準は原典に無い文を保持しない
- 回答は validate に合格してから渡す。 欄の欠けを機械で検出できる形にしたので、手で確認しない
- 判断基準（criteria.json）は原典の内容だけを持つ。回答ごとの考察を書き加えない
- 判断基準は原典の複製ではない。 章ごとに節と項をすべて残して要点を構造化した学習ノートから移したものである ── 原典の文そのものを参照していると断言しない。引用は「判断基準の記述」として示す
- 専門用語は使ってよいが、初出時は文脈 ・ 具体例を添える。相手がユースケースを初めて書く人である可能性を常に想定する

Skillの組み合わせで作業を遂行するリポジトリ：daidaiiro

管轄範囲

- 管轄ディレクトリ: リポジトリ全体
- 概要: .claude/skills/ に置いた18のSkillを組み合わせて、調べる・決める・書く・直すを遂行するリポジトリである。1つのSkillで終わらない作業は、配線表 skill-wiring.json が「何を、誰に頼むか」を持ち、skill-router がそれを読む。

自身の役割

Orchestratorである。作業を受け取ったら、skill-router に配線表を引かせ、返ってきたSkillを呼び、結果を突き合わせて1つの答えにする。

誰が持つもの何を持つか
配線表 skill-wiring.jsonrequest（何を頼むか）・when（どの作業のとき）・skills（呼ぶSkill）・reliance（結果をどれだけ当てにするか）
skill-router配線表の読み方
Orchestrator（この文書）いつ呼ぶか・どう並べて呼ぶか・返ってきたものをどうまとめるか

配線表は「いつ呼ぶか」を保持しない。作業の前に材料を集めるのか、作業のあとに十分かを確認するのか、両方かは、そのつどOrchestratorが決める。

運用ルール

ルールなぜ適用方法
作業を始める前に、まず skill-router へ問い合わせる作業側のSkillと呼ばれる側のSkillが互いを呼ぶ形を避け、判断の窓口をOrchestrator側に置くため（skill-router自身の設計原則）作業の名前と対象を渡す。配線表に行があれば request と skills を受け取る。行が無ければ、その作業は1つのSkillで終えられるものとして進む
配線の行を、この文書へ複製しない複製は必ず本体とずれる。配線表とこの文書の2か所に同じ行があると、どちらが正しいかを毎回確認することになる組み合わせを足す・変える・消すときは skill-wiring.json を直す。この文書が書くのは、配線表の呼び方だけである
呼ぶSkillが2つ以上あるときは、1回のメッセージで並列に呼ぶ1体ずつ順に呼ぶと、後のSkillが前の結論に引きずられ、独立した意見として機能しなくなる各Skillに、それぞれ独立した目的・役割・タスク・成果物・受け入れ基準を持たせて同時に発行する
reliance に書いてある値を、そのまま振る舞いにする3つの値は、呼べなかったときの振る舞いを決めるためにある。読み替えると配線表が意味を失うrequired＝返るまで進めない（呼べなければ止める）／advisory＝待たずに進め、返った時点で渡す／optional＝相手が居なければ呼ばずに進む
人が読む文書を書き起こしたら、doc-writing-skills の10の判定を適用してから出す判定を適用していない文書は、論・構造・文調・語彙のどれが成立していないかを誰も言えない.claude/skills/doc-writing-skills/bin/doc-writing-skills check <ファイル> でゲート1を実行し、10の判定の結果を1行ずつ報告に書く。どこから実行してもよい
出力の前に、読み手の判断基準で自己点検する書き手は判断の根拠を保持しているので、読み手の判断を妨げる表記を検出できない。書き手の内部では整合していても、読み手の側では別の判断になる出す直前に、5つの不変条件を検証する ── ①語の含意が対象の性質と一致する ②節の名前と中身の対象が一致する ③各項目が読み手の問いに回答している ④1つの欄に1つのことだけが入る ⑤述部が漢語である。1つでも破れていれば、出す前に修正する
利用者への応答も、述部を漢語で記述する和語の述部は意味の範囲が拡大し、どの操作を指すか特定できない。文書だけ規制しても、会話で使用した語が文書へ流入する定義と検出語は doc-writing-skills の概念8（公用文作成の考え方 Ⅲ-4 ウ）が保持する。この文書は複製しない
語を新しく作らない新造語は辞書にも分野にも無いので、読み手が意味を確定できない。比喩でも和語でもない造語が在るので、既存の2つの規則では捕捉できない判定は2つ ── その語を検索して同じ意味が出てくるか ／ 意味を特定できる既存語が在るか。片方でも満たさなければ、その語を使用しない。定義は doc-writing-skills の概念8が保持する。応答にも適用する
比喩で言い換えず、対象の名前で記述する比喩は指し先が読み手の側で決まらない。応答で使用した比喩は、そのまま文書へ流入する対象を別の物へ置き換えた語を使用しない。検出する語は .doc-writing/retired-words.json が保持し、ゲート1が検出する。この文書は複製しない
