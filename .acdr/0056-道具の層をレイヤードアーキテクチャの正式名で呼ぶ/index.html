道具の層をレイヤードアーキテクチャの正式名で呼ぶ

決めたこと

道具のソースの3層を「サービス層を挟んだレイヤードアーキテクチャ」と定め、文書 ・ フォルダ ・ crate の名前を、その層の正式名（プレゼンテーション層 ・ サービス層 ・ 業務ロジック層）で呼ぶ。

なぜ決める必要があるか

契約の独自の語（部品 ・ 宣言 ・ 入口 ・ 許可辺）は、利用者から「ものすごくわかりにくい」と指摘された。確立した語へ寄せるため、ddd-advisor に判断基準で照らさせた。この構成は依存の逆転（内側が抽象を定義し、外側が実装する）を持たないので、ヘキサゴナルでもクリーンでもなく、サービス層を挟んだレイヤードアーキテクチャである（判断基準 architecture-patterns）。そこで語をレイヤードの層の正式名に一致させる。フォルダと crate の名前も改める。文書だけ改めると、文書は「業務ロジック層」、コードは parts という2つの語彙を、読み手が対応づけることになる。いま決めるのは、これから6つの言語の組の雛形を起こすからである（ブレストボード skills-creator-profiles）。後で改めると、その6組も直す対象に加わる。あわせて、検査が許していた「層を飛ばす依存」（入口から部品）を禁じる。許していたのは、道具の層のために決めた規則ではない。no-more-spaghetti の一般則「依存は外から内へ向かってよい」を、Rust へ移したとき（コミット edd3499）に当てはめた結果であり、層を飛ばしてよいかを判断した記録は無い。サービス層を置く理由は道具の一覧を1か所に保つことであり、飛ばすと一覧を経ない呼び出し方ができる。既存の14件の Skill に、層を飛ばす依存は0件である（2026-09-30 に Cargo.toml を検索した）。

比較した案と、採らなかった理由

案採らなかった理由
ヘキサゴナルとクリーンのハイブリッドの語（アダプタ ・ ユースケース ・ ドメイン）で呼ぶ両者の核心である依存の逆転を、この構成は持たない。名乗ると、備えていない性質を名前で主張することになる。「ドメイン」は集約などのドメインモデルを連想させ、業務の状態を持たない変換の関数の層と一致しない
純ヘキサゴナルへ作り替える（ファイルと外部コマンドの前にポートを置く）判断基準では、ポートとアダプターが向くのはドメインモデルを使う複雑な業務ロジックである。道具の大半は変換の関数なので、実装が1つしかない抽象が増えるだけである
業務ロジック層のフォルダを core と呼ぶ判断基準で「コア層」が別名に挙がるのは、ポートとアダプターの系統の表だけである。レイヤードの表の別名は「ドメイン層 ・ モデル層」で、core を使うと外したヘキサゴナルの語彙が戻る
業務ロジック層のフォルダを logic と略すレイヤードの層の名前として一般的な語ではない。正式名の直訳 business_logic なら、文書の「業務ロジック層」と対応表なしで1対1に読める
文書の語だけ改め、フォルダと crate は parts ・ declare のまま残す文書とコードで語彙が2つになり、読み手が対応づけることになる。今回わかりにくいと指摘されたのは、まさにこの種の対応づけである

道具の契約：tool-contract

目的

Skill が道具（実行ファイル）を伴うとき、呼ぶ側に形を推測させないために使用する。

道具ごとに呼び出し方の形が違うと、呼ぶ側は呼ぶたびに本文を読み直す。
契約は、呼び方を1つに固定する。

契約は、呼ぶ側から観察できるものだけを規定する（ACDR 0036）。道具を書く言語と、
配布するかどうかは、利用者に委ねる。言語ごとの実装の形は言語の組が持ち
（いまは references/profiles/rust.md だけ）、配布は任意の機能として
references/distribution.md が持つ。

置く先中身
契約（この文書）CLI と MCP の2つのプレゼンテーション層と起動のコマンド ・ CLI の規約 ・ 1つの道具の一覧から CLI と MCP を組む ・ MCP の規約 ・ Skill のフォルダの求め方 ・ 外部の道具 ・ 層と依存の向き ・ 1段目の検査
言語の組実行ファイルの置き場所 ・ ソースの構成 ・ 雛形 ・ 組み立てのコマンド ・ 2段目の検査
配布（任意）配布物 ・ 導入スクリプト ・ 組み立ての定義

言語の組を作ってよい言語の条件は、公式の MCP の SDK が在ることだけである。
組が持つのは、雛形 ・ 組み立てのコマンド ・ ソースの検査の3つである。

原則

能力は1つ、呼び出し方は複数である。

能力をサービス層の道具の一覧に1度だけ書き、CLI と MCP はその一覧から組む。
能力を2か所に書くと、片方だけが古くなる。

呼び出し方が欠けても、能力は欠けない。
MCP の実装が無い環境では、MCP サーバーは立たず、CLI だけが動く。

層と依存の向き

道具のソースは、サービス層を挟んだレイヤードアーキテクチャで組む。 層は3つである。
依存は上から下へだけ向け、層を飛ばさない。

層置くもの依存してよい先呼び出し方を持つか
プレゼンテーション層（CLI ・ MCP）呼び出し方。引数を受け、結果を印字し、終了コードを返すサービス層持つ。CLI はシェルから呼ぶ唯一の経路
サービス層道具の一覧（名前 ・ 引数 ・ 説明）と、業務ロジック層の関数との対応。外部の道具を tool.json から読み、業務ロジック層へ渡す業務ロジック層持たない
業務ロジック層組み立て ・ 描画 ・ トークン ・ 検査など無し持たない

サービス層を置くのは、プレゼンテーション層が2つ在るからである。 CLI と MCP の違いから業務ロジックを隔離し、道具の一覧を1か所に保つ。

業務ロジック層に、集約 ・ エンティティ ・ リポジトリの型を作らない。 この層が置くのは、業務の状態を保持しない変換の関数である ── 層の名前から連想してドメインモデルの型を導入すると、使わない抽象が増える。

この構成を、ヘキサゴナルアーキテクチャともクリーンアーキテクチャとも称さない。 両者の核心は依存の向きを逆にすること（内側が抽象を定義し、外側が実装する）であり、この構成はそれを保持しない ── 称すると、備えていない性質を名前で主張することになる。

ポートを導入するのは、業務ロジック層が使う外部（ファイル ・ 外部コマンド）を差し替える必要が生じたときに限る。 それまでは、実装が1つしかない抽象を作らない。

どう守らせるかは、言語の組が決める（Rust は crate の境界に置き、各 Cargo.toml が依存の向きを宣言する）。

ガードレール

- 節の構成を、対応する雛形と一致させる。助言の Skill は advisor-creator の雛形、それ以外は
こちらの雛形を満たす ── どちらを適用するかは節の有無で決まる（名前で分岐すると、Skill が
増えるたびに検査を直すことになる）
- 道具を持つ Skill には、道具の契約を適用させる（references/tool-contract.md）── 呼び出し方の形が道具ごとに違うと、呼ぶ側は呼ぶたびに本文を読み直すことになる
- 同じ概念の仕組みは、同じ実装の形にさせる。入力の契約（スキーマ）・トークンの正本・入力の検査・置き場所を、Skill ごとに違う形で実装させない ── 概念が同じで形が違うと、1つを読んで得た理解が、次の Skill で通用しない
- 能力を2か所へ記述させない。CLI と MCP は、サービス層の道具の一覧から組ませる ── 同じ能力を2度書くと、片方だけが古くなる
- 業務ロジック層の関数に呼び出し方を付けさせない。業務ロジック層の関数は道具の一覧に載せない ── 載せると、同じ能力に呼び方が2つできる
- 道具の層を、サービス層を挟んだレイヤードアーキテクチャにさせる。依存は上から下へだけ向け、層を飛ばさせない ── 飛ばすと、道具の一覧を経ない呼び出し方ができる。業務ロジック層に集約 ・ エンティティ ・ リポジトリの型を作らせない
- 道具に印字させない。戻り値は {ok, findings, data} とし、印字と終了コードはプレゼンテーション層が持つ ── 道具が印字すると、MCP から呼んだときに戻り値が空になる
- ガードレールと手順を、不変条件で記述させる。1回の出来事・特定の語・特定の形を規則にしない ── 規則が事例の形を取ると、その形だけが規制され、他の形は通過する。規則が禁じるのは性質であって、その性質が現れた1つの形ではない
- 例を規則本体へ混ぜさせない。例を添えるなら「例」と明示し、規則の文とは分離する ── 混ざると、読み手は例の範囲を規則の範囲として解釈する
- SKILL.md は必ずスキルフォルダのルートに置く。サブフォルダには置かない
- テンプレートファイルは assets/ ではなく references/ に置く
- 不要なフォルダは作らない。使うものだけ作る
- プレースフォルダーを記入する前に必ずreferences/placeholder-definitions.mdを参照する。定義票なしで記入しない
- スキル名は英小文字・ハイフン区切りに統一する（スペース・アンダースコア不可）
- ユーザーが要件を明確にしていない場合は作成を開始しない。必ずヒアリングを先に完了させる
- 新しいSkillに、特定の外部ツール・システム（Waffle、特定のCLI/MCP等）の存在を自ら判定して振る舞いを変えるロジックを持たせない。汎用のSkillが具体的な実装の有無を参照するのは依存性の方向違反であり、正しい向きは「具体的なシステムの側が汎用Skillを自分の中に注入・統合する」（composition-rootの原則）。特定システムとの統合が必要な場合は、そのSkill自体は単一の環境非依存な実装のままにし、統合はSkillの外側（呼び出し側・Orchestrator側）に置く設計を選ぶ
