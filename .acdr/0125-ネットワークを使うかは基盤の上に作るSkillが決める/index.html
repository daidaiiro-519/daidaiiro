ネットワークを使うかは、基盤の上に作る Skill が決める

決めたこと

ネットワークに出ない決まりは schema-driven の crate にだけ当て、ネットワークを使うかは、基盤の上に作る Skill が自分のアダプタで決める。スキーマの供給元を出ていく側のポートに分ける

なぜ決める必要があるか

ACDR 0122 は「ネットワークに出る機能を外す」と決めたが、それがどの crate に当たるかを書いていなかった。schema-driven は基盤なので、その上に作る Skill へ転写される。fact-check のように原文を取得する Skill はネットワークを使う。決まりを製品全体に当てると、その Skill が作れない。ヘキサゴナル（ACDR 0121）では、入出力の違いは出ていく側のポートとアダプタに寄せる。そこで、基盤はポートを定義するだけにし、ネットワークを使う実装はその Skill のアダプタに置く。外のスキーマを $ref で使いたい場合も、基盤は取りに行かず、Skill のアダプタが取得して渡す。そのために、これまで Files の中にあった「$ref の先のスキーマを返す」処理を、スキーマの供給元（Schemas）のポートに分けた

どう変わるか

変更前と変更後

何が変更前変更後
ネットワークに出ない決まりの範囲schema-driven（範囲を書いていない）schema-driven の crate（転写される部分）。検査は crate を指定して行う（cargo tree -p schema-driven-core -i reqwest など）
ネットワークを使う Skill決めていないその Skill の adapters/outbound が、core のポートを実装するときに使う
$ref の先のスキーマポート Files の sibling_schemas が返すポート Schemas の referenced が返す。基盤のアダプタは同じディレクトリから読み、外のスキーマは Skill のアダプタが取得して渡す

比較した案と、採らなかった理由

案採らなかった理由
ネットワークに出ない決まりを、基盤の上に作る Skill すべてに当てるfact-check のように原文を取得する Skill が作れない
基盤に、ネットワークを使う機能を入れておく（jsonschema の resolve-http など）使わない Skill にも、黙って外へ取りに行ける経路が入る
