土台のヘキサゴナルの図と判定の文脈を直す

決めたこと

抽象概念の土台のヘキサゴナルの図を、矢印が呼び出し ・ 依存 ・ 実装の向きだけを表し、ポートが六角形の縁に並ぶ形にし、セッションのタブの判定の手順に、別の文脈で判定するよう書くことを足す。

なぜ決める必要があるか

ヘキサゴナルの図は、domain から application への上向きの矢印で「domain はポートを知らない」と依存の向きに反していた。application からの線は3つのポートのうち1つにしか届かず、ポートの箱は六角形の外に置かれ、API の矢印は application の箱の下の何も無い所を指していた。セッションのタブは、Semantic Agent Schema の版31 でボード sas-open-decisions の Q2 が決めた「判定の手順に、別の文脈で判定するよう書き、判定したのが誰かは見分けない」を持っていなかった。図をポートとアダプターの型に、タブの文を Q2 の決定の一般の形に合わせる。

何が変更前変更後

比較した案と、採らなかった理由

案採らなかった理由
domain から application への矢印を残し、「値を返す」と説明を足す。依存の向きと戻り値の流れが同じ記号になり、「domain はポートを知らない」と読み分けられない。
application からポートへの線を1本のまま、ポートを束ねる囲みに向ける。どのモジュールがどのポートを使うかが読めない。
ポートの箱を六角形の内側に入れる。ポートは中と外の境の約束で、縁に置く型と合わない。アダプターとの間も遠くなる。
判定した人を見分けて、書いた本人の判定を断る。サブエージェントの ID は親の会話と同じなので見分けがつかず、作成者のテストも正当な水準である（Q2 の反証）。
判定のたびに新しい文脈を立てるよう手順に書く。毎回すべてを読み直し、プロンプトキャッシュが効かない（Q2 の実測）。続けて使うかは Semantic Agent Schema の具体に置く。
