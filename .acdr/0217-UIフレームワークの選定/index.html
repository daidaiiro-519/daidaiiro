UI フレームワークを Angular に決める

決めたこと

AI だけでコードを書く開発の UI フレームワークを Angular にし、AI が書いたものの合否をツールの検査で決める。

なぜ決める必要があるか

semantic-contract-core v0.3 は UI フレームワークを「Angular / Svelteも検証器・Renderer・チーム特性で評価し、未決。」としたままで、技術を選ぶ軸だけを「AI 生成実装の機械的検証可能性」に置いていた。利用者は、AI だけで書く前提で「ルールが厳格で、書き方が公式で決まっている UI」を条件にした。Angular ・ Svelte ・ React の公式資料を原文で照合した結果、この条件をいちばん満たすのは Angular だった。PoC を始める前に UI フレームワークと合否の決め方を決めておかないと、PoC の結果が本番の判断材料にならない。

どう変わるか

変更前と変更後

何が変更前変更後
UI フレームワークAngular ・ Svelte ・ Vue ・ React を比べる候補として並べ、未決のまま。Angular（2026-10-31 時点の安定版 22.2.4）にする。
AI が書いたものの合否決める検査が無い。AI の誤りは、画面を触った人が気づくまで残る。コンパイラと lint が書き方の誤りをエラーにし、spec の試験と AXE が振る舞いとアクセシビリティを検査する。見た目だけは、スクリーンショットの差分を人が見て決める。

比較した案と、採らなかった理由

案採らなかった理由
Svelte（5.57.3 ／ SvelteKit 3.1.1）にする。ダイアログ ・ フォーカスの部品が公式に無く、新しいフォームの仕組み（remote functions）は experimental なので、そこを自分たちで決めて作ることになる。
React（19.3.1）にする。ルーター ・ データ取得 ・ フォーム ・ スタイルを本体が決めていないので、構成を固定するルールを自分たちで作って維持することになる。
Vue にする。Options API と Composition API の2通りの書き方があり、AI が混ぜて書く。公式で書き方が1つに決まっていない点で React と同じ弱点を持つ（原文では調べていない）。
Go と templ と htmx で、サーバーが HTML を返す形にする。htmx の属性は文字列なので、hx-target の打ち間違いをコンパイラが検出しない。ダイアログのフォーカスなど、ブラウザ側の操作も自分で作ることになる。
Rust の Leptos にする。部品のエコシステムが小さく、AI の知識も少ない。検証の crate をブラウザと共有する利点は、WASM が要らない構成では無くなる。

UI フレームワークの調査結果：Angular ・ Svelte ・ React

結論

AI だけでコードを書く開発の UI フレームワークには、Angular を選ぶ。

選ぶ条件は「ルールが厳格で、書き方が公式で決まっていること」である。3つのうち、この条件をいちばん満たすのは Angular だった。

条件Angular がどう満たすか
書き方が公式で決まっているルーター ・ フォーム ・ HTTP ・ 試験 ・ ビルドを、すべて公式が提供している
AI が書いたものの合否を、ツールで決められるコンパイラの設定と angular-eslint で、古い書き方と型の誤りをエラーにできる
UI の部品を公式から使えるダイアログ ・ フォーカス ・ キーボード操作を、公式の CDK と Angular Aria から使える
AI が最新の書き方で書く公式が、AI 向けの指示（best-practices.md）と Agent Skills を出している

この文書の読み手は、UI フレームワークを選ぶ人と、選んだ理由をあとから確かめる人である。

Svelte を選ばなかった理由

ダイアログ ・ フォーカスの部品と、フォームの仕組みを、自分たちで決めて作ることになるからである。 原文は "you are still responsible for making sure your application code is accessible." と書いている。SvelteKit 3 で設定ファイルが svelte.config.js から vite.config.js へ移り、eslint-plugin-svelte の文書がまだ古い置き場所を前提にしているという食い違いもある。

コードの短さと、svelte-autofixer を AI の作業のループの中で呼べる点は、Angular より優れている。

React を選ばなかった理由

ルーター ・ データ取得 ・ フォーム ・ スタイルを、本体が決めていないからである。 原文は "does require that you make choices on which tools to use for routing, data fetching, and other common usage patterns." と書いている。選んだ構成を固定するルールを、自分たちで作って維持することになる。

React Compiler 1.0 と eslint-plugin-react-hooks 7 を使えば、hooks の誤りは Angular と同じ程度に lint で検出できる。AI が最初の1回で正しく書ける割合がいちばん高いのも、React だと考えられる（推測）。

Angular の厳格化の仕組み

書き方の誤りは、コンパイラの設定と lint でエラーにする。 設定キーとルール名は、すべて原文で照合した。

種類設定キー ・ ルール名エラーにするもの
コンパイラstrictTemplates（既定で有効）テンプレートの型の誤り
コンパイラstrictStandalonestandalone でない部品
コンパイラstrictInjectionParameters ・ strictInputAccessModifiers型が決まらない注入、private な input への書き込み
コンパイラextendedDiagnostics（defaultCategory を error）呼び忘れた signal など、18 件の拡張診断
lint（recommended）prefer-standalone ・ prefer-inject ・ prefer-on-push-component-change-detection ・ template/prefer-control-flowNgModule ・ コンストラクターでの注入 ・ *ngIf などの古い書き方
lint（個別に有効にする）prefer-signals ・ no-developer-preview ・ no-experimentaldecorator の input ・ 安定していない API
lint（accessibility）template/alt-text ・ template/label-has-associated-control ・ template/click-events-have-key-events など 11 本アクセシビリティの誤り
lint（typescript-eslint）no-explicit-any ・ template/no-any型の検査を無効にする書き方（any ・ $any()）

コンパイラと lint で検出できない誤りは、別の検査で検出する。

コンパイラと lint で検出できない誤り検出する検査
振る舞いの誤り（例：承認の前に承認ボタンが出る）spec の単体テスト。ng generate が作る spec は「部品が作れる」ことしか確かめないので、振る舞いの試験は、AI PdM の Blueprint の設計書（docs/08_IMPLEMENTATION_HANDOFF.md）と受け入れの条件（docs/09_POC_ACCEPTANCE_AND_TEST_PLAN.md）から書く
見た目の誤りPlaywright でライト ・ ダーク ・ 狭い幅のスクリーンショットを撮り、差分を取る
AXE が検出するアクセシビリティの誤り（best-practices.md が "It MUST pass all AXE checks." と求めている）AXE の検査。公式の Skill の手順には入っていないので、試験に足す

AI が書いたときに起きること

AI が誤った書き方をしても、検査がエラーを返し、AI がそのエラーを読んで直す。 次の表は、決める前と決めたあとで、同じ誤りがどう扱われるかを並べたものである。

AI が書いたもの決める前決めたあと
*ngIf で条件を書いた何で検査するかが決まっていないので、古い書き方のまま残るtemplate/prefer-control-flow がエラーを返し、AI が @if に書き直す
@Input() のデコレーターで入力を書いた同じく残るprefer-signals がエラーを返し、AI が input() に書き直す
型を any にした同じく残るno-explicit-any がエラーを返し、AI が型を書く
クリックで開くメニューを <div> で作り、キーボードで操作できない画面を触った人が気づくまで残るtemplate/click-events-have-key-events と AXE の検査がエラーを返し、AI が <button> か Angular Aria の Menu に直す
候補を選ぶ前に承認ボタンを表示した画面を触った人が気づくまで残るspec の試験が失敗し、AI が表示の条件を直す
狭い幅で承認ボタンがはみ出した画面を触った人が気づくまで残るPlaywright のスクリーンショットの差分が出て、人が見て合否を決める

最後の行だけは、合否を人が決める。見た目の正しさは、どの検査でも決められないためである。

AI 向けの公式の仕組み

best-practices.md は AI に正しい書き方を教えるもので、守らせるものではない。 守ったかどうかは、上の厳格化の仕組みで確かめる。

もの置き場所中身
best-practices.mdangular/angular の packages/core/resources/best-practices.mdstandalone ・ signals ・ @if/@for ・ input()/output() ・ Signal Forms ・ inject() を使うこと、any ・ ngClass ・ CommonModule を使わないこと、WCAG AA と AXE を満たすこと。ng new --ai-config=claude などで、AI ツールごとの設定ファイルとして置かれる
Agent Skillsgithub.com/angular/skillsangular-developer（領域ごとの references 44 本の索引）と angular-new-app。Agent Skills の公開の仕様に沿っているので、Claude 以外の AI ツールでも使える。angular-developer は、書き終えたら ng build が通るまで直すことを手順にしている

Angular を選ぶときの制約

AI が最初の1回で正しく書ける割合は、React より低い。 学習しているコードの量が少なく、古い書き方（NgModule ・ *ngIf）のコードが多く含まれるためである（推測）。古い書き方は lint とコンパイラがエラーで返すので、できあがるものの正しさは下がらない。

制約中身
ネイティブのモバイルアプリ公式が提供する手段は PWA（ng add @angular/pwa）までである。React は推奨の一覧に Expo を挙げている
ファイルの数ng generate component は ts ・ html ・ css ・ spec の4つを作る
拡張診断の増え方公式は "The Angular team intends to add or enable new extended diagnostics in minor versions of Angular" と書いている。版を上げると、新しい警告やエラーが出ることがある

デザインの自由さは、3つとも変わらない。CDK の Dialog と Angular Aria は見た目を持たないので、AI PdM の Blueprint（AI_PdM_Purpose_Discovery_Blueprint_v0.9.zip）の design-system/tokens/ にあるデザイントークン（palette-tokens.json ・ themes.css）で、見た目を作れる。見た目が Material Design になるのは、Angular Material を使った場合だけである。
