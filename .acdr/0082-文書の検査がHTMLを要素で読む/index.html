文書の検査が、HTML の頁を要素で読む

決めたこと

doc-writing-skills のゲート1は、HTML の頁を要素ごとの単位で判定し、タグとコードを書き手の文として判定しない。

なぜ決める必要があるか

ACDR 0081 の頁にゲート1を実行すると、2件の「強調が描画されない」が出た。どちらも差分に並んだ Rust の注記の行で、閉じの ** の直後に在るのは文字ではなく </span> のタグだった。ゲート1は HTML の頁も Markdown として1行ずつ解析するので、タグの文字を本文と数え、コードの行も本文として判定していた。SKILL.md の説明は「既存のmdやHTMLの本文を直すときに必ず使う」と HTML を対象に含めているので、HTML を正しく解析しないのは Skill の欠陥である。利用者から「doc-writing-skillsは直さないんですか？」と問われた。

どう変わるか

変更前と変更後

何が変更前変更後
HTML の頁の解析Markdown として1行ずつ解析する（タグも本文の文字として数える）要素ごとの単位へ分割する（見出し ・ 段落 ・ 箇条書き ・ 表の欄 ・ 引用）
HTML の中のコード本文として判定するpre ・ code の中身はコードとして処理し、script ・ style ・ template の中身は判定しない
記号で囲んだ中の **強調の記法として判定する判定しない（Markdown でも同じ）
acdr のコードの差分コードの行を表の欄に直接置くコードの行を code の要素に格納する。見た目は変化しない

比較した案と、採らなかった理由

案採らなかった理由
HTML の頁ではタグを取り除いてから、Markdown として解析する1行に並んだ要素が1つの単位になり、見出しと表の欄の区別が消える。コードの行とその説明の区別も消えるので、コードを本文として判定する誤りが残る
acdr の頁だけを、ゲート1の対象から外す記録の本文（決定 ・ なぜ ・ 比較した案）は人が読む文書であり、CLAUDE.md の規則はゲート1の適用を求めている。外すと本文の誤りも検出しない
doc-writing-skills の側で、acdr の差分の欄（class="cd"）をコードとして扱うdoc-writing-skills が acdr の内部の形を知ることになる。HTML の標準の要素（code）で表せば、どの頁にも同じ規則が適用される

技術文書としても学術文書としても違和感のない日本語を書く。

論意味が通り、論が成立している
構造情報が、その型に合った形で置かれている

#概念規則判定
1読み手が組み立て直す作業を、書き手が負担する1文の中で、読み手に計算をさせない。名詞句には、指し先を文書の中に置く名詞句を1つずつ抜き出し、「何の」「どこの」「どっちの」「誰が」を問う。文書の中の文字列で答えられない名詞句が1つでもあれば、その文は書けていない。「読み返して不自然か」で判定しない——書き手は指し先を知っているので、不自然に見えない
2情報の型が、置く形を決める対比・条件・手順・分岐を、散文に置かないその段落を、表か図に置き直せるかを試す
3数が増えたら、形を変える並べるものが3つ以上なら、箇条書きか表にする数える
4見出しは、本文を読まずに全体を掴ませる見出しの階層を飛ばさない。見出しを追えば全体の内容がつかめるようにし、見出しを目立たせる。番号は付けても付けなくてもよい ── 統一されているかだけを確認する見出しだけを抜き出して、順に読む。そのうえで、どの本文がどの見出しに属すかが見た目で分かるかを確認する
5結論を先に置き、根拠を後ろに置く節の最初の一文を結論にする各節の先頭文だけを並べて読む
6読み手は、形の違いを意味の違いとして読む同じ立場のものは同じ形で書く。文体は文書の中で1つにする並んでいるものの語尾を見比べる
7語の意味は、文脈の中で定まる同じ文脈では、1つの意味に1つの語だけを対応づける。文脈が変わるなら、変わることを書く用語を列挙し、同じ意味の別の語が無いかを確認する
8読み手が誰かで、選ぶ語と構成が変わる読み手を先に決める。語は、読み手の世界にすでにある語から選ぶ。分野で定着した専門用語はそのまま使い、自分が作った語・訳した語は使わない。使うなら、新しい語だと書いて定義する。名前のあるものを、描写で呼ばない語の出どころを提示できるかを確認する。「この文書のために作った」「英語から訳した」なら、言い換えるか定義する。そのうえで、書いた操作や物に、分野で通っている名前があるかを1つずつ問う。あるなら、描写ではなくその名前を書く——「均す」ではなく正規化する、「流す」ではなく実行する、「鵜呑みにしない」ではなくそのまま信じない。ふつうの日本語の語も、この判定に掛ける。作った語でも訳した語でもないので、出どころだけを確認すると通り抜ける。読み手が分野の外の人でも、描写に置き換えてはならない。言い換えてよいのは、日常語で意味が表せるものだけである（頻回→頻繁に）。日常語で表せないものは、その名前のまま使い、説明を添える
9読み手が一度に扱える量には限りがある1文は短くする。段落は3行から7行にする。文書の限度を決める数える
10比喩と定型句は、読み手によって解けない比喩は、例として明示するときだけ使うその比喩を字義どおりに読んで、意味が通るかを試す

名詞句で終わることは、それ自体では欠陥ではない。
見出し・箇条書きの項目・表のセルは、名詞句で置いてよい（Google と JTF が認めている）。
判定1が見るのは、文の中で読み手が戻るかどうかである。

Step 3: 直したか、残したかを明示する

判定に該当した箇所を、直すか、理由を付けて残すかのどちらかにする。
理由が書けないなら、それは直す対象である。

Step 4: 2つのゲートを実行する

ゲート1は機械が決める。

doc-writing-skills check <ファイル...>
doc-writing-skills check <ファイル...> --synonyms 用語.tsv
検査拠って立つもの
見出しの階層が飛んでいる概念4
文体が混ざっている概念6
並んだ項目の語尾が統一されていない概念6
文字で図や表を描いている概念2
同じ意味の語が2つある（対を渡したとき）概念7
強調が描画されない媒体の決め

最後の1つだけ、概念から導けない。
マークダウンの記法に拠るもので、5つの原典はどれも描画について書いていない。
別枠であることを、--list と名簿に書いてある。

概念3と概念9は、ゲートに入らない。
数は数えられるが、いくつで形を変えるかは文脈で変わるので、0件にできない。
判定として、書き手が適用する。

利用者への応答には、reply を適用する。
応答で使用した語は、そのまま文書へ流入するので、文書と同じ語彙表で照合する。
適用するのは和語の述部と廃語の2つだけで、見出しや文体の判定は適用しない。

doc-writing-skills reply --message <本文>   # 本文を直接渡す（MCP も同じ）
doc-writing-skills reply                    # Claude Code の Stop フックの入力を標準入力から読む

検出があれば、Stop フックが読む {"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":…}} を出力する。
decision: "block" を使わない ── Claude Code はそれを hook error として表示する。additionalContext なら会話は同じく続き、
表示は Stop hook feedback になる（code.claude.com/docs/en/hooks :2620・2631、2026-09-27 取得）。
Stop フックは応答を表示したあとに走る ── 表示を止めることはできず、修正した全文を続けて出させる。

語の単位で判定できない不自然さは、review でモデルに審査させる。
造語 ・ 比喩 ・ 主述の不整合 ・ 含意の不一致 ・ 幼い語り口 ・ 回りくどさは、語彙表では検出できない。
review は、判定基準（references/review-criteria.json）・手順（references/document.json の review-instruction）・
事例（プロジェクトの .doc-writing/review-examples.json）を1つの依頼文へ組む。判定はモデルが実施する。

doc-writing-skills review --message <本文>                 # 文書（全部の基準を適用する）
doc-writing-skills review --message <本文> --scope reply   # 前後の文脈を保持しない本文（文脈を要する基準を外す）

適用するのは、文書を出す前だけである。会話の応答には、応答のたびに適用しない ──
審査のたびにモデルのトークンを消費し、得られる判定は確率的である。会話の応答には、
トークンを消費しない reply（語彙表の照合）だけを適用する。

判定は確率的である。ゲート1の代わりにしない。 実測（指摘された文15件 ・ 指摘の無い文15件）で、
ゲート1と併用して検出13〜14件 ・ 誤検出2件だった。

ゲート2は書き手が判定する。
報告に、10の判定すべての結果を1行ずつ書く。1つでも欠けていれば、通っていない。

ガードレール

- 運用の覚書の書き方を、どの文書にも使わない。ゲート1の「述部が和語である」が検出する語は、書いた本人が読み返すための書き方であって、読み手のための書き方ではない。CLAUDE.md と Skill も例外にしない ── 例外にすると、そこで書いた語がそのまま本文へ流れる。どの文書でも、操作の名前で書く
- 名前のあるものを、描写で呼ばない。その操作に分野の名前があるなら、自分の言葉で言い換えない
- 比喩で言い換えない。対象を別の物へ置き換えた語を使わない ── 指し先が読み手の側で決まらない（文書か、欄か、クラスかを、読み手が推測することになる）。利用者への応答も同じである ── 応答で使用した語は、そのまま文書へ流入する。対象の名前で書く。検出する語は廃語の一覧が保持する ── 散文で例を並べると、その例が本文へ流入する。ただし、普通の語の一部になる語は一覧へ入れられない ── 部分一致で正しい語まで検出するためである（「段」は段階 ・ 段落 ・ 手段 ・ 段組みの一部である）。その種の語は機械で検出できないので、書く時点で遵守する
- 文語寄りの語を使わない。「営み」「所以」「〜ねばならない」のように、書き言葉のためだけに選んだ語は、ふだん話す語へ替える。判定は、同じことを口で説明するときにその語を使うか ── 使わないなら、読み手にとっては飾りであって、意味を1つも足していない
- 廃語を使用しない。一度破棄した語の一覧はこのSkillの外にある ── いつ何を破棄したかはプロジェクトごとに相違するので、ここへ書くと書いたプロジェクトでしか使えない検査になる。既定では .doc-writing/retired-words.json を、対象のファイルから上へたどって探す。無ければこの検査は走らない（失敗にしない）
- 和語へ言い換えない。名前も、述部もである。原典が和語を勧めるのは広報・解説であって、事務的・専門的な文書ではない。名前を和語にすると必ず新語になり（メタデータ→「頭」、出典→「指す先」）、述部を和語にすると意味の範囲が広がる（適用される ・ 有効である ・ 作用する が、1語にまとまってしまう）。判定は2つ ── その語を検索して同じ意味が出てくるか。意味を特定できる漢語が在るか

言い換え先は、references/predicates.json が定義する。
ゲート1の「述部が和語である」はその定義で検出し、検出した1件ごとに言い換え先を出力する。
この文書は定義を複製しない ── 複製は本体とずれ、どちらが正しいかを毎回確認することになる。
- 指し先の無い名詞句を書かない。「ずれ」「外を指す名前」のように、それが何を指すかを文書の中に書いていない語を使わない。見出しに置く語は、見出しだけで指し先が分かる形にする（「ずれた34件」ではなく「仕様と実装のずれ34件」）
- 散文で書けることを、散文で書かない。対比・条件・一覧・手順は表、分岐・流れ・包含は図にする
- 桁を空白で整列させて、表に見せない。表はマークダウンの表で書く
- ASCII で図を描かない。図は mermaid か SVG で書く
- 同じ文脈で、同じ意味に2つの語を対応づけない。文脈が変わるなら、変わることを書く
- 訂正の記録を本文に残さない。文書には現行の正しい内容だけを書く。履歴は git が持つ
- 数値は原典の文字列で確認してから書く。要約を経由して引かない
- 確認していない内容を、確認したように書かない。推測は推測と分かる形で書く
- 原典から導けない決めを、原典の記述として書かない。こちらの決めだと書く
- ゲートを実行していないものを、出さない。実行していないなら、そう書く

意思決定を、変更前と変更後の差分ごと記録するSkill：acdr

ACDR は Any Change Decision Record である。 分野を限定しない ── 何を決めたときでも、変更前と変更後の差分ごと残す。

目的

何かを決めたとき、決定と、その差分と、なぜそう決めたかを1枚へ保存するために使用する。文書・コード・設計・方針のいずれでもよい。分野を問わない ── この Skill は、対象が何の仕事に属するかを認知しない。

人は、変更前と変更後が見えていると判定が速い。 差分が無いまま承認を求めると、「この決定は何を土台にして決まったのか」を読む側が毎回復元することになる。成熟した環境では、決定の大半が既存のものへの変更である。だから差分を既定にし、新規のときだけ差分が空になる。

残すのは、承認の前と後で同じ1枚である。 状態が proposed から accepted へ変わるだけで、記録の形は変化しない。リポジトリに置くので、差分に載り、変更の理由がPRに出力される。

役割

- 決定を、4つの節（決めたこと ・ なぜ決める必要があるか ・ どう変わるか ・ 比較した案と採らなかった理由）にする
- 変更を1件ずつ、どこ・何から何に・なぜの3つ組にする
- 対象の文書を描画し、変更箇所を押すと変更前と理由が開く形にする
- 理由が欠けている変更を、記録に包含しない
- 正本へ適用する前に見せ、承認を得てから適用する
- 承認が下りたら状態を accepted にして、リポジトリへ保存する

処理対象と成果物

処理対象

これから決めようとしていること。多くは既存の文書・コード・設計への変更で、新規のこともある。

成果物

記録1件は、フォルダ1つである。

.acdr/<番号>-<短い名詞句>/
  acdr.json    ← 正本。節と、変更の3つ組を保持する
  flow.svg     ← 図（組ませた相手が返す。無い場合は配置しない）
  index.html   ← 組成した成果物。acdr.json から導出される

acdr.json が正本で、index.html は導出されるものである。 同じ acdr.json から、実行場所に依存せず同一の index.html が出力される。

中身を複製しない。 変更後の全文は対象の文書が保持している。記録が保持するのは、節と、対象のパスと、3つ組だけである。

index.html を手で直さない。 正本は acdr.json である ── 手で直すと、次に組成した時点で失われる。

承認済みの記録は封印される。 承認後の最初の組成で、対象の文書の sha256 が acdr.json へ保存される。以降、対象の文書が変化した状態で組み直そうとすると拒否する ── 組み直すと承認時点の姿が失われる。--check はその場合に「承認時点の姿である」と報告する。意図して組み直す場合は --force を渡す。

入力の想定

受け取る情報解釈・既定値
決めようとしていること明示されなければ、直前の会話から決定を書き起こす。推測で補完しない
対象の文書明示されなければ、変更しようとしている文書すべてを対象とする。無ければ新規として扱う
変更前の内容正本の現在の中身をそのまま取る。適用済みなら、gitの作業ツリーとHEADの差から取る
なぜ明示されなければ、そのとき何と食い違っていて何に一致させたかを書き起こす
除外した案明示されなければ、検討した案と、それぞれ何が成立しないかを記述する

実行手順

Step 1: 何を出す文書かを、外から取る

その文書が何を出すべきかは、その文書の中には無い。中から取ると、旧路線の記述が旧路線を残す根拠になる。成果物を決めている親文書・定義票・仕様の記述から取り、見出しの並びだけで出すものが出るかを判定する。出していなければ、本文の校正に入らず構造の案を先に出す。

Step 2: 対象の全文を読む

頭から終わりまで確認する。検索で見当を付けて周辺のみを確認する方法を採用しない ── 置換のすり抜け、説明なしで残った旧い値、見出しと中身の食い違いは、どれも検索では検出されない。

Step 3: 節を記入する

上部の節は4つだけである（ACDR 0045）── 読み手は、決めたこと ・ なぜ ・ どう変わるか ・ 何と比べたかだけで判定できる。
具体の変更箇所と理由は、下の面が持つ。

節キー中身
決めたことdecision決めてほしいこと1件。能動態の完全な文で、手段を記述しない
なぜ決める必要があるかwhy何と食い違っていて、何に一致させたか
どう変わるかfigure ・ figure_caption ・ shift図と、抽象の側の変更前と変更後（what ・ from ・ to）。この Skill は描画しない ── 図は design-svg が組む
比較した案と、採らなかった理由alternativesoption と why_not。反証を通過しなかった案であり、未解決の懸念ではない
状態（見出しの札）statusproposed ／ accepted ／ superseded
置き換えた記録supersedesこの決定が置き換えた記録の番号

how ・ applies_to ・ after_approval は、過去の記録のために形に残してあるが、描画しない。新しい記録に書かない ──
手段と適用先は、下の面の変更箇所と理由が示す。

キーは ASCII で、値は人が読む日本語である。 機械が分岐するもの（キー ・ status）と、
人が読むもの（本文）を、同じ文字体系に混在させない。

decision ・ why ・ alternatives の3つは、欠けたら道具が停止する。 欠けた記録は、あとから誰も補完できない。比較した案が無いことと書き忘れは、読み手には同じに見える。

Step 4: 変更を3つ組にする

1件ずつ、どこ（読み手がその場所を開ける粒度）・何から何に（変更前の原文をそのまま。要約しない）・なぜを完備させる。書けない変更は記録に含めない ── 書けないのは、変更の意図が自分でも掴めていないということである。削除も1件として扱い、消えた場所に印を配置する。

「変更前」と「なぜ」は平文である。 タグを書いても文字として出る ── 「変更前」は原文をそのまま出す欄なので、タグを解釈してはならない。節（決定 ・ 対象 ・ なぜ）のほうは HTML を受ける。

「どこ」は、描画したあとの本文に現れる文字列で指定する。 マークダウンの記法を含めると一致しない ── 描画後は <b> や <code> になっている。

Step 5: 作業コピーへ適用して、1枚を組む

正本は触らない。作業コピーへ適用してから組成する。操作は3つだけである。

acdr new .acdr/0007-<短い名詞句> "題"    起こす（雛形から）
acdr inspect .acdr/0007-<短い名詞句>     入力を検査する
acdr render .acdr/0007-<短い名詞句>      組む
acdr render .acdr/0007-<短い名詞句> --check 1   差が無いかを検査する

CLI は1つである。 どの操作も --json を付けると機械が読む形で出て、終了コードは 0 正常 ／ 1 検出あり ／ 2 誤用である。

acdr.json の形は references/acdr.schema.json が決め、雛形は references/spec-template.json が保持する。生成物ではなく、入力を検査する ── 生成物の検査からは、複製が正しく生成されたことしか判明しない。しかも不合格の時点で HTML は既に出ている。不合格なら HTML を1バイトも出さない ── 検査は4系統で、形（スキーマ）・欄の完備（節と3つ組）・散文（1つの欄への主張の同居 ・ 1文の長さ ・ 見出しや表の混入。引用と原文は除外する）・参照の解決（図と対象の文書の実在）である。

面の中身は、拡張子で決まる。

拡張子置き方
.md描画した見た目。印は語の単位で付く
コード（.py ・ .js ・ .json ・ .go ・ .rs ・ .rb ・ .sh ・ .sql ・ .yaml ・ .toml ・ .css ・ .xml ほか）Git の統合差分。旧と新の行番号 ・ + / - ・ 文脈3行。印は行の単位で付く
それ以外（.html など）そのままの見た目。CSS を隔てるので iframe へ流し込み、届かなければ Shadow DOM へ切り替える

docs が空なら、節だけの1枚になる。

新しい種別の枠を追加する場合は、タブの押す処理の配線と、枠の挿入先の2点を確認する。 どちらが欠けても印は開かない ── 面の種別を増やす操作は、配線と挿入先の2か所へ同時に及ぶ。

Git は差分を出すが、なぜ変えたかを出さない。 そこを補完するのがこの道具である ── まとまりごとに理由を添え、印を押すと開く。変更前は - の行が示すので、before の記述は省略してよい。

変更前は git show <rev>:<パス> で取得する。 記録へ複製しない。rev の既定は HEAD で、docs の項目に書くと変更できる。取得できない場合と差分が無い場合は、全文を置く。

理由が付いていないまとまりは、組成の検査が件数を出す。 差分の見出しにも表示する ── 0件にしてから提示する。

コードの印は行の単位である。 語の単位で付けると、色付けが挿入した要素と交差してどちらかが壊れる ── コードの変更は行の単位で読むものなので、行で足りる。

色付けは近似である。 構文解析を実施せず、行ごとに正規表現を適用する ── 文字列の中の予約語のような事例は取り違える。読解の補助であり、判定の根拠にしない。

冪等である。 docs のパスはリポジトリの根から解決するので、どこから実行しても同一のものが出力される。--check は組み直した結果と index.html を比較し、差が在れば 1 を返す。

Step 6: 開いて閉じることを確認する

描画して、実際に押す。1度押すと変更前と理由が出て、2度押すと閉じる。「すべて開く／閉じる」も両方向とも動作する。印が内側のタブに隠れることがある ── タブの先頭の一覧から、押してその印まで運べることを確認する。

Step 7: 理由の欠けを確認する

「なぜ」が「一致させるため」だけになっていないか（何と何を一致させたかを書く）。変更内容の言い換えになっていないか。変更前が要約になっていないか。

Step 8: 見せて、承認を得てから適用する

1枚を渡し、返事を待つ。「適用しました。確認してください」と記述しない ── それは承認ではなく追認を求めている。

承認が下りたら、状態を accepted にして組み直し、正本へ適用し、.acdr/ の1枚と索引をコミットする。差し戻されたら3つ組を直して Step 3 から再実行する。止められた場合は適用しない。

後の決定が、この決定を置き換えたときは、古いほうの状態を superseded にし、置き換えた記録を指す ── 消さない。

出力形式

1枚のHTMLである。 先頭に節、その下に対象の文書が並ぶ。チャットには次のみを記述する。

書くこと書き方
何件直したか数と、いちばん影響の大きい1件
いちばん影響の大きい1件どこで、何が食い違っていて、何に一致させたか
直していない箇所理由が書けなくて保留にしたものが在れば、そう書く
何と照らしたかStep 1 で外から取った先。照らしていないなら、そう書く
全文を読んだか読んだと書く。読んでいないなら、読んでいないと書く
正本の状態まだ適用していないことと、適用してよいかを聞く

変更の一覧をチャットに並べない。 それは1枚の役目である。

ガードレール

- 中身を複製しない。 変更後の全文は対象の文書が保持する。記録が保持するのは節と3つ組だけである
- 対象が何の仕事に属するかを、この Skill が認知しない。 特定の分野の語彙・規則・スキーマを持ち込まない ── 使う側がこの Skill を呼ぶのであって、この Skill が使う側を知ることはない
- 何を出す文書かを、外から取得してから改訂する。 文書の中の記述を、その文書を直す根拠にしない
- 構造が合っていなければ、本文を直さない。 先に構造の合意を取る
- 対象の全文を読んでから直す。 検索で見当を付けて周辺のみを確認する方法を採用しない
- 正本へ適用する前に見せる。 適用してから提示しない
- 理由が欠けている変更を包含しない。 推測で理由を補完しない
- 変更前を要約しない。 原文をそのまま保持させる
- 比較した案を削除しない。 案と、採らなかった理由を保存する
- 節の語を負の側へ偏向させない。 「除外」「負担」ではなく「比較した案」と記述する ── 負の語が残ると、未解決の懸念が存在すると読解され、承認の判定が遅延する
- 抽象の側の変更前と変更後を記述する。 枠が保持するのは具体の差分である ── 抽象の対比が欠けると、下に並ぶ差分が何のためかを読み手が復元することになる
- 図を省略しない。 形の変化を図で確認できる形式にする。描画はこの Skill が実施せず、SVG の文字列を受け取るのみである
- 状態を自由文にしない。 proposed ／ accepted ／ superseded の3つ以外を書かない ── 自由文にすると、承認されているかを読む側が判定することになる
- 置き換えられた記録を削除しない。 superseded にして、置き換えた記録を指す
- 新規を例外として区別しない。 差分が存在しない決定も同一の形式で、docs を空欄とする
- 描画して押すまで出さない。 開閉が動作することを目視で確認する
- 色・寸法を直書きしない。 見た目は references/tokens.json が保持するトークンから引く ── 直書きすると、配色を替えたときにそこだけ取り残される。トークンの正本は1つである ── 2か所に書くと、どちらが正しいかを毎回確認することになる
- 入力の検査を、組み立てと同じ場所に置かない。 組み立てが検査を兼ねると、不合格の判明が生成物のあとになる ── 不合格なら HTML を1バイトも出さない
- 決定の文に手段を混在させない。 決定は「何を採るか」で、手段は下の面の変更箇所と理由が示す ── 手段だけを上に置くと、下の差分が何のためかを読み手が復元することになる
- 差し色を1つに限定する。 状態のラベル（承認済み）以外に別の色を使わない ── 1本だけ違う色の線が在ると、意味が在るものとして読解される
- 題を二重に出さない。 題は節が持ち、枠の見出しには出さない
- 生成物に文字コードを宣言する。 <meta charset="utf-8"> を先頭に置く ── 無いとHTTPで配ったときに推測になり、化ける
- 承認済みの記録を組み直さない。 記録は承認時点の姿である ── 後に対象の文書が変化しても、記録はその時点を保持する
- 外部のCDNやスクリプトを参照しない。1枚で完結させる
