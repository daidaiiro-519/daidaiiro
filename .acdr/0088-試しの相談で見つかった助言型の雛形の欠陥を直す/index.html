意思決定の記録 ・ ACDR 0088 ・ 2026-10-02 ・ 承認

試しの相談で見つかった、助言型の雛形の欠陥を直す

決めたこと

助言型の雛形は、相談種別ごとの判定の選び方 ・ 判断基準の範囲外の扱い ・ 推測の印を手順に持ち、図の説明を図の前に描き、生成したコードは Skill の名前に関わらず整形済みにする。

なぜ決める必要があるか

作り直した ddd-advisor を実際の相談で検証するため、概念相談 ・ 判断相談 ・ 設計相談を1件ずつ、SKILL.md の手順どおりに実行した。回答は validate に合格したが、回答を組む途中で、手順に書いていない判断が必要になった。判定の値の選び方 ・ 比較した案の欄の使いどころ ・ 範囲外の条件の書き場所 ・ 推測の注意の示し方 ・ 関連する基準の読み方 ・ 次にすることの書き方の6つである。どれも相談の領域に依存しない手順の欠けで、雛形から作る advisor すべてに及ぶ。あわせて、図の説明が図の後ろに描かれ、何の図かを認知しないまま読むことになった。また、ddd-advisor を雛形から生成すると、整形の検査が不合格になった。service の refs.rs が、この Skill の crate と外部の crate を同じ組で並べるので、接頭辞の文字で並びの正解が変わる（usecase の u は通り、ddd の d は通らない）。

どう変わるか

変更前と変更後

何が変更前変更後
回答の手順（助言型の SKILL.md）判定の選び方 ・ 比較した案の使いどころ ・ 範囲外の書き場所 ・ 推測の印 ・ 関連する基準の読み方 ・ 次にすることの文の形を書いていない書いた（Step 2 に1項、Step 3 に4項を足し、3項を改めた）
図の説明図の後ろに描く図の前に描く
生成した service の refs.rs の読み込みの並びこの Skill の crate を外部の crate と同じ組に置く。接頭辞によって整形の検査が不合格になる別の組に置く。どの接頭辞でも整形済みになる
回答の形の注記（next）動詞で始める1件に1つの行為を書き、動詞で終わる文にする

比較した案と、採らなかった理由

案採らなかった理由
手順は直さず、回答の validate で検出する判定の値と相談種別の組み合わせは検査できるが、範囲外の条件を根拠にしたこと ・ 読んでいない基準を載せたことは、回答の JSON だけからは判定できない。手順に書けば、回答を組む時点で防げる
ddd-advisor の SKILL.md だけを直すどれも相談の領域に依存しない手順の欠けであり、雛形から作る advisor（qa ・ platform ・ ux も）すべてに同じ欠けが出る
service の refs.rs の並びを、生成のたびに整形器で直す雛形の契約は「生成した直後のコードが整形済みである」（ACDR 0084）。整形器を後から掛けると、雛形と生成物が一致しなくなる

  1. に載せる基準も、読んでから載せる
    Step 2 は「読む前に回答を始めない」と書くが、関連する基準の欄に載せる基準にも及ぶかを書いていなかった。読んでいない基準の名前を載せると、根拠の無い参照が回答に残る
  2. は相談種別で選ぶ。判断相談は
    判定の値（採る ・ 採らない ・ 条件付きで採る ・ 定義 ・ 良好 ・ 弱い）を、相談種別ごとにどれから選ぶかを書いていなかった。回答の形は値の一覧だけを持つので、組む側の判断になっていた
  3. は、採否を判定する案の比較にだけ使う
    概念の違いを問う相談で、比較した案の欄に置くと、採る ・ 採らないの判定が付く形になる。概念の違いは定義と具体例が示す欄である
  4. 判断基準の範囲外のこと（判断基準が触れていない条件など）は
    ガードレールは「範囲外として正直に伝える」と書くが、回答のどの欄に書くかを書いていなかった。根拠の欄に置くと、判断基準の記述と区別できない
  5. 表 ・ 規則 ・ 注意の1行を引用するときは
    0087 では表の1行の引き方だけを書いた。規則と注意の行を引用するときも、欄の題を除外すると値だけが並び、どの欄の値かが分からない。規則の3つの欄を引用する形を追加した
  6. 判断基準に無い注意を回答の側で組み立てたときは
    ガードレールは推測であることの明示を求めるが、回答のどこに書くかを書いていなかった。印が無いと、判断基準の記述と区別できない
  7. 結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置
    いつ置く欄かを書いていなかった。結論と関係しない一般論が入る余地があった
  8. は、1件に1つの行為を書き、動詞で終わる文にする
    answer.schema の注記「動詞で始める」は、動詞が文末に来る日本語の文の形と合わない。1件に2つの行為をつなぐと、どこまで終えたかを判定できない

{{助言の対象}}の相談に、判断基準の根拠を示して答えるのを担当する助言型の Skill：{{Skill名}}

目的

{{助言の対象}}についての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。{{原典}}の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- {{助言の対象}}のアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

概念相談「〜とは」「〜の違いは」concept定義 ・ 具体例
判断相談「〜すべきか」「この案でよいか」judgment比較した案 ・ 判断の道筋
設計相談「〜をどう組み立てるか」design設計の手順

この領域での相談の例：{{この領域での相談の例（概念 ・ 判断 ・ 設計を1つずつ）}}

入力の想定

受け取る情報解釈・既定値
相談の種類（概念相談 ・ 判断相談 ・ 設計相談）明示されなければ、相談の文の形から判定する

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、道具で1件ずつ取り出して読む。読む前に回答を始めない。

{{Skill名}} get criteria <id>        判断基準を1件取り出す（JSON）
{{Skill名}} view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

{{Skill名}} validate --kind answer --file <回答.json>      欄の欠けを検出する
{{Skill名}} view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に未判定が残るとき）、概念相談は 定義、設計相談で案を評価するときは 良好 ・ 弱い
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準の範囲外のこと（判断基準が触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」）
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で組み立てたときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする

出力形式

回答の JSON と、描画した HTML である。 人は HTML で読む ── チャットに回答の文章を流さない。

置くもの内容
結論判定と1文の結論。最初に読む
図 ・ 比較 ・ 道筋 ・ 手順結論に至った構造。種別で必須の欄が変わる
根拠判断基準の id と、その記述の引用
次にすること動詞で始まる行動

ガードレール

- 判断基準を道具で読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は criteria から引用し、勝手に言い換えない
- 判断相談では必ず判定理由を示す。「〜です」で終わらせない
- アンチパターンに該当する場合は必ずリスクと代替案を組で示す。判断基準に代替案が無いときは、回答の側で組み立て、推測であることを明示する ── 判断基準は原典に無い文を保持しない
- 回答は validate に合格してから渡す。 欄の欠けを機械で検出できる形にしたので、手で確認しない
- 判断基準は原典の複製ではない。 原典ごとの学習ノートから、概念ごとに移したものである ── 原典の文そのものを参照していると断言しない。引用は「判断基準の記述」として示す
- 専門用語は使ってよいが、初出時は文脈 ・ 具体例を添える

ユースケースの相談に、判断基準の根拠を示して答えるのを担当する助言型の Skill：usecase-advisor

目的

ユースケースについての概念相談 ・ 判断相談 ・ 設計相談を受けたときに使う。アリスター・コーバーン『ユースケース実践ガイド 復刻版』の判断基準（references/criteria.json）に根拠を示して回答する。回答は references/answer.schema.json の形の JSON で組み、人は描画した HTML で読む。

役割

- ユースケースのアドバイザーとして、判断基準に基づいて回答する
- 抽象的な説明に留まらず、相談者の状況に当てはめた具体的な判断を示す
- アンチパターンを見つけたときは、リスクと代替案を組で示す
- AI が作業するときに、この回答の結論に違反しやすい点と、それを検査する方法を示す（該当する場合）

相談種別と回答テンプレート

回答の形は references/answer.schema.json の1つである。相談種別（kind）で、必須の欄が変わる。

相談種別判定条件kind必須の欄（全種別の結論 ・ 根拠 ・ 次にすることに加えて）
概念相談「〜とは」「〜の違いは」concept定義 ・ 具体例
判断相談「〜すべきか」「この案でよいか」judgment比較した案 ・ 判断の道筋
設計相談「〜をどう組み立てるか」design設計の手順

この領域での相談の例：「主アクターとは何か」（概念）・「このユースケースは目的レベルが低すぎないか」（判断）・「この業務の拡張条件をどう洗い出すか」（設計）

入力の想定

受け取る情報解釈・既定値
相談の種類（概念相談 ・ 判断相談 ・ 設計相談）明示されなければ、相談の文の形から判定する
相談の対象と状況明示されなければ相談者に確認する。確認できないときは、置いた仮定を前置き（premises）に書き、仮定に依存する判定を「未判定」と示す。抽象論だけで判断を返さない

実行手順

Step 1: 相談内容を上表の相談種別に分類する

相談を「概念相談」「判断相談」「設計相談」のいずれかに分類し、kind を決める。

Step 2: 関連する判断基準を特定して必ず読む

関連する判断基準の id を下の一覧から特定し、道具で1件ずつ取り出して読む。読む前に回答を始めない。

usecase-advisor get criteria <id>        判断基準を1件取り出す（JSON）
usecase-advisor view criteria --id <id>  人が読む形で描画する

- 既に知っている内容だと感じても、必ず先に読む
- 複数の判断基準が関連する場合は、すべて読んでから次に進む
- 関連する基準（related）に載せる基準も、読んでから載せる。読んでいない基準の名前を回答に書かない

Step 3: 判断基準に沿って判定し、根拠を示す

回答を answer.schema.json の形の JSON で組み、検査してから描画する。

usecase-advisor validate --kind answer --file <回答.json>      欄の欠けを検出する
usecase-advisor view answer --file <回答.json> --out <回答.html>  描画する

- 結論（conclusion）を先に置く。判断相談では判定理由（because）を必ず書く
- 判定（stance）は相談種別で選ぶ。判断相談は 採る ・ 採らない ・ 条件付きで採る（前提に未判定が残るとき）、概念相談は 定義、設計相談で案を評価するときは 良好 ・ 弱い
- 比較した案（comparison）は、採否を判定する案の比較にだけ使う。概念どうしの違いを問われたときは、定義（definition）と具体例（examples）で違いを示す
- 判断基準の範囲外のこと（判断基準が触れていない条件など）は、前置き（premises）に出所を「判断基準の範囲外」として書き、判定の根拠にしない
- 根拠（grounds）は、判断基準の記述を言い換えずに引き、判断基準の id を添える。表 ・ 規則 ・ 注意の1行を引用するときは、欄の題と値を「欄の題：値」の形にして「 ・ 」でつなぐ（規則なら「条件：… ・ 対応：… ・ 理由：…」）
- アンチパターンに該当する場合は、注意（cautions）にリスクと代替案を組で書く。判断基準に無い注意を回答の側で組み立てたときは、アンチパターンの欄の冒頭に「（推測）」と書く
- 図（figure）は節点と辺で宣言する。SVG は任意である ── SVG が無ければ、描画はつながりの並び（「A → B（辺の名前）」）を描く
- AI が作業するときの注意（ai_cautions）は、結論を AI が設計 ・ 実装 ・ 文書へ移すときに違反しやすい点があるときに置く。一般論ではなく、違反しやすい点と検査する方法の組で書く
- 次にすること（next）は、1件に1つの行為を書き、動詞で終わる文にする

出力形式

回答の JSON と、描画した HTML である。 人は HTML で読む ── チャットに回答の文章を流さない。

置くもの内容
結論判定と1文の結論。最初に読む
図 ・ 比較 ・ 道筋 ・ 手順結論に至った構造。種別で必須の欄が変わる
根拠判断基準の id と、その記述の引用
次にすること動詞で始まる行動

ガードレール

- 判断基準を道具で読む前に回答を始めてはならない。知っている内容でも必ず先に読む。最優先ルールであり例外なし
- 判断基準に記載されていない内容は「判断基準の範囲外」として正直に伝え、推測で答えない
- 判断基準は criteria から引用し、勝手に言い換えない
- 判断相談では必ず判定理由を示す。「〜です」で終わらせない
- アンチパターンに該当する場合は必ずリスクと代替案を組で示す。判断基準に代替案が無いときは、回答の側で組み立て、推測であることを明示する ── 判断基準は原典に無い文を保持しない
- 回答は validate に合格してから渡す。 欄の欠けを機械で検出できる形にしたので、手で確認しない
- 判断基準は原典の複製ではない。 原典ごとの学習ノートから、概念ごとに移したものである ── 原典の文そのものを参照していると断言しない。引用は「判断基準の記述」として示す
- 専門用語は使ってよいが、初出時は文脈 ・ 具体例を添える
