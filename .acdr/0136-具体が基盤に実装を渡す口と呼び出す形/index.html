意思決定の記録 ・ ACDR 0136 ・ 2026-10-06 ・ 承認

具体が基盤に実装を渡す口と、基盤を呼び出す形

決めたこと

具体は、コンポーネントの実装をポート Design に、固有のツールを ExtraTools に渡し、基盤の crate の公開の関数と型を呼び出して自分のツールを作る

なぜ決める必要があるか

ボード schema-driven-build の論点5（C）で、具体は自分のヘキサゴナルを持ち、基盤の crate を転写して呼び出すと決めた。要求事項は、実装を渡す口の形と、具体から呼び出す公開の形を、3c で試してから ACDR で決めることだった。テスト用の小さな具体（部品 page ・ section ・ pill ・ table と、ツール seal）で試し、基盤の側に具体の名前を1つも置かずに作れた。

どう変わるか

変更前と変更後

何が変更前変更後
コンポーネントの実装を渡す口無い（ACDR 0128 の19種類を基盤が描画する予定だった）ポート Design（components ・ parts ・ page ・ section ・ render）。基盤は Renderer（value ・ node ・ node_at ・ part ・ text ・ tone）を渡す
HTML の作り方文字列を作る型 Html。作れるのは、文字をエスケープするか、部品のプレースホルダーを置換するかだけで、具体は HTML の文字列を作れない。プレースホルダーと渡した名前が1つでも合わなければエラー
ページのレイアウトpage と section を予約したコンポーネントの名前にする（論点5の前の答え）Design のメソッド page と section にする。具体のコンポーネントの名前と重ならない
ツールの一覧基盤の7つで固定（TOOLS と dispatch）Toolbox。基盤のツールのあとに具体の ExtraTools を追加する。引数の検査は基盤が行い、基盤のツールと同じ名前は追加できない。CLI と MCP は Toolbox から作る
具体から呼び出す公開の形決まっていないcore は application（Instances ・ Checks ・ contexts ・ ViewEngine ・ PageRenderer ・ page_errors）と domain と ports を公開する。adapters は inbound の Toolbox ・ ExtraTools ・ cli::run_in と、outbound の fs ・ jmespath を公開する

比較した案と、採らなかった理由

案採らなかった理由
Design が HTML の文字列を返すエスケープ漏れを、具体ごとに探すことになる。型で防げば、具体はエスケープしていない文字を入れられない
page と section を予約したコンポーネントの名前にする具体が同じ名前のコンポーネントを作れなくなり、予約の名前の一覧を基盤が持ち続けることになる
具体のツールの引数を、具体が自分で検査する知らない引数 ・ 必須 ・ 文字列かの検査が具体ごとに書かれ、基盤のツールと振る舞いがずれる
