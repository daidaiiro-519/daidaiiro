意思決定の記録 ・ ACDR 0133 ・ 2026-10-06 ・ 承認

描画の文脈の形を決める

決めたこと

描画の文脈の6つの値の形を page.schema.json の context に書き、参照の解決と導出値は検査と同じものを使う

なぜ決める必要があるか

ACDR 0128 で文脈の6つの名前は決めたが、形は決めていなかった。questions は page.schema.json にしか出てこず、注釈の仕様に定義が無い。derived のキー、links の target、referrers が項目を指されたときの表し方も決まっていない。形が決まらないと、ページテンプレートを書く人も AI も、式で何を取れるかが分からない。そこで、3b の実装で形を試し、使えた形を仕様に書く。

どう変わるか

変更前と変更後

何が変更前変更後
文脈の形6つの名前と、括弧の中の短い説明だけ（page.schema.json の expr）#/$defs/context に、6つの値の形を JSON Schema で書く。組んだ文脈がこの形に合うことを、テストが確かめる
derived「x-derive を持つプロパティごとの value ・ title ・ declared ・ questions」。キーと questions の中身が決まっていないキーはインスタンスの根からの場所（先頭の / を除く。例：classification、parts/0/c）。questions は rules の when に出てくるプロパティを出てきた順に1回ずつ並べ、key ・ title ・ answer を持つ
links ・ referrerslinks は at ・ value ・ target、referrers は at ・ from。target の形と、項目が指されたときの表し方が決まっていないtarget は「インスタンスの id」か「インスタンスの id.項目の id」で、決まらなければ null。referrers は item を足し、指された項目の id（インスタンスそのものなら null）を持つ
参照の解決検査（check.rs）の中にだけあるcheck.rs の graph が解決して、検査と描画の文脈の両方が使う

比較した案と、採らなかった理由

案採らなかった理由
描画の側で参照を解決し直す同じ参照が、検査では見つかり描画では見つからない、ということが起こりうる。解決の決まり（to ・ item ・ bare ・ in ・ only）を2か所で持つことになる
derived のキーをプロパティの名前だけにする配列の中のオブジェクトが x-derive を持つと、同じ名前が何度も出てキーが重なる
links の target を指す先の値（インスタンスや項目そのもの）にする文脈が大きくなり、同じ値が何度も入る。名前は name() で、値は instances から引ける
