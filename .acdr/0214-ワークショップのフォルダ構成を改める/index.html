ワークショップのフォルダ構成を改める

決めたこと

ai-workshop のフォルダを、配るもの（dist/）・作る材料（src/）・前の版（archive/）・作業の記録（review/）に分け、配るものを本ごとに1フォルダにまとめる。

なぜ決める必要があるか

見るものが proposal/out と material-1/out にファイルの種類ごとに分かれ、1本の資料をそろえるのに5か所を開く必要があった。三教材に共通のオリエンテーションとはじめにが「教材1」のフォルダにあり、共通の部品も企画書と教材1のフォルダに分かれて互いに読み合っていた。

変更前と変更後

何が変更前変更後
配るものの置き方proposal/out と material-1/out の中に、slides ・ pdf ・ scripts ・ videos ・ audio と種類ごとに置く。dist/<本>/ に、slides.html ・ slides.pdf ・ script.md ・ video.mp4 ・ audio.mp3 をまとめて置く。
作る材料の置き方proposal/src と material-1/src と material-2 に、共通の部品が混ざる。src/shared（共通）・ src/proposal ・ src/lessons（オリエンテーション・はじめに・教材1）・ src/lesson-2。
前の版out/versions/ の中に置く。archive/proposal と archive/lessons に置く。

比較した案と、採らなかった理由

案採らなかった理由
フォルダは変えず、README で場所を案内する。1本の資料が5つのフォルダに分かれる形と、オリエンテーションが教材1のフォルダにある形が残る。
作る材料も本ごとに src/orientation ・ src/intro ・ src/lesson-1 に分ける。7本は1つの build_lessons.py と共通の図の部品で組んでおり、分けると同じ部品を3か所に置くことになる。
build_deck.py と build_videos.py も共有部分と本ごとの部分に分けて src/shared へ移す。コードの書き換えが要り、出力が1バイトも変わらないことを、場所の変更と同時には保証できない。
review/ の作業コピーも dist や src と同じ規則で並べ直す。承認済みの ACDR が review/ の中のファイルを指しており、動かすと記録から開けなくなる。

社内AI人材育成ワークショップ：運営設計案

AIの活用を、仕事全体の生産性と品質の改善につなげることを目指す。参加者は、自分の業務に合ったSkillsを作り、Agentsで作業を進め、結果を確認して改善できるようになる。そのために、三つの教材で、目的と要件の明確化（教材1）、業務のモデル化と設計（教材2）、AI活用の実践と改善（教材3）を順に学ぶ。

参加者は、自分の業務で改善したいことと、何が変われば達成かを決め、学んだ考え方を判断の観点と手順としてSkillsにまとめて試す。改善したいことの選択と解法の判断は参加者に委ね、三つの教材と継続的な相談で支える。

部長向けの説明は [スライド](detail/slides.html)（38枚）、話す内容は [発表原稿](detail/script.md) を参照する。本書は開催条件を詰めるための案であり、以下の提案事項は確定していない。

背景

AIの登場で、資料や設計書、コード、テストを作成する負担は大きく下がった。一人でも、短時間で作成できるようになった。ただし、作成したものをそのまま使えるわけではない。要件や元の情報と照合し、合わなければ修正して再確認する。作成が速くなった分、確認する対象も増える。

何をどう確認するかは、人によって異なることがある。経験から身につけた確認の観点が、チームで共有されていない場合もある。観点が共有されていないと、見落としが後の工程で見つかり、手戻りにつながる。その結果、作成は速くなっても、案件全体の工数や期間は短縮されないことがある。

問われているのは、作成の速さだけではない。AIの活用が、確認や修正まで含めた仕事全体の生産性と品質の改善につながっているかである。AIツールを導入するだけでは、この状況は変わりにくい。

企画の目的と身につける力

企画の目的は、AIの活用を、仕事全体の生産性と品質の改善につなげることである。そのために、参加者が次の4つの力を身につける。

力内容学ぶ教材
1何を実現し、どんな要件を満たすかを明確にする教材1
2業務で扱う対象や判断、守る条件をモデルに表し、設計へつなぐ教材2
3その考え方を、判断の観点と手順としてSkillsにまとめる教材3
4Skillsを使って作業を進めるAI（Agents）で作業し、結果を人が根拠と照らして確認し、改善する教材3

Skillsは、判断の観点と手順をまとめ、AIが作業のたびに使えるようにしたものである。Agentsは、Skillsを使って作業を進めるAIである。どれも特定のツールの操作ではなく、ツールが替わっても使える力である。

成果の差は、ツールの操作に詳しいかどうかでは埋まらない。確認の観点が人によって違うままでは、AIで速く作っても、手戻りは減りにくい。何を実現し、何を確かめるかを、AIが使える形にできるかが差になる。

企画の構成

企画は2つの施策で構成する。1つ目はワークショップで、参加者が、AIを使って自分の業務を改善できるようになる。2つ目はAI活用を促進する基盤づくりで、AIを使った改善のやり方が、部内で共有され、使い続けられるようにする。ワークショップだけでは、身につけたやり方は参加者の中にとどまる。基盤づくりで部内に広げる。

施策主体目標本書の節
ワークショップ参加者（12月の参加時アンケートで先着15〜20名）AIを使って、自分の業務を改善できるようになる期待する効果 〜 最低限の提出物
AI活用を促進する基盤づくり運営チーム（人選した約3名）AIを使った改善のやり方が、部内で共有され、使い続けられるAI活用を促進する基盤づくり

ワークショップで実践した事例とSkillsをポータルに載せ、運営は事例と機会を発信する。両者で、仕事全体の改善が部内で続く状態を目指す。

期待する効果

教材で学んだ考え方を業務に残し、問題に早い段階で気づけるようにする。効果の大きさは、実践を通じて検証する。

教材業務に残るもの期待する業務の変化
教材1　目的と要件の明確化作業ごとの目的・要件と、達成の基準要件の解釈のずれに、作成前やレビューで気づきやすい
教材2　業務のモデル化と設計業務のモデルと、設計の理由変更の影響を把握しやすく、確認の範囲を絞り込みやすい
教材3　AI活用の実践と改善判断の観点と手順をまとめたSkillsAIと人が同じ観点で確認でき、確認の質が人に左右されにくい

目指すのは、必要な品質を満たしながら、手戻りと確認・修正の手間を減らし、案件全体の工数と期間を短縮することである。Skillsが残るため、担当者が替わっても、同じ観点で確認できる。AIの結果は、これからも人が確認する。組織の層で何を目指すかは、AI活用を促進する基盤づくりで示す。効果をどう確認するかは、「到達目標と評価」の節で示す。

到達目標と評価

参加者は、改善したいことを決め、学んだ考え方をSkillsにまとめて業務で試し、何が変わったかを確認する。人は、具体を知って初めて、改善したいことを思い描ける。そのため、改善したいことは教材をすべて視聴したあとの12月の参加時アンケートで書く。10月の事前アンケートでは、いまのAIの使い方、確認・修正の手間、チームでの共有を聞き、終了時の比較の元にする。

主KPIは2つを提案し、どちらもアンケートの回答で数える。

主KPI定義
目的と要件の明確化率参加時アンケートで、教材を見る前と比べて、改善したい業務の目的と、満たす要件を明確にできるようになったと「そう思う」「ややそう思う」と答えた人の割合。「わからない」は分母から除く
改善の達成率参加時に書いた改善のうち、1件以上を、何が変われば達成か（工数・期間・品質のどれがどう変わるか）に照らして達成したと、根拠と記録を添えて終了時アンケートで答えた参加者の割合。分母は参加者で、開始時点で固定する

補助の指標は、作ったSkillsを自分だけで使った人と、チームでも使った人に分けて測る。

補助の指標定義
実務でAIを使う人の増加この4週間に、仕事でAIを「月に数回」以上使う人の、事前と終了時の変化
確認・修正の手間の変化作ったSkillsを使った業務で、確認や修正の手間が「大きく減った」「少し減った」と答えた人の割合
チームでの改善の実施チームで使った人のうち、振り返りの場を1回以上開いた人の割合
やり方のチームへの定着チームで使った人のうち、AIの使い方の共有が進んだ人と、新しく入った人の立ち上げが短くなった人の割合

あわせて、AI活用を促進する基盤づくりを先行トライアルとして検証する指標を、同じアンケートとポータルの記録から取る。設問・尺度・数え方の正本は [アンケート・効果測定案](survey-and-evaluation.md) とする。同書は、回答をMicrosoft Formsの4本のフォームで集める前提で記述している。事前と参加時は準備期間の希望者が、終了時は参加者と、参加しなかった希望者がそれぞれ回答する。

アンケートは、KPIに使う問いに絞る。事前は7問（約3分）、参加時は改善1件で8問（約5分）とし、各フォームの冒頭で、目的・問いの数と時間・回答を見る人・人事評価に使わないことを示す。

視点実施すること残す成果
参加者2月に、作ったSkillsを業務で使い、確認・修正の手間がどう変わったかを確認する。最終共有会で、何が変わったかを共有する使えるSkills、試した結果と改善
運営参加時の明確化の実感と、終了時の改善の達成を数える主KPI
運営事前・終了時の同じ項目を比較する実務での利用頻度・確認と修正の手間・チームでの共有・立ち上げ期間
運営根拠と記録、チームで使った記録を確認する定量の変化を説明する実例と、残る課題

自己申告と他の人による確認を区別し、同じ人の比較と回答人数を示す。個々の成果物について時間削減などを測れた場合は、条件と確認・修正の手間を添えて補足する。

テーマの選び方

テーマは、運営から示さない。何を改善したいかを自分で考えることが、この企画で身につけたいことの一部だからである。改善の姿を思い描けるように、教材の中で例を示す。

テーマ変更は認める。試した結果と変更理由を残し、規模を小さくすることも前進として扱う。既存のSkillや設定の改良も認め、本人が決めた改善と変更判断を説明できることを求める。

教材

チームで使う場合は、定期的に振り返りの場を開き、どのSkillsの、どこで、何がうまくいかないかを持ち寄る。形は、レトロスペクティブ・イベントストーミング・ブレインストーミングなど、チームに合うものを選ぶ。

教材は、社内のナレッジ共有ポータルで、準備期間の希望者に提供する。ポータルには、教材動画と参加者の実践を集める。参加者は、作ったSkillsを、目的と要件・判断の観点と手順・使い方・試した結果と改善と一緒に載せる。そのうえで、カテゴリとタグを設計し、業務に合うSkillsにたどり着きやすくする。希望した人も、ポータルで探して、自分の業務で試したり、作るときの参考にしたりできる。今期はトライアルとし、利用者はワークショップの参加者と希望者に限る。結果がよければ、AI活用を促進する基盤づくりで部内に広げる。

AI活用を促進する基盤づくり

AI活用を促進する基盤づくりは、AI活用を促す場と、そこで得た事例とノウハウを集める基盤を、組織の取り組みとして定着させるものである。中身は、ナレッジ共有ポータルと、アイデアソンやワークショップなど継続的にAI活用を促す取り組みである。

AIの進化は速い。使い方を知るほど、AIで改善できる業務の幅が広がる。ただ、こうした情報は自分から追いかけないと分からない。だから、新しい使い方に触れる機会を組織の取り組みとして続け、そこで得たノウハウをポータルに集める。

運営と利用者は、どちらも受け身にならず、発信と共有を往復させる。運営チームは、環境を整え、AI活用を促す取り組みと情報を発信する。参加者を含むメンバーは、それを受け取って自分の業務で試し、事例とノウハウを共有する。運営は、共有された事例とノウハウを受けて、次の発信と基盤の改善につなげる。この往復が続けば、AI活用が部内で循環する。

ナレッジ共有がうまくいかない、とよく言われる。GitHubやConfluenceは、何にでも使えるよう使い道を広く取っているため、使い方の多くが利用者に委ねられ、置き方や探し方が人によってばらばらになる。そこで、ナレッジ共有ポータルは、作ったSkillsとナレッジを載せ、探して使うことに用途を限定する。載せる項目（目的と要件・判断の観点と手順・使い方・試した結果）を決め、カテゴリとタグで探せるようにし、共有のハードルを下げる。これは教材1と同じ考え方で、何のためのポータルかを先に決め、そこから載せる項目と探し方を決めている。

今期は、ワークショップと並行して、この基盤を先行トライアルとして小さく試す。その結果で、次の期に部内へ広げるかを判断する。

AI活用ワークショップのアンケート・効果測定案

主KPIは、目的と要件の明確化率と、改善の達成率の2つである。目的と要件の明確化率は、教材を見る前と比べて、改善したい業務の目的と満たす要件を明確にできるようになったと感じるかを聞いて数える。改善の達成率は、参加時に書いた改善のうち、1件以上を達成した人の割合である。補助の指標は、終了時に、作ったSkillsを同じチームの人にも使ってもらったかを聞き、自分だけで使った人とチームで使った人に分けて測る。AI活用を促進する基盤づくりは先行トライアルとして、参加者と、参加しなかった希望者の終了時アンケートと、ポータルの掲載記録から検証する。

設問質問の種類
選択肢で答える設問（すべての尺度と、達成できたかを含む）Choice。複数選択の設問は、複数の回答を許す。Likert・Rating・Ranking は使わない

長めに答える設問（達成に必要なこと）Text。長い回答を許す

設問のまとまりは Section で分け、答える人は Add branching の分岐で分ける。分岐の移動先は、[forms-copilot-prompts.md](forms-copilot-prompts.md) の表に置く。
