9月のボードの決定を、モデリングとコーディングのボードに合わせて改める

決めたこと

ボード usecase-schema-driven の決まり11本のうち7本を、ボード usecase-modeling-coding の決定に合わせて改める。

なぜ決める必要があるか

ボード usecase-modeling-coding で、9月のボードを土台にしたうえで、5つの点を決め直した。語（事業領域 ・ 業務領域 ・ 業務サービスを、DDD の原語のドメイン ・ サブドメイン ・ ドメインサービスへ）、宣言の種類（値オブジェクトを足して7種類）、シナリオの持ち主（ユースケースだけ。集約とドメインサービスは条件を持つ）、人が読む射影（ドメインのビジョンから目的の連鎖としてたどる）、引き算の対象（シナリオに加え、条件 ・ 保証 ・ 手順と補償 ・ 公開された言葉 ・ 品質の要求の ID）である。9月のボードの決まりの表がこのままだと、2つのボードが同じ事柄について別のことを言う。決まりの表を新しい決定に合わせ、各論点のタブは決着した当時の答えとして残す。試作（trial/spike）の改修は、試作を正本へ起こすときに行う。

比較した案と、採らなかった理由

案採らなかった理由
9月のボードの各論点のタブの答えまで書き換える各論点のタブは、決着した当時の論証と一体である。答えだけを書き換えると、論証と答えが食い違う。決まりの表を現在の決まりにし、タブは当時の記録として残す
9月のボードは変えず、新しいボードだけを正とする9月のボードの決まりの表が古いまま残り、2つのボードが同じ事柄について別のことを言う。読む人がどちらが正かを毎回確認することになる
試作（trial/spike）も同時に改修する試作の Rust のコードと試験は、宣言の種類と nodes を前提にしている。改修は試作を正本へ起こす作業と重なるので、そのときに新しい形で起こす

  1. ACDR 0092 で改めた
    決まりの表を改めたことと、各論点のタブは当時の答えのまま残したことを、表の前置きに書く。書かないと、表とタブが食い違って見える
  2. 単位は宣言とシナリオ・条件
    論点3：シナリオに加えて条件もテストと結ぶ単位になり、事業領域はドメインと呼ぶ（新しいボードの論点1 ・ 論点7）。論点6：値オブジェクトを宣言の種類として足し、ドメインの宣言は7つの欄を持ち、適用するリポジトリは実装の定義へ移した（論点2 ・ 3 ・ 7）。論点4：シナリオは主アクターと目的を持つユースケースのものであり、集約とドメインサービスは条件を持つ（論点7）。論点5：人が読む射影は、ドメインのビジョンを先頭に、目的の連鎖としてたどる形にした（論点6）
  3. <b>文脈をまたぐ業務のために種類を立てない</b>
    値オブジェクトを7種類目として足したので、「7種類目を立てない」は新しい決定と食い違う。この論点が禁じていたのは、文脈をまたぐ業務のための種類である。その趣旨を保ったまま語を直し、公開された言葉と、手順と補償の欄を足した（論点7）
  4. 仕様が必要とする ID（シナリオ
    論点11：引き算の対象を、シナリオ ・ 条件 ・ 保証 ・ 手順と補償 ・ 公開された言葉 ・ 品質の要求の ID の和集合にした（論点7）。論点12：シナリオはユースケースの操作の下にだけ置き、集約とドメインサービスの操作の下には条件を置く（論点7）
