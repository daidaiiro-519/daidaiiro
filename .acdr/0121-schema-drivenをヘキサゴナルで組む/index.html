schema-driven をヘキサゴナルで組む

決めたこと

schema-driven の道具を、ヘキサゴナル（ポートとアダプタ）で組む。core（domain ・ application ・ ports）と adapters（inbound ・ outbound）と cli ・ mcp に分け、業務の分け方は core の中の名前に出す

なぜ決める必要があるか

schema-driven の宣言から導いた実装の型は、中核の参照と導出値がドメインモデル、ほかの3つがトランザクションスクリプトである。ddd-advisor の判断基準は、ドメインモデルにポートとアダプタを対応づける。skills-creator の雛形がレイヤードなのは「道具は手続き的な変換である」という前提による（ACDR 0058）ので、schema-driven には当たらない。道具の中の構成は契約で強制せず、Skill ごとの設計である（ACDR 0059）。雛形の4層を保っていた規則（ACDR 0071）は no-more-spaghetti の .coding-rules にあり、no-more-spaghetti の廃止で持ち主がいない。そこで向きは、crate の依存（Cargo）と clippy の std::fs の禁止で止める。決めた過程はボード schema-driven-build の論点1にある

どう変わるか

変更前と変更後

何が変更前変更後
道具の構成skills-creator の雛形の4層（data_access ・ business_logic ・ service ・ cli と mcp）core（domain ・ application ・ ports）・ adapters（inbound ・ outbound）・ cli ・ mcp
依存の向きを止める仕組み.coding-rules/rules.json の層の並びを、no-more-spaghetti の inward が測るcrate の依存（Cargo）と、core の clippy.toml の disallowed-methods（std::fs）
crate の名前略した接頭辞（例：ds_ ・ sd_）製品名を付けた名前（schema-driven-core ・ schema-driven-adapters ・ schema-driven-cli ・ schema-driven-mcp）

比較した案と、採らなかった理由

案採らなかった理由
skills-creator の雛形の4層（レイヤード）に合わせる中核のドメインモデルをレイヤードに載せることになり、業務ロジックが入出力の層に依存する
業務の分け方ごとに crate を分けるサブドメインは問題の側の分け方で、crate はコンパイルの単位である。対応させる理由が無い
描画と転写だけレイヤードにする2つもポートを通せば入出力から離れる。組み立てが2通りになるだけである

対象の文書に変更が無い決定である ── 差分は出ない。
