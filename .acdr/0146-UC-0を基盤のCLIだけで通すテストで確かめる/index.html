UC-0 を、基盤の CLI だけで通すテストで確かめる

決めたこと

要約レベルの UC-0「構造化データを正本として持つ」を、基盤の CLI だけで作成から承認まで順に呼ぶテストで確かめ、render の説明を ACDR 0140 の動きに合わせる

なぜ決める必要があるか

宣言は4回目の完了の条件に UC-0 を入れている。UC-1〜10 はそれぞれテストがあるが、5つのユースケースを1つの正本に順に使って、保証が成り立つかを見るテストは無かった。通しで呼ぶと、ユースケースどうしの受け渡し（create が返す未記入、update が返す検証エラー、render と approve が同じ検証を使うこと）を確かめられる。書いている途中で、render の説明が 0140 より前のままであることも分かった。

どう変わるか

変更前と変更後

何が変更前変更後
UC-0 の確かめ方無い（部品ごとのユースケースのテストだけ）基盤の CLI で UC-1 → UC-7 → UC-3 → UC-6 → UC-8 を順に呼ぶ system のテスト2件
成功保証 SG-1確かめていない承認記録に、作成した正本が入る
最小保証 MG-1UC-8 の単体のテストだけ検証エラーのある正本は、描画も承認記録も書かれない
render の説明（MCP のツールの一覧に出る）無い種類は基盤の既定のページで描画するdocument は基盤の文書、具体の種類は具体のデザインで描画する。どちらでもなければ1ページも書かずに失敗する

比較した案と、採らなかった理由

案採らなかった理由
UC-0 は要約レベルなので、部品のユースケースのテストで足りるとする部品ごとのテストは、それぞれ自分で用意したデータを使う。create が返した未記入を prompt と update が受け、その結果を render と approve が同じ検証で読む、という受け渡しは確かめていない
具体のデザインを持つテスト用の具体で通す基盤だけで使う人（具体のデザインを持たない人）の道を確かめられない。基盤の文書の契約なら、基盤の CLI だけで描画まで通る
render の説明は SKILL.md を書くときにまとめて直す説明は MCP のツールの一覧に出るので、SKILL.md より先に AI エージェントが読む。誤った説明のまま残す理由が無い

26fn run(dir: &Path, args: &[&str]) -> (i32, Value) {
