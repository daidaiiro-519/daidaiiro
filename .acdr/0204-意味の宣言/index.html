段1：意味の宣言（Abstract ・ Concrete ・ glossary と、create ・ get ・ patch ・ validate）

決めたこと

段1として、Concrete と glossary を Abstract の版に照らして宣言できるようにし、create ・ get ・ patch ・ validate で作る ・ 読む ・ 変える ・ 検証するを行えるようにする。

なぜ決める必要があるか

段0 で場面を走らせる仕組みはできたが、実行ファイルは何もしなかった。計画の段1（U1 ・ U23）は、利用者が ACDR の Concrete を雛形から作り、x-prompt を書き、Abstract に照らして検証が通ることを受け入れにしている。段2 のインスタンスの検証は、Concrete を宣言できることを前提にする。

どう変わるか

変更前と変更後

何が変更前変更後
コマンド実行ファイルは何もしないcreate ・ get ・ patch ・ validate。--json で {ok, findings, data}、終了コード 0 ・ 1 ・ 2
検査①（patch）無い$id と $schema の書き換え ・ 使えない op ・ 根の置き換え ・ 無い場所 ・ 作業の根の外のパスは refused で断り、ファイルに触れない

比較した案と、採らなかった理由

案採らなかった理由
build.rs で schemas/v1/ を読み、取り込む2つのファイルなら include_str! で足りる。build.rs は std::fs を使い、domain の入出力の禁止に例外を作ることになる
JSON Patch の crate（json-patch）を使うmove と copy を断る規則と、$id と $schema を書き換えさせない規則は、その外で書くことになる。4つの op なら依存を増やさずに書ける
glossary を $id で引くための索引を持つ手元の DB は段3a で作る。いまは作業の根の .json を名前の順に読み、同じ $id が2つなら誤りにする方法で足りる
glossary を別のコマンドで作るコマンドが増える。glossary は $id の種類が glossary と決まっているので、create --kind glossary で区別できる
検査②で外れたら保存しないQ8（保存は断らない）に反する。書きかけの Concrete を AI が直すときの手がかりが残らない
AI ・ 人が判定する rule では reads を必須にするJSON Schema の節で、reads を書かなければインスタンスの全体を読むと決めてある。不変条件 I4 の「読む欄を持つ」は、書かなかったときの全体で満たす
