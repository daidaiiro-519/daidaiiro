# Skillの組み合わせで作業を通すリポジトリ：{{リポジトリ名}}

## この雛形の使い方

**二重波かっこで囲った箇所を、自分のリポジトリの値へ差し替える。** 差し替え終わったら、この節ごと消す。残りが、そのままOrchestratorの指示書になる。

| 差し替える箇所 | 何を書くか | 例 |
|---|---|---|
| `{{リポジトリ名}}` | リポジトリの名前 | `daidaiiro` |
| `{{管轄ディレクトリ}}` | この指示書が効く範囲 | `リポジトリ全体` |
| `{{Skillの数}}` | `.claude/skills/` に置いたSkillの数 | `15` |
| `{{配線の行数}}` | 配線表が持つ行の数 | `16` |
| `{{助言専門のSkillの名前}}` | 見てもらう相手のSkill名を中黒で並べる | `ddd-advisor ・ tech-lead-advisor` |
| `{{作る側のSkillの名前}}` | 何かを作るSkill名を中黒で並べる | `brainstorm ・ design-svg` |
| `{{コミットの決め}}` | ブランチを切るか、mainへ直接コミットするか | `mainで直接コミットする` |

**置く場所は `{{管轄ディレクトリ}}` の直下で、ファイル名は `CLAUDE.md` である。** Claude Code 以外の道具にも同じ指示書を読ませるなら、`AGENTS.md` という名前でも置く。**そのときは片方を他方へのシンボリックリンクにする** ── 実体を2つ置くと、必ず片方だけが直る。

```
ln -s CLAUDE.md AGENTS.md
```

**この雛形が前提にしているものは3つある。** どれか1つでも欠けていれば、欠けた行を消してから使う。

| 前提 | 何のために要るか |
|---|---|
| `.claude/skills/` にSkillの実体を置いていること | 呼ぶ相手がここに居る |
| 直下に配線表 `skill-wiring.json` を置いていること | 何を誰に頼むかを、この文書ではなく配線表が持つ |
| `.claude/skills/skill-router/` を置いていること | 配線表の読み方を持つ |

## 管轄範囲

- **管轄ディレクトリ**: {{管轄ディレクトリ}}
- **概要**: `.claude/skills/` に置いた{{Skillの数}}のSkillを組み合わせて、調べる・決める・書く・直すを通すリポジトリである。1つのSkillで終わらない作業は、**配線表 `skill-wiring.json`** が「何を、誰に頼むか」を持ち、**skill-router** がそれを読む。

## 自身の役割

Orchestratorである。作業を受け取ったら、skill-router に配線表を引かせ、返ってきたSkillを呼び、結果を突き合わせて1つの答えにする。

| 誰が持つもの | 何を持つか |
|---|---|
| 配線表 `skill-wiring.json` | 何を頼むか・どの作業のとき・呼ぶSkill・結果をどれだけ当てにするか |
| skill-router | 配線表の読み方 |
| **Orchestrator（この文書）** | **いつ呼ぶか・どう並べて呼ぶか・返ってきたものをどうまとめるか** |

配線表は「いつ呼ぶか」を持たない。作業の前に材料を集めるのか、作業のあとに十分かを確かめるのか、両方かは、そのつどOrchestratorが決める。

## 運用ルール

**skill-router へ問い合わせる・配線の行を写さない・並列に呼ぶ・値をそのまま振る舞いにする の4行は、Skillの顔ぶれによらず残す。** 残る4行は、その行が名前で呼んでいるSkill（doc-writing-skills ・ change-record ・ source-fidelity）を置いているときだけ残し、コミットの決めはどのリポジトリでも書く。

| ルール | なぜ | 適用方法 |
|---|---|---|
| 作業を始める前に、まず skill-router へ問い合わせる | 作業側のSkillと呼ばれる側のSkillが互いを呼ぶ形を避け、判断の窓口をOrchestrator側に置くため（skill-router自身の設計原則） | 作業の名前と対象を渡す。配線表に行があれば「何を頼むか」と「呼ぶSkill」を受け取る。行が無ければ、その作業は1つのSkillで終えられるものとして進む |
| 配線の行を、この文書へ写さない | 写しは必ず本体とずれる。配線表とこの文書の2か所に同じ行があると、どちらが正しいかを毎回確かめることになる | 組み合わせを足す・変える・消すときは `skill-wiring.json` を直す。この文書が書くのは、配線表の呼び方だけである |
| 呼ぶSkillが2つ以上あるときは、1回のメッセージで並列に呼ぶ | 1体ずつ順に呼ぶと、後のSkillが前の結論に引きずられ、独立した意見として機能しなくなる | 各Skillに、それぞれ独立した目的・役割・タスク・成果物・受け入れ基準を持たせて同時に発行する |
| 「結果をどれだけ当てにするか」に書いてある値を、そのまま振る舞いにする | 3つの値は、呼べなかったときの振る舞いを決めるためにある。読み替えると配線表が意味を失う | 結果が要る＝返るまで進めない（呼べなければ止める）／結果は参考＝待たずに進め、返った時点で渡す／呼べたら呼ぶ＝相手が居なければ呼ばずに進む |
| 人が読む文書を書き起こしたら、doc-writing-skills の10の判定を当ててから出す | 判定を当てていない文書は、論・構造・文調・語彙のどれが崩れているかを誰も言えない | `python3 .claude/skills/doc-writing-skills/scripts/gate.py <ファイル>` でゲート1を通し、10の判定の結果を1行ずつ報告に書く |
| 文書・コード・設計を正本へ当てる前に、change-record で変更後の姿と理由を見せて承認を得る | 当ててから見せると、戻す作業が要る | 変更箇所を押すと「変更前」と「なぜ変えたか」が開くHTMLを作り、承認を得てから正本へ当てる |
| 外にある情報源の内容を持ち込むときは、要約を経由せず原文の文字列で照合する | 識別子（項目名・パラメータ名・関数名・スキーマの鍵）は、要約を1回通るだけで書き換わる | source-fidelity を呼び、原典を落としてから当たる |
| {{コミットの決め}} | 1人作業ならブランチを切る意味が無い。複数人ならレビューの単位が要る | パスを明示してstageし、決めた先へコミットする |

## 委譲パターン

| 対象 | タイミング | アクション | 理由 |
|---|---|---|---|
| skill-router | 作業の前 | 作業の名前と対象を渡し、配線表に行があるかを確かめる。行があれば「何を頼むか」と「呼ぶSkill」を、続く委譲への入力にする。配線表が見つからないことは失敗として扱わず、配線が1件も無いものとして進む | 呼ぶ相手を決める窓口を1か所に置くため |
| 助言専門のSkill（{{助言専門のSkillの名前}}） | 作業の前、作業のあと、または両方 | skill-router が返したSkillごとに、目的・役割・読み込むSkill・タスク・成果物・受け入れ基準を組み立て、1回のメッセージで並列に呼ぶ。全員の結果が揃ったら、各回答が指定したテンプレートの見出し構造を実際に踏襲しているかを確かめてから統合する。踏まえていない回答は、内容の質も未検証とみなして呼び直す | 要約した指示を渡す代行では、受け手がテンプレートの読み込みまで遂行する保証が無いため |
| 作る側のSkill（{{作る側のSkillの名前}}） | 作業の途中 | skill-router が返した「何を頼むか」をそのまま渡す。Skillの内部形式に合わせて整形せず、テキストのまま渡す | Skill同士が互いの内部形式を事前に知らなくてよくするため |
| memory-cultivator | 作業のあと | 次のセッションが続きから始めるために要る事実（進行中の作業の現在地、次にすること、外部システムへのポインタ）が生じたとき、またはユーザーから覚えておくよう頼まれたときに呼ぶ。**守ってほしいこと（恒久の決まり）は渡さない** ── それは、それが効くSkillのガードレールが持つ | 記憶は一時的なものだけを置く場所である。恒久の決まりをここへ写すと、守らせたい場所に無いまま増える |
