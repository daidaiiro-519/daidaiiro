# 01. ビジョンと課題認識

## 出発点
AI実装では、型の不一致、依存方向の逸脱、ドメインの不変条件の見落とし、仕様変更の伝播漏れが発生し得る。自然言語プロンプトやハーネスだけで全てを縛るのは不完全で、保守負担も大きい。

## 中心原則
> AIに正しく書かせる努力だけでなく、不正な成果物を機械的に検出・拒否できる設計空間を作る。

AIが生成しやすいこと（generation ease）と、AI生成物を検証しやすいこと（verifiability）は分けて測定する。型検査に通ったことは業務仕様を満たしたことと同義ではない。

## ユーザーの方向性
- JSONはAI・フロントエンド・バックエンド間で共有しやすく、特定言語に縛られないデータ表現。
- JSON Schemaを、単なるデータ検証以上の独自Semantic Contract Core構想の土台として考えたい。
- 表現力・構成の自由度を持たせつつ、Schemaで許される構造の内側に閉じ込めたい。
- 既存の成熟した標準（JSON Schema、OpenAPI）は再利用したい。
- TypeSpecのような既存の上位仕様言語を正本にすると、その抽象選択に拘束される懸念がある。概念を参考にし、独自の上位モデルは自分で設計したい。
- AI生成コードの型・依存境界・状態に対する機械的な診断能力を言語選定の柱にしたい。

## 目指す開発体験
1. 人とAIが意図・意味・制約を契約として定義する。
2. 構造と参照の整合性を検証する。
3. 標準契約と各言語の型・クライアント等を導出する。
4. AIが生成できない業務ロジックなどを補完する。
5. コンパイラ・Validator・テスト・依存関係検査を実行する。
6. 構造化診断からAIが修正する。ただしSemanticな変更の確定は承認ポリシーに従う。

## 目標ではないこと
- JSONだけで全てのビジネスロジックを表すこと。
- JSON Schema Validatorを自作すること。
- あらゆる違反をコンパイル時に発見できると主張すること。
- 既存フレームワークを全否定すること。
